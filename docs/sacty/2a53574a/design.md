# 設計：実装の無い進め方では、工程の PR をベースブランチへ直接出す（PBI-464）

## スコープ

実装の工程が無いタスクでは、タスクブランチを作らずに、要求要件・設計の PR を工程のブランチからベースブランチへ出す。
マージを承認にし、sacty のブランチを残さない。

- 対象
  - 工程の PR の向き先・起点・作り直しの判定（`apps/daemon/src/service.ts`）と、投影の検査（`packages/core/src/projection.ts`）
  - マージ・クローズ・完了のときのブランチの削除（人がコミットを足したブランチは消さずに残し、作業履歴に記録する）
  - 中止の確認に示す消すブランチ（`apps/daemon/src/task-mcp.ts` の `cancelTargets`）を、削除の規則と合わせる
  - 派生の記録（`apps/daemon/src/prompts.ts` の `deriveRecord`）に文書のパスを足す
  - テスト、仕様書（日英）・図 `approval-branches`、ユーザー文書（日英）、ADR、作業履歴
  - 分割（`split`）の親タスクも直接の流れにする
- 対象外
  - 実装のある進め方とタスク分割の子タスクの流れ（タスクブランチのまま）
  - リモートに残っている過去のタスクのブランチの片付けと、backlog の 5（依頼の範囲の外）
  - 要求要件・設計の PR の競合の表示（今までどおり記録しない）

## 確認したいこと

- must：なし
- should
  - S-1：開いている工程の PR を作り直すのは、前の工程の PR が後からマージされたときだけでよいか。推奨：はい（ほかの人のマージでベースブランチが進んでも、同じ PR を更新する）。
    - 理由：受け入れ条件 4 の「起点がベースブランチになる以外は今までどおり」を、今の「前の工程の直しで起点が進んだら作り直す」に当てた。ベースブランチの先頭と比べると、ほかの人のマージのたびに PR が作り直される。
    - 懸念：開いている PR はベースブランチの最新を取り込まないので、同じ文書をほかのタスクが直すと、マージのときに利用者が競合を GitHub で解く手間が出る。

確認しないと決めたこと
- 競合の表示：記録しない（今までどおり）。文書のパスはタスクごとに別（`<documentsDir>/<ID8>/`）で、ほかの変更と競合しにくいため。
- ブランチの保護と CI：何もしない。ベースブランチへ出すのは利用者の決定で、保護と CI の下でマージするかは、マージする人が決めるため。

## 既定で決めたこと

- 対象の判定：タスクブランチが無く、`steps` に `implement` が無いタスク（以下「直接の流れ」）。`steps` は `StepsChosen` の後で実装を増減しないので、途中で切り替わらない。
- ブランチの削除に失敗しても止めずに警告だけにし、記録は足さない。完了のときに残りを消し直す（すでに無いブランチは消せたものとする）。
- 派生の記録のパスは、直接の流れでマージした PR の行だけに付ける（タスクブランチの流れの文書は、ベースブランチに無いことがあるため）。
- アップデートの前に作ったタスクで、まだタスクブランチも工程の PR も無いものは、直接の流れで進む（作ったものが無いので、途中の切り替えに当たらない）。このことをユーザー文書と ADR に書き、利用者が、アップデートの後に始まる要求要件の PR の向き先がベースブランチになると分かるようにする。

## 処理の流れ

| 所 | タスクブランチの流れ（変えない） | 直接の流れ |
| --- | --- | --- |
| `stepPullRequestsOn` | タスクブランチがあれば true | 工程の PR の記録があれば true（画面の提出の数で false にしない） |
| タスクブランチ | 無ければ作る（`TaskBranchCreated`） | 作らない |
| 工程のブランチの名前 | `<タスクブランチ>-<工程>-<回>` | 同じ（`sacty/task-<ID8>-<工程>-<回>`） |
| 新しいブランチの起点と `base` | タスクブランチの先頭 | `repository.baseBranch` を取得した先頭 |
| PR の向き先 | タスクブランチ | `repository.baseBranch` |
| 作り直し | 閉じた・マージした、または先頭が `base` と違う | 閉じた・マージした、または前の工程の PR が後からマージされた（S-1） |
| マージした文書を読む（`readMergedDocument`） | タスクブランチを取得して読む | ベースブランチを取得して読む |

- ブランチの削除（直接の流れだけ）は、すべての経路が次の1つの規則を通す（規則は1つの関数に置く）。
  - 経路：PR の確認・作り直し（`publishStepPullRequest`）・直しの間のマージ（`endStepReworkInPublish`）・完了（`workspaceRetirable` になり、作業領域を消す前）・中止の片付け。
  - 分類は、削除する時点の `stepPullRequests` の状態で決める（経路や、前の経路で消せなかったかでは決めない）。上から順に当てる。
    1. 無条件に消す：マージを記録した PR のブランチ（`StepBranchKept` の有無に関わらない。人のコミットはマージで取り込み済み）と、sacty がこの手で閉じた（作り直しの `supersede`）PR のブランチ。
    2. 消さない：`StepBranchKept` を記録したブランチ。
    3. 比べて消す：それ以外（人のクローズ、作り直しで見つけた閉じていた PR〔`superseded`〕、完了・中止で残っているブランチ）。削除の直前に先頭を取得し、`stepBranchCommits` の最後の push と同じときだけ消す。
  - 比べた結果
    - 違うとき：消さずに `StepBranchKept`（`branch`・取得した `head`・sacty が最後に push した `pushed`）を記録する。
    - リモートにブランチが無い（取得が `couldn't find remote ref` で失敗する）とき：消せたもの（中止は cleanup に done）とする。GitHub がマージの後に消した場合を含む。
    - それ以外の取得の失敗（通信など）・`stepBranchCommits` に記録が無いとき：消さず、記録も足さない。完了・中止のときに同じ規則でやり直し、そこでも取得できなければ残す（中止は cleanup に失敗として記録する）。
  - sacty が同じ PR を更新するとき、取得した PR のブランチの先頭（`parent`）が最後の push と違えば（人のコミットに積んだら）、`StepBranchKept` を記録する。人のコミットを含むので、後で先頭が同じでも消さない（マージされたときは 1 で消す）。
  - 削除は、比べた先頭が今も同じときだけにする（`repos.deleteBranch` に期待する先頭を渡し、`--force-with-lease` で消す）。取得から削除までの間に人が push したら、消せずに残る。
  - 投影は `StepBranchKept` を記録したブランチを、その PR のマージを記録するまで `sactyBranches` から除く。PR が開き直されても外さない（人のコミットがあるため）。
  - 中止の確認（`cancelTargets`）は、同じ分類で消すブランチを示す。2 のブランチと、3 で比べた結果で残りうるブランチは「触れないもの」に理由つきで示す（例：「人がコミットを足したため、消しません」「先頭が sacty の最後の push と違えば、消しません」）。
  - 引き継いだ PR は工程の PR を作らないので、`sactyBranches` から除く今の決まりのままで、人のブランチは消えない。
- 派生の記録：直接の流れでマージした PR の行に、文書のパス（`StepPullRequestPublished` の `path`）を足す。例：`- 設計の PR（merged）：<URL>（文書：docs/sacty/<ID8>/design.md）`。

## 影響範囲

- 投影：`StepBranchPushed`・`StepPullRequestPublished` の検査を、「タスクブランチがある、または `steps` に `implement` が無い」にする。
  - 互換性：新しいイベント `StepBranchKept` を足す。直接の流れのタスクを1件でも記録した後は、前の版のデーモンは整合性のエラーで作業履歴を投影できず、起動しない。前の版へ戻せなくなることは許容し、仕様書と ADR に明記する（前例は PBI-462 の互換性の注記。`docs/spec/approval.md`「工程の PR の直しの間のマージ」）。
- テスト：TV-1〜TV-27 は、daemon と core の自動テスト（`apps/daemon/src/daemon-step-pull-requests.test.ts` などに足す）で確かめ、判定・向き先・削除の規則を戻すと落ちるようにする。文書の観点は差分で確かめる。
- 文書
  - 仕様書：`docs/spec/approval.md`「PR での承認」に直接の流れを書き、PR の本文の Issue の注記（「タスクブランチへのマージでは閉じない」）を、ベースブランチへの PR でも閉じない書き方に直す。`docs/spec/tasks-and-steps.md` の完了・中止の片付けと派生の記録を直す。`docs/spec/event-log.md` に `StepBranchKept` を書く。`docs/spec/mcp-server.md` の中止の確認の消すブランチ（`cancelTargets`）を直す。英語の版も合わせる。
  - 図：`scripts/docs-diagrams/diagrams/tasks.mjs` に、直接の流れの図を足し、`npm run docs:diagrams` で作り直す。今の `approval-branches` は「実装がある進め方」の図と書き添える。
  - ユーザー文書：`docs/user/tasks.md`（と `tasks.en.md`）の「PR が作られる順序」・分割の親の記述・タスクブランチが残るという記述・前の工程に戻したときの直しの PR の向き先・競合の表示の「タスクブランチへの PR」を直す。人がコミットを足した工程の PR のブランチは残ることも書く。`docs/user/mcp.md`（と英語の版）の中止で消すブランチにも、残るブランチを書き添える。
  - ADR を足し、作業履歴 `docs/worklog/YYYYMMDD-pbi-464-<スラッグ>.md` を足す。ADR に互換性（前の版へ戻せないこと）を書く。
  - 置き換え：新しい ADR の置き換え元に `docs/adr/20261013-1318-superseded-step-pull-request-approval.md`（決定 2：要求要件・設計の PR をタスクブランチへ出す）を書き、古い ADR の置き換え先に新しい ADR を足す（`docs/adr/README.md` の両方向の決まり）。

## テスト観点

- [TV-1] 実装の無い進め方の要求要件の PR が、タスクブランチを作らずにベースブランチへ向く
  - 入力：steps が requirements → design（design-only）で、タスクブランチの無いタスクの要求要件の工程が終わる
  - 期待結果：TaskBranchCreated は記録されず、工程のブランチ sacty/task-<ID8>-requirements-1 がベースブランチの先頭から作られ、pulls.upsert の baseBranch がベースブランチになる
- [TV-2] 要求要件の PR のマージが承認になり、設計の PR がマージを取り込んだベースブランチの最新から作られる
  - 入力：1 の要求要件の PR が GitHub でマージされ、ベースブランチの先頭がマージのコミットに進んだ後に、設計の工程が終わる
  - 期待結果：requirements の StepApproved が記録され、設計の PR のブランチの親がマージ後のベースブランチの先頭で、PR の向き先がベースブランチになる
- [TV-3] 最後の工程の PR のマージで、タスクが完了する
  - 入力：直接の流れの設計の PR が、人が PR の中で文書を直してからマージされる
  - 期待結果：design の StepApproved が記録されてタスクが完了になり、承認済みの成果はベースブランチを取得して読んだ人の版になる
- [TV-4] ほかの人のマージでベースブランチが進んでも、開いている工程の PR を更新する
  - 入力：直接の流れの設計の PR が開いている間に、別のコミットがベースブランチにマージされ、設計を差し戻して直しが終わる
  - 期待結果：新しい PR は作られず、同じ PR のブランチに直しのコミットが積まれ、前の PR は閉じられない
- [TV-5] 前の工程の PR が後からマージされたら、工程の PR を作り直す
  - 入力：直接の流れで設計の PR が開いている間に要求要件へ戻し、要求要件の新しい PR がマージされた後に、設計の工程が終わる
  - 期待結果：前の設計の PR が閉じられ、新しい設計の PR が、要求要件のマージを含むベースブランチの最新から、回を 1 つ進めたブランチで作られる
- [TV-6] 閉じられた工程の PR は、ベースブランチの最新から作り直す
  - 入力：直接の流れの設計の PR を人が閉じた後に、設計の工程をやり直して終わる
  - 期待結果：新しい PR が、ベースブランチの最新を親にした新しいブランチから、ベースブランチへ作られる
- [TV-7] マージを記録した工程の PR のブランチを消す
  - 入力：直接の流れで、PR の確認が工程の PR のマージを見つける場合と、直しの間に工程の PR がマージされる場合（どちらも、マージの前に人がそのブランチにコミットを足していた場合を含む）
  - 期待結果：どちらの場合も、その PR のブランチについて repos.deleteBranch が呼ばれる
- [TV-8] 人がクローズした PR のブランチは、先頭が sacty の最後の push と同じときだけ消す
  - 入力：直接の流れで、PR の確認が人による工程の PR のクローズを見つけ、リモートのブランチの先頭が stepBranchCommits の最後の push のコミットと同じ
  - 期待結果：その PR のブランチについて、期待する先頭をその先頭にして repos.deleteBranch が呼ばれ、StepBranchKept は記録されない
- [TV-9] 人がコミットを足してクローズした PR のブランチは、消さずに残して記録する
  - 入力：直接の流れで、PR の確認が人による工程の PR のクローズを見つけ、リモートのブランチの先頭が sacty の最後の push のコミットと違う
  - 期待結果：repos.deleteBranch は呼ばれず、StepBranchKept（branch・取得した head・sacty が最後に push した pushed）が記録される
- [TV-10] 人がクローズした PR のブランチの先頭を取得できなければ、消さずに完了のときに比べ直す
  - 入力：直接の流れで、人によるクローズを見つけたときにブランチの先頭の取得が通信の失敗で失敗し、その後に完了のときの取得では先頭が sacty の最後の push と同じになる
  - 期待結果：クローズのときは repos.deleteBranch が呼ばれず StepBranchKept も記録されず、完了のときにそのブランチについて repos.deleteBranch が呼ばれる
- [TV-11] 作り直しで sacty が閉じた工程の PR のブランチを消す
  - 入力：5 の作り直しで、sacty が開いている前の設計の PR を閉じる
  - 期待結果：閉じた PR のブランチについて、先頭を比べずに repos.deleteBranch が呼ばれる
- [TV-12] 作り直しで見つけた、人がすでに閉じていた PR のブランチは、先頭を比べてから消す
  - 入力：直接の流れで設計の直しが走っている間に、人が設計の PR のブランチにコミットを足して PR を閉じ、その後に直しが終わって作り直しが閉じた PR を見つける
  - 期待結果：repos.deleteBranch は呼ばれず、そのブランチの StepBranchKept が記録される
- [TV-13] sacty が人のコミットに積んだブランチは、先頭が同じでも消さない
  - 入力：直接の流れで、開いている工程の PR のブランチに人がコミットを足し、直しで sacty が同じ PR を更新した後に、人がコミットを足さずに PR を閉じる
  - 期待結果：更新のときに StepBranchKept が記録され、クローズのときも完了のときも、そのブランチについて repos.deleteBranch は呼ばれない
- [TV-14] StepBranchKept を記録したブランチも、その PR がマージされたら消す
  - 入力：直接の流れで、人のコミットに sacty が積んで同じ PR を更新し StepBranchKept を記録した後に、人がその PR をマージする
  - 期待結果：マージのときに、そのブランチについて先頭を比べずに repos.deleteBranch が呼ばれ、完了のときの sactyBranches にそのブランチは残らない
- [TV-15] 比べてから消すまでの間に人が push したら、ブランチは消えない
  - 入力：比べて消す経路で、先頭を取得した後、削除の前にリモートのブランチに別のコミットが push される
  - 期待結果：repos.deleteBranch は取得した先頭を期待する値として呼ばれ、削除が断られてブランチがリモートに残る
- [TV-16] 完了したとき、残っている sacty のブランチを作業領域を消す前に消し、残したブランチは消さない
  - 入力：直接の流れで、人がコミットを足した後にマージされ削除に失敗した工程のブランチと、マージされていない PR の StepBranchKept を記録したブランチが残ったまま、最後の工程の承認で完了する
  - 期待結果：作業領域を消す前に、マージされた PR のブランチについて先頭を比べずに repos.deleteBranch が呼ばれ、StepBranchKept は記録されず、StepBranchKept を記録したブランチについては呼ばれない
- [TV-17] ブランチを消せなくても、完了は止まらない
  - 入力：完了のときのブランチの削除で、repos.deleteBranch が例外を投げる
  - 期待結果：警告が出るだけで、タスクは完了のままになり、作業領域は消され、一時停止は記録されない
- [TV-18] 直接の流れのタスクを中止すると、工程のブランチを消し、残したブランチ・すでに無いブランチ・ベースブランチは消さない
  - 入力：直接の流れで、要求要件の PR が開いていて（リモートの先頭が最後の push と同じ）、前の回の StepBranchKept を記録したブランチと、人が閉じて GitHub で消されたブランチがあるタスクを中止する
  - 期待結果：TaskCancelled の cleanup に、開いていた PR の工程のブランチの削除と、リモートに無いブランチが done で記録され、StepBranchKept を記録したブランチ・タスクブランチ・ベースブランチの削除は試みられない
- [TV-19] クローズのときに先頭を取得できなかったブランチは、中止のときに比べてから消す
  - 入力：直接の流れで、人がコミットを足して工程の PR を閉じ、クローズのときの先頭の取得が通信の失敗で失敗した後にタスクを中止する（中止のときの取得で先頭が最後の push と違う場合と、中止のときも取得が通信の失敗で失敗する場合）
  - 期待結果：どちらの場合も repos.deleteBranch は呼ばれず、違う場合は StepBranchKept が記録され、取得が失敗した場合は cleanup にそのブランチが failed で記録される
- [TV-20] 中止の確認が、削除の規則と同じ分類で消すブランチを示す
  - 入力：直接の流れで、開いている工程の PR のブランチと、StepBranchKept を記録したブランチがあるタスクの中止の確認（cancelTargets）を読む
  - 期待結果：開いている PR のブランチは deleteBranches に入り、StepBranchKept を記録したブランチは deleteBranches に入らず、untouchedBranches に人がコミットを足したため消さないという理由とともに入る
- [TV-21] 派生の記録に、マージした工程の文書のパスが入る
  - 入力：直接の流れで完了したタスクから派生を作る
  - 期待結果：派生の指示の元のタスクの記録に、マージした要求要件・設計の PR の行ごとに、その PR の path（docs/sacty/<ID8>/<工程>.md）が入る
- [TV-22] 派生の作業領域に、前のタスクの文書がある
