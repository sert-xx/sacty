# 設計：実装の無い進め方では、工程の PR をベースブランチへ直接出す（PBI-464）

## スコープ

実装の工程が無いタスクでは、タスクブランチを作らずに、要求要件・設計の PR を工程のブランチからベースブランチへ出す。
マージを承認にし、sacty のブランチを残さない。

- 対象
  - 工程の PR の向き先・起点・作り直しの判定（`apps/daemon/src/service.ts`）と、投影の検査（`packages/core/src/projection.ts`）
  - マージ・クローズ・完了のときのブランチの削除
  - 派生の記録（`apps/daemon/src/prompts.ts` の `deriveRecord`）に文書のパスを足す
  - テスト、仕様書（日英）・図 `approval-branches`、ユーザー文書（日英）、ADR、作業履歴
  - 分割（`split`）の親タスクも直接の流れにする
- 対象外
  - 実装のある進め方とタスク分割の子タスクの流れ（タスクブランチのまま）
  - リモートに残っている過去のタスクのブランチの片付けと、backlog の 5（依頼の範囲の外）
  - 要求要件・設計の PR の競合の表示（今までどおり記録しない）

## 確認したいこと

- must：なし
- should：なし

確認しないと決めたこと
- 競合の表示：記録しない（今までどおり）。文書のパスはタスクごとに別（`<documentsDir>/<ID8>/`）で、ほかの変更と競合しにくいため。
- ブランチの保護と CI：何もしない。ベースブランチへ出すのは利用者の決定で、保護と CI の下でマージするかは、マージする人が決めるため。

## 既定で決めたこと

- 対象の判定：タスクブランチが無く、`steps` に `implement` が無いタスク（以下「直接の流れ」）。`steps` は `StepsChosen` の後で実装を増減しないので、途中で切り替わらない。
- 同じ PR を更新するかは、ベースブランチの先頭と比べない。前の工程の PR が、この工程の PR を記録した後にマージされたときだけ作り直す（ほかの人のマージでは作り直さない）。
- ブランチの削除に失敗しても止めずに警告だけにし、記録は足さない。完了のときに残りを消し直す（すでに無いブランチは消せたものとする）。
- 派生の記録のパスは、直接の流れでマージした PR の行だけに付ける（タスクブランチの流れの文書は、ベースブランチに無いことがあるため）。
- アップデートの前に作ったタスクで、まだタスクブランチも工程の PR も無いものは、直接の流れで進む（作ったものが無いので、途中の切り替えに当たらない）。

## 処理の流れ

| 所 | タスクブランチの流れ（変えない） | 直接の流れ |
| --- | --- | --- |
| `stepPullRequestsOn` | タスクブランチがあれば true | 工程の PR の記録があれば true（画面の提出の数で false にしない） |
| タスクブランチ | 無ければ作る（`TaskBranchCreated`） | 作らない |
| 工程のブランチの名前 | `<タスクブランチ>-<工程>-<回>` | 同じ（`sacty/task-<ID8>-<工程>-<回>`） |
| 新しいブランチの起点と `base` | タスクブランチの先頭 | `repository.baseBranch` を取得した先頭 |
| PR の向き先 | タスクブランチ | `repository.baseBranch` |
| 作り直し | 閉じた・マージした、または先頭が `base` と違う | 閉じた・マージした、または前の工程の PR が後からマージされた |
| マージした文書を読む（`readMergedDocument`） | タスクブランチを取得して読む | ベースブランチを取得して読む |

- ブランチの削除（直接の流れだけ。`repos.deleteBranch`）
  - PR の確認でマージ・クローズを記録したとき、その PR のブランチを消す。
  - 作り直しで sacty が前の PR を閉じたとき、そのブランチを消す。
  - 完了（`workspaceRetirable` になった）とき、作業領域を消す前に `sactyBranches` の残りを消す。
  - 中止は今の片付けのまま（`sactyBranches` に工程のブランチが入っている）。
  - 引き継いだ PR は工程の PR を作らないので、`sactyBranches` から除く今の決まりのままで、人のブランチは消えない。
- 派生の記録：直接の流れでマージした PR の行に、文書のパス（`StepPullRequestPublished` の `path`）を足す。例：`- 設計の PR（merged）：<URL>（文書：docs/sacty/<ID8>/design.md）`。

## 影響範囲

- 投影：`StepBranchPushed`・`StepPullRequestPublished` の検査を、「タスクブランチがある、または `steps` に `implement` が無い」にする。
  - 互換性：新しいイベントは足さないが、直接の流れのタスクを1件でも記録した後は、前の版のデーモンは整合性のエラーで作業履歴を投影できず、起動しない。前の版へ戻せなくなることは許容し、仕様書と ADR に明記する（前例は PBI-462 の互換性の注記。`docs/spec/approval.md`「工程の PR の直しの間のマージ」）。
- 文書
  - 仕様書：`docs/spec/approval.md`「PR での承認」に直接の流れを書き、PR の本文の Issue の注記（「タスクブランチへのマージでは閉じない」）を、ベースブランチへの PR でも閉じない書き方に直す。`docs/spec/tasks-and-steps.md` の完了の片付けと派生の記録を直す。英語の版も合わせる。
  - 図：`scripts/docs-diagrams/diagrams/tasks.mjs` に、直接の流れの図を足し、`npm run docs:diagrams` で作り直す。今の `approval-branches` は「実装がある進め方」の図と書き添える。
  - ユーザー文書：`docs/user/tasks.md`（と `tasks.en.md`）の「PR が作られる順序」・分割の親の記述・タスクブランチが残るという記述を直す。
  - ADR を足し、作業履歴 `docs/worklog/YYYYMMDD-pbi-464-<スラッグ>.md` を足す。ADR に互換性（前の版へ戻せないこと）を書く。

## テスト観点

- [TV-1] 実装の無い進め方の要求要件の PR が、タスクブランチを作らずにベースブランチへ向く
  - 入力：steps が requirements → design（design-only）で、タスクブランチの無いタスクの要求要件の工程が終わる
  - 期待結果：TaskBranchCreated は記録されず、工程のブランチ sacty/task-<ID8>-requirements-1 がベースブランチの先頭から作られ、pulls.upsert の baseBranch がベースブランチになる
- [TV-2] 要求要件の PR のマージが承認になり、設計の PR がマージを取り込んだベースブランチの最新から作られる
  - 入力：1 の要求要件の PR が GitHub でマージされ、ベースブランチの先頭がマージのコミットに進んだ後に、設計の工程が終わる
  - 期待結果：requirements の StepApproved が記録され、設計の PR のブランチの親がマージ後のベースブランチの先頭で、PR の向き先がベースブランチになる
- [TV-3] 最後の工程の PR のマージで、タスクが完了する
  - 入力：直接の流れの設計の PR が、人が PR の中で文書を直してからマージされる
  - 期待結果：design の StepApproved が記録されてタスクが完了になり、承認済みの成果はベースブランチを取得して読んだ人の版になる
- [TV-4] ほかの人のマージでベースブランチが進んでも、開いている工程の PR を更新する
  - 入力：直接の流れの設計の PR が開いている間に、別のコミットがベースブランチにマージされ、設計を差し戻して直しが終わる
  - 期待結果：新しい PR は作られず、同じ PR のブランチに直しのコミットが積まれ、前の PR は閉じられない
- [TV-5] 前の工程の PR が後からマージされたら、工程の PR を作り直す
  - 入力：直接の流れで設計の PR が開いている間に要求要件へ戻し、要求要件の新しい PR がマージされた後に、設計の工程が終わる
  - 期待結果：前の設計の PR が閉じられ、新しい設計の PR が、要求要件のマージを含むベースブランチの最新から、回を 1 つ進めたブランチで作られる
- [TV-6] 閉じられた工程の PR は、ベースブランチの最新から作り直す
  - 入力：直接の流れの設計の PR を人が閉じた後に、設計の工程をやり直して終わる
  - 期待結果：新しい PR が、ベースブランチの最新を親にした新しいブランチから、ベースブランチへ作られる
- [TV-7] マージ・クローズを記録した工程の PR のブランチを消す
  - 入力：直接の流れで、PR の確認が工程の PR のマージ、または人によるクローズを見つける
  - 期待結果：その PR のブランチについて repos.deleteBranch が呼ばれる
- [TV-8] 作り直しで sacty が閉じた工程の PR のブランチを消す
  - 入力：5 の作り直しで、sacty が前の設計の PR を閉じる
  - 期待結果：閉じた PR のブランチについて repos.deleteBranch が呼ばれる
- [TV-9] 完了したとき、残っている sacty のブランチを作業領域を消す前に消す
  - 入力：直接の流れで、マージの後に消せなかった工程のブランチが残ったまま、最後の工程の承認で完了する
  - 期待結果：作業領域を消す前に、stepBranches の残りについて repos.deleteBranch が呼ばれる
- [TV-10] ブランチを消せなくても、完了は止まらない
  - 入力：9 の完了で、repos.deleteBranch が例外を投げる
  - 期待結果：警告が出るだけで、タスクは完了のままになり、作業領域は消され、一時停止は記録されない
- [TV-11] 直接の流れのタスクを中止すると、工程のブランチを消す
  - 入力：直接の流れで要求要件の PR が開いているタスクを中止する
  - 期待結果：TaskCancelled の cleanup に工程のブランチの削除が done で記録され、タスクブランチの削除は試みられない
- [TV-12] 派生の記録に、マージした工程の文書のパスが入る
  - 入力：直接の流れで完了したタスクから派生を作る
  - 期待結果：派生の指示の元のタスクの記録に、マージした要求要件・設計の PR の行ごとに、その PR の path（docs/sacty/<ID8>/<工程>.md）が入る
- [TV-13] 派生の作業領域に、前のタスクの文書がある
  - 入力：直接の流れで完了したタスクから派生を作り、派生の作業領域をベースブランチから用意する
  - 期待結果：派生の作業領域の起点のコミットが設計のマージを含むベースブランチの先頭で、docs/sacty/<元の ID8>/design.md がある
- [TV-14] 実装のある進め方は、今までどおりタスクブランチを使う
  - 入力：steps が requirements → design → implement のタスクで、要求要件・設計・実装の工程を順に終える
  - 期待結果：TaskBranchCreated が記録され、要求要件・設計の PR はタスクブランチへ、実装の PR はタスクブランチからベースブランチへ向く
- [TV-15] 分割の子タスクは、今までどおりタスクブランチを使う
  - 入力：分割で作られた、実装の工程を持つ子タスクの要求要件の工程が終わる
  - 期待結果：子タスクのタスクブランチが作られ、要求要件の PR はそのタスクブランチへ向く
- [TV-16] 分割の親タスクは、ベースブランチへ直接出す
  - 入力：steps が requirements → design → split → integrate の親タスクの要求要件の工程が終わる
  - 期待結果：TaskBranchCreated は記録されず、要求要件の PR の向き先がベースブランチになる
- [TV-17] タスクブランチがすでにある実装の無いタスクは、今の流れのまま進む
  - 入力：TaskBranchCreated を記録済みで、steps に implement が無いタスクの設計の工程が終わる
  - 期待結果：設計の PR はタスクブランチへ向き、比べる先はタスクブランチの先頭で、ブランチの削除は完了のときに行われない
- [TV-18] 投影が、実装の無いタスクだけ、タスクブランチの無い工程の PR の記録を受け付ける
  - 入力：タスクブランチの無いタスクに StepBranchPushed と StepPullRequestPublished を投影する（steps に implement が無い場合と、ある場合）
  - 期待結果：implement が無ければ stepBranches と stepPullRequests に入り、implement があれば ActivityIntegrityError になる
- [TV-19] 仕様書に、直接の流れが書かれている
  - 入力：docs/spec/approval.md・approval.en.md と docs/spec/tasks-and-steps.md・tasks-and-steps.en.md の差分
  - 期待結果：対象の判定、向き先と起点、作り直しの条件、ブランチを消す時点（マージ・クローズ・作り直し・完了・中止）、派生の記録のパス、PR の本文の Issue の注記、前の版に戻せない互換性が、日英で同じ内容で書かれ、approval-branches の図とともに直接の流れの図が載っている
- [TV-20] ユーザー文書に、直接の流れが書かれている
  - 入力：docs/user/tasks.md・tasks.en.md の差分
  - 期待結果：実装の無い進め方では要求要件・設計の PR がベースブランチへ向き、マージで文書がベースブランチに入り、sacty のブランチは完了・中止で消えることが、です・ます調で日英に書かれ、タスクブランチが残るという記述と分割の親の記述が直っている
- [TV-21] ADR と作業履歴が足されている
  - 入力：docs/adr と docs/worklog の差分
  - 期待結果：docs/adr に、直接の流れにした決定・判定の条件・作り直しの比べ方・前の版に戻せない影響を書いた ADR があり、docs/worklog に pbi-464 の作業履歴がある
