# PBI-460 設計：PR のレビューから Sacty の過程の情報を外し、Sacty の記録に移す

## スコープ

PR に投稿するレビューを、判定・総評・指摘・修正の判断に要る検証の結果・リスク評価・AI の印だけにする。
外した過程の情報は、レビューのエージェントが返す新しい記録の JSON で Sacty に残し、タスクの画面と get_task で読めるようにする。

- 対象
  - 本文の組み立て（`buildReviewBody`・`VERDICT_ABSENT_LINE`）、レビューの指示（prompts.ts）、止まった知らせ（review-stop-notice.ts）
  - 既定のスキル review-dispatch の `pr-review` の流れ（SKILL.md・pr-review.md・aggregation.md・verification-run.md・linked-docs.md・repo-guidance.md・screen-capture.md の本文に書く決まり）
  - 記録（core の events・projection、デーモン、画面、MCP の get_task）、仕様書・ユーザー文書（日英）、ADR、作業履歴、テスト
- 対象外
  - 自己レビュー（`self-review` の流れ）の出力の書き方。スキルの共通の箇所は、`pr-review` のときだけ変わる書き方にする
  - 判定の決め方・観点の段階・担当を 0 件しか起動しない実行のやり直し（PBI-379）
  - すでに PR に投稿したレビューの書き直し

## 確認したいこと

### must

1. 本文の「レビューの範囲」にある各行を、PR に残すか記録へ移すかを、次の表の線引きにしてよいか。
   推奨：表のとおり。読む人が何を確かめればよいかが変わる行だけを、中身の言葉で PR に残す。
   懸念：線引きが違うと、スキル・指示・テストの文言を作り直すことになる。PR の読み手は、残すべき未確認の所（例：読めなかった文書）を知らずにマージしうる。

| 行 | 扱い |
| --- | --- |
| 取得できなかった文書、省略された差分、既存のレビューを読めない、画面を撮っていない、検証を実行していない・止まった | PR に中身の言葉で残す（何が未確認で、読む人が何をすればよいか） |
| 絞った再レビュー | PR には「前回（`abc1234`）以降の変更と前回の指摘だけを確かめた」とだけ書き、理由と起動しなかった観点は記録へ |
| 観点の見方（担当の数・逐次モード）、絞らなかったことと理由、検証を絞ったこと、基準にしなかったリポジトリの指示 | 記録へ |

### should

1. PR から外す範囲に、表示されない HTML コメントの目印（`<!-- sacty-review:<タスク ID>:<回> -->`・`sacty-review-stop:`・`sacty-risk-declined:`）のタスク ID を含めるか。
   推奨：含めない（目印は残す）。
   懸念：消すと、Sacty が自分の投稿と止まった知らせを見分けられず、二重の投稿・前回のレビューの読み落とし・知らせの解消漏れが起きる。
2. 検証が通ったことを、PR の本文に書くか。
   推奨：書かない。落ちたもの・確かめられなかったものだけを書き、通った結果と経過（使い回したなど）は記録に残す。
   懸念：PR の読み手は、指摘が無いレビューで「検証したのか」を本文から確かめられない。書く場合は、スキルと指示に 1 行の決まりを足すだけで済む。
3. 前回の回の記録が無い再レビュー（記録の欄が無い以前の作業履歴、記録の JSON が無かった・読めなかった回）を、絞らない側に倒すか。
   推奨：倒す（デーモンが `rereviewNarrowOf` と文書だけの判断で、記録が無いことを絞らない理由にする）。
   懸念：版を上げた後の最初の再レビューは PR 全体を見るため、時間と費用が 1 回分増える。倒さないと、本文から未確認の所が消えた回で、見られなかった観点を見ないまま絞る。

### 確認しないと決めたこと

- 判定が無いときの行：「見ていない観点がある」を外し、「確かめられなかった所がある・対象を読めなかったため、判定を付けていません」に変える。受け入れ条件 3 が観点の語を禁じているため。
- リスク評価の省略の案内：タスクの ID を外し「依頼した人は、Sacty のタスクの画面で確かめられます」にする。受け入れ条件 1 がタスクの ID を禁じているため。
- 投稿の間に先頭が変わったときの「Sacty の『再レビュー』でレビューできます」：残す。依頼した人の操作の案内で、受け入れ条件 1 の項目に当たらず、PBI-450 が案内を認めているため。
- 止まった知らせ：理由の要点に担当・サブエージェントの文が入る、担当が 0 件のレビューの一時停止は、要点を中身の言葉の固定の文にする。受け入れ条件 1 が Sacty の PR のコメントを対象にしているため。

## 既定で決めたこと

- 記録の受け渡しは、新しい見出し `sacty-review-record` の JSON にする（セルフレビューの報告 `sacty-self-review` と同じ形の前例）。投稿する本文からは取り除く。
- 記録が読めない・上限を超えるときは、レビューは使い、記録だけを無し（null）にする。レビューの投稿を止めない。
- 新しい ADR で、PBI-349 の「観点の見方を本文に 1 行書く」と PBI-379 の決定 6 の本文の側を置き換える（置き換え元・置き換え先を書く）。

## データ

`AgentRunCompleted` の payload に optional の `reviewRecord`（`ReviewRecord | null`）を足す。
欄を足すだけで、イベントの種類と列挙の値は増やさない（前の版のデーモンは、知らない欄を捨てて読める）。

| 欄 | 中身 | 上限 |
| --- | --- | --- |
| `mode` | `subagents`・`sequential` | - |
| `viewpoints` | 観点ごとの `id`・`status`（`launched`・`relaunched`・`failed`・`substituted`・`not_launched`）・`reason` | 100 件 |
| `notReviewed` | 見られなかった観点と理由 | 100 件 |
| `dismissed` | 採用しなかった指摘の題・観点・理由 | 100 件 |
| `dropped` | 既存の指摘と重なる・目的の範囲の外・対応済みや却下済みと重なる件数と、その中の `must` の数 | - |
| `scope` | 絞った・絞らなかったことと理由、基準にしなかった指示など | 20 件 |
| `verification` | 検証の経過（実行・使い回し・止まった・実行しない）の文 | 20 件 |

- 文は 1 件 500 文字まで。秘密の値は、記録の前に `auditRedactor(task)` で伏せる。
- projection：`task.reviewRecord`（`round` 付き）を、`reviewDispatch` と同じく回ごとに置き換える。`ReviewRestarted` で `previousReview.record` に写す。
- エージェント・モデル・切り替え・担当の数は、既存の `reviewDispatch` を使う。

## 処理の流れ

1. 指示：観点の見方の 1 行を書かせる指示を外し、記録の JSON の形を示す。本文に書かない語（観点の ID・担当・サブエージェント）と、未確認の所の書き方を示す。
2. スキル：`pr-review` は、集約の記録を「依頼した側が決めた形で返す」とし、本文に書く決まりを上の線引きに直す。件数の行（重なり・範囲の外・対応済み）は記録へ移す。不採用の指摘を本文に一覧で書かないと明記する。
3. 完了できないとき（pr-review.md 38 行）：本文の最初に「レビューを完了できませんでした」と、確かめられなかった所を中身の言葉で書く（例：「入力の検査の抜けは確かめていません。src/api の変更を、人が確かめてください」）。
4. 本文の組み立て：末尾は「---」と「AI がレビューしました（人間は確認していません）。」だけにし、`reviewDispatchLines` を外す。
5. 再レビュー：`rereviewLines` の `previousReview` のデータに `record`（`notReviewed`・止まった検証・判定の有無）を足す。スキルの規則 10・11 の「前回の本文に書かれている」を「依頼した側が渡した前回の記録に書かれている。記録が渡されないときは、前回の本文に書かれている」に直す。

## 影響範囲

- 画面：タスクの詳細のレビューの欄に、記録の各欄を回ごとに出す（日英の文言を足す）。記録の無い回は、欄を出さない。
- get_task：`reviewDispatch` と `reviewRecord` を返す。仕様書 mcp-server.md（日英）に欄を書く。
- 文書：intake.md（日英）の「本文の最初に見られなかった観点」「最後の行にエージェントと担当の数」の説明を、画面と get_task で読む説明に変える。

## テスト観点

- [TV-1] 投稿する本文の末尾に、AI の印だけが残り、過程の情報が出ない
  - 入力：reviewDispatch（runtime・model・configuredAgentId・subagents 5）を持つタスクで buildReviewBody を呼ぶ
  - 期待結果：本文に「AI がレビューしました（人間は確認していません）」があり、タスクの ID・エージェントの製品名・モデル・「切り替え」・「担当」・「サブエージェント」の文字列が、先頭の目印の HTML コメントの外に無い
- [TV-2] 判定が無い回の行が、観点の語を使わない
  - 入力：回の判定が missing: absent のタスクで buildReviewBody を呼ぶ
  - 期待結果：判定の行が「判定：付いていません」で始まり、「観点」の語を含まない
- [TV-3] リスク評価の省略の案内に、タスクの ID が出ない
  - 入力：上限を超える長さのリスク評価を持つ、指摘なしの回のタスクで buildReviewBody を risk: true で呼ぶ
  - 期待結果：本文に「Sacty のタスクの画面で確かめられます」があり、タスクの ID が先頭の目印の外に無い
- [TV-4] 担当が 0 件のレビューで止まった知らせが、過程の語を使わない
  - 入力：担当を 1 件も起動しないレビューが上限の回数続いて一時停止したタスクで、止まった知らせの本文を作る
  - 期待結果：本文の理由の行が中身の言葉の固定の文になり、「担当」「サブエージェント」の語を含まない
- [TV-5] レビューの指示が、観点の見方の 1 行を求めず、記録の JSON を求める
  - 入力：初回の PR のレビューのタスクで buildPrompt(task, "review", extra) を呼ぶ
  - 期待結果：指示に「観点をどう見たかを1行で書く」が無く、sacty-review-record の JSON の形と、本文に観点の ID・担当・サブエージェントの語を書かないこと、確かめられなかった所を何が未確認で読む人が何をすればよいかで書くことがある
- [TV-6] 記録の JSON を読み、作業履歴に残し、本文から取り除く
  - 入力：sacty-review-record の正しい JSON（viewpoints に substituted と not_launched、dismissed 2 件、dropped、verification を含む）を付けたレビューの答えで実行を終える
  - 期待結果：AgentRunCompleted の reviewRecord に各欄が残り、task.reviewRecord が今回の回の番号で投影され、投稿する本文に JSON のブロックと sacty-review-record の文字列が無い
- [TV-7] 記録の JSON が読めない・上限を超えるときも、レビューは投稿される
  - 入力：形の崩れた sacty-review-record、または viewpoints が 101 件の記録を付けたレビューの答えで実行を終える
  - 期待結果：reviewRecord が null で記録され、レビューの本文は投稿され、タスクは一時停止しない
- [TV-8] 記録の文の秘密の値を伏せる
  - 入力：verification の文に、タスクの秘密情報の値を含めた記録を付けて実行を終える
  - 期待結果：作業履歴の reviewRecord に、その値が残らず伏せた形になる
- [TV-9] 記録を回ごとに置き換え、再レビューで前回の記録に写す
  - 入力：回 1 で記録あり・ReviewRestarted・回 2 で記録の欄が無い実行、の順のイベントを投影する
  - 期待結果：回 2 の完了の後、task.reviewRecord は undefined、previousReview.record は回 1 の記録と同じ
- [TV-10] 記録の欄が無い以前の作業履歴を読める
  - 入力：reviewRecord と previousReview.record の欄が無い、レビューを含む作業履歴を投影し、そのタスクで get_task と画面を開く
  - 期待結果：例外にならず、get_task に reviewRecord が無く、画面のレビューの欄に記録の項目が出ない
- [TV-11] 画面に記録の各欄を出す
  - 入力：reviewRecord（mode・viewpoints・notReviewed・dismissed・dropped・scope・verification）と reviewDispatch を持つタスクの詳細を、日本語と英語で表示する
  - 期待結果：観点ごとの扱いと理由、見られなかった観点と理由、採用しなかった指摘と理由、落とした件数、検証の経過、エージェント・モデル・切り替えが、それぞれの言語の文言で表示される
- [TV-12] get_task が記録とエージェントの情報を返す
  - 入力：reviewRecord と reviewDispatch を持つタスクに get_task を呼ぶ
  - 期待結果：答えに reviewRecord の各欄と、reviewDispatch のエージェント・モデル・担当の数・切り替え前のエージェントがある
- [TV-13] 再レビューの指示に、前回の記録を渡す
  - 入力：previousReview.record の notReviewed が 1 件ある再レビューのタスクで buildPrompt(task, "review", extra) を呼ぶ
  - 期待結果：前回のレビューのデータの JSON に、その観点と理由を含む record がある
- [TV-14] 前回の記録が無い再レビューは、範囲と検証を絞らない
  - 入力：前回の回に判定はあるが previousReview.record が無い（または null の）タスクで、絞りの条件に他は当たる再レビューを始める
  - 期待結果：rereviewNarrow と rereviewDocsOnly が付かず、絞らなかった理由がログに 1 行出る
- [TV-15] スキルの pr-review の本文の決まり
  - 入力：review-dispatch の SKILL.md・pr-review.md・aggregation.md・verification-run.md・linked-docs.md・repo-guidance.md・screen-capture.md の差分
  - 期待結果：pr-review の本文に、観点の ID・数・担当・逐次モード・不採用の指摘の一覧・落とした件数・検証のやり方を書かず、集約の記録で返すと書かれ、確かめられなかった所の書き方は設計の線引きの表どおりで、self-review の出力の決まりは変わらず、特定の言語・sacty・Node.js の名前を含まない
- [TV-16] スキルの完了できないときの書き方
  - 入力：pr-review.md の「完了できないとき」の差分
  - 期待結果：本文の最初に「レビューを完了できませんでした」と、何が未確認で読む人が何をすればよいかを中身の言葉で書き、見られなかった観点の ID と理由は記録に残すと書かれている
- [TV-17] スキルの規則 10・11 が前回の記録を読む
  - 入力：SKILL.md と pr-review.md の規則 10・11 の絞らない条件の差分
  - 期待結果：見られなかった観点・止まった検証・判定が無いことを、依頼した側が渡した前回の記録で確かめ、記録が渡されないときは前回の本文で確かめると書かれ、それ以外の条件は変わっていない
- [TV-18] 仕様書・ユーザー文書・ADR
  - 入力：docs/spec の tasks-and-steps・context・event-log・mcp-server、docs/user の intake（日英）と新しい ADR の差分
  - 期待結果：本文に過程の情報を書かないこと、reviewRecord の欄と上限・読めないときの null、画面と get_task での読み方、前回の記録が無い再レビューは絞らないことが日英で同じに書かれ、ADR に PBI-349 の決定と PBI-379 の決定 6 の本文の側を置き換えることが書かれている
