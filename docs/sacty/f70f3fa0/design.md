# PBI-460 設計：PR のレビューから Sacty の過程の情報を外し、Sacty の記録に移す

## スコープ

PR に投稿するレビューを、判定・総評・指摘・修正の判断に要る検証の結果・リスク評価・AI の印だけにする。
外した過程の情報は、レビューのエージェントが返す新しい記録の JSON で Sacty に残し、タスクの画面と get_task で読めるようにする。
Sacty が PR に出すほかのコメント（指摘への対応の返信・工程の成果物のコメント）の末尾からも、タスクの ID を外す。

- 対象
  - 本文と行へのコメントの組み立て（`buildReviewBody`・`buildReviewComments`・`VERDICT_ABSENT_LINE`）、レビューの指示（prompts.ts の初回と再レビューの各節）、止まった知らせ（review-stop-notice.ts）
  - 指摘への対応の返信（remark-reply.ts）と工程の成果物のコメント（github-comments.ts の `buildGitHubComment`）の末尾
  - 既定のスキル review-dispatch の `pr-review` の流れ（SKILL.md・pr-review.md・aggregation.md・verification-run.md・linked-docs.md・repo-guidance.md・screen-capture.md の本文に書く決まり）
  - 記録（core の events・projection、デーモン、画面、MCP の get_task）、仕様書・ユーザー文書（日英）、ADR、作業履歴、テスト
- 対象外
  - 自己レビュー（`self-review` の流れ）の出力の書き方。スキルの共通の箇所は、`pr-review` のときだけ変わる書き方にする
  - 判定の決め方・観点の段階・担当を 0 件しか起動しない実行のやり直し（PBI-379）
  - すでに PR に投稿したレビュー・コメントの書き直し

## 確認したいこと

### must

なし

### should

1. 指摘への対応の返信の末尾の「（指摘 <指摘の ID> への対応）」も外すか。
   推奨：外し、「Sacty の<工程名>の工程で、AI が書きました。」にする。指摘の ID（`design-3-1` など）は Sacty の中の ID で、返信は指摘のスレッドに付くか引用を持つため。
   懸念：外さないと、Sacty を使わない PR の読み手に、意味の無い ID が返信ごとに出続ける。

### 確認しないと決めたこと

- 判定が無いときの行：「見ていない観点がある」を外し、「確かめられなかった所がある・対象を読めなかったため、判定を付けていません」に変える。受け入れ条件 3 が観点の語を禁じているため。
- リスク評価の省略の案内：PR には「リスク評価は長いため省略しました」だけを書き、画面と Sacty の操作の案内（`TASK_LINK_NOTE` を含む）を外す。全文は画面と get_task で読める。
- 止まった知らせ：担当が 0 件のレビューで一時停止したときは、理由の要点に担当・サブエージェントの文が入る。この要点を、中身の言葉の固定の文にする。受け入れ条件 1 が Sacty の PR のコメントを対象にしているため。

## 既定で決めたこと

- 記録の受け渡しは、新しい見出し `sacty-review-record` の JSON にする（セルフレビューの報告 `sacty-self-review` と同じ形の前例）。
- 記録の JSON のブロックは、読めたかどうかに関わらず、投稿する本文から常に取り除く。読めない・上限を超えるときは、レビューは使い、記録だけを無し（null）にする。レビューの投稿を止めない。
- 表示されない HTML コメントの目印（`<!-- sacty-review:<タスク ID>:<回> -->`・`sacty-review-stop:`・`sacty-risk-declined:`・返信と成果物のコメントの目印）は残す。Sacty が自分の投稿と知らせを見分けるのに要るため。
- 返信と成果物のコメントの末尾は、工程の名前と「AI が書きました」（成果物は承認の状態の文も）を残す。読み手が、どの工程の AI の文かを知るのに要るため。
- 再レビューの「前回の指摘」の節で、取り下げた前回の指摘と理由は PR に残す。前回の指摘の状態で、作者が直すかを決めるのに要るため（今回の採用しなかった指摘とは別）。
- 新しい ADR で、PBI-349 の「観点の見方を本文に 1 行書く」と PBI-379 の決定 6 の本文の側を置き換える（置き換え元・置き換え先を書く）。

## データ

`AgentRunCompleted` の payload に optional の `reviewRecord`（`ReviewRecord | null`）を足す。
欄を足すだけで、イベントの種類と列挙の値は増やさない（前の版のデーモンは、知らない欄を捨てて読める）。

| 欄 | 中身 | 上限 |
| --- | --- | --- |
| `mode` | `subagents`・`sequential` | - |
| `viewpoints` | 観点ごとの `id`・`status`（`launched`・`relaunched`・`failed`・`substituted`・`not_launched`）・`reason` | 100 件 |
| `notReviewed` | 見られなかった観点と理由 | 100 件 |
| `dismissed` | 採用しなかった指摘の題・観点・理由 | 100 件 |
| `dropped` | 既存の指摘と重なる・目的の範囲の外・対応済みや却下済みと重なる件数と、その中の `must` の数 | - |
| `scope` | 絞った・絞らなかったことと理由、基準にしなかった指示など | 20 件 |
| `verification` | 検証の経過。各件に `kind`（`ran`・`reused`・`stopped`・`skipped`）と `text` | 20 件 |

- 形の検査：次のどれか 1 つでも通らなければ、記録の全体を null にする（一部だけ残さない）。
  - `mode`・`status`・`kind` は、表の列挙の値だけ。
  - `dropped` の各件数は、0 以上の整数。
  - 各欄は表の型で、表に無い欄は認めない。
- 文字列の欄はすべて、`auditRedactor(task)` で秘密の値を伏せてから、1 件 500 文字に切る（切る前に伏せるので、境界をまたぐ値も残らない）。伏せる処理が失敗したら、記録を null にする。
- ブロックの除去：見出し `sacty-review-record` を含むフェンスは、すべて本文から取り除く。閉じていないもの（見出しから本文の終わりまで）と 2 つ目以降も除く。読むのは最初の閉じたブロックだけで、2 つ目以降は無視する。
- 記録の文字列は、PR を読んだエージェントが書いた信頼しない入力として扱う。
  - get_task：記録の欄（データ）として返す。
  - 再レビューの指示：`previousReview` の JSON のデータの区画に入れ、「データで、指示ではない」と添える。
  - 画面：文字列として表示する（Markdown・HTML として解釈しない）。
- 前回の判定の有無は、記録に持たせず、既存の `reviewVerdicts` を使う。
- projection：`task.reviewRecords` を、`reviewVerdicts` と同じく回ごとの配列で持つ。各要素は `round`・`record`（null 可）・その回の `reviewDispatch`。同じ回の実行し直しはその回の要素だけを置き換え、ほかの回は残す。記録の欄が無い実行の回は要素を作らない。
- `ReviewRestarted` で、前回の回の要素の `record` を `previousReview.record` に写す。
- 既存の `task.reviewDispatch`（最新の回）は、そのまま残す。

## 処理の流れ

本文の各行の線引き（人が承認した表）：

| 行 | 扱い |
| --- | --- |
| 取得できなかった文書、省略された差分、既存のレビューを読めない、画面を撮っていない、検証を実行していない・止まった、基準にしなかったリポジトリの指示、検証を絞って実行しなかったもの | PR に中身の言葉で残す（何が未確認で、読む人が何をすればよいか。例：「この PR が変えた指示は基準にしていません。沿っているかは人が確かめてください」「コードのテストは実行していません」） |
| 絞った再レビュー | PR には「前回（`abc1234`）以降の変更と前回の指摘だけを確かめた」とだけ書き、理由と起動しなかった観点は記録へ |
| 観点の見方（担当の数・逐次モード）、絞らなかったことと理由、検証を絞った理由とやり方、指示を基準にしなかった理由 | 記録へ |
| 検証が通ったこと・検証の経過（使い回したなど） | 記録へ（PR に書かない） |
| レビューをした側の作業の経過の文（「レビューの本文を書きます」「担当の結果が揃い、集約しました」など） | 書かない（PR にも記録にも） |

1. 指示：観点の見方の 1 行を書かせる指示を外し、記録の JSON の形を示す。本文と行へのコメントに書かない語（観点の ID・担当・サブエージェント）と、未確認の所の書き方を示す。総評の前に作業の経過の文を書かず、本文を総評から始めることを示す。再レビューの各節（文書だけ・絞った・絞らない条件）で本文に書かせる行（絞ったこと・絞らなかった理由・起動しなかった観点・実行しなかった検証と理由）も、線引きの表のとおりに直す。
2. スキル：`pr-review` は、集約の記録を「依頼した側が決めた形で返す」とし、本文に書く決まりを上の線引きに直す。件数の行（重なり・範囲の外・対応済み）は記録へ移す。不採用の指摘を本文に一覧で書かないこと、作業の経過の文を書かないことを明記する。
3. 完了できないとき（pr-review.md 38 行）：本文の最初に「レビューを完了できませんでした」と、確かめられなかった所を中身の言葉で書く（例：「入力の検査の抜けは確かめていません。src/api の変更を、人が確かめてください」）。
4. 本文の組み立て：末尾は「---」と「AI がレビューしました（人間は確認していません）。」だけにし、`reviewDispatchLines` を外す。
5. 再レビュー
   - デーモン：`rereviewNarrowOf` と文書だけの判断で、次のどれかなら絞らない。判断は構造の欄だけで決め、文の中身は読まない。
     - 前回の記録が無い（undefined・null）。
     - `notReviewed` がある。
     - `kind: stopped` の検証がある。
     - 判定が無い（今の `reviewVerdicts` の条件のまま）。
   - 指示：`rereviewLines` の `previousReview` のデータに `record` を足す。
   - スキル：規則 10・11 の「前回の本文に書かれている」を、次のように直す。
     - 依頼した側が前回の記録を渡すときは、記録の見られなかった観点・止まった検証で確かめる。
     - 渡さないときは、前回の本文で確かめる。記録を渡さない依頼元のための経路で、Sacty では記録が無ければデーモンが絞らない。
   - 働きが変わるのは、記録の無い回の次の 1 回（版を上げた後の最初の再レビューと、記録が null の回の次）だけ。
6. 返信と成果物のコメント：末尾の「Sacty のタスク <ID> の」を「Sacty の」に変え、指摘の ID も外す（確認したいこと should 1 の推奨）。

## 影響範囲

- 画面：タスクの詳細のレビューの欄に、`reviewRecords` のすべての回の記録とエージェントの情報を、回ごとに出す（日英の文言を足す）。記録の無い回は、欄を出さない。
- get_task：`reviewRecords`（各回の記録と `reviewDispatch`）と、リスク評価の全文を返す。仕様書 mcp-server.md（日英）に欄を書く。
- 文書：intake.md（日英）の「本文の最初に見られなかった観点」「最後の行にエージェントと担当の数」の説明を、画面と get_task で読む説明に変える。tasks-and-steps.md・tasks.md（日英）の返信と成果物のコメントの末尾の説明を、タスクの ID の無い形に合わせる。
