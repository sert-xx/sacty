# 要求要件：人がドラフトを外した PR を、sacty がドラフトへ戻さない

## スコープ

最後のドラフトの切り替えが sacty でない「ドラフトを外す」だった PR（以下、人が外した PR）を、sacty はドラフトへ戻さない。戻さなかったことは作業履歴に残す。
切り替えの履歴を読めないときは、戻さない側に倒す。

- 対象：
  - sacty がドラフトへ戻す経路（直しの提出・PR の確認・レビューの回の始め・外す間の変化・重ねた PR の付け替え）
  - 作業履歴の新しい記録と、その表示
  - 仕様書・ユーザー文書（日英）・ADR・作業履歴・テスト
- 対象外：
  - 一時停止に伴う戻し（Q-2）
  - 人がドラフトにした PR を、sacty が外し直す振る舞い
  - 戻さなかった後のレビューの回（今のまま続く。Q-4）

## 確認したいこと

### must

- Q-1：人が外した後に PR の先頭が変わったとき（sacty が直しを提出した・人がコミットを足した）も、戻さないか。推奨：戻さない。受け入れ条件1が「直しの始め」を挙げているため。
  - 懸念：レビューしていない直しがマージできる状態になります。外した人が気づかずにマージすると、レビューしていない変更が main に入ります。

### should

- Q-2：一時停止に伴う戻し（`settlePausedDraft`）は、今のまま戻すか。今の例外（重ねた PR の「指摘なし」待ち、一時停止の理由が `unchanged`・`needs_decision`）は、今のまま戻さない。推奨：戻す。ユーザー文書が「マージを止めたいときは一時停止」と案内しているため。
  - 懸念：一時停止の間に人が外してすぐマージすると、次の PR の確認で戻り、PR #501 と同じく「まだドラフト」で失敗します。マージするには、再開してから外す手間が残ります。
- Q-3：重ねた PR に直しを提出したとき、次のように扱うか。推奨：下のとおり。ADR `20261108-0615-stack-dependent-subtasks-on-reviewed-pull-requests` が、重ねた PR は人が外してマージしてよいとしているため。
  - 人が外した PR：戻さず、タスクも止めない（`pr.stackDraftFailed` にしない）。
  - 履歴を読めない・sacty の切り替えかを決められない PR：戻さず、今の `pr.stackDraftFailed` と同じくタスクを止める。人が外したと分からない PR を、依存先より先にマージできる状態で承認待ちにしないため。再開すると提出からやり直せる。
  - 懸念：人が外した重ねた PR は、直した後も依存先より先にマージできます。読み取りの失敗が続く間は、重ねた PR のタスクが提出のたびに止まります。
- Q-4：戻さなかった PR を、台帳では「指摘なし」を待つ状態のままにするか。推奨：そのままにする。マージは今も承認として進むため。
  - 懸念：人がマージするまでレビューの回と提案の選り分けが続き、そのぶんの費用がかかります。
- Q-5：sacty が自分の切り替えかを決められない PR（この変更の前に切り替えた PR など）は、戻さないか。推奨：戻さない。受け入れ条件4と同じ向きにするため。
  - これは受け入れ条件3（sacty がドラフトにした・外した PR の振る舞いを変えない）から外れます。外れるのは、この変更のデプロイの時点で開いている PR だけです。
  - 懸念：デプロイの時点で sacty が外していた PR に人がコミットを足しても、ドラフトに戻らず、レビューしていない先頭がマージできる状態になります。
- Q-6：新しい記録を作業履歴に書いた後は、前の版のデーモンへ切り戻せない（前の版は未知の種類の記録を拒み、作業履歴を読めず起動しない）。互換の層は作らず、このことを仕様書・ADR に書くか。推奨：作らずに書く。切り戻すことはまれで、互換の層の分だけ変更が大きくなるため。
  - 懸念：記録が1件でも入った後に切り戻した運用者は、デーモンが起動せず、その記録を作業履歴から手で除くまで、すべてのタスクが止まります。

### 確認しないと決めたこと

- 「人が外しても戻す」という既存の記述（`docs/user/tasks.md` の1335行、仕様の `settleDraft`・`redraftAwaiting`）とテストは、依頼どおりに変える。受け入れ条件1が明示しているため。1339行の「マージを止めたいときは一時停止」の案内は、R-7 により変えない。
- PR #501 の 05:02:44 に戻した経路は特定しない。R-5 がすべての経路を対象にするので、作るものは変わらないため。
- 人と sacty の切り替えの見分け方（GitHub の actor が同じアカウントになる件）は、設計で決める。要求は判定の結果だけを定めるため。

## 既定で決めたこと

- 作業履歴への記録は、人が外した1回につき1件にする（PR の確認は1分ごとなので、確認のたびには記録しない）。
- 読めずに戻さなかったことは、読めない状態が続く間に1件だけ記録する。理由は「人が外した」と分ける。
- 記録の契機は、今なら戻す条件を満たす PR を戻さなかったときに限る（元からドラフトの PR など、戻す必要の無い PR では記録しない）。読めない間に人が外したときは「読めなかった」を記録し、読めた後に「人が外した」を1件記録する。
- 記録には、どの外し（または読めない状態の始まり）かを識別する値を含め、重複の判定を作業履歴から復元できるようにする（再起動の後も同じものを2件記録しない）。
- sacty が自分の切り替えを見分ける材料は、再起動で消えない形で持つ（今のメモリー上の値だけにしない）。

## 受け入れの確かめ方

### 自動のテストで確かめること

- フェイクの GitHub に切り替えの履歴（人の外し・sacty の切り替え・読み取りの失敗）を返させ、R-1 と R-4〜R-11 を確かめる。再起動を挟んでも、R-1 の判定と R-4・R-9・R-11 の記録の件数が変わらないことも確かめる。
- 「人が外した PR を戻す」前提の既存のテスト（`apps/daemon/src/daemon-step-pull-requests.test.ts`・`daemon-split.test.ts`）を、新しい決まりに合わせる。
- 修正を戻すと、R-4・R-5・R-8 のテストが落ちる。
- R-2・R-3 は、差分で文書の中身を確かめる。あわせて `tests/docs` が通る。

### 人が確かめること

- 実際の GitHub で、sacty と同じアカウントで PR のドラフトを外したとき、sacty が戻さず、作業履歴に1件残る。
  - 懸念：GitHub のタイムラインへの反映が遅れるなど、フェイクと違う振る舞いだと、PR #501 と同じくマージが「まだドラフト」で失敗します。
