# 設計：同じ原因の要修正が続いたときに、範囲を絞る案を添えて人の判断を早める（PBI-492）

## スコープ

同じ原因の `must` が2回目以降なら、レビューは範囲を絞る案を本文に添える。
3回目以降の PR のレビューは、その `must` に `needs_decision` の印を付けて、今ある「直しでは解消できない指摘での一時停止」（PBI-452）で止める。人の指摘が同じ回にあっても止める。
3回目以降のセルフレビューは、報告に人の判断が要ることを書き、タスクの画面のセルフレビューの欄に出す。

- 対象
  - 既定のスキル review-dispatch の `aggregation.md`・`pr-review.md`・`self-review.md`（主対象が `user-doc` のときも含む）
  - `apps/daemon/src/prompts.ts` の再レビュー・セルフレビュー・`needsDecisionLines` の指示
  - `needsDecisionOf` の止める条件、セルフレビューの報告の記録と画面の表示
  - 仕様書（日英）・利用者向け文書（日英）・ADR・作業履歴・テスト
- 対象外
  - PR のレビューの止め方・画面の見出し・PR への知らせの新設（今の `needs_decision` の一時停止をそのまま使う）
  - セルフレビューでの一時停止（画面に出すだけ）
  - 要修正の重さの決め方と、同じ原因の判定の仕方（依頼の範囲の外）

## 確認したいこと

- must
  - Q-1：3回目以降は、今の `needs_decision` の一時停止で止めるか（推奨：止める）。
    理由：人が手で止めていた所を代わりに止められ、画面・PR のコメント・再開の仕組みを足さずに済む。
    懸念：止めずに知らせるだけがよかった場合、承認の代理の人が、3回目のたびに PR のコメントか再開で答えるまでタスクが進まない。
  - Q-2：セルフレビュー（PR の無い工程の中）の3回目以降は、止めずに、タスクの画面のセルフレビューの欄に「人の判断が要ること」として出すだけでよいか（推奨：よい）。
    理由：止める仕組みは PR のレビューの子タスクにしか無い。要求要件・設計は提出の後に承認を待つので、人はその画面で読む。
    懸念：実装の工程では提出の後に PR のレビューへ自動で進むので、人がタスクの画面を開くまで、欄に出たことに気づかない。
- should
  - Q-3：人が一時停止で判断した原因に、後の回で同じ原因が続いたとき、再び印を付けないでよいか（推奨：付けない。今の「人の判断がある指摘には付けない」を同じ原因にも当てる）。
    懸念：人が「直しを続ける」と答えた原因は、その後は何回続いても止まらず、今と同じ往復に戻る。
  - Q-4：人の指摘が同じ回にあっても止める変更を、同じ原因の3回目の印だけでなく、すべての `needs_decision` の印に当ててよいか（推奨：よい。印を見分ける欄を足さずに済む）。
    懸念：PBI-452 の印で、人が PR にコメントした回も止まるようになり、その人は直しを進めるのに画面か PR で再開する手間が増える。
- 確認しないと決めたこと
  - ADR：PBI-424 の ADR の「自動で止めない・通知しない」と、PBI-452 の ADR の止める条件（人の指摘が無い）を変えるので、`docs/adr/README.md` の一部の置き換えの手順で、新しい ADR を足し、2つの ADR を `superseded` にする（手順が決まっている）。
  - 範囲を絞る案を人が選んだ後の扱い：今の `deferredByPerson`（後続に回した指摘を出さない）と `decidedPauseLines`（人が受け入れた止めた指摘を要修正に残さない）で足りるので、仕組みを足さない（受け入れ条件に無い）。
  - `user-doc`：同じ原因が続くことの明示・範囲を絞る案・3回目以降の知らせは当てる。方針の観点（C-17・D-1）の起動と、直し方の案の3項目は、今のとおり当てない（方針を見る観点が無い）。

## 既定で決めたこと

- 3回目の数え方は PBI-424・PBI-465 のまま（`delivered` が `false` の回は数えない）。回数が「少なくとも N 回目」で3に届かないときは印を付けない。
- 3回目の印は、`pr-review.md` と `needsDecisionLines` の「直す量が多い・直し方が決まっていないだけなら付けない」の例外として足す。
- 画面の見出し（「直しでは解消できない指摘があるため一時停止」）と文言 `review.needsDecision` は変えない。理由は印の根拠の文（何回目か・範囲を絞る案）で出す。
- セルフレビューの報告の欄は `needsDecision`（文字列の配列。1件に、原因・何回目か・範囲を絞る案・満たせなくなる条件）にする。無い・空なら今の表示のまま。

## 処理の流れ

1. 再レビューで、同じ原因の `must` が2回目：本文に直し方の案（PBI-424）と、範囲を絞る案と照らした結果を書く。判定は変えない。
2. 3回目以降（PR のレビュー）：同じく書き、その `must` に `needs_decision` を付ける。同じ回に人の指摘があっても、親は直しに入らず、今の仕組みで止まり、PR にコメントし、画面に指摘と根拠を出す。再開の後、人の指摘と残った指摘を一緒に選り分ける。
3. 3回目以降（セルフレビュー）：記録と報告の総評に書き、報告の `needsDecision` に入れる。sacty は `AgentRunCompleted` の `selfReview` に残し、画面のセルフレビューの欄に「人の判断が要ること」として出す。止めない。

## テスト観点

- [TV-1] PR の再レビューの指示に、2回目以降の範囲を絞る案の求めが入る
  - 入力：前回のレビューがある PR のレビューの子タスクの指示と、前回のレビューが無い初回の指示を、prompts.test.ts で組み立てる
  - 期待結果：再レビューの指示には、範囲を絞る案（受け入れる・範囲の外にする・後続に回す、と残る影響）を1つ以上、総評かその指摘の本文に書くことと、承認済みの要求要件・受け入れ条件と照らして満たせなくなる条件を書くことが入り、初回の指示には入らない
- [TV-2] PR のレビューの印の条件に、同じ原因の3回目以降が入る
  - 入力：PR のレビューの子タスクの指示（needsDecisionLines を含むもの）を prompts.test.ts で組み立てる
  - 期待結果：同じ原因の must が3回目以降（delivered が false の回を数えず、「少なくとも N 回目」で3に届かないときを除く）なら needs_decision を付け、根拠の文に何回目かと範囲を絞る案を書くことが入る
- [TV-3] セルフレビューの指示に、範囲を絞る案と3回目以降の報告の needsDecision が入る
  - 入力：2回目以降のセルフレビューの指示を prompts.test.ts で組み立てる
  - 期待結果：2回目以降は範囲を絞る案と照らした結果を報告の summary と記録に書くこと、3回目以降は人の判断が要ることを報告の needsDecision に書くことが入り、「回数で止める・止めない決まりは足さない」は入らない
- [TV-4] 人の指摘と印の付いた要修正が同じ回に取り込まれても止まる

  - 期待結果：ReworkJudged・ChangesRequested を記録せず、TaskPaused（理由 needs_decision）を記録し、人の指摘は pendingReview に残り、再開の後に人の指摘と印の付いた指摘がともに差し戻しに入る
- [TV-5] セルフレビューの報告の needsDecision が記録され、画面に出る
  - 入力：needsDecision に1件を持つ sacty-self-review の報告で工程を終え、その記録と、needsDecision が無い記録で、タスクの詳細のセルフレビューの欄を描く
  - 期待結果：AgentRunCompleted の selfReview と投影の selfReviews に needsDecision が残り、欄の先頭に「人の判断が要ること」と1件の文が、欄を開かなくても見える形で出て、needsDecision が無い記録では今の表示のまま出ない
- [TV-6] 既定のスキルに、範囲を絞る案と3回目以降の規則が書かれている
  - 入力：default-skills.test.ts で aggregation.md・pr-review.md・self-review.md を読む
