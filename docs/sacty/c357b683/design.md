# 設計：ADR・作業履歴のファイル名の日時を、今の UTC の時刻に合わせる

## スコープ

実装・直しの指示に、指示を作った時刻（UTC）と「日時は推測せず、今の時刻を確かめて書く」決まりを入れる。
提出の前の基準とレビューの観点で、足したファイルの記録の日時（ファイル名と、それと対になる本文の日時の欄）が今より後なら直させる。

- 対象
  - 実装・直しの指示（`apps/daemon/src/prompts.ts` の実装の全部の枝）と、`buildPrompt` に時刻を渡す `apps/daemon/src/service.ts`
  - 提出の前に確かめる、レビューの基準（`apps/daemon/src/final-review-criteria.ts`）
  - 既定のコンテキスト：`rules.md` と、レビューの観点 X-1（`viewpoints.md`・`review-execution/references/X-1.md`）
  - 仕様書（日英）、この PR の ADR・作業履歴、テスト
- 対象外
  - main にある未来の日時の ADR（`20261121-1900-…`〜`2100-…`）の名前の直し
  - デーモンが足したファイルの名前を読んで提出を止める検査（確認したいことの must 1）
  - 要求要件・設計・文書作成の工程の指示に時刻を入れること（既定の規則で確かめさせる）
  - 本文の期限・予定日など、記録の日時ではない日時（未来でも直させない）

## 確認したいこと

### must

1. 受け入れ条件 2 を、デーモンの検査ではなく、提出の前の基準と PR のレビューの観点 X-1 で満たしてよいか。
   - 推奨：よい。デーモンの検査にすると、対象のリポジトリごとに違う日時の形とタイムゾーンを決め打ちすることになり、条件 3（汎用のまま）と両立しにくい。
   - 懸念：実装の担当とレビューの担当がどちらも見落とすと、未来の日時の PR が出る（#516 と同じ）。確実に止めたいなら、デーモンの検査に作り直すことになり、基準の実装の作業が無駄になる。

### should

1. 確かめる対象を、条件 2 の ADR に限らず、記録の日時を名前に持つファイル（作業履歴など）の名前と、対になる本文の日時の欄にしてよいか。
   - 推奨：よい。条件 3 で基準と X-1 に ADR の語を書けないので、汎用の文は「記録の日時」で書くほかない。本文のほかの日時は対象外にして、期限・予定日の誤検知を防ぐ。
   - 懸念：ADR だけに絞りたい場合、基準の文と X-1 を書き直し、TV-5・TV-7 の期待する結果も直すことになる。

### 確認しないと決めたこと

- 時刻を入れる工程は、実装・直しだけにする。要求要件・設計・文書作成の工程には、全工程に渡る `rules.md` の決まりで今の時刻を確かめさせる。受け入れ条件 1 が実装・直しだけを挙げているため。

## 既定で決めたこと

- 指示の時刻は `2026-11-21T10:30:00Z` の形（秒まで・UTC）にする。
- `buildPrompt` の `extra` に `now`（ミリ秒）を足し、service は `this.now()` を渡す。渡されないときは `Date.now()` を使い、実装の指示に時刻が必ず入るようにする。
- 未来かを比べる「今」は、提出の直前にコンテナで確かめた時刻にする（指示の時刻は実行の開始の時刻で、長い実行では古くなるため）。
- タイムゾーンは指示では決めず、「リポジトリの決まりに従う」と書く。比べるときは、今の時刻をリポジトリの決まりのタイムゾーンに直してから比べ、決まりが無ければ UTC で比べる（JST の正しい日時を、UTC の今より後と誤って判定しないため）。

## 構成

| 置き場所 | 変更 |
| --- | --- |
| `prompts.ts` | 実装の 5 つの枝（`WORKSPACE_TOOL_LINES` を使う所）に、時刻の行を足す。行は「この指示を作った時刻は `<時刻>`（UTC）。ファイル名・本文に日時を書くとき（ADR・作業の記録など）は推測で決めず、書く直前にコンテナで今の時刻を確かめる（`date -u` など）。タイムゾーンと形はリポジトリの決まりに従う」 |
| `final-review-criteria.ts` | 定数 `FUTURE_TIMESTAMP`（このタスクで足したファイルの、作成・決定・記録の日時として書いたファイル名と対になる本文の日時の欄が、提出の直前に確かめた今の時刻より後。今の時刻はリポジトリの決まりのタイムゾーンに直して比べ、決まりが無ければ UTC）を足し、`FINAL_REVIEW_CRITERIA` と `implementReviewCriteriaLines` の基準に加える。テストの仕組みの有無・`scope` に関わらず入れる |
| `rules.md` | 「作業の範囲」に「日時をファイル名・本文に書くときは、推測せずに今の時刻を確かめる」を足す。ADR・`YYYYMMDD-HHMM` など sacty の docs の決まりは書かない |
| X-1 | 見るものに「差分で足したファイルの、記録の日時として書いたファイル名と対になる本文の日時の欄が、レビューの時点の今より後（今はリポジトリの決まりのタイムゾーンに直して比べ、決まりが無ければ UTC）」を足し、`X-1.md` にチェックポイントを足す。期限・予定日などの日時は見ない |

## 影響範囲

- 仕様書：`docs/spec/tasks-and-steps.md`・`.en.md` の「提出の前のセルフレビュー」の基準の一覧と、実装の指示の時刻。`docs/spec/context.md`・`.en.md` の既定の規則。
- この PR の ADR・作業履歴の名前と本文の日時は、`date -u` で確かめた時刻にする。
- 時刻の行は実行ごとに変わる。指示の全体を固定した値と比べるテストがあれば、時刻を固定する。

## テスト観点

- [TV-1] 通常の実装の指示に、渡した時刻と、日時を推測せず今の時刻を確かめて書く決まりが入る
  - 入力：承認済みの設計があるタスクで、buildPrompt(task, "implement", { now: Date.UTC(2026, 10, 21, 10, 30, 0) }) を呼ぶ
  - 期待結果：指示に「2026-11-21T10:30:00Z」と、ファイル名・本文の日時を推測で決めず書く直前にコンテナで今の時刻を確かめる行が含まれ、時刻の行を外すと落ちる
- [TV-2] 要求要件を省いた実装・テストの仕組みが無い実装・不具合の修正の指示にも、時刻の行が入る
  - 入力：それぞれの枝に入るタスク（設計だけ承認・noTestsReason あり・basis が reproduce）で、同じ now を渡して buildPrompt(task, "implement", …) を呼ぶ
  - 期待結果：どの枝の指示にも「2026-11-21T10:30:00Z」と時刻の行が含まれる
- [TV-3] 直し（指摘を受けたやり直し）の指示にも、時刻の行が入る
  - 入力：人の指摘と AI のレビューの指摘（sacty_review）がある実装のタスクで、now を渡して buildPrompt(task, "implement", …) を呼ぶ
  - 期待結果：指摘の行と並んで、「2026-11-21T10:30:00Z」と時刻の行が含まれる
- [TV-4] service が、実装の実行の指示に、時計（now）の時刻を入れる
  - 入力：daemon-implement の統合テストで、時計の依存を 2026-11-21T10:30:00Z に固定して実装の工程を実行する
  - 期待結果：エージェントに渡した指示に「2026-11-21T10:30:00Z」が含まれ、service が now を渡さないと落ちる
- [TV-5] 提出の前に確かめる基準に、足したファイルの記録の日時が今より後なら直す基準が、比べるタイムゾーンと対象の範囲とともに入る
  - 入力：テストの仕組みがあるタスク・テストの仕組みが無いタスク・pullRequestReview を渡したタスクで、buildPrompt(task, "implement", …) を呼ぶ
  - 期待結果：どの指示の「提出の前に確かめる、レビューの基準」にも FUTURE_TIMESTAMP の語と、記録の日時として書いたファイル名と対になる本文の日時の欄を、リポジトリの決まりのタイムゾーン（決まりが無ければ UTC）に直した提出の直前の今と比べて後なら直す行があり、FINAL_REVIEW_CRITERIA から外すと既存の一覧のテストが落ちる
- [TV-6] 既定の規則が、汎用の形で日時の確かめ方を書いている
  - 入力：apps/daemon/default-context/rules.md の差分
  - 期待結果：「日時をファイル名・本文に書くときは、推測せずに今の時刻を確かめる」旨があり、ADR・YYYYMMDD-HHMM・docs/adr など sacty の docs の決まりの語が無い
- [TV-7] レビューの観点 X-1 が、足したファイルの未来の記録の日時を、比べるタイムゾーンと対象の範囲を決めて見る
  - 入力：viewpoints.md の X-1 の行と review-execution/references/X-1.md の差分
  - 期待結果：差分で足したファイルの、記録の日時として書いたファイル名と対になる本文の日時の欄が、リポジトリの決まりのタイムゾーン（決まりが無ければ UTC）に直したレビューの時点の今より後なら指摘し、期限・予定日などの日時は見ないことが書かれ、sacty・ADR の形の語が無い
- [TV-8] 仕様書（日英）が、時刻の行と新しい基準を書いている
  - 入力：docs/spec/tasks-and-steps.md・.en.md と docs/spec/context.md・.en.md の差分
  - 期待結果：日英の両方に、実装・直しの指示に指示を作った UTC の時刻が入ること、基準の一覧に FUTURE_TIMESTAMP の基準があること、既定の規則が今の時刻を確かめさせることが同じ内容で書かれている
