# 設計：入口を足す・変える変更での、差し替えない実行とテスト（PBI-451）

## スコープ

入口を足す・変える実装では、ビルドした成果物でその入口を差し替えずに1回動かして結果を実装の説明に書かせる。PR のレビューの C-4 では、その記載が無いことと、差し替えたテストだけで確かめた道を指摘させる。

- 対象
  - `apps/daemon/src/prompts.ts` の `implementVerificationLines`（「提出の前の検証」）に、行を1つ足す
  - 既定のコンテキストの `review-execution/references/C-4.md` と、`review-dispatch/references/viewpoints.md` の C-4 の行
  - テスト（`prompts.test.ts`・`default-skills.test.ts`）、`docs/spec/tasks-and-steps.md`（英語の版も）、ADR、作業履歴
- 対象外
  - 新しい観点 ID（C-19 など）。C-4 に足す
  - PR の本文を組み立てる所（`implementDescription` など）と、コンテナに入れる道具

## 確認したいこと

- must：なし
- should
  - 入口の出力の形を変えずに値の誤りだけを直す変更（入口から呼ばれる内部の値の計算の修正など）でも、差し替えない実行を求めるか。推奨：求めない（範囲は下の「入口を変える」の1文）。理由：要求4のとおり、入口を足す・変えない変更に手順を増やさない。差し替えたテストだけの道は、C-4 の (a) がどの変更でも拾う。懸念：内部の修正で入口が本物の環境でだけ壊れる変更（PBI-399 の直し方を内部で変えるなど）は、実装の工程で一度も動かされず、人が PR の版を動かすまで見つからない。
  - 記載が無い指摘と、差し替えない道のテストが無い指摘の重要度は、どれにするか。推奨：NG 例の目安を `should` にする。理由：記載やテストが無くても、変更が壊れているとは限らない。懸念：PBI-399 のような本物でだけ壊れる不具合を人が `must` で止めたいなら、`should` の指摘ではドラフトのままマージされうる。

確認しないと決めたこと

- 並行の PR #506 との競合：確かめない。#506 の変更は prompts.ts の 5600 行目より後（PR の本文）と、tasks-and-steps.md の 1256・1293 行目付近。今回の変更は prompts.ts の 4741 行目付近と、仕様書の 286・1576 行目付近で、重ならない。
- 新しい観点を必須にするか条件付きにするか：新しい観点を足さず、C-4 に足すと決めた。依頼が「どちらでもよい」としていて、C-4 は必須の観点なので、担当が増えず、実行の時間も延びない。

## 既定で決めたこと

- 行は条件を付けず、コードの実装・修正のすべてに出す。文の頭で「入口を足す・変えない変更では何もしない」と言い切る。入口を足したかは、オーケストレーターには判定できないため。
- 「入口を変える」は、入口の外から見える契約（呼び方・引数・出力の形〔項目・型・書式〕・終了コード・既定の振る舞い）を変えることとする。出力の形を変えずに値の誤りだけを直す変更と、契約を変えない内部の変更は含めない。この1文を、足す行と C-4 の (b) の両方に使う。
- 文書だけの依頼（`documentsOnly`）では、この行を出さない。
- 語は「入口」にし、最初に例（CLI のコマンド・道具・API のエンドポイントなど、利用者や呼び出し側が直接使うもの）を添える。前例は C-18・`CAUSE_PROPERTY_TEST_ITEM`。
- C-4 の NG 例4（fake timers を勧める例）は残す。「差し替えたら、本物を通る小さなテストも1本」と1文を足す。

## 構成

- 足す行（`implementVerificationLines`。テストの範囲の行の後）：入口を足す・変える変更だけが対象（「入口を変える」の範囲は上の1文）。ビルドした成果物（ビルドが無ければ配る形のまま）で、その入口を時計・タイマー・通信などを差し替えずに1回以上動かす。動かした入口・動かし方・結果を実装の説明に書く。差し替えたテストの実行は、これに数えない。作業領域で動かせなければ理由を書く。
  - 外部への書き込み・削除・送信・課金を伴う入口と、本番の資源に触れる入口は動かさず、その理由を書く。外部を読むだけの通信は、ダミーの値で動かすか、その1回の実行にだけ認証情報を外して動かす。外せなければ動かさず、理由を書く。
  - 外し方：環境変数は、その実行の子プロセスでだけ外すか空にする。設定ファイルは、設定の置き場所を指す環境変数を空の一時ディレクトリに向けて読ませない。作業領域の外にある認証情報のファイルの実物は、移さない・消さない・読まない。
  - 動かし方（コマンド行・URL・環境変数）と結果のどちらにも、トークン・認証ヘッダーなどの秘密の値を書かない。
  - この関数は `implementSelfReviewLines` だけから呼ばれる。direct・要求要件／設計あり・不具合の修正・PR のレビューの子タスクがレビューする回の、どの経路にも出る。
- C-4.md
  - 確かめる手順に 6 を足す。(a) 差し替え（時計・タイマー・乱数・通信・ファイルシステムなど）をしたテストだけで確かめた道を数え、差し替えない道を通る小さなテストが無ければ指摘する。差し替えた部品が返す値の形（型・範囲・精度・単位）は、本物と違いうる。その境目は、差し替えたテストでは通らないので見落とされる、と理由を書く。(b) PR の本文が渡されたとき、入口を足す・変える変更（範囲は足す行と同じ1文）で、差し替えない実行の結果か、動かせなかった理由の記載が無ければ指摘する。渡されないとき（自己レビュー）は (b) を行わない。
  - チェックポイントの「モックが実装を置き換えすぎ」の隣に「差し替えの境目」を足す。
  - NG 例7（言語を明記）：差し替えた時計は整数を返し、本物の時計は小数を返す。その値を、整数しか受けない待ち時間の引数に渡す。差し替えたテストだけが通る。
- viewpoints.md：C-4 の「見るもの」に、差し替えたテストだけの道と、入口を足す・変える変更での差し替えない実行の記載を足す。段階・必須か条件付きかは変えない。
- docs/spec/tasks-and-steps.md の 286 行目付近（`implementVerificationLines` の説明）に、足した行の要約を足す（英語の版も）。ADR を1つと、作業履歴 `docs/worklog/20261121-pbi-451-<スラッグ>.md` を足す。

## テスト観点

  - 入力：steps が implement だけで documentsOnly の無いタスクで、buildPrompt(task, "implement") を組み立てる
  - 期待結果：「--- 提出の前の検証 ---」の節の1つの行に、入口を足す・変える変更だけが対象で足さない・変えない変更では何もしないこと、「入口を変える」は入口の外から見える契約（呼び方・引数・出力の形〔項目・型・書式〕・終了コード・既定の振る舞い）を変えることで、出力の形を変えずに値の誤りだけを直す変更と契約を変えない内部の変更は含めないこと、ビルドした成果物（ビルドが無ければ配る形のまま）で時計・タイマー・通信などを差し替えずに1回以上動かすこと、動かした入口・動かし方・結果を実装の説明に書くこと、差し替えたテストの実行は数えないこと、動かせなければ理由を書くこと、外部への書き込み・削除・送信・課金を伴う入口と本番の資源に触れる入口は動かさず理由を書くこと、外部を読むだけの通信はダミーの値か、その1回の実行にだけ認証情報を外して動かし（環境変数は子プロセスでだけ外すか空にし、設定ファイルは設定の置き場所を指す環境変数を空の一時ディレクトリに向ける）、作業領域の外の認証情報のファイルの実物は移さない・消さない・読まないこと、外せなければ動かさず理由を書くこと、動かし方と結果のどちらにも秘密の値を書かないことが書かれている

  - 入力：reproduce を done にした不具合の修正のタスク、requirements・design を done にしたタスク、PR のレビューの子タスクがレビューする（セルフレビューを省く）タスクで、それぞれ implement の指示を組み立てる

  - 期待結果：PR の本文が渡されたとき、入口を足す・変える変更（実装の行と同じ、入口の外から見える契約〔出力は形〕を変えるという範囲の文で、出力の形を変えずに値の誤りだけを直す変更を含めない）で、差し替えない実行の結果か動かせなかった理由の記載が無ければ指摘すること、渡されないとき（自己レビュー）はこの確かめを行わないこと、入口を足す・変えない変更では何もしないことが書かれている
