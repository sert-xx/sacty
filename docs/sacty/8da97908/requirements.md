# 要求要件：実時間の経過に上限・下限を置くテストを、時間に頼らない検査に直す

## スコープ

テストの中で、かかった実時間に上限・下限を置いて合否を決める検査を洗い出し、CI の機械の遅さで落ちない検査に直す。
直した後も、元の検査が確かめていたこと（固まらない・期限で止まる・線形の時間で終わるなど）は確かめ続ける。

- 対象
  - `Date.now()`・`performance.now()` の差に上限・下限を置く検査（20 ファイル・29 件。`host-mcp.test.ts:683` の下限 45ms と `remark-line.test.ts:105` を含む）と、S-1 で含める 2 件（計 31 件）
  - テストのために本体に足す、時計・期限の差し込み口
  - 作業履歴（`docs/worklog/YYYYMMDD-pbi-473-<スラッグ>.md`）の一覧
- 対象外
  - CI の `--no-file-parallelism` を外すこと（テストを速くすることは範囲外のため）
  - 本体の時間切れの値の見直し

## 確認したいこと

### must

- **M-1 線形の時間を見る検査（約 20 件）の直し方**：推奨は、経過時間の検査を外し、入力の大きさを「2 乗の時間に戻した版はそのテストの時間切れ（既定 5 秒）で落ち、通常の版は R-9 の負荷下でもその時間切れの 5 分の 1 未満で終わる」大きさに合わせること。
  理由：入力の長さと時間の関係は、偽の時計・合図・回数では確かめられず、比で見る案も実時間に頼るため。
  懸念：ほかの答え（処理の回数を本体で数える、など）が望みなら、20 件の直し方と本体の差し込み口の設計が全部やり直しになる。

### should

- **S-1 範囲の境目のものを含めるか**：推奨は、`daemon-implement.test.ts:4157` の 3 秒の `Promise.race` と、同じテストの PBI-430 の 800ms の前提を含め、`wait.test.ts:70` の `testTimeLeftMs`・`github.test.ts:1293` の `githubRetryAfterMs`・固定の待ちは含めないこと。
  理由：前の 2 つは遅い機械で落ちうるが、後の 3 つは遅くなるほど通りやすいか、実時間の経過を測っていない。
  懸念：含めないまま進めると、`daemon-implement.test.ts` が遅い CI で落ち、次のタスクの CI を読む人がまた切り分けに時間を使う。
- **S-2 `audit-causes.test.ts:606` の「最初の原因が出るまで 2 秒以内」**：推奨は、2 秒を要件ではなく固まらないことの目安と見て時間の検査を外し、同じテストのボタンの数・ページの大きさの検査で「提案の数に比例しない」ことを確かめ続けること。テスト名の「2 秒以内」も外す。
  懸念：2 秒が画面の要件なら、要件を確かめるテストが無いまま PR がマージされる。
- **S-3 本体を壊して落ちることを確かめる検査と、負荷のかけ方**：推奨は、`host-mcp.test.ts:648`・`host-mcp.test.ts:683`・`daemon-context.test.ts:392`・`daemon-steps.test.ts:497`・`redact.test.ts:82` の 5 件で壊し、CPU のコア数と同じ数の CPU を使い切るプロセスを並べて全件を 5 回流すこと。
  懸念：壊す検査の選び方が違えば、実装の後で確かめ直す手間が要る。
- **S-4 線形の検査の 2 乗版の実測を、約 20 件すべてで行うか**：推奨は、すべてで行う（R-11）。依頼の「主な数件で壊す」より広い。
  理由：測らないと、S-3 の 5 件のほかは、入力が 2 乗への退行を捕まえる大きさかを誰も確かめられない。
  懸念：数件に絞りたいなら、R-11 の実測の手間（約 20 件ぶん本体を壊して測る）が実装に余分にかかる。

### 確認しないと決めたこと

- 件数：依頼の「約 25 件」でなく、grep で見つけた 29 件を対象にする（受け入れ条件 1 が「リポジトリ全体から洗い出す」と決めているため）。
- 本体に時計の差し込み口を足すか、テストの中で偽の時計・`AbortSignal.timeout` の差し替えを使うか：設計で検査ごとに決める（受け入れ条件 3 がどちらも認め、どちらでも R-5・R-6 は変わらないため）。

## 既定で決めたこと

- M-1 の通常の版の余裕を、負荷下で時間切れの 5 分の 1 未満とした（負荷下で 5 秒に近づいて落ちないため）。

## 受け入れ条件

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | 作業履歴 | 洗い出しの検索の条件（時刻の差・`elapsed` などの変数を経由する差・`setTimeout` との競争・`waitFor` の期限など）と、対象の検査ごとに、ファイル・テスト名・今の閾値・直し方を 1 行で載せる |
| R-2 | 作業履歴 | 時間に頼らない検査に置き換えなかったものごとに、置き換えられない理由と、余裕を広げたか外したかを載せる |
| R-3 | テスト | R-2 に載せて余裕を広げたもの以外に、実時間の経過に上限・下限を置く検査を含まない（Vitest のテストの時間切れは、この検査に数えない） |
| R-4 | 本体（テストでないコード） | 差し込み口の追加のほかに、変更を含まない |
| R-10 | 置き換えた検査 | 作業履歴の直し方に書いた「元の検査が確かめていたこと」を、書いた代わりの手段で確かめる |
| R-11 | 作業履歴 | 線形の時間を見る検査ごとに、2 乗に戻した版と通常の版（R-9 の負荷下）の実測の時間を載せ、M-1 の大きさの条件を満たす |
| R-12 | 作業履歴 | R-6 で壊した検査ごとに、壊した本体の箇所と、落ちたテスト名を載せる |

## 受け入れの確かめ方

### 自動のテストで確かめること

- R-6〜R-9：作業領域でコマンドを実行して確かめる。R-6 は、壊した差分を戻してから R-7 を流す。
- R-3：R-1 に載せた検索の条件でリポジトリを検索し直し、残った一致が R-2 の一覧と一致することを確かめる。
- R-1・R-2・R-4・R-5・R-10〜R-13：差分と作業履歴を読んで確かめる。作業履歴の形は `tests/docs/docs.test.ts` が確かめる。
