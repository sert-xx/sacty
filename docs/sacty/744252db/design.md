# 設計：作業履歴を最初の提出で漏れなく書けるようにする（PBI-483）

## スコープ

作業履歴のひな形とスキルに、最初の提出で5つの型を満たす書き方を足す。
5つの型は、コマンドと結果・実行しなかった検証の理由・回ごとの指摘と対応・残したこと・PR の番号の5つ。
ひな形の節の有無は、docs のテストで確かめる。

- 対象
  - `docs/worklog/README.md`（ひな形と書き方の規則）
  - sacty-docs スキルの2つの写し（`.claude/skills/sacty-docs/SKILL.md`・`.agents/skills/sacty-docs/SKILL.md`）の「作業履歴」の項
  - `CONTRIBUTING.md`「ドキュメント」の作業履歴の1行
  - `tests/docs/docs.test.ts`（ひな形の節の検査を1つ足す）
  - このタスクの作業履歴 `docs/worklog/<PR を作った日>-pbi-483-<スラッグ>.md`
- 対象外
  - 実データの作業履歴（過去のファイルとこれから足すファイル）への節の検査
  - `docs/README.md`「作業履歴（worklog/）」の方針の文（書く内容の4点は今のままで足りる）
  - `apps/daemon/default-context/`、過去の作業履歴

## 確認したいこと

### must

なし

### should

1. 節の検査を、ひな形だけでなく、これから足す作業履歴（日付で区切る）にも課すか。
   - 推奨：ひな形だけに課す。依頼は「ひな形の節の有無」と書いている。新しいファイルにも課すと、これからのすべてのタスクを CI が縛る新しい決まりになる。
   - 懸念：節を落とした新しい作業履歴も CI を通る。漏れを見つけるのは今と同じく PR のレビューになり、直しの回が残ることがある。
2. 「レビューの指摘と対応」を、回ごとの小見出し（`### 設計の PR #<番号>`・`### この PR の 1 回目`）で分けてよいか。
   - 推奨：小見出しで分ける。#551 では前の工程の PR の分とこの PR の分が1つの表に混ざり、前回の指摘への対応が読み取れなかった。
   - 懸念：表の列（「回」）で分けたいなら、ひな形・スキル・このタスクの作業履歴を書き直すことになる。

### 確認しないと決めたこと

- 最初の提出の「レビューの指摘と対応」：前の工程（要求要件・設計）の PR の指摘があれば書く。この PR の分は「まだ無い（最初の提出）」と書く。受け入れ条件1で、この節を必ず置くと決まっているため。
- 前の工程の PR の指摘とこの PR の指摘：小見出しで分ける（should 2 と同じ形）。#551 への提案が、分けることを求めているため。
- ひな形に無い独自の節：5つの節を消さず、順も変えなければ、足してよいと明記する。過去のファイルに例が多く、禁じる根拠が依頼にも文書にも無いため。

## 既定で決めたこと

- 「確かめたこと」は表にする。`CONTRIBUTING.md`「PR を出す前に確かめること」の4つのコマンドを1行ずつ並べ、結果（成否・件数）か、実行しなかった理由を書く。
- 規則に2つの禁止を書く。実行しなかった理由に「手順に無い」と書かない。PR の本文を指すだけで済ませない。
- `CONTRIBUTING.md` は1行だけ直し、作業履歴に書く5つの中身と、ひな形が正本であることを書く。

## 構成

| ファイル | 変えること |
| --- | --- |
| `docs/worklog/README.md` | 次の5点を直す。<br>・「確かめたこと」を表（`コマンド \| 結果`）にし、build の行の例を置く。<br>・「レビューの指摘と対応」を回ごとの小見出しにする。<br>・「残したこと」は、無くても「なし」と書いて節を残すと書く。<br>・`PR` の欄の規則に書き足す。sacty では実装の工程の後に PR ができるので、最初の提出は `なし` にする。PR を作った後の提出（レビューへの対応の回）で `#<番号>` を書き足す。<br>・独自の節の扱いを書く。 |
| スキルの2つの写し | 「PR を出す前に確かめること」の4を直し、5つの中身とひな形へのリンクを書く。5つは、コマンドと結果・実行しなかった検証と理由・回ごとの指摘と対応・残したこと・PR の番号を後で書き足すこと。2つの写しは同じ内容にする。 |
| `CONTRIBUTING.md` | 「ドキュメント」の作業履歴の行に、5つの中身とひな形へのリンクを書く。 |
| `tests/docs/docs.test.ts` | ひな形のコードブロックを検査する。`## ` の見出しが `目的`・`したこと`・`確かめたこと`・`レビューの指摘と対応`・`残したこと` の順にあり、`- PR: #<番号> \| なし` の行があることを確かめる。 |

## テスト観点

- [TV-1] ひな形の「確かめたこと」に、コマンドと結果の書き方がある
  - 入力：変更後の docs/worklog/README.md のひな形と規則
  - 期待結果：CONTRIBUTING.md の4つのコマンド（lint・typecheck・vitest・build）を1行ずつ、結果（成否・件数）か実行しなかった理由で書く表と、PR の本文を指すだけにしないことが書かれている
- [TV-2] 実行しなかった検証の理由の書き方がある
  - 入力：変更後の docs/worklog/README.md の「確かめたこと」の説明
  - 期待結果：実行しなかった検証（例 npm run build）とその理由を書くこと、build は CONTRIBUTING.md の手順にあるので理由に「手順に無い」と書かないことが書かれている
- [TV-3] 「レビューの指摘と対応」を回ごとに書く書き方がある
  - 入力：変更後の docs/worklog/README.md のひな形と規則
  - 期待結果：前の工程の PR とこの PR の回ごとに小見出しで分けること、最初の提出ではこの PR の分を「まだ無い（最初の提出）」と書くこと、後の回で前回の指摘ごとの対応を書き足すことが書かれている
- [TV-4] 「残したこと」を必ず置く規則がある
  - 入力：変更後の docs/worklog/README.md
  - 期待結果：「残したこと」の節は消さず、無ければ「なし」と書くことが書かれている
- [TV-5] PR の番号を後の提出で書き足す前提がある
  - 入力：変更後の docs/worklog/README.md の先頭の項目の書き方
  - 期待結果：sacty では実装の工程の後に PR ができるので最初の提出では番号が分からず PR を なし にすること、PR を作った後の提出で #<番号> に書き足すことが書かれている
- [TV-6] スキルの2つの写しが5つの中身を挙げ、一致する
  - 入力：変更後の .claude/skills/sacty-docs/SKILL.md と .agents/skills/sacty-docs/SKILL.md の「作業履歴」の項で npx vitest run tests/docs を実行する
  - 期待結果：両方の項に5つの中身とひな形へのリンクが書かれ、「2つの写しが同じ内容である」のテストが通る
- [TV-7] CONTRIBUTING.md の作業履歴の行が5つの中身を挙げる
  - 入力：変更後の CONTRIBUTING.md「ドキュメント」の節
  - 期待結果：作業履歴の行に、5つの中身とひな形（docs/worklog/README.md）へのリンクが書かれている
- [TV-8] ひな形の節の検査が、節の欠けと順の違いで失敗する
  - 入力：足したテストに、ひな形から「残したこと」の見出しを消した本文と、「残したこと」と「レビューの指摘と対応」の順を入れ替えた本文を渡す
  - 期待結果：どちらも検査が失敗し、変更後の docs/worklog/README.md では npx vitest run tests/docs が通る

  - 期待結果：docs/worklog/ の差分は README.md とこのタスクの作業履歴の追加だけで、既存の作業履歴のファイルは変わっていない
