# 要求要件：要求要件・設計の PR で「提案あり」の直しと再レビューを打ち切る（PBI-481）

## スコープ

要求要件・設計の PR で、提案だけの判定が続いたら、自動の直しに入らずに人の承認を待つ。
要修正と人の指摘では、今までどおり直しに入る。

- 対象
  - デーモンの、要求要件・設計の PR のレビューの判定を受けた後の扱い（実装の工程が無い進め方の PR も含む）
  - 打ち切った後の知らせ（承認の画面・タスクの概要と作業履歴。日英）
  - 仕様書（`approval`・`event-log`）とユーザー文書（`tasks`・`intake`）の日英、ADR、作業履歴
- 対象外
  - 実装の PR の選り分けと打ち切り（PBI-440 の振る舞い）
  - レビューの観点と、提案の出しやすさ
  - 自動の直しの間に人がマージしたら承認として扱う、今の振る舞い

## 確認したいこと

### must

- 打ち切りの規則を「提案だけの判定が 2 回続いたら、2 回目は直さずに人の承認を待つ」にし、実装の PR の AI の選り分けは使わなくてよいか。
  推奨：はい。選り分けの担い手・判定し直し・ドラフトは実装の PR が前提で、広げる範囲が大きいため。#556・#560 は 2 回目の判定で収まっている。
  懸念：選り分けを望んでいたなら、R-1・R-2・テスト・ADR を作り直すことになり、設計と実装の作業が無駄になります。

### should

- 要修正の後と、人の指摘による直しの後に出た提案だけの判定は、1 回目として数え直し、直しを 1 回するか。
  推奨：はい（R-2）。直した中身への提案を 1 回は取り込むため。
  懸念：人の指摘の後は直さずに止めたかったなら、人が差し戻すたびに 1 往復（数分〜十数分）余計にかかります。
- 人が PR に直接コミットした後の再レビューで提案だけが出たとき、数え直さずに続けて数えるか。
  推奨：はい。人の編集を AI の直しが書き換えないようにするため。
  懸念：数え直したかったなら、人のコミットの後に、人の承認を待たずに 1 往復回ります。
- 「ドラフトを外して」は「直しに入らない承認待ちにする」と読み、要求要件・設計の PR をドラフトで作る変更はしなくてよいか。
  推奨：はい。今の要求要件・設計の PR はドラフトで作っておらず（#554・#561）、外すドラフトが無いため。
  懸念：自動の直しの間はドラフトにして、人に途中でマージさせないことを望んでいたなら、PR の作り方を変える作業が追加で要ります。

### 確認しないと決めたこと

- 人の承認待ち・回数で止める形：採ってよいと決めた。PBI-436 の ADR は実装の PR について採らなかったが、依頼の受け入れ条件 1 が例に挙げているため。理由の違いは新しい ADR に書く（R-10）。
- リスク評価：打ち切った回にも付けない。PBI-440 の ADR とユーザー文書が、要求要件・設計の PR に評価を付けないとしているため。
- 記録の形（新しい記録を足すか、今の記録を広げるか）：設計で決める。要求は R-5・R-6 に見せる中身で決まるため。
- 「設計の PR で 5 回」の数え方：確かめない。打ち切りの規則の判断に影響しないため。

## 既定で決めたこと

- 打ち切りの知らせは、実装の PR の「提案が残っている」の知らせと同じ場所（承認の画面・タスクの概要）に出す。
- 届かなかったレビューの回は、提案だけの回に数えない（実装の PR の数え方と同じ）。

## 要求

### イベント駆動

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-1 | 要求要件・設計の PR で、提案だけの判定が、前の回の提案だけの判定に続いて出たとき（間に要修正・人の指摘による直しが無い） | デーモン | 直しを始めず、タスクを人の承認待ちにする |
| R-2 | 要求要件・設計の PR で、提案だけの判定が 1 回目（初回、または要修正・人の指摘による直しの後の最初の回）に出たとき | デーモン | 直しを 1 回始める |
| R-3 | 要求要件・設計の PR で、要修正（`needs_decision` の印なし）の判定が出たとき | デーモン | 前の提案だけの回の数によらず、直しを始める |
| R-4 | R-1 で打ち切った PR に、人が要対応とコメントした・画面から差し戻したとき | デーモン | 直しを始める |
| R-5 | R-1 で打ち切ったとき | Web 画面 | 承認の画面とタスクの概要に、提案が残っていること・再レビューしていないこと・直させる方法（PR に要対応とコメントする・画面から差し戻す）を日英で出す |
| R-6 | R-1 で打ち切ったとき | Web 画面 | 作業履歴に、提案だけの判定が続いたため直しに入らなかったこと・提案が残っていること・直させる方法（PR に要対応とコメントする・画面から差し戻す）を示す行を 1 行、日英で出す |

## 受け入れの確かめ方

### 自動のテストで確かめること

- R-1〜R-4・R-7：合成のレビューの判定で、次の境界ごとに直しを始めるかを確かめる。打ち切りの変更を戻すと落ちる。
  - 初回の提案（直す）・2 回続いた提案（直さない）・要修正の後の提案（直す）・人の指摘の後の提案（直す）・人のコミットの後の提案（続けて数える）・打ち切りの後の要修正と人の指摘（直す）・打ち切りの後の再起動（直さない）
- R-5・R-6：打ち切った状態のタスクで、画面の知らせと、作業履歴の行（直しに入らなかったこと・提案が残っていること・直させる 2 つの方法を含む）を日英で確かめる。
- R-8：今の `daemon-suggestion-triage.test.ts` などの選り分けのテストが変えずに通る。
- R-9〜R-11：差分で、各文書に要求の記述があることを確かめる。`tests/docs` が通る。
- `npm run lint`・`npm run typecheck`・`npm test` が通る。
