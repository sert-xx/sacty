# PBI-436 AI のレビューの提案を、直しに入る前に選り分ける

## スコープ

sacty が作った実装の PR で、AI のレビューの提案を、直しに入る前に AI が 1 件ずつ「この PR で対応する／対応しない」に分ける。
対応しない提案は PR に理由を返信するだけにし、後の再レビューが蒸し返さないよう、毎回データとして渡す。

- 対象
  - 取り込みの後の選り分けの実行と記録（`service.ts`・`prompts.ts`・core のイベントと投影・作業履歴の表示）
  - 直しに入らないときの返信と、同じ先頭の判定のし直しの開始
  - 再レビューの指示（`rereviewLines`・`rejudgeLines`）、直しの指示、既定のスキル `pr-review.md` の再レビューの決まり
  - 仕様書・ユーザードキュメント（日・英）、ADR、作業履歴、結合のテスト
- 対象外
  - 要求要件・設計の PR の AI のレビュー（判定のし直しと `ReviewDeferrals` が実装の PR だけの仕組みのため）
  - 実装が直しの中で申告する `declined`・`deferred` と人の決定の手順、返信の組み立て（`remark-reply.ts`）の形
  - 集約が対応済み・却下済みと重なる指摘を弾く決まり

## 既定で決めたこと

- 提案の単位：デーモンが、AI のレビューの本文を行頭の `[提案]` で 1 件ずつに分ける（行へのコメントは 1 件で 1 つ）。`[提案]` の頭の無い文・`[要修正]` は選り分けない（直す側に倒す）。
  - 分け方は、実際に投稿されるレビューの形で決める（承認のときに足した）。本文の「指摘」の節の指摘は、太字の見出し（`**[提案] 題**（場所）` の形）で始まり、行へのコメントは、目印の HTML コメントの後に `[提案]` が続く。行頭の素の `[提案]` だけを探さない。総評・「前回の指摘」の節の文中に出る `[提案]`（件数や状況の説明）は、提案の 1 件として数えない。分け方のテスト（TV-2）は、既定のスキルが決める書式どおりの本文と行へのコメントで確かめる。
  - 同じ指摘が、本文の「指摘」の節と行へのコメントの両方に出ることがある。選り分けの材料に両方を渡し、同じ指摘には同じ判断を付けさせる（片方だけが対応する・もう片方が対応しない、にならない。食い違ったら対応する側にそろえる）。
- 承認のときの決定：should 1 は推奨どおり（返信した後に一時停止し、人が選ぶ。新しい文言で知らせる）。should 2 は推奨どおり（実際の時刻）。
- 選り分けは、PR の工程のエージェントの新しい実行（role `triage`、実装後のコードの読み取り専用の写し、代わりのエージェントでのやり直し付き）。人の指摘が混ざる回も、戻し先の判断とは別の実行にする。
- 迷うときの倒し方：その PR で提案だけの回が続いていなければ「対応する」、続いていれば（2 回目以降）「対応しない」。
- 対応しないとした提案を再レビューに渡す上限は、`deferredByPerson` と同じ 50 件・1 件 600 文字（切ったら印を付ける）。
- 選り分けの費用は、`event-log.md` の費用の表に「提案の選り分け」の行を足して数える。

## データ

- イベント `SuggestionsTriaged`（actor `agent`）：`items[]`（`id`・`remark` の位置・提案の文・`decision`（`address`/`decline`）・`reason`・`defaulted`）、`runResult`・`agentId`・`runId`・`usage`・`costUsd`。
- 投影
  - `pendingReview.triage`：記録済みなら、起動し直しても選り分けを実行し直さない。
  - 提案がすべて対応しない指摘は、`pendingReview` から外し、`Task.remarks` に `status: declined`・`triaged: true`・`origin` 付きで足す。残らなければ `pendingReview` を消す。
  - 一部だけ対応しない指摘は、`pendingReview` に残し、対応しない提案を指摘に付けて持つ（直しの指示と返信に使う）。
  - `Task.declinedSuggestions[]`（提案の文・理由・元の URL・回）：消さずに積む。
- `awaitingRemarkReplies`：`triaged` の指摘は、提出の回によらず、次の承認待ちで返信する。一部だけ対応しない指摘は、実装の対応の後ろに、対応しない提案と理由を足す。
- 返信に足す文：「直しに入る前に AI が判断し、この PR では対応しません。直させたいときは、PR に要対応とコメントしてください。」

## 処理の流れ

1. 取り込み（`importFeedbackNow`）の後、`pendingReview.triage` が無く、AI のレビューの提案が 1 件以上あれば、選り分けを実行する。
   - 材料：タスクの依頼・受け入れ条件・承認済みの要求要件と設計・PR の説明、今回の指摘、前の回の指摘と対応（`Task.remarks`）、`declinedSuggestions`、レビューの回、提案だけの回が続いた数（子タスクの `reviewVerdicts`）。
   - 基準：AC2 の対応する・対応しないの基準と、上の倒し方を指示に書く。
2. `SuggestionsTriaged` を記録する。指摘が残らなければ、同じ追記に `ReviewRejudgeRequested`（`reason: triaged`）を入れ、直しに入らない。
3. 指摘が残れば、今の戻し先の判断（`judgeRework`）と差し戻し（`settleReview`）に進む。直しの指示には、対応しない提案を「この PR では直さず、対応も書かない」として載せる（`ownerDeferralLines` と同じ形）。
4. 返信が済むと、今の `rejudgeDue` で子タスクが同じ先頭を 1 回だけ判定し直す。
5. 再レビューの指示：毎回、`declinedSuggestions` を `declinedByAuthor` としてデータに渡す。「前回の指摘」の節は「対応を確かめた／未対応／PR を作った側が対応しないと判断した」の三択にする。対応しないとした提案は、未対応に数えず、もう一度指摘せず（同じ原因の別の現れとしても）、判定の根拠にしない。要修正の重さと確かめたとき・影響が大きくなったときだけ、根拠付きで `[要修正]` にする。`rejudgeLines` の「取り下げるのは当たらないときだけ」は、実装が断った指摘だけに当てる。
6. 判定のし直しの回が `[要修正]` を出せば、一時停止せずに直しに入る。提案だけを残せば 1 に戻り、すべて対応しないなら返信して一時停止する（should 1）。

## エラー時の振る舞い

- 実行の失敗・答えを読めない・判断の無い提案：その提案を `address`・`defaulted: true` として記録し、直しに入る。
- 選り分けの間に人が差し戻した・指摘が変わった：`ReworkJudged` と同じく記録しない。止めるための中断は、費用だけを `runResult: interrupted` で残す。

## 影響範囲

- `Task.remarks` に、直しを経ない指摘が入る。差し戻しの回数・直しの指示の前の回の指摘・画面の指摘の一覧が、`triaged` の指摘を直しの対象に数えないようにする。
- 作業履歴（`apps/web` の labels）：`SuggestionsTriaged` の行に「提案 N 件のうち M 件をこの PR で対応しない」、詳細に提案ごとの判断と理由、費用を出す。

## テスト観点

- [TV-1] 選り分けの指示に、判断の材料と基準と倒し方が入る
  - 入力：依頼・受け入れ条件・承認済みの要求要件と設計・PR の説明・前の回の指摘と対応・declinedSuggestions があり、提案だけの回が 2 回続いた実装の PR で、選り分けの指示を組み立てる
  - 期待結果：指示に、それぞれの材料・今回の提案の一覧（id 付き）・レビューの回と提案だけの回の続いた数、AC2 の対応する・対応しないの基準、回が進むほど敷居を上げること、迷ったら（提案だけの回が続いているので）対応しない側に倒すことが含まれる
- [TV-2] 提案の単位の分け方
  - 入力：本文に行頭の [要修正] 1 件・[提案] 3 件を含む AI のレビューの本文と、[提案] の行へのコメント 1 件と、頭の無い行へのコメント 1 件を取り込む
  - 期待結果：選り分けの対象は、本文の [提案] 3 件と [提案] の行へのコメント 1 件の計 4 件だけで、[要修正] と頭の無いコメントは対象にならず差し戻しの指摘に残る
- [TV-3] 提案だけの回ですべて対応しない（結合）
  - 入力：偽の GitHub で、子タスクの判定が suggestions の AI のレビューを取り込み、選り分けの答えがすべて decline
  - 期待結果：実装の実行・コミット・push が起きず、各元の投稿に「対応していません。理由：」と AI の判断である旨と要対応のコメントで直せる旨の返信が 1 通ずつ投稿された後、子タスクに同じ先頭の ReviewRestarted が 1 回記録され、その回の指示に declinedByAuthor と未対応に数えない文が入り、指摘なしの判定でドラフトが外れリスク評価が出る
- [TV-4] 一部だけ対応する
  - 入力：提案 3 件のうち 1 件を address、2 件を decline とする答えで、直しの後に PR が更新されて再レビューが始まる
  - 期待結果：直しの指示の対応の対象は address の 1 件だけで、decline の 2 件は「この PR では直さず、対応も書かない」の節にあり、再レビューの指示のデータの declinedByAuthor に 2 件が入る
- [TV-5] 1 つの本文に対応する提案と対応しない提案が混ざるときの返信
  - 入力：1 つの AI のレビューの本文の [提案] 2 件のうち 1 件を address、1 件を decline とし、実装が addressed で提出する
  - 期待結果：その本文への返信は 1 通だけで、実装の対応の後ろに、対応しない提案の文と理由と AI の判断である旨が続き、目印・書き出し・署名・秘密情報の伏せ・4,000 文字の上限・@ の扱いは今の返信と同じ
- [TV-6] 要修正と提案が混ざる回
  - 入力：子タスクの判定が changes_required で、本文に [要修正] 1 件と [提案] 2 件があり、提案 2 件がともに decline
  - 期待結果：直しに入り、指示の対応の対象に [要修正] の指摘が必ず入り、提案 2 件は対応を求めない節に入る
- [TV-7] 人の指摘と AI のレビューの指摘が混ざる回
  - 入力：人のコメント 1 件と、[提案] だけの AI のレビューの本文を同じ回に取り込み、提案がすべて decline
  - 期待結果：人の指摘は選り分けの対象にならず、今までどおり judgeRework の実行で戻し先と noAction が判断されて直しに入る
- [TV-8] 人が要対応とコメントして覆す
  - 入力：提案をすべて対応しないとして返信した後に、人が PR にその提案を直すよう求めるコメントを書く
  - 期待結果：人の指摘として取り込まれ、選り分けを通らずに直しに入る
- [TV-9] 選り分けの実行の失敗・読めない答え
  - 入力：選り分けの実行が失敗する場合と、答えの JSON を読めない場合
  - 期待結果：どちらも、すべての提案が address・defaulted として SuggestionsTriaged に記録され、今までどおり直しに入る
- [TV-10] 一部の提案に判断が無い答え
  - 入力：提案 3 件のうち 2 件にだけ decline の判断がある答え
  - 期待結果：判断の無い 1 件は address・defaulted として記録されて直しの対象になり、2 件は対応しない提案として扱われる
- [TV-11] 判定のし直しの回が要修正を出す
  - 入力：すべて対応しないとした後の同じ先頭の判定のし直しで、子タスクが [要修正] を含む changes_required を出す
  - 期待結果：一時停止せずに直しに入る
- [TV-12] 判定のし直しの回が提案を残し、それもすべて対応しない
  - 入力：同じ先頭の判定のし直しで、子タスクが提案だけを残し、選り分けがすべて decline
  - 期待結果：理由が返信され、2 回目の判定のし直しは始まらず、タスクは提案が残った旨の文言で一時停止する

  - 入力：1 回目の後に提案 A を decline、2 回目の後に提案 B を decline とし、PR を更新した 3 回目と 4 回目の再レビューの指示を組み立てる
  - 期待結果：3 回目と 4 回目の両方で、declinedByAuthor に A と B の文・理由・元の URL が入る（authorReplies に A が無くても入る）
- [TV-14] declinedByAuthor の件数と長さの上限
  - 入力：対応しないとした提案が 51 件あり、そのうち 1 件の文が 601 文字
  - 期待結果：指示のデータには 50 件だけが入り、長い 1 件は先頭 600 文字で切られて切った印が付く
- [TV-15] 再レビューと判定のし直しの指示の文
  - 入力：declinedByAuthor のある、通常の再レビューと、同じ先頭の判定のし直しの回の指示を組み立てる
  - 期待結果：どちらも、「前回の指摘」の節に PR を作った側が対応しないと判断したと書くこと、未対応に数えず・同じ原因の別の現れとしても再指摘せず・判定の根拠にしないこと、要修正の重さと確かめたとき・影響が大きくなったときだけ根拠付きで要修正にすることが書かれ、「取り下げるのは当たらないときだけ」と「対応を確かめた／未対応」の二択の文が declinedByAuthor の指摘に当たる読み方を残さない

  - 入力：SuggestionsTriaged（提案 4 件のうち 3 件を decline、費用 0.3 ドル）を記録したタスクの作業履歴
  - 期待結果：行の要点に「提案 4 件のうち 3 件をこの PR で対応しない」が、詳細に提案ごとの判断と理由が出て、費用 0.3 ドルが表示され、タスクの費用と予算に数えられる
