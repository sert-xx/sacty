# 要求要件：Sacty が作る PR の説明とコメントを、人が読んで判断する情報だけにする（PBI-471）

## スコープ

Sacty が作る PR の説明と、人への確認・指摘への返信のコメントから、Sacty の内部の ID・語・過程の情報と、同じ中身の繰り返しを外す。
外した情報は、Sacty の画面と `get_task` に今までどおり残す。

- 対象
  - 実装・要求要件・設計の PR の説明（テンプレートの有り無し、作り直し・更新・人が直した説明のマージの後を含む）
  - 人に確かめてほしいことのコメント、指摘への返信のコメント
  - 実装の説明を書くエージェントへの指示、仕様書（日英）・ユーザー文書（日英）、PBI-450 の決定を置き換える ADR、作業履歴
- 対象外
  - PR に投稿するレビューの本文（PBI-460）と、実装の説明の末尾の自己レビュー
  - コミットのメッセージの `sacty task <ID>`
  - 画面の表示（「確かめる項目」の数え方を含む）

## 確認したいこと

### must

- 設計に戻した・レビューが止まった・後続に回す決定の知らせも、今回直すか。直す対象は、画面へのリンクと、後続に回す決定の知らせに出るタスク ID・指摘の ID。
  推奨：直さない。依頼の 1b は人への確認と返信だけを挙げている。PBI-450 は、これらのリンクを再開・差し戻しの案内として残すと決めている。
  懸念：直すのが正しかった場合、これら4種の知らせに、開けない URL と内部の ID が残ります。別の PBI で同じ組み立てをもう一度直すことになります。

### should

- 説明に、表示されない HTML コメントの目印（`<!-- sacty task <ID> -->`）を足すか。
  推奨：足す。人が直した説明のマージは、今は可視の `sacty task` の行を手がかりにしている。
  懸念：足さないのが正しかった場合、利用者は PR の説明のソースからタスクを探せません。マージの指示も、別の手がかりで作り直すことになります。
- 「指摘への対応」の要点の1行を、誰が書くか。
  推奨：工程のエージェントが、対応の答えと一緒に書く。Sacty のレビューの本文は見出しと目印から始まるので、機械で切ると要点にならない。
  懸念：機械で切るのが正しかった場合、エージェントへの指示と答えの形を足した分が無駄になります。要点の欄の無い古い記録の扱いも要ります。
- エージェントが説明に書いた指摘の ID（`implement-1-1` など）を、指示で止めるだけにするか、説明を組み立てるときにも除くか。
  推奨：両方。指示だけでは、受け入れ条件 7 のテストで、説明に出ないことを確かめられない。
  懸念：指示だけが正しかった場合、エージェントが書いた文の一部を組み立てで消すので、意味が欠ける文が出ます。
- 承認の案内の1〜2文に、何を残すか。
  推奨：「マージすると承認になる」と「直してほしい所は、この PR にコメントかレビューで書く」の2文。指摘の担当とコミットの記録の説明は外す。
  懸念：ほかの案内も要る場合、指摘の伝え方を知らない読み手が、画面で差し戻せることを知りません。

### 確認しないと決めたこと

- テンプレートありの説明：テンプレート無しと同じ条件に合わせる。依頼は「Sacty が作る PR の説明」とだけ書き、2つを分けていないため。
- 出典の数え方：PR の説明からだけ外し、画面は変えない。受け入れ条件 5 が、画面で今までどおり読めることを求めるため。
- コミットのメッセージのタスク ID：変えない。PR の説明ではなく、依頼の受け入れ条件にも挙がっていないため。
- #521 の大きさの食い違い（依頼では 27KB、いま読めるのは約 10KB）：確かめない。どちらでも外すものは変わらないため。

## 既定で決めたこと

- 要求要件を省いたときは節を残し、「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」のように内部の語を使わずに書く。
- 観点の表を出すときは、見出しを実際の列に合わせる。結果の列が無ければ「実行結果」と書かない。
- 人への確認のコメントでは、指摘の ID の代わりに、指摘のコメントへの GitHub のリンクを示す。「戻し先の判断」「作り直しの実行」も内部の語を使わずに書く。
- 返信の書き出しは、元の指摘へのリンクだけにする（「[この指摘](URL)への返信です。」の形）。

## 要求

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | デーモンが作る PR の説明 | 可視の文に、タスクの ID・レビューの指摘の内部の ID を含まない |
| R-2 | デーモンが作る PR の説明 | Sacty のレビューの本文・行へのコメントの写し（目印・見出し・エージェントの行・コメントが付いた行の写し）を含まない |
| R-3 | デーモンが作る PR の説明 | 内部の語（オーケストレーター・工程・子タスク・担当・サブエージェント・観点の番号）を含まない |
| R-4 | デーモンが作る PR の説明 | 「レビューの進め方」の節と、AI のレビューの状況など書いた時点の状態を含まない |
| R-5 | デーモンが作る要求要件・設計の PR の説明 | 「確かめる所」に、確かめる項目の件数と、引用・導出・推論の数を含まない |
| R-6 | デーモンが作る実装の PR の説明 | 「最後の直し」の各項目を、説明の中で1回だけ出す（箇条書きの直しを含む） |
| R-7 | デーモンが作る PR の説明 | 目的・変更、確かめ方、人が確かめること、AI が作った印、マージで承認になることの1〜2文を含む |
| R-8 | デーモンが作る要求要件・設計の PR の説明 | 確認したいことと、指摘ごとの要点1行と対応（直したこと・直さなかった理由）を含む |
| R-9 | 人に確かめてほしいことのコメントと指摘への返信 | 画面の URL・タスクの ID・指摘の内部の ID・返信の種類（書いた人・指摘の種類）を含まない |
| R-10 | 実装の説明を書くエージェントへの指示 | 指摘の内部の ID と、読み手の判断に要らない作業の細部（日時の選び方など）を書かない決まりを含む |
| R-11 | 画面・`get_task` | 説明から外したタスクの ID・指摘の ID と全文・出典の数え方を、今までどおり出す |

### イベント駆動

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-12 | 観点が依頼の1行だけになる実装の PR の説明を作るとき | デーモン | 説明に観点の表を出さない |
| R-13 | 実装の PR の説明に、確かめたテストを載せるとき | デーモン | テストの名前の全文を並べず、出すのは件数とテストのファイルまでにする |

### 望まない振る舞い

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-14 | 以前の版が作った説明（可視のタスク ID の行あり）を人が直した後に、説明を更新する場合 | デーモン | 人が足したのではない可視のタスク ID の行を、更新後の説明に残さない |
| R-15 | 以前の書き出し（「…への返信です。」）の返信を読む場合 | デーモン | 状態（対応した・対応していない など）を、今までどおり読み取る |

## 受け入れの確かめ方

- 自動のテストで確かめること
  - 合成のタスクから、実装の PR の説明（テンプレートの有り無し・作り直しの後）と、要求要件・設計の PR の説明を作る。それらで R-1〜R-8・R-12・R-13 を確かめる。R-1・R-6・R-12 の修正を戻すとテストが落ちる
  - 人への確認・返信のコメントで R-9 を、古い説明のマージで R-14 を、古い返信で R-15 を、画面・`get_task` で R-11 を確かめる
  - `npm run lint`・`npm run typecheck`・`npx vitest run`・`npm run build` が通る
- 差分で確かめること
  - R-10 の指示の文と、仕様書（日英）・ユーザー文書（日英）が、新しい説明・コメントの形と合う
  - PBI-450 の決定（レビューの進め方・AI のレビューの状況・人への確認のリンク）を置き換える新しい ADR と、作業履歴（`docs/worklog/<YYYYMMDD>-pbi-471-<slug>.md`）がある
- 人が確かめること
  - 実際に作られた PR の説明を GitHub で読み、Sacty を使っていない人が判断するのに足りるか。懸念：足りないと、承認する人は画面を開かないと判断できず、この変更の狙いが外れます。
