# 要求要件：Sacty が作る PR の説明とコメントを、人が読んで判断する情報だけにする（PBI-471）

## スコープ

Sacty が作る PR の説明と、Sacty が PR・Issue に書くコメントから、Sacty の内部の ID・語・過程の情報、手元の画面の URL と、同じ中身の繰り返しを外す。
外した情報は、Sacty の画面と `get_task` に今までどおり残す。

- 対象
  - 実装・要求要件・設計の PR の説明（テンプレートの有り無し、作り直し・更新・人が直した説明のマージの後を含む）
  - 人に確かめてほしいこと・指摘への返信・設計に戻した・レビューが止まった・後続に回す決定の、各コメント
  - 後続に回す決定で Sacty が作る Issue の題と本文
  - 実装の説明を書くエージェントへの指示、仕様書（日英）・ユーザー文書（日英）、PBI-450 の決定を置き換える ADR、作業履歴
- 対象外
  - PR に投稿するレビューの本文（PBI-460）と、実装の説明の末尾の自己レビュー
  - コミットのメッセージの `sacty task <ID>`
  - 画面の表示（「確かめる項目」の数え方を含む）
  - 投稿済みのコメントと、更新しない古い説明の書き換え（説明は、次に更新したときに新しい形になる）

## 既定で決めたこと

- 要求要件を省いたときは節を残し、「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」のように内部の語を使わずに書く。
- 観点の表を出すときは、見出しを実際の列に合わせる。結果の列が無ければ「実行結果」と書かない。
- コメントで指摘を示すときは、指摘の ID の代わりに指摘のコメントへの GitHub のリンクを使う（返信の書き出しは「[この指摘](URL)への返信です。」）。リンクが作れない指摘（画面から書かれた指摘など）は、指摘の要点の1行で示す。
- 「指摘への対応」の要点の1行は、工程のエージェントが対応の答えと一緒に書く。Sacty のレビューの本文は見出しと目印から始まり、機械で切ると要点にならないため。
- エージェントが説明に書いた指摘の ID（`implement-1-1` など）は、指示で止め、説明を組み立てるときにも除く。指示だけでは、説明に出ないことをテストで確かめられないため。

## 要求

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | デーモンが作る PR の説明（実装の説明の末尾の自己レビューを除く） | 可視の文に、タスクの ID・レビューの指摘の内部の ID を含まない |
| R-2 | デーモンが作る PR の説明（実装の説明の末尾の自己レビューを除く） | Sacty のレビューの本文・行へのコメントの写し（目印・見出し・エージェントの行・コメントが付いた行の写し）を含まない |
| R-3 | デーモンが作る PR の説明（実装の説明の末尾の自己レビューを除く） | 内部の語（オーケストレーター・工程・子タスク・担当・サブエージェント・観点の番号）を含まない |
| R-4 | デーモンが作る PR の説明（実装の説明の末尾の自己レビューを除く） | 「レビューの進め方」の節と、AI のレビューの状況など書いた時点の状態を含まない |
| R-5 | デーモンが作る要求要件・設計の PR の説明 | 「確かめる所」に、確かめる項目の件数と、引用・導出・推論の数を含まない |
| R-6 | デーモンが作る実装の PR の説明 | 「最後の直し」の各項目を、説明の中で1回だけ出す（箇条書きの直しを含む） |
| R-7 | デーモンが作る PR の説明 | 目的・変更、確かめ方、人が確かめること、AI が作った印と、承認の案内の2文（「マージすると承認になる」「直してほしい所は、この PR にコメントかレビューで書く」）を含む |
| R-8 | デーモンが作る要求要件・設計の PR の説明 | 確認したいことと、指摘ごとの要点1行と対応（直したこと・直さなかった理由）を含む |
| R-9 | Sacty が PR・Issue に書くコメント（スコープの対象の5種）と、後続に回す決定で作る Issue の題・本文 | 画面の URL・タスクの ID・指摘の内部の ID・内部の語・返信の種類（書いた人・指摘の種類）を含まない |
| R-10 | 実装の説明を書くエージェントへの指示 | 指摘の内部の ID と、読み手の判断に要らない作業の細部（日時の選び方など）を書かない決まりを含む |
| R-11 | 画面・`get_task` | 説明から外したタスクの ID・指摘の ID と全文・出典の数え方を、今までどおり出す |
| R-16 | デーモンが作る PR の説明 | タスクの ID を含む、表示されない HTML コメントの目印を1つ含む |
| R-17 | 再開・差し戻しの案内を含むコメント（人への確認・設計に戻した・レビューが止まった・後続に回す決定） | 案内を、URL ではなく「Sacty の画面で〜してください」の形の文で含む |

| R-18 | 人が直した説明（新しい形・可視のタスク ID の行がある古い形のどちらでも）を更新するとき | デーモン | 人の直しを今までどおりマージで残す |

### 望まない振る舞い

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-14 | 以前の版が作った説明（可視のタスク ID の行あり）を人が直した後に、説明を更新する場合 | デーモン | 人が足したのではない可視のタスク ID の行を、更新後の説明に残さない |
| R-15 | 返信（以前の書き出し「…への返信です。」・新しい書き出しのどちらでも）を読む場合 | デーモン | 状態（対応した・対応していない など）を読み取る |
| R-19 | 人が説明の目印を書き換えた・消した場合 | デーモン | 更新後の説明に、そのタスクの ID の目印を1つだけ置き、PR の見分けとマージの対象を変えない |
| R-20 | 要点の記録が無い（以前の版で記録した）指摘の対応を説明に載せる場合 | デーモン | 要点の行を出さずに対応だけを書き、指摘の全文を写さない |

## 受け入れの確かめ方

- 自動のテストで確かめること
  - 合成のタスクから、実装の PR の説明（テンプレートの有り無し・作り直しの後）と、要求要件・設計の PR の説明を作る。それらで R-1〜R-8・R-12・R-13・R-16 を確かめる。R-1・R-6・R-12 の修正を戻すとテストが落ちる
  - 5種のコメントと後続に回す決定で作る Issue の題・本文で R-9 を、5種のコメントで R-17 を、新旧の説明のマージで R-14・R-18 を、目印を書き換えた・消した説明で R-19 を、要点の無い古い記録で R-20 を、新旧の書き出しの返信で R-15 を、画面・`get_task` で R-11 を確かめる
  - `npm run lint`・`npm run typecheck`・`npx vitest run`・`npm run build` が通る
- 差分で確かめること
  - R-10 の指示の文と、仕様書（日英）・ユーザー文書（日英）が、新しい説明・コメントの形と合う
  - PBI-450 の決定（レビューの進め方・AI のレビューの状況・コメントの画面へのリンク）を置き換える新しい ADR がある。理由に、PR の読み手が画面なしで判断できるようにすることを書く
  - 作業履歴（`docs/worklog/<YYYYMMDD>-pbi-471-<slug>.md`）がある
- 人が確かめること
  - 実際に作られた PR の説明を GitHub で読み、Sacty を使っていない人が判断するのに足りるか。懸念：足りないと、承認する人は画面を開かないと判断できず、この変更の狙いが外れます。
