# 設計：Sacty が作る PR の説明とコメントを、人が読んで判断する情報だけにする（PBI-471）

## スコープ

PR の説明（4系統）と Sacty が書くコメント・Issue の固定の文を書き換え、エージェントが書いた文から指摘の ID を除いて、R-1〜R-20 に合わせる。
外した情報は今までどおり台帳に残り、画面と `get_task` の実装は変えない。

- 対象
  - `prompts.ts` の説明の組み立て（実装・要求要件・設計、テンプレートの有り無し）と、実装の説明の指示
  - `pr-body-merge.ts`・`remark-reply.ts`・`human-ask-notice.ts`・`rework-notice.ts`・`review-stop-notice.ts`・`deferral-notice.ts`・`decision-notice.ts`（確認したいこと 1）
  - 指摘への対応に要点の欄を足す（`RemarkResponse`・`TaskRemark`）
  - 仕様書・ユーザー文書（日英）、ADR、作業履歴、文言を確かめている既存のテスト
- 対象外
  - 工程の成果として投稿するコメント（`github-comments.ts` の「Sacty の<工程名>の工程で AI が書きました」）と、要求要件の全文のコメント
  - 後続のタスクの題「後続に回した指摘 <ID>」（後続のタスクの PR の題になるが、説明ではない）
  - 以前の版の記録があるときだけ出る文（ゴールガーディアン・最終レビューの所見）

## 確認したいこと

### must

なし

### should

1. 「人の判断を待って止めています」のコメント（`decision-notice.ts`）も、R-9・R-17 と同じに直すか。推奨：直す（要求要件の5種に無いが、同じ画面の URL が出る）。
   懸念：直さないと、このコメントにだけ `http://127.0.0.1:4700/tasks/<ID>` が残り、PR の読み手が開けないリンクを見ます。
2. 後続に回す決定のコメントと Issue で、AI のレビューの指摘は、全文の引用をやめて要点と元のコメントへのリンクにするか。推奨：する（全文に目印・見出し・エージェントの行が入り、R-9 に反する）。
   懸念：Issue を開いた人は、指摘の細部を読むのに元の PR のレビューを開く手間が1回増えます。
3. 承認の案内を2文だけにし、「PR の中で直してからマージしても承認になる」の文を外すか。推奨：外す（受け入れ条件 3 が 1〜2 文と決めている）。
   懸念：PR の中でファイルを直したい人が、直すと承認にならないと思ってコメントで頼み、往復が1回増えます。

## 既定で決めたこと

- 説明の冒頭の「Sacty のタスク「<題>」の…です」の行を、4系統とも外す（題の繰り返しのため）。
- 目印は `<!-- sacty task <タスク ID> -->` の1行にし、説明の最後（footer の末尾）に置く。GitHub で `sacty task` を探す手がかりを残す。
- 要点は、工程のエージェントが `sacty-responses` の `gist`（1行・120 文字まで）に書く。無い・空のときは R-20 の扱いにする。
- 返信の末尾を「Sacty の AI が書きました。」にする（R-9 の「工程」）。新しい ADR は、PBI-450 の決定 1・3 と PBI-460 の決定 9 を一部置き換える。
- テストのファイルは、テストの名前の ` › ` より前の部分にする。` › ` の無い名前は、件数にだけ数える。

## 構成

### PR の説明

| 所 | 変更 |
| --- | --- |
| 4系統の共通 | 冒頭の行・`aiReviewBodyLines`・「レビューの進め方」（`REVIEW_BODY_LINES`）を外す。footer を「この PR は Sacty が作成しました。」・承認の2文・目印にする |
| 承認の2文 | 「この PR をマージすると、<実装・設計・要求要件>を承認したことになります。」（監視があれば「…なり、マージの後の監視を終えるとタスクが完了します。」）と「直してほしい所は、この PR にコメントかレビューで書いてください。」 |
| 最後の直し（R-6） | 最初の段落が結論の頭に収まるときだけ結論に出し、残りを節に出す。収まらず切るときは、結論に出さず、全文を節にだけ出す（今は、切った頭と全文の両方が出る） |
| 確かめ方（R-12・R-13） | 見出しを「確かめ方」にする。観点が依頼の1行（`withoutRequirements` の REQ）なら、表と詳細を出さず「テスト：N 件（`a.test.ts`・…）」の1行にする。表のセルと詳細のテストも、件数とファイルにする |
| 要求要件を省いたとき | 「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」（skip-requirements の組み合わせでは「依頼の内容と承認済みの設計を」） |
| 確かめる所（R-5） | 問いとの区別の行を「人に決めてほしい問いは「確認したいこと」にあります。」にする。`provenanceGuideLines` から件数の行とサブエージェントの行を外し、項目の行だけを残す（PR でだけ使う関数で、画面は別の実装） |
| 指摘への対応（R-2・R-8・R-20） | `- <要点>` と `  - 対応：<対応の文>` にする。要点が無ければ `- 対応：<対応の文>` だけにする。指摘の全文は載せない |
| 内部の語の文（R-3） | 重ねた PR・分割の範囲・省いた続き・セキュリティの範囲・テストなしの根拠・「承認済みの前の工程」・設計の直しの文から、子タスク・工程・オーケストレーター・観点 SEC-MIN を外す。設計の直しの指摘は要点で示す |
| エージェントが書いた文（R-1） | 実装の説明・対応の文・確かめたいこと・設計の直しの理由から、`<工程のキー>-<回>-<番号>` の形の ID を、それだけを囲む括弧ごと除く（`withoutRemarkIds`。コメントにも当てる） |

### コメント・Issue（R-9・R-17）

指摘はリンク（`remarkOriginUrl`）で示し、作れなければ要点、要点も無ければ示さない。
画面のリンクと注釈（`taskLink`・`taskLinkNote`）は、これらに渡さない。

| 投稿 | 変更 |
| --- | --- |
| 指摘への返信 | 書き出しを「`[この指摘](URL)への返信です。`」にする（通常のコメントには引用を続ける）。`ORIGIN_KIND` と書いた人の区別を外す |
| 人への確認 | 「戻し先の判断で」「作り直しの実行が」と指摘の ID を外す。末尾「意図と違うときは、この PR にコメントするか、Sacty の画面で差し戻してください。」 |
| 設計に戻した | 「工程」を外し、合図の語を「実装で直す」にする（戻し先の判断の指示の例にも足す）。末尾「意図と違うときは、Sacty の画面で差し戻してください。」 |
| レビューが止まった | 再開のしかた「Sacty の画面で、このタスクを再開してください。」 |
| 後続に回す決定 | 「**指摘 <ID>**」をリンク・要点にする。末尾「意図と違うときは、Sacty の画面で差し戻してください。」 |
| 人の判断を待つ（should 1） | 末尾「補足を付けて再開するときは、Sacty の画面で再開してください。」 |
| 後続の Issue | 題を要点（無ければ、目印・見出しを除いた最初の行）にし、末尾からタスク ID と指摘の ID を外す |

## データ

- `RemarkResponse.gist?: string`、`TaskRemark.gist?: string`（対応と同じ提出回のもの）。`sacty-responses` の形と指示に `gist` を足す。
- 実装の説明の指示（`IMPLEMENT_REPORT_LINE` と「既定で決めたこと」の指示）に、指摘の ID と、作業の細部（日時の選び方など）を書かない決まりを足す（R-10）。

## 処理の流れ（人が直した説明の更新）

- エージェントへの指示の「`sacty task` を含む行を残す」を、「sactyPrevious にあった可視の `sacty task` を含む行は残さない。人が足した行は残す」に変える。
- マージの結果（自動・エージェントのどちらも）から、sactyPrevious と同じ文の可視の `sacty task <ID>` の行と、目印の行をすべて除き、末尾に正しい目印を1つ置く（R-14・R-19）。

## テスト観点

- [TV-1] 実装の PR の説明（テンプレート無し）に、タスクの ID・指摘の ID・内部の語・レビューの進め方・AI のレビューの状況が出ない
  - 入力：要求要件を省いた作り直しの後の合成のタスクで、実装の説明に「（implement-1-1 への対応）」を含み、AI のレビューの状況が none のものから説明を作る
  - 期待結果：HTML コメントを除いた説明に、タスクの ID・`implement-1-1`・オーケストレーター・工程・子タスク・担当・サブエージェント・「レビューの進め方」・「AI のレビュー：」が無く、「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」がある
- [TV-2] テンプレートありの実装の PR の説明にも、同じ情報が出ない
  - 入力：観点の見出しのある PR テンプレートと、1 つ目の観点と同じ合成のタスクから、テンプレートを埋めた説明を作る
  - 期待結果：HTML コメントを除いた説明に、タスクの ID・`implement-1-1`・1 つ目の観点の内部の語・「レビューの進め方」・「AI のレビュー：」が無い
- [TV-3] 固定の文が出る場合の説明に、内部の語と観点の番号が出ない
  - 入力：重ねた PR・分割の子タスク・セキュリティ対応・テストの仕組みが無い・skip-requirements の組み合わせ・設計の直しのあるタスクから、それぞれ実装の PR の説明を作る
  - 期待結果：どの説明の HTML コメントを除いた文にも、子タスク・工程・オーケストレーター・担当・サブエージェント・`SEC-MIN`・指摘の ID が無い
- [TV-4] 説明に、タスクの ID の目印が1つだけある
  - 入力：実装（テンプレートの有り無し）・要求要件・設計の PR の説明を、同じタスクから作る
  - 期待結果：4つの説明のそれぞれに `<!-- sacty task <タスク ID> -->` がちょうど1回あり、それ以外にタスクの ID が無い
- [TV-5] 最後の直しの各項目が、説明に1回だけ出る
  - 入力：作り直しの後の実装の説明で、最後の直しが字下げの無い箇条書きの5項目（合わせて 240 文字を超える）のタスクと、1文だけのタスクから説明を作る
  - 期待結果：5項目のタスクでは各項目の文がちょうど1回出て、結論に「最後の直し」の行が無い。1文のタスクでは、その文が結論にだけ1回出て、「## 最後の直し」の節が無い
- [TV-6] 観点が依頼の1行だけのとき、観点の表を出さず、テストは件数とファイルだけにする
  - 入力：要求要件・設計を省き、REQ の観点に `a.test.ts › 名前1`・`a.test.ts › 名前2`・`b.test.ts › 名前3` を対応させたタスクから説明を作る
  - 期待結果：説明に `| 観点 |` の表と「観点ごとの詳細」が無く、「テスト：3 件（`a.test.ts`・`b.test.ts`）」があり、「名前1」〜「名前3」が無い
- [TV-7] 設計の観点の表でも、テストの名前の全文を並べない
  - 入力：承認済みの設計の観点 TV-1 に、テストの名前を3件対応させたタスクから説明を作る
  - 期待結果：見出し「確かめ方」の表と詳細に、TV-1 のテストが「3 件（ファイル）」の形で出て、テストの名前の ` › ` より後ろの文が無い
- [TV-8] 実装の PR の説明に、判断に要る情報と承認の案内の2文がある
  - 入力：人が確かめることが1件あるタスクから、実装の PR の説明（テンプレートの有り無し）を作る
  - 期待結果：どちらの説明にも、変更の要約・「確かめ方」・人が確かめることの項目・「この PR は Sacty が作成しました。」・「この PR をマージすると、実装を承認したことになります。」・「直してほしい所は、この PR にコメントかレビューで書いてください。」がある
- [TV-9] 要求要件・設計の PR の説明に、確認したいことと、指摘ごとの要点と対応がある
  - 入力：should の問いが1件あり、要点「エラーの文言を直す」と対応の文のある指摘を持つ設計のタスクから、PR の説明（テンプレートの有り無し）を作る
  - 期待結果：どちらの説明にも、確認したいことの問い・「- エラーの文言を直す」・「  - 対応：<対応の文>」・AI が作った印・承認の2文があり、タスクの ID と指摘の ID が無い
- [TV-10] Sacty のレビューの本文と行へのコメントの写しが、説明に出ない
  - 入力：`<!-- sacty-review:… -->`・「## Sacty のレビュー」・「## 総評」・「## 指摘」・「観点ごとの担当（サブエージェント）」・「（コメントが付いた行の内容：「…」）」を全文に含む AI のレビューの指摘に対応した設計のタスクから、説明を作る
  - 期待結果：説明に、`sacty-review`・「## Sacty のレビュー」・「## 総評」・「## 指摘」・「サブエージェント」・「コメントが付いた行の内容」が無く、指摘の要点と対応はある
- [TV-11] 確かめる所に、確かめる項目の件数と出典の数え方が出ない
  - 入力：引用 3・導出 14・推論 1 の出典の分類で、分類が逐次（sequential）の設計のタスクから説明を作る
  - 期待結果：「確かめる所」に、「確かめる項目：」・「引用 3」・「導出 14」・「推論 1」・「サブエージェント」が無く、推論の項目の ID の行はある
- [TV-12] 要点の記録が無い古い指摘の対応は、要点の行を出さず、全文を写さない
  - 入力：`gist` の無い対応の記録（以前の版の形）を持つ指摘のある設計のタスクから、説明を作る
  - 期待結果：「指摘への対応」に「- 対応：<対応の文>」だけがあり、指摘の全文の文が無い
- [TV-13] 指摘への返信に、返信の種類・内部の語・ID が出ない
  - 入力：AI のレビューの本文から取り込んだ指摘と、人の通常のコメントから取り込んだ指摘への返信を作る
  - 期待結果：どちらも書き出しが「[この指摘](<元のコメントの URL>)への返信です。」で、末尾が「Sacty の AI が書きました。」で、「Sacty の AI が書いた」・「人が書いた」・「レビューの本文」・「通常のコメント」・「工程」・タスクの ID・指摘の ID が目印の外に無い
- [TV-14] 人への確認のコメントで、指摘をリンクか要点で示し、画面の案内を文で書く
  - 入力：PR のコメントから取り込んだ指摘と、画面から書いた要点のある指摘に、確かめたいことがあるタスクで、画面の URL が `http://127.0.0.1:4700` のときにコメントを作る
  - 期待結果：目印の外に `http://127.0.0.1`・タスクの ID・指摘の ID・「戻し先の判断」・「作り直しの実行」が無く、元のコメントへのリンクと画面から書いた指摘の要点と「Sacty の画面で差し戻してください。」がある
- [TV-15] 設計に戻した・レビューが止まった・人の判断を待つコメントに、画面の URL と内部の語が出ない
  - 入力：画面の URL が `http://127.0.0.1:4700` のときに、設計に戻した・レビューが止まった・人の判断を待つの3種のコメントを作る
  - 期待結果：3種とも目印の外に `http://`・タスクの ID・「工程」・「タスクの画面は、依頼した人のマシンでだけ開けます。」が無く、「Sacty の画面で」で始まる「〜してください。」の文がある
- [TV-16] 後続に回す決定のコメントに、指摘の ID・画面の URL・AI のレビューの全文が出ない
  - 入力：PR のコメントの人の指摘・AI のレビューの指摘（全文に目印と見出しを含む）・画面から書いた指摘の3件を後続に回すと決めたタスクで、コメントを作る
  - 期待結果：目印の外に指摘の ID・`http://127.0.0.1`・`sacty-review`・「## 総評」が無く、元のコメントへのリンクと要点と「Sacty の画面で差し戻してください。」がある
- [TV-17] 後続に回す指摘から作る Issue の題と本文に、ID と内部の語が出ない
  - 入力：要点「エラーの文言を直す」のある AI のレビューの指摘（全文の最初の行が `<!-- sacty-review:… -->`）から Issue を作る
  - 期待結果：題が「[PR #<番号> follow-up] エラーの文言を直す」で、本文の目印の外にタスクの ID・指摘の ID・`sacty-review`・「サブエージェント」が無い
- [TV-18] 新旧の書き出しの返信から、状態を読み取る
  - 入力：「Sacty の AI が書いたレビューの本文（[このレビュー](…)）への返信です。」と「[この指摘](…)への返信です。」の書き出しで、頭が「**対応しました。**」と「**対応していません。** 理由：」の返信を読む
  - 期待結果：どちらの書き出しでも、状態が addressed と declined に読める
- [TV-19] 以前の版の説明を人が直した後の更新で、可視のタスク ID の行を残さず、人の直しを残す
  - 入力：前回の説明に「Sacty のタスク「題」の成果物です（sacty task <ID>）。」の行があり、人が別の行に補足を足した PR の説明を更新する
  - 期待結果：更新後の説明に可視の `sacty task <ID>` の行が無く、人の補足と目印が1つある
- [TV-20] 新しい形の説明を人が直した後の更新で、人の直しを残す
  - 入力：新しい形の前回の説明に、人が補足を足し、見出しの言い回しを直した PR の説明を更新する
  - 期待結果：更新後の説明に、人の補足と見出しの直しと、今回の更新の中身がある
- [TV-21] 人が目印を書き換えた・消した説明の更新で、目印を1つだけ置き、PR の見分けを変えない
