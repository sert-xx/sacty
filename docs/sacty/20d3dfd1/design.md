# 設計：Sacty が作る PR の説明とコメントを、人が読んで判断する情報だけにする（PBI-471）

## スコープ

PR の説明（4系統）と、Sacty が書くコメント・Issue の固定の文と、後続のタスクの題を書き換える。エージェントが書いた文からは指摘の ID を除く。これで R-1〜R-23 に合わせる。
外した情報は今までどおり台帳に残る。画面と `get_task` の実装は変えない。

- 対象
  - `prompts.ts`：説明の組み立て（実装・要求要件・設計、テンプレートの有り無し）、実装の説明の指示、指示の中の題
  - `pr-body-merge.ts`・`remark-reply.ts`・`human-ask-notice.ts`・`rework-notice.ts`・`review-stop-notice.ts`・`deferral-notice.ts`・`decision-notice.ts`
  - 指摘への対応に要点の欄を足す（`RemarkResponse`・`TaskRemark`）
  - 仕様書・ユーザー文書（日英）、ADR、作業履歴、文言を確かめている既存のテスト
- 対象外
  - 工程の成果として投稿するコメント（`github-comments.ts`）と、要求要件の全文のコメント
  - 以前の版の記録があるときだけ出る文（ゴールガーディアン・最終レビューの所見）
  - 作成済みの後続のタスクの題

## 既定で決めたこと

- 説明の冒頭の行「Sacty のタスク「<題>」の…です」を、4系統とも外す。題の繰り返しのため。
- 目印は `<!-- sacty task <タスク ID> -->` の1行にし、説明の最後（footer の末尾）に置く。GitHub で `sacty task` を検索する手がかりを残すため。
- 要点は、エージェントが `sacty-responses` の `gist`（1行・120 文字まで。URL・ID・内部の語を書かない）に書く。
- 返信の末尾を「Sacty の AI が書きました。」にする（R-9 の「工程」を外す）。
- 後続のタスクの指示では、見出しを「後続に回した指摘への対応」に固定する。人が画面で題を直しても、指示には入らない。

## 構成

### PR の説明

| 所 | 変更 |
| --- | --- |
| 4系統の共通 | 冒頭の行・`aiReviewBodyLines`・「レビューの進め方」を外す。footer を「この PR は Sacty が作成しました。」・承認の2文・目印にする |
| 承認の2文（R-7） | 「この PR をマージすると（PR の中で直してからでも）、<実装・設計・要求要件>を承認したことになります。」と「直してほしい所は、この PR にコメントかレビューで書いてください。」 |
| 最後の直し（R-6） | 最初の段落が結論の頭に収まるときだけ結論に出し、残りを節に出す。収まらないときは結論に出さず、全文を節にだけ出す |
| 確かめ方（R-12・R-13） | 見出しを「確かめ方」にする。観点が依頼の1行だけなら、表と詳細を出さず「テスト：N 件（`a.test.ts`・…）」の1行にする。表のセルと詳細も件数とファイルにする（ファイルはテストの名前の ` › ` より前） |
| 要求要件を省いたとき | 「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」 |
| 確かめる所（R-5） | `provenanceGuideLines` を PR 用に分け、件数の行とサブエージェントの行を外す。画面の表示は変えない |
| 指摘への対応（R-2・R-8・R-20） | `- <要点>` と `  - 対応：<対応の文>` にする。要点が無ければ `- 対応：<対応の文>` だけにする。全文は載せない |
| 内部の語の文（R-3） | 重ねた PR・分割の範囲・セキュリティの範囲・テストなしの根拠・設計の直しの固定の文から、子タスク・工程・オーケストレーター・`SEC-MIN` を外す |
| エージェントが書いた文（R-1） | `<工程のキー>-<回>-<番号>` の形の ID を、それだけを囲む括弧ごと除く（`withoutRemarkIds`。コメントにも使う） |

### コメント・Issue・後続のタスク（R-9・R-17・R-21〜R-23）

- 指摘は、元のコメントへのリンク（`remarkOriginUrl`）で示す。リンクが作れなければ要点で示し、要点も無ければ指摘の最初の行で示す。`taskLink`・`taskLinkNote` は、これらのコメントに渡さない。
- 題の元の1行（`deferralTitleText`）は、要点か、`<!--` と `#` で始まる行を飛ばした最初の行から作る。`publicText` で秘密の値と内部のパスを伏せ、URL・UUID・指摘の ID を除いて、`DEFERRAL_TITLE_MAX`（80）で切る。Issue と後続のタスクで、この1行を共通に使う。

| 投稿 | 変更 |
| --- | --- |
| 指摘への返信 | 書き出しを「`[この指摘](URL)への返信です。`」にする。`ORIGIN_KIND` と、書いた人の区別を外す |
| 人への確認 | 「戻し先の判断で」「作り直しの実行が」と指摘の ID を外す。末尾を「意図と違うときは、この PR にコメントするか、Sacty の画面で差し戻してください。」にする |
| 設計に戻した | 「工程」を外す。末尾を「意図と違うときは、Sacty の画面で差し戻してください。」にする |
| レビューが止まった | 再開の案内を「Sacty の画面で、このタスクを再開してください。」にする |
| 人の判断を待つ | 末尾を「補足を付けて再開するときは、Sacty の画面で再開してください。」にする |
| 後続に回す決定（R-22） | 「**指摘 <ID>**」と全文の引用を、リンクと要点の1行にする。末尾を「意図と違うときは、Sacty の画面で差し戻してください。」にする |
| 後続の Issue | 題を `[PR #N follow-up] <題の1行>` にする。本文の「## 指摘」を要点とリンクにし、末尾からタスクの ID と指摘の ID を外す |
| 後続のタスク | 題を Issue と同じ `<タグ> <題の1行>` にする。依頼の JSON に `gist` を足す。`buildDeferralTask` に `secrets` を渡す |

## データ

- `RemarkResponse.gist?: string` と `TaskRemark.gist?: string` を足す（対応と同じ提出回のもの）。`sacty-responses` の形と指示に `gist` を足す。
- 実装の説明の指示（`IMPLEMENT_REPORT_LINE` と「既定で決めたこと」の指示）に、指摘の ID と、作業の細部（日時の選び方など）を書かない決まりを足す（R-10）。

## 処理の流れ

- 人が直した説明の更新：エージェントへの指示の「`sacty task` を含む行を残す」を、「sactyPrevious にあった可視の `sacty task` の行は残さない。人が足した行は残す」に変える。
- マージの結果（自動・エージェントのどちらも）から、sactyPrevious と同じ文の可視の行と目印の行をすべて除き、末尾に正しい目印を1つ置く（R-14・R-19）。
- 指示の中の題（R-23）：エージェントへの指示に題を書く所（`# ${task.title}`・「タイトル：」・「元のタスク：」など。`prompts.ts`・`risk-assessment.ts`・`audit-prompts.ts`）は `instructionTitle(task)` を通す。後続のタスク（`derivedFrom.deferredRemarkId` がある）では、固定の見出しを返す。

- ADR：新しい ADR を足す。PBI-450 の ADR（`20261121-1800-…`）と PBI-460 の ADR（`20261121-1603-…`。決定 9）を `superseded` にして、置き換え先を書く。
- 作業履歴：`docs/worklog/<YYYYMMDD>-pbi-471-<slug>.md`。

## テスト観点

- [TV-1] 実装の PR の説明（テンプレート無し）に、タスクの ID・指摘の ID・内部の語・レビューの進め方・AI のレビューの状況が出ない
  - 入力：要求要件を省いた作り直しの後の合成のタスクで、実装の説明に「（implement-1-1 への対応）」を含み、AI のレビューの状況が none のものから説明を作る
  - 期待結果：HTML コメントを除いた説明に、タスクの ID・`implement-1-1`・オーケストレーター・工程・子タスク・担当・サブエージェント・「レビューの進め方」・「AI のレビュー：」が無く、「要求要件の文書は作らず、依頼の内容を受け入れの基準にしました。」がある
- [TV-2] テンプレートありの実装の PR の説明にも、同じ情報が出ない
  - 入力：観点の見出しのある PR テンプレートと、1 つ目の観点と同じ合成のタスクから、テンプレートを埋めた説明を作る
  - 期待結果：HTML コメントを除いた説明に、タスクの ID・`implement-1-1`・1 つ目の観点の内部の語・「レビューの進め方」・「AI のレビュー：」が無い
- [TV-3] 固定の文が出る場合の説明に、内部の語と観点の番号が出ない
  - 入力：重ねた PR・分割の子タスク・セキュリティ対応・テストの仕組みが無い・skip-requirements の組み合わせ・設計の直しのあるタスクから、それぞれ実装の PR の説明を作る
  - 期待結果：どの説明の HTML コメントを除いた文にも、子タスク・工程・オーケストレーター・担当・サブエージェント・`SEC-MIN`・指摘の ID が無い
- [TV-4] 説明に、タスクの ID の目印が1つだけある
  - 入力：実装（テンプレートの有り無し）・要求要件・設計の PR の説明を、同じタスクから作る
  - 期待結果：4つの説明のそれぞれに `<!-- sacty task <タスク ID> -->` がちょうど1回あり、それ以外にタスクの ID が無い
- [TV-5] 最後の直しの各項目が、説明に1回だけ出る
  - 入力：作り直しの後の実装の説明で、最後の直しが字下げの無い箇条書きの5項目（合わせて 240 文字を超える）のタスクと、1文だけのタスクから説明を作る
  - 期待結果：5項目のタスクでは各項目の文がちょうど1回出て、結論に「最後の直し」の行が無く、1文のタスクでは、その文が結論にだけ1回出て「## 最後の直し」の節が無い
- [TV-6] 観点が依頼の1行だけのとき、観点の表を出さず、テストは件数とファイルだけにする
  - 入力：要求要件・設計を省き、依頼の観点に `a.test.ts › 名前1`・`a.test.ts › 名前2`・`b.test.ts › 名前3` を対応させたタスクから説明を作る
  - 期待結果：説明に `| 観点 |` の表と「観点ごとの詳細」が無く、「テスト：3 件（`a.test.ts`・`b.test.ts`）」があり、「名前1」〜「名前3」が無い
- [TV-7] 設計の観点の表でも、テストの名前の全文を並べない
  - 入力：承認済みの設計の観点 TV-1 に、テストの名前を3件対応させたタスクから説明を作る
  - 期待結果：見出し「確かめ方」の表と詳細に、TV-1 のテストが「3 件（ファイル）」の形で出て、テストの名前の ` › ` より後ろの文が無い
- [TV-8] 実装の PR の説明に、判断に要る情報と承認の案内の2文がある
  - 入力：人が確かめることが1件あるタスクから、実装の PR の説明（テンプレートの有り無し）を作る
  - 期待結果：どちらの説明にも、変更の要約・「確かめ方」・人が確かめることの項目・「この PR は Sacty が作成しました。」・「この PR をマージすると（PR の中で直してからでも）、実装を承認したことになります。」・「直してほしい所は、この PR にコメントかレビューで書いてください。」がある

- [TV-10] Sacty のレビューの本文と行へのコメントの写しが、説明に出ない

  - 期待結果：説明に、`sacty-review`・「## Sacty のレビュー」・「## 総評」・「## 指摘」・「サブエージェント」・「コメントが付いた行の内容」が無く、指摘の要点と対応はある
- [TV-11] 確かめる所に、確かめる項目の件数と出典の数え方が出ない
  - 入力：引用 3・導出 14・推論 1 の出典の分類で、分類が逐次（sequential）の設計のタスクから説明を作る
  - 期待結果：「確かめる所」に、「確かめる項目：」・「引用 3」・「導出 14」・「推論 1」・「サブエージェント」が無く、推論の項目の ID の行はある
- [TV-12] 要点の記録が無い古い指摘の対応は、要点の行を出さず、全文を写さない
  - 入力：`gist` の無い対応の記録（以前の版の形）を持つ指摘のある設計のタスクから、説明を作る
  - 期待結果：「指摘への対応」に「- 対応：<対応の文>」だけがあり、指摘の全文の文が無い

  - 期待結果：3種とも目印の外に `http://`・タスクの ID・「工程」・「タスクの画面は、依頼した人のマシンでだけ開けます。」が無く、「Sacty の画面で」を含む「〜してください。」の文がある

  - 期待結果：目印の外に指摘の ID・タスクの ID・`http://127.0.0.1`・`sacty-review`・「## 総評」が無く、元のコメントへのリンク2件と要点と「Sacty の画面で差し戻してください。」がある
