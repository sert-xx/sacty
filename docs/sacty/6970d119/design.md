# 設計：要求要件・設計の PR の本文に「確認したいこと」を出す（PBI-439）

## スコープ

要求要件・設計の PR の本文に、成果物の「確認したいこと」の件数・中身・答え方・答えずにマージしたときの扱いを出す。\
振る舞い（答えずにマージすると推奨の答えで進む）は変えない。

- 対象
  - 節の読み取りと本文の節の組み立て（新しいファイル `apps/daemon/src/step-questions.ts`）
  - `buildStepPullRequestBodyText`・`buildStepPullRequestBodyParts`（`apps/daemon/src/prompts.ts`）と「確かめる所」の補足の1行
  - `fillTemplate` の省けない部分（`apps/daemon/src/pr-template.ts`）と、秘密の値の受け渡し（`apps/daemon/src/service.ts`）
  - テスト、仕様書・利用者向けの文書（日英）、作業履歴
- 対象外
  - must が残るときにマージを止める・ドラフトにすること、問いの構造の記録・MCP、画面（`apps/web`）
  - 実装の PR の本文、成果のファイルの内容（`buildStepDocument`）、エージェントへの指示の文

## 確認したいこと

### must

なし

### should

1. テンプレートに沿わせる本文で、節をどこに置くか。
   - 推奨：summary（目的）の中で、冒頭の1文（「マージすると承認になります」）の後・「確かめる所」の前に置く。承認の案内の3行は footer（本文の最後）のままにする。
   - 理由：「確かめる所」より前に問いを見せるという依頼の意図に沿う。
   - 懸念：目的の見出しが無いテンプレートでは、summary ごと「sacty の記録」に畳まれ、PR を読む人は開かないと問いを読めない（件数と答え方の行は残す）。
2. 写す中身の上限を 6,000 文字にしてよいか。
   - 推奨：6,000 文字。should 5件と must 数件が収まる長さ。
   - 懸念：must が多い大きな成果物では後ろが切れ、PR を読む人が成果のファイルを開く手間が増える。

### 確認しないと決めたこと

- PBI-436（PR #483）との衝突：読み取りと組み立ては新しいファイルに置き、`prompts.ts` では 2 つの関数と `BodyParts` だけを変える。文書は既存の節に書き足さず、小さな節を足す。タスクの「進め方」の指定で決まるので確かめない。
- 人が本文を直していたとき（3方向のマージ）の結合のテスト：人が直していない場合だけにする。マージの振る舞いは PBI-334 のままで、今回は変えないため。

## 既定で決めたこと

- must・should の両方の札が見つかったときだけ件数を書く。片方だけのときや、札の下が箇条書きでない文のときは、形 D と同じに件数を書かない。
- Issue の自動クローズは、写した文の `close(s|d)`・`fix(es|ed)`・`resolve(s|d)` と `#` の間に U+200B を挟んで防ぐ。
- `withoutMentions` は `human-ask-notice.ts` から import せず、新しいファイルに同じ1行を持つ。`human-ask-notice.ts` が `prompts.js` を import しているので、import すると循環になる。

## 構成

| ファイル | 変更 |
| --- | --- |
| `step-questions.ts`（新規） | `readStepQuestions(output)` が節を読み取る。`stepQuestionsLines(read, path, form)` が本文の節の行と、省けない行を返す。依存は `@sacty/core` の `openingFence`・`closesFence` だけ |
| `prompts.ts` | 2 つの関数に `secrets?` を足す。`hideSecrets` → `withoutInternalPathsDeep` の後に節を組み込む。`BodyParts` に `keep?` を足す |
| `pr-template.ts` | `fillTemplate` が `parts.keep` を `keep` に足す |
| `service.ts` | `publishStepPullRequest` が 2 つの関数に `usedSecrets` を渡す |

## データ

`readStepQuestions` は次のどれかを返す（タスクの値には記録しない）。

| 種類 | 条件 | 本文 |
| --- | --- | --- |
| `empty` | 成果物が空 | 節を足さない |
| `missing` | 名前が「確認したいこと」の見出し・太字の札が無い（英語の成果物を含む） | 「確認したいこと：成果物から読み取れませんでした。成果のファイル `<path>` の冒頭で確かめてください。」の1行 |
| `none` | 節の本文が「なし」だけ（形 C）か、must・should とも「なし」 | 「確認したいこと：なし（must・should とも問いはありません）」の1行 |
| `counted` | must・should の札があり、それぞれ「なし」か箇条書き | 件数と中身 |
| `uncounted` | 節はあるが、上の決まりで数えられない（形 D など） | 件数を書かずに中身 |

## 処理の流れ

1. 節を探す。
   コードブロックの外にある ATX 見出しか太字の札のうち、名前が「確認したいこと」で始まる最初の行を節の始まりとする。「確認しないと決めたこと」や、本文の中に出る語は当たらない。
   節は、同じ深さか浅い見出し（太字の札は深さ 7）で終わる。
2. 札を読む。
   見出し・太字の札・箇条書きの頭（`- must：なし`・`- **should**`）にある must・should を、大文字か小文字かを問わずに読む。
   - 件数は、札の下でいちばん浅い箇条書き・番号付きの並びの項目の数にする。札の行の後ろが「なし」なら 0、「なし」以外の文があって並びが無ければ 1（`- should：…（推奨：…）`）にする。
   - 「確認しないと決めたこと」の見出し・札・行から節の終わりまでは、写さない。
3. 写す中身を整える。
   秘密を伏せて内部のパスを置き換えた後の成果物から取り、6,000 文字で切る。切ったら「…（長いので省きました。続きは成果のファイル `<path>` の「確認したいこと」の節で確かめてください）」を足す。
   閉じていないコードブロック・HTML のコメント・`<details>` を閉じ、@ メンションと閉じるキーワードを無効にして、最後に空行を置く。
4. 節を組み立てる。
   見出しは、テンプレートを使わない本文では `## 確認したいこと`、テンプレートに沿わせる本文では `**確認したいこと**` にする。
   - 1行目
     - must があるとき：「must 1件・should 2件。must は、後で答えが違うと分かると、それまでの作業が無駄になる問いです。」
     - must が無いとき：「should 2件（must はありません）。」
     - `uncounted` のとき：「人に決めてほしい問いがあります（件数は成果物の形から数えられませんでした）。」
   - 2〜3行目
     - 「- 答えるには、この PR にコメントしてください。sacty が取り込み、答えを成果物に反映します。」
     - 「- 答えずにマージすると、推奨の答えで次の工程に進みます（must も同じです）。」
   - その後に、写した中身を置く。
5. 本文に置く。
   テンプレートを使わない本文では、承認の案内の後・`## 確かめる所` の前に置く。テンプレートに沿わせる本文では、should 1 の推奨の位置に置く。
   1〜3行目（`none`・`missing` のときはその1行）を `keep` に入れる。
6. 「確かめる所」の見出しの直後に、「出典（引用・導出・推論）の確かめです。人に決めてほしい問いは「確認したいこと」に出ます。」を足す。
   足すのは PR の本文だけで、`provenanceGuideLines` は変えない。

本文は提出のたびに、そのときの `task.outputs[step]` から作る。\
そのため、答えて節から外れた問いは、再提出の本文からも消える。

## テスト観点

- [TV-1] 問いが両方あるとき（形 A）の、テンプレートを使わない本文の節
  - 入力：成果物の「## 確認したいこと」に `### must` 1件・`### should` 2件（推奨の答えを含む）と `### 確認しないと決めたこと` がある設計で、buildStepPullRequestBodyText を呼ぶ
  - 期待結果：承認の案内の後・「## 確かめる所」の前に「## 確認したいこと」があり、1行目に must 1件・should 2件と must の意味、続く2行に答え方（PR にコメント・答えずにマージすると推奨の答えで進む）があり、must・should の項目と推奨の答えが写され、「確認しないと決めたこと」の文は写されない
- [TV-2] 形 B の読み取りと件数
  - 入力：`- must：なし`、`- should` の下に番号付きの2件、その後に見出しでない行「確認しないと決めたこと」と箇条書きがある成果物
  - 期待結果：1行目が「should 2件（must はありません）。」で始まり、写した中身に「確認しないと決めたこと」以降の文が無い
- [TV-3] must だけ・should だけのとき
  - 入力：形 A で must 2件・should「なし」の成果物と、must「なし」・should 1件の成果物
  - 期待結果：前者は1行目に must 2件・should 0件と must の意味が出て、後者は「should 1件（must はありません）。」が出る
- [TV-4] 問いが無いとき
  - 入力：節の本文が「なし」だけ（形 C）・形 A で両方「なし」・形 B で両方「なし」の 3 つの成果物
  - 期待結果：どれも本文に「確認したいこと：なし（must・should とも問いはありません）」の1行が出て、件数・答え方の行と中身は出ない
- [TV-5] 件数を数えられないとき（形 D）
  - 入力：「## 確認したいこと」の下が `- **Q-1**：…` から `- **Q-3**：…` の並び（入れ子の箇条書きを含む）の成果物
  - 期待結果：1行目が件数を書かない「人に決めてほしい問いがあります（…）」で、「0件」「なし」の語が節に無く、答え方の2行と Q-1〜Q-3 の中身が出る
- [TV-6] 節が見つからないとき・成果物が空のとき
  - 入力：見出しが「## Open questions」だけの英語の成果物と、成果物が空の工程
  - 期待結果：前者は「0件」「なし」を書かずに成果のファイルのパスで確かめるよう案内する1行が出て、後者は本文に確認したいことの行が何も足されない
- [TV-7] 語「確認したいこと」を節の始まりと取り違えない
  - 入力：節より前の本文の文と、コードブロックの中に「## 確認したいこと」、本物の節（太字の札 `**確認したいこと**` で should 1件）がある成果物
  - 期待結果：件数が should 1件になり、写した中身が本物の節の項目だけになる
- [TV-8] テンプレートに沿わせる本文
  - 入力：目的・変更の見出しのある PR テンプレートと、形 A で must 1件・should 1件の成果物で buildStepPullRequestBodyParts と fillTemplate を通す
  - 期待結果：目的の見出しの中で、冒頭の1文の後・「**確かめる所**」の前に「**確認したいこと**」の節があり、件数・must の意味・答え方の2行・中身が出て、件数と答え方の行が fillTemplate の keep に入る
- [TV-9] 「確かめる所」の補足
  - 入力：出典の分類（確かめる項目 0件）がある設計で、2 つの本文の形を作る
  - 期待結果：どちらも「確かめる所」の直後に、出典の確かめであり人に決めてほしい問いは「確認したいこと」に出る旨の1行があり、「確かめる項目：0件」の語は変わらない
