# 設計：実装の工程から、承認済みの要求要件・設計の文書の誤りを直せるようにする

## スコープ

実装の工程の作業領域に、承認済みの要求要件・設計のファイルを置き、承認した中身を変えない直し（テスト・書式・リンクの誤り、レビュー・人の指摘への対応）をそのまま実装の PR に入れる。
直したファイルは、sacty が PR の本文に載せる。

- 対象
  - 実装の作業領域へのファイルの配置と、実装の PR のコミットへの取り込み（`service.ts`・`repository.ts`）
  - 直したファイルの記録と、実装の PR の本文の節（`packages/core` の `BranchPushed`・投影、`prompts.ts`）
  - 実装の指示と、PR のレビュー・戻し先の判断の指示（`prompts.ts`）
  - 仕様書・ユーザー文書（日英）、ADR の置き換え、作業履歴（`docs/worklog/`）、テスト
- 対象外
  - 既定のスキル（`default-context/skills/review/`）の、承認済みの文書を根拠として扱う決まり（受け入れ条件 5 のとおり、変えない）
  - 局所の設計の直し（`sacty-design-edit`）の検査と反映、変更の申し出の仕組み
  - 実装の工程のほかの工程（直し・分割の子タスクなど）の作業領域
  - 直した内容を `task.approved`（sacty が持つ承認済みの本文）へ読み戻すこと

## 確認したいこと

- Q-1（must）：ファイルを作業領域に置いて直させる方式でよいか。
  - 推奨：置く（A）。受け入れ条件 1 の「作業領域から読めて直せる」を文字どおり満たし、`tests/docs` のような検査も作業領域で再現できる。
  - 懸念：対案の、作業領域の外のまま `sacty-design-edit` を要求要件に広げる方式（B）を人が望んでいた場合、配置・取り込み・除外の作業がすべて無駄になる。
- Q-2（should）：直した内容を `task.approved` に読み戻さなくてよいか。
  - 推奨：読み戻さない。人が PR で直した文書も読み戻さない今の扱いと同じで、承認の根拠を書式の直しで動かさない。
  - 懸念：次の回の指示とレビューの子タスクに渡す承認済みの全文は、直す前の文のままになる。同じ誤りを AI のレビューが本文の写しから再び指摘すると、1 周増える。
- Q-3（should）：「中身を変えない直し」を機械で検査しなくてよいか。
  - 推奨：検査しない。指示で範囲を決め、PR の本文の節と差分を、次の AI のレビューと人のマージで確かめる（`sacty-design-edit` と同じ考え方）。
  - 懸念：実装が決定の文を書き換えても sacty は止めない。人が差分を読まずにマージすると、承認していない決定が入る。

確認しないと決めたこと
- 新しいイベントは足さない。既存の `BranchPushed` に省略できる項目を足す。前の版は知らない項目を読み捨てるので（`z.object` は strict でない）、版を戻せる。
- 人が PR で「この PR で直してよい」と明示した指摘は、受け入れ条件 2 の範囲なら直し、範囲の外なら変更の申し出にする、と指示に書く。範囲は受け入れ条件 2 が決めているため。

## 既定で決めたこと

- 置いたファイルと、公開のときのタスクブランチのファイルの両方が変わっていたら、上書きせずに公開を止める（`pr.failed`。人がタスクブランチで直した内容を消さない）。
- 「書き換えても PR に残らない・書式を直さず検査の設定を直す」の文は、旧来の最終レビューの経路（`feedbackLines`）も含め、すべて「作業領域のファイルを直す」に変える。
- PR の本文の節には、直したファイルのパスだけを sacty が載せる。何を・なぜ直したかは、指示で実装の説明（PR の本文の「変更」）に書かせる。

## 構成

| 所 | 変更 |
| --- | --- |
| 実装の作業領域の準備 | 実行の始めに、`stepPullRequests` のパスのファイルを、タスクブランチの最新から作業領域の同じパスに置く。置いた内容を作業領域の外（gitDir の下）に控える |
| `repository.ts` の `stage` | 置いたパスを、`.sacty-tools/` と同じくインデックスに載せない。差分・範囲の判定・文書だけの判定・`treeId`・公開が、置いたファイルを実装の変更と見ない |
| 実装の PR の公開（`service.ts`） | 置いたパスごとに、控え・作業領域・タスクブランチの 3 つを比べる。作業領域だけが変わっていれば `overrides` に入れる。変わっていなければ今の `keep` のまま。設計の直しは、その上に当てる |
| 記録 | `BranchPushed` に `documentFixes`（直したパスの一覧。省略できる）を足し、投影でその PR の分を和にして持つ |
| PR の本文 | 「承認済みの文書の直し」の節に、直したパスを並べ、何を・なぜ直したかは「変更」の節にあると書く |
| 実装の指示 | 新しい節に、ファイルの置き場所、直してよい範囲（受け入れ条件 2）、中身を変えるときは設計の直し・変更の申し出にすること、直したら実装の説明に何を・なぜを書くことを書く。`proposalLines`・`designEditLines`・`stepDocumentFixText`・`implementVerificationLines` の「作業領域に無い・変更できない」の文を合わせる |
| レビューの指示 | `reviewReworkLines` と戻し先の判断（7186 行目付近）の implement の説明に、「この PR の承認済みの文書の、中身を変えない誤りは implement で直せる」を足す。`needsDecisionLines` に、その誤りには `needs_decision` を付けないと足す |
| 文書 | ADR を足し、`20261101-0353-…` の決定 2・4 を置き換える（superseded に改名）。`docs/spec/approval.md`（固定の例外）、`docs/spec/tasks-and-steps.md`（提出の前の検証・実装の検証）、`docs/user/tasks.md` の日英 |

## エラー時の振る舞い

- 置いたファイルの直しだけで、コードの変更が無い回も、コミットを作る（`git.nothingToCommit` にしない）。
- 作業領域とタスクブランチの両方で同じファイルが変わっていたら、どのファイルかと直し方（どちらかに合わせてから再開）を示して止める。push しない。
- 実行の途中で置いたファイルが消されたときは、直していないものとして `keep` のままにする。

## テスト観点

- [TV-1] 実装の作業領域に、承認済みの要求要件・設計のファイルが置かれる
  - 入力：要求要件・設計の PR をタスクブランチにマージ済みのタスクで、実装の工程を始める
  - 期待結果：実装のエージェントの実行の時点で、作業領域の `stepPullRequests` の各パスに、タスクブランチの最新と同じ内容のファイルがある
- [TV-2] 作業領域で直した承認済みの文書が、実装の PR のコミットと本文に入る
  - 入力：実装のエージェントが、作業領域の requirements.md の囲まれていない仮リンクをバッククォートで囲んで提出する
  - 期待結果：push したコミットの requirements.md が直した内容になり、PR の本文の「承認済みの文書の直し」の節にそのパスが載る（公開の取り込みか本文の節の変更を戻すと、テストが落ちる）
- [TV-3] 直していないファイルは、タスクブランチの内容のまま入る
  - 入力：実行の途中に人がタスクブランチの design.md を直し、実装のエージェントは置いたファイルを変えずに提出する
  - 期待結果：push したコミットの design.md は人が直した内容で、PR の本文に「承認済みの文書の直し」の節が出ない
- [TV-4] 作業領域とタスクブランチの両方で同じファイルが変わっていると、公開を止める
  - 入力：実行の途中に人がタスクブランチの requirements.md を直し、実装のエージェントも作業領域の requirements.md を直して提出する
  - 期待結果：push せずに pr.failed で止まり、理由に requirements.md のパスと直し方が出る
- [TV-5] 置いたファイルは、作業領域の差分に出ない
  - 入力：置いたファイルを直し、コードも1ファイル変えた作業領域で、diff・diffFiles・diffStats を呼ぶ
  - 期待結果：結果に、変えたコードのファイルだけがあり、置いたファイルのパスが無い
- [TV-6] 置いたファイルの直しだけでも、コミットを作る
  - 入力：PR の指摘で実装に戻した回に、実装のエージェントが requirements.md だけを直し、コードを変えずに提出する
  - 期待結果：git.nothingToCommit にならず、requirements.md を直した新しいコミットが push される
- [TV-7] 作業領域の直しと設計の直しが、両方とも設計のファイルに入る
  - 入力：実装のエージェントが、作業領域の design.md の 1 か所を直し、別の箇所の sacty-design-edit も出す
  - 期待結果：push したコミットの design.md に、作業領域の直しと設計の直しの両方が入る
- [TV-8] 実装の指示に、置き場所・直してよい範囲・差し戻す範囲・記録のしかたが書かれる
  - 入力：要求要件・設計の PR があるタスクの、実装の工程の指示を作る
  - 期待結果：指示に、ファイルのパス、直してよい範囲（テスト・書式の誤り、中身を変えないレビュー・人の指摘への対応）、中身を変えるときは設計の直しか変更の申し出にすること、何を・なぜ直したかを実装の説明に書くことがあり、「作業領域に無い」「書き換えても PR に残らない」「凍結されていて、あなたは変更できません」の文が無い
- [TV-9] 承認済みの文書の PR が無いタスクでは、ファイルを置かず、指示も変わらない
  - 入力：既存の PR を引き継いだタスク（continuedPullRequest）の、実装の工程を始める
  - 期待結果：作業領域に成果物のファイルが置かれず、実装の指示に承認済みの文書の直しの節が無い
- [TV-10] レビューの子タスクと戻し先の判断の指示が、承認済みの文書の誤りを implement で直せると扱う
  - 入力：実装の PR のレビューの子タスクの指示（reviewReworkLines）と、工程のエージェントの戻し先の判断の指示を作る
  - 期待結果：両方に「この PR の承認済みの文書の、中身を変えない誤りは implement で直せる」の文と、その誤りに needs_decision を付けない文があり、要求要件・設計の決定を変える指摘は前の工程に戻す説明が残る
- [TV-11] 仕様書・ユーザー文書・ADR に、実装から承認済みの文書を直せることが書かれる
  - 入力：docs/spec/approval.md・docs/spec/tasks-and-steps.md・docs/user/tasks.md とその英語の版、ADR の差分
  - 期待結果：日英の両方に、作業領域に置く場所、直してよい範囲と差し戻す範囲、PR の本文の節、両方が変わったときに止まることが書かれ、新しい ADR と 20261101-0353 の ADR が置き換え元・置き換え先で相互にリンクされている
