# 設計：実装の工程から、承認済みの要求要件・設計の文書の誤りを直せるようにする

## スコープ

実装の工程の作業領域に、承認済みの要求要件・設計のファイルを置き、承認した中身を変えない直し（テスト・書式・リンクの誤り、レビュー・人の指摘への対応）をそのまま実装の PR に入れる。
直したファイルと、その差分・直した理由は、sacty が PR の本文に載せる。

- 対象
  - 実装の作業領域へのファイルの配置と、実装の PR のコミットへの取り込み（`service.ts`・`repository.ts`）
  - 直したファイルの記録と、実装の PR の本文の節（`packages/core` の `BranchPushed`・投影、`prompts.ts`）
  - 実装の指示と、PR のレビュー・戻し先の判断の指示（`prompts.ts`）
  - 仕様書・ユーザー文書（日英）、ADR の置き換え、作業履歴（`docs/worklog/`）、テスト
- 対象外
  - 既定のスキル（`default-context/skills/review/`）の、承認済みの文書を根拠として扱う決まり（受け入れ条件 5 のとおり、変えない）
  - 局所の設計の直し（`sacty-design-edit`）の検査と反映、変更の申し出の仕組み
  - 実装の工程のほかの工程（直し・分割の子タスクなど）の作業領域
  - 直した内容を `task.approved`（sacty が持つ承認済みの本文）へ読み戻すこと

## 確認したいこと

- Q-1（must）：ファイルを作業領域に置いて直させる方式でよいか。
  - 推奨：置く（A）。受け入れ条件 1 の「作業領域から読めて直せる」を文字どおり満たし、`tests/docs` のような検査も作業領域で再現できる。
  - 対案（B）は、作業領域の外のまま `sacty-design-edit` を要求要件に広げる。作る量は小さいが、実装は文書をファイルとして読めず、検査も作業領域で再現できない。#535 のように検査が落ちても、その場で原因を確かめて直せず、条件 1 を満たさない。
  - ADR 20261101-0353 の決定 2 の理由は、置いたパスを範囲の判定から外す（理由 1）と、直した内容を `overrides` で PR に入れる（理由 2）で手当てする。
  - 懸念：B を人が望んでいた場合、配置・取り込み・除外の作業がすべて無駄になる。
- Q-2（should）：直した内容を `task.approved` に読み戻さなくてよいか。
  - 推奨：読み戻さない。人が PR で直した文書も読み戻さない今の扱いと同じで、承認の根拠を書式の直しで動かさない。
  - 懸念：次の回の指示とレビューの子タスクに渡す承認済みの全文は、直す前の文のままになる。指示で PR・作業領域のファイルを正とさせるが、レビューが写しに従って直し済みの所を再び指摘すると、同じ先頭のまま `unchanged` で止まり、人の手が要る。
- Q-3（should）：「中身を変えない直し」を機械で検査しなくてよいか。
  - 推奨：検査しない。指示で範囲を決め、PR の本文の節に載せる差分を、次の AI のレビューと人のマージで確かめる（`sacty-design-edit` と同じ考え方）。
  - 懸念：実装が決定の文を書き換えても sacty は止めない。人が差分を読まずにマージすると、承認していない決定が入る。

確認しないと決めたこと
- 新しいイベントは足さない。既存の `BranchPushed` に省略できる項目を足す。前の版は知らない項目を読み捨てるので（`z.object` は strict でない）、記録を読める版には戻せる。前の版は置いたファイルを範囲の判定から外さないので、実装の途中のタスクで戻すと、置いたファイルが実装の変更に数えられる（ユーザー文書に書く）。
- 人が PR で「この PR で直してよい」と明示した指摘は、受け入れ条件 2 の範囲なら直し、範囲の外なら変更の申し出にする、と指示に書く。範囲は受け入れ条件 2 が決めているため。

## 既定で決めたこと

- 置いたファイルと、公開のときのタスクブランチのファイルの両方が変わっていて、内容が違えば、上書きせずに公開を止める（`pr.failed`。人がタスクブランチで直した内容を消さない）。
- 「書き換えても PR に残らない・書式を直さず検査の設定を直す」の文は、旧来の最終レビューの経路（`feedbackLines`）も含め、すべて「作業領域のファイルを直す」に変える。
- 直した理由は、実装が出力の `sacty-document-fixes`（パスと理由）で出す。sacty は push ごとに、パス・理由・差分（1 ファイル 40 行まで）を記録し、PR の本文に載せる。
- PR の本文に載せる理由は 500 文字までに切り、切ったことを示す。

## 構成

| 所 | 変更 |
| --- | --- |
| 実装の作業領域の準備 | 実行のたびに、`stepPullRequests` の各パスについて、控えが無いか、作業領域のファイルが控えと同じ（直していない）ときだけ、タスクブランチの最新を作業領域の同じパスに置き、控え（gitDir の下）を取り直す。控えと違う（直してある）ときは置き直さない。再実行・続き・再開・PR の指摘で戻した回に、push 前の直しを残すため |
| `repository.ts` の `stage` | 置いたパスを、`.sacty-tools/` と同じくインデックスに載せない。差分・範囲の判定・文書だけの判定・`treeId`・公開が、置いたファイルを実装の変更と見ない |
| 続きの実行の目印 | `workspaceFingerprint` は、`treeId` に置いたパスごとのファイルの内容のハッシュを足して作る。置いたファイルの直しだけで終わった続きの実行を、進んでいない（stalled）と数えない |

| PR の本文 | 「承認済みの文書の直し」の節に、push ごとのパス・理由・差分を並べる。理由が無ければ「理由の記載なし」と出す。パス・理由・差分のすべてに伏せ（`redactText`）を通す |
| 実装の指示 | 新しい節に、ファイルの置き場所、作業領域のファイルが指示に写した承認済みの全文より新しい正であること、直してよい範囲（受け入れ条件 2）、中身を変えるときは設計の直し・変更の申し出にすること、直したら `sacty-document-fixes` に何を・なぜを書くことを書く。`proposalLines`・`designEditLines`・`stepDocumentFixText`・`implementVerificationLines` の「作業領域に無い・変更できない」の文を合わせる |
| レビューの指示 | `reviewReworkLines` と戻し先の判断（7186 行目付近）の implement の説明に、次を足す。PR の承認済みの文書のファイルを、渡した全文の写しより新しい正とする。本文の節に載った中身を変えない直しは、想定どおりの差分として指摘しない。中身を変える直しは決定の変更として前の工程に戻す。この PR の文書の中身を変えない誤りは implement で直せる。`needsDecisionLines` に、その誤りには `needs_decision` を付けないと足す |
| 文書（ADR） | ADR を足し、`20261101-0353-…` の決定 2・4・5 を置き換える（superseded に改名し、置き換え先に、置き換わった部分を 1 行で書く）。`20261106-0005-…` は置き換えない。置いたファイルは `treeId` に入らないので、文書を検査しうる検証を使い回さない決まりは続く。前提の「作業領域に無い」が変わったことは、新しい ADR の影響に書く |
| 文書（仕様書・ユーザー文書） | `docs/spec/approval.md` の「画面での承認」（固定の例外の行）・「実装の PR の本文の組み立て」・「PR のレビューの子タスク」・「直しでは解消できない指摘での一時停止」・「PR の指摘の取り込み」（戻し先の判断）・「設計の直し（sacty-design-edit）」（土台）。`docs/spec/tasks-and-steps.md`（提出の前の検証・実装の検証・実装の指示・人が PR に足したコミットの取り込み・実装の PR の作成）、`docs/spec/event-log.md`（`documentFixes`）、`docs/user/tasks.md`。すべて日英 |

## エラー時の振る舞い

- 置いたファイルの直しだけで、コードの変更が無い回も、コミットを作る（`git.nothingToCommit` にしない）。
- 作業領域とタスクブランチの両方で同じファイルが変わっていて内容が違えば、どのファイルかと直し方（どちらかに合わせてから再開）を示して止める。push しない。
- 実行の途中で置いたファイルが消されたとき、控えが無いとき（更新の前に始まった実装の再開など）は、直していないものとして `keep` のままにする（文書を消す差分を入れない）。
- 置いたパスがシンボリックリンク・通常のファイルでないもの・作業領域の外へ解決されるものに変わっていたら、そのパスを示して止める（`pr.failed`）。push しない。

## テスト観点

- [TV-1] 実装の作業領域に、承認済みの要求要件・設計のファイルが置かれる
  - 入力：要求要件・設計の PR をタスクブランチにマージ済みのタスクで、実装の工程を始める
  - 期待結果：実装のエージェントの実行の時点で、作業領域の `stepPullRequests` の各パスに、タスクブランチの最新と同じ内容のファイルがある
- [TV-2] 作業領域で直した承認済みの文書が、実装の PR のコミットと本文に入る
  - 入力：実装のエージェントが、作業領域の requirements.md の囲まれていない仮リンクをバッククォートで囲み、sacty-document-fixes にパスと理由を書いて提出する
  - 期待結果：push したコミットの requirements.md が直した内容になり、PR の本文の「承認済みの文書の直し」の節にそのパス・理由・差分が載る（公開の取り込みか本文の節の変更を戻すと、テストが落ちる）
- [TV-3] 直した理由が、後の push の後も PR の本文に残る
  - 入力：1 回目の提出で requirements.md を理由付きで直し、PR の指摘で戻した 2 回目の提出では文書を直さずにコードだけを変える
  - 期待結果：2 回目の push の後の PR の本文にも、1 回目の requirements.md のパス・理由・差分が載る
- [TV-4] PR の本文の直しの節に載せる値が、伏せ・長さ・パスの限りを守る
  - 入力：実装のエージェントが requirements.md を直し、sacty-document-fixes に、秘密の値を含む 600 文字の理由の項目と、stepPullRequests に無いパス（src/index.ts）の項目を書いて提出する
  - 期待結果：PR の本文の節で、秘密の値が伏せられ、理由が 500 文字で切れて切ったことが示され、src/index.ts の項目は載らない
- [TV-5] 再実行・2 回目の回でも、push 前の直しが置き直しで消えない
  - 入力：実装のエージェントが作業領域の requirements.md を直した後、検証の失敗で同じ工程を再実行する（タスクブランチの requirements.md は変わっていない）
  - 期待結果：再実行の時点の作業領域の requirements.md は直した内容のままで、その回の提出で push したコミットにも直しが入る
- [TV-6] 直していないファイルは、タスクブランチの内容のまま入る
  - 入力：実行の途中に人がタスクブランチの design.md を直し、実装のエージェントは置いたファイルを変えずに提出する
  - 期待結果：push したコミットの design.md は人が直した内容で、PR の本文に「承認済みの文書の直し」の節が出ない
- [TV-7] 作業領域とタスクブランチの両方で同じファイルが変わっていると、公開を止める
  - 入力：実行の途中に人がタスクブランチの requirements.md を直し、実装のエージェントも作業領域の requirements.md を別の内容に直して提出する
  - 期待結果：push せずに pr.failed で止まり、理由に requirements.md のパスと直し方が出る
- [TV-8] 控えが無いときは、作業領域に無いファイルを削除と扱わない
  - 入力：控えが無く、作業領域に置いたパスのファイルも無い状態（更新の前に始まった実装の再開）で、コードを変えて提出する
  - 期待結果：push したコミットの requirements.md・design.md はタスクブランチの内容のままで、PR の本文に「承認済みの文書の直し」の節が出ない
- [TV-9] 置いたパスがシンボリックリンクなら、公開を止める
  - 入力：実装のエージェントが、作業領域の requirements.md を作業領域の外のファイルを指すシンボリックリンクに置き換えて提出する
  - 期待結果：push せずに pr.failed で止まり、理由に requirements.md のパスが出て、リンク先の内容はどのコミットにも入らない
- [TV-10] 置いたファイルは、作業領域の差分に出ない
  - 入力：置いたファイルを直し、コードも1ファイル変えた作業領域で、diff・diffFiles・diffStats を呼ぶ
  - 期待結果：結果に、変えたコードのファイルだけがあり、置いたファイルのパスが無い
- [TV-11] 置いたファイルの直しだけでも、コミットを作る
  - 入力：PR の指摘で実装に戻した回に、実装のエージェントが requirements.md だけを直し、コードを変えずに提出する
  - 期待結果：git.nothingToCommit にならず、requirements.md を直した新しいコミットが push される
- [TV-12] 何も変えない提出は、置いたファイルがあっても nothingToCommit で止まる
  - 入力：要求要件・設計の PR があるタスクの実装で、コード・置いたファイルのどちらも変えず、設計の直しも出さずに提出する
  - 期待結果：git.nothingToCommit になり、新しいコミットは push されない
- [TV-13] 置いたファイルの直しだけで終わった続きの実行を、進んでいないと数えない
  - 入力：実装のエージェントが未完了と申告し、続きの実行で requirements.md だけを直して、また未完了と申告して終わる
  - 期待結果：workspaceFingerprint が前の実行と違う値になり、その実行は stalled と数えられず、次の続きの実行に進む
- [TV-14] 作業領域の直しと設計の直しが、両方とも設計のファイルに入り、再開で二重に当たらず、直しの記録も残る
  - 入力：実装のエージェントが、作業領域の design.md の 1 か所を理由付きで直し、別の箇所の sacty-design-edit も出す。push がリモートに届いた後、BranchPushed の記録の前に止めて再開する
  - 期待結果：1 回目の push と再開の後のコミットの design.md に、作業領域の直しと設計の直しが 1 回ずつ入り、再開で pr.failed にならず、再開の後の BranchPushed の documentFixes と PR の本文に design.md のパス・理由・差分が載る
- [TV-15] 実装の指示に、置き場所・正の扱い・直してよい範囲・差し戻す範囲・記録のしかたが書かれる
  - 入力：要求要件・設計の PR があるタスクの、実装の工程の指示を作る
  - 期待結果：指示に、ファイルのパス、作業領域のファイルが写した全文より新しい正であること、直してよい範囲（テスト・書式の誤り、中身を変えないレビュー・人の指摘への対応）、中身を変えるときは設計の直しか変更の申し出にすること、何を・なぜ直したかを sacty-document-fixes に書くことがあり、「作業領域に無い」「書き換えても PR に残らない」「凍結されていて、あなたは変更できません」の文が無い
- [TV-16] 承認済みの文書の PR が無いタスクでは、ファイルを置かず、指示も変わらない
  - 入力：既存の PR を引き継いだタスク（continuedPullRequest）の、実装の工程を始める
  - 期待結果：作業領域に成果物のファイルが置かれず、実装の指示に承認済みの文書の直しの節が無い
- [TV-17] レビューの子タスクと戻し先の判断の指示が、承認済みの文書の誤りを implement で直せると扱う
  - 入力：実装の PR のレビューの子タスクの指示（reviewReworkLines）と、工程のエージェントの戻し先の判断の指示を作る
  - 期待結果：両方に、PR の文書のファイルを写しより新しい正とする文、本文の節に載った中身を変えない直しを指摘しない文、「この PR の承認済みの文書の、中身を変えない誤りは implement で直せる」の文、その誤りに needs_decision を付けない文があり、要求要件・設計の決定を変える指摘は前の工程に戻す説明が残る
- [TV-18] 仕様書・ユーザー文書・ADR に、実装から承認済みの文書を直せることが書かれる
  - 入力：docs/spec/approval.md・docs/spec/tasks-and-steps.md・docs/spec/event-log.md・docs/user/tasks.md とその英語の版、ADR の差分
  - 期待結果：日英の両方に、作業領域に置く場所と置き直さない条件、直してよい範囲と差し戻す範囲、PR の本文の節（パス・理由・差分、伏せと理由の長さの上限）、両方が変わったときに止まること、BranchPushed の documentFixes、前の版に戻すと置いたファイルが実装の変更に数えられることが書かれ、approval.md では「画面での承認」の固定の例外・「実装の PR の本文の組み立て」・「PR のレビューの子タスク」・「直しでは解消できない指摘での一時停止」・「PR の指摘の取り込み」・「設計の直し（sacty-design-edit）」の各節が合わせてあり、新しい ADR と 20261101-0353 の ADR が置き換え元・置き換え先（決定 2・4・5）で相互にリンクされ、新しい ADR の影響に 20261106-0005 の扱いが書かれている
