# 要求要件：タスクの PR が、ほかのタスクのマージ済みの作業履歴を書き換えないようにする（PBI-497）

## スコープ

PR が、ほかのタスクのマージ済みの作業履歴（`docs/worklog/`）の本文を変えたら、CI で落として直し方を出す。エージェントへの指示と正本の決まりにも、同じことを書く。

- 対象
  - PR のときの CI の検査と、そのテスト
  - 既定のコンテキストの規則（`apps/daemon/default-context/rules.md`）と、sacty-docs スキルの2つの写し
  - 正本（`docs/README.md`・`docs/worklog/README.md`）の文と、このタスクの作業履歴・ADR
- 対象外
  - 既に書き換えられた過去の作業履歴を元に戻すこと
  - ADR の本文の書き換えの検査
  - main への push のときの検査（比べる PR が無い）
  - ベースとの競合のときの指示（`apps/daemon/src/prompts.ts`）の変更

## 確認したいこと

### must

- M-1：同じ PBI の別の PR が、マージ済みの同じファイルに書き足すことを、正本の決まりでも許すか。
  - 推奨：許す。`docs/worklog/README.md` の「別の PR で続きをしたら、新しいファイルを足す」を「新しいファイルを足すか、同じタスクのファイルに書き足す」に直し、`docs/README.md`・sacty-docs の写しも合わせる。受け入れ条件 2 と 5 を両方満たすには、正本を直すしかないため。
  - 懸念：「正本は変えず、検査で落とす」が正しかった場合、検査の通す範囲と正本の直しを作り直すことになる。
- M-2：PR の側のタスクを何で見分けるか。
  - 推奨：PR の題に含まれる最初の `PBI-<番号>` を使い、ファイル名の日付（`<YYYYMMDD>-`）を除いた部分の先頭の `pbi-<番号>-` と突き合わせる。題に番号が無ければ、日付の後が `pr-<その PR の番号>-` のファイルだけを同じタスクとみなす。内容の名前だけのファイル（`20261019-codex-prompt-double-dash.md` など7件）は、どの PR から見ても、ほかのタスクのものとして扱う。
  - 理由：sacty の PR の題は `PBI-<番号> …`・`[設計] PBI-<番号> …` の形（#590〜#604 で確かめた）。ブランチ名 `sacty/task-<ID>` に番号は無い。本文の `PR:` は `なし` のまま残ることがある（`docs/worklog/20261122-pbi-489-review-services.md`）。
  - 懸念：人が題に PBI 番号を書かずに出した PR は、自分のタスクのファイルへの書き足しでも CI が落ちる。題を直せば検査はやり直される（R-14）が、直すまで PR は落ちたまま残る。
- M-3：同じタスクのマージ済みのファイルで、別の PR に追記以外（既存の行の変更・削除）を許すか。
  - 推奨：許さない（追記だけを通す。切れたリンクの直しは除く）。マージベースに無い、その PR の中のファイルは、どの変更も通す。ひな形が求める `PR:` の値や「まだ無い（最初の提出）」の書き換えは、マージ前の同じ PR の中で済むため。
  - 懸念：後の PR が先頭の `PR:` に自分の番号を足すなど、既存の行を直す運用を望む場合、その PR は CI で落ち、新しいファイルを足す手間が増える。

### should

- S-1：エージェントが、提出の前に作業領域でこの検査を流せるようにするか。
  - 推奨：しない（CI だけで検査し、検査の判定はテストで確かめる）。sacty の作業領域は git のリポジトリでないことがあり、ベースとの差分を取れないため。
  - 懸念：エージェントが提出の前に気づけず、CI が落ちてから直す1周が残る。

### 確認しないと決めたこと

- 「マージ済み」の基準：PR の先頭とベースのマージベースにあるファイルとする。main を取り込むとマージベースが進むので、#590 の形も落とせる。
- 切れたリンクの直し：変更前のリンクの行き先が PR の先頭に無く、変わった行がリンクの行き先だけ違い、直した先が PR の先頭にあるものとする。行き先が PR の先頭にある（切れていない）リンクの付け替えと、リンクの文言の変更は落とす。sacty-docs の 6 が「切れたリンク」だけを許し、#590 の実例（ADR の名前の変更）がこれで通るため。
- 指示の置き場所：既定の `rules.md`（一般の言い方）と sacty-docs の 6 に置く。#588 は競合の解消ではない普通のコミットで書き換えたので、競合のときだけ出る指示では防げないため。
- 一般の言い方の語：「ほかのタスク・ほかの人が書いた、マージ済みの記録の文書」とし、sacty のタスクの「作業履歴」と取り違えない語にする。受け入れ条件 3 の求めのとおりのため。
- ADR：CI で決まりを強制する方針として、`docs/adr/` に1件足す。sacty-docs の 3（方針を決めたら ADR）に当たるため。

## 既定で決めたこと

- 仕様書・ユーザードキュメントは変えない（このリポジトリの CI は、どちらにも書かれていない）。日英の突き合わせも対象にならない。

## 受け入れの確かめ方

- 自動のテストで確かめること：R-1〜R-7・R-11・R-13〜R-15。合成の git のリポジトリ（ベースのコミット、main の取り込みのマージコミット、PR のコミット）と PR の題を入力にして、検査の合否と出力を確かめる。R-14 は、CI の設定が題の変更で検査を起動し、題を変えた入力で判定が変わることを確かめる。検査を外して R-1〜R-3・R-13・R-15 のテストが落ちることも確かめる。`npx vitest run tests/docs` も通す。
- 差分で確かめること：R-8〜R-10・R-12 の文書の中身。
- 人が確かめること：GitHub Actions の実際の PR で、R-1 の形の変更が落ち、R-6 の形の変更が通ること。題を変えると検査がやり直されること。
  - 懸念：ベースの履歴の取り方や起動の条件などの CI の設定が実際の環境と違うと、検査が素通りするか古い結果が残り、#588・#590 と同じ書き換えがまたレビューまで残る。
