# 要求要件：再レビューで新しく出す要修正を、実際の利用で起きるものと直しが生んだものに絞る（PBI-500）

## スコープ

再レビュー（2回目以降）で新しく出す要修正を、直しが生んだ後退・直っていない前回の要修正・実際の利用で起きる不具合に限り、それ以外を提案にする。
あわせて「外部の者が意図して揃えられる条件は数えない」を攻撃を想定する入力とセキュリティに限り、同じ原因が続くときは範囲を絞って提案にできるようにする。

- 対象
  - 既定のレビューのスキル（`review-execution`、`review-dispatch` の `pr-review`・`aggregation`・`self-review`）
  - sacty のレビューの指示（`apps/daemon/src/prompts.ts` の PR レビューの再レビューと、自己レビューの2回目以降）とテスト
  - 仕様書（`context`・`tasks-and-steps`・`approval` の日英）、ADR、作業履歴
- 対象外
  - 人の再開の補足をレビューに渡すこと（PBI-499）と、自己レビューの回数の上限
  - 初回のレビューの重さの表と、PR の判定（要修正が1件以上なら「修正が必要」）

## 確認したいこと

### must

- 自己レビューの2回目以降にも、R-1・R-4 の決まりを当てるか。
  推奨：当てる。`aggregation` の同じ原因の決まりは PR レビューと自己レビューで共通で、片方だけ変えると受け入れ条件 5 の「食い違わない」を満たしにくい。
  懸念：当てないのが正しかった場合、自己レビューの指示・スキル・テストの直し（R-12 と、R-13 の自己レビューの分）が無駄になり、提出の前に直すはずの要修正が提案に落ちます。
- R-3（細工した入力を条件として数える）を、初回のレビューにも当てるか。
  推奨：当てる。数え方は初回と再レビューで共通で、受け入れ条件 2 は回を限っていない。受け入れ条件 4 の「初回の重さの決まり」は重さの表と不適合の扱いを指すと読む。
  懸念：初回は変えない意図だった場合、初回の要修正が減り、数え方を初回用と再レビュー用に分けて作り直すことになります。

### should

- 再レビューで、ふつうの使い方か1つの条件で起き、影響が中で、受け入れ条件の不適合でない新しい指摘を、提案にしてよいか。
  推奨：提案にする（受け入れ条件 1 の文のとおり、影響が大か不適合のものだけを要修正に残す）。
  懸念：要修正に残す意図だった場合、データの不整合など影響が中の新しい不具合が、提案として直されずにマージされます。

### 確認しないと決めたこと

- 同じ先頭を判定し直す回：再レビューとして扱い、R-1 を当てる。前回のレビューがある回で、新しい差分が無いので (a) は起きず、扱いが分かれないため。
- 「直しが生んだ後退」：前回のレビューの先頭以降の差分が持ち込んだ欠陥とする。受け入れ条件 1 が「前回からの変更（直し）」と書いているため。
- R-4 と PBI-492 の人の判断の求め：補う。R-4 に当たる現れは要修正でなくなり印も付かず、当たらない現れには今の流れ（3回目以降は印を付けて止める）がそのまま残るため。
- 作業履歴の数：依頼の背景の数を、集計の範囲（PR #570〜#609）と、数え直していないことを添えて書く。依頼が今の数を残すことだけを求めているため。

## 既定で決めたこと

- `aggregation` の「判定・重さ・再レビューの範囲は変えない」は、R-4 の例外を書き足して残す。

## 要求

主語の「スキル」は既定のレビューのスキル、「指示」は sacty がレビューに渡す指示を指す。

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | スキル | 再レビューで新しく出す要修正を、(a) 前回以降の変更が生んだ後退、(b) 前回の要修正のうち直っていないもの（重さの見直しの決まりは今のまま）、(c) ふつうの使い方か1つの条件で起き、受け入れ条件・要求要件が述べる場面そのもので求められた振る舞いにならないか影響が大のもの、に限り、ほかの新しい指摘は今の決まりの重さによらず提案にする、と書いている |
| R-2 | スキル | 初回のレビューに R-1・R-4 を当てず、初回の重さの表と、直しが生んだ後退・不適合を要修正にする決まりを今のまま書いている |
| R-3 | スキル | 「外部の者が意図して揃えられる条件は数えない」を、要求要件・設計・依頼がその入力を信頼できないとするとき、またはセキュリティ（秘密の値・認証・認可・権限）にかかわるときだけに当て、それ以外は細工した入力も条件として数える、と書いている |
| R-4 | スキル | 同じ原因が続き、レビューが示した範囲を絞る案で残る現れが R-1 で要修正に当たらないものだけなら、その現れを提案にし、人の判断を求めない（印も `needsDecision` も付けない）、と書いている |
| R-5 | スキル | R-4 で提案にした回は、総評に、範囲を絞って提案にしたことと残る現れを書く、と定めている |
| R-6 | スキル | R-1〜R-5 の文に、sacty・このリポジトリ・特定の言語の名前を含まない |
| R-7 | 仕様書（日英） | `context`・`tasks-and-steps`・`approval` の記述が、R-1〜R-5 と食い違わず、日英が同じ内容である |
| R-8 | 作業履歴 | 背景の数（レビュー 143 回中 96 回が要修正、連鎖の型ごとの数、3回目以降の要修正約 48 件の 35%・65% の内訳）と、集計の範囲（PR #570〜#609）を書いている |
| R-9 | ADR | 新しい ADR が R-1・R-3・R-4 の方針を書いて `置き換え元` に PBI-358・PBI-492 の ADR を挙げ、その2件は `superseded-` の名前・置き換え済みのステータスにし、`置き換え先` に新しい ADR と置き換えた部分を1行で書いている |

## 受け入れの確かめ方

### 自動のテストで確かめること

- `apps/daemon/src/prompts.test.ts`：R-10〜R-12（前回のレビューの有無・自己レビューの回で指示を作り、決まりの文の有無を確かめる）
- `apps/daemon/src/default-skills.test.ts`：R-1〜R-5 の文がスキルにあること
- R-13：決まりの文を1つずつ外して上の2つを流し、落ちることを確かめて作業履歴に残す
- `npx vitest run tests/docs`：R-7〜R-9 の文書の検査

### 差分で確かめること

- R-1〜R-6：スキルの差分の文
- R-7〜R-9：仕様書・作業履歴・ADR の差分の文
