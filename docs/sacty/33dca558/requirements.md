# 要求要件：タスクの作成時に複数のリポジトリを指定する

## スコープ

タスクの作成時に、プロジェクトの対象のリポジトリを複数指定できるようにする。
指定したタスクは、いまのリポジトリを指定しないタスクと同じ進め方（オーケストレーターが進め方を選び、分割するときは子ごとにリポジトリを付ける）で進める。
そのうえで、リポジトリの候補を指定したものだけに絞る。
親の要求要件・設計・分割の工程は、指定した各リポジトリのコードを読み、リポジトリごとの要求要件と、何を実装するかを書く。

- 対象：作成のダイアログと `POST /api/tasks` の入力、指定したタスクの進め方（候補の絞り込み・コードの読み方）、docs
- 対象外
  - 再実行・派生・スケジュールタスク・テンプレートの入力で、複数を指定すること
  - 作成の後に、指定したリポジトリを変えること
  - 別のリポジトリの子の間の依存の扱い（いまどおり、依存先が片付くまで待つ）

## 確認したいこと

### must

- M-1：複数の指定は、新しい経路にしないでよいか。いまのリポジトリを指定しないタスクの経路に「候補の絞り込み」として足す形を考えている。
  - 推奨：足す。
    分割・子のリポジトリの照合・統合レビューの写しの並べ方はすでにある。
    経路が2つになると、仕様と実装の保守が倍になる。
  - 懸念：依頼者が別の進め方（例：作成の直後に必ずリポジトリごとの子を作る）を考えていた場合、R-7・R-11 と設計を作り直すことになる。
- M-2：進め方を `split` に固定せず、オーケストレーターに選ばせるか。
  - 推奨：選ばせる。
    調べて1つのリポジトリで足りれば、指定の中から1つを選んで分けずに進める。
    コードを変えない仕事なら investigate などにする。
  - 懸念：依頼者が「指定したら必ずリポジトリごとの子タスク」を期待していた場合、PR が1つだけのタスクができ、利用者が指定の意味を取り違える。

### should

- S-1：分割で、指定したリポジトリの一部にだけ子を作ること、1つのリポジトリに複数の子を作ることを許すか。
  - 推奨：どちらも許す。
    変更が要らないリポジトリに、中身の無い子を作らせないため。
  - 懸念：全部のリポジトリに子を求める場合は、分割の答えの検査と止め方を足す作業が要る。
- S-2：複数を指定したタスクを再実行・派生したとき、指定を引き継ぐか。
  - 推奨：今回は引き継がない（入力は単数の `repo` のまま）。
    依頼が「タスク作成時」だけを書いているため。
  - 懸念：再実行で「リポジトリ無し」を選ぶと、候補がプロジェクトの対象全体に戻り、利用者は絞り直せない。
- S-3：API は、単数の `repo` を残して、複数を渡す項目を別に足すか。
  - 推奨：足す。
    両方を渡したら断り、1件だけ渡したら単数の `repo` と同じに扱う。
  - 懸念：`repo` に配列も受ける形を望む場合、API の例と入力の検査を作り直す。
- S-4：複数の指定に上限を設けるか（1件の指定は R-9 のとおり単数の `repo` と同じに扱い、複数は2件から）。
  - 推奨：10 件を上限にする（R-1・R-2・R-14）。
    指定したリポジトリはすべて、親の工程で写しを用意して読む（R-10）。そのため、件数に比例して準備の時間と指示の量が増える。
  - 懸念：11 件以上にまたがるタスクでは、利用者が全部を指定できない。その場合は、リポジトリを指定しないタスク（候補はプロジェクトの対象全体）で作ることになる。上限を設けないなら R-14 を消す。

### 確認しないと決めたこと

- 依頼の「承認されたら子タスクを作る」の承認は、設計の承認とする。
  分割案を人が承認しないという ADR（20261012-0226）の決定が、置き換えられずに残っているため。
- スケジュールタスク・テンプレートには広げない。
  依頼が「タスク作成時」だけを書いているため。
- 親の工程で、各リポジトリのコードを読む（R-10）。
  リポジトリごとに何を実装するかは、コードを読まないと設計できないため。
- 作業領域での写しの並べ方と、作業履歴のイベントの形は、設計で決める。

## 既定で決めたこと

- 同じリポジトリを重ねて指定したら、1つにまとめる。
- 情報収集は、指定したリポジトリをすべて読む（いまの「多くても3つ」の目安を当てない）。

## 受け入れ条件

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | デーモン | タスクの作成の入力で、プロジェクトの対象のリポジトリの一覧を受け付ける（複数は 2〜10 件。1件は R-9） |
| R-2 | 作成のダイアログ | リポジトリを 2〜10 件選んでタスクを作れる（ja・en の文言） |
| R-3 | デーモン | 単数の `repo`・`noRepo` を持つ既存の作業履歴のタスクを、変更前と同じリポジトリと進め方で読む |
| R-4 | デーモン | 単数の `repo` の入力（省略・`null` を含む）を、変更前と同じ意味で受け付ける |
| R-5 | docs | docs/spec（tasks-and-steps・split-and-integrate）と docs/user/tasks の ja・en に、複数を指定したタスクの作り方と進み方を載せる |
| R-6 | docs | 方針の ADR と、このタスクの worklog を足す |

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-7 | リポジトリを2件以上指定してタスクを作ったとき | デーモン | 指定したリポジトリの一覧を持つ、リポジトリの決まっていないタスクとして記録する |
| R-8 | リポジトリを2件以上指定したタスクを表示したとき | タスクの一覧と詳細 | 指定したリポジトリをすべて表示する |

| ID | 状態 | システム | 応答 |
| --- | --- | --- | --- |

| R-11 | 複数を指定したタスクで、リポジトリが決まっていない間 | デーモン | オーケストレーターの選ぶリポジトリ・止まったタスクで人が選ぶリポジトリ・分割の子のリポジトリ・情報収集が読む候補を、指定したリポジトリだけにする |
| R-12 | 複数を指定したタスクの設計の工程の間 | 設計の工程の指示 | 指定したリポジトリごとに、そのリポジトリで実装することを書く節を求める |
| R-18 | 複数を指定したタスクの要求要件の工程の間 | 要求要件の工程の指示 | 各要求が、指定したリポジトリのどれに当たるかを示すよう求める |

| ID | トリガー | システム | 応答 |

## 受け入れの確かめ方

- 自動のテストで確かめること
  - R-1〜R-4・R-7〜R-19：偽の GitHub と偽のエージェントの答えで確かめる。
    R-3 は、変更前の形の作業履歴を読ませる。
    R-2・R-8 は、画面を描画して ja・en の文言を確かめる。
    R-2 は、さらに複数の候補を選んだ作成のフォームを送り、デーモンへの作成の入力に、選んだリポジトリがすべて入ることを確かめる。
  - R-5・R-6：差分で docs の中身を確かめ、`npx vitest run tests/docs` を通す。
- 人が確かめること
  - 両方のリポジトリに変更が要ると分かっている課題で、実際の2つのリポジトリを指定したタスクを作る。そのうえで、親の設計が両方のコードに基づいていること、承認の後にそれぞれのリポジトリへ子の PR が出ることを確かめる。
    偽の GitHub では、写しの用意と PR の作成先の誤りを見つけられないので、利用者の意図しないリポジトリに PR が出るおそれが残る。
