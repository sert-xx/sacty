# 要求要件：受け入れ条件がそろい設計の判断が要る依頼を、設計 → 実装で進める（PBI-420）

## スコープ

要求要件の工程を持たず、設計 → 実装（→ マージの後の監視）で進める組み合わせを足す。
オーケストレーターは、受け入れ条件がそろっていて設計の判断が要る依頼でこれを選び、人に確かめたいことは設計の「確認したいこと」で尋ねる。

- 対象：組み合わせの定義、選び方の指示、設計・実装・PR のレビュー・受け入れの確認の指示、画面の選択肢と表示（日英）、組み合わせの名前を受ける設定、仕様書・ADR・作業履歴・利用者向けの文書（日英）
- 対象外：
  - `sacty mcp` の `create_task` に組み合わせの引数を足すこと（指定は画面だけでできる）
  - 設計の判断が要らない依頼の選び方を変えること（R-5 は、いまの文を保つ要求）、`standard` を選んだ後に要求要件を飛ばす見直し、PR のレビューの見る範囲（PBI-419）
  - この組み合わせのタスクを、この組み合わせを知らない古い版に戻して読むこと（依頼は、新しい版が古い記録を読む向きだけを求める）

## 確認したいこと

### must

なし

### should

なし

### 確認しないと決めたこと

- 実装を含む組み合わせを列挙する所（既存の PR の引き継ぎ・リポジトリが要るもの・マージの後の監視の文書）：`standard` と同じく入れる（R-8）。
  依頼が「設計の工程は標準と同じ」と決めているので確かめない。
  `NEVER_LIGHT_PLANS` は `standard` を含まないので入れない。
- 工程の見直しで設計を飛ばすか：飛ばされない。
  見直しは工程が終わった後にしか走らず、この組み合わせでは設計が最初の工程なので、決めることが無い。

## 既定で決めたこと

- 実装の工程の指示に、タスクの内容（依頼の本文）を入れる（R-11）。
  いまの `standard` の実装の指示（設計がある経路）は入れないが、要求要件が無いと依頼の受け入れ条件を実装が読めないため。

## 要求

「理由（reason）」はオーケストレーターの答えの JSON の項目、「集めた情報」はタスクの開始時に集めた情報を指す。

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | 組み合わせの定義 | 工程が設計 → 実装 → マージの後の監視の順で、要求要件の工程を持たない組み合わせを、キー `skip-requirements` で持つ |
| R-2 | 選び方の指示 | 「受け入れ条件がそろっていて（実装だけを選ぶときと同じ基準）、設計の判断（新しい仕組み・層をまたぐ作りの選択）が要るなら、この組み合わせを選び、reason に要求要件を省いた理由と、人に確かめたい点（あれば 1 つずつ）を書く」旨の文を含み、「受け入れ条件が詳しくても設計の判断が要るなら standard」の文を含まない |
| R-3 | 選び方の指示 | 「R-2 の場合は、人に確かめたいこと（依頼に書かれていない判断・書き忘れ・ほかのタスクや PR との衝突・共有の状態や項目に新しい意味を載せる・公開の API や項目の変更の扱い）があっても要求要件を残さない」旨の文を含む |
| R-4 | 選び方の指示 | 依頼が曖昧・受け入れ条件がそろっていない・依頼と文書やコードや方針が食い違い作るものが変わる・判断しきれない、のどれかなら要求要件を残す旨と、R-3 にも当たるときは R-4 を優先する旨の文を含む（R-3 の衝突はほかのタスクや PR との衝突、R-4 の食い違いは依頼と文書・コード・方針の間のもの） |
| R-5 | 選び方の指示 | 設計の判断が要らないときは、人に確かめることが無ければ `direct`、あれば `skip-design` を選ぶ旨の文を保つ（いまの選び方と同じ） |
| R-6 | 画面 | 新しいタスクの進め方の選択肢と、組み合わせの名前・工程の並びの表示に、この組み合わせを日本語「要求要件を省く」・英語「Skip requirements」で出す |
| R-7 | 設定 | 組み合わせの名前を受ける設定（`budget.per_plan_usd` など）で、この組み合わせのキーを受ける |
| R-8 | 実装の組み合わせの列挙 | 既存の PR を引き継げる組み合わせ・リポジトリが要る組み合わせ・マージの後の監視の文書に、この組み合わせを `standard` と同じく含める |
| R-9 | sacty | この組み合わせを知らない版が書いたタスクと作業履歴を、変更の前と同じに読む |

### イベント駆動

条件の「設計 → 実装のタスク」は、組み合わせが `skip-requirements` のタスク（オーケストレーターが選んだものと人が指定したものの両方）を指す。

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-10 | 設計 → 実装のタスクの設計の工程を実行するとき | 設計の指示 | 要求要件の工程を省いたことと、タスクの内容と集めた情報を要求要件として扱うことを書き、人が指定したタスクでは「オーケストレーターの判断で」と書かない |
| R-11 | 設計 → 実装のタスクの実装の工程を実行するとき | 実装の指示 | タスクの内容を含み、要求要件が無く依頼と承認済みの設計を基準にする旨を書き、「承認済みの要求要件」を前提にした文を含まない |
| R-12 | 設計 → 実装のタスクの PR のレビュー・受け入れの確認・最終レビュー（統合レビューの基準）の文を作るとき | 各指示 | 基準を依頼と設計とし、「承認済みの要求要件」を前提にした文を含まない |
| R-13 | オーケストレーターがこの組み合わせを選び、reason を返したとき | 設計の最初の実行の指示 | reason を JSON のデータとして含め、挙げた点を「確認したいこと」に出すか「確認しないと決めたこと」に理由つきで書くよう指示する |
| R-14 | 人がタスクの作成時に画面でこの組み合わせを指定したとき | オーケストレーター | 組み合わせを選び直さず、設計 → 設計の承認（設計の PR のマージ） → 実装の順に進める |

### 文書

| ID | システム | 応答 |
| --- | --- | --- |
| R-15 | リポジトリの文書 | 仕様書・利用者向けの文書（日英）・ADR・作業履歴を `docs/README.md` の方針どおりに直す。PBI-283・PBI-288 の ADR の「設計の判断が要るなら `standard`」を新しい ADR が置き換えた関係を書く |

## 受け入れの確かめ方

### 自動のテストで確かめること

- この組み合わせのタスクが、設計 → 設計の承認 → 実装の順に進み、要求要件の工程を持たない（R-1・R-14）
- 人が指定したとき、オーケストレーターの答えにかかわらず選び直さない（R-14）
- 選び方の指示に R-2〜R-5 の文（reason に確かめたい点を挙げる文・R-4 を優先する文を含む）があり、「設計の判断が要るなら standard」の文が無い
- 設計の最初の実行の指示に reason が渡り、reason が無いときと他の組み合わせでは渡らない（R-13）。設計の指示に R-10 の文があり、人が指定したタスクでは「オーケストレーターの判断で」が無い
- 実装の指示が R-11 を満たす
- PR のレビュー・受け入れの確認・最終レビューの基準の文が R-12 を満たす
- 既存の PR の引き継ぎとリポジトリが要る組み合わせの判定が、この組み合わせを `standard` と同じに扱う（R-8）
- 画面の表示名（日英）と工程の並び、`budget.per_plan_usd` のキー（R-6・R-7）
- 既存の組み合わせ（`standard`・`direct` など）の作成と工程の選択を書いた記録を読むと、変更の前と同じ組み合わせ・工程になる（R-9）
- `tests/docs` が通り、差分で、仕様書・利用者向けの文書（日英）・マージの後の監視の文書にこの組み合わせがあり、新しい ADR と置き換えの関係・作業履歴がある（R-8・R-15）
