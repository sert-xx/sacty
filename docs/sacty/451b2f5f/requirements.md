# 要求要件：受け入れ条件がそろい設計の判断が要る依頼を、設計 → 実装で進める（PBI-420）

## スコープ

要求要件の工程を持たず、設計 → 実装（→ マージの後の監視）で進める組み合わせを足す。
オーケストレーターは、受け入れ条件がそろっていて設計の判断が要る依頼でこれを選び、人に確かめたいことは設計の「確認したいこと」で尋ねる。

- 対象：組み合わせの定義、選び方の指示、設計・実装・PR のレビュー・受け入れの確認の指示、画面の選択肢と表示（日英）、組み合わせの名前を受ける設定、仕様書・ADR・作業履歴・利用者向けの文書（日英）
- 対象外：
  - `sacty mcp` の `create_task` に組み合わせの引数を足すこと（確認したいこと S-1）
  - 設計の判断が要らない依頼の選び方、`standard` を選んだ後に要求要件を飛ばす見直し、PR のレビューの見る範囲（PBI-419）

## 確認したいこと

### must

なし

### should

- S-1：`sacty mcp` の `create_task` でこの組み合わせを指定できるようにするか。
  - 推奨：しない（画面でだけ指定できる）。
    いまの `create_task` はどの組み合わせも指定できず、`docs/spec/mcp-server.md` が「進め方を送らない」と決めているので、「ほかの組み合わせと同じ方法」はこれに当たる。
  - 懸念：依頼者が MCP からの指定を求めていた場合、MCP の利用者はこの進め方を指定できず、引数の追加と仕様書・ADR の改訂を別のタスクでやり直すことになる。
- S-2：組み合わせのキーと表示名を何にするか。
  - 推奨：キー `skip-requirements`、表示名「要求要件を省く」・「Skip requirements」。
    既存の `skip-design`（設計を省く）とそろう。
  - 懸念：キーは `budget.per_plan_usd` の設定と作業履歴に残るので、後で変えると、利用者の設定と古い記録の読み替えが要る。

### 確認しないと決めたこと

- 実装の組み合わせを列挙する所（オーケストレーターが挙げた (3)。既存の PR の引き継ぎ・リポジトリが要るもの・マージの後の監視の文書）：`standard` と同じく入れる（R-8）。
  条件 1 が「標準の設計の工程と同じ」と決めているので確かめない。
  `NEVER_LIGHT_PLANS` は `standard` を含まないので入れない。
- 工程の見直しで設計を飛ばすか（オーケストレーターが挙げた (4)）：飛ばされない。
  見直しは工程が終わった後にしか走らず、この組み合わせでは設計が最初の工程なので、決めることが無い。

## 既定で決めたこと

- 実装の工程の指示に、タスクの内容（依頼の本文）を入れる（R-11）。
  いまの設計がある経路は入れないが、要求要件が無いと依頼の受け入れ条件を実装が読めないため。

## 受け入れの確かめ方

### 自動のテストで確かめること

- この組み合わせのタスクが、設計 → 設計の承認 → 実装の順に進み、要求要件の工程を持たない（R-1・R-14）
- 人が指定したとき、オーケストレーターの答えにかかわらず選び直さない（R-14）
- 選び方の指示に R-2〜R-5 の文がある
- 設計の最初の実行の指示に reason が渡り、reason が無いときと他の組み合わせでは渡らない（R-13）。設計の指示に R-10 の文がある
- 実装・PR のレビュー・受け入れの確認の指示が R-11・R-12 を満たす
- 画面の表示名（日英）と工程の並び、`budget.per_plan_usd` のキー（R-6・R-7）
- 既存の組み合わせの記録を読むテストと `tests/docs` が通る（R-9・R-15）
