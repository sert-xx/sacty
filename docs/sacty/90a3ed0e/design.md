# 設計：PR のレビューの「判定なし」を、レビューができなかった場合だけにする

## スコープ

主対象（差分、または本文で示された主対象の文書）を読めたレビューには、確かめられなかった所があっても判定を付けさせる。
判定なしは、主対象を読めなかったときだけにする。
要求要件・設計の PR では、判定なしで指摘も無い回では直しに入らず、人を待つ。

- 対象
  - sacty のレビューの指示（`apps/daemon/src/prompts.ts` の判定の節・`VERDICT_ABSENT_LINE`）
  - 要求要件・設計の PR で判定なし（`absent`）の回を受けたときの扱い（`service.ts`・新しいイベント・画面の作業履歴の文言）
  - 既定のスキル `review-dispatch` の `pr-review.md`・`aggregation.md`
  - 仕様書・ユーザー文書（日英）、ADR の置き換え、作業履歴、テスト
- 対象外
  - 実装の PR で判定なしの回を受けたときの扱い（今のまま。その PR の工程の直しに入る）
  - 判定の読み取り（`absent`・`invalid` の読み分け、本文から判定を推し量らない決まり）と、判定なしの回の取り込み（`sactyReviewsOf`）
  - 提出の前の自己レビュー（`self-review.md`）。判定なしの扱いが無いので変えない

## 確認したいこと

### must

- Q-1：要求要件・設計の PR で、取り込んだ指摘がすべて子タスクの最後の回（判定が `absent`）の投稿で、その回に指摘が無い（行へのコメントが無く、本文に `[要修正]`・`[提案]` の札が無い）ときだけ、直しに入らずに新しいイベント `StepVerdictAbsentHeld` を記録して人の承認を待つ形でよいか。指摘がある回は、今のまま直しに入る。
  - 推奨：はい。今は、指摘の無い判定なしの回でも設計のやり直しと再レビューが回る（#571）。指摘がある回を止めないので、指摘は落ちない。札は PBI-436 の提案の選り分けと同じく読み、判定は推し量らない。
  - 懸念：新しいイベントを1件でも記録すると、前の版のデーモンは作業履歴を読めず起動できない。版を戻す運用がある場合、利用者が戻せなくなる。

### should

- Q-2：判定のブロックはあるが読めなかった回（`invalid`）は、今のまま直しに入る形でよいか。
  - 推奨：はい。本文に要修正が書かれていることがあり、止めると要修正が直されないまま人の承認待ちになる。
  - 懸念：読み取りの失敗が続く PR では、`invalid` の回ごとに直しと再レビューが回り、費用が延びる。
- Q-3：本文で示された文書を主対象にしたレビューで、その文書を取得できないときは、差分を読めても判定なしにする形でよいか（根拠として読むだけの文書を取得できないときは、判定を付けて本文に書く）。
  - 推奨：はい。受け入れ条件 2 の「対象の文書を読めなかった」に当たる。主対象でない文書は、受け入れ条件 1 の「確かめられなかった所」として扱う。
  - 懸念：根拠の文書と照らせば見つかる食い違いがあっても、判定が「指摘なし」なので、人が見落としうる。

### 確認しないと決めたこと

- スキル `pr-review` で「見られなかった観点（親が代わりに見ても見られなかった）」があり、`must` が無いときも、判定を付ける。受け入れ条件 1 と利用者の決定（2026-11-22）がこの場合を含むので、人に確かめない。
- 受け入れ条件 6 の「自己レビュー」は、sacty が自分の PR に付ける PR のレビューの子タスクと読む。判定の指示は `buildPrompt` の1か所にあり、子タスクと、GitHub から取り込んだレビューだけのタスクが共有している。提出の前の自己レビューには判定なしの扱いが無いので、どちらの読み方でも変える所は同じになる。
- 指摘なしの回が増えるので、リスク評価の付く回・見守りが完了する回・再レビューを絞る回も増える。判定なしを減らす依頼の目的どおりの結果なので、人に確かめない。

## 既定で決めたこと

- `VERDICT_ABSENT_LINE` は「判定：付いていません（レビューが判定を付けませんでした。差分や対象の文書を読めなかったレビューには、判定を付けません。本文と行へのコメントを確かめてください）」にする。
- `pr-review.md` の、見られなかった観点がある回は、本文の最初に確かめられなかった所を書く。判定を付ける回なので、「レビューを完了できませんでした」「確かめられた範囲での暫定」は書かない。
- 集約の記録の `verdict` の `incomplete` は、自己レビューのためだけに残す。PR のレビューでは使わず、`must` の有無で `passed`・`changes_required` にする。

## 構成

| 場所 | 変えること |
| --- | --- |
| `prompts.ts` 判定の節 | 付けないのは、主対象（差分。本文で示された文書を主対象にしたときはその文書）を読めなかったときだけ。主対象を読めれば、作業領域のコードや根拠の文書を読めなくても判定を付ける。確かめられなかった所があっても、`must` が無ければ `suggestions`・`no_findings` を付け、確かめられなかったことを本文の最初に書く。CI の実行中・画面を確かめられない・環境で動かないテストは、判定を付けない理由にしない、と明記する。`changes_required` の行は変えない |

## 影響範囲

- `StepVerdictAbsentHeld` を記録した後は、前の版のデーモンに戻せない。このことを ADR の影響に書き、`event-log` の種類の数を 144 から 145 に直す。

## テスト観点

- [TV-1] 確かめられなかった所があっても、要修正が無ければ判定を付けさせる指示になっている
  - 入力：PR のレビューの子タスクと、GitHub から取り込んだレビューだけのタスクのそれぞれで、レビューの工程の指示を作る
  - 期待結果：どちらの指示の判定の節にも、確かめられなかった所があっても要修正が無ければ suggestions か no_findings を付け、確かめられなかったことを本文の最初に中身の言葉で書くとあり、「無ければ付けません」の文が無い
- [TV-2] 判定を付けないのは、主対象を読めなかったときだけと指示する
  - 入力：レビューの工程の指示を作る
  - 期待結果：判定の節で、判定を付けない場合が主対象（差分、または本文で示された主対象の文書）を読めなかったときだけになっていて、主対象を読めれば作業領域のコードや根拠の文書を読めなくても判定を付けるとあり、付けないときに理由を本文の最初に書かせる文が今のまま残っている
- [TV-3] CI の実行中・画面の見え方・環境で動かないテストを、判定を付けない理由にしないと指示する
  - 入力：レビューの工程の指示を作る
  - 期待結果：判定の節に、CI の実行中・画面の見え方を確かめられない・レビューの環境で動かないテストがあることは判定を付けない理由にせず、本文に書くとある
- [TV-4] 要修正があるときの changes_required の付け方が変わっていない
  - 入力：レビューの工程の指示を作る
  - 期待結果：確かめられなかった所があっても、今回の先頭のコミットで成り立つ要修正の指摘があれば changes_required を付ける文と、changes_required の定義の行が起点のコミットと同じ意味で残っている
- [TV-5] 判定なしの回の本文の判定の行が、読めなかったことを理由として示す
  - 入力：判定のブロックが無い（verdictMissing が absent）レビューの結果から、投稿する本文を作る
  - 期待結果：判定の行が「判定：付いていません（レビューが判定を付けませんでした。差分や対象の文書を読めなかったレビューには、判定を付けません。本文と行へのコメントを確かめてください）」になり、「確かめられなかった所がある」を含まない
- [TV-6] 要求要件・設計の PR で、指摘の無い判定なし（absent）の回だけでは直しに入らず人を待つ
  - 入力：設計の PR の承認待ちで、PR のレビューの子タスクの最後の回が判定なし（missing が absent）で、行へのコメントが無く本文に [要修正]・[提案] が無いその回の投稿だけが取り込まれた
  - 期待結果：PullRequestReviewImported の後に StepVerdictAbsentHeld（step・number・commit・round）が記録され、ChangesRequested・ReworkJudged と設計の工程の実行が起きず、タスクは awaiting_approval のまま pendingReview が無くなる
- [TV-7] 判定を読めなかった回（invalid）と、実装の PR の判定なしの回は、今のまま直しに入る
  - 入力：(a) 設計の PR で子タスクの最後の回が missing invalid、(b) 実装の PR で子タスクの最後の回が missing absent で、それぞれ指摘の無いその回の投稿だけが取り込まれた
  - 期待結果：どちらも StepVerdictAbsentHeld が記録されず、起点のコミットと同じく ReworkJudged（理由 rework.reviewTaskUnreadable）が記録されてその PR の工程の直しに入る
- [TV-8] 要求要件・設計の PR で、判定なしの回に指摘があれば直しに入る
  - 入力：設計の PR で、子タスクの最後の回（missing absent）について、(a) 本文に [要修正] の指摘がある、(b) 行へのコメントに [提案] がある、(c) その回の投稿と人の要対応のコメントが一緒に取り込まれた
  - 期待結果：どれも StepVerdictAbsentHeld が記録されず、(a)(b) は ReworkJudged（理由 rework.reviewTaskUnreadable）で設計の工程の直しに入り、(c) は人の指摘を含めた直しに入る
- [TV-9] StepVerdictAbsentHeld の投影と作業履歴の文言
  - 入力：承認待ちで pendingReview があるタスクに StepVerdictAbsentHeld を投影し、作業履歴の文言を日英で作る
  - 期待結果：pendingReview が外れ、前提（承認待ち・pendingReview がある・PR の番号と工程が一致）を満たさなければ ActivityIntegrityError になり、文言が日英で「判定が付かなかったため直しに入らなかった」旨と、直させたいときの操作を示す
- [TV-10] 既定のスキルのレビューの判定の規則
  - 入力：apps/daemon/default-context/skills/review/review-dispatch/references/pr-review.md と aggregation.md
  - 期待結果：判定を書かないのは差分も作業領域も読めない・主対象の文書を取得できないときだけで、見られなかった観点があっても must の有無と重さで判定し、見られなかった所を本文の最初に書くとあり、PR のレビューでは incomplete を使わず、例に特定のリポジトリ・sacty に寄せた語が無い
- [TV-11] 仕様書・ユーザー文書・ADR の記述
  - 入力：docs/spec の tasks-and-steps・approval・context・event-log・risk-assessment・intake、docs/user/intake（それぞれ日英）、docs/adr
  - 期待結果：判定なしが主対象を読めなかった場合だけであること、要求要件・設計の PR で指摘の無い判定なし（absent）の回は直しに入らず人を待ち、指摘がある回は今のまま直しに入ること、StepVerdictAbsentHeld（種類の数 145）が日英で同じ内容で書かれ、新しい ADR が 20261114-0158 の判定の部分を置き換え（superseded に改名・置き換え先と置き換え元のリンク）、記録後は前の版に戻せないことが影響に書かれている
