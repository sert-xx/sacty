# 要求要件：実装の担当が、依頼と関係ないファイルを整形して差分を膨らませないようにする（PBI-484）

## スコープ

実装・修正の工程で、整形だけで変わったファイルを PR に入れないようにする。
sacty が提出の前の検証で担当の差分を検査し、そのようなファイルがあれば提出を受け付けず、担当に戻させて出し直させる。指示でも防ぐ。担当が依頼で求められたと申告した整形と、整形だけと安全に判定できない変更は残す。

- 対象
  - 実装の担当への指示（`apps/daemon/src/prompts.ts` の「提出の前の検証」）と、出し直しの指示
  - 提出の前の検証での、担当の作業領域の差分の検査
  - 仕様書 `docs/spec/tasks-and-steps`・`docs/spec/approval`、ユーザー文書 `docs/user/tasks`（日英）、作業履歴
- 対象外
  - sacty が PR のファイルを書き戻すこと（再開の補足で取りやめ）
  - リポジトリ全体の整形のやり直し、biome の版・設定の変更（依頼の範囲の外）
  - 依頼で変えたファイルの中の、別の設定での整形を検査で戻させること（指示だけで防ぐ。M-1）

## 確認したいこと

### must

- M-1：依頼で変えたファイルの中の、リポジトリと違う設定の整形（PR #524 の約 2000 行、#542）も防ぐか。
  推奨：指示（R-1）で防ぎ、検査では戻させない。整形だけの差分の塊を戻させると、受け入れ条件 3 が認める `npm run format` の結果も戻してしまうため。
  懸念：指示が守られないと、#524 のような同じファイルの中の膨らみは PR に残り、レビューの費用は減りません。
- M-2：防ぎ方を、sacty の検査で提出を受け付けず担当に戻させる形にし、出し直しが上限を超えたら受け付けるか（指示だけ・知らせるだけにしないか）。
  推奨：検査で受け付けずに戻させ（R-3）、指示（R-1・R-2）も足す。上限を超えたら受け付けて件数だけを知らせる（R-4。再開の補足の決定）。受け入れ条件 4 が提出を入力にしたテストを求め、条件 2 が「提出しない」を求めるため。
  懸念：上限を超えて受け付けた PR には、無関係な整形のファイルが残り、条件 2 を満たしません。レビューの担当と承認する人は、その分の差分をこれまでどおり読むことになります。指示だけを望んでいた場合は、検査・テスト・仕様書の作業の大半が無駄になります。
- M-3：整形だけのファイルが依頼で求められたかを、担当の申告で決めるか。
  推奨：申告されたものだけを残し（R-13）、申告の無いものは関連を確かめられないとして戻させる（R-3）。差分の形だけでは、依頼された整形と無関係な整形を区別できないため。
  懸念：整形を求める依頼で担当が申告を忘れると、出し直しを求められ、上限まで実行の費用が増えます。

### should

- S-1：検査を、biome 以外のリポジトリにも当てるか。
  推奨：当てる。ツールに依らず、sacty が構文を解析できる言語のファイルで、構文木が起点と同じときだけ整形だけとし（R-18）、それ以外は戻させない（R-7・R-12・R-17）。
  懸念：解析できる言語に限るので、それ以外の言語のファイルの整形は PR に残ります。
- S-2：出し直しの上限を何回にするか。
  推奨：2 回。整形を戻すだけの直しで、上限までに直らない担当は、さらに回しても直らないことが多いため。
  懸念：少なすぎると、無関係な整形が残ったまま受け付ける PR が増え、多すぎると、出し直しの実行の費用が増えます。
- S-3：担当に戻させたファイルのパスを、利用者に知らせないか。
  推奨：知らせない。一覧は担当への出し直しの指示にだけ渡し、PR の本文（引き継いだ PR と PR を作らないときはタスクの詳細）には、上限を超えて残ったときの件数だけを載せる（R-4・R-14・R-16。再開の補足の決定）。
  懸念：担当が依頼された整形の申告を忘れて戻すと（差分が無くなり PR を作らない場合を含む）、そのパスはどこにも出ず、承認する人は、求めた整形が消えたことに差分を読まないと気づけません。

### 確認しないと決めたこと

- 「依頼で変えたファイル」：差分に整形以外の変更を含むファイルと、担当が依頼で求められた整形と申告したファイルとする。担当が触ったファイルを記録する仕組みは無いため。
- 直しの回・セキュリティ対応・文書だけの依頼：どれの提出にも当てる。受け入れ条件 2 が実装の担当を限っていないため。
- 原因：実装で確かめ、作業履歴に書く（受け入れ条件 1）。biome の版・設定が原因なら別の件にする（依頼の範囲の外）。

## 既定で決めたこと

- 構文を解析できない言語と、空白が意味を持つのに構文木で表せると確かめていない言語（Python・YAML・Makefile・Markdown など）は、整形だけかを判定できないものとして戻させない（R-7）。

## 受け入れの確かめ方

- 自動のテストで確かめること
  - 合成の git の作業領域で、整形だけのファイルと整形以外の変更のファイルを含む提出が受け付けられず、出し直しの指示に前者のパスが載り、担当が戻した後の PR の差分が後者だけになる（R-3・R-6）。上限を超えたら受け付け、本文に件数だけが載る（R-4）。検査を戻すとテストが落ちる
  - 担当が戻さずに出し直すと、再検査で同じファイルが再び検出され、上限まで受け付けられない。出し直しの間に人が PR に足したコミットの変更は検出されない（R-18）
  - 整形だけのファイルを含まない提出で、差分が変わらない（R-5）。R-7・R-12 の入力と、申告したファイル（R-13）で出し直しを求めない
  - 文字列の内外 × 空白・改行・カンマ × 構文上の位置（`return` の直後、JSX のテキスト、テンプレート・正規表現の中、引数の区切り、末尾）の組み合わせで、構文木が変わるものは出し直しを求めず（R-12・R-17）、変わらないものだけで求める（R-18）
  - 担当が全部戻して差分が無くなった提出で、変更なしとして扱われる（R-14）。引き継いだ PR で、PR の題・本文が変わらず、タスクの詳細に件数と申告が載る（R-16）
  - 指示の文に、R-1・R-2・R-15 の内容がある（`prompts.test.ts`）
  - 仕様書・ユーザー文書・作業履歴の中身を差分で確かめる（R-9〜R-11）
- 人が確かめること：なし
