# 設計：整形だけで変わったファイルを、担当に戻させてから提出する（PBI-484）

## スコープ

実装・修正の工程の提出で、担当が整形だけで変えたファイル（申告の無いもの）を sacty が見つけたら、提出を受け付けず、同じセッションで担当に git の差分を見て戻させ、出し直させる。
sacty はどのファイルの内容も変えず、差分の本文も作らない。
書き戻しを前提にした従来の R-3・R-4 などは、担当に出し直させ、上限を超えたときに残った件数を知らせる方針に読み替える。
指示でも、リポジトリの設定の外での整形と、依頼の外のファイルの整形を止める。

- 対象
  - 指示：`apps/daemon/src/prompts.ts` の `implementVerificationLines`（実装・修正・直しの回・セキュリティ対応・文書だけの依頼の提出に共通）と、出し直しの実行の知らせ
  - 検査：`apps/daemon/src/formatting-only.ts`（新規）、`service.ts` の実装の実行の開始と検証待ち、`repository.ts`（ツリーどうしの差分・blob の読み取り）
  - 申告の読み取り：`prompts.ts` の `extractBlocks`
  - 記録・表示：`packages/core` のイベント・投影、PR の本文、Web のタスクの詳細
  - 文書：`docs/spec/tasks-and-steps`・`approval`・`event-log`（日英）、`docs/user/tasks`（日英）、作業履歴
- 対象外
  - JavaScript・TypeScript・JSON 以外の言語のファイル（R-7 で出し直しを求めない）
  - 引用符・セミコロン・括弧の付け外しなど、空白・改行・末尾のカンマ以外の整形（R-18 で整形だけとみなさない）
  - 「見逃しうる場合」に挙げたファイルの中の、担当の整形（検査から外す）

## 確認したいこと

### must

なし

### should

- Q-1：構文の解析に、`@babel/parser` をデーモンの実行時の依存に足してよいか。
  推奨：足す。`typescript` は開発時の依存（7 系はネイティブで、JavaScript から構文木を取る API が無い）で、デーモンの実行時に無いため。
  懸念：依存を増やしたくない場合、検査の実装を別の解析器で作り直す手間が増えます。
- Q-2：検査する言語を、JavaScript・TypeScript（JSX を含む）・JSON に限ってよいか（要求要件の S-1 の「解析できる言語」の範囲）。
  推奨：限る。PR #539・#524・#542 の膨らみはどれも TypeScript で、1つの解析器で扱えるため。
  懸念：CSS・Markdown・Python などの整形だけの変更は、出し直しを求めずに PR に残ります。
- Q-3：引用符（`'a'` と `"a"`）・セミコロン・括弧の付け外しを、整形だけとみなさずに残してよいか。
  推奨：残す。R-18 が除くのは位置と区切りの空白・改行・末尾のカンマだけのため。
  懸念：prettier の既定などで引用符まで変えたファイルは、出し直しを求めずに PR に残ります。
- Q-4（削除：起点を実行の開始の作業領域にしたので、人が PR のブランチで変えたファイルは検査に入らない）
- Q-5（削除：出し直しの上限は、要求要件の S-2 で 2 回に決まった）
- Q-6（削除：間の取り込みで変わったファイルは、R-20 で検査から外すと決まった）
- Q-7：`FormattingOnlyRejected` を一度記録したら、前の版のデーモンへ戻せない（`EventInput` で読めず起動できない）ことを受け入れてよいか。
  推奨：受け入れる。互換の層は作らず、不具合は直した版で直す（PBI-468 と同じ）。起点は既存の `AgentRunStarted` の任意の欄にして、新しい種類はこの1つに限る。
  懸念：出し直しを1回でも記録した後に不具合が見つかった運用者は、前の版へ戻せず、直した版が出るまで待つことになります。

## 既定で決めたこと

- 申告は、そのタスクの実装の工程のすべての回のものを合わせて使う（直しの回で申告し直さなくても残る）。
- 起点のツリー・差分・ファイルを読めないときは、止めずに、検査せずに受け付ける（R-7。セキュリティ対応の範囲の検査のように止めない）。
- 申告のパスは伏せた後の値で照らす。秘密値を伏せた後に同じになるパスどうしは取り違えうるが、ファイルが PR に残るだけで受け入れる。
- `.jsonc` は、コメント・末尾のカンマを許すかがツールで違うので検査しない（R-7）。

## データ

- `AgentRunStarted.payload.formattingBaseline`（任意。実装の工程だけ）：`tree`（起点の作業領域のツリーの ID。退避した git のメタデータに書く）・`merged`（間の取り込みの、前と後のツリーの ID の組の配列）。
- `FormattingOnlyRejected`（新規）：`count` だけ。パスは持たない。
- `FinalReviewSkipped.payload.formatting`（任意）：`remained`（上限を超えて残った件数）・`declared: {path, reason}[]`。
- 投影 `Task.formattingCheck`：提出ごとに最後の `FinalReviewSkipped` の値で置き換える。出し直しの回数は、起点を記録した後の `FormattingOnlyRejected` の数。
- 申告：理由は伏せの後に 300 文字で切る。パスは `validPath` を通らないもの・差分に無いものを捨て、タスクで伏せる秘密値を `redact` で伏せた値だけを記録・表示する。
- 前の版との互換（Q-7）：足した欄は前の版が読まずに捨てる。`FormattingOnlyRejected` は前の版が読めないので、戻せるのは最初の記録の前まで。
  - event-log（日英）に、戻す前に作業履歴の `activity` の表に `type` が `FormattingOnlyRejected` の行が無いことを確かめる手順と、種類の数（144 から 145）を書く。

## 起点（R-19・R-20）

- 起点は、一連の出し直しの最初の実行を始めたときの作業領域（実装の前の取り込みで入った、人が PR に足したコミットを含む）。取り直さない。
- 続きの実行（未完了の続き・申告の出し直し・整形の出し直し・時間切れの再開）は起点を引き継ぐ。間の取り込み（`PullRequestHeadMerged`・ベースブランチの取り込み）が作業領域を変えたら、取り込みの前と後のツリーを `merged` に足し、その間で変わったファイルを検査から外す。
- 検査は PR を出す前の取り込みより前に行うので、その取り込みで入る人の変更は検査に入らない。

## 見逃しうる場合

検査は担当の手元でのできる範囲のものとし、次のファイルは検査から外す（出し直しを求めず、提出の内容のまま PR に入る。担当の整形は PR に残る）。

- 一連の出し直しの間の取り込みで内容が変わったファイル（R-20）
- 追加・削除・名前の変更・モードの変更を含むファイル（内容の整形と同時にモードを変えたものを含む。R-19）
- パスが `validPath` を通らないファイル（日本語などの ASCII の外の文字・空白・タブ・改行を含むなど。申告できないため。申告しても捨て、表示もしない。R-19）
  - ASCII の外の文字を通さないので、Unicode の正規化の違いで申告と差分のパスが食い違うことは起きない。先頭が `-` の名前は通り、ほかと同じに検査する（sacty はパスを git の引数に渡さない）
- 整形だけか確かめられないファイル（R-7。上の対象外の言語と `.jsonc` を含む）

## 判定（R-12・R-17・R-18）

- 拡張子で解析の仕方を決める：`.ts`・`.mts`・`.cts` は typescript、`.tsx` は typescript と jsx、`.js`・`.jsx`・`.mjs`・`.cjs` は jsx で解析する。`.json` は、起点と提出の両方が `JSON.parse` を通るときだけ、式として解析する（末尾のカンマ・コメントを含む JSON は通らないので R-7）。
- 起点と提出の両方を解析し、構文木を比べる。除くのは位置（`start`・`end`・`loc`・`range`）と、括弧・末尾のカンマの位置（`extra.parenStart`・`extra.trailingComma`）だけ。
  - 文字列・テンプレート・正規表現・数値の `extra.raw`、JSX のテキストの値、コメントの種類と中身は比べる。
- どちらかが解析できない・テキストでない（NUL を含むなど）・読めないときは、整形だけとみなさない（R-7）。

## 影響範囲

- 担当が全部戻すと、既存の `NothingToCommitError` の扱いで変更なしになる（R-14）。PR を作った後の直しなら、今までどおり止まる。
- 作業履歴には、原因と再現のコマンド・結果を書く（候補：作業領域の外の写しへの `npx biome format`、依存に無い `npx prettier`）。
