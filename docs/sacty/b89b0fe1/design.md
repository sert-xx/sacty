# PBI-489 設計：PR のレビューの子タスクで、親の実装の工程のサービスを起動する

## スコープ

sacty が作った実装の PR のレビューの子タスクで、その PR の先頭を作った親の実装の実行と同じサービス（共用の compose を含む）を、レビューの実行の1回ごとに起動する。
起動・停止・後片付け・安全の検査は、今の工程の経路をそのまま使う。エージェントと compose のサービスのコンテナにメモリーの上限を付けて、需要の上限を保証する。daemon のすべての工程の実行の始まりを1つの容量の管理に通し、Docker のホストの空きと、実行中の実行の上限の合計から、始められるかを1件ずつ決める。レビューは、空きが足りないとき・起動に失敗したとき・PR の先頭に対応する記録が無いときに、サービス無しで続ける。

- 対象
  - `service.ts` の `serviceSpec`（子の `review` のときに、PR の先頭のコミットを作った親の実装の実行の `ServicesStarted` から指定を作る）、実行ごとの指定の固定、容量の管理（判定と予約）、起動の失敗の扱い
  - `ServicesStarted` の `compose` に、取得の元のリポジトリ（`repo`）を足す
  - `agents/docker.ts` の `dockerRunArgs` のメモリーの上限（`--memory`）、`services.ts` の `sanitizeCompose` のサービスのメモリーの上限と、Docker のホストの空きのメモリーを読む処理
  - `prompts.ts` の、起動しなかった理由を伝える指示の1行
  - 仕様書（`services.md`・`tasks-and-steps.md`・`approval.md`、日英）、利用者向けの文書（`docs/user/compose.md`、日英）、ADR・作業履歴、テスト
- 対象外
  - スキル `docker-services` の本文（PBI-486）。起動の失敗のときも、今の「サービスは起動していません」の版を置く
  - 要求要件・設計の PR のレビューの子タスク、PR の取り込みで作ったレビューだけのタスク
  - 起動の数・メモリーの上限の新しい設定、別の daemon・sacty の外のコンテナとの予約の共有

## 確認したいこと

### must

なし

### should

1. 空きが足りないとき、今の工程（調査・再現・実装など、レビューの子タスク以外）の実行を待たせるか。
   推奨：待たせる。この daemon のほかの実行が終わって空きが足りるまで待ち、ほかに実行中の実行が無ければ待たずに始める。
   懸念：混んでいる時間に、今の工程の始まりが遅れ、タスクの終わりが今より遅くなる。待たせないと、レビューの判定の後に始まった工程の分で空きを超え、両方のテストがメモリー不足で落ちうる。
2. 起動しなかったことと理由を、レビューの担当に伝えるか。
   推奨：伝える。指示に「サービス（compose・サービス名）を起動していません：理由」の1行を足し、スキルは本文を変えない。理由は、起動の失敗・空きの不足（空きと上限の合計）・PR の先頭に対応する記録が無い・共用の compose の取得の元が分からない、のどれか。
   懸念：伝えないと、担当は「サービスを使わない PR」と区別できず、DB が要るテストを確かめなかった理由を本文に正しく書けない。
3. メモリーの上限の値を、いくつにするか。
   推奨：固定の値にする。エージェントのコンテナは 3 GiB。compose のサービスは、compose に上限（`mem_limit`・`deploy.resources.limits.memory`）があればその値、無ければ 1 サービス 1 GiB。今のエージェントのコンテナの使用量は約 0.4 GB（このコンテナの `memory.peak`）。
   懸念：上限に届いたコンテナはその中で止められる（OOM）ので、今は通る大きなテストや DB が落ちうる。空きが 9.6 GiB の今の環境では、サービス付きの実行（4 GiB）は同時に 2 件までになる。既定の 3 本のうち 3 本目は、今の工程なら待ち、レビューならサービス無しになる。
4. PR の先頭に対応する記録を特定できないとき（人がコミットを積んだ先頭、`repo` の無い以前の版の共用の compose の記録）に、サービス無しで続けるか。
   推奨：続ける。先頭のコミットと同じ `commit` の親の `BranchPushed` が無いときと、記録の `compose` に `repo` が無いときは起動せず、should 2 の理由を伝える。
   懸念：人がコミットを積んだ PR と、この変更の前に実装した共用の compose の PR は、レビューで DB が要るテストが流れない。親の今の指定から推すと、PR と違う compose・取得の元で確かめるおそれがある。
5. 受け入れ条件 5 の実機の確かめを、誰がするか。
   推奨：人が docker のある環境でする。実装の工程は、手順（使う compose と、確かめる DB のテスト）を作業履歴に書く。sacty のコンテナに docker が無い（`which docker` で確かめた）ため。
   懸念：決めないと、実装の PR が実機で確かめないまま出て、確かめ忘れのままマージされうる。

### 確認しないと決めたこと

- 「実装でサービスを使った」の判定：レビューの対象の先頭のコミット（`reviewTarget.headCommit`）と同じ `commit` の、親の最後の `BranchPushed` を探す。それより前で最後の `step: implement` の `AgentRunStarted` の runId に `ServicesStarted` があること（実績）で決める。`ServicesStarted` が無ければ起動しない。
  - 計画（`task.services`）は使わない。親が後から再実行・再プッシュしても、レビューする先頭のコミットを作った実行の記録だけを使う。
- 再レビューの回ごとの起動：毎回起動する。前回からの差分が文書だけの回（`rereviewDocsOnly`）も起動する。仕様の「実行の1回ごとに起動し、終わったら消す」のまま。
- メモリー（受け入れ条件 4）：同時に動く compose は、今と同じく最大 `maxParallelTasks` 組（レビューの子タスクも `queuedTaskIds` で上限に数え、1つのタスクは同時に1つの工程しか実行しない）。ただし、レビューの分だけ重なりやすくなる。そのため、すべての実行の始まりを、空きと実行中の需要の予約で1件ずつ決める（処理の流れ）。
  - 需要は見込みで数えず、コンテナに付けたメモリーの上限の合計で数える。構成が違う compose でも上限を超えて使えないので、予約に収まる。
  - 今の sacty の環境（コンテナから見たメモリー）は、合計 15.6 GiB・空き 9.6 GiB（`free -m`）。上限の合計（should 3）で数えると、サービス付きの実行は同時に 2 件まで入る。上限の 10 本では入らないので、この判定が要る。
  - 制御の外に残るもの：別の daemon や sacty の外のコンテナが、判定の後に始める・増やす分は予約できない。判定の時点の `MemAvailable` に入る分だけを数え、そのことを仕様書に書く。
- PR #584（PBI-487。情報収集と計画の指示・`servicesReason` を直す）との重なり：この設計は情報収集と計画の指示に触れず、`prompts.ts` の変更は `servicePromptLines` の近くだけなので、範囲は分けない。

## 既定で決めたこと

- 共用の compose は、親の実装の実行の `ServicesStarted` の `compose` の `repo` から、`commit` を ref にして取得する。
- 起動の失敗には新しいイベントを足さない。`ServicesStarted`（`step: review`）は起動したときだけ記録する。
- 失敗しても続けるのは、レビューの子タスクの `review` の工程だけにする。今の工程は、失敗のときに工程を止める扱いのまま。
- 空きのメモリーを読めないときは、判定をせずに始める（予約は登録する）。読めないことで実行を止めない。
- レビューは、エージェントとサービスの分が足りないときは、待たずにサービス無しにする。待つと、ほかの実行が終わるまでレビューが進まないため。

## 処理の流れ

- `serviceSpec(task, step)`：`step === "review"` で `task.reviewOf?.step === "implement"` のとき、親を `tasks.get(reviewOf.taskId)` で引く。
  - 親のイベント（`activity.forTask`）から、レビューの対象の先頭のコミットについて上の判定の `ServicesStarted` を探し、`file`・サービス名・共用の compose（名前・`repo`・`commit`）を返す。無ければ undefined。
  - 対応する `BranchPushed` が無いときと `repo` が無いときは、起動しない理由（should 4）を返す。
  - `serviceSpec` は実行の始まりに1回だけ呼び、結果を runId に結び付けて daemon の中に持つ（すべての工程）。`stopServices` と共用の compose のディレクトリの片付けは、引き直さずにこの値で決め、終わったら外す。レビューの実行の間に親が再プッシュして記録が変わっても、同じ runId で止めて片付ける。
  - daemon が落ちて値が失われた分は、今と同じく daemon の起動のときの孤児の掃除で消す。
- メモリーの上限（すべての工程）
  - エージェントのコンテナの `docker run` に `--memory`（should 3）を付ける。
  - `sanitizeCompose` は、残す各サービスの上限を読み、無ければ既定の上限を `mem_limit` に入れる。compose 1 組の需要は、残す各サービスの上限の合計にする。
- 工程の実行の始まり（`startServices` を呼ぶ前。すべての工程）
  1. daemon の中の1つの待ち行列で、判定と予約の登録を1件ずつ行う。前の判定の予約の登録が終わるまで、次の判定をしない。
  2. 空き＝Docker のホストの `MemAvailable` −Σ（この daemon で実行中の各実行の予約 − その実行のコンテナの今の使用量。0 未満は 0）。
     - `MemAvailable` は、エージェントのイメージで `cat /proc/meminfo` を実行して読む。Docker の外の負荷・ほかの daemon・外部のコンテナの今の使用量を含む。
     - 予約として、実行ごとに、エージェントの上限と、起動する compose の需要を、実行の始まりから終わりまで持たせる。コンテナは上限を超えて使えないので、判定の後に使用量が増えても予約を超えない。
  3. 需要（エージェント＋指定があれば compose 1 組）が空きに入れば、予約を登録して進む。
  4. 入らないとき
     - レビューの子タスク：compose の分を外す。エージェントの分が入るか、ほかに実行中の実行が無ければ、サービス無しで進む。どちらでもなければ、エージェントの分が入るまで待つ。
     - それ以外：この daemon のほかの実行が終わるたびに判定し直して待つ（should 1）。ほかに実行中の実行が無ければ、待たずに予約を登録し、サービスも起動して進む。
     - 待つ間に人が止めたら、今の起動の前の確かめと同じく `run.stoppedByPerson` で止める。待っている実行は、後ろの実行の判定を止めない。
- レビューの子タスクでの起動の結果
  - `startServices` が `ok: false` で `run.stoppedByPerson` なら、今と同じく実行を止める。
  - 次のときは、予約から compose の分を外し、`executed` を失敗にせずにレビューを実行する。スキルは `serviceSkill([])` にし、指示に起動しなかった理由の1行（should 2）を足す。
    - それ以外の失敗（`services.unsafe`・共用の compose の取得の失敗・`up` の失敗など）
    - 4 でサービス無しにしたとき
    - `serviceSpec` が起動しない理由を返したとき
- 安全の検査・正規化・ラベル・孤児の掃除・イメージの確定は、同じ `services.start` を通るので変えない。

## データ

- `ServicesStarted` の `compose` に、任意の項目として `repo`（取得の元のリポジトリ）を足す。共用の compose から起動したすべての工程で記録する。投影は変えない。

## エラー時の振る舞い

- コンテナが上限に届いたときは、Docker がそのコンテナの中のプロセスを止める（OOM）。sacty は検知しない。担当には、テストの失敗やサービスの停止として見える。ほかの実行には及ばない。

## 影響範囲

- `services.md`（日英）の「いつ起動するか」に、次のことを書く。あわせて「実装の工程の後に、テストのためにサービスを起動することはない」を書き換える。

  - エージェントとサービスのメモリーの上限と値、実行の始まりの空きと予約の判定、足りないときに今の工程が待つこと
  - 判定の外にあるもの（判定の後に、別の daemon・外部のコンテナが使う分）
  - レビューで空きが足りないときと、起動に失敗したときに、サービス無しで続けること
  - 同時に動く compose の上限
- `services.md`（日英）の「起動と停止」の正規化に、`mem_limit` を入れることを足す。
- `tasks-and-steps.md`（日英）の「PR のレビューだけのタスク」の検証の項と、`approval.md`（日英）の「PR のレビューの子タスク」の親から引き継ぐものに、サービスを足す。
