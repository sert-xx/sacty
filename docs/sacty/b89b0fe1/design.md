# PBI-489 設計：PR のレビューの子タスクで、親の実装の工程のサービスを起動する

## スコープ

sacty が作った実装の PR のレビューの子タスクで、その PR の先頭を作った親の実装の実行と同じサービス（共用の compose を含む）を、レビューの実行の1回ごとに起動する。
起動・停止・後片付け・安全の検査は今の工程の経路をそのまま使う。起動の前に、Docker のホストの空きと、実行中の工程の見込みの需要から、起動できるかを1件ずつ決める。足りないとき・起動に失敗したときは、サービス無しでレビューを続ける。

- 対象
  - `service.ts` の `serviceSpec`（子の `review` のときに、PR の先頭を作った親の実装の実行の `ServicesStarted` から指定を作る）、起動の前のメモリーの判定と予約、起動の失敗の扱い
  - `services.ts` の Docker のホストの空きのメモリーを読む処理
  - `prompts.ts` の起動しなかった理由を伝える指示の1行
  - 仕様書（`services.md`・`tasks-and-steps.md`・`approval.md`、日英）、利用者向けの文書（`docs/user/compose.md`、日英）、ADR・作業履歴、テスト
- 対象外
  - スキル `docker-services` の本文（PBI-486）。起動の失敗のときも、今の「サービスは起動していません」の版を置く
  - 要求要件・設計の PR のレビューの子タスク、PR の取り込みで作ったレビューだけのタスク
  - 今の工程（調査・再現・実装）の起動をメモリーで止めること（需要として数えるだけ）、起動の数の新しい設定
  - 別の daemon との予約の共有

## 確認したいこと

### must

なし

### should

1. 起動に失敗したことを、レビューの担当に伝えるか。
   推奨：伝える。指示に「サービス（compose・サービス名）の起動に失敗しました：理由」の1行を足し、スキルは本文を変えない。
   懸念：伝えないと、担当は「起動しない PR」と区別できず、DB が要るテストを確かめなかった理由を本文に正しく書けない。
2. 見込みの需要の値を、いくつにするか。
   推奨：固定の値で、エージェントの実行 1 件が 1.5 GiB、compose 1 組が 0.5 GiB（レビューの起動に要る空きは 2 GiB）。実機の確かめ（TV-14）で、`docker stats` の実測が見込みに収まるかを確かめる。
   懸念：大きな compose（複数の DB・検索エンジンなど）では見込みを超えて使い、同時に動く実装の工程のテストが落ちうる。
3. 受け入れ条件 5 の実機の確かめを、誰がするか。
   推奨：人が docker のある環境でする。実装の工程は手順（使う compose と、確かめる DB のテスト）を作業履歴に書く。sacty のコンテナに docker が無い（`which docker` で確かめた）ため。
   懸念：決めないと、実装の PR が実機で確かめないまま出て、確かめ忘れのままマージされうる。

### 確認しないと決めたこと

- 「実装でサービスを使った」の判定：親の最後の `BranchPushed`（PR の先頭を作ったプッシュ）より前で、最後の `step: implement` の `AgentRunStarted` の runId に `ServicesStarted` があること（実績）で決める。無ければ起動しない。
  - 計画（`task.services`）は使わない。親を後から再実行して指定が変わっても、プッシュの無い再実行はレビューに影響しない。プッシュがあれば、PR の先頭と一緒に変わる。
- 再レビューの回ごとの起動：毎回起動する。前回からの差分が文書だけの回（`rereviewDocsOnly`）も起動する。仕様の「実行の1回ごとに起動し、終わったら消す」のまま。
- メモリー（受け入れ条件 4）：同時に動く compose は、今と同じく最大 `maxParallelTasks` 組（レビューの子タスクも `queuedTaskIds` で上限に数え、1つのタスクは同時に1つの工程しか実行しない）。ただし、レビューの分だけ重なりやすくなる。そのため、レビューの起動は、空きと実行中の需要の予約で1件ずつ決める（処理の流れ）。
  - 今の sacty の環境（コンテナから見たメモリー）は、合計 15.6 GiB・空き 9.0 GiB（`free -m`）。既定の 3 本がすべてサービス付きのレビューでも 6 GiB で収まる。上限の 10 本では収まらないので、この判定が要る。
  - 判定の後に、別の daemon や sacty の外のコンテナが使う分は予約できない。判定の時点の空きに入る分だけを数え、そのことを仕様書に書く。
- PR #584（PBI-487。情報収集と計画の指示・`servicesReason` を直す）との重なり：この設計は情報収集と計画の指示に触れず、`prompts.ts` の変更は `servicePromptLines` の近くだけなので、範囲は分けない。

## 既定で決めたこと

- 共用の compose は、親の実装の実行の `ServicesStarted` の `compose.commit` を ref にして取得する（取得の元は、親の `task.services.compose.repo`）。サービス名は、その記録の `services` の名前を使う。
- 起動の失敗には新しいイベントを足さない。`ServicesStarted`（`step: review`）は起動したときだけ記録する。
- 失敗で続けるのは、レビューの子タスクの `review` の工程だけにする。今の工程は、失敗のときに工程を止める扱いのまま。
- 空きのメモリーを読めないときは、予約の判定をせずに起動を試みる。読めないことでレビューのサービスを止めない。
- メモリーが足りないときは、待たずにサービス無しで続ける。待つと、ほかの実行が終わるまでレビューが進まないため。

## 処理の流れ

- `serviceSpec(task, step)`：`step === "review"` で `task.reviewOf?.step === "implement"` のとき、親を `tasks.get(reviewOf.taskId)` で引く。親のイベント（`activity.forTask`）から上の判定の `ServicesStarted` を探して、`file`・サービス名・共用の compose を返す。無ければ undefined。
  - `startServices`・`stopServices` はどちらも `serviceSpec` で決める。親の記録は実行の間に変わらないので、起動・停止・共用の compose のディレクトリの片付けの判断がそろう。
- 工程の実行（`service.ts` の `startServices` を呼ぶ所）：子の `review` で指定があるとき
  1. daemon の中の1つの待ち行列で、判定と起動を1件ずつ行う。前の判定の起動（予約の登録）が終わるまで、次の判定をしない。
  2. 空き＝Docker のホストの `MemAvailable` −Σ（この daemon で実行中の各実行の予約 − その実行のコンテナの今の使用量。0 未満は 0）。
     - `MemAvailable` は、エージェントのイメージで `cat /proc/meminfo` を実行して読む。Docker の外の負荷・ほかの daemon・外部のコンテナの今の使用量を含む。
     - 予約は、実行中のすべての工程の実行に、エージェント 1 件と、起動した compose の組の数の分の見込み（should 2）を、実行の始まりから終わりまで持たせる。判定の後に使用量が増える分も、予約の内に数える。
  3. 空きが、レビューの見込み（エージェント＋compose 1 組）より少なければ、起動しない。足りれば予約を登録して `startServices` を呼ぶ。
  4. `startServices` が `ok: false` で `run.stoppedByPerson` なら、今と同じく実行を止める。
  5. それ以外の失敗（`services.unsafe`・共用の compose の取得の失敗・`up` の失敗など）のときと、3 で起動しなかったときは、予約の compose の分を外し、`executed` を失敗にせずにレビューを実行する。スキルは `serviceSkill([])` にし、指示に起動しなかった理由の1行（should 1。メモリーのときは空きと見込み）を足す。
- 安全の検査・正規化・ラベル・孤児の掃除・イメージの確定は、同じ `services.start` を通るので変えない。

## 影響範囲

- `services.md`（日英）の「いつ起動するか」に、次のことを書く。あわせて「実装の工程の後に、テストのためにサービスを起動することはない」を書き換える。
  - 使える工程と、レビューの子タスクの扱い（PR の先頭を作った実装の実行の記録で決めること）
  - 起動の前の空きと予約の判定、見込みの値
  - 判定の外にあるもの（判定の後に、別の daemon・外部のコンテナが使う分）
  - 足りないときと失敗のときに、サービス無しで続けること
  - 同時に動く compose の上限
- `tasks-and-steps.md`（日英）の「PR のレビューだけのタスク」の検証の項と、`approval.md`（日英）の「PR のレビューの子タスク」の親から引き継ぐものに、サービスを足す。
- `docs/user/compose.md`（日英）の「どの工程で使うか」に、実装の PR のレビューを足す。

## テスト観点

- [TV-1] 実装でファイルの compose を使ったタスクの PR のレビューで、同じサービスを起動して担当をつなぐ
  - 入力：親に、最後の BranchPushed より前の最後の implement の実行の ServicesStarted（file と services）があり、reviewOf.step が implement の子タスクの review の工程を、偽の services で実行する
  - 期待結果：services.start がその記録と同じ file・サービス名で呼ばれ、step: review の ServicesStarted が記録され、スキルと指示に接続先が入り、実行の後に同じ runId で services.stop が呼ばれる
- [TV-2] 実装で共用の compose を使ったタスクの PR のレビューで、同じコミットの共用の compose を取得して起動し、後で片付ける
  - 入力：親の implement の実行の ServicesStarted が compose（共用の compose の名前とコミット）を持ち、reviewOf.step が implement の子タスクの review の工程を実行する
  - 期待結果：共用の compose がそのコミットを ref にして実行ごとのディレクトリに取得されて起動し、ServicesStarted に同じ名前とコミットが入り、実行の後にそのディレクトリが消える
- [TV-3] 実装でサービスを使っていないタスクの PR のレビューでは起動しない
  - 入力：親の最後の BranchPushed より前の最後の implement の実行に ServicesStarted が無い子タスクの review の工程を実行する
  - 期待結果：services.start と services.stop は呼ばれず、ServicesStarted は記録されず、スキルは「サービスは起動していません」の版になる
- [TV-4] 親の計画が後から変わっても、PR の先頭を作った実装の実行のサービスを使う
  - 入力：親の task.services を、最後の BranchPushed の後に、サービスの指定を消した・別の file に変えた状態にし、プッシュより前の implement の実行には元の file の ServicesStarted がある子タスクの review の工程を実行する
  - 期待結果：どちらの場合も services.start は元の file・サービス名で呼ばれ、変えた後の指定は使われない
- [TV-5] 要求要件・設計の PR のレビューでは、親がサービスを使っていても起動しない
  - 入力：親に implement の実行の ServicesStarted があり、reviewOf.step が requirements または design の子タスクの review の工程を実行する
  - 期待結果：services.start は呼ばれず、ServicesStarted は記録されない
- [TV-6] レビューでサービスの起動に失敗しても、サービス無しでレビューを続け、失敗を担当に伝える
  - 入力：偽の services.start が ok: false（services.unsafe など）を返す状態で、実装の PR のレビューの子タスクの review の工程を実行する
  - 期待結果：工程は失敗にならずにエージェントが実行され、指示に起動の失敗と理由の1行が入り、スキルは「サービスは起動していません」の版で、ServicesStarted は記録されない
- [TV-7] レビューのサービスの起動の間に人が止めたら、今の工程と同じく実行を止める
  - 入力：実装の PR のレビューの子タスクで、services.start の待ちの間にタスクを一時停止する
  - 期待結果：エージェントは実行されず、止めた理由は run.stoppedByPerson になり、起動したサービスは止めて消される
- [TV-8] 前回からの差分が文書だけの再レビューでも起動する
  - 入力：rereviewDocsOnly が決まった、実装の PR のレビューの子タスクの review の工程を実行する
  - 期待結果：services.start が親の記録と同じ file・サービス名で呼ばれ、step: review の ServicesStarted が記録され、実行の後に services.stop が呼ばれる
- [TV-9] 空きが見込みより少ないと、レビューでサービスを起動せずに続け、理由を担当に伝える
  - 入力：実行中の実行が無い状態で、偽の MemAvailable をレビューの見込みより 1 バイト少ない値と、ちょうど見込みの値にして、実装の PR のレビューの子タスクの review の工程をそれぞれ実行する
  - 期待結果：1 バイト少ないときは services.start が呼ばれずにエージェントが実行され、指示に空きと見込みを含む起動しなかった理由の1行が入り、ちょうど見込みのときは services.start が呼ばれる
- [TV-10] 同時に判定する複数のレビューが、同じ空きを二重に使わない
  - 入力：偽の MemAvailable を、レビューの見込みの 1.5 倍に固定し、実装の PR のレビューの子タスク 2 件の review の工程を同時に始める
  - 期待結果：services.start は 1 件だけで呼ばれ、もう 1 件は起動しなかった理由の1行を指示に入れてサービス無しで実行される
- [TV-11] 実行中の工程の予約のうち、まだ使っていない分を空きから引く
  - 入力：サービス付きの実装の工程が 1 件実行中で、そのコンテナの今の使用量が予約より少なく、偽の MemAvailable からその差を引くとレビューの見込みに足りない状態で、レビューの子タスクの review の工程を実行する
  - 期待結果：services.start は呼ばれず、レビューはサービス無しで実行され、実装の工程が終わって予約が外れた後のレビューでは services.start が呼ばれる
- [TV-12] 空きのメモリーを読めないときは、判定をせずに起動を試みる
  - 入力：偽の /proc/meminfo の読み取りが失敗する状態で、実装の PR のレビューの子タスクの review の工程を実行する
  - 期待結果：services.start が呼ばれ、起動に成功すれば step: review の ServicesStarted が記録される
- [TV-13] 仕様書と利用者向けの文書（日英）に、レビューでの起動の決まりが書かれている
  - 入力：docs/spec/services.md・tasks-and-steps.md・approval.md と docs/user/compose.md の日英の差分を読む
  - 期待結果：実装の PR のレビューの子タスクが、前回からの差分が文書だけの回も含めて、PR の先頭を作った親の実装の実行のサービスを実行の1回ごとに起動すること、それ以外のレビューでは起動しないこと、起動の前に Docker のホストの空きと実行中の予約から1件ずつ判定する方法と見込みの値、判定の後の別の daemon・外部のコンテナの増加は数えないこと、足りないときと起動に失敗したときはサービス無しで続けて担当に伝えること、同時に動く compose が最大 maxParallelTasks 組であることが日英の両方に書かれ、「実装の工程の後に、テストのためにサービスを起動することはない」の文が残っていない
- [TV-14] 実機で、サービスを使うタスクの PR のレビューで DB が要るテストが流れる
  - 入力：docker のある環境で、実装の工程で DB の compose を使ったタスクの PR のレビューの子タスクを実行し、その実行のログと docker stats を見る
  - 期待結果：レビューの実行のログに、compose のサービスの起動と、DB が要るテストを実行して通った出力があり、実行の間の docker stats のエージェントと compose の使用量の合計が見込みに収まり、実行の後に sacty の所有のラベルの付いたコンテナが残っていない
