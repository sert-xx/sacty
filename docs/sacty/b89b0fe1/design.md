# PBI-489 設計：PR のレビューの子タスクで、親の実装の工程のサービスを起動する

## スコープ

sacty が作った実装の PR のレビューの子タスクで、その PR の先頭を作った親の実装の実行と同じサービス（共用の compose を含む）を、レビューの実行の1回ごとに起動する。
起動・停止・後片付け・安全の検査は、今の工程の経路をそのまま使う。レビューは、起動に失敗したとき・PR の先頭に対応する記録が無いときに、サービス無しで続ける。同時に起動する数は、今の上限（`maxParallelTasks`）にそのまま含める。

- 対象
  - `service.ts` の `serviceSpec`（子の `review` のときに、PR の先頭のコミットを作った親の実装の実行の `ServicesStarted` から指定を作る）、実行ごとの指定の固定、起動の失敗の扱い
  - `ServicesStarted` の `compose` に、取得の元のリポジトリ（`repo`）を足す
  - `prompts.ts` の、起動しなかった理由を伝える指示の1行
  - 仕様書（`services.md`・`tasks-and-steps.md`・`approval.md`、日英）、利用者向けの文書（`docs/user/compose.md`、日英）、ADR・作業履歴（実機のメモリーの測定を含む）、テスト
- 対象外
  - スキル `docker-services` の本文（PBI-486）。起動の失敗のときも、今の「サービスは起動していません」の版を置く
  - 要求要件・設計の PR のレビューの子タスク、PR の取り込みで作ったレビューだけのタスク
  - メモリーの予約・需要の見積もり・コンテナのメモリーの上限・起動の数の新しい上限（受け入れ条件の読み替え）

## 確認したいこと

### must

なし

### should

1. 起動しなかったことと理由を、レビューの担当に伝えるか。
   推奨：伝える。指示に「サービス（compose・サービス名）を起動していません：理由」の1行を足し、スキルは本文を変えない。理由は、起動の失敗（メモリー不足を含む）・PR の先頭に対応する記録が無い・共用の compose の取得の元が分からない、のどれか。
   懸念：伝えないと、担当は「サービスを使わない PR」と区別できず、DB が要るテストを確かめなかった理由を本文に正しく書けない。
2. PR の先頭に対応する記録を特定できないとき（人がコミットを積んだ先頭、`repo` の無い以前の版の共用の compose の記録）に、サービス無しで続けるか。
   推奨：続ける。先頭のコミットと同じ `commit` の親の `BranchPushed` が無いときと、記録の `compose` に `repo` が無いときは起動せず、should 1 の理由を伝える。
   懸念：人がコミットを積んだ PR と、この変更の前に実装した共用の compose の PR は、レビューで DB が要るテストが流れない。親の今の指定から推すと、PR と違う compose・取得の元で確かめるおそれがある。
3. 受け入れ条件 5 の実機の確かめと、受け入れ条件 4 のメモリーの測定を、誰がするか。
   推奨：人が docker のある環境でする。実装の工程は、手順を作業履歴に書き、人が測った値と、足りなくなる心配があるかを書き足す。sacty のコンテナに docker が無い（`which docker` で確かめた）ため。
   - 手順に書くこと：使う compose（`postgres` の公式イメージ1サービス）、DB に接続するテスト（`DATABASE_URL` で `select 1` を流すテストをリポジトリに置く）、タスクの作成から実装・レビューの子タスクの実行まで、見るログ（`ServicesStarted`・テストの出力）、測る値（`docker stats --no-stream`）、後片付けの確かめ（`io.sacty.owner` のコンテナが残らない）
   懸念：決めないと、実装の PR が実機で確かめないまま出て、確かめ忘れのままマージされうる。

### 確認しないと決めたこと

- 「実装でサービスを使った」の判定：レビューの対象の先頭のコミット（`reviewTarget.headCommit`）と同じ `commit` の、親の最後の `BranchPushed` を探す。それより前で最後の `step: implement` の `AgentRunStarted` の runId に `ServicesStarted` があること（実績）で決める。`ServicesStarted` が無ければ起動しない。
  - 計画（`task.services`）は使わない。親が後から再実行・再プッシュしても、レビューする先頭のコミットを作った実行の記録だけを使う。
- 再レビューの回ごとの起動：毎回起動する。前回からの差分が文書だけの回（`rereviewDocsOnly`）も起動する。仕様の「実行の1回ごとに起動し、終わったら消す」のまま。
- PR #584（PBI-487。情報収集と計画の指示・`servicesReason` を直す）との重なり：この設計は情報収集と計画の指示に触れず、`prompts.ts` の変更は `servicePromptLines` の近くだけなので、範囲は分けない。

## 既定で決めたこと

- 共用の compose は、親の実装の実行の `ServicesStarted` の `compose` の `repo` から、`commit` を ref にして取得する。
- 起動の失敗には新しいイベントを足さない。`ServicesStarted`（`step: review`）は起動したときだけ記録する。
- 失敗しても続けるのは、レビューの子タスクの `review` の工程だけにする。今の工程は、失敗のときに工程を止める扱いのまま。
- 起動の失敗の詳細（安全の検査のメッセージなど。PR の compose の値を含みうる）は、指示の中で外部のデータとして区切り、その中の指示に従わないと添える。

## 受け入れ条件の読み替え

受け入れ条件 4 を、依頼の補足（再開で人が足したもの）のとおり、次で満たすとする。

- サービスの同時起動の上限は、今は `maxParallelTasks`（タスクの同時実行の数）だけ。レビューの子タスクも `queuedTaskIds` で数え、1つのタスクは同時に1つの工程しか実行しないので、同時に動く compose は最大 `maxParallelTasks` 組のまま。新しい上限は作らない。
- 実機で、サービスを使うレビューを1回流したときのメモリーの使い方（測った値と、足りなくなる心配があるか）を作業履歴に書く。同時に動かすタスクの数は、利用者が運用で抑える。
- 起動に失敗したとき（メモリー不足を含む）は、レビューをサービス無しで続け、確かめられなかったことを本文に書く。

## 処理の流れ

- `serviceSpec(task, step)`：`step === "review"` で `task.reviewOf?.step === "implement"` のとき、親を `tasks.get(reviewOf.taskId)` で引く。
  - 親のイベント（`activity.forTask`）から、レビューの対象の先頭のコミットについて上の判定の `ServicesStarted` を探し、`file`・サービス名・共用の compose（名前・`repo`・`commit`）を返す。無ければ undefined。
  - 対応する `BranchPushed` が無いときと `repo` が無いときは、起動しない理由（should 2）を返す。
  - `serviceSpec` は実行の始まりに1回だけ呼び、結果を runId に結び付けて daemon の中に持つ（すべての工程）。`stopServices` と共用の compose のディレクトリの片付けは、引き直さずにこの値で決め、終わったら外す。レビューの実行の間に親が再プッシュして記録が変わっても、同じ runId で止めて片付ける。
  - daemon が落ちて値が失われた分は、今と同じく daemon の起動のときの孤児の掃除で消す。
- レビューの子タスクでの起動の結果
  - `startServices` が `ok: false` で `run.stoppedByPerson` なら、今と同じく実行を止める。
  - 次のときは、`executed` を失敗にせずにレビューを実行する。スキルは `serviceSkill([])` にし、指示に起動しなかった理由の1行（should 1）を足す。
    - それ以外の失敗（`services.unsafe`・共用の compose の取得の失敗・`up` の失敗など。メモリー不足による失敗を含む）
    - `startServices` が例外を投げたとき（起動の準備の書き込みの失敗など）。原因付きの失敗として扱い、その runId の起動途中のサービスと共用の compose のディレクトリを片付けてから続ける
    - `serviceSpec` が起動しない理由を返したとき
- 安全の検査・正規化・ラベル・孤児の掃除・イメージの確定は、同じ `services.start` を通るので変えない。

## データ

- `ServicesStarted` の `compose` に、任意の項目として `repo`（取得の元のリポジトリ）を足す。共用の compose から起動したすべての工程で記録する。投影は変えない。

## 影響範囲

- `services.md`（日英）の「いつ起動するか」に、次のことを書く。あわせて「実装の工程の後に、テストのためにサービスを起動することはない」を書き換える。
  - 使える工程と、レビューの子タスクの扱い（PR の先頭のコミットを作った実装の実行の記録で決めること、特定できないときはサービス無しで続けること）
  - レビューで起動に失敗したとき（メモリー不足を含む）に、サービス無しで続けること
  - 同時に動く compose が、レビューを含めて最大 `maxParallelTasks` 組であること
- `services.md` の「いつ起動するか」と `tasks-and-steps.md` の `SERVICE_STEPS` の行（日英）は、3つの工程をオーケストレーターが選べる工程と書き、実装の PR のレビューの子タスクの例外を併記する。
- `tasks-and-steps.md`（日英）の「PR のレビューだけのタスク」の検証の項と、`approval.md`（日英）の「PR のレビューの子タスク」の親から引き継ぐものに、サービスを足す。
- `docs/user/compose.md`（日英）の「どの工程で使うか」に、sacty が作った実装の PR のレビュー（取り込んだ PR のレビューは起動しない）を足す。
- 作業履歴に、受け入れ条件 4 の実機のメモリーの測定と、修正を戻したときにテストが落ちた結果を書く。
