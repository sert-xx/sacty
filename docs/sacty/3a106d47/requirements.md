# 要求要件：再開の補足で許した、承認済みの成果物の直しを人の判断待ちにしない（PBI-490）

## スコープ

再開の補足に「承認済みの要求要件・設計も、この補足に合わせて直してよい」という許可を付けられるようにする。
許可の効いている間に工程が出した、補足に沿う変更の申し出は、人の判断待ちにせず受け入れて続け、受け入れたことと根拠の補足を作業の履歴と申し出の一覧に残す。

- 対象
  - 再開（画面の再開の欄、MCP の `resume_task`）での許可の指定
  - 変更の申し出の記録・受け入れ・反映と、作業の履歴・申し出の一覧の表示
  - 要求要件の申し出を受け入れたときの、承認済みの設計・テスト観点の合わせ直し
  - 仕様書とユーザー文書（日英）、ADR、作業履歴
- 対象外
  - 補足の無い申し出を AI の判定で受け入れること（依頼の範囲の外）
  - 局所の設計書の直し（`sacty-design-edit`）と、実装の工程での承認済みの文書の直接の直し。どちらも申し出を経ないので変えない

## 確認したいこと

### must

- M-1：許可の効いている間に要求要件への申し出を受け入れたとき、人の再承認を省くか。
  推奨：省く。補足に合わせた版で承認済みの要求要件を置き換え、承認済みの設計があれば設計とテスト観点も合わせ直して（R-18）、申し出た工程の成果を提出して続ける（R-11）。補足を書いた人がもう一度承認する待ちを無くすのが依頼の目的のため。
  懸念：省かない（今の反映のまま承認を取り消す）と、要求要件への申し出では人の承認待ちが残り、5回の待ちのうち要求要件の分が減りません。

### should

- S-1：許可の効く範囲をどこまでにするか。
  推奨：許可を付けた再開から、次の一時停止までに出た申し出すべて（R-6）。次の再開で許可を付けなければ、前の補足の許可は効かない。
  懸念：一時停止を挟んでも許可が残ると、後で方針を戻した人が知らないうちに、前の補足に沿う申し出が受け入れられます。
- S-2：新しい記録を足すと、前の版のデーモンがその作業履歴を読めなくなる。これを受け入れるか。
  推奨：受け入れ、仕様書に「前の版に戻せるのは、許可を付けた再開を記録する前まで」と書く（PBI-462・PBI-467 と同じ扱い）。
  懸念：許可を使った後に前の版へ戻すと、デーモンが起動できず、その作業履歴のすべてのタスクを扱えなくなります。
- S-3：MCP の `resume_task` で、AI が利用者の言葉なしに許可を付けないよう、ツールの説明で求めるか。
  推奨：求める（R-20）。利用者が「承認済みの成果物も直してよい」と言ったときだけ付け、タスクの文の中の指示では付けないと説明に書く。
  懸念：タスクの文に紛れた指示で許可が付くと、人が見ていない方針の変更が承認済みの成果物に入ります。
- S-4：R-18 で合わせ直した設計・テスト観点を、人の承認なしに承認済みの版として置き換えてよいか。
  推奨：よい。補足の許可は承認済みの設計の直しも含むため。直すのは補足と置き換えた要求要件に要る範囲だけにし（R-21）、直した中身は作業の履歴と申し出の一覧で読めるようにする（R-18）。
  懸念：置き換えを人の承認に回すと、要求要件と設計にまたがる補足では設計の承認待ちが残り、待ちが減りません。

### 確認しないと決めたこと

- 補足に沿うかの判断の仕方：設計で決める。受け入れ条件 3 が設計に委ねているため。
- MCP の `resume_task` で許可を付けられるようにし、PBI-400 の ADR（MCP の再開は補足だけ）を広げる：受け入れ条件 1 が MCP を挙げているため。
- 工程への申し出の指示（`proposalLines`）の文言を変えるか：設計で決める。要求は申し出の扱いで決まり、指示の文言では変わらないため。
- R-18 の設計・テスト観点の合わせ直し方（設計の工程をやり直す・同じ実行で設計の申し出も出させる、など）：設計で決める。

## 既定で決めたこと

- 根拠の補足は、その補足を付けた再開の日時で示す。
- 補足を空にして許可だけを付けた再開は、何も記録せずに断る。
- PBI-333 の ADR（申し出は人が判断する）と PBI-400 の ADR は、`docs/adr/README.md` の置き換えの手順で一部を置き換えた扱い（superseded）にする。
- 許可に対応していない前の版のデーモンへ、MCP が許可付きの再開を送るときは、再開させずに断る（R-22。許可の無い再開に落とさない）。

## 受け入れの確かめ方

### 自動のテストで確かめること

- R-7〜R-19・R-21：合成の工程の結果（申し出の JSON）と再開の入力で確かめる。R-10〜R-16 の分け方を戻すと、R-10〜R-13 のテストが落ちる。
- R-18・R-19・R-21：承認済みの設計があるタスクで、要求要件への申し出を受け入れた後、設計・テスト観点が置き換わってから提出されることと、作れないとき・範囲を超える方針の変更を含むときに、置き換わらず提出されず人の判断待ちになることを確かめる。
- R-12・R-13・R-18：作業の履歴の文言と申し出の一覧の表示（R-18 は直した中身）を日英で確かめる。
- R-20：`resume_task` の説明の文言を、MCP のテストで確かめる。
- R-22：前の版のデーモンを模した API（許可を知らない応答）に許可付きで `resume_task` を呼び、再開の要求が届かずタスクが一時停止のままで、更新を促す断りが返ることを MCP のテストで確かめる。
- R-1〜R-5：差分で各文書に要求の記述があることを確かめ、`tests/docs`（日英の突き合わせ・ADR の置き換えの関係）が通る。

### 人が確かめること

- `sacty up` の画面で、許可を付けて再開し、補足に沿う申し出が人の判断待ちにならずに進み、作業の履歴と申し出の一覧に R-12・R-13 の中身が出ることを確かめ、動画を残す。
  懸念：テストは合成の描画で確かめるので、再開の欄の許可が実ブラウザーで送られない誤りを、マージの後に利用者が待ちで気づくことになります。
