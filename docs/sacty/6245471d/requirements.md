# PBI-467 一時的な git push の失敗をやり直す：要求要件

## スコープ

PR を作る・直しを積むときの `git push` が一時的と見られる失敗で拒まれたら、デーモンは間を置いて push だけをやり直してから止める。
止まった後に再開したら、済んでいる実行をやり直さずに push からやり直す。
停止の理由の文は、失敗の行が先に読めるようにする。

- 対象
  - 実装の PR・引き継いだ PR・要求要件と設計の PR の push
  - 停止の理由の文（push の失敗のとき）、作業履歴の記録と画面の表示名
  - 仕様書（日英）・ユーザー文書（日英）・ADR・worklog
- 対象外
  - ブランチの削除の push（PR を作る・直しを積む push ではないため）
  - push 以外の git の操作と、エージェントの実行の失敗のやり直し

## 確認したいこと

### must

- 再開の直前に PR へ指摘が届いていたら、push からやり直す（R-11）より、指摘を読んで差し戻す今の決まり（docs/user/tasks.md「一時停止の間に実装の PR へ届いた指摘」）を優先するか。
  - 推奨：差し戻しを優先し、指摘が無いときだけ push からやり直す。届いた指摘を反映しないまま PR を更新しないため。
  - 懸念：2回目の事例が AI のレビューの指摘による差し戻しだったなら、この推奨では同じ再実行（約7分・約0.4ドル）が利用者に残る。
- 2回目の事例で直しの実行からやり直した原因を、作業履歴で確かめられるか（再開の直後のイベント）。
  - 推奨：確かめたうえで進める。原因の候補は、上の指摘の差し戻し・人の足したコミットとの競合・要求要件と設計の PR の経路で、どれかによって直す所が変わる。
  - 懸念：原因が R-11 で直す所の外にあると、R-11 を満たしたつもりで再実行が残り、利用者が時間と費用を払い続ける。

### should

- 停止の理由の文から除く `remote:` の行は、案内の行（`Create a pull request`・URL など）だけにし、拒否の理由を書いた行（`remote: error: ...` など）は残すか。
  - 推奨：残す（R-10）。保護・ルールでの拒否は、理由が `remote:` の行にだけ出るため。
  - 懸念：全部除くと、保護・ルールで止まったタスクの理由が `[remote rejected]` の1行になり、人が何を直せばよいか分からない。

### 確認しないと決めたこと

- やり直す範囲：PR を作る・直しを積む push の全部とし、ブランチの削除は外す。依頼の文言（「PR を作る・直しを積むときの git push」）で決まるため。
- 一時的とみなす失敗の分け方・`LC_ALL=C` の要否・既存のやり直しの仕組みの使い回し・記録のイベントの形・待つ間の実行の枠の扱い：設計の工程で決める。要求（R-1〜R-11）はどれを選んでも変わらないため。
- 回数と間隔：依頼が「決め打ちの定数でよい」としているので、設計で決める。

## 既定で決めたこと

- 待つ間に一時停止・中止・停止でやめたときは、やり直しの記録を残さず、一時停止の理由も上書きしない（レビューの GitHub の問い合わせのやり直しと同じ）。
- 停止の理由の文を直すのは、push の失敗のときだけにする。

## 要求

主語の「デーモン」は sacty のデーモン（apps/daemon）を指す。

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | デーモン | 一時的とみなす失敗とそうでない失敗を、デーモンの言語の設定（`LANG`）に依らず同じに分ける |
| R-2 | この変更の PR | 仕様書（日英）・ユーザー文書（日英）・ADR（日本語）・docs/worklog に、やり直す失敗の種類・回数・間隔・作業履歴に出ることを含める |

### イベント駆動

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-3 | push が一時的とみなす失敗（`[remote rejected] ... (failed)`・GitHub の内部エラー・接続の失敗）で終わったとき | デーモン | タスクを止めずに、決めた間隔を置いて同じコミットを同じブランチへ、決めた回数まで push し直す |
| R-4 | push をやり直す前のとき | デーモン | 何回目か・上限の回数・待つ時間・失敗の文（秘密の値を伏せたもの）を作業履歴に記録する |
| R-5 | やり直した push が通ったとき | デーモン | 通ったことと、通るまでにやり直した回数を作業履歴に記録する |
| R-6 | やり直しの記録を作業履歴の画面に出すとき | 画面 | 日英それぞれの表示名で出す |

### 望まない振る舞い

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-7 | push が一時的でない失敗（保護・ルールでの拒否、`[remote rejected]` で理由が `(failed)` 以外、fast-forward でない、認証の失敗）で終わった場合 | デーモン | やり直さずに、今までと同じ理由でタスクを止める |
| R-8 | 上限の回数までやり直しても push が通らなかった場合 | デーモン | 今までと同じ理由（`pr.failed` など）でタスクを止める |
| R-9 | push をやり直すまで待つ間に、一時停止・中止・デーモンの停止を求められた場合 | デーモン | push せずに待つのをやめる |
| R-10 | push の失敗でタスクを止める場合 | デーモン | 停止の理由の文から `remote:` の案内の行を除き、失敗の行を文の先頭に置く（秘密の値を伏せてから切り詰める順は変えない） |

### 複合

| ID | 状態 | トリガー | システム | 応答 |

| R-11 | push の失敗で止まり、PR に新しい指摘が届いていない間 | 人がタスクを再開したとき | デーモン | エージェントの実行を始めずに、止まった push からやり直す |

## 受け入れの確かめ方

### 自動のテストで確かめること

- R-1・R-3〜R-5・R-7〜R-11：偽の push に、git の標準エラーの形の失敗（`[remote rejected] ... (failed)`・保護での拒否・fast-forward でない・認証の失敗・`remote:` の案内の行を含む文）を返させ、やり直しの回数・作業履歴・停止の理由・再開の後のエージェントの実行の有無を確かめる。R-1 は、言語の設定を変えて同じ結果になることを確かめる。
- R-6：作業履歴の表示名のテストで、日英の表示名を確かめる。
- R-2：差分で文書の中身を確かめ、`npx vitest run tests/docs` を通す。
- 修正を戻すと、上のテストが落ちることを確かめる。
