# PBI-467 一時的な git push の失敗をやり直す：要求要件

## スコープ

PR を作る・直しを積むときの `git push` が一時的と見られる失敗で拒まれたら、デーモンは間を置いて push だけをやり直してから止める。
止まった後に再開したら、済んでいる実行をやり直さずに push からやり直す。
停止の理由の文は、失敗の行が先に読めるようにする。

- 対象
  - 実装の PR・引き継いだ PR・要求要件と設計の PR の push
  - 停止の理由の文（push の失敗のとき）、作業履歴の記録と画面の表示名
  - 仕様書（日英）・ユーザー文書（日英）・ADR・worklog
- 対象外
  - ブランチの削除の push（PR を作る・直しを積む push ではないため）
  - push 以外の git の操作と、エージェントの実行の失敗のやり直し

## 確認したいこと

### must

- 再開の直前に PR へ指摘が届いていたら、push からやり直す（R-11）より、指摘を読んで差し戻す今の決まり（docs/user/tasks.md「一時停止の間に実装の PR へ届いた指摘」）を優先するか。
  - 推奨：差し戻しを優先し、指摘が無いときだけ push からやり直す。届いた指摘を反映しないまま PR を更新しないため。
  - 懸念：2回目の事例が AI のレビューの指摘による差し戻しだったなら、この推奨では同じ再実行（約7分・約0.4ドル）が利用者に残る。
- 2回目の事例で直しの実行からやり直した原因を、作業履歴で確かめられるか（再開の直後のイベント）。
  - 推奨：確かめたうえで進める。実装の PR・要求要件と設計の PR は、今のコードでも再開で PR の作成（push）からやり直すので、原因は push の外（上の指摘の差し戻し・人の足したコミットとの競合など）にあると見られる。
  - 懸念：原因を直さないと、R-11 を満たしても再実行が残り、利用者が時間と費用を払い続ける。

### should

- 停止の理由の文から除く `remote:` の行は、案内の行（`Create a pull request`・URL など）だけにし、拒否の理由を書いた行（`remote: error: ...` など）は残すか。
  - 推奨：残す（R-10）。保護・ルールでの拒否は、理由が `remote:` の行にだけ出るため。
  - 懸念：全部除くと、保護・ルールで止まったタスクの理由が `[remote rejected]` の1行になり、人が何を直せばよいか分からない。
- やり直しの記録が、前の版のデーモンで読めない形になってよいか。
  - 推奨：よいとし、event-log の仕様書に「一度記録したら前の版に戻せない」と書く（PBI-452・PBI-462 と同じ扱い）。
  - 懸念：やり直しを記録した後にデーモンを前の版へ戻した運用者は、そのタスクのログを読めず、デーモンを起動できない。

### 確認しないと決めたこと

- やり直す範囲：PR を作る・直しを積む push の全部とし、ブランチの削除は外す。依頼の文言（「PR を作る・直しを積むときの git push」）で決まるため。
- 一時的とみなす失敗の見分け方・`LC_ALL=C` の要否・既存のやり直しの仕組みの使い回し・記録のイベントの形・待つ間の実行の枠の扱い：設計の工程で決める。要求（R-1〜R-13）はどれを選んでも変わらないため。
- 回数と間隔：依頼が「決め打ちの定数でよい」としているので、設計で決める。

## 既定で決めたこと

- 停止の理由の文を直すのは、push の失敗のときだけにする。
- ref のロックの競合（`cannot lock ref`）など、R-3 にも R-7 にも挙げない失敗は、一時的でないとして止める（R-7）。

## 要求

主語の「デーモン」は sacty のデーモン（apps/daemon）を指す。

### 常時

| ID | システム | 応答 |
| --- | --- | --- |
| R-1 | デーモン | 一時的とみなす失敗とそうでない失敗を、デーモンの言語の設定（`LANG`）に依らず同じに分ける |
| R-2 | この変更の PR | 仕様書（日英）・ユーザー文書（日英）・ADR（日本語）・docs/worklog に、やり直す失敗の種類・回数・間隔・作業履歴に出ることを含め、event-log の仕様書に新しい記録と前の版が読めるかを、ユーザー文書に停止の理由の文から案内の行が除かれ失敗の行が先頭に来ることを含める |

### イベント駆動

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-3 | push が一時的とみなす失敗（`[remote rejected] ... (failed)`・GitHub の内部エラー・HTTP 5xx（`RPC failed; HTTP 500` など）・レート制限（429、レート制限の 403）・接続の失敗）で終わったとき | デーモン | タスクを止めずに、決めた間隔を置いて同じコミットを同じブランチへ、決めた回数まで push し直す |
| R-4 | 間を置いた後、push をやり直す直前のとき | デーモン | 何回目か・上限の回数・待った時間・失敗の文（秘密の値を伏せたもの）を作業履歴に記録する |
| R-5 | やり直した push が通ったとき | デーモン | 通ったことと、通るまでにやり直した回数を作業履歴に記録する |
| R-6 | やり直しの記録を作業履歴の画面に出すとき | 画面 | 日英それぞれの表示名で出す |
| R-13 | やり直した push で、同じコミットがすでにブランチの先頭にある（前の回で push が通っていて応答だけが失われた）とき | デーモン | 通ったとして扱い（R-5）、その回もやり直しの回数に数える |

### 望まない振る舞い

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-7 | push が一時的でない失敗（保護・ルールでの拒否、`[remote rejected]` で理由が `(failed)` 以外、fast-forward でない、認証の失敗、R-3 に当たらない失敗）で終わった場合 | デーモン | やり直さずにタスクを止める。停止の種類（理由のコード）は今までと同じで、文は R-10 に従う |
| R-8 | 上限の回数までやり直しても push が通らなかった場合 | デーモン | 通らなかったことと、やり直した回数を作業履歴に記録して、タスクを止める。停止の種類は今までと同じ（`pr.failed` など）で、文は R-10 に従う |
| R-9 | push をやり直すまで待つ間に、一時停止・中止・デーモンの停止を求められた場合 | デーモン | push せずに待つのをやめ、やり直しの記録を残さず、一時停止の理由も上書きしない |
| R-10 | push の失敗でタスクを止める場合 | デーモン | 停止の理由の文から `remote:` の案内の行を除き、失敗の行を文の先頭に置く（秘密の値を伏せてから切り詰める順は変えない） |
| R-12 | 引き継いだ PR の push が、一時的とみなす失敗のまま上限の回数まで通らなかった場合 | デーモン | 人が PR のブランチを進めた（`pr.continuedBranchMoved`）とせず、R-8 と同じ push の失敗として止める |

## 受け入れの確かめ方

### 自動のテストで確かめること

- R-1・R-3〜R-5・R-7〜R-10・R-12〜R-13：偽の push に、git の標準エラーの形の失敗（`[remote rejected] ... (failed)`・HTTP 5xx・レート制限・保護での拒否・fast-forward でない・認証の失敗・`remote:` の案内の行を含む文）と、前の回で通っていた状態を返させ、やり直しの回数・作業履歴・停止の理由を確かめる。R-1 は、言語の設定を変えて同じ結果になることを確かめる。
- R-11：実装の PR・要求要件と設計の PR で、再開の後にエージェントを実行せず push をやり直すことを確かめる。今のコードでも成り立つ経路なので、修正を戻すと落ちることは、やり直しが起きることの部分だけで確かめる。
- R-6：作業履歴の表示名のテストで、日英の表示名を確かめる。
- R-2：差分で文書の中身を確かめ、`npx vitest run tests/docs` を通す。
- 修正を戻すと、上のテストが落ちることを確かめる。
