# 設計：PR の文を画面に頼らない形にし、製品名を「Sacty」にそろえる

## スコープ

Sacty が GitHub に投稿する文から、依頼した人のマシンの画面に頼る案内を外し、読む中身を PR の中に置きます。
あわせて、結論の行を絞り、人が読む文の製品名を「Sacty」にそろえます。

- 対象
  - 知らせ 4 種（人に確かめてほしいこと・設計に戻した・レビューが止まった・後続に回す決定）のタスクの画面へのリンクと注釈
  - 実装の PR と、要求要件・設計の PR の本文（決まった形とテンプレートに沿わせる形の両方）
  - 返信・コメントの署名と書き出しの文、Sacty のレビューの本文、知らせ 4 種の本文、PR の指摘から作る Issue の本文の製品名
  - 本文が空のレビューの原因の記録、仕様書・利用者向けの文書（日英）、ADR、作業履歴
- 対象外
  - エージェントへの指示の文の中の「sacty」（人は読まない）
  - 画面から書かれた指摘の「内容は、タスクの画面で読めます」（`deferral-notice.ts`。依頼の範囲の外）
  - 返信の投稿のしかた（REST の `/replies`）の変更（確認したいことの S-1 の推奨による）

## 確認したいこと

### must

- M-1：本文の全体が上限（65,000 文字）を超えるとき、承認済みの要求要件（再現）の全文だけを、Sacty のコメントに分けて載せる形でよいですか。そのほかの省いた続きは本文の `<details>` に置き、それでも本文の後ろを切ったときは、切った文字数と理由を書きます。
  - 推奨：はい。受け入れ条件はレビュアーの判断に要るので、上限を超えても PR の中で全部を読める形にします。省いた続きは本文の中に収まる長さに上限があります。
  - 懸念：本文の更新のたびにコメントを書き換えるので、PR の通知を見ている人に、本文の更新とは別の通知が届きます。

### should

- S-1：本文が空のレビューは、投稿のしかたを変えず、「GitHub は行へのコメントへの返信 1 件ごとにレビューを 1 件作る」と仕様書と作業履歴に書くだけでよいですか。
  - 推奨：はい。確かめたことは次のとおりで、返信を 1 件のレビューにまとめる方式は、人の下書きとぶつかります。
    - REST の `/replies`：PR #470・#480・#499・#501 の返信のすべてに、返信ごとに別の `pull_request_review_id` が付いていました。
    - GraphQL の `addPullRequestReviewThreadReply`：返信は必ずレビューに属します（スキーマの `PullRequestReviewComment.pullRequestReview`）。`pullRequestReviewId` を省いたときに空のレビューができるかは、書き込みができないので確かめていません。
    - 保留中のレビューにまとめて出す：同じ PR で 1 人に 1 件しか持てません。Sacty は人と同じアカウント（例：sert-xx）で投稿するので、人が画面で書きかけたレビューに Sacty の返信が混ざり、一緒に出てしまいます。
  - 懸念：レビュアーの PR の会話の欄に、返信の数だけ空のレビューが並び続けます。
- S-2：結論から移す 2 項目の置き場所は、決まった形の本文では結論の直後の「## レビューの進め方」（main）、テンプレートに沿わせる本文では footer の Sacty の記録（承認の案内の前）でよいですか。
  - 推奨：はい。footer は上限で省かれず、足すのは決まった長さの 5 文だけなので、承認の案内と `sacty task <ID>` が切れません。テンプレートの目的の節も依頼の内容に絞れます。
  - 懸念：開いている PR で人が結論を直していると、次の更新で 3 方向のマージが重なり、PR ごとにオーケストレーターのエージェントを 1 回実行する費用がかかります。

### 確認しないと決めたこと

- 分けたコメントの目印：`<!-- sacty-basis:<タスクの ID> -->` を足し、取り込みの見分けに加えます（足さないと人の指摘として取り込まれます）。
- 「人が読む文」の境目：GitHub に投稿する文だけを直します。依頼の受け入れ条件 4 が対象を列挙しているためです。

## 既定で決めたこと

- 注釈は、リンクのある文の直後に「タスクの画面は、依頼した人のマシンでだけ開けます。」の 1 文を足します。`SACTY_WEB_URL` を URL として読めないときも添えます。読めない URL は開けるかも分からないので、開けない人に向けた注意を残す側に倒します。
- Issue を作れなかった理由は、伏せ済みの `failure` を、URL の資格情報（`redactUrlCredentials`）と内部のパス（`withoutInternalPaths`）も伏せてから 1 行にし、500 文字までにして知らせに書きます。
- 既定のコンテキスト（`apps/daemon/default-context/`）は変えません。PR に投稿する文が無いためです。

## PR の本文の形

- 結論：「変更」「最後の直し」と、不合格のまま進めた記録・人が確かめること（`keep` のまま）。
- 「## レビューの進め方」：`REVIEW_BODY_LINE` を次の 1 項目 1 文に分け、AI のレビューの行を続けます。
  - Sacty のレビューの子タスクが、この PR をレビューして投稿します。
  - 指摘があれば Sacty が直し、指摘なしになるとドラフトを外します。
  - Sacty はテストの実行と CI の待ちをしないので、CI の結果はこの PR のチェックで確かめてください。
  - AI のレビュー：この head（abc1234）には、Sacty の AI のレビューがまだ付いていません。
  - この状況は本文を書いた時点のものなので、最新の状況はこの PR のレビューの欄で確かめてください。
- 要求要件の全文：マージで承認した PR が無いとき、要点の後に `<details>` で全文を載せます。全文を入れると本文が上限を超えるときは、`<details>` の代わりに、全文のコメントへのリンクを置きます。
- 全文のコメント：目印の後に全文を載せ、コメントの上限を超える分は続きのコメントに分けます。本文を作り直すたびに、目印で見つけた同じコメントを書き換えます。
- 省いた続き：人が確かめることの 1 項目・一覧、所見、子タスクの内容は、省いた続きを `<details>` に載せます。決まった形の本文では結論の後（main）、テンプレートに沿わせる本文では Sacty の記録の先頭（main）に置きます。footer には上限のある行だけを置きます。
- `<details>` とコメントに載せる文は、HTML のコメントを除き（`withoutHtmlComments`）、`<details`・`</details>` を `&lt;details`・`&lt;/details>` にしてから載せます。
- 要求要件・設計の PR の AI のレビューの行も、上の 2 文の形にします。

## 影響範囲

- 3 方向のマージ：目印と `keep` の作りは変えないので、古い形の本文を祖先にしたマージはそのまま動きます。
- マージの結果が上限を超えてオーケストレーターにまとめさせるとき：指示に「削った所に、削った文字数と GitHub の上限を書いた 1 文を置く」を足します。
- 取り込み：見分けは HTML のコメントの目印で行い、今の目印は変えません。
- 文書：`docs/spec/approval.md`・`intake.md`・`tasks-and-steps.md`、`docs/user/intake.md`・`tasks.md`・`notifications.md` を日英で直し、作業履歴を足します。
- ADR：新しい ADR で `docs/adr/20261101-1400-pr-body-conclusion-first.md` の「全文の場所（タスクの画面）」を一部置き換えます。
  - 新しい ADR の `置き換え元` に古い ADR へのリンクを書きます。
  - 古い ADR を `git mv` で `20261101-1400-superseded-pr-body-conclusion-first.md` にし、`ステータス` と `置き換え先`（置き換えた部分）だけを直します。本文は書き換えません。
  - 古い名前へのリンク（`docs/worklog/20261101-pbi-264-pr-body-summary.md` など）を直します。
- PR の説明に、変わった文の前・後の例を載せます。
