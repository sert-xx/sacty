# 設計：PR の文を画面に頼らない形にし、製品名を「Sacty」にそろえる

## スコープ

Sacty が GitHub に投稿する文から、依頼した人のマシンの画面に頼る案内を外し、読む中身を PR の中に置きます。
あわせて、結論の行を絞り、人が読む文の製品名を「Sacty」にそろえます。

- 対象
  - 知らせ 4 種（人に確かめてほしいこと・設計に戻した・レビューが止まった・後続に回す決定）のタスクの画面へのリンクと注釈
  - 実装の PR と、要求要件・設計の PR の本文（決まった形とテンプレートに沿わせる形の両方）
  - 返信・コメントの署名と書き出しの文、PR の指摘から作る Issue の本文の製品名
  - 本文が空のレビューの原因の記録、仕様書・利用者向けの文書（日英）、ADR、作業履歴
- 対象外
  - エージェントへの指示の文の中の「sacty」（人は読まない）
  - 画面から書かれた指摘の「内容は、タスクの画面で読めます」（`deferral-notice.ts`。依頼の範囲の外）
  - 返信の投稿のしかた（REST の `/replies`）の変更（確認したいことの S-1 の推奨による）

## 確認したいこと

### must

- M-1：省いた続きは、本文の中の折りたたみ（`<details>`）に置き、本文の全体が上限（65,000 文字）を超えて後ろを切ったときだけ、切った量と理由を書く形でよいですか。Sacty のコメントには分けません。
  - 推奨：はい。承認済みの要求要件と省いた続きは本文の前のほうに置くので、切られるのは主に後ろの「変更」と観点の表になるためです。
  - 懸念：要求要件だけで 55,000 文字ほどを超えるタスクでは、全文の後ろが PR から読めなくなり、レビュアーが受け入れ条件の一部を確かめられません。

### should

- S-1：本文が空のレビューは、投稿のしかたを変えず、「GitHub は行へのコメントへの返信 1 件ごとにレビューを 1 件作る」と仕様書と作業履歴に書くだけでよいですか。
  - 推奨：はい。#499 で返信 10 件に空のレビュー 10 件が対応し、返信は必ずレビューに属します。1 件にまとめるには保留中のレビューが要り、同じアカウントで投稿する Sacty のレビューとぶつかります。
  - 懸念：レビュアーの PR の会話の欄に、返信の数だけ空のレビューが並び続けます。
- S-2：結論から移す 2 項目の置き場所は、決まった形の本文では結論の直後の「## レビューの進め方」、テンプレートに沿わせる本文では末尾の Sacty の記録（承認の案内の前）でよいですか。
  - 推奨：はい。末尾は長さの上限で省かれず、テンプレートの目的の節を依頼の内容に絞れます。
  - 懸念：開いている PR で人が結論を直していると、次の更新で 3 方向のマージが重なり、PR ごとにオーケストレーターのエージェントを 1 回実行する費用がかかります。

### 確認しないと決めたこと

- 分けたコメントの目印：M-1 の推奨ではコメントに分けないので足しません。M-1 の答えが「分ける」なら、`<!-- sacty-` で始まる目印を足し、取り込みの見分けに加えます。
- 「人が読む文」の境目：GitHub に投稿する文だけを直します。依頼の受け入れ条件 4 が対象を列挙しているためです。
- GraphQL の返信に変えても空のレビューが避けられないときの書き方：S-1 の推奨の文にまとめます。

## 既定で決めたこと

- 注釈は、リンクのある文の直後に「タスクの画面は、依頼した人のマシンでだけ開けます。」の 1 文を足します。`SACTY_WEB_URL` を URL として読めないときも添えます。
- Issue を作れなかった理由は、伏せ済みの `failure` を 1 行にし、500 文字までにして知らせに書きます。
- 既定のコンテキスト（`apps/daemon/default-context/`）は変えません。PR に投稿する文が無いためです。

## PR の本文の形

- 結論：「変更」「最後の直し」と、不合格のまま進めた記録・人が確かめること（`keep` のまま）。
- 「## レビューの進め方」：`REVIEW_BODY_LINE` を次の 1 項目 1 文に分け、AI のレビューの行を続けます。
  - Sacty のレビューの子タスクが、この PR をレビューして投稿します。
  - 指摘があれば Sacty が直し、指摘なしになるとドラフトを外します。
  - Sacty はテストの実行と CI の待ちをしないので、CI の結果はこの PR のチェックで確かめてください。
  - AI のレビュー：この head（abc1234）には、Sacty の AI のレビューがまだ付いていません。
  - この状況は本文を書いた時点のものなので、最新の状況はこの PR のレビューの欄で確かめてください。
- 要求要件の全文：マージで承認した PR が無いとき、要点の後に `<details>` で全文を載せます。
- 省いた続き：人が確かめることの 1 項目・一覧、所見、子タスクの内容は、省いた続きを結論の後の `<details>` に載せます。
- 要求要件・設計の PR の AI のレビューの行も、上の 2 文の形にします。

## 影響範囲

- 3 方向のマージ：目印と `keep` の作りは変えないので、古い形の本文を祖先にしたマージはそのまま動きます。
- 取り込み：見分けは HTML のコメントの目印で行い、目印は変えません。
- 文書：`docs/spec/approval.md`・`intake.md`・`tasks-and-steps.md`、`docs/user/intake.md`・`tasks.md`・`notifications.md` を日英で直し、ADR（20261101-1400 の全文の場所を PR の中に改める）と作業履歴を足します。
- PR の説明に、変わった文の前・後の例を載せます。

## テスト観点

- [TV-1] ループバックのホストでは、知らせ 4 種のタスクの画面へのリンクに注釈が付く
  - 入力：SACTY_WEB_URL を http://127.0.0.1:4700・http://localhost:4700・http://[::1]:4700 にして、人に確かめてほしいこと・設計に戻した・レビューが止まった・後続に回す決定の知らせを組み立てる
  - 期待結果：どの知らせも、/tasks/<ID> へのリンクの文の直後に「タスクの画面は、依頼した人のマシンでだけ開けます。」がある
- [TV-2] ループバックでないホストと、読めない URL の注釈
  - 入力：SACTY_WEB_URL を https://sacty.example.com と、URL として読めない文字列にして、同じ 4 種の知らせを組み立てる
  - 期待結果：https://sacty.example.com では注釈が無く、読めない文字列では注釈がある
- [TV-3] AI のレビューの行が画面を案内しない
  - 入力：aiReview の status を none・reviewing・attached・unknown にして、実装の PR と要求要件・設計の PR の本文を組み立てる
  - 期待結果：どの本文にも「承認の画面」が無く、「最新の状況はこの PR のレビューの欄で確かめてください。」の 1 文があり、AI のレビューの行に括弧書きの注釈が無い
- [TV-4] 決まった形の本文の結論とレビューの進め方の節
  - 入力：最後の直し・不合格のまま進めた記録・人が確かめることがあるタスクで、テンプレートの無い実装の PR の本文を組み立てる
  - 期待結果：「## 結論」の項目は変更・最後の直しだけで、記録と人が確かめることが続き、その後の「## レビューの進め方」に設計の 3 文と AI のレビューの 2 文が 1 項目ずつある
- [TV-5] テンプレートに沿わせる本文のレビューの行の置き場所
  - 入力：PR テンプレートがあるリポジトリで、実装の PR の本文を組み立てる
  - 期待結果：目的の節にレビューの行と AI のレビューの行が無く、末尾の Sacty の記録の承認の案内の前に、同じ 1 項目 1 文の行がある
- [TV-6] マージで承認した PR が無いときの要求要件・再現の全文
  - 入力：mergedStepPullRequests が空で、approved.requirements と、再現の工程のタスクの approved.reproduce に複数の段落の成果があるタスクの本文を組み立てる
  - 期待結果：要点の後の <details> に成果の全文がそのまま入り、「タスクの画面で確かめてください」が無い
- [TV-7] 人が確かめることの 1 項目と一覧が上限を超えたとき
  - 入力：1,200 文字の項目 1 件と、合わせて 6,000 文字を超える項目を持つタスクの本文を組み立てる
  - 期待結果：結論の項目は上限で切られ、切られた項目の全文と入りきらない項目が結論の後の <details> にあり、本文に「タスクの画面」が無い
- [TV-8] 不合格のまま進めた記録の所見と子タスクの内容が上限を超えたとき
  - 入力：所見が 1,200 文字の不合格の記録と、内容が 9,000 文字の分割の子タスクで本文を組み立てる
  - 期待結果：所見と子タスクの内容の全文が <details> で本文にあり、「続きは sacty のタスクの画面で」が無い
- [TV-9] 本文の全体が上限を超えたときの省いた文
  - 入力：main と footer をつなぐと 65,000 文字を超える本文を limitBody に渡す
  - 期待結果：省いた所に、省いた文字数と GitHub の本文の上限を書いた文があり、「タスクの画面」が無く、keep と footer が残る
- [TV-10] Issue を作れなかった理由を知らせに書く
  - 入力：秘密の値を含むエラーで createIssue が失敗する後続に回す決定を処理する
  - 期待結果：知らせに失敗の理由が 1 行で書かれ、秘密の値は伏せ字になり、「作業履歴にあります」が無い
- [TV-11] 人が読む文の製品名と、変えない識別子
  - 入力：実装の PR・要求要件・設計の PR の本文（決まった形とテンプレート）、指摘への返信、工程のコメント、PR の指摘から作る Issue の本文を組み立てる
  - 期待結果：人が読む文の製品名はすべて「Sacty」で、`sacty task <ID>`・`<!-- sacty-` の目印・ラベル・ブランチ名は変わらない
- [TV-12] 新しい文の投稿を、取り込みが Sacty のものと見分ける
  - 入力：新しい文で組み立てた返信・人に確かめてほしいことの投稿・設計に戻した・レビューが止まった・後続に回す決定の知らせを、PR のフィードバックとして読む
  - 期待結果：どれも Sacty の投稿と見分けられて人の指摘として取り込まれず、readRemarkReply は返信の状態を、書いたとおりに読む
- [TV-13] 古い文言の投稿も見分ける

  - 期待結果：今までと同じく Sacty の投稿と見分けられ、readRemarkReply は対応した・対応しない・後続に回す提案の状態を読む
- [TV-14] 古い形の本文を祖先にした 3 方向のマージ
  - 入力：前回の記録が今までの形の本文で、人が「変更」の節に 1 行足した PR を、新しい形の本文で更新する
  - 期待結果：人が足した行と新しい「## レビューの進め方」の両方を含む本文にマージされ、重なったときはオーケストレーターにまとめさせる経路に進む
- [TV-15] 本文が空のレビューの原因の記録
  - 入力：差分の docs/spec/approval.md の指摘への対応の返信の節（英語の版も）と、作業履歴を読む

  - 期待結果：結論の項目、レビューの進め方の節、注釈を付ける条件、要求要件の全文と省いた続きの置き場所、省いた量の書き方、製品名の決まりが新しい振る舞いのとおりに書かれ、画面で続きを確かめる案内が残っていない
