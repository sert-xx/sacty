# 要求要件：人の差し戻しの回数の上限を無くす（PBI-414）

## スコープ

同じ工程への人の差し戻しを、回数によってエスカレーションにしない。
以前の版で上限のために止まったタスクは、残った指摘を元の形のまま使い、人の補足を別に足して進められるようにする。

- 対象
  - デーモンの差し戻し（画面・PR の指摘の取り込み・一時停止からの再開・「この PR で直す」）と `sacty mcp` の `request_changes`
  - 残った指摘を持つエスカレーションの画面と、その差し戻しの入力
  - 上限を前提にした文言（画面〔日英〕・`sacty mcp`・デーモンのメッセージ）と、過去の記録の表示
  - 仕様書（承認と差し戻し・MCP サーバー）・ユーザードキュメント（日英）・ADR・作業履歴
- 対象外
  - `sacty mcp` からの戻し先・原因・工程の設定の指定と、エスカレーション中のタスクの差し戻し
  - 人の差し戻しの回数の上限でない上限（AI のレビューの指摘だけの回の扱い・予算・AI の自動のやり直し・指摘の 50 件と 1 件 2,000 文字）と、`change_proposed` のエスカレーション

## 確認したいこと

### must

なし

### should

- `too_many_changes` で止まったタスクを、エスカレーションした工程とは別の工程に戻すとき、残った指摘を引き継ぐか。
  推奨：引き継がず、人の補足だけで差し戻す（今の決まり。`rework_confirmation` だけは戻し先を問わず引き継ぐ）。
  懸念：引き継ぐのが正しかった場合、別の工程に戻したタスクで PR の指摘が対応されず、PR に返信も付きません。
- 残った指摘と人の補足を合わせて 50 件を超えるとき、断るか。
  推奨：50 件の上限は人の補足だけに当て、合わせた件数では断らない（2,000 文字を補足だけに当てるのと同じ分け方）。
  懸念：合わせて断るのが正しかった場合、51 件以上の差し戻しを記録したタスクが残り、検査と画面を作り直す手間が出ます。

### 確認しないと決めたこと

- 以前の版の画面・呼び出しが送る「上限を超えて差し戻す」の指定：断らずに無視する（R-19）。
  入力は知らない項目を捨てる作りで、画面とデーモンは同じ版で配られるため。
- 新しく記録する差し戻しの `overLimit`：常に偽にする（R-1）。
  上限が無く、表示「上限を超えて」が新しい記録に出ないことが受け入れ条件 4 から決まるため。
- 残った指摘の書き直し：できなくする（R-12）。
  利用者の決定 2（元の形のまま渡し、補足は別の欄）で決まっているため。
- ADR の置き換えの範囲（全体か一部か）：設計で決める。
  `docs/adr/README.md` の決まりで決められるため。
- `changeRounds` を残すか・使われなくなったコードをどこまで消すか：設計と実装で決める。
  依頼が実装に任せているため。

## 既定で決めたこと

- 差し戻しの指摘は、残った指摘を元の順に並べ、その後ろに人の補足を並べる。
- 人の補足は、今の差し戻しの欄と同じく 1 行を 1 件とする。

## 受け入れの確かめ方

### 自動のテストで確かめること

- `npm run lint`・`npm run typecheck`・`npx vitest run --no-file-parallelism` が通る。
- R-8〜R-11 の経路ごとに、同じ工程への 4 回目の人の差し戻しが `ChangesRequested` になり、`TaskEscalated` が記録されない。
- 以前の版の作業履歴（`too_many_changes`・`rework_confirmation` のエスカレーション、`overLimit: true`）を合成して、R-12〜R-19・R-2・R-3 を確かめる。
  複数行の指摘と 2,000 文字を超える指摘、`origin` のある指摘を含める。
- AI のレビューの指摘だけの差し戻し・`change_proposed` のエスカレーションの今のテストが、変えずに通る。

### 人が確かめること

- 以前の版で `too_many_changes` で止まったタスクを画面で開き、残った指摘と補足の欄を見て差し戻す。
  画面の並びが崩れると、利用者が残った指摘を読めずに判断します。
- その差し戻しの後、GitHub の PR で元のコメントに返信が付く。
  付かないと、PR のレビューの担当者が対応を知れません。
