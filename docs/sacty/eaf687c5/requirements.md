# 要求要件：人の差し戻しの回数の上限を無くす（PBI-414）

## スコープ

同じ工程への人の差し戻しを、回数によってエスカレーションにしない。
以前の版で上限のために止まったタスクは、残った指摘を元の形のまま使い、人の補足を別に足して進められるようにする。

- 対象
  - デーモンの差し戻し（画面・PR の指摘の取り込み・一時停止からの再開・「この PR で直す」）と `sacty mcp` の `request_changes`
  - 残った指摘を持つエスカレーションの画面と、その差し戻しの入力
  - 上限を前提にした文言（画面〔日英〕・`sacty mcp`・デーモンのメッセージ）と、過去の記録の表示
  - 上限を前提にした記述のある仕様書（承認と差し戻し・MCP サーバー・取り込みなど）・ユーザードキュメント（日英）・ADR・作業履歴
- 対象外
  - `sacty mcp` から戻し先・原因・工程の設定を指定すること。`sacty mcp` からエスカレーション中のタスクを差し戻すこと（画面からの差し戻しは対象）
  - 人の差し戻しの回数の上限でない上限（AI のレビューの指摘だけの回の扱い・予算・AI の自動のやり直し・指摘の 50 件と 1 件 2,000 文字）と、`change_proposed` のエスカレーション
  - 差し戻しの回数の表示を足すこと

## 確認したいこと

### must

なし

### should

- `too_many_changes` で止まったタスクを、エスカレーションした工程とは別の工程に戻すとき、残った指摘を引き継ぐか。
  推奨：引き継がず、人の補足だけで差し戻す（今の決まり。`rework_confirmation` だけは戻し先を問わず引き継ぐ）。
  懸念：引き継ぐのが正しかった場合、別の工程に戻したタスクで PR の指摘が対応されず、PR に返信も付きません。
- 残った指摘と人の補足を合わせて 50 件を超えるとき、断るか。
  推奨：50 件の上限は人の補足だけに当て、合わせた件数では断らない（2,000 文字を補足だけに当てるのと同じ分け方）。
  懸念：合わせて断るのが正しかった場合、51 件以上の差し戻しを記録したタスクが残り、検査と画面を作り直す手間が出ます。
- 新しい版を配る前から開いていた画面で差し戻すと、残った指摘が補足の欄に入ったまま届き、同じ文が二重になる。これを許すか。
  推奨：許す。配布をまたいだ操作だけで起きるうえ、複数行の指摘は行に割れて届くため、同じ行を除いても重複を防ぎきれない。
  懸念：防ぐのが正しかった場合、その操作をしたタスクで、やり直しが同じ指摘に二度対応し、PR に同じ返信が 2 件付きます。

### 確認しないと決めたこと

- 以前の版の画面・呼び出しが送る「上限を超えて差し戻す」の指定：断らずに無視する（R-19）。
  上限が無くなって指定の意味が無いうえ、配布の前から開いていた画面からも送られうるため。
- 新しく記録する差し戻しの `overLimit`：常に偽にする（R-1）。
  上限が無いうえ、表示「上限を超えて」は以前の版の記録にだけ出すと依頼で決まっているため。
- 残った指摘の書き直し：できなくする（R-12）。
  残った指摘は元の形のまま渡し、人の補足は別の欄で足すと利用者が決めているため。

## 既定で決めたこと

- 差し戻しの指摘は、残った指摘を元の順に並べ、その後ろに人の補足を並べる。
- 人の補足は、今の差し戻しの欄と同じく 1 行を 1 件とする。

## 受け入れの確かめ方

### 自動のテストで確かめること

- `npm run lint`・`npm run typecheck`・`npx vitest run --no-file-parallelism` が通る。
- 要求ごとに、合成の作業履歴で確かめる。作業履歴には、以前の版の `too_many_changes`・`rework_confirmation` のエスカレーションと、`overLimit: true` の差し戻しを含める。

| ID | 入力 | 期待 |
| --- | --- | --- |
| R-1・R-8〜R-11 | 経路ごとに、同じ工程への 4 回目の人の差し戻し | `ChangesRequested`（`overLimit` が偽）が記録され、`TaskEscalated` が記録されない |
| R-2・R-3 | `overLimit: true`・`too_many_changes` を含む作業履歴 | 読み込みが失敗せず、画面・作業履歴の表示・`get_task` が以前の版の記録と分かる文を出す |
| R-12 | 複数行の指摘を含む残った指摘 5 件 | 画面に 5 件が元の文で出て、補足の欄が別にある。PR を作った工程では承認のボタンが出ない |

- AI のレビューの指摘だけの回の扱いと、`change_proposed` のエスカレーションを確かめるテストが通る。人の指摘で上限に当たってエスカレーションになると期待するテストは、R-8 に合わせて期待を変える。
- R-5〜R-7：新しい ADR と置き換えの記載、日英の仕様書・ユーザードキュメントの直し、作業履歴の 1 件を、差分で確かめる。`tests/docs/docs.test.ts` が通る。

### 人が確かめること

- 以前の版で `too_many_changes` で止まったタスクを画面で開き、残った指摘と補足の欄を見て差し戻す。
  画面の並びが崩れると、利用者が残った指摘を読めずに判断します。
- その差し戻しの後、GitHub の PR で元のコメントに返信が付く。
  付かないと、PR のレビューの担当者が対応を知れません。
