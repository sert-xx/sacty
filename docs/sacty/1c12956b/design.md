# 設計：実装の PR の局所の設計の決定は、実装の PR の中で設計書も直す（PBI-446）

## スコープ

実装の PR の指摘の戻し先を、「方針の変更は設計、局所の変更は実装」に分ける。
実装で直す回は、実装が出した設計の直しを sacty が承認済みの設計に反映し、同じ実装の PR に入れる。
設計に戻した回は、実装の PR に知らせを1通投稿する。
困りごと：局所の指摘でも設計の1周（約 30 分・約 10 ドル・人のマージ1回）が足される。採らなかった案：変更の申し出（人が画面で1件ずつ認める）で直す。

- 対象
  - 戻し先の基準の文（実装の PR の2つの経路：レビューの子タスク・工程のエージェント）
  - 実装が出す設計の直し、sacty の検査と反映、実装の PR のコミットと本文、作業履歴の行（画面の日英）
  - 設計に戻したときの、実装の PR への投稿と、次の取り込みで外すこと
  - 仕様書 `approval`・`tasks-and-steps`（日英）、ユーザードキュメント `tasks`（日英）、新しい ADR と 2026-11-01 の ADR の置き換え、作業履歴
- 対象外
  - 要求要件・設計の PR の戻し先の基準（今の文のまま）
  - 設計のテスト観点の直し（実装から直せるのは設計の本文だけ）
  - 既定のコンテキスト（戻し先の基準を持たないので触らない）

## 確認したいこと

- must
  1. 1回の判断に局所と方針の指摘が混ざるとき、全部を設計に戻すか。
     推奨：はい（設計のやり直しで局所の指摘も扱え、実装と設計が同時に直す食い違いが無い）。
     懸念：方針の指摘1つのために、局所の指摘も設計の1周を待ち、本件で減らしたい回数が残る。
  2. 「迷えば実装に倒す」から、セキュリティ・認可・保存するデータの形・移行に触れる指摘を除き、迷えば設計に戻すか（依頼の「迷えば実装」には除外が無い）。
     推奨：除く（これらは方針の変更の例に入る取り返しにくい決定で、実装に倒すと設計の PR を経ずに main に入る）。
     懸念：これらに触れる局所に見える指摘（認可の文言の1行など）でも、設計の1周が残る。除かないと、セキュリティの決定が人の設計のレビューを経ないまま入る。
- should
  1. 人が「実装の工程で直す」と明示した指摘は、セキュリティ・認可・保存するデータの形・移行の決定を変えても実装で直すか。
     推奨：はい（受け入れ条件 3。人が承認を実装の PR のマージで兼ねると選んでいる）。
     懸念：人が設計への影響に気づかずに書くと、セキュリティの決定が設計の PR のレビューを経ないまま main に入る。
  2. 方針を変える直しを、下の機械の検査（直せる節の限定を含む）と次の回の AI のレビューで見分けるので足りるか（判定のための AI の実行も、語による内容の検査も足さない）。
     推奨：足りる（戻し先の判断が、指摘ごとに局所と判定済み。判定を足すと毎回の費用が増え、語の検査は言語・製品に寄るので受け入れ条件 1 の汎用の決まりと合わない。直しは PR の設計のファイルの差分と本文に前・後が載り、人がマージで見る）。
     懸念：今回の指摘の ID を付けた、既定値の1行に見えるセキュリティの決定の書き換えを AI のレビューも見落とすと、人が設計として見ないまま main に入る。
  3. 反映しなかった設計の直しがあっても、実装は止めずに提出し、PR の本文に直しと理由を載せるか。
     推奨：はい（止めると、局所の1行のために人の判断待ちが戻る）。
     懸念：人が本文を見落とすと、指摘は直ったように見えて、設計書が古いまま main に入る。
  4. テスト観点の入力・期待結果を変える指摘は、今回は設計に戻すか（基準の文に例外として書く）。
     推奨：はい（観点は実装のテストの対応と結び付いていて、直すと対応の引き継ぎが要る）。「いいえ」なら、`sacty-design-edit` に観点の直しを足し、反映でテストの対応を消す。
     懸念：観点の文言1つの指摘のために、本件で無くしたい設計の1周が残る。
  5. 設計を直したとき、外への書き出し（export）を直した後の版でやり直すか。
     推奨：しない（`approved.design.at` を変えない。人がマージする前に、直した設計を外へ出さない）。
     懸念：書き出し先（チケットなど）の設計が、直す前の版のまま残る。

## 既定で決めたこと

- 設計の直しは置き換え（`before`・`after`）の形で出させ、全文は出させない（範囲の検査と、PR での読みやすさのため）。
- 反映は `ChangeApplied` と違い、`implementHistory`・`implementBase` を消さない（同じ PR の続きなので、説明とテストの対応を引き継ぐ）。設計のセルフレビュー・出典の分類は「記録なし」にする。
- 人の明示に従う文は、実装の PR の判断にだけ入れる。
- 局所の直しは `sacty-design-edit`、方針の変更は変更の申し出（`sacty-change-proposal`）と、実装の指示に書き分ける。
- 実装の PR のマージで、PR の設計のファイルを承認済みの設計に読み戻さない（承認済みは反映した版のまま）。

## 構成

| 所 | 変えること |
| --- | --- |
| `prompts.ts` `reworkDecisionLines(own, gateStep)` | gateStep が実装のときだけ、次の文を足す：設計の決定の変更を方針・局所に分ける文、迷えば実装に倒す文（セキュリティ・認可・保存するデータの形・移行は除く）、承認済みのテスト観点の入力・期待結果を変える指摘は design とする文、人の明示に従う文。理由の書式を「決定を変えない／変える（局所）／変える（方針）：…」にする。要求要件の決定の変更の扱いは今のまま |
| `reviewReworkLines`・`buildReworkPrompt` | 実装の PR の候補 `design` の説明を「方針の変更が要る」にする |
| 実装の直しの指示 | PR の指摘で実装に戻した回で、設計が承認済みのときだけ、`sacty-design-edit` の出し方と、方針は申し出で出すことを足す。承認済みの設計は今も指示に入るので、作業領域に成果物を入れない決定（PBI-262）は保つ。新しい版を出す前に implement と判断した回を再開するときも、指示は今の版で作り直す（戻し先の判断は作り直さない） |
| `packages/core` | イベント `DesignEdited`（実装の提出回・実行の ID・反映後の全文・反映した直し・反映しなかった直しと理由。どれも伏せた後）を足す。投影は全文で `approved.design.output`・`outputs.design` を置き換え、設計のセルフレビュー・出典の分類を記録なしにする。`at`・`implementHistory`・`implementBase` は変えない。同じ実行の2つ目は記録しない |
| `service.ts` | 実装の出力を検査し、`DesignEdited` を実装の提出の記録より前に記録する。再開で同じ実行の記録があれば、検査をやり直さずに使う。コミットでは、設計のファイルを `keep` から外し、タスクブランチの先頭のファイルに、まだコミットに入れていない `DesignEdited` の置き換えを記録順に当てて書く（人が直した内容とテスト観点の節を保つ。実装の PR のブランチはタスクブランチなので、前の回にコミットした直しは先頭に入っている）。`before` は、承認済みの設計と、その置き換えを当てた後のファイルの両方で探す。ファイルが無いタスクは、承認済みの設計と PR の本文だけを直す。PR の本文の「設計の直し」に、直しごとの前・後・指摘を載せる |
| `rework-notice.ts`（新規） | 設計に戻した知らせを作る。伝え方は「次の回から、指摘に『実装の工程で直す』と書く」（設計のやり直しはすでに始まっている）。新しい版が記録した実装の PR の design の判断（`ReworkJudged` に印を足す）の後に投稿し、目印 `<!-- sacty-rework-notice:<タスク ID>:<回> -->` で二重の投稿を防ぐ。秘密情報の伏せ・600 文字・`@`・内部のパス・セキュリティの組み合わせ・失敗の扱いは、人に確かめてほしいことの投稿と同じにする |
| `github.ts` | `isReworkNotice` を足し、`isHumanAskNotice` で外している所のすべて（PR の指摘の取り込み、`service.ts` のレビューの見守りの返信の数え方）で同じく外す |
| 仕様書 `approval` | 「承認した成果は固定される」に、局所の設計の直しを実装の PR のマージで承認する例外を書く |

出力の形：`{"sacty-design-edit": {"edits": [{"remarks": ["指摘の ID"], "before": "承認済みの設計の原文", "after": "直した後", "reason": "理由"}]}}`

- `DesignEdited` を一度記録すると、前の版のデーモンは作業履歴を読む段階で失敗して起動できない（`activity.ts` の `toEvent` が知らない種類で失敗する）。記録した後は版を戻せないことを、新しい ADR の影響に書く。

## エラー時の振る舞い

次の直しは反映しない。
理由を `DesignEdited` と PR の本文に残し、実装の提出は続ける。

- `remarks` が、今回の対応する指摘に無い
- `before` が空、承認済みの設計またはタスクブランチの設計のファイルに無い、または2か所以上にある
- `before` が、冒頭の3節（スコープ・確認したいこと・既定で決めたこと）か「テスト観点」の節にある
- 見出しの行を足す・消す・変える、`before`・`after` が 2,000 文字を超える、11 件目以降
- `before`・`after`・`reason` が秘密情報の値を含む、または `after` が内部のパス・`@` の付く名前を含む（PR の本文・イベントに載せる文は、知らせと同じく伏せ・内部のパスの置き換え・`@` の無効化をする）
- 同じ出力に変更の申し出もある（全部を反映せず、申し出だけを扱う）
- ブロックが読めない（直しは0件とし、読めなかったことを本文に載せる）

## テスト観点

- [TV-1] 工程のエージェントの戻し先の指示に、重さで分ける基準が入る
  - 入力：設計が承認済みのタスクで、gateStep を実装にして buildReworkPrompt を呼ぶ
  - 期待結果：方針の変更（方式・構成・範囲・受け入れ条件・公開するインターフェース・保存するデータの形・セキュリティ・移行）だけを design、局所の変更（文言・表や一覧の1行・既定値・行の追加）を implement とする文、迷えば implement に倒す文（セキュリティ・認可・保存するデータの形・移行を除く）、承認済みのテスト観点の入力・期待結果を変える指摘を design とする文、理由に変える（局所）／変える（方針）を書かせる例が入る
- [TV-2] レビューの子タスクの指示に、同じ基準が入る
  - 入力：gateStep を実装にした ReviewReworkContext で reviewReworkLines を呼ぶ
  - 期待結果：観点 1 と同じ基準の文が入り、候補 design の説明が方針の変更が要るものになっている
- [TV-3] 要求要件の決定を変える指摘の戻し先は変わらない
  - 入力：観点 1・2 と同じ呼び出し
  - 期待結果：承認済みの要求要件の決定を変える指摘を requirements に戻す文が今の文のまま入っている
- [TV-4] 要求要件・設計の PR の基準は変わらない
  - 入力：gateStep を設計・要求要件にして buildStepReworkPrompt と reviewReworkLines を呼ぶ
  - 期待結果：起点（be4d26d）と同じ基準の文で、方針・局所の文と人の明示に従う文は入らない
- [TV-5] 人の指摘の戻し先の明示に従う
  - 入力：gateStep を実装にして buildReworkPrompt を呼ぶ
  - 期待結果：人の指摘が「設計に戻す」「実装の工程で直す」などと戻し先を明示していれば、それに従う文が入る
- [TV-6] 設計の直しの出し方は、PR の指摘で実装に戻した回だけに入る
  - 入力：設計が承認済みで PR の指摘で実装に戻した回（新しい版の前に implement と判断した ReworkJudged から再開する回を含む）と、初回の実装・設計の工程が無いタスクの回で実装の指示を作る
  - 期待結果：前者にだけ sacty-design-edit の形・今回の指摘の ID・方針の変更は sacty-change-proposal で出すという文が入り、後者には入らず、再開の回でも ReworkJudged は新しく記録されない
- [TV-7] 局所の直しが承認済みの設計に反映される
  - 入力：今回の指摘の ID と、承認済みの設計とタスクブランチの設計のファイルに1か所だけある本文の節の before を持つ直しを出した実装の実行が終わる
  - 期待結果：反映後の全文を持つ DesignEdited が実装の提出の記録より前に1件記録され、approved.design.output と outputs.design の該当箇所だけが after になり、approved.design.at・テスト観点・implementHistory・implementBase は変わらず、設計のセルフレビューと出典の分類が記録なしになる
- [TV-8] 記録した列の再生が同じ設計になる
  - 入力：観点 7 の後のイベントの列を、空の状態から投影し直す
  - 期待結果：approved.design.output と outputs.design が、記録の時点と同じ反映後の全文になる
- [TV-9] 記録の後に止まって再開しても、二重に記録しない
  - 入力：観点 7 の DesignEdited の記録の後、実装の提出の前にデーモンを止めて再開する
  - 期待結果：同じ実行の DesignEdited は1件のままで、PR の本文の直しは「反映した」と載る
- [TV-10] 実装の PR に直した設計と直しの説明が入る
  - 入力：人が設計の PR で本文を直してマージしたタスクで、観点 7 の後に実装の PR を出し、さらに次の PR の指摘で実装に戻した回に、1回目の after の一部を before にした2つ目の直しを出す
  - 期待結果：各回のコミットの設計のファイルが、タスクブランチの先頭のファイルの before だけを after にしたもので（人の直し・1回目の直し・テスト観点の節は1つのまま残る）、2つ目の直しも反映され、PR の本文の「設計の直し」に前・後・指摘が載る
- [TV-11] 設計のファイルが無いタスクでも直しを反映する
  - 入力：設計を画面で承認したタスク（タスクブランチに設計のファイルが無い）で、観点 7 と同じ直しを出す
  - 期待結果：承認済みの設計と PR の本文の「設計の直し」が直り、コミットに設計のファイルは足されない
- [TV-12] その後のレビュー・直し・設計のやり直しは直した設計を基準にする
  - 入力：観点 7 の後に、レビューの子タスクの指示、戻し先の判断の指示、方針の変更で設計に戻したときの設計の指示を作る
  - 期待結果：どれも承認済みの設計の節が直した後の文になっている
- [TV-13] 範囲を超える直しは反映されない
  - 入力：今回の指摘に無い ID・承認済みの設計に無い before・2か所にある before・確認したいことの節の before・テスト観点の節の before・見出しの行を変える after・2,001 文字の after・11 件目の直し・秘密情報の値を含む after・内部のパスを含む after・@ の付く名前を含む after・変更の申し出と同時の直しを、それぞれ出す
  - 期待結果：どれも承認済みの設計と PR の設計のファイルを変えず、理由が DesignEdited と PR の本文に残り、実装の PR は提出される
- [TV-14] 設計に戻した回に、実装の PR へ知らせが1通だけ投稿される
  - 入力：実装の PR の指摘の判断が design になる（子タスクの rework の経路と工程のエージェントの経路のそれぞれ）。投稿の後に同じ判断から再開する。別に、新しい版の前に記録した design の判断から再開する
  - 期待結果：前者は目印付きの知らせが1通だけ投稿され、戻したこと・理由・設計の PR を承認すること・次の回から「実装の工程で直す」と書く伝え方が書かれ、後者は投稿されない
- [TV-15] 知らせが次の取り込みとレビューの見守りで数えられない
  - 入力：観点 14 の知らせが Bot でないプロジェクトの gh のアカウントで投稿された PR で、PR の指摘を取り込み、別にレビューの見守りが作者の返信を数える
  - 期待結果：知らせは人の指摘として取り込まれず戻し先の判断の材料にならず、見守りの返信にも数えられず再レビューが始まらない
- [TV-16] 知らせと設計の直しの本文は今の PR への投稿と同じ作法で作られる
  - 入力：知らせの理由と、直しの before・after・reason・反映しなかった理由に、秘密情報の値・@ の付く名前・内部のパス・600 文字を超える文を含め、セキュリティの組み合わせのタスクと投稿が失敗する場合も試す
  - 期待結果：PR の本文・知らせ・DesignEdited・設計のファイル・承認済みの設計のどれにも値と内部のパスが残らず、PR の本文と知らせでは @ の後に幅の無い空白が入り、知らせは 600 文字で切られ、セキュリティの組み合わせでは投稿せず、失敗してもタスクの状態は変わらない
- [TV-17] 作業履歴に設計の直しの行が出る
  - 入力：DesignEdited を含むタスクの作業履歴を日英の画面で開く
  - 期待結果：反映した件数と反映しなかった件数の分かる行が、日本語と英語の文言で出る
- [TV-18] 変えないものが変わらない
  - 入力：実装の PR の判断の指示・選り分けの指示・変更の申し出の指示を作る
  - 期待結果：cause の選択肢、選り分けで対応しないとした提案を判断の材料から外すこと、指摘の重み、sacty-change-proposal の形と条件が起点と同じ
- [TV-19] 仕様書・ユーザードキュメントに新しい基準と道が書かれている
  - 入力：docs/spec/approval.md・tasks-and-steps.md と docs/user/tasks.md、それぞれの英語版の差分
  - 期待結果：方針・局所の分け方と例、迷えば実装に倒すこととその除外、人の明示に従うこと、設計の直しの検査と反映と PR での見え方、承認した成果の固定の例外、設計に戻した知らせが日英で同じ構成で書かれ、tests/docs が通る
