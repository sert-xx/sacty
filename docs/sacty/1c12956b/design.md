# 設計：実装の PR の局所の設計の決定は、実装の PR の中で設計書も直す（PBI-446）

## スコープ

実装の PR の指摘の戻し先を、「方針の変更は設計、局所の変更は実装」に分ける。
実装で直す回は、実装が出した設計の直しを sacty が承認済みの設計に反映し、同じ実装の PR に入れる。
設計に戻した回は、実装の PR に知らせを1通投稿する。

- 対象
  - 戻し先の基準の文（実装の PR の2つの経路：レビューの子タスク・工程のエージェント）
  - 実装が出す設計の直し、sacty の検査と反映、実装の PR のコミットと本文、作業履歴の行（画面の日英）
  - 設計に戻したときの、実装の PR への投稿
  - 仕様書 `approval`・`tasks-and-steps`（日英）、ユーザードキュメント `tasks`（日英）、新しい ADR と 2026-11-01 の ADR の置き換え、作業履歴
- 対象外
  - 要求要件・設計の PR の戻し先の基準（今の文のまま）
  - 設計のテスト観点の直し（実装から直せるのは設計の本文だけ）
  - 既定のコンテキスト（戻し先の基準を持たないので触らない）

## 確認したいこと

- must：なし
- should
  1. 反映しなかった設計の直しがあっても、実装は止めずに提出し、PR の本文に直しと理由を載せるか。
     推奨：はい（止めると、局所の1行のために人の判断待ちが戻る）。
     懸念：人が本文を見落とすと、指摘は直ったように見えて、設計書が古いまま main に入る。
  2. 方針を変える直しを、下の機械の検査と次の回の AI のレビューで見分けるので足りるか（判定のための AI の実行を足さない）。
     推奨：足りる（戻し先の判断が、指摘ごとに局所と判定済み。判定を足すと毎回の費用が増える）。
     懸念：既定値の1行に見えるセキュリティの決定を AI のレビューも見落とすと、人が設計として見ないまま main に入る。
  3. テスト観点の文言を変える指摘は、今回は設計に戻すままでよいか。
     推奨：はい（観点は実装のテストの対応と結び付いていて、直すと対応の引き継ぎが要る）。
     懸念：観点の文言1つの指摘のために、本件で無くしたい設計の1周が残る。
  4. 知らせに書く「実装で直させたいときの伝え方」は、次の回からの書き方（指摘に「実装の工程で直す」と書く）でよいか。
     推奨：はい（設計に戻した回は、すでに設計のやり直しが始まっていて、実装に戻す操作が無い）。
     懸念：その回を実装に戻したい人は、手段が設計の PR の承認か差し戻ししか無いことを、知らせから読み取れない。
- 確認しないと決めたこと
  - 局所と方針が1回に混ざるとき：方針の変更が1つでもあれば、全部を設計に戻す。今の「1つでも変えるなら戻す」を保て、局所の指摘も設計のやり直しで扱えるので確かめない。
  - 重さを画面・集計に出すか：理由の文に書かせるだけにする。受け入れ条件 1 が理由に書くと決めているので確かめない。
  - `sacty-proposal`：コードの `sacty-change-proposal` と同じものとし、変えない。
  - 受け入れ条件 3：人の明示に従う文は今の指示に無い（`apps/daemon/src/prompts.ts` で確かめた）ので足す。

## 既定で決めたこと

- 設計の直しは置き換え（`before`・`after`）の形で出させ、全文は出させない（範囲の検査と、PR での読みやすさのため）。
- 設計のファイルは実装の PR のコミットで差し替え、タスクブランチには積まない（`pr.taskBranchChanged` と、人のコミットの取り込みが変わらない）。
- 反映は `ChangeApplied` と違い、`implementHistory`・`implementBase` を消さない（同じ PR の続きなので、説明とテストの対応を引き継ぐ）。
- 人の明示に従う文は、実装の PR の判断にだけ入れる。

## 構成

| 所 | 変えること |
| --- | --- |
| `prompts.ts` `reworkDecisionLines(own, gateStep)` | gateStep が実装のときだけ、次の文を足す：設計の決定の変更を方針・局所に分ける文、迷えば実装に倒す文、人の明示に従う文。理由の書式を「決定を変えない／変える（局所）／変える（方針）：…」にする。要求要件の決定の変更の扱いは今のまま |
| `reviewReworkLines`・`buildReworkPrompt` | 実装の PR の候補 `design` の説明を「方針の変更が要る」にする |
| 実装の直しの指示 | PR の指摘で実装に戻した回で、設計が承認済みのときだけ、`sacty-design-edit` の出し方を足す。承認済みの設計は今も指示に入るので、作業領域に成果物を入れない決定（PBI-262）は保つ |
| `packages/core` | イベント `DesignEdited`（回・反映した直し・反映しなかった直しと理由）を足す。投影で `approved.design.output`・`outputs.design` を置き換える |
| `service.ts` | 実装の出力を検査し、`DesignEdited` を記録してから提出する。コミットの設計のファイルを `buildStepDocument` の内容にする。PR の本文の「設計の直し」に、直しごとの前・後・指摘を載せる |
| `rework-notice.ts`（新規） | 設計に戻した知らせを作る。判断を記録した後に投稿し、目印 `<!-- sacty-rework-notice:<タスク ID>:<回> -->` で二重の投稿を防ぐ。秘密情報の伏せ・600 文字・`@`・内部のパス・セキュリティの組み合わせ・失敗の扱いは、人に確かめてほしいことの投稿と同じにする |

出力の形：`{"sacty-design-edit": {"edits": [{"remarks": ["指摘の ID"], "before": "承認済みの設計の原文", "after": "直した後", "reason": "理由"}]}}`

## エラー時の振る舞い

次の直しは反映しない。
理由を `DesignEdited` と PR の本文に残し、実装の提出は続ける。

- `remarks` が、今回の対応する指摘に無い
- `before` が空、承認済みの設計に無い、または2か所以上にある
- 見出しの行を足す・消す・変える、`before`・`after` が 2,000 文字を超える、11 件目以降
- ブロックが読めない（直しは0件とし、読めなかったことを本文に載せる）

## テスト観点

- [TV-1] 工程のエージェントの戻し先の指示に、重さで分ける基準が入る
  - 入力：設計が承認済みのタスクで、gateStep を実装にして buildReworkPrompt を呼ぶ
  - 期待結果：方針の変更（方式・構成・範囲・受け入れ条件・公開するインターフェース・保存するデータの形・セキュリティ・移行）だけを design、局所の変更（文言・表や一覧の1行・既定値・行の追加）を implement とする文、迷えば implement に倒す文、理由に変える（局所）／変える（方針）を書かせる例が入る
- [TV-2] レビューの子タスクの指示に、同じ基準が入る
  - 入力：gateStep を実装にした ReviewReworkContext で reviewReworkLines を呼ぶ
  - 期待結果：観点 1 と同じ基準の文が入り、候補 design の説明が方針の変更が要るものになっている
- [TV-3] 要求要件の決定を変える指摘の戻し先は変わらない
  - 入力：観点 1・2 と同じ呼び出し
  - 期待結果：承認済みの要求要件の決定を変える指摘を requirements に戻す文が今の文のまま入っている
- [TV-4] 要求要件・設計の PR の基準は変わらない
  - 入力：gateStep を設計・要求要件にして buildStepReworkPrompt と reviewReworkLines を呼ぶ
  - 期待結果：起点（be4d26d）と同じ基準の文で、方針・局所の文と人の明示に従う文は入らない
- [TV-5] 人の指摘の戻し先の明示に従う
  - 入力：gateStep を実装にして buildReworkPrompt を呼ぶ
  - 期待結果：人の指摘が「設計に戻す」「実装の工程で直す」などと戻し先を明示していれば、それに従う文が入る
- [TV-6] 設計の直しの出し方は、PR の指摘で実装に戻した回だけに入る
  - 入力：設計が承認済みで PR の指摘で実装に戻した回と、初回の実装・設計の工程が無いタスクの回で実装の指示を作る
  - 期待結果：前者にだけ sacty-design-edit の形と今回の指摘の ID が入り、後者には入らない
- [TV-7] 局所の直しが承認済みの設計に反映される
  - 入力：今回の指摘の ID と、承認済みの設計に1か所だけある before を持つ直しを出した実装の実行が終わる
  - 期待結果：DesignEdited が記録され、approved.design.output と outputs.design の該当箇所だけが after になり、テスト観点・implementHistory・implementBase は変わらない
- [TV-8] 実装の PR に直した設計と直しの説明が入る
  - 入力：観点 7 の後に実装の PR を出す
  - 期待結果：コミットの設計のファイルが直した後の buildStepDocument と同じ内容になり、タスクブランチは進まず、PR の本文の「設計の直し」に前・後・指摘が載る
- [TV-9] その後のレビュー・直しは直した設計を基準にする
  - 入力：観点 7 の後に、レビューの子タスクの指示と戻し先の判断の指示を作る
  - 期待結果：どちらの承認済みの設計の節も直した後の文になっている
- [TV-10] 範囲を超える直しは反映されない
  - 入力：今回の指摘に無い ID・承認済みの設計に無い before・2か所にある before・見出しの行を変える after・2,001 文字の after・11 件目の直しを、それぞれ出す
  - 期待結果：どれも承認済みの設計を変えず、理由が DesignEdited と PR の本文に残り、実装の PR は提出される
- [TV-11] 設計に戻した回に、実装の PR へ知らせが1通だけ投稿される
  - 入力：実装の PR の指摘の判断が design になる（子タスクの rework の経路と工程のエージェントの経路のそれぞれ）。投稿の後に同じ判断から再開する
  - 期待結果：目印付きの知らせが1通だけ投稿され、戻したこと・理由・設計の PR を承認すること・「実装の工程で直す」と書く伝え方が書かれている
- [TV-12] 知らせの本文は今の PR への投稿と同じ作法で作られる
  - 入力：理由に秘密情報の値・@ の付く名前・内部のパス・600 文字を超える文を含め、セキュリティの組み合わせのタスクと投稿が失敗する場合も試す
  - 期待結果：値が伏せられ、600 文字で切られ、@ の後に幅の無い空白が入り、内部のパスが置き換わり、セキュリティの組み合わせでは投稿せず、失敗してもタスクの状態は変わらない
- [TV-13] 作業履歴に設計の直しの行が出る
  - 入力：DesignEdited を含むタスクの作業履歴を日英の画面で開く
  - 期待結果：反映した件数と反映しなかった件数の分かる行が、日本語と英語の文言で出る
- [TV-14] 変えないものが変わらない
  - 入力：実装の PR の判断の指示・選り分けの指示・変更の申し出の指示を作る
  - 期待結果：cause の選択肢、選り分けで対応しないとした提案を判断の材料から外すこと、指摘の重み、sacty-change-proposal の形と条件が起点と同じ
- [TV-15] 仕様書・ユーザードキュメントに新しい基準と道が書かれている
  - 入力：docs/spec/approval.md・tasks-and-steps.md と docs/user/tasks.md、それぞれの英語版の差分
  - 期待結果：方針・局所の分け方と例、迷えば実装に倒すこと、人の明示に従うこと、設計の直しの検査と反映と PR での見え方、設計に戻した知らせが日英で同じ構成で書かれ、tests/docs が通る
- [TV-16] ADR と作業履歴が作法どおりにある
  - 入力：docs/adr と docs/worklog の差分
  - 期待結果：新しい ADR が置き換え元に 2026-11-01 の ADR を指し、古い ADR は superseded のファイル名・ステータス・置き換え先になり本文は変わらず、作業履歴へのリンクが直り、PBI-446 の作業履歴がひな形どおりにある
