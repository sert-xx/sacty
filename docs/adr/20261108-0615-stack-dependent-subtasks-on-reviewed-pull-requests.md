# 依存のある子タスクは、依存先の PR が最終レビューに合格した時点で、その PR のブランチに重ねて始める

- 日時: 2026-11-08 06:15 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-317
- 置き換え元: [大きなタスクを「タスク分割」の工程で子タスクに分け、子ごとに PR を作って依存の順に進める](20261012-0226-superseded-task-split-into-subtasks.md)（依存する子を、依存先の PR のマージの後に始める部分）
- 置き換え先: なし

## 背景

タスク分割の子タスクは並べて進むが、依存のある子タスクは `blocked` で始まり、依存先がすべて片付く（PR のマージなど）まで始まらなかった。
依存先の PR を人がレビュー・マージするまでの時間が、そのまま後の子タスクの待ちになっていた。
人は、待ちを減らす方法として「依存先のブランチから先に始める（重ねた PR）」を選んだ（2026-11-08）。
分割をもっと細かく選ばせる・同時実行の数の既定を上げる、は選ばなかった。

重ねて始めるには、次を決める必要があった。

- いつ始めるか（依存先のどの状態で）
- 起点（作業領域・PR の向き先）
- 依存先が直された・マージされた・中止されたときの、子タスクの作業領域と PR の扱い
- 依存先が複数あるときの起点
- マージの順序（依存先より先に子をマージさせない）の守らせ方
- デーモンを再起動しても状態を失わない記録の仕方

## 決定

- 始める時点：依存先の実装の PR が最終レビューに合格して承認待ちになったら（ドラフトを外す段の PR。人が不合格のまま進めた PR・引き継いだ人の PR は除く）、マージを待たずに子タスクを始める。
  依存先が完了したら・中止を人が認めたらの、今までの始め方も残す。依存先の PR がマージ済み（マージの後の監視の途中）で、ほかの PR に重ねていないなら、その依存先はベースブランチに入ったものとして扱う。重ねたまま先にマージされた依存先は、変更が重ねた先の PR のブランチにしか入っていないので、重ねた先がマージされて付け替えるまで、ベースブランチに入ったものとして扱わない。
- 起点：依存先の PR のブランチの、合格したコミットで作業領域を用意する（`TaskUnblocked` の `stackedOn`）。子タスクの起点のブランチ（`repository.baseBranch`）と PR の向き先は、依存先の PR のブランチにする。オーケストレーターが選ぶベースブランチは使わない。作業領域を用意する前に依存先がマージされたら、付け替えた起点のブランチ（`stackedBase`）の最新で用意する。
- 依存先が直されたら：ベースブランチの取り込みと同じ時点（実装を始める前・最終レビューの前）に、依存先の PR の、合格したコミットだけを取り込む。依存先が作り直しの途中（合格した PR が無い）なら取り込まない。衝突は、ベースブランチの取り込みと同じ扱い（目印を残して実装に解消させる）。承認待ちの間は取り込まない。
- 依存先がマージされたら：子タスクの起点のブランチを、依存先の PR が入ったブランチ（ふつうはベースブランチ）に付け替える（`StackedDependencyMerged`）。承認待ちの PR は、PR の確認（60秒ごと）で GitHub の向き先を付け替え、本文を書き直してドラフトを外す（`PullRequestRetargeted`）。付け替えている間は子タスクを実行せず、GitHub を待つ間に差し戻しなどでタスクが変わったら、ドラフトを外さず記録しない。作業領域への取り込みは、次のやり直しで、依存先の合格したコミットを共通の祖先にして行う。
- 依存先が中止されたら：重ねた子タスクを一時停止し、再開させない（中止はできる）。依存先の変更の上に作ったので、そのまま進めると中止した変更を持ち込むため。合格する前に依存先が中止されたときは、今までどおり子タスクを始めない。
- 依存先が複数あるとき：重ねられる1つ（X）があり、ほかの依存先の変更がすべて X の合格したコミットに入っていると確かめられる（X が待った依存先で、ベースブランチに入ったか、X の重ねの連なりにある）なら、X に重ねる。決められなければ（重ねる先を1つに決められない・別のリポジトリ・合格していない）待つ。互いに独立した依存先は、片方がマージされても、もう片方に重ねない（もう片方の合格したコミットに、マージされた側の変更が入っていないため）。
- マージの順序：重ねている間は、子タスクの PR を、検証に通った後もドラフトのままにする。ドラフトにできなければ（リポジトリがドラフトを使えない・切り替えに失敗した）、ドラフトでない PR にせず、承認待ちにせずに止める。本文の先頭に、どの PR に重ねたか・それより先にマージしないこと・マージされたら sacty が向き先を付け替えてドラフトを外すことを書く。人がドラフトを外して先にマージしたら、今までと同じく、マージを承認として扱う（子タスクの変更は依存先の PR のブランチに入る。依存先がマージされたら、その先へ付け替える）。
- 記録：`TaskUnblocked` の `stackedOn`（重ねた先とコミット）、`StackedDependencyMerged`（付け替え）、`PullRequestPublished` の `baseBranch`（重ねた子タスクの PR の向き先）、`PullRequestRetargeted`（GitHub の向き先の付け替え）。取り込みは今までの `BaseBranchMerged`。どれも作業履歴なので、再起動しても失わない。

## 理由

- 始める時点を「最終レビューに合格」にしたのは、人が依存先をレビューし始められる状態と、子が重ねられる状態をそろえるため。合格する前の PR は作り直されうるので、重ねると取り込み直しが増える。
- 取り込むのを合格したコミットだけにしたのは、依存先の作り直しの途中（検証の待ちのドラフト）の内容を子に入れないため。ブランチの先頭（人が積んだもの・作り直しの途中のもの）は使わない。
- 承認待ちの間に取り込まないのは、ベースブランチの取り込みと同じ方針にそろえるため（取り込んだら最終レビューをし直すことになり、人がレビューしている PR が変わる）。依存先が squash でマージされると、付け替えた PR の差分に依存先の変更が重なって見えることがある。差し戻し・指摘で実装をやり直すと、ベースブランチを取り込んで解消する。
- マージの順序の守らせ方は、次から選んだ。
  - PR の向き先を依存先のブランチにする（採用）：GitHub の差分が子の変更だけになり、レビューしやすい。ただし、それだけでは子を先にマージすると、子の変更が依存先の PR に入ってしまう。
  - ドラフトのままにする（採用）：GitHub はドラフトの PR をマージさせないので、うっかり先にマージするのを防げる。レビュー・コメントはドラフトのままでもできる。人がドラフトを外せばマージできるので、人の判断を止めすぎない。
  - 本文に書くだけ：守らせる力が無い。
  - sacty がマージを検知して拒む・止める：マージは取り消せないので、検知してからでは守らせられない。人の操作を後から否定することにもなる。
  - 依存先がマージされるまで子の PR を作らない：子をレビューできず、待ちが減らない。
- 依存先の中止で子を止めるだけにし、ベースブランチから作り直さないのは、作業領域を起点から作り直す仕組み（実装のやり直しを捨てる）が無く、人が子を中止して統合レビューの修正の子タスクに任せるほうが、今の仕組みで扱えるため。
- 依存先が複数あるときに、ほかの依存先の変更が入っていると確かめられるときだけ重ねるのは、重ねた先の合格したコミットに無い依存先の変更が、子の作業領域に入らないまま進むのを防ぐため（重ねている間は、ベースブランチではなく重ねた先だけを取り込む）。確かめられなければ待つ（安全側）。
- 重ねた PR をドラフトにできないときに止めるのは、ドラフトでない重ねた PR を承認待ちにすると、マージの順序を守らせる仕組みが本文だけになるため。
- 依存先が複数あるときに連なりだけを重ねるのは、別々の依存先の変更を1つのブランチにまとめる起点（複数の PR をマージしたコミット）を sacty が作ると、どの PR にも対応しないブランチを向き先にすることになるため。

## 影響

- 依存の無い子タスク・分割しないタスクの振る舞いは変わらない（PR の向き先の記録・付け替えは、重ねた子タスクの PR だけ）。
- 依存先の PR がマージ済みでマージの後の監視の途中の子タスクも、片付くのを待たずに始まる（その依存先が、ほかの PR に重ねていないとき）。
- ドラフトの PR を使えないリポジトリでは、重ねた子タスクは PR を出せずに止まる（依存先の PR がマージされた後に再開すると、ドラフトにせずに進む）。
- 重ねた子タスクの承認待ちの PR は、依存先がマージされるまでドラフトのまま。
