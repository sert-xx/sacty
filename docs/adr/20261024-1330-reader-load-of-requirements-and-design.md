# 要求要件・設計の冒頭に人間が判断することを分けて置き、書く量を変更に比例させ、セルフレビューに書きすぎの観点を足す

## 背景

要求要件・設計が、変更の規模に比べて長くなることが多かった。
人間が見落としていたことを補う価値はあるが、量が多いと、承認する人の認知の負荷が高くなる。

原因は、指示とスキルが記述を足す方向にだけ働いていたことにある。

- 設計の指示が、どのタスクでも構成・データ・処理の流れ・エラー時の振る舞い・影響範囲を書かせていた。テスト観点には、必ず異常系と境界値を含めさせていた。
- EARS の指示とスキルが、正常系の要求ごとに異常系を足させていた。
- セルフレビュー（`design-doc`）の必須の観点は、欠落を探すもの（D-3 完全性など）だけで、書きすぎを指摘する観点が無かった。D-3 は、要件の無い非機能にも「対象外」と書くことを求めていた。`must` も `should` も直させ、最大 5 回まわしていた。
- 確認したいことには、件数の上限も優先度も無かった。

## 決定

- 要求要件・設計の最初に「確認したいこと」と「既定で決めたこと」の2つの節を置かせる。
  - 確認したいことは、重要な順に最大 5 件にし、1件ごとに推奨の答えと理由を添えさせる。上限を超えた分は、推奨の答えで決めて「既定で決めたこと」に回させる。
  - 人間がこの2つの節を読めば承認するかを決められるようにし、詳細はそのあとに置かせる。
- 詳細には、依頼と今回の変更に要ることだけを書かせる。既存の仕組みが保証していて変わらない振る舞い、今回の変更で起こりえない異常系・非機能、当てはまらない観点の「対象外」、依頼に無い機能、重複は書かせない。設計の節とテスト観点の異常系・境界値も、今回の変更に関係するものに絞らせる。
- EARS の異常系は、今回の変更で新しく起こりうるものだけを書かせる（指示とスキル `ears-requirements`）。
- 既定のスキル `review-dispatch` の `design-doc` の必須の観点に、D-10（簡潔さ・範囲）を足す。D-3 は、今回の変更で起こりうる欠落だけを見るようにし、関係しない観点に「対象外」を求めない。
- 自己レビューの `design-doc` では、記述を足す `should` を作者の判断で直すものにし、D-10 の `should` は直させる。

## 理由

- 補足を消すのではなく、人間が判断することと参考の詳細を分けて並べれば、補足の価値を残したまま、読む量を減らせる。推奨の答えがあれば、人間は同意するだけで済むことが多い。
- 欠落を探す観点しか無いと、自己レビューを回すほど文書が長くなる。書きすぎを探す観点を必須にし、足す指摘と削る指摘の扱いに差を付けて、長くなる方向の圧力を打ち消す。
- 2つの節を sacty が読み取って画面に別に出す案もあったが、成果物の本文の形を変えるだけで効果が出るので、まずは指示とスキルで行う。読み取って出すのは、効果を見てから決める。
- 変更の規模（小・中・大）をオーケストレーターから工程に渡して分量の目安にする案は、データの流れの変更を伴うので、この決定には含めない。

## 影響

- 要求要件・設計の成果物の最初に、2つの節が並ぶ。人間は、異論のある項目だけを指摘して差し戻す。
- 異常系・非機能の記述が減るので、要る記述まで省かれたときは、人間が指摘で足させる。
- プロジェクトのコンテキストで `review-dispatch` を差し替えているときは、D-10 は足されない（指示の側の決まりは効く）。
