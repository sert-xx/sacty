# 要求要件・設計の本文から作業のメモを締め出し、依頼者に不利益な既定を「確認したいこと」に出させ、最初の提出では ID を欠番なく振らせる

- 日時: 2026-11-01 13:50 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-263
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験で、要求要件・設計は、おおむね読みやすかったが、次のことが起きた。

- S13：要求要件の末尾の区切り線の後ろに、人の指摘（main の取り込み）への対応の報告が、本文として残った。要求要件の出力の全体が、そのまま承認の画面と PR のファイルになるため。
- S9：依頼者に不利益な既定（利用停止は戻すときに判定し直さない）を、「既定で決めたこと」に置き、「確認したいこと」に出さなかった。
- S8：依頼者が一番決めたいこと（どこまで速くするか）が should に埋もれ、推奨が依頼者の意図と逆を向いていた。
- S6・S8：要求要件の ID に欠番（R-5）や、別タスクの要求要件への参照だけの項目があった。

どれも、人が承認の判断をする文書に、判断の邪魔になるものが残った、または判断すべきことが埋もれた例。

## 決定

- 要求要件・設計の指示に、本文に書くものを決める（`deliverableBodyLines`）。
  - 作業の経過・指摘への対応の報告・エージェント向けのメモ・タスクの ID は、区切り線の後ろを含め、本文のどこにも書かせない。指摘への対応は、`sacty-responses` の JSON に書かせる。
  - ID は、最初の提出では 1 から欠番なく振らせる。差し戻しで項目を消したときは、ID を詰めず、「R-5（削除：理由）」のように行を残して、欠番の理由が分かるようにさせる。
  - 別の文書を参照する項目には、参照先の中身を1行で併記させる。
  - 提出の前に、本文を読み直して確かめさせる。
- 「確認したいこと」と「既定で決めたこと」の置き方を直す（`readerLoadLines`）。
  - 依頼の目的に関わる判断は must に置く。確認したいことは、依頼者が一番決めたいことから並べ、推奨の答えは依頼の意図に沿う向きにする。
  - 依頼者に不利益が出うる既定（元に戻せない・失われる・使えなくなる・手間や費用が増える・依頼の意図と逆に働く）と、依頼の目的に関わる判断は、「既定で決めたこと」に置かず「確認したいこと」に出す。should の上限を超えるときも、これらは既定に回さない。
- 検出と修正は、提出の前のセルフレビューで行わせる。
  - D-6 に、本文に残った作業の経過・指摘への対応の報告・エージェント向けのメモ、理由の分からない ID の欠番、参照だけの項目を足す。D-10 に、目的に関わる判断・不利益な既定が既定に紛れていないか、確認したいことの並びを足す。メモ・参照だけの項目・紛れ込みは `must`、理由の分からない欠番は `should` とし、記述を足す指摘でも直させる。
  - 既定のスキルはあらゆるリポジトリの文書のレビューにも使われるので、足した観点は、要求要件・設計など人が承認する成果物（D-10 は「確認したいこと」「既定で決めたこと」の節がある文書）に限る。ID を持たない文書や、経緯を書く節がある文書（ADR・CHANGELOG など）には当てはめない。
- 既定のスキル `ears-requirements` の「ID は直しても付け直さない。消した要求の ID は使い回さない」は変えない。「最初の提出では 1 から欠番なく振る」と、「差し戻しで消した要求は、行を残して欠番の理由が分かるようにする」を足す。

## 理由

- 本文に残ったものは、承認する人が読む文書の邪魔になり、承認の判断を誤らせる。判断すべきことは、冒頭の「確認したいこと」に出ていれば、詳細を読まずに決められる。
- ID を詰めて振り直すと、人の指摘・承認済みの設計のテスト観点（TV が R を指す）・PR のコメントが指す ID がずれ、承認済みの文書と食い違う。返信に新しい ID を書かせても追い切れない。そこで ID の固定（直しても付け直さない）は守り、欠番は、最初の提出（まだ誰も ID で指していない）では出さず、差し戻しで消したときは「R-5（削除：理由）」の行で理由を示す。読む人が引っかかるのは、理由の分からない欠番なので、それを探す。
- 検出を sacty のコードで機械的に行わない。区切り線の後ろの文章は、正当な区切りと見分けにくく、誤検出で工程を止める損失が大きい。ID の欠番は検出しやすいが、検出した後に直させるには、エージェントの再実行（費用）が要り、仕組みを足す範囲になる（範囲外：予算・差し戻しの仕組み）。既に提出の前に動くセルフレビューに観点を足す方が、既存の流れで直せる。
- 本文を読み直させる指示と、セルフレビューの観点の両方に書くのは、書く側の読み直しだけでは、書いた本人の見落としが残るため。セルフレビューは、別の担当が文書を読む。

## 影響

- 要求要件・設計の本文に作業のメモが残りにくくなる。ただし LLM の遵守に頼るので、残ることはありうる。残ったときは、人が差し戻しの指摘で消させる。
- 差し戻しで消した要求の行が、文書に残る。欠番の理由が分かる代わりに、削除の行が1行ずつ増える。
- 目的に関わる判断が must に置かれるので、「確認したいこと」の must が増えうる。
