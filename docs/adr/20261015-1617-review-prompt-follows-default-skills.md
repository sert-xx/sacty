# PR のレビューのタスクは既定のスキルでレビューし、出力の形と投稿は sacty が決める。判定を3つにする

- 日時: 2026-10-15 16:17 UTC
- ステータス: 採用
- 関係する PR・タスク: #121、PBI-111
- 置き換え元: [sacty が作る PR に取り込むラベルを付け、別のタスクのレビューを元のタスクの PR の指摘として取り込む](20261014-1445-superseded-label-sacty-pull-requests-for-review.md)
- 置き換え先: なし

## 背景

PR のレビューだけのタスク（工程 `review`）のプロンプトと、既定のスキル（`git`・`review-dispatch`）の前提が食い違っていた。

- プロンプトは、エージェントに本文と JSON（行へのコメント・評価）を書かせ、sacty が 1 件の `COMMENT` のレビューとして投稿する。
  スキルにも、どちらを優先するかにも触れていなかった。
- スキルは、エージェントが自分で `gh api` で投稿する前提だった。
  行へのコメントの JSON を貼らない、位置の無い指摘は人に確かめる、総評に `@login` を入れる、投稿の直前に先頭のコミットを確かめる、と書いていた。
- 評価は真偽値（`changesRequested`）で、行へのコメントが1件でもあると `true` になった。
  提案だけのレビューでも、元のタスクに差し戻しとして届きえた。

エージェントがスキルに従って自分で投稿すると、sacty の投稿と二重になりうる。
目印による重複の確認は sacty の投稿どうしにしか効かない。
JSON を出さない、人に確かめて止まる、というおそれもあった。

## 決定

- 投稿は今のまま sacty がする。プロンプトとスキルを、それに合わせる。
  - プロンプトに、既定のスキル `review-dispatch`（流れは `pr-review`）と `writing` を使うこと、自分では投稿しないこと、
    スキルと食い違えばプロンプトの出力の形を優先することを書く。
  - 既定のスキル（`git`・`review-dispatch`）に、依頼した側が出力の形と投稿のしかたを決めていればそれに従い、自分では投稿しないことを書く。
    自分で投稿する手順は、自分で投稿するように頼まれたときだけ使う。sacty に限った書き方はしない。
  - 位置を付けられない指摘で人に確かめるのは、確かめる相手（対話で依頼した人）がいるときだけにする。
    いなければ止まらずに総評に書く。sacty のタスクでは本文に書かせる。
- スキルの決まりを、sacty の投稿に取り入れる。
  - 指摘の頭は `[要修正]`・`[提案]`。行へのコメントは重さ（`severity`）を書かせ、sacty が頭を付ける。
  - 判定を3つ（`changes_required`・`suggestions`・`no_findings`）にする（`reviewChangesRequested` は `reviewVerdict` に置き換える）。
    `[要修正]` の行へのコメントがあれば修正が必要にする。行へのコメントがあるだけでは修正が必要にしない。
    元のタスクに届けるのは、修正が必要な回と判定を読めない回だけ（PBI-88 の決定のうち、評価の部分を置き換える）。
  - 総評の先頭に、sacty が PR の作者の `@login` と判定を書く。AI による投稿である旨は、今の固定の文だけにする。
- 再レビューでは、前回の sacty のレビュー（本文・行へのコメント）と、その投稿の後の PR の作者の返答を、データとしてプロンプトに渡す。
  前回の指摘ごとに、対応を確かめたか・未対応かを書かせる。
- 投稿の直前に PR の先頭を確かめる。途中で push されていたら、レビューしたコミットに対して投稿し、その旨を本文に書く。
  最新のコミットは、人が「再レビュー」でレビューする。
- 言語：sacty が付ける見出し・判定・注記・固定の文と、指摘の頭は日本語で固定する。
  エージェントの本文と指摘の文は、リポジトリの文章の決まり（`writing` の順）に従わせ、決まりが無ければ日本語にする。

## 理由

- 投稿を sacty に残すのは、目印による二重の投稿の防止・行へのコメントを受け付けられないときの投稿し直し・投稿の記録を、sacty が持っているため（ステークホルダーと合意）。
- 依頼した側に従う決まりをスキルに書くのは、スキルが sacty の外（人が対話でレビューを頼む）でも使われ、そこでは自分で投稿する手順が要るため。
  どちらの使い方でも、投稿する人が1人に決まる。
- 判定を3つにするのは、提案だけのレビューを差し戻すと、毎回むだなやり直しの費用がかかるため。
  `[要修正]` の行へのコメントで判定を引き上げるのは、エージェントの判定が軽すぎて、直すべき指摘が元のタスクに届かないのを防ぐため。
- `@login` と判定を sacty が書くのは、PR の作者の login を sacty が API で確かに読め、判定の文を言い回しで揺らさないため。
- 途中で push されたときに最新でやり直さないのは、やり直しの費用がかかり、push が続くと投稿できないため。
  レビューしたコミットに対して投稿すれば、行へのコメントの位置もずれない。
- 頭と固定の文を日本語にするのは、sacty が頭を読んで判定に使い、固定の文を今の日本語の投稿とそろえるため。
  ほかの言語の固定の文は、要る人がいれば後で足す（今は決めていない）。

## 影響

- 前の版で記録した判定（`reviewChangesRequested`）は読まない。その回は判定を読めない回として、元のタスクに届く（本番ではまだ使っていない）。
- 英語のリポジトリでも、頭（`[要修正]`・`[提案]`）と sacty の固定の文は日本語になる。
- 投稿の直前に PR を読む API の呼び出しが1回増える。読めなければ、投稿せずに一時停止する。
