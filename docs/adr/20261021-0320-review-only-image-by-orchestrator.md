## 背景

PR のレビューだけのタスクは、工程の選択の費用をかけないために、オーケストレーターを使わずに工程をレビューだけにしていた。
イメージは、プロジェクトの対象か再実行で指定したものだけを使い、指定が無ければ既定のイメージで動いていた。

その後、レビューの親が対象のプロジェクトの検証コマンド（テスト・lint など）を実行するようになった
（[レビューの検証を親が共有し、結果の分析を独立した観点にする](20261015-0428-review-verification-results.md)）。
既定のイメージはオーケストレーター用の最低限のもの（Node.js・git・Claude Code・Codex）で、ほかの言語のツールやテストのブラウザが入っていない。
そのため、イメージを指定していないプロジェクトでは、Java・Go・Python などのリポジトリの PR のレビューで検証を実行できなかった。
既定のイメージで動いたことも、作業履歴に記録されていなかった。

## 決定

- PR のレビューだけのタスクで、`images` を設定していて、プロジェクトの対象・再実行でイメージを決めていないときは、
  オーケストレーターに、レビューの工程のイメージだけを選ばせる。工程はこれまでどおりレビューだけに決め、選び直させない。
- 指示では、PR が触るコードの言語・版と検証に要るもの（ブラウザのテスト・DB のクライアントなど）から `images` を選ばせる。
  既定のイメージは最後の手段とし、選ぶときは合わない理由を書かせる（工程のイメージの選び方と同じ）。
- 既定のイメージを選んだら、理由を `StepsChosen` の `defaultImageReasons` に、理由が無ければ `imagesUnexplained` に記録する。
- 選んだときの `StepsChosen` はオーケストレーターの記録にし、選んだ実行の費用を記録する。答えを読めない・`images` に無い名前なら、
  `OrchestratorFailed` を記録して止める（代わりのエージェントがあれば、それで選び直す）。
- `images` を設定していない・イメージを決めているときは、これまでどおりオーケストレーターを使わない（費用は 0）。

## 理由

- 検証コマンドを実行するレビューでは、イメージが合わないとレビューの質が落ちる。工程の選択と同じ方法でイメージを選ばせれば、
  既にある指示・答えの検査・既定のイメージの理由の記録をそのまま使える。
- 比べた案：
  - リポジトリのファイル（`go.mod`・`pom.xml` など）から、AI を使わずに決める。`images` には名前と説明しか無く、決まった規則では
    選びにくいので採らなかった。
  - プロジェクトの対象でイメージを指定してもらう運用で回避する。直す量は少ないが、指定を忘れたプロジェクトで同じことが起こるので
    採らなかった。
- 工程の選択（費用の大きい工程の組み合わせの判断）は今までどおりさせないので、費用はイメージを選ぶ1回の実行の分だけ増える。

## 影響

- `images` があり、イメージを決めていないプロジェクトの PR のレビューは、オーケストレーターの実行の分だけ費用と時間がかかる。
- `StepsChosen` の項目は増えない。理由の文は、イメージを選んだときに別の文（`review.reviewOnlyImageChosen`）にする。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の「オーケストレーター」、利用者向けは [取り込み](../user/intake.md) と
  [コンテナイメージ](../user/images.md) に書く。
