# 同時に保存したプロジェクトの設定は、互いの変更を併合し、併合できないときだけ拒否する

- 日時: 2026-11-03 22:50 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-301
- 置き換え元: [プロジェクトの設定の保存は、読み込んだ版を照合し、変わっていれば上書きせずに知らせる](20261101-1347-superseded-project-save-version-check.md)（「4. 併合：しない」の部分）
- 置き換え先: なし

## 背景

PBI-274 で、プロジェクトの設定の保存に版の照合を入れ、読み込んだ後にほかの保存があれば拒否するようにした。
その後の実証実験（5人の担当が SactyTest の対象を足す場面）で、最初の保存は拒否され、読み直して足し直して保存できたのに、保存の後の読み直しで自分の追加が消えていた。
消えた原因は、実験の記録からは特定できていない（未確認）。コードの上では、版の照合と保存は同じ同期の処理で行われ、画面も読み直すと内容と版を取り直すので、サーバーと画面のどちらかの実装の誤りは見つかっていない。
拒否と読み直しに頼る流れは、重なるたびに全員が読み直して足し直すことになり、読み直した内容と版の組が食い違う場面（複数の画面・手動の呼び出しなど）があれば、同じ消失が起きうる。

## 決定

読み込んだ後にほかの保存があっても、互いの変更が重ならなければ、拒否せずに併合して保存する。併合できないときだけ、これまでどおり 409 で拒否する。

1. **元の定義を残す**：保存のたびに、版（`updatedAt`）ごとの定義をプロジェクトごとに新しい 50 版まで残す（`project_revisions`）。
2. **3つの定義で併合する**：読み込んだ版の定義（元）・今の定義・保存しようとする定義。
   - 対象（`targets`）は1件ずつ。どちらかが足した対象、どちらかが消した対象、一方だけが変えた対象は残す。同じ対象を両方が違うように変えた・一方が消して一方が変えたときは併合できない。順序は今の定義のままで、足した対象は後ろに付ける。
   - ほかの項目（名前・コンテキスト・チケット・共用の compose・GitHub のアカウント）は項目ごとに、一方だけが変えたならその変更を採る。両方が違うように変えたら併合できない。
3. **併合した結果も、通常の保存と同じ検査に通す**（項目の形・対象の重複）。検査に通らなければ保存しない。
4. **併合できない・元の版が残っていない**ときは、設定も版も変えずに 409（`project.changedElsewhere`）。
5. **画面**：併合して保存したときは、画面がほかの保存の変更を見ていないので、版に進めず、併合したことと再読み込みのボタンを出し、再読み込みするまで保存を止める。古い基準の版のまま続けて保存すると、元の版との差で併合し直されるため、自分が直前に足した対象を消すなどの変更が取り消せず（元の版には無いので残る）、成功と表示されて変更が反映されないため。
6. `PUT` の `If-Match` は必須のまま（無ければ 428）。作成・インポートは版を要らない。

## 理由

- 読み直して足し直す流れは、重なるたびに全員が待たされ、読み直した画面と版の組が食い違えば、同じ消失が起きる。サーバーが元の定義と照らして併合すれば、画面の状態によらず、互いの追加は消えない。
- PBI-274 は、項目ごとの併合を「互いに関係する項目（重複の検査・コンテキストの合成）を、誰も見ていない組み合わせで保存しうる」ので採らなかった。今回は、併合を、重ならない変更（別々の対象の追加・削除、別々の項目の変更）に限り、同じ対象・同じ項目を両方が違うように変えたときは拒否する。併合した結果も重複などの検査に通し、併合したことを画面に知らせて再読み込みを促す。見ていない組み合わせが保存されうる点は残るが、それは、拒否のたびに全員が足し直す形が実際に変更を消したことと比べて、小さいと判断した。
- 元の定義を版ごとに残すのは、3つの定義での併合に要るため。50 版は、同時に設定を開いている人数が多くても足りる余裕として決めた（根拠のある数ではない）。古くなって消えた版からの保存は、併合せずに拒否する。
- 検討したほかの案：対象の和集合だけを取る（古い画面の保存が、消した対象を復活させるので採らない）。保存を直列にして画面で確かめ直す（画面を経由しない呼び出しで防げないので採らない）。

## 影響

- 古い画面で保存しても、重ならない変更なら保存される。画面は最新ではないので、再読み込みを案内する。
- 同じ対象・同じ項目を違うように変えたとき、元の版が 50 版より古いときは、これまでどおり拒否する。
- 保存先に `project_revisions` の表が増える（デーモンが起動するときに作る。古い保存には元の定義が無いので、その版からの保存は併合できず拒否する）。
- sacty の設定（`PUT /api/settings`）・スケジュールタスク（`PUT /api/schedules/:id`）には入れていない。同じ型の上書きは、これらに残る。
- 仕様は [アーキテクチャ](../spec/architecture.md)。使い方は [同時に変更したとき](../user/project-settings.md#同時に変更したとき)。
