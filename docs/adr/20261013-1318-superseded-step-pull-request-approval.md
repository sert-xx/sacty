# Git 管理のリポジトリでは、要求要件・設計を工程ごとにタスクブランチへの PR にし、そのマージを人の承認とする

- 日時: 2026-10-13 13:18 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: #67、PBI-57
- 置き換え元: なし
- 置き換え先: [人が PR の中で直してからマージしても承認・完了として進め、sacty の成果と人が直した最終の成果の両方を記録する](20261013-1425-accept-human-edited-merge.md)（提出と違う内容のマージを承認にせず判断を待つ部分）

## 背景

要求要件・設計の成果は sacty の画面で承認していた。#20 で、成果物チェック（実装の PR）は PR のマージで承認するようにしていた。
要求要件・設計の承認を、Git 管理のリポジトリでどう行うかを決める必要があった。

## 決定

- 人の承認が要る工程ごとに PR を作り、承認＝マージにする。
  1. ベースブランチの起点のコミットから、タスクブランチ（`sacty/task-<短いID>`）を作る。
  2. 要求要件のブランチから、要求要件の PR をタスクブランチへ出す。
  3. マージされたら、設計の PR をタスクブランチへ出す。
  4. マージされたら、タスクブランチの最新に実装を積み、実装の PR をベースブランチへ出す（CI が動くように）。
- 成果のファイルは、既定で `docs/sacty/<短いID>/requirements.md`・`design.md`（設計にはテスト観点も入れる）。規約に置き場所が
  あれば、オーケストレーターが決める（形が正しいものだけ使う）。
- PR のマージを人の承認として記録して次へ進む（PBI-56 の書き出しはこの後に動く）。PR を作った工程は、画面から承認しない
  （PR の URL を示す）。マージされずに閉じられた・sacty の提出と違う内容でマージされたときは、承認にせず人の判断を待つ。
- 工程の PR のレビュー・行へのコメント・通常のコメントを取り込み、ゴールガーディアンが判断する（人の確認なし。PBI-58 と同じ）。
  - その工程のやり直し：同じ PR を更新する（PR のブランチの最新に積み、強制プッシュしない）。
  - 前の工程：直しの PR をタスクブランチに新しく作り、マージされたら後ろの PR を作り直す（開いていた古い PR は閉じる。マージ済みの PR は戻さない）。
  - 判断できない：その工程をやり直す。差し戻しの回数の上限のエスカレーションは残す。
- 中止したら、開いている PR をすべて閉じ（マージ済み・閉じたものは触らない）、タスクブランチと工程のブランチを消す。
- 調査だけ・レビューだけ・不具合の修正など、要求要件・設計の無いタスクでは、タスクブランチも PR も作らない。タスクブランチを作る前に
  PR を作れなくなったら、画面での承認に切り替える。
- イベント `TaskBranchCreated`・`StepBranchPushed`・`StepPullRequestPublished` を足し、`TaskBranchCreated` のあるタスクだけを新しい流れに
  する（過去の作業履歴は、これまでどおり画面で承認する）。

## 理由

- 実装の PR をベースブランチへ出すのは、CI が動くようにするため（PR の本文）。
- 人が提案のコミットを積んでいても強制プッシュしないため、PR のブランチの最新に積む（PR の本文）。
- 工程ごとに PR で承認する方針そのものの理由と、比べたほかの案は記録に無い。

## 影響

- 要求要件・設計の承認は GitHub の PR の上で行う。画面からは承認できない。
- 実装の作業領域は起点のコミットのまま。実装の工程からの設計の変更の申し出をゴールガーディアンが認めても、リポジトリの
  `design.md` は更新しない。
- 実際の GitHub での動作（タスクブランチへの PR・ブランチの削除）は、この時点では確かめていない。
