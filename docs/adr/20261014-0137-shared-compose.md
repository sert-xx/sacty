# プロジェクト共用の docker compose を設定に書けるようにし、オーケストレーターが要ると判断したタスクだけで実行ごとに取得・起動する

- 日時: 2026-10-14 01:37 UTC
- ステータス: 採用
- 関係する PR・タスク: #78、PBI-70
- 置き換え元: なし
- 置き換え先: なし

## 背景

テストに要る Cassandra・Redis などの compose ファイルが、対象のリポジトリではなく、チームで共用する別のリポジトリにあることがある。
これまでは対象のリポジトリの compose だけを起動していた（PBI-47・PBI-60 の仕組み）。

## 決定

- プロジェクトの設定（画面・エクスポート）に「共用の compose」（名前・リポジトリ・ブランチかタグ・compose ファイル・説明）を足す。複数持てる。
- 設定しただけでは取得も起動もしない。オーケストレーターに名前・ファイル・説明を渡し、タスクごとに使うかを判断させ、使う・使わない理由
  （`servicesReason`）を必ず書かせる。選んだ共用の compose（名前・リポジトリ・ref・ファイル）・理由・取得したコミットを作業履歴に残し、画面に出す。
  設定に無い名前を選んだら、イメージ（PBI-41）と同じく理由を示してオーケストレーターの失敗として止める。
- 取得：リポジトリごとのキャッシュ（`$SACTY_HOME/cache/shared-compose`）を実行のたびに ref の最新へ更新し、そのコミットの中身を実行ごとのディレクトリ
  （`workspaces/_shared-compose/<runId>`）に書き出す。同じリポジトリのキャッシュの更新と書き出しは、デーモンの中で直列化する。終わったら消す。
- 起動・安全の確かめ・localhost の転送は PBI-47・PBI-60 と同じ仕組みを使う（取得したディレクトリを作業領域として扱い、マウントはその中だけ）。
- `container_name` はこれまでどおり外すが、共用の compose では、外した名前を sacty のネットワークの別名（aliases）にする（サービス名と同じ・ほかの
  サービスの名前・名前の形でないものは別名にしない）。対象リポジトリの compose は、これまでどおり外すだけ。
- healthcheck は既存の `docker compose up --wait --wait-timeout 300` で待つ。遅いサービスは、共用の compose に healthcheck を書く前提。
- リポジトリは git の URL（https・ssh・`git@host:path`）かローカルの絶対パスだけ。相対パスと、URL のユーザー名・パスワード・トークンは拒否する。
  private のリポジトリは、コンテキストリポジトリと同じ `gitAuth`（HTTPS の GitHub はプロジェクトの gh のアカウント、環境変数でだけ渡す）で取得する。
  取得・起動の失敗の出力は、認証の値を伏せてから切り詰める。
- 取得・起動の待ちの間に一時停止・中止されたら、起動を見送る・打ち切る（取得したディレクトリを片付け、起動したものを止めて消す）。

## 理由

- 別名にするのは、テストの設定が固定の名前で接続していても届くようにするため。別名はプロジェクトごとのネットワークの中だけなので、ほかのタスクと
  ぶつからない（PR の本文）。`container_name` を外すのは、並行して起動するとぶつかるため。
- 取得を直列化し実行ごとに書き出すのは、並行するタスクが、ほかのタスクがマウントしている初期化スクリプトを書き換えないため（PR の本文）。
- 相対パスを拒否するのは、デーモンのカレントディレクトリ次第で取得先が変わるため。URL の認証の値を拒否するのは、画面・作業履歴に出るため（PR の本文）。
- 取得・起動の後にも一時停止・中止を確かめるのは、取得の待ちの間に止めても取得の後にサービスを起動し、`up --wait` の待ち（最大300秒）まで停止が
  遅れるというレビューの指摘への対応。

## 影響

- 共用の compose を設定していないプロジェクトの動作は変わらない。作業履歴の「工程を決定」に、選んだサービスと理由が出るようになる（表示が増えるだけ）。
- 共用の compose を使うタスクでは、実行のたびにリポジトリの取得が入る。
- 取得そのもの（git fetch）は打ち切らず、終わってから起動を見送る。
- private のリポジトリの実際の認証は、この PR の時点では確かめていない。
