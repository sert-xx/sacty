# 工程が終わるごとにオーケストレーターが要らない工程を飛ばし、要求要件・設計を省く組み合わせ direct を足す

- 日時: 2026-10-21 12:07 UTC
- ステータス: 採用
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: なし

## 背景

オーケストレーターは、タスクの開始時に1回だけ工程の組み合わせを選び、その後は選んだ工程をすべて実行していた（飛ばすのは、
スキルが無いときのマージの後の監視だけ）。実装する組み合わせはどれも要求要件か再現を含み、要求要件を書かない実装の組み合わせは無かった。

工程を選ぶ時点では、まだ前段の調査をしていない。たとえば「`/restricted` へのリンクをサイドメニューに足し、管理者だけに出す」という
依頼では、調査の前には「管理者の定義・管理の仕方・管理画面・ほかの役割ごとの表示」などが要りそうに見え、要求要件・設計を含む組み合わせを
選びやすい。ところが調査すると、既に `isAdmin` のような判定があり、それでリンクの表示を切り替えるだけの作業だとわかることがある。
それでも工程は変えられず、要らない文書・テスト観点を作り、人の承認を待ち、費用と時間をかけていた。

## 決定

- 工程の見直しを足す。工程が終わるごとに（前段の調査の完了・承認など）、まだの工程に飛ばせる工程が残っていれば、次の工程を実行する前に、
  オーケストレーターに終わった工程の成果を読ませ、要らない工程を飛ばさせる（`StepsSkipped`）。
  - 飛ばせるのは、要求要件・設計・再現（`SKIPPABLE_STEPS`）だけで、組み合わせに実装があるときだけ。工程を足す・並べ替えることはさせない。
  - 見直しは、工程を選んだオーケストレーターのセッションを再開して行う。
  - 実行できない・答えを読めないときは、止めずに飛ばさないで進める（見直しは成果物を作らない補助の判断なので、止めるほうが損が大きい）。
- 組み合わせ `direct`（調査 → 実装 → マージの後の監視）を足す。依頼が受け入れ条件として明確で、既存の仕組みを使う局所的な変更に使う。
- 要求要件・設計を経ない実装は、タスクの内容と前段の調査の結果に従い、観点 `REQ` をタスクの目的（依頼の内容）として、テストと
  ゴールガーディアンの最終レビューで確かめる。

## 理由

- 最終的な成果は、ゴールガーディアンの最終レビューと、人間の PR のマージで判断される。オーケストレーターの役割は、タスクを適切に流す
  ことなので、調査で分かったことに合わせて工程を減らしてよい。
- 工程を選ぶ時点の情報（タスクの内容とコードの一読）だけでは判断しきれないことがある。開始時の選択だけを賢くするより、調査の結果を
  読んだ後に見直すほうが確かに判断できる。
- 比べた案：
  - 開始時の選択だけで、`direct` を足す。要求要件が明確なタスクには効くが、調査してはじめて単純とわかるタスクには効かないので、
    見直しと両方を入れた。
  - 見直しで工程を足す・並べ替えることも許す。組み合わせの前提（タスク分割の前の設計など）が崩れ、投影と画面の扱いが複雑になる。
    足りない工程は、ゴールガーディアンの最終レビュー・人間の差し戻しで補えるので、飛ばすことだけにした。
  - 調査の工程のエージェントに、後の工程が要るかを答えさせる。調査の指示と成果が工程の選択の判断と混ざり、工程を選ぶ役割が分かれるので、
    工程を選んだオーケストレーターに任せた。
- 見直しの実行の費用はかかるが、オーケストレーターのセッションを再開するので小さく、飛ばせれば工程の実行と人の承認の分を省ける。
  飛ばせる工程が残っていないとき（`direct`・設計の承認の後など）は見直さない。

## 影響

- 要求要件・設計・再現を含む組み合わせでは、工程が終わるごとにオーケストレーターの実行が1回増えうる（飛ばせる工程が残るときだけ）。
- 要求要件を経ない実装は、人間が承認した受け入れ条件が無いまま進む。依頼の解釈の違いは、PR のレビューで直す。
- 飛ばした工程には差し戻せない。要る工程を飛ばしていたら、人間は実装を差し戻すか、タスクを作り直す。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の「工程の見直し」と「進め方の組み合わせ」、費用は [作業履歴](../spec/event-log.md) の「費用」、
  利用者向けは [タスクを進める](../user/tasks.md) に書く。
