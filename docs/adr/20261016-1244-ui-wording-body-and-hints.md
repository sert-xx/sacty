# 画面の文言を本文と補足に分け、仕組みの説明はツールチップで出す

- 日時: 2026-10-16 12:44 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-117
- 置き換え元: なし
- 置き換え先: なし

## 背景

画面の文章が説明口調で読みづらいという指摘があった（ステークホルダー、2026-10-16）。辞書（`apps/web/src/i18n/messages/`、日英で約
2,900 行）を読むと、読みづらさは次の型に分けられた。

- カードの見出しの脇の note が、仕組みを説明している（「タスクごとに使い回す（正本は作業履歴）。質問には複製して答える」など）。
- 設定の節ごとに、3〜5 行の説明の段落が常に出ている。
- 人の判断を求める場面で、仕組みの全部を毎回説明している（実装の承認の案内は約 230 字）。
- 括弧書きの注釈・言い訳が本文に混ざる（「（人間の承認なし）」「（理由の記載なし）」）。
- 内部の役割（オーケストレーター・ゴールガーディアン）が主語の説明文が多い。
- 設定ファイルの項目名（`config.yaml` の `gateway.platforms` など）が本文に出る。
- 読み込み中の文やボタンにまで補足の括弧が付く。

英語の文言も日本語を訳した同じ構造なので、同じ問題があった。

## 決定

- 画面の文言を、本文（常に見える文）と補足（ツールチップ）に分けて持つ。本文は「いま何が起きているか」と「次に何をするか」だけにし、
  仕組み・理由・数値・設定ファイルの場所・用語の定義は補足に移すか消す。取り消せない操作・費用・他人に見える操作の注意、エラー、
  判断に要る案内は本文に残す。
- 補足は、見出し・ラベル・値の横の小さな印（i のアイコン）に、マウスを乗せる・キーボードで止まる・タップすると出す。Esc と外側の
  クリックで閉じる。補足の文は閉じていても DOM に置き、印の `aria-describedby` で結び付ける。補足が無ければ印を出さない。
- 規則を仕様書（[画面の文言と補足](../spec/ui-wording.md)）に書き、辞書の文字列の葉をテストで機械的に確かめる（本文の改行・長さ・
  括弧書き、補足の長さ。例外は理由つきの一覧）。
- 作業履歴の 1 行は「何をした・何が起きた」だけにし、結果の矢印（「→ 人間の判断待ち」）と言い訳の括弧を付けない。古い作業履歴に
  文のまま記録されたものは、そのまま出す。
- デーモンが作って画面に出す文（core の辞書）は変えない。エラーと失敗の理由であり、CLI・Slack の通知と共有するため。

## 理由

- 画面を開いたときに、いまの状態と次にすることだけが目に入り、仕組みは知りたいときだけ読めるようにするため。説明を読み飛ばす手間を
  なくし、判断を速くする。
- ツールチップを Popover（ホバーでも開く）で作ったのは、Tooltip の部品がタッチで開かないため。タップとキーボードでも同じ文に
  届くようにした。
- 規則をテストで確かめるのは、文言を足すたびに説明口調へ戻るのを防ぐため。関数の文言は呼び出さないと文にならないので、テストの
  対象にせずレビューで見る。
- 分割せずに 1 本で行ったのは、画面ごとに調子がばらつかないようにするため（ステークホルダー）。

## 影響

- 画面の文言の多くが変わる。文言を固定していたテストを直した。
- ユーザードキュメントで画面の文言を引用している所（テストのコマンドの欄、前の提出の見出し、更新が止まっているときの表示）を直した。
- 画面の文言を足す・変えるときは、仕様書の規則に従い、補足は `hint`・`*Hint` のキーに書く。規則から外れると `wording-policy.test.ts`
  が落ちる。
