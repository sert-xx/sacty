# 秘密情報を伏せる木は、節を型付き配列で持ち、とても長い値でもメモリを値の長さに比例させる

- 日時: 2026-11-21 17:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-444
- 置き換え元: なし
- 置き換え先: なし

## 背景

値の全体の出現を探す木は、値の文字ごとに節を 1 つ持ち、節ごとに `Map` を作っていた。2MB の値 1 つで約 650MB（1 文字あたり約 300 バイト）を使った。
JSON でない認証ファイルは中身の全体が 1 つの値になり、コンテナの中のエージェントは、そのファイルを任意の大きさに書き換えられる。巨大なファイルで、デーモンのメモリを使い切るおそれがあった。

## 決定

- 節を型付き配列（最初の子の文字・最初の子・失敗の遷移・一致する値の長さ）で持つ。1 文字あたり約 14 バイト（値の形が 1 つ・木が 1 本のとき）。
- 子が 2 つ以上ある節の 2 つ目以降の子だけを `Map` に入れる。そうなる節の数は値の数以下なので、長い値の途中の節（子が 1 つ）は `Map` を持たない。
- 認証ファイルは、JSON として読めるかどうかにかかわらず、取り出す前のファイルの大きさで 1MiB の上限を判定する。超えたら、中身を読まず、伏せる対象から外さずに、実行を失敗にする。
  - ホストの認証ファイル（`invocation.ts`）は、大きさを見て、上限を超えていれば読まない。コンテナに写すときの hash の計算（`docker.ts` の `hashOfStaged`）も同じ上限で読むので、起動の前に超えていれば、コンテナを起動せず、認証の失敗にする。この経路では、セッションログにも作業履歴にも何も残らない（まだ出力が無い）。コンテナが終わった後の `collectSecrets` も同じ上限で調べる。
  - コンテナの中で超えた（エージェントが大きくした）ときは、実行の出力を返さず、認証の失敗にし、使用量は残す。ホストの認証ファイルへの書き戻しもしない。
  - 以降は、コンテナの中で大きくされた場合。写したエージェントのセッションのファイルも残さない（写さず、作業履歴に「大きすぎて写さなかった」理由だけを残す）。時間切れの実行で超えたときは、時間切れの結果を返す。
  - コンテナの停止を確かめられなかった・デーモンの停止の結果は、上限超えの失敗より優先して返す（出力は返さないまま）。
  - セッションログは、この実行の出力を残さない（溜めていた分は書かずに捨てる。いままでの分も消し、「出力を残さない」旨の 1 行だけにする）。伏せる対象にできない値が、ログに混ざりうるため。
  - 失敗の文言は、読めない認証ファイルの既存の文言を使う（大きすぎるときも同じ。パスにはホストの認証ファイルのパスを渡す）。利用者には、その実行が認証の失敗になり、出力とセッションログの中身が見えないことだけが見える。
  - 本物の認証ファイルは数 KB〜数十 KB なので、1MiB で正当な利用は止まらない。
- `StreamRedactor` は、値の集合が前回と同じ間は、値の形（JSON のエスケープ）・並べ替え・木を作り直さない。集合の比較は要素の `===` で、長い値でも文字数に比例して比べない。
- 走査・失敗の遷移の作り方は変えない（時間は値と入力の長さに比例する）。

## 理由

- 節を軽くするだけでは、ファイルの大きさに上限が無く、コンテナの中のエージェントが大きくした分だけ、木（値の形ごと・`ByteRedactor` の UTF-8 の長さ・`StreamRedactor` の 2 本、`snapshot` と `close` の `redact` ごと）が増える。実際の経路では、1 文字あたりの量が約 14 バイトの数倍になる。原因は長さに上限が無いことなので、上限を置き、超えたら失敗にする。
- 失敗にする倒し方は、利用者が出力の中身を見られなくなる代わりに、秘密を残す余地が無い。大きすぎる値を伏せる別の方法（`indexOf` の区間の併合など）は、同じ文字が続く入力で二乗になりうるので、採らなかった。
- 上限を 1MiB にすると、値 1 つの木は約 15MB に収まる。実行 1 つあたりの経路は、値の形が最大 2 つ（そのまま・JSON のエスケープ）、木が `StreamRedactor` 2 本・`ByteRedactor` 1 本（UTF-8 のバイト数で最大約 3 倍）・`snapshot`/`close` の `redact` で 1 本ずつ作る間、作る間は `queue`（1 文字 4 バイト）が加わる。最大でも数百 MB の範囲で、上限が無いときのように値の長さに比例して増え続けない。

## 影響

- 伏せる結果は、上限以下の値では変わらない。重ならない入力の結果は変わらない。
- 大きすぎる認証ファイルの実行は、認証の失敗になる。コンテナの中で大きくされたときは、出力を返さない。セッションログには、この実行の出力を残さない（1 行だけ）。大きくされた値は伏せる対象に入らないため。
- `redact`・`compileSecrets` 自体は、長さの上限を持たない。木の大きさは値の長さに比例する（デーモンは認証ファイルからは、上限を超える値を作らない）。ホストの認証ファイルは、`invocation.ts` が上限を超えるものを読まない。コンテナに写すときの hash の計算と写した後の検査も同じ上限で読むので、全体をメモリに読まず、起動の前に実行が失敗になる。
- `StreamRedactor` の 1 回の `push` の時間は、持ち越す分（いちばん長い値の長さ）に比例する。上限があるので、1 回あたり 1MiB 程度の走査になる。前回の木の状態は持ち越さない。
- 数字（約 14 バイト・1MiB の値で約 15MB）は、値の形が 1 つ・木が 1 本のときのもの。値の形が増える（改行・引用符を含む）と木も増え、`ByteRedactor` は UTF-8 のバイト数で数える。
- 作業履歴の `AgentSessionArchived` の `notArchived` に新しい値 `secret_file_too_large` を足した。この値を含む行は、前の版のデーモンでは読めなくなりうる。1MiB 超の認証ファイルの実行の記録ができた後に前の版へ戻すときは、戻す前に、そのタスクの作業履歴を確かめる（確かめていない）。
