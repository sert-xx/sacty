# 文書だけの依頼の実装のセルフレビューは、文書向けの観点で走らせる

- 日時: 2026-11-03 08:30 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-295
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験（findings F38、S2 r3）で、Markdown だけの依頼（`plan=direct`）の実装のセルフレビューが、コード向けの観点（C-1〜C-6・C-15）の担当を起動した。PBI-285 で検証のコマンドは省かれたが、観点の選び方は変わっていなかった。
原因は、実装・修正の工程の指示（`selfReviewLines`）が、主対象の種類を `code` に固定していたこと。スキル `review-dispatch` は主対象の種類の必須観点を全部起動するので、種類が `code` なら文書だけの変更でもコード向けの観点が起動する。PBI-284 で入れた文書だけの依頼の判定（`documentsOnly`）は、この指示から見られていなかった。

## 決定

- 成果物が文書のファイルだけと判断された依頼（`documentsOnly`）の実装の工程では、セルフレビューの主対象の種類を `user-doc` にする。スキルの規則どおり、文書向けの必須観点（U-1〜U-4）、条件に当てはまる条件付き観点（U-5・U-6 など）、横断の観点（X-1、条件付きで X-2）が起動し、コード向けの観点は起動しない。
- 文書だけかの判定は、PBI-284 の `documentsOnly` をそのまま使う。別の判定を持たない。
- 文書は作業領域のファイルを直接直すので、要求要件・設計の下書きのための指示（作業領域の外の一時ファイル）は付けない。
- コードを含む依頼（`documentsOnly` が無い）は、今までどおり `code`。

## 理由

- 文書だけの変更にコード向けの観点を走らせても、指摘が出ず、時間とトークンだけを使う。
- `documentsOnly` は、実装の差分に文書以外が1つでもあれば最終レビューの前に止める（PBI-284）ので、文書だけという前提は崩れたまま進まない。判定を二重に持つと、食い違ったときにどちらが正しいか分からなくなる。
- 既定のスキルは変えない。種類ごとの観点の選び方は、すでにスキルにある。

## 影響

- 文書だけの依頼の実装のセルフレビューは、コード向けの観点の担当を起動しない。
- 不具合の修正は `documentsOnly` にならないので、`code` のまま。
