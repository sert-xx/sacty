# レビューのタスクは、判定が指摘なしになるまで完了にせず、PR の変化を見守って自動で再レビューする

- 日時: 2026-11-19 19:25 UTC
- ステータス: 採用
- 関係する PR・タスク: #452、PBI-411
- 置き換え元: [レビューを依頼された PR とレビュー用のラベルの PR を取り込み、オーケストレーターを使わずにレビューだけを行う](20261013-0335-superseded-review-only-pr-intake.md)（投稿で完了し、次のレビューは人が「再レビュー」で始める部分と、PR のマージ・クローズで中止する部分）
- 置き換え先: なし

## 背景

PR のレビューのタスクは、判定に関係なく、レビューを投稿した時点で完了していた。画面は、指摘が残っていても「完了」と出した。
指摘の後には、PR の作者の修正か反論がある。その後のレビューは、人が「再レビュー」を押すか、GitHub で再依頼するまで始まらなかった
（sacty が作った PR の子タスクだけは、親の更新で自動で再レビューしていた）。
実装のタスクは、PR にレビューが届くと自動で取り込んで直す。レビューのタスクだけが、投稿の後の変化を見ていなかった。
終わっていないレビューのタスクは、PR がマージ・クローズされると中止していた（レビューを投稿した後のタスクは完了していたので、対象にならなかった）。

## 決定

人が決めたこと（選択式の問いへの答え）。

- 対象は、すべてのレビューのタスク（ラベルで取り込んだ PR・依頼で取り込んだ PR・sacty が作った PR の子タスク）。判定が指摘なしになるまで、完了にしない。
- 再レビューのきっかけは、新しいコミットの push と、push 無しの作者の返信。返信では、同じ先頭を 1 回だけ判定し直す。続けての push・返信は、静かになるまで待って 1 回にまとめる。
- 見守り中に PR がマージ・クローズされたら、中止ではなく完了にし、理由を残す。
- 費用の歯止めは、タスクごとの予算の上限だけ。再レビューの回数の上限は設けない。

実装で決めたこと。

- 状態：投稿の記録（`PullRequestReviewPosted`）に見守りの印（`watch`）を足し、印のある投稿で、今の回の判定が指摘なしでなければ、完了にしない（`reviewWatching`）。工程（`steps`）は今までどおり `done` にし、状態（`status`）は `idle` のまま。「完了」の判定（`isFinished`）だけが、見守りを見る。
- この仕組みより前の投稿（印が無い）は、判定に関係なく完了のまま。見守りにも、自動の再レビューの対象にもしない。
- 「提案あり（マージは可）」と、判定が無い回（付けなかった・読めなかった）も、指摘なしではないので完了にしない。
- 指摘なしで完了した後は、PR の先頭の変化だけで再レビューする。返信・コメントだけでは始めない。
- レビューを投稿する前（実行待ち・実行中。再レビューの実行中も）に PR がマージ・クローズされたら、今までどおり中止する。
- sacty が作った PR の子タスクの再レビューは、今までどおり親の流れが決める（親が PR を更新して承認待ちに戻った・人がコミットを足した・親が指摘をすべて断った）。見守りは、子タスクの終わり（マージ・クローズで完了）だけを扱う。
- GitHub の再依頼は、今までどおり新しいタスクを作り、元のタスクには何も記録しない（[GitHub のレビュー再依頼は完了タスクを戻さず別タスクにする](20261019-0503-review-rerequest-new-task.md)）。元のタスクが見守り中でも同じ。再依頼で作った、より新しいタスクがある元のタスクは、PR の変化では再レビューを始めない。
- ドラフトの PR でも、同じように再レビューする。
- 見守りに入ったことは通知しない。完了の通知は、完了になったときだけ出す。
- 最後の投稿から時間がたった PR は、間を空けて読む（1 時間を過ぎたら 5 分ごと、24 時間を過ぎたら 30 分ごと）。

## 理由

- 人の言葉：「レビュータスクは指摘して終わりではない。指摘に対して修正や反論があるはず」「一度『指摘なし』になった場合はステータスを完了として、その後人間が変化を加えたりした場合は再レビューのトリガーをする」。
- 投稿の記録に印を足す形にしたのは、状態を作業履歴から作り直すため。判定のしかただけを変えると、過去に指摘なしでない判定で完了したタスクが、作業履歴の再生で一斉に見守りに変わり、PR の変化で再レビューを始める（1 回あたり数ドルかかる）。
- 工程を `done` のままにしたのは、子タスクの投稿を待つ親の流れ・作業領域の片付け・監査・続きのタスクの作成が、工程が終わったこと（`isCompleted`）で決めているため。これらは変えない。
- 提案ありを完了にしないのは、人の言葉が「指摘なしになるまで」であるため。提案だけの繰り返しの費用は、予算の上限で止める。
- 完了の後を先頭の変化だけにしたのは、お礼の一言のようなコメントで、再レビューの費用を使わないため。
- 実行中のマージ・クローズを中止のままにしたのは、実行を止めて費用を止める今の仕組みを使うため。実行を止めて完了にする形は、実行の打ち切りの後に完了へ進める仕組みが要るので、今回は入れない。前の回のレビューを投稿したタスクも「中止」と出ることは、分かった上で残した。
- 子タスクの再レビューを親の流れに任せたのは、親が直している途中の push で再レビューを始めないため（親が承認待ちに戻ってから、1 回だけ始める）。
- 再依頼で元のタスクに何も記録しないのは、再依頼の ADR の「元タスクの状態・投稿・履歴は変えない」を保つため。比べた案：元のタスクの見守りを終える記録を足して完了にする（元のタスクが「PR の対応待ち」のまま残らないが、再依頼の ADR の決定を改めることになる）、見守り中の再依頼は同じタスクの再レビューにする（再依頼の ADR の「別タスク」を、完了したタスクだけに狭めることになる）。どちらも採らなかった。
- 読む間隔を空けるのは、開いたままの PR の見守りが増えても、GitHub への問い合わせ（1 回の確認で 1 件）を増やし続けないため。

## 影響

- レビューのタスクは、指摘なしになるか、PR がマージ・クローズされるまで、「終わっていないタスク」に残る（人の出番には数えない）。
- push・返信のたびに再レビューの費用がかかる。止まるのは、タスクの予算の上限に達したとき。
- 取り込んだ後の push が、人の操作なしに検証で動く：今までは、新しいコミットを動かすには人の「再レビュー」か GitHub の再依頼が要った。これからは、PR が開いている間（指摘なしで完了した後も）、push のたびに、push した人やフォークかどうかを確かめずに再レビューし、PR のコードがエージェントのコンテナで動く。取り込んだ時点の信頼の判断が、その後の push にも及ぶ。止めるには、タスクを一時停止か中止する（フォークの PR は人の操作を待つ・プロジェクトごとに見守りを切る、は入れていない）。
- 以前の版に戻すと起動できなくなりうる：新しいイベント（`ReviewWatchEnded`）と、`ReviewRestarted` の新しい理由（`pushed`・`replied`）は、以前の版には知らない値で、作業履歴は追記だけなので、これらが 1 件でも記録された後に以前の版へ戻すと、デーモンが作業履歴を読めずに起動できない（イベントを足す変更に共通）。戻すときは、この版より前に取った `sacty.db` の控えに戻すか、戻さずに前へ直す。
- 再依頼で新しいタスクができた元のタスクは、PR がマージ・クローズされるまで「PR の対応待ち」のまま残る。
- 見守り中のタスクは終わっていないタスクなので、そのタスクがあるプロジェクトは削除できない（PR がマージ・クローズされるか、タスクを中止するまで）。
- 再レビューの実行中に PR がマージ・クローズされると、前の回のレビューを投稿したタスクも「中止」になる。
- `sacty mcp` の要約の `state` は、見守り中は `idle`（`completed` ではない）。`review.watching`・`review.watchEnded` で見分ける。
