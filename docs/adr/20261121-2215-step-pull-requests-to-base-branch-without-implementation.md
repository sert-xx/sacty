# 実装の無い進め方では、タスクブランチを作らず、工程の PR をベースブランチへ直接出す

- 日時: 2026-11-21 22:15 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-464
- 置き換え元: [Git 管理のリポジトリでは、要求要件・設計を工程ごとにタスクブランチへの PR にし、そのマージを人の承認とする](20261013-1318-superseded-step-pull-request-approval.md)（決定 2：実装の工程が無い進め方で、要求要件・設計の PR をタスクブランチへ出す部分）
- 置き換え先: なし

## 背景

要求要件・設計を PR で承認するタスクは、進め方に実装の工程が無い（`design-only` など）ときも、タスクブランチ `sacty/task-<ID8>` を作り、PR をタスクブランチへ出していた。
実装の PR が無いので、タスクブランチはベースブランチにマージされず、文書はベースブランチに入らない。
続きのタスク（派生）はベースブランチから始まるので、文書を引き継げない。
タスクブランチと工程のブランチも、リモートに残る（利用者の指摘、2026-11-21）。

## 決定

利用者の決定（2026-11-21）：実装を含まない進め方では、タスクブランチを作らず、工程の PR をベースブランチへ直接出し、マージで承認する。

- 対象の判定（直接の流れ）：`TaskBranchCreated` が無く、`steps` に `implement` が無いタスク（`directStepFlow`）。
  `steps` は `StepsChosen` の後で実装を増減しないので、途中で切り替わらない。
  分割の親も対象にする（子タスクはベースブランチか依存先の PR のブランチから始まるので、親のタスクブランチが無くても困らない）。
  実装のある進め方と、分割の子タスクは、今までどおりタスクブランチを使う。
- 向き先と起点：工程のブランチ `sacty/task-<ID8>-<工程>-<回>` を、ベースブランチの先頭から作り、PR をベースブランチへ出す。
  マージした文書は、ベースブランチを取得して読む。
- 作り直しの比べ方：開いている PR は、ほかの人のマージでベースブランチが進んだだけでは作り直さず、同じ PR のブランチに積む。
  別の工程の PR が、その PR を出した後にマージされたときだけ作り直す（設計は、要求要件のマージを取り込んだベースブランチの最新から作る）。
  閉じた・マージした PR の作り直しは、今までどおり。
- ブランチの削除：sacty が作ったブランチを残さない。
  削除の規則を 1 つの関数に置き、PR の確認・作り直し・直しの間のマージ・完了・中止のすべてが通る。
  - 分類は、削除する時点の `stepPullRequests` の状態で、上から順に決める。
    1. 無条件に消す：マージを記録した PR のブランチ（`StepBranchKept` の有無に関わらない）と、sacty がこの手で閉じた PR のブランチ。
    2. 消さない：`StepBranchKept` を記録したブランチ。
    3. 比べて消す：それ以外。削除の直前に先頭を取得し、sacty が最後に push した先頭と同じときだけ、その先頭を期待して消す（`--force-with-lease`）。
  - 先頭が違えば、消さずに `StepBranchKept` を記録する。人がコミットを足したブランチは、人のコミットに sacty が積んだブランチを含め、その PR がマージされるまで消さない。
  - リモートにブランチが無ければ、消せたものとする。ほかの取得の失敗・最後の push の記録が無いときは、消さず、完了・中止のときにやり直す。
  - 削除に失敗しても、タスクは止めない。
- 中止の確認（`cancelTargets`）は、同じ分類で消すブランチを示し、残すブランチは理由つきで「触れないもの」に出す。
- 派生の記録に、直接の流れでマージした PR の行ごとに、文書のパスを付ける。
- アップデートの前に作ったタスクのうち、まだタスクブランチも工程の PR も無いものは、直接の流れで進む（作ったものが無いので、途中の切り替えに当たらない）。
  アップデートの後に始まる要求要件の PR の向き先は、ベースブランチになる。
  すでにタスクブランチがあるタスクは、今までどおりの流れで進む。

## 理由

- 文書をベースブランチに入れると、続きのタスクが引き継ぎ、リモートに sacty のブランチが溜まらない。
- 作り直しを、ベースブランチの先頭と比べると、ほかの人のマージのたびに PR が作り直される。前の工程のマージだけを見れば、今までの「前の工程の直しで起点が進んだら作り直す」と同じ意味になる。
  採らなかった案：ベースブランチの先頭と比べる（上の理由）。
  懸念：開いている PR はベースブランチの最新を取り込まないので、同じ文書をほかのタスクが直すと、マージする人が競合を GitHub で解く。文書のパスはタスクごとに別なので、まれ。
- 人がクローズした PR のブランチを無条件に消すと、人がコミットを足した内容も消える。先頭を比べ、違えば残す（人の指摘）。
  経路ごとに判定を書くと、経路の間で判定がずれるので、1 つの規則にし、状態で分類を決める。
- 競合の表示は、記録しない（今までどおり）。ブランチの保護と CI は、ベースブランチへ出すのが利用者の決定で、マージする人が決める。

## 影響

- 新しいイベント `StepBranchKept` を足した。
  直接の流れのタスクを 1 件でも記録した後は、前の版のデーモンは、タスクブランチの無い工程の PR の記録を整合性のエラーにし、作業履歴を投影できずに起動しない。
  前の版へ戻せなくなることは許容する（前例：[要求要件・設計の自動の直しの間の PR のマージを承認にし、直しを捨てる](20261121-1619-step-pull-request-merge-during-rework.md)の互換性）。
- すでにリモートに残っている過去のタスクのブランチの片付けと、実装の PR がある段階で要求要件・設計へ差し戻すときの起点は、この決定の範囲の外。
