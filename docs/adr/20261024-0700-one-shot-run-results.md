# Claude Code の実行で後で起こす予約を使わせず、結果が何回も出ても本文と使用量を正しく取る

- 日時: 2026-10-24 07:00 UTC
- ステータス: 採用
- 関係する PR・タスク: #213、PBI-154
- 置き換え元: [Claude Code を stream-json で動かし、最後の答えは標準出力を溜めずに行ごとに読んで取り出す](20261013-1533-superseded-claude-stream-json-output.md)（最後の `result` から出力と使用量を読む部分）
- 置き換え先: なし

## 背景

PR のレビューのタスク（4回目の再レビュー）で、レビューの工程が 42 分かかり、投稿の本文が途中の要約に置き換わった。
セッションのログで確かめたところ、次のとおりだった。

- エージェントは、検証や観点の担当の終わりを待つあいだに、`ScheduleWakeup` で 20 分後・30 分後に起こす予約をした。
  最終の答え（総評と判定の塊）は 06:20 に出たが、`claude -p` は予約が残っているので終わらず、06:46 に起こされるまで 26 分残った。
  同じタスクの前の3回は `ScheduleWakeup` を使わず、最後の出力の直後に終わっていた。
- 起こされたエージェントは「レビューは終わっていて、本文は前のメッセージにある」と答え、それが最後の `result` になった。
  sacty は最後の `result` を答えにするので、その要約が PR に投稿され、判定も読み取れなかった。
- `claude -p` は、バックグラウンドの処理の通知が来るたびに番を進め、`result` をそのたびに出す（この実行では 48 回）。
  `result` の `usage` はその番の分だけで、実行の全体（サブエージェントを含む）は `modelUsage` にある。
  sacty は最後の `result` の `usage` で費用を数えていたので、通知が何回も来る実行では数分の1になっていた（例：記録 1.60 USD、CLI の集計 8.14 USD）。

## 決定

- Claude Code の実行では、`--disallowedTools` で `ScheduleWakeup`・`CronCreate`・`CronDelete`・`CronList`・`RemoteTrigger` を使わせない。
- 答えに決まった見出しの塊を必ず含める役割では、その塊のキー（引用符で囲んだ見出し）を含む最後の `result` を答えにする。含むものが無ければ、これまでどおり最後の `result`。
  対象は、レビュー（`sacty-review-verdict`）・最終レビュー（`sacty-final-review`）・再現（`sacty-reproduction`）・分割（`sacty-split`）・統合レビュー（`sacty-integration-review`）・情報収集（`sacty-gathered`）（`answerMarker`）。
  目印を渡したのに当たらず、`result` が2つ以上あったときは、`result` の数と使用量の出どころを、デーモンのログとセッションログ（標準エラー）に1行残す。
  引用符で囲むのは、返答の文が名前に触れただけで当たらないようにするためである。
- 使用量は、最後の `result` の `modelUsage` の、モデルごとのトークン数の合計にする。無ければ、各 `result` の `usage` の合計にする。
  保存したセッションを再開・複製した実行（オーケストレーター・質問への答え）は、`modelUsage` に前の実行の分も入る（小さなモデルで2回続けて確かめた。2回目の `modelUsage` の出力のトークン数が、1回目と2回目の和だった）。そのため、各 `result` の `usage` の合計にする。

## 理由

- sacty の実行は一度きりで、終わったら結果を受け取る。後で起こす予約や定期の実行は、実行の中では役に立たず、残ると実行が終わらない。
  `RemoteTrigger` は実行の外にルーチンを作るので、同じく使わせない。
- `result` の項目（`origin` など）では、最終の答えの番と、その後の番を見分けられなかった（予約で起きた番も、最初の依頼の番も `origin` が空）。
  答えの形が決まっていない工程では、本文を選ぶ規則を作れない。そこで、予約を止めて、後の番が来る主な原因をなくす。
  そのうえで、答えに決まった見出しの塊を必ず含める役割は、その塊を目印にする。塊が読めないと、不合格や読めない判定になるためである。最初はレビューの工程だけにしていたが、最終レビューなども同じことが起こりうると PR のレビューで指摘された。
  当たらなかったときに記録を残すのは、同じ事故が起きたとき、運用者がどの `result` を答えにしたかを調べられるようにするためである。
- 費用の上限は使いすぎを止めるためのものなので、少なく数えるほうが害が大きい。`modelUsage` はサブエージェントの分も含む実行の全体の値なので、それを使う。

## 影響

- 通知が何回も来る実行（観点の担当を並べるレビューなど）の費用の記録が、これまでより大きくなる（サブエージェントの分を含むため）。予算の警告や上限に早く届く。
- サブエージェントの別のモデルの分も、実行したエージェントの単価で換算する。モデルごとの単価での換算はしない。
- 再開・複製した実行の使用量には、サブエージェントの分が入らない（これまでと同じ）。
- 目印のある役割で、塊を付けた答えの後に、塊の無い答えを出し直したとき（レビューを完了できなかったなど）は、前の答えが本文になる。
- 目印の無い役割（実装・調査など）では、最終の答えの後に通知への返答の番が来ると、これまでどおりその返答が答えになる。予約を止めたので起こりにくくなるが、残っていたバックグラウンドの処理が後で終わったときは起こりうる。
- `modelUsage` は、項目ごとに各 `result` の `usage` の合計と大きいほうを取る。読める項目を持つモデルが無ければ使わない。CLI のキーの名前が変わっても、費用が 0 にはならない。
- エージェントが予約のツールを呼ぶと、使えないと返される。
