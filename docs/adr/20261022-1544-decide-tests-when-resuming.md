# テストが決まらずに止まったタスクは、人が再開のときにテストのコマンドかテストなしを決められ、決めずに再開すると工程の選択からやり直す

## 背景

エージェントのスキルを集めたリポジトリや、ドキュメントを置くだけのリポジトリでタスクを実行すると、オーケストレーターがテストのコマンドを決められずに止まる（`orchestrator.testCommandUnknown`）、という報告があった。
止まったときの文言は「タスクの内容にテストの実行方法を書いて、作り直してください」だったが、次の問題があった。

- そもそもテストを書く種類のリポジトリではないので、書けるテストの実行方法が無い。
- 止まったタスクの詳細には「再開する」しか無く、タスクの内容を直せない（中止して再実行すれば直せるが、文言からはわからない）。
- 「再開する」を押すと、選んだ工程のまま調査・要求要件・設計・実装まで進み、費用をかけた後の検証で同じ理由でまた止まる。

テストの仕組みが無いリポジトリのための `noTests`（PBI-94）はすでにあった。
しかし、オーケストレーターへの指示が「分からなければ空にする（推測で書かない）」「テストの仕組みはあるのにコマンドが分からないときは `noTests` を書かない」と、迷ったら止める側に倒れる書き方で、既定のスキル `plan-steps` にも `noTests` のことが無かった。
実際の AI は、`scripts/` などを見てテストの仕組みが無いと言い切れずに、`testCommand` も `noTests` も空にしていたと考えられる（実際の答えは確かめていない）。

## 決定

1. **オーケストレーターへの指示**：「分からなければ空」「テストの仕組みはあるのにコマンドが分からないときは書かない」をやめる。
   調べる場所（パッケージの設定・Makefile などのタスクの定義・CI の設定・pre-commit・README・CONTRIBUTING・AGENTS.md・CLAUDE.md・テストのディレクトリやファイル）を挙げ、リポジトリが実際に使っているコマンドを `testCommand` に書かせる。
   調べても見つからなければ `noTests` に根拠を書かせ、実装する組み合わせでは両方を空にさせない。
   スキル集・ドキュメントだけのリポジトリもこれに当たると例を挙げる。
   既定のスキル `plan-steps` にも同じ決まりを書く。
   sacty がテストのファイルを探す歯止め（`checkNoTests`）は残す。
2. **人が決める**：テストが決まらずに止まったタスク（実装か再現を含むのに、テストのコマンドも `noTestsReason` も無い）の再開で、人がテストのコマンドを指定するか、理由を書いてテストなしで進めるかを選べるようにする（`ResumeTaskInput` の `tests`）。
   新しいイベント `TestsDecided`（人の記録）に残し、投影の `testCommand` か `noTestsReason` にする（`testsDecidedBy: person`）。
   - テストなしは、オーケストレーターが `noTests` を答えたタスクと同じく進める。人の判断なので、テストのファイルを探す歯止めは当てない。
   - 不具合の修正（再現の工程がある）は、テストなしにできない（再現をテストで確かめるため）。
   - 人が決めたら、工程は選び直さない。画面・実装と最終レビューの指示・PR の本文で、人が決めたことを示す。
3. **決めずに再開したとき**：工程を選んだ直後に止まり、まだどの工程の成果も無ければ、`TaskResumed` の `rechooseSteps` を記録し、選んだ工程と工程の選択で決めたものを消して、工程の選択からやり直す（予算の上限は残す）。
   工程を始めた後なら、今までどおり止まった所から再開する。
4. 止まったときの文言は、作り直しではなく、再開のときの選び方（テストのコマンド・テストなし・決めずに再開）を案内する。

## 理由

- 「作り直す」は、テストを書かないリポジトリでは打つ手が無く、画面にも手段が無かった。止まったタスクの上で人が決められれば、作り直さずに進められる。
- 人がテストなしを選べると、テストの仕組みがあるのに黙ってテストなしで通ることが起きうる。ただし人が理由を書いて選んだことは作業履歴・画面・PR の本文に残り、実装の人の承認も要るので、気づける。オーケストレーターの判断（AI）だけでテストなしにするときの歯止めは、これまでどおり残す。
- テストのファイルらしいもの（テスト用ではない `scripts/test_helper.sh` など）を誤って当てたとき、これまではリポジトリのファイルの名前を変えるしかなかった。人の判断では歯止めを当てないので、リポジトリを変えずに進められる。
- 決めずに再開したとき、同じ工程のまま進めると、テストが無いことは変わらないので、費用をかけた後の検証で必ずまた止まる。工程の選択からやり直せば、直した指示のもとで、オーケストレーターが `noTests` を答え直せる。
- 工程の選択からやり直すのに、新しいタスクを作らず投影の項目を消すことにした。中止したタスクの再実行（新しいタスクを作る）と違い、まだどの工程も成果を出していない状態に限るので、消す項目は工程の選択（`StepsChosen`）で決めたものだけで済む。
- 比べた案：
  - 再開を拒み、テストの扱いを必ず選ばせる。決めずに再開してオーケストレーターに選び直させたいこともあるので、選べるようにした。
  - 止まったタスクの内容（説明）を直せるようにする。投影と作業履歴の扱いが大きくなり、テストを書かないリポジトリでは直す内容が無いので、テストの扱いだけを決められるようにした。

## 影響

- 作業履歴に `TestsDecided` と、`TaskResumed` の `rechooseSteps` が加わる。これより前の版の sacty はこれらを読めない。
- 工程の選択からやり直すと、オーケストレーターの実行が1回増える（費用は工程の選択の記録に入る）。
- 決めずに再開したときに消すのは、工程の選択で決めたもの（工程・理由・テストのコマンド・イメージ・サービス・書き出し先など）。止まっている間に人が工程のイメージ・エージェントを変えていたら、それも消える（選んだ工程に結びつくため）。
- 実際の AI のオーケストレーターが、新しい指示で `noTests` を答えるようになるかは確かめていない。
