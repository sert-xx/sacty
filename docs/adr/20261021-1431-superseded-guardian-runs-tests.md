## 背景

実装の検証では、sacty がテストのコマンドを別のコンテナ（テストのコンテナ）で実行し、終了コードが 0 で観点がすべてテストに対応していれば、
ゴールガーディアンの最終レビューへ進めていた。ゴールガーディアンには、テストの結果を出力の末尾 8,000 文字だけ渡し、指示では
「判断の根拠は、差分とテストの結果だけにする」としていた。

テストのコマンドが複数の種類のテスト（例えば Small と Medium）を順に実行するリポジトリで、テストはすべて通っていたのに、最終レビューが
不合格になった。末尾に入っていたのは後の種類の一部だけで、ゴールガーディアンは観点に対応するテスト（Medium のもの）の結果を見られず、
指示どおり渡されたものだけで判断したため。利用者からは、テストを実行する必要があるならゴールガーディアンが自分で実行すればよく、
sacty が別に実行する必要は無い、という方針が示された。

## 決定

1. **実装の検証**：sacty はテストのコンテナを使わず、`TestsRun`・`TestsSkipped` を記録しない。実装の工程が終わる（`verification` が
   `pending`）と、差分を取り、ゴールガーディアンの最終レビューを、実装後の作業領域の使い捨ての写しで、実装の工程のイメージ
   （無ければ再現の工程のイメージ。そのイメージの `env` も渡す）で実行する（これまでは既定のイメージだった）。写しの .git は、作業領域の .git
   （エージェントが書き換えられる）ではなく、エージェントが触る前に退避したメタデータの写しにする（git を参照する検証も動くように。これまでの
   写しには .git が無かった）。テスト（検証）の
   コマンド（オーケストレーターの `testCommand`、テストの仕組みが無いタスクでは実装が申告したコマンド）があれば、指示で、そのコマンドを
   作業領域で実行させ（セットアップはしてよい）、出力の末尾だけでなく全体（コマンドが実行するすべての種類のテスト）を確かめさせ、
   終了コードが 0 で失敗が無いときだけ通ったものとし、テストやコマンドを変えて通さないよう求める。結果は `sacty-final-review` の中の
   `tests`（`command`・`exitCode`・`output`（抜粋）・`missingCommands`）で申告させる。判断の根拠は「差分と、作業領域の実装後のコード・
   あなたが実行したテストの結果」にする。
2. **sacty に残す機械的な歯止め**：テストのコマンドがあるときは、ゴールガーディアンが終了コード 0 を申告したときだけ合格にする（申告が
   無ければ不合格）。実装がテストを対応させていない観点は、ゴールガーディアンの判定にかかわらず不合格にする（`review.viewpointUnmapped`。
   テストの仕組みが無いタスクには当てない）。申告されたテストは `FinalReviewed` の `tests`（`command` は sacty が渡したコマンド。抜粋は
   8,000 文字まで）に記録する。
3. **ツールがイメージに無いとき**：ゴールガーディアンが `missingCommands` に書いた名前のうち、テストのコマンドの中に語として書いてあるもの
   （`/` を含まない）があれば、判定を記録せずに、費用を `FinalReviewFailed` に記録して一時停止する（`verify.commandMissing`。工程は実装）。
   再開すると、実装ではなく最終レビューからやり直す。
4. **サービス**：テストのコマンドがある最終レビューでは、実装の工程のサービスを、ゴールガーディアンの実行の前に起動し（`ServicesStarted` の
   `forTests` は「検証（最終レビューの中のテスト）のため」の意味にする）、イメージを ID に確定させてから、そのネットワークと localhost の
   転送につなぎ、接続先を指示に足し、終わったら消す。起動できなければ、ゴールガーディアンを実行せずに一時停止する（`verify.testsUnavailable`）。
5. **やり直しと示し方**：最終レビューに通らなかったときの実装のやり直しの指示・PR の本文・チャットの判定の説明に、ゴールガーディアンが
   実行したテスト（コマンド・終了コード・抜粋）を出す。画面の実装の成果物は「ゴールガーディアンが実行したテスト」として出す。
6. **時間の上限**：`run_timeout.test_minutes` は、テストのコンテナの上限ではなく、テストを実行する役割（`final-review`・`reproduce`）の
   既定の上限に足す分にする（役割の上書きが無ければ `agent_minutes + test_minutes`。上書きがあればそれ）。設定の名前と既定（20 分）は変えない。
7. **再現の確かめ**：不具合の修正の再現でも、sacty はテストを実行しない。再現のエージェントに、テストのコマンドを自分で実行し、書いたテストが
   不具合のために失敗することを確かめて、`sacty-reproduction` に `reproduced`・`command`・`exitCode`・`output` を書かせる。sacty は、
   再現のテストの申告があり、`reproduced` が `true` で、0 でない整数の終了コードの申告があるときだけ再現できたとし、工程の完了と同じトランザクションで
   `ReproductionChecked` を記録する（それ以外は再現できなかったとし、`reproduce.noTests` か `reproduce.notChecked` を添えて人の判断を待つ）。
   それより前の版で sacty の確かめを待っていたタスクは、再開・再起動のときに、テストを実行せずに再現できなかった（`reproduce.notChecked`）と
   記録する。
8. **作業履歴の互換**：`TestsRun`・`TestsSkipped` と、`verification` の `tests_passed` は、それより前の作業履歴を読むためだけに残す。
   `FinalReviewed`・`FinalReviewFailed` は、`verification` が `pending` でも `tests_passed` でも受け付ける。実装の `AgentRunCompleted` で、
   前のテストの結果（`lastTests`・`testsSkippedAt`）を消す。

## 理由

- ゴールガーディアンが自分でテストを実行すれば、出力のどこを読むかを自分で決められ、末尾の切り詰めで観点に対応するテストの結果が
  抜け落ちることが無くなる。テストのコードと結果を突き合わせて、対応するテストが実行され通っているか（スキップされていないか）も確かめられる。
  利用者の方針（ゴールガーディアンが実行すれば、sacty が別に実行する必要は無い）にも合う。
- 出力をもっと長く渡す・テストの種類ごとに分けて渡す案は、どこまで渡せば足りるかがリポジトリによって決まらず、同じ問題が残るので採らなかった。
- 終了コード 0 の申告と、テストの対応が無い観点の不合格を sacty に残すのは、モデルの判定だけで「テストが通らないのに合格」「観点に
  テストが無いのに合格」にならないようにするため（これまでの機械的な合否の条件を、申告に対して保つ）。
- 最終レビューを実装の工程のイメージで動かすのは、テストを実行するのに、実装が使った言語のツールが要るため。
- ツールが無いときに実装をやり直さずに止めるのは、これまでと同じく、実装をやり直しても直らないため。見分けを sacty の出力の読み取り
  （sh の文言）からゴールガーディアンの申告に変えるのは、sacty がテストを実行しなくなったため。テストのコマンドに語として書いてある名前
  だけを当てるのは、これまでと同じく、イメージの問題とリポジトリの問題を分けるため。
- `test_minutes` を足すのは、テストを別に実行していたときのエージェントとテストの上限の合計と同じ時間を、テストを実行する役割に残すため。
- 再現も同じく変えたのは、sacty がテストを実行する仕組みを残さないためと、再現のエージェントが書いたテストを自分で実行して確かめるほうが、
  失敗の理由（不具合のためか、構文の誤りなどか）まで確かめられるため。

## 影響

- **秘密情報の露出**：対象リポジトリのテストのコードは、ゴールガーディアンのエージェントのコンテナの中で動く。このコンテナは、ほかの
  工程のエージェントのコンテナと同じく、エージェントの認証の値と、ゲートウェイを使う実行では実行ごとのゲートウェイのトークンを持つ。これまでのテストのコンテナには、
  秘密情報・認証ファイル・ゲートウェイを渡していなかった。実装のエージェントはすでにリポジトリのコードを動かせるので、露出の範囲は
  実装の工程と同じだが、最終レビューの実行もその範囲に入る。
- **機械的な判定の喪失**：テストの合否は、sacty が実行した終了コードではなく、ゴールガーディアンの申告で決まる。申告を偽ることを sacty は
  確かめられない。終了コード 0 の申告が要ることと、テストの対応が無い観点の不合格は残る。
- 最終レビューは、テストの実行の分だけ時間と費用が増える。テストを実行する役割の時間の既定は `agent_minutes + test_minutes` になる。
- 再現のエージェントの申告が無い・`reproduced` が `true` でない再現は、再現できなかったとして人の判断を待つ。再現のテストのイメージの
  ツールが無いことによる一時停止（`verify.commandMissing` の再現の工程）と、テストの実行基盤の失敗（`reproduce.runFailed`）は、新しい実行では起きない。
- 前の版の作業履歴（`TestsRun`・`TestsSkipped`・`tests_passed`）は読める。画面では「テストの実行」として出す。
