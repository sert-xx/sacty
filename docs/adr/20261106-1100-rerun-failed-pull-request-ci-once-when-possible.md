# 実装の PR の CI の失敗ジョブを、できるときにコミットごとに1回だけ再実行する

- 日時: 2026-11-06 11:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-311
- 置き換え元: なし
- 置き換え先: なし

## 背景

最終レビューの前に作った実装の PR の CI が、たまたま落ちたジョブのせいで `failed` になると、ゴールガーディアンは変更と無関係と確かめられないまま判定することになる。`failed` のまま実装に戻すと、実装で直らない失敗で実装と最終レビューを繰り返す。

## 決定

- CI が `failed` で終わったら、最終レビューに進む前に、失敗した GitHub Actions の実行の失敗したジョブをコミットごとに1回だけ再実行し、その結果を `PullRequestCiFinished` に記録する。
- 再実行はできる場合だけ行う。権限不足・ネットワークの失敗・Actions 以外のチェックだけの失敗などでできなければ、スキップして元の `failed` のまま進む。それを理由にタスクを止めない・失敗にしない（人が決めた）。
- GitHub に頼む前に `PullRequestCiRerunRequested` を記録する。頼めたかが分からないまま再起動しても、2回頼まないことを優先する。
- 頼んだ実行が頼む前の試行のまま失敗していれば、再実行が始まっていないものとして待つ。5分たっても始まらなければ、今の失敗を結果にする。
- 再実行で通ったときの元の失敗は最終レビューに渡し、不安定な失敗の候補として扱わせる。

## 理由

- 頼む前に記録しないと、頼んだ後・記録の前に止まったとき、再起動の後に2回目を頼んでしまう。逆の順にしたので、記録の後・頼む前に止まると再実行は無いまま5分待つが、失うのは待ち時間だけで、結果は元の失敗のままになる。
- `tests.flakyFailures` の `runs`・`passes` は作業領域で実行し直した回数で、`checkFlakyFailures` が確かめる。CI の再実行を数えると、その基準が別の意味になる。また、申告はテストのコマンドが失敗したときだけ読むので、作業領域で失敗しない CI の失敗は申告しても捨てられる。そこで、作業領域でも失敗したときだけ `tests.flakyFailures` に書かせ、それ以外は `humanChecks` に書かせる。検査は変えない。
- 再実行で通っても、変更が持ち込んだレース条件かもしれない。通ったことだけで無関係とは見なさず、差分で変えたテスト・コードに関わる失敗は不合格にさせ、再実行で通ったジョブの結果は使い回させない。

## 影響

- CI の待ち時間は、失敗したときに最長で再実行の分だけ延びる（上限の 60 分は再実行の時刻から数え直す）。
- プロジェクトの GitHub のアカウントに Actions への書き込みの権限が無いと、再実行はされない（動きは今までと同じ）。
- 複数の実行のうち一部だけ頼めたときは、頼めなかった実行が始まらないので、結果が出るまで最長で5分待つ。
- マージの後の監視は変えない。
