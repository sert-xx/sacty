# 実装の途中は関係するテストだけを実行し、全件は最後の変更の後に実装の工程で1回実行する

- 日時: 2026-11-08 06:02 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-316
- 置き換え元: なし
- 置き換え先: なし

## 背景

実装の工程は、テストをいつ・どの範囲で実行するかを指示していなかった。
既定のスキルのセルフレビューの検証（`verification-run`）は、回ごと（初回・再レビュー）に見つけた検証を全部実行させるので、直すたびにテストの全件が走っていた。
最終レビューでも、ゴールガーディアンがテストのコマンドを実行する。
PBI-305 で、実装の工程が最後の変更の後に実行した検証の記録（`sacty-verification`）があれば、最終レビューは同じ内容の結果として使い回すようにした（[同じ内容で実行済みの検証は、記録と CI の結果を使い回し、覆われていない分だけを実行する](20261106-0005-reuse-verification-results-for-same-content.md)）。使い回せるのは `coverage` が `full` の記録だけである。

途中のテストを関係するものに絞ると速くなるが、次のことに気をつける必要があった。

- 全件を省いて提出させない。関係するテストだけの結果を、全件の結果として使い回させない。
- 全件を、実装の工程と最終レビューの両方で重ねて実行しない（PBI-305 の使い回しと二重にしない）。
- 既定のコンテキストは、あらゆる言語の対象リポジトリに配られる。特定の言語・テストの実行器に寄せた指示にしない。

## 決定

- 実装・修正の工程（文書だけの依頼と、テストの仕組みが無いタスクを除く。実行するテストが無いため）の「提出の前の検証」で、途中（実装と確かめの繰り返し・セルフレビューの各回）は、変更に関係するテスト（変えたファイルのテスト・足したテスト・変えたコードを使うテスト）だけを実行してよいとする。選び方は、リポジトリのテストの実行器の絞り込みから決めさせ、決められなければ全件を実行させる。
- 全件は、最後の変更の後（セルフレビューを終え、もう作業領域を変えないとき）に、実装の工程が1回実行する。全件の失敗を直したら、直した後にもう1回実行させる。関係するテストだけの結果で提出させない。
- 記録では、全件を `coverage` の `full`、関係するテストだけを `partial`（`note` に選び方と実行したテスト）にさせる。記録の形は変えない。
- 最終レビューは、実装の工程の記録のテスト（`kind` が `test`）が関係するテストだけ（`partial`）で全件（`full`）が無ければ（`partialTestsOnly`）、実装の工程のテストの結果を使い回させず、テストのコマンドを実行させる（CI が全体を覆うと確かめられたときは、CI の結果を使い回してよい。PBI-305 のまま）。テストを記録していない記録（lint などテスト以外の検証だけ）と、最終レビューのテストのコマンドと同じコマンドを全体で実行した記録があるときは、関係するテストの記録が混ざっていても、今までどおり使い回させる。テストのコマンドがテスト以外の検証だけのこともあり、全件のテストが無いことだけで断ると、正しい使い回しまで断るため。
- CI の結果の前の最終レビュー（PBI-314）の記録に全件（またはテストのコマンドと同じコマンドの全体の結果）があれば、CI が落ちて最終レビューし直すときは、それを使い回してよい（`reusedFrom` に、その段を表す値が無いため、どちらかに全件があれば使い回しの申告を認める）。
- 実装の工程の記録のテストが関係するテストだけで、どちらの記録にも全件が無いのに、ゴールガーディアンが実装の工程から使い回した（`reusedFrom` が `self-review`）と申告したら、sacty は判定として記録せず、判定を読み取れなかったときと同じく、最終レビューを出し直させる（実装には戻さない）。
- 既定のスキル（`verification-run`・`self-review`・`review-dispatch`）にも、`self-review` のテストは回ごとには関係するものだけでよく、全件は修正を終えた後に1回、と書く（`scope` が `all` で、実行するテストがあるときだけ）。`pr-review` は今までどおり全件（使い回せる分を除く）。

## 理由

比べた案：

- 案A（採用）：全件は実装の工程の最後に1回。最終レビューは、その記録を使い回す。記録が無い・`partial` だけなら、最終レビューが全件を実行する。
  全件の失敗を実装の工程の中で直せるので、最終レビューの不合格（実装と検証をまるごとやり直す）が増えない。PBI-305 の使い回しと PBI-315（不合格を提出の前に防ぐ）の向きに合う。
- 案B：実装の工程は関係するテストだけにし、全件はいつも最終レビューで実行する。
  指示は短くなるが、関係するテストでは見つからない失敗が、最終レビューの不合格として返ってくる。実装のやり直しの費用が、省いた全件の時間より大きくなりうる。PBI-305 の使い回しの意味も薄れる。
- 案C：sacty の指示だけに書き、既定のスキルは変えない（またはその逆）。
  文面は少ないが、スキルの `verification-run` が回ごとに全部を実行させるので、指示と食い違う。エージェントがスキルに従えば、途中も全件が走り、効果が出ない。スキルだけに書くと、sacty の「提出の前の検証」から全件を1回実行することが読み取れない。

sacty の側の確かめ（記録に全件が無ければ使い回させない・申告を認めない）を足したのは、関係するテストの記録が増えると、指示だけでは全件を飛ばす経路が残るため。
申告を認めないときに不合格にしないのは、ゴールガーディアンの申告の誤りで、実装の誤りではないため。

実際のエージェントで、実装の工程の時間や最終レビューの不合格の数がどう変わるかは確かめていない（費用がかかるので、人の判断で評価する）。

## 影響

- 実装の工程のテストの実行は、回ごとの全件から、回ごとの関係するテストと最後の1回の全件になる。
- 関係するテストの選び方は、エージェントの判断に任せる。選び方の誤りで落ちるテストは、最後の全件で見つかる。
- エージェントが関係するテストだけの結果を `full` と申告すると、sacty は見分けられない（記録は申告のため）。
