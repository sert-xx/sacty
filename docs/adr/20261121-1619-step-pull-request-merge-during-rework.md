# 要求要件・設計の自動の直しの間の PR のマージを承認にし、直しを捨てる

- 日時: 2026-11-21 16:19 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-462
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件・設計の PR は、人のマージを承認にしている（[人が PR の中で直してからマージしても承認・完了として進める](20261013-1425-accept-human-edited-merge.md)）。
ただし、承認待ちから自動の直し（差し戻し・PR の指摘や提案の取り込み）に入った後は、PR を見守っていなかった。
直しの間に人が PR をマージすると、sacty は直しを続け、マージ済みの PR を見て新しいブランチ・PR を作り、人にもう一度承認を求めていた。
人がマージの前に PR の中で直した箇所は、直しの版の新しい PR で黙って元に戻りうる。

実装の PR では、作り直しの間のマージを承認として扱っている（PBI-276）。
要求要件・設計の PR にも、同じ扱いが要るかを決める必要があった。

## 決定

- 要求要件・設計の自動の直しの間（実行待ち・実行中・待機・一時停止）に、人が直しを始めたときの承認待ちの PR をマージしたら、マージを承認として扱う。
  - 実行は止め、直しの結果は使わず、新しいブランチ・PR は作らない。
  - 承認する成果とテスト観点は、承認待ちだった提出の版にする。人が PR の中で直してからマージしたなら、人の版を承認済みにする。
  - PR に、マージを承認として扱ったこと・直しを取り込まなかったこと・捨てた提案の件数を、1回だけ知らせる。実装の PR の作り直しをマージで止めたときも、同じ知らせを書く。
- 設計の PR の指摘で要求要件へ戻している間に、人が元の設計の PR をマージしても、承認にしない。PR に、設計の承認として扱っていないこと・要求要件の承認の後に設計の PR を作り直すことを、1回だけ知らせる。
- 保存するイベントの形を変える。`ReworkStoppedByMerge` に `step`（工程）を足し、工程の直しの停止にも使う。この記録を一度保存したら、前の版のデーモンには戻せない。

## 理由

- 人のマージを承認にする決まりに、直しの間もそろえる。人がマージした時点で、人はその版を承認したと読める。
- 直しの版で新しい PR を作ると、人がマージの前に直した箇所が、直しの版で黙って戻る。マージの時点の版を承認にすれば、人の直しが残る。
- 要求要件へ戻している間の設計の PR は、要求要件の直しの最中に出ていたものなので、設計の承認にしない。人はマージで承認したつもりでいるので、黙って作り直さず、PR に知らせる（人間の指摘 design-3-1）。作業履歴に記録しない理由は、記録に無い。
- `ReworkStoppedByMerge` に `step` を足したのは、実装の作り直しの停止と、止め方・記録・画面の扱いをそろえるため。別の名前のイベントと比べた記録は無い。

検討した別案と、採らなかった理由：

- 直しを待ってから、直しの版で新しい PR を作り、承認待ちにする（この決定の前の動き）。人のマージを承認として扱わず、人にもう一度承認を求める。人がマージの前に直した箇所が直しの版で戻り、人がそれに気づけないので採らなかった。

## 影響

- `step` 付きの `ReworkStoppedByMerge` を記録した後は、前の版のデーモンは作業履歴を投影できず（実装の記録として読み、整合性のエラーになる）、起動できない。作業履歴は追記だけで、手では直せない。運用者は、更新の前のバックアップで戻す。
- この版へ入れ替えた時点で、マージ済みの PR の上で直しが走っていたタスクも、入れ替えの後の最初の見守りが同じ扱いにする。
- 承認にしなかった設計の PR のマージは、作業履歴に残らず、PR の知らせの目印だけで1回にしている。
- 仕様は [承認と差し戻し](../spec/approval.md#工程の-pr-の直しの間のマージ) にある。
