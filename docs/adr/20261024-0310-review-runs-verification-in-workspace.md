# PR のレビューの工程が、作業領域で依存関係を取得して検証を実行する

- 日時: 2026-10-24 03:10 UTC
- ステータス: 採用
- 関係する PR・タスク: #212、PBI-153
- 置き換え元: なし
- 置き換え先: なし

## 背景

PR のレビューのタスクで、レビューの工程が「作業領域に node_modules が無いので、typegen・tsc・vitest は手元で流していません。結果は CI と作者の報告によります」と報告した。

既定のスキル `review-dispatch` の手順（`verification-run`）は、観点の担当を起動する前に、依存関係をロックファイルどおりに入れて検証を実行するよう定めている。
セッションのログで確かめたところ、次のとおりだった。

- 1回目のレビューは、手順の `pr-review` は読んだが、参照先の `verification-run` は開かなかった。作業領域に依存関係が無いのを見ただけで検証を見送り、担当には「ローカルでは実行していない」と渡した。
- 再レビューは、スキルを使わずに、差分と CI の結果だけを読んで終えた。
- sacty のレビューの指示には「コードは変更しない」だけがあった。調査の工程やゴールガーディアンの指示にある「依存関係の取得やテストは実行してかまわない」は無く、オーケストレーターが決めたテストのコマンドも渡していなかった。

同じイメージを使う調査の工程では、依存関係の取得もテストの実行もできていたので、環境ではなく指示の問題だった。

## 決定

- レビューの工程の指示（初回・再レビュー）に、次を書く。
  - 作業領域で、依存関係をロックファイルどおりに取得し、検証のコマンドを実行してよい（変更は残らない）。検証は、スキルの手順（`verification-run`）で、観点の担当を起動する前に実行する。
  - 作業領域は PR のコードだけの写しで、依存関係やビルドの成果物は無い。それを理由に検証を見送らない。CI の結果や作者の報告を、自分で実行した結果の代わりにしない。
  - オーケストレーターが決めたテストのコマンドがあれば、検証のコマンドの候補として示す。リポジトリの手順・CI の設定と照らして使わせる。
  - 実行できなかった検証は、コマンドと止まった理由を本文に書く。
- 再レビューの指示に、スキルの再レビューの手順でレビューし、今回のコードで検証を実行し直すことを書く。
- 指示は、特定の言語やパッケージマネージャを書かない。

## 理由

- スキルにはすでに手順があり、エージェントがそこまで読まなかったことと、sacty の指示が実行してよいことを伝えていなかったことが原因だった。指示で手順と許可をはっきりさせるのが、いちばん小さな直し方になる。
- sacty がレビューの前にテストのコマンドを実行して結果を渡す案は採らなかった（ステークホルダーの判断）。変更が大きく、レビューの時間も延びるため。
- オーケストレーターのテストのコマンドは、ベースブランチから決めたものなので、PR が CI の設定を変えたときは合わない。そのため、候補として示し、リポジトリの手順と照らして使わせる。

## 影響

- レビューの工程で依存関係の取得と検証の実行が増え、時間と費用がかかる。
- 指示で求めるだけなので、強制はできない。エージェントが従わなければ、同じことは起こりうる。
- DB などのサービスが要る検証は、レビューの工程ではサービスを起動しないので、実行できなかったこととして本文に書かれる。
