# PR のレビューの工程が、作業領域で依存関係を取得して検証を実行する

- 日時: 2026-10-24 03:10 UTC
- ステータス: 採用
- 関係する PR・タスク: #212、PBI-153
- 置き換え元: なし
- 置き換え先: なし

## 背景

PR のレビューのタスクで、レビューの工程が「作業領域に node_modules が無いので、typegen・tsc・vitest は手元で流していません。結果は CI と作者の報告によります」と報告した。

既定のスキル `review-dispatch` の手順（`verification-run`）は、観点の担当を起動する前に、依存関係をロックファイルどおりに入れて検証を実行するよう定めている。
セッションのログで確かめたところ、次のとおりだった。

- 1回目のレビューは、手順の `pr-review` は読んだが、参照先の `verification-run` は開かなかった。作業領域に依存関係が無いのを見ただけで検証を見送り、担当には「ローカルでは実行していない」と渡した。
- 再レビューは、スキルを使わずに、差分と CI の結果だけを読んで終えた。
- sacty のレビューの指示には「コードは変更しない」だけがあった。調査の工程やゴールガーディアンの指示にある「依存関係の取得やテストは実行してかまわない」は無く、オーケストレーターが決めたテストのコマンドも渡していなかった（元のタスクは、PR の URL を本文に書いた通常のタスクで、オーケストレーターがテストのコマンドを決めていた）。

同じイメージを使う調査の工程では、依存関係の取得もテストの実行もできていたので、環境ではなく指示の問題だった。

## 決定

- レビューの工程の指示（初回・再レビュー）に、次を書く。
  - 作業領域で、依存関係をロックファイルどおりに取得し、検証のコマンドを実行してよい（変更は残らない）。対象のファイルは書き換えない（フォーマッターなどは確かめるだけのモードで実行する）。検証は、スキルの手順（`verification-run`）で、観点の担当を起動する前に実行する。
  - 作業領域は PR のコードだけの写しで、依存関係やビルドの成果物は無い。それを理由に検証を見送らない。CI の結果や作者の報告を、自分で実行した結果の代わりにしない。
  - オーケストレーターが決めたテストのコマンドがあれば、検証のコマンドの候補として示す。リポジトリの手順・CI の設定と照らして使わせる。
    PR の取り込みで作ったレビューだけのタスクは、オーケストレーターが工程を選ばないのでテストのコマンドが無く、候補は示さない（エージェントがリポジトリの手順と CI の設定から決める）。
  - 実行できなかった検証は、コマンドと止まった理由を本文に書く。
- 再レビューの指示に、再レビューでもスキル `review-dispatch` でレビューし、今回のコードで検証を実行し直すことを書く。
  スキルの再レビューの手順は前回以降の差分を求めるが、sacty は PR 全体の差分だけを渡すので、手順までは指定しない（読めなければ、スキルは初回として扱う）。
- テストを実行する役割（時間の上限に `test_minutes` を足す役割）に、`review` を加える。
- PR のコードがエージェントの認証情報のあるコンテナで動くことは、利用者向けの文書と仕様書に書いて受け入れる（ステークホルダーの判断）。
- 指示は、特定の言語やパッケージマネージャを書かない。

## 理由

- スキルにはすでに手順があり、エージェントがそこまで読まなかったことと、sacty の指示が実行してよいことを伝えていなかったことが原因だった。指示で手順と許可をはっきりさせるのが、いちばん小さな直し方になる。
- sacty がレビューの前にテストのコマンドを実行して結果を渡す案は採らなかった（ステークホルダーの判断）。変更が大きく、レビューの時間も延びるため。
- 検証を信頼できる PR（同じリポジトリのブランチ・作者がメンバーなど）だけに絞る案は採らなかった（ステークホルダーの判断）。
  どの PR をレビューさせるかは、人が取り込み（ラベル・レビューの依頼）やタスクの作成で決めている。また、スキルの手順にはもとから検証の実行があった。
- オーケストレーターのテストのコマンドは、ベースブランチから決めたものなので、PR が CI の設定を変えたときは合わない。そのため、候補として示し、リポジトリの手順と照らして使わせる。

## 影響

- レビューの工程で依存関係の取得と検証の実行が増え、時間と費用がかかる。時間の上限は、役割の上書きが無ければ `agent_minutes` + `test_minutes`（既定 50 分）になる。
- 検証では、PR のコード（依存関係のインストールのスクリプト・テスト）がエージェントのコンテナで動き、コンテナにあるエージェントの認証の値（`CLAUDE_CODE_OAUTH_TOKEN` など。codex の subscription では、実行の後にホストへ書き戻す `auth.json`）に触れられる。
  これまでも検証を実行したレビューでは同じだったが、見送らないよう指示するので、どのレビューでも起こる。
  codex の subscription では、書き換えた `auth.json` が中身を確かめずにホストへ書き戻され、残る。実行の間は、ゲートウェイを通して、プロジェクトの GitHub のアカウントでの読み取りと MCP の中継も使える。
  取り込みは、フォークや Bot の PR かどうかで絞らず、ラベルの自動の付与や CODEOWNERS などの自動の依頼では人が判断しないまま取り込まれうる。Bot の依存関係の更新の PR でも、新しい版のインストールのスクリプトが動く。
  フォークからの PR や作者を信頼できない PR を、取り込ませない・「レビューだけ」で選ばないよう、利用者向けの文書（`user/intake`・`user/tasks`）に書いた。
- 指示で求めるだけなので、強制はできない。エージェントが従わなければ、同じことは起こりうる。
- DB などのサービスが要る検証は、レビューの工程ではサービスを起動しないので、実行できなかったこととして本文に書かれる。
