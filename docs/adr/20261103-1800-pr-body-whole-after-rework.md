# 作り直しの後の PR の本文を PR 全体の説明にし、回をまたぐ「人が確かめること」を1件にまとめる

- 日時: 2026-11-03 18:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-299
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験 S5 r4（findings F44。F3 の再発）で、実装の PR が最終レビューの不合格と人の差し戻しで2回作り直された。最後の本文は、「結論」の変更・「変更」・「検証」・観点表のテスト（18 件から 3 件）が、最後の直し（Python の `Order` と共有の例の位置）だけを説明していた。スキーマ・API・ワーカー・Web に何を足したかの説明が消え、本文だけでは何の PR か分からなかった。
原因は2つあった。実装の説明も観点とテストの対応も、sacty は最新の提出のものだけを持ち、PR の本文はそれをそのまま載せる。直しの実行の指示は、説明を全体にするとも、直しを分けて書くとも言っていなかった。
また、[前の回の「人が確かめること」を引き継ぐ決まり](20261103-1100-carry-human-checks-across-final-reviews.md)（PBI-294）は、完全に同じ文しか重ねないので、回ごとに言い換えられた「この環境だけの結果」の注記が、5件中3件の実質重複になった。

## 決定

- 実装の提出ごとの出力を、`Task.implementHistory` に古い順に持つ（10 件まで）。あわせて、前の提出までの PR 全体の説明の土台を `Task.implementBase` に別に持つ（履歴が上限で古い提出を捨てても、土台は消えない）。上流の工程（要求要件・設計など）を承認し直したとき、承認済みの上流の成果物を変える申し出を適用したときは、どちらも空に戻す。
- 直しの実行（前の実装の説明を添える実行）の指示で、実装の説明を PR が加える変更の全体の説明にさせ、今回の直しだけを説明の最後の「## 最後の直し」の節に分けて書かせる。観点とテストの対応も PR 全体の対応にさせる。
- PR の本文は、説明を「最後の直し」の節とそれ以外に分け、それ以外を PR 全体の説明（結論の変更の要約・「変更」）、節を最後の直し（結論の1行と「最後の直し」の節）にする。節を書かずに最後の直しだけを書いた提出は、前の提出までで最後に全体の説明として書かれたもの（無ければ最初の提出）を全体の説明にし、その提出の説明全体を最後の直しにする。
- 観点とテストの対応は、直しの提出で、今回の申告に出てくる観点に限り、前の提出までのテストを残して足す（今回の申告に出てこない観点には足さない。テストなしの申告はそのまま使う）。
- 「人が確かめること」は、前の回の項目と同じ趣旨のとき、ゴールガーディアンに新しく書かせず、その項目を書き直した1件を `updatedHumanChecks`（「<番号>：<書き直した項目>」）に書かせ、sacty が前の項目を置き換える。同じ見出し「この環境だけの結果」の項目は、sacty が最後の1件にまとめる。全角半角・空白・大文字小文字・文末の句点だけが違う項目も1件にする。まとめたものは `FinalReviewed` の `mergedHumanChecks` に残す（書き方の違いだけの項目の1件化（`uniqueChecks`）では、文字列として同じ項目の重なりは、情報が減らないので残さない。同じ見出しの1件化は、前の回と今回に分かれていれば、同じ文でも残す）。

## 理由

- 本文が見るのは最新の提出だけなので、直しの説明が全体の説明を置き換える。説明を全体にさせる指示だけでは、守られなかったときに同じ失敗に戻る（実装の説明の報告を除く PBI-264 でも、指示だけでは消えなかった）。そのため、指示と、守られなかったときの機械的な代わり（前の提出の説明を土台にする）の両方を置く。この代わりは、説明を捨てず、必ず前の全体の説明を残す側に倒す。
- 観点とテストの対応も、最新の申告だけを持つため、直しに触れたテストだけになる（18 件が 3 件）。指示に加えて、前の提出までのテストを残す。
- 「人が確かめること」の重なりは、文の類似度で機械的に判定すると、似た別の項目（同じ書式の確認項目・版の番号だけが違う項目）を同じとして落としうる。PBI-294 の「根拠なしに落とさない」を守るため、同じ趣旨かの判断はゴールガーディアンに書き直しとして明示させ、sacty は番号のつく申告と、固定の見出し、書き方だけの違いのような確実なものだけをまとめる。
- 比べた案：
  - 提出のたびに、エージェントに PR の本文を書き直させる案は、費用・時間・出力の揺れが増えるので採らなかった（[PR の本文の規則を決まった形にした ADR](20261014-1517-pr-body-follows-repository-template.md) と同じ考え方）。
  - 文字の類似度で「人が確かめること」を重ねる案は、上のとおり別の項目を落としうるので採らなかった。

## 影響

- 作り直しの後の実装の PR の本文に、「最後の直し」の節と結論の1行が増える。作り直しが無いタスク、既存の PR を引き継いだタスク（本文を変えない）は変わらない。
- 前の回の項目を書き直しても、元の趣旨を保つかは sacty は確かめない（元の文は `mergedHumanChecks` に残る）。PBI-294 の、外す理由の真偽を確かめない制限と同じ。
- テストの対応は、削除・改名したテストの前の名前が残りうる（今回の申告に出てくる観点にだけ足すので、観点ごとの数は増える一方になりうる）。
- 実装の説明を節に分けて書かない提出が続くと、全体の説明は最初の提出（または最後に全体を書いた提出）のままになる。途中の直しの説明は本文に出ない。
