# PR のリスク評価を出す（レビューの省略・自動のマージには使わない）

- 日時: 2026-11-16 16:32 UTC
- ステータス: 採用
- 関係する PR・タスク: #391、PBI-362
- 置き換え元: なし
- 置き換え先: なし

## 背景

AI が書く変更が増えると、人が PR をレビューする時間が足りなくなる。
すべての PR を同じ深さで読むのではなく、変更のリスクに合わせてレビューの深さを変えたい、という要望があった。
手本にしたのは、Meta が公開している RADAR（Risk Aware Diff Auto Review）と Diff Risk Score の考え方。

公開されている一次情報から読み取れたことは、次のとおり。

- RADAR は、リスクの低い変更のレビューとランドを自動にし、リスクの高い変更を人のレビューへ回す、段になった絞り込み（[arXiv:2605.30208](https://arxiv.org/abs/2605.30208)）。
  段は、作者の分類、資格の確認（決定的な規則）、Diff Risk Score、LLM によるレビュー、決定的な検証。
- LLM によるレビューは、変更を「安全の合図」（振る舞いを変えないリファクタリング・使われていないコードの削除・文書やコメントの更新・テストの追加など）と
  「リスクの合図」（レビューの手間が大きい・大きな構造の変更・見つかった不具合・性能のリスク・セキュリティの脆弱性）に分類する。
  リスクの合図が1つでもあれば、自動の受け入れから外す。
- Diff Risk Score は、変更が本番の障害を起こす見込みを予測するモデル（[Meta のブログ](https://engineering.fb.com/2025/08/06/developer-tools/diff-risk-score-drs-ai-risk-aware-software-development-meta/)、[arXiv:2410.06351](https://arxiv.org/abs/2410.06351)）。
  入力は、変更の題・テスト計画・ファイル名と差分。回帰の版は、変更の大きさ・広がり・過去の障害・作者の実績なども使う。
- RADAR の出力は「自動で通す」か「人へ回す」の2つ。人のレビューへ回したときに、レビューする人へリスクの段階や理由を見せるか、
  人に勧めるレビューの深さを段階で示すかは、読んだ範囲では確かめられなかった。

sacty には、障害の実績から学習したモデルも、作者やファイルの過去の実績の記録も無い。
また、最初から評価によって自動化の度合いを変えるのは、評価がどれだけ当たるか分からないうちは危うい。

## 決定

- PR のリスク評価を「出す」ことだけを入れる。評価によって、レビューを省く・自動でマージする・工程を変える・レビューの観点を増減することはしない。
- 評価する場面は2つ。
  - sacty が実装の PR を作る・更新する前。オーケストレーターのエージェントに、実装後のコードと差分を読ませ、PR の説明に載せる。
  - GitHub の PR から取り込んだレビューのタスクの、レビューの工程。レビューの答えと一緒に出させ、投稿するレビューのコメントに載せる。
- sacty が自分の PR のために作ったレビューの子タスクのコメントには、載せない。
- 段階は、低・中・高の3つ。段階ごとに、人に勧めるレビューの深さを、sacty が決まった文で出す。
  - 高：リスクの合図（セキュリティ・取り消しにくい変更・互換性の変更・構造や広い範囲の変更・性能や並行処理・不具合の疑い・大きな差分・確かめていない振る舞い）に1つでも当たる。設計と影響から確かめる。
  - 低：合図に当たらず、すべての変更が安全な種類に入る。流し読みでよい。
  - 中：その間。変えた振る舞いの箇所を読む。
- 合図が1つでもあれば、エージェントが付けた段階に関わらず、sacty が高にする。
- 重要な制約として、RADAR に関するスキルやコンテキストがその実行に読み込まれているときは、その内容を、上の基準より優先させる（人の指示。2026-11-17）。
  答えの形（段階の3つの値・合図の名前・項目）は、sacty が読むので変えさせない。
- 評価は、段階のほかに、根拠（変更の種類・影響の範囲・取り消しやすさ・確かめた範囲）と、とくに見る箇所を持つ。
- 点数（数値）は出さない。
- 評価できなかったとき（予算の上限・実行の失敗・答えを読めない）は、PR の作成・レビューの投稿を止めず、評価できなかったことと理由を載せる。
- 評価の結果は、作業履歴（`PullRequestRiskAssessed`）に残し、画面のタスクの詳細に出す。

## 理由

- 人が読んで、レビューの深さを決められる形にするため。段階だけでは何を見ればよいか分からないので、根拠と、とくに見る箇所を添える。
- 段階の決め方を、RADAR の LLM によるレビューと同じ形（リスクの合図が1つでもあれば高い側に倒す）にしたのは、基準を表に書けて、人が評価の理由を追えるため。
  合図の種類は、RADAR のリスクの合図に、Diff Risk Score の入力の観点（変更の大きさ・広がり・テスト計画）と、取り消しやすさ・互換性を足した。
- 読み込まれた RADAR のスキル・コンテキストを優先させるのは、プロジェクトやリポジトリが自分たちのリスクの見方を持っているとき、sacty の既定の基準より、その決まりのほうが実情に合うため。
  評価の対象（PR の説明・差分など）に書かれた記述まで優先させると、PR を書いた側が評価を下げられるので、読み込まれたものに限る。
- 勧める深さを sacty の決まった文にしたのは、同じ段階なら同じ深さを勧めるため（エージェントに書かせると、回ごとに言い方が変わる）。
- 点数を出さないのは、障害の実績から学習したモデルが無く、数値が根拠の無い精度を装うことになるため。
- PR を作る前の評価を、実装のエージェントではなくオーケストレーターの別の実行にしたのは、書いた本人の自己評価にしないため。
- レビューのタスクでは、レビューの工程のエージェントに一緒に出させる。差分とコードをすでに読んでいるので、別の実行を足さずに済む。
- レビューの子タスクのコメントに載せないのは、その PR の説明に、PR を作る前の評価がすでに載っているため。載せるかどうかは、依頼の範囲に入っていない。
- 評価の失敗で止めないのは、評価が補助の情報で、成果物ではないため。

## 影響

- 実装の PR を作る・更新するたびに、オーケストレーターの実行が1回増える（同じコミットは評価し直さない）。費用は、タスクの予算に入る。
- PR の説明に「リスク評価」の節が増える。人が直した PR の本文との3方向のマージは、今までどおり働く。
- 評価は AI の読みによる目安で、当たるかどうかは確かめていない。評価が当たっていたかを、差し戻しやリバートの実績と突き合わせる仕組みは無い。
- 評価によってレビューの深さ・自動化の度合いを変えることと、レビューの子タスクのコメントへの記載は、今回は入れていない。
