# 工程の成果物を人間の承認ゲートで止め、差し戻しの指摘を累積してエージェントに渡し、上限を超えたらエスカレーションにする

- 日時: 2026-10-10 07:32 UTC
- ステータス: 採用
- 関係する PR・タスク: #3、PBI-7
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件の工程の成果物を、人間が確かめてから次の工程（設計）へ進める仕組みが必要だった。差し戻したときに、指摘を
エージェントへ確実に伝え、同じ工程で差し戻しが続くときの扱いも決める必要があった。

## 決定

- 要求要件の工程の後に、人間の承認ゲートを置く。承認待ちは `StepSubmitted` として台帳に明示的に記録する。
- 成果物チェックの画面（`/tasks/[id]/review`）で、承認と差し戻しをする。差し戻しには指摘が1件以上必要（1行に1件）。
- 承認・差し戻しの入力には、画面が表示していた提出回（submission）を必須にし、現在のゲートと一致しなければ 409 で拒否する。
- 指摘はタスクごとに累積して台帳に記録し、再提出のたびに、有効な指摘の全件と前回の下書きをエージェントに渡す。
- エージェントには、指摘ごとの対応を決まった形式（JSON のブロック）で返させ、本文からは取り除いて画面に表示する。知らない指摘の ID は無視する。
  再提出のたびに、その工程の有効な指摘の対応をいったん未回答に戻し、今回回答されたものだけを入れて、回答した提出回も記録する。
- 前提が変わった指摘は人間が無効にでき、以降はエージェントに渡さない。
- 同じ工程への差し戻しが上限（3回）を超えるとエスカレーションにし、人間が承認するか、上限を超えて差し戻すかを選ぶ。
- 承認・差し戻し・指摘の無効化・エスカレーションは、すべて台帳に記録する。
- 承認待ちのあいだは予算の超過で止めない。予算は次の実行の前に判定する。
- タスクの一覧の「あなたの出番」に、承認待ち・エスカレーション・一時停止のタスクを出す。

## 理由

- 承認待ちを `StepSubmitted` で明示的に記録するのは、ゲートの有無をコードの定数だけで決めると、将来その定数を変えたときに
  過去の台帳の復元の結果まで変わってしまうため（PR の本文）。
- 承認待ちのあいだに予算で止めないのは、すでに人間の判断で止まっているため（PR の本文）。
- 提出回の照合を必須にしたのは、古い成果物を開いたままのタブから、未確認の新しい成果物を承認できてしまったため（レビューの指摘）。
- 回答の無い指摘を未回答に戻すのは、前回の対応の文が残り、最新の成果物への対応と誤って承認するおそれがあったため（レビューの指摘）。
- 上限を 3 回にした理由は、記録に無い。

## 影響

- 承認すると次の工程（設計）が実行の対象になる。設計は PBI-8 で実装するので、この時点では待機する。
- 指摘ごとの「再発なし」の判定は、PBI-10（ゴールガーディアンの最終レビュー）に回した。
- PBI-2 のときに作ったタスク（要求要件を実行済みで待機中）は、承認ゲートの導入前の台帳なので、承認待ちにはならない。
- 指摘を入力したまま「承認する」を押すと、入力した指摘は確認なしに捨てられる。
