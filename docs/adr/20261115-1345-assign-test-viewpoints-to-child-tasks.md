# 分割の子タスクに、親の設計のテスト観点を割り当て、観点の対応が欠けた実装を提出にしない

- 日時: 2026-11-15 13:45 UTC
- ステータス: 採用
- 関係する PR・タスク: #380、PBI-348
- 置き換え元: なし
- 置き換え先: なし

## 背景

2026-11-15、タスク分割の子タスクの実装が、範囲の一部だけを実装して終わった。
仕組みの側の欠陥（未完了の実装がそのまま提出になる・変更の無いやり直しで行き止まりになる）は、[終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない](20261115-1224-stop-incomplete-implementation-and-unchanged-rework.md) で直した。

指示の側にも、2つの欠陥があった。

1. 子タスクに、完了の基準が渡っていなかった。
   設計のテスト観点（TV-n）は、設計の本文と別に記録している。
   分割の指示にも、子タスクの内容にも、設計の本文だけを渡していたので、テスト観点は分割のエージェントにも子タスクにも届かなかった。
   子タスクは、親の要求要件・設計が承認済みなので、ほぼ必ず、要求要件・設計を省いた実装になる。
   その指示の観点は「REQ：タスクの目的を満たす」の1つだけで、テストを1件対応させれば、「すべての観点にテストを対応させる」を形の上で満たせた。
2. 要求要件・設計を省いた実装の指示が、子タスクに合っていなかった。
   冒頭の文が「依頼が明確で、既存の仕組みに沿った変更のため」に固定で、範囲の広い子タスクにも、小さい変更として伝わった。
   範囲を実装し終えてから検証と報告に進む順序も、書いていなかった。
   今回の実行は、最初の小さな差分に、全件のテストとビルドまで実行して、報告を書いて終わった。

人が決めたこと（2026-11-15）：この2つを、仕組みの修正（PBI-347）の後に、1つの PR で直す。

## 決定

- タスク分割は、親の承認済みの設計のテスト観点を、子タスクに割り当てる。
  - 分割の指示に、テスト観点を添える。答えの子タスクごとに、その子タスクが満たす観点の ID を書かせる。
  - 子タスクでは確かめられない観点は、割り当てずに、統合レビューで確かめる観点として、理由と一緒に挙げさせる。
  - どの子タスクにも統合レビューにも入っていない観点・設計に無い ID・理由の無い統合レビューの観点があれば、子タスクを作らずに止める。
  - 割り当てた観点は、中身ごと、分割の記録と子タスクに残す。
  - 統合レビューの指示に、どの子タスクにも割り当てなかった観点と理由を添える（統合レビューは、もともとすべてのテスト観点を判定する）。
- 子タスクの実装は、割り当てられた観点のすべてにテストを対応させる。
  設計の工程がある子タスクは自分の設計のテスト観点を、再現の工程がある子タスクは再現のテストを、今までどおり観点にする（割り当てられた観点は使わない）。
- 実装の、観点とテストの対応に欠けた観点があれば、完了と申告していても、提出しない。
  欠けた観点を渡して実装をやり直し、続けて欠ければ一時停止する（未完了のときと同じ扱い）。
  - 観点は、承認済みの設計のテスト観点か、割り当てられた観点。子タスクに限らない。
    実装の指示が並べる観点と同じ決め方にして、指示に無い観点の対応は求めない。
  - テストの仕組みが無いタスクと、文書だけの依頼は、テストを書かないので除く。
  - 観点が「REQ」だけのタスクと、再現の工程があるタスクは、確かめない。
  - 変更が要らないとわかった実行も、同じ確認を通る（既存のテストを観点に対応させてから、変更なしの確認に進む）。
- 子タスクの、要求要件・設計を省いた実装の指示は、小さい変更という前提の文の代わりに、次のことを伝える。
  - 親タスクの分割で作った子タスクで、要求要件・設計は親タスクで承認済みであること
  - 小さな変更とは限らないこと
  - 範囲は、タスクの内容の、見出し「親タスクの要求要件（承認済み）」より前に書かれたことのすべてであること（その見出しから後ろは、sacty が親タスクから添えたもの）
- どの実装の指示にも、範囲のすべてを実装してから、提出の前の検証と実装の説明に進む順序を書く。
- 次の子タスクは、タスクの目的（REQ）を観点にして進む。
  - 親の設計にテスト観点が無い分割の子タスク
  - 統合レビューの後に追加する、修正の子タスク
  - この決定の前に作った子タスク

## 理由

- テスト観点は、人が設計の承認で認めた、受け入れの確かめ方である。
  子タスクに渡せば、子タスクの実装の完了の基準になり、子タスクごとに書き直す必要が無い。
- 割り当てを分割のエージェントに決めさせるのは、どの観点がどの子タスクの範囲に入るかは、分け方を決めたエージェントが分かっているためである。
  子タスクの側で、親の観点の全体から自分の分を選ばせる案は採らなかった。子タスクごとに選び方がずれて、どの子タスクも拾わない観点が出るおそれがある。
- すべての観点を、子タスクか統合レビューに入れさせるのは、分割で観点が抜け落ちるのを防ぐためである。
  統合レビューで確かめる観点に理由を求めるのは、割り当てを考えずに、すべてを統合レビューに回す答えを減らすためである。
- 観点の対応の欠けを sacty が確かめるのは、指示だけでは守られないことがあるためである（今回の実行は、テストを1件だけ対応させて終わった）。
  観点とテストの対応は、すでに実装の報告にあり、欠けは機械的に分かる。
  以前の版のテストの実行の記録（`TestsRun`）は、テストが対応していない観点を持ち、やり直しの指示に渡していた。sacty がテストを実行しなくなった後は、対応の欠けを確かめる所が無かった。
- 子タスクに限らず確かめるのは、「すべての観点にテストを対応させる」を、設計のあるタスクの実装の指示も求めているためである。
  子タスクだけに確かめると、同じ指示の守られ方が、タスクの形で変わる。
- 進める順序を書くのは、最初の小さな差分に検証と報告まで済ませて終える進み方を、指示で防ぐためである。
  指示で防げなかったときは、完了の申告と、観点の対応の確認で止まる。

## 影響

- 設計にテスト観点のあるタスクの分割では、分割の答えに、観点の割り当てが要る。割り当ての無い答えは、子タスクを作らずに止まる。
- 子タスクの実装の PR の本文の観点の表と、PR のレビューの子タスクに渡す観点は、割り当てられた観点になる。
- 設計のあるタスク（子タスクに限らない）で、観点とテストの対応に欠けがある実装は、PR にならずに、やり直しになる。
- 画面：親タスクの「子タスク」に、子タスクごとの観点の ID と、統合レビューで確かめる観点が出る。子タスクの詳細に「割り当てられたテスト観点」が出る。
- 子タスクの大きさの目安・子タスクが選ぶ工程の組み合わせ・実装のエージェントの選び方は、この決定に含めていない（人がまだ決めていない）。
