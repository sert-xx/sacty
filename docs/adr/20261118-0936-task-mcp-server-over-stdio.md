# 起動中の sacty を操作する MCP サーバーは、CLI が stdio で動かし、MCP の 2026-07-28 版に合わせる

- 日時: 2026-11-18 09:36 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-392
- 置き換え元: なし
- 置き換え先: なし

## 背景

PR を直した後の再レビューは、ブラウザで sacty の画面を開き、タスクの詳細の「再レビューして PR に投稿」を押して始めていた。
PR を直しているのは手元の AI（Claude Code・Codex）なので、その AI から、起動中の sacty を MCP で操作できるようにしたい。
最初に要るのは、PR やブランチ名からレビューのタスクを特定して、再レビューにすること。
タスクの作成や、オーケストレーターを MCP の呼び出し側で置き換えることは、将来の案として挙がっている（今回は作らない）。

決めることは、つなぎ方（stdio か HTTP か）、認証、合わせる MCP の仕様の版、ツールの範囲、絞り込みをどこでするか、ブランチ名からレビューのタスクを探す方法。

決める前に、公式の仕様（modelcontextprotocol.io）と、Claude Code・Codex の公式の文書で、次を確かめた（2026-11-18）。

- MCP の最新の版は 2026-07-28。`initialize` の握手とセッションを廃止し、要求ごとに版と機能を持つ形になった。`server/discover` が必須。
  前の版（2025-11-25 まで）のクライアントを受けるかは、サーバーが選べる。
- stdio：標準出力には MCP のメッセージだけを書く。標準入力が閉じたら終わる。認証の仕様（OAuth 2.1）は HTTP のためのもので、stdio では従わず、資格情報は環境から取る。
- Streamable HTTP：`Origin` の検証は必須。ローカルでは 127.0.0.1 だけに束縛すること・認証は推奨。
- ツール：結果の形（`outputSchema`）を出し、構造のある結果（`structuredContent`）と同じ JSON の文を返すことが推奨。
  引数の誤り・業務の誤りは、ツールの実行のエラー（`isError`）で返す（AI が読んで直せるように）。
- Claude Code・Codex は、どちらも stdio と HTTP（固定のヘッダー・OAuth）の MCP サーバーを登録できる。
- デーモンがすでに使っている公式の SDK の v1（`@modelcontextprotocol/sdk`）は 2025-11-25 まで。v2（`@modelcontextprotocol/server`）が 2026-07-28 を実装し、前の版のクライアントも受ける。
- いまのデーモンの API は 127.0.0.1 だけで待ち受け、`sacty up` の起動のたびに作り直す Bearer トークンを求める。`Origin` は見ていない。

つなぎ方と認証・仕様の版は、案ごとに失うものを添えて、利用者に選んでもらった。

## 決定

- MCP サーバーは、CLI のコマンド `sacty mcp` が標準入出力（stdio）で動かす。デーモンには、MCP の入口も新しい API も足さない（利用者の選択）。
- MCP の仕様は 2026-07-28 に合わせ、`initialize` で始める前の版のクライアントも受ける。`sacty mcp` だけ、公式の SDK の v2 で作る。
  デーモンのほかの MCP（ゲートウェイの中継）は v1 のまま残し、移行は別のタスクにする（利用者の選択）。
- ツールは、引数の形と結果の形を出し、構造のある結果と同じ JSON の文を返す。失敗は、ツールの実行のエラーで返す。
- `sacty mcp` は、ツールが呼ばれるたびに `SACTY_HOME/daemon.json` を読み、画面と同じデーモンの API を呼ぶ。認証は足さない（利用者の選択）。
- ツールは、`list_tasks`（一覧と検索を1つに）・`get_task`・`rereview_task` の3つ。タスクの絞り込みと要約は、MCP サーバーの側でする。
- ツールの定義（名前・説明・引数・処理）は表（`TOOLS`）に持ち、デーモンの API の呼び出しは、インターフェース（`SactyApi`）で切り離す。
- 定義は `apps/daemon/src/task-mcp.ts` に置き、`@sacty/daemon/task-mcp` として CLI に公開する。API の呼び出しは `packages/cli/src/mcp.ts` に置く。
- レビューの対象を確かめたときに、PR の元のブランチの名前を記録する（`ReviewTargetResolved` の `headBranch`。省ける項目）。
  タスクは、再レビューを始めても消さない `reviewBranch` に持つ。
- `daemon.json` に、画面の URL（`web`）を足す（ツールの結果に、タスクの画面の URL を入れるため）。

## 理由

- stdio にした理由：
  - デーモンの API のトークンは、`sacty up` の起動のたびに作り直す。HTTP の MCP にすると、起動のたびに AI の CLI の設定のトークンを書き換えることになる。
    stdio なら、`sacty mcp` が呼び出しのたびに `daemon.json` を読むので、登録は一度で済み、sacty を起動し直しても使い続けられる。
  - 待ち受けるポートも、認証の入口も増えない。`daemon.json` は本人だけが読める（0600）ので、使えるのは `sacty up` を動かした本人だけになる。
    `sacty context preview`・`sacty launch` と同じ道（[CLI は、sacty up が書く接続先のファイルを通して、動いているデーモンの API を呼ぶ](20261014-0701-cli-daemon-connection-file.md)）。
  - Claude Code も Codex も、stdio の MCP サーバーを登録できる。
  - 仕様でも、stdio は認証の仕様の対象の外で、資格情報は環境から取る決まり。
  - 採らなかった案：
    - HTTP・認証なし：同じ PC のどのプロセスからでも再レビューを始められる。仕様の「認証は推奨」にも沿わない。
    - HTTP・固定のトークン：起動し直しても変わらないトークンの保存と配り方の仕組みが要る。仕様の標準（OAuth 2.1）ではない独自の認証になる。
    - HTTP・OAuth 2.1：認可サーバーの実装が要り、手元の1人が使うには大きすぎる。
- 2026-07-28 に合わせた理由：最新の標準に従うという要望。前の版のクライアントも受けるので、手元の CLI がどちらの版で話しても使える。
  既存の中継を同じ PR で v2 に移す案は、エージェントの実行に関わる所に手が入り、範囲が大きくなるので採らなかった。
  v1 のまま出す案は、最新の仕様に合わず、2026-07-28 だけを話すクライアントとつながらないので採らなかった。
- 一覧と検索を1つのツールにした理由：絞り込みの引数を持つ一覧で足りる。AI に渡すツールは、少ないほうが選びやすい。
- 絞り込みを MCP サーバーの側でする理由：デーモンの API を増やさずに済む。画面が3秒ごとに呼んでいる `GET /api/tasks` と同じ負荷で、手元の1人が使うには足りる。
  タスクが増えて重くなったら、デーモンに絞り込みの API を足して `SactyApi` の実装を差し替える（ツールの定義は変えない）。
- 定義をデーモンのパッケージに置いた理由：zod と MCP の依存は、デーモンのパッケージにまとまっている（v2 の SDK もそこに足した）。
  タスクの PR の読み方（`referencedPullRequest`）も、デーモンのパッケージにある。
- PR の元のブランチの名前を記録する理由：sacty の外で作った PR のレビューのタスクは、PR のリポジトリと番号しか持たず、ブランチ名から探せなかった。
  いちばんの使い道（手元の AI が、自分の作業しているブランチの PR の再レビューを頼む）で要る。
  MCP サーバーが GitHub に問い合わせて番号を調べる案は、`sacty mcp` に GitHub の認証を持たせることになるので、採らなかった。
- 将来の案（タスクの作成・オーケストレーターの置き換え）に備えて、ツールを表に足すだけで増やせる形にし、トランスポートと API の呼び出しを定義から切り離した。
  HTTP が要るようになったら、同じ定義を別のトランスポートに載せられる。

## 影響

- デーモンのパッケージの依存に `@modelcontextprotocol/server`（v2）が増え、v1 と並ぶ。テストのために、リポジトリの開発用の依存に `@modelcontextprotocol/client`（v2）が増える。
- 一覧（`list_tasks`）は、消したプロジェクトのタスクを出さない（詳細の API が無いものとして返すため）。
- `sacty mcp` を登録した AI は、利用者に代わって再レビューを始められる（費用がかかり、PR に投稿する）。
  毎回確かめるかどうかは、AI の CLI の権限の確認に任せる。ツールの注釈で、読み取りだけでないことを示す。
- タスクの説明・レビューの本文が、ツールの結果として AI に渡る。
- この版より前にレビューの対象を確かめたタスクは、次に確かめる（再レビューする）まで、ブランチ名では見つからない（PR の番号では見つかる）。
- `daemon.json` の `web` は、前の版の `sacty up` が書いたファイルには無い（そのときは、ツールの結果に画面の URL が入らない）。
- 仕様は [MCP サーバー](../spec/mcp-server.md)。
