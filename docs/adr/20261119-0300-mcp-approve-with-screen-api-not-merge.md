# sacty mcp の承認は、画面の「承認する」と同じ API に限り、PR のマージは入れない

- 日時: 2026-11-19 03:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-396
- 置き換え元: なし
- 置き換え先: なし

## 背景

`sacty mcp` は、成果物と実行の一覧を読めるようになった（[前の ADR](20261119-0200-mcp-read-deliverables-and-runs-by-byte-range.md)）。読んだ後に承認するには、画面を開く必要があった。
機能を1つずつ足す流れの3回目として、承認待ちの工程の承認を足す。
sacty の承認は2通りある（[承認](../spec/approval.md)）。画面での承認（PR を作らない工程）と、PR のマージでの承認（実装・PR のある要求要件・設計。画面の API は断る）。
決める必要があったのは、どこまでを MCP から承認できるようにするか、承認の対象と手段をどう確かめさせるか、結果を受け取れなかったときの扱い。

## 決定

- ツール `approve_step`（`task_id`・`step`・`submission`）を足す。デーモンの既存の `POST /api/tasks/:id/approve` に `{ step, submission }` を送るだけで、デーモンの承認の動き・記録・API は変えない。
  PR のマージで承認する工程・再現できなかった再現・承認待ちでない・古い回・二重の呼び出しは、API が断る理由をそのまま返す（古い回の「画面を更新して」だけは、MCP の層で、`get_task` で確かめ直す案内に置き換える）。
- **MCP から PR をマージしない。** PR のマージは GitHub への書き込みで、権限が大きい。入れるかどうかは、人がまだ決めていないので、承認の範囲に入れない。
  PR のマージで承認する工程では、承認せず、マージする PR の URL を返す。
- 承認する提出（工程と回）は、呼ぶ側が必ず指定する。いま承認待ちの工程・回と違えば、承認しない。
- 承認の前に確かめる手段として、タスクの要約に、承認待ちのときだけ `approval`（承認待ちの工程・提出の回・承認の手段）を足す。既存の欄は変えない。MCP の層が、タスクから作る（前の版のデーモンでも入る）。
- 先に `GET /api/tasks/:id` で、消したプロジェクトのタスクを無いものとして断る（承認の API は、プロジェクトを確かめないため。`rereview_task` と同じ）。
- 承認の API を呼んだ後に結果を受け取れなかったとき（時間切れ・切断・本文を読めない・5xx）は、承認されている可能性があること・自動でやり直さないこと・`get_task` で確かめてから呼び直すことを返す（`create_task` と同じ考え方）。
- 注釈は `readOnlyHint: false`・`destructiveHint: false`・`idempotentHint: false`・`openWorldHint: true`。

## 理由

- 画面と同じ API なら、記録も次の工程の始まり方も画面と同じで、MCP 専用の経路・記録が増えない。画面でできないことを、MCP でできるようにしない。
- PR のマージを入れると、GitHub への書き込みの権限が MCP に要る。人の決定を待つ。URL を返せば、利用者は GitHub で承認できる。
- 提出を指定させれば、古い成果物を見て頼んだ承認が、新しい提出に効くことを防げる。二重の呼び出しも、2回目は承認待ちでない（または回が違う）として断られ、記録は増えない。
- 結果を受け取れなかったときに、デーモンに冪等のキーを足せば、前の版のデーモンで通らなくなる。確かめてから呼び直す案内にとどめる。

## 影響

- 登録した AI は、利用者に頼まれたときに、画面と同じ承認ができる。承認すると次の工程が始まり、時間と費用がかかり、取り消せない。毎回確かめるかは、AI の CLI の権限の確認に任せる。
- 結果を受け取れなかったときに、承認されたかが分からない可能性が残る（確かめてから呼び直す）。
- PR のマージで承認する工程は、MCP からは進められない。後で入れるなら、別の決定として足す（この作りは、後から足せる）。
- 仕様は [MCP サーバー](../spec/mcp-server.md#approve_step)、利用者向けは [手元の AI から操作する](../user/mcp.md#承認する) に書く。
