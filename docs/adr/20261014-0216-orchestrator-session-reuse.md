# オーケストレーターのセッションをタスクごとに保存して再開し、チャットは保存したセッションの複製で答える

- 日時: 2026-10-14 02:16 UTC
- ステータス: 採用
- 関係する PR・タスク: #79、PBI-67
- 置き換え元: なし
- 置き換え先: なし

## 背景

オーケストレーター（工程の選択・チケットのトリアージ）とチャットは、実行のたびに新しいセッションで始めていた。#75 で、エージェントの元のセッションの
ファイル（伏せた後のもの）を実行ごとに写して記録するようになり、それを土台にセッションを使い回せるようになった。

## 決定

- `SACTY_HOME/sessions/<タスク>/orchestrator/` に、AI の種類・エージェントの ID・セッションの ID（`session.json`）と、実行ごとのセッションのファイル
  （`generations/<実行>/files/`。いまのものと1つ前だけ）を保存する。記録したハッシュと一致するものだけを写す。
- オーケストレーターの実行は、同じタスク・同じエージェントのセッションがあれば、ファイルを実行の設定の場所に戻して再開する（Claude Code：`--resume <ID>`、
  Codex：`codex exec … resume <ID> <指示>`）。指示はこれまでどおり台帳から作る。
- 次のときは新しく始めて理由を残し、タスクは止めない：初めて（`first`）・エージェントの ID か AI の種類が違う（`agent_changed`）・ファイルが無い・
  ハッシュが違う・記録が読めない（`files_broken`）・上限で省かれた（`truncated`）・AI が再開を受け付けなかった（`resume_failed`）。
- 再開を受け付けなかったとみなして始め直すのは、何も使わずに失敗し、かつ保存したセッションを戻せなかった（`run.sessionRestoreFailed`）か、AI ごとに
  本体にある再開を拒んだ文が出たときだけ。タイムアウト・コンテナの停止を確かめられない・途中で落ちた・利用上限・認証の失敗・人が止めた場合・使ってから
  失敗した場合は始め直さない。再開を指定したのに別のセッションの ID が出たときは、新規（`resume_failed`）として記録する。
- 同じタスクのオーケストレーターの実行は同時に1つだけ（並ぶ）。
- チャットは保存したセッションを複製して答え（Claude Code：`--fork-session`、Codex：複製が無いので実行ごとの使い捨ての場所で再開）、保存しない。
- ゴールガーディアン・工程のエージェントは変えない（毎回新しい）。
- 作業履歴に `OrchestratorSessionUsed`（mode：resumed / new / forked、セッション ID、再開元、理由、保存の結果）を記録し、タスク詳細に
  「オーケストレーターのセッション」カードを出す。
- エージェントの出力から読んだセッション ID は `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$` だけ受け付ける。
- 中止の片付けで、タスクのオーケストレーターのセッションを消す（#75 の実行ごとの写しは監査用に残す）。

## 理由

- セッション ID の形を限るのは、コンテナがコマンドの引数を差し込めないようにするため（PR の本文）。
- 始め直す条件を絞ったのは、使用量が分からないだけの一般のエラー（タイムアウト・停止の未確認など）を再開の拒否とみなすと、前のコンテナが残ったまま次の実行を
  始めたり、失敗を隠して工程を進めたりするというレビューの指摘（P1）への対応。拒否の文は、推し量って広く取らず、手元の本体（Claude Code 2.1.296・
  Codex 0.160.0）に入っている文字列から選んだ（返信）。
- Codex のチャットを使い捨ての場所で再開するのは、Codex に複製が無いため（PR の本文）。
- タスクごとに使い回すこと自体を選んだ理由（費用・文脈の引き継ぎなど）と、ほかの案との比較は記録に無い。

## 影響

- 2回目以降のオーケストレーターは、前の経緯を引き継いで動く。チャットは元のセッションに混ざらない。
- 再開に使うのは伏せた後のファイルで、Codex は `*.sqlite` を戻さず rollout と `history.jsonl` だけで再開する。
- 同じタスクのオーケストレーターは並ぶので、前の実行が終わるまで次が始まらない（ほかのタスク・工程のエージェントは待たない）。
