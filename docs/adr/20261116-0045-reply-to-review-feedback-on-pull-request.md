# 取り込んだ PR の指摘への対応を、指摘ごとに PR に返信する

- 日時: 2026-11-16 00:45 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-352
- 置き換え元: なし
- 置き換え先: なし

## 背景

2026-11-16、分割の子タスクの実装の PR で、PR のレビューの子タスクの指摘（レビューの本文 1 件・行へのコメント 5 件）を取り込み、実装をやり直した。

- 実装は、指摘ごとの対応（`sacty-responses`）を出力した。5 件は直し、1 件は、子タスクの範囲の外として断った。
- PR には、指摘への返信が 1 つも無かった。対応の内容は、PR の本文と、人に確かめてほしいことのコメントにしか出なかった。
  指摘した人・AI は、指摘の場所で、対応されたか・断られたかを読めなかった。
- PR のレビューの子タスクの再レビューには、「作者が『対象外』『後続で対応』と返した論点は、もう一度指摘しない」という決まりがある。
  作者の返答が空だったので、この決まりは効かず、断った指摘が、再レビューのたびに要修正として繰り返された。

調べて分かったことは次のとおり。

- 指摘ごとの対応には、対応したか・しなかったかの区別が無かった。
- 指摘の ID から、元の GitHub のコメントを辿る対応が、タスクに残っていなかった。
- 行へのコメントに返信する GitHub の呼び出しが無かった。

人が決めたこと（2026-11-16）：

- レビューを受けて修正したら、対象のレビューに返信する。対応したのか、理由があって却下したのかを書く。
- 行へのコメントには、そのコメントに返信する。それ以外のコメントには、PR のコメントとして返信する。
- 人が作った PR を引き継いで直すタスクの指摘にも、返信する（同じ日に尋ねて、今回に含めると決まった）。

## 決定

- PR のレビュー・コメントから取り込んだ指摘に、元のコメント（取り込みのキーと PR の番号）を持たせる。
- 工程のエージェントに、指摘への対応ごとに、対応した（`addressed`）か、理由があって対応しなかった（`declined`）かを申告させる。
  申告が無い・読めないときは、対応の文だけを返信する。
- 作り直した成果が承認待ちに戻ったとき（PR を更新した後）に、対応のある指摘ごとに、sacty がプロジェクトの gh のアカウントで返信する。
  - 行へのコメントの指摘：そのコメントへの返信。GitHub が、宛先を理由に返信を断ったら（元のコメントが消えた・返信への返信は受け付けない、など）、PR のコメント。権限の不足・レート制限では回さずに、失敗を残す。
  - レビューの本文・通常のコメントの指摘：元へのリンクを付けた PR のコメント。
- 1件の指摘には、1回だけ返信する。
- 返信の頭に目印（`<!-- sacty-reply:<タスク ID>:<指摘の ID>:<提出回> -->`）を置き、記録（`RemarkRepliesPosted`）と目印で、二重の投稿を防ぐ。
- 返信に失敗しても、タスクは止めない。失敗は作業履歴に残し、やり直さない。
- 返信は、ホストとアカウントごとに、1件ずつ、間隔をあけて投稿する。GitHub のレート制限に当たったら、そこで投稿を止め、残りの指摘の返信も、失敗として作業履歴に残す（やり直さない）。行への返信が制限で断られても、PR のコメントに回さない。
- 返信に使うアカウントを、投稿の前に記録する（`RemarkRepliesStarted`）。投稿済みの返信と見なすのは、記録したアカウントが投稿した、目印で始まる投稿だけ。PR の指摘の取り込みからも、記録したアカウントの返信を除く。投稿されたかが分からないとき（一覧を読めない・行への返信の答えを受け取れず、探し直しても見つからない）は、重ねて投稿せず、失敗を残す。
- PR のレビューの子タスクは、PR を読む前に、PR を作ったタスクの返信がまだなら、先に投稿する。
- sacty の返信は、PR の指摘として取り込まない。レビューの工程にだけ、作者の返答として渡す。
- セキュリティの組み合わせのタスクと、GitHub のアカウントを選んでいないプロジェクトでは、返信しない。
- 前の工程に戻した指摘（実装の PR の指摘を、設計で直したなど）は、その工程の対応を、元の PR を更新した提出で返信する。
- 引き継いだ PR（人が作った PR を直すタスク）の、実装に渡した指摘にも、同じように返信する。
  - 実装の工程の指示で、指摘ごとの ID（取り込みのキー）を渡し、対応した指摘と、対応しない・対応できない指摘について、指摘ごとの対応を出力させる。
  - 一度返信した指摘には、後の提出で繰り返し返信しない。作り直しの指示では、返信した指摘に印を付ける。

## 理由

- 返信を、工程のエージェントの頼み（`sacty-github-comments`）に任せず、sacty が投稿する：エージェントが頼みを書くかどうかに左右されず、指摘ごとに、元のコメントの場所へ確実に返せる。エージェントは GitHub に書き込めず、行へのコメントの ID も知らない。
- 承認（マージ）を待たずに返信する：承認の後では、PR を見ている人と、再レビューに届かない。承認を待つ提出で頼まれたコメントの投稿と同じ時点にした。
- 1件の指摘に 1回だけ返信する：工程のエージェントは、提出のたびに、その工程の有効な指摘すべてに対応を書く。提出のたびに返信すると、差し戻しを重ねた PR で、古い指摘への同じ返信が増え続ける。同じ論点がもう一度指摘されれば、それは新しいコメントなので、新しく返信する。
- 行への返信ができないときに PR のコメントへ回す：GitHub は、返信への返信と、消えたコメントへの返信を受け付けない。返信を諦めるより、どのコメントへの返信かをリンクで示して残すほうが、指摘した人に届く。
- 投稿されたかが分からないときに重ねない：重ねた投稿は消せず、指摘した人に同じ返信が2つ届く。失敗は作業履歴に出るので、人が PR に書ける。
- レビューの前に返信を投稿する：PR を作ったタスクとレビューの子タスクは並んで動く。返信を親の次の実行に任せると、子が先に PR を読み、対応しなかった理由が再レビューに渡らない。
- レート制限に当たった返信も、やり直さない：この PR のレビューの途中で、レート制限のときだけ間を置いてやり直す作りを入れた。やり直すには、GitHub が示す期限を守ること・同じアカウントのほかのタスクと待ちを合わせること・デーモンを起動し直しても期限を保つこと・制限が続くときに待ちを延ばして回数に上限を設けることが要り、アカウントごとの状態の置き場所から設計が要ると分かった。指摘への返信の範囲を超えるので、外して、ほかの失敗と同じ扱い（作業履歴に残し、人が PR に書ける）に戻した。投稿の間隔と、制限を宛先の拒否と区別して投稿を止めることは残した。やり直しは、別に扱う。
- 失敗をやり直さない：承認を待つ提出で頼まれたコメントの投稿と同じ扱いにした。権限が無いなど、待っても変わらない失敗で、承認待ちのタスクが実行待ちに残り続けないようにする。
- 再レビューには、既存の決まり（作者の返答）で渡す：sacty が作った PR の作者は、sacty のアカウントなので、返信を作者の返答として渡せば、新しい指示を足さずに、断った論点の繰り返しを止められる。
- 引き継いだ PR の指摘の ID に、取り込みのキーを使う：キーは、GitHub のコメントの種類と ID なので、実行をまたいで変わらず、返信先にそのまま使える。差し戻しの指摘（`Task.remarks`）にはしない（差し戻しの回数・戻し先の判断・承認の画面の指摘の扱いを変えないため）。
- 引き継いだ PR では、対応が要らないものに対応を書かせない：渡すデータには、作者の返答や済んだやり取りも入る。すべてに返信させると、返信の要らないコメントにも投稿が付く。
- 返信した指摘に印を付けて渡す：sacty の返信は、PR の指摘として渡さないので、エージェントは、どの指摘に返信が済んだかを、データから読めない。

## 影響

- 作業履歴に、`RemarkRepliesStarted`・`RemarkRepliesPosted` が増える。`ContinuedFeedbackPassed` に、指摘ごとの対応（`responses`。任意）が増える。`ChangesRequested` の指摘に `origin`、指摘への対応に `status` が増える（どちらも任意。以前の作業履歴はそのまま読める）。
- 以前の作業履歴の指摘（`origin` が無い）には、返信しない。
- 工程の指示の、指摘への対応の形に `status` が増える。引き継いだ PR の実装の指示の、PR の指摘のデータに `id`（と、返信した指摘の `answered`）が増える。
- sacty が作った PR では、差し戻しのたびに、対応のある新しい指摘の数だけ、sacty のアカウントの投稿が増える。
- PR のレビューの子タスクの再レビューで、作者の返答に sacty の返信が入る。
