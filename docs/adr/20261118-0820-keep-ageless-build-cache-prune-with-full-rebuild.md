# ビルドキャッシュの片付けの後はイメージを最初から作り直すと分かったうえで、期間の絞り込みの無い片付けを続ける

- 日時: 2026-11-18 08:20 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-391、#430
- 置き換え元: [ビルドキャッシュの片付けで、期間の絞り込みをやめ、使っていないものをすべて消す](20261117-2249-superseded-prune-build-cache-without-age-filter.md)（「影響」の、片付けの後に作り直すのは共有していない層だけ・共有している層は残る、という見込みを、実測で置き換えた。期間で絞らない決定はそのまま）、[エージェントのイメージのビルドで、引数を使う直前で宣言し、取得物を BuildKit の cache マウントに置く](20261112-1526-superseded-image-build-cache.md)（「結果」の、層のキャッシュが外れても取得物がマウントにあれば取り直さない、がビルドキャッシュの片付けの後にも成り立つという読み方を置き換えた。cache マウントを使う決定はそのまま）
- 置き換え先: なし

## 背景

PBI-389 の ADR で、ビルドキャッシュの片付けを、期間で絞らない `docker builder prune -f` にした（`sacty image build` の後と、デーモンの6時間ごとの片付け）。
そのときは、失うものを「片付けの後の最初のビルドでは、いまあるイメージと共有していない層を作り直す」、残るものを「いまあるイメージと共有している層」と書いた。
共有している層が残るので、同じ版のイメージの作り直しは速いまま、という見込みだった。

2026-11-18 の実測で、この見込みが誤りと分かった。
確かめた環境は、Rancher Desktop、Docker 29.5.3、buildx v0.35.0、BuildKit v0.30.0。ほかの版では確かめていない（未確認）。

| 試したこと | 結果 |
| --- | --- |
| `sacty image build default` を2回続ける（作った後に `docker builder prune -f` が走る） | 2回とも、キャッシュに当たった手順は 17 のうち 0。それぞれ約1.5分。イメージの ID は毎回変わった |
| 既定のイメージと同じ Dockerfile を、片付けを挟まずに2回作る | 2回目は 17 のうち 17 がキャッシュに当たった |
| 小さな Dockerfile で、2回作った後に `docker builder prune -f` を実行し、もう1回作る | キャッシュに当たった手順は 0。片付けで消えた量は 20kB だけだった |
| 期間つきの片付け（`--filter until=72h`・`until=168h`）の後に作る | すべての手順がキャッシュに当たった |
| 容量の上限つきの片付け（`--max-used-space 100GB`・`12GB`。キャッシュは 14.79GB、イメージと共有していない分は 3.1GB） | 何も消えず、17 のうち 17 がキャッシュに当たった |
| 容量の上限つきの片付け（`--max-used-space 2GB`） | 1.77GB が消え、次のビルドは 17 のうち 0 |

分かったこと：

- 期間で絞らない片付けの後は、いまあるイメージと共有している層の実体は残る（その分は、`docker system df` のビルドキャッシュの量から減らない。共有していない分は消える）。しかし、次のビルドは、その層をキャッシュとして使わない。
- `sacty image build` は、作り終えるたびに片付ける。そのため、続けて実行しても、毎回すべての手順を実行し直す。デーモンの片付け（6時間ごと）も同じ引数なので、その後の最初のビルドも同じになると見ている（デーモンの片付けの後のビルドは、試していない）。
- Dockerfile は、キャッシュに当たる作りになっている（片付けを挟まなければ、すべての手順が当たる）。
- cache マウント（[イメージの作成でパッケージの取得をキャッシュする決定](20261112-1526-superseded-image-build-cache.md)）の中身は、片付けで消える。小さな Dockerfile（`RUN --mount=type=cache` を持つもの）で、片付けの前後を比べた。
  - build-arg を変えて3回作ると、2回目からマウントの中身が残っていた（`docker buildx du --verbose` に、種類が `exec.cachemount` の記録が1件。同じ ID のまま、使用回数が増えた）。
  - `docker builder prune -f` の後は、`exec.cachemount` の記録が0件になり（`source.local` の2件も消えた）、次のビルドではマウントの中身が空だった。
  - sacty の Dockerfile のマウント（`sacty-build-cache`・`sacty-npm-cache`）そのものでは、前後を比べていない。片付けの後の状態で、`exec.cachemount` の記録が0件だった（88件すべてが `regular` で、イメージと共有）ことは見た。
  - `docker build --no-cache` で作ると、cache マウントも毎回新しくなった（ID が毎回変わり、中身は空）。sacty は `--no-cache` を付けない。

分からなかったこと：

- 層の実体が残るのに、キャッシュとして使われない理由（BuildKit のコードでは確かめていない）。
- 言語ごとのイメージ・コンテキストのイメージを最初から作り直す時間（計っていない）。

## 決定

- 期間で絞らない片付け（`docker builder prune -f`）を続ける。`sacty image build` の後と、デーモンの片付け（起動した後の最初と、その後は6時間に1回）の両方で、動きは変えない。
- 片付けの後・`sacty image build` のたびに、イメージを最初から作り直すことを受け入れる。
- 仕様書・ユーザードキュメント・コードのコメントの、「共有している層は残る」「作り直すのは共有していない層」と読める記述を、実測に合わせて直す。
- ユーザードキュメントの「OS のセキュリティの更新を入れる」は、「`image build` はビルドのキャッシュを使うので、作り直しただけではパッケージを取り直さないことがある」という前提をやめ、「作り直すと取り直す。ビルドのログに `CACHED` と出た手順があれば、キャッシュを消して作り直す」という手順にする。

## 理由

- 「このまま続ける」ことは、リポジトリの持ち主が、上の実測を見て決めた（2026-11-18 UTC）。ディスクの使用量を抑えることを優先し、作り直しの時間を受け入れる。
- 期間つきの片付けに戻す案は、採らなかった。キャッシュは壊さないが、PBI-389 の ADR の実測のとおり、古いキャッシュがほとんど消えない（消えたのは 2.6GB で、約 47GB が残った）。
- 容量の上限つきの片付け（`--max-used-space`）は、採らなかった。試した値は 100GB・12GB・2GB の3つ。100GB・12GB では何も消えず、2GB では直前のビルドのキャッシュまで当たらなくなった。試した値の中には、ディスクを空けることと、キャッシュを残すことを両立できるものが無かった。12GB と 2GB の間の値は試していない（未確認）。
- 片付けの回数を減らす案（`sacty image build` の後は片付けない、間隔を延ばすなど）は、比べていない。動きを変えないと決めたため。

## 影響

- 失うもの
  - `sacty image build` は、毎回、すべての手順を実行し直す。実測では、既定のイメージで約1.5分。言語ごとのイメージの時間は計っていない。
  - デーモンの片付けも同じ引数なので、その後に作るコンテキストのイメージも、最初から作り直すと見ている（デーモンの片付けの後のビルドは、試していない）。片付けを挟まずに作ったビルドは、前のビルドのキャッシュに当たる。
  - Dockerfile の手順の並べ方と cache マウント（[イメージの作成でパッケージの取得をキャッシュする決定](20261112-1526-superseded-image-build-cache.md)）が効くのは、片付けを挟まないビルドの間だけになる。cache マウントの中身も片付けで消えるので、その ADR の「層のキャッシュが外れても、取得物がマウントにあれば取り直さない」は、片付けの後には成り立たない（この読み方を置き換えた。cache マウントを使う決定・手順の並べ方の決定は、そのまま）。
  - 作り直すたびに、OS のパッケージは、その時点の版を取り直す。同じ版の sacty で作り直しても、イメージの中身（ID）が変わる。
- 得るもの：片付けのたびに、いまあるイメージと共有していない分のビルドキャッシュが消える。PBI-389 の ADR の実測では、32.58GB が消え、共有している 14.1GB が残った。2026-11-18 の実測の時点では、ビルドキャッシュ 14.79GB のうち、共有していない分は 3.1GB だった。
- PBI-389 の ADR の「影響」のうち、この ADR で置き換えたのは、「片付けの後の最初のビルドでは、いまあるイメージと共有していない層を作り直す」と「残るもの：いまあるイメージと共有している層は残った」の読み方。ほかの項目（sacty 以外のキャッシュも消えること・2分の上限・6時間の間隔・ホストの空き）は、そのまま。
- 2026-11-18 より前（期間つきの片付けの頃）に、既定のイメージが版ごとに最初から作り直されていた理由は、分かっていない。期間つきの片付けはキャッシュを壊さないので、この実測では説明がつかない。
- どの版の Docker・BuildKit でも同じ動きかは、確かめていない（未確認）。
