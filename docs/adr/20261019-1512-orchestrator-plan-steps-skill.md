# オーケストレーターにもコンテキストを渡し、工程の選択を既定のスキル plan-steps にして答えの JSON を検査させる

- 日時: 2026-10-19 15:12 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-146
- 置き換え元: なし
- 置き換え先: なし

## 背景

オーケストレーターが「選んだ工程を読み取れませんでした」で止まった。調べると、工程は選べていたが、答えの JSON の末尾の `}` が欠けていて、
sacty が JSON として読めなかった（ステークホルダー）。工程の選び方と答えの出し方はオーケストレーターへの指示（プロンプト）にだけ書いてあり、
出す前に答えの形を確かめる手順が無かった。
また、既定のコンテキスト（規則・スキル）は工程の実行には渡していたが、オーケストレーターの実行には渡していなかったので、スキルを足しても届かなかった。

## 決定

- 既定のコンテキストに、工程の組み合わせを選んで決められた形の JSON で答えるスキル `plan-steps` を置く。候補の比べ方（目的・成果物・変更対象・規模の順。
  無条件の既定や受け皿にしない）、理由の書き方、答えの JSON の決まりと、出す前にファイルに書いて `jq`（無ければ `python3`・`node`）で構文と形を検査し、
  通るまで直してから本文の最後に 1 回だけ出す手順（`references/json-check.md`）を書く。
- オーケストレーターの指示（対象リポジトリあり・なし）は、このスキルに従うよう求める。プロジェクトのコンテキストでスキルを消していても最低限がわかるよう、
  検査して通るまで直すこと・答えを 1 回だけ出すことは指示にも書く。
- オーケストレーターの実行にも、工程の実行と同じく既定のコンテキストとプロジェクトのコンテキストを渡し、`ContextResolved` を記録する。
  コンテキストを用意できなければ、実行せずに `OrchestratorFailed` を記録して一時停止する。
- 答えを読む側（`extractStepPlan`）は変えない。壊れた答えは今までどおり読めないものとして止める。

## 理由

- 目で見て確かめるだけでは閉じ括弧の欠けや末尾のカンマを見落とすので、道具で検査して通るまで直す手順を、エージェントが毎回読む場所（スキル）に置く。
- 読む側で閉じ括弧を補うなどの寛容さを足すと、どこまで補うかの線引きが曖昧になり、途中で切れた答え（項目の欠け）を正しいものとして読む恐れがある。
  正しい JSON を出させる方が、読み取りの規則を単純に保てる。
- スキルを既定のコンテキストに置くには、オーケストレーターにコンテキストを渡す必要がある。工程と同じコンテキストにすれば、規則（CONTRIBUTING などの
  プロジェクトの決まり）もオーケストレーターの判断に使え、記録（`ContextResolved`）もほかの実行と揃う。

## 影響

- オーケストレーターの実行のたびに、コンテキストの取得・合成（コンテキストリポジトリの clone）が 1 回増える。プロジェクトのコンテキストの MCP サーバーと
  段階の定義もオーケストレーターに渡る。段階の定義を置いた実行なので、ほかの実行と同じく費用は推定（`estimated`）として記録する。
- チケットを読んでリポジトリ・題・概要を決める実行（`TicketTriaged`）と、オーケストレーターへの質問は、この決定の範囲外で、コンテキストを渡さないまま。
- コンテキストの取得に失敗するプロジェクトでは、工程の実行だけでなく、工程の選択も止まる（再開すると選び直す）。
- 規則は[コンテキストの合成](../spec/context.md#既定の工程の選択用スキル)と[タスクと工程](../spec/tasks-and-steps.md#オーケストレーター)に記す。
