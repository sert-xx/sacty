# 実装の PR がベースブランチと競合しないよう、Sacty がホストでベースブランチの最新を作業領域にマージし、親が 2 つのマージコミットで出す

- 日時: 2026-11-01 03:40 UTC
- ステータス: 採用
- 関係する PR・タスク: #261
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験（S7 試行 1）で、並行する別のタスクの PR が先にマージされ、実装の PR がベースブランチ（main）と競合したまま（GitHub の `mergeable` が `CONFLICTING`）になった。
人が差し戻しで「main を取り込んで競合を解消する」ことを頼んだが、Sacty にはその手段が無く、同じ状態が続いた。
最終レビューは 2 回不合格になり、約 9 ドルを使って一時停止した。

- 実装の作業領域には、認証付きの `git fetch` も `gh` も無い。エージェントは main の履歴を取れず、読み取り API で main の変更ファイルの内容を取って、作業ツリーに書き込んだ。
- 実装のエージェントは、コミットとプッシュを禁止されている。Sacty が作業領域の内容を、前にプッシュしたコミットだけを親にした通常のコミットにしてプッシュする。エージェントが `git merge` で作業ツリーに残したマージの途中の状態（第 2 の親）は、使われない。
- その結果、PR は競合したまま、別のタスクの変更（29 ファイル +1033/-53）が、実装の変更として混ざった。最終レビューは、変更の範囲を超えているとして不合格にし続けた。

同じ根は、S4 試行 1 の PR でも見つかっている（スカッシュでマージされた main と競合した PR を、作り直して費用が増えた）。
Sacty には、ベースブランチとの競合を検知する仕組みも、解消する仕組みも無かった。

## 決定

人が決めた方針「ホストでマージ」に従う。PR がベースブランチと競合しうるときは、Sacty がホストで、ベースブランチの最新を作業領域にマージする。履歴は書き換えない（強制プッシュ・リベースをしない）。

1. **方式**：ホスト（退避したメタデータの git）で、作業領域の内容とベースブランチの先頭を 3 方向でマージする（`git merge-tree --write-tree`）。共通の祖先は、作業領域が今ベースにしているコミットにする（取り込む前は起点のコミット、取り込んだ後はその先頭）。結果を作業領域に書く。
   - 競合しなければ、そのまま書く。
   - 競合したファイルには、目印（`<<<<<<<`・`=======`・`>>>>>>>`）を残して書く。上が実装の側、下がベースブランチの側。競合したファイルの一覧を記録する（`BaseBranchMerged`）。
   - 作業領域には、コミットを作らない。履歴に残るのは、提出のときに作るマージコミットだけ。
2. **提出するコミット**：ベースブランチの先頭が、前にプッシュしたコミットの履歴にまだ含まれていなければ、その先頭を第 2 の親にしたマージコミットにする（親が 2 つ）。含まれていれば、これまでどおり親は 1 つ。内容が前と変わらなくても、含まれていなければマージコミットを作る（PR がベースブランチの先頭を含む履歴になるように）。コミットの日時は提出ごとに決まるので、再開しても同じコミットになる。
3. **取り込む時点**（検知と取り込みは同じ操作。GitHub の `mergeable` は読まず、ホストが取得したベースブランチの先頭で決める）：
   - 実装の実行を始める前。初回も、差し戻し・PR の指摘の取り込み・再レビューなどで実装をやり直すときも同じ。競合した目印は、その実行の指示で、解消するよう渡す。
   - 最終レビューの前（実装の実行の間にベースブランチが進んだとき）。最終レビューは取り込んだ後のコードで行い、PR はマージコミットで出す。PR の CI を待つ間は、最終レビューに進まないので、取り込まない。CI の結果が出た後（競合で一時停止したタスクを再開して、実装をやり直さずに最終レビューへ戻ったときを含む）にベースブランチが進んでいれば、そのとき取り込む。競合すれば実装をやり直し、競合しなければ PR をマージコミットで作り直して、CI を待ち直す（前の CI の結果は、取り込む前のコードのものなので使わない）。
   - 承認待ちの間には、取り込まない。人が差し戻す・PR の指摘を書くと、実装のやり直しの前に取り込む。
4. **エージェントへの指示**：競合したファイルの一覧と、解消の仕方を渡す。上下の意味、両方の意図を生かすこと、ベースブランチ側の変更を自分の変更として書き直さない・消さないこと、目印の行をすべて消すこと、git でのマージ・リベース・フェッチ・コミット・プッシュをしないこと。
5. **最終レビューとの関係**：
   - 目印が残っているファイルがあれば、最終レビューに進まない（ゴールガーディアンを実行しない）。競合したファイルを渡して実装をやり直す（`BaseConflictsRemained`。検証に通らなかったものとして数える）。
   - 最終レビューの指示に、取り込んだこと、差分は取り込んだ先頭からの実装の変更であること、ベースブランチ側の変更は実装の差分ではなく変更の範囲・過剰さの判定に含めないこと、競合を解消した内容が壊していないかを確かめることを伝える。
   - 実装の差分・変更なしの判定の起点は、取り込んだ先頭にする。記録した起点のコミットは変えない。
6. **解消できなかったときの止め方**：目印が残って通らないことは、ほかの検証の失敗と同じ上限（`MAX_VERIFY_ATTEMPTS`、3 回）を数える。ただし、最終レビューの前の取り込みで新しく競合したとき（実装の実行の間にベースブランチが進んだ）は、エージェントの誤りではないので数えず（`BaseConflictsRemained` の `fresh`）、競合したファイルを渡してやり直す。前の取り込みの目印が残っているときは数える。続けて通らなければ一時停止（`verification`）にし、競合したファイルを示す。再開すると、目印のあるファイルを渡して実装をやり直す。目印の残る実装は、人が「レビューへ進める」こともできない。
7. **取り込めないとき**：ベースブランチの取得・マージに失敗したら（ネットワーク・ホストの git が古いなど）、実装を実行せず、理由を示して一時停止する。再開すると取り込みからやり直す。
8. **範囲に入れないもの**：既存の PR を引き継ぐタスク（人の PR のブランチに積むので、人が決める）。承認待ちの PR がベースブランチに遅れたことの自動の検知（人の差し戻しか指摘を待つ）。

## 理由

- 作業領域で `git fetch` や `git merge` をさせる案は採らない。認証をエージェントに渡さない方針（作業領域の `.git` はエージェントが書き換えられるので、ホストでは使わない）と、コミットとプッシュを Sacty だけが行う方針を保つ。ホストなら、認証付きでベースブランチを取得でき、競合の結果を確かめられる。
- 取り込み方を、作業領域の履歴を書き換えないマージにした。強制プッシュ・リベースは、人が見ている PR の履歴を書き換え、人の方針（履歴を書き換えない）に反する。PR の「ブランチを更新」（GitHub の API）は、競合のときに使えず、競合の解消をエージェントに渡せない。
- 3 方向のマージの共通の祖先に、作業領域が今ベースにしているコミットを使う。作業領域は、そのコミットに実装の変更を加えたものなので、実装の変更とベースブランチの変更だけが合わさる。結果の作業領域は「取り込んだ先頭に実装の変更を加えたもの」になり、実装の差分・変更なしの判定・コミットの内容が、そのまま正しくなる。
- 実装の実行の前と最終レビューの前の 2 か所にした。実行の前に取り込めば、差し戻しや PR の指摘の対応と競合の解消を、1 回の実行で行える。最終レビューの前にもう一度確かめるのは、長い実行の間にベースブランチが進むことがあり、競合の目印の解消を確かめる場所でもあるため。CI の結果が出た後に取り込んだときは、PR を作り直して CI を待ち直す。取り込んだコードで CI を通さずに最終レビューへ進むと、CI の結果と最終レビューのコードがずれるため。実際の試行で、最初は CI の結果が出た後（再開した直後）には取り込まない作りにしていたため、競合で止まったタスクを再開すると、取り込まずに古いコードで最終レビューが走り、同じ理由で不合格になった（費用の無駄）。そのため、この時点でも取り込む。
- 目印を最終レビューの前に検出するのは、ゴールガーディアンの費用を、競合が残っていると分かっている実装にかけないため。ほかの検証の失敗と同じ上限で止めるのは、新しい仕組みを足さずに、同じ「やり直す → 3 回で止める」を使うため。
- 競合の検知に PR の `mergeable` を使わない。GitHub は計算が遅れ、`UNKNOWN` を返すことがある。ホストが取得したベースブランチの先頭と作業領域で決めれば、Sacty が自分で確かめられ、PR を作る前の実装でも同じ判定になる。
- 承認待ちの間に取り込まないのは、人が PR を読んでいる間に、PR の中身を変えないため。人が差し戻すか指摘を書いたときは、実装をやり直すので、その前に取り込む。

## 影響

- 実装の作業領域の内容が、ホストの操作で書き換わる。エージェントが動いていない間（実行の前と最終レビューの前）にだけ行う。作業領域の `.git` は読まず、書き換えない。
- ベースブランチの取得に失敗すると、実装が始まらずに止まる。ホストの git は 2.40 以上（`git merge-tree --write-tree` と `--merge-base` が使える版。2.39 以前では `--merge-base` が使えない）が必要。古ければ `git.mergeTreeUnsupported` で止まり、更新を案内する。
- 競合していない取り込みでも、PR の履歴にマージコミットが入る。ベースブランチ側の変更は、PR の差分（ベースブランチとの差）には含まれない。
- 競合のうち、目印を入れられないもの（バイナリ・片方での削除など）は、目印の有無では解消を確かめられない。エージェントに一覧は渡すが、最終レビューに進めるかは、目印のあるファイルだけで決まる。
- 目印の検出は、sacty が書く目印の行を見る。始めの行（`<<<<<<<`）と終わりの行（`>>>>>>>`）には、ツリーかコミットの ID のラベルが付くので、そのラベルの付いた行が1つでも残っていれば「残っている」とする（片方だけ消し忘れたときも）。ラベルの無い似た行（git の競合の説明の文書など）は目印にしないので、もともとそのような行を含む文書の誤検出は起きにくい。単独の `=======` は、Markdown の見出しの下線と区別できないので見ない。そのため、始めと終わりの行を消して `=======` だけを残した場合は、検出できない（最終レビューと人のレビューで見つける）。両側が同じファイルを別名へ改名して内容も競合したときなど、git は目印を長くし（`<<<<<<<<`）、ラベルにパスを付ける（`<ID>:ours.txt`）ので、7 文字以上の目印と、ID のあとのパスのラベルも目印として見る。
- 競合したファイルの数には上限（1000 件。`MAX_BASE_CONFLICTS`）を置く。記録した一覧が、目印を検査する対象のすべてなので、切り捨てない。上限を超えるときは、作業領域を書き換える前に、件数と上限を示して止める（`git.tooManyConflicts`）。
- ディレクトリとファイルの名前が衝突した競合では、git が片方を `<名前>~<ID>` に避けて置く。これも目印を持たないので、避けた名前のパスが残っているうちは、解消していないものとする。指示で、何が起きたかと、残す内容を正しい名前にして避けた名前のものを消すことを伝える。
- 最終レビューの前の取り込みで新しく競合した場合は、検証に通らなかった回数に数えない。実行の間にベースブランチが進むたびに新しく競合しうるので、数えない回数に上限は無いが、数えないのは新しい競合が出たときの1回だけで、続くやり直しで目印が残っていれば数える。ベースブランチが進み続ける限りは、やり直しが続きうる。
- ホストでの取り込みと作業領域への書き込みの間でデーモンが止まると、作業領域は取り込み済みで、記録（`BaseBranchMerged`）だけが無い状態になりうる。次の取り込みは、同じ内容を重ねて取り込むだけで、競合した目印が残っていれば、目印が重なることがある。まれなので、特別な復旧は作らなかった。
- `Task.baseMerge`（最後の取り込み）、`BaseBranchMerged`・`BaseConflictsRemained` が加わる。それより前の版の記録は、そのまま読める。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md#ベースブランチの取り込み)。使い方は [ベースブランチが進んだとき](../user/tasks.md#ベースブランチが進んだとき)。
