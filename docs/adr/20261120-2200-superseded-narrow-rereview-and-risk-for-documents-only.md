# 文書だけを直した後の再レビューは観点と検証を絞り、リスク評価は引き継ぐ

- 日時: 2026-11-20 22:00 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: PBI-421
- 置き換え元: [依頼が軽いときは、自己レビューの観点を絞る](20261117-0359-superseded-narrow-self-review-for-light-requests.md)（PR のレビューを対象外とした部分）
- 置き換え先: [PR のリスク評価は、レビューが指摘なしになった回だけにする](20261121-0300-superseded-risk-assessment-only-when-review-has-no-findings.md)（リスク評価の引き継ぎ）、[再レビューは、前回の指摘の確認と前回以降の差分に絞る](20261121-0400-rereview-narrowed-to-previous-findings-and-changes.md)（観点の絞り。検証の絞りは、そのまま）

## 背景

sacty が自分の PR に付けるレビューの子タスクは、指摘なしになるまで、PR の先頭が進むたびに再レビューする。直しが文書の数行だけでも、再レビューは初回と同じ規則で観点を決め直し（15 件前後の担当）、全テストを実行していた（1 回 7〜9 分・5〜7 ドル）。
PR を更新する前のリスク評価（オーケストレーターの実行。1〜2 分）も、先頭が進むたびに、差分の中身によらずやり直していた。
2026-11-17（PBI-369）の ADR は、観点を絞る規則を軽い依頼の自己レビューに限り、PR のレビューは対象外とした。その決定を、この条件に限って変える。

## 決定

- 前回レビューした先頭から今回の先頭までの差分が文書だけの再レビューは、主対象が `code` の PR に限り、起動する観点と検証を絞る。規則の本体は既定のスキル `review-dispatch` の規則 10 に置き、規則 8・9 と同じく、依頼した側（デーモンの指示）が明示したときだけ当てはめる。
- 「文書だけ」の判定は、デーモンが 1 か所で持ち（`documentsOnlySince`）、再レビューの絞りと、リスク評価の引き継ぎで共有する。前回のコミットが今回の祖先で、変わったパスの拡張子が文書（`isDocumentsOnly`）で、エージェントへの指示（名前が `AGENTS.md`・`CLAUDE.md`・`GEMINI.md`・`SKILL.md` のもの、`.` で始まるディレクトリの下）と、今回の木で `SKILL.md` があるディレクトリの下を含まないこと。名前に制御文字を含むパス、変わったパスのディレクトリが 200 件を超える場合、確かめられないものは、文書だけにしない。差分が空のときは文書だけにしない。
- 判定は二段にする。デーモンは名前と拡張子で見て、指示に変わったパスを添えて明示する。親は、変わったファイルを開き、主対象の種類の考え方で見直す（文書でない・迷う・エージェントへの指示・コードやテストが読み込む文書・前回の本文の未対応の `must` が文書でないものに及ぶ・前回の本文に見られなかった観点がある、なら絞らない）。既定のスキルは、拡張子だけでは決められない（あらゆる言語・リポジトリに配るため）。
- 絞るときに起動するのは、前回の指摘に関わる観点、変えた文書の種類の正確さと安全性の観点（`user-doc` は U-1・U-5、`design-doc` は D-2・D-5）、X-1。検証は `scope: docs` で、コードのテストは `skipped` と理由を残す。判定・重み・前回の指摘の確認の書き方は変えない。
- 絞る条件の「PR の差分の起点が前回と同じ」は、GitHub の `base.sha` では見ず、PR の向き先のブランチが前回と同じで、前回と今回の merge-base が同じことで見る。`base.sha` は、ベースブランチが進むだけで変わり、マージの多いリポジトリで絞れなくなるため。ベースを取り込んだ・向き先を替えた・履歴を書き換えたときは、起点か向き先が変わるか、取り込んだ変更が前回以降の差分に入るので、絞らない。このため、レビューの対象と前回のレビューの記録に、向き先のブランチと向き先のコミットを足した。
- リスク評価は、前回の評価（評価できたもの）から今回までが文書だけで、PR の差分の起点（`workBaseCommit`）が同じなら、エージェントを実行せず、前回の評価の写しを `PullRequestRiskAssessed` に記録する（費用 0。評価した元のコミットを `inheritedFrom` に持つ）。新しいイベントは作らず、投影の「最後の評価だけを持つ」と PR の説明の読み方を、そのまま使う。比べる起点は前回の記録のコミットなので、引き継ぎを重ねても、文書でない変更が入った提出では評価し直す。
- 再レビューの絞りは、前回の回の判定をタスクの記録から読む。GitHub の再依頼で作ったタスクは、前回の判定を持たないので、絞らない（新しい状態を足さない）。
- 変えないもの：初回のレビュー、自己レビュー、規則 8・9、主対象が文書の PR の再レビュー、`via` が `review` の評価。

## 理由

- 直しが文書だけのとき、コードのテストと 15 件前後の担当は、判断に使われず、時間と費用だけがかかる。
- 絞る条件を、確かめられたときだけに限り、迷えば絞らないので、安全側に倒れる。

## 影響

- 文書だけを直した後の再レビューとリスク評価が軽くなる。
- 一覧にないエージェントへの指示の文書・コードやテストが読み込む文書は、デーモンの判定では文書だけになりうる。再レビューでは親が見直して絞らないが、リスク評価の引き継ぎでは、段階が前回のままになることがある。リスク評価は人のレビューの深さの目安で、工程を変えないので、受け入れた。
- 向き先のブランチと向き先のコミットを持たない過去のレビュー・評価の記録の後は、1 回、絞らず・引き継がずに、今までの規則で扱う。
