# スキルなどエージェント向けの指示の文書は、テストを書かずに差分で確かめ、ふつうは direct か skip-design で進める

- 日時: 2026-10-27 00:20 UTC
- ステータス: 採用
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: なし

## 背景

スキル（SKILL.md）を作るタスクが、要求要件 → 設計 → 実装の流れ（`standard`）になり、うまく進まないことがあった。

- スキルは文書だが、エージェントの振る舞いを変えるのが目的なので、設計のテスト観点が「〜のとき、エージェントは〜する」という振る舞いの形で書かれやすい。
- テストを書かずに差分で確かめてよい（`untested`）のは「実行される振る舞いの無い変更（文書・コメント・文言など）」だけで、ゴールガーディアンは「振る舞いを変えるのにテストが無ければ不合格」と判定する。
  エージェント向けの指示がどちらに当たるかを決めていなかったので、実装もゴールガーディアンも振る舞いの変更として扱い、テストを求めていた。
- 振る舞いを確かめるにはエージェントを起動するしかなく、作業領域のテストでは確かめられない。
- オーケストレーターの組み合わせの選び方には、スキルの例が無かった。

## 決定

- エージェント向けの指示の文書（スキルの SKILL.md と references・AGENTS.md・CLAUDE.md・規則・プロンプトの文など）は、実行される振る舞いの無い変更として扱う。
  - 実装には、テストを書かずに差分で確かめると申告させる（エージェントを起動して確かめるテストを書かせない）。スキルに含めるスクリプトなど、実行されるコードはコードとして扱わせる。
  - ゴールガーディアンには、その変更を振る舞いを変えないものとして扱わせ、エージェントを起動して確かめることを求めさせない。
- 設計では、その文書を書く・直す観点を、エージェントがどう振る舞うかではなく、文書に何が書かれているべきか（手順・条件・決まり）で書かせる。
- オーケストレーターには、エージェント向けの指示をリポジトリに足す・直すタスクは、ふつう `direct` か `skip-design` にさせる（複数のスキルにまたがって広い設計判断が要るなら `standard`）。テストや観点を決めるために要求要件・設計の工程を足させない。

## 理由

- 作業領域で確かめられない振る舞いをテストで求めても、実装は形だけのテスト（ファイルがある・文字列を含む）を書くか、やり直しを繰り返すしかない。文書として差分で確かめるほうが、確かめられることと判定が合う。
- 指示の文書がどう効くかは、最終的に人が PR で確かめる。
- 作業領域では確かめられないこととして人の確認（`humanChecks`）に回す案もあったが、今回は採らなかった（利用者が、文書として差分で確かめる案を選んだ）。

## 影響

- スキルの中のスクリプトなど、実行されるコードには、今までどおりテストを求める。
- 指示の文書の変更が実際にエージェントの振る舞いをどう変えるかは、sacty の検証では確かめない。
