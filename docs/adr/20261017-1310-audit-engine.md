# 完了したタスクを、作業履歴に記録しながら2段で監査する

- 日時: 2026-10-17 13:10 UTC
- ステータス: 採用
- 関係する PR・タスク: #135、PBI-125
- 置き換え元: なし
- 置き換え先: なし

## 背景

PBI-124 で、監査の画面と API の形を、裏側のモックで先に作った（[監査の画面を、裏側のモックで先に作り、モックは環境変数で切り替える](20261017-1145-audit-ui-with-mock.md)）。
PBI-125 では、完了したタスクを実際に監査する。ステークホルダーの要求は次のとおり。

- タスクの完了時に自動で監査する。
- まずタスク全体を大まかに監査し、懸念のある工程は別のセッションで自動で深掘りする（一度に全体を見るとコンテキストが大きすぎるため）。
- 監査の予算は、タスクの予算とは別に持つ。
- 同じ原因をタスクをまたいでまとめ、改修をマージした後にまた見つかったら再発として示す。
- 人が却下した提案は、理由を以後の監査に渡す。

## 決定

- **記録先**：監査は、監査したタスクの作業履歴に追記する（`AuditQueued`・`AuditSurveyed`・`AuditDeepDived`・`AuditCompleted`・`AuditFailed`・
  `AuditBudgetWarned`・`AuditBudgetPaused`・`AuditCapRaised`・`AuditProposalAdopted`・`AuditProposalRejected`）。actor は監査の実行が
  `auditor`、人の判断が `person`。タスクの状態・工程は変えない。
- **費用**：監査の費用は `auditCostUsd` に持ち、タスクの予算（`costUsd` を持つイベントの合計）には入れない。監査の状態の `usedUsd` に足す。
- **始まり**：タスクが完了した瞬間の追記で `AuditQueued` を足す。この機能より前に完了していたタスクは監査しない。
- **実行**：ワーカーの待ち行列に入れ、1回の実行でエージェントの実行を1つだけ進める。大まかな監査は懸念のある工程を最大 3 つ挙げ、
  深掘りは工程ごとに原因を最大 3 つ、原因ごとに提案を最大 2 つ出す。どちらも毎回新しいセッションで、セッションログとコードの写しを
  読み取り専用で渡す。使う AI は `audit_agent`（無ければ `guardian_agent`、それも無ければ `default_agent`）。
- **根拠の件数**：sacty が作業履歴とセッションログから数え、指示と記録に入れる（エージェントに数えさせない）。
- **原因のまとめ**：深掘りに同じプロジェクトの既存の原因の鍵と、却下された提案と理由を渡し、同じ原因なら既存の鍵を使わせる。
- **再発**：改修のタスクの PR のマージの時刻より後に、同じ鍵の原因が見つかれば再発とする（記録から決め、再発のイベントは持たない）。
- **採用**：対象リポジトリ・コンテキストのリポジトリが宛先なら、そのリポジトリを対象にした改修のタスク（`start: "audit"`）を作る。先に採用を
  記録してから作り、作る前に止まったら起動のときに作る。sacty の既定のコンテキスト（ゴールガーディアンのプロンプト・既定のスキル）が
  宛先なら、利用者のプロジェクトにはタスクを作らず、採用だけを記録する。
- **失敗と中断**：実行の失敗・出力を読めないときは `AuditFailed` にし、それ以上進めない。デーモンを止める・タスクを中止するときに
  終わった実行は記録せず、次に起動したときに同じ段から実行する。
- **予算の通知**：80% は作業履歴に記録する（タスクの予算の 80% と同じく、Slack には送らない）。上限に達したら、次の実行の前に一時停止する。
- **モック**：`SACTY_AUDIT_MOCK=1` のときは監査を動かさず、モックを返す（PBI-124 のまま）。

## 理由

- 作業履歴に記録すると、監査の結果・人の判断・予算の変更を、タスクと同じ追記専用の台帳で辿れる（構想の「証跡は追記専用で残す」）。
  画面の形は、その記録を畳み込んで作れる（PBI-124 の ADR の見通しのとおり）。
- 費用の欄の名前を `costUsd` にすると、型の検査（`CHARGED_EVENT_TYPES`）でタスクの予算に入れることになる。監査の予算は別に持つので、
  名前を分けた。
- この機能より前に完了したタスクまで監査すると、入れた直後に多数の監査が動き、予想しない費用がかかる。
- 待ち行列に入れると、同時に実行する数の上限で費用と負荷を抑えられる。1回で1つずつ進めると、予算の確かめと中断からの再開が段ごとにできる。
- 根拠の件数をエージェントに数えさせると、監査ごとに数え方がぶれ、ダッシュボードの推移が比べられない。
- 原因の同じさの判断は、文の比較では難しいので、既存の原因の一覧を渡してエージェントに判断させる。鍵は同じプロジェクトの中だけで比べる
  （コンテキストの分離のため）。
- sacty 宛ての改修のタスクを利用者のプロジェクトに作ると、sacty とは関係の無いリポジトリで作業が始まる。セルフヒーリング（sacty への
  Issue の作成）はまだ無いので、採用の記録と提案の文だけを残す。提案の文は、タスクやコンテキストの中身ではなく、監査が書いた改修の内容だけ。
- 出力を読めない監査を何度もやり直すと、費用が増える。失敗として止め、理由を見せる。止めるときの実行の終わりは失敗ではないので、
  やり直す。

## 影響

- core に監査のイベントと、タスクの監査の状態（`Task.audit`）、改修のタスクの元の提案（`Task.auditFix`）を足した。
- config.yaml に `audit_agent` を足した。エージェントの役割に `audit`・`audit-dive` を足し、スタブの出力（`stub.audit`・`stub.audit_dive`）を足した。
- 監査を始めるのは、デーモンの監査を有効にしたとき（`ServiceDeps.audit`）だけ。main.ts はモックでないときに有効にする。テストでは既定で無効。
- 改修のタスクは、宛先のリポジトリがプロジェクトの対象に無くても作る。リポジトリにアクセスできなければ、そのタスクが通常どおり理由を示して止まる。
