## 背景

実装の工程の後、sacty は実装の PR をドラフトで作り、ゴールガーディアンの最終レビュー（作業領域の写しでテストを実行して合否を判定する）と、PR の CI の待ち・失敗した CI の1回の再実行・不安定なテストの台帳を回していた。
この仕組みでの失敗（テストが決まらずに止まる・環境が原因の失敗・権限で実行できない など）が重なり、利用者にとって煩わしかった（ステークホルダーの指摘、2026-11-12）。
一方で、sacty が作る PR は、PR を作ったタスクのレビューの子タスクが、指摘なしになるまでレビューするようになった（[sacty が作る PR のレビューを、PR を作ったタスクの子タスクにし、指摘なしになるまで繰り返す](20261112-0609-review-sacty-pull-requests-in-child-tasks.md)）。

人が決めたこと（2026-11-12）：

- やめるのは、最終レビューのテストの実行に加え、PR の CI の待ち・失敗した CI の再実行・不安定なテストの台帳まで。CI の結果は、レビューの子タスクが見て指摘にする。
- 実装の工程のエージェント自身が作業中にテストを実行することは残す。
- 指摘なしの後は、人が PR のマージで承認する。

## 決定

- 実装の工程が終わったら、最終レビューもテストのコンテナも CI の待ちもせずに（`FinalReviewSkipped`）、実装の PR をドラフトで作って承認待ちにし、PR のレビューの子タスクに渡す（PR の公開の記録に `awaitingReview`）。
- 子タスクの判定が、PR の今のコミットで指摘なし（`no_findings`）になったら、sacty がドラフトを外す（`PullRequestMarkedReady`）。指摘があれば、PR の指摘の取り込みで実装を直し、子タスクが再レビューする。直して PR を更新したら、ドラフトに戻す。
- sacty は PR の CI を待たない・再実行しない。子タスクには、レビューする先頭のコミットの CI の状態を sacty が読んで渡し、変更による失敗を要修正の指摘に、変更と関係の無い失敗を人が確かめることにさせる。終わっていなければ待たずにレビューさせる。
- 依存のある分割の子タスクは、依存先の PR のレビューが指摘なしになった時点で、依存先のブランチに重ねて始める。重ねた PR は、依存先がマージされて向き先を付け替えた後にレビューし、指摘なしでドラフトを外す。
- 最終レビュー・CI の待ちの途中だった古いタスクは、次の実行（再開を含む）で `FinalReviewSkipped` を記録して、新しい流れに乗る。
- 画面から、「レビューへ進める」の操作と、不安定なテストの台帳の表示を外す。関連するタスクのリンクに、レビューの子タスクの状態・何回目・判定を出す。
- 最終レビューの仕組み（ゴールガーディアンの実行・CI の待ち・不安定なテストの台帳）は、デーモンの依存 `finalReview` を有効にしたときだけ動く形で残す（デーモンの起動では無効）。工程の流れを確かめる既存のテストのためで、ゴールガーディアンの撤去と一緒に消す。

## 理由

- レビューの子タスクが PR をレビューし、CI の結果も読んで指摘にするので、sacty が別にテストを実行して合否を決める必要が薄い。sacty による実行の失敗（環境・権限・テストの決め方）で止まることが無くなる。
- 指摘なしまでドラフトにしておくと、人が承認（マージ）できる状態が、PR の見た目で分かる。
- 仕組みのコードを一度に消すと、工程の流れを確かめる多くのテストを同時に書き換えることになり、変更が大きくなる。依存で切り替えて、まず振る舞いを変える。

## 影響

- 実装の PR の CI が落ちていても、sacty は待たずにレビューの子タスクに渡す。CI の結果をどう扱うかは子タスクのレビューに任せる（読めなかったときは、読めなかったことを書かせる）。
- 子タスクの判定が指摘なしでも、人がマージする前に CI の結果を確かめる必要がある（PR の本文にも書く）。
- 不安定なテストの台帳には、新しい記録が増えない。台帳を読む API と、台帳からタスクを作る口は残る（古い記録のため）。
- 依存のある子タスクの開始は、依存先のレビューが指摘なしになるまで遅くなる。
