## 背景

実行のイメージは、工程ごとに決めていた。オーケストレーターは工程ごとに `images` から選び、作成・タスクの詳細・再開・差し戻しでも、
人は工程ごとにイメージを選んでいた。テストは実装の工程のイメージで、最終レビューもそのイメージで動いていた。

次に、依存関係の準備（依存の取得など）を工程の間で使い回すことを検討している。工程ごとにイメージが違うと、
ある工程で準備したものを別のイメージの工程で使えるとは限らない。そこで、使い回しの前に、イメージの選択を工程ごとからタスクごとに変えることを
人が決めた（2026-11-08）。

## 決定

- タスクのイメージを1つにする。タスクのすべての工程・テスト・最終レビューを、そのイメージで動かす。
- 決め方の優先の順は今と同じ：再実行の指定 → 作成時の人の指定 → プロジェクトの対象の指定 → オーケストレーターの選択
  （指定が無く、`images` の候補も無ければ既定のイメージ）。決まったものは `StepsChosen` の `image` と `imageSource` に記録する
  （作成時の指定は `request`）。
- オーケストレーターには、タスクに1つのイメージを `image` と理由（`imageReason`）で答えさせる。`images` の候補を見せたのに既定のイメージを選んだときは、
  合わない理由を1つ（`defaultReason`）書かせ、`StepsChosen` の `defaultImageReason` に残す。理由が無ければ `imageUnexplained` に
  「理由が無い」ことを記録し、タスクの詳細と作業履歴に出す。PR のレビューだけのタスクも同じ形にする。
- 作成（`CreateTaskInput`・`TaskCreated` の `image`）・タスクの詳細（`POST /api/tasks/:id/image`。`TaskImageChanged` を記録する）・再開
  （`ResumeTaskInput` の `image`）・差し戻し（`RequestChangesInput` の `image`）で選ぶのも、タスクのイメージにする。
  人が後から変えたものは、すべての工程の次の実行から使い、実行中のものは変えない。作成時の指定は、今までどおり進め方を選んだときだけにする。
- 工程ごとのエージェントの選択（`agents`）は変えない。
- 古い版の作業履歴（工程ごとの `images` を持つ `TaskCreated`・`StepsChosen` と、`StepImageChanged`）は、そのまま読む。
  投影は工程ごとのイメージを残し、実行は、タスクのイメージが無ければ工程ごとのイメージを使う。タスクの詳細では、
  工程ごとに最後に設定したイメージと、実行で使ったイメージ（実行の記録 `AgentRunStarted`・`DeploymentCheckStarted` の `image` に残す。名前の無い古い記録は、作業履歴をたどって求める）を出す。古いイベントの型は消さない。古い版のタスクで人がタスクのイメージを選ぶと、それからは
  タスクのイメージを使う（`TaskImageChanged` の `from` は無い）。
- 工程ごとにイメージを変える API（`POST /api/tasks/:id/images`）は消す。

## 理由

- 依存関係の準備を工程の間で使い回すには、すべての工程が同じイメージで動く必要がある。
- 1つのタスクは1つのリポジトリ（または1つのリポジトリの無い作業）を扱い、イメージはリポジトリの言語・ツールで決まると考えた。
  工程ごとに違うイメージが要る場面があるかは、確かめていない。
- 優先の順を変えないのは、人の指定がオーケストレーターの選択に勝つという今までの考え方を保つため。
- 既定のイメージの理由を1つにするのは、候補を見せたのに既定のイメージにした判断を、工程の数だけ書かせずに確かめられるようにするため。
- 古い版の作業履歴を読めるようにするのは、作業履歴は追記だけで書き換えないため（[作業履歴は追記だけ](20261010-0628-append-only-ledger.md)）。
  古いタスクを途中から新しい形に移すと、どのイメージで動いたかがわからなくなる。
- 工程ごとの API を残さないのは、残すとタスクのイメージと工程ごとのイメージの両方を書けてしまい、どちらを使うかが分かりにくくなるため。
- 比べた案：工程ごとの選択を残し、既定値をタスクのイメージにする。工程ごとに違うイメージを選べると、依存関係の準備を使い回せる前提が崩れ、選ぶ所も2つになるので採らなかった。

## 影響

- 新しいタスクでは、設計などの工程も実装と同じイメージで動く（言語のイメージは既定のイメージより大きいことがあり、最初の実行のイメージを作る時間が増えうる）。
- 古い版で工程ごとの指定を一部の工程だけにしたタスクを、工程の選択からやり直すと、タスクのイメージ（オーケストレーターの選択など。決まらなければ既定のイメージ）が優先する。
- 仕様は [工程とタスク](../spec/tasks-and-steps.md)、利用者向けは [タスク](../user/tasks.md) と [コンテナイメージ](../user/images.md) に書く。
