# 終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない

- 日時: 2026-11-15 12:24 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: #378、PBI-347
- 置き換え元: [実装の最終レビュー（テストの実行）と PR の CI の待ちをやめ、PR のレビューの子タスクの指摘なしでドラフトを外す](20261112-0714-superseded-review-child-task-replaces-final-review-and-ci-wait.md)（実装の工程が終わったら、確かめずに実装の PR を作る・更新する部分）
- 置き換え先: [未完了で終わった実装の実行を、同じセッションの続きから進め、続きの上限を 10 回にする](20261115-2254-continue-incomplete-implementation-in-same-session.md)（提出しなかったときに、実装を最初からやり直し、3 回続けて終わらなければ一時停止する部分）

## 背景

2026-11-15、タスク分割の子タスクの実装が、範囲の一部だけを実装して終わった。
差分は 23 行で、実装の説明の先頭に「実装は未完了です」と書かれていた。
sacty は、そのまま提出して実装の PR を作った。

PR のレビューの子タスクは「修正が必要」と指摘した。
やり直しの実行も、何も変えずに「未完了」と書いて終わり、sacty はまた提出した。
PR の先頭のコミットが変わらないので、子タスクは再レビューを始めなかった。
タスクは「実装の PR のマージ待ち」のまま、ドラフトの PR を抱えて動かなくなった。止まったことは、人に知らされなかった。

仕組みに、2つの欠陥があった。

1. 実装の実行が終わると、範囲を実装し終えたかを確かめずに提出する。
   最終レビューをやめたとき（[ADR](20261112-0714-superseded-review-child-task-replaces-final-review-and-ci-wait.md)）に、提出の前の関門が無くなった。
   エージェントが本文に未完了と書いても、sacty は読まない。
2. やり直しが PR の内容を変えなくても、提出にする。
   子タスクは同じ先頭を再レビューしないので、指摘が残ったまま、指摘なしにも作り直しにもならない。

人が決めたこと（2026-11-15）：

- この2つを、1つの PR で直す。
- 子タスクに渡す完了の基準と、実装の指示の見直しは、その後に別の PR で直す（PBI-348）。

## 決定

- 実装の工程は、範囲を実装し終えたかを、言語の名前が `sacty-completion` のコードブロックの中の JSON で必ず申告する（完了か未完了か。未完了なら残っていること）。
  sacty は、このコードブロックだけを申告として読む。
- sacty は、完了と申告した実行だけを提出に進める。
  完了にするのは、申告のコードブロックのすべてを、決まった形どおりに読めて、すべてが完了のときだけ。
  未完了と申告した実行と、申告が無い・読めない実行は、提出しない（PR を作らない・更新しない）。
  読めない申告は、次のもの：JSON として読めない・決まったキーのほかのキーがある・同じキーが重複している・コードブロックが閉じていない。
- 申告は、提出の前の競合の確認より先に確かめる。未完了の実行は、競合の目印が残っていても、未完了として記録する（競合は、完了と申告した実行で確かめる）。
- 提出しなかったときは、残っていることを指示に添えて、実装をやり直す。
  3 回続けて終わらなければ、一時停止して、残っていることを出す（理由 `incomplete`）。
  やり直しても作業領域の内容（git のツリーの ID）が変わらなければ、回数を待たずに止める。
  止めるときは、未完了の記録と一時停止を、同じ追記で記録する。
- AI のレビューが指摘を残した実装の PR の先頭を、やり直しの実装が変えなかったら、提出にせずに一時停止する（理由 `unchanged`）。
  先頭は、sacty が前に出したコミットのことも、人が PR に足したコミットのこともある。
  再開すると、指摘を渡して実装をやり直す。
  この理由で止まっている間は、人が PR のドラフトを外しても、sacty はドラフトに戻さない（人が指摘を採らないと判断して、マージで承認できる）。
- 次のやり直しは、何も変えなくても、今までどおり提出する。
  - 子タスクがその先頭を指摘なしにしている・まだレビューしていない・レビューの途中
  - 子タスクの指摘なしを待たない PR（既存の PR を引き継ぐタスクなど）
- 申告させる前の版の記録（実装の完了に申告の項目が無い）は、今までどおり提出に進める。

## 理由

- 提出の前に sacty が自分で確かめる手段（テストの実行・最終レビュー）は、失敗が多くてやめている。
  エージェントは、実装し終えていないことを自分で分かっていた（本文にそう書いた）。
  その判断を決まった形で申告させれば、sacty は新しい実行を足さずに、未完了の提出を止められる。
- 申告の無い実行を完了として扱うと、申告を書き忘れた未完了の実行が、今までどおり PR になる。
  申告を必須にして、無ければ提出しない側に倒した。
  申告を書き忘れた完了の実行は、やり直しの1回で申告されるので、損は実行1回で済む。
- 申告を専用のコードブロックに区切ったのは、どこからどこまでが申告かを、推し量らずに決めるためである。
  はじめは、本文の中の JSON（見出し `sacty-completion` を持つもの）を探して読んでいた。
  この読み方では、読める JSON を探す処理と、読めない申告を見出しの文字列で探す処理が食い違い、壊れた未完了の申告を見落として、併記された完了の申告で提出するおそれがあった（PR のレビューの指摘）。
  同じキーの重複・決まっていないキー・複数の食い違う申告も、1つずつ塞ぐ形になっていた。
  テストのコマンドの申告と同じく、専用のコードブロックだけを読み、中身のすべてを決まった形どおりに読めたときだけ完了にすれば、読み落としは「申告なし」の側（提出しない側）にだけ倒れる。
  コードブロックの外に同じ名前が出てきても、申告なしにはしない。実装の説明が、この名前に触れることがあるためである（申告の仕組みそのものを変えるタスクなど）。
- 申告を競合の確認より先に確かめるのは、先に競合で戻ると、未完了の記録が残らず、残っていることが次の指示に渡らないためである（PR の独立レビューの指摘）。
  競合したファイルは、解消するまで実装の指示に載り続けるので、後に回しても見落とさない。
- 未完了のやり直しの回数は、既存の「提出の前の検証に通らないときのやり直し」と同じ 3 回にした（`MAX_VERIFY_ATTEMPTS`）。
  作業領域が変わらないときに回数を待たないのは、同じエージェントでやり直しても進まない見込みが高いためである（今回の2回目の実行は、何も変えなかった）。
  変わったかは、差分の文字列ではなく、作業領域のツリーの ID で比べる。差分の文字列は大きいと先頭だけに切り詰めるので、後ろだけを変えた進捗を見落とすためである。
- 変更の無いやり直しは、自動でやり直さずに止める。
  指摘を渡したやり直しが何も変えなかったのは、エージェントが直せなかったか、指摘が当たらないと判断したかのどちらかで、どちらも人の判断が要る。
- 同じ先頭をもう一度レビューさせる案は採らなかった。
  同じ内容には同じ指摘が返り、AI のレビューの往復には回数の上限が無いので、予算の上限まで繰り返すおそれがある。
- 止める条件を「子タスクがその先頭に指摘を残している」に絞ったのは、ほかのやり直しは行き止まりにならないためである。
  人の質問に答えるだけで何も変えないやり直しは、今までどおり提出して、人が読めるようにする。
- ほかの理由の一時停止では、止めている間に PR をマージさせないよう、sacty が PR をドラフトに戻す。
  変更の無いやり直しで止めたときは、人が PR を確かめて判断する場面なので、人が外したドラフトを戻さない。
  戻すと、人がドラフトを外してからマージするまでの間に取り消されて、指摘を採らない判断を反映できない。
- 一時停止の理由を新しく2つ足した（`incomplete`・`unchanged`）。
  既存の `verification` は、以前の版の最終レビューの不合格を指し、不合格のまま進める操作の対象になるので、流用しなかった。

## 影響

- 実装の工程の指示に「完了の申告」の節が増える。申告のコードブロックは、実装の説明（PR の本文）からは取り除く。
- 完了と申告したのに実装し終えていない実行は、今までどおり PR になり、PR のレビューの子タスクが指摘する。
  その指摘のやり直しが何も変えなければ、この決定で止まる。
- 未完了が続くと、最大 3 回の実装の実行の費用がかかる。
- 一時停止の理由が増えたので、画面・お知らせ・ダッシュボードの文言に、2つの理由を足した。
- 自動でやり直す回数（3 回）は、人がまだ決めていない。すぐ止める形にするなら、回数の定数を変える。
- AI のレビューの往復の回数の上限と、進まないときに実装を上の段階のエージェントに上げることは、この決定に含めていない。
