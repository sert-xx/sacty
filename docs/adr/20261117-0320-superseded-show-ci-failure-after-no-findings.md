# 指摘なしの後に実装の PR の CI が失敗していたら、タスクの詳細に出す（読み続けず、自動では扱わない）

## 背景

sacty は、実装の PR の CI を待たない（[実装の最終レビュー（テストの実行）と PR の CI の待ちをやめ、PR のレビューの子タスクの指摘なしでドラフトを外す](20261112-0714-superseded-review-child-task-replaces-final-review-and-ci-wait.md)。CI を待たないことは、今も変わっていない）。
PR のレビューの子タスクは、レビューの時点の CI の状態を読み、終わっていないものは待たずに「実行中」と書く。

このため、子タスクが CI の実行中に「指摘なし」を出し、その後に CI が落ちても、PR を作ったタスクは人の承認待ち（マージ待ち）のままだった。
実際に、人が GitHub を見るまで、CI が落ちたことに気づけなかった。

はじめは、CI を読み続けて、失敗と回復を記録し、状態の表示（一覧・「あなたの出番」）にも出す形で作った。
レビューで、読み続ける仕組みへの指摘が6回続いた（ほかの PR の確認を遅らせる・未完了の通信が積み重なる・取り消された CI や空の一覧を通ったと扱う・一覧の取得の打ち切り・GitHub の API の利用の上限）。

## 決定

- 人の承認を待つ実装の PR（レビューの子タスクの指摘なしを待っていないもの）について、PR の確認で先頭のコミットの CI を読み、失敗していたら、先頭のコミットごとに1度だけ記録して、タスクの詳細に出す。
- CI を読み続けない。1回の PR の確認で読むのは1件だけ。先頭のコミットごとに、5分おきに、12回まで読む。
- 出すだけにする。実装の工程への差し戻し・再レビュー・ドラフトへの変更・CI の再実行・通知は行わない。
- 記録した後の変化（再実行で通ったなど）は、読まない・反映しない。状態の表示（一覧・「あなたの出番」）も変えない。

## 理由

- 求められたのは、CI が落ちたことが、タスクを見た人に分かること。自動でどこまで扱うか（差し戻す・再レビューさせる・CI を待ってから指摘なしにする）は、費用と待ち時間に関わる方針で、人が決めていない。
- 読み続ける仕組み（回復の判定・読む間隔の切り替え・件数が多いときの並べ方）は、正しく保つための条件が多く、レビューのたびに新しい抜けが見つかった。読む回数を先頭のコミットごとに決めれば、GitHub への問い合わせの数・1回の確認で待つ時間・未完了の通信の数が、どれも決まった上限になる。
- 回復を記録しないと、再実行で通った後も表示が残る。これを、状態の表示（一覧・「あなたの出番」）に出すと、古い結果が人の出番の理由として並ぶ。そこで、タスクの詳細にだけ、読んだ時刻と一緒に出し、その時点の結果であることを示す。
- 比べた案：レビューの子タスクが、CI が終わるまで判定を出さない。CI を待たない方針と食い違うので採らなかった。
- 比べた案：失敗を、AI のレビューの指摘として親タスクに届けて、実装をやり直させる。変更と関係の無い失敗（不安定なテスト・CI の環境）でもやり直しが始まり、費用がかかる。

## 影響

- 拾わない失敗がある：最初に読んでから1時間ほどたっても終わらない CI、その後に始まった CI、通った後に再実行されて落ちた CI。
- 表示は、PR を更新する・マージする・閉じるまで残る（再実行で通っても消えない）。
- CI の失敗は、タスクの詳細に出るだけなので、人がタスクを開かなければ気づかない（一覧の状態・通知には出ない）。
- 失敗が、変更によるものか、関係の無いものかは、sacty は判断しない。人が PR で確かめる。
- 仕様は [指摘なしの後の CI の失敗の表示](../spec/approval.md#指摘なしの後の-ci-の失敗の表示) にある。
