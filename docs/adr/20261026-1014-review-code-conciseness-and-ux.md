# 既定のレビューに、要らないコードを探す観点と、画面を撮って UX を見る観点を足す

- 日時: 2026-10-26 10:14 UTC
- ステータス: 採用
- 関係する PR・タスク: #229
- 置き換え元: なし
- 置き換え先: なし

## 背景

既定のレビュー用スキル（`review-dispatch`・`review-execution`）には、次の2つが欠けていた。

- 要らないコードを消す観点。設計書には書きすぎを探す D-10 があるが、コードでは C-5（保守性・設計）のチェックポイントの1行に「未使用」「過剰設計」があるだけだった。欠落を探す観点だけでは、レビューを回すほどコードが増え、認知負荷と技術的負債が高まる。
- 利用者にとって良い UI/UX かを見る観点。C-13（UI・アクセシビリティ）は部品の作り（状態の表示・ラベル・キーボード操作）をコードで見るだけで、操作の流れ・情報の配置・見た目の崩れは見ていなかった。好みの指摘を出さない規則もあり、UX の指摘はほぼ出なかった。

## 決定

- コードの必須の観点に C-15（簡潔さ・範囲）を足す。依頼のどれのためにもない変更、起こりえない状態への防御、使われないコード、今回の変更で使われなくなった既存のコード、1 つしか実装の無い抽象化、言い直すだけのコメント、重複したテスト、残す理由の無い互換のための層を見る。C-5 からは要らないコードの項目を移す。
- UI を変えるときの条件付きの観点に C-16（UX・利用者の流れ）を足す。C-13 は部品の作り、C-16 は利用者が目的を達せるかを見る。
- C-13 か C-16 を起動するとき、親は担当の起動の前に、Playwright でアプリの画面を撮って両方の担当に渡す（`screen-capture.md`）。
  - 撮るのは、すでにある Playwright とブラウザが動き、アプリを起動する方法が見つかるときだけ。Playwright やブラウザを新たに入れない。
  - 撮れないとき・途中で失敗したときは、画面を諦めて理由を記録し、担当はコードを読んで確かめる。レビューは止めない。

## 理由

- 要らないコードは、1 つ 1 つは正しく動くので、正しさや保守性の観点では指摘されにくい。設計書の D-10 と同じく、「依頼のどれのためにあるか」で読む専用の観点にしないと見落とす。必須にするのは、どの変更でも起こりうるため。
- 誤って要るコードを消させないよう、消してよい根拠（呼び出し元が無い・起こりえない）をコードで確かめることを求め、外部に公開する I/F は対象から外す。
- UX の問題（崩れ・重なり・入口の無さ・フィードバックの無さ）の多くは、コードからは見えず、画面を見れば分かる。
- 画面を撮れる環境はリポジトリと実行するイメージによって違う。撮れる環境を前提にするとレビューが止まるので、撮れるときだけ撮り、撮れなければこれまでどおりコードで確かめる。新たにブラウザを入れないのは、時間と容量がかかり、ネットワークに出られない環境もあるため。
- 撮るのは親が1回だけにする。担当ごとにアプリを起動すると、ポートと作業領域を取り合う（検証の実行と同じ理由）。

## 影響

- コードのレビューでは、担当が1つ増える（C-15）。UI を変えるときは、さらに C-16 が増え、画面を撮る時間（上限の目安 15 分）がかかる。
- 自己レビューでは `should` も直すので、C-15 の指摘で要らないコードが消えていく。
- 画面を撮るには、レビューを実行するイメージに Playwright とブラウザが入っている必要がある。入っていなければ、これまでと同じくコードだけで見る。
