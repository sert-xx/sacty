# sacty が作るコミットのメッセージは、リポジトリが Conventional Commits の形を定めているときだけ、その形にする

- 日時: 2026-11-04 02:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-301（A8）
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験 S5 r2 で、sacty が作ったコミットのメッセージが、タスクの題のまま（`<題>` と `sacty task <ID>` の2行）だった。対象のリポジトリは Commitizen の形（`feat:` など）を定めていたので、コミットのメッセージの検査（commitlint）や履歴の読みやすさの決まりに合わなかった。

## 決定

- **リポジトリがコミットメッセージの形を定めているときだけ、1行目の題に種類を付ける**（`feat: <題>`）。定めている、とみなすのは次のどれか。
  - Commitizen・commitlint の設定のファイルがある（`.czrc`・`.cz.json`・`commitlint.config.*`・`.commitlintrc*` など）
  - `package.json` に commitlint・commitizen の設定か依存がある
  - AGENTS.md・CLAUDE.md・CONTRIBUTING・README が、Conventional Commits・Commitizen・commitlint に触れる、または `feat:` と `fix:` の両方を例に挙げている
- **定めを読むのは、起点のコミット**。エージェントが書き換えた作業領域は読まない。再開しても同じコミットになる。読めなければ、定めが無いものとして題のままにする。
- **種類は3つだけ**。文書だけの依頼の実装と、要求要件・設計の PR のコミットは `docs`、不具合の修正は `fix`、それ以外は `feat`。題がすでに `type:` の形なら、重ねて付けない。
- **定めが無いリポジトリでは、今までどおり**題のままにする。2行目以降の `sacty task <ID>` は変えない。

## 理由

- 定めが無いリポジトリに `feat:` を付けると、履歴の形を勝手に変える。定めを確かめたときだけ付ければ、既存の振る舞いは変わらない。
- Conventional Commits は、Commitizen・commitlint が使う形で、実験で定めていたリポジトリもこれだった。ほかの形（チケットのキーを角括弧で付けるなど）は、設定から形を読み解けないので、今回は扱わない。
- 定めを作業領域でなく起点のコミットから読むのは、エージェントが書き換えた設定でコミットの形が変わらないようにし、コミットの日時と同じく、再開で同じコミットを作り直せるようにするため。
- 種類をエージェントに決めさせる案は、コミットを作るのが sacty で、エージェントの出力に依らず決まる範囲（文書だけか・不具合の修正か）で足りるので採らない。

## 影響

- 1行目の長さは変えない。長さの上限（commitlint の `header-max-length` など）を定めるリポジトリでは、長い題が収まらないことがある。
- commitlint が1行目の形を独自に決めている設定（`headerPattern`・`parserPreset`）と、`type-enum` で種類を限る設定は、読み解かない。種類が許されないと、リポジトリの検査に通らない。
