# 出力の JSON はデコードした形でも伏せ、書き出しのトークンは選んだ接続先に縛る

- 日時: 2026-10-18 04:36 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-131
- 置き換え元: なし
- 置き換え先: なし

## 背景

Codex Security の指摘が 2 つあった。

- 実行の出力の秘密値を伏せる処理は、デコード前の生の文字列にしか当たらなかった。レビューの JSON で秘密値の 1 文字を Unicode エスケープすると、
  伏せる処理を通り抜け、取り出すときの JSON のデコードで元の値に戻って、PR のコメントとして GitHub に投稿された。
- ゲートウェイは、許可リストを登録した実行（操作・文書）だけ、PF・MCP の接続先を絞っていた。書き出しは画面で接続先を 1 つ選ぶが、許可リストを
  登録しなかったので、トークンで選んでいないホストの PF・MCP も使えた。

## 決定

- 実行の出力を伏せる所（`executeLogged` と、認証ファイルの値を伏せる Docker の実行）で、生の文字列を伏せた後に、出力の JSON の文字列のうち、
  エスケープを戻すと値を含むものも伏せた文字列に置き換える（`redactEscaped`）。取り出す処理（レビュー・監査・再現のテストなど）ごとには
  入れない。
- 書き出しの実行も、操作・文書と同じく許可リストを登録する（選んだ PF、または選んだ MCP サーバーだけを置いたコンテキストの MCP）。

## 検討した案

- **取り出す処理ごとに、デコードした後で伏せる**：監査は既にそうしているが、JSON を取り出す処理はほかにも多く、足し忘れが起きる。出力を
  伏せる一か所で直せば、後から足す取り出しにも効く。
- **秘密値をエスケープした形をすべて作って伏せる**：1 文字ずつエスケープするかどうかの組み合わせが多すぎる。デコードした形で確かめるほうが
  確実である。
- **通常の工程も接続先を絞る**：工程はどの組織内 PF も使える設計（PBI-35）で、工程ごとに使う接続先を決める仕組みが無い。今回は、接続先を
  選んでいる書き出しだけを揃える。

## 結果

- sacty が出力の JSON をデコードしても、実行に渡した値は戻らない（わざと base64 などで漏らす出力は、これまでどおり伏せる処理では防げない）。
- 書き出しのエージェントが誘導されても、選んでいない接続先の権限は使えない。
