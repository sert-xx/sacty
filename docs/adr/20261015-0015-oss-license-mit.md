# sacty を MIT ライセンスの OSS として公開し、コントリビュートと脆弱性の報告の窓口を文書にする

- 日時: 2026-10-15 00:15 UTC
- ステータス: 採用
- 関係する PR・タスク: #103、PBI-96
- 置き換え元: なし
- 置き換え先: なし

## 背景

リポジトリは GitHub で公開しているが、LICENSE が無く、利用・改変・再配布してよいかが決まっていなかった。各 package.json は
`"private": true` で、`license` の欄も無かった。外から Issue・PR・脆弱性の報告を受ける手順も書いていなかった。

## 決定

- ライセンスを MIT にする（ステークホルダーが決めた）。リポジトリのルートに `LICENSE` を置き、著作権者は git の作者の名前
  `sert-xx`、年は最初のコミットの年の 2026 にする。
- ルート・apps・packages の各 package.json に `"license": "MIT"` を書く。`"private": true` は変えない（npm に公開するかは決めていない。
  `private` は誤って npm に公開しないための設定で、ライセンスとは別のため）。
- 依存のライセンスは、MIT のコードと一緒に使えて、sacty のソースにコピーレフトの義務を持ち込まないものに限る。
  今の依存の調べた結果は、このときの作業履歴に残す。
- ルートに `CONTRIBUTING.md`（開発の環境・変更の流れ・PR の前に確かめること・docs の方針の要点）と `SECURITY.md`
  （対象のバージョン・非公開の報告の仕方）を置き、README からライセンスとともにリンクする。
- 脆弱性の報告は、GitHub の非公開の報告（Security のタブの「Report a vulnerability」）で受ける。窓口が開いていないときは、
  詳細を書かない Issue で連絡を求めてもらう。個人のメールアドレスは載せない。
- 行動規範（CODE_OF_CONDUCT）は、今は置かない。

## 理由

- 著作権者を `sert-xx` にしたのは、すべてのコミットの作者がこの名前（と、GitHub のマージのコミットの表示名）で、GitHub のアカウント名とも
  一致し、個人の本名を新たに載せずに済むため。表記は PR でステークホルダーに確かめる。
- `private` を残したのは、npm への公開を決めていないため。外すと `npm publish` で誤って公開できてしまう。ライセンスの表示は
  `license` の欄と LICENSE で足りる。
- 非公開の報告を窓口にしたのは、メールアドレスを公開せずに、報告の内容を公開前に保守する人とだけ共有できるため。
- 行動規範を置かなかったのは、保守する人が1人で、違反の報告を受ける窓口（連絡先）と対応の体制をまだ決めていないため。
  窓口の無い行動規範は守らせる手段が無い。外からの参加が増えたら足す。

## 影響

- LICENSE の著作権者と年は、ステークホルダーの確認で変わることがある。
- 依存を足すときは、ライセンスが MIT と両立するか（GPL などのコピーレフトでないか）を確かめる。
- GitHub の非公開の報告は、リポジトリの設定で有効にする必要がある（この決定の時点では無効）。有効にするまでは、`SECURITY.md` の
  「窓口が開いていないとき」の手順になる。
