# コンテキストの mcp.yaml の command の MCP サーバーを、既定でホストで起動してゲートウェイ経由にし、コンテキストリポジトリを config.yaml と同じくらい信頼する

- ステータス: 採用
- 関係する PR・タスク: #89、PBI-84
- 置き換え元: [コンテキストリポジトリの HTTP の MCP サーバーは、既定でゲートウェイ経由にし、認証のヘッダーはホストで付ける](20261013-0411-superseded-context-http-mcp-via-gateway.md)（command のサーバーをコンテナの中で起動する部分）
- 置き換え先: なし

## 背景

コンテキストリポジトリの `mcp.yaml` のうち、HTTP の MCP サーバーはゲートウェイ経由（認証のヘッダーはホストで付け、
エージェントには実行ごとのトークンだけを渡す）にしていたが、`command`（stdio）の MCP サーバーはコンテナの中で起動していた。
そのため、`command` のサーバーの `env` の秘密情報は、値を環境変数でコンテナに渡していた。ホストで動かす MCP サーバーは、
`config.yaml` の `gateway.mcp_servers` に書いたものだけだった。

ステークホルダーの意図は「`command` のサーバーも、`gateway.mcp_servers` と同じようにホストで動かすのを既定にする」で、
プロジェクトのコンテキストの MCP がすべてコンテナから直接になっていたことで食い違いがわかった。

ホストでコマンドを動かすと、コンテキストリポジトリを編集できる人が、sacty を動かすホストで任意のコマンドを動かせることになる。
その扱い（許可の一覧や人の承認を設けるか）も決める必要があった。

## 決定

- `mcp.yaml` の `command` のサーバーは、既定でホストで起動し、エージェントにはゲートウェイの URL（`/ctx-mcp/<名前>`）と
  実行ごとのトークンだけを渡す。`env` の秘密情報はホストで取り出し、コンテナには渡さない。
- コンテナの中で動かすサーバーには `via_gateway: false` と書く（HTTP のサーバーと同じ項目。どちらも「ゲートウェイ経由か」の意味）。
- 信頼の前提：コンテキストリポジトリ（継承の親を含む）を `config.yaml` と同じくらい信頼する。許可するコマンドの一覧や、
  人の承認は設けない。この前提を利用者向けの説明に明記する。
- 起動・準備・中継・後片付けは、`gateway.mcp_servers` の仕組み（ホストの MCP サーバー）を使い回す。
- プロジェクトごとに分ける：ゲートウェイの中の名前は、プロジェクトと中身（名前・コマンド・引数・`env`・時間切れ・層の
  リポジトリと commit）から作り、実行のトークンごとに、そのタスクのプロジェクトのものだけを結びつける（`platforms.yaml` の
  外部 PF と同じ分離）。同じ中身でも、プロジェクトが違えば別のプロセスにする。
- 使い回しと停止：同じプロジェクト・同じ中身なら実行をまたいで同じプロセスを使う。中身が変われば新しく起動する。使っている
  実行が無くなったものは、同じプロジェクト・同じ名前の新しい中身が使われたらすぐに、そうでなければ最後に使ってから30分で止める。
- 作業ディレクトリ：そのサーバーを書いた層のリポジトリの写し（`SACTY_HOME/context-mcp/layers`。`.git` は写さない）。
  取得した層は実行の後に消えるため、プロジェクトと層の commit ごとに写して持つ。
- 準備を待つ上限は120秒（`startup_timeout_sec` がそれより長ければ、その値）。コマンドがホストに無いときは、どの MCP サーバーの
  どのコマンドかと、ホストに入れるか `via_gateway: false` を書くよう、作業履歴に警告を残す。

## 理由

- 秘密情報をコンテナに渡さないこと・エージェントの設定を HTTP の MCP に揃えることは、HTTP のサーバーと `gateway.mcp_servers` で
  すでに採っている形で、`command` のサーバーだけが例外になっていた。
- 信頼の前提はステークホルダーの決定。`config.yaml` も、編集できる人がホストでコマンドを動かせる点で同じであり、許可の一覧や
  承認を設けると、コンテキストの変更のたびに人の操作が要る。代わりに、コンテキストリポジトリを編集できる人を絞る運用を求める。
- 項目を `via_gateway` に揃えたのは、HTTP と `command` のどちらでも「ゲートウェイ経由か（ホストか、コンテナから直接か）」の
  意味で通り、新しい項目を覚えずに済むため。`run_on: host | container` のような新しい項目も考えたが、HTTP の既存の項目と
  二重になるので採らなかった。
- 中身に層の commit を含めたのは、作業ディレクトリのファイル（スクリプトや設定）が変わったときにも起動し直すため。
  そのため、規約だけを変えた commit でも起動し直す（安全側に倒した）。
- プロジェクトをまたいで同じ中身のプロセスを共有しないのは、MCP サーバーが作業ディレクトリやプロセスの中に状態を持ちうるため。
- 30分・120秒の値は、実行の間隔と、`npx`・`uvx` の初回の取得にかかる時間を見込んだもの。測って決めた値ではない。

## 影響

- これまでコンテナの中で動いていた `command` のサーバーは、更新の後、ホストで動く。ホストに `npx`・`uvx` などが無ければ、
  入れるか `via_gateway: false` を書く必要がある。相対パスは、作業領域ではなく、層のリポジトリの写しから解決する。
- ホストで動くサーバーは、デーモンと同じ利用者・同じ環境変数で動く。コンテキストリポジトリへの書き込みの権限は、
  ホストでのコマンドの実行の権限と同じ重さになる。
- MCP のツールの結果に秘密情報が含まれると、エージェントに渡る（`gateway.mcp_servers` と同じ。sacty は伏せない）。
- プロジェクト・commit ごとに層の写しを `SACTY_HOME` に持つ（使われなくなったら消す）。
