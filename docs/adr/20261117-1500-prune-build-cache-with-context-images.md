# デーモンのコンテキストのイメージの片付けでも、3日使っていないビルドキャッシュを消す

- 日時: 2026-11-17 15:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-388、#425
- 置き換え元: [`sacty image build` の後に、古い版のイメージと使っていないビルドキャッシュを片付ける](20261106-1440-superseded-prune-old-images-after-build.md)（ビルドキャッシュを消す期間を、7日から3日に変えた。ほかの決定はそのまま）
- 置き換え先: なし

## 背景

ビルドキャッシュを消すのは、`sacty image build` を人が実行したときだけだった（7日より長く使っていないもの）。
デーモンは、使わなくなったコンテキストのイメージを自動で消すが、そのときはビルドキャッシュを消していなかった。
コンテキストのイメージは、定義の中身が変わるたびに新しい名前で作り直すので、sacty を動かし続けているだけで、ビルドキャッシュが増え続けた。
2026-11-17 の実測では、ビルドキャッシュが 49.8GB・288 件で、うちイメージと層を共有していない分が 29.8GB だった。
288 件の大半は数日前に使われたもので（4日前が 86 件、9〜12日前が約 100 件）、7日の期間では、そのうち半分ほどしか対象にならなかった。

## 決定

- デーモンが、使わなくなったコンテキストのイメージを片付けるとき、続けて、3日より長く使っていないビルドキャッシュも消す（`docker builder prune -f --filter until=72h`）。
- `sacty image build` の片付けの期間も、7日から3日に変える。デーモンの片付けと同じ期間にする。
- 期間は設定にしない。
- デーモンの片付けでは、今のイメージの片付けの仕組みをそのまま使う。
  - 条件：作っている最中・読み直しの最中・設定やコンテキストを読めていないときは消さない。
  - 上限：イメージの片付けと合わせて2分。過ぎたら docker を止めて先に進む。デーモンを止めるときも止める。
  - 失敗（docker の失敗・時間切れ）は、ログに出すだけにし、イメージの作成・読み直し・タスクの実行に関わらせない。
- イメージの一覧を取れなくても、消すイメージが無くても、ビルドキャッシュは消す。
- デーモンのビルドキャッシュの片付けは、前に成功してから6時間が経つまでは走らせない（定数。設定にしない）。
  - 前に成功した時刻は、メモリーの中だけに持つ。デーモンを起動した後の最初の片付けでは走らせる。
  - 失敗・時間切れ・停止では時刻を進めず、次の片付け（片付けの条件を満たしていれば、遅くとも5分後の読み直し）で試し直す。
  - `sacty image build` の片付けは、実行のたびに走らせる（変えない）。
- デーモンのログには、結果を解釈せずに出す。
  - 成功：片付けを実行したことと、docker の出力の最後の行（消すものが無かったときも出す）。
  - 失敗：docker の終了コードと出力の最後の行。失敗が続けば、片付けのたびに出す（抑えない）。
  - 打ち切り：時間切れとデーモンの停止で文言を分け、ビルドキャッシュの片付けを始める前か後かも分ける。

## 理由

- 期間を3日にすること、デーモンの片付けと `sacty image build` で同じ期間にすること、設定の項目を足さないことは、リポジトリの持ち主が決めた（2026-11-17）。
- イメージを消してからキャッシュを消すのは、イメージを消しても層がビルドキャッシュに残るため（置き換え元の ADR と同じ理由）。
- イメージの片付けと同じ所で消すのは、作成・読み直しと重ならない条件と、上限の時間・デーモンの停止で止める仕組みが、すでにあるため。
  別の時機（定期の処理を足すなど）は比べていない。
- 間隔を置くのは、イメージの片付けが読み直しのたび（5分ごとを含む）に動くのに対し、消す対象は「3日使っていないもの」で、毎回走らせても消えるものがほとんど変わらないため。
  間隔を置けば、成功の行は1日に数行で済み、結果を解釈せずにそのまま出せる。
  失うのは、3日を過ぎたキャッシュが消えるまでの遅れが、最大で間隔の分だけ増えること。
- 6時間という値は、リポジトリの持ち主が決めた（2026-11-17。2回目のレビューの「数時間〜1日」の範囲から）。
- この PR の途中では、毎回走らせて、出力から空いた容量を読み、消すものが無いとき（0）と、前と同じ失敗の行を出さない作りにしていた（1回目のレビューの対応）。
  docker の出力の解釈と、前に出した行の覚えが増え、同じ失敗が続いていることがログから分からなくなるので、やめた（2回目のレビューの指摘）。
- 失敗の行を抑えないのは、消せていないことが事実で、続いていることがログで分かるようにするため。
- docker の出力の形は、何も消えない条件（`docker builder prune -f --filter until=87600h`）で、標準出力の最後の行が `Total:<タブ>0B`、終了コードが 0 だった（リポジトリの持ち主が、2026-11-17 に実物で確かめた）。
  実際に消えたときの出力の形は、確かめていない（未確認）。出力は解釈しないので、形が違っても、最後の行がそのままログに出る。
- 打ち切りの文言を分けるのは、デーモンの停止のときには次の片付けが無く、2分の上限に掛かり続けているのか通常の停止なのかを、ログで見分けられるようにするため。

## 影響

- `docker builder prune` は Docker 全体のビルドキャッシュが対象なので、sacty 以外が作ったキャッシュも、3日使っていなければ消える（置き換え元の ADR のときと同じ扱い。期間が短くなった）。
- 3日より長く作り直していないイメージは、次に作るときに層のキャッシュが効かず、時間がかかる。
  [イメージの作成でパッケージの取得をキャッシュする決定](20261112-1526-image-build-cache.md)の cache マウントの中身もビルドキャッシュの一部なので、7日ではなく3日使わなければ消える。
- ビルドキャッシュが多いと、2分の上限の中で消し終えないことがある。そのときは打ち切ってログに出し、次の片付け（片付けの条件を満たしていれば、遅くとも5分後の読み直し）でまた消す。
  打ち切ったときに、それまでに消した分が残るか・やり直しになるかは、確かめていない（未確認）。
  docker が動かないなど失敗が続く間は、読み直しのたび（5分ごと）に失敗の行が出る。
- 設定（`config.yaml`）か、どれかのプロジェクトのコンテキストを読めない間は、イメージの片付けと同じ条件なので、ビルドキャッシュも消さない。ログにも出ない。
  この間は、「遅くとも5分後の読み直しで試し直す」も成り立たない。読めない状態が続くと（認証切れ・リポジトリの削除など）、キャッシュは増え続け、手での片付け（`sacty image build`・`docker builder prune`）が要る。
  `builder prune` は残すイメージの一覧を使わないので、ビルドキャッシュの片付けだけ条件を緩める案がある（3回目のレビューの指摘）。この PR では採らず、動きを変えていない（決まっていない）。
- デーモンを起動し直すたびに、最初の片付けでビルドキャッシュの片付けが1回走る。
- 間隔は、壁時計（`Date.now`）で測る。時計が戻って、前に成功した時刻より前になったときは、間隔が過ぎたものとして走らせる。時計が少し戻っただけ（前に成功した時刻より後）なら、戻った分だけ次の片付けが遅れる。
- 成功の行は標準出力に、失敗と打ち切りの行は警告（`console.warn`）に出す。
- 期間は変えられない。必要になったら設定を足す。
- 仕様書：[デーモンの起動と終了](../spec/daemon-lifecycle.md)の「コンテキストのイメージの作成」、[エージェントの実行](../spec/agent-execution.md)の `sacty image build` の項。
