## 背景

sacty 自身のユーザードキュメントを読みやすく直したとき（#371）、直した所の多くは、エージェントが文書を書くときの決まりに無いことだった。

- 最初に、何の文書か・誰のための文書かが書かれていない。
- 節が、書き足した順に並んでいる。節が、細かい条件の箇条書きから始まる。
- 経緯（「これまでどおり」「以前は」）と、位置での参照（「下の」）が残っている。
- 構成や流れが、文章だけで書かれている。

既定のコンテキストと工程の指示を調べると、次のことが分かった。

- 既定のスキル `writing` は、読む人が前提（暗黙知）を持っているとして、情報を絞ることを決まりの最初に置いている。
  PR の本文や要求要件・設計には合う。
  その場にいなかった人が後から読むユーザーガイド・手順書・README では、読む人が知らない語や前提まで「読む人がすでに知っていること」として省かれ、読めなくなる。
- 文書作成の工程（`document`）の指示も、初版を最小限にする決まり（`minimalDraftLines`）を使っていた。
  読者はタスクが示す人としていたが、「初版は最小限にする」「書くか迷ったら書かない」は、どの読者にも当てていた。
  文書の組み立て方の指示は無かった。
- 図と画像の決まりは、書く側のどこにも無かった。
  レビューの観点（U-4）は画像の参照切れを見るが、いつ図にするか・スクリーンショットをどう使うかは示していなかった。
- 文書作成の工程は、提出の前のセルフレビューの対象ではなかった。
  文書向けのレビューの観点（U-1〜U-4：コードとの同期・手順の成立・読み手の適合・静的品質）はあるが、原稿には使われていなかった。
- テンプレート「ドキュメント構築」は、全体の構成と主な処理の流れを書かせるが、図を求めていなかった。

## 決定

- `writing` は、読む人がその件の前提を知っているかで、文章の種類を2つに分ける。
  種類を決めることを、決まりの最初に置く。
  - 承認・判断・返信のための文章（PR の本文、レビュー、コメント、要求要件・設計、調査の結果、報告）は、情報を絞る（変えない）。
  - 後から読まれる文書（ユーザーガイド、手順書、README、運用の文書）は、読む人が目的を果たすのに要ることを、省かずに書く。
    読む人が知らない語と前提は、要る情報として書く。
    目的に要らないこと（内部の仕組み・経緯・検討の過程）は、こちらでも書かない。
  - 種類は、文章の名前ではなく、読む人で決める。
    PR や Issue でも、読む人がその件を知らなければ、背景と再現の手順を省かない。
  - 経緯や判断を残すための文章（変更履歴、リリースノート、決定の記録、議事録、コミットメッセージ）には、「今の状態だけを書く」を当てない。
- `writing` に、資料を2つ足す。
  前からある決まり（改行、箇条書きと表、語と言い回し、確認の懸念、スコープ、簡潔さ）は変えない。
  - `references/documents.md`：後から読まれる文書の組み立て方。
    最初に書くこと、並べる順、節の最初の要点、番号付きの手順と結果・確かめ方、今の状態だけを書くこと、ほかの節を名前とリンクで指すこと、既存の文書への書き足し方。
  - `references/figures.md`：図と画像。
    - 図にするのは関係だけにし、1つの図で伝えることを1つにする。
    - 図の要点は本文にも書く（図を、本文の並べ直しにはしない）。
    - 形式は、書き出し先で決める。
      テキストで書いた図を表示できる所ではテキスト、表示できないが画像を置ける所では画像にし、どちらもできない所では図にせず、箇条書きか表で書く。
    - スクリーンショットは絞り、撮れないとき・画像を置けないときは、撮ったことにしない。
- 文書作成の工程の指示は、初版を一律に最小限にする決まりをやめ、読者が前提を知っているかで書く量を決めさせる（`documentDraftLines`）。
  - 前提を知っている読者（報告・議事録・草稿）には、最小限に書かせる。
  - 前提を知らない読者（ユーザーガイド・手順書・README）には、省かずに書かせる。
  - 組み立て方と、図・画像の要点を、指示にも書く。
  - 原稿には画像のファイルを付けられないので、図は、原稿の中にテキストで書く形式にさせ、書き出し先がそれを表示できると分かっているときだけ使わせる。
    画像が要る所は、画面の名前と見る所を言葉で書かせ、原稿の末尾の未確認事項にまとめさせる。
- 文書作成の工程も、提出の前のセルフレビューの対象にする（`SELF_REVIEW_STEPS`）。
  - 主対象の種類は、原稿の種類でエージェントに決めさせる（ユーザーガイド・手順書・報告などは `user-doc`、設計書・比較や判断の記録などは `design-doc`）。
  - 原稿はリポジトリのファイルにしないので、下書きを一時ファイルに書いて対象にさせ、リポジトリの検証は実行させない。
  - 担当には、決めた読者と、読者が前提を知っているかを伝えさせる。
    前提を知らない読者に向けた原稿では、読者が知らない語・前提を削る指摘に従わせず、前提を知っている読者に向けた原稿では、記述を足す指摘は `must` だけを直させる。
  - 外部に直接書く文書は、書く前の下書きをセルフレビューし、直し終えてから書かせる。
  - 外部の既存のページを直すときは、レビューの範囲を、直した箇所とその直しが直接必要にした箇所にさせ、範囲の外への指摘ではページを直させない。
  - 差し戻しの直しは、前回の提出がパスしていて、前回の原稿が空でなければ、指摘に関わる観点だけで見させる（実装の工程と同じ）。
  - 調査・作業の工程は、対象にしないままにする。
- テンプレート「ドキュメント構築」に、次のことを足す。
  - 全体の構成（依存の向き）と、主な処理の流れ（通る順と分かれ道）を、図でも示す。
  - ドキュメントの最初に、何について書いたものか・どの作業の前に読むかを書く。
  - 図の形式は、リポジトリの既存の図に合わせる（図が無い・同じ形式で作れないときは、Markdown の中にテキストで書ける形式）。

## 理由

- 「情報を絞る」は、読む人が前提を持っているから成り立つ。
  前提を持たない読む人に同じ決まりを当てると、用語と前提の説明が削られる。
  決まりを弱めずに、当てる文章を分けた。
  承認のための文章では、情報が多いと読む人が確かめずに承認してしまうという、もとの理由がそのまま残る。
- 種類を分ける軸を「読む人が前提を知っているか」にしたのは、文書の名前（報告書・手順書）より、依頼と置き場所から判断しやすいため。
  報告書は、関係者が読むなら絞り、後から別の人が読むなら省かずに書く。
- 資料を足す形にしたのは、`writing` が、必要なときに資料を読む作り（SKILL.md に要点、references に例）のため。
  PR の本文などを書くときに読む量を増やさない。
- 図の形式を1つに決めなかったのは、既定のコンテキストが、あらゆるリポジトリと書き出し先（GitHub、Confluence など）に渡るため。
  テキストで書いた図を表示できる所では、テキストにする（差分が読め、エージェントも読み書きできる）。
  表示できないが画像を置ける所では、画像にし、後から直せる形で残す。
  図を作るスキル（既定の `drawio`）は、画像にするときだけ使わせる（このスキルは、どの図も、まず draw.io の形式のファイルにするため）。
- 「図にしか無い情報を作らない」とせずに「図の要点は本文にも書く」としたのは、本文に図の中身をすべて書かせると、図が本文の言い直しになり、文章が短くならないため。
- 画面を撮れないときの決まりを書いたのは、文書作成の工程のエージェントは、ふつう対象の画面を開けないため。
  無い画像への参照や、想像で作った画像が原稿に入ると、読む人は誤った画面を信じる。
- 文書作成の原稿で、図を使う条件を絞ったのは、原稿に画像のファイルを付けられないため。
  工程の成果は原稿の文字だけで、承認の画面にも書き出しにも、画像は渡らない。
  画面の Markdown は、テキストで書いた図（Mermaid など）も描かない。
  表示されない図や、無い画像への参照を、原稿に入れさせない。
- 経緯や判断を残すための文章を別に書いたのは、変更履歴や決定の記録は、後から読まれるが、経緯そのものが中身のため。
  「今の状態だけを書く」を当てると、中身が無くなる。
- 文書作成のセルフレビューで、主対象の種類をエージェントに決めさせるのは、原稿の種類（手順書か、設計書か）がタスクごとに違い、sacty が実行の前に決められないため。
- 外部に直接書く文書を、書く前に見直させるのは、外部に書いた文書は承認を待たずに読まれるため。
  同じ理由で、外部の既存のページを直すときは、レビューの範囲を直した箇所に絞らせる。
  スキルのセルフレビューは、文書の全体を見て `must` と `should` を直すので、範囲を絞らないと、依頼に無い所を、承認の前に書き換えてしまう。
- 担当に読者を伝えさせるのは、原稿の書き方の決まり（読者で書く量を決める）と、レビューの基準を食い違わせないため。
  伝えないと、前提を知らない読者に要る説明が「書きすぎ」として削られ、関係者向けの報告には説明が足される。
- 調査・作業の工程を対象にしないままにしたのは、今回の問題（後から読まれる文書の読みやすさ）に関わらないため。
  調査の結果は、初版を最小限にする決まりのままにする。
- レビューの観点（U-3 など）は変えなかった。
  今の観点（想定読者、用語の説明、最初に知るべきことが先にあるか、構成、例）が、足した決まりの主な所を見ている。
  節の最初の要点や経緯の言い回しのような細かい所は、書く側が `writing` の「見直し」で確かめる。

## 影響

- 文書作成の工程の費用が、セルフレビューの分（担当のサブエージェントを含む）だけ増える。
  予算の上限は、今のまま守る。
- 文書作成の成果物のカードと承認の画面に、セルフレビューの結果（パス・パスしていない・記録なし）が出る。
  この変更より前の記録には出ない。
- 前提を知らない読者に向けた原稿は、これまでより長くなる。
  短くしたいときは、人が差し戻しで求める。
- プロジェクトのコンテキストに同じ名前のスキル `writing` があると、そのスキルが既定のものを上書きするので、足した資料は読まれない。
  工程の指示は「あれば、それに従う」としているので、そのときは、指示に書いた要点だけが効く。
- 足した決まりで、エージェントの書く文書がどれだけ読みやすくなるかは、実際のタスクでは確かめていない。
