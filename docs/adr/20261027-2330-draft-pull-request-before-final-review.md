# 実装の PR を最終レビューの前にドラフトで作り、CI を待ってからゴールガーディアンが判定し、合格したらドラフトを外してレビューへ進める

- 日時: 2026-10-27 23:30 UTC
- ステータス: 採用
- 関係する PR・タスク: #239
- 置き換え元: [「PR作成」の工程をなくし、実装の工程の中で PR を作って承認を待つ](20261015-1430-superseded-implement-step-opens-pull-request.md)（最終レビューに合格した後に実装の PR を作る部分）
- 置き換え先: なし

## 背景

実装の PR は、ゴールガーディアンの最終レビューに合格した後に作っていた。
このため、次のことが起きていた（利用者の報告、2026-10-27）。

- 合格するまで PR が無いので、実装がどのような状態になっているかを確かめにくい。
- CI の上での振る舞い（ワークフローの修正など）は、PR を作らないと確かめられない。
  ゴールガーディアンは作業領域でテストを実行するが、CI の結果は見ていなかった。
- 最終レビューに続けて通らずに止まったタスクは、人がよいと判断しても PR のレビューへ進められない。
  再開すると実装をやり直すだけで、PR が無いので人がレビューする場所も無かった。

## 決定

- 実装の工程が終わったら、最終レビューの前に、sacty が実装をプッシュして実装の PR をドラフトで作る（更新する）。
  レビュー用のラベルは付けず、承認待ちにもしない（`PullRequestPublished` の `verifying`・`draft`）。
  リポジトリがドラフトの PR を使えなければ、ドラフトでない PR にする。
  承認待ちの後に差し戻してやり直した実装は、PR をドラフトに戻す。
- sacty は、PR の先頭のコミットの CI を、マージの後の監視と同じ仕組みで待つ（PR の確認のたびに読む。CI が無ければ 5 分、上限は 60 分）。
  待つ間は費用がかからない。
  結果を `PullRequestCiFinished` に記録してから、最終レビューに進む。
- 最終レビューは、作業領域（手元）と PR の状態を合わせて判定する。
  sacty が読んだ CI の結果と失敗したジョブのログの抜粋を、指示ではないデータとして渡す（GitHub の読み取りの中継があれば、ゴールガーディアンは gh で PR も読める）。
  CI の失敗が変更によるものなら不合格、変更と関係の無いものと確かめられたら「人が確かめること」に回す。
  sacty は、CI の結果だけでは機械的に不合格にしない。
- 合格したら、ドラフトを外し（GraphQL の `markPullRequestReadyForReview`）、レビュー用のラベルを付けて、実装の承認待ちにする。
  外せなければ、承認待ちにせずに止める（再開すると、ここからやり直す）。
- 実装の検証が続けて通らずに止まった（`verification`）タスクは、人の判断で「レビューへ進める」ことができる（`VerificationOverridden`）。
  最終レビューはやり直さず、合格したときと同じくドラフトを外してラベルを付け、実装の承認待ちにする。
  PR の本文に、人が不合格のまま進めたことを書く。
- 既存の PR を引き継ぐタスクは、これまでどおり、検証に通った後に人の PR へ積む（最終レビューの前には積まない）。

## 理由

- 最終レビューの前に PR があれば、人はいつでも実装の状態を見られ、CI の結果も得られる。
  ドラフトにしておけば、まだレビューの段階ではないことを示せ、レビュー用のラベルで別のタスクのレビューが始まることも無い。
- CI を待つのは sacty にした。
  エージェントに待たせると、待つ間も費用がかかり、実行の時間の上限にも当たる。
  マージの後の監視で、CI を待って読む仕組み（`readCi`）がすでにあった。
  待たずにすぐ最終レビューをする案は、CI が終わっていないことが多く、CI の結果を判断に入れられないので採らなかった（利用者の選択、2026-10-27）。
- CI の失敗の扱いは、ゴールガーディアンに判断させた（利用者の選択、2026-10-27）。
  CI には、秘密情報が無い・外部のサービスが落ちているなど、変更と関係の無い失敗がある。
  機械的に不合格にすると、実装をやり直しても直らないのに、やり直しを繰り返す。
  作業領域のテストの環境による失敗と同じ扱いにした。
- 人がレビューへ進める操作は、ゴールガーディアンの判定を人が覆すことになる。
  止まったタスクだけに限り、作業履歴（actor が person）と PR の本文に残すことで、後から確かめられるようにした。
- 引き継いだ既存の PR は人の PR なので、通っていない実装を最終レビューの前に積むと、その PR のレビュアーに未完成の変更を見せることになる。
  このため、これまでの扱いを変えなかった（CI を見る必要があれば、後で別に決める）。

## 影響

- 最終レビューの前に、CI の分だけ待つ（CI が無いリポジトリは 5 分、CI が終わらなければ最大 60 分）。
- 検証の途中の実装が、ドラフトの PR として対象のリポジトリに公開される。
  最終レビューに通らなければ、やり直した実装で同じ PR を更新する。
  中止すると、これまでどおり PR を閉じる。
- 最終レビューの前のコミットは、実装の工程が終わった時刻で作る。
  検証に通った後も内容は同じなので、同じコミットのままドラフトを外す（CI を2回動かさない）。
- PR をドラフトにする・外すには、gh のアカウントのトークンに、PR を書き換える権限が要る（PR を作る権限と同じ）。
