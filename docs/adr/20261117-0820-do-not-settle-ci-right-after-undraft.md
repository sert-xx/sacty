# 実装の PR の CI を、最初に読んだ回と、ドラフトを外した直後には「読み終わり」にしない

- 日時: 2026-11-17 08:20 UTC
- ステータス: 採用
- 関係する PR・タスク: #418、PBI-381
- 置き換え元: [指摘なしの後の CI の失敗の表示を、CI を読んでいる間に通ったら消す](20261117-0440-superseded-clear-ci-failure-when-ci-passes-while-reading.md)（失敗が無い・通った先頭を、すぐに読むのをやめる部分）
- 置き換え先: なし

## 背景

人の承認を待つ実装の PR の CI を、先頭のコミットごとに、5分おきに、12回まで読んでいる（置き換え元の ADR）。
失敗の表示が無く、CI が1つ以上あって、すべて終わっていて失敗が無ければ、その先頭は、その回で読むのをやめていた（読み終わり）。

sacty は、レビューの子タスクの「指摘なし」で PR のドラフトを外し、同じ PR の確認の中で CI を読む。
対象のリポジトリのワークフローが、ドラフトを外したこと（`pull_request` の `ready_for_review`）で走る設定のとき、新しい実行が GitHub の一覧に載る前に読むと、前からある実行（ドラフトの間に終わったもの）だけを見て、読み終わりにする。
その後に CI が落ちても、表示は出ない。この表示がいちばん要る場面で、出ないことになる。

同じことは、次の場面でも起きる。

- ドラフトを外した後に人がコミットを足すと、sacty は PR をドラフトに戻し、再レビューで指摘なしになったら外し直す。再レビューの間に、足した先頭の CI（プッシュで始まったもの）を読み終わりにしていると、外し直したことで始まる CI を読まない。
- 失敗の表示を出している間に、新しい先頭の、前からある実行だけを見て「通った」として、表示を消して読み終わりにする。

GitHub の文書には、イベントから実行が一覧に載るまでの時間の記載が無い（遅れることがあると書かれているのは、`schedule` だけ）。
`ready_for_review` は、`pull_request` の既定の種類（`opened`・`synchronize`・`reopened`）に入っていないので、影響を受けるのは、ワークフローに明示したリポジトリだけ。
実物のリポジトリで、遅れは測っていない（未確認）。

## 決定

- その先頭を読み終わりにするのは、次のどちらからも、5分（`PR_CI_SETTLE_MS`。読み直しの間隔と同じ）以上たった後の読み取りだけにする。
  - その先頭を、最初に読んだ時刻。
  - sacty が、その PR のドラフトを外した時刻（指摘なしで外した・外し直した・重ねた PR の付け替えで外した）。
- それより前の読み取りでは、失敗が無くても、間隔の後に読み直す。失敗の表示を出していて、通っていたら、表示は消すが、読み終わりにはしない。
- 読み終わりにした先頭も、その後に sacty がドラフトを外したら、読み終わりを取り消して、読み直す。
- 読む期間・回数の上限は変えない（先頭のコミットごとに、5分おきに、12回まで）。読み終わりにしなかった読み取りも、取り消した後の読み取りも、同じ上限に数える。読んだ回数は、数え直さない。
- 1回の PR の確認で読むのは1件だけ、のままにする。読み続ける仕組み・並列の読み取り・間隔の切り替えは、足さない。
- ドラフトを外した時刻は、デーモンのメモリーに持つ。記録（イベント）には足さない。

## 理由

- 長さを、読み直しの間隔（5分）と同じにしたのは、読み取りが間隔ごとにしか起きないため。これより短くしても、次に読むのは5分後で、動きは変わらない。これより長くすると、読み終わりまでの読み取りが1回増える。5分は、ドラフトを外した直後の読み取りの、次の1回で、読み終わりにできる最も短い長さ。
- 5分で足りるかは、確かめていない。GitHub の文書に遅れの上限は無く、実物でも測っていない。ふだんは、イベントから実行が一覧に載るまでは数秒、と見ている（文書の裏づけは無い）。GitHub の側の障害で5分より遅れたときは、拾えない。
- 最初に読んだ時刻からも数えるのは、デーモンを再起動すると、ドラフトを外した時刻を忘れるため。再起動の直後に、外した直後の先頭を読んでも、最初の読み取りでは読み終わりにしない。レビューの子タスクを使わない PR（人だけがレビューする PR）でも、同じ決まりになる。そのぶん、どの先頭も、読み終わりまでに少なくとも2回読む（これまでは1回）。
- ドラフトを外した時刻を、記録（イベント）から求めないのは、仕組みを小さく保つため。記録から求めると、投影に項目が増える。メモリーに持つ方法で困るのは、外してから5分のうちに再起動したときだけで、それは、最初に読んだ時刻から数えることで補える。
- 読み終わりを取り消すのは、足したコミットの再レビューが5分より長くかかると、外し直す前に読み終わりにしてしまうため。回数を数え直すと、上限が増える（読む回数の上限を変えない、という決定に合わない）ので、数え直さない。
- 比べた案：ドラフトを外した後、決まった回数だけ読むまで読み終わりにしない。再レビューの間の読み取りを数えてしまい、外し直した直後の読み取りで読み終わりにする。採らなかった。
- 比べた案：指摘なしを待っている間・再レビューの間は、CI を読まない。失敗の表示を出す対象が変わる（人が足したコミットの CI の失敗が、再レビューが終わるまで出ない）。採らなかった。
- 比べた案：ドラフトを外した直後だけ、短い間隔で読み直す。間隔の切り替えは、読み続ける最初の版で、指摘が続いた仕組み。採らなかった。

## 影響

- どの先頭も、CI がすべて終わっていて失敗が無くても、少なくとも2回読む。GitHub への問い合わせは、先頭のコミットごとに1回分増える（上限は、12回のまま）。
- 失敗の表示を、読み終わりにしない間に消した後、同じ先頭の CI が落ちていたら、出し直す。
- 拾わないもの：
  - ドラフトを外してから5分たっても、一覧に載らない CI。
  - 回数の上限に達した先頭の、その後にドラフトを外したことで始まる CI。
  - 人が GitHub でドラフトを外したことで始まる CI のうち、その先頭を読み終わりにした後に始まったもの（sacty が外したときと違い、読み終わりを取り消さない）。
