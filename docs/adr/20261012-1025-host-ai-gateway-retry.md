# AI の呼び出しをホストの sacty のゲートウェイ経由にでき、ゲートウェイが API キーを持ってレート制限（429）などをリトライする

- 日時: 2026-10-12 10:25 UTC
- ステータス: 採用
- 関係する PR・タスク: #39、PBI-37
- 置き換え元: なし
- 置き換え先: なし

## 背景

利用者の環境の Bedrock にはレート制限があり、429 が返るとエージェントがエラーで止まっていた。#38 では、Bedrock の API キーを
実行のときにコンテナへ渡し、Codex が直接 Bedrock に送っていた。

## 決定

- sacty の起動時に、ホストでゲートウェイを動かす。127.0.0.1 の空いているポートで待ち受け、コンテナからは `host.docker.internal`
  （`--add-host host.docker.internal:host-gateway`）で届く。実行中のトークンだけを受け付ける。
- config.yaml のエージェントに `via_gateway: true` を書くと（このときは Codex × Bedrock）、Codex の組み込みの Bedrock のプロバイダーの
  向き先（`base_url`）だけをゲートウェイにする。コンテナの `AWS_BEARER_TOKEN_BEDROCK` には実行ごとのトークンを入れ、ゲートウェイが
  本物の API キーに差し替えて上流に転送する。API キーはコンテナに渡さない。
- 429・5xx・接続の失敗は、Retry-After（無ければ1秒から倍にしていく間隔）で待ってリトライする。上限（`gateway.retry.max_attempts`・
  `max_wait_sec`。既定 8 回・600 秒）は config.yaml で変えられる。上限に達したら、レート制限であきらめたことがわかる文
  （`gave up after N attempt(s) ... 429 (rate limited)`）で返し、エージェントは利用上限として一時停止する（再開でやり直せる）。
- 待ち時間の上限は、成功するまでの一続きの失敗で数える。上限に達した後は、待たずに1回だけ転送する。成功すると数え直す。
- 応答はストリーミングのまま返し、返し始めた後はリトライしない。コンテナとの接続が切れたら（一時停止・中止）、待つのもリトライもやめる。
  本文の受信の途中で接続が切れても、そのリクエストだけの終わりとして扱い、デーモン全体は止めない。
- リトライした実行は、回数・原因・待った時間を作業履歴に残す（`AiRequestsRetried`）。
- 後の外部の PF の API・MCP のタスクは、このゲートウェイに機能を足す。

## 理由

- 429 のリトライをゲートウェイに任せるのは、レート制限の 429 でエージェントが止まっていたため（PR の本文）。
- 向き先だけを変えるのは、Codex の組み込みの Bedrock のプロバイダーは `base_url` だけを上書きでき、Bedrock 固有の振る舞いをそのまま
  使えるため。`AWS_BEARER_TOKEN_BEDROCK` にトークンを入れるのは、Codex がその値を Bearer で送るため（PR の本文）。
- 上限の後は待たずに1回だけ転送するのは、Codex 自身も失敗すると5回やり直すので、待ち時間が何倍にもならないようにするため（PR の本文）。
- 127.0.0.1 と実行中のトークンに限るのは、エージェントのコンテナからだけ使え、ほかのアプリからは使えないようにするため（PR の本文）。
- 本文の受信の途中の切断を受け止めるのは、未処理の ECONNRESET でデーモン全体が終わり、ほかの並行のタスクや管理の API まで止まるため（レビュー）。

## 影響

- 「利用上限で一時停止」の説明は、サブスクリプションの利用上限だけでなく、API のレート制限にも当てはまる文にした。
- ゲートウェイはデーモンと同じプロセスで動くので、ゲートウェイの未処理の失敗はデーモン全体に響く。
