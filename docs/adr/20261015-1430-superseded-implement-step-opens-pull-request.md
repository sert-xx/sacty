# 「PR作成」の工程をなくし、実装の工程の中で PR を作って承認を待つ

## 背景

工程の並びは「…→ 実装 → PR作成（`pr`。仕様書では成果物チェック）」だった。要求要件・設計は、それぞれの工程の中で PR を作り、人が PR の
マージで承認する。実装には承認が無く、別の工程 `pr` で sacty が PR を作り、人が PR のマージで承認していた。

人が確かめる点は同じなのに、実装だけ別の工程になっていた。これは MVP の工程の並び（要求要件・設計・実装・PR作成）の名残だった。画面の
名前「PR作成」も、要求要件・設計でも PR を作るので、何の工程かわかりにくかった（ステークホルダー、2026-10-15）。

## 決定

- 工程 `pr` をなくす。工程の組み合わせ・オーケストレーターへの指示・工程の一覧・画面から外す（標準は 調査 → 要求要件 → 設計 → 実装、
  不具合の修正は 調査 → 再現 → 実装）。
- 実装を、承認のある工程にする。実装の工程の中で、エージェントの実行・テスト・ゴールガーディアンの最終レビュー・手戻りの後、合格したら
  sacty が実装の PR を作り（今までの `pr` の工程の処理）、実装の承認待ちにする。PR のマージで実装を承認すると、タスクは完了する。
- 承認・差し戻し・PR のマージでの承認・PR の指摘の取り込みの扱いを、要求要件・設計とそろえる。今の `pr` の工程にあった振る舞い（変更なしの
  完了・PR テンプレート・レビュー用のラベル・タスクブランチからの PR・マージの後の監視・PR の指摘の戻し先・予算・中止で閉じる・子タスク）は、
  実装の工程で同じく動かす。
- 「PR作成」「成果物チェック」という言い方は、工程・承認の名前としては使わない（実装・実装の承認と呼ぶ）。以前の版を説明するところだけに残す。
- 古い記録は捨て、互換の層は作らない。工程 `pr` を含むタスク（処理中のものを含む）と、つながったタスク（分割の親子・修正のタスクと元の
  タスク）を、デーモンの起動時に作業履歴から消し、件数をログに出す。`step_agents.pr` は設定の誤りにする。

## 理由

- 人が確かめるもの（PR）と確かめ方（マージ）が要求要件・設計と同じなので、同じ形にすれば工程の意味を迷わない。
- 承認待ちになる前に PR を作る間の状態は、実装の工程の中の「PR の作成の待ち」として持つ。工程を分けなくても、一時停止・再起動・PR の作成の
  失敗の後に、実装をやり直さずに PR の作成からやり直せる。
- まだ本番で使っていないので、古い記録を読む互換の層（`pr` を実装に読み替えるなど）は作らない。読み替えを持つと、二つの形を
  ずっと保つ必要がある（ステークホルダー、2026-10-15）。
- 作業履歴は追記専用だが、読めない記録を残すとデーモンが起動できないので、起動時に1回だけ、該当するタスクの記録を消す。タスク分割の親子と
  修正のタスクは、片方だけを消すと、残った方が消えたタスクを待ち続けたり作り直したりするので、一緒に消す。

## 影響

- 以前の版で作ったタスクのうち、工程 `pr` を含むものは、処理中でも消える。GitHub のブランチと PR、作業領域は残る（利用者が片付ける）。
- 開いている PR（PBI-107・108・109 など）と同じ所を触るので、後からマージする側が追従する。
