# 要求要件の受け入れ条件を EARS 形式で書かせ、既定のスキル ears-requirements を同梱する

- 日時: 2026-10-17 01:30 UTC
- ステータス: 採用
- 関係する PR・タスク: #132、PBI-122
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件の工程の指示は、受け入れ条件を「検証できる形の箇条書き」で書くとだけ求めていた。
書き方がタスクごとにばらつき、条件・きっかけ・振る舞いの区別や異常系の抜けを、承認する人が読み取る必要があった。
ステークホルダーから、要件定義を EARS（Easy Approach to Requirements Syntax）の形式で整理し、そのためのスキルを既定のコンテキストに置くよう求められた。

## 決定

- 既定のコンテキストに、EARS の文型で要求要件を書くスキル `ears-requirements` を置く。
  - 文型（常時・イベント駆動・状態駆動・望まない振る舞い・オプションと、その組み合わせ）を日本語と英語で持つ。
  - 1文1要求、ID（`R-1` など）、合否を決められる応答、異常系、実装の方法を書かないこと、見直しの観点を決める。
  - 依頼した人の指示と対象のリポジトリの要求要件の決まりを、このスキルより優先する。
- 要求要件の工程の指示で、受け入れ条件を EARS の形式で書かせ、スキルがあれば従わせる。
  文型・ID・異常系の書き方は、指示にも短く書く。
- 設計など、ほかの工程の指示と出力の形は変えない。

## 理由

- 文型で条件ときっかけと応答が分かれると、抜けと曖昧さに気づきやすく、設計のテスト観点に対応づけやすい。
- スキルにすると、プロジェクトのコンテキストで上書き・削除でき、sacty の外の使い方でも同じ書き方を使える。
- プロジェクトがスキルを消しても形式が崩れないよう、要点は指示にも残す。
- 設計の工程は「受け入れ条件をすべて網羅する」テスト観点を求めていて、受け入れ条件が EARS になってもそのまま使える。

## 影響

- 要求要件の成果物の受け入れ条件が、ID 付きの EARS の文になる。以前のタスクの成果物は変わらない。
- プロジェクトのコンテキストに同じ名前のスキルを置けば、既定のスキルを上書きできる。
