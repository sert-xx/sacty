# 監査の出力の JSON が文字列の中で崩れていても、直して読み、読めなければ何が読めなかったかを残す

- 日時: 2026-11-03 09:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-293
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験 S16 r3（findings F41）で、監査の深掘りの担当が出した JSON のメモリーの本文に、エスケープしていない二重引用符（`"1,200"・"abc"` など）が入っていた。sacty は JSON として読めず、「監査を実行できなかった」とした。深掘りの費用（約 $1.36）が無駄になり、理由の文からは何が悪かったか分からなかった。出力の中身（3 つの原因・提案）は十分に出ていた。

## 決定

- **監査の 2 つの出力（大まかな監査・深掘り）は、崩れを直しながら読む**：エスケープしていない二重引用符・文字列の中の制御文字・JSON にない `\` のエスケープ・閉じる括弧の前のカンマを直す。二重引用符は、次に来る文字がその場所の区切りでなければ文字列の一部とみなす。JSON として読める答えが最後の答えなら、直さずそのまま使う。
- **読めなければ、何が読めなかったかを失敗の理由に残す**：JSON が無い・壊れている位置（JSON の行と文字・前後の文字）・項目が足りない、の 3 通り。記録済みの大まかな監査の結果・終えた深掘り・費用は残す（もともと失敗の記録は、それらを消さない）。
- **指示にも、二重引用符のエスケープを書く**。
- **AI への読み直しの依頼（再実行）は足さない**。

## 理由

- 崩れの多くは引用符で、文脈から確実に直せる。直して読めば、費用をかけた深掘りを捨てずに済む。
- AI に直させる再実行は、費用がもう一度かかり、同じ崩れを繰り返しうる。出力の形を強制する仕組み（構造化出力）は、サブスクリプションで動く CLI 型のエージェントには使えるとは限らない。
- 直した結果は、これまでと同じ検査（形・上限・宛先・根拠の ID）を通すので、誤って直した場合も、使われるのは形の合う値だけ。

## 影響

- 引用符のずれで区切りの判定を誤ると、文字列の切れ目が違って読まれることがある。その結果が形に合わなければ、これまでどおり読めない扱いになる。
- ほかの工程の JSON（判定・自己レビューなど）は、今回は直さない。同じ崩れが出たら、同じ読み方を広げる。
