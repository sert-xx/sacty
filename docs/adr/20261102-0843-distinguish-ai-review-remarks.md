# sacty 自身の AI のレビューの指摘を、人の指摘と区別して扱う

- 日時: 2026-11-02 08:43 UTC
- ステータス: 採用
- 関係する PR・タスク: #279、PBI-275
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty のレビューのタスク（レビュー用のラベルで取り込んだもの）は、作ったタスクの PR（要求要件・設計・実装）に、プロジェクトのアカウント
（人と同じアカウント）の名前でレビューを投稿する。その指摘は、[取り込みの経路に関わらず](20261025-2245-import-sacty-reviews-from-any-intake.md)
作ったタスクに PR の指摘として届く。届いた指摘は人の指摘と同じに扱われ、実験（S14・S18・S19）で次のことが起きた。

- 作業履歴に「指摘5件（人間）」と出た。5件のうち4件は AI のレビューだった。
- 差し戻しの回数に数えられ、同じ工程への差し戻しの上限（3回）に早く達した。監査も AI の指摘を「人の差し戻し」と数えた。
- 人が書いた「さっきの指摘は無しで」を、AI のレビューのことと読んだ。
- 古い head へのレビューが遅れて届き、実装が余分に1回走った。

## 決定

- AI のレビューの指摘は、今までどおり作ったタスクに届ける。ただし人の指摘と区別する。
- 見分けるのは投稿の目印（`sacty-review:`）で、アカウントでは見分けない。取り込みの記録（`PullRequestReviewImported`）と、差し戻しの指摘に、出どころ（`source: sacty_review`）を残す。
- AI のレビューの指摘だけの回は、人の差し戻しの回数と、同じ工程への差し戻しの上限に数えない。人の指摘が混ざる回は数える。費用の上限は変えない。
- 作業履歴・承認の画面・ダッシュボードの品質の信号・監査の根拠の件数で、人の指摘と分けて表示・集計する。
- 取り込むときに、レビューが対象にした PR の head（コミット）が PR の今の head と違えば、取り込まずに捨て、理由を作業履歴に残す（`PullRequestReviewDiscarded`）。
- エージェントへの指示で、人の指摘と AI のレビューの指摘を分けて渡し、人の指摘にある「さっきの指摘」「前の指摘」などは人の指摘を指すと伝える。

## 理由

- AI のレビューの内容は妥当なことが多く、届けないと、sacty の自己検証の価値が減る（人が決めた方針）。区別だけを足せば、人の回数・上限・監査・「さっき」の参照先が AI に引きずられない。
- アカウントで見分けると、人と同じアカウントで投稿される構成では見分けられない。目印は、レビューのタスクが投稿するときに必ず入れる。
- 上限に数えない案ではなく、そもそも届けない案は採らなかった（AI のレビューの指摘で直せるものを、人の確認まで残すことになる）。AI のレビューの繰り返しの費用は、予算の上限で止める。
- 古い head へのレビューは、すでに直された内容に対する指摘なので、取り込むと余分な実行になる。対象のコミットが分からない投稿は、古いかどうか分からないので取り込む。PR の head を読めないときは、AI のレビューだけ次の確認に回す（指摘を落とさず、古いものを取り込まないため）。

## 影響

- AI のレビューだけの差し戻しは、actor が `sacty` になる。ダッシュボードの品質の信号に「AI のレビューの差し戻し」、監査の根拠に「AI のレビューの指摘」が増える（過去の記録は、出どころを持たないので人の指摘のまま）。
- 監査の根拠の件数の記録（`AuditSurveyed` の `counts`）に種類（`aiReviewRemark`）が増える。以前の記録は、無い種類を 0 として読む。
- 規則は[承認と差し戻し](../spec/approval.md#ai-のレビューの指摘)・[取り込み](../spec/intake.md)・[監査](../spec/audit.md)・[アーキテクチャ](../spec/architecture.md)に記す。
- 引き継いだ人の PR など、別の sacty が投稿した（このデーモンの台帳に無い）AI のレビューは、目印だけでは区別せず、これまでどおり扱う。
