# GitHub の時刻がこの機械の時計とずれても取り込みが遅れないよう、PR の指摘の待ち時間と検索の読んだ位置を、この機械の時計で抑える

- 日時: 2026-11-01 13:52 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-270
- 置き換え元: なし
- 置き換え先: なし

## 背景

2026-11-01 に、取り込みが約1時間遅れる例が2つあった。

- PR の指摘の取り込み：PR へのコメントを、コメントの時刻の約1時間後に取り込んだ（同じタスクの別の PR では約2分）。
- PR のレビューの取り込み：レビュー用のラベルを付けた PR のレビューのタスクが、ラベルから約62分後にできた（取り込みの間隔は 60 秒）。

どちらも、この機械の時計を GitHub の時刻と比べる、または GitHub の時刻をそのまま持つ作りに当たっていた。調べると、2026-11-01 の 08:00〜09:00（UTC）ごろ、GitHub が付けるコメント・レビュー・PR・ラベルなどの時刻が、実際の時刻（この機械の時計。NTP で合っていた）より1時間先になっていた。HTTP の `Date` ヘッダーは合っていた。根拠は作業履歴に書いた。

## 決定

- PR の指摘の取り込みで待つ2分は、各フィードバックについて、GitHub の時刻と、デーモンが初めて見た時刻（メモリーだけ）の早い方から数える。
- 取り込みの検索（GitHub）の読んだ位置は、その検索を始めた時刻より先には進めず、先なら始めた時刻に戻す。

## 理由

- 2つとも、時計が合っていない相手（GitHub）の時刻を、この機械の時計と同じ軸で扱っていたのが原因。GitHub の時刻は、見た時点で「もう書かれている」ことの上限にはならないが、見た時刻は上限になる。
- 待ち時間を「見た時刻」だけで数える案は採らなかった。デーモンを再起動した直後に、前から付いていたコメントを2分待たせるため。早い方を使えば、時刻が合っているときの動き（コメントの時刻から2分）は変わらない。
- 読んだ位置を戻す案は、毎回「検索を始めた時刻から少し前」に固定する案より変更が小さい。検索のページ送りは GitHub の更新日時のまま使い、持ち越す位置だけを抑える。
- GitHub の時刻が先に進んでいる間は、その間に更新されたものを毎回読み直す。取り込み済みの判定はタスクの取り込み元の番号で行うので、二重には取り込まない。
- GitHub の時刻が、合っていた状態から遅れる側へ変わったときは、持った位置より古い更新日時が付くことがあり、この決定では防がない（時刻が戻る側の変化を、検索を始めた時刻で抑えるだけ）。

## 影響

- [PR の指摘の取り込み](../spec/approval.md#pr-の指摘の取り込み)と[取り込み](../spec/intake.md)の仕様書を直した。
- 先に進んだ時刻の間に更新された PR・Issue は、時刻が戻るまで毎回検索の結果に含まれる。
