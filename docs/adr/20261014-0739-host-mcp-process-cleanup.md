# ホストの MCP サーバーは自分のプロセスグループで起動して子孫ごと止め、前回の残りは記録と所有元のデーモンで確かめて次の起動で片付ける

- 日時: 2026-10-14 07:39 UTC
- ステータス: 採用
- 関係する PR・タスク: #86、PBI-78
- 置き換え元: なし
- 置き換え先: なし

## 背景

`sacty up` を止めても、ホストの MCP サーバー（`gateway.mcp_servers`）のプロセスが親を失って残っていた。SDK の `StdioClientTransport` は直接の子にしか
シグナルを送らないので、`npx` のようなラッパーが起動した子孫（と、標準入力が閉じて先に終わったラッパーの子）が残る。デーモンが突然落ちたときに
残ったものも片付けていなかった。

## 決定

- ホストの MCP サーバーは、自分のプロセスグループで起動する。止めるときは、標準入力を閉じて自分で終わるのを待ち、残ったグループと子孫を SIGTERM で止め、
  猶予の後に SIGKILL する。MCP サーバーが自分で終わったとき（`exit` で検知する）も、残った子孫を止める。
- デーモンのシャットダウンでは、実行の後片付けを待たずにホストの MCP サーバーを止め始める。例外などで終わるときも、グループに SIGTERM を送る。
- 起動したプロセスと子孫を、PID と開始時刻の組で `SACTY_HOME/host-mcp/processes/` に記録する。記録には、書いたデーモン（所有元）の PID と開始時刻も持たせる。
- デーモンの起動のときに、前回の残りを片付ける。止めるのは、所有元のデーモンが終わっていて、いま動いているプロセスの PID と開始時刻が記録と一致するもの
  （と、その子孫・記録どおりに動いているリーダーのグループ）だけ。デーモン自身・その親・PID 1・デーモン自身のグループは止めない。ps が使えないときは何も止めない。
  記録していない子孫は止めない。
- compose のサービスも、起動したデーモンをコンテナのラベル `io.sacty.owner` に残し、そのデーモンが動いているものは起動時の片付けで止めない。
  ラベルの無いものはこれまでどおり止める。所有元を確かめられないときは止めない。
- Windows は対象外。

## 理由

- 子孫ごと止めるのは、SDK の transport が直接の子しか止めず、ラッパーの子孫が残っていたため（PR の本文・コミット）。
- PID と開始時刻の組で確かめるのは、PID が再利用されたほかのプロセスを止めないため（PR の本文・コミット）。
- 記録していない子孫を止めないのは、安全な側に倒すため（PR の本文の補足）。
- 後片付けを待たずに止め始めるのは、CLI の30秒の強制終了に巻き込まれないため（PR の本文）。
- 所有元で判定するのは、レビューで、同じ SACTY_HOME で2つ目の `sacty up` を起動すると、1つ目が使っている MCP サーバーを止めると指摘されたため。
  レビューは「同じホームの二重起動を回収の前に排除する」案も挙げたが、#85 で同じホームの2つ目の sacty は警告して動き続ける扱いになっているため採らなかった
  （レビューへの返信）。所有元で判定すれば、listen の前に片付けても衝突しない。
- compose に同じ判定を足したのは、docker は SACTY_HOME をまたいで共有されるので、別のホームの sacty のサービスも止めていたため（レビューへの返信）。
- `exit` で検知するのは、子孫がパイプを開いたままだと `close` が来なかったため（レビューの指摘・コミット）。

## 影響

- デーモンが突然落ちる直前（最後の記録から10秒以内）に起動された子孫で、リーダーが先に終わっていたものは、次の起動でも片付けられないことがある。
- Windows ではこの片付けが効かない。
- 以前の sacty が起動した（ラベルの無い）compose のサービスは、起動時の片付けでこれまでどおり止まる。
