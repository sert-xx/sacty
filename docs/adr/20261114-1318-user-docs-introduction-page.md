# ユーザードキュメントに紹介のページを置き、その画面は紹介のためのデータで撮る

- 日時: 2026-11-14 13:18 UTC
- ステータス: 採用
- 関係する PR・タスク: #369
- 置き換え元: なし
- 置き換え先: なし

## 背景

ユーザードキュメントは、設定・コマンド・画面の操作のページでできていて、sacty をはじめて知る人が「何ができて、なぜ使うのか」をつかめるページが無かった。
利用者から、一般的なプロダクトの紹介のように、図と画面を使って「使ってみよう」と思えるページを求められた。長い文章や実装の細部から始まると、はじめての人が面食らうため。

最初の版を書いた後に、仕様書と突き合わせて見直すと、次の問題が見つかった。

- 短く言い切ろうとして、実装と合わない文になっていた。
  - 「AI のコンテナに渡るのは、その実行のあいだだけ使えるトークン」：AI のサービスの認証は、コンテナに渡る。
  - 「AI の呼び出しも、設定すればゲートウェイを通せる」：通せるのは、Codex を Bedrock か OpenAI 互換の接続先で使うときだけ。
  - 「あなたに届くのは、AI のレビューを通った PR」：ドラフトで待たせるのは実装の PR だけで、sacty はマージを止めない。
  - 冒頭の図が、承認を最後の1回だけに描いていた（承認は工程ごとにある）。
- 画面の画像に、設定やトラブルの説明のためのデータで撮った既存のスクリーンショットを使っていた。
  エラーや上限で止まったタスクが多く、監査の画面にはモックの表示があり、紹介の文と合わない所もあった。

## 決定

- ユーザードキュメントに、紹介のページ `introduction.md`（英語の版は `introduction.en.md`）を置き、目次の先頭に並べる。
  リポジトリの README からもリンクする。
- 紹介のページは、困りごとと、それに答える特長を1対1で並べ、図と画面を中心に、短い文で書く。
  工程・設定・コードの名前、既定値、手順は書かず、詳しいページへリンクする。
- 書くことは、ほかのユーザードキュメントと同じく実装と一致させる。
  できること・できないことを言い切る文は仕様書で確かめてから書き、設定が要ること・条件があることは省かない。
  守られていないもの（AI のサービスの認証はコンテナに渡る）も書く。
- 紹介のページの画面は、紹介のためのデータ（`scripts/docs-screenshots/seed-intro.mjs`）で撮る。
  ふだんの使い方が伝わる状態（あなたの出番・マージの後の監視・完了と、作業履歴の監査の記録）だけを入れ、止まったタスクは入れない。
  - 撮影は場面（`docs`・`intro`）ごとにデータを分け、場面を指定して撮れるようにする。
  - データを書く道具は `seed-lib.mjs` に分け、2つのデータで使う。
- 規則は `docs/README.md` の「ユーザードキュメントの書き方」に書く。

## 理由

- 紹介を `docs/user/README.md`（概要と目次）に書かず、別のページにしたのは、図と画面で長くなり、目次が下に追いやられるため。
- 困りごとと特長を1対1にしたのは、特長だけを並べると、読む人が自分の問題との関係を自分で探すことになるため。
- 紹介でも言い切りを仕様書で確かめるのは、はじめての人は紹介の文をそのまま信じて、任せる範囲を決めるため。
  特に、鍵と権限の扱いを実際より安全に書くと、利用者の判断を誤らせる。
- 既存のスクリーンショットを使い回さないのは、あのデータが、止まった状態・エラーの状態を説明するために作ってあるため。
  紹介に使うと、ほとんどのタスクが止まっているように見える。
- 比べたほかの案と、採らなかった理由は次のとおり。
  - 既存のデータ（`seed.mjs`）に紹介のためのタスクを足す：すべてのプロジェクトをまたぐ画面（ダッシュボード・お知らせの件数）が変わり、既存のスクリーンショットをすべて撮り直すことになる。
  - 既存のスクリーンショットを切り抜く：撮り直せなくなり、画面を変えたときに合わせられない。
  - 紹介のページには画面を載せない：実際の画面が無いと、図だけでは使う様子が伝わらない。

## 影響

- 利用者に見える振る舞いを変える PR では、紹介のページの記述と図が合わなくならないかも確かめる（[docs の入口](../README.md)）。
  紹介のページは具体的な値や名前を書かないので、直す所は少ないが、役割の分担・鍵の扱い・承認の流れを変えるときは直す。
- 承認待ちの PR があるデータでは、デーモンが PR のレビューの子タスクを作って実行しようとする。
  紹介のためのデータには、レビューを終えた子タスクを入れてある。データを直すときは、これを保つ。
- スクリーンショットを撮るときの設定で、新しい版のお知らせを止めた（`update_check: false`）。
  リリースの有無とネットワークで、撮るたびに画面が変わるのを避けるため。既存の場面にも効く。
- タスクの詳細の画面は、紹介のページに載せていない。
  撮るときは GitHub を読めず、AI のレビューの状況が「分かりません」と出るため。
