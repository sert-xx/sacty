## 背景

文書作成（`document`）の工程には、承認の前に外部の接続を渡さない決まりがあり、次のどれも渡していなかった。

- sacty の既定のコンテキストと、プロジェクトのコンテキスト（規則・スキル・MCP サーバー・外部 PF）
- ホストの外部 PF（`gateway.platforms`）と MCP サーバー（`gateway.mcp_servers`）
- GitHub の読み取りの中継

そのため、文書作成のエージェントに差し戻しで MCP・外部 PF・スキルを使うよう指示しても、「そのようなスキルは無い」と答えた。
コンテキストのプレビューはプロジェクトとして合成した結果を出すので、文書作成の工程に渡らないことは画面からはわからなかった。
利用者からは、文書を作るうえでも外部 PF で情報を集める必要がある、文書作成の工程に変な縛りを入れないでほしい、という依頼があった。

## 決定

- 文書作成の工程にも、ほかの工程と同じく、合成したコンテキスト（既定のコンテキストとプロジェクトのコンテキスト）・ホストと
  コンテキストの外部 PF・MCP サーバー・GitHub の読み取りの中継を渡す。
- ゲートウェイで、文書作成の実行の PF・MCP を絞らない（絞るのは、接続先を決めて使う作業（`operation`）と書き出しだけ）。
- 文書作成の指示から「外部の接続・プロジェクトのコンテキストを渡していない」を除き、渡していることと、それらで情報を集めることを伝える。
  原稿そのものは外部やリポジトリに直接書かず出力し、承認の後に書き出す、という流れは変えない。

## 理由

- 文書は、外部の資料（チケット・既存の文書・GitHub の Issue など）や組織の規約・スキル（既定の文章用スキル `writing` を含む）を
  もとに書くことが多い。人がタスクの本文や差し戻しに貼って補う前の方式は、手間が大きく、利用者の依頼に合わない。
- 外部 PF・MCP の使える範囲は、ほかの工程と同じく、ゲートウェイの許可（`allow`）とコンテキストの設定で決まる。文書作成だけを
  さらに絞る理由は、承認の前に外部の接続を渡さないという決まりのほかに無く、その決まりを利用者の依頼でやめた。
- GitHub への投稿は、ほかの工程と同じく、承認の後に sacty がする（エージェントは出力で頼むだけ）ので、承認を外部への反映の境界にする
  仕組みは保たれる。

## 影響

- 文書作成のエージェントは、承認の前に外部 PF・MCP を呼べる。PF の `allow` に書き込みの API があれば書き込めるのは、ほかの工程と同じ。
  指示では原稿を外部に直接書かないよう伝えるが、強制はしない。
- 文書作成の実行でも、コンテキストの取得に失敗すれば、ほかの工程と同じく実行の失敗にして一時停止する。
- 実行ごとに `ContextResolved` を記録する。

  [ゲートウェイ](../user/gateway.md)に記載する。
