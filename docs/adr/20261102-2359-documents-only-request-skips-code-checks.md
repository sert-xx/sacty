# 文書だけの依頼では、テストのコマンドにコードの検証を入れず、依頼の判断と差分が食い違ったら最終レビューの前に止める

- 日時: 2026-11-02 23:59 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-284
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験（S2。Go の大きなリポジトリに Markdown のドキュメントを書き起こす依頼）で、オーケストレーターが、文書だけの依頼に、リポジトリ全体の検証（`go test`・`golangci-lint`・pnpm のビルド）を `testCommand` に設定した。
実行のイメージに Go が無く、最終レビューで止まった。差分が文書だけならツール不足で止めない扱いは [PBI-158 の ADR](20261031-1510-docs-only-missing-tools-to-human-checks.md) で入れたが、要らない重い検証を設定すること自体は変わらなかった。

また、`noTests`（テストの仕組みが無い）は、起点のコードにテストのファイルがあるリポジトリでは矛盾として止まる。文書だけの依頼でも、`testCommand` を空にする道が無かった。
オーケストレーターへの指示では、「ツールが選べるイメージのどれにも無くても `testCommand` は書く」と「`testCommand` はそのイメージで動くコマンドにする」が順序なく並んでいた。既定のイメージの説明も、実際の中身（作業用の CLI・drawio・セキュリティの検査の道具が入る）より少なかった。

## 決定

- 成果物が文書のファイルだけの依頼（オーケストレーターの答えの `documentsOnly: true`）では、オーケストレーターに、文書の変更が及ばないコードの検証（テスト・lint・型の検査・ビルド）を `testCommand` に入れさせない。リポジトリに文書向けの検証（リンクの検査・markdown の lint・文書のフォーマットなど）があればそれだけを書かせ、無ければ `testCommand` を空にして `noTests` に根拠を書かせる。
  コードも変える依頼では、これまでどおり、変更が及ぶ範囲の検証のすべてを `&&` でつなぐ（[検証のコマンドが複数あるとき](20261021-2237-join-verification-commands.md)は変えない）。
- 文書だけの依頼（`documentsOnly`）は、`noTests` を答えたときの、起点のコードのテストのファイルを探す歯止めを行わない。
- 文書だけの依頼の判断は、実装の差分で確かめる。最終レビューの前に、差分に文書のファイル以外が1つでもあれば、ゴールガーディアンを実行せず、判定も記録せずに一時停止する（`verify.documentsOnlyContradicted`）。再開のときに、人がテストの扱いを決め直せる（決めたら `documentsOnly` の判断は使わない）。
  文書のファイルの一覧は、PBI-158 の差分による判定（`isDocumentsOnly`）と同じものを使い、オーケストレーターへの指示にも同じ一覧を示す。
  `documentsOnly` は、実装を含み、不具合の修正でない組み合わせのときだけ受け付ける。
- オーケストレーターの指示で、`testCommand` のツールを持つイメージを優先して選ばせ、どのイメージにも無いときだけ、`testCommand` を書いたうえで `imageReason` に理由を書かせる。
- 既定のイメージの説明を、実際の中身に合わせる。説明と中身が食い違わないよう、イメージを作る手順（`packages/cli/docker/`）と突き合わせるテストを足した。

## 理由

- 文書の変更が及ばない検証は、費用と時間を使い、実行のイメージにツールが無ければ止まる原因にもなる。依頼の段階で、要らない検証を設定させないのが根本の対策。
- 文書だけの依頼で `testCommand` を空にするには `noTests` が要るが、テストのファイルがあるリポジトリでは使えない。文書だけの依頼に限って歯止めを外すが、判断が誤っていたとき（コードも変わったとき）に、検証なしでコードの変更が通ると、歯止めを外した意味が逆になる。そのため、判断を差分で確かめ、食い違ったら最終レビューの前に止める。
- 食い違ったときの止め方は、PBI-158 の「差分が文書だけでなければ止める」と同じ向き（止める側に倒す）。再開で人がテストの扱いを決められるようにして、止まったままにならないようにした。
- 採らなかった案
  - `testCommand` を文書向けの最小のコマンドに、sacty かオーケストレーターが推測して作る案：リポジトリに根拠の無いコマンドを推測で作らない決まりと衝突する。
  - 必要なツールがイメージに無いことを、実装の前に申告させて止める案：今回は見送りとした（人の判断）。

## 影響

- `StepsChosen` に `documentsOnly`（`true` のときだけ）が増える。無い記録は従来どおり。
- 文書だけの依頼と判断されても、差分にコードがあれば最終レビューの前に止まる。オーケストレーターが誤って文書だけと判断しても、コードの変更が検証なしで通ることは無い。
