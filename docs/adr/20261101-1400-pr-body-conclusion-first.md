# 実装の PR の本文を、結論を冒頭に置き、要求要件・設計は要点とリンクにし、表のセルを短くする

- 日時: 2026-11-01 14:00 UTC
- ステータス: 採用
- 関係する PR・タスク: #268、PBI-264
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験（11 シナリオのうち記録のある 10）で、sacty が作る実装の PR の本文が読みにくいことが、8 つのシナリオで出た。

- 承認済みの要求要件の全文を再掲している（最大で本文 24 KB・135 行）。
- 「観点 → テスト → 実行結果」の表の 1 セルに、テスト名と 900〜1,500 文字のレビュー文が入る。
- 結論（最終レビューの判定・人が確かめること）が本文の末尾にある。冒頭に「何を変えたか」の要約が無い。
- エージェントの作業の報告（「コミット・プッシュはしていません」など）と、「合格。合格。」の重複が残る。

PR の本文はレビューの入口で、人が最初に読む。要求要件・設計はすでに別の PR で人が承認している。

## 決定

テンプレートを使わない実装の PR の本文（`buildPullRequestBodyText`）を、次のようにする。テンプレートに沿わせる本文（`buildPullRequestBodyParts`）は、見出しの形を保ち、中身だけ同じ規則にする。

1. 冒頭に「結論」を置く。変更の要約、最終レビューの判定と所見の頭、人が不合格のまま進めた記録、人が確かめることを入れる。人が確かめることと不合格のまま進めた記録は、長さの上限でも省かない（`keep`）。
2. 承認済みの要求要件（再現のタスクは不具合の再現）は、最初の段落の頭と、全文のある場所（マージで承認した PR へのリンク。無ければタスクの画面）にする。
3. 観点の表は「観点・テスト・最終レビュー」の 3 列にし、セルは短くする。入力・期待結果・テスト全件・所見は、折りたたみに出す。最終レビューの全文は、結論の頭より長いときだけ折りたたむ。
4. 実装のエージェントの説明から、作業の経過の報告の文を機械的に除く。実装の指示にも、説明が PR の本文にそのまま載ることと、経過の報告は書かないことを書く。
5. 最終レビューの所見の頭の判定の語は除く（判定は別に書く）。

## 理由

- 結論を冒頭に置くと、人が全文を読まなくても、マージの前に確かめることがわかる。長さの上限で後ろが省かれても、確かめることは残る。
- 要求要件・設計は人が承認済みで、全文の置き場所（PR・タスクの画面）がある。本文に重ねると、読む量が増え、本文が上限（65,000 文字）に近づく。要点とリンクなら、どの承認の経路でも全文に行ける。
- 表のセルの長文は、表が崩れて読めない。折りたたみに移せば、情報は減らない。
- 経過の報告は、指示だけでは消えなかった（実装の指示にすでに「コミットやプッシュはしない」とあっても書かれた）。そのため、指示と機械的な除去の両方を行う。除去は、話題の語と状態の語を両方含む短い文だけに絞り、機能や内容を指す語（プッシュ通知・コミットメッセージ）は残す。誤って除く可能性は残るが、除かれるのは本文の報告の 1 文に限る。
- 比べた案：エージェントに PR の本文を書き直させる案は、費用・時間・出力の揺れが増えるので採らなかった（[PR の本文の規則を決まった形にした ADR](20261014-1517-pr-body-follows-repository-template.md) と同じ考え方）。

## 影響

- 実装の PR の本文の要求要件に、受け入れ条件の全文は出ない。レビューする人は、リンクの PR か、タスクの画面で全文を見る。
- 既存の PR を引き継いだタスクは PR の本文を変えないので、影響しない。
