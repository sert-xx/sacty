# 最終レビューの判定基準を、同じ定義のまま実装の工程に先に渡す

- 日時: 2026-11-08 03:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-315
- 置き換え元: なし
- 置き換え先: なし

## 背景

最終レビューで不合格になると、実装と検証をまるごとやり直す。
不合格の理由になる基準（範囲外の変更・既存のテストの期待を弱める変更・リファクタリングでの振る舞いの変化・観点を検証していないテストなど）は、最終レビューの指示にだけあるか、実装の指示の一部の分岐にしか無かった。
実装のエージェントは、最終レビューが何を見るかを知らないまま提出していた。PR がレビューできるまでの時間を縮める案の1つとして、人が進めることを決めた（2026-11-08）。

## 決定

- 実装・修正の工程のすべての分岐の指示に、「提出の前に確かめる、最終レビューの基準」の節を足す。最終レビューで不合格になる基準を、提出の前に差分で1つずつ確かめさせる。
- 何が当たるかの言葉（範囲外の振る舞いの変更・テストの期待を弱める変更など）は、1つのモジュールに定義し、最終レビューの指示と実装の指示の両方がそれを使う。当たったときの扱い（最終レビューは不合格にする・実装は入れない）だけを、それぞれの指示で書く。
- 定義を最終レビューの指示に組み込むときは、最終レビューの指示の文を一字も変えない（判定は変えない）。
- 範囲の拠り所は、タスクの進め方の言葉にする（要求要件を省いたタスクに「承認済みの要求要件」と書かない）。
- AI のレビューの過去の指摘への応え方（要求に対する欠陥の修正にとどめる）は、実装で避けることとして伝えるが、不合格の基準とは分けて書く。最終レビューは、AI の指摘に応えた要求を超える変更を不合格にせず、人の確認に回すため（PR #321 のレビュー）。
- テストで、基準の一覧のすべてが、当てはまる分岐の両方の指示にあることを確かめる。

## 理由

- 最終レビューで不合格になる前に、実装の工程で気づければ、1周分の実装・検証の時間と費用が要らなくなる。
- 定義を共有しないと、片方だけ直して、実装が確かめたことと最終レビューが見ることがずれる。
- 最終レビューの判定は、実装の自己申告で弱めない。実装が先に確かめても、最終レビューは同じ基準で確かめ直す。

## 影響

- 仕様は [タスクと工程：提出の前のセルフレビュー](../spec/tasks-and-steps.md#提出の前のセルフレビュー) に書く。
- 実装の指示が、およそ 1,300 文字長くなる（要求要件・設計のある最小のタスクで、4,370 文字から 5,677 文字）。
- 差し戻しが実際に減るかは、実際のエージェントで確かめていない（作業履歴に書く）。
