# 受け入れ条件が明示した API の変更では、「公開 API の形を変える」を要求要件を残す理由にしない

- 日時: 2026-11-03 05:30 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-288
- 置き換え元: [受け入れ条件が詳しく、人に確かめることが無い依頼では、要求要件を省く](20261102-2357-superseded-skip-requirements-for-detailed-acceptance.md)（要求要件を残す条件のうち、公開している API・項目の名前や形を変える部分）
- 置き換え先: なし

## 背景

PBI-283 で、受け入れ条件が詳しく人に確かめることが無い依頼は要求要件を省くようにしたが、「外に公開している API・項目の名前や形を変える」依頼は要求要件を残す例外にした（S10 の改名のように、使っている側と食い違いうるため）。
S5 の再実験（r2。注文に必須の `shipping_country` を足す依頼）で、オーケストレーターは要求要件を残した。理由の1つは「POST /api/orders の形を変える」だったが、その変更は受け入れ条件にはっきり書かれていた。もう1つの理由は、異常系のテストの中身・空の入力・列の位置のような細かい既定が残ることで、これは PBI-283 が省いてよいとしたものだった。出てきた要求要件は「確認したいこと：なし」で、$33.47 かかった。
例外の字面が、PBI-283 の動機になった S5 自身を除外していた。

## 決定

- 受け入れ条件が外に公開している API・項目の変更（変更後の名前・形・必須かどうか・エラーのときの扱い）をはっきり書いていて、使う側との食い違いも人に確かめることが無いときは、「公開 API・項目の名前や形を変える」は要求要件を残す理由にしない。変更そのものを依頼が決めているため。
- 受け入れ条件に書かれていない API・項目の変更が要るとき、または使う側との食い違いを人に確かめる必要があるときは、今までどおり要求要件を残す（S10）。改名のように、既存の使う側がどうなるか（旧名を残すか・移行するか）が依頼から決まらない変更は、はっきり書いたことにならない。集めた情報に、使う側が変更で動かなくなりうるとあり、その扱いを受け入れ条件が決めていないときも残す。
- 細かい既定（空白・上限・並び・列や項目の位置・異常系のテストの中身・空の入力の扱いなど）が残ることは、要求要件を残す理由にしない。実装が決め、PR の「既定で決めたこと」で人が確かめる（PBI-283 の決めのとおり）。
- PBI-283 のほかの例外（曖昧・文書やコードとの食い違い・人に確かめたい判断・書き忘れや衝突・共有の状態に新しい意味を載せる）と、設計の判断が要るときに `standard` にすることは変えない。

## 理由

- 受け入れ条件が API の変更を書いているなら、人に確かめることは、変更そのものではなく、使う側との食い違いの有無に絞られる。それが無ければ、要求要件で決めるのは細かい既定だけになる。
- 比べた案：公開 API の変更を例外から外す案は、S10 のような受け入れ条件の無い改名でも省かれうるため採らない。例外を「受け入れ条件に書かれていない変更・使う側との食い違い」に狭める。

## 影響

- オーケストレーターの指示（`DETAILED_ACCEPTANCE_LINE`）が変わる。組み合わせの種類・工程・セルフレビューは変わらない。
- 受け入れ条件に書かれた API の変更でも、使う側が別のリポジトリにあるなどの食い違いが集めた情報から見えなければ、要求要件は省かれる。使う側との食い違いは、オーケストレーターが見える範囲でしか判断できない。
- 規則は[工程の選択](../spec/tasks-and-steps.md#受け入れ条件が詳しい依頼)に記す。
