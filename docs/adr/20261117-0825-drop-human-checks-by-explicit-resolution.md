# 統合レビューが前の回の「人が確かめること」を外す申告は、外す種類を明示したオブジェクトだけを読む

- 日時: 2026-11-17 08:25 UTC
- ステータス: 採用
- 関係する PR・タスク: #417、PBI-382
- 置き換え元: なし
- 置き換え先: なし

## 背景

[統合レビューの「人が確かめること」](20261116-2255-integration-review-human-checks.md) で、前の回の項目は sacty が引き継ぎ、次の統合レビューが番号と理由を挙げたものだけを外すと決めた。
実装では、答えの `droppedHumanChecks` に「<番号>：<外す理由>」の文字列を書かせ、書き方の揺れ（全角・小文字、区切りが `：`・`:`・ハイフン類、1項目に複数の番号）も読んでいた。確かめ済みの項目が、書き方の違いで残らないようにするため。

この読み方は、番号の後に区切りの記号があれば、後ろの文の中身を見ずに理由として採る。`H1：まだ確かめられないので外さない` や `H1 - 外さない` は、外す申告として読まれ、確かめていない項目が「人が確かめること」から「外した項目」に移る。
区切りの記号が無い文（`H1 は外さない`）だけは除いていたが、区切りつきの否定の文は残っていた。エージェントがこの形で書く頻度は、わからない。

あわせて、次の2つがあった。

- 1項目に複数の番号があると、理由が一部の番号だけに当たっていても、全部が外れる（`H1、H2：H1 は確かめられた。H2 はまだ`）。
- 文字列を読む正規表現が、番号の後に長い空白が続く項目で、長さの2乗の時間がかかる。`H1` の後に空白 50,000 文字と1文字を置いた項目の読み取りに 1.5 秒、400,000 文字では 99.5 秒かかった（統合レビューの読み取りの関数を直接呼んで測った）。デーモンは同期処理なので、その間ほかの処理が止まる。

## 決定

- 外す申告は、1項目ずつ `{"id": "<番号>", "resolution": "<verified か obsolete>", "reason": "<外す理由>"}` のオブジェクトで書かせる。`resolution` は、今回のコードとテストで確かめられたなら `verified`、要らなくなったなら `obsolete`。
- 外すのは、番号が前の回の項目の1つを指し、`resolution` がこの2つの値のどちらかで、理由があるオブジェクトだけ。外すかどうかを、理由の文の中身や区切りの記号では決めない。
- それ以外の申告（文字列・`resolution` が無い、またはほかの値・理由が無い・1つのオブジェクトに複数の番号・前の回に無い番号）は、外さない。これまでどおり、記録（`unreadDroppedHumanChecks`）に残し、画面に出す。文字列は、外す意図の文（`H1：確かめられた`）でも外さない。
- 外さなかった申告（文字列・番号を1つとして読めないオブジェクトを含む）に、ある番号が出てくるときは、その番号の外す申告も採らない（`["H1：まだ外さない", {"id": "H1", "resolution": "verified", …}]` では、H1 を外さない）。番号は、H と数字の並びを、文字列の中と、オブジェクト・配列の中のキーと値から探す。探した番号は、外す申告を止めるためだけに使い、外す判定には使わない。
- 画面の見出しは、「外す申告のうち、読み取れなかったもの」から「外す申告のうち、採らなかったもの」に変える（形の正しい申告も、食い違いで採らなければ、ここに出るため）。
- 迷う形は、すべて外さない側（人が確かめる）に倒す。
- 指示では、外さない項目を `droppedHumanChecks` に書かないこと、外さない理由は判定の説明の文に書くことを伝える。
- 記録の形（`IntegrationReviewed` の `droppedHumanChecks`・`unreadDroppedHumanChecks`）は変えない。`resolution` は記録しない。

## 理由

- 項目を外す誤りと、外さない誤りでは、重さが違う。外す誤りは、確かめていないことが、確かめたものとして人に届く。外さない誤りは、人が確かめる項目が1つ多く残るだけで、申告は「読み取れなかったもの」として画面に出るので、人が自分で判断できる。
- 比べた案：否定の語（「外さない」「まだ」「未確認」、`keep`・`not` など）を含む文を除く。語の一覧は、日本語でも英語でも漏れる（「外せない」「保留」「要確認」、`still open`・`pending` など）。漏れたときに外す側に倒れるので、採らなかった。
- 比べた案：肯定の語（「確かめられた」など）を含む文だけを採る。「確かめられたとは言えない」のような文を採ってしまうので、採らなかった。
- 比べた案：指示を強めるだけにする。読み方が変わらなければ、指示に従わない答えで同じことが起きるので、採らなかった。
- 外す種類を決まった値で書かせれば、外す意思は、文ではなく値で表される。値が無い・違う答えは、外さない側に倒れる。番号を1つに限れば、理由がどの番号に当たるかを読み分ける必要が無い。
- 文字列を、外す申告としては読まなくなるので、長さの2乗の時間がかかる正規表現が要らなくなる。番号と `resolution` は、32文字より長ければ読まない。止めるために番号を探す照合は、繰り返しの回数に上限のあるものだけにし、長さに比例する時間で終わる。
- 止めるために番号を探すのは、文の中身を読むことになるが、誤って拾っても、外さない側に倒れるだけなので、採った。番号が H と数字の形で書かれていない食い違い（「1 番目はまだ」など）は、拾えない。
- [統合レビューの「人が確かめること」の ADR](20261116-2255-integration-review-human-checks.md) は、置き換え済みにしていない。その決定（前の回の項目は sacty が引き継ぎ、番号と理由を挙げたものだけを外す）は今も成り立ち、この ADR は、外す申告の書かせ方と読み方を足しただけのため。

## 影響

- 指示に従わず、文字列で外す申告を書いた答えでは、確かめ済みの項目も外れずに残る。人は、「外す申告のうち、採らなかったもの」を読んで、自分で判断する。
- 採らなかった申告の文に、たまたま H と数字の並び（例：`SSH2`）があると、その番号の外す申告も採らない。人が確かめる項目が1つ多く残る。
- エージェントが、確かめていない項目に `verified` を書けば、外れる。理由の中身が実際の解消を伴っているかは、sacty は確かめない（以前と同じ）。
- 以前の記録（外した項目と理由の組・読み取れなかった申告の文字列）は、そのまま読める。
- 読み取れなかった申告の長さには、上限を設けていない（人に渡す情報として、切り詰めない）。
- 仕様は [タスク分割と統合レビュー](../spec/split-and-integrate.md#統合レビュー) にある。
