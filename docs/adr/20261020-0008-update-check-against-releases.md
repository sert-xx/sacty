# sacty の最新版を、動いている版と GitHub Releases の最新のリリースで比べて知らせる

- 日時: 2026-10-20 00:08 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-147
- 置き換え元: [sacty の最新版を、手元のコミットと GitHub の main で比べて知らせる](20261018-1213-superseded-update-check-against-main.md)
- 置き換え先: なし

## 背景

更新の知らせ（PBI-135）は、リリースを運用していなかったので、動いている sacty のコミットと GitHub の `main` を比べ、`main` に手元に無いコミットが
あれば知らせていた。そのため、ドキュメントだけの変更がマージされても知らせが出ていた。置き換え元の ADR は「リリースの運用を始めたら GitHub Releases に
切り替える」と決めていた。2026-10-19 に 1.0.0 を GitHub Releases で公開し、版と既定のイメージの名前を揃える運用を始めた
（[版は 1.0.0 から semver で付け、タグと GitHub Releases でリリースする](20261019-2345-semver-releases.md)）。

## 決定

- デーモンは、動いている sacty の版（`apps/daemon/package.json` の `version`）と、GitHub の sacty の最新のリリース（`/releases/latest` の `tag_name`。
  `v<版>`）を semver の `MAJOR.MINOR.PATCH` として数で比べ、最新のリリースの版が新しいときだけ、画面に更新を勧める（最新の版・動いている版・リリースのページ）。
- 同じ・手元が新しい（開発中）・リリースが無い・取得できない・タグが版の形でない・下書きやプレリリースのときは黙る。確かめる間隔（1日）と
  `update_check: false` の振る舞いは変えない。
- 画面の更新の手順に `npx sacty image build` を含める（既定のイメージの名前が版に連れて変わるため）。

## 理由

- リリースのときだけ知らせれば、利用者は変更の要約（リリースの説明）を見て更新を判断できる。`main` のコミットの比較では、変更のたびに知らせが出て、
  何が変わったかはコミットの一覧でしか分からなかった。
- 版は `package.json` から読めるので、git の作業ツリーでない置き方でも確かめられる。コミットの比較は `git rev-parse` と、GitHub がそのコミットを
  知っていることが要った。
- semver の比較は 3 つの数の比較で足りるので、ライブラリは足さない。

## 検討した案

- **`main` のコミットの比較を残し、リリースの比較を足す**：知らせが 2 種類になり、利用者がどちらに従うか迷う。リリースの運用を始めたので、1つにした。
- **タグの一覧から最新を選ぶ**：`/releases/latest` が下書き・プレリリースを除いた最新を返すので、それを使う方が簡単で、API の呼び出しも 1 回で済む。

## 影響

- `main` の変更がマージされただけでは知らせは出ない。利用者に届けたい変更は、リリースを作って届ける（`CONTRIBUTING.md` の「リリース」）。
- `main` を追っている開発中の環境（版がリリースより新しい、または同じ）では知らせが出ない。
- `GET /api/status` の `update` の形が `behindBy`・`compareUrl` から `latest`・`current`・`releaseUrl` に変わる。古い画面と新しいデーモンの組み合わせでは
  知らせが出ない（どちらも同じリポジトリから動かすので、通常は揃う）。
