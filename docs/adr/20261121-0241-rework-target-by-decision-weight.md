# PR の指摘の戻し先は、決定の重さで分け、設計に戻すのは方針の変更だけにし、局所の設計の直しは実装の PR に入れる

- 置き換え先: なし

## 背景

実装の PR への指摘の戻し先は、「承認済みの決定を変えるか」で決めていた（置き換え元の ADR）。
この基準では、設計書の表の1行や文言のような小さな直しも、承認済みの決定を変えるとして設計に戻る。
設計に戻すと、設計の作り直しと人の承認をもう一度挟むので、費用も手間も、小さな直しに見合わない。

一方、設計書の直しを実装の PR に入れるには、承認済みの設計を実装の途中で書き換えることになる。
これまでは、承認済みの成果物を変えるには、変更の申し出で人が1件ずつ認める経路しかなかった。

## 決定

利用者の決定（2026-11-21）：

- 戻し先の基準は、決定の重さで分ける。
  - 方針の変更（方式・構成の選び直し、範囲・受け入れ条件の変更、外に公開するインターフェースや保存するデータの形、セキュリティ、移行など、取り返しにくい決定）だけを、設計に戻す。
  - 局所の変更（文言・表や一覧の1行・既定値・行の追加）は、実装で直す。
  - 1つでも方針の変更が混ざる回は、全部を設計に戻す。
  - どちらとも言い切れないときは、実装に倒す。セキュリティ・認可・保存するデータの形・移行に触れる指摘だけは、迷えば設計に戻す。
  - テスト観点の文言だけの変更（入力・期待結果の中身を変えない）は実装で直す。入力・期待結果の中身を変える、観点を足す・消す指摘は設計に戻す。
  - 人の指摘が戻し先を明示していれば、それに従う。
- 実装で直す回に、設計書の直しが要るときは、実装が置き換えの形で出す設計の直し（`sacty-design-edit`）を、sacty が承認済みの設計に反映し、同じ実装の PR に入れる。
  設計書の直しの承認は、実装の PR のマージで兼ねる。反映できない直しは、理由を残して反映せず、実装の提出は続ける。
- 設計に戻した回は、実装の PR に知らせを1通投稿する。
- 置き換え元の ADR を置き換える（要求要件の決定を変える指摘の戻し先と、要求要件・設計の PR の指摘の基準は、置き換え元のまま）。

## 理由

- 小さな設計書の直しのために、設計の作り直しと再承認を挟むのは見合わない。決定の重さで分ければ、取り返しにくい決定だけを人の承認に回せる。
- 局所の直しは、実装の PR のレビューとマージで人が見られる。同じ PR で直せば、設計書と実装がずれない。
- 採らなかった案：変更の申し出で直す。人が画面で1件ずつ認める必要があり、局所の直しのたびにタスクが人の判断待ちで止まる。

## 影響

- 局所の設計書の直しは、実装の PR に入り、そのマージで承認される。承認済みの設計の「固定される」に、この例外ができる。
- 設計の直しの反映は、範囲に収まるかを機械で見ない。次の回の AI のレビューと人のマージで見る。
- 新しいイベント `DesignEdited` を記録する。**`DesignEdited` を記録した後は、前の版の sacty に戻せない**（前の版は、知らない種類のイベントを読めず、起動できない）。
- 判断はエージェントの読み取りによる。方針の変更を局所と誤ると、承認なしに設計書が直る。そのため、セキュリティ・認可・保存するデータの形・移行に触れる直しは反映しない。
