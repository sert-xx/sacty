# 要求要件・設計・実装の工程で、提出の前に review-dispatch のセルフレビューをパスするまで繰り返させ、結果を記録して画面に出す

- ステータス: 採用
- 関係する PR・タスク: #130、PBI-120
- 置き換え元: なし
- 置き換え先: なし

## 背景

成果物の品質を担保したい（ステークホルダー）。既定のスキル `review-dispatch` には、自分の成果物を提出の前に観点ごとに見直す `self-review` の流れ
（指摘 → 修正 → 再レビュー、最大 5 回）がある。しかし、工程の指示がこのスキルを使わせていたのは PR のレビューの工程（`pr-review`）だけで、
要求要件・設計・実装の工程は、セルフレビューをするかどうかをエージェントに任せていた。セルフレビューをしたかどうかも、人には見えなかった。

## 決定

- 要求要件・設計・実装の工程（実装は、不具合の修正・テストの仕組みが無いタスクも含む）の指示に、提出の前に `review-dispatch` の `self-review` で
  セルフレビューし、`must` の指摘が無くなる（パスする）まで修正と再レビューを繰り返すことを書く。主対象の種類は、要求要件・設計が `design-doc`
  （下書きを作業領域の外の一時ファイルに書いて対象にする）、実装が `code`。上限はスキルの規則（初回を含めて最大 5 回）で、上限に達しても
  `must` が残れば、残った指摘を報告して提出させる。差し戻し・PR の指摘によるやり直しも同じ。
- 結果は、見出し `sacty-self-review` の JSON（回数・パスしたか・残った `must`・見られなかった観点・総評）で報告させる。sacty は読んで成果物の
  本文から取り除き（承認・凍結・書き出し・工程の PR の成果物に混ぜない）、`AgentRunCompleted` の `selfReview` に記録する。報告が無い・読めない
  ときは `null`（記録なし）にし、工程は止めない。
- 画面は、成果物のカード・実装のカード・承認の画面と作業履歴の行に、パス・パスしていない・記録なしを出す。パスしていない・記録なしは
  警告の色にする。
- 文書作成・調査・作業の工程は対象にしない（ステークホルダーが挙げていない）。

## 理由

- 品質の担保は、エージェントにループを任せるだけでなく、した結果を人が承認の前に見られることで成り立つ。報告の形を決め、記録して出すことにした。
- スキルの「自己レビュー」の節を成果の説明に書かせると、要求要件・設計の成果物（凍結・書き出し・工程の PR のファイル）に混ざるので、
  決まった JSON にして sacty が取り除く。
- 報告が無いときに工程を止めると、AI の出力の揺れで工程が止まりやすくなる。止めずに「記録なし」と警告で出し、人の判断に任せる。
- パスしていないときに sacty が提出を止めないのは、上限まで直しても残る指摘は、人が承認・差し戻しで判断するのが筋だから（スキルの規則も、
  残った問題を書いて提出する）。

## 影響

- 工程の費用が、セルフレビューの分（担当のサブエージェントを含む）だけ増える。予算の上限は今のまま守る。
- `AgentRunCompleted` に `selfReview`（任意・null あり）、投影に `selfReviews` を足した。それより前の記録には無い（画面に出さない）。
