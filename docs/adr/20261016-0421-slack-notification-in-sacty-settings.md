# Slack の通知先を、プロジェクトの設定から sacty の設定に移し、すべてのプロジェクトの通知を1つの送り先に送る

- ステータス: 採用

## 背景

Slack の通知の設定（送り先の種類・URL・チャンネル・トークンの参照・言語・メンション）を、プロジェクトごとに持っていた。プロジェクトが
増えると、同じ設定をプロジェクトごとに繰り返すことになる。ステークホルダーが、通知の設定を1か所（すべてのプロジェクトに共通の
「sacty の設定」）で行いたいと決めた（2026-10-16）。破壊的な変更で、既存のデータの移行と互換の層は要らないことも、ステークホルダーが
了承した。

## 決定

- 通知先（`notification`。項目・検査は今までと同じ）を、sacty の設定（`SactySettings`）に1つだけ持つ。プロジェクトの定義からは外す
  （`ProjectNotification` は `SlackNotification` にした）。プロジェクトに保存してあった通知先は読まない（読み込みの検査で捨てる）。
  移さない。
- すべてのプロジェクトのタスクの通知を、sacty の設定の送り先に送る。どのプロジェクトのタスクかがわかるように、本文の題名の前に
  `[プロジェクトの名前]` を付ける。どの工程の通知かがわかるように、工程の名前を入れる（承認待ちは承認を待つ工程、エスカレーションは
  エスカレーションした工程、一時停止は止まったときの工程。日英）。完了や、工程を決める前の一時停止のような、工程に結びつかない通知には、
  工程を入れないか、工程を決める前と書く。送る条件とメンションの付け方は変えない。
- 送れなかった理由は、sacty 全体で最後の1つを持って画面の警告に出す（プロジェクトごとにしない）。テストの通知は
  `POST /api/settings/notification-test` にし、sacty の設定の画面から送る。
- 起動時と sacty の設定を保存したときに、通知先のトークン・Webhook の URL を取り出す（取り出せなければ、sacty の設定の警告として出す）。
- プロジェクトのエクスポートの形式の版を 5 に上げ、通知先を含めない。通知先を含んでいた版 3・4 のファイルは、理由を示す文言
  （`input.exportVersionWithNotification`）で断る。版 5 のファイルに通知先を書き足したものは、知らない項目として断る。

## 理由

- 通知先を1か所にするのは、プロジェクトごとに同じ設定を繰り返さないため（ステークホルダー）。
- 本文にプロジェクトの名前を入れるのは、1つの送り先にすべてのプロジェクトの通知が混ざるため（ステークホルダー）。工程の名前を
  入れるのは、どの工程の通知かをわかるようにするため（ステークホルダーの追記）。
- 古い通知先を移さないのは、ステークホルダーが移行も互換の層も要らないとしたため。プロジェクトごとに違う送り先を持っていた場合、
  どれを sacty の設定にするかを機械的には決められないことも、移さない理由になる。
- 版 3・4 を「知らない項目」として黙って捨てずに版の違いで断るのは、PBI-103 で版 3 を理由つきで断ったのと同じく、利用者が気づかずに
  通知の設定を失わないようにするため。
- 設定を保存したときにも秘密情報を取り出すのは、プロジェクトの設定を保存したときに通知先の秘密情報を取り出していた
  （PBI-107）のを保つため（タスクの実行中に 1Password の認証を求めないため）。

## 影響

- プロジェクトごとに違う Slack の送り先（ワークスペース）へ送ることは、できなくなる。
- 以前に設定したプロジェクトの通知先は効かなくなるので、sacty の設定で設定し直す（されるまで通知しない）。
- 版 3・4 のエクスポートのファイルは、インポートできない。今の sacty でエクスポートし直す。
- 仕様は [通知](../spec/notifications.md)・[書き出し](../spec/export.md)・[秘密情報](../spec/secrets.md) に書く。
