# テストの仕組みが無いリポジトリでは、テストを飛ばし、ゴールガーディアンがタスクの目的から受け入れを判定する

- 日時: 2026-10-15 00:00 UTC
- ステータス: 採用
- 関係する PR・タスク: #105、PBI-94
- 置き換え元: なし
- 置き換え先: なし

## 背景

実装の工程を含むタスクは、オーケストレーターがテストのコマンドを決められないと、費用をかける前に止めていた
（`orchestrator.testCommandUnknown`）。実装の検証が「テストのコマンドを実行し、終了コード 0 で、観点がすべてテストに対応する」ことを
前提にしていたため。README しかないリポジトリで「Sacty セットアップ」を実行すると、ここで止まった。テストの仕組みどころか言語の
セットアップも無いリポジトリで、そのセットアップのためのタスクが作られることもある。

一方で、テストの仕組みがあるのにコマンドを決められなかったリポジトリが、黙ってテストなしで通ってしまうと、検証の意味が無くなる。

## 決定

1. **テストが無いと判断する条件**：オーケストレーターが、`testCommand` を空にしたうえで、テストの仕組みが無いと判断した根拠を
   `noTests` に書いたときだけ、テストの無いタスクとして進める。`StepsChosen` の `noTestsReason` に根拠を残す。
   - `noTests` を書かずに `testCommand` が空なら、今どおり止める（決められなかった）。
   - `testCommand` があれば `noTests` は捨てる（テストのコマンドがあるときの動作は変えない）。
2. **黙って通らないための歯止め**：オーケストレーターがテストが無いと答えても、sacty が対象リポジトリの起点のファイルの名前を見て、
   テストのファイルの名付けの慣習（`test`・`tests`・`__tests__` のディレクトリの中、`test_*`・`*_test`・`*.test`・`*.spec`・
   `*_spec`・`*Test`・`*Tests`・`Test*` の形の名前）に当たるファイルがあれば、テストの無いタスクとして扱わずに止める
   （`orchestrator.noTestsContradicted`。見つけたファイルを示す）。ファイルが多すぎて確かめきれないときも止める。
   止めるときは、テストのコマンドを決められなかったときと同じく、`noTestsReason` を持たない `StepsChosen` を記録する。
3. **目的での判定**：テストの無いタスクの実装の検証は、テストを実行せずに `TestsSkipped` を記録して最終レビューへ進む。
   ゴールガーディアンは、タスクの目的（題と内容）・承認済みの要求要件（あれば設計）と、実装後のコード・差分・実装の説明から、
   観点ごとに受け入れを判定する。テストが無い・観点にテストが対応していないことを理由に不合格にしない。観点（設計のテスト観点、
   無ければ `REQ`）、合格・不合格、`MAX_VERIFY_ATTEMPTS` の上限は、テストのあるタスクと同じにする。
4. **実装でテストが用意されたとき**：テストの無いタスクの実装の工程が、タスクの求めでテストの仕組みを用意したら、そのコマンドを
   見出し `sacty-test-command` で申告させる。申告があれば、sacty はそのコマンドでテストを実行し、終了コード 0 を合格にする
   （観点にテストが対応していないことでは不合格にしない）。そのうえで、最終レビューで目的から判定する。申告は実装の提出ごとに読み直す。
5. **再現の工程**：テストの無いタスクには、不具合の修正（`bugfix`）を選ばせない。オーケストレーターへの指示で選ばないよう求め、
   選ばれたら、テストの無いタスクとして扱わずに止める（`orchestrator.bugfixNeedsTests`）。
6. **示し方**：タスクの画面・成果物チェックの承認の画面（実装の成果物）・PR の本文に、テストのコマンドが無いためテストでは
   検証していないこと（実装で用意したテストを使ったなら、そのこと）と、目的から判定したこと、オーケストレーターの根拠を出す。
   成果物チェックの人の承認は今どおり要る。

## 理由

- 根拠の明示を条件にしたのは、「決められなかった」と「無い」を分けるため。答えが空なだけのときは、今の止める動作を残す。
- 名前の慣習で確かめるのは、言語やツールに依らず、テストのあるリポジトリのほとんどにテストのファイルがあるため。言語ごとの設定
  ファイル（テストのツールの設定など）を並べる方法は、言語が増えるたびに直す必要があり、採らなかった。当たったファイルがテストで
  なかった（誤検知の）ときは止まるだけで、今の動作より悪くならない。タスクの内容にテストの実行方法を書けば、今どおり進められる。
- 判定の材料に実装の説明を加えたのは、テストの結果という外からの裏付けが無いので、何をどう満たしたかの申告が要るため。申告だけで
  合格にしないよう、コードと差分で裏付けられることだけを根拠にするよう指示する。
- 実装で用意したテストを使うのは、テストで確かめられるものは確かめたほうが、目的だけでの判定より確かなため。申告されたコマンドは、
  テストのコマンドと同じくテストのコンテナで実行するので、実装のエージェントがもともと変えられるテストより強い権限にはならない。
- 不具合の修正を選ばせないのは、再現の工程が「失敗するテストを書き、sacty が失敗を確かめる」ことで成り立っており、テストが無いと
  再現できたかを sacty が確かめられないため。目的で判定する案は、再現の工程に承認が無く、人の確かめも挟まらないので採らなかった。
- 止めるときに `noTestsReason` を記録しないのは、再開してもテストを飛ばさない（テストのコマンドを決められなかったときと同じく、
  検証で止まる）ようにするため。

## 影響

- `StepsChosen` に `noTestsReason`、実装の `AgentRunCompleted` に `testCommand`（実装が申告したテストのコマンド）、新しいイベント
  `TestsSkipped` が増える。これまでの作業履歴の読み方は変わらない。
- テストのコマンドを決められるタスクの検証・再現・画面・PR の本文は変わらない。
- 名前で確かめる歯止めは、テストのファイルを持たないテスト（ソースの中に書く単体テスト・ドキュメントの中のテストなど）を見分けられない。
  そのようなリポジトリでオーケストレーターが誤ってテストが無いと答えたときは、オーケストレーターへの指示（仕組みがあるのにコマンドが
  分からないなら書かない）と、画面・PR の本文の「テストで検証していません」の表示と根拠、成果物チェックの人の承認で気づく。
