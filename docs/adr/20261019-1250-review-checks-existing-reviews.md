# PR のレビューは、PR にすでにあるレビューを入力に揃え、他のレビュアーと同じ指摘を繰り返さない

- 日時: 2026-10-19 12:50 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-144
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty の PR のレビューのタスク（既定のスキル `review-dispatch` の `pr-review`）は、PR の差分とコード、再レビューでは自分の前回の投稿と作者の返答だけを
入力にしていた。他のレビュアーが PR ですでに指摘している問題を、sacty がもう一度同じように指摘し、PR の作者が同じ指摘を二度さばく手間が増えていた
（ステークホルダー）。

## 決定

- sacty は、review の工程を実行する前に、対象の PR にすでにあるレビュー・行へのコメント・通常のコメント（他のレビュアーの指摘と作者の返答。
  このタスクのアカウントの目印付きの投稿は除く）を読み、指示とは分けた JSON のデータとしてエージェントに渡す。初回も再レビューも渡す。
  件数（新しい 30 件）と 1 件の長さ（2000 文字）に上限を置く。読めなければそう伝えてレビューは止めず、理由をデーモンのログに残す。
- 既定のスキル `review-dispatch`（`pr-review`）に「既存のレビューの確認」を足す。親が担当を起動する前に既存の指摘の状況を確かめ、集約で、
  既存のレビューで指摘済みの問題（同じ箇所・同じ問題。言い換えを含む）は `must` でも不採用にし（理由「既存のレビューで指摘済み」）、判定に数えない。
  総評には省いた件数だけを書き、既存の指摘の本文は写さない。既存の指摘は担当に渡さず、観点も減らさない。
- スキルは汎用のまま（sacty 固有の名前・形に寄せない）。依頼した側が既存のレビューを渡していないときは、PR から読めるときだけ取得する。

## 理由

- 既存の指摘は作者にすでに届いているので、繰り返しても作者の手間が増えるだけで、レビューの価値は上がらない。
- 重なりの判断は、観点ごとの担当ではなく、全観点の結果を見る親が集約で行う方が、担当の見落とし（既存の指摘に引きずられて観点を狭める）を防げる。
- 既存のレビューの取得は、PR の指摘の取り込みで使っている読み出し（`PullRequests.feedback`）を流用でき、エージェントに GitHub の認証を渡さずに済む。

## 影響

- 初回のレビューでも PR のレビュー・コメントを 1 回読む（API の呼び出しが 1 回増える）。
- sacty の判定（修正が必要・提案あり・指摘なし）は、sacty 自身が新たに採用した指摘で決まる。他のレビュアーの未対応の `must` は、
  その人の指摘として作者に届いていて、元のタスクの PR の指摘の取り込みでも人の指摘として取り込まれる。
