# コンテキストのリポジトリのサブモジュールを取得し、組織で別に管理するスキルなどを写さずに使えるようにする

- 日時: 2026-10-22 15:03 UTC
- ステータス: 採用
- 関係する PR・タスク: #200
- 置き換え元: なし
- 置き換え先: なし

## 背景

組織で、sacty とは別のリポジトリでスキルを管理していることがある。
コンテキストリポジトリの `skills/` に使うには写すしかなく、同じスキルを2か所で管理することになっていた。
git のサブモジュールで置いても、sacty は `git clone --depth 1` だけで取得していたので、サブモジュールは空のディレクトリのままで、中のスキルは黙って欠けていた。
シンボリックリンクは、コンテキストでは扱わない（[コンテキストではシンボリックリンクを扱わない](20261010-1203-reject-symlinks-in-context.md)）。

## 決定

- git で取得する層は、取得の後に、層に関わるサブモジュール（層のディレクトリの中にあるものと、層のディレクトリを含むもの）を `git submodule update --init --recursive --depth 1 -- <パス>` で取得する。
  層に関わらないサブモジュールは取得しない。
- ローカルのパス（file のプロトコル）のサブモジュールは取得しない（`protocol.file.allow=never`）。
- 認証は、コンテキストリポジトリと同じ環境変数（同じホストなら gh のトークン）とホストの git の認証を使う。
- 記録するコミットは、これまでどおりコンテキストリポジトリのコミットだけにする。
- `ref` の無いローカルのパスの層（今の中身を読む層）は、サブモジュールを取り込まない。
  層のディレクトリの下に取り込んでいないサブモジュールがあれば、`context.submoduleNotCheckedOut` で止める。
- サブモジュールの `.git`（ファイル）は、実行のときに置くファイルに含めない。

## 理由

- サブモジュールは、git の標準の仕組みで別のリポジトリを決まったコミットで取り込めるので、写さずに1か所で管理でき、どの版を使ったかもコンテキストリポジトリのコミットで決まる。
  そのため、サブモジュールのコミットを別に記録しなくても、作業履歴からどの中身で実行したかがわかる。
- 層に関わるサブモジュールだけを取得するのは、モノレポにアプリのための大きなサブモジュールや、認証の要る別のリポジトリがあっても、コンテキストの取得を遅くしたり失敗させたりしないため。
- ローカルのパスのサブモジュールを取得しないのは、git で取得した層がローカルのパスを `extends` に書けないのと同じく、取得したコミットの中身でホストのディレクトリを読ませないため。
  git も既定ではサブモジュールの file のプロトコルを許さないが、git の版や設定に頼らないよう明示する。
- 今の中身を読む層で sacty がサブモジュールを取り込まないのは、ホストのディレクトリ（利用者の作業ツリー）を変えないため。
  黙ってスキルが欠けるより、理由と直し方を示して止めるほうがわかりやすいので止める。

## 影響

- サブモジュールを置いていたコンテキストリポジトリは、サブモジュールの中身（スキル・規約など）も使うようになる。
  サブモジュールを取得できない（認証が無い・ローカルのパスを指す）と、これまでと違って取得の失敗で止まる。
- `ref` の無いローカルのパスの層で、取り込んでいないサブモジュールがあると止まるようになる。
- 仕様は [コンテキストの合成](../spec/context.md#層) に書いた。
