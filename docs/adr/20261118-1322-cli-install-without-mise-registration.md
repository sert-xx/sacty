# sacty コマンドの入口を mise に登録するのをやめ、いつも ~/.local/bin などに置く

- 日時: 2026-11-18 13:22 UTC
- ステータス: 採用
- 関係する PR・タスク: #432
- 置き換え元: [sacty コマンドを、Node.js の版に関係しない場所の起動の入口で入れ、入れたときの Node.js で動かす](20261111-0054-superseded-cli-install-launcher-with-fixed-node.md)（入口を mise に登録する決定と、mise で入れたときの確かめ・消し方を置き換える）
- 置き換え先: なし

## 背景

`npm run cli:install` は、`PATH` に `mise` があると、入口を版ごとのディレクトリ（`~/.local/share/sacty/mise/<版>/bin/sacty`）に置き、`mise link sacty@<版>` と `mise use --global sacty@<版>` で mise に登録していた。
リポジトリの持ち主から、mise を使う環境で、この入れ方がうまくない、と報告があった（どの症状かは聞いていない）。
次の3つは、コードと前の ADR を読んだ作者（AI）が、弱い所と推測したもの。持ち主の環境で起きていることとは確かめていない。
- 版を上げるたびに、mise の利用者全体の設定（`~/.config/mise/config.toml`）の `sacty` の行が変わる。前の版の登録とディレクトリは残り続ける。
- mise のレジストリに無い名前（`sacty`）を `mise link` で登録する使い方で、前の ADR を書いたときも、実際の mise では確かめていない。
- シムも `mise activate` も設定していないシェルでは、登録しても `sacty` を実行できない。

持ち主は、mise の設定の `_.path` に、リポジトリの `bin` を直接足す案も検討していた。
作者が、mise に登録せずにいつも `~/.local/bin` に置く案を出し、持ち主がそれを選んだ。
症状を聞いていないので、この決定で持ち主の困りごとが無くなるかは、持ち主が mise のある環境で入れ直して確かめる（どのディレクトリでも `sacty` と打って、リポジトリの版で動くこと）。

## 決定

- `npm run cli:install` は、mise があっても mise に登録せず、いつも `SACTY_BIN_DIR`、無ければ `~/.local/bin` に入口を置く（前は、mise が無いとき・登録に失敗したときの動き）。
- 入口の作り（`cli:install` を動かした Node.js の絶対パスで、このリポジトリの `packages/cli/bin/sacty.js` を動かすシェルのスクリプト）は変えない。
- 前の版が mise に登録した sacty は、自動では外さない。`mise` は呼ばず、mise の設定も、登録も、前の版の入口のディレクトリも消さない。
  前の版の入口のディレクトリ（`~/.local/share/sacty/mise`）があれば、その中の入口を、置いた入口と同じ中身に書き直し、登録が残っていれば手で外す、という形で手順を注意に出す（PR #432 のレビュー）。
  注意を出す条件は、このディレクトリがあることで、mise の登録が残っているかは確かめない（`mise` を呼ばないため）。
- 置いた後の確かめは、mise の有無に関係なく、`PATH` で最初に見つかる `sacty` が置いた入口か、だけにする。
  最初に見つかるのが、書き直した前の版の入口のときは、同じに動くので注意にしない。前の版の入口のディレクトリがあって、ほかの `sacty`（mise のシムなど）が最初に見つかるときは、前の版の mise の登録なら手順で外す、と知らせる（PR #432 のレビュー）。

## 理由

- 置き場所を1つにすれば、mise の設定に触れず、版ごとの登録も溜まらない。`~/.local/bin` は Node.js の版に関係しない。
  mise の配布元の入れ方では mise 自体が `~/.local/bin` に入るので、mise を使う環境では `PATH` に入っていることが多い、と作者は考えた（作者の知識で、確かめていない。Homebrew などで mise を入れた環境では当てはまらない）。持ち主の環境で `PATH` に入っているかも確かめていない。入っていなければ、`cli:install` が注意で知らせる。
- 前の登録を自動で外さないのは、実際の mise で確かめられない操作（`mise unuse`）で、利用者の mise の設定と登録を書き換えないため（PR #432 のレビュー）。
  はじめは `mise unuse --global sacty` で外す実装にしたが、ほかの方法で mise に入れた sacty まで設定から外すおそれがあり、外した後の動きも確かめられなかった。この後始末が要るのは、前の版で入れた人の1回だけなので、手順を知らせることにした。
- 前の版の入口を書き直すのは、登録が残っている間、mise が前の版の入口を `PATH` に載せ、置いた入口より先に見つかると考えたため（mise が、登録した道具の bin を `PATH` のどこに載せるかは、実際の mise では未確認）。
  書き直しておけば、どちらが先に見つかっても同じ Node.js・同じリポジトリで動く。書き直すのは、目印のある sacty の入口だけ。
- 比べた案と採らなかった理由：
  - mise の設定の `_.path` に、リポジトリの `packages/cli/bin` を足す。`sacty.js` は `#!/usr/bin/env node` で始まるので、いるディレクトリの Node.js で動き、Node.js の版の問題（前の ADR の背景）が戻る。bin のファイルの名前も `sacty.js` で、`sacty` とは打てない。
  - mise に登録したまま、登録の溜まりだけを直す（版ごとではない1つのディレクトリを、決まった版の名前で登録する）。設定の行が版ごとに変わること・登録が溜まることは無くせるが、レジストリに無い名前を `mise link` で登録する使い方と、シムか `mise activate` が要ることは残る。mise で版を確かめられる良さも、版の名前を固定すると無くなる。持ち主は、登録しない案を選んだ。
  - 版に関係しない sacty 専用のディレクトリに入口を置き、`_.path` に足す。利用者の mise の設定を書き換えることになり（この決定で避けたいこと）、mise を使わない人には別の置き方が要るので、置き方が2通りになる。`~/.local/bin` を `PATH` に入れたくない人は、`SACTY_BIN_DIR` で置き場所を選べる。

## 影響

- mise で sacty の版を確かめる（`mise ls sacty`）ことは、できなくなる。版は `sacty --version` で確かめる。
- 持ち主の環境で `~/.local/bin` が `PATH` に入っているかは、確かめていない。`~/.local/bin` が `PATH` に無い環境では、前は mise が `PATH` に載せていた `sacty` が、`PATH` に足すまで使えなくなる（`cli:install` が注意で知らせる）。
- 前の版で入れた利用者は、前の版の入口のディレクトリを消すまで、`cli:install` のたびに注意が出る（前の版で登録に失敗して、ディレクトリだけが残った人にも出る）。外す手順（設定の行・mise の登録・前の版の入口のディレクトリ）は、実際の mise では確かめていない（この ADR を書いたときの環境に mise を入れられなかった）。
- 入口を消すには、置き場所の `sacty` を消すだけになる。
- 仕様は [アーキテクチャ](../spec/architecture.md#パッケージ)、利用者向けは [はじめに](../user/getting-started.md#どのディレクトリでも-sacty-を使う) に書く。
