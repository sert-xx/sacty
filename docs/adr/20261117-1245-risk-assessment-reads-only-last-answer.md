# PR のリスク評価は、最後に出た答えだけを読み、読めなければ前の答えにさかのぼらない

- 日時: 2026-11-17 12:45 UTC
- ステータス: 採用
- 関係する PR・タスク: #421、PBI-386
- 置き換え元: なし
- 置き換え先: なし

## 背景

リスク評価の答えの読み取りは、出力の中の JSON を後ろから順に読み、形の合わないものを飛ばして、前のものへ進んでいた。
出力に評価の答えが 2 つ以上あり、最後の 1 つが読めない形（知らない合図が混ざる・上げ幅が決めた値でない、など）のとき、前に出た答えが使われた。

読めない形を決めたのは、合図・上げ幅を読み落として、低い段階を載せないためだった。
前に出た答えは、エージェントが合図・上げ幅を足す前の下書きでありうる。前の答えにさかのぼると、足した合図を落とした、低い段階が載りうる。

PR のレビューの判定は、最後のブロックが読めなければ、前のブロックを使わない。評価だけが、逆の扱いだった。

## 決定

- 最後に出た評価の答えが読めなければ、評価できなかったと記録する。前に出た答えは使わない（リポジトリの持ち主の決定。2026-11-17）。
- 答えが 2 つ以上あり、最後の答えが読めるときは、今までどおり、最後の答えを使う。

実装で決めたこと（持ち主の確認は、この ADR を書いた時点ではまだ）。

- 「評価の答え」は、評価の見出しを最上位のキーに持つ、JSON として読めるオブジェクトとする。見出しの値がオブジェクトでないものも、評価の答え（読めない答え）として数える。
- 出力の中で最後に出た見出しのキー（`"sacty-risk-assessment":` の形）が、最後の評価の答えの中に無いときは、最後の答えが読めないものとして、前の答えにさかのぼらない。次の形が当たる。
  - JSON として読めない答え（末尾のカンマ・途中で切れた、など。見出しが最初のキーでなくても）
  - ほかのオブジェクトの中に入れ子になっている答え（読める・読めないを問わない）
  - 本文が、見出しをキーの形（引用符とコロン付き）で書いているだけの箇所
- 見出しの名前だけに触れている本文と、JSON の文字列の値の中に書かれた見出し（引用符がエスケープされる）は、数えない。
- 評価できなかった理由は、前に出た読める答えを、最後の答えが読めないために使わなかったときだけ、別の文言（`pr.riskLastUnreadable`）にする。答えが無い・1 つだけの答えが読めないときは、今までの文言（`pr.riskUnreadable`）のまま。
- ほかの読み取り（工程の選択・判定など）が使う、後ろから順に読む共通の関数は、変えない。

## 理由

- 持ち主が、最後の答えが読めなければ評価できなかったと記録する、と決めた。
- JSON として読めない答え・入れ子の答えも数えるのは、形の合わない答えと同じ理由（前の答えが、足す前の下書きでありうる）が当たるため。
- 最後の答えを、形ごとの見つけ方の足し合わせではなく、「最後に出た見出しのキーが、最後の読める答えの中にあるか」の 1 つの確かめで見分ける。形ごとに見つけると、見つけられない形が残り、その形では前の答えにさかのぼる（最初の実装は、見出しを最初のキーに持つ壊れた答えだけを見つけていて、入れ子と、見出しが最初のキーでない壊れた答えで、さかのぼった。レビューの指摘で改めた）。
- 本文が見出しをキーの形で書いているだけでも、読めないものとする。読める評価を捨てることがあるが、「評価できませんでした」と載るだけで、低い段階を載せるより安全な側に倒れる。検証の記録の読み取りも、同じ倒し方をしている。
- 最後のキーだけを見るのは、出力を 1 回走査するだけで済ませるため。壊れた答えをすべて見つける共通の関数は、閉じない答えが多く並ぶ出力で、出力の長さの 2 乗の時間がかかる（レビューの担当の実測）。評価の読み取りからは、呼ばない。
- 理由の文言を分けるのは、記録を見た人が、「答えが無かった」のか「最後の答えが壊れていて、前の答えを捨てた」のかを、出力を調べ直さずに見分けられるようにするため。

## 影響

- 評価の答えを 2 つ以上出し、最後の答えの形が崩れた実行は、評価できなかった記録になる。PR を作る前の評価は、次に PR を出し直すときに評価し直す。レビューの工程の評価は、「評価できませんでした」と載る。
- レビューの本文が、評価の答えの後ろに、評価の見出しをキーの形で書いていると（壊れた JSON の引用・`"sacty-risk-assessment":` と書いた説明）、評価できなかった記録になる。
- 配列の中に書かれた答え（`[{"sacty-risk-assessment": …}]`）は、今までどおり、評価の答えとして読む（JSON の候補の見つけ方が、配列の中のオブジェクトを候補にするため）。
- 評価は、レビューの省略・マージには使っていないので、工程の進み方は変わらない。
