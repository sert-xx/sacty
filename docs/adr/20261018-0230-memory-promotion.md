# メモリーの昇格は大まかな監査で判断し、コンテキストへの昇格は改修の提案にする

- 日時: 2026-10-18 02:30 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-128
- 置き換え元: なし
- 置き換え先: なし

## 背景

構想ドキュメントの「昇格」は、メモリーに溜まった教訓のうち恒久化すべきものを、コンテキストリポジトリへの PR として出す仕組みである。
ステークホルダーと決めた方針は、昇格を判断するのは監査だけで、昇格には階層の移動と、メモリーをやめてコンテキストにするものがある、というもの。

## 決定

- **判断するのは大まかな監査**：大まかな監査は完了したタスクごとに必ず動くので、何も起きなかったタスク（深掘りの無いタスク）でも判断できる。
  深掘りは差し戻しや試行錯誤があった工程だけで動くので、そこに置くと、問題なく役立ち続けたメモリーが昇格しない。
- **判断の材料**：タスクの階層のメモリーの、有効な最終利用日と、役に立った回数（役に立ったと判断したタスクの数）を渡す。目安は 2 回以上
  役に立ったこととし、指示に書く。
- **階層の移動は記録から決める**：移した先を `AuditSurveyed` に記録し、メモリーの置き場所は、すべての移した記録を時刻の順に当てて決める。
  登録した記録は書き換えない（追記専用）。
- **コンテキストへの昇格は改修の提案にする**：今の「提案 → 人が採用 → 改修のタスク → PR」に乗せ、コンテキストの変更は必ず人の PR の
  レビューを通る。原因の鍵を `memory:<ID>` にし、提案に元のメモリーを持たせ、改修の PR がマージされたら元のメモリーを消す。
- **同時に動く監査**：大まかな監査は同じプロジェクトでも同時に動くので、記録の時点で、メモリーが残っているか・まだタスクの階層にあるか・
  提案中でないかを確かめ直す。

## 検討した案

- **深掘りで判断する**：同じプロジェクトでは1つずつ動くので重なりを気にしなくてよいが、問題の無かったタスクでは動かず、役立ち続ける
  メモリーほど昇格の機会が無い。
- **昇格だけの監査の段を足す**：判断の材料は大まかな監査と同じで、費用が増えるだけになる。
- **コンテキストに直接書く**：人のレビューを通らずにコンテキストが変わり、構想の「工程定義・コンテキストの変更は人の PR のレビューを通す」
  に反する。

## 結果

- 置き場所の合わないメモリーが直り、何度も役立つ知見がコンテキストに育つ。
- 移動・提案・採用・マージ・削除がすべて作業履歴に残り、監査の欄で追える。
