# 要求要件の受け入れ条件を文型ごとの見出しと表で書き出させる

- 日時: 2026-10-25 06:30 UTC
- ステータス: 採用
- 関係する PR・タスク: #222
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件の受け入れ条件は、EARS の文を ID と文型の名前を添えた箇条書きで並べていた（例：`R-1（イベント駆動）`）。
同じきっかけや主語が何行も続くと、文が長く、どこが違うのかを人が読み取りにくかった。
利用者から、文型ごとに見出しを分け、文型の要素（トリガー・システム・応答など）を列にした表で書き出すよう求められた。

## 決定

- 既定のスキル `ears-requirements` に「書き出す形」を足す。
  - 文型ごとに見出しを分け、文型の表の順に並べる。要求が無い文型の見出しは書かない。機能などのまとまりの見出しがあれば、その1つ下の見出しにする。
  - 文型ごとの列は次のとおり（英語は Trigger・State・Feature・System・Response）。
    - 常時：ID・システム・応答
    - イベント駆動・望まない振る舞い：ID・トリガー・システム・応答
    - 状態駆動：ID・状態・システム・応答
    - オプション：ID・機能・システム・応答
    - 複合：ID・状態・トリガー・システム・応答
  - 1行に1つの要求を書き、行を左から読むと文型の1文になるようにする。条件の列は「とき」「の間」「場合」まで書き、応答の列は「しなければならない」を除く（「してはならない」は残す）。
  - 文型の名前を ID に添える書き方はやめる（見出しで分かる）。
- 要求要件の工程の指示（`earsLines`）にも、見出しと列を短く書く。
- 1文1要求・ID・合否を決められる応答などの書き方の決まりは変えない。

## 理由

- 同じ文型の要求を同じ列で見比べられ、きっかけ・主語・応答の違いが読み取りやすい。
- 行を左から読めば EARS の1文になるので、文型の検査や設計のテスト観点との対応づけは今までどおりできる。
- 条件の列につなぎの語を残すのは、状態の「の間」ときっかけの「とき」を取り違えにくくするため。応答の「してはならない」を残すのは、否定を落とさないため。

## 影響

- 以後の要求要件の成果物は、受け入れ条件が文型ごとの表になる。以前のタスクの成果物は変わらない。
- 依頼した人の指示や対象のリポジトリの要求要件の決まりが別の形を求めれば、そちらが優先する（スキルの従う順は変えない）。
