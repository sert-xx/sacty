# 同じ内容で実行済みの検証は、記録と CI の結果を使い回し、覆われていない分だけを実行する

- 日時: 2026-11-06 00:05 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-305
- 置き換え元: [PR のレビューの工程が、作業領域で依存関係を取得して検証を実行する](20261024-0310-superseded-review-runs-verification-in-workspace.md)（CI の結果を自分で実行した結果の代わりにしない部分）
- 置き換え先: なし

## 背景

実装の PR を1つ出すまでに、同じ内容（コミット）に対して、同じ検証が何度も実行されていた（利用者の報告、2026-11-05）。

- 実装の工程：セルフレビューの検証（`verification-run`）と、指示の「提出の前の検証」。同じ内容に2回走りうる。
- 最終レビューの前のドラフトの PR の CI。
- ゴールガーディアンの最終レビュー：テストのコマンドと、フォーマッター・リンターなどの検証。
- レビュー用のラベルで作るレビューのタスク：`verification-run` の全部。指示は「CI の結果や作者の報告を、自分で実行した結果の代わりにしない」だった。

sacty は検証に通った後も同じコミットのままドラフトを外すので、CI・最終レビュー・PR のレビューは同じコミットを見ている。
実装の工程の最後の検証も、sacty がそのまま作業領域をコミットするので、同じ内容である。
トークンと時間がかかっていた。

一方で、次のことにも気をつける必要があった（利用者の指摘）。

- 一部のテストしか実行していない段がある（変更したファイルに絞った lint など）。それを全体を実行したものとして省くと、確かめていない所が残る。
- CI が無いリポジトリもある。CI で確かめられるはずだと見なして省いてはいけない。
- CI は、資源の都合でテストを段階的に（ジョブの分割・matrix・shard・前の段階が通ったときだけ次を実行など）実行することがある。

## 決定

- 検証を実行した段が、検証の記録（見出し `sacty-verification`）を申告する。コマンドごとに、種類・コマンド・覆った範囲（`full`：コマンドが定める対象の全体、`partial`：一部だけ）・結果（`passed`・`failed`）・結果の抜粋を書かせる。止まった・実行しなかったものは記録しない。
  - 実装の工程は、作業領域を最後に変えた後に実行した検証だけを申告する。sacty は台帳（`AgentRunCompleted` の `verificationRecord`）に残す。ベースブランチの取り込みなどで作業領域が変わったら、記録を使わない。
  - ゴールガーディアンは、自分で実行したものと、前の段から使い回したもの（元の段とともに）を申告する。sacty は、最終レビューの前に作った実装の PR のコミットを付けて台帳（`FinalReviewed` の `verificationRecord`）に残す。
    sacty が PR に足す成果物のファイルを写しに入れられなかったときは、写しが PR のコミットと同じ内容ではないので、どのコマンドも一部だけ（`partial`）にして、無かったファイルを残す。
- 次の段は、前の段の記録と CI の定義・結果から、どこまで覆われているかを自分で判断し、覆われていない分だけを実行する。
  - 最終レビューには、実装の工程の記録と CI の結果を渡す。テストのコマンドの全体が覆われていれば、実行せず、使い回した結果と元の段（`reusedFrom`）を申告させる。
  - sacty が作った PR のレビューのタスクには、その PR を作ったタスクの最終レビューの記録を、コミットが PR の先頭と同じときだけ渡す。人の PR は、CI の結果だけを使い回せる。
  - 使い回せるのは、全体を実行して結果が出たものだけ。一部だけの記録は、覆った範囲を除いた残りを実行する。
  - CI は、ワークフローの定義と各ジョブの結果・ログから、段階・分割を合わせて全体を覆うと確かめられたものだけを実行済みにする。飛ばされた・条件で実行されなかったジョブは何も覆わない。ジョブの名前だけで推し量らない。CI が無い・読めないときは、CI で実行されたものとして扱わない。
  - 確かめられないものは実行する。PR の作者の報告は、これまでどおり使い回さない。
- 実装の工程の中では、提出の前の検証とセルフレビューの検証を、同じ内容なら1回の実行で両方に使う。
- 既定のスキル `verification-run` に「1.5 使い回せる結果を探す」を足し、sacty の外の使い方でも同じ判断をさせる。

## 理由

- 検証の結果は、同じ内容なら決まる（利用者の判断）。使い回せる範囲はなるべく使い回す。
  このため、実装の工程（工程エージェント自身）の結果も、最終レビューで使い回す。ゴールガーディアンが自分で確かめる範囲は狭くなるが、記録には結果の抜粋があり、ゴールガーディアンは差分とコードで判定する。
- 覆った範囲（`full`・`partial`）を記録に持たせ、一部だけのものは使い回さないことで、一部のテストしか実行していない段の結果で全体を省くことを防ぐ。
- CI の照らし方は、決まった規則（ワークフローに同じコマンドがある、など）にしなかった（利用者の判断）。CI は段階・分割で実行することがあり、ジョブとコマンドの対応はリポジトリごとに違う。エージェントに定義とログを読ませて判断させる。
- 記録は sacty が台帳に残して渡す。エージェントのコンテナの一時ファイルは段をまたいで残らず、PR のレビューは別のタスクなので、台帳を通さないと渡せない。
- コミットが変わった PR（人がプッシュした後など）・作業領域が変わった実装には、記録を渡さない。内容が違う結果を使い回さないため。

## 影響

- 同じ内容への検証の重複が減り、最終レビューと PR のレビューの時間と費用が下がる。
- 使い回しの判断はエージェントに任せるので、強制はできない。誤って覆われていると判断すれば、実行していない検証が残りうる。迷ったら実行するよう指示している。
- 実装の工程の記録は工程エージェントの申告なので、偽の記録を作れば、最終レビューが検証を実行しないことがありうる。
- sacty が PR に足す成果物のファイルは、実装の工程の作業領域に無いので、そのファイルを検査しうる検証は、実装の工程の記録から使い回させない。
