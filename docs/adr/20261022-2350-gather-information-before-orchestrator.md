# オーケストレーターの前に情報収集のエージェントを置き、集めた情報をすべての工程とゴールガーディアンに引き継ぐ

## 背景

実際に使ってみて、オーケストレーターがタスクの内容（チケットの本文）だけから進め方を選ぶと、人の判断とずれることがわかった。
人は、チケットに書かれていることだけでなく、親のストーリー・エピックの目的、チケットに貼られた URL の中身、関係する文書や議論など、
暗黙のうちに周りの情報を集めてから進め方を決めている。

それまでの仕組みでは、周りの情報を読むのは次のときだけだった。

- チケットのトリアージ：サブタスクなら親とほかのサブタスクを読むが、目的は作業するリポジトリ・題・概要を決めることで、エピックまでは辿らない。
- 前段の調査（`investigate`）：オーケストレーターが進め方を選んだ後に動き、主に対象リポジトリのコードを読む。

また、工程ごとのエージェントとゴールガーディアンは、それぞれの指示に入っているもの（タスクの内容・承認済みの成果物）しか知らず、
同じ背景を毎回自分で集め直すか、知らないまま進めていた。

## 決定

- タスクの開始時（工程を選ぶ前）に1回、情報収集のエージェントを動かす。
  取り込み元のチケットの親（ストーリー・エピック）・リンク・コメント、本文にある URL、使える MCP サーバー・外部 PF・コンテキストの規約から、
  タスクに関係する情報を集めて絞り込み、決まった見出しのまとめ（と情報源）を出させる。
  結果は作業履歴に `InformationGathered`（actor は `gatherer`）として記録する。
- チケットから取り込んだタスクでは、情報収集がチケットのトリアージを兼ねる。同じ実行で、集めた情報からプロジェクトの対象の中で
  作業するリポジトリを選び、タスクの題と概要も書かせる（`TicketTriaged` を actor `gatherer` で、費用を持たずに記録する）。
  決められなければ、集めた情報は残して止め、人がリポジトリを選んで再開したら、チケットのトリアージだけをやり直す（集め直さない）。
  人がリポジトリを選んだら固定し、題と概要を書き直すのは今までと同じ。
- 情報収集は外部の情報を集める役割とし、対象リポジトリのコードの調査は今までどおり調査の工程に任せる。
  読むだけで、書き込み・送信はさせない。
- まとめは、オーケストレーター（工程の選択・工程の見直し・質問への答えなど）・やり直すチケットのトリアージ・すべての工程・ゴールガーディアンの指示に添える。
- ゴールガーディアンには、人間が承認したものではないので背景の理解にだけ使い、判定の根拠にしないよう添える。
- 承認ゲートは設けない。まとめはタスクの詳細に出し、人が読めるようにする。
- 集められなかった・読めなかったときは、工程の選択と同じく `OrchestratorFailed`（actor は `gatherer`）を記録し、代わりのエージェントで集め直すか一時停止する。
  集めずに先へは進めない。
- AI は `step_agents.gather`、無ければオーケストレーターの AI。費用はタスクの予算に入れる。
- 分割の子タスクは集め直さず、親のまとめを子タスクの内容に添える。工程を選び終えたタスク（この仕組みの前のものを含む）では集めない。

## 理由

- 進め方の判断は、タスクの周りの情報があって初めて人の判断に近づく。オーケストレーター自身に集めさせると、工程の選択の指示が
  大きくなり、集めた情報が工程の選択の答えの中に埋もれて、後の工程やゴールガーディアンに渡せない。
  役割を分けて、まとめを独立した記録にすると、どの指示にも同じものを添えられる。
- トリアージを兼ねさせたのは、トリアージもチケット（と親）を読み解く作業で、情報収集の一部だから。
  別々に動かす案（情報収集 → トリアージ）も一度作ったが、同じチケットを2回読み、実行が1回多くなる。
  トリアージを先にする案（トリアージ → 情報収集）は、リポジトリ選びが今までどおりチケットの本文だけに頼ることになり、
  エピックや設計書から「どのリポジトリの話か」を判断できない。兼ねさせると、集めた全体を見てリポジトリを決められ、実行も1回で済む。
- 調査の工程に寄せる案は採らなかった。調査は進め方を選んだ後に動き、組み合わせによっては無い（設計だけ・文書作成・作業）。
  また、調査はコードを読む工程で、外部の情報を集める役割とは前提（リポジトリの用意の有無）が違う。
- 集めた情報を指示の外（ファイル）で渡す案は採らなかった。読まれるかどうかがエージェント次第になり、ゴールガーディアンの判定に
  何が入ったかを作業履歴から追えなくなるため。
- ゴールガーディアンにも渡すのは、用語・経緯・関係する仕様を知らずに判定すると、承認済みの成果物の意図を取り違えることがあるため。
  ただし、[監査が登録したメモリーの ADR](20261018-0130-audit-memory.md) で、ゴールガーディアンの判定の材料を承認済みのものに限る
  （公正さの原則）としているので、判定の根拠にはさせない。
- 承認ゲートを設けないのは、[前段の調査を承認せずに次へ進める決定](20261012-0516-preliminary-investigation-without-approval.md)と同じく、
  人が判断するのは成果物であり、そのための下調べで止めると待ちが増えるため。
- 失敗したら止めるのは、[オーケストレーターが失敗したら止める決定](20261013-0003-stop-when-orchestrator-fails.md)と同じく、
  情報が無いまま進めると、この仕組みを入れた目的（人の判断に近づける）が失われるため。

## 影響

- どのタスクも、工程を選ぶ前にエージェントの実行が1回増え、その分の費用と時間がかかる（チケットのタスクは、トリアージの実行を兼ねるので増えない）。
- チケットのトリアージの費用は、情報収集の費用に含まれ、工程ごとの費用の表の「チケットの読み取り」の行には出なくなる（やり直したときだけ出る）。
- まとめは 30000 文字までで、オーケストレーター・工程・ゴールガーディアンの指示に毎回入るので、その分の入力のトークンが増える。
- 外部の文書やチャットを読ませるには、ゲートウェイの外部 PF かコンテキストの MCP サーバーに接続先を入れておく必要がある。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md#情報収集) にある。
