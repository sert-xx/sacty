# 完了したタスクの作業領域は、もう使わなくなった時点で消し、中断で残った一時領域は起動時に消す

- 日時: 2026-10-26 00:22 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-157
- 置き換え元: なし
- 置き換え先: なし

## 背景

作業領域の根（`SACTY_HOME/workspaces`）が、使い続けると十数 GB まで増えた。残っていたのは次の2種類だった。

- 実行ごとの一時領域（`_guardian`・`_snapshots`・`_review` などの下の `<実行 ID>`）。実行の finally で消すが、実行中にデーモンを止める・
  再起動すると残る。再起動の後は新しい実行 ID でやり直すので、二度と使わない。起動時に片付けていたのは `_shared-compose` だけだった。
- 完了したタスクの作業領域（`<タスク ID>`）と、退避した git のメタデータ（`_git/<タスク ID>.git`）。消していたのは中止のときだけで、
  完了したタスクのものは残り続けた。

完了の後も作業領域を使う処理がある（監査は実装の作業領域の写しを読む。質問への答え・再レビュー・完了したタスクの中止も使う）ため、
いつ消せるかを決める必要があった。

## 決定

- 完了したタスクは、もう作業領域を使わなくなった時点で、作業領域と退避した git のメタデータを消す。
  - 工程をすべて終えて止まっていて、監査をするタスクは監査が終わった（完了か失敗）もの。予算で止まった監査・工程の外のマージの後の監視を
    待っている以前のタスク・停止を確かめられなかったコンテナがあるタスクは残す。
  - 実行・質問への答えの途中なら消さず、その終わりに消す。
- デーモンの起動時（実行を再開・始める前）に、動いている実行のものでない実行ごとの一時領域と、上と同じ基準でもう使わない完了したタスク・
  どのタスクのものでもない作業領域を消す。
- 消すのは作業領域の根の下で、タスク・実行の ID（UUID）の形をした名前のものだけ。リンクの先はたどらない。動いているコンテナが
  マウントしている場所と重なれば消さず、Docker に問い合わせられなければ何も消さない。消せなくても、理由をログに残して続ける。
- 消した後に作業領域を使う操作は、記録した起点のコミットで用意し直す（工程の実行の準備・コードの写しを渡す実行の前・完了したタスクの中止）。

## 理由

- 完了したタスクの作業領域は、監査が終わればほとんど使わない。使う操作（再レビュー・質問・中止）は、もともと消えた作業領域を同じ起点で
  用意し直す仕組み（`prepareRepository`）があるので、それに寄せれば残しておく必要がない。
- 監査は実装の作業領域の写しを読むので、監査が終わるまでは残す。予算で止まった監査は上限を上げて続けられるので、終わったとは扱わない。
- 一定の日数だけ残す案・容量の上限で古いものから消す案は採らなかった。設定が増え、いつ消えるかが利用者にわかりにくくなるうえ、
  消した後に用意し直す仕組みがあるので、残す利点が小さいため。
- 実行ごとの一時領域は、実行 ID が実行ごとに新しく、再起動の後に使われないので、起動時に消してよい。デーモンはインスタンスのロックで
  1つだけ動くので、起動時には自分の実行は動いていない。ただし前のデーモンが突然落ちるとコンテナが残りうるので、動いているコンテナの
  マウントと突き合わせる。

## 影響

- ディスクの使用量が、動いているタスクと監査の途中のタスクの分にとどまる。
- 完了したタスクへの質問・再レビューは、clone をし直すぶん時間がかかる。質問への答えに渡すコードは起点のコードなので変わらない。
  監査の後に実装後のコードの写しを使う処理は、起点のコードを読むことになる（いまは監査だけが使い、監査の後には使わない）。
