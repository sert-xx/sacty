# 画面は、起動ごとの秘密で入ったブラウザだけが使える

- 日時: 2026-10-18 04:14 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-129
- 置き換え元: なし
- 置き換え先: なし

## 背景

画面（Next.js）は呼び出し元を確かめず、デーモンのトークンを付けてどのリクエストも中継していた。画面は 127.0.0.1 で待ち受けるが、工程の
コンテナも `host.docker.internal` 経由でホストの 127.0.0.1 に届く（ゲートウェイがこの経路で動いている）。対象リポジトリのテストや、
プロンプトインジェクションでコンテナ内のコードが動くと、画面を通して承認のゲートを通す・他のプロジェクトの情報を読む・設定を変える
ことができた（Codex Security の指摘）。Next.js の Server Actions の Origin と Host の比較は、ブラウザでないクライアントが両方を偽れるので、
認証の代わりにならない。

## 決定

- `sacty up` が起動ごとに画面の入り口の秘密を作り、画面にだけ渡す（デーモンには渡さない。デーモンは工程のコンテナを動かすため）。
- 端末に、秘密を含む入り口の URL を表示する。開いたブラウザに、秘密から作った値の cookie（`HttpOnly`・`SameSite=Lax`）を渡す。
- Proxy で、すべてのリクエストの Host（ループバックだけ）と cookie を確かめる。デーモンへ中継する所（`daemonFetch`）でも cookie を
  確かめ直す（Proxy の範囲から外れた入口があっても、デーモンのトークンを使わせない）。
- 入り口の URL は、その起動の間は何度でも使える。起動し直すと秘密が変わり、前の cookie と URL は使えなくなる。

## 検討した案

- **Host と Origin の確かめだけ**：DNS rebinding は防げるが、コンテナ内のクライアントは Host・Origin を自由に付けられるので、承認の
  代行を防げない。
- **使い捨ての入り口の URL**：URL が漏れたときの危険は小さくなるが、別のブラウザで開き直すたびに起動し直す必要がある。URL は利用者の
  端末にしか出ず、起動し直せば使えなくなるので、その起動の間は何度でも使えるようにした。
- **コンテナからホストへの通信を遮断する**：ゲートウェイ（AI・組織内 PF・MCP の中継）が同じ経路を使うので、画面のポートだけを
  遮断する仕組みが Docker の環境ごとに要る。画面の側の認証のほうが、環境に依らない。
- **パスワードでのログイン**：1 人のローカルの道具に、パスワードの管理を持ち込むことになる。起動した端末を持っていることを本人の
  証明にすれば足りる。

## 結果

- 工程のコンテナで動くコードは、画面を通してデーモンを操作できない。
- 利用者は、起動のたびに端末の URL を開く必要がある（cookie が残っていても、起動し直したら入り直す）。
- 通知（Slack など）のリンクは、入ったブラウザなら今までどおり開ける（`SameSite=Lax`）。入っていなければ、入り方を出す。
