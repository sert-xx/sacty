## 背景

#6 で、実装・テストの実行・最終レビューまでを作った（PBI-10 の前半）。後半（PBI-10b）として、最終レビューに通った成果を
対象リポジトリに出し、人間が最後に確かめる場所を決める必要があった。

## 決定

- PR の作成の工程は、エージェントではなく sacty が実行する。最終レビューに通ると、自動で実行待ちになる。
- コミットは、#6 で退避した git のメタデータで作る（一時インデックス・外部のコマンドなし）。エージェントが書き換えた作業領域の git の設定は評価しない。
  作業領域の HEAD は動かさない。作者はホストの git の利用者の設定を使う。
- コミットの作者とコミッターの日時は、その提出の最終レビューの日時に固定する（`GIT_AUTHOR_DATE`・`GIT_COMMITTER_DATE`）。
- プッシュ先は `sacty/task-<id>`。再提出は前回のコミットに積み、強制プッシュはしない。
- PR は、`repository.pull_request`（`provider: github`・`token_secret`）を設定したときだけ GitHub API で作る。2回目以降の提出では同じ PR の本文を更新する。
  設定が無ければ、ブランチのプッシュまでにする。トークンはキーチェーンから取り出し、エラーの文から取り除いてから台帳に記録する。
- PR の本文には、承認済みの要求要件、「観点 → テスト → 実行結果」の表、テストの結果、最終レビューを載せる。
- 起点から変更が無ければ、PR を作らずに理由を記録して止める。
- PR を作ったら、成果物チェックのゲートで止める。承認するとタスクは完了。差し戻すときは、やり直す工程（実装・設計・要求要件）を選べ、既定は実装。
  実装への指摘には工程のエージェントが対応を答え、その対応は成果物チェックの何回目の提出への対応かを記録する。

## 理由

- コミットの日時を固定するのは、プッシュの後、台帳に記録する前に失敗して再開すると、作り直したコミットが前回プッシュしたものと枝分かれし、
  non-fast-forward で拒否されて PR の作成まで進めなくなることがレビューで再現されたため。同じ提出なら同じコミットになるので、
  プッシュと記録の間でプロセスが落ちた場合も回復できる。副作用の前に台帳へ記録する方式では、その場合を回復できない（レビューへの返信）。
- 実装への対応を成果物チェックの提出回に対応付けるのは、実装は成果物チェックの提出として人間に示すため（レビューへの返信）。
- PR の作成を sacty が行う理由、強制プッシュをしない理由、PR の作成を設定したときだけにする理由は、記録に無い。

## 影響

- PR の作成を設定しなければ、ブランチのプッシュまでで成果物チェックに進む。
- 実際の GitHub への PR の作成は、この時点では確かめていない（外部に公開される操作のため）。
- #6 で最終レビューに通り、PR の作成の手前で待機していたタスクは、起動の時に実行待ちにする。
