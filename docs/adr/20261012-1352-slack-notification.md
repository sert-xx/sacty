# 人間の出番（承認待ち・エスカレーション・一時停止・完了）を、プロジェクトごとに設定した Slack の通知先に送る

- 日時: 2026-10-12 13:52 UTC
- ステータス: 採用
- 関係する PR・タスク: #44、PBI-38
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty を自走させるうえで、人間の出番を知らせる手段が無かった（構想の「通知」）。利用者の環境では、認証の要らない Slack Proxy
（Slack API と同じ形で、chat.postMessage にチャンネルと本文を送る）を経由する。Slack のワークスペースが複数あり、Proxy のホストも違う。

## 決定

- 通知するのは、承認待ち（要求要件・設計・成果物チェック・統合レビュー・再現できなかった判断など。差し戻して出し直したときも）・
  エスカレーション・一時停止・タスクの完了。人間が自分で一時停止したときは通知しない。
- 通知先はプロジェクトの設定（`notification`）で選ぶ：Slack API の形（`slack-api`：URL・チャンネル・任意のトークン）か Incoming Webhook
  （`slack-webhook`：URL を秘密情報として書く）。言語（日本語・英語）もプロジェクトの設定。設定しなければ通知しない。エクスポートにも含める。
- 秘密情報（トークン・Webhook の URL）は、名前か `op://` の参照だけを受け付ける（値の URL を書いたら誤り）。作業履歴・画面・ログに出さない。
- 本文（Slack の mrkdwn。タイトルなどは逃がす）に、タスクのタイトル・何の判断か・タスクと承認の窓口へのリンク（成果物チェックは PR も）を
  入れる。画面の URL は、`sacty up` で起動した画面の URL（`SACTY_WEB_URL`）。
- 作業履歴を書いたときに、状態の変わり方を見て通知する。送るのは待たず、送れなくてもタスクは止めない。Slack API の `ok:false` も
  送れなかったとして扱う。送れなかった理由は秘密情報を伏せ、プロジェクトごとにタスクの一覧の画面に出し、送れたら消す。
  HTTP の失敗の本文は、伏せてから理由の長さを制限する。
- プロジェクトの設定の画面から、保存した設定でテストの通知を送れる。

## 理由

- 自走させるうえで、人間の出番を知らせる手段が無かったため（PR の本文）。
- 通知する場面と、Slack Proxy を経由することはステークホルダーが決めた（PR の本文）。Slack Proxy が Slack API と同じ形で、ワークスペースごとに
  ホストが違うことが、通知先をプロジェクトごとに書く前提になった（PR の本文）。
- 通知先の2つの形・言語をプロジェクトの設定にすること・人間が自分で止めたときは通知しないこと・送れなくてもタスクを止めないことは
  PO が決めた（PR の本文）。それぞれの理由は記録に無い。
- HTTP の失敗の本文を伏せてから切り詰めるのは、先に切り詰めると、境界をまたぐトークン・Webhook の URL の一部がログ・画面の警告・
  テストの通知の例外に残っていたため（レビュー）。

## 影響

- ワークスペースが違えば、プロジェクトごとに送り先を変えられる。
- 通知が送れなくてもタスクは進むので、送れなかったことは画面の警告で気づく必要がある。
