# 質問への答えだけのコメントを新しい要望と分けて軽く直し、レビュー・判断の読み違いと作り込みを防ぐ

- 日時: 2026-11-04 04:10 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-302（B1〜B6）
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験 r5（2026-11-04、1.16.0）で、差し戻し・レビュー・判断に関わる問題が見つかった。

- S5：要求要件の should（確認したいこと）に「推奨どおり」と答えただけのコメントが、原因「新しい要望・方針の変更」の差し戻しになり、要求要件を丸ごと作り直した（セルフレビュー・出典の分類も走った。報告額で約 $1.45）。成果物の変化は答えの書き足しだけだった（F48）。
- S16：Sacty のレビューが、レビューした head では直っていた指摘を「未対応」と書き、判定を「修正が必要」にした。行コメントは [提案] 1 件だけだった（F50）。
- S14：ゴールガーディアンが、89 行目へのコメントを 88 行目の内容として読んだ。
- S16：要求要件にも設計にも無いキュー（共有の仕組み）が、4 回続けて実装に入った。
- S5：オーケストレーターが要求要件を残す理由に 3 つ挙げたが、要求要件の「確認したいこと」に出たのは 1 つだけだった。残した理由のうち 2 つは、受け入れ条件と既定で決められる点（完了の条件に含めるコマンドの食い違い・受け入れ条件が決めた変更に伴う呼び出し側の扱い）だった（F34 の再発）。
- S14：監査が、SactyTest 全体（プロジェクトの階層）のメモリーに、依頼者の答え（画面は要らない・15 分にそろえる・上限なしなど）を事実として登録した。次に同じ種類のシナリオを流すと、答えが漏れる（F49）。

## 決定

- **質問への答えだけのコメントは、差し戻しの原因を `question_answer` として、新しい要望（`new_request`）と分けて記録する**。要求要件・設計の PR のとき、ゴールガーディアンが、戻し先・原因と一緒に、答えが推奨どおりか（`answer`: `as_recommended`・`changes_decision`）も判断する。
  - **推奨どおりで、その PR の工程を直すときだけ、答えの反映だけの軽い直しにする**。前回の下書きを元に、答えた項目を「確認したいこと」から外し、答えを反映する所だけを直す。セルフレビューは走らせず、読み直す 3 点だけ確かめさせる。出典の分類と、指摘ごとの対応の報告は今までどおり。
  - 推奨と違う答え・答えの扱いを読めなかったときは、今までどおりの直し（作り直しとセルフレビュー）にする。
- **前の指摘の対応は、レビューする head のファイルで確かめさせる**。未対応と書くときは、読んだ箇所を添えさせ、示せないものは未対応と書かせない。判定「修正が必要」は、その head で成り立つ要修正の指摘に基づかせる。指示と既定のスキルの決まりで、sacty は未対応の主張を head の内容と照らさない。
- **行コメントの指摘には、そのコメントが付いた行の内容と直前の 2 行を添える**。GitHub のコメントの diff の抜粋（`diff_hunk`）から取る。ゴールガーディアンと直しの実行には、行番号から数えず、添えた行の内容で箇所を確かめさせる。
- **実装には、要求要件・設計に無い共有の仕組みを足させない**。どうしても要るときは、実装の説明に理由を書かせ、最終レビューが「人が確かめること」に挙げる。理由が無い・足さなくても満たせるものは、範囲外として不合格にする。
- **オーケストレーターが要求要件を残した理由を、最初の要求要件の実行に渡す**。理由ごとに「確認したいこと」に出すか、「確認しないと決めたこと」に確認しない理由を書かせる。あわせて、人に確かめることが無い理由（作るものが変わらない文書どうし・文書と受け入れ条件の食い違い、受け入れ条件が決めた変更に伴う追従、実装が決められる食い違い）だけでは、要求要件を残させない。#285・#289 の決まりと、残すべき例外は変えない。
- **監査が登録するメモリーを、登録の前に機械的に検査する**。依頼者を主語にした文がある、または依頼者が書いた文（依頼の本文・人の指摘・再開の補足）を写した部分があるメモリーは登録せず、題と理由を `AuditDeepDived` の `skippedMemories` に残す。あわせて、監査の指示にも、依頼者の答えを事実として書かないことを足す。

## 理由

- 質問に答えるのは正しい使い方で、答えるほど費用がかかる形にしてはならない。推奨どおりの答えは承認済みの決定を変えないので、成果物を作り直す理由が無い。判断は戻し先の判断と同じ実行でできるので、実行を増やさない。
- 軽い直しの条件を狭く（推奨どおり・その PR の工程・判断した指摘の集合そのもの）したのは、決定を変える答えを軽く扱って、反映漏れを人に見せないため。迷うときは今までどおりの直しに倒す。
- セルフレビューを省く代わりに読み直す 3 点を決めたのは、答えの反映が小さな変更で、前回の下書きがセルフレビューを通っているため。記録なしになるので、次の直しは全体をレビューする。
- 前の指摘の「未対応」は、前の版や前回の判定を根拠にすると、直っていても残る。head のファイルを開いて読ませ、読んだ箇所を添えさせれば、根拠の無い未対応の主張が書きにくくなる。機械で検査しないのは、未対応の主張が正しい場合（前回の指摘が本当に残っている）と見分けられないため。
- 行番号は、エージェントが成果物の行を数える限りずれうる。GitHub が返す抜粋なら、コメントを書いた人が見ていた行そのものを確かに渡せる。
- 共有の仕組みは、正常な使い方のテストが通っても、失敗後に状態が残る回帰を持ちうる（#302 A2）。足させないことが先で、足したなら理由を人に見せる。
- オーケストレーターの理由は、要求要件の工程の費用をかける根拠なので、確認事項に結び付ける。結び付かない理由は、残す理由として弱いので、先に残させない。
- 依頼者の答えをメモリーにすると、次のタスクの依頼に混ざって要求を先に決める。指示だけでは防げなかった（#294 は工程の指示を優先させただけ）ので、登録の前に検査する。

## 影響

- どれも指示の文面と機械的な検査での対策で、エージェントが従うかは確率的に変わる。実タスクでは未確認。
- 要求要件を残す理由の見直しは、実際の AI に依頼を当てた比較で、S5 r5 の情報収集の出力に対して省く割合が 2/7 から 7/7 になり、残すべき依頼（S8・S9・S10・S13a）は変更後すべて残った（[作業履歴](../worklog/20261104-pbi-302-r5-followups.md)）。通しの実行では未確認。
- 軽い直しではセルフレビューをしないので、答えの反映で成果物が崩れても、次の直しまでセルフレビューは入らない。人が PR で確かめる。
- 行へのコメントの指摘に添える行の内容は、コメントが付いた行とその前だけ（後ろの行は GitHub の抜粋に無い）。
- 依頼者の答えの検査は、依頼者を主語にした文と、依頼者の文の写しだけを見つける。言い換えた答えは見つけられない。
