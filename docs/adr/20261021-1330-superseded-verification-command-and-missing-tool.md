# テストのコマンドを検証のコマンドに広げ、ツールがイメージに無ければイメージを直す案内で止める

- 日時: 2026-10-21 13:30 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: [ゴールガーディアンが最終レビューの中でテストを実行し、sacty はテストのコンテナを使わない](20261021-1431-superseded-guardian-runs-tests.md)（ツールが無いことを sacty のテストの実行の終了コード 127 と出力で見分け、`TestsRun`・`ReproductionChecked` を記録せずに止める部分）

## 背景

Kubernetes のマニフェストのリポジトリで実装のタスクを作ると、「オーケストレーターが、対象リポジトリのテストのコマンドを決められませんでした」
（`orchestrator.testCommandUnknown`）で止まった。オーケストレーターへの指示は、テストのコマンドを package.json・Makefile・CI から決めさせ、
「テストの仕組みはあるのにコマンドが分からないときは `noTests` を書かない」としていた。マニフェストのリポジトリには、単体テストは無いが、
CI で `kustomize build`・`kubeconform` などの検証を実行していることが多く、これを「テストのコマンド」と呼んでよいかが指示から読み取れず、
`testCommand` も `noTests` も空になりやすかった。

また、検証のツールが入っているイメージが無いと、テストのコマンドを決めても、テストの実行が `command not found`（終了コード 127）で失敗する。
これはふつうのテストの失敗として扱われ、実装をやり直しても直らないまま、`MAX_VERIFY_ATTEMPTS` 回の実装の費用をかけて一時停止していた。

## 決定

1. **検証のコマンドもテストのコマンドにする**：オーケストレーターへの指示で、`testCommand` を「テスト（検証）のコマンド」とし、テストのコードが
   無くても、成果物を機械的に確かめる検証（`kustomize build`・`helm lint`・`kubeconform`・`terraform validate`・`yamllint` など）を
   CI・Makefile・pre-commit が実行しているなら、それを書かせる。そうした設定が無くても、リポジトリの形からツールが決まる
   （`kustomization.yaml` なら `kustomize build`、`Chart.yaml` なら `helm lint` など）なら書いてよい。`noTests` は、テストの仕組みも
   検証のコマンドも無いときだけにする。
2. **ツールがイメージに無くても空にさせない**：使うツールが選べるイメージのどれにも無くても、`testCommand` を書かせる（空にすると
   「決められなかった」で止まり、何が足りないかが分からないため）。テストを実行するイメージの選び方の例に、検証のツールを足す。
3. **ツールが無いことを見分けて案内する**：テストの実行が終了コード 127 で、出力に sh の `<名前>: not found`・`<名前>: command not found`
   の行があり、その名前がテストのコマンドの中に語として書いてあるときは、テストの結果（`TestsRun`）・再現の確かめ（`ReproductionChecked`）を
   記録せずに一時停止する（`verify.commandMissing`）。文言には、ツールの名前・テストのイメージの名前・工程を出し、`images.<名前>` の
   `packages`・`run` でツールを入れて `sacty image build` で作り直す（既定のイメージなら `images` にイメージを足す）か、工程のイメージを変える
   よう案内する。検証（再現の確かめ）を待ったまま止めるので、再開するとテストから実行し直す。

## 理由

- 検証のコマンドを含めたのは、「決められなかった」で止めるより、リポジトリが実際に使っている検証で確かめるほうが、テストの無いタスクとして
  目的だけで判定するより確かなため。「テストの仕組みはあるのにコマンドが分からないときは止める」方針（[テストの仕組みが無いリポジトリ](20261015-0000-superseded-verify-without-test-command.md)）は変えない。
- テストのコマンドに語として書いてある名前だけを当てるのは、イメージの問題とリポジトリの問題を分けるため。`npm test` の中のスクリプトが
  使うツールが無いのは依存の入れ忘れなど実装で直りうるので、今どおり実装をやり直す。`/` を含む名前（`./scripts/check.sh`）も、
  リポジトリのファイルなので当てない。
- テストの結果を記録しないのは、再開したときに実装をやり直さず、直したイメージでテストから実行し直すため（サービスを起動できなかったときと同じ）。
- 終了コード 127 だけでなく出力の行も見るのは、テストのコマンドの中の別のプログラムが 127 を返したときに、イメージの問題と誤って案内しないため。

## 影響

- 新しい文言 `verify.commandMissing` が増える。イベントの形は変わらない。
- テストのコマンドを決められるタスクで、テストのコマンドに書いたツールが無いときは、実装をやり直さずに止まる（これまでは実装を3回やり直して
  から止まっていた）。
- sh の文言で見分けるので、`sh` が dash・busybox・bash 以外で文言が違うイメージでは見分けられず、今どおりテストの失敗になる。
