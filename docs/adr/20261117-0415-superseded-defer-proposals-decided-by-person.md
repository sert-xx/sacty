# 後続に回すかどうかは人が決め、実装は案と理由までを出す

- 日時: 2026-11-17 04:15 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: #406、PBI-370
- 置き換え元: なし
- 置き換え先: [人の差し戻しの回数の上限を無くす](20261120-0100-no-limit-on-human-change-requests.md)（「この PR で直す」の差し戻しを上限に数える部分）、[AI のレビューの提案に対応するかどうかは、直しに入る前に AI が PR の範囲で判断し、対応しない判断は AI で終える](20261120-2109-superseded-triage-ai-review-suggestions-before-rework.md)（AI のレビューの提案について、この PR で直さないかの最終決定を人がする部分。直しに入る前に AI が判断して終える）

## 背景

指摘への対応の申告は、「対応した」「理由があって対応しなかった」の 2 つだった（[取り込んだ PR の指摘への対応を、指摘ごとに PR に返信する](20261116-0045-superseded-reply-to-review-feedback-on-pull-request.md)）。指摘を、この PR では直さずに後続に回す、という選択肢が無く、実装は、範囲を広げてでも応じるか、断るかしかなかった。

実際に、次のことが起きた。

- 稀な条件の指摘に応じるために、実装が新しい仕組みを足し、次の回からは、その仕組みへの指摘が続いた。レビューが 13 回続いた PR があった。
- 範囲の外の読み取りへの指摘に、実装が 4 回続けて応じ、PR の変更が 2 倍に増えた PR があった。

レビューの側の重みの基準は、[レビューの指摘の重みを、影響の大きさと起きやすさで決め、自己レビューは要修正だけを修正に戻す](20261117-0244-superseded-review-finding-weight-by-impact-and-likelihood.md)で決めた。ここでは、指摘を受けた側と、人の決定を決める。

人が決めたこと（2026-11-17。選択式で 1 件ずつ確かめた）：

1. 後続に回すかどうかの最終決定は、人。実装が出せるのは、「後続に回したい」という案と理由まで。
2. 実装が PR に返信するときは、決まったことのように書かない。案であり、人に確認中で、まだ決まっていないことを明記する（指摘した人がすぐに読んで、議論が起きうるため）。
3. 決める時点は、マージ前にまとめて。実装は案を返信して往復を続け、人の承認の画面に一覧を出し、1 件ずつ「後続に回す／この PR で直す」を人が決める。人が「この PR で直す」と決めたら、差し戻しになる。
4. 人の PR のレビューの指摘にも、実装は案を出せる。
5. 人が後続に回すと決めた要修正は、AI のレビューの判定で未対応に数えない。
6. 案にしてよい指摘：提案の重み（影響が小、または影響が中で稀）のうち、直すのに新しい仕組みが要るもの・PR の範囲の外のもの。小さく閉じて範囲の中の提案は、その PR で直す。影響が大のものは直す。直すために、新しい仕組みを自分で足さない。
7. どれを選んでも、決定と指摘の一覧は、PR のコメントに残す。

人が後続に回すと決めた指摘の扱い（sacty の後続のタスクを作る・GitHub の Issue を作る・何もしない）を選べるようにすることも決まっているが、この決定には含めない（後の PR で足す）。

## 決定

- 申告：実装の工程の、差し戻しの指摘への対応に、`deferred`（後続に回したい案）を足す。理由は、対応の文に書く。指示で、上の 6 の基準を伝える。
- 返信：案への返信の頭に「この PR では直さず、後続に回したいという案です（人に確認中で、まだ決まっていません）」と書き、末尾に、タスクを承認する人がマージの前に決めることを添える。
- 一覧と決定：実装の承認待ちのとき、まだ決めていない案を承認の画面に出し、人が 1 件ずつ決める。決定は作業履歴に記録する（`DeferralsDecided`）。
  - 「この PR で直す」が 1 件でもあれば、同じ追記で、その指摘を実装に差し戻す。
  - 決定のたびに、決定と指摘の一覧を、PR に 1 件コメントする。
- レビューの判定：人が後続に回すと決めた指摘を、PR のレビューの子タスクに、指示とは分けたデータで渡し、重みに関わらず、未対応に数えさせない。

着手のときに決めたこと（人の確認は、まだ）：

- 人に確認中の案を、レビューがどう扱うか：提案の重みなら、未対応に数えず、もう一度指摘させない（人が決めるまで、AI どうしの往復を続けない）。要修正の重みなら、人が後続に回すと決めるまで、未対応として残させる。
- 先頭を変えずに、指摘のすべてを、断るか案にしたとき：[AI のレビューの指摘をすべて断って何も変えなかったら、断った理由を返信し、同じ先頭を 1 回だけ判定し直させる](20261117-0250-reply-and-rejudge-when-all-findings-declined.md)と同じく、提出にして返信する。その決定は変えず、新しい申告（案）を、断った指摘と同じ扱いに足す。ただし、案が 1 件でもあれば、同じ先頭の判定のし直しは、案のすべてを人が決めてから始める。
- 一度案にした指摘は、後の実行に、対応させる指摘として渡さない（人に確認中の案も）。人が決めるまで、実装に直させない・取り下げさせない。
- 「この PR で直す」の差し戻しは、人の差し戻しとして、回数（同じ工程への差し戻しの上限）に数える。指摘の文は元の指摘の文で、人が決めたことの印を付けて実装に渡す。
- 一覧は、提出の時点から出す（レビューの往復の途中でも決められる）。
- 決める前でも、PR のマージは止めない。決めないままマージしたら、マージを承認として進め、案は決めないまま残る。
- 案を出せるのは、実装の工程の、差し戻しの指摘（PR のコメントから取り込んだ指摘と、画面から書いた指摘）だけ。実装のほかの工程と、引き継いだ PR で実装に渡した指摘には、出せない。
- PR のコメントを残せなかったときは、理由を作業履歴に記録し、やり直さない。セキュリティの組み合わせのタスクでは、PR にコメントしない。
- PR のコメントに、指摘の文と理由を載せるのは、その PR のコメントから取り込んだ指摘だけ。sacty の画面から書いた指摘は、指摘の ID と決定だけを載せる。

## 理由

- 案を、対応の申告の 1 つにする：指摘ごとの対応の文・PR への返信・二重の投稿の防ぎ方・レート制限に当たったときのやり直しを、そのまま使える。
- 人に確認中の案を、提案の重みなら数えさせない：数えると、レビューが同じ指摘を出し、実装が同じ案を返す往復が、人が決めるまで続く。要修正の重みを残すのは、人が決める前に、AI が要修正を取り下げたことにしないため。
- 判定し直しを、人が決めてから始める：決める前に判定し直すと、案にした要修正が未対応のまま残り、1 回だけの判定し直しを使って、一時停止になる。人が決めた後なら、後続に回すと決めた指摘を数えずに判定できる。
- 一度案にした指摘を、実装に渡さない：PR に「人に確認中」と返信したまま、実装が黙って直す・取り下げると、PR の返信と実際が食い違う（1 件の指摘には、1 回だけ返信するため）。
- 「この PR で直す」を、新しい差し戻しの指摘にする：差し戻しには指摘が要り、回の番号・指摘の ID・PR への返信（直したことを、元のコメントにもう一度返信する）を、今の作りのまま使える。
- マージを止めない：PR は GitHub でマージされ、sacty は止められない。ドラフトに戻して止める案は、指摘なしでドラフトを外す今の決まり（[最終レビューをしない流れ](../spec/tasks-and-steps.md#最終レビューをしない流れ)）と重なるので、採らなかった。
- 画面から書いた指摘の文を、PR に載せない：画面から書いた指摘と、それへの対応は、今まで PR に出していない（指摘への対応の返信は、PR のコメントから取り込んだ指摘だけ）。決定のコメントで、初めて PR に出すことはしない。内容は、タスクの画面で読める。
- 引き継いだ PR の指摘に案を出させない：引き継いだ PR の指摘は、実装のたびに渡し直す別の記録（`continuedResponses`）で、差し戻しの指摘ではない。案の記録と一覧を、もう 1 つの記録にも足すことになるため、最初の版では扱わない。

## 影響

- 実装の指示に、案の書き方と基準が増える。案にした指摘は、人が決めるまで、どの実行も直さない。
- 承認の画面とタスクの詳細に、後続に回したい指摘の一覧（件数）が出る。人の判断が 1 つ増える。
- 「この PR で直す」は、人の差し戻しの回数を 1 つ進める。
- 人が後続に回すと決めた指摘は、PR のコメントに残るだけで、別のタスクや Issue にはならない（後の PR で足す）。
- 決めないままマージされた案は、PR の返信が「人に確認中」のまま残る。
- 同じ先頭の判定のし直しは、今までどおり 1 回だけ。案の決定を待って判定し直した後、同じ先頭でもう一度、何も変えずに案を出しても、提出にせずに一時停止する。
