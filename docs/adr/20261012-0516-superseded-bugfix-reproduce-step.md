## 背景

不具合の修正も、要求要件・設計から始める工程の組み合わせで進めるしかなかった。不具合を直す前に、それが本当に再現できるかを
確かめる手段が無く、直した後に同じ不具合が直ったことを確かめる観点も無かった。

## 決定

- 工程 `reproduce` と、工程の組み合わせ `bugfix`（再現 → 実装 → PR作成。先頭に前段の調査を置く）を足す。オーケストレーターが選ぶ。
  要求要件・設計は省く。大きな修正が要るものは、オーケストレーターが標準の工程を選ぶ。
- 再現の成果物は「失敗するテスト」。再現のエージェントは clone（書き込める作業領域）にテストを書き、`sacty-reproduction` で
  再現のテストを申告する（不具合は直さない）。テストは PR に含める。
- sacty がテストのコマンドを実行し、`ReproductionChecked` を記録する。失敗したら再現できたとして、人間の承認なしに実装へ進む。
  通った・申告が無いときは再現できなかったとして、人間の判断を待つ（差し戻すと再現をやり直す。承認では進めない。中止はできる）。
- テストの実行基盤の失敗（Docker を起動できない・時間切れ・コンテナの停止を確かめられない・`docker run` の終了コード 125）は、
  再現できたとしない。理由を示して、確かめを待ったまま一時停止し、再開でテストを実行し直す。
- 確かめの途中でデーモンが止まっても、再起動の後に確かめる。
- 実装には、タスク・再現の説明・再現のテスト・再現のときのテストの出力を渡し、テストを通すように直させる。検証の観点は `REPRO`
  （再現のテストが通る）。PR の本文では、要求要件の代わりに再現の説明を載せる。
- 成果物チェックからの差し戻しでは、再現には戻せない。再現は変更の申し出の対象にしない。

## 理由

- 成果物チェックから再現に戻せないのは、実装した後のコードでは再現できないため（PR の本文）。
- テストの実行基盤の失敗を再現できたとしないのは、非ゼロの終了コードをすべて再現できたとすると、テストが一度も実行されていない
  ときも実装へ進むため。コンテナの停止を確かめられないときは、テストがまだ作業領域を使っているおそれもある（レビュー）。
- 終了コード 125 も実行基盤の失敗とするのは、Docker の仕様で 125 が Docker 自身の失敗を表し、デーモンに接続できない・イメージを
  取得できないときに注記なしで 125 が返るため（レビュー）。
- 再現できたら承認なしに進めること、要求要件・設計を省くことの理由は記録に無い。

## 影響

- 画面に、工程・作業履歴の再現、再現の説明と確かめの結果（コマンド・終了コード・再現のテスト・出力）を出す。再現できなかったときは
  承認のボタンを出さず、差し戻しの導線を出す。再現の成果物は、人間の承認ではなく sacty の確かめとして出す。
- テストの実行基盤が失敗したら、人間が原因を確かめて再開するまで止まる。
- 実装の検証（`TestsRun`）では、実行基盤の失敗はこれまでどおりテストの不合格として扱う（誤って先へ進むことはないので変えなかった）。
