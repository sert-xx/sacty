# PR に投稿するレビューには判断に要る情報だけを書き、Sacty の過程の情報は Sacty の記録に残す

- 日時: 2026-11-21 16:03 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-460
- 置き換え元: [PR のレビューで親が担当に渡す範囲を差分で決め、観点をどう見たかを本文に書く](20261115-1515-superseded-review-range-decided-by-diff-and-viewpoint-line.md)（本文に観点の見方を1行書く部分）、[観点ごとの担当を 1 件も起動しなかった PR のレビューは、採らずにやり直させ、続いたら止める](20261117-1015-superseded-reject-reviews-that-start-no-reviewers.md)（決定 6 の、本文の最後にエージェント・モデル・担当の数・切り替えを出す部分）
- 置き換え先: なし

## 背景

Sacty が PR に投稿するレビューには、修正の判断に要る情報のほかに、Sacty の過程の情報が入っていた。
たとえば、観点の番号・数・名前、観点ごとの担当の起動と失敗、採用しなかった指摘と落とした件数、動いたエージェント・モデル・切り替え、検証のやり方、Sacty のタスクの ID、作業の経過の文（「レビューの本文を書きます」など）。

PR を読む人（作者・ほかのレビュアー）は、Sacty を使っていないことがある。
その人には、これらの情報は使えず、直すべきか・何が問題かを読み取る邪魔になる。
利用者は 2026-11-21 に、PR には判断に要る情報だけを書き、過程の情報は Sacty の記録に移すと決めた。

## 決定

1. PR に投稿するレビュー（本文・行へのコメント・Sacty が出す PR のコメント）には、判定、総評（本文は総評から始める）、指摘、修正の判断に要る検証の結果（落ちたもの・確かめられなかったもの）、リスク評価、「AI がレビューしました（人間は確認していません）。」の印だけを書く。
2. 次のものは PR に書かない：観点の番号・数・名前、観点ごとの担当の数・起動・失敗、採用しなかった指摘とその一覧、落とした件数、動いたエージェント・モデル・切り替え、Sacty のタスクの ID、検証のやり方（使い回したなど）と通った検証、作業の経過の文。
3. 確かめられなかった所は、本文に中身の言葉で書く（何が未確認で、読む人が何をすればよいか）。観点の番号・担当の語は使わない。取得できなかった文書・省略された差分・読めない既存のレビュー・撮っていない画面・実行していない／止まった検証・基準にしなかったリポジトリの指示も同じ。
4. 絞った再レビューは、本文に「前回（abc1234）以降の変更と前回の指摘だけを確かめた」とだけ書く。絞った理由と起動しなかった観点は記録に書く。取り下げた前回の指摘と理由は、前回の指摘の状態なので、本文の「前回の指摘」の節に残す。
5. 過程の情報は、レビューのエージェントが、本文の後の、情報文字列が `sacty-review-record` のコードブロックの JSON で返す。Sacty は、検査して秘密の値を伏せ、作業履歴（`AgentRunCompleted` の `reviewRecord`）に残し、タスクの画面と MCP の `get_task` で読めるようにする。読めない記録は `null` にし、レビューは投稿する。
6. 投稿する文字列からは、記録を読めたかどうかに関わらず、記録のブロックを取り除く。見出しの無いフェンスは、中身が記録に固有の欄名（`viewpoints`・`notReviewed`・`dismissed`・`dropped`・`verification`）のうち 2 種類以上をキーに持つときに取り除く（見出しの付いたものは、中身によらず取り除く）。
7. 表示されない HTML コメントの目印（タスクの ID を含む）は、投稿とコメントに残す。
8. 同じタスクの再レビューを絞るかは、前回の記録の構造の欄（見られなかった観点・止まった検証）で決める。記録が無い回は絞らない。
9. 返信と工程の成果物のコメントの末尾も、タスクの ID を外し、「Sacty の<工程名>の工程で、AI が書きました。」などにする。担当を起動しないレビューが続いて止まったときの知らせの理由は、過程の語を使わない固定の文にする。

## 理由

- PR を読む人は Sacty を使っていないことがある（利用者の 2026-11-21 の決定）。過程の情報は、Sacty の利用者が画面と `get_task` で読めれば足りる。
- 確かめられなかった所を消すと、読む人が見落としに気づけない。番号や担当の語ではなく中身の言葉で書けば、Sacty を使わない人も何を確かめればよいかが分かる。
- 前の決定の理由は、画面と `get_task` で確かめる形で保つ。
  - [PBI-349 の決定](20261115-1515-superseded-review-range-decided-by-diff-and-viewpoint-line.md)は、Codex では担当の起動が実行のログに出ないので、本文に観点の見方を書かせた。いまは、記録の `mode`・`viewpoints` と、回ごとの担当の数を、画面と `get_task` で確かめる。
  - 見出し（`sacty-review-record`）を付け忘れた、欄名が 1 種類だけの記録は、PR に残りうる。欄名はフェンスごとに数えるので、記録を複数のフェンスに分けた場合も同じである。設定の例が別々のフェンスに分かれているときに、まとめて消えないようにするために受け入れた。
- [PBI-379 の決定](20261117-1015-superseded-reject-reviews-that-start-no-reviewers.md)は、起動が 1 件だけのレビューに人が気づけるよう、本文と画面に担当の数を出した。本文の側をやめ、画面と `get_task` で気づく形にする。
- 記録を JSON のブロックで返させるのは、判定のブロック（`sacty-review-verdict`）と同じく、依頼した側が決めた形で返させ、形を検査できるから。中身は PR を読んだエージェントが書いた信頼しない入力なので、データとして扱い、画面では文字列のまま出す。
- 見出しの無いフェンスや、閉じていないブロックも取り除くのは、エージェントが見出しを書き損ねたときに、過程の情報が PR に出るのを防ぐため。
- 目印を残すのは、Sacty が自分の投稿と知らせを見分けるため。目印は表示されないので、PR を読む人の邪魔にならない。
- 絞りの判断を構造の欄だけで決め、文の中身を読まないのは、信頼しない入力の文で Sacty の判断が変わらないようにするため。

## 影響

- 見出しの無いフェンスは、記録に固有の欄名を 2 種類以上キーに持つときだけ取り除く。`verification:` だけを持つ設定の例のように、1 種類だけなら PR に残る。2 種類以上を持つ記録と関係のない例は消える（指摘の文は残る）。
- [PBI-379 の決定](20261117-1015-superseded-reject-reviews-that-start-no-reviewers.md)の、担当を 0 件しか起動しない実行は採らずにやり直す決まりは変えない。画面の、エージェント・モデル・担当の数・切り替えの表示も残る。
- [PBI-459 の決定](20261121-1330-parent-reviews-failed-viewpoints.md)の影響の節にある「本文の観点の数」は、本文に観点の数を書かなくなったので、当てはまらない。代わりに見た観点は、記録の `viewpoints` に `substituted` として残る。
- 前回の記録が無い回（これより前の作業履歴の回・記録を読めなかった回）は、同じタスクの再レビューを絞らない。この版にした直後の再レビューは、PR 全体を見る。
- PR を読む人は、過程の情報を PR から読めない。Sacty の利用者は、タスクの詳細のレビューの欄と `get_task` で読む。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の PR のレビューの節、[作業履歴](../spec/event-log.md) の投影の節、[MCP サーバー](../spec/mcp-server.md)、[コンテキスト](../spec/context.md) の既定のスキルの節にある。
