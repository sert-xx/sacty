# 後続に回した指摘の扱いの結果をタスクの詳細に出し、後続のタスクを元の PR の引き継ぎの候補にしない

- 日時: 2026-11-17 12:45 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-384
- 置き換え元: なし
- 置き換え先: なし

## 背景

[後続に回すと決めた指摘の扱いを、人が指摘ごとに選ぶ](20261117-0504-choose-handling-of-deferred-findings.md)で、人が、後続に回すと決めた指摘ごとに「sacty の後続のタスクを作る」を選べるようにした。後続のタスクは、元のタスクが完了してから作る。見直しのレビューで、次の 2 点が見つかった。

1. 後続のタスクの結果（後続のタスクへのリンク・作れなかった理由）は、元のタスクの完了の後に記録する。扱いの結果を出していたのは、承認の画面の決定済みの記録だけで、これは実装の承認待ちの間だけ出る。完了の後に記録される結果は、そこには出ない。作れなかったとき（やり直さない）、人は、完了したタスクの作業履歴を開かないと気づけなかった。仕様書とユーザードキュメントは、決定済みの記録に出ると書いていた。
2. 後続のタスクの依頼には、元の PR の URL がある。タスクに対象リポジトリの PR のリンクがあると、オーケストレーターに、その PR を引き継ぐかを決めさせる（[既存の PR を直すタスクは、PR を引き継いで同じブランチに積み、文書だけの観点はテストを書かずに差分で確かめる](20261025-1337-continue-existing-pull-request.md)）。引き継ぐと答えると、元の PR は、元のタスクが扱ったマージ済みの PR なので、引き継げず、工程を決めずに止まる。再開しても、同じ答えになりうる。実際に引き継ぐと答えた例は、確かめていない（エージェントの判断しだい）。

## 決定

- 後続のタスクか Issue を作る扱いの指摘と、その結果を、タスクの詳細に出す。タスクの状態によらず出す（完了の後も読める）。できなかった指摘があれば、注意の色にする。
- 承認の画面の決定済みの記録は、今のまま（実装の承認待ちの間だけ）。
- 中止したタスクでは、結果の記録がある指摘だけを出す。
- 人が後続に回すと決めた指摘の後続のタスク（作成の記録に、指摘の ID がある）は、既存の PR の引き継ぎの候補にしない。オーケストレーターに、引き継ぐかを決めさせる項目を出さず、答えにあっても読まない。
- 後続のタスクの依頼の文は、変えない（題と依頼は sacty が決めた文だけ。指摘・理由・元の PR は、指示とは分けたデータ）。

いずれも、着手のときに決めたこと（人の確認は、まだ）。

## 理由

- 結果を出す場所をタスクの詳細にしたのは、完了したタスクで人が開くのが、タスクの詳細だからである。承認の画面は、承認待ちでないタスクでは、決めるものが無い。
- 一覧を扱いのある指摘だけにしたのは、タスクの詳細で要るのが、作ったもの・作れなかったものだからである。「この PR で直す」と決めた指摘と、何もしない扱いの指摘は、結果が無い。
- 中止したタスクで、結果の無い指摘を出さないのは、後続のタスクを作らず、途中で止まった Issue の作成も記録しないので、「完了後に作成」「作成中」と出すと、起きないことを予定として見せるためである。
- 引き継ぎの候補から外す判定を、作成の記録で行うのは、依頼の文の中の文字列で判定すると、外から来た文で取り違えうるためである（後続のタスクの照合と同じ）。マージ済み・閉じた PR を一律に候補から外す方法は、オーケストレーターへの指示を作る前に GitHub へ問い合わせることになり、人が作ったタスクの振る舞いも変えるので、採らなかった。
- 依頼から元の PR の URL を除く方法は、エージェントが指摘の出どころを読めなくなるので、採らなかった。

## 影響

- 人が画面から作った続きのタスクと、人が作ったタスクの、PR の引き継ぎは、今までどおり。
- 後続のタスクは、新しいブランチと PR で直す。
- 後続のタスクの再実行も、作成の記録を引き継ぐので、引き継ぎの候補にならない。
