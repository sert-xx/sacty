# 環境が原因のテストの失敗と、作業領域では確かめられない確かめ方を、人の確認として最終承認へ回す

- 日時: 2026-10-24 11:24 UTC
- ステータス: 採用
- 関係する PR・タスク: #215、PBI-155
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty のリポジトリのタスク（質問欄のショートカット）で、最終レビューが3回続けて不合格になり、一時停止した。
3回とも、実装は承認済みの要求要件に沿っているとゴールガーディアンが判定していた。

- テストのコマンドの終了コードが毎回 1 だった。
  失敗したのは、デーモンのプロセスの後始末を確かめるテスト 16 件で、止めたプロセスが消えるのを待って時間切れになっていた。
  エージェントのコンテナは `docker run` に `--init` を付けていなかったので、PID 1 がエージェントの CLI（Node.js）になり、終わった子プロセス（ゾンビ）が回収されなかった。
  ゴールガーディアンは、変更を外した起点の状態でも同じように失敗することを確かめていた。
- 最終レビューは、終了コードが 0 でなければ、観点の判定にかかわらず不合格にしていた（[ゴールガーディアンが最終レビューの中でテストを実行し、sacty はテストのコンテナを使わない](20261021-1431-superseded-guardian-runs-tests.md)）。
  1回目は観点がすべて検証済みだったが、この規則だけで不合格になった。
- 承認済みの要求要件の受け入れの確かめ方に「macOS の標準の日本語入力と Windows の Microsoft IME で確かめる」とあった。
  作業領域（Linux のコンテナ）では確かめられないので、2・3回目はそれを理由に不合格になった。
  実装をやり直しても直らない。

## 決定

- エージェントのコンテナ（工程・ゴールガーディアン）を `docker run --init` で起動する。
  PID 1 の init が、終わった子プロセスを回収する。
- 要求要件の工程の指示で、受け入れの確かめ方を書くときは、次の2つに分けさせる。
  - 自動のテストで確かめること：エージェントが作業領域でテストを実行して確かめる。実機や特定の環境の振る舞いは、合成の入力・イベントで模擬して確かめる形にする。
  - 人が確かめること：作業領域では確かめられないもの（実機・特定の OS・入力方式・外部のサービス・目視など）。最終承認で人が確かめる項目になる。
- 最終レビューで、ゴールガーディアンは次のとおりにする。
  - 承認済みの確かめ方のうち、作業領域では確かめられないものは、それを理由に不合格にしない。確かめられる範囲をテストが検証しているかで判定し、残りを `humanChecks` に書く。テストやコードで確かめられるのに確かめていないことは、`humanChecks` に回さずに不合格の理由にする。
  - テストの失敗がすべて環境によるもの（変更を外した起点の状態でも同じように失敗する、または差分と関係の無い環境の要因で失敗すると確かめられる）なら、失敗したテストごとに名前と根拠を `tests.environmentFailures` に書き、テストの失敗を理由に不合格にしない。1件でも、変更によるもの・環境によると確かめられないものがあれば、空にして、テストが通らなかったものとして判定する。
- sacty は、終了コードが 0、または 0 以外で `environmentFailures` があるときに、テストが通ったものとする（`guardianTestsPassed`）。終了コードの申告が無ければ、これまでどおり不合格にする。終了コードが 0 のときの `environmentFailures` は記録しない。
- `humanChecks` と `environmentFailures` は `FinalReviewed` に記録し、実装の PR の本文に「人が確かめること」のチェックリストとして、タスクの詳細の画面の最終レビューに「人が確かめること」として出す。
  実装のやり直しの指示には、環境による失敗を「実装で直す対象ではない」として渡す。

## 理由

- 環境の問題は、実装をやり直しても直らない。不合格のまま繰り返すと、費用を使って一時停止するだけになる。
  コンテナの側で直せるもの（ゾンビの回収）は直し、直せないもの（実機の確認など）は、人が判断できる形で最終承認に回す。
- 環境が原因かどうかを sacty が自分で（起点のコミットでテストを実行し直して）確かめると、テストの時間が倍になり、サービスの起動などの扱いも増える。
  判断はゴールガーディアンに根拠つきで申告させ、PR の本文と画面に出して、人がマージの前に確かめる。
- 実機の確認を受け入れの確かめ方にそのまま書くと、ゴールガーディアンはそれを満たせない。
  要求要件の段階で、自動のテストで確かめることと人が確かめることを分けておくと、承認する人も、最終承認で何を確かめるかが前もってわかる。

## 影響

- ゴールガーディアンが環境の失敗と誤って申告すると、変更による失敗を見逃して合格にするおそれがある。
  根拠を書かせ、観点に対応するテストが通っていることを確かめさせ、PR の本文のチェックリストで人に確かめてもらうことで抑える。
- 統合レビュー・レビューの工程のテストの扱いは変えない。
- それより前の版の `FinalReviewed` には `humanChecks`・`environmentFailures` が無く、これまでどおりに読む。
