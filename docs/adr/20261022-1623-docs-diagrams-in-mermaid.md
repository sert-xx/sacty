## 背景

仕様書（docs/spec）とユーザードキュメント（docs/user）は文章と表だけで書いていた。
ゲートウェイの中継の経路、コンテキストの層の重なりと継承、タスクの工程の進み方、PR での承認のブランチの関係などは、文章だけでは全体の形がつかみにくい。
図を足すにあたり、図をどの形式で持ち、どう実装と一致させ続けるかを決める必要があった。

## 決定

- 図は、言語の名前を `mermaid` にしたコードブロックで、本文の中に書く。
  画像のファイル（PNG・SVG）や、draw.io などの別のファイルにはしない。
- 文章だけではわかりにくい構成・流れ・状態の移り方・層の重なりにだけ使う。
- 図も本文と同じく実装と一致させ、図にした振る舞いを変える PR で図も直す。
- 色・アイコン・装飾は付けない。
- 英語の版にも同じ図を、同じ行の数で置く。

方針は [docs の入口](../README.md) の「共通の規則」に書き、スキル（`sacty-docs`）にも図を直すことを足した。

## 理由

- Mermaid は GitHub がそのまま描画するので、利用者は追加のツール無しで図を見られる。
- テキストなので、本文と同じ PR で差分としてレビューでき、実装の変更に合わせて直しやすい。
  画像のファイルは、元のデータと画像の両方を直す手間がかかり、ズレに気づきにくい。
- 英語の版の突き合わせ（`tests/docs`）は、コードブロックの数と行の数を比べるので、図を片方の言語だけに足す・直すと検査で気づける。
- 色やアイコンを付けないのは、GitHub のライトとダークの表示のどちらでも読めるようにし、図を情報の形だけに絞るためである。

  図を足す・直すときは、描画して確かめる。
