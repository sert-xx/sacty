# sacty mcp の続きの作成（派生）は、画面の既定値のまま題と内容だけを送り、題の変更は題だけを送る

- 日時: 2026-11-20 09:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-412
- 置き換え元: なし
- 置き換え先: なし

## 背景

`sacty mcp` は、中止したタスクの再実行まで（[再実行の ADR](20261119-1000-superseded-mcp-rerun-minimal-screen-defaults.md)）できる。その ADR は、完了したタスクからの続きの作成（派生）をこの版に入れなかった。機能を1つずつ足す流れとして、派生と題の変更を足す（17個から19個）。
派生（[派生の ADR](20261028-0054-derive-follow-up-task.md)）は、新しいタスクを作って工程を始め（時間と費用がかかる）、何度でも作れる。入力の `repo` は省略できず、`plan` は省略できる。デーモンは、セキュリティの組み合わせのタスクでは、`plan` を省くと `security-fix` で作る。
題の変更（[題の変更の ADR](20261108-1453-rename-task-title.md)）は、中止のほかは状態を問わず通り、すでに作った PR の題とブランチ名は変えない。説明（body）を変える API は無い。

## 決定

- ツール `derive_task`（`task_id`・`title`・`body`）と `rename_task`（`task_id`・`title`）を足す。入力は `z.strictObject`（知らない引数を断る）。デーモンの既存の `POST /api/tasks/:id/derive`・`POST /api/tasks/:id/title` だけを呼ぶ。デーモンのサービス・API の入口・`@sacty/core`・画面は変えない。
- 派生は、作業するリポジトリ・進め方を引数にしない。画面の「続きのタスクを作る」の既定値を送る：`repo` は `source?.repo ?? repo ?? repository?.url`（無ければ `null`）、`plan` は送らない。選びたいときは、画面で行う。
- 派生を、API に送らずに断る（`deriveBlock`。要約の `canDerive`・`get_task` の `deriveBlocked` も同じ関数）：無い（消したプロジェクトのタスクを含む）・中止した・完了していない・セキュリティの組み合わせ（`isSecurityTask`）。題・内容は、core の `DeriveTaskInput` で検査して断る。セキュリティの組み合わせは、進め方がセキュリティ対応に決まり、記録にレポートが入るので、今回は狭い側（断って画面へ）にする。
- `rerunBlock` の完了したタスクの案内は、続きを作れるときは `derive_task`、作れないとき（セキュリティの組み合わせ）は画面にする（`deriveBlock` の結果で切り替える）。中止したタスクの派生の断りは、そのタスクが `rerun_task` で再実行できるときだけ、再実行を案内する。
- 題の変更は、無い・中止した・題が `RenameTaskInput` に通らないものを、送らずに断る。今と同じ題・題の PR のリンクが変わる題は、デーモンの理由を返す。要約に「変えられるか」の欄は足さない。
- 要約に `canDerive`・`derivedFrom`（派生で作ったタスクにだけ。元の ID）・`derivedTasks`（作った元のタスクにだけ）を足す。`get_task` には、完了したタスクで続きを作れないときだけ `deriveBlocked` を足す。
- 結果は、ほかの書き込みのツールと同じ形（短い文・要約）。派生は `derive`（`originalTaskId`・`newTaskId`）、題の変更は `rename`（`from`・`to`）を足す。
- 注釈は、どちらも `readOnlyHint: false`・`destructiveHint: false`・`idempotentHint: false`・`openWorldHint: true`。
- 結果を受け取れなかったとき：派生は、作られている可能性を返し、自動でやり直さず（呼び直すと二重に作られる）、元のタスクの `derivedTasks` に、呼ぶ前に無かった ID が増えたかで確かめる。題の変更は、`get_task` の `title` で確かめる（変わっていなければ、呼び直してよい）。

## 理由

- 画面の既定値のままなら、リポジトリ・進め方という人の判断を MCP から受け取らずに済み、既存の API をそのまま呼べる（再実行と同じ考え方）。
- 派生は何度でも作れるので、再実行と違って、2回目を MCP の層で断って二重を防ぐことができない。結果を受け取れなかったときは、`derivedTasks` の増減で確かめる案内にし、自動の再試行はさせない。
- セキュリティの組み合わせのタスクの続きをデーモンの既定のまま作ると、画面で人が選ぶ進め方を、MCP が黙って決めることになる。先に断り、画面に任せる。
- 題の変更は、状態の条件が「中止していない」だけで、同じ題での2回目は断られるだけなので、呼び直しても害が無い。

## 影響

- 登録した AI は、利用者がはっきり頼んだときに、完了したタスクから続きのタスクを作れる。工程が始まり、時間と費用がかかる。作ったタスクは消せない。呼ぶたびに別のタスクができる。
- 題の変更は、今の実行を止めない。この後に作る PR の題と本文・コミット・通知が新しい題になる（`openWorldHint: true`）。すでに作った PR の題とブランチ名は変わらない。
- リポジトリ・進め方を指定しての派生、セキュリティの組み合わせのタスクからの派生、説明（body）の変更（デーモンに API が無い）は、この版に入れない（利用者の判断待ち）。
- 先読みと送信の間に状態が変わる窓は残る（このときはデーモンが断る。タスクは増えない）。
- 仕様は [MCP サーバー](../spec/mcp-server.md#derive_task)、利用者向けは [手元の AI から操作する](../user/mcp.md#完了したタスクから続きのタスクを作る) に書く。
