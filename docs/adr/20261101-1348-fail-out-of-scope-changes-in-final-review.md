# 最終レビューで、依頼にも承認済みの要求要件・設計にも無い変更と、既存のテストの期待を変える変更を、観点 SCOPE の不合格にする

- 日時: 2026-11-01 13:48 UTC
- ステータス: 採用
- 関係する PR・タスク: #264、PBI-273
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験（S13a）で、ベースブランチを取り込んだ後の実装が、依頼にも承認済みの要求要件・設計にも無い変更を足した。狭い画面向けのカード表示と「一覧を再取得」のボタンで、先にマージした PR のテスト（`rooms.spec.ts` の `scrollWidth > clientWidth`）の期待まで逆にしていた。
ゴールガーディアンは最終レビューでこれに気づいたが、不合格にせず、「人が確かめること」に回しただけだった。人が PR で差し戻して、実装のやり直しだけで直った。

それまでの最終レビューには、範囲外の変更を不合格にする決まりがなかった。
観点はテスト観点（設計）・`REPRO`・`REQ` で、「依頼に無いものを作っていないか」は、要求要件・設計を省いたタスクの `REQ` の説明に書いてあるだけだった。ベースブランチ側の変更や成果物を「範囲・過剰さの判定に含めない」という除外はあったが、含める側の判定の指示は無かった。

## 決定

1. **ゴールガーディアンに、差分の変更ごとに範囲を確かめさせ、範囲外を `outOfScope` に申告させる。**
   - 基準は、最終レビューの指示に載せている承認済みの要求要件・設計（省いたタスクはタスクの内容（依頼）・再現のテスト）と、人間の過去の指摘。
   - 範囲外：どれにも当たらない振る舞いの変更（画面・API・設定・既定値・文言の変更、機能・操作の追加。良い変更に見えても同じ）、既存のテストの期待を弱める・逆にする変更（期待値の変更・検証の削除・テストのスキップや削除）。後者は、要求要件・設計が、そのテストの確かめている振る舞いを変えることを求めているときだけ範囲内。先にベースブランチへマージされたテストも同じ。
   - 範囲内：求められた変更に要る変更（呼び出し元の追従・型・求めた振る舞いのテストの追加や更新・競合の解消）、振る舞いを変えない整形・リファクタリング、リポジトリの決まり（AGENTS.md・CONTRIBUTING・PR テンプレートなど）が、この種の変更に伴って求める変更（README・CHANGELOG・版・ドキュメント・生成物の更新）。決まりは要求要件・設計に書かれないことがあり（S13 では CHANGELOG の版が論点になった）、範囲外にすると、実装が外せず空回りするため。決まりは最終レビューの指示に載せていないので、ゴールガーディアンが作業領域のファイルと既存の変更の慣習を読んで確かめ、確かめられないものは範囲外にせず人の確認に回す。ベースブランチ側の変更と成果物は、これまでどおり判定に含めない。
2. **sacty は、`outOfScope` の申告が1件でもあれば、観点 `SCOPE` を不合格にして判定に足す。** 設計のテスト観点とは別の ID にし、申告が無ければ何も足さない（既存の観点・テストの対応・画面の観点の表は変わらない）。
   - 申告は文字列の一覧（`humanChecks` と同じ読み方）。観点を増やす代わりに申告欄を足すのは、範囲外の変更が設計のどの観点にも属さず、観点ごとの判定では表せないため。
3. **範囲内か判断できないものは、不合格にせず `humanChecks` に回させる。** 依頼や要求要件の解釈が分かれるときは、人の確認に回す、という今までの扱いのとおり。
4. **やり直しの指示に、範囲外の変更だけを起点の状態に戻して外し、ほかは残すことを伝える。** S13a で、1回目の直しが元からあった指定（表の `minWidth`）まで外し、最終レビューがもう1回不合格にした。外すのは挙げられた変更だけ、外した後に差分で確かめる、と書く。
5. **セキュリティ対応には入れない。** 観点 `SEC-MIN`（差分が修正の範囲と照らして最小限か）が、同じことをより厳しく見る。指示にも出力の形にも出さず、申告があっても読まない。
6. **画面には、実装の成果物の最終レビューに「範囲外の変更」として理由を出す。** `SCOPE` は設計の観点の表に無いので、別の欄で出す。

## 理由

- 範囲外の変更は、マージの後で取り除くより、PR の前に実装のやり直しで外すほうが安い（S13a では、実装 $0.48＋$0.46 のやり直し）。人の差し戻しを待つ必要もない。
- 不合格の基準を「承認済みの成果物にあるか」にしたのは、人が承認した範囲を守るのがゴールガーディアンの役割で、基準が人の承認に結びつくため。良い変更かどうかは基準にしない（別のタスクとして頼む）。
- 既存のテストの期待を変える変更は、範囲外の中でも特に害が大きい（先にマージされた別のタスクの振る舞いを黙って変える）ので、名指しで書く。要求要件・設計が変えるよう求めているときは、範囲内にする。
- 判断が分かれるものを不合格にすると、実装が直せない不合格を繰り返す（空回り）。そこで、不合格にするのは「どれにも根拠が無いと言える」変更だけにし、根拠を書けないものは申告させない。解釈が分かれるものは人の確認に回す。
- 空回りの歯止めは、既存の `MAX_VERIFY_ATTEMPTS`（3回）。続けて通らなければ一時停止し、範囲内だと判断する人は「レビューへ進める」で進められる。ゴールガーディアンは、前回の判定を渡されない新しいセッションで判定する（既存の決まり。実装の説明も、テストの仕組みが無いタスクにしか渡さない）ので、実装が「外せない」と説明しても判定に届くとは限らない。ここは、人が一時停止で判断する。
- 比べたほかの案（採らなかった）：
  - 設計のテスト観点（`REQ` など）の理由に書かせて、その観点を不合格にする案：範囲外の変更はどの観点にも属さず、不合格にする観点を選べない。設計の観点が複数あると、どれを落とすかも決まらない。
  - すべてのタスクに常設の観点 `SCOPE` を足して毎回判定させる案：全タスクの出力の形・テストの対応・画面の観点の表が変わり、判定の無い観点は不合格になるため、既存のタスクの動作を壊しうる。申告があったときだけ足す形にした。
  - sacty が差分を機械的に範囲と照らす案：セキュリティ対応のように範囲を宣言する工程が無く、要求要件・設計は文章なので、機械的には判定できない。

## 影響

- 要求要件・設計・依頼に無い変更があると、最終レビューが不合格になり、実装をやり直す。人が PR で気づいて差し戻す手間は減る。
- 判定は LLM で行うので、指示のとおりに範囲外を見つけて申告するか、範囲内を誤って範囲外とするかは、指示の文言に依存する。申告の読み方・観点の足し方・やり直しの指示・指示の文言は、テストで確かめた（判定自体はテストで確かめられない）。
- 誤って範囲内の変更を範囲外とすると、実装が外せず、3回の不合格で一時停止する。人が「レビューへ進める」で進められる。
- 範囲内か判断できない変更は「人が確かめること」に残る。
