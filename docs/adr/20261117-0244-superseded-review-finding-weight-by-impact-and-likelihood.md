# レビューの指摘の重みを、影響の大きさと起きやすさで決め、自己レビューは要修正だけを修正に戻す

- 日時: 2026-11-17 02:44 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: PBI-358
- 置き換え元: なし
- 置き換え先: [再レビューの要修正を絞る](20261123-2239-rereview-findings.md)（再レビューの重さと条件の数え方・同じ原因の判断の一部）

## 背景

既定のレビュー用スキルの重要度は、`must`（不具合・セキュリティ・データ破損・要件の不適合・互換性の破壊）、`should`、`nit` の 3 つで、起きやすさを見る決まりが無かった。
起こりうる不具合は、稀な条件が重なったときだけ起きるものでも `must` になり、PR のレビューは `must` が 1 件でもあれば「修正が必要」になる。

このため、PR のレビューと実装の往復が長く続くことが、繰り返し起きた。

- ある PR では、レビューが 13 回続いた。要修正は約 22 件で、誤った指摘は見当たらなかったが、そのうち約 7 件は、稀な条件が重なったときだけ起きて実害の小さいもの、約 7 件は、指摘への直しのために足した仕組みの穴だった。
- 別の PR では、同じ題材の要修正が 4 回続き、変更が約 2 倍に増えた。
- 2026-11-17 の 1 日でも、3 つの PR で同じ形（直しのために足した仕組みの、稀な条件での穴への要修正）が出て、うち 2 つは、仕組みそのものを PR から外した。

自己レビュー（工程の中のレビュー）も、`should` だけで修正に戻していた。

## 決定

リポジトリの持ち主が、2026-11-17 に次の基準を決めた。

- 重要度は、起きたときの影響の大きさ（大・中・小）と、起きやすさ（普通・条件つき・稀）の表で決める。
  - 影響：大（データの破損・消失、セキュリティ、取り消せない外部への作用、互換性の破壊）は、起きやすさを問わず `must`。
  - 影響：中（機能の一部が動かない、ほかの処理を止める、誤った結果を見せる）は、稀なら `should`、それ以外は `must`。
  - 影響：小（手で直せる、表示や通知の過不足、分かりにくさ）は `should`、稀なら出さない。
  - 稀は、独立した条件が 2 つ以上重なったときだけ起きること。条件つきは、1 つの条件で起きること。
  - 受け入れ条件・要求要件の不適合は、起きやすさを問わず `must`。
- 担当は、指摘ごとに、起きる条件（何と何が重なると起きるか）と、起きたときの実害を書く。
- 再レビューと、前回の指摘への直しで足した・変えた箇所への指摘にも、同じ表を当てる。
- 自己レビューは、`must` だけを修正に戻す。`should`・`nit` だけでは戻さない。
- PR のレビューの判定の決まり（`must` が 1 件以上なら「修正が必要」）は変えない。重みの基準が変わることで、判定が変わる。

実装で決めたこと（持ち主の確認は、この ADR を書いた時点ではまだ）。

- 条件の数え方：障害・珍しい入力や量・処理の重なり・珍しい操作を数える。ふつうの使い方で満たされる前提と、外部の者が意図して揃えられる条件は数えない。1 つの原因が続けて引き起こすことは、まとめて 1 つに数える。
- 不適合の範囲：根拠（受け入れ条件・要求要件・設計）が述べる場面そのもので、求められた振る舞いにならないことに限る。根拠に書かれていない条件がさらに重なったときだけ起きるものは、表で決める。
- 親（集約）は、担当の重要度を、書かれた条件と実害から同じ表で確かめ、合わなければ決め直して記録に残す。親は、条件や実害を足さないが、書かれた条件に数え方の規則を当てはめて数え直すことはしてよい。
- 担当は、「影響：小 × 稀」として出さなかったものを、見出し・条件・実害とともに `not_raised` に残す。親は、それも同じ表で確かめ、出さないままのものを不採用の記録に残す。
- `pr-review` の再レビューで、前回 `must` として出した指摘が、表では `should` に当たると分かったときは、未対応でも `must` に数えない。
- 自己レビューで、`must` が無い回は、`should`・`nit` を直さずに提出へ進む。ただし、`design-doc` の記述を削る `should`（書きすぎの指摘）など、工程の指示が直すと決めているものは、これまでどおり直す。
- `nit` は、実害の無いもの（表記・命名・好み）に使う。観点の資料の NG 例に付いた重要度は書き換えず、「ふつうの使い方か 1 つの条件で起きるときの目安で、稀なときは表で決め直す」と、担当のスキルに書く。

## 理由

- 往復が続いた PR の指摘は、誤りではなかった。足りなかったのは、「正しいが、いま直すほどではない」を分ける基準だった。影響と起きやすさを分けて書かせると、重さの根拠を、作者も人も読める。
- 影響：大を起きやすさで下げないのは、データの破損や秘密の値の漏れは、稀でも取り返しがつかないため。
- 外部の者が意図して揃えられる条件を数えないのは、攻撃として起こせるものを「稀」に逃がさないため。
- 不適合の範囲を限ったのは、実物で確かめたときに、担当が「稀・影響は中」と書いた指摘を、「仕様に書かれた振る舞いを満たさない」ことを理由に `must` にしたため（仕様が述べる場面に、仕様に無い条件がもう 1 つ重なったときだけ起きる穴だった）。限らないと、仕様に書かれた仕組みの稀な穴が、すべて不適合として `must` に残る。
- 親に確かめさせるのは、担当が条件と実害を書いた上で、表と違う重要度を付けることがあるため（同じ実物）。
- 自己レビューで `must` が無い回に `should` を直させないのは、直すと、レビューで見ていない変更が提出に入るため。
- `design-doc` の記述を削る `should` を残したのは、書きすぎは、読む人が読み切れずに承認する原因で、以前の決定（[人間が読む成果物の初版を最小限にし、詳しさは人間の差し戻しで足す](20261025-0222-superseded-minimal-first-drafts.md)。一部が後の ADR で置き換えられている）が、この指摘を直させているため。持ち主の決定がこの例外に及ぶかは、確かめていない。
- 比べた案と、採らなかった理由。
  - 往復の回数に上限を設ける：決まっていない（この決定の範囲外）。
  - 観点の資料の NG 例の重要度を、1 件ずつ書き換える：例は、ふつうの使い方か 1 つの条件で起きる場面で書かれていて、表と食い違わない。書き換える量が多く、観点の中身に手を入れることになる。

## 影響

- 稀な条件が重なったときだけ起きる、影響が中以下の指摘は、PR のレビューで `[提案]` になり、判定は「提案あり（マージは可）」になる。直すか、後に回すかは、指摘を受けた側と人が決める（その申告と、人の決定の画面は、別の変更で扱う）。
- 稀で実害の小さい指摘は、PR には出なくなる。見落としても困らないものに限るが、条件の数え方を誤ると、出すべき指摘が出なくなる。出さなかったものも、条件と実害が担当の結果（`not_raised`）と親の記録（不採用）に残るので、親が数え直し、人が後から確かめられる。
- 置き換え元は「なし」にした。自己レビューで `should` も直すことを決めた ADR は見つからなかった（スキルの最初の版からの決まりだった）。次の 2 件は、それを前提として述べているが、決定そのものは変わらないので、置き換え済みにしない。
  - [既定のレビューに、要らないコードを探す観点と、画面を撮って UX を見る観点を足す](20261026-1014-review-code-conciseness-and-ux.md)：影響の節の「自己レビューでは `should` も直すので、C-15 の指摘で要らないコードが消えていく」は、成り立たなくなる。C-15 の `should` は、`must` を直す回に作者の判断で直すか、PR のレビューで `[提案]` として出る。
  - [文章の種類を読む人が前提を知っているかで分け、後から読まれる文書の組み立て方と図・画像の決まりを writing に足し、文書作成の工程でもセルフレビューをさせる](20261115-0017-writing-kinds-figures-and-document-self-review.md)：理由の節の「セルフレビューは `must` と `should` を直す」は、`must` を直す、に変わる。範囲を絞る決定は、そのまま効く。
- 担当の出力に、`condition`・`impact`・`likelihood`・`impact_level` が増える。親の記録に、`reweighted` が増える。
- 自己レビューの回数が減る（`should` だけの回で終わる）。
