## 背景

それまでの工程の組み合わせでは、1つのタスクを1つの流れ（1つの PR）で進めるしかなく、大きなタスクを分けて進める手段が無かった。
分けるなら、分割案を誰が認めるか、子タスクの工程・成果・依存・予算・中止をどう扱うかを決める必要があった。

## 決定

- 工程 `split` と、工程の組み合わせ「要求要件 → 設計 → タスク分割」を足す。オーケストレーターが選ぶ。分割は設計の承認の後だけ。
- タスク分割のエージェントが、承認済みの要求要件・設計とコード（読み取り専用）から、子タスクの一覧（内容・受け入れ条件・依存）を書く。
  子が2〜10件でない・key の重複・存在しない依存・循環のときは、理由を記録して止める（再開で分割し直す）。
- 分割案は人間が承認しない。分割案と理由を作業履歴に残し、そのまま子タスクを作る。子タスクの内容には、親の承認済みの要求要件と設計を添える。
- 子タスクの成果は子ごとの PR。子タスクの工程は子ごとにオーケストレーターが選ぶ。分割は1段だけ（子タスクは分割を選べない）。
- 依存する子は、依存先の PR がマージ（完了）されてから始める。子タスクは依存の順に1件ずつ実行する。子がすべて片付いたら親を完了にする。
- 子タスクはそれぞれ予算の上限を持ち、親には子の費用の合計を出す。
- 子が中止されたら、親は人間の判断を待つ（再開で中止を認め、依存する子も始める）。親を中止すると、終わっていない子も中止する。
  親の中止の途中でデーモンが止まっても、再起動の後にワーカーが、中止された親を持つ子を実行せずに中止する。
- 作業履歴に `TaskSplit`・`TaskUnblocked`・`SplitCompleted`、`TaskCreated.parent`、一時停止の理由 `child_cancelled` を、
  状態に `blocked`（依存待ち）・`waiting_children`（子タスクの完了待ち）を足す。

## 理由

- 子タスクを1件ずつ実行するのは、そのときのワーカーが1件ずつ処理するため（並行は別の PBI にした）（PR の本文）。
- 再起動の後に子を中止する経路を足したのは、親の中止を記録してから子を中止し終えるまでの間にデーモンが止まると、再起動の後に
  中止されていない子が実行され、人間が親を中止した後も費用を使い続けるうえ、親をもう一度中止しても伝播をやり直せなかったため（レビュー）。
- 分割案を承認しないこと・分割を1段に限ること・子ごとに PR にすることの理由は記録に無い。

## 影響

- 子タスクを持つ親は、子の完了を待つ状態になり、一時停止できない。
- 画面では、親に子タスクの一覧（状態・依存・PR）・進み具合・費用の合計、子に親へのリンクを出し、一覧では子を親の下に字下げする。
- 分割案が不正なら止まるので、再開で分割し直す必要がある。
