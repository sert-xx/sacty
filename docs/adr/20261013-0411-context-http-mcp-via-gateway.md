# コンテキストリポジトリの HTTP の MCP サーバーは、既定でゲートウェイ経由にし、認証のヘッダーはホストで付ける

- 日時: 2026-10-13 04:11 UTC
- ステータス: 採用
- 関係する PR・タスク: #57、PBI-49
- 置き換え元: なし
- 置き換え先: なし

## 背景

コンテキストリポジトリの `mcp.yaml` に書いた HTTP の MCP サーバーには、コンテナから直接つないでいた。認証のヘッダーに秘密情報を使うと、その値がコンテナに入る。
ホストで動かす MCP サーバー（PBI-36）は、すでに実行ごとのゲートウェイのトークンで使わせていた。

## 決定

- `mcp.yaml` の HTTP のサーバーは、既定で sacty のゲートウェイ経由にする。エージェントの設定（Claude Code の mcp.json・Codex の config.toml）では、
  ゲートウェイの URL（`http://host.docker.internal:<port>/ctx-mcp/<名前>`）と、実行ごとのゲートウェイのトークンだけを渡す（ホストの MCP サーバーと同じ仕組み）。
- 元の URL と認証のヘッダー（秘密情報はホストで取り出す）は、実行の登録と一緒にゲートウェイだけに持たせる。実行が終わると、そのトークンでは使えない。
- ゲートウェイは、MCP の Streamable HTTP に要るヘッダー（`content-type`・`accept`・`mcp-session-id`・`mcp-protocol-version`・`last-event-id`）だけを上流に送り、
  認証のヘッダーはホストに持った値を付ける。エージェントが付けた認証・クッキーなどは送らない。応答（SSE を含む）はそのまま返し、リダイレクトはたどらない。
- サーバーに `via_gateway: false` と書くと、これまでどおりコンテナから直接つなぐ。`command` のサーバーは、これまでどおりコンテナの中で起動する。

## 理由

- 認証のヘッダーの秘密情報を、ホストで付けてコンテナに渡さないため（PR の本文）。
- リダイレクトをたどらないのは、認証のヘッダーをほかの宛先に送らないため（PR の本文）。
- ヘッダーを決まったものだけにした理由は、記録に無い。

## 影響

- コンテナには、HTTP の MCP サーバーの元の URL と認証の値が入らない。
- 直接つなぐ必要のあるサーバーは、`via_gateway: false` を書く。
- Rancher Desktop などでは、ゲートウェイに届く `gateway.host_address` の設定が要る。
