# 人の差し戻しの回数の上限を無くす

## 背景

同じ工程への人の差し戻しが 3 回に達すると、次の差し戻しはエスカレーション（`too_many_changes`）になり、人が承認するか「上限を超えて差し戻す」かを選ぶまで止まっていた。
PR のコメントから取り込んだ差し戻しも数えるので、PR でやり取りを続けるだけで上限に達し、そのあとは取り込みのたびに止まった。
そのほかにも害があった。

- 一時停止から再開したときの扱いが経路で違った。作り直しの途中で止めたタスクは上限で止めず、承認待ちで止めたタスクは上限で止まり、案内と食い違った。
- エスカレーションの画面は、複数行の残った指摘を行ごとに割り、指摘の出どころ（`source`）と元の PR のコメント（`origin`）を失い、PR への返信も無くなった。
- 取り込んだ指摘の 2,000 文字の検査を外した後（PBI-413）は、残った指摘を書き直して送ると 2,000 文字で断られた。

## 決定

- 同じ工程への人の差し戻しの回数に、上限を置かない。画面・PR の指摘の取り込み・一時停止からの再開・「この PR で直す」・`sacty mcp` の `request_changes` のどの経路でも、何回目でも `ChangesRequested` を記録してやり直す。新しく記録する `overLimit` は常に偽にする。
- 上限で止まったタスク（以前の版の記録）は、残った指摘を元の形のまま渡し、人の補足を別の欄で足して進められるようにする。
  - 差し戻しの指摘は、残った指摘を元の順に並べ、その後ろに人の補足を並べる。補足は 1 行を 1 件とする。
  - 残った指摘を引き継ぐのは、エスカレーションした工程へ差し戻すとき。`rework_confirmation` は戻し先を問わず引き継ぐ（今の決まりのまま）。`too_many_changes` で別の工程へ差し戻すときは、補足だけで差し戻す。
  - 1 件 2,000 文字・50 件の検査は、人の補足だけに当てる。残った指摘は長さでも件数でも断らない。
  - 以前の版の画面・呼び出しが送る「上限を超えて差し戻す」の指定は、断らずに無視する。
  - 残った指摘も補足も無ければ、今の断り（`gate.remarksRequired`）で断る。
- 以前の版の作業履歴（`overLimit: true` の `ChangesRequested`・`too_many_changes` の `TaskEscalated`）は、誤りなく読み込み、画面・作業履歴の表示・`get_task` で以前の版の記録と分かる文で出す。
- 変えないもの：AI のレビューの指摘だけの差し戻しを人の回数に数えない扱い、予算の上限、AI の自動のやり直し、指摘の 50 件と 1 件 2,000 文字（人が書く指摘）、`change_proposed` のエスカレーション。
- 差し戻しの回数の表示は足さない。

## 理由

- 上限は、差し戻しが続く理由（外部のコメントが続く・指摘が的外れで直らない）を区別せず、人の判断を求める回数だけで止めていた。止まった後に人ができるのは承認か差し戻しの続行だけで、止まること自体は判断の助けにならなかった。
- 上限を 3 回にした理由は、元の ADR に記録が無い。
- 外部のコメントが続くことによる費用は、予算の上限（タスクの費用）が受ける。差し戻しの回数では止めない。（予算の上限が、外部のコメントによる連続したやり直しを実際に止めるかは、このタスクでは確かめていない。）
- 残った指摘を書き直しの欄に入れる作り（以前の版）は、行ごとの分割と 2,000 文字の検査を招いた。元の形のまま渡し、補足を別に足せば、どちらも起きない。
- 検討して採らなかった案：上限の数を増やす（止まる場所が変わるだけで、害は残る）。上限を設定にする（上限が要らない害は消えない）。

## 影響

- 差し戻しの上限でエスカレーションになるタスクは、新しく生まれない。以前の版で止まったタスクは、画面で残った指摘と補足の欄を見て進められる。
- 古い版のデーモンへ切り戻すと、上限で再び止まることがある。
- 画面を配る前から開いていた画面で差し戻すと、残った指摘が補足の欄に入ったまま届き、同じ文が二重になることがある。配布をまたいだ操作だけで起きる。
