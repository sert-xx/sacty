# docker compose のサービスは sacty がホストで実行ごとに起動し、エージェントとテストのコンテナをそのネットワークにつなぐ

## 背景

docker compose で DB やモック API を起動してから確認・テストするリポジトリがある。エージェントとテストは、権限を落としたコンテナで動いていて、Docker を使えない。

## 決定

- エージェントには Docker の権限を渡さない。sacty（ホスト）がサービスを起動し、エージェントとテストのコンテナをそのネットワークにつなぐ。
- オーケストレーターが工程を選ぶときに、compose ファイル・起動するサービス・サービスを使う工程（実装・再現・不具合の調査）を決める（`StepsChosen` の `services`）。
  内容の調査と、オーケストレーター・ゴールガーディアンでは起動しない。
- 工程のエージェントの実行と、テストの実行の1回ごとに、`docker compose -p sacty-svc-<実行の ID> up -d --wait` で起動し、終わったら `down -v --remove-orphans` で消す。
  デーモンが途中で終わって残ったサービスは、次の起動のときに消す。
- 起動するときに、`ports`（ホストのポート）・`container_name`・ネットワークとボリュームの固定の名前を外す。
- サービスのイメージは、compose ファイルに書かれた名前のまま、ホストの Docker で取得・ビルドする。
- エージェントのプロンプトに、サービスの接続先（例 `db:5432`）と、docker のコマンドは使えないこと・実行の後にデータが消えることを書く。
- 起動できなければ、工程は実行せずに止め（`AgentRunFailed`）、テストは実行せずに止める。作業履歴に「サービスを起動」を残す。

## 理由

- 実行ごとに別のプロジェクト名にするのは、同じリポジトリのタスクを並行で動かしてもぶつからないようにするため（PR の本文）。
- ポート・固定の名前を外すのは、ほかのタスクとぶつからないようにするため（PR の本文）。
- エージェントに Docker の権限を渡さない理由は、PR の本文には書かれていない。レビューでは、信用できないリポジトリのサービスがホストの Docker を操作できることを危険として扱っている（レビュー）。

## 影響

- サービスは実行のたびに作り直され、データは残らない。
- サービスの接続先は、サービス名とコンテナのポート（例 `db:5432`）になる。ホストのポートには出ない。
- サービスのイメージの取得には、ホストの Docker の認証（`docker login`）を使う。
