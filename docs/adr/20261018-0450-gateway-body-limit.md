# ゲートウェイが受け取る本文に上限を設ける

- 日時: 2026-10-18 04:50 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-132
- 置き換え元: なし
- 置き換え先: なし

## 背景

ゲートウェイは、コンテナからの要求の本文を、上流へ送る前に上限なしにホストのメモリーへためていた（AI・組織内 PF・コンテキストの MCP・
ホストの MCP の中継で共通）。実行のトークンを持つコンテナが大きな本文を送り続けると、デーモンのメモリーが尽きて、他のタスクも止まる
（Codex Security の指摘）。

## 決定

- 1 つの要求の本文は 64 MiB まで（超えたら 413）。`Content-Length` が上限を超えていれば読む前に断り、無くても受け取った量で止める。
- 同時に受け取っている本文の合計は 256 MiB まで（超えたら 503、`Retry-After: 1`）。ためた分は、応答を返し終えるまで数える（上流へ送って
  いる間も、ホストのメモリーにあるため）。
- 受け取った分は 16 KiB のブロックに写して持ち、合計には確保したブロックの大きさで数える（届いた chunk をそのまま持つと、1 バイトの
  chunk ごとに Buffer と配列の要素が残り、数えた量よりずっと多くのメモリーを使う。PR #144 レビュー指摘）。
- 断るときは、理由を返してから接続を切る（残りの本文を受け取らない）。
- 値は固定にし、設定では変えない。

## 検討した案

- **上限を設定で変えられるようにする**：AI の API の要求の上限（数十 MB）より大きければ足り、利用者が調整する理由が見当たらない。
  必要になったら足す。
- **ためずに流して転送する**：AI の中継は、失敗したときに同じ本文で送り直す（リトライ）ので、本文を持っておく必要がある。
- **実行ごとに合計を分ける**：1 つのコンテナが複数の要求を同時に送れば、実行ごとの上限でも全体を圧迫できる。デーモンのメモリーを守るには
  全体の合計で抑えるほうが確実である。

## 結果

- 1 つの工程のコンテナが、デーモンのメモリーを使い尽くして他のタスクを止めることはできない。
- 64 MiB を超える要求は、AI の API に届く前にゲートウェイで断られる（AI の API の上限より大きいので、普通の要求は妨げない）。
- 確認の中で、curl などが大きな本文に付ける `Expect: 100-continue` を上流への fetch に写して、必ず失敗していた（502）ことが分かったので、
  上流に送らないヘッダーに足した。
