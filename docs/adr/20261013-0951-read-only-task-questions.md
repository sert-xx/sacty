# タスクの詳細から、オーケストレーターにタスクの状況を読み取り専用で質問でき、質問と答えは作業履歴のイベントで残す

- 日時: 2026-10-13 09:51 UTC
- ステータス: 採用
- 関係する PR・タスク: #63、PBI-54
- 置き換え元: なし
- 置き換え先: なし

## 背景

人がタスクの状況（何が承認され、何が指摘され、いくらかかったか）を知るには、作業履歴や成果を自分で読むしかなかった。
構想ドキュメントの「人間からの質問」にあるように、オーケストレーターに質問できるようにしたい。質問が作業の計画や状態に
影響しないこと、費用と予算の扱いを決める必要があった。

## 決定

- タスクの詳細から質問できる。オーケストレーターが、タスクの台帳（作業履歴・承認済みの成果物・工程の出力・判定・指摘・費用・
  直近の質問と答え）と、用意済みのタスクなら対象リポジトリの起点のコードの使い捨ての写しを、読み取り専用で読んで答える。計画は変えない。
- 質問と答えは、イベント `QuestionAsked`（人）と `QuestionAnswered`（答え・答えられなかった理由・費用）で残す。タスクの状態・工程・
  承認済みの内容には触れない。答え待ちの質問は 1 件まで。
- 答えは工程の実行とは別に動かす。作業中のタスクでも質問でき、作業を止めない。作業中の実行には話しかけない。一時停止では止めず、
  中止では止めて中断を記録する。デーモンの起動時に答えの無い質問は中断として記録する。答えを記録できないときは、費用を引き継いで
  答えられなかったこととして記録する（次の質問を塞がない）。
- 答えの費用はタスクの費用に入れ、工程ごとの費用の表に「質問への答え（オーケストレーター）」の行を出す。予算の上限に達したタスク
  （ちょうども含む）・中止したタスク・答え待ちの間は質問できず、理由を出す。予算は質問を受け付ける前に判定する。
- 答えは秘密情報を伏せてから切り詰める。作業履歴の行には質問・答えの本文を出さない。指示はコマンドの引数の上限に収まるよう
  4 万字に収める（作業履歴は新しいものから）。
- API は `POST /api/tasks/:id/questions`。

## 理由

- 読み取り専用で計画を変えないのは、構想ドキュメントの「人間からの質問」のとおりにするため（PR の本文）。
- 指示の長さを収めるのは、コマンドの引数の上限を超えないため（PR の本文）。
- 答えを記録できなかったときの代わりの記録に費用を引き継ぐのは、レビューで、費用が 0 になりタスクの予算と費用の表が過少になることが
  わかったため（レビューとその返信）。
- 予算を受け付ける前に判定する（1 回の答えで上限を超えうる）のは、工程と同じ考え方にしたため（PR の本文）。
- 答えを工程と別に動かす・答え待ちを 1 件までにする理由と、比べたほかの案は記録に無い。

## 影響

- 質問は台帳に残り、開き直しても読める。答えの費用がタスクの予算を使う。
- 1 回の答えで予算の上限を超えることがある（超えたら、次の工程の実行の前に予算で止まる）。
- 人が質問の本文に書いた秘密情報は伏せない（伏せられるのは、実行に渡した秘密情報だけ）。
