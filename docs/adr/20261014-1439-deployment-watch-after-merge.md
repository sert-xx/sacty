# sacty のタスクの実装の PR がマージされたら、CI/CD とデプロイ後のアプリを見届け、失敗したら修正のタスクを登録する

- 日時: 2026-10-14 14:39 UTC
- ステータス: 採用
- 関係する PR・タスク: #97、PBI-89
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty のタスクは、実装の PR（成果物チェック）のマージで完了していた。マージでできたベースブランチのコミットに対する CI/CD が
通ったか、デプロイされたアプリが動いているかは、人が見に行くしかなかった。失敗していたら、修正のタスクを自動で登録したい。

決める必要があったこと：

- どのマージを見るか、何を CI/CD とみなし、何を失敗とみなすか、CI/CD が無いときと終わらないときにどうするか。
- デプロイの確認を、どの仕組みで・どのエージェントで行い、その費用と予算をどう扱うか。
- 修正のタスクの二重の登録と、修正のタスクのマージでまた失敗したときの、際限の無い登録の連鎖をどう止めるか。
- デーモンを再起動したときに、監視がどうなるか。
- プロジェクトごとに使うかを選べるか、既定をどうするか。

## 決定

### 対象と既定

- プロジェクトの設定 `deploymentWatch`（真偽値）が `true` のプロジェクトだけで行う。書いていない・`false` なら行わない
  （記録も増えない）。既定は Off。
- 見るのは、sacty のタスクの実装の PR（成果物チェック、工程 `pr`）のマージだけ。要求要件・設計の PR（タスクブランチへの PR）は
  見ない。マージを記録するとき（`PullRequestMerged`・`StepApproved` と同じ追記）に、監視を始めた記録（`DeploymentWatchStarted`）を
  入れる。見るコミットは GitHub が返すマージのコミット（`merge_commit_sha`）。取れなければ監視を飛ばす（理由 `no_commit`）。
- 修正のタスクも、ふつうのタスクとして実装の PR を作るので、そのマージで同じく監視する。

### 状態

監視の状態は、`waiting`（待っている）・`passed`（通った）・`failed`（失敗）・`skipped`（飛ばした）・`timed_out`（時間切れ）の5つ。
`waiting` には、CI/CD を待っている（`ci`）か、デプロイの確認を待っている・している（`check`）かの段階を持つ。

### CI/CD の監視

- PR の確認（60秒ごと）のときに、マージのコミットの GitHub Actions のワークフローの実行（`/actions/runs?head_sha=`）・
  チェック（`/commits/<sha>/check-runs`。GitHub Actions のジョブはワークフローの実行で見るので除く）・
  コミットの状態（`/commits/<sha>/status`）を読む。
- どれも無いまま、監視を始めてから 5 分（`DEPLOYMENT_CI_GRACE_MS`）たったら、CI/CD が無いとして飛ばす（理由 `no_ci`）。
  ワークフローの作成には少し時間がかかるので、すぐには決めない。
- すべて終わっても、次の確認（60秒後）で同じ並びになるまで決めない（CI の後に `workflow_run` などで現れるデプロイのワークフローを
  見落とさないため）。
- 1つでも終わっていなければ待つ。監視を始めてから 60 分（`DEPLOYMENT_CI_TIMEOUT_MS`）たっても終わらなければ時間切れ。
  時間は監視を始めた記録の時刻から数える（デーモンを再起動しても延びない）。
- すべて終わったら判定する。失敗とみなすのは、結論が `failure`・`timed_out`・`action_required`・`startup_failure` のもの
  （コミットの状態は `failure`・`error`）。`cancelled`・`skipped`・`neutral`・`stale` は失敗とみなさない（同時実行の取り消しで
  新しいコミットに譲ったものなどで、修正のタスクを作らないため）。
- 失敗したら、失敗したワークフロー・ジョブ（5件まで）ごとに、ジョブのログの末尾（80行まで）を取り、秘密情報を伏せてから、
  1件 3000 文字に切り詰める。伏せるのは、使った GitHub のトークンと、よくある秘密情報の形（GitHub・Slack・AWS のトークン、
  秘密鍵、`Authorization` の値、`password=` などの値）。

### デプロイの確認

- CI/CD が通ったら、マージのコミットに、デプロイの確認のスキル `deployment-observer` があるかを見る。原本は
  `.agents/skills/deployment-observer/SKILL.md`、`.claude/skills/deployment-observer` は原本へのシンボリックリンクの想定。
  先に `.agents` を、無ければ `.claude` を見て、どちらかが使えれば使う。途中のシンボリックリンクは、リポジトリの中を指すものだけ
  たどる（リポジトリの外を指す・たどりすぎるものは使わない）。無ければ、デプロイの確認を飛ばして、監視は `passed` で終える
  （スキルを作るタスクは作らない）。
- スキルがあれば、ワーカーが、エージェント（`step_agents.deployment`、無ければ `default_agent`）を、マージのコミットのコードの
  使い捨ての写しと、プロジェクトのコンテキスト（外部 PF・MCP サーバー）を渡して実行し、スキルに従ってデプロイの完了と
  デプロイ後のアプリの状態を確かめさせる。何を「デプロイの完了」とみなすかはスキルに任せる。答えは見出し `sacty-deployment` の
  JSON（`result`：`healthy`｜`unhealthy`｜`unknown`、`summary`、`evidence`）。
- `healthy` なら `passed`、`unhealthy` なら `failed`（修正のタスクを登録する）。確かめられなかった（`unknown`・実行の失敗・答えを
  読めない・中断）なら `skipped`（理由つき）で、修正のタスクは作らない。

### 費用と予算

- デプロイの確認の費用は、元のタスクの予算に入れる（`DeploymentChecked` は費用を持つイベント）。CI/CD の監視は AI を使わない。
- 確認の前に予算の上限に達していたら、確認を実行せずに飛ばす（理由 `budget`）。完了したタスクなので、一時停止にはしない
  （再開する工程が無い）。80% の通知は、ほかの実行と同じく記録する。

### 修正のタスク

- 失敗したら、元のタスクに登録の記録（`DeploymentFixRegistered`。作るタスクの ID・題・本文を持つ）を書いてから、
  修正のタスク（`start: deployment`、`fix` に元のタスク・種類・目印・段数）を作る。作る前にデーモンが止まっても、次の確認で
  記録から作り直す。
- 本文には、元のタスク・PR・コミット・失敗したワークフロー・ジョブ・実行へのリンクと、ログの抜粋（伏せた後）を入れる
  （デプロイの確認なら、結果の要点と根拠）。元のタスクの画面に修正のタスクを、修正のタスクの画面に元のタスクを出す。
- 二重の登録を防ぐ：同じプロジェクトに、同じ目印（CI/CD は、リポジトリと失敗したワークフロー・ジョブの名前の組。デプロイは
  リポジトリ）の修正のタスクがまだ終わっていない（中止していない、かつ、完了していないか、完了してもその監視を待っている）なら、
  新しく作らず、そのタスクを記録する（`DeploymentFixSuppressed`、理由 `duplicate`）。
- 連鎖の上限：元のタスクの段数を 0、修正のタスクの段数を、それを作ったタスクの段数 + 1 とし、段数が 3（`MAX_FIX_CHAIN`）を
  超える修正のタスクは作らない（`DeploymentFixSuppressed`、理由 `chain_limit`）。1つの監視で作る修正のタスクは1つまで。
  修正のタスクは人の承認（PR のマージ）を経るので、人が止めない限り、マージのたびに最大1つ、連鎖は3段で止まる。

### 再起動

- CI/CD を待っている監視は、再起動の後もそのまま続く（時間の上限は監視を始めた時刻から）。
- デプロイの確認の実行中に止まったら、起動のときに確かめられなかった（中断）として記録し、`skipped` にする（やり直さない。
  中断を繰り返してエージェントの費用を使い続けないため）。まだ始めていない確認は、起動の後にワーカーが実行する。
- 修正のタスクの登録の途中で止まったら、次の確認で作り直す。

### 中止

- 元のタスクを中止したら、監視は終わる（その後は記録しない）。確認の実行中なら、ほかの実行と同じく止める。

## 理由

- 既定を Off にしたのは、受け入れ条件の「設定していないプロジェクトの動作は変わらない」を、既存のプロジェクトでもそのまま守るため。
  新しいプロジェクトだけ On にする案は、エクスポート・インポートで既定がずれるので採らなかった。
- 監視の開始をマージの記録と同じ追記にしたのは、後から「完了したタスクを探して見る」方式だと、この版にする前に完了した
  タスクまで見始めてしまうため。
- CI/CD の状態の途中経過は作業履歴に書かない（60秒ごとに書くと作業履歴が膨らむ）。結果だけを書く。
- 失敗の判定から `cancelled` を外したのは、`concurrency` の `cancel-in-progress` で取り消されたデプロイのワークフローに、
  修正のタスクを作らないため。そのぶん、本当に取り消されて動いていないことは見逃す（デプロイの確認のスキルで補う）。
- デプロイの確認を PR の確認の中で直接実行せず、ワーカーに回したのは、エージェントの実行（数分かかる）で PR の確認を止めないため。
  ワーカーに回すと、同時に実行する数の上限・一時停止と中止での停止・終了のときの後片付けが、ほかの実行と同じになる。
- 確認できなかったときに修正のタスクを作らないのは、アプリの不具合の根拠が無いため（作るとエージェントの失敗のたびにタスクが増える）。
- 予算の上限で一時停止にしないのは、完了したタスクを一時停止すると、再開でやり直す工程が無く、画面の操作が意味を持たないため。
- 連鎖の上限を3段にしたのは、2回直しても同じところで落ちるなら、自動の修正ではなく人が見る段階と考えたため（値は運用で見直す）。
  重複の判定を「同じ目印の終わっていない修正のタスク」にしたのは、ベースブランチが壊れたまま別のタスクがマージされたとき、
  同じ失敗の修正のタスクを増やさないため。
- 再起動で中断した確認をやり直さないのは、確認の途中で止まり続ける（費用だけがかかる）ことを避けるため。必要なら、人が
  修正のタスクを作る。

## 影響

- 作業履歴のイベントが7つ増える（`DeploymentWatchStarted`・`DeploymentCiFinished`・`DeploymentCheckStarted`・`DeploymentChecked`・
  `DeploymentWatchSkipped`・`DeploymentFixRegistered`・`DeploymentFixSuppressed`）。費用を持つイベントは13種類になる。
- タスクの作られ方に `deployment`（修正のタスク）が増える。
- `config.yaml` の `step_agents` に `deployment` を書ける。
- 対象のリポジトリの GitHub のアカウントには、Actions とチェックを読む権限が要る（読めなければ、時間切れまで待って終わる）。
- 仕様は [デプロイの監視](../spec/deployment-watch.md)。
