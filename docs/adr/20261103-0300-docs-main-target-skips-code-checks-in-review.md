# 文書が主対象のレビューでは、文書に効く検証だけを実行し、コードの検証を実行しない

- 日時: 2026-11-03 03:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-285
- 置き換え元: なし
- 置き換え先: なし

## 背景

既定のスキル `review-dispatch` の「検証の実行」は、`self-review`・`pr-review` のどちらでも、見つけたフォーマッター・リンター・型チェック・テスト・ビルドをすべて実行させた。文書だけの変更には「文書向けのリンターなどがあれば実行する」とだけ書かれ、コードの検証を省く決まりが無かった。
実験では、要求要件の工程の 37 回の実行のうち 20 回で検証のコマンド（依存の取得・テスト・リポジトリ全体の検査・ビルド）を実行していた。要求要件の PR への sacty のレビューも、依存の取得の後にテストやリポジトリ全体のフォーマットの検査を実行していた。時間とトークンを使うが、文書の判断には使われなかった。

## 決定

- 主対象が文書（`design-doc`・`user-doc`）のレビューでは、`self-review`・`pr-review` のどちらでも、変えた文書に効く検証（文書のフォーマッター・文書の lint・リンクの検査など、リポジトリにあるもの）だけを実行する。コードのテスト・ビルド・型チェック・コードのリンターは実行しない。テストランナーで書かれた文書だけの検査（リンク・参照・生成物の一致など）は、文書に効く検証として実行する。文書に効く検証が無ければ、何も実行しない。
  - 対象のファイルを引数で絞れるツールは、変えた文書に絞って実行する。絞れず、コードも検査してしまうものは実行しない。
- 主対象が `code`（文書とコードの両方を変える PR を含む）は、今までどおり全部を実行する。
- 主対象が文書でも、レビューの範囲の差分にコードの変更が含まれるときは、全部を実行し（`scope` は `all`）、X-2 も `code` と同じに起動する。
- `summary.json` に実行した範囲（`scope`: `all`・`docs`）を残す。
- 検証結果の分析の観点 X-2 は、`scope` が `docs`（主対象が文書で、差分にコードの変更が無い）のときは、文書に効く検証を実行したときだけ起動する。CI の結果だけでは起動せず、CI に失敗したチェックがあれば、レビューの範囲に 1 行書く。`scope` が `docs` のときの X-2 は、意図して実行していない検証を指摘しない。
- sacty の PR レビューの指示は、スキルの規則どおりに文書に効く検証だけを実行するよう添える。

## 理由

- 文書の判断に、テスト・ビルド・型チェックの結果は使われない。実行すると、時間と費用がかかるうえ、文書と関係のない失敗の分析が混ざる。
- 差分にコードが含まれるときまで省くと、コードの変更が検証されないまま通る。主対象の種類だけでなく、差分も見て、省く側に倒しすぎない。
- CI の結果は、コードの検証が中心になりやすい。文書の判断のための分析には使わないが、失敗したことは人に伝える。
- 既定のスキルはあらゆる言語・リポジトリに渡るので、特定の言語やツールに寄せずに書く。

## 影響

- 文書が主対象のレビューでは、検証にかかる時間と費用が減る。文書に効く検証が無いリポジトリでは、検証を実行しない。
- 文書が主対象のレビューでは、テストやビルドの失敗は検出されない。文書の判断に関わる変更（コードの変更を含む）は、上の規則で全部の検証の対象になる。
- 仕様書は[既定のコンテキスト](../spec/context.md#既定のレビュー用スキル)と[タスクと工程](../spec/tasks-and-steps.md)に、利用者向けは[取り込み](../user/intake.md)に記す。
