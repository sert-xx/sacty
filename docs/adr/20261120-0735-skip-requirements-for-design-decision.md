# 受け入れ条件がそろい設計の判断が要る依頼は、要求要件を省き、設計 → 実装で進める

- 日時: 2026-11-20 07:35 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-420
- 置き換え元: [受け入れ条件が詳しく、人に確かめることが無い依頼では、要求要件を省く](20261102-2357-superseded-skip-requirements-for-detailed-acceptance.md)（設計だけを残して要求要件を省く組み合わせを足さず、設計の判断が要る依頼を `standard` にすること）、[受け入れ条件が明示した API の変更では、「公開 API の形を変える」を要求要件を残す理由にしない](20261103-0530-superseded-api-change-in-acceptance-keeps-no-requirements.md)（設計の判断が要るときに `standard` にすること）
- 置き換え先: なし

## 背景

PBI-283 は、設計の判断が要る依頼を、受け入れ条件が詳しくても `standard`（要求要件 → 設計 → 実装）にした。PBI-288 もこれを変えなかった。
PBI-395 では、受け入れ条件がそろっていて設計の判断が残る依頼で、要求要件の工程が受け入れ条件を言い直しただけになった。PR・レビュー 2 回・人の判断の分だけ、時間と費用がかかった。

## 決定

- 組み合わせ `skip-requirements`（`design` → `implement` → `deployment`。要求要件の工程を持たない）を足す。設計の工程は `standard` と同じ。
- オーケストレーターは、受け入れ条件がそろっていて（`direct` を選ぶときと同じ基準）、設計の判断（新しい仕組み・層をまたぐ作りの選択）が要るなら、この組み合わせを選ぶ。`reason` に、要求要件を省いた理由と、人に確かめたい点（あれば 1 つずつ）を書く。
- 人に確かめたいことがあっても（依頼に書かれていない判断・書き忘れ・ほかのタスクや PR との衝突・共有の状態や項目に新しい意味を載せる・公開の API や項目の変更の扱い）、要求要件を残さない。確かめたいことは、設計の「確認したいこと」で尋ねる。最初の設計の実行に、`reason` を JSON のデータとして渡す。
- 依頼が曖昧・受け入れ条件がそろっていない・依頼と文書やコードや方針が食い違い作るものが変わる・判断しきれない、のどれかなら、設計の判断が要っても要求要件を残す。上の 2 つにともに当たるときは、要求要件を残す側を優先する。
- 設計の判断が要らないときの選び方（確かめることが無ければ `direct`、あれば `skip-design`）は変えない。
- 実装の指示は、タスクの内容（依頼）を含み、依頼と承認済みの設計を基準にする。
- 人がタスクの作成時に画面で指定できる。`sacty mcp` の `create_task` には、組み合わせの引数を足さない。
- 既存の PR の引き継ぎ・リポジトリが要る組み合わせの判定・マージの後の監視は、`standard` と同じに扱う。

## 理由

- 要求要件の工程を省いても、確かめたいことは設計の「確認したいこと」で人に尋ねられるので、人の判断は失われない。
- 比べた案：PBI-283 のとおり `standard` のままにする案は、PBI-395 のように要求要件が受け入れ条件の言い直しになる費用が残るため、採らない。
- 工程の見直しは、工程が終わった後にしか走らない。この組み合わせでは設計が最初の工程なので、設計を飛ばすかを決めることは無い。

## 影響

- オーケストレーターの指示（`DETAILED_ACCEPTANCE_LINE`・`planDescriptions`）と、設計・実装・PR の本文・提出の前のレビューの基準の文が変わる。ほかの組み合わせの工程・指示は変わらない。
- `StepsChosen.plan` と `TaskCreated.plan` は `STEP_PLANS` のキーから作る列挙なので、この組み合わせを知らない版が書いた記録は、そのまま読める。この組み合わせを知らない古い版が、この組み合わせのタスクを読むことは求めない。
- 規則は[工程の選択](../spec/tasks-and-steps.md#受け入れ条件がそろい設計の判断が要る依頼)に記す。
