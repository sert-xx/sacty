# 同じ SACTY_HOME のデーモンは OS のファイルロックで1つに限り、2つ目はデータに触れる前に終わる

- 日時: 2026-10-14 08:13 UTC
- ステータス: 採用
- 関係する PR・タスク: #87、PBI-79
- 置き換え元: なし
- 置き換え先: なし

## 背景

同じ `SACTY_HOME` で2つ目のデーモンが起動すると、起動の処理（共用の compose の実行ごとの取得の削除、`recoverInterrupted` による中断の記録など）が
1つ目に影響していた。同じポートなら listen で失敗する前にこれらが走り、別のポートなら同じ台帳・DB に2つが書いていた。

## 決定

- デーモンは、起動してすぐ（`SACTY_HOME` を作った直後）に `SACTY_HOME/daemon.lock` の OS のファイルロック（SQLite の排他ロック。中身は fcntl のロック）を取る。
  取れなければ2つ目として終わる。DB を開く・片付け・中断の回復・listen など、データに触れる起動の処理はすべてロックの後にする。
- 2つ目のデーモンは、動いているデーモンの接続先・PID・起動時刻を表示して、専用の終了コード（3）で終わる。`sacty up` はそのコードを見たら、ほかの sacty が
  動いているため起動しなかった旨を表示して失敗（終了コード1）で終わり、画面を起動せず、`daemon.json` も書かない。
- 動いているデーモンの接続先・PID・起動時刻は `daemon-owner.json` に書く。表示のためだけで、判定には使わない。止めるときは自分が書いたものだけを消す。
- 違う `SACTY_HOME` のデーモンは並行して動ける。

## 理由

- OS のファイルロックにしたのは、ロックはプロセスが持ち、どう終わっても（SIGKILL を含む）OS が外すので、突然落ちて残った印や PID の再利用で起動が止まらないため。
  PID と開始時刻の照合では、ファイルの書き換えと照合の間に競合が残る（PR の本文）。
- ロックはファイル（inode）に掛かるので、同じホームを別の書き方（シンボリックリンク）で指しても二重に起動できない（PR の本文）。
- fcntl のロックは子プロセスに引き継がれないので、デーモンが MCP サーバーなどを残して落ちても次の起動ができ、残ったものは #86 で決めた片付けで止まる
  （所有元のデーモンは終わっているので、所有元の判定とも矛盾しない）（PR の本文）。
- SQLite の排他ロックにしたのは、`node:sqlite` を既に使っていて依存が増えないため（PR の本文）。

## 影響

- 同じ `SACTY_HOME` で sacty を2つ動かすことはできなくなる。
- `daemon-owner.json` の内容は表示のためだけで、2つの起動がほぼ同時のときは前回の残りの PID を表示することがある（判定には影響しない）。
