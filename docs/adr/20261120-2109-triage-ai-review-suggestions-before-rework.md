# AI のレビューの提案に対応するかどうかは、直しに入る前に AI が PR の範囲で判断し、対応しない判断は AI で終える

## 背景

sacty が作った実装の PR は、PR のレビューの子タスクが指摘なしになるまでレビューし、提案ありの回も完了にせずに見守る（[レビューのタスクは、判定が指摘なしになるまで完了にせず、PR の変化を見守って自動で再レビューする](20261119-1925-review-task-watches-pr-until-no-findings.md)）。
PR を作ったタスクは、届いた指摘を、提案（`[提案]`）を含めて必ず直しに入っていた。
AI のレビューの指摘だけなら、戻し先は子タスクの答えから実行せずに決めていた（[置き換え元](20261112-0748-superseded-review-child-task-decides-rework-target.md)）。

そのため、提案だけの回が続くと、直し・push・再レビューの往復が止まらなかった。
直しで足した文面の細部に新しい提案が付き、それを直すとまた提案が付く。
実例では、提案だけの往復に約 1 時間 40 分・約 25 ドルかかった。
1 往復は中央値で約 20 分、費用は直しが 1〜2 ドル、再レビューが 5〜8 ドルかかる。

実装が直しの中で指摘を断る仕組み（`declined`）と、後続に回したい案を人が決める仕組み（[後続に回すかどうかは人が決め、実装は案と理由までを出す](20261117-0415-superseded-defer-proposals-decided-by-person.md)）はあった。
どちらも、直しの実行に入った後に働くので、実行・push・再レビューの往復は省けなかった。
また、後続に回すかの最終決定を人がするので、提案ごとに人の手間がかかっていた。

## 決定

- 実装の PR の、AI のレビューの提案は、直しに入る前に、AI（PR の工程のエージェント。実装後のコードの読み取り専用の写しで動く）が、PR の範囲を考えて、提案ごとに「この PR で対応する／対応しない」と理由を判断する（選り分け）。
  - 判断の基準は、PR の目的の範囲と、直さないと出る害・後の手戻りで決める。好み・書式・言い回し、直しで足した文面の細部への新しい提案、同じ原因の別の現れ、蒸し返しは対応しない。
  - 回が進むほど対応する敷居を上げ、提案だけの回が 2 回以上続いたら、原則すべて対応しない。
- 対応しない判断は、AI で終える。人が 1 件ずつ決める手順は置かない。判断と理由は、PR に返信し、sacty の作業履歴に残す。
- 人は、PR に要対応とコメントすれば覆せる（人の指摘として取り込まれ、選り分けを通らずに直す）。sacty の画面から差し戻すこともできる。
- 要修正（`[要修正]`）と、人の指摘は選り分けず、今までどおり直す。
- 判断できなかった提案（実行の失敗・答えを読めない・判断が無い・理由の無い decline）は、対応する側にして直しに入る。
- 提案のすべてを対応しないとして、直す指摘が残らなければ、直しの実行をせず、理由を返信してから、同じ先頭を 1 回だけ判定し直させる（[AI のレビューの指摘をすべて断って何も変えなかったら、断った理由を返信し、同じ先頭を 1 回だけ判定し直させる](20261117-0250-reply-and-rejudge-when-all-findings-declined.md)の仕組みを使う）。
  判定し直した回に残った提案もすべて対応しないなら、返信の後に一時停止して、人が選ぶ。
- 再レビューには、対応しないとした提案と理由を毎回渡し、未対応に数えさせず、蒸し返させない。要修正の重さに当たると分かったときだけ、新しい要修正にできる。
- 選り分けは実装の PR だけで行う。要求要件・設計の PR、自己レビュー、GitHub から取り込んだ PR のレビューだけのタスクは変えない。

## 理由

比べた案と、採らなかった理由は次のとおり。

| 案 | 採らなかった理由 |
| --- | --- |
| 提案を一律に受け入れる（今までの振る舞い） | 提案だけの往復が止まらず、時間と費用がかかる |
| 提案を一律に弾く | 直さないと害が出る提案や、PR の目的に沿う提案まで落とす |
| 提案だけなら、人の承認を待つ | 提案ごとに人の手間がかかる。sacty が人を待つ時間が増える |
| 提案だけの回を 3 回で止める | 利用者が採らないと決めた。回数で止めても、止めるまでの往復は省けない |
| 直しの実行の中で断らせる（今の `declined`） | 直しに入ってから断るので、実行・push・再レビューの往復は省けない |

直しに入る前に選り分ければ、対応しない提案のために往復を起こさない。
対応しない判断を AI で終えても、判断と理由が PR に残り、人はコメントで覆せるので、人の判断を奪わない。
判断できないときに対応する側に倒すのは、AI の誤りで直すべき提案を落とさないためである。

## 影響

- 良い点：対応しない提案のための直し・push・再レビューの往復が無くなる。人が提案ごとに決める手間も無い。
- 悪い点：提案のある回には、選り分けの実行（1〜2 分）とその費用が足される。費用はタスクの予算に入り、工程ごとの費用の表の「提案の選り分け」の行に出る。
- 悪い点：AI が、直すべき提案を対応しないと誤って判断するおそれがある。人は、PR の返信と作業履歴で判断と理由を読み、PR に要対応とコメントして覆せる。判断できないときは対応する側に倒す。
- 作業履歴に `SuggestionsTriaged` を足し、`ReviewRejudgeRequested` に `reason: triaged` を足した。
- 仕様は [承認と差し戻し](../spec/approval.md#直しに入る前の提案の選り分け)、[タスクと工程](../spec/tasks-and-steps.md#pr-のレビューだけのタスク)、[作業履歴](../spec/event-log.md#費用) にある。
