# 秘密情報を伏せる木は、節を型付き配列で持ち、とても長い値でもメモリを値の長さに比例させる

- 日時: 2026-11-21 13:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-444
- 置き換え元: なし
- 置き換え先: なし

## 背景

値の全体の出現を探す木は、値の文字ごとに節を 1 つ持ち、節ごとに `Map` を作っていた。2MB の値 1 つで約 650MB（1 文字あたり約 300 バイト）を使った。
JSON でない認証ファイルは中身の全体が 1 つの値になり、コンテナの中のエージェントは、そのファイルを任意の大きさに書き換えられる。巨大なファイルで、デーモンのメモリを使い切るおそれがあった。

## 決定

- 節を型付き配列（最初の子の文字・最初の子・失敗の遷移・一致する値の長さ）で持つ。1 文字あたり約 14 バイト。
- 子が 2 つ以上ある節の 2 つ目以降の子だけを `Map` に入れる。そうなる節の数は値の数以下なので、長い値の途中の節（子が 1 つ）は `Map` を持たない。
- 値の長さに上限は置かない。上限を置かないので、値・ファイルを伏せる対象から外す場合も、伏せる側に倒す・失敗にする場合も無い。どの値も、今までどおり伏せる。
- 走査・失敗の遷移の作り方は変えない（時間は値と入力の長さに比例する）。

## 理由

- 上限を置くと、超えた値を別の方法で伏せるか、出力を伏せるか、実行を失敗にするかを選ぶ必要があり、利用者に見える振る舞いが変わる。節を軽くするだけで、2MB が約 28MB（1 文字あたり 30 バイト以下）になり、足りる。
- 採らなかった案：長い値を木に入れず `indexOf` で探す。同じ文字が続く入力で二乗になりうる。

## 影響

- 伏せる結果は変わらない。
- 32MB の値でも、木は約 450MB の配列で、止まらずに作れる。それ以上の値は、読めた範囲で同じ比例で増える（`readFileSync` が読めない大きさのファイルは、今までどおり読まずに飛ばす）。
- 値が長いと、少しずつ届く出力の持ち越しも値の長さの分だけ増える（長さに比例）。

## 確かめたこと

- `redact-long.test.ts`：木の配列の大きさが 1 文字あたり 30 バイト以下で、長さに比例すること（GC や時間に左右されない数え方）。2MB の値の伏せが 1 秒以下。長い値の重なり・境目をまたぐ出力（`StreamRedactor`・`ByteRedactor`）で、1 文字も残らないこと。
- 木の持ち方を元の `Map` の版に戻すと、このテストは落ちる（木の配列が無い）。
