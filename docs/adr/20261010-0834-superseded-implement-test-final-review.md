## 背景

#4 で設計とテスト観点を承認できるようになったが、実装の工程は無かった。実装がテスト観点を満たしたことを、エージェントの
申告だけに頼らずに確かめる方法を決める必要があった。PBI-10 は大きいので2つに分け、この PR は前半（PBI-10a）として、
実装・テストの実行・最終レビューを扱う。

## 決定

- 対象リポジトリは、config.yaml の `repository`（`url`・`base_branch`・`test_command`）で指定する。
- sacty が対象リポジトリをホストの git の認証で clone し、その clone を作業領域にして工程のエージェントを実行する。起点のコミットは
  `RepositoryPrepared` として台帳に記録する。
- 実装の工程には、承認済みの要求要件・設計・テスト観点と、これまでの人間の指摘を渡す。エージェントは観点ごとのテストの対応を
  `sacty-test-map` で申告する。「観点 → テスト → 実行結果」の対応表は、sacty が申告・テストの結果・最終レビューの判定から作る。
- テストは、エージェントとは別のコンテナで実行し、秘密情報（環境変数・認証ファイル）を渡さない。ネットワークは既定のものを使う。
  合格の条件は、終了コードが 0 で、かつすべての観点に対応するテストがあること。結果は出力の末尾とともに `TestsRun` で記録する。
  テストごとの合否は読まない。
- テストに合格したら、ゴールガーディアンが空の作業領域・新しいセッションで最終レビューする。渡すのは、承認済みの成果物、差分
  （新しいファイルを含む）、観点とテストの対応、テストの結果、人間の指摘。過去の最終レビューの判定と、工程のエージェントの説明は渡さない。
  判定は観点ごと・指摘ごと（「再発なし」）に `FinalReviewed` で記録し、判定が無い観点や指摘は不合格として扱う。
- 検証（テスト・最終レビュー）に通らなければ、失敗の内容を渡して実装をやり直す。3回続けて通らなければ一時停止し、再開すると数え直す。
  前の工程に戻ったら、検証の途中経過と失敗の回数は持ち越さない。
- 最終レビューを実行できなかったとき（利用上限など）は、実装をやり直さずに止め、再開すると最終レビューからやり直す。そのときも、
  使った分の費用を `FinalReviewFailed` に記録して予算に入れる。
- 差分を取得できなければ、最終レビューをせずに一時停止し、再開すると差分の取得からやり直す（テストは繰り返さない）。

## 理由

- テストのコンテナを既定のネットワークで実行するのは、`npm ci` などの依存の取得に必要なため（PR の本文。ネットワークを切る設定は、
  必要なら PBI-10b 以降で足すとした）。
- 観点とテストの対応をエージェントの申告にもとづかせ、申告どおりに観点を検証しているかはゴールガーディアンが差分を見て判定する
  （PR の本文で、判断してほしい点として挙げた）。
- 最終レビューの失敗の費用を記録するのは、記録しないと費用の表示と予算の制限が実際の使用量から外れることがレビューで再現されたため。
- 差分を取得できないときに止めるのは、差分はテストが観点を本当に検証するかを判断するための必須の入力で、合否の安全をエラー文を見た
  モデルの判断に依存させるべきではないため（レビューの指摘）。
- テストを別のコンテナで秘密情報なしに実行する理由、最終レビューに過去の判定を渡さない理由、やり直しを 3 回にした理由は、記録に無い。

## 影響

- 対象リポジトリの設定は、PBI-5 のプロジェクトの設定で置き換える予定とした。
- PBI-8・9 のときに設計を承認し、実装の工程が無かったため待機していたタスクは、起動の時に実行待ちにする。
- 一時停止に、理由の説明（`pausedMessage`）を付けられるようになる。
