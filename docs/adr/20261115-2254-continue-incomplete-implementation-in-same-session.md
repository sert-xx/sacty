# 未完了で終わった実装の実行を、同じセッションの続きから進め、続きの上限を 10 回にする

- 日時: 2026-11-15 22:54 UTC
- ステータス: 採用
- 関係する PR・タスク: #381、PBI-350
- 置き換え元: [終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない](20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)（提出しなかったときに、実装を最初からやり直し、3 回続けて終わらなければ一時停止する部分）
- 置き換え先: なし

## 背景

2026-11-15、終わっていない実装を提出しない仕組み（[前の決定](20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)）を、止めてあった分割の子タスクで確かめた。

- 実装のエージェント（Codex）は、3 回とも 1〜5 分で実行を終え、未完了と申告した。
- sacty は、3 回とも提出せずに実装をやり直し、3 回目の後に一時停止した。未完了の実装は PR にならなかった。
- 3 回とも作業領域は進み、残っていることは 7 件、7 件、5 件と減った。ただ、3 回では終わらなかった。
- 文脈の上限には当たっていなかった（1回の呼び出しは最大で約 9.7 万トークン、上限は 47.5 万）。エージェントが、自分で実行を終えていた。
- やり直しは、毎回新しいセッションで、指示の全文を読むところから始まっていた。前の実行の会話は引き継いでいなかった。

完了の条件を満たすまで続けさせる仕組みとして、次の3つを比べた。

- Claude Code の `/goal`：非対話の実行（`claude -p`）でも使える。別の小さいモデルが、会話を読んで条件を満たしたかを判定する。
  Codex にもゴールの機能はあるが、非対話の実行（`codex exec`）は、最初のターンが終わると終了し、ゴールの続行は走らない（版 0.167.0 のソースを読んだ結果。実行しては確かめていない）。
  途中で終えていたのは Codex なので、これだけでは直らない。
- 終了時のフック（Stop フック）：どちらのエージェントにもあり、終了を止めて続行させられる。フックの置き方はエージェントごとに違う。1回の実行の中で続くので、予算は実行が終わるまで確かめられない。
- セッションの再開：sacty は、時間切れで止めた実行を、同じセッションの続きから進める仕組みを、すでに持っている（PBI-280）。

人が決めたこと（2026-11-16）：

- sacty が同じセッションを続きから再開する形にする。`/goal` と Stop フックは使わない。
- 続ける回数の上限は、10 回にする（はじめ 18 回と伝えたのは打ち間違いで、同じ日に 10 回と決め直した）。
- 指示の文言の見直しも一緒に入れる。

## 決定

- 実装の実行が未完了で終わったら（未完了と申告した・申告が無いか読めない・観点とテストの対応が欠けた）、次の実装の実行は、同じエージェントのセッションの続きから進める。
  時間切れで止めた実行の続きと、同じ仕組みを使う。
  - セッションを続けられないとき（エージェントを変えた・写したセッションが無いか壊れている・AI が再開を受け付けない）は、最初から実行し直す。
  - 続けたか、最初から実行し直したかは、時間切れの続きと同じ記録に、未完了の続きであることを添えて残す。
- 続きの実行の指示は、次のように渡す。
  - 未完了の後に一時停止が無い（自動の続き）：続きの指示と、実行ごとに変わりうる案内（始める前の取り込みで競合したファイル・起動したサービスの接続先など）だけを渡す。指示の全文は送り直さない。
  - 未完了の後に一時停止を挟んだ（人が再開した）：続きの指示の後に、指示の全文を続ける。
- 作業領域が進んでいる間は続ける。続きの実行が 10 回に達しても未完了なら、一時停止する（前の決定では、未完了が 3 回続くと止めていた）。
  続けても作業領域の内容が変わらなければ、回数を待たずに一時停止する（前の決定のまま）。
  人が再開すると、回数を数え直す（前の決定のまま）。
- 完了の申告の指示に、次のことを足す。
  - この実行の中で、範囲のすべてを実装し終える。途中で実行を終えても、sacty は同じセッションを再開するだけで、進まない。
  - 未完了で終えてよいのは、これ以上進められないとき（人の判断や、外部の状態の変化が要るとき）だけ。
  - エージェントには確かめられないこと（CI の結果など）は、残っていることではなく、人が確かめることとして書く。

## 理由

- 最初からやり直すと、前の実行の会話（読んだもの・試したこと・判断）を捨てる。続きから進めれば、同じ調査を繰り返さずに、止まったところから進められる。
- セッションの再開を選んだのは、どちらのエージェントでも同じ形にでき、すでにある仕組みを使えるためである。
  続きの1回ごとに、作業履歴に記録が残る。予算の確認・一時停止・中止も、続きの間に入る。
  Stop フックで1回の実行の中で続ける形は、予算を実行が終わるまで確かめられず、エージェントごとにフックの置き方を持つ必要がある。
- 自動の続きで指示の全文を送り直さないのは、続きのたびに全文を足すと、文脈が膨らむためである（時間切れの続きは、まれなので、全文を送り直している）。
  一時停止を挟んだ続きで全文を送るのは、人の補足や、止めている間に届いた指摘が入りうるためである。
- 上限を回数だけにせず、作業領域が進んでいるかも見るのは、進んでいる間は続ける価値があり、進まないなら続けても費用がかかるだけのためである。
- 指示の文言を直したのは、前の指示が「未完了なら sacty がやり直させる」と伝えていて、区切りのよい所で実行を終えてよいと読める余地があったためである。
  実物の確認では、残っていることに「CI の結果を確かめる」が入っていた。エージェントには確かめられないことが残っていることに入ると、完了と申告できなくなる。

## 影響

- 未完了が続くタスクは、最大で、最初の実行と 10 回の続きの実行の費用がかかる（前の決定では 3 回の実行）。予算の上限は、続きの間にも効く。
- 続きの実行は、前の実行のセッションのファイルを戻して始める。作業履歴に「未完了で終わった実装の実行のセッションを続けた」の行が増える。
- 続ける回数の上限（10 回）は、実物の結果を見て、変えることがある。
- 終了時のフックや `/goal` を使った、1回の実行の中での続行は、この決定に含めていない。
- 実装のエージェントを、未完了の回数やタスクの大きさで上の段階に変えることは、この決定に含めていない（人がまだ決めていない）。
