# 文書作成の成果物は出力した原稿の本文だと指示し、外部には書かせず、差し戻しでは前回の原稿を直させる

## 背景

文書作成（`document`）のタスクで、外部の PF（Confluence・Notion など）にある文書の内容を直すよう差し戻したところ、次のことが起きた。

- 最初に作られた文書とは別の文書が、外部に新しく作られた。
- タスクの最終報告（「〜のドキュメントを作成。エージェント ID は〜」のような内容）も、外部に文書として作られた。

文書作成のエージェントには、[ほかの工程と同じく外部 PF・MCP を渡している](20261022-1505-document-step-gets-context.md)。
指示は「原稿そのものは外部やリポジトリに直接書かず出力する」だけで、次のことを伝えていなかった。

- 何が成果物か（出力の全体が原稿として保存され、承認の後にそのまま書き出されること）
- タスク・指摘が外部への作成・更新を求めていても、書かないこと
- 差し戻しで直す対象は前回の原稿であること

そのため、エージェントが外部に直接文書を作り、出力には作業の報告を書いた。
差し戻しでは、指摘の「外部の文書を直す」に従って外部に別の文書を作った。
人が承認すると、作業の報告が原稿として書き出された。

利用者からは、何が成果物かを明確にし、修正のときはその成果物を続けて直すべきで、成果物でないものを sacty の外に出してはいけない、という指摘があった。

## 決定

- 文書作成の指示に「成果物」の節を置き、次のことを伝える（`documentDeliverableLines`）。
  - 成果物は、出力する原稿の本文そのもの（指摘への対応の JSON を除く出力の全体）で、それを人間が承認する。
  - 外部サービス・リポジトリには何も書かない（外部は読むだけ）。タスク・チケット・指摘・規約が外部への作成・更新を求めていても同じ。
  - 承認された原稿は sacty が書き出す。書き出し先が決まっていれば接続先と置き場所を、書き出したページがあればその URL を伝える。
  - 作業の報告（作成した旨・URL・タスクやエージェントの ID・手順）を出力に書かず、原稿の前後に説明を付けない。
  - 差し戻しでは、前回の原稿を直して全文を出力し、別の文書を作らない。外部のページを直すよう求める指摘も、前回の原稿への指摘として扱う。
- 書き出しの指示にも、書くのは書き出すファイルの内容の1ページだけで、書き出しの報告を別のページやコメントとして書かないことを足す。
- 「既存文書の直接更新依頼は作業で扱います」の一文は、文書作成のエージェントに外部を直接直してよいと読める余地があるので、文書作成の指示から除く
  （既存の外部文書の直接更新を `operation` で扱うことは、オーケストレーターの指示のとおり変えない）。

## 理由

- 成果物を1つ（sacty に保存した原稿）に決めれば、承認する物・書き出す物・差し戻しで直す物が同じになり、外部に別の文書や報告が出ない。
- 差し戻しの指摘は、人が外部で読んだ文書を指して書かれることが多い。指示でそれが前回の原稿のことだと伝えないと、エージェントは指摘の文面どおりに外部を直そうとする。
- ゲートウェイで文書作成の実行の外部 PF を読み取り（GET・HEAD）だけにする案は採らなかった。
  Notion の検索のように POST で読む API があり、文書作成で外部の資料を読めるようにした[前の決定](20261022-1505-document-step-gets-context.md)の目的を損なう。
  MCP のツールは、読み取りか書き込みかを sacty からは区別できず、絞れない。

## 影響

- 文書作成のエージェントは、引き続き外部 PF・MCP に書き込める（強制はしない）。外部に書かないことは指示で伝える。
- 仕様は[タスクと工程](../spec/tasks-and-steps.md)・[書き出し](../spec/export.md)、操作は[タスクを進める](../user/tasks.md)に記載する。
