# PR の本文のリンクの解析を別スレッドで行い、5 秒で打ち切る

- 日時: 2026-11-17 16:38 UTC
- ステータス: 採用
- 関係する PR・タスク: #427、PBI-372
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty が作る PR の本文から、コンテナの作業領域（`/workspace`）へのリンクを外す変換は、本文を Markdown のパーサー（`mdast-util-from-markdown`）で解析する。
解析はデーモンのスレッドで同期に動いていた。記号が本文の上限（65,000 文字）近くまで続く本文では、解析が終わるまで、デーモンのほかの処理（HTTP の応答・停止の操作）が待つ。
データは壊れない。実害は待ちだけだが、待ちは数十秒になりうる。

直す前のコードで測った（先頭に作業領域へのリンクを1つ置き、記号を続けた本文。変換の全体の時間。1台の開発機での1回の計測）。

| 続けた記号 | 8,000 文字 | 16,000 文字 | 32,000 文字 | 65,000 文字 |
| --- | --- | --- | --- | --- |
| `>` | 0.05 秒 | 0.09 秒 | 0.99 秒 | 3.70 秒 |
| `*a` | 0.22 秒 | 0.57 秒 | 2.22 秒 | 14.95 秒 |
| `*_` | 0.54 秒 | 2.08 秒 | 9.83 秒 | 53.97 秒 |
| `1. ` | 0.43 秒 | 1.58 秒 | 6.05 秒 | 26.91 秒 |
| `+ ` | 0.77 秒 | 2.83 秒 | 11.67 秒 | 56.17 秒 |

時間は、長さのおよそ2乗で伸びる。ふつうの本文（リンクが上限まで並ぶ）は、同期の解析で 0.1 秒ほど。

直し方の候補は2つあった。

- (a) 解析を別スレッド・別プロセスに分け、時間で打ち切る。
- (b) 解析する本文に上限（大きさ・形）を置き、超えたら解析せずに、変えずに使う。こちらのほうが、変更は小さい。

## 決定

(a) にした。持ち主の確認は、この ADR を書いた時点ではまだ。

- 解析と置き換えを、Node.js の別スレッド（`worker_threads`）で動かす。デーモンのスレッドは、答えを待つだけにする。
- 待つ時間の上限は 5 秒。超えたら別スレッドを止めて、本文を変えずに使う（PR の作成・更新は止めない）。
- 解析に失敗した（例外・別スレッドのエラー・別スレッドを起動できない・別スレッドが答えずに終わった）ときも、本文を変えずに使う。
- 打ち切った・失敗したことは、デーモンのログに残す（タスクの ID・リポジトリ・理由。失敗には、原因の短い文字：例外の名前・エラーのコード・終了コード）。作業履歴（タスクの記録）には残さない。本文の中身と、例外のメッセージは、ログに出さない。
- 別スレッドは、解析する本文ごとに1つ起動し、答えを受け取ったら止める。作業領域へのリンクがありえない本文（これまでの事前の判定）では、起動しない。
- 同時に動かす別スレッドは、1つにする。ほかの本文は、来た順に待つ（レビューの指摘で足した）。
- 時間の上限（5 秒）は、順番が来て別スレッドを起動してから数える。順番を待つ時間は、入れない。
- 別スレッドのメモリ（古い世代のヒープ）の上限を、128MB にする（Node.js の `resourceLimits`。レビューの指摘で足した）。超えたら、別スレッドはエラーで終わり、本文を変えずに使う。
- 遅くなる本文を、解析の前に形で見分けることは、しない。

## 理由

(b) を採らなかった理由。同期の解析は途中で止められないので、(b) は、遅くなる本文を解析の前に確実に見分けられることが条件になる。測った結果、見分けられなかった。

- 大きさの上限では足りない。`+ ` の繰り返しは、8,000 文字で 0.77 秒かかる。1 秒に収めるには上限を 8,000 文字ほどにすることになり、上限近くまでのふつうの本文（結果を変えてはいけない）を解析できなくなる。
- 形の上限では足りない。遅くなる形は、挙がっていた5つだけではなかった。16,000 文字で測ると、`*a_` は 3.52 秒、`1) ` は 1.62 秒、`> + ` は 1.35 秒、`> 1. ` は 0.94 秒、`**_` は 0.91 秒、`[*` は 0.78 秒、`a*` は 0.74 秒。
  強調の記号（`*`・`_`）は、ふつうの文字と混ざっていても遅い（`a*`）。入れ子（引用・箇条書き）は、種類を混ぜても遅い（`> + `）。
  一方、同じ記号でも、遅くならない並びがある（`* `・`_a`・`***` は、16,000 文字で 0.03 秒以下）。記号の数で線を引くと、強調や箇条書きの多いふつうの本文を巻き込むか、遅い並びを通すかの、どちらかになる。
  遅くなるかどうかは、パーサーの中の処理（強調の組の探し方・入れ子の扱い）で決まり、パーサーを動かさずに外から決めきれない。パーサーの版が変われば、遅い形も変わりうる。
- (a) は、形を問わずに、待ちを時間で区切れる。

別プロセスではなく別スレッドにした理由。起動が軽い（リンク1つの本文で、起動を含めて 0.04 秒）。止めるのは、どちらでもできる。

上限を 5 秒にした理由。ふつうの本文は 0.1〜0.3 秒（別スレッドの起動を含む。上限までリンクが並ぶ本文で 0.13 秒、見出し・表・コード・箇条書きの繰り返しで 0.23 秒）で終わるので、20 倍ほどの余裕がある。コンテナの実行などで CPU が混んでいても、ふつうの本文を打ち切らないための余裕として取った。
上限を長くしても、デーモンのほかの処理は待たない。長くすると増えるのは、PR の作成・更新の待ちと、打ち切るまで別スレッドが使う CPU。数十秒かかる本文は、外しても読める本文にはならないので、長く待つ価値は小さいと考えた。5 秒という値そのものに、ほかの根拠は無い。

ログだけにした理由。受け入れ条件は「作業履歴かログで分かる」こと。作業履歴に出すには、イベントの種類・画面の表示・ユーザードキュメントが増える。稀な条件で、PR の作成は止まらないので、小さいほうにした。

別スレッドを使い回さない理由。打ち切りは、スレッドを止めることで行う。使い回すと、止めた後の作り直しが要る。PR の作成・更新のたびの 0.04 秒は、ほかの処理（GitHub への問い合わせ）に比べて小さい。

同時に動かす数を 1 にした理由。上限が無いと、遅い本文が重なった数だけ、CPU とメモリを使う。上限を付ける前に、遅い本文（65,000 文字の `+ `）を4件同時に解析すると、プロセスのメモリ（RSS）は 47MB から最大 1,462MB になった（1件では 476MB）。
1 にすれば、使う資源は、重なった数によらず1つ分になる。ふつうの本文は 0.1〜0.3 秒で終わるので、ふつうの本文どうしの順番待ちは短い（上限までリンクが並ぶ本文を4件同時に呼ぶと、4件目は 0.49 秒で返った）。
2 にすれば、遅い本文が1つあっても、ふつうの本文は待たずに済むが、使う資源は2つ分になる。遅い本文は稀で、待ちは最大 5 秒なので、小さいほうにした。

順番を待つ時間を、時間の上限に入れない理由。入れると、遅い本文の後ろに並んだふつうの本文が、解析を始める前に時間切れになり、外せるはずのリンクが残る（ふつうの本文の結果を変えない、という条件に反する）。
入れないので、PR の作成・更新の待ちは、前に並んだ遅い本文の数 × 5 秒まで伸びる。遅い本文を4件同時に呼ぶと、5・10・15・20 秒で順に打ち切った。遅い本文とふつうの本文を交互に4件呼ぶと、5.00 秒（打ち切り）・5.11 秒（外した）・10.11 秒（打ち切り）・10.22 秒（外した）で返った。
待つ間も、デーモンのほかの処理は待たない（デーモンのスレッドが止まった最大は、3.1 ミリ秒）。待っているのは、その PR を作る・更新するタスクだけ。

メモリの上限を 128MB にした理由。長さの上限いっぱいのふつうの本文を3種類（リンクの並び・見出しと表とコードと箇条書きの繰り返し・日本語の文とリンクの繰り返し）、上限を変えて解析した。

| ヒープの上限 | リンクの並び | 見出し・表・コード・箇条書き | 文とリンク |
| --- | --- | --- | --- |
| 16MB | メモリ不足 | メモリ不足 | メモリ不足 |
| 32MB | 外した | メモリ不足 | 外した |
| 40MB | 外した | 外した | 外した |
| 64MB・128MB・256MB | 外した | 外した | 外した |

ふつうの本文に要るのは 40MB まで。その3倍ほどの 128MB にした（ふつうの本文が、上限に掛からないための余裕）。3倍という値そのものに、ほかの根拠は無い。
この上限は、ヒープの大きさだけを区切る。プロセスのメモリ（RSS）は、それより増える（スタックや、ヒープの外の領域）。遅い本文（65,000 文字の `+ `）1件のとき、RSS の最大は、上限なしで 476MB、128MB の上限で 324MB、64MB の上限で 267MB だった。
128MB の上限では、測った遅い本文は、メモリ不足になる前に、5 秒の時間切れになった（32MB の上限では、メモリ不足のエラーになり、本文を変えずに使う側へ倒れることを確かめた）。メモリを区切っているのは、主に、同時に動かす数と時間の上限で、ヒープの上限は、その外の歯止めになる。

## 影響

- 直した後の計測（ビルドした成果物。同じ開発機。同時数とメモリの上限を付けた後）。65,000 文字の `>`・`*a`・`*_`・`1. `・`+ ` は、どれも 5.00 秒で打ち切り。その間に、デーモンのスレッドが止まった最大の時間は、どの形でも 5 ミリ秒未満（直す前は、上の表の時間だけ止まっていた）。ふつうの本文（上限までリンクが並ぶ）は 0.14 秒。
- 遅い本文を4件同時に呼んだとき、プロセスのメモリ（RSS）は 110MB から最大 395MB（上限を付ける前は、47MB から最大 1,462MB）。
- 遅い本文が重なると、後ろに並んだ本文の PR の作成・更新は、前の遅い本文の数 × 5 秒まで遅れる。
- デーモンの停止は、解析の途中・順番待ちの本文があっても、待たない（遅い本文を4件重ねて 0.3 秒後に `process.exit(0)` を呼ぶと、全体で 0.49 秒で終わった）。
- 記号が上限近くまで続く本文では、作業領域へのリンクが残る（直す前は、数十秒かけて外していた）。PR の作成・更新は、その本文につき最大 5 秒遅れる。
- 直す前（デーモンのスレッドで最後まで解析する）のメモリは、測っていない。
- 別スレッドのスタックは、デーモンのスレッドより大きい（Node.js の既定）。スタックの大きさは、変えていない（メモリの上限は、ヒープだけに付けた）。深い入れ子の本文のうち、これまでスタックがあふれて外せなかったものの一部（8,000 文字の `1. ` など）は、外せるようになる。ふつうの本文の結果は変わらない。
- 変換の本体を、別スレッドで読むファイル（`apps/daemon/src/pr-body-links-worker.ts`）に移した。このファイルは、テストでは TypeScript のまま Node.js に読ませるので、ほかのソースファイルを import しない（型だけの import と、パッケージの import だけ）。
- デスクトップ版は、ビルドした成果物（`apps/daemon/dist`）をそのまま同梱し、同梱した Node.js で動かすので、別スレッドのファイルは、ふつうのファイルとして読める（asar の中には入らない）。同梱の手順そのもの（`npm run desktop:package`）は、動かして確かめていない。
- リンクを外す方針そのものの見直し（表示の文字をインラインコードに入れる案など）は、この決定の範囲の外。
- 仕様は [承認と PR](../spec/approval.md#長さ秘密の値台帳) にある。
