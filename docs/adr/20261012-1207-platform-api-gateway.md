# 外部の PF（プラットフォーム）の API は、ホストのゲートウェイがホワイトリストに合うリクエストだけを PF の認証を付けて中継する

- 日時: 2026-10-12 12:07 UTC
- ステータス: 採用
- 関係する PR・タスク: #42、PBI-35
- 置き換え元: なし
- 置き換え先: なし

## 背景

MCP サーバーが無い PF（プラットフォーム）を、エージェントが API で使う手段が無かった。PF の認証情報をエージェントのコンテナに
渡すと、エージェントが任意の API を呼べてしまう。#39 で、ホストのゲートウェイを置いていた。

## 決定

- config.yaml の `gateway.platforms` に、PF ごとの転送先（`upstream`）・説明・認証のかけ方・使える API のホワイトリスト（`allow`）を書く。
- 認証は「どのヘッダーに・何を付けるか」で書く。形は、固定のキーをヘッダーに付ける・API キーなどでトークン（JWT など）を取得して付ける・
  独自のヘッダーにトークンを付ける、の3つ。トークンの窓口・本文（JSON・フォーム。`{{secret}}` に秘密情報）・応答のトークンと期限の場所は
  PF ごとに書く。期限が切れる前・PF に拒否された（401・403）ときに取り直し、1回だけ送り直す。同時の取得は1回にまとめる。
- ホワイトリストは「メソッド パス」で書く（`*` は1階層、`**` はそれ以下すべて）。合わないリクエストは 403 で拒否し、使える API の一覧を返す。
  送る URL を先に作り、パス・クエリが URL として解釈しても変わらないとき（`#`・空白・`.` や `..` のまとめが無い）だけ、同じパスで判定して送る。
  変わるなら 400 で、上流には一切送らない。
- ゲートウェイは `/r/<実行のトークン>/pf/<PF>/…` を中継する。エージェントには、実行のトークンを含む URL（`SACTY_PF_URL`）と、使える PF と API の
  一覧（指示）だけを渡す。エージェントが付けた認証のヘッダー・クッキーは捨てる。
- PF の認証情報は起動時にまとめて用意し、ゲートウェイのメモリーにだけ持つ。用意できない PF は、どの PF かを状態の warnings として
  タスクの一覧の画面に出す（工程を実行できない problems とは分ける）。ほかの PF は使える。
- 秘密情報を取り出した後のすべての失敗（ヘッダー・本文の組み立て、送信、応答の読み取り）で、理由から秘密情報（値そのもの・JSON の文字列にした形・
  各行）を伏せる。トークンの窓口の失敗の応答は、伏せてから理由の長さを制限する。

## 理由

- 認証の形を3つにし、トークンの窓口を PF ごとに設定で書くことはステークホルダーが、認証の書き方・ホワイトリストの書き方・`SACTY_PF_URL` を
  渡すことは PO が決めた（PR の本文）。それぞれの理由と、比べたほかの案は記録に無い。
- 認証情報をゲートウェイだけが持つのは、エージェントに渡さずに PF の API を安全に使わせるため（PR の本文）。
- 送る URL で判定するのは、`#` 以降はフラグメントとして落ちるので、`POST /api/v1/tickets/123#x/comments` が許可され、許可していない
  `/api/v1/tickets/123` に PF の認証を付けて送られていたため（レビュー）。
- 失敗のすべてで伏せるのは、改行を含む秘密情報をヘッダーに入れたときの例外が値をそのまま含み、画面の警告・起動のログ・ゲートウェイの 502 の
  本文に出ていたため。伏せてから切り詰めるのは、先に切り詰めると境界をまたぐ秘密情報の一部が伏せられずに残っていたため（レビュー）。
- エージェントが付けた認証のヘッダーを捨てる処理は、ゲートウェイが同じヘッダーを本物の値で上書きするので振る舞いは変わらないが、
  守りの二重化として残した（PR の本文）。

## 影響

- エージェントが使える PF の API は、ホワイトリストに書いたものだけになる。足りなければ config.yaml に書き足す。
- 秘密情報は、1Password の参照（#41）でも書ける。
