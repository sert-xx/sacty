# 費用は概算だけを出し、工程の組み合わせごとに予算を決められるようにする

- ステータス: 採用

- 置き換え先: なし

## 背景

- ダッシュボードの「費用と予算」は、費用を「実請求」（`estimated` でない費用）と「概算」（サブスクリプションなどの換算値）に分けて出していた。
  ところが「実請求」の値も、sacty がエージェントの結果の使用量と単価から計算した値で、実際の請求額ではない。sacty には実際の請求額を
  取り込む・直す手段が無く、「実請求」という名前は、実際の請求と合っているように誤解させる。
- タスクの予算の上限は、すべてのタスクで `budget.default_per_task_usd` だった。調査だけのタスクとタスク分割のタスクでは、かかる費用の
  桁が違うのに、同じ上限で止まる（小さいタスクには緩く、大きいタスクにはすぐ止まる）。

## 決定

- ダッシュボードの費用は、`estimated` で分けずに、1つの「概算」として出す（集計の `costs.today`・`costs.days7` は米ドルの数）。
  予算に近いタスクの「概算」の印も出さない。タスクの詳細の費用の「概算」の印（換算値を含むこと）は、これまでどおり出す。
- `config.yaml` に `budget.per_plan_usd`（工程の組み合わせ `StepPlan` ごとの予算）を足す。オーケストレーターがその組み合わせを選んだら、
  `StepsChosen` の `budgetCapUsd` に記録し、タスクの予算の上限をその値にする。書いていない組み合わせは、これまでどおり
  `budget.default_per_task_usd`（タスクを作ったときの上限）のまま。
- 工程を選ぶ前に人が上限を上げていたら（`BudgetCapRaised`）、組み合わせの予算で上書きしない。
- 組み合わせの予算で上限を変えたら、80% の通知をし直す（前の上限での通知を引き継がない）。

## 理由

- 実際の請求額を扱えないのに「実請求」と書くと、利用者が請求の確認にダッシュボードを使い、誤った判断をする。すべての費用を同じ
  「概算」として出せば、sacty の値が目安であることがわかる。
- 組み合わせは、タスクの規模と費用をよく表す（調査だけ・設計だけ・タスク分割など）。オーケストレーターが組み合わせを選ぶのは
  タスクを作った後なので、上限はタスクを作ったときには決められず、工程を選んだ記録で変える。上限の変更を `StepsChosen` に
  記録するので、作業履歴を読み直したときに、設定がその後で変わっても同じ上限になる。
- 人が上げた上限は、そのタスクについての人の判断なので、設定の既定値より優先する。

## 影響

- `DashboardSummary` の `costs.today`・`costs.days7` の形が変わる（`actualUsd`・`estimatedUsd` から米ドルの数へ）。デーモンと画面は
  同じ版で動くので、移行は要らない。
- `budgetCapUsd` を持たない `StepsChosen`（この変更より前の作業履歴を含む）は、これまでどおりの上限になる。
- 投影の予算に `raised`（人が上限を上げた）を足した。
