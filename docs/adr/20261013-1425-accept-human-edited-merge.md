# 人が PR の中で直してからマージしても承認・完了として進め、sacty の成果と人が直した最終の成果の両方を記録する

- 日時: 2026-10-13 14:25 UTC
- ステータス: 採用
- 関係する PR・タスク: #70、PBI-63
- 置き換え元: [PR のあるタスクの成果物チェックは、最新の提出の PR がマージされたことを承認とみなし、画面では承認しない](20261011-0010-superseded-deliverable-check-by-pr-merge.md)（提出と一致しないマージを承認にせず判断を待つ部分）、[Git 管理のリポジトリでは、要求要件・設計を工程ごとにタスクブランチへの PR にし、そのマージを人の承認とする](20261013-1318-superseded-step-pull-request-approval.md)（提出と違う内容のマージを承認にせず判断を待つ部分）
- 置き換え先: なし

## 背景

PR が sacty の出したコミットと違う内容でマージされると（人が PR の中でファイルを直した・提案のコミットを積んだ）、承認にせず人の判断を
待っていた（`merged_outdated`）。#20 では実装の PR について、#67 では要求要件・設計の PR について、そう決めていた。

## 決定

- 違う内容でマージされても、その工程の承認として進める。実装の PR ならタスクを完了にする。最終レビューはやり直さない
  （人がマージした＝人が承認した）。前の版で `merged_outdated` のまま止まっているタスクも、次の確認で進む。
- 要求要件・設計は、その PR のマージの時点のコミット（GitHub の PR の状態のマージのコミット、取れなければ PR の先頭のコミット）から、
  成果のファイルだけを、退避した git のメタデータで読む（作業領域・利用者の git の設定は使わない）。人が直した版（sacty の目印の行は除く）を
  承認済みの成果にし、後の工程・差し戻しの後の作り直しも人の版から始める。
  - ファイルが消された・中身を読めない（1MiB 超・UTF-8 でない・NUL・通常のファイルでない）ときは、sacty の版を承認済みにし、そのことを
    記録する（止めない）。
  - 取得できない一時的な失敗（ネットワーク・認証・GitHub の一時的なエラー）のときは、何も記録せず、次の確認でやり直す。
  - 読んでいる間に中止・差し戻し・再提出があれば、承認を記録しない。
- 設計の承認済みの成果は人が直したファイルの全文にする。ただし最終レビューの基準になるテスト観点は、sacty が出したものを引き継ぐ。
- 要求要件・設計の PR で成果のファイル以外も直されていたときは、PBI-57 の守り（実装の PR を出す前に止める）のまま。
- 台帳（`PullRequestMerged` に省略できる項目を足す）に、sacty が出したコミット（`submitted`）・人が直した最終のコミット（`commit`）・
  マージのコミット（`mergeCommit`）・人が直したか（`edited`）・要求要件・設計は sacty の版と人の版の本文（中身が同じなら本文は残さない）を
  残す。過去の作業履歴はそのまま読める。
- 画面に、人が直してマージしたこと・両方のコミット・GitHub の比較へのリンク・マージのコミットを出し、要求要件・設計の欄では人の版を
  承認済みとして出し、sacty の版も開けるようにする。

## 理由

- 最終レビューをやり直さないのは、人がマージした＝人が承認した、とするため（PR の本文）。
- 設計の全文を人の版にし、テスト観点は sacty のものを引き継ぐのは PO の判断。テスト観点を Markdown から読み直すのは壊れやすいため（PR の本文）。
- 両方の版を記録するのは、監査のため（PR の本文）。
- マージの時点のコミットから読むのは、レビューで、タスクブランチの先端を読むと、マージから確認までの間に積まれた未レビューの変更を
  承認済みの成果にしてしまい、台帳のマージのコミットと承認済みの本文も一致しなくなることがわかったため（レビューとその返信）。
- 取得の一時的な失敗で sacty の版を承認しないのは、人の版を取りこぼさないため（PR の本文）。
- 人の判断を待つ扱いをやめた理由そのものと、比べたほかの案は記録に無い。

## 影響

- 人が PR の中で直してマージすれば、そのまま次の工程・完了に進む。sacty の版と人の版の差は、台帳と画面で追える。
- 台帳に、両方の版の本文を最大 1MiB ずつ残す。
- 人が Markdown の中でテスト観点を直しても、最終レビューの基準には反映しない。
