# 監査の画面を、裏側のモックで先に作り、モックは環境変数で切り替える

- 日時: 2026-10-17 11:45 UTC
- ステータス: 採用
- 関係する PR・タスク: #134、PBI-124
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty の一番重要な機能として、完了したタスクの監査を作る（ステークホルダー）。目的はソフトウェアファクトリーの精度を上げること。
完了したタスクの過程（工程の判断から完了まで）から、差し戻し・指摘・試行錯誤の原因を探し、コンテキスト・スキル・リンター・テストなどの
改修を提案して、人が選んだものを PR にする。ステークホルダーは、まず裏側をモックにして画面で挙動を確かめ（PBI-124）、その後に
ロジックを作る（PBI-125）、と2つに分けることを選んだ。

## 決定

- 画面と API の形を先に決める。監査のデータの形（`TaskAudit`・`ProjectAudits`・`AuditDashboard`）と入力の検査は core に置き、
  画面とデーモンが共有する。デーモンの API は `AuditService` の形だけを使い、PBI-125 で実装を差し替える。
- モック（`MockAuditService`）は、環境変数 `SACTY_AUDIT_MOCK=1` で起動したときだけ使う。既定は監査の無い実装（`NoAuditService`）。
  モックのデータには `mock: true` を付け、画面は「モック」の印を出す。採用・却下・再開はデーモンのメモリにだけ持つ。
- モックは、プロジェクトの完了したタスクに場面を割り当てる。根拠は、そのタスクの作業履歴の行と実行に結び付ける。
- 監査の予算は、タスクの予算とは別に、config.yaml の `budget.default_per_audit_usd`（既定 1 米ドル）を既定の上限にする。
- 監査の結果は、プロジェクトをまたいで集約しない。ダッシュボードにはプロジェクトごとの件数だけを出す。
- 改修の提案の宛先は、対象リポジトリ・コンテキストの層（depth）・sacty の既定のコンテキストのどれか。ゴールガーディアンの
  プロンプトと既定のスキルは、sacty の既定のコンテキストとして宛先にする（ステークホルダーの「ガーディアンへ還元」）。
- 却下には理由を必須にする。レポートは Markdown で、日時は年を含めた UTC にする。

## 理由

- 画面を先に動かすと、監査で何が分かり、どう改修につなげるかを、ロジックを作る前に画面で判断できる（ステークホルダー）。
- モックを既定で有効にすると、利用者の画面に偽の監査が出る。main にマージしても既定の動きを変えないよう、明示的に切り替えたときだけにした。
- 環境変数にしたのは、config.yaml の項目にすると利用者向けの設定として残り、PBI-125 の後に消す手間が増えるため。
- 実際の完了したタスクに場面を割り当てると、タスクの詳細・監査の画面・ダッシュボードの行き来と、根拠から作業履歴への移動を、
  本物のタスクで確かめられる。
- 監査の予算をタスクの予算に含めると、完了したタスクの予算が後から増え、タスクの費用の意味が変わる（ステークホルダーは別の予算を選んだ）。
- プロジェクトをまたいで原因や提案の中身をまとめると、別の企業・組織のコンテキストの情報が混ざる（構想の「分離は仕組みで強制する」）。
- 却下の理由は以後の監査に渡し、同じ提案を繰り返さないために使う（ステークホルダー）。レポートはファイルとして後で読むので、画面の
  短い日時（年なし）にしない。

## 影響

- サイドメニューに「監査」を足した（プロジェクトの画面だけ。`/projects/current/audit` は表示しているプロジェクトの監査へ移す）。
- PBI-125 では、`AuditService` の実装を作業履歴の記録から作るものに差し替え、モックの切り替えは残してよい。
