## 背景

プロジェクトの設定は、#8 で決めた「GitHub Issue の取り込み元」（単位・対象・ラベル）と「リポジトリの設定」（ベースブランチ・テストのコマンド・PR を作るか）に分かれていた。#27 で、画面で作るタスクの対象をリポジトリの設定から選ぶようにし、#29 で「PRを作る」を「PR作成許可」にした。動作確認で、取り込み元とリポジトリの設定が分かれているのは想定と違い、プロジェクトに設定した Org もしくはリポジトリに対してタスクを作れ、Issue や PR をトリアージしてタスク化できるものだ、というフィードバックがあった。

## 決定

- プロジェクトには「対象」（`{scope: "org" | "repo", target}`）の一覧だけを登録する。取り込み元・リポジトリの設定・PR作成許可は無くす。同じ Org・リポジトリは1つのプロジェクトにだけ置けること、範囲が狭いほうが優先する規則は引き継ぐ。
- エクスポートの形式の版を 2 にし、版 1 は読まない（移行の手段は設けない）。
- 画面でタスクを作るときは、対象の中のリポジトリだけを受け付ける。対象がリポジトリ1つだけなら、選ばなくてもそれが対象になる。Org の対象は、プロジェクトの gh のアカウントで読んだその Org（Org でなければそのユーザー）のリポジトリから選ぶ。アーカイブしたものと、ほかのプロジェクトがリポジトリ単位で担当するものは除く。
- 個人のアカウントを対象にしたときは、公開のリポジトリに加えて、トークンで読めるリポジトリのうちその持ち主のものも候補にする。候補が無くても、対象があればリポジトリ名を入力でき、対象の範囲かはデーモンが確かめる。
- PR作成の工程は常に PR を作る。対象に登録すると PR が作られることを、注意書きとして書く。
- 取り込みのラベルは sacty 全体の設定にする（次のタスクで対応）。それまでは、すべての対象で `sacty` に固定する。

## 理由

- 取り込み元とリポジトリの設定が分かれているのは想定と違う、という動作確認のフィードバックによる（本文）。
- 移行の手段を設けない理由は、この PR の記録に無い。
- 個人のアカウントの非公開のリポジトリを候補に含めるのは、`/users/{owner}/repos` はトークンを付けても公開のリポジトリしか返さず、非公開のリポジトリが候補から漏れることがレビューで指摘されたため（レビュー・コミット）。

## 影響

- 以前のプロジェクトの定義は読み込めるが、対象が空になるので、設定画面で対象を登録し直す必要がある。
- 対象に登録したリポジトリでは、PR作成の工程で必ず PR が作られる。
- 候補を返す API `GET /api/projects/:id/repositories` を足した。読めなかった Org は、トークンを伏せた理由を返す。
