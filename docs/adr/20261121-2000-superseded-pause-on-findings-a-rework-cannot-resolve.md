# セキュリティ対応の変更行数の上限をやめ、レビューが直しでは解消できないと印を付けた指摘で止めて、人の判断を待つ

- 日時: 2026-11-21 20:00 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: PBI-452
- 置き換え元: なし
- 置き換え先: [同じ原因の要修正が続く場合に人の判断を求める](20261123-0007-superseded-repeated-cause-decision.md)（繰り返し時の停止と停止条件）

## 背景

セキュリティ対応には、変えた行の数の上限（300 行）があった。
PBI-438 では、依頼の受け入れ条件を満たすと必ず上限を超え、レビューが 5 回続けて行数を要修正にした。
3 回目以降、レビューは「方式を変えても収まらない。人が判断する」と結論したが、判定は「修正が必要」のままで、親は毎回直しに入り、往復が止まらなかった。

## 決定

利用者の決定（2026-11-21）：

- 変えた行の数の上限をやめる。数え方・外し方の仕組みは作らない。範囲の外のファイルの検査と、最小限の変更かの確かめ（`SEC-MIN`）は残す。
- PR のレビューが、要修正に「直しでは解消できず、人の判断が要る」と印（判定のブロックの `needs_decision`）を付けた回は、直しに入らず、承認待ちのまま一時停止する。PR のコメント（人の了承か方針）か、画面・MCP の再開で再開する。
- 止めるのは、レビューの子タスクがあるすべてのタスク。「セキュリティ対応」と判定する基準は変えない。
- 人の判断は、止めた回ごとに指摘と組みで記録し、以後のレビューに渡す。同じ先頭では、印で止め直さない。
- 既定のレビューの観点 C-17 の制約の列挙から、行数の上限を外す（上限が無くなったため）。

## 理由

- 行数は、タスクごとに合う大きさが違う。数で縛ると、受け入れ条件を満たせない往復を生む。
- 直しでは解消できないと根拠で示せる指摘は、直しを重ねても解消しない。人の判断を待つほうが、費用も時間も小さい。
- 採らなかった案：止めずに、レビューの判定を「提案あり」に下げる。要修正の重みを、往復を止めるために曲げることになる。
- 採らなかった案：差し戻しの記録と同じ追記で止める。戻し先が設計の回で、再開・マージの見張りが成り立たない。承認待ちのまま止める案にした。

## 影響

- 前の版に戻せない記録は、理由 `needs_decision` の `TaskPaused` だけ（前の版は `PauseReason` を読めない）。一度記録したら戻せない。
  違反の記録（`lines` を持たず、`max` に固定で 300）と、足した欄（`needsDecision`・`items[].by`・`TaskPaused.commit`・`ReworkStoppedByMerge.decision`）は、前の版が読める。
- 切り戻す前の確かめ方：作業履歴の `activity` の表に、`type` が `TaskPaused` で `payload` の `reason` が `needs_decision` の行が無いこと。
- 読める版を先に出す 2 段の公開はしない。止まるのは印の付いた回だけで、印が無ければ戻せる。分けると、依頼の往復を止める振る舞いが 1 版遅れる。
- 版を入れた時点で始まっていたレビューの子タスクの回は、印を書かないので、今までどおり直しに入る。以前の版が記録した行数の違反は、読み込み、行数を表示せず、範囲の外のファイルが無ければ違反なしとして扱う。
- 既定のレビューの観点 C-17 の例から、行数の上限を外す。
