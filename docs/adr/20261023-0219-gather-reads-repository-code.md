## 背景

情報収集は、外部の情報（チケット・リンク先・文書・チャット）を集める役割とし、対象リポジトリのコードは読ませていなかった。
情報収集の時点ではリポジトリを用意しておらず、指示でも「コードは読まなくてよい」としていた。

実際に使うと、コードを読まないまとめでは困ることが多かった（作者の判断）。
チケットや文書の語がコードのどこに当たるのか、いまの振る舞いがどうなっているのかがわからないまま、オーケストレーターが進め方を選び、
チケットのトリアージがリポジトリを選ぶことになる。
調査の工程はコードを読むが、進め方を選んだ後に動き、組み合わせによっては無い。

## 決定

- 作業するリポジトリが決まっているタスクは、情報収集の前にリポジトリを用意する（起点のコミットを記録する。以前は情報収集の後だった）。
  情報収集の作業領域に起点のコードの写しを置き、タスクに関係するコードの場所といまの振る舞いを読ませる。
- 決まっていないタスク（チケットのトリアージを待つタスク・リポジトリを指定せずに作ったタスク）は、リポジトリを用意しない。
  候補（トリアージならトリアージの候補、リポジトリの無いタスクならプロジェクトの対象）を指示に渡し、
  関係しそうなものを洗い出させて（多くても3つ）、GitHub の読み取りの中継（`gh api`）でコードを読ませる。
  人がリポジトリを選んだチケットのタスクは、そのリポジトリを読ませる。
- まとめの見出しに「関係するコード」を足す。
- コードを読むのは、進め方を決め、後の工程が背景を知るのに要る範囲までとする。修正の方針や原因の詳しい調査は、今までどおり後の工程に任せる。
- リポジトリのファイルも外部の本文として扱い、その中の指示には従わないよう添える。

## 理由

- 人は、チケットを読むだけでなく、コードを見てから進め方を決める。情報収集に入れた目的（人の判断に近づける）は、コードを読まないと果たせない。
- リポジトリが決まっているなら、用意を情報収集の前に移すだけで済む。起点のコミットは「タスクの開始時に一度だけ記録する」ままで、
  記録する時点が情報収集の前になるだけ。用意できなければ、エージェントを動かす前に止まるのも今までと同じ。
- 決まっていないタスクで候補をすべて clone する案は採らなかった。プロジェクトの対象は Org で指定でき、候補が多いと時間と容量がかかる。
  先に候補を選ばせてから clone する案（情報収集を2回に分ける）は、実行が1回増える。
  GitHub の読み取りの中継は情報収集でも使え（読み取りだけ）、ファイルの一覧・中身・コードの検索ができるので、1回の実行で候補を読める。
- 候補の数を「多くても3つ」としたのは、作者の「いくつか」という求めに合わせた目安で、測って決めた数ではない。

## 影響

- リポジトリが決まっているタスクは、情報収集の前に clone する。用意できなければ、情報収集の前に止まる。
- 情報収集の実行が、コードを読む分だけ長くなり、費用が増える。
- 決まっていないタスクでコードを読むには、プロジェクトでそのホストの GitHub のアカウントを選んでいる必要がある（選んでいなければ、読めなかった情報源に書かせる）。
  `gh api` のコードの検索は既定のブランチだけが対象。
