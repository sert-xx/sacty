# サービスのビルドに共有のタグを付けさせず、エージェントのイメージを ID に確定させる

- 日時: 2026-10-18 04:30 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-130
- 置き換え元: なし
- 置き換え先: なし

## 背景

docker compose のサービス（PBI-47）の検査は、ビルドの元の場所や特権は確かめていたが、サービスの `image`・`pull_policy`・`build.tags` を
見ていなかった。リポジトリの Compose に、エージェントと同じイメージ名（既定は `sacty-agent:0.1.0`）と `pull_policy: build` を書くと、
サービスをビルドしたときにホストの共有のタグが上書きされる。後で動く別のタスク・工程のエージェントは、そのタグのまま認証ファイルを
持って起動するので、リポジトリの作者がタスクの境界を越えて認証を奪えた（Codex Security の指摘）。

## 決定

- `build` を持つサービスからは `image` と `build.tags` を外し、`pull_policy: build` にする。compose が実行ごとのプロジェクトの名前
  （`<プロジェクト>-<サービス>`）を付け、止めるときに `down --rmi local` で消す。拒否はしない（`build` と `image` を並べて書く Compose は
  よくあり、拒否すると既存のリポジトリで動かなくなるため）。
- ビルドの結果を実行の外（ホストのディレクトリ・レジストリ）へ書き出す `build.cache_to` は拒否する。
- サービスを使う工程では、起動する前にエージェントのイメージを `docker image inspect` でイメージ ID に確定させ、その ID で実行する。

## 検討した案

- **エージェントのイメージ名と同じ `image` だけを拒否する**：エージェントの名前（既定・設定・工程ごと）をすべて検査に渡す必要があり、
  後でイメージの種類を足したときに漏れる。ビルドのタグを実行の名前に閉じれば、どの名前でも書き換えられない。
- **`build` と `image` の併記を拒否する**：確実だが、既存のリポジトリの Compose がそのままでは動かない。
- **イメージ ID の確定だけ**：同じ実行の中では効くが、書き換えられたタグは残り、後で始まる別のタスクは書き換えられたイメージを確定させて
  しまう。タスクの境界を守るのは、ビルドのタグを閉じるほうである。

## 結果

- リポジトリの Compose がどう書かれていても、サービスのビルドがホストのタグを書き換えない。
- ビルドしないサービス（`image` だけ。例 `postgres:16`）は今までどおり使える。取りに行くイメージはレジストリのものなので、ここでは制限しない。
- 毎回ビルドするので、同じイメージを使い回していたリポジトリでは起動が遅くなることがある（ビルドのキャッシュは効く）。
- ビルドしたイメージを、別のサービスが `image` の名前で参照していた Compose は動かなくなる（その名前のイメージができないため）。
