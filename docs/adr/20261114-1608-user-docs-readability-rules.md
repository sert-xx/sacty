# ユーザードキュメントに読みやすさの規則を足し、目次を目的ごとに分け、長いページの節を利用の流れの順に並べる

- 日時: 2026-11-14 16:08 UTC
- ステータス: 採用
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: なし

## 背景

ユーザードキュメント（`docs/user/`）は、機能を足す PR が、その機能の説明を書き足して育ってきた。
書いてあることは実装と一致しているが、利用者にとっては読みにくくなっていた。

- 文と節
  - 節の最初から細かい条件の箇条書きが始まり、何の節か・いつ読む節かが分からない所があった。
  - 利用者がすること（手順）が、箇条書きや段落に埋もれている所があった。
  - 条件を1文に並べた長い文や、種類の違う話（ふつうの場合・例外・内部の動き・以前の版の話）が混ざった長い箇条書きがあった。
  - 「これまでどおり」「このリリースより前」のような、書き足したときの経緯の言い回しが残っていた。
- ページの構成
  - 「タスクを進める」（`tasks.md`）は約 1,100 行あり、節が書き足した順に並んでいた。
    たとえば、PR での承認の説明より前に、テストの仕組みが無いリポジトリの説明があった。
  - 更新の前のバックアップの案内が `tasks.md` の最後にあり、更新の手順（`getting-started.md`）を読む人には見えなかった。
  - 目次（`docs/user/README.md`）は、ページを番号で1列に並べ、説明は節の名前の列挙だった。
    デスクトップ版のページだけが、番号の外にあった。
- 規則
  - 書き方の規則（`docs/README.md`）は、文体・事実の照合・置き場所を決めていた。
    読みやすさについては、「利用者が目的から引けるように分ける」「利用者がすること（手順）と、その結果を書く」だけだった。

## 決定

- 読みやすさの規則を、`docs/README.md` の「書き方の規則」に足す。
  - 節の最初に、その節で分かること・できることを書く。
  - 利用者がすることは、番号付きの手順にする。結果・例外・細かい条件は、その後に書く。
  - 1文に1つのことを書く。3つ以上の条件・項目の列挙は、箇条書きか表にする。表のセルには短い文を書く。
  - 機能を足すときは、箇条書きの最後に足すだけにせず、節の流れのどこに入るかを決めて書く。
  - 今の振る舞いだけを書き、経緯の言い回しを使わない。以前の版から使っている人への案内は、それと分かる節や段落にまとめる。
  - ほかの節は、位置（「下の〜」）ではなく、リンクで指す。
  - 長いページは、節を利用の流れの順に並べ、最初に「このページの内容」（したいこと → 読む節）を置く。
- 目次は、目的ごとの見出し（はじめる・タスクを任せる・設定する・調べる）に分けて、読む順に並べる。
  説明は、そのページで何をするか・何が分かるかを書く。
- `tasks.md` は、ページを分けずに、節を利用の流れの順に並べ替える。
  - 順序は、作る・探す・見る → sacty が自分で進める部分 → 承認・差し戻し → 進んでいるタスクへの操作 → 依頼の種類ごとの進み方 → 以前の版のタスク。
  - 見出しの文言は変えない（ほかのページと ADR が、見出しのアンカーへリンクしている）。
- 更新の前のバックアップの節は、`getting-started.md` の「sacty を更新する」の下へ移し、更新の手順からリンクする。
- 今あるページを、この規則で直す。事実（設定の名前・既定値・条件・手順）は変えない。

## 理由

- 規則を足すのは、今あるページを直すだけでは、次に機能を足す PR で同じ書き足しが起きるからである。
  ユーザードキュメントを直す人とエージェントは、`docs/README.md` を読んでから書く（スキル `sacty-docs`）。
- `tasks.md` を分けなかった理由は、次のとおり。
  - 分ける案（タスクを作る・承認する・依頼の種類ごとの進み方、の3ページなど）も比べた。
    分けると、ほかのページと ADR からの約 40 のリンクの行き先のページが変わり、どこで分けるかの判断も要る。
  - 節の並べ替えは、見出しの文言が同じならリンクが切れない。
    まず、順序と「このページの内容」で引けるようにし、分けるかどうかは、その結果を見てから決める。
- 目次を番号の1列から目的ごとの見出しにしたのは、利用者が目的（設定したい・止まって困っている）からページを引くためである。
  読む順は、見出しの順と、見出しの中の順で保つ。
- バックアップの節を移したのは、更新する人が読むのは更新の手順だからである。
- 文を直すだけで、順序と目次を変えない案は、採らなかった。引きにくさが残る。

## 影響

- ユーザードキュメントを足す・直す PR は、読みやすさの規則に従う。
  規則は `tests/docs` では確かめられない（テストは、リンク・日英の形・目次にあることを確かめる）ので、レビューで見る。
- `tasks.md` は長いままである。分けるときは、見出しのアンカーへのリンク（ユーザードキュメント・ADR）を直す。
- 節を並べ替えたので、ページの中の位置での参照（「下の〜」）は、リンクに直した。
  節を足すときは、利用の流れのどこに入るかを決め、「このページの内容」の表にも足す。
- 目次にページを足すときは、目的ごとの見出しのどれに入るかを決める（日英の両方）。
- 日本語の版と英語の版は、これまでと同じく、同じ内容・同じ形に保つ（[docs の入口](../README.md)の「英語の版」）。
