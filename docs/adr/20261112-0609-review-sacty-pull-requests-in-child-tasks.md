## 背景

sacty は、作る PR（要求要件・設計の PR と実装の PR）にレビュー用のラベルを付け、PR のレビューの取り込みで、作ったタスクとは別の「PR のレビューだけのタスク」にしていた。
この形には、次の問題があった（ステークホルダーの指摘）。

- レビューが始まるかが、取り込みの設定（ラベル・トリアージの On/Off）と取り込みの間隔に左右される。
- 元のタスクとレビューのタスクのつながりが PR の番号頼みで、元のタスクの画面からたどれない。
- 指摘を直して PR を更新しても、レビューのタスクは再レビューしない（人が「再レビュー」を押す必要があった）。指摘なしになるまで回すには、人の操作が要る。

ステークホルダーの要望は、PR を作った工程の子タスクとしてレビューを足し、レビューの指摘と修正を指摘なしになるまで繰り返すこと。
指摘なしの後は、今までどおり人が PR のマージで承認する。`[提案]` だけの回も直させ、回数の上限は設けず予算の上限で止める（2026-11-12 に人が決めた）。

## 決定

- sacty は、作る PR ごとに、その PR をレビューする子タスク（PR のレビューだけのタスク。`source.review: sacty`）を、取り込みを通さずに直接作る。
  子タスクは `TaskCreated` の `reviewOf` に親と PR を作った工程を持ち、親には `ReviewTaskCreated` を記録する。1つの PR に1つ。
  作る時点は、今までラベルを付けていた時点（要求要件・設計の PR は作った直後、実装の PR はドラフトを外したとき）。
- PR の確認（60秒ごと）で、親が承認待ちで、子タスクがレビューを終えていて、レビューした先頭が親の今のコミットと違えば、sacty が子タスクを再レビューに戻す（`ReviewRestarted` の `reason: updated`）。
  同じコミットでは1回だけ戻す。
- 子タスクの指摘は、今までどおり PR の指摘の取り込みで親に届け、親が直す（戻し先の判断も今のまま）。指摘なしの回は届けない。
- sacty の PR にはラベルを付けない。sacty が作った PR は、ラベル・レビューの依頼のどれでも取り込まない。
  レビュー用のラベルは、sacty が作っていない PR の取り込みにだけ使う。
- 子タスクは分割の子タスク（`parent`）とは別の関係にし、分割の待ち・統合レビューに混ぜない。

## 理由

- 子タスクを直接作れば、設定や取り込みの間隔に関わらず、PR を作った時点でレビューが始まり、親子の関係を作業履歴に残せる。
- 再レビューの合図を「親が承認待ちに戻り、PR の先頭が進んだ」にしたのは、直している途中（承認待ちでない）に重ねてレビューせず、直し終えた版だけをレビューするため。
  親のコミットと GitHub の先頭がずれる（ほかで push された）ときに、毎回戻し続けないよう、同じコミットでは1回にした。
- 既存のレビューだけのタスク（指示・判定・投稿・指摘の取り込み）をそのまま使い、作り方と再レビューの合図だけを変えた。新しいレビューの仕組みを作るより、今の振る舞いを保ちやすい。
- 分割の `parent` を使わなかったのは、分割の子タスクは「すべて片付いたら親が次へ進む」「統合レビューの対象」という意味を持ち、レビューの子タスクに当てはまらないため。
- ラベルを付け続ける案（取り込みと子タスクを併用）は、二重にレビューする恐れがあり、採らなかった。

## 影響

- レビュー用のラベルを設定していなくても、sacty の PR はレビューされる。sacty の PR に人がラベルを付けても、取り込まれない。
- 子タスクの費用は子タスクの予算に数える。親と子のそれぞれの予算で繰り返しが止まる。
- 以前の版の記録（ラベルの予定・付けた記録・ラベルから取り込んだレビューのタスク）は読める。終わっていないレビューのタスクがある PR には、子タスクを作らない。
