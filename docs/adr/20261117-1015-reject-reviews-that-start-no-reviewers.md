# 観点ごとの担当を 1 件も起動しなかった PR のレビューは、採らずにやり直させ、続いたら止める

- 日時: 2026-11-17 10:15 UTC
- ステータス: 採用
- 関係する PR・タスク: #420、PBI-379
- 置き換え元: なし
- 置き換え先: なし

## 背景

PR のレビュー（工程 `review`）は、既定のスキル `review-dispatch` に従い、観点ごとの担当（サブエージェント）を起動して結果を集める決まりになっている（必須の観点は、対象の大小にかかわらず全部起動する）。

実行の記録を調べると、一部のエージェントで動いたレビューが、この決まりを守っていなかった。

- スキルの `SKILL.md` を読んだ後、流れの資料（`references/pr-review.md`）を開かず、指示に入っている差分と周りのコードを自分で数回読んで、本文と判定を書いて終える。
- 本文には「担当に分けずに自分で見た」と正直に書いている。つまり、決まりを知らないのではなく、省いている。
- 担当を起動した回と起動しなかった回で、使えるツール・担当の定義・モデル・指示の文に差は無かった。差分の大きさでも説明できなかった。
- 担当を起動しなかったレビューは、「修正が必要」の判定を 1 回も出していなかった。担当に分けたレビューを 1 回も受けずにマージされた PR が出た。

なぜ資料を開かずに終えるのかは、分からない（その実行の考えた過程は、記録に残っていない）。
見立ては、次の 2 つ。

- 指示が、進める順と省けないことを言っていなかった。指示は出力の形を詳しく決め、差分をそのまま渡している。スキルを使うことは 1 行で、「観点をどう見たかを 1 行で書く」という行が、担当に分けない見方も選べるように読める。
- 省いても、何も起きなかった。sacty は、担当を起動したかを見ていなかった。

人の決定は、次のとおり。

- 担当を起動しなかった回は、起動するまでやり直させる。やり直しは 3 回まで。それでも起動しなければ、タスクを一時停止して人に知らせる。
- 切り替え先のエージェントの設定は変えない。指示とやり直しで、担当を起動させる。

## 決定

1. 指示で、進める順（`SKILL.md` の後に、流れの資料と観点カタログを読む。起動表を作って担当を起動する。結果が揃ってから本文を書く）と、担当を起動する前に自分で指摘を書き始めないこと、対象の大小・再レビューかどうかによらず起動を省かないことを伝える。エージェントの種類によらず、同じ文を渡す。
2. 既定のスキルの `SKILL.md` の、役割の表のすぐ後に、次に読む資料を名指しし、親が担当を起動せずに自分で見て終えるのはスキルに従ったレビューではないと書く。特定のエージェントの製品に寄せた記述は足さない。
3. sacty が、レビューの実行ごとに、起動した担当の数を、写したエージェントのセッションのファイルから数えて、実行の記録（`AgentRunCompleted` の `reviewDispatch`）に残す。数え方は、エージェントの種類ごとに決める。担当のセッションのファイルが残る種類では、起動のツールの名前に頼らず、そのファイルを数える。数えるのは、担当のセッションの名前の形（`agent-<16進の ID>.jsonl`）のファイルだけにする（担当でない内部の記録が同じ場所に置かれても、担当として数えないため。手元の実行の記録では、この場所のファイルは、この形と `journal.jsonl` だけだった）。数えられないとき（セッションのファイルが無い・親のセッションが無いなど）は「分からない」とし、やり直しにしない。
4. 担当を起動する手段がその実行にあったと確かめられ、起動が 0 件だった実行は、判定と本文を採らず、PR に投稿しない。失敗として記録し、止めずに、前の実行が担当を起動しなかったことを指示に足して、やり直す。やり直しは 3 回まで。その次も 0 件なら、理由を付けて一時停止する。人が再開すると、回数を数え直して、もう一度試す。
5. 手段があったと確かめられない実行（スキルの逐次モード）は、0 件でも今までどおり通す。
6. 投稿するレビューの本文の最後と、タスクの画面に、レビューしたエージェント・起動した担当の数・切り替え先で実行したことを出す。PR は公開されうるので、本文に出すのは、エージェントの種類（製品の名前）とモデルだけにする。利用者が付けた設定の名前（エージェントの ID。認証の方式や組織の名前を含みうる）は、タスクの画面にだけ出す。
7. sacty が見るのは、起動が 0 件かどうかだけにする。担当の中身・質・必須の観点が揃っているかは、判定しない。

## 理由

- 指示とスキルの文だけでは、守られる保証が無い。これまでも、スキルには「必須の観点は全部起動する」と書いてあった。省いた回を見分けて採らないことを、sacty の側に持たせる。
- 省いた回を「読み取れませんでした」のように本文に書いて投稿する案は採らなかった。担当に分けていないレビューが PR に残り、「指摘なし」として読まれるのを防げない。
- エージェントの種類ごとに指示を分ける案は採らなかった。足す文はスキルの決まりと同じ向きで、担当を起動しているエージェントの振る舞いを変えない。種類ごとの分岐は、指示の組み立てを複雑にする。
- 必須の観点が揃っているかまで確かめる案は採らなかった。担当の起動の記録から、どの観点の担当かを確かに読み取る方法が、エージェントの種類ごとに要る。仕組みが大きくなり、穴への対応が続く。0 件かどうかは、どの種類でも数えるだけで分かる。
- 起動が 1 件だけのレビュー（数だけ合わせたもの）は、この仕組みでは見分けられない。本文と画面に担当の数を出すので、人が気づける。
- 数えられないときと、手段を確かめられないときに通すのは、担当を起動する手段が無い環境と、数え方を知らない種類のエージェントで、レビューが止まり続けるのを避けるため。

## 影響

- 担当を起動しなかった実行の費用は、失敗の記録として、タスクの費用に入る。やり直しのぶん、費用が増える（上限は、最初の実行とやり直し 3 回の 4 回ぶん）。
- 担当を起動しないレビューが続くと、レビューのタスクが止まり、PR にも止まったことのコメントが付く（レビューが止まったときの知らせと同じ仕組み）。
- エージェントの、セッションのファイルの形（担当の起動の記録のされ方）が変わると、正しく数えられなくなる。変わり方によって、振る舞いが違う。
  - 親のセッションの場所が変わって見つからないときは、「分からない」になり、やり直しは働かない（本文と画面には、確かめられなかったと出る）。
  - 親のセッションは読めて、担当の起動だけが今の形で残らなくなったとき（担当のセッションのファイルの名前の形が変わったときも）は、担当を起動した実行も 0 件と数える。手段があったと確かめられれば、正しいレビューを採らずにやり直し、4 回ぶんの費用を使って止まる。エージェントの版を上げたときは、担当の数が出ているかを確かめる。
- スキルが担当を起動しないと決めている場合のうち、対象を読めないとき（流れの資料の「完了できないとき」。「レビューを完了できませんでした」と書く）も、手段があって 0 件なので、sacty は採らずにやり直し、続けば止める。このとき、一時停止の知らせに出る理由は「担当を起動しないレビューが続いた」で、読めなかったという実際の理由は出ない（採らなかった実行の出力は、実行のログに残る）。
- 担当を起動しなかったために採らなかった実行は、`AgentRunFailed` に `reviewDispatch` を付けて記録する（エージェントの実行は完了している）。この記録を読む側の扱いは、次のとおりに決めた。
  - 工程ごとの費用の表：失敗と分けて「使わなかった」と出す（結果の種類を 1 つ足すだけで済むため）。
  - エラーレポート：分類は、ほかの `AgentRunFailed` と同じ `error` のままにする。理由の文言（`review.notDispatched`・`review.notDispatchedPaused`）で見分けられ、分類を足すと、エラーレポートの形と分析の指示まで変わるため。
  - 監査のやり直しの数：ほかの `AgentRunFailed` と同じに数える。実際に、実行のやり直しだから。
  - 作業履歴の文・通知：実行の失敗の文に、理由の文言が出る。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の PR のレビューの節と、[コンテキスト](../spec/context.md) の既定のスキルの節にある。
