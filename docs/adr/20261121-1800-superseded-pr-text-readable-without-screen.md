# PR の本文・コメントを、画面を開けないレビュアーにも読める形にし、製品名を「Sacty」にそろえる

- 日時: 2026-11-21 18:00 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: PBI-450
- 置き換え元: [実装の PR の本文を、結論を冒頭に置き、要求要件・設計は要点とリンクにし、表のセルを短くする](20261101-1400-superseded-pr-body-conclusion-first.md)（全文の置き場所を「タスクの画面」とした部分）
- 置き換え先: [PR の説明とコメントを、Sacty を使っていない人が読んで判断できる情報だけにする](20261121-2200-pr-description-and-comments-for-decision-only.md)（決定 1 の画面へのリンク、決定 3 のレビューの進め方と AI のレビューの状況、本文のタスク ID の行）

## 背景

GitHub の側だけで PR を読む人は、依頼した人のマシンで動く Sacty の画面を開けない。
それなのに、Sacty が PR に投稿する文には、画面を開かないと読めない案内（「承認の画面で確かめてください」「続きはタスクの画面で」など）と、`http://127.0.0.1:4700/tasks/...` へのリンクが残っていた。
[実装の PR の本文を、結論を冒頭に置く ADR](20261101-1400-superseded-pr-body-conclusion-first.md) は、承認済みの要求要件の全文の場所を「マージで承認した PR か、タスクの画面」とし、レビューする人が全文を見る場所の 1 つに画面を数えていた。

結論には、変更・最後の直しのほかに、仕組みの説明の長い括弧書きが 2 行あった。
人が読む文の製品名も、「sacty のタスク」「Sacty：…」と混じっていた。
実装の PR に、本文が空のレビューが並ぶ件は、原因を確かめていなかった。

## 決定

PR の本文・コメントは、依頼した人のマシンでしか見られない情報に頼らない。

1. タスクの画面へのリンクは、「この PR を作ったタスク」の意味と、依頼した人が画面で行う操作の案内にだけ使う。画面の URL（`SACTY_WEB_URL`）のホストが `127.0.0.1`・`localhost`・`[::1]` のとき（と URL として読めないとき）は、リンクの文の直後に「タスクの画面は、依頼した人のマシンでだけ開けます。」を添える。
2. 画面に頼っていた中身は、PR の中で完結させる。
   - AI のレビューの状況は、最新の状況を「この PR のレビューの欄」で確かめるように案内する。
   - マージで承認した PR が無いときの承認済みの要求要件（再現）の全文は、本文の `<details>` に載せる。全文を入れると本文が上限を超えるときは、全文だけを Sacty のコメント（目印 `<!-- sacty-basis:<タスク ID> -->`）に分け、本文にリンクを置く。
   - 長さで省いた続き（人が確かめること・所見・子タスクの内容）は、本文の `<details>`「省いた続き」に載せる。本文の全体を上限で切るときは、切った文字数と GitHub の上限を書く。
   - Issue を作れなかった理由は、知らせの中に、伏せた 1 行で書く。
3. 結論には、変更・最後の直しと、省けない行（不合格のまま進めた記録・人が確かめること）だけを置く。レビューの進め方と AI のレビューの状況は、結論の外の節に、1 項目 1 文で置く。
4. 人が読む文の製品名は「Sacty」、コマンド・識別子・機械が読む目印は `sacty` のままにする。
5. 本文が空のレビューは、GitHub が行へのコメントへの返信 1 件ごとに作るので、投稿のしかたは変えず、仕様書に原因と確かめた範囲を書く。

## 理由

- 画面を開けない人にとって、「画面で確かめてください」は何も伝えない。レビュアーが判断に要る受け入れ条件は、PR の側に写すのが確実である。
- 全文を本文に重ねると、本文が上限（65,000 文字）に近づく。上限を超えるときだけコメントに分けると、通常の本文は短いまま、上限を超えても PR の中で全部を読める。
- 省いた続きの全文を本文の折りたたみに置くと、結論と footer（省かれない部分）は上限のある行だけで済み、承認の案内と `sacty task <ID>` が切れない。
- 分けたコメントに目印を付けて取り込みの見分けに加えるのは、足さないと、全文が人の指摘として取り込まれるため。
- 本文が空のレビュー：確かめたのは REST の `/replies`（PR #470・#480・#499・#501 の返信のすべてに、返信ごとに別のレビュー ID が付いていた）。GraphQL の `addPullRequestReviewThreadReply` は、`pullRequestReviewId` を省いたときに空のレビューができるか、書き込みができないので確かめていない。保留中のレビューにまとめる方式は、同じ PR で 1 人に 1 件しか持てず、人と同じアカウントで投稿する Sacty の返信が、人が画面で書きかけたレビューに混ざるので採らない。
- 比べた案：画面へのリンクをすべて外す案は、依頼した人にとって、再開・差し戻しの案内が無くなるので採らなかった。注釈を添えれば、依頼した人にも、そうでない人にも使える。

## 影響

- レビューする人は、リンクの PR か、本文の折りたたみか、全文のコメントで、承認済みの要求要件の全文を PR の中で読む。
- 本文を更新するたびに全文のコメントを書き換えるので、PR の通知を見ている人に、本文の更新とは別の通知が届くことがある。
- 結論から「レビューの進め方」が移るので、開いている PR で人が結論を直していると、次の更新で 3 方向のマージが重なり、オーケストレーターにまとめさせる費用がかかることがある。目印と `keep` の作りは変えないので、古い形の本文を祖先にしたマージは動く。
- レビュアーの PR の会話の欄には、返信の数だけ空のレビューが並び続ける。GraphQL で避けられると分かったときは、投稿のしかたを直す。
