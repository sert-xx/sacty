# マージの後の監視を工程にし、するかどうかを対象のリポジトリのスキルの有無でタスクごとに決め、どこまで見るかはスキルに任せる

- 日時: 2026-10-16 06:33 UTC
- ステータス: 採用
- 関係する PR・タスク: #126、PBI-116
- 置き換え元: [sacty のタスクの実装の PR がマージされたら、CI/CD とデプロイ後のアプリを見届け、失敗したら修正のタスクを登録する](20261014-1439-superseded-deployment-watch-after-merge.md)
- 置き換え先: なし

## 背景

マージの後の監視（CI/CD を待つ → デプロイの確認のスキルでアプリを確かめる → 失敗したら修正のタスクを登録する）は、プロジェクトの
設定 `deploymentWatch` で On・Off していた。監視は工程ではなく、実装の PR のマージで完了したタスクの裏で動いていた。

- プロジェクトごとに On・Off を設定する手間がある。リポジトリによって、監視が要るか（デプロイしているか・確かめる手段があるか）が違う。
- 監視の途中のタスクが「完了」に見え、終わっていないことを追えない。一時停止・中止・再起動の扱いも、ほかの工程と違っていた。
- スキルが無くても CI/CD だけは見ていた。
- 何をどこまで確かめるか（CI/CD だけか、デプロイ後のアプリまでか）は、リポジトリによって違う。デプロイしていないリポジトリでも、
  CI/CD の確認は要ることがある。

まだ本番で使っていないので、互換の層は作らない。ただし、作業履歴（台帳）は書き換えない。

## 決定

### 工程にする

- 工程 `deployment`（画面の名前は「マージの後の監視」・After-merge watch）を足し、実装を含む組み合わせ（`standard`・`skip-design`・
  `bugfix`）の最後（実装の後）に置く。タスク分割の親は持たない（子タスクが、それぞれの実装の PR で持つ）。
- 人の承認は無い。実装の PR のマージ（実装の承認）でこの工程へ進み、今の監視（CI/CD を待つ → スキルに従った確認 → 失敗したら
  修正のタスクの登録）を行う。監視が終わったら（通った・失敗して修正のタスクを決めた・飛ばした・時間切れ）工程を終え、タスクを
  完了にする。失敗しても、元のタスクは止めない（修正のタスクに引き継ぐ）。
- 監視の間は、タスクを完了にしない（待機のまま、終わっていないタスクとして出す）。

### するかどうか

- プロジェクトの設定 `deploymentWatch` は無くす。画面・定義・API・保存の検証・エクスポート・インポートから外す。以前の書き出しの
  ファイルにあっても、読み込みを止めずに捨てる（保存した定義に残っていても読まない）。
- 工程を選ぶとき（オーケストレーターが組み合わせを選んだ直後、`StepsChosen` の前）に、sacty が起点のコミットでデプロイの確認の
  スキル `deployment-observer`（今の置き場所）を探す。あれば工程に入れ（パスを記録）、無い・使えない・探せないなら理由を付けて
  工程を飛ばす（`skip`）。飛ばしたら CI/CD も見ない。
- 組み合わせを選ぶ AI には決めさせない。スキルの有無はファイルで決まり、AI に判断させると結果がぶれるため。組み合わせの説明には、
  スキルがあるときだけ sacty が決めることを書く。
- 決めた後のスキルの増減：
  - 実装の PR がスキルを足しても、このタスクでは見ない（工程を選んだときに決めたことを変えない。次のタスクから見る）。
  - 実装の PR がスキルを消したら、工程は続け、CI/CD を見て、マージのコミットにスキルが無ければスキルに従った確認を飛ばして通ったにする
    （今の「スキルが無い」の扱い）。消したことは、CI/CD の結果の理由でわかる。
- 実装の PR をマージせずに実装を承認した（変更が無い）なら、見るマージが無いので工程を飛ばす。

### どこまで見るかはスキルに任せる

- 工程の中で、CI/CD の確認・デプロイの確認のどれをするか、どう確かめるかは、スキルの書き方で決まる。sacty は見る範囲の設定を持たない。
- 待つのは sacty。CI/CD が終わるのを待つ（時間の上限）・CI/CD の失敗の判定・ログの抜粋と秘密情報を伏せることは、今の sacty の
  確かめ方のまま工程の中で行う。エージェントに CI/CD やデプロイを待たせると、待つ時間を sacty が制御できず、費用もかかるため。
  sacty の判定で CI/CD が失敗していれば、エージェントを使わずに修正のタスクを登録する。
- CI/CD が通ったら、スキルに従ってエージェントに確かめさせる。sacty が見た CI/CD の実行・チェックをデータとして渡し、スキルの
  CI/CD の確認の仕方（どのワークフローが何を確かめるか・無視してよい失敗など）とデプロイの確認の仕方に従わせる。長く待たない
  （終わっていなければ判断できないとする）よう指示する。予算の上限も今どおり守る。
- 答えの形（見出し `sacty-deployment` の JSON）は、CI/CD の確認（`ci`：passed・failed・skipped・unknown）とデプロイの確認
  （`deployment`：healthy・unhealthy・skipped・unknown）それぞれの結果・要点・飛ばした・判断できない理由と、全体の要点・根拠にする。
  全体の結果は sacty が決める（どちらかが失敗なら失敗、そうでなく判断できないものがあれば判断できない、ほかは通った）。
  以前の形（`result` だけ）は読まない（互換の層を作らない）。
- 「Sacty セットアップ」のゴールで作らせるスキルも合わせる。CI/CD のあるリポジトリでは、デプロイしていなくても作る。CI/CD の確認の
  仕方の reference（`references/ci.md`）を作らせる。デプロイしていなければ、デプロイの確認を飛ばす（skipped と理由）と書かせる。
  CI/CD の無いリポジトリでは今どおり作らない（工程は飛ばされる）。

### ほかの工程とそろえる

- 工程の表示・進み具合・費用の表（工程の行。実行中も出す）・工程のイメージ（オーケストレーターが選び、人が変えられる）・通知の
  工程の名前を、ほかの工程とそろえる。
- 一時停止：監視の間は止められる。止めている間は CI/CD を見ず、確認も実行しない。確認の実行中なら、コンテナを止め、結果にせずに
  （確かめ直す記録）再開で確かめ直す。
- 再起動：確認の実行中に止まったら、ほかの工程の実行と同じく中断として一時停止し、再開で確かめ直す。CI/CD の待ちは今どおり続く。
- 中止：監視を終える。マージした実装の PR は閉じない（閉じられないため）。

### 以前の作業履歴

- 工程の無い、完了したタスクの監視の記録（PBI-116 より前）は、書き換えずにそのまま読み、これまでどおり完了したタスクのまま見届ける
  （止めた・止まった確認は、確かめられなかったとして終える）。

## 理由

- 工程にすると、監視の途中のタスクを終わっていないタスクとして追え、一時停止・中止・再起動・費用・通知をほかの工程と同じ仕組みで扱える。
- スキルの有無で決めると、プロジェクトの設定が要らず、リポジトリごとに監視が要るかを、そのリポジトリの持ち主がスキルで表せる。
  スキルが無いのに CI/CD だけ見る振る舞いは、何を見ればよいかがリポジトリに書かれていないまま監視することになるのでやめる。
- 決めた後のスキルの増減を、工程を選んだときの決定に固定するのは、工程の並びが途中で変わらないようにするため（足したときに工程を
  増やすと、承認の後に工程が増えて見え、作業履歴からも追いにくい）。消したときに CI/CD を見続けるのは、工程に入れた以上、
  sacty が持つ確かめ方は使えるため。
- 待つ・時間の上限・失敗の判定・ログを伏せることを sacty に残すのは、際限なく待たない・費用をかけない・秘密情報を出さないことを、
  スキルの書き方によらず守るため。範囲をスキルに任せるのは、何を確かめるべきかを sacty が一律に決められないため。

## 影響

- `StepKey` に `deployment` が増え、`STEP_PLANS` の実装を含む組み合わせの最後に入る。`StepsChosen` に、するかどうか（`deployment`）を持つ。
- `DeploymentChecked` に、CI/CD・デプロイの確認それぞれの結果（`ci`・`deployment`）と、確かめ直す記録（`retry`）を持つ。
- `step_agents.deployment` は、工程のキーとして読む（書き方は変わらない）。
- 以前に作ったデプロイの確認のスキルで答えの形を書いていても、sacty の指示の形が優先される。以前の形の答えは読めず、判断できなかった
  ものとして扱われる。
- プロジェクトの設定で `deploymentWatch` を On にしていたプロジェクトでも、スキルが無ければ監視しなくなる。
