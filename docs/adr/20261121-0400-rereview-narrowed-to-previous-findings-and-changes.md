# 再レビューは、前回の指摘の確認と前回以降の差分に絞る

- 日時: 2026-11-21 04:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-432
- 置き換え元: [文書だけを直した後の再レビューは観点と検証を絞り、リスク評価は引き継ぐ](20261120-2200-superseded-narrow-rereview-and-risk-for-documents-only.md)（再レビューの観点の絞り。検証の絞りは残す）
- 置き換え先: なし

## 背景

タスクの登録からマージまでの時間の調査で、PR の再レビューは初回と同じ規模だった（担当の数の中央値はどちらも 14、時間は約 8 分）。
再レビューは全体の時間の約 2 割で、費用の最大の部分を占める。直しが数行でも、PR 全体を、初回と同じ全部の必須観点で見直していた。

「再レビューの範囲は PR 全体で、観点は初回と同じ規則で決め直す」という決まりは、前回以降の差分だけを見ると、直し方が別の箇所を壊したときに見落とす、という理由で、スキル review-dispatch の流れ（`pr-review` の「再レビュー」）とデーモンの再レビューの指示（`rereviewLines`）に置かれていた。この決まりを明文で決めた ADR は無い。2026-11-20 の ADR（PBI-421）は、前回以降が文書だけの再レビューに限って、この決まりの例外（観点と検証の絞り）を作った。

## 決定

- 再レビュー（そのレビューのタスクに、前回の自分の投稿の記録 `previousReview` がある回）は、見る範囲と起動する観点を、前回の指摘の確認と、前回レビューした先頭から今回の先頭までの差分に絞る。規則の本体は、スキル review-dispatch の規則 11 と `pr-review` の「絞った再レビュー」に置く。
- 絞るかどうかは、依頼した側（デーモン）が決めて、指示の独立した節で明示する。スキルは、明示がある回だけ絞り、PR のコメント・レビューを読んで「自分の前回の投稿がある」と判断したことだけでは、範囲も観点も絞らない。ほかの人（ほかの人が起動した sacty を含む）の投稿は、形が同じで読み違える余地があるため。規則 8・9・10 と同じ「明示している場合に限り」の形にする。
- その sacty にとっての初回（前回の自分の投稿の記録が無い回）は、PR にほかの人・ほかの sacty のレビューがいくつあっても、同じ台帳の別のタスクが過去に同じ PR をレビューしていても、絞らない。区別は、デーモンのタスクごとの記録（`previousReview`）だけで行い、PR 上の投稿の読み取りには頼らない。
- 絞った回に起動するのは、前回の指摘に関わる観点、X-1、前回以降の差分が起動条件に当たる条件付き観点、前回以降の差分の種類で決まる安全性の観点（C-3・D-5・U-5。文書なら U-1・D-2 も）、X-2、X-3・R（前回以降の差分に当てはまるときだけ）。ほかの必須観点は、起動表に理由つきで残し、見られなかった観点に数えない。この絞りは規則 1・5 より優先する。同じ先頭を判定し直す回は、前回の指摘に関わる観点と X-1 だけにする。実装の前の文書の PR（規則 9）の再レビューにも当てる。
- 規則 10（前回以降が文書だけ）は、観点の絞りを規則 11 に任せ、検証の絞り（`scope: docs`、コードのテストを `skipped`）だけを残す。検証は、絞った回でも新しい先頭で実行し直す（前回の結果の使い回しはしない）。
- 判定のしかたは、PBI-421 の `rereviewDocsOnlyOf` に倣い、デーモンが 1 か所（`rereviewNarrowOf`）で持つ。次のどれかに当たる・確かめられない・迷うときは、絞らず、理由をログに 1 行残す。
  - 前回の先頭を取得できない・今回の先頭の祖先でない。前回の起点・向き先の記録が無い、または向き先・差分の起点（merge-base）が前回と変わった（起点は PBI-421 と同じく、`base.sha` ではなく merge-base で見る）。
  - 前回の回に判定が無い。前回の回の担当の起動を確かめられなかった（前回の回の `reviewDispatch` の担当の数が 0 件と数えた回。数えられなかった `null` は、起動できなかった証拠が無いので絞る）。
  - 前回以降に変わった行数が、今回の PR 全体の差分の行数の半分を超える（ちょうど半分は絞る）。前回以降に変わったファイルのうち、前回の時点の PR の差分に無かったものが 3 つ以上あり、かつ変わったファイルの半分を超える。
  - 前回以降の差分が空・100 万字を超える・名前に制御文字や引用符を含むパスがある（渡せない）。
  - PR を作ったタスクが、前の工程へ戻って作り直した後の提出（前回の回の指摘の戻し先が、その PR の工程より前の工程）。
- 数の値の理由：行数の半分は、直しが PR の半分までなら、前回以降の差分と、その影響を受ける箇所で見落としにくい、という見立ての目安（PR の大半を作り直した直しは、PR 全体で見る）。新しいファイルの 3 つ以上かつ半分超は、前回までに見ていない所を広く触った直しを拾うための目安で、1〜2 個のファイルの追加は、ふつうの直しとして絞る。値は定数（`REREVIEW_NARROW_*`）で、実物の再レビューの結果を見て変えられる。
- GitHub の再依頼で作ったタスクは、前回の自分の投稿は持つが、前回の回の判定を持たないので、絞らない（PBI-421 と同じ。判定を写す・新しい状態を足すことはしない）。
- 前回以降の差分は、PR 全体の差分と同じ流儀で渡す（指示とは分けた JSON のデータ。6 万字を超えるときは先頭だけを載せ、全体を読み取り専用のファイルに置く）。
- 変えないもの：自己レビュー、初回のレビュー、検証の実行（絞った回でも実行し直す）、前回の指摘の書き方・重みの見直し・作者の返答・既存のレビューとの重なり・PR の目的の範囲の外（PBI-426）・判定と重みの決め方・リスク評価を指摘なしの回だけ出すこと（PBI-429）。`must` は、前回以降の差分の外でも採用する。同じ原因が続くとき（PBI-424）は、絞っていても方針の観点を起動する。

## 理由

- 直しが数行でも、PR 全体を初回と同じ観点で見直すと、時間と費用が直しの大きさに見合わない。前回の指摘の確認と前回以降の差分に絞れば、担当の数と時間を減らせる。
- 絞るかどうかをデーモンの記録で決めれば、PR 上の投稿の読み違え（ほかの人や、ほかの sacty の投稿を自分の前回の投稿と取り違える）で、初回を絞ることがない。
- 確かめられない・迷うときに絞らない条件を多く置き、親にも絞らない条件を持たせたので、絞りが原因で、PR 全体を見るべき回を絞ることを、少なくできる。

## 受け入れた見落としの種類

- 前回以降の差分に当たらず、前回の指摘にも関わらない観点は起動しないので、前回以降の変更の影響が、前回以降の差分から離れた箇所（変えていないコード・テスト・文書）に及んでいても、起動した観点の担当（とくに X-1 と、直しと PR のほかの箇所の食い違いを見る依頼）が気づかなければ、見落とす。`must` は、見つかれば差分の外でも採用するが、担当に差分の外を見に行かせはしない。
- 前回以降の差分がコードのとき、安全性の観点（C-3）は起動するが、正しさの観点（C-1）は、前回の指摘に関わらない限り起動しない。直しが新しい処理を足して論理の誤りを入れても、前回の指摘が C-1 に関わらなければ、その誤りを見るのは X-1 だけになり、見落とすことがある（ふつうの回は、前回の `must` の多くが C-1 に関わるので、C-1 も起動する）。起動する観点を足すかは、人が決める。この ADR は、足さずに、この見落としを受け入れる。
- 初回のレビューで出なかった既存の欠陥は、絞った再レビューでは見つからない。次の回（前回以降の差分に当たる観点）か、人の確認で拾う。
- 絞った後に、PR 全体をもう 1 回見る回は足さない。
- 行数・ファイルの数の値は目安で、境界の近くでは、絞るべきでない回を絞る・絞ってよい回を絞らないことがありうる。

## 他の決定との関係

- 規則 10（PBI-421）の ADR のうち、再レビューの観点の絞りの部分を置き換える。検証の絞り・判定の二段（デーモンが名前と拡張子で見て、親が内容を見直す）・起点を merge-base で見ること・再依頼のタスクを絞らないことは、そのまま残す。
- 実装の前の文書の PR（PBI-419）の「再レビューも、初回と同じ規則で決め直す」は、規則 11 を重ねる形で変わる。D-3・D-4・D-6 を起動しない決まりは、そのまま。
- 自己レビューの再レビュー（前回 `must` の観点と X-1 だけ）の決まりは変えない。担当に渡す範囲を差分で決め、途中で広げない決まり（PBI-349）、重みの見直し・同じ原因が続くとき・PR の目的の範囲の外の決まりも、そのまま。
