# 人間が読む成果物の初版を最小限にし、詳しさは人間の差し戻しで足す

- 日時: 2026-10-25 02:22 UTC
- ステータス: 採用
- 関係する PR・タスク: #219
- 置き換え元: [要求要件・設計の冒頭に人間が判断することを分けて置き、書く量を変更に比例させ、セルフレビューに書きすぎの観点を足す](20261024-1330-superseded-reader-load-of-requirements-and-design.md)
- 置き換え先: なし

## 背景

前の ADR で要求要件・設計の書く量を抑えたが、成果物はまだ人間が読むには情報が多い。
sacty で草案を作った後、手元の別のエージェントで「見やすくする」直しを何度も重ねて、ようやく読める文書になっている。

人間は前提（暗黙知）を持っているので、要ることだけが書かれた文書が読みやすい。
情報が多いと、人間は読む気を失い、中身を確かめずに承認してしまう。
人間の承認で成果物を固める sacty の目的が失われる。

## 決定

- 人間が読む成果物（要求要件・設計・文書・調査が目的のタスクの調査の結果）の初版は、最小限にさせる（`minimalDraftLines`）。
  - 読む人がすでに知っていること（依頼の言い直し・背景・一般論・用語の説明・既存のコードの説明）、採らなかった案、まとめを書かせない。書くか迷ったら書かせない。
  - 人間が差し戻しで詳しくするよう求めたら、求めた所だけを詳しくさせる。求めで足した記述は、あとの直しでも削らせない。
- 要求要件・設計は、次のように絞る。
  - 確認したいことを must と should に分ける。must（後で違うと分かると、それまでの作業が無駄になるもの）は件数の上限を設けない。should（後で違うと分かると、追加の作業が要るもの）は最大 5 件にし、超えた分は推奨の答えで決めて「既定で決めたこと」に回させる。
  - 既定で決めたことは、人間が異論を持ちうるものだけにし、最大 5 件にする。既存のやり方にそのまま従っただけのことは書かせない。
  - 全体の行数の目安を、小さな変更で 20 行、大きな変更でも 60 行ほどにする（決まった形の JSON は数えない）。
  - テスト観点の数を、受け入れ条件を確かめるのに要る分だけにさせる。
- 自己レビューの `design-doc` では、記述を足す指摘は `must` だけを直させ、`should` は直させない。D-10 は `should` も直させる。
- D-10 に、読む人がすでに知っていること・採らなかった案・既定で決めたことの並べすぎを足す。人間の求めで足した記述は削る指摘にしない。
- 既定のスキル `writing` に「情報を絞る」を足し、`ears-requirements` に要求を最小限にすることを足す。
- 既定の規則（`rules.md`。CLAUDE.md・AGENTS.md として渡る）に、人が読む文章は必ず `writing` を使って書くことを足す。

## 理由

- 足りない情報は、人間が差し戻しで求めれば足せる。多すぎる情報は、人間が読み切れず、差し戻しの指摘にもつながらない。少ない側から始める方が、人間が中身を確かめる。
- 行数の目安を数で示すのは、「簡潔に」だけでは、エージェントが書く量がほとんど変わらないため。目安の数は、1画面で読み切れる量から決めた。実際の成果物を見て直す。
- 確認したいことは、件数より、後で発覚したときの損失で分ける。作業が無駄になる問いを件数の上限で落とすと、損失が大きい。追加の作業で済む問いは、推奨の答えで先に進めても取り返せるので、件数を絞る。
- 工程の指示には `writing` に従うよう書いていたが、工程の外の文章（PR へのコメント・報告など）には届かない。どの工程でも読む規則に書く。
- 自己レビューで足す `should` を作者の判断にしていたが、作者（エージェント）は足す方に寄る。`must` だけにして、足す方向の圧力を止める。

## 影響

- 初版の成果物が短くなる。要る記述まで省かれたときは、人間が差し戻しの指摘で足させる。差し戻しの回数が増えることがある。
- 文書（`document`）の工程では、読者がタスクの示す人のとき、その人の前提に合わせる。
