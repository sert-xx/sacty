# 文書原稿と単発の外部作業を独立した承認工程で扱う

- 日時: 2026-10-15 23:53 UTC
- ステータス: 採用
- 関係する PR・タスク: [#123](https://github.com/sert-xx/sacty/pull/123)、PBI-112、PBI-113
- 置き換え元: なし
- 置き換え先: なし

## 背景

開発・調査・設計・レビュー向けの工程だけでは、利用者向け原稿の作成と予定表などの単発更新を適切に表現できない。また、standard を無条件に推奨する指示は目的に合う候補の比較を妨げる誘因になる。実際の選択比率と実モデルの分類精度は未評価であり、偏りが発生していたとは断定しない。

## 決定

- リポジトリ無しの原稿作成には document を追加する。Markdown 原稿を画面で承認し、任意の外部書き出しは既存の仕組みを使う。承認前の原稿作成には外部接続とプロジェクトコンテキストを渡さず、外部原稿の読取も行わない。元の本文や規約は人間がタスク本文・差し戻しで提供する。リポジトリ内の文書変更は既存の PR 経路を使う。
- リポジトリ無しの外部単発作業には単一工程の operation を追加する。既存のオーケストレーターが接続先・対象 ID/URL・依頼内容と前提・確認方法を選定し、依頼に従って1回実行して結果の確認・承認を待つ。追加の準備エージェント・準備成果物・実行前承認は設けない。対象・接続先の不足は実行開始前に停止する。
- 実行は選定された接続先1つだけを利用し、開始を永続化する。成功結果の根拠を人間が確認して完了にする。失敗・中断・再起動・結果不明では自動再実行せず停止する。開始後の差し戻しは許可しない。
- 工程の選択では目的・成果物・変更対象・規模を比較し、standard を無条件に推奨しない。

## 理由

原稿の承認と外部状態の変更は異なる境界である。要求要件・設計へ偽装すると成果物の形式と承認の意味が合わない。単発作業のために準備と実行を別工程・別承認に分けるのは過剰という利用者の判断を受け、実行前の選定は既存オーケストレーター内で行う。外部操作を通常の工程と同じように再実行すると、応答を失った場合に二重変更になる。開始済みの実行を止め、人間が実際の状態を確かめて未実施分だけを新しいタスクにする方式を選ぶ。

## 影響

外部操作の書込1回と読戻確認はプロンプトで指示するものであり、接続先側の exactly-once 保証ではない。通常の成果書き出しの失敗は従来どおりタスクを止めない。外部の直接更新を成功必須とする依頼は単一の作業工程を使う。定期業務・監視・複数接続先の長期業務は今回の範囲に含めない。

仕様は[タスクと工程](../spec/tasks-and-steps.md)、操作は[タスクを進める](../user/tasks.md)に記載する。実モデルによる分類評価と本番の選択実績の評価は未実施である。

新しい工程名を含むイベントを保存した DB は、工程の enum が旧来のままの版では読み込めず、起動に失敗する。旧版へ戻すための互換層は追加しない。更新前にデーモンを停止してデータディレクトリ（`SACTY_HOME` の指定先、未指定なら `~/.sacty`）をバックアップし、旧版へ戻す場合は更新前のバックアップを使う。バックアップ以後の新規タスク・進捗履歴は復元されず、すでに行った外部変更は巻き戻らない。とくに外部作業の開始記録を失うと重複実行の危険があるため、実際の外部状態を確認し、実施済みの操作を再送しない。
