# 統合レビューで人の確認だけが残った観点は、不合格にせず、人が確かめることとして承認待ちに出す

- 日時: 2026-11-16 22:55 UTC
- ステータス: 採用
- 関係する PR・タスク: #396、PBI-363
- 置き換え元: なし
- 置き換え先: なし

## 背景

統合レビューは、すべての観点を満たし、足りないこと（`findings`）が無いときだけ合格にし、不合格ならタスク分割に戻って修正の子タスクを足していた。
答えには、人が確かめることを書く欄が無かった。

複数のリポジトリを指定する機能を sacty 自身に実装させたとき、統合レビューで、作業領域では確かめられない観点（実際の GitHub とエージェントを使った確認）だけが残った。
統合レビューはその観点を満たさないとして不合格にし、修正の子タスクが作られた。
修正の子タスクでは、この観点は直せない（コードに足りないことは無く、確かめる環境が無いだけ）。
人が自分で確かめても、その結果を親タスクに伝える手段が無かった。

## 決定

- 統合レビューの答えに、人が確かめること（`humanChecks`）の欄を足す。
- 作業領域では確かめられないことが残る観点は、コードとテストで確かめられる範囲で判定させ、残ることを `humanChecks` に書かせる。`findings` には書かせない。
- `humanChecks` は合否に使わない。あっても、ほかが満たされていれば合格にし、修正の子タスクを作らずに、統合レビューの承認待ちにする。
- 承認待ちの画面に「人が確かめること」として出す。人は確かめてから承認し、満たしていなければ差し戻す。
- 前の回の統合レビューが挙げた項目は、次の統合レビューが挙げなくても、sacty が引き継ぐ。外すのは、次の統合レビューが、確かめられた・要らなくなったとして、同じ文を挙げたものだけ。
- 項目は、人に渡す情報として扱い、形が崩れていても・長くても、落とさない・切り詰めない。

## 理由

- 修正の子タスクは、コードに足りないことを直すためのもの。確かめる環境が無いことは、子タスクでは解消できず、作っても通らない統合レビューを繰り返すだけになる。
- 以前の版の最終レビューにも、同じ考えの「人が確かめること」があった（作業領域では確かめられないことを、最終承認で人が確かめる）。統合レビューも同じ形にそろえる。
- 人が確かめた結果を伝える手段は、新しく作らず、既にある統合レビューの承認・差し戻しを使う。承認が「確かめた」、差し戻しが「満たしていない」を表す。
- 項目を次の回に挙げ直させるのではなく sacty が引き継ぐのは、不合格の回に挙げた項目が、修正の子タスクの後の統合レビューで挙げられないと、人に渡らないまま承認待ちになるため（以前の版の最終レビューの「人が確かめること」も、同じ理由で引き継いでいた）。
- 比べた案：観点ごとに「人の確認が要る」という印を持たせ、sacty がその観点を合否から外す。観点の判定の形（最終レビューと共通）を変えることになり、変更が広がるので採らなかった。
- 比べた案：`findings` が空で `humanChecks` があるときは、満たさない観点があっても合格にする。エージェントの答えの矛盾を sacty が合格の側に倒すことになり、確かめられる不足を見逃しうるので採らなかった。

## 影響

- エージェントが、作業領域で確かめられることを確かめずに `humanChecks` に回すと、不足が合格として人に届く。指示で禁じているが、sacty は機械的には確かめない。人は、項目が本当に作業領域で確かめられないことかも見る必要がある。
- 人が確かめた結果を、項目ごとには記録しない。どの項目を確かめて承認したかは、作業履歴からは分からない。
- 仕様は [タスク分割と統合レビュー](../spec/split-and-integrate.md#統合レビュー) にある。
