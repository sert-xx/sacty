# 既定のコンテキストに、観点ごとのサブエージェントを並列に起動して集約するレビュースキル（親と担当を別のスキル）を同梱する

- ステータス: 採用
- 関係する PR・タスク: #72、PBI-65
- 置き換え元: なし
- 置き換え先: なし

## 背景

単一のエージェントでは、レビューの対象が大きい・観点が広いときに、指摘すべき箇所を見落とす。sacty のレビューの工程で
使える、見落としを防ぐレビューの手順を、どのプロジェクトにも渡る既定のコンテキストに置く必要があった。

## 決定

- 既定のコンテキストのグループ `review` の下に、親の `review-dispatch` と観点担当の `review-execution` の2つのスキルを置く。
- 流れは2つ：自己レビュー（指摘 → 修正 → 再レビューのループ、最大5回。投稿しない）と PR レビュー（対象を変えないワンショット。
  sacty のレビュー工程の投稿形式に合わせる）。sacty の「レビュー」の工程は常に PR レビュー。ゴールガーディアンの最終レビュー・
  統合レビューは対象外。
- カテゴリーごとの専門家ではなく、観点ごとの担当にする。主対象の種類（コード・設計書・利用者向け文書）の必須観点は、
  対象の大小にかかわらず全部起動する。条件付き観点は起動の条件を判定し、起動しなかった観点と理由を記録して、投稿の本文
  （折りたたみ）にも載せる。判定に迷ったら起動する。カタログに無い欠陥を拾う横断の観点を常に1つ起動する。
- 観点カタログは1ファイル。観点ごとの詳しい資料（30 観点）を担当側に置き、担当は自分の観点のファイルだけを読む。
- 親と担当の混線を止める：スキルの説明文に役割を書き、両方の冒頭に依頼文で親か担当かを判定する表を置く。依頼文の雛形に
  「サブエージェントを起動しない・review-dispatch を使わない」の禁止の行を入れ、担当が親の手順を実行した結果は捨てて起動し直す。
  Codex は既定のコンテキストの `agents/codex/config.toml` でサブエージェントを有効にし、`max_depth = 1` で担当からの起動を止める。
- サブエージェントを起動できない環境では、親が観点ごとの依頼文を先に全部書き、宣言して担当に切り替え・親に戻る「逐次モード」で
  順に行う。これを「途中で役割を変えない」の唯一の例外とし、逐次モードであることを記録と本文に書く。
- スキルも観点の資料も、特定の言語・枠組み・sacty 自身の構成に寄せない。NG 例は複数の言語で書く。

## 理由

- 観点ごとに必須観点を全部起動するのは、見落としを防ぐという目的のため（PR の本文の「設計の判断」）。横断の観点は、
  カタログの網羅の不足を補うため。
- 利用者の環境のワークフロー固有の仕組み（gate の証跡など）は書かず、fail-close・初回は全観点が揃うまで投稿しない・
  再レビューでは修正必須の指摘は常に採用し任意の指摘は直近差分の中だけ、という考え方は残した（PR の本文）。
- 起動できない環境の手順を用意したのは、サブエージェントの起動方法が実行環境で違うため（PR の本文）。逐次モードの切り替えの
  手順は、代替の手順が役割の判定と循環するというレビューの指摘への対応。
- 混線を止める仕組みは、親が担当の手順を実行したり、担当がサブエージェントの起動を始めたりしないようにするため（PR の本文と
  コミットのメッセージ）。
- 特定の言語に寄せないのは、どのプロジェクト・どの言語の成果物にも使われるため（PR の本文）。
- ゴールガーディアンの最終レビュー・統合レビューを対象外にしたのは、プロンプトが判定の形式と根拠を決めているため（PR の本文）。

## 影響

- どのプロジェクトのレビューの工程でも、既定でこのスキルが worker に渡る。雛形は既定のスキルを変えない。
- 観点が足りなければカタログに足し、資料も足す前提。
- sacty のレビューの工程は、再レビューでも前回のレビューと前回以降の差分をプロンプトに渡していないので、スキルの再レビューの
  採用の規則を生かすには sacty 側の改善が要る（この PR では扱っていない）。
- 実際の worker がサブエージェントを起動する様子は、この PR の時点では確かめていない。
