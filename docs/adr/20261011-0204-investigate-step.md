# 「調査」の工程を足し、結果は人間が承認して完了にし、Issue から取り込んだタスクは結果を Issue にコメントで返す

- 日時: 2026-10-11 02:04 UTC
- ステータス: 採用
- 関係する PR・タスク: #24、PBI-18
- 置き換え元: なし
- 置き換え先: なし

## 背景

#23 で、オーケストレーターが決まった候補から工程を選ぶようにした。ステークホルダーが最初に足したい工程として「調査」を挙げた。コードを調べて報告するだけの工程で、実装や PR は作らない。

## 決定

- 工程の種類に `investigate` を足し、オーケストレーターの候補に「調査だけ」を足す。質問・原因の調査・影響範囲の確認・見積もりなど、変更ではなく情報を求めているときに選ぶ。
- 調査のエージェントは、起点のコードを読み取り専用で読み、調査の結果（Markdown）を書く。結論・根拠（ファイルと行）・関係する箇所や影響範囲・確認したいことを書かせ、推測と確かめた事実を区別させる。
- 調査は承認ゲートのある工程にする。人間が承認するとタスクは完了。差し戻しで調べ直させられる（指摘は累積し、前回の結果とともに渡す）。
- GitHub Issue から取り込んだタスクは、完了したら人間が承認した結果を、プロジェクトの gh のアカウントで Issue にコメントとして返す。長すぎる結果は省略する。返せなければ理由を記録し、何度も返そうとはしない。画面で作ったタスクは返さない。
- コメントにタスクごとの目印（HTML コメント）を入れ、投稿の前に既存のコメントを目印で探し、あればその URL を記録して投稿しない。

## 理由

- 調査を足すこと、結果を人間が承認して完了にすること、Issue に返すことは、ステークホルダーと決めた（本文）。それぞれの理由は記録に無い。
- 目印で既存のコメントを探すのは、投稿の後、記録の前に止まると、次の実行で同じ結果を再投稿することがレビューで再現されたため（レビュー・コミット）。

## 影響

- 調査だけのタスクは、実装・PR を作らずに完了する。
- Issue へのコメントは、照合（コメント一覧の取得）に失敗したときも投稿せず、失敗として記録する。
- 画面は、調査の結果を Markdown として出し、承認済みなら折りたたむ。
