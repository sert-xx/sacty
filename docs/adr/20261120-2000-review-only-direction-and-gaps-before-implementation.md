# 実装が後に続く要求要件・設計の PR のレビューは、方針と抜けだけを見る

- 日時: 2026-11-20 20:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-419
- 置き換え元: なし
- 置き換え先: なし

## 背景

2026-11-19（PBI-395）、要求要件・設計の PR にも、実装の PR と同じ重さのレビュー（観点ごとの担当 11〜12 件、1回 4〜5 ドル・約7分）が提出のたびに走り、3件で約 23.7 ドルかかった。
要求要件のレビューは設計・実装の細部まで、設計のレビューはテスト観点の値と粒度まで求め、その多くは実装のレビューでもう一度確かめることになった。
PR のレビューの指示は、PR の工程によらず同じ文で、既定のスキルの `design-doc` の必須観点（D-1〜D-6・D-10）は全部起動していた。

## 決定

- 指示（`reviewDocBeforeImplementLines`）は、レビューする PR が要求要件・設計の PR で、PR を作ったタスクの `implement` の工程が残っている（飛ばしていない）ときだけ、次を明示する。この PR は実装の前の文書の PR で、実装の PR は後で別にレビューされること、このレビューは方針と抜けだけを見ること。
- 規則の本体は既定のスキル `review-dispatch`（規則 9・`pr-review` の「実装の前の文書の PR」）に置き、依頼した側が明示したときだけ当てはめる。明示が無い実行は変えない。指示にも要点を書く（プロジェクトがスキルを差し替えても分かるように。PBI-369 と同じ形）。
- 方針と抜け（指摘にしてよい）：目的・範囲、依頼・上位の要求との食い違い、要求・受け入れ条件の抜けと矛盾、方式の選択とその理由、確認したいことの出し方、取り返しにくい決定（外に公開する I/F・保存するデータの形・セキュリティ・移行）の誤りと抜け。
- 実装のレビューに任せる（指摘にしない）：実装の手段の細部、テスト観点の値・粒度・境界値の並べ方、言い回し。ただし、手段やテスト観点が方針を誤らせる、または受け入れ条件を取りこぼす（観点がまるごと抜けている）ときは指摘にしてよい。
- 起動する観点（主対象が `design-doc`）は、D-1・D-2・D-5・D-10 と X-1。条件付き観点・X-2・X-3・R は通常の規則で決める。
  - 残す理由：D-1（目的・範囲・方式の選択と理由・上位の要求との対応）、D-2（成り立たない・既存と矛盾する方針、I/F）、D-5（セキュリティ・規定。取り返しにくい）、D-10（確認したいことに判断が出ているか）、X-1（観点の外の欠陥の探索）が、方針と抜けにそのまま当たる。
  - 起動しない理由：D-3（完全性）と D-4（検証可能性）は、異常系・境界・テスト観点の入力と期待結果の具体さが中心で、実装のレビューに任せる範囲に当たる。D-6（形式・明確さ）は言い回しに当たる。取り返しにくい決定（保存するデータの形・移行）と受け入れ条件の抜けは、起動する観点の担当への依頼文に書いて見させる。起動しなかった観点は、通常の規則どおり起動表に理由つきで残す。
  - 担当の段階は変えない。
- 変えないもの：実装の PR、取り込んだ PR（PR を作ったタスクが無い）、実装の工程が残らないタスク（設計だけ・分割・文書作成など）や実装を飛ばしたタスクの PR のレビュー。判定、指摘の重み（PBI-358）、戻し先の書き方、再レビューの規則。
- 提案だけのレビューで自動の直しを止めることは、利用者の決定で入れない。

## 理由

- 実装の PR は後で別にレビューされるので、文書の PR で実装の細部まで詰めると、同じ確かめを二重にする。方針と抜けは、実装の後では取り返しにくいので、文書の PR で見る。
- 観点を絞る合図を指示が出し、規則をスキルに置くのは、PBI-369 と同じで、明示が無いレビューを変えずに済む。

## 影響

- 要求要件・設計の PR のレビューは、起動する担当が減り、費用と時間が下がる。
- 実装の細部の不備は、要求要件・設計の PR では指摘されず、実装の PR のレビューで指摘される。
- 実装の判定は、PR を作ったタスクの工程が、レビューの指示を作る時点のものによる。設計の承認の後に実装を飛ばすと決まっても、それ以前の要求要件・設計の PR のレビューは絞ったままである。
