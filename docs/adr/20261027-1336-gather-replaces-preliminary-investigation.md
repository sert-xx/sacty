# 情報収集がコードを調べるので、実装する組み合わせから前段の調査を外し、調査だけのタスクの結果の形を依頼に合わせる

## 背景

実装する組み合わせ（標準・設計を省く・直接実装・分割・不具合の修正・セキュリティ対応）は、先頭に前段の調査を置き、関係するコードの場所・いまの振る舞い・影響範囲・テストの書き方などを後の工程に渡していた。
その後、オーケストレーターの前に情報収集を置き（[オーケストレーターの前に情報収集のエージェントを置く](20261022-2350-superseded-gather-information-before-orchestrator.md)）、情報収集が対象リポジトリのコードも読むようにした（[情報収集が、対象リポジトリのコードも読む](20261023-0219-gather-reads-repository-code.md)）。
集めた情報は、すべての工程に渡る。
このため、前段の調査は情報収集と同じことを二重にしていた（作者の判断）。

調査だけのタスクは、結果の形（結論・根拠・関係する箇所・確認したいこと）を指示で決めていて、依頼に形の指定（表・章立てなど）があっても合わせられなかった。

## 決定

- 標準・設計を省く・直接実装・分割・不具合の修正の組み合わせから、先頭の `investigate` を外す。
- セキュリティ対応（`security-fix`）は、前段の調査を残す。
- 情報収集は、作業するリポジトリが決まっている（用意した）タスクでは、テストの書き方（フレームワーク・実行のコマンド・置き場所と名付け・既存のテストの例）もまとめる。
  前段の調査が書いていたもののうち、情報収集に無かったもの。
- テストの書き方は慣習の事実として書かせ、このタスクでテストが要るかは書かせない。
  テストの扱い（`testCommand`・`noTests`）はオーケストレーターが決める。
  オーケストレーターと工程のエージェントの指示にも、まとめにテストの書き方があってもテストが要るとは限らないと添える。
- 影響範囲・不具合の原因の見当は、情報収集に足さない。
  後の工程（要求要件・設計・再現・実装）のエージェントは、リポジトリを持っていて自分で読める。
- 調査だけのタスクの結果の形は、依頼に指定があればそれに従わせる。
  今までの形は、指定が無いときの既定にする。
  根拠（ファイルと行）を添えること、推測と確かめた事実を分けることは、形にかかわらず守らせる。

## 理由

- 前段の調査を外すことと、調査だけのタスクの結果の形を依頼に合わせることは、作者が決めた。
- セキュリティ対応を残すのは、修正の範囲の宣言（`sacty-security-scope`）を前段の調査が出していて、sacty がそれで実装の差分を照らすため。
  実装のエージェントに宣言させると、自分の変更を縛る範囲を自分で決めることになり、歯止めとして弱くなる。
- テストの書き方を集めるのを、リポジトリが決まっているタスクに限るのは、作者の指定による。
- テストの要否をまとめに書かせないのは、まとめにあるだけでテストを書く・求めるものと受け取られないようにするため（作者の指摘）。
- 不具合の修正は、前段の調査（不具合の調査）でセットアップしてサービスを動かして確かめていたが、すぐ後の再現の工程が同じことをするので外した。

## 影響

- 実装するタスクは、前段の調査の分だけ実行が1回減り、費用が減る。
- 工程の見直しは、前段の調査の後には無くなる。
  標準では、要求要件の承認の後に設計を見直す。
  不具合の修正では、再現を見直す機会が無い（再現が要らなければ、オーケストレーターが直接実装を選ぶ）。
- 要求要件を経ない設計・実装は、タスクの内容と集めた情報に従う。
  前段の調査がある（セキュリティ対応と、前段の調査を置いていた版の作業履歴の）タスクは、今までどおりその結果に従う。
- 工程は `StepsChosen` に記録しているので、前段の調査を置いていた版のタスクは、そのまま前段の調査を含んで進む。
- 分割の子タスクは情報収集をしない（親のまとめを内容に引き継ぐ）ので、子タスクの工程は、親のまとめとリポジトリのコードから進む。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md#進め方の組み合わせ) にある。
