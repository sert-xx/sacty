# コンテキストリポジトリの層の platforms.yaml で、プロジェクトごとのゲートウェイの外部 PF を mcp.yaml と同じ規則で定義する

- 日時: 2026-10-14 05:34 UTC
- ステータス: 採用
- 関係する PR・タスク: #83、PBI-74
- 置き換え元: なし
- 置き換え先: なし

## 背景

ゲートウェイの外部 PF（プラットフォーム）は、ホストの `config.yaml` の `gateway.platforms` にだけ書け、すべてのプロジェクトで共通だった。
MCP サーバーはコンテキストリポジトリの層（`mcp.yaml`）でプロジェクトごとに合成できるが、外部 PF は合成の対象ではなかった。

## 決定

- コンテキストリポジトリの層に `platforms.yaml`（最上位のキー `platforms:`）を置ける。書ける項目と名前の規則は `gateway.platforms` と同じ。
- 合成の規則は MCP と同じ：下位の層が上書きし、`locked.platforms`・`remove.platforms` を使える。
- ホストの `gateway.platforms` は今までどおりすべてのプロジェクトで使える。同じ名前があればホストのものを使い、警告（`context.hostPlatform`）を残す。
- 認証は秘密情報の名前で参照し、値はホストのゲートウェイが使うときだけ取り出す。エージェント・作業履歴・画面には、名前・層・説明・allow だけを出す。
- コンテキストの PF は、そのタスクの実行のトークンにだけ登録し、ほかのプロジェクト（ほかの実行のトークン）からは使えない（404。上流に送らない）。
- チケットの取り込み・トリアージ・コメント・成果の書き出しでも、プロジェクトのコンテキストの PF を使える。ホストに無い名前の取り込み先は、
  プロジェクトごとに検索する。
- コンテキストの PF のチケットは、プロジェクトとあわせて識別する（設定の競合・担当の判定・重複の排除。取り込んだチケットに `scope: project` を記録する）。
  ホストの PF のチケットは、今までどおりプロジェクトをまたいで識別する。
- コンテキストの PF の認証の失敗は、画面の状態（タスク一覧の警告）には出さず、使ったエージェントへの応答で返す。

## 理由

- ファイル名と最上位のキーは、`mcp.yaml` に合わせた（PR の本文の「判断したこと」）。
- ホストに無い名前の取り込み先をプロジェクトごとに検索し、チケットをプロジェクトとあわせて識別するのは、同じ名前でもプロジェクトごとに別の PF のため
  （PR の本文、レビューの指摘への対応）。
- 認証の失敗を画面の状態に出さないのは、同じ名前の PF がプロジェクトごとにありうるため（PR の本文）。
- 信頼の考え方は mcp.yaml と同じ：コンテキストリポジトリに書いた PF は、書いた秘密情報を書いた転送先に送る（PR の本文）。
- 同じ名前ならホストのものを使うのは、ホストの MCP と同じ扱いにするため（PR の本文）。

## 影響

- コンテキストリポジトリに書ける人は、その PF の転送先と、送る秘密情報の名前を決められる（README に書いた）。
- `scope` の無い既存の取り込みのイベントは、ホストの PF のチケットとして扱う。
- 形の誤りは `context.fileInvalid` で層と項目を示して止める。
