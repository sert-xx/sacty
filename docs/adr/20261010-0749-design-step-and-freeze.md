# 承認済みの要求要件から設計とテスト観点を作り、差し戻し先を選べるようにし、承認した成果物は凍結する

- 日時: 2026-10-10 07:49 UTC
- ステータス: 採用
- 関係する PR・タスク: #4、PBI-8
- 置き換え元: なし
- 置き換え先: なし

## 背景

#3 で要求要件の承認ゲートを作り、承認すると設計が実行の対象になるようにしたが、設計の工程はまだ無かった。設計の段階で、
後の実装で確かめる観点（テスト観点）を決めること、設計を見て要求要件に問題があったときの戻り方、承認した成果物が
後から変わらないことを決める必要があった。

## 決定

- 設計の工程は、人間が承認して凍結した版の要求要件だけをプロンプトに渡し、設計とテスト観点を作って承認ゲートで止まる。
- テスト観点は、エージェントが JSON のブロック（`sacty-test-viewpoints`）で返す。各観点は「何を確かめるか・入力・期待結果」。
  項目が欠けた観点は取り込まず、ID（TV-1…）は sacty が振る。
- テスト観点は画面に観点ごとのカードで出す。0 件のときは差し戻すよう警告を出す。
- 設計を差し戻して再実行するときは、前回のテスト観点を ID・何を確かめるか・入力・期待結果つきでプロンプトに入れ、直さない観点も含めて全件を出し直させる。
- 設計の承認ゲートでは、やり直す工程として「設計」か「要求要件（再承認が必要）」を選べる。要求要件に戻すと、要求要件と設計の承認を取り消し、
  要求要件がもう一度承認されるまで設計を実行しない。指摘と差し戻しの上限は、やり直す工程ごとに付けて数える。
  エスカレーションの後でも、上限に達していない工程に戻すなら通常の差し戻しとして扱う。
- 承認の時に、成果物とテスト観点をタスクに記録して凍結する（`approved`）。承認済みの工程の実行の完了は、台帳の復元（projection）で拒否する。
  要求要件を変える経路は、要求要件への差し戻しとその後の再承認だけにする。
- 起動の時に、PBI-7 で承認されて設計で待機していたタスクを実行待ち（`StepQueued`）にする。PBI-7 までの台帳は、そのまま読める。

## 理由

- 前回のテスト観点をプロンプトに入れるのは、テスト観点が本文から取り除かれて別に保存されるので、TV-n を指した指摘で差し戻しても
  次のエージェントに観点の中身が渡らなかったため（レビューの指摘）。全件を出し直させるのは、ID を sacty が提出ごとに振り直すため（レビューへの返信）。
- 起動の時に実行待ちにするのは、PBI-7 の承認では次が待機になっていたので、設計で待機したまま進まないタスクが残るため（PR の本文）。
- テスト観点を JSON のブロックで返させる理由、凍結を復元の段階で拒否する理由は、記録に無い。

## 影響

- 要求要件が変わるのは、人間の再承認を通ったときだけになる。
- 承認済みの工程の実行の結果は、台帳に記録されても状態に反映されない。
