# PR の説明とコメントを、Sacty を使っていない人が読んで判断できる情報だけにする

- 日時: 2026-11-21 22:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-471
- 置き換え元: [PR の本文・コメントを、画面を開けないレビュアーにも読める形にし、製品名を「Sacty」にそろえる](20261121-1800-superseded-pr-text-readable-without-screen.md)（決定 1 の画面へのリンク、決定 3 のレビューの進め方・AI のレビューの状況、本文のタスク ID の行）、[PR に投稿するレビューには判断に要る情報だけを書き、Sacty の過程の情報は Sacty の記録に残す](20261121-1603-superseded-pr-review-without-process-info.md)（決定 9 の、返信と成果物のコメントの末尾の工程名）

## 背景

PR を読む人は、Sacty を使っていないかもしれない。[PBI-460](20261121-1603-superseded-pr-review-without-process-info.md) は、PR に投稿するレビューを、判断に要る情報だけにした。
しかし、Sacty が作る PR の説明と、Sacty が PR・Issue に書くコメントには、まだ次の情報が残っていた。

- タスクの ID・指摘の内部の ID・手元の画面の URL（`http://127.0.0.1:4700/...`）
- レビューの本文・行へのコメントの写し（目印・見出し・担当の行を含む）
- 内部の語（オーケストレーター・工程・子タスク・担当・サブエージェント・観点の番号）
- 「レビューの進め方」と AI のレビューの状況（書いた時点で古くなる）
- 同じ中身の繰り返し（最後の直しが結論と節の両方に出る、など）

説明が長くなり、人が判断に要る所を探す手間が増えていた。画面の URL は、依頼した人のマシンでしか開けない。

## 決定

PR の説明・Sacty が PR・Issue に書くコメント・後続の Issue と後続のタスクの題は、人が読んで判断する情報だけにする。Sacty の画面と `get_task` には、外した情報を今までどおり残す。

1. 説明は、目的・変更、確かめ方、人が確かめること、確認したいこと、指摘への対応（要点 1 行と、直したこと・直さなかった理由）、AI が作った印、承認の案内 2 文だけにする。冒頭の「Sacty のタスク…」の行、「レビューの進め方」、AI のレビューの状況は置かない。
2. タスクの ID は、表示されない HTML コメントの目印 `<!-- sacty task <タスク ID> -->`（説明の最後）にだけ置く。人が目印を書き換えた・消したときは、更新のときに正しい目印を 1 つだけ置く。
3. 指摘は、ID ではなく、元のコメントへのリンクと、要点の 1 行で示す。要点は、工程のエージェントが対応と一緒に書く（`gist`）。無い記録では、目印・見出し・引用の行を除いた指摘の最初の行を使う（説明では、要点の行を出さない）。要点は、秘密の値・内部のパス・URL・指摘の ID を除き、`@` を無効にして、120 文字（題は 80 文字）までにする。
4. エージェントが書いた文の中の指摘の ID は、指示で書かせず、組み立てでも除く。括弧の中が ID だけなら括弧ごと、それ以外は「指摘」に置き換えて、文を壊さない。
5. 画面の URL とその注釈は、コメントに書かない。再開・差し戻しの案内は、「Sacty の画面で〜してください」の文にする。
6. 後続に回す決定で作る Issue と後続のタスクの題は、指摘の要点から作る（`[PR #N follow-up] <要点>`）。エージェントへの指示の見出しには題を使わず、要点と文は指示と分けたデータで渡す。
7. 実装の説明の確かめ方は、観点が依頼の 1 行だけなら表を出さず、テストは件数とファイルだけにする。

## 理由

- PR の読み手が、画面を開かなくても判断できるようにするため。画面を開かないと判断できない説明は、承認する人の手間を増やす。
- 内部の ID・語・過程の情報は、PR の読み手には意味がなく、判断を妨げる。外した情報は、Sacty の画面と `get_task` に残るので、依頼した人は辿れる。
- 目印は表示されないので、読み手の邪魔にならず、GitHub で `sacty task` を検索する手がかりを残せる。
- 要点を機械で切らずにエージェントに書かせるのは、Sacty のレビューの本文が見出しから始まり、冒頭を切っても要点にならないため。以前の記録は、要点を出さずに対応だけを書く。
- 題を指示の見出しに使うと、PR にコメントを書ける人の文が指示として読まれる。見出しを固定し、要点はデータで渡す。
- 比べた案：画面へのリンクをすべて外さず注釈で補う案（PBI-450）は、PR に書く案内の文が内部の画面に頼ったままになるので、採らなかった。

## 影響

- 開いたままの古い形の説明と、投稿済みのコメントは書き換えない。説明は、次に更新したときに新しい形になる。
- 人が直した説明のマージでは、以前の版が作った可視のタスク ID の行を、残さない。人が足した行は残す。
- 返信の読み取りは、新旧どちらの書き出しも読む。
