## 背景

同じ「人の出番」を、ダッシュボードの「あなたの出番」・ヘッダーのベル・タスクの一覧の上のカード・`sacty mcp` の `list_tasks` が、別々の判定・別々の並びで出していた。
判定の写しが画面・MCP・デーモンの集計に 3 つあり、ベルは AI が PR の指摘の戻し先を判断中の承認待ちや消したプロジェクトのタスクも数えた。
承認待ち・エスカレーション・一時停止は同じ橙で出て、欄の高さは 5 件分なので、長く止まっている一時停止が 5 件あると、いま来た承認待ちはスクロールしないと見えなかった。
ベルを「ほかのプロジェクト」「このプロジェクト」に分けた理由は、元の ADR に記録が無い。

## 決定

- 人の出番か・どちらの組か・並びを、`packages/core` の `personTurnGroup`・`personTurnTasks` の 1 か所に置く。画面・MCP・デーモンの集計の写しはやめる。
- 組は 2 つ。上の組 `decision`（承認待ち・エスカレーション。AI が戻し先を判断中の承認待ちは入れない）と、下の組 `paused`（一時停止。理由は問わない）。並びは上の組 → 下の組、組の中は待ち始めの古い順、同じなら ID の順。
- ダッシュボードは組ごとに見出しと件数を出す（見出しは「判断で進むタスク」「再開を待つタスク」）。ベルは「ほかのプロジェクト」「このプロジェクト」の組分けをやめ、同じ 2 つの組を出す。ベルの件数・プロジェクトの切り替えの対応待ちの件数も同じ判定で数える。消したプロジェクトのタスクはベルから消える。
- 一覧の上のカードは同じ対象・同じ並びにする（見出しは出さない）。MCP の `order` は `personTurnGroup_waitingSince_asc` にし、各タスクに `personTurnGroup` を足す。
- 承認待ちの PR を Sacty の AI がレビューしている間（`aiReview.status` が `reviewing`）は、3 か所の行の状態に「・AI のレビュー中」を添える。組と並びは変えない。一覧の応答に、承認待ちで PR が開いているタスクだけの `aiReview` を詳細と同じ計算で載せる。
- ヘッダーと一覧のカードの待ち始めは、ダッシュボード・MCP と同じ `GET /api/dashboard` から読む。

## 理由

- 同じ出番を同じ対象・同じ順で見せるには、判定と並びが 1 か所にあるのが確実。写しは、片方を直して他方が古くなる（MCP の写しのコメントにも「画面の判定が変わったら合わせる」とあった）。
- 判断すれば進むものを上に固定すれば、止まったままのものが増えても、欄を開いた時点で見える。色は同じなので、組の見出しの文で区別する。
- ベルをプロジェクトで分けると、プロジェクトを選んだ画面と「すべてのプロジェクト」の画面で並びが変わり、ダッシュボードとも違ってしまう。各行にプロジェクトの名前は出ているので、分けなくても見分けられる。

## 影響

- ベルの件数が、AI が判断中の承認待ちと消したプロジェクトのタスクの分だけ減る。MCP の説明にあった「ベルは件数が違う」は事実でなくなる。
- MCP の `order` の値が変わる（`waitingSince_asc` → `personTurnGroup_waitingSince_asc`）。`needs_person` でない呼び出しは変わらない。
- ヘッダー・一覧のカードの取り直しで、デーモンの集計（`GET /api/dashboard`）も読む。
