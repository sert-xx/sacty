# PR へのレビューとコメントを指摘として取り込み、戻し先はゴールガーディアンが判断し、設計・要求要件まで戻すときは人間に確認する

## 背景

#20 で、成果物チェックを PR のマージで承認するようにした。差し戻しは、PR から取り込めるまで画面で受け付けていた。PR に付いた指摘を差し戻しとして取り込むこと、そのとき実装・設計・要求要件のどこまで戻すかを誰が決めるかを決める必要があった。

## 決定

- 見守り（1分ごと）で、開いている PR へのフィードバックを、プロジェクトの gh のアカウントで読む。対象は、Request changes と本文のあるコメントのレビュー、行ごとのコメント、PR への通常のコメントの3つ。承認のレビューと bot のものは含めない。Request changes に限らず、指摘として扱う。
- 最後のフィードバックから2分たってから、まだ取り込んでいないものをまとめて取り込み、人間の操作として記録する。1件のフィードバックを1件の指摘にする（行ごとのコメントにはファイルと行を添える）。1件 2,000 文字・1回 50 件までにし、残りは次の取り込みに回す。
- 取り込んだフィードバックの種類と ID・作者・日時・URL を作業履歴に記録し、二重に取り込まない。指摘は画面からの差し戻しと同じく累積し、最終レビューで再発を確かめる。
- 戻し先（実装だけ・設計から・要求要件から）は、ゴールガーディアンが新しいセッションで判断する。渡すのは、承認済みの要求要件・設計・テスト観点と指摘だけ（タスクの内容や経緯は渡さない）。
- 実装だけなら、そのまま差し戻して同じ PR を更新する。設計・要求要件まで戻す、または判断できないときは、人間の確認に回す。人間が選んだ戻し先に、取り込んだ指摘を引き継ぐ。

## 理由

- 戻し先をゴールガーディアンが判断すること、設計・要求要件まで戻すときに人間に確認することは、ステークホルダーと決めた。後者は、承認済みのものを変えることになるため（本文）。
- Request changes に限らずコメントも指摘として扱うのは、GitHub では自分の PR に Request changes を付けられず、同じアカウントでレビューしてもコメントで差し戻せるようにするため（本文。ステークホルダーの判断）。
- 2分待つのは、コメントは何件かに分けて書かれるため（本文）。
- 取り込み済みにするものと指摘にするものを同じ 50 件のバッチから作るのは、51 件目以降が指摘に反映されないまま取り込み済みになり、取りこぼすことがレビューで再現されたため（レビュー）。

## 影響

- PR の上のコメントが、そのまま差し戻しの指摘になる。
- ゴールガーディアンの判断の分、費用がかかる（予算に入れる）。
- フィードバックの一覧は、全ページを読んでから絞り込む。トークンを送るので、たどるのは API と同じ場所の URL だけにし、ページ数に上限を設ける。
