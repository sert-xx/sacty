# 受け入れ条件が詳しく、人に確かめることが無い依頼では、要求要件を省く

- 日時: 2026-11-02 23:57 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: PBI-283
- 置き換え元: なし
- 置き換え先: [受け入れ条件が明示した API の変更では、「公開 API の形を変える」を要求要件を残す理由にしない](20261103-0530-api-change-in-acceptance-keeps-no-requirements.md)（要求要件を残す条件のうち、公開している API・項目の名前や形を変える部分）

## 背景

実験で、全費用の9割前後が要求要件と設計だった（S8 で 93%、S10 で 92%）。
S5 は、依頼に受け入れ条件が詳しく書かれていたのに、オーケストレーターが要求要件を残した。要求要件で決めたのは細かい既定（空白・XX・列の位置）だけで、費用の8割（$24.35 / $30.20）を使った。
`direct`（要求要件・設計を省く）は、「局所的で既存の仕組みを使う変更」に限って選ばせていたため、3つの言語にまたがる S5 では選ばれなかった。

## 決定

- 依頼に、確かめられる受け入れ条件（入力と期待する結果・振る舞い・エラーのときの扱い・対象の範囲）がそろっていて、人に確かめることが無く（残るのは細かい既定を決めることだけ）、設計の判断も要らないときは、局所的でなくても `direct` を選ばせ、要求要件を省く。省いた理由を `reason`（工程の決定の理由）に書かせる。
- 次のどれかに当たるときは、受け入れ条件が詳しく見えても要求要件を残す（`skip-design` か `standard`）。判断しきれないときも残す。
  - 依頼が曖昧（S8）。
  - 依頼と文書・コードが食い違う（S9）、既存の方針（互換など）との食い違い（S10）。
  - 依頼に書かれていない判断を人に確かめたい。
  - 書き忘れていそうなことや、ほかのタスク・PR と同じ所を変える衝突が見える（S13）。
  - 既存の共有の状態・項目（フラグ・列・状態の種類）に新しい意味を載せる・状態を増やす（S13 の `isActive` に廃止・予約停止を載せる依頼のように、ほかの機能と食い違いうる）、または外に公開している API・項目の名前や形を変える（S10 の改名のように、使っている側と食い違いうる）。
- 要求要件を省いた実装は、細かい既定を既存の実装・規約に合わせて決め、実装の説明に「既定で決めたこと」の節を分けて書く。実装の説明は PR の本文に載るので、人は実装の PR で確かめる。依頼の受け入れ条件は1つずつ満たすことを確かめさせる。
- セルフレビューの回数・モデル・エフォートは変えない（人の方針は「品質は下げたくない」）。

## 理由

- 要求要件は費用の大半を占める。受け入れ条件がそろい、人に確かめることが無ければ、要求要件で決めることは細かい既定だけになり、費用に見合わない。細かい既定は、実装の PR で人が確かめられれば足りる。
- 曖昧・食い違い・言い忘れ・衝突は、人に確かめることなので、要求要件が要る。省く基準を厳しくするのは「受け入れ条件が詳しい」ことだけで、これらの依頼では省かない。
- 比べた案：
  - `skip-design` の説明を広げる案：要求要件が残るので、費用が下がらない。
  - 設計だけを残して要求要件を省く組み合わせを足す案：S5 のように設計を要さない依頼が実験の主な例なので、まず足さない。設計の判断が要る依頼は、受け入れ条件が詳しくても `standard`（要求要件が付く）にする。
  - 判断しきれないときも省く案：品質を下げないという方針に反するので、残す。

## 影響

- オーケストレーターの指示（`DETAILED_ACCEPTANCE_LINE`・`planDescriptions`）と、`direct` の実装の指示（`directImplementLines`）が変わる。組み合わせの種類・工程・セルフレビューは変わらない。
- 工程の見直し（工程が終わるごとに飛ばす判断）は変えていない。要求要件を省く判断は、タスクの初めの組み合わせの選択で行う。
- オーケストレーターは、集めた情報にあるものからしか食い違い・衝突を見られない。S13 のように、ほかのタスクがまだ PR を出していない並行の依頼は、依頼単体では詳しい受け入れ条件に見えるので、省かれうる（Sacty に並行するタスクを見る仕組みが無いため。残した制限）。
- 規則は[工程の選択](../spec/tasks-and-steps.md#受け入れ条件が詳しい依頼)に記す。
