# PR のリスク評価の段階を、合図の重さと、依存の版の更新の上げ幅で決める

- 日時: 2026-11-17 04:33 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: #408、PBI-377
- 置き換え元: [PR のリスク評価を出す（レビューの省略・自動のマージには使わない）](20261116-1632-superseded-pr-risk-assessment.md)
- 置き換え先: [依存の版の更新の上げ幅を読み取れないときは、PR のリスク評価の段階を中にする](20261117-0455-unknown-dependency-update-is-medium.md)（上げ幅を読み取れない依存の更新の段階。高から中に変えた。ほかの決定は、そのまま）

## 背景

PR のリスク評価は、8 つのリスクの合図のどれか 1 つに当たれば「高」にしていた。
このリポジトリの PR #394〜#404 のレビューに載った評価 38 回を数えると、次のとおりだった。

- 段階は、高が 35 回、中が 3 回、低が 0 回。段階では、レビューの深さを分けられていなかった。
- 高の回の合図は、性能・並行処理 24、不具合の疑い 21、取り消しにくい変更 16、構造・広い範囲の変更 15、確かめていない振る舞い 13、大きな差分 11、セキュリティ 10、互換性の変更 7。
- 合図が 1 つだけで高になった回が 5 回あった。うち 3 回は「不具合の疑い」だけ、2 回は依存のパッチの更新（3 ファイル）の「セキュリティ」だけだった。
- 「不具合の疑い」は、レビューが指摘を 1 件でも持つと付く傾向があった（同じ PR で、指摘のある回は高、指摘なしの回は中）。
- 依存のパッチの更新は、既知の脆弱性を直す更新で、リスクを下げる変更だった。

リポジトリの持ち主が、この事例を見た上で、基準を決め直した（2026-11-17）。

## 決定

- 合図に、重い・軽いを付ける。
  - 重い合図：セキュリティにかかわる振る舞いの変更、取り消しにくい変更、互換性の変更。1 つでもあれば「高」。
  - 軽い合図：性能・並行処理、構造・広い範囲の変更、大きな差分、確かめていない振る舞い。軽い合図だけなら、2 つ以上で「高」、1 つなら「中」。
  - 「不具合の疑い」は、合図から外す。
- 依存の版の更新だけの PR は、上げ幅で決める。メジャーは「高」、マイナーとパッチは「低」。
- 変えないこと：段階は 3 つ。点数は出さない。評価でレビューを省かない・自動でマージしない。RADAR に関するスキルやコンテキストが読み込まれていれば、それを基準より優先する。

ここまでが、人の決定である。次のことは、実装のときに、安全な側（段階が高く出る側）で決めた。

- 段階は、合図の重さと上げ幅から、sacty が決める。合図があるときは、エージェントが付けた段階を使わない。合図が無いときは、エージェントが付けた段階のままにする（高も、そのまま）。
- 「セキュリティ」の合図は、セキュリティにかかわる振る舞いを変える変更に付けさせる。脆弱性を直すための依存の版の更新には付けさせず、上げ幅で決める。
- 依存の版の更新そのもの（版の指定の変更と、そこから機械的に作られるファイルの変更）には、合図を付けさせない。
- 上げ幅を読み取れない更新（版の付け方が分からない、番号の版ではないもので指している、更新の前か後の版を確かめられない、版を下げている、など）は「高」にする。
- その依存の版の付け方で、互換性を約束していない上げ幅は、メジャーと同じに扱わせる。
- 複数の依存を更新するときは、いちばん大きい上げ幅で決める。依存を新しく足す・外すことは、版の更新として扱わない。
- 依存の版の更新と一緒に、ほかのコードや設定を変えているときは、その変更を合図と安全な種類で決め、高いほうにする。
- sacty が自分で段階を上げるのは、メジャーと、上げ幅を読み取れない更新だけ。マイナー・パッチの更新だけの変更が「低」になるのは、エージェントが合図を付けず、低と答えることによる。
- 上げ幅が決めた値でない答えは、読めないものとする（上げ幅を読み落として、低い段階を載せないため）。上げ幅の項目が無い答えは、更新が無いものとして読む。
- 「不具合の疑い」は、以前の記録を読むために、記録の型には残す。答えにあれば読み捨てる。
- PR の説明・レビューのコメント・画面で、合図の名前に重さを添え、依存の版の更新があれば上げ幅を出す。

## 理由

- 重い・軽いを分けたのは、合図によって、外れたときの影響が違うため。重い合図の 3 つは、変更を元に戻すだけでは済まないか、変更の外にいる利用者に及ぶ。軽い合図の 4 つは、読む手間や見落としやすさを示すが、1 つだけでは、設計から確かめる深さまでは要らない。
- 「不具合の疑い」を外したのは、不具合があるかどうかは、レビューの指摘と判定が別に示すため。評価は、変更そのもののリスクを示すものにする。
- 依存の更新を上げ幅で決めるのは、差分（版の指定と、機械的に作られるファイル）を読んでも、リスクを判断できないため。互換性の約束は、上げ幅が示す。
- 合図があるときにエージェントの段階を使わないのは、同じ合図の組に、同じ段階を付けるため。エージェントには「迷ったら高いほう」と指示しているので、エージェントの段階を残すと、軽い合図が 1 つでも高になりやすい。
- 合図が無いときにエージェントの高を残すのは、読み込まれた RADAR のスキル・コンテキストで段階を決めた答えを、下げないため。
- 上げ幅を読み取れない更新を高にしたのは、メジャーかもしれない更新を、低として載せないため。人の決定には無いので、持ち主の確認が要る。
- マイナー・パッチの更新だけかどうかを sacty が差分から確かめないのは、依存の書き方が、言語や道具ごとに違うため。sacty の基準は、あらゆるリポジトリの対象に渡る。
- 重さを名前に添えるのは、人が、段階の理由（重い合図が 1 つか、軽い合図が 2 つか）を、基準の表を引かずに追えるようにするため。
- 点数にしない理由は、置き換え元の ADR のとおり（障害の実績から学習したモデルが無い）。重さは 2 種類だけにし、数値の重みにはしない。

## 影響

- 段階の決め方と、合図の種類が変わる。評価する場面・載せ方・評価できなかったときの扱い・評価でレビューを省かないことは、置き換え元の ADR のまま。
- 以前の記録（合図に「不具合の疑い」がある・古い基準で高になった評価）は、そのまま読めて、そのまま表示される。評価し直さない。
- 新しい決まりで PR #394〜#404 の先頭のコミットを評価し直すと、低 1・中 7・高 3 に分かれた（評価の指示を、別のエージェントに 1 回ずつ渡して確かめた。実際のレビューの工程では確かめていない）。
- 実物の 38 回の合図の組に、段階の決まりだけを当てはめると、高 32・中 6 だった。合図そのものが、古い基準（1 つでも当たれば高）のもとで多く付いていたためで、段階が分かれるかどうかは、エージェントが合図をどれだけ絞って付けるかによる。
- マイナー・パッチの更新だけの変更を低にするのは、エージェントの読みによる。エージェントが上げ幅を読み違えると、メジャーの更新が低として載りうる。
