## 背景

GitHub へのアクセス（PR の作成・レビューの投稿・指摘の読み込み・clone とプッシュ）は、すべてデーモンがホストで、プロジェクトの gh の
アカウントで行っていた。エージェントのコンテナには `gh` もトークンも無い（選んだ AI の認証だけを渡す決まり）。

利用者が自分で PR を作り、レビューの指摘への対応だけを依頼したタスクで、オーケストレーターは「作業」（`operation`）を選び、作業の
エージェントは PR の情報を読もうとして `gh` を使い、失敗した（ステークホルダー、2026-10-21）。PR の情報をエージェントに渡す仕組みが無く、
作業の工程は、オーケストレーターが選んだ接続先（MCP・PF）1つしか使えなかった。

ステークホルダーの依頼は次のとおり。

- 少なくとも、読み取りの `gh` の操作を、ゲートウェイ経由でできるようにする。
- その仕組みは、既定で有効にし、設定で変えられないようにする。
- 「作業」などの工程でも、ゲートウェイ経由で PR の情報を読み、対応の結果を PR に投稿するための出力ができるようにする（エージェントが決まった
  形で頼み、sacty が投稿するのでもよい）。

## 決定

- ゲートウェイに、GitHub の読み取りの中継（`/r/<実行のトークン>/github/<ホスト>/<パス>`）を足す。設定は無く、切れない。
  - タスクのプロジェクトでホストごとに選んだ gh のアカウントを、実行に結びつける。トークンはホストで取り出してゲートウェイが付け、
    コンテナには渡さない。
  - REST の `GET`・`HEAD` と、GraphQL の `query` の操作だけを送る。書き込みは断る。
  - ページ送り（`link`）とリダイレクト（`location`）の API の URL は、中継の URL に書き換える。
- 文書作成（`document`）の実行を除く、タスクのすべての実行（工程・オーケストレーター・ゴールガーディアンなど）に、中継の URL
  （`SACTY_GITHUB_URL`）・ホスト・既定のホスト（`GH_HOST`）を渡し、指示の末尾に読み方を足す。
- エージェントのイメージの `gh` を、`gh api` だけを中継に送るもの（`packages/cli/docker/gh-shim.cjs`）にする（`PATH` の先頭に置く）。
- PR・Issue への投稿は、エージェントにさせない。エージェントは、工程の出力に `sacty-github-comments` の JSON で投稿の内容を書き、人間が
  その工程の成果を承認した後に、sacty がプロジェクトの gh のアカウントで投稿する。投稿先は、プロジェクトの対象（と、タスクの取り込み元・
  作業するリポジトリ）の PR・Issue だけ。結果は `GitHubCommentsPosted` に記録する。レビューの工程は、これまでどおり書いたレビューを投稿する。
- 単発作業の接続先に `github`（`name` はホスト）を足す。オーケストレーターの接続先の候補に、gh のアカウントを選んだホストを出す。

## 理由

- 読み取りをゲートウェイの中継にしたのは、トークンをコンテナに入れないため（選んだ AI の認証だけを渡す決まりを守る）。本物の `gh` に
  `GH_TOKEN` を渡す案は、トークンがコンテナに入り、出力から伏せる対象も増えるので採らなかった。
- 本物の `gh` をイメージに入れて中継に向ける案は、`gh` が HTTPS の API にしか送らず、ゲートウェイは HTTP なので、中継に向けられない。
  また、プライベートのレジストリだけを使う環境では、`gh` を取得できないことがある。`gh api` だけを受ける小さな代わりにした。`gh pr view`
  などのほかのコマンドは使えないが、使えないことと `gh api` の使い方を示す。
- 書き込みを中継で許さず、承認の後に sacty が投稿するのは、エージェントの出力（PR の説明・コメントに書かれた指示に影響されうる）が、
  人間の確認なしに外部に出ないようにするため。成果の書き出しと同じく、承認を外部への反映の境界にした。
- 投稿先をプロジェクトの対象に限るのは、エージェントに、ほかのリポジトリへ書かせないため。読み取りは、アカウントが読めるものに限られ、
  GraphQL では対象のリポジトリに絞れないので、絞らない。
- 文書作成を除くのは、承認の前に外部の接続を渡さないと決めたため（置き換え元の ADR の文書作成の部分は変えない）。
- 設定で切れないようにしたのは、ステークホルダーの依頼による。読み取りだけで、アカウントを選んだホストだけなので、いつも渡してよいと判断した。

## 影響

- 単発作業は、選定した接続先に加えて、GitHub を読める（書き込みは、承認の後の sacty の投稿だけ）。
- エージェントの指示が、GitHub の読み方の分だけ長くなる。
- `gh` を使うには、イメージを作り直す必要がある。作り直す前のイメージでも、curl では読める。
- エージェントの出力に書かれた投稿は、承認の後に外部に出る。承認する人が、投稿の内容（成果の末尾の JSON）を確かめる必要がある。
- 既存の PR に修正を積む（プッシュする）ことは、まだできない。コードを直すタスクは、これまでどおり新しい PR になる。
