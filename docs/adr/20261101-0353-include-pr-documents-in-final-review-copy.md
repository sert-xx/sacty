# 最終レビューの作業領域の写しに、実装の PR に入る要求要件・設計の成果物を PR のコミットの内容で入れ、リポジトリ全体の検査を PR と同じ中身で行わせる

- 日時: 2026-11-01 03:53 UTC
- ステータス: 採用
- 関係する PR・タスク: #262、PBI-262
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験（S4 の試行 1・2、S6、S7 の計 4 回）で、リポジトリ全体を対象にする検査（`prettier --check .`）が、最終レビューの作業領域の写しでは通り、PR の中身では落ちることが繰り返された。
Sacty は、承認済みの要求要件・設計を、対象リポジトリの PR に `docs/sacty/<タスクの短い ID>/` のファイルとして入れる。
このファイルは、実装の作業領域にも、最終レビューの写しにも無い（実装の PR のコミットを作るときに、タスクブランチから引き継ぐ）。
そのため、ゴールガーディアンの検査は成果物を含まない状態で実行され、通って見える。PR では、整形されていない成果物のファイルで落ちる。
毎回、人が PR で気づいて差し戻し、`.prettierignore` に行を足して直った（タスクごとに行が増える。S7 では、足した設定を確かめるだけのテストまで増えた）。

直前の変更（#260）で、最終レビューの指示に「写しで通った、リポジトリ全体に効く検査は、PR の中身では未確認として `humanChecks` に書いて人の確認に回す」と足した。
しかし、最終レビューは合格のままで、人が確認して差し戻す手間は減らなかった。#260 は、写しに成果物を足す変更を、判断が要るとして範囲から外していた。

人が決めた方針は「写しに含めて検査」。最終レビューの作業領域に、PR に入る成果物を入れ、PR と同じ中身で検査する。落ちれば実装が直す（人の差し戻しは要らない）。

## 決定

1. **最終レビューの写しに、成果物のファイルを PR のコミットの内容で入れる。**
   - 入れるファイルは、要求要件・設計の PR のファイルのパス（実装の PR のコミットを作るときに引き継ぐものと同じ一覧）。内容は、最終レビューの前に作った実装の PR のコミット（`pullRequestCi.commit`。CI を待つコミット）にあるもの。
     タスクブランチの最新ではなくこのコミットにするのは、PR の中身そのものになり（人が PR の中で直してマージした内容も含む）、ネットワークや認証が要らず（作った時点で退避したメタデータにある。用意し直したときだけ取得する）、検査した対象が CI の対象と同じコミットになるため。
   - 写しにあった同じパスのファイルは置き換え、コミットに無いパスは写しからも消す。PR のコミットを作るときの `keep`（実装が成果物のパスに書いた内容は PR に残らない）と同じ扱い。写しの中のリンクはたどらない（途中のディレクトリがリンクなら消してから書く）。
2. **実装の工程の作業領域には入れない。**
   - 実装の作業領域は、そのままコミットの元になり、差分・変更の範囲（セキュリティ対応の範囲の照合）・文書だけの差分の判定・ベースブランチの取り込みの対象になる。成果物を入れると、sacty が置くファイルが実装の変更として混ざり、範囲・過剰さの判定を誤らせる。
   - 実装のエージェントが書き換えても、PR には残らない（`keep`）。入れると、書き換えられる文書が見えてしまう。
   - 実装のエージェントは、成果物で落ちる検査を、最終レビューの指摘で知る（やり直しの上限の中で直る）。
3. **最終レビューの指示（`pullRequestContentLines`）を、写しに入れたかで分ける。**
   - 入れたとき：検査は PR と同じ中身で実行される。成果物が原因の失敗も不合格の理由にする（人の確認に回さない）。成果物は実装の変更ではなく差分に出ないので、変更の範囲・過剰さ・観点の判定に含めず、中身（要求要件・設計の文面）をレビューしない。
   - 入れられなかったとき：#260 で足した指示のとおり。写しで通った検査は、PR の中身では未確認として人の確認に回し、写しで失敗した検査は不合格のまま。コミットを取得できない場合と、成果物のファイルを写しに書けない場合（通常のファイルでない・1 MiB を超える・UTF-8 のテキストでない）は、どちらも最終レビューを止めずに、警告を出してこの指示で続ける。ファイルの確かめは、写す前に `readFile` で行い、写しの作成の途中で失敗して止まる経路を作らない（指示が、写しに入れたかと食い違わない）。ネットワークや成果物の例外の都合で、最終レビュー全体を止めるより、未確認として人の確認に回すほうが、これまで（#260）の挙動と揃う。
   - 成果物を PR に足さないタスク（要求要件・設計の PR が無い・既存の PR を引き継ぐ）では、節を入れず、写しにも入れない。
4. **成果物で検査が落ちたときの直し方を、指摘に書かせる。**
   - 成果物は sacty が置く承認済みの文書で、実装が書き換えても PR に残らないので、ファイルの書式を直させない。
   - 検査の設定（`.prettierignore`・markdownlint の除外など）を、リポジトリの方針に合わせて直させる。リポジトリにすでに生成物・文書の扱いがあればそれに従う。無ければ、置き場所が sacty 専用の既定の `docs/sacty/` なら、それをまとめて対象外にする。オーケストレーターが既定でない置き場所（`docs/` など）を決めたときは、リポジトリのほかのファイルと共有されうるので、その全体を対象外にすると他のファイルの検査が外れる。タスクの ID のディレクトリに当たる範囲（パターン）に限らせ、置き場所の全体は対象外にしない。どちらも、タスクの ID ごとのファイルやディレクトリを 1 つずつ足さない。
   - この設定の直しは、検査を通すために必要な変更なので、変更の範囲外・過剰とはしない。ただし、設定を確かめるだけのテストは足させない（S7 で、`.prettierignore` の中身を確かめる 34 行のテストが足された）。
5. **実装のやり直しの指示でも、成果物のせいで落ちたことを伝える。** 最終レビューの不合格で、テストだけが理由のとき、やり直しの指示（`feedbackLines`）は「実装で直る失敗が無ければ、無関係な変更を足さない」と伝える。実装の作業領域には成果物が無いので、原因が見えず、変更の無い再提出を繰り返して一時停止しうる。そこで、成果物を PR に足すタスクでは、次を伝える。
   - 成果物が PR に入ること、書き換えても残らないこと、そのファイルで検査が落ちているときは書式ではなく検査の設定をリポジトリの方針に合わせて直すこと（決定 4 と同じ直し方）。「無関係な変更を足さない」の文は、成果物のファイルで落ちた検査も直す対象に含める。
   - 最終レビューの所見・テストの出力・観点の理由に、このタスクの成果物のディレクトリのパスが出ていれば、そのパスを挙げて、変更の無い再提出をしないよう伝える。ゴールガーディアンの指摘の書き方に頼らず、sacty が出力の文字列から見つける。別のタスクの ID のディレクトリは、このタスクの成果物とは見なさない。

## 理由

- 検査を PR と同じ中身で実行すれば、通るか落ちるかが判定できる。#260 の「未確認として人の確認に回す」では、判定が人に残り、合格のまま差し戻しが続いた。
- 写しのコミットを PR のコミットにするのは、PR のコミットが、検査したい対象そのもの（CI が見るコミット）だから。成果物のパスの一覧が同じなので、`keep` と食い違わない。
- 実装の作業領域に入れない理由は、決定 2 のとおり。入れる案は、差分・範囲・文書だけの判定・ベースブランチの取り込みの 4 か所で、成果物を除く処理が要り、漏れると範囲の判定が誤る。写しだけなら、差分を取る処理は変わらない。
- 直し方を指示に書くのは、失敗の直し方が、実装のエージェントにとって自明でないため。成果物は書き換えても残らないので、書式を直す方向に進むと直らない。タスクごとに行を足すと、タスクのたびに設定が増える（S6・S7 で実際に起きた）。
- 比べたほかの案（採らなかった）：
  - 実装の作業領域にも成果物を入れる案：決定 2 のとおり、範囲の判定を誤らせるので採らない。実装のエージェントが事前に気づける利点はあるが、最終レビューの指摘で直る。
  - sacty が、成果物をリポジトリの整形に合わせて書く案：リポジトリごとの整形（言語・ツール）を sacty が知る必要があり、範囲外。
  - 成果物のディレクトリを、sacty が検査の対象外に足す案：対象のリポジトリの設定ファイルを sacty が書き換えることになり、リポジトリの方針に従う判断が要る。実装に、方針に合わせて直させる。

## 影響

- 成果物を PR に足すタスクで、リポジトリ全体の検査が成果物で落ちるときは、最終レビューが不合格になり、実装がやり直す。人が PR で気づいて差し戻す手間は要らない。やり直しは、最終レビューの不合格の上限（`MAX_VERIFY_ATTEMPTS`）の中で数える。
- ゴールガーディアンは判定を LLM で行うので、指示のとおりに不合格にするかは、指示の文言に依存する。写しに成果物が入ることと、検査が成果物で落ちることは、テストで確かめた（指示の判定自体はテストで確かめられない）。
- 写しには、実装の作業領域に無い成果物が入る。ゴールガーディアンが写しで `git status` を見ると、成果物が未追跡のファイルとして見える。
- コミットを取得できず写しに入れられなかったとき（ネットワークや認証の失敗）は、これまで（#260）と同じ挙動に戻る。気づけるのは、デーモンの警告と、最終レビューの「人が確かめること」。
