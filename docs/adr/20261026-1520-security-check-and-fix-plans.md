# セキュリティチェックとセキュリティ対応を、既存の工程の組み合わせとして足し、対応の差分を修正の範囲と照らして最小限に保つ

- ステータス: 採用

## 背景

依存の脆弱性やサプライチェーン攻撃への備えとして、sacty で次の2つを扱いたいという要望があった。

- セキュリティチェック（成果物はレポート）
- セキュリティ対応（成果物は PR）

対応は、チェックのレポートから始めることも、特定の問題（CVE・GHSA・アラート）から直接始めることもある。
対応の PR は、問題を解消する最小限の変更でなければならない。リファクタリングなどが混ざるとレビューに時間がかかり、修正が遅れるため。

## 決定

- 新しい工程は作らず、工程の組み合わせ（`STEP_PLANS`）を2つ足す。
  - `security-check`：`investigate` だけ。区分（`dependency`・`supply-chain`・`code`・`secret`・`config`）ごとに点検させ、レポートの本文の後に、見出し `sacty-security-findings` の JSON で指摘の一覧を出させる。人が画面で承認する。
  - `security-fix`：`investigate` → `implement` → `deployment`。要求要件・設計は置かない。前段の調査で問題を確かめ、修正の範囲（変えてよいファイル・上げる依存・解消を確かめるコマンド）を、見出し `sacty-security-scope` の JSON で宣言させる。範囲の宣言は人が承認しない（最終的な PR で人が確かめるため）。
- 最小限の変更は、指示だけでなく、次の2つで守らせる。
  - sacty が、実装の差分を修正の範囲と照らす。範囲の外のファイル（テストのファイルは除く）を変えた、またはロックファイルを除いて 300 行を超えて変えたら、最終レビューの観点 `SEC-MIN` を、ゴールガーディアンの判定にかかわらず不合格にする。
  - ゴールガーディアンが、最終レビューで観点 `SEC-MIN`（差分の変更ごとに修正に要るか）を判定する。観点 `REQ` は「問題が解消したか」で、範囲の宣言の確かめのコマンドを実行して確かめさせる。
- 承認したセキュリティチェックのレポートから、区分ごとに1つずつ対応のタスク（`start: security`・進め方 `security-fix`）を作れるようにする。説明には、その区分の指摘だけを入れる。
- テンプレート `security-check` を足す（進め方を `security-check` に決める）。スケジュールタスクから定期的に点検できる。
- セキュリティの組み合わせのタスクでは、成果（レポート・範囲）を取り込み元の Issue・PR にコメントしない。PR・Issue へのコメントの頼み（`sacty-github-comments`）も投稿しない。
- 公開リポジトリへの対応の PR は、ほかの実装と同じく作る（プッシュの前に人の確認を待たない）。
- 既定のイメージに、検査の道具 osv-scanner と gitleaks を足す。版を固定し、同じリリースのハッシュのファイルで確かめて入れる。

## 理由

- 成果物の形（承認するレポート・マージで承認する PR）は、今の調査と実装の工程で足りる。工程を作ると、承認・差し戻し・一時停止・片付けを作り直すことになる。
- 指示だけでは最小限の変更は守られない。sacty が機械的に確かめられること（ファイル・行の数）は sacty が確かめ、変更ごとの要否のように読まないと判断できないことはゴールガーディアンに判定させる。
- ロックファイルは、依存を1つ上げるだけでも大きく変わるので、行の数に数えない。中身が範囲の依存だけかは、ゴールガーディアンに確かめさせる。
- 対応のタスクを区分ごとにすると、1つの PR の変更の種類がそろい、レビューしやすい（利用者の判断）。
- 範囲の宣言を人が承認しないのは、急ぎの対応を遅らせないためと、範囲は最終的な PR の本文に出て人が確かめられるため（利用者の判断）。
- レポートや範囲は攻撃の手がかりになるので、公開されうる Issue・PR には書かない。公開リポジトリへの PR そのものは、利用者の判断で止めない。
- ハッシュをこのリポジトリに固定する方法（draw.io と同じ）は、決めた時点でリリースの添付物を取得できず、ハッシュを確かめられなかったので採らなかった。リリースのハッシュのファイルで確かめれば、壊れた取得は止められる（リリースそのもののすり替えは防げない）。
- 比べた案：
  - `bugfix` のように再現の工程を置く。依存・設定の更新では再現のテストを書けず、工程を飛ばす判断が増えるので、コードの脆弱性の回帰のテストは実装の工程で書かせることにした。
  - 範囲の外を変えたら実装の工程を止める。範囲の外を変えずに直せることが多く、やり直しで直るので、最終レビューの不合格にして実装をやり直させる。

## 影響

- 変えた行の数の上限（300 行）は、設定では変えられない（`SECURITY_FIX_MAX_CHANGED_LINES`）。
- 範囲の外を変えないと直せないときは、実装が理由を説明に書き、検証が続けて通らなければ一時停止する。人が前段の調査に差し戻して範囲を広げる。
- 指摘の一覧と範囲の宣言は、調査の成果物の本文に JSON のまま残り、sacty は必要なときに本文から読む。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の「セキュリティチェックとセキュリティ対応」、利用者向けは [タスクを進める](../user/tasks.md) に書く。
