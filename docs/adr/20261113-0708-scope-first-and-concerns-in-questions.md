# 要求要件・設計はスコープを最初に置き、人への確認には確認しない場合の懸念を添える

- 日時: 2026-11-13 07:08 UTC
- ステータス: 採用
- 関係する PR・タスク: #363
- 置き換え元: なし
- 置き換え先: なし

## 背景

人から、sacty が書く文章について次の要望があった。

- 要求要件・設計が要求の一覧から始まり、スコープが意図どおりかを読み取るのがつらい
- 人への確認に、確認しないとどうなるかが書かれておらず、確かめる手間に見合うかを判断しにくい
- 英語を単純に訳した語（entry point →「入口」）や、一般的でない言い回しが混じる
- 「。」の後の改行が、書き出し先（GitHub と Confluence など）によって表示に出ない

## 決定

- 要求要件・設計は、「スコープ」「確認したいこと」「既定で決めたこと」の順に節を置き、詳細はそのあとに書かせる（`readerLoadLines`）。
  スコープには、何を実現するか（1〜3文）と、対象・対象外を書かせる。
  対象外は、読む人が含まれると思いそうなものだけにし、当てはまらない観点のための「対象外」は引き続き書かせない。
- 「確認したいこと」の1件ごとに、確認しないまま推奨の答えで進めた場合の具体的な懸念を書かせる。
  人が確かめること（`humanChecks`）も、確かめないまま進めた場合の懸念を添えさせる。
- 既定の規則（`rules.md`）で、人に確認・判断を求めるときは、確認しない場合の具体的な懸念を項目ごとに1〜2文で添えるよう求める。
  一般論にせず、懸念のために文章を長くしない。
- 既定のスキル `writing` に、書き出し先ごとの改行の書き方、英語を直訳しないこととカタカナ語の扱い（`references/wording.md`）、人に確認を求める書き方、要求要件・設計の並べ方を足す。

## 理由

範囲が先に分かると、読む人は要求を1つずつ読む前に、範囲のずれに気づける。
懸念が書かれていれば、読む人は推奨のまま承認してよいかを、その項目だけで決められる。
懸念を書けない項目は、人に聞くまでもないと作者が気づける。

## 影響

- 要求要件・設計の冒頭が1節増える。
  スコープの節の分だけ、分量の目安を、小さな変更で 20 行から 25 行に、大きな変更で 60 行から 65 行ほどに増やす（`DRAFT_LINES`）。
- 自己レビューの D-10 で、スコープが最初にあるかと、確認したいことに懸念があるかを見る。
