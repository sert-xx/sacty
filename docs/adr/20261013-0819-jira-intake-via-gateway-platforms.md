# JIRA のチケットは、gateway.platforms の接続先をそのまま使い、プロジェクトに書いた取り込み先からラベルで取り込む

- 日時: 2026-10-13 08:19 UTC

- 関係する PR・タスク: #62、PBI-52
- 置き換え元: なし
- 置き換え先: なし

## 背景

GitHub の Issue・PR のほかに、JIRA（Jira Cloud・Jira Server / Data Center）のチケットもタスクとして取り込みたい。
JIRA の接続と認証をどこに持つか、どのチケットを取り込むか、結果をどう返すかを決める必要があった。

## 決定

- 接続先は `gateway.platforms` の外部の PF（プラットフォーム）の設定をそのまま使い、JIRA 専用の設定は足さない
  （Asana・Linear なども同じ仕組みで足せる）。
- プロジェクトの設定に、取り込み先（接続先・種類・JIRA のプロジェクトのキー）を複数書ける。接続先は `gateway.platforms` から選ぶ。
  同じ接続先の同じキーは、1 つのプロジェクトにだけ書ける。
- 「sacty の設定」に、チケットの取り込むラベル（すべての取り込み先で共通）と On/Off を置く（PBI-53 と同じ形）。
- デーモンは、ラベルの付いた、終わっていないチケットのキーと要約だけを探してタスクにする。二度は取り込まない。
  Cloud は `/rest/api/3/search/jql`（nextPageToken）、Server / DC は `/rest/api/2/search`（startAt）で、ページを送って読む
  （1 回の取り込みで最大 10 ページ）。上限で止めたら続きの位置を持ち、次の回にそこから読む。最後まで読んだら先頭に戻り、
  検索に失敗したら先頭から読み直す。
- 調査の結果と PR の URL をチケットにコメントする（チケットの状態は変えない）。
- `allow` に無い API は、デーモンも呼ばない。失敗の理由に含まれる認証の値は、伏せてから切り詰める。コンテナには、実行ごとの
  ゲートウェイのトークンだけを渡す。

## 理由

- JIRA 専用の設定を足さず `gateway.platforms` を使う理由として、Asana・Linear なども同じ仕組みで足せることが書かれている（PR の本文）。
  それ以上の理由と、比べたほかの案は記録に無い。
- 検索の続きを次の回に引き継ぐのは、レビューで、対象の終わっていないチケットが 500 件を超えると、毎回先頭の 500 件を読み続けて
  残りを取り込めないことがわかったため（レビューとその返信）。
- 状態を変えずにコメントだけ返す理由は記録に無い。

## 影響

- JIRA を使うには、`gateway.platforms` に接続先を書き、`allow` に必要な API を書く（README に設定の例）。
- 実際の JIRA（Cloud・Server / DC）での動作は、偽の JIRA のテストでしか確かめていない。
- 取り込みの状態（検索の続きの位置）を、検索の条件ごとに持つ。
