# エージェントを段階で固定し、sacty が接頭辞を外した名前でサブエージェントの定義を置き、スキルは段階の名前で担当を起動する

- ステータス: 採用
- 関係する PR・タスク: PBI-119
- 置き換え元: なし
- 置き換え先: なし

## 背景

`config.yaml` の `agents` は利用者が好きな名前で書き、`step_agents` で工程ごとに選ぶ。サブエージェント（既定の review スキルの観点担当）は
親のモデルを引き継ぐだけで、観点ごとに違う強さのモデルを使えなかった。モデルの世代が変わるたびに、スキルや設定のあちこちを直すのも避けたい。
Claude Code と Codex では、サブエージェントの定義の置き方と形が違う（Claude Code は `agents/<名前>.md` の frontmatter、Codex は
`agents/<名前>.toml`）ので、スキルにツールごとの書き方を持ち込みたくない。

## 決定

- `agents` の名前のうち `claude_<段階>`・`codex_<段階>` を段階のエージェントとして扱う。段階は `lite`・`entry`・`standard`・`advanced`・`ultimate`
  の 5 つ。新しい節は作らず、今の `agents` の書き方のまま（`step_agents` にも書ける）。接頭辞と `runtime` が合わなければ設定の誤り。
- 工程を動かすとき、その runtime の段階のうち、工程のエージェントと認証・接続先（`auth`・`endpoint`・`via_gateway`）が同じものだけを、
  接頭辞を外した名前のサブエージェントの定義として設定の場所に置く（Claude Code は `agents/<段階>.md`、Codex は `agents/<段階>.toml`）。
  サブエージェントは親と同じプロセスで動き、接続先は親のものを使うため。違う段階は置かず、`agents.tierConnectionDiffers` を注意に残す。
- 段階の定義に渡すのは `model`・`reasoning_effort` だけ。書いていなければ、親のモデルを引き継ぐ定義にする。
- コンテキストリポジトリに同じパスがあれば sacty のものを使い、`context.reservedTierFile` を警告する。置いた段階は `ContextResolved` の
  `tiers` に記録し、コンテキストのプレビューにも同じファイルを出す。
- review スキルは、観点カタログの「観点ごとの段階」で観点ごとに段階を決め、親はその名前のサブエージェントを指定して担当を起動する。
  定義が無い段階は親と同じモデルで起動し、起動表に「親と同じ」と書く。逐次モードは変えない。
- 段階の名前はステークホルダーの案のまま（より適切な名前があれば変えてよい、との指示）。

## 理由

- 同じスキルの定義で、どちらのツールでも同じ段階の担当を起動できる。利用者は段階のモデルを 1 か所直すだけで最新モデルに追従できる。
- 新しい節を作らず `agents` の名前で分けたのは、段階のエージェントも普通のエージェントとして工程に使えるようにし、設定の形を増やさないため。
- 接続先が違う段階を置かないのは、親のトークン・接続先で別の契約のモデル名を黙って呼ばないため。
- 段階ごとの担当の費用は、今の仕組み（親の結果の使用量 × 親の単価）では正確でない。実行のログから担当ごとの使用量を取る仕組みは、
  この決定の範囲外（仕様書に概算のまま、と書く）。

## 影響

- `config.yaml`：`claude_<段階>`・`codex_<段階>` の名前が予約になる。雛形に例を足す。
- デーモン：段階の選択（`apps/daemon/src/agents/tiers.ts`）、設定の場所への配置（`planContext` の `extraFiles`）、作業履歴とプレビュー。
- 既定の review スキル：観点カタログの「観点ごとの段階」、起動表の「段階」の列、担当への依頼の指定。
- 確かめていないこと：worker が実際に段階の名前でサブエージェントを起動する様子（作業履歴に書く）。
