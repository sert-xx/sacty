# 承認する人が見る所を絞るため、要求要件・設計の項目の出典を、書いたエージェントとは別のサブエージェントに分類させる

- 日時: 2026-10-27 14:27 UTC
- ステータス: 採用
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件・設計は、EARS の文型で書かせているので項目が多くなる。
承認ゲートは要るが、承認する人の負担はできるだけ小さくしたい。
そこで、どこを注意して見るべきかを、承認する人に示す必要があった。
タスク・チケット・人の指摘に書かれたことを、そのまま項目にしたものは、意図に沿っている見込みが高いので、ざっと見ればよい。
逆に、Input に無く、検討の途中やセルフレビューで足したものは、意図に沿っていない可能性があるので、確かめる必要がある。

## 決定

- 確度のような指標は作らず、項目ごとの出典を、引用（`input`）・導出（`derived`）・推論（`inference`）に分ける。
- 分類は、成果物を書いたエージェントではなく、既定のスキル `classify-provenance` に従うサブエージェントにさせる。
  書いたエージェントは、担当を1つ起動し、答えを手を加えずに見出し `sacty-provenance` の JSON で付ける。
- 担当には、sacty が作業領域の外に読み取り専用で置いた Input（タスクの内容・指摘・調査の結果・承認済みの要求要件）と、最終版だけを読ませる。
  依頼文には、Input の要約・言い換えと、書いた経緯・どの項目を足したかを書かせない。
- 引用には、Input の原文を整形せずに抜き出させる。
  sacty は、空白・Markdown の記号・文字の形をそろえた上で、抜き出しが Input にあるかを照らす。
  要求の文そのものと Input の意味の近さは見ない。
- 人が確かめる項目は、推論・原文の見つからない引用・分類の無い項目にする。
  サブエージェントを起動できず、書いたエージェントが自分で分類した（逐次モード）ときは、すべての項目にする。
- 人間の承認でどう使うかは、書いたエージェントへの指示に書かない。
- 結果は記録し、成果物のカード・承認の画面・要求要件と設計の PR の本文に出す。
  答えが無くても工程は止めない。

## 理由

- 確度をエージェントに自己申告させると、ほとんどが高になる。出典の種類で分ければ、指標は要らない。
- 要求の文は整形されるので、要求の文と Input を機械で突き合わせるには意味の近さを見る必要があり、難しい。
  抜き出しは原文を写せばよいので、実在するかを部分一致で確かめられる。
  照らせるのは根拠が実在することまでで、根拠から要求を導いた解釈が正しいかは確かめられない。
  それでも、言い換えた・作った根拠は安く見つけられる。
- 書いた本人に分類させると、ごまかす動機が無くても、自分で足したものを Input 由来だと思い込みやすい。
  導出のような境界のあいまいな区分にも寄りやすい。
  書いていない担当なら、どの区分にしても得も損も無い。
- sacty は自分自身のリポジトリも開発するので、使い道を伏せきれない。分類を別の担当にすれば、伏せることに頼らなくてよい。
- 依頼文と答えの受け渡しは書いた本人が行うので、汚染が入る余地が残る。
  Input をファイルで渡させて要約を挟ませず、抜き出しは sacty が照らすことで、その余地を小さくした。
  分類のラベルの書き換えまでは防げないが、使い道を書いていないので、書き換える動機は小さい。
- sacty が分類を別の実行として起動する形は、工程と台帳のイベントが増える。
  まずは工程の実行の中のサブエージェントで始め、汚染が見られたら移す。スキルはどちらでも使える。

## 影響

- 要求要件・設計の工程の実行に、分類の担当の分の費用と時間が足される。
- 設計で分類するのはテスト観点（`TV-n`）だけで、設計の本文の判断は分類しない（本文の「既定で決めたこと」で示す）。
- テスト観点の ID は sacty が項目の欠けた観点を除いて振るので、担当が JSON の順で数えた ID とずれることがある（欠けた観点があるときだけ）。
- 区分の付け方が合っているかを、差し戻しの実績で確かめる仕組みは、まだ無い。
