# 既存の PR を直すタスクは、PR を引き継いで同じブランチに積み、文書だけの観点はテストを書かずに差分で確かめる

- 日時: 2026-10-25 13:37 UTC
- ステータス: 採用
- 関係する PR・タスク: #223
- 置き換え元: なし
- 置き換え先: なし

## 背景

人が作った PR にレビューの指摘が付き、その PR の修正を sacty のタスクにしたところ、次のことが起きたと報告があった。

- 既存の PR とは別の、新しい PR が作られた。
  実装の PR は、いつも sacty のブランチ（`sacty/task-<ID>`）からベースブランチへの PR として作っていた。
  タスクの内容にある PR のリンクを使うのは、レビューの工程だけだった。
- `docs/` に作ったドキュメントを読めるかを確かめる、意味の無いテストが足された。
  最終レビューは、実装がテストを対応させていない観点を、機械的に不合格にする（`review.viewpointUnmapped`）。
  文書だけを直す観点でもテストの対応が要るので、ファイルを読むだけの形のテストを書かせていた。
  要求要件・設計を PR で承認するタスクでは、成果のファイル（`docs/sacty/...`）も PR に入るので、これを対象にしたテストも起こりえた。

どちらも sacty の成果の信頼を損なうので、仕組みで防ぐ必要があった。

## 決定

- タスクの題か内容に対象リポジトリの PR のリンクがあるときは、オーケストレーターが、その PR そのものを直す依頼かを決める（答えの `continuePullRequest`）。
  直す依頼なら、sacty が PR を確かめて引き継ぐ。
  - 作業領域を PR の元のブランチの先頭で用意し、実装を同じブランチに積む（強制プッシュはしない）。
    新しいブランチ・PR を作らず、PR の題・本文を変えず、レビュー用のラベルも付けない。
  - PR にあるレビュー・コメントを、工程の指示に渡す。
    それより前の指摘は、PR の指摘として取り込み直さない（実装の工程の最後の実行を始めた時で分ける）。
  - 要求要件・設計は PR にせず、画面で承認する。
  - 中止しても、PR を閉じず、ブランチを消さない。
  - 開いていない PR・フォークの PR・sacty のほかのタスクの PR は引き継がない。
    そのときは、新しい PR を作らないように、工程を決めずに止める。
- 実装は、実行される振る舞いの無い変更（文書・コメント・文言など）だけの観点を、テストを書かずに差分で確かめると申告できる（テストの対応の `untested`）。
  ゴールガーディアンが、振る舞いを変えないことを差分で確かめて判定し、振る舞いを変えるのにテストが無ければ不合格にする。
  実装・設計の指示に、ファイルがある・読めることだけを確かめるテストや観点を作らないこと、sacty が置く要求要件・設計のファイルを対象にしないことを書く。

## 理由

- 引き継ぐかを sacty が PR のリンクの有無だけで決めると、「#12 と同じ直し方をほかの所にも」のように PR を参考にするだけのタスクまで、人の PR に積んでしまう。
  依頼の意図はタスクの文から判断するしかないので、工程を選ぶオーケストレーターに決めさせた。
  画面で人が指定する案は、指定を忘れると今回と同じことが起きるので採らなかった（人が指定する口を足すのは、後で要れば別に決める）。
- 引き継げない PR のときに新しい PR で進めると、報告された問題がそのまま起きる。
  費用は判断の1回分なので、止めて人が確かめる方を選んだ。
- 人のブランチに強制プッシュすると、人の変更を消しうる。
  前にプッシュしたコミットに積むだけにし、ブランチが進んでいたら止める。
- 文書だけの観点にテストを強いると、形だけのテストが増え、テストを保守する費用だけがかかる。
  テストを外せるのは振る舞いの無い観点だけにし、その判断はゴールガーディアンが差分で確かめるので、実装がテストを省く逃げ道にはならない。
  設計の工程で観点ごとに確かめ方を決める案もあったが、設計を省く組み合わせ（`direct`）でも同じ問題が起きるので、実装の申告とゴールガーディアンの確認にした。

## 影響

- 引き継いだ PR の実装の承認は、その PR のマージになる（人の PR のまま）。
- 引き継いだ PR の説明には、sacty の実装の説明や検証の結果を書かない（題・本文を変えないため）。
  それらは sacty のタスクの画面で見る。
