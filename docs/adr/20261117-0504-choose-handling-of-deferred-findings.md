# 後続に回すと決めた指摘の扱いを、人が指摘ごとに選ぶ

- 日時: 2026-11-17 05:04 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-370
- 置き換え元: なし
- 置き換え先: なし

## 背景

[後続に回すかどうかは人が決め、実装は案と理由までを出す](20261117-0415-defer-proposals-decided-by-person.md)で、人が、実装の案を 1 件ずつ「後続に回す／この PR で直す」と決められるようにした。後続に回すと決めた指摘は、PR のコメントに残るだけで、その後の扱いは人に任せていた。

人が決めたこと（2026-11-17）：後続に回すと決めた指摘の扱いも、人がその場で選ぶ。状況やリポジトリによって、選びたい扱いが変わるためである（Issue で管理している・人が自分で作る・すぐに sacty の後続のタスクにしたい・把握したので何もしなくてよい）。最初の版は、指摘ごとに「sacty の後続のタスクを作る」「GitHub の Issue を作る」「何もしない（把握した・自分で作る）」から選ぶ。プロジェクトごとに既定を決められる。ほかのチケット管理ツールでの作成は、後の版にする。どれを選んでも、決定と指摘の一覧は PR のコメントに残す。

## 決定

- 後続に回すと決めるときに、指摘ごとに、扱いを選ぶ：sacty の後続のタスクを作る・GitHub の Issue を作る・何もしない。
- プロジェクトの設定に、扱いの既定を持つ。承認の画面の選択肢の初めの値になり、扱いを渡さない決定（API）にも使う。既定が無ければ、何もしない。
- 決定のコメントに、指摘ごとの扱いを書く。

着手のときに決めたこと（人の確認は、まだ）：

- GitHub の Issue は、決定のときに、実装の PR のリポジトリに作る。
- sacty の後続のタスクは、元のタスクが完了してから作る（PR がマージされ、残りの工程が終わった後）。マージの前には作らない。PR がマージされずに終わったタスク・中止したタスクでは、作らない。作りは、完了したタスクの続きのタスクと同じにする。
- 作れなかったとき（Issue も、後続のタスクも）は、理由を作業履歴に記録し、やり直さない。決定は変えない。
- セキュリティの組み合わせのタスクでは、Issue を作らない。
- sacty の画面から書いた指摘でも、人が Issue を作ると選んだら、その文を Issue に載せる。
- 扱いの既定は、プロジェクトのエクスポートに入れない。

## 理由

- Issue を、決定のときに作る：人が「作る」と選んだその場の操作で、作った Issue の URL を、決定のコメントに載せられる。
- 後続のタスクを、完了の後に作る：マージの前に始めると、後続のタスクは、この PR の変更が入っていないベースブランチから始まる。指摘は、この PR が足したコードへのものなので、対象のコードが無いまま始まるか、同じ所を変えて競合する。完了したタスクの続きのタスクの作り（元のタスクの記録を渡す）を、そのまま使える。「すぐに取りかかってほしい」という望みには、マージの後すぐ、で応える。
- やり直さない：Issue や後続のタスクを、自動で作り直すと、二重に作りうる。失敗は、作業履歴と承認の画面に出して、人が判断する。
- セキュリティのタスクで Issue を作らない：指摘に、脆弱性や修正の範囲の詳細が入りうる（指摘への返信・人に確かめてほしいことのコメントと同じ扱い）。
- 画面から書いた指摘の文を、Issue には載せる：決定のコメントには載せない（人が選んでいないため）が、Issue は、人がその指摘を Issue にすると選んだ結果で、文が無いと Issue にならない。
- 既定をエクスポートに入れない：エクスポートの形式を変えると、以前の版の sacty が、新しいファイルを読めなくなる（知らない項目を受け付けない）。既定は、インポートの後に選び直せる。

## 影響

- プロジェクトの設定に、欄が 1 つ増える。承認の画面の案ごとに、扱いの選択が増える。
- 「GitHub の Issue を作る」を選ぶと、sacty が、プロジェクトの GitHub のアカウントで Issue を作る（取り消すには、人が Issue を閉じる）。
- 後続のタスクは、作られるとすぐに始まり、費用がかかる（予算の上限は、タスクごとの既定）。
- ほかのチケット管理ツールでの作成は、扱っていない。
