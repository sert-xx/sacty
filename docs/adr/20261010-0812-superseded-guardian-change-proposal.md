# 承認済みの成果物の変更の申し出は、判定ごとに新しいセッションのゴールガーディアンが判定し、要求要件の変更は人間の再承認に回す

## 背景

#4 で、承認した要求要件と設計を凍結した。後の工程のエージェントが、凍結した成果物の変更を申し出る道と、その申し出を
判定する仕組みが必要だった。

## 決定

- 工程のエージェントは、その工程より前の承認済みの成果物（要求要件・設計）の変更を申し出られる。形式は JSON のブロック
  `sacty-change-proposal` で、変更する成果物・理由・根拠の事実・変更後の全文を書く。1回の実行で1件までで、ID（CP-n）は sacty が振る。
  対象外の工程への申し出は無視する。
- ゴールガーディアンは、判定ごとに別の実行（コンテナ・空の設定ディレクトリ・工程とは別の空の作業領域）で起動し、判定の後に作業領域を消す。
  プロンプトに入れるのは、承認済みの要求要件と設計、変更の理由、根拠の事実、変更後の全文だけ。チケット・下書き・指摘・過去の判定は渡さない。
  使う AI は `guardian_agent` で指定でき、省略すると `default_agent` を使う。
- 設計の変更は、認められれば承認済みの設計とテスト観点を置き換える。要求要件の変更は、認められても要求要件から先の承認を取り消し、
  変更後の要求要件を承認ゲートに出す（再承認の後に設計を作り直す）。却下されたら、申し出た工程の成果物をそのまま提出する。
- 判定できないとき（「判定できない」の判定、判定の形式が読めない、実行の失敗、デーモンの停止による中断）はエスカレーションにし、人間が
  タスクの詳細で「変更を認める／認めない」を選ぶ。
- 台帳には `ChangeProposed`・`ChangeJudged`（記録者はゴールガーディアン）・`ChangeDecided`・`ChangeApplied` を書き、タスクの詳細の
  「変更の申し出と判定」に出す。ゴールガーディアンの費用も予算に入れる。
- 判定と後始末、人間の判断と後始末、実行の完了と提出は、それぞれ1回の台帳の追記（同じトランザクション）で記録する。
  途中までしか記録されていない台帳も、起動の時に足りない後始末を記録して先に進める（冪等）。
- ゴールガーディアンは、工程の実行の後に予算を判定せずに実行し、予算を超えていれば判定の後（次の工程の実行の前）に一時停止する。

## 理由

- 変更後の全文を渡すのは、何を判定するかを示すため（PR の本文）。
- 判定と後始末を同じ追記にしたのは、その間でプロセスが止まると、タスクが待機のままゲートも実行待ちも無く、人間の判断も拒否される状態に
  なることがレビューで再現されたため。
- 判定ごとに新しいセッションにする理由、渡す情報を絞る理由は、記録に無い。

## 影響

- 判定中のタスクは、実行待ち・実行中でなくても作業中として扱い、一覧と詳細の自動更新を続ける。
- 判定できなかった申し出への導線は、承認ゲートの画面ではなく、タスクの詳細の判断のフォーム（`/tasks/:id#proposals`）にする。
- 実装の工程（PBI-10）からは、設計にも申し出られるようになる。
