# エラーレポートを Markdown のダウンロードにし、オーケストレーターの分析を任意で足す

- 日時: 2026-10-29 06:09 UTC
- ステータス: 採用
- 関係する PR・タスク: #254
- 置き換え元: なし
- 置き換え先: なし

## 背景

タスクでエラーが起きたときに、何が起きたかを人に渡して調べてもらう手段が無かった。
画面の作業履歴・実行のログは見られるが、sacty の処理とエージェントの動きを1つにまとめたものは無く、画面を開けない人には渡せない。
エラーの報告は一般にはサーバーに送るが、sacty は通信できない環境でも使う。
また、エラーの箇所は詳しく知りたい一方で、作業履歴やセッションログ（1実行で最大 18MB）を丸ごと入れると、テキストファイルとして重すぎる。

## 決定

- エラーレポートは、デーモンが作業履歴とセッションログから作る Markdown にし、画面からファイルとしてダウンロードさせる。サーバーには送らない。
- エラーの箇所（新しい5件）だけを詳しく書き（直前の記録・記録の JSON・標準エラー出力の末尾・エージェントの最後の出来事）、ほかの実行はエージェントの動きの要約、作業履歴は1件1行にする。
  部分ごとに上限を置き、全体を 256KB までにする。作業履歴は入る分だけ入れ、間を省く。
- オーケストレーターの分析は、人が求めたときだけ実行する（費用がかかるため）。
  分析は作業履歴に記録し（`ErrorAnalysisRequested`・`ErrorAnalyzed`）、次に作るレポートに入れる。
  分析は、質問への答えと同じく、オーケストレーターのセッションの複製で、セッションログを読み取り専用で渡して実行する。
- セッションログの読み分け（Claude Code・Codex）を画面から core に移し、画面とデーモンで同じものを使う。

## 理由

- ファイルなら、通信できない環境でも、メールや持ち運べる媒体で渡せる。Markdown は、そのまま読めて、チケットや AI にも貼れる。
- 大きさに上限を置くのは、ファイルを開く・貼る・AI に読ませるときに重くしないため。原本のログは sacty に残るので、レポートは要約でよい。
- 分析を記録にするのは、ダウンロードのたびに AI を実行しない（時間と費用がかからない）ためと、何度でも同じ分析を入れたレポートを作れるようにするため。
  ダウンロードの中で分析を待つ案は、分析に数分かかり、画面の要求が待ちきれないので採らなかった。
- 分析を質問の仕組み（`QuestionAsked`）に載せる案は、人の質問と答えの一覧に分析が混ざり、レポートに入れる分析を選び分けられないので採らなかった。

## 影響

- 作業履歴のイベントが2種類増え、費用を持つイベントに `ErrorAnalyzed` が加わる（工程ごとの費用の表に「エラーの分析」の行が増える）。
- レポートの節や上限を変えるときは、[エラーレポート](../spec/error-report.md) を直す。
- レポートは秘密情報を伏せ直さない（作業履歴とセッションログは記録のときに伏せてある）。記録の伏せ方を変えるときは、レポートにも影響する。
