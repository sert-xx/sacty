# 承認待ちの成果物の確認したいことは、専用の読み取りのツールで返す

- 日時: 2026-11-22 00:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-475
- 置き換え元: なし
- 置き換え先: なし

## 背景

要求要件・設計の成果物の冒頭には、人への問いを書く「確認したいこと」の節（must・should）がある。
`sacty mcp` からは、問いがあるか・何件か・中身が何かを、成果物の全文（`get_deliverable`）を読まないと知れない。`get_task` の `humanAsks` にも出ない。
手元の AI が承認待ちのタスクを追うとき、問いを見落とし、答えずにマージ（推奨の答えで進む）しがちになる。

## 決定

- 読み取りのツール `get_step_questions` を足す。承認待ち（`awaiting_approval`）の要求要件・設計の成果物から、must・should の件数と、問いごとの文を返す。読み取れないときは「読み取れなかった」と返し、「問いは無い」とは返さない。
- `get_task` には欄を足さない。タスクの要約（`list_tasks`・`get_task`・`wait_for_task`）には、問いの有無と件数だけの `stepQuestions` を足す。
- 読み取りは MCP の層で、`get_task` と同じ `GET /api/tasks/:id` のタスクに、PR の本文を作るときと同じ `readStepQuestions` を呼んで行う。デーモンの HTTP API は足さない。結果はタスクの値に記録せず、呼ぶたびに成果物から読む。
- 答える専用のツールは足さない。答えは今までどおり、PR のコメントか `request_changes` の `comments` で書き、`howToAnswer` で案内する。
- 対象は、PR の本文に問いを出す工程と同じ、承認待ちの要求要件・設計に限る。人の判断待ち（`escalated`）と、must・should に分けない調査の成果物は対象にしない。

## 理由

- `get_task` の結果は、すでに説明・レビューの本文・`humanAsks` などで大きい。問いの本文を足すと、問いに用のない呼び出しでも大きくなる。件数だけを要約に出し、中身は必要なときに読むツールに分けると、結果の大きさを抑えられる。
- `readStepQuestions` は MCP の層から呼べる。`humanAsks` も MCP の層で core の関数をそのまま使っており、同じ形にすると、デーモンの API を増やさず、前の版のデーモンとの食い違いも起きない。
- 同じ処理を使うので、MCP の件数が PR の本文の件数と食い違わない。

## 影響

- ツールが 1 つ増える（20 個）。要約に `stepQuestions` の欄が増える。`wait_for_task` の cursor には入れない（問いが変わるのは新しい提出のときで、状態の変化でもう待ちが起きる）。
- `readStepQuestions` の `counted` に、問いごとの文（`items`）を足した。件数は `items` の数から出す。PR の本文の見た目は変えない。
- 調査の工程と、人の判断待ちの工程の問いは、今までどおり `get_deliverable` で全文を読む。
- 仕様は [MCP サーバー](../spec/mcp-server.md#get_step_questions) にある。
