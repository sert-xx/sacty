# タスクの詳細で工程ごとのエージェントを人が変えられるようにし、config.yaml の step_agents より優先する

- 日時: 2026-10-17 00:05 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-121
- 置き換え元: なし
- 置き換え先: なし

## 背景

工程のエージェントは config.yaml の `step_agents`（無ければ `default_agent`）で決まり、タスクごとには変えられなかった。エラーで止まった・
差し戻した工程だけ、より強いエージェント（段階）で実行し直したい、という要望がある（ステークホルダー）。config.yaml を書き換えると、ほかの
タスクまで変わる。工程のイメージは、タスクの詳細から変えられる（PBI-106）。

## 決定

- 工程のイメージ（PBI-106）と同じ形にする。タスクの詳細で、工程ごとのエージェントを config.yaml の `agents` の名前から選べる。工程の状態は
  問わず、その工程を次に実行するときから使う。中止したタスクでは変えられない。
- 変えたら `StepAgentChanged`（`step`・`from`・`to`。actor は person）を作業履歴に足す。投影は `agents`・`agentChanges` に持つ。
- 工程の実行・マージの後の監視の確認・外部作業・書き出しは、人が選んだエージェントを `step_agents` より優先する（`stepAgentFor`）。
- 選んだ名前が config.yaml から消えていたら、既定に戻さず一時停止する（書き出しは、書き出せなかった理由にする）。
- オーケストレーター・ゴールガーディアン（判定・最終レビュー・統合レビュー・戻し先の判断）は対象にしない。
- 選べるエージェントの一覧と、config.yaml で決まる工程ごとの名前は、デーモンの状態で返す（秘密の値・接続先の URL は出さない）。stub は、
  今のエージェントが stub のときだけ選択肢に出す。

## 理由

- 工程のイメージと同じ考え方にすると、画面の扱い（いつから使うか・決めた元・候補を確かめられないとき）と作業履歴の読み方がそろう。
- 消えた名前で既定に戻すと、人が強いエージェントを選んだつもりで弱いエージェントで動き、気づけない。止めて選び直してもらう。
- オーケストレーター・ゴールガーディアンは、工程の成果を判定する側なので、タスクの中で工程と一緒に変えると判定の基準がぶれる。要望も
  工程のエージェントだった。

## 影響

- 状態（`GET /api/status`）に `agents`・`stepAgents` を足した。`SactyConfig` に `agents`（すべてのエージェント）を足した。
- 段階のサブエージェント（PBI-119）は、選んだエージェントを親として置く（接続先が同じ段階だけ）。
