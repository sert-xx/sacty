## 背景

これまでタスクは画面で作るチケットからだけ始まった。GitHub の Issue からタスクを作れるようにし、どの Issue をどのプロジェクトが
担当するかを決める必要があった。PBI-5 は大きいので2つに分け、この PR は前半（PBI-5a）として、プロジェクトと Issue の取り込みを扱う。

## 決定

- プロジェクトは、台帳と同じ SQLite の `projects` テーブルに保存する。起動の時に「デフォルト」を用意し、画面で作るチケットはそこに入れる。
- プロジェクトに、GitHub Issue の取り込み元（単位・対象・ラベル）を Org 単位かリポジトリ単位で登録する。
- 同じ Org・同じリポジトリは、複数のプロジェクトに登録できない（保存の時に検査し、409 で理由を出す。名前の大文字・小文字は区別しない）。
  Org と、その中のリポジトリを別のプロジェクトに登録するのはよく、担当の判定ではリポジトリの指定（範囲が狭い方）を優先する。
  Org の取り込み元の画面に、ほかのプロジェクトがリポジトリ単位で担当している除外リポジトリを出す。
- 取り込みはポーリングで行う。`config.yaml` の `github.token_secret` を設定すると、`poll_interval_sec`（既定 300 秒）ごとに、取り込み元ごとに GitHub の
  検索 API で開いている Issue（PR を除く）を探す。「今すぐ取り込む」で間隔を待たずに実行でき、最後の取り込みの時刻・件数・エラーを出す（トークンは取り除く）。
- 担当のプロジェクトは取り込むたびに判定し、その取り込み元のラベルが付いた Issue だけを取り込む。リポジトリと Issue の番号で、二重に取り込まない。
- 取り込んだ Issue はタスクになり、`TaskCreated` に `start: github_issue` と `source`（リポジトリ・番号・URL）を記録する。Issue の本文とタイトルは切り詰めない
  （10,000 文字の制限は、画面で手入力するチケットにだけ残す）。
- 検索の失敗は取り込み元ごとに記録し、ほかの取り込み元の検索と、取れた結果の取り込みは続ける。
- 検索は更新日時の順に行い、検索 API の 1,000 件の上限を超えるときは更新日時で範囲を区切ってたどる。取り込み元ごとにどこまで読んだか（cursor）を
  デーモンのメモリーに覚え、次の取り込みはそこから続ける。レート制限で止まったら、その回のほかの検索をやめる。GitHub が不完全な結果を返したら、
  取れた分は取り込むが、cursor はそのページの手前に留める。取り切れなかったときは、黙って成功にせず取り込み元のエラーとして記録する。
  プロジェクトの設定が変わったら、cursor を忘れて先頭から読み直す。

## 理由

- 担当のラベルが付いた Issue だけを取り込むのは、Issue の本文がエージェントに渡るので、ラベルを付けられる人（リポジトリの書き込みの権限を持つ人）が、
  実行してよい依頼かを判断する前提にしたため（PR の本文で、判断してほしい点として挙げた）。
- 検索の失敗を取り込み元ごとに分けるのは、1つの取り込み元の失敗で無関係なプロジェクトも取り込めなくなることがレビューで再現されたため。
- 範囲を区切ってたどるのは、同じ検索の先頭 1,000 件だけを見ると、1,001 件目以降に永久に届かないため（レビューの指摘）。
- cursor を覚えて続きから読むのは、範囲を増やして1回の取り込みのリクエストが増え、検索 API のレート制限で毎回先頭から失敗して取り込みが 0 件になる
  ことがレビューで再現されたため。並びを更新日時にしたのは、一巡した後は前回より後に更新された Issue だけを探せば済み、古い Issue に後から
  ラベルが付いても拾えるため（レビューへの返信）。
- 不完全な結果で cursor を進めないのは、その時刻より前の Issue をすべて取れたとは限らないため（レビューの指摘）。
- 設定の変更で読み直すのは、担当の判定が変わりうるので、以前はほかのプロジェクトの担当で取り込まなかった Issue を取りこぼさないため（レビューへの返信）。
- 本文を切り詰めないのは、上限より後に書かれた受け入れ条件や制約が台帳にもエージェントへの入力にも残らず、取り込み済みになるので後から補われないため
  （レビューの指摘）。Issue の本文には GitHub 側の上限（65,536 文字）がある（レビューへの返信）。
- 取り込み元の登録の単位を Org とリポジトリにした理由、重複を禁じてリポジトリの指定を優先する理由、ポーリングにした理由は、記録に無い。

## 影響

- 一覧はすべてのプロジェクトのタスクを表示する。ヘッダーでのプロジェクトの切り替えは PBI-4 に回した。
- cursor はメモリーに持つので、デーモンを再起動すると先頭から読み直す（取り込み済みの Issue は二重に取り込まない）。
- 実際の GitHub からの取り込みは、この時点では確かめていない。
