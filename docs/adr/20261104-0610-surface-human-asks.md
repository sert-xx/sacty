# 人に確かめてほしいことを、PR のコメントと承認の画面の目立つ所に出す

- 日時: 2026-11-04 06:10 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-301
- 置き換え元: なし
- 置き換え先: なし

## 背景

PR の指摘を受けた作り直しで、指摘の意図が合っているかを人が確かめないと分からないことがある。
実験（S14 の r2〜r4）で、次のことが起きた。

- 指摘への聞き返し（「どの発言を指すか読み取れない」）が、作業履歴の判断文にだけ出て、PR を見ている人は気づけなかった。r3 では承認の画面の「人が確かめること」に出たが、最終レビューが拾えたときだけだった。
- 実行が消えた値を作り直したことが、対応欄の「元と違う所があれば指摘して」にだけ書かれ、承認の画面の対応欄でしか見えなかった。
- ゴールガーディアンの戻し先の判断文は 600〜1,000 文字になり、画面で読みにくかった（S7）。

## 決定

- 「人に確かめてほしいこと」として、次の2つを集める（`humanAsks`）。
  - ゴールガーディアンが戻し先を判断できなかった理由。
  - 作り直しの実行が、指摘への対応（`sacty-responses`）に添えた `confirm`（聞き返し・推測で決めたこと）。確かめたいことがあるときだけ書かせる。
- 承認待ちに戻った成果物について、承認の画面とタスクの詳細の目立つ所（承認の案内の下）に出し、同じ内容をその成果物の PR にコメントする（1回の提出につき1件）。
- PR のコメントは、目印を付け、人間の指摘として取り込まない。外から来た文なので、秘密情報を伏せてから切り詰め、`@名前` で他人に通知が飛ばないようにする。
- 戻し先の判断の文は、画面では先頭の1〜2文を要点として先に出し、全文は開いて読めるようにする。作業履歴の記録と、実行に渡す判断文は全文のまま。

## 理由

- PR を見ている人は、sacty の画面を開かない。気づける所は PR のコメントなので、画面だけに出しても気づかれない。
- 最終レビューの「人が確かめること」に頼ると、最終レビューが拾えたときしか出ない。実行自身が一番よく知っている「何を推測したか」を、実行に書かせるのが確実。
- 判断の要点を先に出すのは、全文は根拠で、人がまず知りたいのは戻し先と理由の要約だから。記録を切り詰めないのは、実行に渡す判断文と監査が全文を使うため。

## 影響

- 作り直しの実行の指示に `confirm` の書き方が足される（指摘のある実行だけ）。確かめたいことが無い対応は変わらない。
- PR に、作り直しのたびにコメントが1件増えることがある（確かめたいことがあるときだけ）。GitHub のアカウントを選んでいないプロジェクトでは PR に書かず、画面にだけ出る。
- 利用者向けは[タスクを進める](../user/tasks.md)に、仕様書は[承認と差し戻し](../spec/approval.md#人に確かめてほしいこと)に記す。
