# 既定のレビューで、直し方の方針を確かめ、同じ原因の指摘を1回で出し切る

- 日時: 2026-11-13 23:28 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-342
- 置き換え元: なし
- 置き換え先: なし

## 背景

セキュリティ対応のタスクで、PR のレビューの子タスクと実装の往復が8回続いた（PR は中止した）。
直し方は、中継する本文を自前で解析して危ない名前を探す方針だった。
レビューは回ごとに、同じ原因（中継先のパーサーとの解釈の差）の別の抜け道を1つずつ見つけ、実装はそれを1つずつ塞いだ。
差分は膨らみ、タスクの「最小限の変更」から離れたが、方針を見直す指摘は一度も出なかった。

既定のレビュー用スキル（`review-dispatch`・`review-execution`）には、次の2つが欠けていた。

- 方針そのものを見る観点。コードの観点は、選ばれた方針の中で欠陥を探すものだけだった。代替案を見る観点は設計書の D-1 にしか無い。
- 同じ原因の現れを出し切る決まり。担当は最初の指摘で止めずに最後まで見るが、1つの欠陥について、入力の形を変えた別の現れを探すことは求めていなかった。再レビューは、前回の見落としの `must` を出すことを認めていて、同じ原因の現れが回ごとに1つずつ出ても止める仕組みが無かった。

## 決定

- コードの必須の観点に C-17（方針の妥当性）を足す。もっと単純で確実な方針が無いか、問題の重さとタスクの制約に釣り合うか、境界の場合を際限なく生む形でないか、前回までの指摘に同じ原因の別の現れが続いていないかを見る。段階は `advanced`。C-5・C-15 からは方針の選び方を外す。
- 担当は、欠陥ごとに原因を書き、同じ原因に当たるほかの現れ（入力の形の違い・別の箇所）を探して1件の指摘にまとめ、直し方を原因に向ける。親は観点をまたいで同じ原因の指摘を1件にまとめる。
- 再レビューで、前回までの `must` と同じ原因の別の現れがまた見つかったら、現れをもう1件足さず、C-17 の担当に方針を見直させる。`self-review` の再レビューのように C-17 を起動していない回では、そのときだけ起動する。C-17 が方針を変える指摘を出せば現れをそこにまとめ、出さなければふつうの `must` にする。
- PR のレビューの子タスクの指示にも、指摘を出し切ることと、同じ原因の別の現れが続いたら方針を見直す指摘にすることを書く。

## 理由

- 方針の誤りは、個々の直しが正しいので、方針の中を見る観点では見つからない。必須にするのは、どの変更でも方針は選ばれているため。初回から見れば、`self-review` の段階で方針を見直せる。
- 別の方針は、失うもの（使えなくなる正当な使い方）があるので、失うものを確かめて指摘に書かせ、作者か人が選べるようにする。承認済みの要求要件・設計が決めた方針は、レビューで覆さない（`should` に留める）。
- 方針を変えるかの判断は、親ではなく C-17 の担当にさせる。親は観点のレビューをしない決まり（オーケストレーターに徹する）を崩さないため。
- 「回をまたいで同じ原因が続く」ことは、その回の担当だけでは分からないことがある（新しい現れを見つけるのは C-3 などで、C-17 は見つけていない）。集約で前回までの `must` と照らし、そのときに C-17 を起動し直す。

## 影響

- コードのレビューでは、担当が1つ増える（C-17）。
- 同じ原因の現れを探すぶん、担当1人の時間は延びるが、往復の回数は減る見込み。
- 方針を変える指摘が出ると、実装は書き直しになる。差分は小さくなるが、失うものがある方針への変更は、作者か人が選ぶ。
