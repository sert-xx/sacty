# 監査の提案は、改善案に補足するか、人の案に差し替えて採用できる

- 日時: 2026-10-20 14:49 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-151
- 置き換え元: なし
- 置き換え先: なし

## 背景

監査の改修の提案への判断は、採用（宛先を選び直して改修のタスクを作る）と却下（理由を書く）の2つだけだった。
実際には、原因は合っているが改善案には手を入れたい場面がある。

- 改善案はこちらで決めたい（直し方が現場の事情と合わない）。
- 改善案は概ねよいが、情報を補いたい（既にある設定ファイルに足す、同じ検査が別にある、など）。

どちらも、今は却下して理由を書くか、提案のまま採用して改修のタスクの説明を後から直すしかなかった。却下すると原因も否定した
記録になり（原因の状態が `rejected` になる。[監査の画面を、裏側のモックで先に作る](20261017-1145-audit-ui-with-mock.md)）、
以後の監査にも「この提案は要らない」として渡るので、原因を認めつつ直し方だけを変えたいという判断を残せない。

## 決定

- 採用のときに、人の手入れ（`AuditProposalAdopted` の `note`）を添えられるようにする。種類は2つだけにする。
  - `supplement`（補足する）：監査の改善案はそのまま残し、改修のタスクの説明で改善案の後に「人が足した補足：」として足す。
  - `replace`（差し替える）：人の案を改修の指示にし、監査の改善案は「人が改善案を差し替えました。監査が出した改善案：」として
    後に添える（監査が何を出したかの記録を消さない）。
- 却下は変えない。原因そのものを認めないときの判断として残す。手入れは採用の一部なので、原因の状態は `adopted` になる。
- 手入れは却下の理由と同じ扱いにする：記録する前に秘密情報を伏せ、監査の画面・レポートに出し、以後の深掘りに渡す。
- 長さの上限は 4,000 文字（`AUDIT_ADOPT_NOTE_MAX`）にする。改修のタスクの説明の上限（10,000 文字）の中に、改善案・原因の説明と
  一緒に収めるため。

## 理由

- 判断の種類を増やす（「条件付き採用」などを足す）より、採用に添える手入れにすると、原因の状態・改修のタスクの作り方・
  以後の監査への渡し方を変えずに済む。採用か却下かの二択は、承認ゲートと同じ形のまま保てる。
- 手入れを自由記述1つにし、「足すか・置き換えるか」だけを選ばせると、改修のタスクの説明の組み立てが決まり、人は文章を
  書き分けなくてよい。
- 監査の改善案を残すのは、後から「人が何を変えたか」を読めるようにするため。差し替えた改善案を消すと、監査の出力と改修の
  つながりが追えなくなる。

## 影響

- `AuditProposalAdopted` に `note` が増える。古い記録（`note` の無い採用）は、手入れの無い採用として読む。
- 採用は、秘密情報を伏せるために非同期になる（`adoptAuditProposal` が `Promise` を返す）。却下と同じ形。
- 深掘りの指示に「採用のときに人が手を入れた提案」の節が増える。指示が少し長くなる。
- 画面の採用のフォームに、手入れの開閉と種類の選択・入力が増える。手入れを書かなければ、これまでと同じ操作で採用できる。
