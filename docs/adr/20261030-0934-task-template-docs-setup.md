# タスクのテンプレート「ドキュメント構築」で、実装からドキュメントと、それを参照・直すスキルを作る

- 日時: 2026-10-30 09:34 UTC
- ステータス: 採用
- 関係する PR・タスク: #257
- 置き換え元: なし
- 置き換え先: なし

## 背景

既存のリポジトリには、ドキュメントがほとんど無いものが多い。エージェントはコードを読んで作業するが、目的・用語・全体の構成・
規約などはコードを少し読むだけではわからず、コンテキストが足りずに思ったとおりの成果物を作れないことがある。
実装からドキュメントを作らせ、エージェントがそれを参照する・直す仕組み（スキル）を置きたい。

ただし、次の2つが問題になる。

- すでにドキュメントがあるリポジトリでは、作り直すと既存のものと重なったり、人が書いた内容を壊したりする。
- エージェントが大量のドキュメントを一度に作ると、人がすべてをレビューするのは重く、レビューされないまま信頼されてしまう。

## 決定

- タスクのテンプレートに `docs-setup`（ドキュメント構築）を足す。入口・入力・記録は `sacty-setup` と同じ（題と説明は sacty が決め、
  進め方はオーケストレーターが選ぶ）。
- ゴールでは、次の順に進めさせる。
  1. 既存のドキュメントを棚卸しし、表にする。既存のものは消さない・動かさない・書き直さず、リンクする。置き場所・形・言語が
     決まっていれば従う。
  2. 実装から、コードを少し読むだけではわからないことだけを書く（関数ごとの説明は書かない）。ビルド・テストの実行の仕方は
     `sacty-setup` に任せる。
  3. 参照するスキル `docs-lookup` と、直すスキル `docs-update` を作る。置き場所は `deployment-observer` と同じ規則
     （`.agents/skills/` を原本、`.claude/skills/` を相対のシンボリックリンク）。
- レビューの負担を抑えるため、ゴールに次のことを書く。
  - 新しく作るドキュメントの先頭に、状態（`AI 生成・未レビュー` か `レビュー済み`）と対応するコードの場所を書く。
    `レビュー済み` にするのは人が確かめたときだけ。`docs-lookup` は、未レビューのドキュメントをコードで確かめてから使う。
  - 確かめられないことは推測で書かず `（未確認）` とし、PR の説明に、短く答えられる質問として挙げる。
  - 最初の PR を、棚卸しの結果・入口・全体の構成・2つのスキルに絞り、残りの項目は入口に「未作成」として並べる。
    大きなリポジトリでは、領域ごとの子タスク（`split`）を選んでよい。
- コードは変えさせない。整っていて変更が要らなければ、PR を作らずに調査だけで終える（`sacty-setup` と同じ）。

## 理由

- 既存のドキュメントを書き直させないのは、人が書いた内容（設計の意図・経緯など、コードからはわからないこと）を、エージェントが
  コードから推測した内容で上書きしないため。重複を作らず、リンクでつなぐ。
- 書く範囲を「コードを少し読むだけではわからないこと」に絞ったのは、コードからすぐわかることを書いても、エージェントの助けに
  ならないうえ、レビューする量と、実装とずれる箇所が増えるため。
- 状態を付けたのは、すべてをレビューしてから使う運用は重く、続かないため。未レビューでも手がかりとして使え、読む側が信頼の
  度合いを見分けられるようにした。レビューは、使いながら少しずつ進められる。
- 確かめてほしいことを質問の形にしたのは、人がドキュメントを通して読まずに、知っていることを答えるだけでレビューできるため。
- スキルを参照と修正の2つに分けたのは、使う場面（作業の前に読む・実装を変えたときに直す）が違い、エージェントがいつ使うかを
  `description` で見分けやすくするため。修正のスキルで、実装を変える PR でドキュメントも直させ、作った後にずれていくのを防ぐ。
- 工程を固定しなかったのは、リポジトリの大きさ・既存のドキュメントの量によって、1つの PR で足りるか、分割したほうがよいかが
  変わり、リポジトリを読まないと決められないため（`sacty-setup` と同じ）。

## 影響

- スキルの名前（`DOCS_SKILLS`）と状態の表記（`DOCS_STATUS`）は `apps/daemon/src/task-templates.ts` に置く。スキルの置き場所は
  `DEPLOYMENT_SKILL_PATHS` から作る（同じ規則を2か所に持たない）。
- sacty は、作ったスキルやドキュメントを読まない（工程の処理は変えない）。スキルは、対象のリポジトリで動くエージェントが使う。
- 状態の表記は日本語の固定の文字列なので、英語のリポジトリでもそのまま書かれる（ゴールの文と同じく、画面の言語に合わせない）。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md#タスクのテンプレート)。
