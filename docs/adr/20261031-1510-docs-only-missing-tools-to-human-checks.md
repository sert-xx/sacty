# 差分が文書のファイルだけなら、ツールがイメージに無くても止めずに人の確認へ回し、ツールが無くて止まったタスクは再開でテストの扱いを決め直せる

- 日時: 2026-10-31 15:10 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-158
- 置き換え元: [ゴールガーディアンが最終レビューの中でテストを実行し、sacty はテストのコンテナを使わない](20261021-1431-superseded-guardian-runs-tests.md)（決定3の「ツールがイメージに無いときは止める」の、差分が文書のファイルだけのときの部分）
- 置き換え先: なし

## 背景

実務での実証実験（ドキュメントが少ない Go の大きなリポジトリで、Markdown のドキュメントを書き起こす依頼）で、タスクが最終レビューで止まった。
実装の変更は Markdown のファイルだけで、PR の本文でも「テストなし・差分で確認」と判断していた。
しかしオーケストレーターが、リポジトリの `moon.yml` の検証（`go generate`・`go test -race`・`golangci-lint`・フロントのビルド）をすべてつないだものを `testCommand` に決めていた。
選べるイメージのどれにも Go が入っていなかったため、ゴールガーディアンは最終レビューで `go`・`golangci-lint` を実行できず、`missingCommands` に書いた。

このとき、ゴールガーディアンは観点の判定（要求を満たす）、環境による失敗の申告（差分は Markdown だけなので起点でも同じ）、人が確かめること（Go のある環境でのテスト）まで出していて、止めずに通せば合格になる出力だった。
止めたのは sacty の側で、`missingCommands` が1件でもあれば、判定を記録せずに `verify.commandMissing` で一時停止していた（[ゴールガーディアンが最終レビューの中でテストを実行し、sacty はテストのコンテナを使わない](20261021-1431-superseded-guardian-runs-tests.md)の決定3）。
2つの方針が衝突していた。

- ツールがイメージに無いときは、実装をやり直しても直らないので止める（20261021-1431）。
- 環境が原因のテストの失敗と、作業領域では確かめられないことは、不合格にせず人の確認に回す（[環境が原因のテストの失敗と、作業領域では確かめられない確かめ方を、人の確認として最終承認へ回す](20261024-1124-human-checks-at-final-approval.md)）。

変更が実行される振る舞いを持たない文書だけなら、ツールが無くてコードのテストを実行できなくても、検証の結果は変わらない。
止めてイメージを直させても、人に手間をかけさせるだけになる。
一方で、コードを含む変更は、ツールが無いまま通すと検証されないコードが残るので、これまでどおり止める必要がある。

止まった後の復旧にも問題があった。
`verify.commandMissing` で止まったタスクは `testCommand` が決まっているので、人が再開のときにテストの扱いを変えられなかった（変えられるのは、テストが決まらずに止まったタスクだけ。[テストが決まらずに止まったタスクは、人が再開のときにテストのコマンドかテストなしを決められ、決めずに再開すると工程の選択からやり直す](20261022-1544-decide-tests-when-resuming.md)）。
「文書だけの変更なのでテストなしで進める」と画面から決められず、イメージを足して作り直すしかなかった。

## 決定

1. **文書だけの差分は止めない**：最終レビューで、ゴールガーディアンが `missingCommands` に書いたツール（これまでと同じく、テストのコマンドに語として書いてあり `/` を含まないもの）があっても、タスクの差分が文書のファイルだけなら、一時停止しない。
   - 差分は sacty が取る（`diffStats`。名前の変更は変更元と変更先に分ける）。ゴールガーディアンの申告には頼らない。
   - 文書のファイルは、拡張子が `md`・`markdown`・`rst`・`adoc`・`asciidoc`・`org` のもの。テストのファイルを探すとき（PBI-94）に文書として除く一覧から、`txt` を外したもの（その一覧自体は変えない）。`txt` は requirements.txt・constraints.txt・CMakeLists.txt など、依存やビルドの定義にも使われ、実行される振る舞いを変えうるため、文書とは見なさない。
   - 文書でないファイルが1つでもあれば（文書とコードが混ざる差分、コードを文書の名前に変えた差分を含む）、文書だけとは見なさず、これまでどおり止める。
     差分が空のとき、ファイルごとの変更を取れないときも、止める側に倒す。
   - 止めないときは、ゴールガーディアンの判定を `FinalReviewed` に記録する。`tests.missingCommands` に実行できなかったツールを記録し、その検証を「<ツール> のある環境で、テスト（検証）のコマンドを実行して確かめてください」という項目として `humanChecks` に足す（PR の本文と画面の「人が確かめること」に出る）。
     項目には、ゴールガーディアンが実行したときの終了コードと出力の抜粋を含め、ツール不足のほかの失敗が混ざっていないかも確かめるよう書く。
     抜粋は、`a && b` の前半の失敗が後ろのツール不足の行に隠れないよう、末尾だけでなく、先頭と、途中の失敗らしい行（`error`・`fail` などを含む行）も載せる。
     コマンドと出力は、秘密情報と URL の認証情報（ユーザー名・パスワード・クエリ・フラグメント。スキームの大文字・小文字を問わない）を、全文で伏せてから切り詰める。
     URL の認証情報を伏せる処理は、共通の `redactLog` に足した（CI のログの抜粋にも効く）。
   - このときのテストは、終了コードにかかわらず通ったものとして扱う（`guardianTestsPassed`）。観点・指摘の判定は、ゴールガーディアンのとおりに当てる。
   - ただし、ゴールガーディアンがツール不足のほかの失敗（テストの失敗・lint のエラーなど）を `tests.otherFailures` に1件でも申告したときは、通ったものにしない。止めずに、ふつうの判定にする（終了コードが 0 でなく、環境による失敗の申告も無ければ、テストは不合格で、実装をやり直す）。
2. **ツールが無くて止まったタスクは、再開でテストの扱いを決め直せる**：`verify.commandMissing` で止まった、テストのコマンドが決まっているタスク（テストの仕組みが無いタスクの、実装が申告したコマンドは含めない）も、再開のときにテストのコマンドを指定し直すか、理由を書いてテストなしで進めると決められる（`TestsDecided`）。
   - テストなしにしたときは、止まる前の `testCommand` を消す（残すと同じコマンドをまた実行して止まる）。不具合の修正はテストなしにできない。
   - 決めずに再開したときは、止まった所から最終レビューをやり直す（工程の選択からはやり直さない）。
   - 止まったときの文言に、再開のときの「テストの扱い」で決め直せることを添える。
3. ゴールガーディアンの指示に、ツールが無くても、実行できる検証と観点・指摘の判定を最後まで行うこと、ツール不足のほかの失敗を `tests.otherFailures` に書くことを足す。

## 理由

- 文書だけの差分は、実行される振る舞いを変えない。コードのテストを実行できなくても、起点でも結果は同じなので、イメージを直させて止める意味が薄い。
  人が確かめる項目として残せば、検証が抜けたことは最終承認で見える。
- 文書かどうかを sacty が差分のパスで機械的に判断するのは、ゴールガーディアンの申告（「文書だけなので」）に頼ると、誤って申告したときにコードのツール不足を見逃すため（20261024-1124 の影響と同じ種類のリスク）。拡張子の一覧は小さく保守的にし、迷うもの（画像・設定・拡張子の無いファイル）は文書とは見なさない。
- 止める条件を残したのは、コードを含む変更は、ツールが無いまま通すと検証されないコードが残るため。20261021-1431 の決定3は、文書だけの差分という例外を除いて、そのまま効く。
- 再開でテストの扱いを決め直せるようにしたのは、止まったときの手立てがイメージを足して作り直すことだけだったため。
  文書だけの変更や、そのイメージで検証しなくてよいと人が判断できるときは、画面から決めて進められる。
  人の判断は `TestsDecided` として作業履歴に残る。コードの変更を含むタスクでも、人が責任を持って決めることは、テストが決まらずに止まったタスクと同じ。
- 比べたほかの案（採らなかった）：
  - プロンプトだけで「文書だけなら `missingCommands` を空にする」とゴールガーディアンに指示する案（A-1）：申告に頼るので、上のリスクが残る。
  - オーケストレーターが、文書だけの依頼では `testCommand` を変更が及ぶ範囲に絞る案（B）、不足を実装の前に申告させる案（C）：今回の範囲外。止まる原因の根を断つ案Bは別に検討する。

## 影響

- 文書だけの差分では、検証のコマンドが実行されないまま最終承認に進みうる。ツール不足のほかの失敗が混ざる場合への備えは、次のところまでにした。
  - ゴールガーディアンが `tests.otherFailures` に申告した失敗は、通さない。ただし、これは申告に頼る。ゴールガーディアンが、ツールが無くて実行できなかった以降のコマンドの失敗に気づけない（`&&` でつないだコマンドの途中で止まって、後ろが実行されない）ときは、見逃す。
  - 申告が無いときの備えは、人が確かめる項目に、終了コードと出力の抜粋（先頭・途中の失敗らしい行・末尾）を載せ、ツール不足のほかの失敗が混ざっていないかを確かめるよう書くことだけ。失敗らしい行は文言（`error`・`fail` など）で拾うので、これらの語を含まない失敗は、先頭と末尾にも無ければ載らない。
  - 伏せる処理は、渡せる既知の秘密の値を使っていない（最終レビューの出力は、ゴールガーディアンの実行の後で、既知の値を伏せてから読むので、出力はその分も伏せられている。コマンドは、形による伏せ（トークンの形・`password=` などの代入・URL の認証情報）だけ）。終了コードを 127 に限る案は、`make` 経由で終了コードが変わるなどで、文書だけなのにやり直しが繰り返されるので採らなかった。
- 文書かどうかを拡張子で見るので、次の穴が残る。実行される振る舞いに関わる文書は、文書だけとは見分けられない。
  - 文書のファイルがコードに埋め込まれる・読み込まれる場合（Go の `//go:embed`、Rust の `include_str!`、テストの期待値のファイルにした Markdown、README の例を実行する doctest・ドキュメントのテストなど）。
  - 文書の拡張子のファイルが、ビルドや生成の入力になっている場合。
  - 拡張子が同じでも、中身が文書でないファイル（`.rst` や `.org` を設定に使うツールなど）。
  これらは、人が確かめる項目（実行できなかった検証）で補う。一覧を広げる・狭めるときは、新しい ADR で決める。
- 文書の拡張子の一覧に無い文書（`.mdx` など）と、`.txt` の文書（ライセンスのメモなど）、文書の画像は、文書だけとは見なさず、これまでどおり止まる。
- `FinalReviewed` の `tests` に、省略可の `missingCommands` が加わる。それより前の版の記録は、そのまま読める。
- ツールが無くて止まったタスクは、再開の欄に「テストの扱い」が出る（テストのコマンドの入力欄に、いまのコマンドが初期値で入る）。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md#実装の検証)・[ツールが無くて止まったタスクの再開](../spec/tasks-and-steps.md#ツールが無くて止まったタスクの再開)。使い方は [検証のツールがイメージに無いとき](../user/tasks.md#検証のツールがイメージに無いとき)。
