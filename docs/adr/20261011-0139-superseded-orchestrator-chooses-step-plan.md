# タスクの開始時に、オーケストレーター（AI）がタスクと対象リポジトリのコードを読んで、決まった候補から工程を選ぶ

- 日時: 2026-10-11 01:39 UTC
- ステータス: 置き換え済み（superseded）
- 関係する PR・タスク: #23、PBI-17
- 置き換え元: なし
- 置き換え先: [「PR作成」の工程をなくし、実装の工程の中で PR を作って承認を待つ](20261015-1430-superseded-implement-step-opens-pull-request.md)（候補の組み合わせの最後に PR作成の工程を置く部分）

## 背景

工程は固定（要求要件 → 設計 → 実装 → PR作成）で、オーケストレーターは AI ではなく、決まった工程を記録するだけだった。動作確認で、調査やレビュー、タスク分解も実体のリポジトリを探索する必要があること、今後さまざまなタスクの種別を足すことがフィードバックされた。

## 決定

- タスクを作った時点では工程を決めない。最初の実行で対象リポジトリを用意した後、オーケストレーターを新しいセッションで実行し、工程を選ぶ。起点のコミットのコードを読み取り専用で渡す。オーケストレーターは工程エージェントと同じ AI（`default_agent`）にする。選んだら、同じ実行で最初の工程を続けて行う。
- オーケストレーターは工程を選ぶだけにする。タスクの分割も工程の一つにし、そこへ回すかをオーケストレーターが判断する（分割の工程は後のタスク）。
- 選べるのは、sacty が決めた候補（`STEP_PLANS`）の中だけ。このときの候補は `standard`（要求要件 → 設計 → 実装 → PR作成）と `skip-design`（要求要件 → 実装 → PR作成）。工程の種類を増やすときは候補に足す。
- オーケストレーターの判断は人間が承認しない。選んだ組み合わせ・理由・費用を作業履歴に記録する（費用は予算に入れる）。
- 読めない・候補に無い・実行に失敗したときは、`standard` で進め、そのことと理由を記録する。
- 設計を省いたタスクは、要求要件の受け入れ条件（観点 `REQ`）を、テストの対応の確かめと最終レビューの両方で必須の観点にする。

## 理由

- 調査やレビュー、タスク分解も実体のリポジトリを探索する必要がある、今後さまざまなタスクの種別を足す、という動作確認のフィードバックによる（本文）。
- 工程を選ぶだけにすること・人間が承認しないこと・進める順（このタスク → 調査 → レビュー → 後で分割・再現など）は、ステークホルダーと決めた（本文）。それぞれの理由は記録に無い。
- 失敗したときに `standard` にする理由は記録に無い。
- `REQ` をテストの対応の確かめにも入れたのは、設計を省いた経路で `REQ` にテストを対応させなくても合格扱いになることがレビューで再現されたため（レビュー）。

## 影響

- 工程の選択にオーケストレーターの費用がかかる。
- 工程の種類を足すときは、候補と、オーケストレーターへの指示を足す。
- 画面は、選んだ工程と理由を出し、選ぶ前のタスクは選んでいるところだと出す。
