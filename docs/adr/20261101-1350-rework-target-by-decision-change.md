# PR の指摘の戻し先は、承認済みの決定を変えるかで決め、変えない指摘は実装に戻す

- 日時: 2026-11-01 13:50 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-266
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験で、実装の PR への指摘の戻し先が重くなった（S9）。
「要求要件で確認した『過去の削除は戻せない』を、README と設計メモに書いて」という指摘を、ゴールガーディアンは「承認済みの設計の影響範囲にその項目が無い」ことを理由に、設計から作り直した。
設計の3回目の実行だけで約 $26 かかり、予算の上限を超えた。実装の差し戻しなら約 $2 で済む指摘だった。
一方、S8 では、実装の PR への「画面に見ている範囲を出す」という指摘を設計に戻した。これは、設計が決めた画面の姿を変える指摘だったので、設計に戻すのが妥当だった。

これまでの指示は「できるだけ後ろの工程で解消できるかを先に考える」だったが、何をもって後ろの工程で解消できるとするかが曖昧で、承認済みの成果物に書き漏れがあると前の工程に戻していた。

## 決定

人が決めた方針（2026-11-01）：承認済みの要求要件・設計の決定を変えずに済む指摘は、実装に戻す。決定そのものを変える指摘だけ、前の工程に戻す。

- ゴールガーディアンへの指示に、戻し先を「指摘が承認済みの前の工程の決定（受け入れ条件・振る舞い・画面・API やデータの形・テスト観点・確認して決めたこと）を変えるか」で決めると書く。
  - 変えない指摘（文書への追記、実装の直し、決定済みのことの反映漏れ）は、その PR の工程（実装の PR なら実装）に戻す。承認済みの成果物に書き漏れがあっても、指摘の求めることが承認済みの決定から導けるなら、決定を変えるものとしない。
  - 決定を変える指摘は、今までどおり、その決定を持つ工程に戻す。複数の指摘のうち1つでも変えるなら、その工程に戻す。
- 理由の先頭に、どの決定を変える・変えないかを短く書かせる。
- 要求要件・設計の PR の指摘の判断にも、同じ基準と理由の書き方を指示する。

## 理由

- 前の工程に戻すと、承認済みの成果物を作り直して、人がもう一度承認する。工程ごとの費用が大きく、S9 では上限を超えた。決定を変えない指摘は、そこまでせずに実装で直せる。
- 「影響範囲の一覧に載っているか」ではなく「決定が変わるか」を基準にすれば、書き漏れと決定の変更を分けられる。S8 のように決定を変える指摘は、これまでどおり設計に戻る。
- 理由に決定の変更の有無を書かせるのは、戻し先の判断を後から人が確かめやすくするため。

## 影響

- 文書の追記のような指摘は、実装の差し戻しで済み、前の工程の再実行の費用が減る。
- 判断はゴールガーディアン（LLM）の読み取りによる。決定を変えないと誤って判断すると、実装に戻して直らず、次の指摘で正すことになる。判断のコード（`ReworkJudged` の形、戻し先の候補）は変えていない。
- 理由の書式は指示で求めるだけで、sacty は検査しない。
