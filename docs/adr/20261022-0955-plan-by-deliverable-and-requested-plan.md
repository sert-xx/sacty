# オーケストレーターに成果物から進め方を選ばせ、文書作成・作業のみ・設計だけをリポジトリのあるタスクでも選べるようにし、人がタスクの作成時に進め方を指定できるようにする

## 背景

手順書を作るタスクで対象リポジトリを選ぶと、オーケストレーターが要求要件 → 設計 → 実装の工程（`standard`）を選んでしまう、という報告があった。

調べると、原因は2つあった。

- 選べる組み合わせ（`allowedPlans`）が、`document`・`operation`・`design-only` をリポジトリの無いタスクだけに限っていた
  （[文書原稿と単発の外部作業を独立した承認工程で扱う](20261015-2353-superseded-non-code-workflows.md) と、置き換え元の ADR）。
  リポジトリを選んだタスクでは、文書作成を候補に出せず、実装する組み合わせのどれかを選ぶしかなかった。
- 選び方の指示が「文書という語だけで document にしない」「リポジトリ内の文書変更もファイル変更」と、文書を実装の側へ寄せる書き方だった。
  リポジトリのコードを読んで手順書を作る（リポジトリは変えない）仕事と、リポジトリに文書のファイルを足す仕事を見分ける軸が無かった。

また、オーケストレーターの判断が合わないときに、人が進め方を直す手段が無かった（タスクを作り直しても、同じ判断になりやすい）。

## 決定

- `document`・`operation`・`design-only` を、リポジトリの有無にかかわらず選べるようにする。制限は、`review`（対象リポジトリの PR を指すときだけ）と
  `split`（子タスクでは選べない）だけにする（`selectablePlans`）。
  - リポジトリのあるタスクの文書作成は、起点のコミットのコードを使い捨ての写しで作業領域に置き、根拠として読ませる（リポジトリは変えない）。
  - リポジトリのあるタスクの設計だけは、要求要件・設計を PR でレビューする設定なら、ほかの組み合わせと同じくその PR のマージで承認する。
- 選び方の指示を、成果物から選ぶ形に書き直す。まず成果物（情報・PR のレビュー・リポジトリの外で読まれる原稿・外部への単発の変更・全体の設計・
  リポジトリのファイルの変更）で分け、実装する組み合わせのときだけ規模と明確さで選ばせる。対象リポジトリがあることを実装する組み合わせの理由に
  しないこと、迷うときは「成果を PR でレビューしてリポジトリに残すことが依頼に書かれているか」で決めることを書く。
- タスクの作成（画面・API）で、進め方（`plan`）を任意で指定できるようにする。既定は自動（オーケストレーターが選ぶ）。
  - 指定は `TaskCreated` の `plan` に記録する。作成の時に、タスクの形で選べるかを確かめ、`review` は対象リポジトリの PR のリンクが題か内容に
    あるときだけ受け付ける。
  - 工程を選ぶときは、指定した組み合わせだけを候補にし、オーケストレーターにはベースブランチ・テストのコマンド・イメージなどだけを決めさせる。
  - 指定した組み合わせは、工程の見直しで工程を飛ばさない。

## 理由

- 選ぶ軸を成果物にすると、「手順書」「ドキュメント」といった語やリポジトリの有無に引きずられずに、リポジトリを読んで原稿を作る仕事と、
  リポジトリのファイルを変える仕事を見分けられる。前の指示の「文書という語だけで document にしない」は、リポジトリ内の文書変更を
  document に逃がさないためのものだったが、成果物で分ければ同じことを言える。
- 文書作成の工程は、もともと使い捨ての写しで実行でき、リポジトリを変えない。リポジトリのあるタスクで選べるようにしても、PR やブランチの扱いは
  増えない。
- 人が指定できると、オーケストレーターの判断が合わないときに、作り直さずに直せる。指定しても、リポジトリを読んで決めること（テストのコマンドなど）は
  オーケストレーターに任せる。
- 指定した組み合わせで工程を飛ばすと、人が選んだ進め方と違う結果になるので、飛ばさない。
- 比べた案：
  - 指示だけを直し、リポジトリのあるタスクでも document を選べるようにする（指定は足さない）。判断の誤りを人が直せないままになるので、両方を入れた。
  - 指定を「ヒント」として渡し、オーケストレーターが選び直せるようにする。人の指定が覆ると、指定した意味が分からなくなるので、固定にした。
  - 工程を1つずつ人が選べるようにする。組み合わせの前提（分割の前の設計、実装の前の調査など）が崩れるので、決まった組み合わせから選ぶ形にした。

## 影響

- リポジトリのあるタスクでも、オーケストレーターが文書作成・作業のみ・設計だけを選ぶことがある。
- 人が指定したタスクは、要らない工程があっても飛ばさない。要らなければ、差し戻しや中止で扱う。
- 再実行（中止したタスクのやり直し）は、元のタスクの指定を引き継がない（自動で選ぶ）。
- 仕様は [タスクと工程](../spec/tasks-and-steps.md) の「進め方の組み合わせ」「作成時に指定した進め方」「非開発作業と工程の選択」「工程の見直し」、
  利用者向けは [タスクを進める](../user/tasks.md) の「進め方を指定する」に書く。
