# ユーザードキュメントはです・ます調にし、その書き方の規則は docs/README.md に置く

## 背景

docs/user は利用者がそのまま読むページだが、本文は常体（〜する・〜しない）で書いていた。また、ユーザードキュメントの書き方の
規則（ファイルの分け方・書き方の規則・ひな形）を、利用者向けの入口である `docs/user/README.md` に置いていた。利用者に見える
ページに、開発者向けの規則が混ざっていた。

## 決定

- docs/user の本文は、です・ます調で書く（見出し・表の短い項目・コードブロックの中のコメントは、体言止めや常体のままでよい）。
- `docs/user/README.md` は、利用者向けの概要と目次だけにする。
- ユーザードキュメントの書き方・分け方・ひな形の規則は、`docs/README.md` の「ユーザードキュメントの書き方」に置く。
  docs の方針のスキル（`.claude/skills/sacty-docs/SKILL.md`・`.agents/skills/sacty-docs/SKILL.md`）は、そこを正本として参照する。
- 仕様書・ADR・作業履歴の規則は、これまでどおり各ディレクトリの `README.md` に置く（これらは開発者向けのページなので）。

## 理由

- 置き場所の候補は、スキル・`docs/README.md`・新しい開発者向けのページだった。スキルは「README が正本で、スキルはそれに従う」
  という関係にしてあるので、規則の正本をスキルに移すとこの関係が崩れる。新しいページを足すと、ほかの種類（各ディレクトリの
  README）と置き場所がばらばらになる。`docs/README.md` は docs 全体の方針を書く開発者向けのページで、ユーザードキュメントの方針も
  すでにここにあるので、細かい規則も同じ節の下に置いた。
- です・ます調は、利用者向けのページとして読みやすくするため（ステークホルダーの要望）。

## 影響

- ユーザードキュメントを書く・直すときは、`docs/README.md` の「ユーザードキュメントの書き方」を読む。
- `tests/docs/docs.test.ts` で、規則の節が `docs/README.md` にあり、`docs/user/README.md` に規則の見出し（ファイルの分け方・
  書き方の規則・ひな形）が無いことを確かめる。です・ます調そのものは、テストでは確かめない（レビューで見る）。
- 方針の全体は [docs の入口](../README.md)。
