# 最終レビューの出力の JSON が崩れていても、直して読み、読めなければ何が読めなかったかを残す

- 日時: 2026-11-04 01:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-298
- 置き換え元: なし
- 置き換え先: なし

## 背景

実験 S5 r4（findings F43）で、最終レビューの出力6回のうち3回が、JSON の `tests` の閉じ括弧 `}` を欠いていた（`"otherFailures":[]` の直後）。sacty は出力を読めず、最終レビューをやり直した。やり直しの費用は $3.81 で、最終レビューの費用の 32% にあたる。欠けた `}` を補えば3回とも読め、判定は合格だった。監査の出力には、[PBI-293 の ADR](20261103-0900-read-broken-audit-json-leniently.md) で崩れを直して読む仕組みを入れたが、最終レビューには無かった。

## 決定

- **最終レビュー・統合レビューの出力を、監査と同じ寛容な読み取りで読む**：文字列の中の二重引用符・制御文字・JSON にない `\` のエスケープ・閉じる括弧の前のカンマを直す。
- **最終レビューの `tests` の閉じ括弧の欠けを、項目の名前で補う**：`tests` の中に、判定のオブジェクトの項目（`humanChecks` など）が現れたら、`tests` を閉じ忘れたとみなして、その前に `}` を補う。括弧の数だけで末尾に足すと、`humanChecks` などが `tests` の中に入ったまま読めてしまうため、使わない。
- **直し方が決まらない、または直した結果が期待する形でないときは、読まない**：同じ項目が入れ子の外にも既にある・補ったあとに `tests` の項目が外に現れる・閉じる位置を決める項目がない場合は読めないとし、直した結果に観点の配列と `summary` がなければ読まない。判定を誤って合格にしないことを、読めることより優先する。出力の末尾で括弧が足りないだけの場合も、出力が途中で切れた場合と区別できないので補わない。
- **直して読んだことを、判定の記録（`FinalReviewed`・`IntegrationReviewed`）の `outputRepaired` に残す**。作業履歴の行にも出す。実タスクで効いたかを後から確かめられる。
- **読めなければ、何が読めなかったかを失敗の理由に残す**：最終レビューは `FinalReviewFailed` の理由（今までのやり直し・3回で一時停止はそのまま）、統合レビューは所見に、JSON の何行目の何文字目かを残す。前後の文字は、監査と同じく、エスケープを戻した出力の全体を秘密情報を伏せる関数にかけて変わらないときだけ残す。

## 理由

- 欠けは、次に来る項目の名前で確実に決まる。決まらないときだけ読まなければ、誤って直すおそれは小さく、かつ高い再実行の費用を避けられる。
- AI への再依頼は費用がもう一度かかり、同じ崩れを繰り返しうる。再実行を足す案は、PBI-293 と同じ理由で採らない。
- 直した結果の形を確かめるので、判定が甘くならない（観点や指摘の判定、テストの終了コードは、読めたとおりに使う）。

## 影響

- `tests` の閉じ括弧が、判定のオブジェクトの最後の項目の後ろで欠けた出力（`tests` の外の項目が続かない）は、今までどおり読めない。
- 括弧の数は合っていて、`}` が末尾にずれた出力（`humanChecks` が `tests` の中に入って読める）は、JSON として正しいので、今回は直さない。
- 最終レビューの評価用の読み取り（`assertFinalReviewVerdict`）は、プロンプトの出来を測るので、直さずに読む。
