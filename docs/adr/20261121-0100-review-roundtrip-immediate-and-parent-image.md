# レビューの往復の待ちを削る：sacty のレビューは静かな時間を待たず、提出の直後に再レビューを始め、子タスクは親のイメージで動く

- 日時: 2026-11-21 01:00 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-425
- 置き換え元: なし
- 置き換え先: なし

## 背景

タスクの登録からマージまでの時間の約 17% は、仕組みの待ちだった。そのうち、レビューの往復の待ちが次の3つあった。

- sacty のレビューの投稿を、PR を作ったタスク（親）に取り込むまでの待ち（実測の中央値 154 秒）。取り込みは 60 秒ごとの PR の確認だけが行い、人の指摘も sacty のレビューも区別せず、最後のフィードバックから2分待っていた。sacty のレビューは本文と行へのコメントを 1 回で投稿するので、書き終わりを待つ理由が無い。
- 親が直しを提出してから、子タスクの再レビューが始まるまでの待ち（中央値 35 秒、最大 334 秒）。再レビューを始めるのも、60 秒ごとの確認だけだった。
- 子タスクが工程のイメージを選ぶためのオーケストレーターの実行。子は、親が PR を作ったイメージを引き継いでいなかった（[タスクのイメージ](20261108-0334-task-image.md)）。

## 決定

- 静かな時間は、まだ取り込んでいないフィードバックのうち、人の指摘（`source` が `sacty_review` でないもの）のいちばん新しいものから数える。人の指摘が混ざる回は、sacty のレビューも一緒に待つ。
- 子タスクがレビューの投稿を記録した直後に、親の取り込みを始める。内容は GitHub から読む（子から親へ直接は渡さない）。失敗したら警告だけにして、60 秒ごとの確認が取り込む。
- 親が直しを提出した直後に、その親の子タスクの再レビューを始める。始められなければ、60 秒ごとの確認が始める。
- 取り込みと再レビューは、親ごとに直列に流し、後の方は、先の方が記録した後の台帳で判断する。
- sacty が自分の PR のために作った子タスクは、オーケストレーターを実行せず、親のタスクのイメージで動く（`StepsChosen` の `imageSource` は `parent`）。親のイメージを決められないときだけ、今までの決め方に戻る。再実行・作成時・プロジェクトの対象の指定は、親のイメージより優先する。

## 理由

- 待ちを削る方法のうち、60 秒ごとの確認の間隔を縮める案は、範囲外にした（GitHub への問い合わせが増える）。
- 取り込みの内容を子から親へ直接渡す案は、利用者が入れないと決めた。
- 親のイメージは、子が工程を選ぶ時点の親のタスクのイメージとした。人が後から変えた場合は、変えた後のイメージで動く（親の次の直しも同じイメージで動く）。PR を作った実行のイメージを求める場合の違いは、人が確かめる。
- 別の値（`project` など）を流用すると、作業履歴の「イメージを決めた元」が事実と違うため、`parent` を足した。

## 影響

- [PR のレビューの子タスクと指摘の取り込み](../spec/approval.md)、[工程の選択](../spec/tasks-and-steps.md)、[利用者向けの説明](../user/intake.md)を直した。
- PR を作ったタスクのイメージが、レビューを動かす環境になる。
