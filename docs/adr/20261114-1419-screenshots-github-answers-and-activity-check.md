# スクリーンショットを撮る間は、GitHub の API にデータのとおりの答えを返し、デーモンが作業履歴に書き足したら画像を置き換えない

- 日時: 2026-11-14 14:19 UTC
- ステータス: 採用
- 関係する PR・タスク: なし
- 置き換え元: なし
- 置き換え先: なし

## 背景

ユーザードキュメントのスクリーンショットは、架空のデータを作業履歴に直接入れた一時の `SACTY_HOME` で `sacty up` を起動して撮る（[図とスクリーンショットの ADR](20261022-1732-docs-svg-diagrams-and-screenshots.md)）。
撮る間もデーモンは動いていて、起動の後に PR の確認をする。
このため、次の2つの問題があった。

- データが実装の流れとずれると、デーモンが直そうとして、その結果が画像に写る。
  - 設定・操作・トラブルの説明のためのデータ（`seed.mjs`）は、以前の版の流れ（実装の前段の調査・最終レビュー）で書いたままだった。
    承認待ちの PR に PR のレビューの子タスクが無いので、デーモンが子タスクを作って実行し、撮る環境では失敗した。
    リポジトリの `task-list.png` には、その子タスクが「エラーで一時停止」として写っていた。
  - ずれても、データを入れるスクリプトも撮影も失敗しないので、画像を見るまで気づけなかった。
- 撮る環境では GitHub を読めない。
  - `gh` は代わりのスクリプトで、トークンは架空なので、GitHub の API は認証のエラーを返す。
    デーモンは承認待ちの PR の先頭を読めず、タスクの詳細の「Sacty の AI のレビュー」が「PR の今の head をまだ読めていないため、AI のレビューの状況は分かりません」になる。
    これは、ふだんは起動の直後や GitHub を読めないときにしか出ない表示で、3枚の画像（タスクの詳細・PR での承認・質問の欄）に、注意の色で写っていた。
    紹介のページにタスクの詳細を載せなかったのも、このためだった（[紹介のページの ADR](20261114-1318-user-docs-introduction-page.md)）。
  - 「実際の GitHub は使わない」としていたが、デーモンは撮るたびに、架空のリポジトリの名前と架空のトークンで、実際の GitHub の API に問い合わせていた。
    データがずれていたときは、PR にコメントを書こうとし、リポジトリを取得しようともしていた（どれも認証できずに失敗する）。

## 決定

- 撮る間は、GitHub の API への問い合わせに、データのとおりの答えを返す。
  - `scripts/docs-screenshots/github-stub.mjs` を、`sacty up` のプロセスに読み込ませる（`NODE_OPTIONS` の `--import`）。
    `api.github.com` への `fetch` だけに答え、ほかの宛先はそのまま通す。
  - 答えは、データを入れるスクリプトが、入れた作業履歴から作って `SACTY_HOME` に書く（`seed-lib.mjs` の `githubAnswers`）。
    sacty が作った PR は、台帳に記録した状態・先頭のコミット・ドラフトのまま。マージの後の監視で CI/CD を待っているコミットは、CI が実行中。
  - 答えるのは、PR の確認が読むものだけ（PR の状態、PR のレビューとコメント、コミットの CI/CD）。
    書き込みと、答えを用意していない問い合わせには失敗を返し、ログに出す。
- 撮る間にデーモンが作業履歴に書き足したら、撮影を失敗にし、画像を置き換えない。
  - `capture.mjs` が、データを入れた直後と、撮った後の作業履歴の件数を比べる。
    画像は一時の場所に撮り、書き足しが無いと確かめてから出力先に置く。
  - 失敗のときは、書き足されたイベントの種類とタスクの題を出す。
- データは、今の実装が記録する流れで書く。
  - sacty が作る PR（要求要件・設計・実装）には、レビューを終えた子タスクを入れる（紹介のためのデータと同じ道具 `seed-lib.mjs` を使う）。
  - 以前の版の流れの記録（実装の前段の調査・`FinalReviewed` など）は、その記録を写す画面に要るときだけ入れ、理由をコメントに書く。
    今は、入れているものは無い。不安定なテストの台帳は今の監査の画面に出ないので、台帳のための `FinalReviewed` の記録は消した。

## 理由

- GitHub の答えを用意するのは、「AI のレビューの状況は分かりません」を、ふだんの状態（付いています）で写すためと、撮影を実際の GitHub から切り離すためである。
  比べたほかの案と、採らなかった理由は次のとおり。
  - その表示を含まない範囲で撮る：表示は、承認の案内のすぐ下にあり、タスクの詳細の並びを見せる画像から外せない。
    外すために承認待ちでないタスクで撮ると、PR での承認の画像を撮れない。
  - 撮る環境の制約として、そのまま残す：読む人には、いつも注意が出る画面に見える。
    利用者向けの説明（PR の今の head に AI のレビューが付いているかが出る）とも合わない。
  - デーモンに、GitHub の API の宛先を変える設定を足す：撮影のためだけに、利用者に見える設定と、トークンを別の宛先へ送れる口を増やすことになる。
    すでに Docker・gh・キーチェーンを代わりのスクリプトにしているのと同じく、撮影の側で差し替える。
- 答えをデータから作るのは、台帳と GitHub の状態を必ず一致させるためである。
  別に書くと、データを直したときに答えを直し忘れ、デーモンがドラフトの切り替えや再レビューを始める。
- 書き込みに答えないのは、撮る間にデーモンが GitHub を変えようとするのは、データが流れと合っていないときだけだからである。
  成功を返すと、ずれに気づけない。
- 書き足しで失敗にするのは、データのずれを、画像を見る前に見つけるためである。
  ずれたデータは、作業履歴として読める（投影できる）ので、データを入れるスクリプトでは見つからない。
  画像に写って困るのは、デーモンが直そうとして状態を変えるずれで、そのときは必ず作業履歴に書き足す。
  デーモンが何もしないずれ（終わったタスクの古い記録など）は、これでは見つからない。画像を目で確かめる。
- 画像を一時の場所に撮ってから置くのは、失敗した撮影の画像を、気づかずにコミットしないためである。

## 影響

- 工程の流れ・記録するイベント・PR の確認の動きを変えると、スクリーンショットのデータが古くなることがある。
  デーモンが直そうとするずれなら、次に撮り直すときに撮影が失敗するので、出たイベントを手がかりに、データを今の流れに直す（[docs の入口](../README.md)の「共通の規則」）。
  実装を変える PR で、データを直すことは求めない（画面に写る所が変わったら撮り直す、という今までの規則のまま）。
- 撮る画面の操作（`shots.mjs` の `prepare`）では、作業履歴に書く操作（タスクの作成・承認など）をしない。
  要るようになったら、その分を数えない仕組みを足す。
- デーモンが PR の確認で読む GitHub の API を増やしたら、`github-stub.mjs` に答えを足す。
  足していない問い合わせは、撮るときのログに `[github-stub]` と出る。
- GitHub の API のほかの通信は、差し替えていない。
  データが流れと合っているかぎり、撮る間にデーモンは git でリポジトリを取得しない。合っていないときは取得を試みることがあるが、撮影は失敗になる。
- 撮るときに PR の先頭を読めるようになったので、紹介のページにタスクの詳細を載せなかった理由は無くなった。
  載せるかは、この決定では変えていない。
- 紹介のためのデータ（`seed-intro.mjs`）も、同じ仕組みで撮る。
