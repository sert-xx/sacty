# 指摘なしの後に実装の PR の CI が失敗したら、画面に出す（自動では扱わない）

- 日時: 2026-11-16 22:56 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-364
- 置き換え元: なし
- 置き換え先: なし

## 背景

sacty は、実装の PR の CI を待たない（[実装の最終レビュー（テストの実行）と PR の CI の待ちをやめ、PR のレビューの子タスクの指摘なしでドラフトを外す](20261112-0714-superseded-review-child-task-replaces-final-review-and-ci-wait.md)。CI を待たないことは、今も変わっていない）。
PR のレビューの子タスクは、レビューの時点の CI の状態を読み、終わっていないものは待たずに「実行中」と書く。

このため、子タスクが CI の実行中に「指摘なし」を出し、その後に CI が落ちても、PR を作ったタスクは人の承認待ち（マージ待ち）のままだった。
実際に、人が GitHub を見るまで、CI が落ちたことに気づけなかった。

## 決定

- 人の承認を待つ実装の PR（レビューの子タスクの指摘なしを待っていないもの）について、PR の確認で先頭のコミットの CI を読み、失敗があれば記録して、タスクの状態と詳細に出す。
- 出すだけにする。実装の工程への差し戻し・再レビュー・ドラフトへの変更・CI の再実行・通知は行わない。
- GitHub への問い合わせを増やし続けないよう、すべて通った先頭は読み直さず、失敗した先頭は5分ごと、CI の無い先頭は30分で読むのをやめる。

## 理由

- 求められたのは、CI が落ちたことが人に分かること。自動でどこまで扱うか（差し戻す・再レビューさせる・CI を待ってから指摘なしにする）は、費用と待ち時間に関わる方針で、人が決めていない。決まっていないことを推測で広げない。
- CI を待たない方針（PBI-331）は変えない。待つと、CI の長いリポジトリでレビューが遅れ、CI の無いリポジトリでは待ちの上限まで止まる。
- ベースブランチとの競合の表示（GitHub の状態を読み、変わったときだけ記録して、画面に出すだけ）と同じ形にした。人の出番の画面に並ぶので、見る場所が増えない。
- 比べた案：レビューの子タスクが、CI が終わるまで判定を出さない。CI を待たない方針と食い違うので採らなかった。
- 比べた案：失敗を、AI のレビューの指摘として親タスクに届けて、実装をやり直させる。変更と関係の無い失敗（不安定なテスト・CI の環境）でもやり直しが始まり、費用がかかる。失敗の原因の見分けは、今はレビューの子タスクがレビューの中でしている。

## 影響

- 競合の確認と違い、PR ごとに CI を読む問い合わせ（1回につき3つの一覧）が増える。読む間隔を空けて抑えている。
- CI の失敗は画面に出るだけなので、人が画面を見なければ気づかない（通知は出ない）。
- 失敗が、変更によるものか、関係の無いものかは、sacty は判断しない。人が PR で確かめる。
- 仕様は [指摘なしの後の CI の失敗の表示](../spec/approval.md#指摘なしの後の-ci-の失敗の表示) にある。
