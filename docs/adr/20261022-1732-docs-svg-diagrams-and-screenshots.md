## 背景

docs の概念図を Mermaid で入れたが、利用者から、色・アイコン・配置をきれいにした、もっとリッチな図にしてほしいと求められた。
Mermaid は配置を自動で決めるので、入れ子の枠をまたぐ矢印が崩れやすく、色やアイコンを付けると GitHub のライトとダークの表示のどちらかで読みにくくなる。
あわせて、ユーザードキュメントの画面に関する所には、スクリーンショットがあるとわかりやすいと求められた。

## 決定

- 図は、`scripts/docs-diagrams/diagrams/` に図の定義（カード・枠・矢印の位置と、日本語と英語の文言）を書き、`scripts/docs-diagrams/lib.mjs` で SVG にする。
  日本語の版を `<名前>.svg`、英語の版を `<名前>.en.svg` として `docs/spec/images/`・`docs/user/images/` に置き、本文から画像として使う。
  - 色は種類ごとの少しの色だけを使い、SVG の中の `prefers-color-scheme` でライトとダークを切り替える。
  - アイコンは、定義の中に自分で描いた線のアイコンだけを使う。
    外部の素材・ロゴ・生成した画像は使わない。
  - SVG は手で直さず、定義を直して `npm run docs:diagrams` で作り直す。
    `tests/docs` で、SVG が定義と一致することを確かめる。
- スクリーンショットは、`scripts/docs-screenshots/` で撮る。
  架空のデータを作業履歴に直接入れた一時の `SACTY_HOME` で `sacty up` を起動し、Playwright で日本語と英語の画面を撮る。
  Docker・gh・キーチェーンは、決まった答えを返す代わりのスクリプトにし、実際には使わない。
  監査の画面は、監査のモックのデータで撮る。
- 日英の画像がそろうこと・使われていない画像が無いことを `tests/docs` で確かめる。

## 理由

- 図を定義から作るので、配置を自分で決めて崩れない図にでき、日英で同じ配置の図を作れる。
  SVG を手で書くより、文言だけを直す・図を足すのが楽で、色やアイコンを図ごとにばらばらにしない。
- 比べたほかの案と、採らなかった理由は次のとおり。
  - draw.io（`.drawio.svg`）：自由に描けるが、この環境からは draw.io を取得できず書き出せなかった。
    差分が XML になり、日英で 2 つの図を別々に手で直すことになるので、実装とずれやすい。
  - 画像を生成する：作り手（Claude）には画像を生成する機能が無い。
    生成した絵は中身があいまいになりやすく、仕様書の用語どおりの図にできない。
  - Mermaid のまま色を付ける：配置を決められず、崩れやすさは直らない。
- スクリーンショットを架空のデータで撮るのは、実在の組織や秘密の値を写さず、撮り直しても同じ画面にするためである。
  実際のタスクを動かすには Docker と AI が要り、撮るたびに結果が変わる。
- Playwright は撮るときだけ使い、依存には入れない（`npm install --no-save playwright`）。
  ふだんの開発とテストには要らないためである。

## 影響

- 図を変えるときは、定義を直して `npm run docs:diagrams` を実行する。
  作り直していないと `tests/docs` が落ちる。
- 画面を変えてスクリーンショットに写っている所が変わったら、`npm run build` の後に `npm run docs:screenshots` で撮り直す。
  撮り直さなくてもテストは落ちないので、レビューで見る。
- PR の差分では、図の変更は定義の差分で読める。
  画像そのものは描画して確かめる。
- 方針は [docs の入口](../README.md) の「共通の規則」にある。
