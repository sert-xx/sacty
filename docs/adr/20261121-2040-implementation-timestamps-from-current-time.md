# 実装・直しの指示に指示を作った UTC の時刻を入れ、記録の日時が今より後なら直させる

- 日時: 2026-11-21 20:40 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-469
- 置き換え元: なし
- 置き換え先: なし

## 背景

担当が書いた ADR のファイル名・本文の日時が、未来の時刻になることが続いた（PBI-456・PBI-459 の PR で、人がコメントで直させた）。指示に今の日時が無く、担当が時刻を推測していたため。

## 決定

1. 実装・直しの指示のすべての枝に、指示を作った時刻（UTC、秒まで）と、日時を書くときは推測せず書く直前にコンテナで今の時刻を確かめる決まりを入れる。時刻は `buildPrompt` の `extra.now` で渡し、service は時計の `now` を渡す。
2. 提出の前に確かめる基準 `FUTURE_TIMESTAMP` と、レビューの観点 X-1 で、足したファイルの、記録の日時として書いたファイル名と対になる本文の日時の欄が今より後なら直させる。今は、リポジトリの決まりのタイムゾーンに直して比べ、決まりが無ければ UTC。期限・予定日などの日時は見ない。
3. 既定の規則には、「日時を書くときは今の時刻を確かめる」だけを汎用の形で足す。

## 理由

- 時刻を指示に入れれば、推測する余地が無くなる。時刻が古くなる長い実行でも、書く直前に確かめさせる。
- デーモンがファイル名を読んで止める検査にすると、リポジトリごとに違う日時の形とタイムゾーンを決め打ちすることになり、既定のコンテキストを汎用に保つ条件と両立しない。基準とレビューの観点なら、リポジトリの決まりに従わせられる。
- 要求要件・設計・文書作成の工程には時刻を入れず、既定の規則で確かめさせる。受け入れ条件が実装・直しだけを挙げているため。

## 影響

- 実装の指示は、実行ごとに時刻の行が変わる。
- 担当とレビューのどちらも見落とすと、未来の日時の PR が出うる。確実に止めるには、デーモンの検査を別に足す必要がある。
- すでに main にある未来の日時の名前は、過去の決定を書き換えないので直さない。
