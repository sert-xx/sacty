## 背景

ゴールガーディアンは、変更の申し出の判定・最終レビュー・PR の指摘の戻し先の判断のどれも、空の作業領域で動いていた。最終レビューは、テストの結果と差分（先頭 200KB）だけで判定していた。動作確認で、調査やレビューにも実体のリポジトリを探索する必要があるというフィードバックがあった。

## 決定

- 変更の申し出の判定では、タスクの起点のコミットのコードを渡す（#19 の PBI-15 と同じく、退避した git のメタデータから実行ごとのディレクトリに書き出す）。
- 最終レビューと PR の指摘の戻し先の判断では、実装後のコード（実装の作業領域の .git を除いた写し）を渡す。シンボリックリンクはたどらず、リンクのまま写す。最終レビューには、これまでどおり差分も渡す。
- どれも読み取り専用でマウントし、実行の後に消す。指示で、どのコードか（起点のコミットか実装後か）と、読むだけであることを伝える。
- 渡すのは、コードと、これまでどおり決めた情報だけ。タスクの内容・工程の経緯・過去の判定・コンテキストリポジトリ（規約・スキル）は渡さない。
- 用意できなければゴールガーディアンを実行せず、これまでの実行の失敗と同じに扱う（変更の申し出はエスカレーション、最終レビューは一時停止、戻し先は人間の確認）。

## 理由

- 調査やレビューにも実体のリポジトリを探索する必要がある、という動作確認のフィードバックによる（本文）。
- 戻し先の判断に実装後のコードを渡すのは、実装で直せるかを判断するため（本文）。
- シンボリックリンクをたどらないのは、ホストのファイルの中身を取り込まないため（本文）。

## 影響

- ゴールガーディアンがコードを読む分だけ、判定・レビューの費用が増えることがある。
- ゴールガーディアンの3つの実行を共通の処理にまとめた。
