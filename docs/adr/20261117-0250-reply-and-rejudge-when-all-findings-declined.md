# AI のレビューの指摘をすべて断って何も変えなかったら、断った理由を返信し、同じ先頭を 1 回だけ判定し直させる

- 日時: 2026-11-17 02:50 UTC
- ステータス: 採用
- 関係する PR・タスク: #402、PBI-357
- 置き換え元: [終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない](20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)（AI のレビューの指摘が残る先頭を、やり直しの実装が何も変えなければ、どの場合も提出にせずに一時停止する、という部分）
- 置き換え先: なし

## 背景

[終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない](20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)（PBI-347）では、PR のレビューの子タスクが指摘を残した先頭を、やり直しの実装が何も変えなければ、提出にせずに一時停止して、人が判断すると決めた。同じ先頭は再レビューされず、ドラフトのまま進まなくなるためである。

[取り込んだ PR の指摘への対応を、指摘ごとに PR に返信する](20261116-0045-superseded-reply-to-review-feedback-on-pull-request.md)（PBI-352）は、指摘への対応を PR に返信する。ただし、返信するのは、PR を更新して承認待ちになったときだけである。

この 2 つが重なると、実装が AI のレビューの指摘をすべて「当たらない」「範囲の外」と断り、何も変えなかったとき、次のようになる。

- 断った理由は、PR に返信されない（作業履歴にしか残らない）。
- レビューの子タスクは、断った理由を読まない。判定は「修正が必要」のまま残る。
- タスクは一時停止し、人が、作業履歴から理由を探して判断する。

実際に、範囲の外の指摘を実装がくり返し断って、この状態で止まったタスクがあった。

人が決めたこと（2026-11-17。選択式で確かめた）：断った理由を PR に返信し、レビューの子タスクに、同じ先頭を 1 回だけ判定し直させる。レビューが受け入れれば先へ進む。もう一度指摘が出たら、一時停止して人が判断する（AI どうしの往復を続けない）。

## 決定

上の ADR（PBI-347）の決定のうち、「AI のレビューの指摘が残る先頭を、やり直しの実装が何も変えなければ、提出にせずに一時停止する」を、指摘のすべてを断ったときについて、次のとおりに置き換える。ほかの場合の一時停止と、上の ADR のほかの決定は、今も有効で、変えない。

- やり直しの実装が何も変えず、次のすべてに当たるときは、提出にする（PR の先頭は同じ）。
  - 実装の最新の回の指摘（無効にしていないもの）のすべてが、AI のレビューの指摘で、その PR のコメントから取り込んだもの（元のコメントの記録がある）。
  - そのすべてに、実装が「理由があって対応しなかった」と申告し、理由を書いている。
  - そのどれにも、まだ返信していない。
  - セキュリティの組み合わせのタスクでない。
  - その先頭で、まだ判定し直しを求めていない。
- 提出すると、今の返信の仕組み（PBI-352・PBI-356）が、断った理由を、指摘の場所に返信する。
- 返信が済んだら、レビューの子タスクが、同じ先頭を 1 回だけ再レビューする。返信は、作者の返答として渡る。レビューの指示には、作者の理由が成り立つかを先頭のコードで確かめることを足す。
- 再レビューが指摘なしなら、今までどおりドラフトを外して、人の承認を待つ。
- 再レビューに指摘が残り、取り込んだ指摘のすべてが、その再レビューの AI のレビューの指摘なら、差し戻しの記録と同じ追記で一時停止する。再開すると、残った指摘を渡してやり直す。
- 判定し直しを求めるのは、同じ先頭に 1 回だけ。求めたこと（PR を作ったタスク）と、始めたこと（子タスク）を、どちらも作業履歴に記録する。
- 着手のときに決めたこと（人の確認は、まだ）：上の条件に 1 つでも当たらないとき（人の指摘が混ざっている・対応したと申告した指摘がある・申告の無い対応がある・対応の付いていない指摘がある・元のコメントの記録が無い）は、今までどおり、提出にせずに一時停止する。

## 理由

- 提出にして、今の返信の仕組みを使う：返信は、承認待ちの提出の、まだ返信していない指摘に対して行う作りになっている。提出にすれば、返信の形・二重の投稿の防ぎ方・レート制限に当たったときのやり直しを、そのまま使える。提出にしないまま返信するには、返信の条件と、返信を待つ新しい状態を足すことになる。
- 判定し直しを、返信の後に始める：断った理由を読まずに判定し直しても、同じ指摘が出るだけで、1 回だけの機会を使ってしまう。レート制限の待ちの間は、返信できるまで待つ（ふつうの再レビューは、待ちの間も返信を待たずに始めるが、判定し直しは、返信を読むことが目的のため）。
- 指摘が残ったら、やり直しを始めずに止める：差し戻してやり直させると、実装がもう一度断って、AI どうしの往復がもう 1 回続く。人が決めたとおり、指摘が残った時点で人に渡す。差し戻しの記録は残すので、再開すると、残った指摘がやり直しに渡る。
- 上限を作業履歴に持つ：メモリーに持つと、デーモンを起動し直すたびに、同じ先頭を判定し直してしまう。PR の先頭は進むだけで戻らないので、タスクごとに、最後に求めた先頭を 1 つ持てば足りる。
- 当たらないときは今までどおり止める：返信できない指摘（元のコメントの記録が無い）や、断った理由が書かれていない指摘が混ざると、レビューに渡る理由が欠ける。人の指摘は、AI のレビューが取り下げられるものではない。どちらも、人が判断する今の扱いが安全である。

## 影響

- 指摘のすべてを断った提出では、PR の本文の更新・リスクの評価・承認待ちの通知が、ふつうの提出と同じように行われる（提出の回が 1 つ進む）。
- 判定し直しの再レビューの費用が、1 回ぶん増える（子タスクの予算に数える）。
- 断った理由の返信を投稿できなかった（失敗を記録した）ときも、判定し直しは始まる。その再レビューには、断った理由が渡らない。
- 判定し直しは、先頭ごとに 1 回である。実装が後で PR を変えて先頭が進み、その先頭の指摘をまたすべて断ったときは、その先頭でもう 1 回行う。AI のレビューの往復の回数そのものの上限は、決めていない（予算の上限で止まる）。
- 判定し直した再レビューの指摘に、人の指摘が混ざって届いたときは、止めずに、今までどおり差し戻してやり直す。その後に同じ先頭で何も変えなければ、今までどおり一時停止する。
