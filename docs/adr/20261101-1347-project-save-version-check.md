# プロジェクトの設定の保存は、読み込んだ版を照合し、変わっていれば上書きせずに知らせる

- 日時: 2026-11-01 13:47 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-274
- 置き換え元: なし
- 置き換え先: なし

## 背景

実務での実証実験で、3人の担当が SactyTest のプロジェクトの対象リポジトリをほぼ同時に足したとき、1人が足して保存した直後に、別の担当の保存でその追加が消えた。
プロジェクトの設定の保存は、画面が読み込んだときの内容でプロジェクトの定義をまるごと置き換えていた。版の照合も差分の適用も無く、後から保存した画面が、読み込んだ後の他人の変更を知らずに上書きした。複数の人（やエージェント）が同じプロジェクトの設定を触ると、気づかずに変更が消える。

## 決定

保存のときに、画面が設定を読み込んだ版を照合し（楽観ロック）、その後に変わっていれば、上書きせずに利用者に知らせる。

1. **版**：プロジェクトの `updatedAt`。保存先で、保存するたびに前の値より後の時刻にする（同じミリ秒の2回の保存や時計の巻き戻りでも変わる）。新しい列や項目は足さない。
2. **API**：`PUT /api/projects/:id` は、読み込んだ版を `If-Match` ヘッダーで必須にする。無ければ 428。照合に合わなければ 409（`project.changedElsewhere`）で、設定も版も変えない。照合と保存は同じ同期の処理で行い、同時に保存しても先の変更を後が消さない。作成・インポートは版を要らない。
3. **画面**：設定を読み込んだ版を保存に添える。自分が保存したら、返ってきた版に進める。画面の取り直しで届いた版には進めない。409 のときは、理由と「再読み込みして最新の設定を見る」ボタンを出し、編集中の入力は再読み込みするまで残す。
4. **併合**：しない。別の項目だけを変えていても、古い版の保存は拒否する。

## 理由

- 気づかない上書きを無くすのが目的。照合だけなら小さな変更で足りる。版は、既にある `updatedAt` を使えば、保存先の構造を変えずに済む。同じミリ秒の保存でも変わるようにして、照合の取りこぼしを防ぐ。
- 項目ごとに併合する案は採らない。対象・コンテキスト・チケットなどの項目は互いに関係し（重複の検査・コンテキストの合成）、自動で併合すると、誰も見ていない組み合わせの設定を保存しうる。知らせて、最新を見てからもう一度変えてもらうほうが安全。
- 版の無い `PUT` を受け付けると、API を直接呼ぶ側で同じ事故が起きる。呼べるのは画面のサーバーだけなので、必須にしても互換の問題は小さい。
- 画面の取り直しの版に進めないのは、取り直しで届いた他人の変更を、編集中の画面は見ていないため。進めると、見ていない変更を上書きできてしまう。

## 影響

- `PUT /api/projects/:id` を直接呼ぶ側は、`If-Match` に読み込んだ `updatedAt` を付ける必要がある。
- 古い画面で保存すると、内容に関係なく保存されず、再読み込みが要る。編集中の入力は再読み込みで失われる（画面に残っている間に書き写す）。
- 同じ仕組みは、sacty の設定（`PUT /api/settings`）・スケジュールタスク（`PUT /api/schedules/:id`）には入れていない。同じ型の上書きは、これらにも残る。
- 仕様は [アーキテクチャ](../spec/architecture.md)。使い方は [同時に変更したとき](../user/project-settings.md#同時に変更したとき)。
