# 実装の PR の CI の待ちは、リポジトリに CI が無いと確かめられたら短い猶予で終える

- 関係する PR・タスク: PBI-309、#315
- 置き換え元: なし

## 背景

最終レビューの前に作った実装の PR の CI は、チェックが1つも現れないと `PULL_REQUEST_CI_GRACE_MS`（5分）待ってから `none` にしていた。
CI が無いリポジトリでは、提出のたびに、やり直しのたびに、必ず5分ほど止まる。手元の実行記録では、この待ちが `none` に終わる回が続いていた。

5分を一律に縮めると、ワークフローの作成や外部の CI の報告が遅いリポジトリで、CI を見逃して最終レビューに進んでしまう。

## 決定

- チェックが1つも無いとき、リポジトリに CI が無いと確かめられたら、`PULL_REQUEST_NO_CI_GRACE_MS`（1分）で `none` にする。
- 「CI が無い」は次の両方を満たすこと。
  - 有効なワークフローが無い（`GET /repos/{repo}/actions/workflows` の `state` が `active` のものが0件）。
  - PR の向き先のブランチの先頭のコミットに、チェック・コミットの状態が1つも無い。
- 確かめられないとき（API の失敗、成功の応答でも一覧を読めない、一覧を読み切れない）は、CI が無いとは決めず、今までどおり5分待つ。失敗でタスクを止めない。
- 確かめるのは、チェックが無いまま1分たった確認からで、結果はタスクとコミットごとにメモリーで覚える。読めなかったときは覚えず、次の確認でやり直す。
- マージの後の監視（`pollDeploymentCi`）は変えない。

## 理由

- ワークフローの一覧だけでは、GitHub Actions の外の CI を見逃す。外部の CI を見逃さないよう、ベースブランチのコミットのチェックとコミットの状態も見る。
- 確かめられないときに5分へ戻すのは、短い猶予の誤りは CI の見逃しになり、5分の待ちは今までと同じ費用で済むから。
- 1分たつまで確かめないのは、CI があるリポジトリでは多くの場合それまでにチェックが現れ、API を余分に呼ばずに済むから。短い猶予を0にしないのも、PR に含まれるワークフローなど、確かめた内容に表れない CI のチェックが現れる時間を残すため。
- 結果をコミットごとにするのは、やり直しで PR を更新すると、その間にベースブランチの状態も変わりうるから。台帳には残さない（再起動の後に1回確かめ直すだけで済む）。
- マージの後の監視は、やり直しのたびに繰り返す待ちではないので、この変更の範囲に含めなかった。

## 影響

- CI が無いリポジトリの待ちは、確認の間隔（60秒）の分を含めて1〜2分になる。
- ベースブランチには何も残さず PR にだけ報告する外部の CI で、報告が1分より遅いものは、`none` として最終レビューに進む。
- `dynamic/` で始まるパスの、GitHub が用意するワークフロー（Copilot のレビューなど）も `active` として一覧に出る。これがあるリポジトリは、CI が無くても今までどおり5分待つ。
- 確かめる API には、CI の状態を読むのと同じトークンを使う。
