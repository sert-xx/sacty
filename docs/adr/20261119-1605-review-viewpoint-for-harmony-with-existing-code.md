# 既定のレビューに、既存の実装との調和を見る観点 C-18 を足す

- 日時: 2026-11-19 16:05 UTC
- ステータス: 採用
- 関係する PR・タスク: PBI-405
- 置き換え元: なし
- 置き換え先: なし

## 背景

既存のコードベースに変更を足す PR では、変更そのものの正しさに加えて、既存の実装との調和が要る。
ステークホルダーが挙げた例は、命名の方針が既存と明らかに違う、既存の方針（データの操作は原則 ORM の API とし、生の SQL を使わない、など）と違う、既存が DDD やクリーンアーキテクチャに基づいて業務のロジックの置き場所に意図を持っているのに、それに沿わない、の 3 つ。
どれも、文書やスキルには書かれていないが、リポジトリを読み解けば分かる決まりである。

既定のレビュー用スキルでは、明文の決まりは X-3（リポジトリの指示への準拠）が見て、書かれていない慣習は C-5（保守性・設計）が見ることになっていた。
ただし、C-5 での扱いは次のとおりで、挙げられた例を拾えるとは言いにくかった。

- C-5 は読みやすさ・重複・命名・型・ネストなども見る広い観点で、既存の規約との整合は、15 ほどあるチェックポイントの一部だった。
- C-5 の段階は `entry`（[既定のレビューの観点ごとの段階を下げ、expert も既定で使わない](20261114-1354-lower-review-viewpoint-tiers.md)。照合が中心という理由）。慣習を導くには、差分の外の既存のコードを広く読む必要がある。
- 慣習を導く手順が「既存の似た機能の書き方を知る」の 1 行だけで、何を読み、どの程度そろっていれば慣習とするかが無かった。
- 技術の使い方の方針（データアクセスの方法など）と、業務のロジックの置き場所に当たるチェックポイントと NG 例が無かった。
- 重要度は `should` までだった。

## 決定

- コードの必須の観点に C-18（既存の実装との調和）を足す。見るのは、命名の方針、置き場所と構成、層の分担（業務のロジックの置き場所・依存の向き）、技術の使い方の方針。
- 段階は `standard`。
- 担当は、差分の外から同じ種類の既存のコードを読んで（あれば 3 つ以上）慣習を書き出し、迷うものはリポジトリ全体を検索して数える。今回の変更が足したコードは、慣習の根拠にしない。
- 慣習とするのは、既存がそろっているものだけ。割れているもの・例が 1〜2 件しか無いものは慣習とせず、指摘にしない。
- 慣習からの外れは、次の順で決める。決まった経路から外れたことで、その経路が担う仕組み（認可・入力の検証・トランザクションなど）が効かなくなるものは `must`（外れる理由が書かれていても、承認済みの設計が決めていても出す）。それ以外で、外れる理由が根拠かコードのコメントに書かれているもの・承認済みの要求要件や設計が決めているものは、指摘にしない。どちらでもないものは `should`。
- C-5 からは、既存の規約・構成との整合を外す。C-5 は、リポジトリの慣習に依らない読みやすさ・責務の分け方・重複・言語の一般的な慣習を見る。段階は `entry` のまま。
- 明文の決まりとの照合を X-3 に任せる分担（初回に X-3 を起動したレビューで、依頼文の「見ないもの」に写す）は、C-5 から C-18 に移す。

## 理由

- 独立した観点にしたのは、担当が 1 つの観点だけを新しい文脈で深く見る、というスキルの考え方に合わせるため。C-5 の中に手順を足すだけでは、ほかの多くのチェックポイントと注意を分け合う。
- 必須にしたのは、既存のコードがあるリポジトリへの変更なら、どの変更でも既存との調和が問われるため。既存のコードが少ないリポジトリでは、担当が「慣習が無い」と記録して終える。
- 段階を `standard` にしたのは、差分の外を読んで慣習を導く作業が、型の決まった照合（`entry`）では足りないと判断したため。`advanced` にしなかったのは、レビューの AI の使用量を抑える先の決定があり、必ず動く担当を上位のモデルで増やさないため。
- 慣習と言えないものを指摘にしない歯止めを置いたのは、根拠の無い「既存と違う」という指摘が、好みの押し付けと区別できないため。指摘には、既存の例を 2 つ以上か、数えた件数を書かせる。
- `must` を、既存の仕組みが効かなくなる場合に限ったのは、重要度を影響の大きさと起きやすさで決める決まり（[レビューの指摘の重みを、影響の大きさと起きやすさで決め、自己レビューは要修正だけを修正に戻す](20261117-0244-review-finding-weight-by-impact-and-likelihood.md)）に合わせるため。書き方が既存と違うだけでは、実害は小さい。
- 比べた案：
    - C-5 のチェックポイントと手順を足すだけにする：担当は増えないが、上の理由で採らなかった。
    - C-5 の段階を上げる：C-5 の全部（読みやすさなど）を上の段階で見ることになり、使用量の増え方に対して、慣習の読み解きに効く分が小さい。
- `standard` で慣習を十分に導けるか、指摘がどれだけ増えるかは、測っていない。

## 影響

- コードの初回のレビューで必ず動く担当が 1 つ増える（`standard` の C-18）。`advanced` 4・`standard` 4・`entry` 3 になる。
- C-5 は、リポジトリの慣習との不一致を指摘しなくなる。
- 再レビューと、軽い依頼の自己レビューの起動の規則は変えない（C-18 は、`self-review` の再レビューでは前回の回で `must` を出したときだけ再び起動し、`pr-review` の再レビューでは、ほかの必須観点と同じく毎回起動する。軽い依頼の自己レビューの初回には起動しない）。
- プロジェクトのコンテキストリポジトリで `review-dispatch`・`review-execution` を差し替えているプロジェクトには、効かない。`review-execution` だけを古い版で差し替えていると C-18 の資料が無く、担当は依頼文の「見るもの」「見ないもの」だけで見る。
