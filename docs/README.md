# sacty のドキュメント

sacty のドキュメントは、目的ごとに4種類に分けて、このディレクトリに置く。種類ごとにメンテナンスの方針が違う。
**実装を変えたときに直すのは、基本的に仕様書（と、利用者に見える変更ならユーザードキュメント）だけ**。
ADR と作業履歴は、書いたときの記録として残し、後から実装に合わせて書き換えない。

| ディレクトリ | 種類 | 目的 | 実装との一致 |
| --- | --- | --- | --- |
| [spec/](spec/README.md) | 仕様書 | 今の sacty がどう動くかを、正確に、人が理解しやすく表す | 常に一致させる（ズレを許容しない） |
| [user/](user/README.md) | ユーザードキュメント | sacty を使う人が、設定やコマンドの使い方を理解する | 利用者に見える部分は常に一致させる |
| [adr/](adr/README.md) | ADR（Architecture Decision Record） | いつ・どのような理由で今の仕様に決まったかを残す | 一致させない（決めたときの記録） |
| [worklog/](worklog/README.md) | 作業履歴 | タスクごとに、何をして何を確かめたかの詳細を残す | 一致させない（作業したときの記録） |

ファイル名の規則・本文のひな形・書き方の細かい規則は、各ディレクトリの README.md に書く。ただし、ユーザードキュメントの
README.md は利用者向けの入口（概要と目次）なので、ユーザードキュメントの規則はこのファイルの
[ユーザードキュメントの書き方](#ユーザードキュメントの書き方) に書く。

## 種類ごとの方針

### 仕様書（spec/）

- 書く内容：今の実装の振る舞い・構成・データ・設定の意味と既定値・エラーのときの扱い。主な項目に、対応するコードの場所を付ける。
- 書かない内容：経緯や却下した案（ADR に書く）、作業の記録（作業履歴に書く）、利用者向けの手順（ユーザードキュメントに書く）、
  予定や願望（まだ実装していないこと）、推測（コードで確かめられないことは書かないか、未確認と明記する）。
- メンテナンス：実装を変える PR を出す人（エージェントを含む）が、**同じ PR で**関係する仕様書を直す。レビューする人は、
  実装と仕様書のズレを指摘する。

### ユーザードキュメント（user/）

- 書く内容：インストール・セットアップ、設定ファイルの項目と既定値、コマンドとオプション、画面の操作、トラブルシューティング。
  利用者が目的から引けるように分ける。
- 書かない内容：内部の仕組みの詳細（仕様書に書く）、経緯（ADR に書く）、開発者向けの作業の記録。
- メンテナンス：利用者に見える変更（設定・コマンド・オプション・画面・既定値・エラーの文言など）をする PR を出す人が、同じ PR で直す。
- リポジトリの [README](../README.md) には、sacty の概要・すぐ始める最小の手順・ユーザードキュメントへのリンクだけを書く。
  設定やコマンドの説明を README に重ねて書かない。
- 細かい規則は、次の [ユーザードキュメントの書き方](#ユーザードキュメントの書き方) にある。

#### ユーザードキュメントの書き方

docs/user は利用者がそのまま読むページなので、書き方・分け方・ひな形などの開発者向けの規則は docs/user に置かず、ここに書く。
`docs/user/README.md` には、利用者向けの概要と目次だけを書く。

ファイルの分け方：

- 利用者の目的の単位で1ファイルにする（例 `getting-started.md`（はじめに）・`project-settings.md`・`context.md`・
  `gateway.md`・`notifications.md`・`cli.md`・`troubleshooting.md`）。
- ファイル名は英小文字・数字・`-` だけ。日時は付けない。
- [ユーザードキュメントの目次](user/README.md#目次) に、すべてのユーザードキュメントへのリンクを、読む順に並べる。
- リポジトリの [README](../README.md) からは、この目次（または各ファイル）へリンクする。README に中身を重ねて書かない。

書き方の規則：

- 本文は、です・ます調で書く（見出し・表の短い項目・コードブロックの中のコメントは、体言止めや常体のままでよい）。
- 利用者がすること（手順）と、その結果を書く。内部の仕組みは書かず、必要なら仕様書へリンクする。
- 設定の項目・既定値・コマンドのオプションは、コードと照合してから書く。名前はコードのまま（`default_agent` など）。
- 例の値は架空のもの（`example.com`・`acme`）にし、秘密の値は書かない。
- 対応するコードの場所は、利用者には見せず、ファイルの先頭の HTML コメントに書く（直すときに照合する場所がわかるように）。

  ```markdown
  <!-- 対応するコード: packages/cli/src/index.ts、apps/daemon/src/<ファイル>.ts -->
  ```

- 利用者に見える変更（設定・コマンド・オプション・画面・既定値・エラーの文言）をする PR では、同じ PR で直す。
- 目次にあること・先頭の HTML コメントがあることは、`tests/docs/docs.test.ts` で確かめる。

ひな形：

```markdown
<!-- 対応するコード: <パス>、<パス> -->

# <目的（例 プロジェクトを設定する）>

<このページでできること。前提（先に読むページ）。です・ます調で。>

## <手順や項目>

<手順。コマンドや設定の例。>

| 項目 | 意味 | 既定値 |
| --- | --- | --- |
| `<名前>` | <意味> | `<既定値>` |

## 関係するページ

- [<ページ>](<ファイル>)
```

### ADR（adr/）

- 書く内容：方針や仕様の決定ごとに1件。背景・決定・理由・影響・置き換えの関係。
- 書かない内容：決定に関係しない作業の細部（作業履歴に書く）、今の仕様の全体像（仕様書に書く）。
- メンテナンス：方針を決めた・変えた PR を出す人が、その PR で新しい ADR を足す。**古い ADR の本文は書き換えない**。ほかの ADR で方針が
  変わったら、古い ADR のファイル名にステータスを付け（名前を変える）、置き換えの関係を書き足す。直してよいのは、
  ステータス・置き換えの関係・名前の変更で切れたリンクだけ。
- 却下・置き換え・廃止した ADR の内容が今の実装と矛盾していても、直さない。

### 作業履歴（worklog/）

- 書く内容：タスク（PBI・PR）ごとに1件。何をしたか・何を確かめたか（コマンドと結果）・レビューの指摘と対応・残したこと。
- 書かない内容：秘密の値・個人の情報、git 管理していない一時ファイル（docs/pbi）の内容の丸写し。
- メンテナンス：タスクを行う人が、そのタスクの PR で足す。同じ PR の中のレビューの対応は、その作業履歴に書き足す。PR がマージされた後は、
  実装と矛盾しても直さない。

## 置かないもの

- `docs/pbi/`：PBI の一時ファイル。git 管理しない（`.gitignore` 済み）。上の4種類のどれにも混ぜない。
  ドキュメントから docs/pbi へリンクしない。
- `docs/sacty/`：sacty がタスクの工程で対象のリポジトリに書く成果物（要求要件・設計など）。このリポジトリを対象にした
  タスクで作られることがあるが、上の4種類ではない。

## 共通の規則

- 公開リポジトリなので、特定の組織や勤め先の内部を指す語・その組織の名前や、秘密の値（トークン・パスワード・鍵）・
  個人の情報を書かない。例の値は `example.com`・`acme` のような架空のものにする。
- ドキュメントの中のリンクは相対パスで書く。ファイルの名前を変えたら、そのファイルへのリンクを直す
  （`npx vitest run tests/docs` で、リンク切れとファイル名の規則を確かめられる）。
- これらの方針に従って書く・直すためのスキルを、Claude Code 用（`.claude/skills/sacty-docs/`）と Codex 用
  （`.agents/skills/sacty-docs/`）に置いている。2つの中身は同じで、テストで一致を確かめる。
- この構成と方針を決めた経緯は [ADR](adr/20261014-0816-superseded-docs-structure-and-policy.md) にある。ユーザードキュメントの文体と
  規則の置き場所は、[別の ADR](adr/20261015-0017-user-docs-polite-style-and-rules-location.md) で一部を置き換えた。
