# 承認と差し戻し

承認ゲートのある工程は、人間が承認すると次の工程へ進む。
人間は、sacty の画面か、対象のリポジトリへの PR のマージで承認する（承認＝マージ）。
差し戻すと、選んだ工程からやり直す。
同じ工程への差し戻しが上限を超えると、エスカレーション（人間の判断待ち）になる。
上限に数えるのは人が差し戻した回数で、sacty 自身の AI のレビューの指摘だけの差し戻しは数えない（[AI のレビューの指摘](#ai-のレビューの指摘)）。

関係する ADR: [「PR作成」の工程をなくし、実装の工程の中で PR を作って承認を待つ](../adr/20261015-1430-superseded-implement-step-opens-pull-request.md)、[取り込みを「Issue の取り込み」と「PR のレビューの取り込み」に分け、sacty の PR にはレビュー用のラベルを付ける](../adr/20261015-0240-superseded-split-issue-and-pr-review-intake.md)、[sacty が作る PR に取り込むラベルを付け、別のタスクのレビューを元のタスクの PR の指摘として取り込む](../adr/20261014-1445-superseded-label-sacty-pull-requests-for-review.md)、[sacty が作る PR の本文を、リポジトリ・Org の PR テンプレートの見出しに沿って決まった規則で埋める](../adr/20261014-1517-pr-body-follows-repository-template.md)、[実装に変更が無ければ PR を作らず、人間が確かめて変更なしで完了にする](../adr/20261014-2216-superseded-complete-without-changes.md)、[PR を参照する sacty のタスクの投稿は、取り込みの経路に関わらず、指摘のある回を元のタスクの PR の指摘として取り込む](../adr/20261025-2245-import-sacty-reviews-from-any-intake.md)、[実装の PR を最終レビューの前にドラフトで作り、CI を待ってからゴールガーディアンが判定し、合格したらドラフトを外してレビューへ進める](../adr/20261027-2330-superseded-draft-pull-request-before-final-review.md)、[最終レビューを、実装の PR の CI と並べて進める](../adr/20261108-0232-superseded-final-review-alongside-pull-request-ci.md)、[sacty 自身の AI のレビューの指摘を、人の指摘と区別して扱う](../adr/20261102-0843-distinguish-ai-review-remarks.md)、[sacty が作る PR のレビューを、PR を作ったタスクの子タスクにし、指摘なしになるまで繰り返す](../adr/20261112-0609-review-sacty-pull-requests-in-child-tasks.md)、[PR の指摘の戻し先を、ゴールガーディアンではなく、AI のレビューの指摘はレビューの子タスクが、人の指摘は PR の工程のエージェントが決める](../adr/20261112-0748-review-child-task-decides-rework-target.md)

## 画面での承認

- 承認できるのは、次のすべてを満たすとき。
  - 状態が `awaiting_approval` か `escalated`
  - 工程が承認待ちの工程（`gate.step`）と同じ
  - 画面が見ていた提出の回（`submission`）がいまの回と同じ（違えば `gate.staleSubmission`）
- 文書原稿と作業の成功結果は画面で承認する。
  - 作業には実行前の承認ゲートはなく、依頼に従って実行した後に結果の承認を待つ。
  - 実行開始後は差し戻せない。
  - 失敗や結果不明は承認して完了にせず、外部状態の確認が必要になる。
- 再現（`reproduce`）の承認待ち（再現できなかった）は承認できない。
- PR を作った工程（実装、PR のある要求要件・設計）は、画面からは承認できない（`gate.approveOnPullRequest`）。
  実装に変更が無く PR を作らなかった実装は、画面で承認する（下の「実装に変更が無いとき」）。
- 承認した成果は固定される（承認した工程の出力は、後から変わらない）。
  承認の後、次の工程が実行できる工程なら実行待ちに、そうでなければ `idle` にする。

コード: `apps/daemon/src/service.ts`（`approve`・`gateTask`・`nextAfterApproval`）、`packages/core/src/projection.ts`（`applyEvent` の `StepApproved`）

## PR での承認

要求要件・設計（`StepPullRequestKey`）と実装は、PR で承認する。
実装の PR は、実装の工程が終わったらドラフトで作り、PR のレビューの子タスクが指摘なしにしたらドラフトを外す（[タスクと工程](tasks-and-steps.md#最終レビューをしない流れ)）。
PR の作り方は[タスクと工程](tasks-and-steps.md#実装の-pr-の作成)、以前の版の最終レビューの記録を持つタスクの扱いは[タスクと工程](tasks-and-steps.md#最終レビューがあった版のタスク)にある。
承認・差し戻し・PR のマージでの承認・PR の指摘の取り込みの扱いは、3つの工程で同じ。

要求要件・設計・実装をすべて PR で承認するときのブランチは、次のようになる（タスク ID が 1a2b3c4d で始まる例）。

![PR で承認するときのブランチ](images/approval-branches.svg)

- PR で承認するタスクか（`stepPullRequestsOn`）
  - タスクブランチがあれば、常に PR で承認する。
  - 既存の PR を引き継ぐタスク（`Task.continuedPullRequest`）は、要求要件・設計を PR にしない（[既存の PR の引き継ぎ](tasks-and-steps.md#既存の-pr-の引き継ぎ)）。
  - タスクブランチが無ければ、次のすべてを満たすときに PR で承認する。
    - 対象リポジトリがある
    - 画面で要求要件・設計をまだ提出していない
    - プロジェクトにそのホストの GitHub のアカウントがある
- タスクブランチ `sacty/task-<タスク ID の先頭8文字>` を、ベースブランチの起点のコミットから作る（`TaskBranchCreated`）。
- 要求要件・設計の PR
  - sacty は成果をファイル `<documentsDir>/<タスク ID の先頭8文字>/<工程>.md` にし、工程のブランチ `<タスクブランチ>-<工程>-<回>` からタスクブランチへの PR にする。
  - `documentsDir` はオーケストレーターが決める。
    使えない形なら、既定の `docs/sacty`（`DEFAULT_DOCUMENTS_DIR`）を使う。
  - ファイルの先頭に sacty が作った旨の HTML のコメントを入れ、設計にはテスト観点を含める。
- 要求要件・設計の PR を作り直すか
  - その工程の PR が開いていて、タスクブランチの先頭が変わっていなければ、同じ PR を更新する（その工程のやり直し）。
  - 次のときは、タスクブランチの最新から新しいブランチと PR を作り、開いていた前の PR を閉じる。
    - PR がマージ済み・閉じられた
    - 前の工程の直しがマージされて、タスクブランチが進んだ
  - PR を作れなければ、理由を記録して止める。
- 実装の PR
  - タスクブランチがあれば、実装をタスクブランチの最新に積み、タスクブランチからベースブランチへの PR（実装の PR）にする。
  - タスクブランチが無ければ、sacty のブランチ（`sacty/task-<タスク ID の先頭8文字>`）からベースブランチへの PR にする。
  - タスクブランチに、要求要件・設計のファイル以外の変更が積まれていれば、公開を止める（`pr.taskBranchChanged`）。
  - 既存の PR を引き継ぐタスクは、PR を作らず、引き継いだ PR の元のブランチに積み、その PR を実装の PR にする。
- タスク分割の子タスクは、それぞれ自分のタスクブランチを持つ。
- 画面の「チェックする」の導線（`personAction`）
  - 導線は、タスクの詳細・タスクの一覧・ダッシュボードの「あなたの出番」・ヘッダーのお知らせにある。
  - 次のすべてを満たすとき、導線は PR を新しいタブで開く（`reviewPullRequestUrl`）。
    文言は「PR でチェックする」で、sacty の承認の画面を挟まない（PBI-136）。
    - 状態が `awaiting_approval`
    - 今の提出の PR（`gatePullRequest`）が `open`
    - PR の URL が `https://` で始まる
  - エスカレーションで、人の判断待ちの変更の申し出（`change_proposed`。以前の版の `change_undecidable` も。人がまだ決めていないもの。`openProposal`）があるときは、タスクの詳細の「変更の申し出」（`/tasks/<ID>#proposals`）へ案内する。
  - 次のときは、sacty の承認の画面（`/tasks/<ID>/review`）へ案内する。
    - それ以外のエスカレーション（PR の指摘の戻し先の確認など）
    - 状態が `awaiting_approval` で、今の提出の PR が開いていない（閉じられた、またはマージの後で次の確認がまだ承認を記録していない）・無い
  - 外部へ開くリンクは、見た目の「↗」と読み上げの「新しいタブで開く」で示す（`ActionLink`）。
  - お知らせからは、プロジェクトを切り替えずに開く。
  - ダッシュボード・お知らせでは、導線はタスクの題のリンクなので、題だけを省略し、印は省略の外に置く。
    長い題でも印が残る（PR #148 レビュー提案）。

コード: `apps/daemon/src/service.ts`（`stepPullRequestsOn`・`taskBranchName`・`publishStepPullRequest`・`publish`）、`packages/core/src/events.ts`（`StepPullRequestKey`・`DEFAULT_DOCUMENTS_DIR`・`isDocumentsDir`）、`packages/core/src/projection.ts`（`stepDocumentPath`）、`apps/daemon/src/prompts.ts`（`buildStepDocument`）

## 実装に変更が無いとき

実装の PR を作るとき、実装の作業領域が起点のコミットから何も変わっていなければ（`NothingToCommitError`）、PR を作らない。

- まだ実装の PR を作っていなければ、`NoChangesFound`（この後に提出する実装の回）を記録し、実装を提出する（`StepSubmitted`）。
  PR が無いので、画面で承認できる。
  すべてのタスクで同じ（テンプレートのタスクに限らない）。
- 提出の前に、テストの実行と最終レビューはしない（sacty はテストを実行しない。[最終レビューをしない流れ](tasks-and-steps.md#最終レビューをしない流れ)）。PR が無いので、PR のレビューの子タスクも作らない。
  画面は、承認待ちを「変更なしの実装の承認待ち」とする。
  承認の画面には、実装は何も変えていないことと、実装の説明で変更が要らない理由を確かめることを出す。
- 承認すると、PR を作らずに完了する（「完了（変更なし）」）。
  差し戻すと、ふつうと同じく実装からやり直し、変更があれば PR を作る。
  変更なしの扱いは、その提出回だけ（`deliveredWithoutChanges`：`noChanges.submission` が実装のいまの回で、PR が無い）。
- タスクブランチ（要求要件・設計の PR をマージしたもの）があっても同じ。
  ベースブランチへの PR は作らず、タスクブランチは残る。
- すでに実装の PR を作ったタスクで、作り直した実装に変更が無くなったときは、今までどおり理由（`pr.failed`・`git.nothingToCommit`）を記録して止める。
  開いている PR をどうするかは人が決める。
- 実装の工程の指示には、変更が要らないとわかったらファイルを変えずに、理由と根拠を説明に書くよう入れている。

コード: `apps/daemon/src/service.ts`（`publish`）、`packages/core/src/events.ts`（`NoChangesFound`）、`packages/core/src/projection.ts`（`noChanges`・`deliveredWithoutChanges`）、`apps/daemon/src/prompts.ts`（`NO_CHANGE_LINE`）、`apps/web/src/lib/labels.ts`（`statusText`）

## PR のレビューの子タスク

sacty は、作る PR（要求要件・設計の PR と実装の PR）ごとに、その PR をレビューする子タスクを作る。
PR を作った工程とは別のコンテキスト（別のタスク・別の実行）でレビューさせ、その指摘を [PR の指摘の取り込み](#pr-の指摘の取り込み) で親（PR を作ったタスク）に届けて直させ、指摘なしになるまで繰り返すためである。
PR にラベルは付けない（レビュー用のラベル `reviewLabel` は、sacty が作っていない PR の取り込みだけに使う。[チケットの取り込みと GitHub](intake.md)）。

- 作る時点：要求要件・設計の PR は作った直後。
  実装の PR は、ドラフトで作った直後（指摘なしでドラフトを外す。[実装の検証](tasks-and-steps.md#最終レビューをしない流れ)）。
  依存先の PR に重ねた実装の PR は、依存先がマージされて向き先を付け替えた後に作る（重ねている間は作らない）。
  既存の PR を引き継ぐタスクでは、引き継いだ PR に作る。
- 子タスクは、PR のレビューだけのタスク（`source.review: sacty`。[タスクと工程](tasks-and-steps.md#pr-のレビューだけのタスク)）で、`TaskCreated` の `reviewOf` に親の ID と PR を作った工程を持つ。
  題は `[PR #<番号>] <親の題>`（言語に依存しない形。200 文字まで。長い親の題は、文字の途中で切らずに `…` で切り詰める）、プロジェクトは親と同じ、予算の上限は `budget.default_per_task_usd`（子タスクの費用は子タスクの予算に数える）。
  分割の子タスク（`parent`）とは別で、分割の待ち・統合レビューの対象にしない。
- 親には `ReviewTaskCreated`（子タスクの ID・工程・PR）を記録する（`Task.reviewTasks`）。
  1つの PR（リポジトリと番号）につき1つ。記録のある PR は、更新しても作らない。PR を作り直した（新しい番号）ときは、新しい PR に作る。
  ただし、最後の子タスクが PR のクローズで中止されていれば（`reason: pull_request_closed`）、PR を開き直したときの PR の確認で、新しい子タスクを作って記録を足す（中止したタスクは再レビューできないため。`needsReviewTask`）。
  人が中止した子タスクは作り直さない。
- タスクの詳細の「関連するタスク」に、親から子タスク（工程・PR の番号・子タスクの状態）と、子タスクから親へのリンクを出す（同じ PR に子タスクが複数あっても、状態で区別できる）。
- 作らないとき
  - 親が中止された・中止を求められている。
  - その PR のレビューのタスク（以前の版でレビュー用のラベルから取り込んだものなど）が、終わらずにある（二重にレビューしない）。
  - デーモンの依存で無効にしている（`reviewTasks`。テストで工程の流れだけを確かめるため。デーモンの起動では有効）。
- 作れなくても、PR の作成・承認待ちは失敗にしない（デーモンのログに残し、次の PR の確認で作り直す）。
- PR の確認（60秒ごと）で、承認待ち（`awaiting_approval`）の今の提出の PR（`gatePullRequest`）が開いていれば、次を行う（`reconcileReviewTasks`）。
  一時停止・中止を求められた親は除く。
  - 子タスクの記録が無ければ作る（公開を記録した後、作る前に止まった（停止・クラッシュ）とき）。
    子タスクだけ作って親に記録する前に止まっていたら、作り直さずに記録だけ足す。
  - 子タスクがレビューを投稿して終わっていて（「再レビュー」できる状態）、レビューした先頭のコミット（`reviewTarget.headCommit`）が、親が PR に積んだ今のコミットと違えば、再レビューを始める（`ReviewRestarted`、`reason: updated`、`commit` に親のコミット。actor `sacty`）。
    親が指摘を直して PR を更新し、承認待ちに戻ったときにあたる。直している間（承認待ちでない）は始めない。
    同じコミットでは1回だけ始める（`Task.reviewRestartCommit`。ほかで push されてレビューした先頭が親のコミットと違っても、繰り返さない）。
    一時停止した・一時停止や中止を求められた子タスクは動かさない。
- 子タスクの判定が指摘なし（`no_findings`）なら、親には届かず再レビューも起きないので、PR は人の承認（マージ）を待つ。
  実装の PR（`awaitingReview`）は、PR の今のコミットを指摘なしにしたら、PR の確認で sacty がドラフトを外す（`PullRequestMarkedReady`。[最終レビューをしない流れ](tasks-and-steps.md#最終レビューをしない流れ)）。
- 子タスクには、レビューする先頭のコミットの CI の状態（ワークフローの実行・チェック・コミットの状態と、ワークフローの中のジョブ（GitHub Actions のチェック。ワークフローが成功でも、実行されなかったジョブを伝えるため）。チェックの名前・状態・結論・URL。失敗・実行中のものはすべて、成功したもの（`success`・`neutral`。実行されなかった `skipped` は省かない）は合わせて `REVIEW_CI_MAX` 件まで並べ、残りは件数だけ）を sacty が読んで渡す（`reviewCiOf`・`reviewCiLines`）。sacty は CI を待たないので、子タスクに、変更による失敗を要修正の指摘に、変更と関係が無いと確かめた失敗を本文の人が確かめることにさせ、終わっていないものは待たずに実行中と書かせる。
  CI の読み取りは `REVIEW_CI_TIMEOUT_MS`（30秒）まで待ち、答えが返らなければ、読めなかったものとしてレビューを続ける。
  読めなければ、読めなかったことを渡す（レビューは止めない）。
  GitHub の答えに一覧の配列が無ければ（中継の応答など）、CI がまだ無いとは扱わず、読めなかったものとする。
- セキュリティ対応の実装の PR なら、子タスクに、前段の調査が宣言した修正の範囲（変えてよいファイル・上げる依存）・変えた行の数の上限と、sacty が差分を範囲と照らした結果（`FinalReviewSkipped` の `securityScope`）を渡す（`reviewSecurityLines`）。
  差分が範囲の中の最小限の変更か（観点 `SEC-MIN`）を子タスクに確かめさせ、範囲の外の変更・要らない変更を要修正の指摘にさせる。sacty が違反を見つけていれば、それも要修正の指摘にさせる。
  繰り返しの回数に上限は無く、親と子タスクそれぞれの予算の上限で止まる。
- 子タスクが終わる前に PR がマージ・クローズされたら、子タスクを中止する（PR のレビューだけのタスクと同じ。`checkReviewPullRequests`）。
- 親が中止されたら、PR の確認で、終わっていない子タスクも中止する（`TaskCancelled` の `reason: parent_cancelled`。中止の片付けで PR を閉じなかったときも、レビューを続けない）。
  PR の確認は、子タスクの中止（片付けと記録）を待ってから終わる。
- 以前の版の記録（PR の公開の記録の `label`・`intakeLabel`、`PullRequestLabeled`・`PullRequestLabelFailed`）は読み込めるが、ラベルを付ける予定としては扱わない（台帳は書き換えない）。

コード: `apps/daemon/src/service.ts`（`ensureReviewTask`・`needsReviewTask`・`reconcileReviewTasks`・`reviewTaskTitle`・`retargetPullRequest`・`publishStepPullRequest`・`publish`・`markReady`・`reviewCiOf`）、`apps/daemon/src/prompts.ts`（`reviewCiLines`・`REVIEW_CI_MAX`・`reviewSecurityLines`）、`apps/daemon/src/service.ts`（`REVIEW_CI_TIMEOUT_MS`）、`packages/core/src/events.ts`（`ReviewTaskCreated`・`TaskCreated`・`ReviewRestarted`）、`packages/core/src/projection.ts`（`reviewTasks`・`reviewOf`・`reviewRestartCommit`）、`apps/web/src/components/task-detail.tsx`（`Properties`）

## PR の確認

デーモンは60秒ごとに、今の提出の PR（`gatePullRequest`）があり、状態が承認待ち（`awaiting_approval`）かエスカレーション（`escalated`）のタスクの PR を確かめる（前の確認が終わるまで次を始めない）。

- マージされた：`PullRequestMerged` と `StepApproved`（どちらも actor `person`）を記録する。
  - sacty の提出と違う内容でマージされた（PR の先頭が sacty のコミットと違う）ときも承認にする（`edited`）。
  - 要求要件・設計は、マージしたコミットからファイルを読み、人が直した版を承認した成果にする。
    ファイルが消された・読めないときは sacty の版を承認する。
    取得できなければ記録せず、次の確認でやり直す。
- マージされずに閉じられた：`PullRequestClosed` を記録し、承認にせず人間の判断を待つ。
  画面から承認はできない（差し戻すか中止する）。
- 開き直された：`PullRequestReopened` を記録して見守りを続ける。
- 変わっていない：PR が開いたままで状態が `awaiting_approval` なら、次を順に行う。
  1. 実装の PR なら、ベースブランチとの競合の変化を記録する（[ベースブランチとの競合の表示](#ベースブランチとの競合の表示)）。
  2. レビュー・コメントを指摘として取り込む（[PR の指摘の取り込み](#pr-の指摘の取り込み)）。
- 確認の途中で状態・PR・コミットが変わったときは記録しない。
- 指摘の取り込みの間（戻し先の判断の最中など）にマージされた・マージされずに閉じられたときは、差し戻さない。同じ確認の中で状態を読み直し、上のマージ・閉じられた場合として記録する（[PR の指摘の取り込み](#pr-の指摘の取り込み)）。
- 実装の PR のマージでは、マージの後の監視の工程を飛ばしていなければ、同じ追記でマージの後の監視を始める（[マージの後の監視](deployment-watch.md)）。
- 確認の初めに、承認待ちではなく、実装を作り直している間のタスクの実装の PR も確かめる（[実装の作り直しの間のマージ](#実装の作り直しの間のマージ)）。
- 確認の終わりに、次を順に行う。
  1. コンテキストにする改修の PR がマージされたメモリーを消す（`cleanupPromotedMemories`。[メモリー](memory.md#コンテキストへの昇格)）。
  2. PR のレビューの取り込みのタスクのうち終わっていないものの PR を確かめ、マージされた・マージせずに閉じられたら中止する（`checkReviewPullRequests`）。
  3. 承認待ちの PR のレビューの子タスクを整える（作る前に止まったものを作り、親が PR を更新していたら再レビューを始める。`reconcileReviewTasks`。[PR のレビューの子タスク](#pr-のレビューの子タスク)）。
  4. マージの後の監視を待っているタスクの CI/CD を確かめる（`checkDeployments`）。

### 実装の作り直しの間のマージ

差し戻し・PR の指摘の取り込みで実装を作り直している間（承認待ちではない）に、人が実装の PR をマージしたら、マージを承認として扱い、作り直しを止める。新しい PR は作らない。

- 対象（`reworkingPullRequest`）：実行対象の工程が実装で、状態が実行待ち（`queued`）・実行中（`running`）・待機（`idle`。PR の作成の待ちなど）・一時停止（`paused`）のタスクのうち、`Task.pullRequest` の PR が開いている（`pullRequestState` が `open`）か、承認待ちで閉じられたまま差し戻したもの（`closed`。GitHub で開き直してマージされることがある。マージかどうかは GitHub の状態で決める）。
  - 引き継いだ既存の PR（`Task.continuedPullRequest`）は、初めて提出するまで `Task.pullRequest` が無い。その間も、引き継いだ PR を見守る。投影は、このとき引き継いだ PR を実装の PR として記録してから、マージを記録する（コミットは、引き継いだ時点の PR の先頭）。
  - 要求要件・設計をやり直している間（実行対象の工程が実装でない）は見守らない。実装に進んだ時点で、PR がマージ済みなら同じく止める。
  - 承認待ち・エスカレーション中のタスクは、上の確認が見守る。
- 確認：PR の状態を読み（プロジェクトの gh のアカウント。読めなければ次の確認でやり直す）、マージされていたら次を行う。開いたまま・閉じられたときは何もしない。
  1. 実行中の処理があれば、コンテナを止めて終わりを待つ（一時停止・中止と同じ。止めた実行は、人の一時停止としては記録しない）。止めたコンテナが無くなったと確かめられなければ、一時停止にして進めない（次の確認で確かめ直す）。
     承認か一時停止を記録するまで、このタスクの実行を始めさせない（止めた実行が正常に終わっていても、続きの検証をワーカーが始めない。`runNext` と `queuedTaskIds` が `mergeStopping` を見る）。
     デーモンが実装の実行中に止まって再起動したときは、復旧（`recoverInterrupted`）が、実装の作り直し（開いた PR がある）の実行を `unstoppedRuns` に残して一時停止にするので、停止を確かめるまで承認へ進まない。
     一時停止のときに止めたコンテナを確かめられなかった実行（`unstoppedRuns`）は、止めた実行に含めて残す。
     止めた実行が正常に終わった費用で先に一時停止していた（予算など）ときも、確かめられなかった実行を `unstoppedRuns` に足す（一時停止の理由はそのまま。すでに一時停止しているタスクへの `TaskPaused` は、`unstoppedRuns` を足すときだけ受け付ける）。確かめるまで承認へ進まない。
  2. 止めている間に、承認待ちになった・中止された・別の状態になったなら、ここでは記録しない（承認待ちになったなら、上の確認が扱う）。
  3. `ReworkStoppedByMerge`（actor `sacty`）に続けて、`PullRequestMerged`・`StepApproved`（actor `person`。マージの後の監視の開始も、上の「マージされた」と同じ）を同じ追記で記録する。
- `ReworkStoppedByMerge` の内容：マージされた PR の番号、止めたときの段階（`was`：`queued`・`running`・`verifying`・`publishing`・`paused`）、止めた実行（`stoppedRuns`）、作り直しに渡す前に捨てた指摘（`discardedRemarks`：id と本文。最後の差し戻しの指摘のうち、提出済みの PR に渡していないもの）、捨てた検証の結果の種類（`discardedFeedback`：`tests`・`review`・`merge`）、一時停止の間に届いて反映していなかった PR の指摘の件数（`discardedReview`。[一時停止の間に届いた指摘](#一時停止の間に届いた指摘)）。理由はマージ。
  - projection は、実装の承認待ち（ゲートの提出回は、これまでの提出の回数。提出が無ければ 1）に戻し、捨てた指摘を無効にし、検証・PR の作成の待ち・一時停止の状態を消す。続く `PullRequestMerged`・`StepApproved` が承認として進める。
  - 承認した成果の本文（`approved.implement.output`）は、記録している最新の実装の報告。マージされた内容は PR のコミットが正。
- PR の更新の直前（`publish`。引き継いだ既存の PR の更新も含む）にも、前の PR がマージされていないかを確かめる。マージされていれば、プッシュも PR の作成もせず、同じ記録で承認として進める（確認の前に PR の更新が始まる場合）。
  プッシュの後の確認（新しい PR を作るかの確認、引き継いだ PR の確認）でマージされていたときも、新しい PR は作らず、一時停止にもせず、同じ記録で承認として進める（プッシュの間にマージされた場合）。
- 続きの確認では、承認済みのタスクなので、重ねて記録しない。

コード: `apps/daemon/src/service.ts`（`checkReworkMerges`・`stopReworkForMerge`・`endReworkByMerge`・`mergeApprovalItems`・`publish`・`pauseIfRequested`）、`packages/core/src/projection.ts`（`reworkingPullRequest`・`unreflectedImplementRemarks`・`ReworkStoppedByMerge`）

### 一時停止の間に届いた指摘

関係する ADR: [一時停止の間に届いた PR の指摘を、再開のときに取り込む](../adr/20261102-1900-hold-pr-comments-while-paused.md)

実装の作り直しを一時停止している間（予算の上限・AI の利用上限・認証エラー・エラー・人が止めた、のどれでも）に、実装の PR に人が指摘を書いたときは、その指摘を未反映として残し、再開したあと、止まった工程を走り直す前に反映する。
承認待ちではないので、上の「PR の指摘の取り込み」は動かない。反映の判断は同じ（戻し先の判断は、下の「PR の指摘の取り込み」の担い手が決める）。

- 対象：[実装の作り直しの間のマージ](#実装の作り直しの間のマージ)と同じ PR（`reworkingPullRequest`）。つまり、実行対象の工程が実装で、実装の PR（引き継いだ既存の PR を含む）が開いている（または承認待ちで閉じられたまま差し戻した）タスク。
  - 要求要件・設計をやり直している間に一時停止したタスクは、対象にしない。そのときに届く指摘は、実装に進んで承認待ちになったあとに、通常どおり取り込む。
- 残す（`checkHeldFeedback`・`holdFeedback`）：PR の確認（1分ごと）が、一時停止中（`paused`）のタスクの実装の PR のフィードバックを読み、取り込んでいないものを `PullRequestReviewImported`（`held: true`）で記録する。
  - 取り込み済みの印（`importedFeedback`）を付け、`Task.pendingReview`（承認待ちの取り込みと同じ「取り込んだが、まだ差し戻しに反映していない指摘」）に足す。足していくので、何回かに分けて届いた指摘は1つにまとまる。件数の上限（未反映の指摘の合計で50件、1件 2000 文字）は承認待ちの取り込みと同じ。50件に達している間は、確認が読んでも足せない（追加できる件数が 0）。超えた分は取り込み済みにせず、反映した後の取り込み（承認待ちになったときの通常の取り込み。また一時停止したら、その確認）が足す。
  - 書き終わるのを待たない（反映は再開のときなので、そのあいだに届いたものは足せる）。
  - 差し戻さず、戻し先の判断もせず、費用もかからない。タスクは一時停止のまま。
  - sacty 自身の AI のレビューの指摘は、人の指摘と区別する（[AI のレビューの指摘](#ai-のレビューの指摘)と同じ）。`PullRequestReviewImported` の `items[].source` と `pendingReview.aiReview` を残し、AI のレビューの指摘だけの回は actor `sacty`。古い head へのレビューは、残さずに `PullRequestReviewDiscarded` で捨てる。
  - PR のフィードバックを読めなければ、何も記録せず、次の確認でやり直す。
  - 戻し先の判断が済んだ指摘がある間は、足さない。再開した後（実行待ち・待機）は、一時停止中の確認は足さない（読んでいる間に再開されたときも足さない。再開した後の判断と食い違わないよう、足すのは反映の側だけ）。
  - 同時に走った別の確認（一時停止中の確認と再開の後の確認）が、同じ古い head への AI のレビューを捨てようとしたときは、取り込み済みになったものを除いて記録する（重ねて記録しない）。
- 画面：一時停止中のタスクの詳細に、届いた指摘の件数（AI のレビューの内訳つき）と、再開したときの扱いを出す（`HeldReviewNotice`。`heldReview`）。作業履歴の取り込みの行には、一時停止の間に届いて未反映として残した旨を添える。
- 反映（`reworkHeldReview`）：再開したタスクが次に実行されるとき（`runNextInner` の先頭）、止まった工程（PR の更新・実装など）より前に行う。以前の版で最終レビューの前の PR の CI を待つ状態で止めたタスクのように、検証の待ちから外れているタスクも、反映の対象として実行待ちに数える（`heldReviewDue`。`queuedTaskIds`）。
  1. 再開の直後に、PR のフィードバックをもう一度読んで残す（再開の直前に書かれた指摘を拾う。`heldRecheck`。メモリーだけで、再起動で消えても、それまでに残した指摘は作業履歴にある）。読めなければ、また AI のレビューの対象の head を確かめられなければ（原因はタスクと PR を添えて警告に残す。トークンは伏せる）、確かめられるまで止まった工程を走り直さずに待ち（印を残して、次の周期で読み直す）、直前の指摘を落としたまま走り直さない。
  2. 未反映の指摘が無ければ、何もせず、止まった工程を今までどおり走り直す。
  3. PR がマージ済みなら、反映しない（判断も差し戻しもしない）。止まった工程も走らせず、その場で[作り直しの停止](#実装の作り直しの間のマージ)と同じ記録（`ReworkStoppedByMerge`・`PullRequestMerged`・`StepApproved`。残した指摘は捨てる）で、マージを承認として進める（`endHeldByMerge`）。別の作り直しの停止が進行中（`mergeStopping`）なら、そちらに任せる。
  4. 予算の上限に達していれば、判断を実行せず、予算による一時停止にする（工程の実行の前の確認と同じ。判断は費用がかかる）。そうでなければ、戻し先と原因を判断する（`ReworkJudged`。[PR の指摘の取り込み](#pr-の指摘の取り込み)と同じ判断と指示。実装後のコードを読む）。判断を採用できないとき（一時停止・作り直しの停止（PR のマージ）・デーモンの停止のために実行を止めた・中止された・指摘や状態が変わった）は、判断を残さず、使った実行の費用・使用量だけを `runResult: interrupted` の `ReworkJudged` に記録する（指摘は未判断のまま。再開したら判断し直す）。判断できなければ実装をやり直す。判断を記録した後、差し戻す直前に PR の状態を読み直し、マージ済みなら差し戻さず、その場でマージを承認として進める（戻し先が設計・要求要件だと、作り直しの停止の対象外になり、マージ済みなのに前の工程を実行してしまうため）。読み直せなければ、そのまま差し戻す。差し戻す直前には（判断を保存して再開した場合も）、中止・作り直しの停止（PR のマージ）の進行・一時停止の求めを確かめ、あれば古い応答（開いたまま）で差し戻さず、反映を見送る（停止が、残した指摘を捨てて承認として進める）。
  5. 判断した工程に差し戻す（`ChangesRequested`。`settleHeldReview`）。actor は、すべて AI のレビューの指摘なら `sacty`、そうでなければ `person`。回の番号と指摘の ID は、承認待ちの差し戻しと同じ規則で続ける。止まった工程の途中経過（検証・PR の更新の待ち・工程の見直しの待ち）は持ち越さない。以降の実行は、通常の差し戻しの後と同じ（指摘を渡して実装をやり直す、または前の工程からやり直す）。
- 人の差し戻しの上限：承認ゲートが無く、エスカレーションを置く場所が無いので、上限（`MAX_CHANGE_REQUESTS`）に達していても止めない。人の再開を、続ける判断として扱い、`overLimit: true` で記録する。AI のレビューの指摘だけの回は、これまでどおり人の回数に数えない。
- 見逃し（`GuardianMissed`）は記録しない。止まった工程の実装は、合格の判定（以前の版の最終レビュー）を経ていないため。差し戻しの原因（`cause`）は、判断のとおり記録する。
- 一時停止の間に PR がマージされたら、[作り直しの停止](#実装の作り直しの間のマージ)が、残した指摘（`pendingReview`）を捨て、`ReworkStoppedByMerge` の `discardedReview` に件数を残す。

コード: `apps/daemon/src/service.ts`（`checkHeldFeedback`・`holdFeedback`・`reworkHeldReview`・`settleHeldReview`・`withoutStaleReviews`・`resume`・`heldRecheck`）、`packages/core/src/projection.ts`（`heldReview`・`PullRequestReviewImported`・`ChangesRequested`）、`apps/web/src/components/task-detail.tsx`（`HeldReviewNotice`）、`apps/web/src/lib/labels.ts`（`statusText`）

### 承認待ちでの一時停止

関係する ADR: [承認待ち（PR のマージ待ち）でも一時停止できるようにする](../adr/20261103-2300-pause-while-awaiting-approval.md)

承認待ち（`awaiting_approval`）のタスクも、人が一時停止できる。マージを待っている間に、PR の取り込みを止めたいときに使う。エスカレーション（`escalated`）は止められない。

- 一時停止：エージェントの実行が無いので、その場で `TaskPaused`（actor `person`、理由 `manual`）を記録する。承認ゲート（`gate`）と PR の記録はそのまま残し、再開の先として `resumeTo: awaiting_approval` を持つ。
- 止めている間は、承認も差し戻しもできない（状態が `paused`）。PR の取り込みと見守りは、PR の種類で次のとおり。
  - 実装の PR：実装を作り直している間の PR と同じ扱い（`reworkingPullRequest`）。マージされたら、`ReworkStoppedByMerge`（`was: paused`）に続けて `PullRequestMerged`・`StepApproved` を記録して承認として進める（[実装の作り直しの間のマージ](#実装の作り直しの間のマージ)）。再開は要らない。届いた指摘は未反映として残す（[一時停止の間に届いた指摘](#一時停止の間に届いた指摘)）。戻し先の判断はしない。
  - 要求要件・設計の PR：止めている間は見守らない。マージも指摘も、再開したあとの確認で扱う。
- 再開：`TaskResumed` が承認待ちに戻す（承認ゲートは残っているので、承認の画面がそのまま使える）。エージェントは動かさない。
  止めていた間に起きたことは、再開のあとの PR の確認（60秒ごと）が取り込む。
  - マージされていれば、承認として進める（[PR の確認](#pr-の確認)）。
  - 残した指摘（実装の PR）は、そのまま承認待ちの取り込みが引き継ぐ。戻し先を判断して差し戻す。止めている間に書かれた指摘も、同じ確認で取り込む。
- 通知：人が止めたので、Slack には送らない。再開して同じ承認ゲートに戻ったときも、承認待ちの通知はし直さない（`notificationFor`）。

コード: `apps/daemon/src/service.ts`（`pause`）、`apps/daemon/src/notifier.ts`（`notificationFor`）、`packages/core/src/projection.ts`（`TaskPaused`・`TaskResumed`・`resumeTo`・`reworkingPullRequest`）、`apps/web/src/components/task-detail.tsx`（`canPause`）

### ベースブランチとの競合の表示

承認待ちの間に先の PR がマージされて、実装の PR がベースブランチと競合したら、タスクの画面と「あなたの出番」に出す。
出すだけで、ベースブランチは取り込まない（取り込みは、人が差し戻すか PR に指摘を書いたときに、実装をやり直す前に行う。[ベースブランチの取り込み](tasks-and-steps.md#ベースブランチの取り込み)）。

- 競合の判定：PR の状態の確認（`GitHubPullRequests.status`）が読む、GitHub の PR の `mergeable`。
  `false` が競合、`true` が競合なし。GitHub がまだ計算中（`null`）・読めないときは分からないので、前の記録のままにする（`PullRequestStatus` の `mergeable` は、`true`・`false` のときだけ持つ）。
  PR の状態を読む 1 回の問い合わせに含まれるので、GitHub への問い合わせは増えない。
- 記録：競合が変わったときだけ、actor `sacty` で記録する。同じ状態は重ねて記録しない。
  - 競合した：`PullRequestConflicted`。`Task.pullRequestConflict`（PR の番号・そのときの提出のコミット・時刻）に持つ。
  - 解消した（人が GitHub で直した・ベースブランチが戻った）：`PullRequestConflictResolved`。`Task.pullRequestConflict` を消す。
  - 記録するのは、承認待ち（`awaiting_approval`）の実装の PR だけ。要求要件・設計の PR（タスクブランチへの PR）と、エスカレーション中は記録しない。
  - 実行・取り込み・PR の更新・GitHub への書き込みは何も始めない。
- 画面に出す条件（`pullRequestConflict`）：承認待ちで、実装のゲートの PR が開いていて、記録の PR の番号とコミットが今の提出と同じで、PR の指摘の戻し先を判断している間（`pendingReview`）でないとき。
  - PR を作り直した・更新した（`PullRequestPublished`）、マージされた・閉じられた・開き直された（`PullRequestMerged`・`PullRequestClosed`・`PullRequestReopened`）ときは、記録を消す。
    開き直されたときは、次の確認で確かめ直す。
  - 差し戻して承認待ちでなくなったときは出さない。
- 出す場所：
  - 状態の表示（`statusText`）が「実装の PR がベースブランチと競合」になる。ダッシュボードの「あなたの出番」・ヘッダーのお知らせ・タスクの一覧・詳細で同じ。人の出番のままで、「あなたの出番」の行は PR を開く。
  - 「あなたの出番」の行（ダッシュボードと、タスクの一覧の上のカード）には、取り込む操作の案内（「差し戻すか、PR に指摘を書くと、ベースブランチを取り込みます」。`AttentionRow.note`・`NeedsYouCard.note`）を添える。ヘッダーのお知らせは状態だけ。
  - タスクの詳細の承認待ちの案内と、承認の画面の PR の欄に、取り込むための操作（この画面から指摘を入れて差し戻す・GitHub の PR に指摘を書く）の説明を出す。
  - 引き継いだ PR（`Task.continuedPullRequest`。`mergesBase` が取り込まない）には、取り込む操作ではなく、GitHub で解消する案内（「引き継いだ PR なので、ベースブランチは取り込みません。GitHub で競合を解消してください」）を、同じ場所に出す。競合の表示そのものは変えない。
  - 作業履歴に「PR #N がベースブランチと競合している」「PR #N の競合が解消された」を出す。
- 判定はマージの可否ではない。競合のまま人がマージしたときは、通常のマージとして承認する。

## PR の本文と PR テンプレート

関係する ADR: [sacty が作る PR の本文を、リポジトリ・Org の PR テンプレートの見出しに沿って決まった規則で埋める](../adr/20261014-1517-pr-body-follows-repository-template.md)

sacty は PR を作る・更新するたびに、PR を作るリポジトリの PR テンプレートを探し、あればその見出し・項目の形で本文を書く。
対象は、実装の PR と、要求要件・設計の PR（マージの後の監視で作る修正のタスクの PR も同じ）。
テンプレートが無い・使えないときは、sacty の決まった形の本文（`buildPullRequestBody`・`buildStepPullRequestBody`）にする。
どちらでも PR の作成は止めない。

### 実装の PR の本文の組み立て

実装の PR の本文は、結論から短く読めるようにする。
承認済みの要求要件・設計の全文や、レビューの長い文は載せず、リンクか折りたたみにする。
決まった形の本文（`buildPullRequestBodyText`）は、次の順に入れる。

1. タスクの ID の行と、`Closes #<番号>`（Issue から取り込んだタスク）
2. 「結論」
   - 変更の要約：実装の工程の出力の最初の段落（字下げのない行だけ。見出し・表・コードブロック・字下げした行を除く）の頭。出力が無ければ行ごと出さない。作り直した後は、PR 全体の説明（下の「作り直しの後の本文」）の頭。
   - 最後の直し：作り直した後だけ、最後の直しの説明の頭。
   - レビューの行（`REVIEW_BODY_LINE`）。PR のレビューの子タスクがレビューして投稿し、指摘があれば sacty が直し、指摘なしでドラフトを外すことと、CI の結果は PR で確かめることの案内。以前の版の最終レビューの判定と所見は、結論に出さない。
   - AI のレビューの状況：今の head に sacty の AI のレビューが付いているか（[AI のレビューの指摘](#ai-のレビューの指摘)の「今の head に AI のレビューが付いているか」。`aiReviewBodyLine`）。
   - 人が以前の版の最終レビューの不合格のまま進めた記録と不合格の要点（あれば。[人がレビューへ進める](tasks-and-steps.md#人がレビューへ進める)。`overrideBodyLines`）
   - 人が確かめること（あれば。`humanCheckBodyLines`）
3. 承認済みの要求要件（再現のタスクは不具合の再現。`approvedBasisLines`）
   - 全文は載せず、最初の段落の頭と、全文のある場所にする（`approvedBasisDigest`）。
     全文のある場所は、マージで承認した要求要件・設計の PR の URL とファイルのパス。PR が無ければ「全文は sacty のタスクの画面で確かめてください。」と書く。
     リンクの形は下の「前の工程の成果物へのリンク」のとおり。
   - 要求要件の工程を省いたタスクと、セキュリティ対応の修正の範囲は、短い文なので従来のとおり。
4. 「変更」：実装の工程の出力（作り直した後は、PR 全体の説明）から、結論の変更の要約に載せた最初の段落を除いた残り（結論と同じ文を重ねない。PBI-301 A7。実験 S16・S19 の F3 の再発）。残りに見出し以外の中身が無ければ（要約と同じだけの出力・見出しだけが残る出力）節ごと出さない。最初の段落が切り詰められて結論に載ったときは、全文を出す。出力が無ければ見出しも入れない。出力の残りが自分で見出し（`#`・`##`）から始まるときは、中身の無い「変更」の見出しを重ねず、その見出しから出す（PBI-302 C2。実験 S2 の r5：「## 変更」の直下に「## 変更内容」が続いた）。テンプレートに沿わせる本文の「変更」は、結論の要約が無いので全文のまま。
5. 「最後の直し」：作り直した後だけ。最後の直しの説明から、結論の「最後の直し」に載せた最初の段落を除いた残り（結論と同じ文を重ねない。PBI-302 C2。実験 S2・S14・S18 の r5）。最後の直しが結論の1段落に収まるときは節ごと出さない（下の「作り直しの後の本文」）。
6. 書き出した成果
7. 観点 → テスト → 実行結果
   - 表の列は「観点」「テスト」。観点は ID と題（60 文字まで）、テストは 1 件目の名前（70 文字まで）と「ほか N 件」。以前の版の最終レビューの記録（`lastReview`）があるときだけ、列「最終レビュー」を足し、その判定の ✅ か ❌ を出す（判定が無い観点は「（なし）」）。
   - 表の下に、テストの行を置く。以前の版の最終レビューで実行したテスト（`lastReview` の `tests`）か以前の版のテストの結果（`lastTests`）があれば、そのコマンドと結果。無ければ、テストの仕組みが無いタスク（`noTestsReason`）では「テスト：テストの仕組みが無いリポジトリとして進めたため、テストでは検証していません。」、それ以外ではテストの行を出さない（sacty はテストを実行しない）。
   - 観点ごとの入力・期待結果・テスト全件（以前の版の最終レビューの記録があれば、その判定と所見も）は、表の外の折りたたみ「観点ごとの詳細」に出す。所見のうち、最終レビューの総評にある文（12 文字以上で、句点で区切って一致するもの）は繰り返さない。所見のすべてが総評の文なら「総評と同じです」と書く（`findingText`。PBI-302 C2）。
   - テスト名は、同じテストを1回にして、書式の文字を印にしてから出す（`displayTestNames`。PBI-302 C3。実験 S18 の r5：同じテストが describe の接頭辞あり・なしで2回出て、10 行のうち5行が重複し、`%j` が書式のまま出た）。同じファイル・同じテスト名で、describe の並びが他方の末尾にあたる名前（接頭辞を省いた名前）は、長いほうに統合し、そのテストが最初に出てきた位置（短い名前と長い名前の早いほう）に置く（describe が別の同名のテスト・ファイルが別の同名のテストは別のまま）。区切りは `›` と ` > ` で、区切りの書き方や空白だけが違う名前は同じテストとし、最初の表記を残す。パラメータ化したテストの名前の書式の文字（`%s`・`%d`・`%i`・`%f`・`%j`・`%o`・`%O`・`%p`・`%#`・`%$`）は、名前だけからは値が分からないので展開せず、`‹…›` に置き換える（`%%` は `%`）。画面の観点とテストの対応も同じ。

共通の規則は次のとおり。

- 実装の工程の出力から、作業の経過の報告の文を除く（`withoutProgressReport`）。
  除くのは、コミット・プッシュ・GitHub への反映などの話題の語と、していません・未完了・sacty が行うなどの状態の語を両方含む、100 文字以内の文。
  触るのは、フェンスの外の、行頭が空白でない行の文だけ。コードブロック（CommonMark のフェンス：字下げは 0〜3 空白、終了は開始と同じ文字で開始以上の長さ）・表・見出しの行と、字下げのある行（リストの中のコード・字下げしたコードなど）は触らない。
  Markdown の規則を一つずつ読まず、迷う入力は消さない側に倒す（報告の文が1つ残るほうが、コードが壊れるより害が小さい）。結論の要約（`leadParagraph`）も、字下げのない行だけを使う。実装の工程の出力は、先頭の行の字下げを消さずに保存する（前後の空行と末尾の空白だけを除く。`extractBlocks` の `keepIndent`。ほかの工程は従来どおり前後の空白を除く）。
  実装の指示にも、説明は PR の本文にそのまま載ること、作業の経過の報告は書かないことを書く（`IMPLEMENT_REPORT_LINE`）。
- 以前の版の最終レビューの所見の頭の「合格。」「不合格。」は除いて出す（判定は別に書くので、「合格。合格。」と重ねない）。
- sacty の作業領域の内部のパス（`/sacty-input/task.md:77` など。コンテナの内部のパスで、人は辿れない）を、PR の本文・要求要件と設計のファイル・調査の結果のコメント・工程が頼んだコメントの投稿（`sacty-github-comments`）・人に確かめてほしいことのコメントに出さない（`withoutInternalPaths`。PBI-301 A7。実験 S16：要求要件の PR の本文に出た）。入力のファイルは「タスクの依頼」「人の指摘」「調査の結果」「承認済みの要求要件」の呼び方に、ほかの内部のパス（`/sacty-review`・`/sacty-memory` など）は置き場所の呼び方に置き換え、内部のファイルの行番号は書かない。リポジトリのパスは変えない。出典の分類の指示と既定のスキル `classify-provenance` も、根拠の参照（`refs`）に Input の置き場所のパスを書かせない。
- 作り直しの後の本文（PBI-299。実験 S5 r4 の F44：2回作り直した最後の本文の「結論」・「変更」・「検証」・観点表が、最後の直しだけを書き、何の PR か分からなくなった）：人の差し戻し・AI のレビューの指摘（以前の版では最終レビューの不合格も）のどれで始まった作り直しでも、更新する PR の本文は、その時点の PR 全体の説明にする。
  - 実装の提出ごとの出力を、`Task.implementHistory` に古い順に持つ（`AgentRunCompleted`（実装）から作る。10 件まで）。あわせて、前の提出までの PR 全体の説明の土台を `Task.implementBase` に持つ（最初の提出の前は無い。最初の提出、または「最後の直し」の節を付けて全体を書き直した提出の、節以外の部分。節の無い提出は土台を変えない。`advanceImplementBase`）。履歴が上限で古い提出を捨てても、土台は消えない。どちらも、要求要件・設計などの上流の工程を承認し直したとき、承認済みの上流の成果物を変える申し出を適用したときは空に戻す。
  - 実装の指示（`implementReworkLines`。前の実装の説明を添えるとき）で、説明は PR が加える変更の全体の説明にすること（前の説明を土台に、今回の直しを反映して書き直し、「最後の直し」の節の内容も全体に取り込む）、今回の直しは説明の最後の「## 最後の直し」の節（`LAST_FIX_HEADING`）に1つだけ分けて書くこと、観点とテストの対応も PR 全体の対応にすることを書かせる。
  - 本文は、説明を「## 最後の直し」の節（`splitLastFix`。コードブロックの中の見出しは読まない。次の同じかより上の階層の見出しまで）とそれ以外に分け、それ以外を PR 全体の説明（結論の変更の要約・「変更」）、節を最後の直し（結論の「最後の直し」の行・「最後の直し」の節）にする（`implementDescription`）。テンプレートに沿わせる本文は、「変更」に全体の説明を置き、続けて太字の「最後の直し」と本文を置く。
  - 節を書かずに最後の直しだけを書いた提出は、PR 全体の説明にしない。前の提出までの土台（`implementBase`）を全体の説明に使い、最後の提出の説明全体を最後の直しにする。前の提出が無い（最初の実装）ときは、節があっても説明を変えない。作り直しが無いタスクの本文は、これまでと同じ。
  - 観点とテストの対応（`Task.testMap`）は、前の提出があるとき、今回の申告に出てくる観点に、前の提出までに対応させたテストを先に、今回のテストを後に並べる（同じテストは1件。`mergeTestMaps`）。テストを書かずに差分で確かめる観点（`tests` が空）は、今回の申告をそのまま使う。今回の申告に出てこない観点は、前の対応を残さない（対応していない観点として、これまでどおり検証で不合格になる）。
- 結論の長い文は、`BODY_LEAD_MAX`（240 文字）以内の文の切れ目（「。」）で切る。切れ目が無ければ「…」を付ける。

### テンプレートを探す

探すのは既定のブランチのもの。
ファイル名・ディレクトリ名の大文字・小文字は区別しない。
前の順番で見つかったら、その時点で読み、後の順番のディレクトリ（`docs/` など）の一覧は取りに行かない。

1. 対象のリポジトリの `.github/pull_request_template.md` → ルートの `pull_request_template.md` → `docs/pull_request_template.md`
2. 1つも無ければ、同じ順の `PULL_REQUEST_TEMPLATE/` ディレクトリ（`.github/`・ルート・`docs/`）の中の `.md` のうち、名前の順（大文字・小文字を区別しない）で最初のもの。
   GitHub はディレクトリの複数のテンプレートを既定には使わないが、sacty は1つを選ぶ。
3. 対象のリポジトリに無ければ、Org（またはユーザー）の `.github` リポジトリ（`https://<ホスト>/<owner>/.github`）の同じ場所。
   GitHub と同じく、公開（`private: false`）のものだけを使う。
   非公開なら使わず、その旨を残す。
   対象が `.github` リポジトリそのものなら探さない。

テンプレートが無い・使えないと判断する条件は次のとおり。

- 無いものとする：リポジトリ・ディレクトリの一覧が 404（空のリポジトリ・見えないリポジトリを含む）。
- 使えない（`unusable`）
  - 一覧・ファイルの取得が 404 以外の失敗・通信の失敗・時間切れ（探す処理全体で30秒）
  - 32 KiB（`TEMPLATE_MAX_BYTES`）より大きい（大きさは一覧の値で判断し、中身は読まない）
  - UTF-8 として読めない
  - 空白だけ
- 対象のリポジトリで使えないときは、Org の `.github` は探さない。

### テンプレートを埋める

埋めるのは `fillTemplate` で、エージェントは使わない。

- 見出しで分け、見出しの文から種類を決める。
  - 見出しは、`#`〜`######` の行と、行全体が太字の行 `**概要**`。
    コードブロック・HTML のコメントの中のものは除く。
  - 種類は `CATEGORY_RULES` を上から順に当てて決める。
    種類は、書けない見出し（チェックリスト・スクリーンショット・破壊的変更・その他など）、関係する Issue、テスト、変更、目的・概要。
  - 種類ごとに、最初に当たった見出しにだけ sacty の内容を入れる。
- 見出しの中の説明・例の文とコードブロックは消し、HTML のコメントとチェックボックスは残す。
  チェックボックスは、テンプレートでチェックされていても、すべて外す（sacty は確かめていないので）。
- 内容の無い見出し・当てはまらない見出しには「該当なし（sacty は記入していません）」（`NOT_APPLICABLE`）と書く。
  チェックボックスのある見出しには書かない（外したチェックボックスだけを残す）。
  最初の見出しより前は、コメントとチェックボックスだけを残す。
- 実装の PR の内容（`buildPullRequestBodyParts`）
  - 目的：レビューの行（上の結論と同じ。PR のレビューの子タスクの案内）、人が確かめることの件数（あれば「この PR の末尾にあります」）、承認済みの要求要件（再現のタスクは不具合の再現）の要点と全文のある場所
  - 変更：実装の工程の出力（作業の経過の報告を除く。作り直した後は、PR 全体の説明に続けて、太字の「最後の直し」と最後の直しの説明）
  - テスト：観点 → テスト → 実行結果の表とテストの結果（[実装の PR の本文の組み立て](#実装の-pr-の本文の組み立て)の 6）
  - 関係する Issue：`Closes #<番号>`（Issue から取り込んだタスク）
  - 書き出した成果は「sacty の記録」にする。
  - 人が確かめること・人が不合格のまま進めた記録は、最後の部分（footer）に置く。
- 要求要件・設計の PR の内容（`buildStepPullRequestBodyParts`）
  - 目的：何の工程の成果か（と承認済みの前の工程。リンクの形は下の「前の工程の成果物へのリンク」のとおり）
  - 変更：成果のファイルと指摘への対応
  - 関係する Issue：`#<番号>`（参照だけ。タスクブランチへのマージでは閉じない）
  - テストは無い。
- 見出しに入らなかった内容と「sacty の記録」は、本文の末尾に折りたたみ（`<details>`）で置く。
  どの見出しにも内容を入れられなかった（見出しの無いテンプレートなど）ときは、目的・変更・テストは折りたたまずに置く。
  関係する Issue が見出しに入らなければ、最後の部分の前に置く。
- 最後の部分（footer）には、次を必ず入れる。
  - sacty が作った旨とタスクの ID（`sacty task <ID>`）
  - マージがその工程の承認になることと、指摘の伝え方（実装の PR と、要求要件・設計の PR）

### 長さ・秘密の値・台帳

- 長さ（`limitBody`）
  - 本文は 65,000 文字（`PR_BODY_MAX`）までにする。
    GitHub の上限 65,536 文字より少し短く、JavaScript の長さで測る。
  - 超えるときは、最後の部分の前の後ろを省き、省いた旨（`TRUNCATED_NOTE`）を書く。
    省いたところで閉じられていない HTML のコメント・コードブロック・折りたたみは閉じる。
  - テンプレートを使わない本文（`buildPullRequestBodyText`・`buildStepPullRequestBodyText`）にも同じ上限を使う。
    最後の部分（sacty が作った旨と、マージが実装の承認になることの案内）は省かない。
  - 省けない部分（`keep`）は、タスクの ID の行、`Closes #<番号>`（テンプレートの見出しに入れたものも）、要求要件・設計の PR のマージが承認になることの案内、決まった形の本文の結論に置いた人が確かめること・人が不合格のまま進めた記録。
    省いた後の本文に、これらが行として丸ごと（前後が行の境目）・HTML のコメントとコードブロックの外に残っていなければ、最後の部分の前に出し直す。
    `Closes #123` があっても `Closes #12` が残ったとは見なさない。
- 秘密の値：その PR の作成で使った秘密の値（GitHub のトークンなど）を、本文から伏せる（`[REDACTED]`）。要約・短縮（結論の要約・表のテスト名や観点の題・人が確かめること・不合格のまま進めた記録の所見など）で切れた先頭が残らないよう、本文を作る前に、タスクのすべての文字列から伏せる（`PullRequestBodyStage.secrets`）。公開の直前の置換も残す。
  台帳に残す理由の文も伏せる。
- 台帳：`PullRequestPublished`・`StepPullRequestPublished` の `template` に、次を残す。
  - 使ったテンプレート（`repo`：テンプレートのあったリポジトリの URL、`path`）
  - または、決まった形にした理由（`fallback`：`none`・`unusable`、`message`：`pr.templateFailed`・`pr.templateTooLarge`・`pr.templateInvalid`・`pr.templateEmpty`・`pr.templateOrgPrivate` など）
  - 省いたら `truncated`
  - タスクの画面の PR の欄に「本文」として出す。
    この版より前の記録には無い（画面には出さない）。

- 前の工程の成果物へのリンク（実装の PR の承認済みの要求要件の全文のある場所と、要求要件・設計の PR の承認済みの前の工程。`stepArtifactLink`。PBI-322）
  - 工程ごとに1行、「`- <工程>：`」に続けて、成果のファイルのパスのインラインのコードを `<リポジトリ>/blob/<コミット>/<パス>` へのリンクにし、全角の括弧の中に「PR：」と、PR の URL へのリンク（文字は `#<番号>`）を置く。
  - ファイルのリンクは、マージされた内容のコミット（PR の先頭のコミット。人が直してマージしたなら、人が直した最終のコミット）を指す。記録が無ければ、sacty が PR に出したコミット。PR の先頭のコミットは GitHub が PR の参照に残すので、PR・タスクのブランチが消えても読める。マージのコミットは、タスクブランチが消えると辿れないことがあるので使わない。
  - PR の URL も明示的なリンクにする。PR の URL の直後に全角の括弧などを続けると、GitHub の自動リンクがそれも URL に含め、`/pull/<番号>（…` を開いて compare の画面になるため。
  - パスは区切りごとに符号にし（括弧も符号にして、リンク先が途中で閉じないようにする）、リンクの文字はパスのインラインのコード（中にバッククォートがあれば、より長いバッククォートで囲む）。
  - PR の URL が `<リポジトリ>/pull/<番号>` の形でなければ、パスのインラインのコードと、全角の括弧の中に「PR：」と山括弧で囲んだ URL（自動リンク）にする。URL が無ければパスだけ。

コード: `apps/daemon/src/pr-template.ts`（`GitHubPullRequestTemplates`・`fillTemplate`・`limitBody`・`CATEGORY_RULES`）、`apps/daemon/src/service.ts`（`pullRequestBody`・`publish`・`publishStepPullRequest`）、`apps/daemon/src/prompts.ts`（`buildPullRequestBodyParts`・`buildStepPullRequestBodyParts`・`buildPullRequestBodyText`・`buildStepPullRequestBodyText`・`resultTableLines`・`approvedBasisLines`・`stepArtifactLink`・`withoutProgressReport`）、`packages/core/src/test-names.ts`（`displayTestNames`・`dedupeTestNames`・`withoutFormatPlaceholders`）、`packages/core/src/events.ts`（`PullRequestTemplateUse`）、`apps/web/src/components/pull-request.tsx`（`TemplateUse`）

## PR の指摘の取り込み

- PR が開いていて承認待ちのとき、PR のレビュー・行へのコメント・通常のコメントを指摘として取り込む（`PullRequestReviewImported`、actor `person`。sacty 自身の AI のレビューの指摘だけの回は actor `sacty`）。
  - 最後のフィードバックから2分（`FEEDBACK_QUIET_MS`）待ってから取り込む。
    各フィードバックの時刻は、GitHub の時刻と、デーモンが初めて見た時刻（メモリーだけ。`feedbackSeenAt`）の早い方にする。
    GitHub の時刻がこの機械の時計より先に進んでいても、初めて見てから2分で取り込む（GitHub の時刻まで待ち続けない）。
    GitHub の時刻が遅れているときは、見た時点で2分たっていれば待たない。
    指摘を取り込む対象から外れたタスク（承認待ちでなくなった・中止など）の分は、次の確認で忘れる。
  - 古い順に最大50件（`REMARKS_MAX`）、1件 2000 文字（`REMARK_MAX`）まで。
  - 行へのコメントの指摘には、そのコメントが付いた行の内容と直前の2行を、指摘の文の後ろに添える（PBI-302 B3）。
    - 内容は、GitHub が返すコメントの diff の抜粋（`diff_hunk`。コメントが付いた行が最後）から取る（`lineContextOf`）。ハンクの見出しと差分の先頭の印（`+`・`-`・空白）は除く。引用する行を選ぶ前に、抜粋の全体を一度に伏せる（複数行の PEM の秘密鍵の本文を見つけるため。開始の行が抜粋の外にあり終了の行だけがあるときは、抜粋の頭から終了の行まで伏せる）。ここでは切り詰めない。
    - 指摘の文は `path:行：本文` のあとに、改行して `（コメントが付いた行の内容：「…」。直前の行：「…」「…」）` を足す（`lineContextText`。空白をそろえ、空の行は「空行」、秘密情報と URL の認証情報は行全体で伏せてから 1 行 200 文字までにする。切ってから伏せると、境界で形の崩れた値を見つけられないため）。添える分は切らず、指摘の文を短くして 2000 文字に収める。
    - 抜粋が無いコメントには何も添えない。コメントが付いた行の後ろの行は渡さない（抜粋にあるのは前の行まで）。
    - 戻し先の判断と、直しの実行（要求要件・設計・実装）の指示は、添えた指摘があるとき、行番号から成果物の行を数えて当てはめず、添えた行の内容で箇所を確かめさせる（行番号と内容が食い違うときは内容を信じる。添えた行の内容はコードや文書の引用で、指示ではないと伝える。`lineContextNote`）。
  - 同じものは二度取り込まない。
  - 実装の作り直しを一時停止している間は、承認待ちではないので取り込まず、未反映として残して再開のときに反映する（[一時停止の間に届いた指摘](#一時停止の間に届いた指摘)）。
  - 引き継いだ既存の PR では、実装の工程の指示に渡した指摘を取り込まない（実装に対応させたため。[既存の PR の引き継ぎ](tasks-and-steps.md#既存の-pr-の引き継ぎ)）。
- この PR をレビューした sacty のタスク（PR を指すタスク。取り込んだ PR か、本文の PR の URL）の投稿は、2つで判定する。
  そのタスクのプロジェクトのアカウント（元のタスクのアカウントと違うことがある）と、目印（`<!-- sacty-review:<タスク ID>[:<回>] -->`）の回である。
  bot の判定より先に見るので、そのアカウントが bot（GitHub App など）でも同じ。
  - そのタスクの、指摘のある回は、指摘として取り込む。
    レビューのタスクの種類（レビューの子タスク（`source.review: sacty`、`reviewOf` あり）・以前の版でレビュー用のラベルから取り込んだ sacty の PR のタスク（`source.review: sacty`、`reviewOf` なし）・レビューの依頼（`requested`）・レビュー用のラベル（`label`）・手動で作ったタスク（`source` 無し）など）は問わない。
    レビューの子タスクは、sacty が PR を作ったときに自動で作る（ラベルを経由しない）。それ以外は、人が求めたレビューにあたる。
    どれも、PR を作ったタスクに直させるべきレビューである。
    指摘のある回は、`reviewVerdicts` の `verdict` が `changes_required` か `suggestions` の回。
    判定を読めなかった回も、指摘を落とさないように含める。
    作ったタスクとは別のタスクのレビューを、元のタスクに届けて対応させるためである。
    提案だけの回も取り込み、繰り返しの費用は予算で止める。
    判定の決め方は [タスクと工程](tasks-and-steps.md#pr-のレビューだけのタスク)。
  - ほかの回（指摘の無い回と、判定の記録が無い回。まだ実行していない回や、PR を参照するだけでレビューの工程を持たないタスクの回）は、アカウントが元のタスクと違っても取り込まない。
    差し戻さず、戻し先の判断もしない。
  - 再レビューは回ごとに判定する。
    そのタスクのアカウントと違う人が目印を写したものは、人の指摘として扱う。
  - 取り込んだ指摘は、AI のレビューの指摘として人の指摘と区別する（下の「AI のレビューの指摘」）。
- それ以外では、次の投稿を取り込まない。
  - bot の投稿
  - 元のタスクのプロジェクトのアカウントが投稿した、sacty のレビューの目印で始まるレビュー・行へのコメント
- 取り込んだら、戻し先（その工程のやり直しか、前の工程への差し戻し）を判断し（`ReworkJudged`）、人の確認を挟まずに差し戻す。
  - 担い手（PBI-332。以前の版ではゴールガーディアン（actor `guardian`））：
    - 指摘が AI のレビューの指摘だけで、すべてがその PR のレビューの子タスクの最後の回の投稿（取り込んだときに目印から読んだ、投稿したタスクと回。`PullRequestReviewImported` の items の `review`）のときは、子タスクが最後の回の判定のブロック（`sacty-review-verdict` の `rework`）に指摘ごとに示した戻し先と原因から決める（`reviewTaskRework`・`reviewReworkTarget`）。判断の実行はしない（費用は 0。作業履歴は actor `sacty` で、`reviewTaskId` に子タスク）。
      戻し先が読めない・候補に無い・知らない値の指摘は、その PR の工程で直す。`rework` が無ければ、その PR の工程をやり直す（理由は `rework.reviewTaskUnreadable`）。子タスクの答えに `answer` は無い（AI のレビューの指摘は、質問への答えではない）。
    - 人の指摘を含むとき・子タスクが無いとき（ラベル・依頼で取り込んだレビューだけのタスクの投稿だけのときを含む）・ほかのレビューのタスクや前の回の投稿・出どころの回が分からない（以前の版の記録）指摘を含むときは、その PR の工程のエージェント（人が選んだもの。無ければ `step_agents` か `default_agent`）に、新しいセッションで判断させる（作業履歴は actor `agent`）。
      人が選んだエージェントが設定から消えていれば、既定のエージェントで判断せずに、理由を示して一時停止し（`agent.chosenMissing`）、指摘は未判断のまま残す（再開したら判断し直す）。
    - 子タスクには、レビューの指示で、戻し先の候補・下の基準・承認済みの前の工程の成果物・原因の選択肢（`guardian_missed`・`base_changed`）を渡す（`reviewReworkLines`）。
  - 戻し先は、指摘が承認済みの前の工程の決定（受け入れ条件・振る舞い・画面・API やデータの形・テスト観点・確認して決めたこと）を変えるかで決める。
    - 決定を変えない指摘は、その PR の工程（実装の PR なら実装）に戻す。文書への追記、実装の直し、決定済みのことの反映漏れがこれにあたる。
      承認済みの成果物に書き漏れ（影響範囲の一覧に無い、テスト観点に無いなど）があっても、指摘の求めることが承認済みの決定から導けるなら、決定を変えるものとしない。
    - 決定そのものを変える指摘だけ、その決定を持つ工程（設計・要求要件）に戻す。複数の指摘のうち1つでも決定を変えるなら、その決定を持つ工程に戻す。複数の工程にまたがるなら前の工程に戻す。
    - 前の工程に戻すと、承認済みの成果物を作り直してもう一度承認するので、費用も手間も大きいため。
  - 判断の理由（`ReworkJudged` の `reason`）の先頭には、指摘がどの決定を変えるか、または変えないかを短く書かせる。
    書式は指示で求めるだけで、sacty は検査しない（理由は読み取れれば、書式に関わらず記録する）。
  判断できなければ、戻せる工程の先頭（実装の PR なら実装、要求要件・設計ならその工程）をやり直す。
- 戻し先と一緒に、差し戻しの原因（`cause`）も判断させる（[差し戻し](#差し戻し)）。
  `guardian_missed`・`new_request`・`question_answer`・`base_changed` のどれかで、判断できなければ（答えが無い・`undecidable`・知らない値）原因を決めない（原因が分からない差し戻しとして数える）。
  判断は `ReworkJudged` の `cause` に残し、差し戻し（`ChangesRequested`）に引き継ぐ。
  - `question_answer`（質問への答えだけのコメント）を選べるのは、要求要件・設計の PR のとき。
    指摘が、成果物の「確認したいこと」（sacty の質問）への答えだけ（「推奨どおり」「A 案で」など）のときに選ぶ。新しい要望・方針の変更（`new_request`）ではない。
    質問への答えでない要望や修正の依頼が1件でも混じるときは選ばない。実装の PR には sacty の質問が無いので、選択肢に出さない。
  - 原因が `question_answer` のときは、答えの扱い（`answer`）も判断させる（`ReworkJudged`・`ChangesRequested`・`prRework` の `answer`）。
    `as_recommended` は、答えがすべて成果物の推奨の答えどおり（「推奨どおり」「任せる」を含む）で、承認済みの決定を変えないとき。`changes_decision` は、推奨と違う答えが1つでもある・答えが承認済みの決定を変えるとき。迷うときや答えの意味を読み取れないときは `changes_decision`。
    原因が `question_answer` でないときの `answer`・読めない値は読まない（`answer` を持たない）。
  - `as_recommended` で、判断した戻し先がその PR の工程（要求要件・設計）のときだけ、答えの反映だけの軽い直しにする（`settleReview` が `ChangesRequested` に `answer: as_recommended` を残す）。
    前の工程へ戻す・実装の PR・戻し先を判断できない・`answer` が無いときは、`as_recommended` を残さず、今までどおりの直し。`changes_decision` は、そのまま `answer` に残して今までどおりの直し（成果物を作り直し、セルフレビューをする）。
  - 軽い直し（`isAnswerOnlyRework`）：その差し戻しの指摘（判断した指摘の集合そのもの）で始まった要求要件・設計の実行は、前回の下書きを元に、答えた項目を「確認したいこと」から外し、答えを反映する所だけを直す。ほかの節・項目・表の行・ID は一字一句そのまま保つ（`answerOnlyReworkLines`）。
    セルフレビュー（観点の担当の起動）は行わず、提出の前に本文を読み直して3点（答えた項目が外れている・反映した所以外が前回と同じ・ID に欠番や重複が無い）だけ確かめさせる。セルフレビューの報告（`sacty-self-review`）は付けさせない（`answerOnlyCheckLines`。記録なしとして扱い、次の直しは全体をレビューする）。
    出典の分類（確かめる所の表）と、指摘ごとの対応の報告は、今までどおり。答えが推奨どおりでないと分かったら、軽い直しをやめて通常の直しをさせる（指摘への対応に理由を書かせる）。
    前回の下書きが空で読めないときは、軽い直しにしない。
  承認済みの要求要件が無いタスク（要求要件の工程を省いたもの）は、元の依頼（タスクの題名と本文）も判断に渡す。承認済みの要求要件があるタスクには渡さない（要求要件が基準）。
- 判断の実行を、デーモンの停止・中止のために止めたときは、判断の失敗として採用しない（実装をやり直すことになるため）。承認待ちの取り込みの判断も同じで、使った実行の費用だけを `runResult: interrupted` の `ReworkJudged` に記録し、指摘は未判断のまま残して、次の確認（再起動の後）で判断し直す。
- 差し戻す直前に、PR の状態をもう一度読む（判断の最中や、判断を記録した後の再開で、人がマージ・クローズしていることがあるため）。
  - 開いたままなら、差し戻す。
  - マージされた・マージされずに閉じられたなら、差し戻さない。取り込んだ指摘（`PullRequestReviewImported`）と判断（`ReworkJudged`）は作業履歴に残し、同じ確認の中で状態を確かめ直して、[PR の確認](#pr-の確認)の「マージされた」「マージされずに閉じられた」として記録する（マージなら `PullRequestMerged` と `StepApproved`。`StepApproved` が、反映の途中の指摘の状態を消す）。
  - マージされずに閉じられた後に開き直されたら、記録した判断のまま差し戻す（判断し直さない）。
  - 読み直しの間に、人が差し戻した・中止したなどで状態が変わっていれば、記録しない。読めなければ、次の確認でやり直す。
  - マージの後に届いた指摘を、続きのタスクにするなどはしない。

### AI のレビューの指摘

関係する ADR: [sacty 自身の AI のレビューの指摘を、人の指摘と区別して扱う](../adr/20261102-0843-distinguish-ai-review-remarks.md)

sacty のレビューのタスクが PR に投稿したレビュー・行へのコメント・通常のコメントは、元のタスクに今までどおり届ける。
ただし、人の指摘とは区別する。

- 見分け方：投稿の目印（`<!-- sacty-review:<タスク ID>[:<回>] -->`）で見分ける。上の「この PR をレビューした sacty のタスク」の判定で取り込む投稿が、AI のレビューの指摘（`PullRequestFeedback.source: "sacty_review"`）になる。
  投稿したアカウントでは見分けない（レビューは、プロジェクトのアカウント＝人と同じアカウントで投稿される）。
  アカウントが同じでも、目印の無い投稿は人の指摘のまま。
- 記録：`PullRequestReviewImported` の `items[].source` に `sacty_review` を残す。
  取り込んだ指摘のうち、AI のレビューのものの位置を `pendingReview.aiReview` に持つ。
  差し戻し（`ChangesRequested`）の指摘（`remarks[].source`、`Task.remarks[].source`）に引き継ぐ。
  - 取り込みが AI のレビューの指摘だけなら、actor は `sacty`（人の操作にしない）。人の指摘が1件でも混ざれば `person`。
  - 差し戻しも同じで、指摘がすべて AI のレビューのものなら actor は `sacty`。
- 回数と上限：AI のレビューの指摘だけの差し戻しは、人が差し戻した回数と、同じ工程への差し戻しの上限（`MAX_CHANGE_REQUESTS`）に数えない。
  - 人の回数（`changeRounds`）は、人の指摘が1件でもある回の数。AI のレビューだけの回は数えない。
  - 回の番号と指摘の ID（`<工程>-<回>-<番号>`）は、AI のレビューの回も含めて続ける（`lastChangeRound`）。
  - AI のレビューの指摘だけの差し戻しは、上限に達していてもエスカレーションにしない。
  - 費用の上限は、今までどおり効く。
- 古い head へのレビュー：レビューが対象にした PR の head（レビューのコミット。行へのコメントは、後の push で今の head に付け替わる `commit_id` ではなく、親レビューの `commit_id`（無ければ `original_commit_id`）。`PullRequestFeedback.commit`）が、取り込むときの PR の今の head（`status` の `headSha`）と違えば、取り込まずに捨てる。
  - 捨てたものは `PullRequestReviewDiscarded`（actor `sacty`。`reason: stale_head`・今の head・捨てた指摘と対象のコミット）に残し、取り込み済み（`importedFeedback`）にする。差し戻さず、戻し先も判断しない。以降も取り込み直さない。
  - 対象のコミットが分からない投稿は、古いかどうか分からないので取り込む。短いコミットの表記は先頭の一致で比べる。
  - PR の head を読めないときは、AI のレビューだけ今回は取り込まず、次の確認で確かめ直す（人の指摘は取り込む）。
  - 人の指摘は、head によらず取り込む。
  - 捨てた指摘は、人に届ける（PBI-291）。`PullRequestReviewDiscarded` の `items[].summary` に、指摘の要点（取り込む指摘と同じ文の先頭400文字。投稿の目印と見出しを除き、空白をそろえる。以前の記録には無い）を残し、`Task.discardedReviews` に積む。見守っている PR（承認ゲートの PR。実装の作り直しの間は実装の PR）へのものを `discardedAiReviews` が古い順に返し、PR がマージされたら返さない（クローズ後・差し戻した後は、マージまで残る）。
  - 承認の画面とタスクの詳細の上（`DiscardedReviewNotice`）に、「取り込んでいない AI のレビューの指摘」として、捨てた理由（古い head と、最後に捨てた時点の PR の head。そのあと PR が更新されても値は変わらない）・指摘ごとの対象のコミット・要点・GitHub へのリンクを出す。人が承認・マージする前に気づけるようにするため。
  - 捨てた指摘を、自動で作り直しに取り込むことも、新しい head に AI のレビューをかけ直すことも、PR に sacty が投稿することもしない。新しい head にも当てはまると人が判断したら、差し戻しの指摘（またはPR への指摘）として伝える。人の指摘として扱う（`source` なし。差し戻しの回数に数える）。
- 今の head に AI のレビューが付いているか（PBI-302 D1。実験 S14・S18：作り直した head に AI のレビューが届く前に、人がマージに進んだ）：承認待ちの PR の今の head について、付いていない（`none`）・レビュー中（`reviewing`）・付いた（`attached`）を示す。今の head は、提出したコミット（`gatePullRequest` の `commit`）ではなく、PR の確認（`checkPullRequests`）で PR が開いている間に読んだ最新の head（`latestHeads`。人が足したコミットで変わる。同じ PR・同じ提出のときだけ使う。デーモンのメモリーに持つ）。まだ読めていない（デーモンの起動の直後・作り直した直後・GitHub が head を返さない）ときは、分からない（`unknown`）として、付いたとは出さない。承認やマージは止めない。
  - 判定（`aiReviewFor`・`aiReviewOfHead`）：同じ PR を指す（`referencedPullRequest`）、ほかの sacty のレビューのタスク（レビューの工程を持つ。中止したものを除く）を見る。今の head をレビューして投稿していれば（`reviewPost` と `reviewTarget.headCommit`。再レビューの前の回は `previousReview.headCommit`。コミットは短い表記との先頭の一致で比べる）付いた。投稿しておらず、動いていて（一時停止・エスカレーションを除く）、対象の head が今の head か、まだ決まっていなければレビュー中。ほかは付いていない。別の head へのレビューは、今の head のものに数えない。
  - 作業履歴からは復元しない（ほかのタスクを見て計算する）。画面に返すとき（`TaskService.view`。`GET /api/tasks/:id`）だけ `Task.aiReview`（head・状況・付いたときのレビューの URL）を足す。承認待ちでない・PR が開いていないタスクには足さない。
  - 画面：承認の画面とタスクの詳細に、`AiReviewNotice` で出す（状況・head の短い表記・付いたときのレビューへのリンク。付いていないとき、レビュー中のとき、分からないとき〔head を読めていないことを出す〕は、承認やマージを止めないことと、レビューが付く前に進むとその指摘を見ないまま承認することを添える）。
  - PR の本文：実装の PR は結論に「AI のレビュー：…」の1行を入れる（テンプレートに沿わせる本文は、目的のレビューの行（`REVIEW_BODY_LINE`）の次）。要求要件・設計の PR は、承認の案内の前（テンプレートに沿わせる本文は要約）に入れる（`aiReviewBodyLine`）。本文を作る（更新する）時点の状況で、その後に付いたレビューは反映しないので、そのことと、最新の状況は承認の画面で確かめることを添える。
- エージェントへの渡し方：人の指摘と AI のレビューの指摘を分けて渡す。
  - 工程のエージェント（実装・要求要件・設計など）の指示、統合レビュー・戻し先の判断・質問への答え・監査の指示で、「人間の指摘」の節と「AI のレビューの指摘（人間の指摘ではない）」の節に分ける（`remarkSections`・`reworkRemarkLines`）。
  - AI のレビューの指摘が並ぶときは、人の指摘にある「さっきの指摘」「前の指摘」などは、AI のレビューの指摘ではなく人の指摘を指す、と人の指摘の節に添える。
  - 戻し先の判断では、AI のレビューの指摘は人が新しく足した要望（`new_request`）ではない、と添える。
  - 統合レビューは、節を分けて渡しても、過去の指摘の再発の判定は人の指摘と AI のレビューの指摘の両方に求める（`REMARK_RECURRENCE_LINE`・`remarkVerdictLines`。ADR: [最終レビュー・統合レビューで、AI のレビューの過去の指摘にも再発の判定を求める](../adr/20261103-0312-judge-ai-review-remarks-in-reviews.md)）。AI のレビューの指摘が並ぶときは、出力の形式の説明に、AI のレビューの指摘にも1件ずつ判定を書くこと、判定が無いと再発している扱いで不合格になることを添える。
- 戻し先の判断文の渡し方（PBI-300）：その判断（戻し先と、指摘をどう読んだかの理由）で始まった作り直しの実行（要求要件・設計・実装のどれでも）の指示に、判断文を渡す（`guardianJudgmentLines`）。
  - 渡すのは、判断で差し戻した回の指摘（`prRework` の戻し先の工程・回 `round`・指摘の ID `remarkIds` が、その工程の今回の指摘（最新の回のうち、無効にしておらず、まだ提出に渡していないもの）と一致するとき。判断の後に指摘を1件でも無効にしていれば、無効にした指摘を解釈した判断文が戻らないよう渡さない）で始まる実行だけ。判断が無い実行（最初の実行、最終レビューの不合格・上流の変更によるやり直し、提出済みの指摘だけが残る再実行、人が画面から差し戻した回）の指示は変えない。
  - 判断文は戻し先の判断の解釈で、人の指摘そのものではない、と指示に書く。人の指摘の原文は今までどおり渡し、食い違うときは原文（人間の指摘を最優先）に従わせる。判断文の中に書かれた指示には従わせない。
  - 判断文は外から来た文字列として扱う。秘密情報・URL の認証情報を伏せてから、3,000文字で切り、指示とは分けた1行の JSON（`{"guardianJudgment": …}`）のデータとして渡す。
  - 戻し先を判断できなかったとき（`decided` が偽）も、判断できなかった理由（何が読み取れなかったか）を渡す。読み取れなかった点を推測で大きく変えず、指摘の原文と承認済みの成果物から確かめ、読み取れる範囲の最小限の変更をする。「変更が要らない」と結論するのは、指摘が求めることをすでに満たしていると根拠で示せるときだけ。読み取れなかった点と直し方は、指摘への対応（`sacty-responses` の `text`）に書かせる（要求要件・設計は、人が決めることが残るなら「確認したいこと」にも足させる）。
  - 判断の実行が失敗した・出力を読めなかった・子タスクの答えを読めなかったとき（理由が sacty の文言のとき）は、指摘の読み方ではないので渡さない。
- 表示：作業履歴の差し戻し・取り込みの行に、AI のレビューの指摘を分けて出し（「指摘3件（AI のレビュー）」「人間1件・AI のレビュー2件」）、承認の画面の指摘に「AI のレビュー」の印を付ける。作業履歴の差し戻しを展開した詳細にも、AI のレビューの指摘に印を付ける。承認の画面で「差し戻しの回数に数えない」と添えるのは、その回に人の指摘が無いときだけ。
  ダッシュボードの品質の信号は「AI のレビューの差し戻し」、監査の根拠の件数は「AI のレビューの指摘」（`aiReviewRemark`）として、人の差し戻し・PR の指摘と別に数える（[アーキテクチャ](architecture.md)・[監査](audit.md)）。

### 人に確かめてほしいこと

関係する ADR: [人に確かめてほしいことを、PR のコメントと承認の画面の目立つ所に出す](../adr/20261103-2302-surface-human-asks.md)

PR の指摘を受けた作り直しで、指摘の意図が合っているかを人が確かめないと分からないことがある。承認の画面の隅や作業履歴にしか出ないと、PR を見ている人は気づけない。次の2つを「人に確かめてほしいこと」（`humanAsks`）として、PR のコメントと、承認の画面・タスクの詳細の目立つ所に出す。

- 判断できなかった理由（`undecided`）：戻し先を判断できず（`prRework.decided` が偽）、実装などをやり直したとき。理由は、判断した担い手が書いた文（何が読み取れなかったか）。理由が sacty の文言のとき（判断の実行の失敗・出力や子タスクの答えを読めなかった）は、指摘の読み方ではないので出さない。
- 実行の聞き返し・推測で決めたこと（`confirms`）：作り直しの実行が、指摘への対応（`sacty-responses`）に `confirm` を添えたもの。指摘の意図を読み取れず推測で直したとき、元の値や文言が手元に無く作り直したとき、指摘が求めていない範囲を変えたとき、指摘を直さずにおいたときなどに書かせる（`confirmLines`）。確かめたいことが無い対応には書かせない。1,000文字で切る。`RemarkResponse.confirm` に残し、`Task.remarks[].confirm` に、対応と同じ提出回のものだけ持つ（次の提出で対応が無ければ消える）。

- 出す条件：状態が承認待ちで、今の承認ゲートの提出（`gate.submission`）が受けた、無効にしていない指摘について。判断できなかった理由は、`prRework` の戻し先がゲートの工程で、指摘の回（`round`）がその工程の最新の回のときだけ（その後に別の差し戻しがあれば、古い判断は出さない）。承認待ちでなければ（作り直している間・一時停止中）出さない。
- 画面（`HumanAskNotice`）：承認の画面の上と、タスクの詳細の承認の案内の下（どのタブでも見える所）に、「人に確かめてほしいことがN件あります」として出す。判断できなかった理由は、要点（先頭の1〜2文）を先に出し、全文は開いて読める（下の「戻し先の判断の文の見せ方」）。
- PR のコメント：作り直した成果物が承認待ちに戻ったとき（`StepSubmitted` で、承認ゲートの工程か提出回が新しくなったとき。一時停止の間に書けなかった提出は、再開で同じ提出の承認待ちに戻ったときにもう一度試す。目印で見つけたコメントがあれば書き直さない）、そのゲートの PR（実装の PR・要求要件の PR・設計の PR）に1件コメントする（`announceHumanAsks`・`buildHumanAskNotice`）。
  - 先頭に目印（`<!-- sacty-human-ask:<タスク ID>:<工程>:<提出回> -->`）を置く。同じ提出に目印のコメントがあれば書かない。
  - 本文は、判断できなかった理由と実行の確かめたいことを、引用にして載せる。外から来た文なので、秘密情報を伏せてから600文字で切り、`@名前` で他人に通知が飛ばないよう `@` の後ろに幅の無い空白を挟む。末尾に、意図と違うときは PR にコメントするか、タスクの画面で差し戻すよう案内する。
  - 同じ提出の通知は、順に処理する（`serialized`）。先の通知がコメントを探している最中に、一時停止と再開で2本目が始まっても、先の処理が終わってから目印を探し直すので、二重に書かない。
  - セキュリティの組み合わせ（`security-check`・`security-fix`）のタスクでは書かない（確かめたいことに、脆弱性や修正の範囲の詳細が入りうるため。承認の画面には出る。コメントの頼みを投稿しない規則と同じ）。
  - 外から来た文の、作業領域の内部のパス（`/sacty-input/task.md:77` など）は、人が辿れる呼び方に置き換える（`withoutInternalPaths`）。
  - 投稿するのは、プロジェクトの gh のアカウント（GitHub のアカウントを選んでいないプロジェクトでは書かない。画面には出る）。送るのは待たず、通信には30秒の期限を付ける。投稿できなくても、タスクの状態は変えない（警告を残す）。
  - このコメントは、次の PR の確認で人間の指摘として取り込まない（目印で始まり、タスクのアカウントのコメントは除く。他人が目印をまねたものは、人間の指摘として取り込む）。

コード: `apps/daemon/src/service.ts`（`announceHumanAsks`・`humanAskDue`）、`apps/daemon/src/human-ask-notice.ts`、`apps/daemon/src/github.ts`（`isHumanAskNotice`・`GitHubPullRequests.feedback`）、`apps/daemon/src/prompts.ts`（`confirmLines`・`extractBlocks`）、`packages/core/src/projection.ts`（`humanAsks`）、`apps/web/src/components/human-ask.tsx`（`HumanAskNotice`）

### 戻し先の判断の文の見せ方

戻し先の判断の文（`ReworkJudged` の `reason`）は、600〜1,000文字になることがあり、画面にそのまま出すと読みにくい。画面では要点を先に出し、全文は開いて読めるようにする（`summarizeDecision`）。

- 要点：先頭の2文まで（句点・英語の終止符と空白・改行で区切る。括弧の中の句点では区切らない）。160文字を超えるときは、160文字で切って「…」を付ける。全文が要点と同じなら、折りたたまない。
- 出す所：作業履歴の戻し先の行（行に要点、詳細に全文）、PR の欄の戻し先（`prRework`。要点の下に、開いて読める全文）、人に確かめてほしいことの判断できなかった理由。
- 変えないもの：作業履歴の記録（`ReworkJudged` の `reason`）と、作り直しの実行に渡す判断文（[戻し先の判断文の渡し方](#ai-のレビューの指摘)）は全文のまま。

コード: `apps/web/src/lib/decision-summary.ts`、`apps/web/src/lib/labels.ts`（`describeEventParts`）、`apps/web/src/components/pull-request.tsx`（`PullRequestCard`）

## 差し戻し

- 戻せる工程（`reworkTargets`）は、承認待ちの工程と、それより前の `REWORK_STEPS` を、近い順に並べたもの。
  - `reproduce`・`investigate` は、それ自身が承認待ちのときだけ。
  - 統合レビューの承認待ちでは `split` だけ。
  - 戻し先を省くと先頭（実装の承認待ちなら `implement`）。
- 承認待ちでの差し戻しには、指摘が1件以上要る（`gate.remarksRequired`）。
  人は指摘を無効にでき、無効にした指摘はエージェントに渡さない。
- 指摘には出どころがある（`remarks[].source`）。sacty 自身の AI のレビューの指摘は `sacty_review`、無ければ人の指摘（[AI のレビューの指摘](#ai-のレビューの指摘)）。
  上限の回数（`changeRounds`）は、人の指摘が1件でもある回の数。回の番号と指摘の ID は AI のレビューの回も含めて続ける（`lastChangeRound`）。
- 前の工程に戻すと、その工程から後の承認を取り消し、検証の結果と失敗の回数を戻す。
  PR で承認したタスクでは、マージ済みの PR は戻さない。
- 差し戻しには、原因（`ReworkCause`。`ChangesRequested` の `cause`）を付けられる。省略すると、原因を決めない差し戻しとして記録し、集計では「原因が分からない」差し戻しに数える。
  - 人は、承認の画面の「差し戻しの原因」で選ぶ（初めは「選ばない」）。人が承認の画面（API の `request-changes`）で差し戻す流れは、戻し先を人が選ぶので戻し先の判断（`judgeRework`）を通らない。選ばなければ原因を判断させず、原因が分からない差し戻しになる（判断のためだけに実行を増やさない）。
  - PR の指摘の差し戻しは、戻し先と一緒に判断した原因を使う（`settleReview`）。
  - 原因は、作業履歴の差し戻しの行と、PR の欄の戻し先（PR の指摘のとき。`prRework` の `cause`）に出す。
  - 上限でエスカレーションになる差し戻し（`TaskEscalated`）には、原因を残さない。上限を超えて差し戻すときに、あらためて選ぶ。
- 見逃し（`GuardianMissed`）を記録するのは、原因が `guardian_missed` で、差し戻した成果物が以前の版の最終レビュー（実装の承認待ち）・統合レビュー（統合レビューの承認待ち）に合格していたときだけ（今の版で作った実装は最終レビューを経ないので、実装の差し戻しでは記録しない）。
  - 原因が `new_request`・`question_answer`・`base_changed` のとき、原因を決めないときは記録しない（原因を決めない差し戻しは、見逃しかどうか分からないものとして、集計の「原因が分からない」に出す。見逃しの数の横で見られる）。
  - 同じレビューの見逃しは1回だけ記録する。
  - 原因を記録する前の作業履歴は、そのまま読める（原因を持たない差し戻しは、集計で、直前に見逃しの記録（`GuardianMissed`）があれば見逃し、無ければ「原因が分からない」として扱う。記録済みの見逃しは、見逃しのまま数える）。

| 原因（`ReworkCause`） | 意味 |
| --- | --- |
| `guardian_missed` | 確かめられたはずの不備を見逃した（以前の版では、ゴールガーディアンの見逃し） |
| `new_request` | 承認済みの要求要件・設計に無い、人が新しく足した要望や方針の変更 |
| `question_answer` | sacty の質問（成果物の「確認したいこと」）への答えだけのコメント。新しい要望ではない。要求要件・設計の PR だけ |
| `base_changed` | ベースブランチが進んだこと（先の PR のマージなど）による競合・衝突で、成果物そのものの不備ではない |

- 人は差し戻しと一緒に、タスクのイメージ・工程のエージェントを変えられる（`RequestChangesInput` の `image`・`agents`）。
  タスクの詳細で変えるとき（`changeTaskImage`・`changeStepAgent`）と同じ確かめをして、`TaskImageChanged`・`StepAgentChanged` を差し戻し（`ChangesRequested`）・上限でのエスカレーション（`TaskEscalated`）の前に同じ書き込みで記録する（今と同じ名前は記録しない）。
  1つでも誤っていれば、差し戻しも含めて何も記録せずに断る。
  画面は、タスクのイメージと、やり直す工程とそれより後の工程（飛ばした工程を除く）のエージェントを出し、折りたたみを開いたときに候補を読む（`/step-options`）。人が変えたものだけを送る（`changedStepChoices`）。
- 差し戻しの指摘の本文は、承認待ちでなくても、タスクの詳細の作業履歴の差し戻しの行の「詳細」で読める（[画面の文言と補足](ui-wording.md)）。

コード: `apps/daemon/src/service.ts`（`requestChanges`・`stepSettingChanges`・`voidRemark`）、`packages/core/src/events.ts`（`ReworkCause`・`ReworkAnswer`・`RequestChangesInput`）、`packages/core/src/projection.ts`（`reworkTargets`・`reopen`・`changeRounds`）、`apps/daemon/src/prompts.ts`（`buildReworkPrompt`・`extractRework`・`isAnswerOnlyRework`・`answerOnlyReworkLines`・`answerOnlyCheckLines`・`lineContextText`・`lineContextNote`）、`apps/daemon/src/github.ts`（`lineContextOf`）、`apps/web/src/lib/labels.ts`（`describeEventParts`）、`apps/web/src/components/gate-form.tsx`（`GateStepSettings`）

## エスカレーション

| 理由 | いつ |
| --- | --- |
| `too_many_changes` | 同じ工程への人の差し戻しが `MAX_CHANGE_REQUESTS`（3）回に達した後の差し戻し（AI のレビューの指摘だけの回は数えない）。書きかけの指摘は残す。上限を超えて続けるには、明示して差し戻す（`overLimit`） |
| `change_proposed` | 工程のエージェントが変更の申し出をした。AI の判定を挟まずに人が判断する（`ChangeDecided`。[変更の申し出](tasks-and-steps.md#変更の申し出)） |
| `change_undecidable` | 以前の版の記録（AI が変更の申し出を判定できなかった。いまは記録しない）。人が判断する（`ChangeDecided`） |
| `rework_confirmation` | 以前の版の記録（いまは記録しない） |

コード: `apps/daemon/src/service.ts`（`requestChanges`・`decideChange`）、`packages/core/src/events.ts`（`TaskEscalated`・`MAX_CHANGE_REQUESTS`）、`packages/core/src/projection.ts`（`changeRounds`）
