# Tasks and steps

A task proceeds as a sequence of steps (Investigation, Requirements, Design, Implementation, and so on). The Orchestrator chooses which combination of steps (plan) to use when the task starts (if a person specified a plan when creating the task, that plan is used). Before that, the information gatherer collects and narrows down the information related to the task and gives its summary to the Orchestrator, every step, and the runs that judge (deciding where to send PR comments back to, Integration review) ("Information gathering" below). Agents run the steps, and people decide only at approval steps (approval gates).

When a step agent requests a change to approved requirements or design, a person decides without an AI judging it, except that requests authorized by a resume note are accepted automatically ("Change requests" below). Where PR comments are sent back to is decided from the review child task's answer when all the comments were posted in the last round of the PR's review child task (AI review comments), and otherwise (when a person's comment, a comment from another review task or an earlier round, or a comment of an unknown round is included) by the agent of the PR's step ([Importing PR comments](approval.en.md#importing-pr-comments)).

Approval and Request changes are in [Approval and request changes](approval.en.md); Task split and Integration review are in [Task split and integration review](split-and-integrate.en.md).

## How tasks are created

`start` in `TaskCreated` records where the task came from.

| `start` | How it was created |
| --- | --- |
| `sacty` | Created in the web UI (the older `ticket` is also read as `sacty`) |
| `github_issue`, `github_pull_request` | Intake of a GitHub Issue or PR ([Ticket intake](intake.en.md)) |
| `jira` | Intake of a JIRA ticket |
| `deployment` | A task to fix a failure found by the after-merge watch (`fix` holds the original task, the kind, the marker, and the level. [After-merge watch](deployment-watch.en.md)) |
| `split` | A child task of Task split (`parent` holds the parent's ID and the child tasks that must finish first, `dependsOn`) |
| `audit` | A task created by adopting a fix proposal from an audit (`auditFix` holds the original task and the proposal. [Audit of completed tasks](audit.en.md#causes-and-proposals)) |
| `schedule` | Created by a scheduled task (`schedule` holds the scheduled task's ID and the scheduled time. [Scheduled tasks](scheduled-tasks.en.md)) |
| `security` | A fix task created from a category of an approved security check report (`securityFix` holds the original task and the category. "Security check and security fix" below) |

- A PR-review-only task has `source.review` (`requested` or `label`; `sacty` for the review child task of a PR sacty created, and for a sacty PR taken in from the label by an older version).
  A review child task also has `reviewOf` (the parent's ID and the step that opened the PR; [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
- When creating a task in the web UI, if no repository is specified (`repo: null`), or the repository is omitted and the project's targets are not exactly one repository, the task becomes a task without a repository (`noRepo`). It cannot be created in a project with no targets (`task.repositoryMissing`).
- The API accepts one or more project targets in `repos`. It normalizes names and removes duplicates: one is treated as `repo`, while 2–10 are recorded with `noRepo` and the list in `TaskCreated`. An empty array, a target outside the project, more than 10 distinct targets, or a simultaneous `repo` is rejected. The projection retains the list; old activity remains readable. Orchestrator and human choices are restricted to the list and checked against current targets. If a specified repository cannot be verified, the task stops with its name and checks again on resume.
- The create dialog can add or remove up to 10 (`REPOSITORY_FIELDS_MAX`) repository fields and sends the non-empty values.
  - At the limit, "Add repository" is disabled and the reason (up to 10) is shown next to the button.
  - Adding a field moves the focus to the new field; removing one moves it to the field that took its place (the previous field when the last one was removed) (`focusAfterRemove`).
  - The initial value used when there is exactly one suggestion is put into the first field, if a person has not touched it, when the suggestions arrive. Adding or removing fields alone does not put it in again (removing the field that held the initial value does not bring it back in the remaining field).
  - When the same repository (the same `repoKey`; empty fields do not count) is in two or more fields, the dialog names the later fields (`duplicateRepositoryFields`). The values sent are not changed; the daemon removes the duplicates.
  - While a template is chosen, only the first field is shown, and it is omitted when empty. The added fields and their values are kept and shown again after switching back to "None".
- The "Create task" button in the web UI reads only the list's project (the ID in the URL) before it appears (it does not appear for a project that does not exist). The repository suggestions (the daemon's `GET /api/projects/:id/repositories`; org targets are read with `gh`) are read when the create dialog opens, through the web route `GET /projects/:id/repositories` (read again on every open; a late result from an earlier open is dropped). Rendering the task list and its automatic refresh do not read them. The dialog shows that the suggestions are loading, could not be read, or are empty, and in every state the repository can be typed and the task created. For an org that could not be read, it shows the reason. Projects without targets do not read them.
- The initial budget cap is `budget.default_per_task_usd` (default 1 US dollar).
- The status values are in the "Projection" table of [Activity log](event-log.en.md). There is no "completed" status; a task is complete when every step is `done` or `skip` (`isCompleted`). However, a PR review task is not complete, even with every step finished, while it watches the PR for changes after posting its review (`reviewWatching`) (`isDone`, `isFinished`; [Watching the PR after posting](#watching-the-pr-after-posting)).

### Task templates

If the body of `POST /api/tasks` has `template`, the task is created from a template (`CreateTemplateTaskInput`). The templates are `sacty-setup` (Sacty setup), `security-check` (Security check), and `docs-setup` (Docs setup).

- Only `template`, `projectId`, and `repo` are accepted. Passing `title`, `body`, or any other item gives 400 (sacty decides the title and description). An unknown template, an empty `repo`, or `repo: null` also gives 400.
- The target repository is required. If omitted and the project's targets are exactly one repository, that one is used. Otherwise the task is not created (`task.templateRepositoryRequired`, 409). A repository outside the targets is not accepted, as with ordinary tasks (`task.repositoryUnknown`).
- `template` is recorded in `TaskCreated` (`start` is `sacty`, and `repo` is normalized to the registered name, as with ordinary tasks). It remains in the projection's `Task.template`.
- The title of `sacty-setup` is `Sacty セットアップ（<owner>/<name>）`, and the description (goal) is the text decided by `templateTask`. After creation, as with an ordinary task, the Orchestrator chooses the plan (the template does not decide the steps).
- The title of `security-check` is `セキュリティチェック（<owner>/<name>）`, and the description states the categories to check and that a fix task can be created for each category of the approved report. The `plan` of `TaskCreated` is `security-check` (as with a plan specified at creation, the Orchestrator does not choose the plan again). How to check and the answer format are given in the step's prompt ("Security check and security fix" below).
- The goal of `sacty-setup` is to check the agent configuration needed to handle the target repository with sacty, and to open a PR that fills in what is missing. The text does not assume any particular language or tool. It checks and fills in the following four items.
  1. Instructions for agents (AGENTS.md, CLAUDE.md, and so on; not maintained in two places)
  2. How to run tests (the command and prerequisites; whether they match the current configuration). If the repository has no tests yet, the agent writes that there are none and how to check changes, and does not add a new language or test framework (that is a separate task)
  3. Services needed for tests (how to start them and where to connect; if none are needed, say so)
  4. For repositories with CI/CD (even if they do not deploy), the after-merge watch skill `deployment-observer`. If there is no CI/CD, it is not created (the after-merge watch step is skipped). The original goes in `.agents/skills/deployment-observer/SKILL.md`, and `.claude/skills/deployment-observer` is a relative symbolic link to `../../.agents/skills/deployment-observer`. It has the agent write the front matter (`name`, `description`) and a reference on how to check CI/CD (`references/ci.md`: which workflows and checks verify what, failures that can be ignored, and how to read results and logs). If the repository deploys, the agent writes how to tell that a deployment finished, how to check it, how to connect, and what counts as an error; if it does not deploy, that the deployment check is skipped (`skipped` with a reason). It also writes the promises not to change anything, not to reveal secrets, not to wait long, and to answer `unknown` when it cannot judge, and the shape of the JSON answer under the heading `sacty-deployment` (the results of the CI/CD check and the deployment check). The location, link target, reference, and heading are built from the after-merge watch's `DEPLOYMENT_SKILL_PATHS`, `CI_REFERENCE`, and `DEPLOYMENT_HEADING` ([After-merge watch](deployment-watch.en.md)).
- The goal also says that if everything is in place and no change is needed, the task ends with Investigation only, without a PR, and leaves the check result for each item (if the Orchestrator chooses `investigate`, the task completes when the investigation result is approved in the web UI). If it turns out after the steps have run that no change is needed, the agent is asked to leave the files unchanged and write the check results and reasons in the implementation notes (no PR is opened; a person checks it and the task completes without changes. [Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).
- The title of `docs-setup` is `ドキュメント構築（<owner>/<name>）`, and the description (goal) is the text decided by `templateTask`. As with `sacty-setup`, the Orchestrator chooses the plan (the goal says that for a large repository it may choose `split`, with one child task per area). The goal is to open a PR that builds, from the target repository's code, the docs that agents read before working, and skills to look them up and update them. The text does not assume any particular language or tool.
  1. Take stock of the existing docs (a table of location, content, whether it matches the code, and how to treat it). Existing docs are not deleted, moved, or rewritten; they are linked. Only mismatches that can be confirmed in the code are fixed, minimally; large rewrites stay as proposals. If the location, format, and language are already decided, they are followed; otherwise the docs go in `docs/` with `docs/README.md` as the index.
  2. From the code, write only what cannot be learned by reading a little code (purpose and terms, overall structure and dependency direction, main flows, data, external connections, conventions and invariants). The dependency direction of the overall structure, and the order and branches of the main flows, are also shown in figures. How to build and test is not written (`sacty-setup` covers it). The agent writes, at the top of each new doc, its status (`AI 生成・未レビュー` or `レビュー済み`; `DOCS_STATUS`) and the matching code, and marks everything this task creates as `AI 生成・未レビュー`. What cannot be confirmed is written as `（未確認）` and listed in the implementation notes for a person to confirm (sacty puts the implementation notes in the PR body; [PR body and PR template](approval.en.md#pr-body-and-pr-template)). The docs are read by people who were not there and by agents, neither of whom knows the background, so the agent writes at the top of each doc what it is about and before which work to read it, starts each section with its main point, and gives the mapping between code names and domain terms where they first appear. Figures are used only for relationships that are hard to read in prose (dependency direction, the order a flow passes through, state transitions), in the format of the figures in the repository's existing docs (or, when there are none or the same format cannot be produced, a format written as text inside Markdown). The main point of a figure is also written in the text. The detailed rules follow the default skill `writing` when it is present, and the repository's writing rules take precedence ([Context](context.en.md#default-writing-skill)).
  3. Create the skills `docs-lookup` (look up) and `docs-update` (update) (`DOCS_SKILLS`). They follow the same placement rule as `deployment-observer` (the original in `.agents/skills/<name>/SKILL.md`, and `.claude/skills/<name>` as a relative symbolic link to the original), built from `DEPLOYMENT_SKILL_PATHS`. `docs-lookup` says to check unreviewed docs against the code before using them and to treat the code as correct when they disagree; `docs-update` says to update the docs and the index in the same PR when the code changes (and the figures, when the structure or flow they show changes), and to mark a doc `レビュー済み` only when a person has checked it.
- To keep the review light, the goal of `docs-setup` limits the first PR to the stock-taking results, the index, the overall structure, the two skills, and pointers from the instructions for agents, and lists the remaining items in the index as not yet written. The implementation notes carry the stock-taking table and list what is `（未確認）` as questions that can be answered briefly, and the agent is asked not to write the PR body itself. The code is not changed. Ending with Investigation only when nothing needs to change, and what happens when that turns out after the steps have run, are the same as `sacty-setup`.

Code: `packages/core/src/events.ts` (`TaskTemplate`, `CreateTemplateTaskInput`, `TaskCreated`), `apps/daemon/src/service.ts` (`createTask`, `prepareTemplateTask`, `projectRepository`), `apps/daemon/src/task-templates.ts` (`templateTask`, `DOCS_SKILLS`, `DOCS_STATUS`), `apps/daemon/src/deployment.ts` (`DEPLOYMENT_SKILL_PATHS`, `CI_REFERENCE`, `DEPLOYMENT_HEADING`)

## Steps

| Key | Step | What it does |
| --- | --- | --- |
| `investigate` | Investigation | Examines the code and reports |
| `review` | Review | Reviews an existing PR and posts to the PR |
| `requirements` | Requirements | Writes the requirements |
| `design` | Design | Writes the design and test viewpoints |
| `split` | Task split | Creates child tasks and waits for them to finish |
| `integrate` | Integration review | Checks whether the child tasks' results meet the parent's requirements |
| `reproduce` | Reproduce | Writes a test that reproduces the bug (fails) |
| `implement` | Implementation | Implements. When the Implementation step finishes, sacty opens the implementation PR as a draft and waits for approval; once the PR review child task reports no findings, sacty removes the draft and waits for a person's approval (merging the PR). When a re-judged round leaves only suggestions and all of them are declined, it removes the draft with the verdict still "suggestions" after an assessment-only run (`reason: suggestions_declined`; PBI-440; see [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)) |
| `deployment` | After-merge watch | After the implementation PR is merged, waits for CI/CD, checks as the skill says, and registers a fix task on failure (no human approval. [After-merge watch](deployment-watch.en.md)) |
| `document` | Document | Creates or edits a Markdown draft and waits for approval in the web UI |
| `operation` | Operation | Performs the requested external change once and submits evidence for result approval |

The steps fall into the following categories.

- Steps with an approval gate (`GATED_STEPS`): `investigate`, `requirements`, `design`, `integrate`, `implement`, `document`, `operation`. However, Investigation at the start of a security fix (`security-fix`) (preliminary investigation) moves on to the next step without approval (`StepCompleted`). Only Investigation in a task whose purpose is investigation (the last step is `investigate`) is approved. When the agent's run ends, Implementation waits for approval after sacty opens the implementation PR as a draft ("The flow without the final review" below). Once the PR review child task reports no findings, sacty removes the draft, and a person approves by merging the PR.
- Steps that can be redone through Request changes (`REWORK_STEPS`): `investigate`, `reproduce`, `requirements`, `design`, `implement`, `document`.
- Steps that need a repository (`REPO_STEPS`): `implement`, `reproduce`, `review`.
- Steps the Orchestrator can select to use docker compose services (`SERVICE_STEPS`): `investigate` (only for bug investigation), `reproduce`, `implement`. Review child tasks for implementation PRs opened by sacty also start services based on the implementation record ([Services](services.en.md)).
- Steps that can be exported (`EXPORT_STEPS`): `investigate` (only when it is the last step), `requirements`, `design`, `document`.
- Steps that are not run (not in `EXECUTABLE_STEPS`): `deployment`. After the previous step is approved, the task becomes idle and sacty advances it in the PR check. If the target repository has no skill, the step is skipped when the steps are chosen (`skip`. [After-merge watch](deployment-watch.en.md)). When moving to the next step, `skip` steps are passed over.
- Steps that the step review can skip (`SKIPPABLE_STEPS`): `requirements`, `design`, `reproduce`. Only when the plan has an implementation ("Step review" below).

Code: `packages/core/src/events.ts` (`StepKey`, `GATED_STEPS`, `REWORK_STEPS`, `EXPORT_STEPS`, `exportSteps`), `packages/core/src/projection.ts` (`investigationIsGoal`), `apps/daemon/src/service.ts` (`REPO_STEPS`, `submitEvents`), `apps/daemon/src/prompts.ts` (`SERVICE_STEPS`)

For a task with multiple specified repositories, the Investigation, Requirements, Design, and Split steps (`REPOSITORY_COPY_STEPS`) pass copies of the code to the agent. Before a repository is chosen, the latest default branches are placed in the workspace; afterward, the selected repository is at its starting commit in the workspace and the latest default branches of the others are mounted read-only. The instructions list each repository, location, branch, and commit, ask requirements to identify their repositories, and ask the design to describe implementation per repository. The instructions for the investigation have the agent read the code in the copies even before a repository is chosen. If preparation fails, sacty records the repository and reason, pauses, and retries on resume. Remote `ls-remote` and `fetch` operations for these copies time out after 120 seconds. These operations and clone are stopped on pause or cancellation.

Code: `apps/daemon/src/service.ts` (`runNextInner`, `copiesRepositories`, `REPOSITORY_COPY_STEPS`), `apps/daemon/src/prompts.ts` (`buildPrompt`, `codeLines`)

### Form of the result of a task whose goal is investigation

- The instructions of a task whose goal is investigation have it follow the form of the result (headings, sections, tables, order of items, length, and so on) when the task specifies one.
- When none is specified, it writes the conclusion, the evidence (file and line), the related places and impact, and the open questions, in that order.
- In any form, it adds the file and line to the evidence, separates guesses from facts confirmed in the code, and writes what cannot be decided from the code separately.
- It outputs the result as the body (Markdown).
  Even when a form such as a spreadsheet or CSV is specified, files in the workspace are not kept, so it writes them as tables or code blocks in the body.
- JSON outputs that the instructions require (security check findings, comment requests, and so on) are added regardless of the specified form.

### Length of deliverables that people read

- Among the deliverables people read, the instructions of the steps for requirements, designs, and the investigation result of a task whose goal is investigation state a rule that keeps the first draft minimal (`minimalDraftLines`).
  The preliminary investigation is not read by people, so it does not get this rule.
  For the draft of a document (`document`), the amount to write is decided by the reader (the "document draft" item in this section).
  - The agent assumes that the reader has the background (tacit knowledge), and writes only what the reader needs to decide and work. When in doubt, it leaves the item out.
  - The agent does not write what the reader already knows (restating the request, background, general knowledge, explanations of terms), what the request does not ask for, alternatives it did not take, repeats, or a closing summary.
    Each kind of deliverable adds what not to write (for requirements and designs, the `readerLoadLines` item; for investigation results, the steps taken and code explanations that do not support the conclusion).
  - Each item is one or two lines, and a reason is added in one line only when needed.
  - When a person sends the deliverable back asking for more detail, the agent adds detail only where asked and keeps the rest short. Text added at a person's request is not removed in later revisions.
- Requirements and designs are also written as follows (`readerLoadLines`).
  - The agent does not write explanations of existing code or mechanisms, behavior that existing mechanisms already guarantee and this change does not alter, unwanted behavior, boundaries, or non-functional concerns that this change cannot newly cause, or "out of scope" sections for viewpoints that do not apply.
  - The agent puts three sections, in this order, at the start of the deliverable and writes the details after them, so that a person can first check that the scope is as intended (PBI-340).
    - "スコープ" (scope): what the change achieves (one to three sentences), what is in scope (what this change changes), and what is out of scope (what a reader may expect to be included but this change does not do). Both are always written; if nothing is out of scope, the agent writes "対象外：なし" (none out of scope) so that it can be told apart from an oversight. Viewpoints that do not apply are not listed as out of scope.
    - "確認したいこと" (questions): what a person must decide before it can be settled. Split into must and should; each states the question, a recommended answer, its reason, and the concrete concern if the work goes ahead with the recommended answer unconfirmed (what goes wrong, for whom, and how). "なし" if there are none.
      - must: if the answer later turns out different, the work done until then is wasted. No limit on the number. A decision about the purpose of the request (how far, and in what priority, to achieve it; what the requester most wants to decide) goes here, not in should.
      - should: if the answer later turns out different, extra work is needed. Up to 5 (`SHOULD_QUESTIONS_MAX`).
      - Order: from what the requester most wants to decide (what bears directly on the purpose of the request). What is easily settled by rules or conventions does not come first. The recommended answer leans the way the request intends.
    - "既定で決めたこと" (decided by default): among what the request does not say but the agent decided from the existing code, rules, and conventions, only what a person may disagree with. Up to 5 (`DECISIONS_MAX`). Simply following the existing way is not listed. When the should questions exceed the limit, the less important ones are decided with the recommended answer and moved here.
    - A default that can harm the requester (cannot be undone, loses something, makes something unusable, costs more effort or money, or works against the intent of the request) and a decision about the purpose of the request are not put in "既定で決めたこと"; they go in "確認したいこと". When the should questions exceed the limit, these are not moved to the defaults; the ones that do less harm are.
  - The first Requirements run is given the Orchestrator's reason for keeping Requirements (`reason` of `StepsChosen`, `Task.stepsChoice`) as JSON data separate from the instructions (`orchestratorReason`) (`keepRequirementsReasonLines`; PBI-302 B5). Secrets are hidden and it is cut at 3000 characters. It is not given when there is no reason (a person specified the plan), when it could not decide and fell back to the standard plan, when there is a previous version (a rework run), to a task that does not go through Requirements, or to other steps such as Design.
    For each point the reason gives as a reason for keeping Requirements: if it cannot be decided without asking a person, it goes under "確認したいこと"; if the acceptance criteria, the existing code, or documents settle it, the run writes what it decided and why it does not ask, one per line, as "確認しないと決めたこと" at the end of the "確認したいこと" section. It must not drop a point silently. If it finds something else a person should confirm, it goes under "確認したいこと" too.
  - The target length of the whole deliverable is 25 lines for a small change and about 65 lines even for a large change (`DRAFT_LINES`, including the scope section at the start; JSON blocks with a fixed format are not counted).
  - The body (the whole output except the JSON blocks with a fixed format; it becomes the approval screen and the PR file as it is) has only the deliverable itself (`deliverableBodyLines`).
    - The agent does not write a report of the work's progress, steps, or results, an explanation of how this version differs from the previous one, a report of how it handled a person's remark, a PR comment, or a note added when resuming (the handling of a remark that has an ID goes in the `text` of the `sacty-responses` JSON, with whether it was addressed or declined for a reason in `status`; sacty replies on the PR about remarks imported from the PR: [Replies about how remarks were handled](approval.en.md#replies-about-how-remarks-were-handled); for comments without an ID, that is, comments of a taken-over PR, it does not write what it handled and writes only those it does not handle, as a decision for the person under "確認したいこと", with the comment and the reason; what it wants a person to check or guessed is also written in the response's `confirm`, and the approval screen and a PR comment show it: [Things for a person to check](approval.en.md#things-for-a-person-to-check)), or notes and instructions aimed at agents or sacty, or task and agent IDs, anywhere in the body, including after a `---` rule or at the end.
    - IDs that the agent assigns in the body, such as for requirements and acceptance criteria, run from 1 with no gaps in the first submission. When an item is removed on a send-back, the IDs are not closed up (remarks and approved documents point to them by ID); the row is kept like "R-5（削除：理由）" so that the reason for the gap is clear. The rule does not apply to IDs that sacty assigns (the `TV-n` of test viewpoints are renumbered in the order of the JSON array): a test viewpoint to remove is dropped from the array, and no row for a removed one is made.
    - An item that refers to another document (another task's requirements, a ticket, a PR, and so on) does not only refer to it; it adds what the referenced content asks for in one line.
    - The output starts with the deliverable's first heading; no preamble or work report goes before it.
    - Before submitting, the agent rereads the body from start to end and checks that none of the three above remains.
    - The instructions alone did not keep work reports out (PBI-302 C1; experiments S14 and S16, r5: a lead such as "要求要件を直しました。セルフレビューは…通りました" in the last message became the deliverable as it was), so sacty removes them from the submitted output (`withoutWorkReport`). It removes only paragraphs that contain a report word ("〜ました" or "〜ませんでした" that says what the writer did, such as "直しました", "足しました", or "反映しました", but not one that states background, such as "廃止されました" or "起きました"; "セルフレビュー", "コミット・プッシュ", or a remark ID), and only from the paragraphs before the first heading and from the part after the last `---` rule that has no heading. After the rule, the rule goes too, and only when every paragraph is a report. Sentences inside the body are not changed by even one character, and the inside of code blocks (both fenced and indented) is not read (a code block before the first heading or after the rule is not removed even when it contains a report word, and a `#` or `---` inside it is not read as a heading or a rule). An output with no heading is left as it is. The body after the removal is what the approval screen, the PR file, and the next step's input use. A report mixed into the middle of the body cannot be removed, so detecting and fixing it is done by viewpoints D-6 and D-10 in the self-review of the next section.
- For a document draft (`document`), the amount to write is decided by whether the reader knows the background of the matter (`documentDraftLines`). The first draft is not kept minimal across the board.
  - Before writing, the agent decides the reader and what the reader will be able to do after reading (set it up, operate it, decide, share, and so on). If the task does not say, it decides from the kind of draft and the export destination.
  - For a reader who knows the background (the requester or people involved in the matter reading a report, minutes, a rough draft, and so on), the agent writes minimally. It does not write what the reader already knows (restating the request, background, general knowledge, explanations of terms), and leaves an item out when in doubt.
  - For a reader who does not know the background (someone who was not there reading later: a user guide, a procedure, a README, an operations document, and so on), the agent writes, without leaving anything out, what the reader needs to achieve their goal. Terms and prerequisites the reader does not know are written as needed information.
    - The first few lines make clear what the document is, who it is for, and what is needed first (environment, permissions, documents to read first).
    - Sections follow the order in which the reader proceeds (prepare, start, use, when in trouble), with the normal case first and exceptions and detailed conditions after.
    - Each section starts with its main point in one or two sentences (not an announcement such as "This section explains ...").
    - What the reader does in order is written as numbered steps, with what is needed first (tools, permissions, where to run) before the steps. A step with a visible result states the result, and the end says how to check that it worked. Commands and settings are written so that they can be copied and used as they are.
    - Only the current state is written. History ("as before", "previously") and references by position ("below", "above") are not written.
  - For either reader, the agent does not write mechanisms or history unrelated to the reader's goal, what the request does not ask for, alternatives it did not take (except in a draft that records a comparison or a decision), repeats, or a closing summary.
  - Information that lines up goes in lists and tables, and figures and images are used only where they convey something faster than prose.
    - Only relationships such as structure, flow, and state transitions become figures; steps that just line up in one row, and rearrangements of the text, do not.
    - When the agent outputs a draft (it does not write externally directly), it cannot attach image files (only the text of the draft reaches the approval screen and the export; `EXPORT_FILE`). A figure is written as text inside the draft (such as Mermaid), and only when the agent knows that the export destination renders it. When it does not know, or the destination does not render it, there is no figure and the relationship is written as a list or a table (the Markdown on sacty's screens does not draw text-based figures).
    - When writing externally directly, images may be used only when they can be placed at that destination.
    - When an image (including a screenshot) cannot be provided, the agent does not pretend that it exists. It does not reference an image that does not exist, writes the screen's name and what to look at in words, and collects the places that need an image under the unconfirmed items at the end of the draft.
  - The detailed rules follow the default skill `writing` ("deciding the kind of text" in `references/documents.md`, and `references/figures.md`) when it is present ([Context](context.en.md#default-writing-skill)).
  - When a person sends the draft back asking for more or less detail, the agent changes only what was asked for and keeps the rest. Text added at a person's request is not removed in later fixes.
- The design has only the sections, among structure, data, flow, behavior on errors, and impact, that this change has something to say about. The test viewpoints cover all acceptance criteria and include the unwanted behavior and boundary values that this change can newly cause.
  A viewpoint for a change only to documents, comments or wording has what should be written as its expected result, and the implementation is checked in the diff (it is not a viewpoint that checks that a file exists or can be read; the requirements and design files sacty places are not viewpoints).
  A viewpoint that writes or changes a document of instructions for agents (a skill's SKILL.md and references, AGENTS.md, CLAUDE.md, rules, prompt text, and so on; `AGENT_INSTRUCTIONS`) has what the document should say (steps, conditions, rules) as its expected result, not how the agent behaves (it is not a viewpoint checked by starting an agent).
  The number of viewpoints is only what is needed to check the acceptance criteria, and each viewpoint is written in one sentence.
- The three sections at the start stay in the deliverable's body and appear on the approval screen and in the PR as they are (sacty does not extract them to show them separately). On a send-back, `scopeIsWritten` reads the scope section at the start of the previous draft and decides from whether it has in-scope and out-of-scope label lines (such as "対象外：なし"; "対象外" inside an explanatory sentence does not count) whether to give the exception to add, move, or complete the scope ([Approval and request changes](approval.en.md)).

### Revising requirements and designs after changes are requested

- When requirements or a design are sent back, the instructions (`reworkLines`) give the previous draft and all valid remarks, and tell the agent to start from the previous draft and rewrite only the parts the remarks concern. The agent does not rewrite from scratch.
  - It rewrites only what the current remarks (the valid remarks of the latest round of changes requested for that step) concern, and what becomes inconsistent because of that change. Sections, items, and table rows unrelated to the remarks are kept word for word (no polishing of wording, no reordering, no summarizing, no additions). However, content the body must not hold (such as a report of the work) is removed even from unrelated places when it remains in the previous draft.
  - The handling of remarks from earlier rounds, and text added at a person's request, are already in the previous draft, so the agent does not undo them.
  - When a remark spans several sections, the agent fixes every section it concerns. When a remark changes the direction of the deliverable (purpose, scope, approach), the agent fixes what concerns the direction throughout and keeps what does not.
  - The quality bar is the same as the first draft: the "スコープ", "確認したいこと", and "既定で決めたこと" sections at the start (if the previous draft does not start with a scope section that has in-scope and out-of-scope lines, `scopeIsWritten`, the agent is told, as an exception to keeping unrelated sections as they are, to add it or move it to the start, add any missing line, and reorder), the required sections, and the target length, plus the EARS format and IDs for requirements (IDs are not reassigned, and a removed ID is not reused), and the choice of sections and how test viewpoints are written for designs. For a remark that answers a question, the agent reflects the answer where it applies, removes that item from "確認したいこと", and adds any new thing a person must decide that the change causes.
  - The agent outputs the whole deliverable again (not only the changed parts). The report of how each remark was handled is still required. For a design, all test viewpoints are output again as before (sacty reassigns the IDs).
- When the previous draft is empty (unreadable), it cannot be the base, so the agent rewrites to handle every remark. The self-review is then the normal one (see "Self-review before submitting" below).
- Instructions for a redo without remarks, or without current remarks (for example, a design rebuilt because the requirements changed, even when remarks from past rounds remain, as long as all of them were handled), do not get this section. The current remarks are the valid remarks of the latest round of changes requested for that step that have not yet been given to a submission of that step (no `submittedIn`; whether the remark was answered does not matter) (`currentRemarks`). `submittedIn` is the submission number that `AgentRunCompleted` of the step sets on the remarks it was given, even when the submission lacks the answers.
- The self-review of a revision (`partialReworkReviewLines`) narrows the scope and the number of rounds. The agent makes the judgment, and sacty records the number of rounds (`rounds`).
  - When the self-review of the previous submission did not pass (`passed` is false) or has no record (including after a person edited the document), findings left from it may lie outside the current difference, so the way of fixing stays narrowed but the self-review is the normal one over the whole deliverable (`reviewRework`).
  - From the first review, the scope is the difference from the previous draft and the existing parts that difference directly requires (the previous draft passed self-review when it was submitted, and a person has read it). Only when a remark changes the direction is the scope the whole deliverable.
  - A small remark is one where the places to fix for the current remarks are at most 2 (`SMALL_REMARK_PLACES_MAX`; a question item in "確認したいこと" and the place that reflects its answer count as one place) and the direction does not change (for example, reflecting the answer to a question, or correcting the wording or value of one requirement). The round limit is 2 including the first (`SMALL_REMARK_REVIEW_ROUNDS_MAX`). If the first review has no `must`, the agent submits at that point.
  - For a remark that is not small (more than 2 places to fix, or the direction changes), and when in doubt, the round limit is the normal one (up to 5).
  - The agent writes which case it took at the start of the report's `summary`.
- The instructions for revising Implementation, Document, and Investigation do not get this section.
- If a person merges the PR of that step while Requirements or Design is being revised (after a rejection, imported PR comments, and so on), the revision (the run and the PR update) is stopped and the merge is taken as the approval of the submission that was waiting for approval. The revision's result is not used, and no new PR is created ([Merging during a rework of a step PR](approval.en.md#merging-during-a-rework-of-a-step-pr)).

### Self-review before submitting

- The instructions of the Requirements, Design, Implementation, and Document steps (`SELF_REVIEW_STEPS`; Implementation includes bug fixes and tasks without tests) tell the agent to self-review with the `self-review` flow of the default skill `review-dispatch` before submitting, and to repeat fixing and re-reviewing until no `must` findings are left (it passes) (`selfReviewLines`). The target kind is `design-doc` for Requirements and Design (the draft is written to a temporary file outside the workspace and reviewed) and `code` for Implementation. For the Document step, the agent decides the kind from the kind of draft (`user-doc` for user guides, procedures, READMEs, operations documents, reports, and so on; `design-doc` for design documents and records of comparisons or decisions). The draft does not become a file in the repository, so it is written to a temporary file outside the workspace and reviewed there, and the skill's verification (`references/verification-run.md`) is not run (the reviewers are told that no verification was run). The basis given to the reviewers states the reader the agent decided on and whether that reader knows the background of the matter (so that the rules for writing the draft and the review criteria do not disagree). For a draft for a reader who does not know the background, the agent does not follow findings that remove explanations of terms, prerequisites, or steps the reader does not know; for a draft for a reader who knows the background, it fixes a finding that adds text only when it is a `must` (a `should` that adds text is not fixed even in a round that fixes a `must`; other `should` and `nit` findings, except those the skill and the step's instructions decide to fix, do not send the draft back to fixing on their own). A document written directly to an external service is read without waiting for approval, so the agent self-reviews the draft before writing and writes externally only after it finishes fixing (it passes or reaches the round limit). When fixing a document already written externally, it also writes the fixed content to a temporary file first and self-reviews it. When fixing existing external pages, it keeps the content before and after the fix in a temporary file per page, and limits the review to what it fixed and what that fix directly requires. It does not change a page for a finding outside that range (so that parts the request did not ask about are not rewritten before approval). The instructions for requirements and designs (such as how to fix findings of the named viewpoints D-3 and D-10) are not added to the Document step's instructions. However, for the Implementation of a request that the orchestrator judged to produce only document files (`documentsOnly`; see [Non-development work and plan selection](#non-development-work-and-plan-selection)), the kind is `user-doc` (`implementSelfReviewLines`; a bug fix never gets `documentsOnly`; it uses that `documentsOnly` as is and keeps no judgment of its own; PBI-295). Besides the required viewpoints of the main kind (`user-doc`; U-1 to U-4), the skill starts the conditional viewpoints whose conditions apply (U-5, U-6, and so on) and the cross-cutting viewpoints (X-1, and X-2 when its condition holds), but it starts no code viewpoint (C-n), which belongs to another kind. The documents are edited directly in the workspace, so no temporary-draft instruction is added. A request that includes code stays `code`. The round limit follows the skill (up to 5 including the first); if `must` findings are still left at the limit, the agent reports them and submits. The first round reviews with every viewpoint. Which viewpoints a re-review (the second round on) starts is left to the skill's rule: only the viewpoints that raised a `must` in the previous round, plus X-1 (only X-1 when there was no `must` and only `should` findings were fixed; PBI-286; see [Context](context.en.md)). `should` and `nit` findings alone do not send the work back for fixing, and in a round with no `must` only what is set to be fixed, such as the `should` findings of a `design-doc` below, is fixed (the skill's rule; PBI-358). The instructions (`selfReviewLines`, `partialReworkReviewLines`) decide only the number of rounds and the scope, not the viewpoints to start. However, in a run that fixes after requested changes from a person, a finding from the AI review (those of the step's latest round that have not yet been given to a submission), (in earlier versions, also a failed final review of the implementation), an instruction is added to treat the first self-review of that run as a re-review (`fixRunCauses`, `fixRunReviewLines`; PBI-296; the viewpoints to start follow the skill's rule "the first review of a fix run": only the viewpoints related to the findings of this run, plus X-1; see [Context](context.en.md)). It is added only when the step's previous submission passed its self-review (`passed`); for requirements and designs only when the fix is made from the previous draft (`partial`), and for the Document step only when the previous draft is not empty. When it did not pass, has no record, or the previous draft is empty, the previous run's unresolved issues may remain outside this run's findings, so every viewpoint is used. For a task whose request the Orchestrator judged light and that a person has not overridden to the normal depth ([Self-review depth](#self-review-depth)), an instruction that narrows the viewpoints is added (`lightSelfReviewLines`; PBI-369). The first review starts only the viewpoint for fit to the requirements (D-1 for `design-doc`, C-1 for `code`, U-1 for `user-doc`) and X-1, and also X-3 and R when the repository has rules or review skills. X-2 starts only when a verification that was run failed or warned. A re-review starts only the viewpoints that raised a `must` in the previous round (X-1 too; when there is no viewpoint to start, no re-review is done). The viewpoints that were not started are left in the launch table and in `summary` of the report, and are not written in `notReviewed` (the viewpoints that were started but gave no result). If the agent finds during the work that the change concerns security or is hard to undo, it decides the viewpoints by the normal rules. When this overlaps with the instruction for a fix run, the viewpoints of the first review stay as the fix-run rule says, and only the rules for the re-review apply. It is not added to a step that skips the self-review, or to the PR review step. It is also not added to the task's first run, to a rerun caused only by an upstream change (only submitted findings exist), or to an implementation redo caused only by a failed test run or a conflict marker. For `design-doc`, a finding that adds text is fixed only when it is a `must`, and its `should` is not fixed. A `should` from viewpoint D-10, which points out over-writing, is also fixed (a rule of the instructions and the skill; see [Context](context.en.md)). Even for a D-10 finding, a condition derived from the repository's rules (README, CONTRIBUTING, AGENTS.md, the CHANGELOG policy, the PR template, and so on), such as updating a version, the change history, generated files, or documentation, and how to check it, is not removed as a "rewrite of the rules": a condition whose source in the rules can be cited stays, and when one is removed the summary says why it was confirmed not to follow from the rules. A finding that the content of such a condition is wrong or cannot be checked is answered by fixing the condition, not removing it (PBI-282; experiment S18). Even for a D-10 finding, a statement grounded in the repository's documents (README, AGENTS.md, operations or specification documents, including ones not referenced from README or AGENTS.md) or in existing behavior is not removed only because "it is not in the request or the requirements". The agent either keeps it, showing the ground (the document and its section, or the place in the code), or turns it into a "確認したいこと" item to ask a person whether to keep it; when it removes one, the summary says why it was confirmed to have no ground (PBI-301 A4; experiment S14 r4: D-10 removed "re-fetch after create or cancel", which was grounded in "availability is always the latest in the DB" of `docs/operations.md`, as "not in the requirements"). For requirements and designs, a finding that the body still holds a report of the work's progress, a report of how a remark was handled, or notes aimed at agents, that an item only refers to another document, or that a decision about the purpose of the request or a default that can harm the requester is not in "確認したいこと" is fixed as a `must` even though it adds text. A finding about a gap with no reason in an ID assigned in the body (not the `TV-n` of test viewpoints) in the first submission is fixed even as a `should`, because it only closes up the numbers (viewpoints D-6 and D-10; see [Context](context.en.md)). Redoing after requested changes or PR comments runs with the same instructions. However, when requirements or a design are revised from the previous draft after changes are requested, the scope and the number of rounds are narrowed ([Revising requirements and designs after changes are requested](#revising-requirements-and-designs-after-changes-are-requested)).
- The Implementation and fix steps (with requirements and design, with requirements skipped, without a test setup, and for a bug fix) are told not to add a mechanism shared by several processes (a queue, a lock, serialization, a cache, global state, a shared helper, and so on) that is not in the requirements or design (the task's content for tasks that skipped them) (`SHARED_MECHANISM_IMPLEMENT_LINE`; PBI-302 B4). The requested behavior is met with the existing mechanisms and the processing at that place. A mechanism is added only when the agent confirmed the behavior cannot be met without it, and then the implementation's description gets a final "Reason for adding a shared mechanism" section naming what was added and why it is needed (which requirement cannot be met with the existing mechanisms, and why). An earlier version's final review wrote "shared mechanism added: ... (reason)" in `humanChecks` (it appears under "Things for a person to check" in the PR body) when the reason was given and could be confirmed, and failed the change as out of scope when there was no reason or the behavior could be met without it.
- The Implementation and fix steps (with requirements and design, without requirements, without a test setup, documents only, and bug fixes alike) are told, before the self-review and the verification before submitting, to check the diff one by one against criteria such as out-of-scope changes (`implementReviewCriteriaLines`; PBI-315; these were originally the failing criteria of an earlier version's final review, given in advance. The heading of the instructions is "提出の前に確かめる、レビューの基準", and they say that the implementation PR's review points out changes that match these criteria (and that a finding makes the agent fix the implementation)). The criteria are: behavior changes nobody asked for, changes that weaken the expectations of existing tests, existing behavior changed by a refactoring, changes the repository's conventions require, tests that do not verify the viewpoint (only for tasks with a test setup), shrinking the acceptance check, recovery after a failure in a shared mechanism, and names internal to sacty's workspace written into repository files. When there are earlier AI review comments, the agent is told to limit its responses to them to fixing defects against what was asked. This is given apart from the criteria (the text of the instructions says that, when responding to an AI comment, the agent limits itself to fixing defects against what was asked and does not change behavior beyond that, and that a change that weakens the expectations of existing tests matches the criteria above even when it responds to an AI comment). The out-of-scope criteria and how to respond to AI comments are not given to security fixes (viewpoint SEC-MIN covers them). The words for what each criterion covers use the constants in `apps/daemon/src/final-review-criteria.ts` (`UNREQUESTED_BEHAVIOR`, `TEST_WEAKENING`, `EXISTING_BEHAVIOR`, `CONVENTION_CHANGES`, `HOLLOW_TEST`, `SHALLOW_ACCEPTANCE`, `SHARED_MECHANISM`, `INTERNAL_NAMES`, `FUTURE_TIMESTAMP`) (the list `FINAL_REVIEW_CRITERIA` is there for tests to check that the instructions have every criterion). The basis for the scope is worded for the task's plan (a task without requirements is not told about approved requirements).
- The instructions of the Implementation and fix steps (every branch, including fixes) include the UTC time the instructions were built (in the form `2026-11-21T10:30:00Z`) and a rule that, when writing a date or time in a file name or body (a record, a decision, a work history, and so on), the agent must not guess it but check the current time in the container right before writing (`date -u` and so on) (`timestampLine`. PBI-469). The date format and time zone follow the repository's conventions. The time is passed as `extra.now` of `buildPrompt` (the service passes its clock, `this.now()`; `Date.now()` if it is not passed). It is not put into the Requirements, Design, and Document steps (the default rules given to every step make the agent check the current time when it writes a date; see [Context](context.en.md)). The review criteria to check before submitting also include `FUTURE_TIMESTAMP`: if the date and time in the name of a file added by this task, written as a creation, decision, or record time, and the matching date field in its body are later than the current time checked right before submitting, fix them to the current time. The current time is converted to the time zone of the repository's conventions before comparing, and to UTC if there are none. Dates that are not record times, such as deadlines and planned dates, are not fixed. sacty does not run a check that reads file names and stops (date formats and time zones differ by repository). In PR review, viewpoint X-1 looks at the same thing.
- Implementation and fix instructions tell the agent to format only files it changed, not the entire repository. Formatting within files changed for the request may follow the repository formatter; formatting-only changes to files not changed for the request must be excluded from submission and reverted if included.
- The Implementation and fix steps are told to verify before submitting, ahead of the self-review (`implementVerificationLines`; PBI-301 A3; experiment S18 r4). The agent runs the verification the repository defines, such as formatters, linters, and type checks, on everything that goes into the PR (code, tests, documents, configuration, including files the agent added), and submits after it passes. A tool that can be limited to the changed files may be limited, but files are not left out by kind, such as documents. For a documentation-only request (`documentsOnly`), the agent runs only the verification that applies to documents (a document formatter, a document lint, link and reference checks, and so on) and does not run tests, builds, type checks, or code linters, so that it does not conflict with the self-review rules for documents. Sacty places approved documents that go into the PR in the workspace and instructs the agent to fix test and formatting errors that do not change decisions directly. Verification that was not run or could not run is written with the reason in the implementation's description (not skipped without a reason). The agent does not weaken the configuration or the tests to make verification pass. Tests run only the related ones along the way and the full suite once after the last change ([Test scope while iterating in implementation](#test-scope-while-iterating-in-implementation)). In addition, the self-review instruction (`selfReviewLines`, for every kind of main target) has the agent follow the whole procedure of `references/verification-run.md` of the default skill and not proceed after reading only a heading or some lines.
- The same section has a line that applies only to a change that adds or changes an entry point (a CLI command, a tool, an API endpoint, or anything else that users or callers use directly) (`ENTRY_UNMOCKED_RUN_LINE`; PBI-451; an MCP tool of PBI-399 passed every test with a faked clock but failed with the fractional values of the real clock). The agent runs that entry point at least once from the built artifact (or as shipped, if the repository defines no build) without faking clocks, timers, or communication, and writes the entry point run, how it was run, and the result in the implementation description. Running faked tests does not count. If it cannot be run, the agent writes why. Entry points that write to, delete from, send to, or charge an external service, and entry points that touch production resources, are not run. Whatever the entry point, regardless of whether the agent thinks it communicates, the one run has every authentication route the entry point might use removed (credential environment variables, config files, files at fixed places under the home directory, an auth proxy, and so on): environment variables are removed or emptied only in the child process, and config and home files are handled by pointing the variables that name the config location and the home at an empty temporary directory that is read instead. A read-only external call may be given dummy values. The real credential files are never moved, deleted, or read, inside or outside the workspace. If even one route cannot be removed, the entry point is not run and the agent writes why. No secret value goes in the command or the result, nor when copying them into repository documents such as the worklog. "Changing an entry point" means changing its externally visible contract (how it is called, arguments, the shape of the output (fields, types, format), exit codes, default behavior); a change that only fixes wrong values without changing the output shape, and an internal change that keeps the contract, are not included, and a change that does not add or change one does nothing. The line appears on every code Implementation and fix path (the orchestrator cannot tell whether an entry point was added) and not on a documents-only request. In the PR review, step 6 of C-4 in the default review skill asks for one small test through the unfaked path (real components whose result is decided locally, such as the real clock; real external services are not required; such a test is exempt from steps 2 and 4 and the fragility checkpoint) where a path was verified only by faked tests, and flags a change that adds or changes an entry point without this record (the result or the reason it could not be run). It was added to C-4 instead of a new viewpoint because C-4 is already a required viewpoint, so no assignee is added and the review time does not grow.
- The Requirements and Design steps are also told, ahead of the self-review, to verify the deliverable file that goes into the PR (`documentVerificationLines`; PBI-301 A3; experiment S18 r4: a table in the Requirements PR failed Prettier). sacty puts the deliverable at `<documentsDir>/<short task ID>/<step>.md` (`stepDocumentPath`) in the PR. The draft is a temporary file outside the workspace, so the agent runs the document verification the repository defines (a document formatter, a document lint, a link or reference check) in a way that checks it as the path where it will be placed, and submits after it passes. Only verification that applies to documents is run; tests, builds, type checks, and code linters are not (the rule for when documents are the main target; PBI-285). Verification that was not run or could not run is written with the reason in the `summary` of the self-review report. It is not added for a task that takes over an existing PR, because no deliverable is added to the PR.
- In a step whose submission becomes a PR that sacty creates and that a PR review child task ([Approval](approval.en.md)) reviews, the agent is not told to self-review (`reviewedByPullRequest`, `skippedSelfReviewLines`; PBI-346). This keeps the same deliverable from being reviewed twice, before submitting and in the PR.
  - The self-review is skipped in a run that meets all of the following. A rework run (a person's change request or AI review findings) is the same.
    - The daemon creates review child tasks (`reviewTasks` of `ServiceDeps`; `main.ts` turns it on).
    - The task does not continue an existing PR (no child task is created for a continued PR).
    - For Requirements and Design, the task approves by PR (`stepPullRequestsOn`). For Implementation (including bug fixes), the task has a target repository.
  - The Document step, tasks without a target repository, and tasks that approve Requirements and Design on the screen do not produce a PR, so they self-review as before.
  - The decision is made once before the step run, and the instructions and the record use the same result. When no PR could be created after the run (the task no longer approves by PR), that submission gets neither the self-review nor the PR review.
  - The instructions say that the self-review is not done and why, that only the self-review is skipped and the verification before submitting is not, and that no report (`sacty-self-review`) is attached. The verification before submitting (for Implementation, "Verification before submitting", the verification record, and the full test suite; for Requirements and Design, the verification of the deliverable file) and the Implementation step's "review criteria to check before submitting" are told as before. The instructions about verification, the test scope, re-reading the text, and classifying provenance are worded without mentioning the self-review. For Requirements and Design, the agent is not asked to write the reason for verification it could not run, because there is no report (the PR's CI and the PR review check it).
  - A rework that only reflects answers (`answerOnlyCheckLines`) is unchanged.
  - A run that skipped the self-review has no `selfReview` in `AgentRunCompleted` (it is not `null`, no record, either). The screen shows nothing.
From the third must-fix with the same cause, the report writes the cause, count, narrower-scope proposal, and unmet conditions in `needsDecision`. The screen shows these decisions at the top without collapsing them, and does not pause the task.

- The agent reports the result as JSON under the heading `sacty-self-review` (`rounds`, `passed`, `remaining`, `notReviewed`, `summary`, `needsDecision`). sacty reads only the last one (`extractBlocks`) and removes every report from the deliverable. A report is found as an object whose first key is the heading, even when it is not valid JSON (`headingSpans`). For an unreadable report outside a code fence, only up to the end of the line where it starts is removed, and the text after it is kept. When the last report cannot be read, sacty does not fall back to an earlier one. The agent does not write the "self-review" section the skill puts at the end of the description.
- `rounds` is 1 to 5, and `passed: true` is allowed only when `remaining` is empty. A report that does not match is treated as a wrong shape (`SelfReview`).
- The report is recorded in `selfReview` of `AgentRunCompleted`. When there is no report, or it cannot be read or its shape is wrong, it is `null` (no record). The step does not stop. The projection keeps the report of the latest submission per step in `selfReviews` (absent for steps that do not self-review and for earlier records). When the text is replaced outside a step run (applying a change proposal, or a merge after a person edited the document in the PR), the earlier report did not see the new text, so it becomes no record.
- The screen shows passed (rounds), not passed (rounds and the number of findings left), or no record on the deliverable cards (not on approved deliverables), the Implementation card, and the approval screen. Not passed and no record use the warning color, and when it did not pass, the findings left and the viewpoints not reviewed are shown open. The "finished" line of the Activity also shows it.

### Classifying provenance before submitting

To narrow down what the approver looks at, the Requirements and Design steps (`PROVENANCE_STEPS`) have a subagent other than the authoring agent classify the provenance of each item of the deliverable.

- Before the run, sacty places the input for the classifier read-only at `/sacty-input`, outside the workspace (`provenanceInputs`). It is removed after the run.
  - `task.md`: the task content (including the source ticket, gathered information, and the comments of a continued PR)
  - `remarks.md`: the active remarks for that step (with IDs; only when there are some). A person's remarks and sacty's own AI review remarks are listed under separate headings ([AI review comments](approval.en.md#ai-review-comments))
  - `investigation.md`: the result of the preceding investigation (only when there is one)
  - `requirements.md`: the approved requirements, in the Design step (absent for a task that skipped the Requirements step)
- The instructions (`provenanceLines`) ask the agent, after the self-review, to start one classifier subagent on the final version, following "How to request" of the default skill `classify-provenance`. The items are the requirements in the text (`R-n`) for Requirements and the test viewpoints (the n-th in the JSON as `TV-n`) for Design. The request states the input directory and the path of the final version, and does not include a summary or paraphrase of the input, how the agent wrote it, or which items it added. The agent attaches the classifier's answer unchanged as JSON under the heading `sacty-provenance` (`mode`, and `id`, `kind`, `refs`, and `excerpt` of `items`). When no subagent can be started, the agent classifies the items itself in the skill's sequential mode and sets `mode` to `sequential`. The instructions do not say how the result is used in human approval.
- The kinds (`kind`) are quote (`input`; an item that states what the input says as is), derived (`derived`; derived from the paired unwanted behavior, the investigation result, or conventions of existing code), and inference (`inference`; anything else).
- sacty reads only the last answer (`extractBlocks`) and removes every answer from the deliverable. An unreadable answer is also found by its heading and removed, as with the self-review report. An unreadable answer under a key other than the first (a trailing comma and so on) is also found by the key (`headingMentions`). Inside a code fence, the whole fence is removed; outside one, the line with the key is removed. When the last answer cannot be read, sacty does not fall back to an earlier one.
- The answer is checked and recorded as follows (`checkProvenance`).
  - An answer whose `mode` is neither `subagent` nor `sequential` is treated as unreadable, because it is unknown who classified the items.
  - Only IDs of items in the deliverable are used (`R-n` in the text for Requirements, the test viewpoint IDs for Design; `provenanceIds`). The ID of a requirement row removed on a send-back ("R-5（削除：理由）", "R-5（削除）") is left out, because it is not an item to check (PBI-302 C1; experiment S14, r5: deleted rows were listed under "Where to check"). Only a row whose parentheses start with "削除" followed by a separator (`：` or the closing parenthesis) is left out; a requirement title such as "R-1（削除の確認）" is kept. Unknown IDs, repeated IDs, and unknown kinds are dropped. Items without a classification go to `unclassified`.
  - In Design, the answer's `TV-n` (the n-th in the test viewpoint JSON) is converted to the ID sacty gave (`viewpointRename`). sacty renumbers the viewpoints after dropping those with missing fields, so the position can differ. The classifications of dropped viewpoints are discarded. `TV-n` in the references (`refs`) is converted the same way, and one that points to a dropped viewpoint gets "（取り込まなかった観点）" (a viewpoint not taken in).
  - The excerpt (`excerpt`) is matched against the whole input, and whether it was found is kept in `found`. Before matching, both are normalized to NFKC and whitespace and Markdown symbols (`*`, `_`, backquote, `>`, `#`, `|`) are removed. An excerpt shorter than 4 characters after this is treated as not found. The excerpt of an inference is dropped.
  - The result is recorded in `provenance` of `AgentRunCompleted`. When there is no answer, or it cannot be read or its shape is wrong, it is `null` (no record). The step does not stop.
  - The projection keeps the classification of the latest submission per step in `provenances`. When the text is replaced outside a step run, it becomes no record, as with the self-review.
- The items a person checks (`needsCheck`) are inferences, quotes whose original text is not in the input, and items without a classification. When the authoring agent classified the items itself (`sequential`), every item.
- The screen shows the number of items to check and the number per kind on the deliverable cards (not on approved deliverables) and the approval screen (`ProvenanceNote`). When there are items to check, they are listed open in the warning color, and quotes and derived items are collapsed under "Others". With no record, a warning is shown.
- The body of a Requirements or Design PR has the items to confirm and their grounds under "Where to check" (the PR version, `provenancePullRequestLines`; the number of items to confirm, the counts of quotes, derivations, and inferences, and the line about whether sub-agents classified are not written in the body, PBI-471; the screen is unchanged; in the purpose or summary part when following a template).

## Non-development work and plan selection

The Orchestrator does not recommend `standard` unconditionally. It is told to choose from the deliverable (what the task ultimately asks for), not from keywords or whether there is a target repository, and to choose by scope and clarity only among the plans that implement (`PLAN_SELECTION_LINES`). Having a target repository is not a reason to choose a plan that implements (for example, writing a procedure document by reading the repository is `document`, and adding steps to the README is `direct` or `skip-design`). When in doubt, it decides by whether the request says the result should be reviewed in a PR and kept in the repository (a file name, a location, a PR instruction, and so on). Adding or changing instructions for agents in the repository, such as a skill (SKILL.md) or AGENTS.md, is a change to a document kept in the repository, and is usually `direct` or `skip-design`. Since documents of instructions are checked in the diff without tests ("Verifying the implementation" below), it does not add Requirements or Design to decide tests or viewpoints.

| Request | Plan |
| --- | --- |
| A question or cause analysis | `investigate` |
| A review of an existing PR | `review` |
| Overall design | `design-only` |
| Writing a draft read outside the repository (a procedure document, user guide, report, and so on) | `document` |
| Creating or editing external documents directly and revising them through Request changes (including multiple pages, or pages found by a condition and fixed together) | `document` |
| A local change whose request is clear as acceptance criteria and that uses existing mechanisms | `direct` (no requirements or design) |
| A change with verifiable acceptance criteria in place and nothing for a person to confirm (only fine defaults remain to decide; it need not be local) | `direct` (no requirements or design; "Requests with detailed acceptance criteria" below) |
| A change whose verifiable acceptance criteria are in place and that needs a design decision (a new mechanism, or a choice of structure across layers) | `skip-requirements` (Requirements skipped; see "Requests with acceptance criteria in place that need a design decision" below) |
| A file change in a repository, including documentation, that is local | `direct` or `skip-design` |
| Adding or changing instructions for agents, such as a skill or AGENTS.md | `direct` or `skip-design` (`standard` when it spans several skills and needs broad design decisions) |
| A file change in a repository, including documentation, that needs broad design decisions | `standard` |
| A file change in a repository, including documentation, split into several PRs | `split` |
| Fixing an existing PR itself (addressing review comments on the PR, and so on; "Taking over an existing PR" below) | `direct` (`continuePullRequest`) |
| A reproducible bug | `bugfix` |
| A bug that needs design decisions | `standard` |
| Checking for vulnerabilities and supply chain risks | `security-check` |
| Fixing a specific security problem (a CVE, a GHSA, an alert, a finding of a check), whatever its size | `security-fix` |

The Orchestrator does not add steps by guessing at mechanisms the request does not mention (new roles, admin screens, and so on).

#### Requests with detailed acceptance criteria

Requirements take most of the cost. When the request has its acceptance criteria in place and nothing for a person to confirm, what Requirements would decide is only fine defaults (whitespace, limits, ordering, column positions, and so on).
So the Orchestrator is told to choose `direct` and skip Requirements, even when the change is not local, when all of the following hold (`DETAILED_ACCEPTANCE_LINE`; the descriptions of `direct` and `skip-design` in `planDescriptions` say so too).

- Verifiable acceptance criteria (inputs and expected results, behavior, how errors are handled, and the scope) are in place.
- There is nothing for a person to confirm (only fine defaults remain to decide).
- No design decision (a new mechanism, or a choice of structure across layers) is needed.

When no design decision is needed and any of the following applies, Requirements is kept (`skip-design` or `standard`) even if the acceptance criteria look detailed, and it is told to write what applied in `reason`. Requirements is also kept when it cannot decide. When a design decision is needed, the next section applies.

- The request is ambiguous (no goal or standard, or it is unclear what to do and how far).
- The request conflicts with a document, the code, or an existing policy, and which one to follow changes what is built (behavior, approach, or scope).
- There is a judgment the request does not state (compatibility, how to delete, the scope, and so on) that a person should confirm.
- Something the requester may have forgotten to write, or a collision with another task or PR that changes the same place, is visible (from the gathered information, and so on).
- The change puts a new meaning on an existing shared state or field (a flag, a column, the kinds of a state) or adds a state. This applies even when the request tells it to use an existing flag, if the flag would carry a different meaning (another task may use the same flag for another meaning).
- The change needs a change to the name or shape of a published API or field that the acceptance criteria do not state, or a person should confirm a conflict with the side that uses it (it may conflict with other features or with that side).

The following do not count as reasons to keep it.

- The acceptance criteria clearly state the change to a published API or field (the new name, shape, whether it is required, how errors are handled), and nothing is left for a person to confirm about a conflict with the side that uses it. "Changes the name or shape of a published API or field" is not a reason to keep Requirements, because the request itself decides the change.
  - A change such as a rename, where the request does not settle what happens to the existing side that uses it (keep the old name, or migrate), is not clearly stated.
  - When the gathered information says the side that uses it may stop working because of the change and the acceptance criteria do not settle how to handle it, there is something for a person to confirm, so Requirements is kept.
  - When any other condition for keeping Requirements applies (such as a new meaning on a shared state), it is kept.
- Fine defaults remaining (whitespace, limits, ordering, the position of a column or field, what the tests for error cases contain, how empty input is handled, and so on). The implementation decides them and a person confirms them in the PR under "既定で決めたこと".
- The following, where nothing is left for a person to confirm (PBI-302 B5):
  - A conflict between repository documents, or between a document and the acceptance criteria, that does not change what is built (behavior, approach, or scope), such as which commands count for completion or whether a document should be updated to match the implementation. When there are acceptance criteria, they are followed and the document is updated to match the implementation.
  - Existing callers, tests, or documents following a change the acceptance criteria decided.
  - Items under the gathered information's "conflicts and open points" that the implementation can decide from the request and the existing code and conventions (when the acceptance criteria say not to add features beyond the conditions, it decides not to add the feature).
- The reasons for keeping Requirements are only things that have several answers, that neither the request nor the existing code and documents settle, and that cannot be decided without asking a person, and `reason` states them one by one. What it lists as a reason becomes an item under "確認したいこと" in the Requirements step.

When it chooses `direct`, `reason` is to state why Requirements was skipped (which acceptance criteria are in place and why nothing is left for a person to confirm). It stays in the work history (`StepsChosen`) as the reason for the plan.
An implementation without Requirements decides fine defaults the request does not settle by following the existing implementation and conventions, and writes them one per line in a separate "既定で決めたこと" (decided by default) section of the implementation notes (put in the PR body, so a person confirms them in the PR). When the request lists acceptance criteria, it checks that each is met (`directImplementLines`).
This decision does not change the number of self-review rounds, the model, or the effort.

#### Requests with acceptance criteria in place that need a design decision

Even with the acceptance criteria in place, when a design decision remains, Requirements only restates the acceptance criteria, and the PR, the reviews, and a person's judgment cost time and money (PBI-395).
So the combination `skip-requirements` (`design` → `implement` → `deployment`; it has no Requirements step) is provided. Its Design step is the same as `standard`, and what a person should confirm is asked under "Questions to confirm" in the Design.
The Orchestrator is told to choose this combination when the acceptance criteria are in place (the same criterion as when choosing `direct`) and a design decision (a new mechanism, or a choice of structure across layers) is needed (`DETAILED_ACCEPTANCE_LINE`; the description in `planDescriptions` says so too). It is told to write in `reason` why Requirements was skipped and the points a person should confirm (one by one, if any).

- Requirements is not kept even when there is something for a person to confirm (a judgment the request does not state, something forgotten, a collision with another task or PR, a new meaning on a shared state or field, or how a change to a published API or field is handled). The Design asks it.
- When the request is ambiguous, the acceptance criteria are not in place, the request conflicts with a document, the code, or a policy in a way that changes what is built, or it cannot be decided, Requirements is kept even if a design decision is needed (`standard`).
- When both of the above apply, keeping Requirements wins. A collision is one with another task or PR; a conflict is one between the request and a document, the code, or a policy.
- When no design decision is needed, the choice is as before: `direct` when nothing is left for a person to confirm, `skip-design` when something is.

This combination proceeds as follows.

- The instructions of the Design step (`design`) say that Requirements was skipped and that the task content and the gathered information are treated as the requirements. They do not say "by the Orchestrator's judgment" for a task a person specified when creating it.
- When the Orchestrator chose it, the first Design run is given `reason` as JSON data (`designReasonLines`; secrets hidden, cut at 3000 characters, the same handling as `keepRequirementsReasonLines` for Requirements), and is told to put each point under "Questions to confirm" or to write why it is not confirmed under "Decided without confirming". It is not given for a task a person specified.
- The instructions of the Implementation step include the task content (the request), have no requirements, and take the request and the approved design as the standard. The PR body and the criteria for the review before submitting (`implementReviewCriteriaLines`) also take the request and the approved design as the standard.
- When a person specifies this combination on the screen when creating the task, the Orchestrator's candidates are only this combination (`allowedPlans`), and the task proceeds in the order Design → approval of the Design (merging the Design PR) → Implementation.
- The review of the remaining steps runs only after a step finishes. In this combination Design is the first step, so there is nothing to decide about skipping it.
- `create_task` of `sacty mcp` does not get an argument for the combination (it is specified only on the screen).
- `StepsChosen.plan` and `TaskCreated.plan` are enumerations built from the keys of `STEP_PLANS`, so records written by a version that does not know this combination are read as they are. Reading a task of this combination by an old version that does not know it is not required.

Related ADRs: [A request with its acceptance criteria in place that needs a design decision skips Requirements and proceeds Design → Implementation](../adr/20261120-0735-skip-requirements-for-design-decision.md)

- `document` produces a Markdown draft without enforcing the Requirements or Design format. A person can request changes and approve it in the web UI. Like the other steps, the agent gets the composed context, the host's and the context's external PFs, the MCP servers, and the GitHub read relay (the gateway does not narrow the PFs or MCP servers). For a task with a target repository, the code at the base commit is placed in the workspace as a disposable copy for the agent to read as evidence (the repository is not changed). The instructions tell the agent that sacty saves the output (all of it except the JSON in fixed formats) as the step's result and a person approves it (`documentDeliverableLines`). How to write the draft (the amount and structure that fit the reader, figures and images) is instructed as in [Length of deliverables that people read](#length-of-deliverables-that-people-read), and the review before submitting as in [Self-review before submitting](#self-review-before-submitting). Normally the deliverable is one draft: the agent outputs the full draft and is told not to write to external services or the repository (this is not enforced); it is exported after approval. If the task description (including the source ticket) instructs creating or editing external documents directly, the agent may write them externally as instructed, and the pages it wrote (one or more) become the deliverable. For an instruction such as "find the pages containing … and fix them", the agent finds the matching pages and fixes each. The output then has, per page, a heading (title and URL) and the content after the fix (for a long page, the fixed parts and their surroundings), which a person approves. The agent is told not to create pages or comments externally other than the deliverable, and not to write a work report (that it created something, task or agent IDs, steps) either externally or in the output. When it writes externally directly, it outputs the URLs of the pages it created or edited in that run as JSON under the heading `sacty-document-pages` (`pages`) (`extractDocumentPages`; only http(s) forms, no duplicates, up to `DOCUMENT_PAGES_MAX` (200)). sacty reads this report from the output before extracting the responses to remarks and the like (it is read even when it is in the same JSON object), removes the JSON from the output, and records it in `documentPages` of `AgentRunCompleted`. The projection adds the reported pages to the pages of earlier runs and keeps them in `Task.documentPages` (pages not edited in a run remain part of the deliverable). If there are `documentPages`, the instructions give them, and the agent edits the same pages when it fixes them (it is told not to create another page with the same content). If an export destination is decided, the instructions give the destination and its location. On Request changes, the agent revises the previous draft (or, if it wrote externally directly, the deliverable pages) and outputs the whole result again. It treats a remark asking to fix an external page as a remark on the deliverable, and may add pages when a remark asks to add target pages. If there are `documentPages`, nothing is exported even when an export destination is decided (`exportDue`); the web UI shows the pages written externally instead of the export result. Export is optional and uses the existing mechanism; an export failure does not stop the task from completing. To make a decided change to one unique target only once, use `operation` (creating or editing external documents directly and revising them through Request changes is `document`).
- `operation` runs as a single step. The existing Orchestrator chooses one destination, a unique target ID or URL, the requested change and its preconditions, and how to verify it. For tasks that can choose `operation`, with or without a target repository, the prompt for choosing the steps shows the settings to write, the available destinations, and the answer format (`OPERATION_SETTINGS_LINE`, `operationDestinationLines`). sacty adds no separate preparation agent, preparation deliverable, or approval gate before execution. If the target or destination is missing, the task stops before execution starts.
- The destination kind of an operation (`via`) is `platform`, `mcp`, or `github`. `github` is a GitHub host for which the project chose a gh account, and `name` is the host. The host is listed among the Orchestrator's destination candidates. Reading uses [the GitHub read relay](gateway.en.md#relaying-github-reads), and comments on PRs and issues are written by the agent in its output and posted by sacty after the result is approved ([Requesting comments on PRs and issues](#requesting-comments-on-prs-and-issues)). It cannot change or push code. If no account is chosen for the host, the task stops before execution (`operation.connectionMissing`).
- The task details show the chosen operation settings (`name`, `via`, `target`, `change`, `verification`) as read-only. These are the execution settings the Orchestrator chose, not a new deliverable or approval gate.
- The operation gets only the chosen destination and carries out the request. Apart from the chosen destination, however, [the GitHub read relay](gateway.en.md#relaying-github-reads) is always available (read-only; writes go only to the chosen destination and to sacty's posting after approval). The prompt requires checking the target and preconditions, making every write the request needs (there may be several, such as a parent post and a reply in its thread; there is no limit on the number of writes), and checking the change by reading it back. Each write is made only once: after an error, a timeout, or an unknown result, the agent does not resend the same write, does not make the remaining writes, and reports failure, separating the writes confirmed as successful, those not made, and those whose result is unknown. When a successful result with evidence comes back, the task waits for a person's result approval. On failure, interruption, restart, or an unknown result, the task stops. Based on the persisted start record, sacty rejects Resume and keeps the task stopped. After execution starts, Request changes is unavailable. A person checks the external state, cancels the task, and creates a new task for the work not yet done.
- sacty does not guarantee exactly-once on the external side. Not resending the same write and the read-back check are instructions to the agent. sacty does not add recurring runs, monitoring, arbitrary integrations, or control of work across several destinations. Split a request with several kinds of deliverables into tasks with clear approval boundaries.

## Requesting comments on PRs and issues

A step's agent cannot write to GitHub ([the GitHub read relay](gateway.en.md#relaying-github-reads) is read-only). To comment on a PR or an issue, it writes exactly one of the following JSON in its output. After a person approves the step's output, sacty posts it with the project's gh account.

```json
{"sacty-github-comments": {"comments": [{"url": "https://github.com/acme/app/pull/12", "body": "Markdown body"}]}}
```

- Every step except review can request comments (for `review`, sacty posts the written review). For a task with a security plan (`security-check`, `security-fix`), nothing is posted even if requested (`isSecurityTask`; the report and the fix scope can give attackers a lead). Posting uses the request in the approved output (`approved`). When the output is approved again (the approval time changes), the request of that version is posted. Nothing is posted for a cancelled, paused, or running task. It is posted before the next step (`awaitingGitHubComments`).
- The requests of a step that is approved by merging its PR (implementation, requirements, and design) are posted without waiting for the approval (the merge). After approval, a reply to a review comment would not reach the people watching the PR.
  When the output is awaiting approval (`awaiting_approval`) and the target PR is open, sacty posts the request of that submission once (`awaitingSubmittedGitHubComments`).
  The next submission, after a send-back and rework, posts its own request once. After approval, sacty does not post the same submission's request again.
  As after approval, nothing is posted for the review step, a security task, a cancelled task, a paused task, or a running task. A step approved in the web UI (no PR) posts after approval as before.
  Unreadable requests, the limits on count and length, the limits on targets, the check right before posting, and the marker are the same as after approval.
  Posting for the same task and step is processed one after another (`serialized`). Even if another run starts while the first is still searching or posting, the later one looks for the marker again after the first finishes.
  The post after approval also looks for the marker of the same submission that was used while awaiting approval, and uses that comment if it finds one. So if the PR was merged while the post was in flight and nothing could be recorded, sacty does not post twice.
  Paths inside sacty's workspace in the body are replaced with a name a person can follow (`withoutInternalPaths`).
- If the request cannot be read (two or more, not JSON, a wrong shape, an empty body), there are more than 10 comments (`GITHUB_COMMENTS_MAX`), or a body is longer than 60000 characters (`GITHUB_COMMENT_BODY_MAX`), nothing is posted and the reason is recorded.
- The target must be the URL of a PR (`/pull/<number>`) or an issue (`/issues/<number>`) in the project's targets (a repository or its organization), or in the task's source or working repository. Otherwise only that comment is not posted, and the reason is recorded.
- Right before posting each comment, it checks that no pause or cancel has been requested and that the step's approval has not changed. If it has, no new comment is posted and nothing is recorded (on resume, the already posted ones are found by their markers and it continues).
- A marker (`<!-- sacty-comment:<task>:<step>:<approval time>:<index> -->`) is put at the top of the body and the separator `---` and "Sacty の<工程名>の工程で AI が書き、人間が承認しました。" at the end, and it is posted with the issue comments API (the task ID is not written at the end and is kept only in the marker; `buildGitHubComment`). Before posting, a comment with the marker is searched for and used if found (no double posting even if it stops after posting and before recording).
  For a post made while awaiting approval, the approval-time part of the marker is `submission-<submission>`, and the note at the end is "Sacty の<工程名>の工程で AI が書きました。この工程の成果は、PR のマージで承認されます。".
- The result is recorded in `GitHubCommentsPosted` (the step, the approval time, the URL or the reason per comment, and the reason if unreadable). A post made while awaiting approval has `submission` (the submission number) and an empty approval time. Even if posting fails, the task does not stop. The reason a comment could not be posted appears in the activity history on the screen as this record.
- This comment is not imported as a PR remark: comments posted by the task's account that start with the marker `<!-- sacty-comment:` are excluded when sacty imports PR remarks (`feedback`, `isSactyGitHubComment`). This keeps a reply from becoming a new remark and starting another round of send-backs. Comments that other accounts wrote imitating the marker are not excluded.
- The JSON request is removed from the investigation result returned to the source issue (`buildInvestigationComment`).

## Taking over an existing PR

When the title or description of a task has a link to a PR of the target repository and the task asks to fix that PR itself (addressing review comments on a PR a person opened, and so on), sacty takes over the PR. It opens no new branch or PR and pushes the implementation to the PR's source branch.

Related ADR: [A task that fixes an existing PR takes over the PR and pushes to the same branch, and a documentation-only viewpoint is checked in the diff without a test](../adr/20261025-1337-continue-existing-pull-request.md)

- Whether to take it over is decided by the Orchestrator with `continuePullRequest` in its answer for choosing the steps. The prompt shows this item only for a task that has a PR link and can choose a plan that implements (`CONTINUABLE_PLANS`: `standard`, `skip-requirements`, `skip-design`, `direct`, `bugfix`, `security-fix`) (`continuablePullRequest`). It is not shown for a task imported from a PR or a child task of a split. It is also not shown for the follow-up task of a remark a person decided to defer (it has `derivedFrom.deferredRemarkId`; [Proposals to defer and the person's decisions](approval.en.md#proposals-to-defer-and-the-persons-decisions)), and `continuePullRequest` in its answer is not read (the PR in the request is the original task's merged PR and cannot be taken over; the fix goes to a new branch and PR). The follow-up task's title is made from the remark's gist (`[PR #<number> follow-up] <gist>`; [The one-line gist of a remark](approval.en.md#the-one-line-gist-of-a-remark)). The headings of the instructions to the agent (the steps, the risk assessment, the audit, and the deployment) do not use the title but a fixed "後続に回した指摘への対応" (`instructionTitle`), so that text from outside is not read as an instruction (PBI-471). Links inside a record that sacty appended to the description are not looked at: with the original task's record of a follow-up task (`derivedFrom.record`; [Creating a follow-up task from a completed task (derive)](#creating-a-follow-up-task-from-a-completed-task-derive)) and the previous attempt's record of a task created by a rerun removed (both hold PR URLs and step outputs), only links in the title and the description the person wrote (including the rerun note) are looked at (`rerunEditableBody`). The prompt asks not to write it when the task only refers to the PR for a different change or only reviews the PR, to choose `direct` when the review comments make the fix concrete and `security-fix` when it fixes a security problem, and not to write `baseBranch`. `continuePullRequest` in an answer with a plan that does not implement is not read.
- sacty checks the PR before recording the steps (`resolveContinuedPullRequest`). It takes over only a PR that is open, whose source branch is in the target repository (not a PR from a fork), and that no other sacty task (except cancelled ones) opened (as an implementation PR or a Requirements or Design PR) or took over (`continuedPullRequestOwner`). In case another task checks the same PR at the same time, it checks again right before recording the steps (with no await after that) that no other task handles it. If it cannot be taken over, to avoid opening a new PR, sacty records no steps; it records `OrchestratorFailed` (with the cost of the decision) and `TaskPaused` (`continue.unavailable`) and stops. Resuming chooses the steps again.
- When it can be taken over, the workspace is prepared again at the latest of the PR's source branch (`RepositoryPrepared`; the base branch is that branch and the base is its head), and it is recorded in `continuedPullRequest` of `StepsChosen` (the repository, number, URL, source branch, and target branch). It becomes `Task.continuedPullRequest` in the projection. If the workspace cannot be prepared again, the task stops as when it cannot be taken over.
- The prompts of the steps (except review and the post-merge watch) get the PR being taken over and the reviews, line comments, and regular comments on it (including approvals with a body and reviews posted by sacty tasks; up to the newest 30) as JSON data (`continuedPullRequestLines`, `passedContinuedFeedback`). They tell the agent to keep the PR's purpose and existing changes, change only what the task asks, and write the reason for comments it does not address in its description (Requirements and Design do not let the agent write a report of the work in the body, so it writes the comment and the reason under "確認したいこと" as a decision for the person; comments of a taken-over PR are not in `Task.remarks` and the Requirements and Design steps get no IDs, so it is told not to write them in `sacty-responses`). The implementation step gets an ID per comment (the import key) and writes a response per comment in `sacty-responses`, and sacty replies on the PR ([Replies about how remarks were handled](approval.en.md#replies-about-how-remarks-were-handled)). If they cannot be read, the prompt says so and the reason goes to the daemon's log (the step does not stop).
- Requirements and Design are not opened as PRs; they are approved in the web UI (`stepPullRequestsOn`). This keeps their files out of the taken-over PR.
- An implementation that passes verification is pushed to the PR's source branch (`publishContinued`).
  - It is stacked on the base (the PR's head) or the previously pushed commit, without force-pushing. If the push fails and the branch's head differs from both the base and the previously pushed commit, it pushes again (if the push went through and only the response was lost, the head is this submission's commit, so it passes without changing anything). If that also fails, sacty treats it as pushed by a person and stops (`pr.continuedBranchMoved`). The exception is a push that is still a temporary failure after the retries (3): sacty does not treat it as pushed by a person and stops with `pr.failed` (see "If a push is rejected by a temporary failure" below). This push again runs only for a failure that is not temporary.
  - If a pause or cancel has been requested right before a push (after waiting for authentication, and before pushing again), it does not push (on a pause, it stays waiting to open the PR).
  - If the PR is not open after the push, it stops (`pr.continuedNotOpen`). The exception is when it was merged while the implementation was being reworked: it does not stop, and the merge is taken as the approval ([Merging during a rework of the implementation](approval.en.md#merging-during-a-rework-of-the-implementation)).
  - It does not change the PR's title or description, and adds no review label.
  - If the PR is open, it is recorded in `PullRequestPublished` (with no template and no planned label), and the task waits for the implementation's approval (merging the PR).
  - When there are no changes, it is the same as other tasks ([Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).
- The comments passed to the prompt of a run of the Implement step are recorded in `ContinuedFeedbackPassed` (the run and the keys of the comments passed; `Task.handedOverFeedback` in the projection) when the run finishes, in the same append as its completion (`AgentRunCompleted`). Nothing is recorded if the run could not start or failed. Importing PR comments skips the comments passed, because the implementation addressed them (`handedOverFeedback`). Comments not passed (unreadable, over the limit, or added later) are imported as for other PRs ([Importing PR comments](approval.en.md#importing-pr-comments)).
- The post-merge watch records the PR's target branch as the merge target, not the workspace's base branch (the PR's source branch) (`deploymentWatchEvents`).
- Cancelling neither closes the taken-over PR nor deletes its source branch (it is excluded from `sactyBranches`).
- The web UI shows the PR being taken over (its number and source branch) on the "Step settings" tab of the task details.

## Security check and security fix

Security checks (the deliverable is a report) and fixes (the deliverable is a PR) use the plans `security-check` and `security-fix`. They use the Investigate, Implement, and After-merge watch steps as they are, and add rules to the prompts and the verification.

Related ADR: [セキュリティチェックとセキュリティ対応を、既存の工程の組み合わせとして足し、対応の差分を修正の範囲と照らして最小限に保つ](../adr/20261026-1520-superseded-security-check-and-fix-plans.md)

- Whether a task is a security task is decided by the chosen plan (before choosing, the plan specified at creation) (`taskPlan`, `isSecurityTask`). Both are plans that need a target repository (`REPO_PLANS`); for a task without a repository, the Orchestrator chooses one from the project's targets.
- The investigation prompt (`SECURITY_TOOL_LINES`): the agent does not set up for development, but runs the check tools in the workspace (osv-scanner, gitleaks, and so on), including network access to vulnerability databases, and uses the results as evidence. What it has no tool for or could not run is written as unchecked scope, and it does not write the values of secrets it finds or how to exploit a problem.
- Keeping it off public places: the result is not commented on the source issue or ticket (`awaitingIssueComment`). Requests for comments on PRs and issues are not posted either ("Requesting comments on PRs and issues" above). The export destination is decided as for other tasks.

Code: `apps/daemon/src/security.ts`, `apps/daemon/src/prompts.ts` (`SECURITY_TOOL_LINES`, `securityCheckLines`, `securityScopeLines`, `securityFixImplementLines`, `securityScopeBodyLines`), `packages/core/src/projection.ts` (`taskPlan`, `isSecurityTask`, `canRequestSecurityFix`), `apps/daemon/src/service.ts` (`awaitingIssueComment`, `awaitingGitHubComments`)

### Security check

- The prompt of the investigation (a task whose goal is the investigation) asks for a check per category (`securityCheckLines`). The categories are `dependency` (dependency vulnerabilities), `supply-chain` (supply chain: CI workflows, where dependencies come from and lockfiles, install scripts, pinning image tags), `code` (code vulnerabilities), `secret` (leaked secrets; the workspace is a copy without .git, so only the files are checked and the history is written as unchecked scope), and `config` (configuration and IaC) (`SecurityCategory`).
- Tool results are sorted out (reachable, exploitable, false positive) before they become findings. For each finding, the agent writes the category, the severity (`critical`, `high`, `medium`, `low`), the title, the identifiers, the location, the evidence, and a proposal for the smallest fix.
- After the body of the report, the agent outputs JSON under the heading `sacty-security-findings` (`findings`: `id`, `category`, `severity`, `title`, `refs`, `location`, `fix`). The JSON stays in the body, and sacty reads the last one from the approved body (`extractSecurityFindings`; findings without a category or a title are dropped, a missing severity becomes `medium`, and a missing ID becomes `SF-<number>`).
- The task completes when a person approves it in the web UI (as with other tasks whose goal is the investigation).

### Creating fix tasks from the report

- For a security check task that was approved and completed (and is not cancelled) (`canRequestSecurityFix`), the task details show the findings per category and "Create fix task" (`GET /api/tasks/:id/security-findings`). If the findings cannot be loaded, this is shown separately from having no findings, with a hint to reload.
- "Report" in the properties of a fix task's details shows a link to the report task and the category.
- `POST /api/tasks/:id/security-fixes` (the input is `category` of `RequestSecurityFixInput`) creates the fix task for that category. Only once per category (`security.alreadyRequested`). It is not created if the report is not approved (`security.notReport`) or the category has no findings (`security.noFindings`) (all 409).
- First, `SecurityFixRequested` (the category, the ID of the task to create, the title, the body, all the findings of that category; the actor is `person`) is recorded on the original task, then `TaskCreated` is recorded with that ID. If the daemon stops before creating it, it is created at startup (`resumeSecurityFixTasks`).
- The task created has `start: security`, `plan: security-fix`, and `securityFix` (the original task, the category, and all the findings), and the repository of the original task. The title is `セキュリティ対応：<区分>（<元のタスクの題>）`, and the description has only the findings of that category and a request to fix them with the smallest change (`securityFixTask`). The description lists only the findings that fit in `TASK_BODY_MAX` and gives just the count of the rest (no finding is cut in the middle).
- The prompts of the fix task's steps (investigation, implementation) get all the findings in `securityFix` as JSON data without omission, and the agent is told to solve all of them (`securityFindingLines`).

### Security fix

- The prompt of the preliminary investigation (`securityScopeLines`) has the agent confirm the problem and declare the fix scope as JSON under the heading `sacty-security-scope` (`paths`, `packages`, `verification`, `reason`). Dependencies are raised to the smallest version that solves the problem, and a breaking change, if needed, is stated. The scope is not approved (the preliminary investigation is not approved). sacty reads the last declaration from the body of the preliminary investigation handed over as approved (`securityScope`, `extractSecurityScope`; a declaration with empty `paths` is unreadable).
- The implementation runs with the prompt for an implementation without Requirements or Design ("Step review" above), with the rules for the smallest change (`securityFixImplementLines`) and the scope (as JSON data) added. It tells the agent not to change anything outside the scope (it may add files for regression tests), not to mix in refactoring or reformatting, and to raise dependencies with the package manager. The number of changed lines is not checked (only files outside the scope and whether the change is minimal are). The viewpoint `REQ` is "the problem is solved"; for a dependency or configuration update that cannot be tested, the agent writes in `untested` that it is checked with the check command.
- Before opening the PR (before `FinalReviewSkipped`; `checkSecurityScope`), sacty checks the diff against the scope (`scopeViolation`). The check uses not the diff given to agents (truncated at `DIFF_LIMIT`) but the untruncated paths of the changed files (`diffStats`; the line counts are not used for the check; `git diff --numstat --no-renames`). A rename is split into a deletion of the source and an addition of the destination (so a file outside the scope cannot be hidden by moving it into the scope). For a file without line counts (a binary, or one whose diff is hidden by `-diff` and the like in the workspace's `.gitattributes`), the lines of the old and new contents are counted as all removed and all added (to keep the shape `diffStats` returns, per-path added and removed line counts; the check does not use the counts). An added file has 0 old lines and a deleted file 0 new lines (told apart with `git diff --name-status`); if existing contents cannot be read, the stats count as unobtainable and the task stops. The contents are read one at a time (not starting many processes at once). If they cannot be obtained, the task pauses without recording (`verify.diffUnavailable`).
  - Files outside the scope: files that match none of `paths` (the path itself, below it if it ends with `/`, and `*` for any characters except `/`; `pathInScope`) and are not test files (in a test directory, or with a name following the test naming conventions).
  - If the scope cannot be read, nothing is checked (no violation). The implementation and review prompts say that sacty does not check the scope because there is no declaration, and the review checks whether the change is minimal. The scope section of the PR body does not get this sentence.
  - A diff of any size, including tests and documents, is not a violation by its number of changed lines (PBI-452).
- A violation does not stop the task. The result is recorded in `securityScope` of `FinalReviewSkipped`, written in the scope section of the PR body, and the review child task of the PR is made to report it as a required fix ([The flow without the final review](#the-flow-without-the-final-review)). The record holds the files outside the scope (`outside`) and a fixed `max` (300) that earlier versions can read (it is not read or shown), and no `lines`. Records written by earlier versions with `lines` and `max` are read and not shown; one whose `outside` is empty (a violation of the line count only) is treated as no violation. The final review of earlier versions judged `REQ` plus `SEC-MIN` (whether the diff is minimal) and failed `SEC-MIN` when there was a violation.
- To widen the scope, cancel the task and rerun it (changes cannot be requested on the preliminary investigation; `reworkTargets`). The implementation prompt asks the agent, when it cannot fix the problem without changing something outside the scope, to write the reason and the scope to widen in its description. The rerun task keeps the security plan ("Rerunning a cancelled task" below).
- In the body of the implementation PR, the purpose section is "修正の範囲（セキュリティ対応）" (the files that may change, the dependencies to raise, how to confirm the fix, the reason for the scope) instead of the requirements (`securityScopeBodyLines`). The section starts with the result of sacty's check (and the violation, if any) and says that the review child task of the PR checks whether the change is minimal (`Task.securityScopeCheck`). For a submission from an earlier version without the check result, it says the Goal Guardian judged it. When an existing PR is taken over, its title and body are not changed ("Taking over an existing PR" above), so the scope is checked in the preliminary investigation's result in the task details.
- A PR to a public repository is created as for other implementations.

## Display while processing before the first step

A task's status stays `queued` from creation until the first step's run starts (`AgentRunStarted`).
A task the daemon is actually processing during this time is shown in the web UI as in progress (`working`) with the text of its phase, not as "Queued".

- The phases (`PreparingPhase`) and their texts are as follows.

  | Phase | What is happening | Japanese text | English text |
  | --- | --- | --- | --- |
  | `repository` | Preparing the target repository (including matching the candidates of a task with several repositories) | 対象リポジトリを用意中 | Preparing the repository |
  | `gathering` | [Information gathering](#information-gathering) | 情報を収集中 | Gathering information |
  | `triage` | The ticket triage that is redone after information gathering | チケットを確認中 | Reading the ticket |
  | `planning` | Deciding how to proceed (from choosing the steps until `StepsChosen` is recorded; includes checking the PR to continue and preparing the base branch) | 進め方を判定中 | Deciding how to proceed |
  | `review_target` | Checking the target PR of the review step | レビューする PR を確認中 | Checking the PR to review |
  | `starting` | Any other work until the first step starts (after the steps are chosen: matching the candidates, preparing an external operation, and so on) | 工程の開始を準備中 | Preparing to start the step |

- The phase is kept only in the daemon's memory (`TaskService.preparingPhases`). It is not recorded in the activity log, and the meaning of `queued` does not change.
  `runNext` (matching the candidates) and `runNextInner` (the other phases) set it right before each piece of work starts, and `runNext` always clears it when it ends.
- It is returned to the web UI only when the status is `queued`, the worker is processing the task (`inflight`, the same mark as "running" in the dashboard's step queue), and the task has never started a step run (no `AgentRunStarted` in the activity log; `firstStepStarted`) (`preparingOf`).
  - If a phase is set, that phase is returned.
  - If no phase is set, `starting` is returned.
    So until the first step starts, a task the queue counts as running always has a phase.
  - `preparing` is added to the tasks of `GET /api/tasks` (`listView`), `GET /api/tasks/:id` (`view`), and `GET /api/schedules/:id` (`ScheduledTasks.get`).
- The following tasks have no `preparing` and stay shown as "Queued" (`waiting`).
  - A task waiting for a slot under the parallel limit.
  - A task waiting for context images to be built.
  - A task between the end of one piece of work and the worker starting the next (for example, after information gathering is recorded and before deciding how to proceed starts).
  - A task not processed yet after the daemon restarts.
- After the first step starts, or the task is paused or stops on a failure, the status is no longer `queued`, so it is not shown.
  The web UI follows by reloading its data every 3 seconds.
- A task that returned to `queued` after starting a step run at least once (between steps, retrying a failed run, checking the target PR again for a re-review, and so on) has no `preparing` even while it is processed, and is shown as "Queued" (this display covers only the time until the first step starts).
- The web UI decides with `statusText` and `statusTone`. The task list, the dashboard, the task details, the rows of related tasks, and the scheduled task details use the same functions, and the status filter of the list uses the same kinds.
- Before the steps are chosen, the steps column shows "Steps not chosen yet" (`parts.bits.choosing`).
- The summary of `sacty mcp` carries the same `preparing` ([MCP server](mcp-server.en.md#task-summary)).

## The "what is running now" line in the overview

The overview of the task details shows one line right above the deliverables about what is running now (`RunStatusLine`).

- While a step's agent is running (the status is `running` and `currentRunId` is set), it shows "Running <step name>", the elapsed time, and "View log". It shows for every step.
  - The step name is the `step` of the `AgentRunStarted` with the same `runId` as `currentRunId`. If the activity has no such record, it is the name of the running step.
  - The elapsed time is from the `at` of that `AgentRunStarted` to now. When there is no start record, or its time cannot be read, the elapsed time is not shown, only the name and the log link.
  - The elapsed time (`elapsedText`) reads "under a minute" below 1 minute, "N min" below 1 hour, and from 1 hour "N h" (when the minutes are 0) or "N h M min".
  - The elapsed time advances with a clock kept on the screen (every 60 seconds), not with a refetch of the data. It is not placed in an `aria-live` region (a screen reader does not read each advance).
  - "View log" is `/tasks/<task>/runs/<run>`.
- Before the first step starts (`queued` with `preparing`), it shows only the same words as the status text (`labels.state.preparing`). The start time and the run ID are not passed to the screen, so the elapsed time and the log link are not shown.
- In other states (queued, awaiting approval, awaiting a decision, paused, completed, cancelled) it is not shown. Work that is not a step run (the check before making a PR, the reproduction tests, the watch after the merge) has no `currentRunId`, so the line is not shown.
- In the overview of the run log screen, "Finished" is the finish time when the end record (`finishedAt`) exists. Without it, it is "Running" when the task is still running that run (the status is `running` and `currentRunId` is that run), and otherwise "No end recorded. …". The "is it running" part travels as `running` in the run log screen's data and in its refetch (`/live/tasks/<task>/runs/<run>`; it is also part of the version).
- The paused section shows these links.
  - "View the error report": only when the error report is shown (`showErrorReport`). It moves to `#error-report` (the right column drops below on a narrow width). The heading it lands on stops below the real height of the fixed header (`--sticky-offset`, measured by `useStickyOffset`), so it is not hidden when the title or the buttons wrap.
  - "View the log of the stopped run": only when `stoppedRunId` returns the run that caused this pause. `TaskPaused` has no run ID, so the order decides: it walks back the activity from the last `TaskPaused`.
    - Failures it takes: a failure of a run whose log can be opened and whose kind is an error (`AgentRunFailed`, `OrchestratorFailed`, `FinalReviewFailed`, and so on; `runLogId` returns an ID and `failureKind` is `error`).
    - Where it stops: it does not link when it reaches another run's row (a start, a completion, a non-error failure, and so on), a resume (`TaskResumed`), or a `TaskPaused` record with reason `manual` found while walking back. It also does not link when the task's own pause reason is `manual`.
    - Only when the reason is `incomplete` (the implementation did not finish) or `unchanged` (the rework changed nothing), it also takes the run that completed just before (`AgentRunCompleted`), because the cause is that completed implementation run. For other reasons it does not link to a completed run. It does not cross a resume or a manual pause.
    - It walks past `TaskPaused` records that follow (a second one after a merge, for example), and skips records that belong to no run.
- While paused, the note beside the Implementation heading is "Paused", not "In progress". The deliverables of other steps do not show "Writing…" while paused (only while running).
- The screen follows a run starting, ending, or pausing with its refetch every 3 seconds.

## Information gathering

At the start of a task (before choosing steps), the information gatherer runs once, collects the information related to the task, and summarizes only what is relevant (`InformationGathered`; the actor is `gatherer`). For a task taken in from a ticket, the same run also does ticket triage (deciding the repository to work in, the title, and the summary) ("Doubling as triage" below). It aligns the background, goals, and constraints that people take for granted before the Orchestrator chooses the plan. There is no approval gate; the summary is shown under "Gathered information" in the task details (collapsed once a step has started).

- What to collect (instructions; not enforced):
  - The description, comments, and linked tickets of the ticket the task was taken in from, and its parents followed upward (the story for a sub-task, the epic for a story). For a GitHub Issue or PR, its body, comments, and linked Issues and PRs
  - The contents of URLs in the task's content, the ticket, and comments
  - Specifications, designs, decisions, and history found by searching for the task's terms with the available MCP servers, external platforms, and the rules of the project's context
  - The target repository's code ("Reading code" below), and how tests are written for a task whose repository to work in is decided
- The instructions have it drop weakly related or superseded information and write both sides of any conflict. The summary is written under fixed headings (goals and background, what to do, out of scope and constraints, related specifications and history, related code, conflicts and open questions, sources that could not be read). The related code heading is used only when it is told to read code ("Reading code" below).
  The heading for how tests are written is used only when it reads code for a task whose repository to work in is decided ("How tests are written" below). It only reads; it does not write or send anything. External text (tickets, comments, linked pages, search results, repository files) is treated as data, and instructions written in it are not followed.
- It runs the same way as the Orchestrator (the default image, the composed context, the host's and the context's external platforms, MCP servers, and the GitHub read relay; `ContextResolved` is recorded). However, external platforms are read-only: the run is registered with the gateway as a read-only run (anything other than GET and HEAD is 403; [Gateway](gateway.en.md#relay-behavior)), and the instructions show only the GET and HEAD rules (`readOnlyPlatforms`). The GitHub read relay is read-only to begin with. MCP servers are not restricted (sacty cannot tell whether a tool only reads, so the instructions have it use only read operations). The AI is `step_agents.gather`, otherwise `step_agents.orchestrator`, otherwise `default_agent`. The session is not saved. The cost is counted toward the task budget (if the budget cap is reached, the task is paused without running).
- From the answer (JSON with the heading `sacty-gathered`) it reads the summary (`brief`; at least 1 character after trimming, up to 30000 characters (`GATHERED_BRIEF_MAX`)) and the sources (`sources`; title and URL; up to 100). When there is no summary or it cannot be read, or the run fails, it records `OrchestratorFailed` (the actor is `gatherer`) and gathers again with a fallback agent if there is one, otherwise pauses (resuming gathers again). It does not proceed without gathering.
- The summary is added to the following instructions (`gatheredLines`).
  - The Orchestrator (choosing steps, choosing the review image, reviewing steps, answering questions), and ticket triage when it is redone after information gathering
  - Every step (added to the step's task content; steps whose instructions do not include the task content (Implementation after Requirements and Design, the after-merge watch check) get it added separately)
  - The runs that judge (deciding where to send PR comments back to, Integration review). Since a person has not approved it, the instructions say to use it only to understand the background and not as grounds for the verdict
- Every reader is told that it was gathered from external text, so anything written in it like an instruction is not to be followed.
- How information from outside the target repository is handled (PBI-302 C4; experiment S2, r5: the gatherer read the documents of the repository the target was imported from (upstream) with `gh api` and used them as a source of the summary): the instructions have it write the code or documents of another repository, external URLs, and documents on MCP servers or external platforms in the summary with their origin (repository name or URL) and an explicit "対象のリポジトリの外" (outside the target repository), in an item separate from the target repository's documents and code. The title in `sources` also gets "（対象のリポジトリの外：…）". A lack of documents in the target repository is not to be written as if outside documents made up for it. The instructions for the readers (steps, the runs that judge, the Orchestrator) say not to treat information marked "対象のリポジトリの外" as the target repository's conventions or decisions (`GATHER_OUTSIDE_LINE`, `gatheredLines`).
- It does not gather for tasks whose steps are already chosen (including activity logs from before this mechanism) or for split child tasks (those with `parent`) (`awaitingGathering`). A child task's content includes the parent's summary (`buildChildBody`). A task created by a rerun gathers as a new task.
- A PR review child task (one with `reviewOf`) does not gather when its parent task has a summary; it inherits the parent's summary and sources (`GatheredInherited`; the actor is `sacty`; it has no cost).
  The task holds the inherited summary together with the parent task's ID (`gathered.inheritedFrom`).
  When the summary is attached to a prompt, the prompt adds that it was inherited from what the parent task gathered, and that it predates the PR, so the content of the PR's changes must be checked against the diff and the code (`gatheredLines`).
  "Gathered information" in the task detail also shows that it was inherited from the parent task.
  When the parent task has no summary (for example a task from a version before gathering) or the parent task cannot be found, the child task gathers.
  Review-only tasks taken in from a review request or the review label, and review tasks created manually, gather as usual.

### Reading code

Information gathering also reads the target repository's code (instructions; not enforced). It has it search the code for the task's terms and check the relevant places (files, functions), the current behavior, and existing conventions. It reads only as far as needed to choose the plan and to give the later steps the background; the fix approach and detailed root-cause investigation are left to later steps (such as Investigation). It looks for the repository's documents not only among those referenced from AGENTS.md, CLAUDE.md, or README but also in the list of directories that hold documents, and reads those related to the task's terms, title, and headings. Even a document that is not referenced, if it sets behavior or premises related to the request (data freshness, operational rules, and so on), is written under "関係する仕様・決定・経緯" in the summary with its location and what it sets (PBI-301 A4). How it reads code depends on whether the repository to work in is decided (`buildGatherPrompt`).

- Decided: the repository is prepared before information gathering (`RepositoryPrepared`; the base commit is fixed here), and a disposable copy of the code at the base commit is placed in the gatherer's workspace to read. If it cannot be prepared, the reason is recorded and the task stops before information gathering.
  When multiple repositories were specified, it rechecks the list after a repository is chosen and instructs the agent to read all of them with `gh api`.
- Not decided (a task waiting for ticket triage, a task without a repository): the repository is not prepared. The candidates (the triage candidates for triage, the project's targets for a task without a repository) are passed in the instructions; without a specified list it picks out the likely relevant ones (at most 3), and with a list it reads all specified repositories, using `gh api` through the GitHub read relay (examples are given for listing files, reading contents, and searching code). For a ticket task whose repository a person chose, it reads that repository. Repositories it could not read (no relay, no permission) are written under the sources that could not be read. Tests check that the ways of reading it shows (`GATHER_GH_EXAMPLES`) pass through the image's gh and the gateway's read relay.
- Orgs among the project's targets whose repository list could not be read (`errors` of `projectRepositories`; the reasons have secrets masked) are not among the candidates, so the instructions list the Org and the reason and have it write them under the sources that could not be read. For a task without a repository and without multiple specified repositories, even when no list could be read and there are no candidates, it gathers without stopping (the step to read code is not shown). A task with multiple specified repositories stops before the run if a specified repository cannot be verified. A task waiting for ticket triage stops before the run when there are no candidates ("Doubling as triage" below).
- When there are neither candidates nor unreadable Orgs, the code section is not added to the instructions.

### How tests are written

For a task whose repository to work in is decided (prepared before information gathering), it also summarizes how tests are written (instructions; not enforced; `buildGatherPrompt`).
For a task whose repository is not decided (a task waiting for ticket triage, a task without a repository), it does not.

- What it checks: the test framework, the command that runs the tests, where tests are placed and how they are named, and examples of existing tests for the related places.
  If there is no test mechanism, it writes that there is none.
- It writes them under the summary heading "テストの書き方" (how tests are written).
- It writes them as facts about the conventions, and does not write whether this task writes tests or which tests confirm it.
  The Orchestrator decides how tests are handled (`testCommand`, `noTests`) ("Orchestrator" and "Tasks without tests" below).
- When the summary is added (`gatheredLines`), for a task with a repository to work in, the following is added.
  - The Orchestrator's step selection: how tests are written in the summary is material for the decision, and how tests are handled is decided by the rules of the instructions, not by whether the summary describes it
  - Step agents: how tests are written in the summary does not mean that tests are needed; whether tests are needed follows the Orchestrator's decision and each instruction

### Execution environment and services

Information gathering runs in a container of the default image without starting services. That differs from the later steps' environment (the image the Orchestrator chooses and the services started for each step). For a task that has a repository to work in (including one decided by triage), an "Execution environment and services" section is added to the instructions, and it has the gatherer do the following (instructions; not enforced; `gatherServiceLines`).

- Do not write the tools, versions, or running things (such as a database) found in the gathering container as facts about the later steps' environment. Read the needed language versions and tools from the repository's configuration and write them.
- Assume that sacty starts the compose services the Orchestrator chose for each step run (they are not running during gathering), and that step agents cannot use docker commands but can connect to the services.
- Search for compose files in subdirectories and under various names, including files referenced by test and development instructions or skills.
- Sort what tests and manual checks need into the following three groups by what each one runs, not by whether the compose service has `build`, and write them under the summary heading "Services needed for tests and manual checks".
  1. Apps that run this repository's code: the step agent starts them inside its container (the start procedure, the names of needed environment variables, and the services they connect to)
  2. Dependency apps managed elsewhere, and databases, caches, mocks, and so on: candidates sacty can start (the compose file and the service names)
  3. Dependencies not in compose: the name of a matching shared compose of the project available to the target (the instructions list names, files, and descriptions), or otherwise a dependency sacty cannot start. Triage with no target lists all entries and their links

The Orchestrator settles the services based on this grouping ([Services](services.en.md#when-services-start)). For a task without a repository, this section is not added.

### Doubling as triage

For a task taken in from a ticket whose repository to work in is not decided yet (`awaitingTicketTriage`), information gathering doubles as ticket triage.

- Before the run, it checks the ticket's destination (a platform of the host or the project's context) and the candidate repositories (the project's targets) (`ticketTriageTarget`). If there is no destination or no candidate, it records the reason (`ticket.triageFailed`) and stops without running.
- The instructions list the candidates and have it choose one repository to work in from the gathered information and write the title (with the key first) and the summary. If a person chose the repository, it is fixed to that repository. The answer is the `sacty-gathered` JSON with `repo`, `title`, `summary`, and `reason` added.
- When the summary of the gathered information can be read, it records `InformationGathered` and then one of the following (`ticketTriaged`).
  - If the repository is a candidate and there is a summary, `TicketTriaged` (the actor is `gatherer`). The cost is in `InformationGathered`, so `TicketTriaged` carries no cost. The task's title and content become the written title and summary. However, if a person has renamed the task before that (`TaskRenamed`; [Renaming a task](#renaming-a-task)), the title stays as the person changed it.
  - If it could not decide (the repository is empty or not a candidate, there is no summary, or there is no answer), it records the reason and stops (`ticket.triageFailed`). The gathered information is kept. A person can choose the repository and resume; resuming redoes only ticket triage (`triageTicket`) (it does not gather again). That instruction also includes the gathered information.
- When the summary cannot be read, triage is not recorded either (as above, it gathers again or stops).

## Orchestrator

It runs once before the steps are chosen (when the task starts). The AI is `step_agents.orchestrator` (or `default_agent` if absent); it uses the default image and reads a disposable copy of the code at the base commit. Its cost counts toward the task's budget. If the budget cap has been reached, the task is paused without running it. Like step runs, it receives the default context and the project's context (rules, skills, MCP servers, external PFs, tier definitions), is told the usable PFs together with the host's PFs, and records `ContextResolved` (PBI-146). When a session that could not be resumed is started anew, it is recorded with that run's ID as well. If the context cannot be prepared, `OrchestratorFailed` is recorded and the task is paused without running it (no cost).

The following are read from the answer (JSON under the heading `sacty-steps`) and recorded in `StepsChosen`.

| Item | Meaning and handling |
| --- | --- |
| `plan`, `reason` | The plan and the reason |
| `baseBranch` | The base branch. If it differs from the default branch, the workspace is prepared again on that branch (if it cannot be prepared, the task continues on the default branch and the reason is replaced) |
| `testCommand` | The test (verification) command (passed to the Reproduce step's instructions and as a candidate verification command for the PR review (a PR review child task has no test command of its own, so it gets none); it is not passed to the Implementation step's instructions (only a command a person specified when resuming is passed); sacty does not run it; 1 to 1000 characters). Even without test code, a check that mechanically validates the artifacts (`kustomize build`, `helm lint`, `kubeconform`, `terraform validate`, `yamllint`, and so on) is asked for when CI, a Makefile or pre-commit runs it, or when the shape of the repository decides it (`kustomization.yaml`, `Chart.yaml`, and so on). If there are several checks to run (several kinds of tests, lint, type checking, manifest validation, and so on), all of the ones CI, a Makefile and so on run are asked to be joined with `&&` into one command (not with `;`, and not by picking just one representative). For a request that also changes code, it is told to include all the checks that cover the changes. For a request whose artifacts are only document files (`documentsOnly` below), it is told not to include code checks (tests, lint, type checking, build) that the document changes do not reach, to write only the repository's document checks (link checking, markdown lint, document formatting, and so on) if there are any, and otherwise to leave it empty and write the basis in `noTests`. For the tool, it is told to prefer an available image that has it, and only when no image has it, to write the command anyway (not leave it empty) and give that reason in `imageReason` ("Verifying the implementation" below). Even if there is an Implementation step but no command, the task does not stop (earlier versions paused; `orchestrator.testCommandUnknown`) |
| `noTests` | Read only when `testCommand` is empty: the basis for judging that the repository has neither tests nor a verification command (1 to 2000 characters). For a plan with Implementation, the Orchestrator is told to always write either `testCommand` or `noTests` (it is told to look at the package settings, Makefile, CI settings, development instructions such as the README, and test files, and to write the basis if nothing is found; a repository that only holds skills or documents also falls under this). It is recorded in `noTestsReason` of `StepsChosen` ("Tasks without tests" below) |

It is recorded in `documentsOnly` of `StepsChosen` only for a plan that includes Implementation and is not a bug fix (otherwise it is discarded). A task that has it is not stopped when the base code has test files after it answered `noTests` ("Tasks without tests" below), and is not stopped even if the implementation's diff has anything other than document files (earlier versions stopped it before the final review; "Deciding the tests on resume" below) |

| `repo`, `repoReason` | For a task without a repository that chose a plan needing one, the repository to work in |

- Task image (when `images` is configured and no image is decided)
  - The prompt asks for one image for the task from `images` (not one per step). Answers per step from an older version (`images`, `defaultReasons`) are not read. The tests also run on this image, so it is to be chosen from `testCommand` and the repository's dependencies (browser tests, DB clients, and so on), preferring an image that has the tools of `testCommand`. Only when no image has them, it is told to write `testCommand` anyway and give that reason in `imageReason`.
  - When the task runs in the default image (the image is absent or `default`), the reason is recorded in `defaultImageReason` of `StepsChosen`; without a reason (no image written, or `default` without a reason), `imageUnexplained` is recorded. The task does not stop; it proceeds in the default image, and the Activity and the task details show that there is no reason.
  - Neither is recorded when `images` is not configured, when the image is decided, or for a task that proceeds without a repository.

If the plan does not need a repository, `testCommand`, `baseBranch`, `services`, and `documentsDir` are discarded.

  - Otherwise (no `images`, or the image is decided), the Orchestrator is not used (`StepsChosen` is recorded by sacty, and the cost is 0).

## Step review

After the steps are chosen, each time a step finishes, the Orchestrator skips the remaining steps that are not needed. It does not add or reorder steps. The final deliverable is approved by a person merging the PR.

- Skippable steps (`skippableSteps`): the remaining steps (active or to do) that are in `SKIPPABLE_STEPS` (`requirements`, `design`, `reproduce`). Only when the plan has an implementation (`implement`) that is not skipped. The design before a split and the design-only plan cannot be skipped. Tasks whose plan a person specified at creation (`requestedPlan`) skip nothing (no review).
- When: when a step finishes (completion of the preliminary investigation `StepCompleted`, approval `StepApproved`, and so on; `advance`) and skippable steps remain, the task holds the finished step in `stepReview`. On the next run (`runNextInner`), the steps are reviewed before running the step (`reviewSteps`). For example, `standard` is reviewed after the requirements are approved (design).
  A task in an activity log from a version that had a preliminary investigation is also reviewed after the preliminary investigation (requirements, design, reproduce). `direct` is not reviewed.
- Prompt (`buildStepReviewPrompt`): it passes the task, the finished step's output (up to the first 30,000 characters), the remaining steps, and the skippable steps, and gives guidelines (skip the requirements when the request itself is the acceptance criteria, the design for a local change that follows existing mechanisms, the reproduction when the cause and fix are clear), and says not to keep steps by guessing at mechanisms the request does not mention. It runs as an Orchestrator run (`runOrchestrator`), resuming the task's Orchestrator session.
- The answer (`skip` and `reason` under the heading `sacty-step-review`; `extractStepReview`) is read and `StepsSkipped` (`after`, `steps`, `reason`, and the cost) is recorded as the Orchestrator's. When `steps` is empty, nothing is skipped. An answer that names a step that cannot be skipped, has no reason, or has the wrong shape is treated as unreadable.
- When the run fails or the answer cannot be read, the task does not stop: nothing is skipped and `StepsSkipped` (empty `steps`) is recorded by sacty (the reason is `orchestrator.stepReviewFailed`). However, if the run failed without confirming that its container stopped (`run.containerNotConfirmed`), the task then pauses (`TaskPaused`) so that the original container and the next step's run do not overlap. When the budget cap is reached, the review does not run (the task pauses before the next step and reviews after resuming). If a person pauses or cancels during the review, nothing is recorded.
- Projection: skipped steps become `skip`, and if the active step is skipped, the next step to do becomes active. `stepReview` is cleared by `StepsSkipped`, by redoing from an earlier step (`reopen`), and by starting a step's run (`AgentRunStarted`). For a task with multiple repositories, a run whose preparation failed before the agent started does not clear it. A record when no review is pending, or that skips a step that cannot be skipped, is rejected.
- Changes are not sent back to skipped steps (`reworkTargets`). The task screen does not show the deliverables of skipped requirements, design, or reproduction.
- Steps after skipping: a design whose requirements were skipped treats the task as the requirements. An implementation without requirements and design (`direct`, or both skipped) follows the task and the gathered information (the preliminary investigation's result if there is one; `basisWithoutRequirements`) and verifies the viewpoint `REQ` as the task's purpose (the request) (`withoutRequirements`, `directImplementLines`). The PR body also treats `REQ` as the task's purpose. For a child task to which the parent task's split assigned test viewpoints, both the instruction and the PR body use the assigned viewpoints instead of `REQ` ([Viewpoints the implementation maps tests to](#viewpoints-the-implementation-maps-tests-to)). The verification basis (`verificationBasis`) treats skipped steps as absent.

## Self-review depth

When the request is light, the viewpoints of the self-review before submitting are narrowed (PBI-369).
The Orchestrator judges whether the request is light when it chooses the steps, and a person can override it to the normal depth per task.

- The Orchestrator writes the size of the request (`selfReviewDepth`: `light` or `normal`) and the reason (`selfReviewDepthReason`) in its answer for the plan (`SELF_REVIEW_DEPTH_LINES`).
  It is told to answer `light` only when the change is small and local, does not change existing behavior, public interfaces, or the shape of stored data, and includes neither a security-related change nor a change that is hard to undo.
  When it cannot tell or is unsure, it is told to answer `normal`.
- sacty reads the answer as follows (`extractStepPlan`, `selfReviewDepthOf`).
  - An answer that is not one of the defined values, or a missing answer, is no judgement (treated as normal).
  - A `light` without a reason is no judgement (the reason could not be shown to a person). The reason is kept to 1000 characters.
  - For the security fix plan (`security-fix`), an answer of `light` becomes `normal`, and sacty's own text (`selfReview.depthForcedNormal`, which includes the Orchestrator's reason) is recorded as the reason.
  - For the plan that splits into child tasks (`split`, the parent of a split), an answer of `light` also becomes `normal`, and sacty's own text (`selfReview.depthForcedNormalSplit`, which includes the Orchestrator's reason) is recorded as the reason.
    A child task cannot choose `split` and chooses its own steps, so a child's judgement stays as the child's own answer.
  - Nothing is recorded for a plan with no step that does a self-review (`SELF_REVIEW_STEPS`): PR review only, investigation only, security check, and operation only.
- The judgement is recorded in `selfReviewDepth` and `selfReviewDepthReason` of `StepsChosen`, and the projection keeps it in `Task.selfReviewDepth` (`judged`, `reason`).
  It is cleared when the steps are chosen again (`clearChosenSteps`).
- On the task detail, a person can override a task judged light to the normal depth, and can undo the override (`POST /api/tasks/:id/self-review-depth`, input `depth` of `ChangeSelfReviewDepthInput`; `normal` overrides, `light` undoes it).
  The steps' states do not matter.
  A cancelled task cannot be changed.
  The request is refused with the reason (409) in these cases.
  - The task is not judged light (`selfReview.depthNotLight`; a person cannot make a task with no judgement or a normal judgement light)
  - The depth is already the same (`selfReview.depthUnchanged`)
- A change adds `SelfReviewDepthChanged` (`from`, `to`; the actor is `person`).
  The projection keeps the override in `Task.selfReviewDepthOverride` (removed when it is undone).
  The override is a person's decision, so it stays when the steps are chosen again.
- The step instructions use the depth at the time they are built (`effectiveSelfReviewDepth`: `light` only when the judgement is `light` and there is no override).
  A change applies from the next run of a step that does a self-review, and the current run is not stopped.
  The run of the first step starts right after the steps are chosen, so an override made after seeing the judgement does not apply to that run (after a pause and a resume, it applies from the rerun).
- The screen shows the depth and the reason for the judgement under the reason for the plan on the "Step settings" tab (`SelfReviewDepthNote`).
  A task judged light gets the action "Use the normal depth" ("Back to the judgement (light)" after an override).
  Nothing is shown for a task without a judgement.
  The activity shows who changed it and when.
- The viewpoints of PR reviews (review child tasks and imported review tasks) do not change with this judgement.

Code: `apps/daemon/src/prompts.ts` (`SELF_REVIEW_DEPTH_LINES`, `extractStepPlan`, `lightSelfReviewLines`, `selfReviewLines`), `apps/daemon/src/service.ts` (`selfReviewDepthOf`, `changeSelfReviewDepth`), `apps/daemon/src/server.ts`, `packages/core/src/events.ts` (`SelfReviewDepth`, `SelfReviewDepthChanged`, `ChangeSelfReviewDepthInput`), `packages/core/src/projection.ts` (`effectiveSelfReviewDepth`, `clearChosenSteps`), `apps/web/src/components/self-review-depth.tsx` (`SelfReviewDepthNote`), `apps/daemon/default-context/skills/review/review-dispatch/references/self-review.md`

## Changing the task image

- On the task detail, a person can change the task image (`POST /api/tasks/:id/image`, input `image` of `ChangeTaskImageInput`). Once the steps are chosen, the steps' states do not matter (running, failed or paused, or awaiting approval). A cancelled task cannot be changed.
- A person can also change it together with resuming a paused task ([Budget, pause, resume, and cancel](#budget-pause-resume-and-cancel)) and with requesting changes ([Request changes](approval.en.md#request-changes)) (`image` of `ResumeTaskInput` and `RequestChangesInput`; `stepSettingChanges`). The checks and the record (`TaskImageChanged`) are the same as when changing on the task detail.
- The choices are the names in `images` and `default` (the default image). The screen lists only the names and shows the chosen image's description (`description` in `images`) below the list (so that a long description does not widen the list). sacty refuses the change with the reason (409) in these cases.
  - A name not in `images` (including a name removed from config.yaml; `image.notInImages`)
  - The current name (`image.unchanged`)
  - The steps are not chosen yet (`image.stepsNotChosen`)
  - config.yaml can't be read or parsed. The names can't be checked, so sacty refuses with the settings problem as the reason (`image.configUnavailable`; `default` too)
- When the daemon's status can't be fetched or the settings can't be read, the screen says the choices can't be checked and shows neither the warning that a name is not in `images` nor the change form (`stepImageOptions`; a temporary failure is not mistaken for a removed name).
- A change appends `TaskImageChanged` (`from`, `to`; the actor is `person`). `from` is the name before the change (`default` if none was set; absent for a task with per-step images from an older version). The projection sets the task's `image` to `to` and keeps the last change in `imageChange` (`from`, `to`, time). `StepsChosen` is not rewritten.
- The changed image is used from the next run of every step (starting a step that hasn't started, a retry, or a rerun after rework). The current run is not stopped. A step run fixes its image when `AgentRunStarted` is appended (a change while the run is being prepared does not change that run; `stepImageOf`). The integration review works the same way. An external operation decides and checks its image before preparing its connection and context. If the image is changed while preparing, the run does not start, as with the agent: the task stays queued without pausing, and the next run decides from the latest settings (even for a name added to config.yaml meanwhile). The check of the after-merge watch fixes its image when `DeploymentCheckStarted` is appended. The `image` of `AgentRunStarted` and `DeploymentCheckStarted` records the name of the image the run uses (a name in `images`, or `default`; older records have none).
- Tasks whose project target specifies an image can be changed too. Changing the target's image does not change the image of a task whose steps are already chosen.
- The screen shows the task image, where it came from (the time a person changed it and the previous name, a person's choice at creation, the project target, a person's choice when rerunning, the Orchestrator, or not set) and when a change takes effect (from the next run of every step) (`taskImageInfo`). The Activity shows who changed it, when, and from what to what.
- When the Orchestrator left the task on the default image, where it came from shows the reason for the default image (`defaultImageReason`) or that no reason was given (`imageUnexplained`) until a person changes it. After a person changes it, the person's change is shown. The "Steps chosen" line in the Activity stays as recorded when the steps were chosen (the later `TaskImageChanged` line shows the change).
- On the screen, "Task image" is usually not changed, so only its heading is shown, collapsed. When the choices cannot be confirmed or a name not in `images` is in use, it is shown open so it is not overlooked.
- Activity from an older version (`StepsChosen` with per-step `images`, and `StepImageChanged`) is read as it is. The projection keeps the per-step `images` and `imageChanges`; when there is no task image, each step runs on that step's image. Instead of the task image, the screen shows "per step (older version)" and, for each step, the image set last with where it came from, and the images used in its runs (or that it has not run yet). The images used in runs come from the `image` of the run records (`AgentRunStarted`, and `DeploymentCheckStarted` for the watch step; `stepRunImages`). For older records without `image`, they are worked out by following the activity and taking the task image and the per-step images at that time (a check of an older task without the watch step used the Implementation step's image). While there is no task image, a step whose image set last is not in `images` shows a warning, with guidance that the step stops when it runs and that choosing a task image makes every step use it (the section is shown open). Once a person chooses a task image, every step uses it from then on (the per-step images remain as the last setting).

## Changing a step's agent

- In the task details, a person can change the agent of each step (`POST /api/tasks/:id/agents`; the input is `step` and `agent` of `ChangeStepAgentInput`). The state of the step does not matter. A cancelled task cannot be changed. The targets are the steps run by step agents (`stepAgentChangeable`). The integration review agent is set by `step_agents.integrate` in `config.yaml` (or `default_agent` if absent) and cannot be changed per task, so it is not shown on the screen and is also rejected by the API (`agent.stepNotChangeable`).
- A person can also change them together with resuming a paused task ([Budget, pause, resume, and cancel](#budget-pause-resume-and-cancel)) and with requesting changes ([Request changes](approval.en.md#request-changes)) (`agents` of `ResumeTaskInput` and `RequestChangesInput`; `stepSettingChanges`). The checks and the record (`StepAgentChanged`) are the same as when changing in the task details.
- The choices are the names of the usable agents (the defaults in `config/agents.yaml` with `agents` of config.yaml laid over them, that have an endpoint and a price; [Configuration](configuration.en.md#usable-agents)). A name is taken exactly as the key, without trimming spaces or limiting its length. Inherited names (`constructor`, `toString`, and so on) are not agent names (`definedAgent`). sacty rejects the change with a reason (409) in these cases.
  - A name not among the usable agents (`agent.notInAgents`)
  - The same name as now (`agent.unchanged`)
  - A step not in the task (`agent.stepMissing`)
  - Integration review (`agent.stepNotChangeable`)
  - config.yaml cannot be read (`agent.configUnavailable`)
- A change adds `StepAgentChanged` (`step`, `from`, `to`; actor `person`). `from` is the name before the change (the name decided by config.yaml if no person chose one). The projection sets `agents` to `to` and keeps the last change per step in `agentChanges`.
- Step runs, the check of the after-merge watch, operations, and exports use the agent a person chose in preference to `step_agents` and `default_agent` in config.yaml (`stepAgentFor`). It is decided at the start of a run (`AgentRunStarted`), so a running run does not change. Step runs and the watch read it from the latest task after preparing. An operation reads it from the latest task after looking up its connection. If it changes while an operation or export is preparing (its connection and context), the run does not start with the old agent; the task stays queued and the next run prepares again with the new agent. If a name chosen again while preparing is not in the settings that run read (it was added to config.yaml meanwhile), the task also stays queued without pausing, and the next run decides from the latest settings. If the chosen name is no longer among the usable agents (removed from the settings, or no endpoint or price), the task does not fall back to the default and pauses with `agent.chosenMissing` (an export records it as the reason it could not export). Tier subagents are placed with the chosen agent as the parent.
- The status (`GET /api/status`) returns the agents that can be chosen (name, runtime, model, reasoning effort; no secret values or endpoint URLs) and the name per step decided by config.yaml (`stepAgents`). The screen shows, for each step, the agent, where it came from (config.yaml, a person's choice at creation, or the time and previous name of a person's change), and when it is used (`stepAgentRows`). The choices are not shown when the status cannot be read or the settings cannot be read, and stub is offered only when the current agent is stub (`stepAgentOptions`). A chosen name not among the usable agents is shown with a warning.
- On the screen, "Step agents" is usually not changed, so only its heading is shown, collapsed. When the choices cannot be confirmed or a name not among the usable agents is in use, it is shown open so it is not overlooked.

## Renaming a task

- In the task details, a person can change the task title (`POST /api/tasks/:id/title`; the input is `title` of `RenameTaskInput`). The state does not matter (running, waiting for approval, paused, or finished). A cancelled task cannot be renamed.
- As at creation, spaces around the title are trimmed, and an empty title or one longer than `TASK_TITLE_MAX` (200 characters) is an input error (400; `input.titleRequired`, `input.titleTooLong`). It is refused with a reason (409) when:
  - The title is the same as now (`title.unchanged`)
  - The PR link in the title (the target of a review or of continuing an existing PR; `referencedPullRequest`) would change, disappear, or newly appear (`title.pullRequestChanged`). Tasks taken in from a PR are not checked, because their target is the PR they were taken in from. Before the repository to work in is prepared (right after creation, or after preparation failed), it checks against the PRs of the repository already decided (`repo`, or `source.repo` of the source).
- A change adds `TaskRenamed` (`from`, `to`; actor `person`). The projection sets the task's `title` to `to` and keeps the last change (`from`, `to`, time) in `titleChange`. Ticket triage (`TicketTriaged`) does not overwrite a title a person changed.
- The new title is used from then on wherever the title is used (step instructions, commit messages, notifications, updates of the PR description, exports, and so on). A running run is not stopped. Publishing a PR (implementation, requirements, design) and retargeting a PR wait while holding the task as it was when they started, so they read the title again just before using it for the title of a PR to create and the PR description (`latestTitled`). The description is made after the PR template is read (`pullRequestBody`). The title in a commit message is the title at the time of the commit's date (fixed for each submission) (`titleAt`; `from` of the first `TaskRenamed` added after the record the time came from. "After" is decided by the order of records, not by clock values, so it does not change even if the clock goes back. If that record is not found, a change at the same time or later is used). Even if a person renames the task after creating a PR failed and then resumes, the commit of the same submission stays the same and can be pushed onto the already pushed branch.
- The title of a PR already created is not rewritten (a PR update changes only the description and the base). The branch name is made from the task ID, so it does not change with the title.
- On the screen, "Rename the task" next to the title opens an input with the current title (`TaskTitle`). When it is refused, the reason is shown and the typed title is kept. While saving, and while Japanese input is being converted, Esc does not close it. When it closes, focus returns to "Rename the task". The Activity shows who changed it and from what to what.

## Verifying the implementation

At the start of Implementation, sacty places the step PR documents from the task branch at their paths. It preserves unpublished changes that differ from the saved copies. Documents are excluded from the implementation diff and tree ID, while their contents contribute to the continuation fingerprint.

After the Implementation step, sacty runs neither the final review (running the tests and judging pass or fail) nor the wait for the PR's CI. The implementation PR is opened as a draft and the review child task of the PR reviews it ([The flow without the final review](#the-flow-without-the-final-review); [ADR](../adr/20261112-0714-superseded-review-child-task-replaces-final-review-and-ci-wait.md)).
How tasks with records of an earlier version's final review are handled is in [Tasks from the version with the final review](#tasks-from-the-version-with-the-final-review).

### The flow without the final review

- When the Implementation step finishes, the task waits for verification (`verification = "pending"`); the next run records `FinalReviewSkipped` (actor `sacty`) and makes it wait to open the PR (`publishPending`).
  Merging the base branch again, test containers, and the final review agent are not run (the diff is taken only to check the scope of a security fix). The Implementation step's agent still runs tests while it works.
  - Before `FinalReviewSkipped`, sacty first merges the commits a person added to the PR branch while the implementation ran (`headSyncedBeforePublish`; [Merging commits a person added to the PR](#merging-commits-a-person-added-to-the-pr)). Then it checks that no conflict markers with the base branch remain in the workspace (`conflictsResolved`).
    If any remain, it does not record it, records `BaseConflictsRemained`, and redoes the implementation (counted and stopped the same way as in [Merging the base branch](#merging-the-base-branch)).
    If it cannot check, the task is paused (`merge.failed`).
  - After that, sacty checks whether the implementation run declared that it finished its scope (`implementationCompleted`).
    If the run declared that it is unfinished, or declared nothing, sacty does not record it, records `ImplementationIncomplete`, and redoes the implementation ([Unfinished implementations and reworks that change nothing](#unfinished-implementations-and-reworks-that-change-nothing)).
    Even when the run declared it is complete, the implementation is redone in the same way if the viewpoint-to-test mapping misses a viewpoint ([Viewpoints the implementation maps tests to](#viewpoints-the-implementation-maps-tests-to)).
  - For a security fix task, before `FinalReviewSkipped`, sacty checks the diff against the fix scope declared by the preceding investigation (`checkSecurityScope`; the check is the same as in "Security fix" below).
    The result is recorded in `securityScope` of `FinalReviewSkipped` (if there is a violation, `violation` holds the files outside the scope and the fixed `max` for earlier versions; `Task.securityScopeCheck`).
    If the diff cannot be obtained, sacty pauses without recording it (`verify.diffUnavailable`).
    A violation does not stop the task; sacty writes it in the scope section of the PR body and has the review child task of the PR make it a required fix ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
- The implementation PR is opened as a draft (when updated, it is put back to draft, except a PR whose draft a person removed; failing to do so does not fail opening the PR), `awaitingReview` is added to `PullRequestPublished`, and the task waits for the Implementation approval (`awaitsReview`).
  A task that continues an existing PR does not make it a draft and does not add `awaitingReview`, because it is a person's PR.
  The PR body writes neither a final review line nor an explanation of Sacty's process (PBI-471). The body holds only the purpose and changes, how it was checked, what a person should confirm, the AI-made mark, and the two approval sentences ([Assembling the implementation PR body](approval.en.md#assembling-the-implementation-pr-body)).
- When the PR is opened, a child task that reviews it is created ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
  When the child task's verdict on the current commit is no findings, the PR check has sacty remove the draft and record `PullRequestMarkedReady` (the PR number, commit, and child task; `markReady`). The PR then waits for a person's approval (merge).
  - The current commit is the current head of the PR on GitHub (`pullRequestHead`; at a PR check, the heads of PRs waiting for no findings are read first, `DRAFT_CHECK_CONCURRENCY` (4) at a time in parallel. sacty waits for each answer up to `DRAFT_TIMEOUT_MS` and aborts the request after that). If a person adds a commit during the review, sacty has the child task review that head again and does not remove the draft from a head that was not reviewed. If the head cannot be read, sacty tries again at the next check.
  - sacty reads the state on GitHub and removes the draft whatever `draft` in the ledger says (nothing happens if it is already removed). It records only when the draft was removed.
  - If the task is sent back or the PR is updated while the draft is being removed, sacty does not record it and turns the PR back into a draft if it still waits for the review (in case the request to remove the draft arrives after the next submission's request to make it a draft).
  - After removing the draft, sacty reads the head on GitHub again. If it differs from the head with no findings or cannot be read, sacty does not record it and turns the PR back into a draft (a person added a commit while the draft was being removed; the next check has it reviewed again).
  - Before recording, sacty reads the child task's current state again. If the head being reviewed, the review round, or the number of verdicts differs from before removing the draft, or the verdict is no longer no findings, sacty does not record it and turns the PR back into a draft (a re-review started while the draft was being removed; the next check tries again).
  - If the answer to the request to remove the draft is lost (the draft may have been removed on GitHub), sacty turns the PR back into a draft, does not record it, and tries again at the next check.
  - If sacty cannot turn the PR back into a draft in these cases (`draft` stays in the ledger), it tries again at every check until it confirms the PR is a draft (`redraftAwaiting`).
  - If the answer to removing the draft is lost, the request might still arrive later, so sacty turns the PR back into a draft at every check until it removes the draft and records it after no findings (remembered per PR and carried over to the next submission after the PR is updated).
  - If a draft change request is still unfinished after sacty stopped waiting for its answer (`draftRequests`), sacty does not remove the draft until it finishes (so that a late request to turn it back into a draft does not turn a PR whose draft was removed back into a draft).
    When sacty stops waiting for the answer, it aborts the request. A request that does not finish even after being aborted is no longer counted after `DRAFT_SETTLE_FACTOR` (10) times `DRAFT_TIMEOUT_MS` (so that the draft can be removed after GitHub recovers).
    At every PR check, sacty reads the state on GitHub (`draft`) and matches it to the ledger (`settleDraft`; for requests that sacty stopped waiting for, aborted, or stopped counting and that reached GitHub later. Even if the daemon does not remember them, after a restart, or after a failure, it tries again at the next check).
    The state it should have is decided from the ledger and the child task's current state (`wantsDraft`). If the head on GitHub cannot be read, sacty does not remove the draft (it changes nothing).
    - A PR waiting for no findings should be a draft (except a PR stacked on a dependency's PR, because a person may remove its draft and merge it. A PR whose draft a person removed is not turned back, by the decision below).
    - A PR whose draft was removed after no findings and recorded (waiting for a person's approval) should not be a draft only while the child task has no findings at the current head on GitHub.
      If it is a draft, sacty removes the draft again (`undraftMarkedReady`; only when the head on GitHub can be read).
      If the head on GitHub differs from the head that got no findings (a person added a commit after the draft was removed, whether or not the person turned the PR into a draft), sacty has the child task review that head again,
      and until then turns the PR back into a draft. Once it gets no findings, sacty removes the draft and records `PullRequestMarkedReady` again with that head.
    - If the task is sent back, the PR is updated, a re-review of the child task starts, or the head changes while the draft is being removed again, or the answer to removing the draft is not received,
      sacty turns the PR back into a draft when the task is not finished and the PR number is the same. If the answer to removing the draft is not received while the record is unchanged, the request might still arrive later,
      so sacty turns the PR back into a draft at every check, also for the next submission, until it removes the draft after no findings (`undraftUnsettled`).
    - For a paused task, if its PR is not a draft on GitHub, sacty turns it back into a draft (`settlePausedDrafts`; the PR is not to be merged while the task is paused. A PR waiting for no findings that is stacked on a dependency's PR, the PR of a task paused because a rework changed nothing (`unchanged`), and the PR of a task paused on findings a rework cannot resolve (`needs_decision`) are excluded. sacty checks `DRAFT_CHECK_CONCURRENCY` (4) PRs at a time in parallel).
      Even when the task was paused while the draft was being removed again, the redraft failed, or no answer came back (`DRAFT_TIMEOUT_MS`), sacty tries again at every check while it is paused.
      After the task is resumed, sacty removes the draft of a PR recorded after no findings again, as above.
  - Except for the redraft that goes with a pause (`settlePausedDrafts`), sacty does not turn a PR whose draft a person removed back into a draft (PBI-468). Before every path that turns a PR back into a draft (submitting a fix, `settleDraft`, `redraftAwaiting`, the changes while `markReady` and `undraftMarkedReady` remove the draft, and `redraftAfterRetarget`), sacty reads the last draft switch on GitHub and decides (`mayRedraft`, `PullRequests.draftHistory`).
    The GitHub actor is the same account for a person and for sacty, so sacty does not use it. It records the ID of the switch event (`ReadyForReviewEvent`) it caused in the activity log and matches against it.
    1. It reads the current draft state through REST. If the PR is a draft, it proceeds as before (nothing is recorded).
    2. If it cannot read the draft state or the timeline, it does not turn the PR back into a draft (reason `unreadable`; it reads again at the next check).
    3. If there is no switch at all, or the ID of the last ready switch is in sacty's record of its own (`PullRequestUndraftNoted`), it turns the PR back into a draft as before.
    4. If the last ready switch is not in the record and the last `PullRequestUndraftNoted` has no ID, or only a record from an earlier version exists (a `PullRequestMarkedReady` or a `PullRequestRetargeted` with `ready` that lacks `undraftTracked`, which the version that remembers its removals with `PullRequestUndraftNoted` adds), or the last switch is `convert_to_draft` while the PR is not a draft, it does not turn the PR back into a draft (`undetermined`).
    5. Otherwise, the last ready switch is not in the record, so a person made it, and it does not turn the PR back into a draft (`person`).
  - When sacty removes a draft (`markReady`, `undraftMarkedReady`, the retarget, and the removal after verification), it records `PullRequestUndraftNoted` (PR number, `eventId`) from the answer of `setDraft` (`changed`: whether the switch request was called; `previous`: the ID of the last ready switch before the request; `readyId`: the ID of the last ready switch in the answer) (`noteUndraft`).
    - No change (the draft was already removed and the switch request was not called): nothing is recorded (a PR whose draft a person removed becomes `person` in step 5).
    - No earlier ready switch (read, and zero found) and the answer has an ID: it records that ID (the first removal of a PR sacty created as a draft).
    - The earlier ready switch was read and the answer's ID differs from both that ID and the recorded IDs: it records the ID. If it is the same (the timeline has not caught up yet), sacty reads again once, records the ID if it now differs from both, and otherwise records no ID.
    - The earlier ready switch could not be read, the answer has no ID, or the answer was lost: it records no ID (it cannot tell whether sacty made the last switch, so it does not turn the PR back into a draft). When the answer was lost and the previous record already has no ID, it does not repeat it.
  - When it does not turn a PR back into a draft, it records `PullRequestRedraftSkipped` (PR number, reason; `person` carries the `eventId` of the removal) (`noteRedraftSkipped`). Duplicates are decided from the activity log.
    `person` is not recorded again when the same `eventId` is already recorded. `unreadable` is not recorded when the last record is `unreadable` and nothing has been read since the daemon started (`draftReadable`). `undetermined` is recorded once per PR. Nothing is recorded for a PR that is a draft in the first place.
  - When it submits a fix to a stacked PR, it does not stop with `pr.stackDraftFailed` when the decision is not to turn the PR back into a draft (including when the draft state cannot be read). When the decision is to turn it back and that fails, it stops as before.
  - The review rounds of a PR it did not turn back into a draft go on as they are (the ledger keeps waiting for no findings).
  - After the two new event types (`PullRequestUndraftNoted`, `PullRequestRedraftSkipped`) are recorded, the earlier version of the daemon cannot read the activity log and cannot start (`toEvent` in `activity.ts` parses every row with `EventInput`). There is no compatibility layer. A defect is fixed by releasing a fixed version, not by rolling back ([ADR](../adr/20261121-2022-do-not-redraft-pull-request-a-person-marked-ready.md)).
  - The date and subject of the implementation PR's commit are those of when the Implementation step finished (`outputAt`), because there is no final review date.
  - If the answer to removing the draft says the PR is still a draft, sacty does not record it and tries again at the next check.
  - After the draft is removed, checks compare the reviewed head with the head that got no findings (`reviewedCommit`), so the same head is not reviewed again.
  - sacty waits up to `DRAFT_TIMEOUT_MS` (30 seconds) for GitHub's answers to removing or restoring the draft (including when updating the PR) and to reading the head. If no answer comes, it treats the answer as lost.
  - The recorded head is kept as the head with no findings (including commits a person added), and dependent child tasks stack on it (`reviewedPullRequest`).
  - A PR waiting for no findings is turned back into a draft on GitHub once after the daemon starts, whatever `draft` the ledger has (`redraftAwaiting`; for when it could not be turned back at submission, or the memory that it could not be turned back was lost on restart). If that fails, it is turned back at every check until it has no findings. Once it succeeds, sacty does not repeat it for the same submission. A PR whose draft a person removed, and similar PRs, are not turned back into a draft by the decision (`mayRedraft`).
  If the draft cannot be removed, nothing is recorded and the next PR check tries again. If the parent changes while removing it (request changes, a PR update), nothing is recorded.
- sacty neither waits for nor reruns the PR's CI. No new entries are added to the flaky test ledger.
  After the PR is taken out of draft with no findings, the PR check reads CI and, when it was failing, shows it in the task details and on the task's row in the task list, and clears it when CI passes while it is still being read (it only shows it; [Showing a CI failure after no findings](approval.en.md#showing-a-ci-failure-after-no-findings)).
- Even when the orchestrator cannot decide the test command for a task that includes implementation, or the judgment that there are no tests cannot be used, the task does not stop (it does not stop with `orchestrator.testCommandUnknown` or `orchestrator.noTests*`, because sacty does not run the tests; [Tasks without tests](#tasks-without-tests)).
- In the implementation instructions of a task without tests (`noTestsReason`), the agent is told to run the tests it prepared itself before submitting and to write the command it ran and the result in the implementation's description (sacty does not run the declared test command). It is told that the review child task of the PR checks the acceptance (`NO_TESTS_JUDGE_BY`, `ADDED_TEST_COMMAND_LINE`).

### Merging the base branch

So that the implementation PR does not stay in conflict with the base branch, sacty merges the latest base branch into the implementation workspace on the host. History is not rewritten (no force push, no rebase). A task that takes over an existing PR ([Taking over an existing PR](#taking-over-an-existing-pr)) pushes to a person's PR branch, so it does not merge the base branch.
A child task stacked on a dependency's PR, while stacked, merges in the dependency PR's passing commit instead of the base branch, at the same points and in the same way ([Task split and integration review](split-and-integrate.en.md#child-tasks-stacked-on-a-dependencys-pr)).

- When it merges (`syncBase`):
  - Before the implementation run starts (`runNextInner`). This is the same for the first run and for redoing the implementation after a rejection, after taking in PR comments, or after a re-review.
  - It does not merge while the task waits for approval (when a person rejects it or writes PR comments, it merges before the implementation is redone). A conflict of the PR waiting for approval is shown on the screen ([Showing a conflict with the base branch](approval.en.md#showing-a-conflict-with-the-base-branch)).
  - It does not merge when `ServiceDeps.mergeBase` is `false` (for tests; the default is to merge).
- How it merges:
  1. It fetches the head of the base branch (`repository.baseBranch`) into the saved metadata (`fetchBranch`). If it equals the commit the workspace is currently based on (`workBaseCommit`: the base commit before a merge, the last merged head after it), nothing happens.
  2. If the head is already in that commit's history, nothing happens. Otherwise it merges the workspace contents (including new files; files excluded by `.gitignore` and the tool locations stay out) with the head three ways, using that commit as the common ancestor (`mergeBase`; `git merge-tree --write-tree --merge-base`; the host needs git 2.40 or later, and an older git gives `git.mergeTreeUnsupported`). Because `merge-tree` in git 2.40 to 2.44 does not accept trees, the workspace contents (and the trees with excluded paths removed) are passed as temporary commits that are not on any branch (with a fixed author and date).
     When the merge conflicts but git does not report which files conflicted (for example, it cannot decide where a directory moved, so no markers can be written), the resolution cannot be checked, so it stops without changing the workspace (`git.conflictWithoutFiles`; the same for merging commits a person added to the PR).
     When more than `MAX_BASE_CONFLICTS` (1000) files conflict, it stops without changing the workspace and shows the count and the limit (`git.tooManyConflicts`; the task pauses with `merge.failed`). It uses none of the workspace's git settings, filters, or hooks, and adds no commit to any branch (it creates the temporary commits passed to `merge-tree`, but puts them on no branch).
  3. It writes the result into the workspace (`git read-tree -m -u`). Conflicting files keep markers (`<<<<<<<`, `=======`, `>>>>>>>`): the upper side is the implementation, the lower side is the base branch.
  4. It records the merged head and the list of conflicting files (all of them; it is not truncated) in `BaseBranchMerged`. `Task.baseMerge` holds the last merge. The recorded base commit (`Task.repository.baseCommit`) is not changed. When the workspace is prepared again with another base branch chosen (`RepositoryPrepared`), `baseMerge` is cleared.
- Files with markers left (`conflictMarkers`): among the conflicting files of `BaseBranchMerged`, those that match either of the following.
  - Files that still have any marker line sacty wrote. The start line (`<<<<<<<`) and the end line (`>>>>>>>`) carry a tree or commit ID as a label (`<<<<<<< <ID>`). When both sides rename the same file to different names and the contents also conflict, for example, the markers get longer (`<<<<<<<<`; seven or more are read) and the label gets a path (`<<<<<<<< <ID>:ours.txt`). A marker line forgotten on only one side counts as left. Similar lines without the label, and a lone `=======` (which cannot be told from a Markdown heading underline), are not markers.
  - Paths whose name git moved aside when a directory and a file collided (`<name>~<ID>`), while they still exist.
  It reads only regular files (not symbolic links, and nothing that points outside the workspace) and skips files over 20 MiB. While markers remain, it does not merge again and returns those files. A conflict that cannot hold markers (a binary, a deletion on one side, and the like) cannot be confirmed as resolved by markers, and only one side's contents would remain (the other side's changes could be lost), so the merge stops without changing the workspace (`git.conflictWithoutMarkers`; the same for merging commits a person added to the PR). For each conflicted file it reads the result and counts those without marker lines. A path missing from the result is not counted if both sides removed it (for example, both sides renamed the same file to different names). The names git used to avoid a clash (`<name>~<ID>`) and their original names are checked by whether they remain, so they are not counted.
- The implementation prompt (`mergeConflictLines`): before the implementation run starts, if any file still has markers, the prompt gives the list and how to resolve them: what the upper and lower sides mean, keep the intent of both, do not rewrite or remove the base branch's changes as one's own, remove every marker line, if a file named `<name>~<ID>` exists put the content to keep under the right name and delete the moved-aside file, and do not run git merge, rebase, fetch, commit, or push.
- If markers remain before opening the PR (before `FinalReviewSkipped`; `conflictsResolved`), the PR is not opened; sacty records `BaseConflictsRemained` and the implementation is redone.
  - It counts as a failed verification (`verifyFailures`; the redo prompt gets "the previous verification: conflict markers with the base branch remained" and the list). A record from an earlier version of a merge before verification that newly conflicted (the base branch moved during the implementation run; `fresh` of `BaseConflictsRemained`) is not the agent's mistake, so it is not counted. The current version does not merge the base branch before verification, so merging the base branch does not record `fresh` (merging commits a person added to the PR does; [Merging commits a person added to the PR](#merging-commits-a-person-added-to-the-pr)).
  - If it fails `MAX_VERIFY_ATTEMPTS` (3) times in a row, the task is paused (`verification`) with the conflicting files shown (`verify.mergeConflictsRemain`). Resuming resets the count and redoes the implementation with the files that have markers.
  - A task paused with markers left cannot be moved to review by a person (`canOverrideVerification`).
- When the fetch or the merge fails, the implementation is not run (`AgentRunFailed`) and the task pauses with the reason (`merge.failed`). Resuming starts again from the merge. If the host's git is older than 2.40 and `git merge-tree --write-tree --merge-base` is unavailable, it shows `git.mergeTreeUnsupported`.
- The implementation after a merge:
  - The base of the implementation diff, of the per-file changes, and of the no-changes check is the merged head (`workBaseCommit`). The base branch's own changes are not part of the implementation diff.
  - When the workspace is prepared again, it is prepared at the merged head (not reset to the base commit).
  - The commit that is submitted (`publish`) is a merge commit with the merged head as the second parent when that head is not yet in the history of the parent commit. If it is, there is one parent. If it is not in the history, a merge commit is made even when the contents equal the parent's. The commit date is fixed per submission (resuming makes the same commit).

### Merging commits a person added to the PR

A person may add commits to the branch of a PR that sacty opened (applying a review suggestion, merging the base branch from the GitHub screen, and so on).
sacty merges those commits into the implementation workspace and then stacks on their tip.
It does not remove the person's changes and does not force-push.
A task that takes over an existing PR ([Taking over an existing PR](#taking-over-an-existing-pr)) stacks on the person's PR branch, so it does not merge (`publishContinued` stacks on the previously pushed commit or the tip).

Related ADR: [Merge commits a person added to a sacty PR into the workspace, and keep a person's edits to the PR body with a three-way merge](../adr/20261112-1553-keep-human-edits-on-sacty-pull-requests.md)

- When to merge (`syncPullRequestHead`):
  - Before starting the implementation run (inside `syncBase`, before merging the base branch). The same applies when the implementation is redone after a send-back, imported PR comments, or a re-review.
  - Before opening the PR (`headSyncedBeforePublish`; commits added while the implementation ran).
  - Right before publishing the PR (`publish`).
  - It merges even when the setting `ServiceDeps.mergeBase` (for tests) is `false` (`false` only stops merging the base branch).
- How it merges:
  1. If sacty has not pushed yet, do nothing.
     If markers remain in the files that conflicted in a merge not yet submitted (`pendingHeadMerge`), do not fetch the tip or merge further, and return those files (so that a new merge record does not erase the record of the remaining markers).
  2. Fetch the tip of the branch sacty last pushed (`Task.pushedBranch`) into the moved-aside metadata (`fetchBranch`).
     If it cannot fetch (for example the PR was merged and the branch deleted), continue without merging and write the reason to the daemon log.
  3. If the tip equals the commit sacty last pushed (or the tip of a merge not yet submitted, if any), do nothing.
  4. Otherwise, three-way merge the workspace contents and the tip, with the commit sacty last pushed (or the tip of a merge not yet submitted, if any) as the common ancestor (`mergeBase`; the same mechanism and limit as merging the base branch).
     The requirements and design files carried over from the task branch (`path` of `stepPullRequests`) are removed from the trees on both sides before merging (`exclude` of `mergeBase`).
     Those paths in the workspace are not changed. On submission, sacty compares them with the saved copies, includes workspace fixes, and otherwise carries over the task branch versions.
  5. Record `PullRequestHeadMerged` (the branch, sacty's commit before the merge, the merged tip, and every conflicted file).
     `Task.headMerge` holds the last merge.
     While sacty has not yet stacked on that tip (`from` is the currently pushed commit, on the same branch), it is a merge not yet submitted (`pendingHeadMerge`).
     Because the merge changes the workspace contents, the implementation step's verification result (`implementVerification`) is discarded.
     It is cleared when the workspace is prepared again for a newly chosen base branch (`RepositoryPrepared`).
- On conflicts:
  - Before the implementation run, the conflicted files are passed to the implementation instructions (see "Implementation instructions" below).
  - Before opening the PR, record `BaseConflictsRemained` and redo the implementation. A new conflict is not counted (`fresh`); remaining markers from the previous merge are counted.
  - Right before publishing (waiting to open the PR; `publishPending`), the PR is not opened; the conflicted files become `verifyFeedback` (`merge`) and the implementation is redone (the projection of `PullRequestHeadMerged`; not counted).
  - Whether markers remain is checked the same way as for the base branch merge (`pendingConflicts` is the conflicted files of the base branch merge and of the merge not yet submitted, together).
    If markers from the merge not yet submitted remain right before publishing, sacty does not push and pauses (`pr.headConflicted`).
  - If it cannot merge, it pauses with the reason (`pr.headMergeFailed`).
- Pause and cancel: after waiting for the fetch of the tip, and right before the push (after preparing authentication and so on), sacty checks whether a pause or cancel was requested; if so, it neither pushes nor updates the PR.
- Submitting (`publish`):
  - If there is a merge not yet submitted, stack with the merged tip as the parent (otherwise, as before, the previous PR's commit). When sacty stopped after pushing on the person's tip and before updating the PR and then resumes, it stacks on the commit already pushed to the same branch (going back to the previous PR's commit would not be a fast-forward push).
    Because it stacks on the person's tip, the push is a fast-forward.
  - For a task that stacks on a task branch, the check for changes sacty did not push (`pr.taskBranchChanged`) starts from the merged tip.
    The person's changes that were merged are not checked again.
    When sacty has not stacked the implementation yet (the first submission), it checks from the starting point and stops, as before.
- Implementation instructions (`mergeConflictLines`, `headMergeLines`; the bug-fix flow too): if sacty has merged such commits (`Task.headMerge`; including a redo after sacty stacked on the merged tip and pushed), they say that a person added commits to the PR branch, the merged tip, not to remove, revert, or rewrite the person's changes (change them only when this round's comments ask to), and not to merge, rebase, fetch, commit, or push with git.
  If files conflicted, they give the list, that the part above the marker is the implementation side and the part below is the person's side, and to keep the person's changes while removing every marker line.
  Conflicts with the base branch are passed in a separate section as before (`baseConflictLines`).
  When the previous verification found markers only in files that conflicted in the person's merge, the heading is "前回の検証：人が PR に足したコミットとの競合の目印が残っていました" (`feedbackLines`).
- In the activity log: "Merged the commits a person added to the PR branch … (…) into the workspace", with the number of conflicted files and the first five.

Code: `apps/daemon/src/service.ts` (`syncPullRequestHead`, `syncBase`, `headSyncedBeforePublish`, `conflictsResolved`, `publish`, `pendingConflicts`), `apps/daemon/src/repository.ts` (`mergeBase`), `apps/daemon/src/prompts.ts` (`mergeConflictLines`, `headMergeLines`, `baseConflictLines`, `feedbackLines`), `packages/core/src/events.ts` (`PullRequestHeadMerged`), `packages/core/src/projection.ts` (`headMerge`, `pendingHeadMerge`), `apps/web/src/lib/labels.ts`

### Opening the implementation PR

Publishing stops if the workspace and task branch changed the same document differently. Document-only fixes can be published; a missing copy or workspace file is retained from the task branch. A path that is not a regular file stops publishing.

- When `FinalReviewSkipped` is recorded, the Implementation step is not finished; the task waits to open the PR (`Task.publishPending`; the status is queued). sacty then commits and pushes the implementation workspace and opens the implementation PR as a draft (if there is already a PR, it updates it and puts it back to draft; [The flow without the final review](#the-flow-without-the-final-review)). No agent is used, except that when updating an existing PR, if the person's edits to the body and sacty's new body overlap in the same place, the orchestrator agent reconciles them ([Updating a body a person edited](approval.en.md#updating-a-body-a-person-edited); its cost counts toward the task's budget). The commit date is the time the Implementation step finished (resuming makes the same commit).
  - The first line of the commit (`commitSubject`, `detectCommitConvention`; PBI-301 A8; experiment S5 r2): only when the repository defines the Conventional Commits form does sacty prefix the title with a type (`feat: <title>`). The repository defines it when any of the following holds. A Commitizen or commitlint configuration file exists (`.czrc`, `.cz.json`, `commitlint.config.*`, `.commitlintrc*`, and so on). `package.json` has a commitlint or commitizen setting or dependency. AGENTS.md, CLAUDE.md, CONTRIBUTING, or README mentions Conventional Commits, Commitizen, or commitlint, or gives both `feat:` and `fix:` as examples. A commitlint configuration that sets the first line's form itself (`headerPattern`, `parserPreset`) cannot be interpreted, so it is treated as not defining it (even if `package.json` has a dependency or another file has a setting, the custom form takes priority and no type is added). The definition is read from the base commit, not from the workspace the agent may have edited (`COMMIT_CONVENTION_FILES`; resuming makes the same commit, and when it cannot be read it is treated as not defined and the title is used as is). The type is `docs` for the implementation of a documents-only request, `fix` for a bug fix, and `feat` otherwise; the commit of a Requirements or Design PR is `docs`. A title that already has a type (`feat: …`, `fix(api): …`) is not prefixed again. For a repository with no such definition, the title is used as is, as before. The `sacty task <ID>` on the second line on is unchanged. The commit a task that takes over an existing PR adds is handled the same way. The length of the first line is not changed (a long title may not fit in a repository that sets a length limit).
  - If the repository cannot use draft PRs (GitHub's 422), the PR is opened as a normal PR (a child task stacked on a dependency's PR stops without recording when it cannot be made a draft; [Task split and integration review](split-and-integrate.en.md#child-tasks-stacked-on-a-dependencys-pr)).
  - A task that takes over an existing PR pushes to the person's PR branch and does not open a new PR ([Taking over an existing PR](#taking-over-an-existing-pr)).
- After opening the PR, sacty records `PullRequestPublished` and the implementation submission (`StepSubmitted`, with `step` set to `implement`) in the same append, and the task waits for the Implement approval. If the implementation changed nothing and there is no PR yet, sacty records `NoChangesFound` and the implementation submission without opening a PR ([Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).
  If the rework of the implementation changed nothing in an existing PR and AI review findings remain on its head, sacty pauses the task instead of submitting ([Unfinished implementations and reworks that change nothing](#unfinished-implementations-and-reworks-that-change-nothing)).
- If opening the PR fails, the reason is recorded and the task stops (`pr.failed` and so on). Resuming opens the PR again without redoing the implementation (waiting to open the PR survives a pause and a restart).
- If a push is rejected by a temporary failure, the task does not stop; only the push of the same commit is retried (PBI-467. The same applies to a taken-over PR and to the requirements and design PRs. Deleting a branch is out of scope).
  - Temporary failures: `[remote rejected] ... (failed)`, a GitHub internal error (`Internal Server Error`), HTTP 5xx (`RPC failed; HTTP 500` and so on), rate limits (429, and a 403 that says it is a rate limit), and connection failures (`Could not resolve host`, `Connection reset`, `timed out`, `the remote end hung up unexpectedly` and so on).
  - Failures that are not temporary stop at once without a retry: a rejection by protection or a rule (`GH006`, `GH013`), a `[remote rejected]` whose reason is not `(failed)` (including `refusing to allow an OAuth App ...` because the token has no `workflow` scope), a non-fast-forward (`[rejected]`), an authentication failure, and a failure that matches none of the temporary ones above.
    The reason code that stops the task (`pr.failed` and so on) is the same with or without the retries.
  - Count and waits: up to 3 retries after 15 seconds, 1 minute, and 3 minutes (`pushRetryDelaysMs`). The task keeps its run slot while it waits.
  - The decision is made by running the push with `LC_ALL=C` and reading git's English messages (it does not depend on the daemon's `LANG`).
  - After waiting, right before pushing again, sacty records the retry number, the limit, the wait, and the failure text (secrets hidden) in `PushRetried`.
    When the push goes through it records `PushRetryEnded` (`outcome: pushed` and the number of retries); when it still fails at the limit it records `PushRetryEnded` (`outcome: failed`) and stops as before.
    If the same commit is already at the head of the branch (an earlier try went through and only the response was lost), the push goes through and counts as pushed (that try also counts as a retry).
  - If a pause, a cancel, or a daemon stop is requested while waiting, it stops waiting without pushing (it records nothing and does not overwrite the pause reason).
  - When a person resumes after the stop (including a task stopped before the push-retry records existed) and no new comment has reached the PR, sacty does not run an agent; it redoes the push that stopped.
  - In the reason text that stops the task, sacty drops the `remote:` guidance lines (an empty line, `Create a pull request ...`, `To create a merge request ...`, and a line with only a URL) and puts the failure lines (lines starting with `!`, `error:`, or `fatal:`) first. The `remote:` lines that give the reason for a rejection stay.
- The PR is opened even when the budget cap has been reached (it costs nothing and only waits for a person's approval; see "Budget, pause, resume, and cancel" below). When the body overlaps, the agent is not run if the budget cap has been reached, and the person's body is left unchanged.
- Pausing by a person: if a pause or cancel has been requested before the push or right before opening the PR, the task stops without opening the PR (for a pause, it keeps waiting to open the PR; resuming opens it). If the request comes after opening the PR has started, the PR is finished and recorded first (stopping without recording the opened PR could open a second PR on resume, or leave a PR that cancelling can't close), and then the final state depends on the request.
  - Pause: the task stays waiting for the Implement approval and is not paused. The pause operation reports that the task was not paused because it is waiting for approval (`pause.reachedApproval`; 409).
  - Cancel: after opening the PR finishes, the recorded PR is closed and the task is cancelled (the cleanup in "Budget, pause, resume, and cancel" below).
- Waiting for approval (approval by merging the PR, Request changes, and importing PR comments) works the same as for Requirements and Design ([Approval and request changes](approval.en.md)). Approving the implementation by merging the PR moves on to the after-merge watch step (if it is skipped, the task is completed).
- If a person merges the implementation PR while the implementation is being reworked (after a rejection or imported PR comments), the rework (the run and the PR update) is stopped and the merge is taken as the approval. No new PR is created ([Merging during a rework of the implementation](approval.en.md#merging-during-a-rework-of-the-implementation)).

### Viewpoints the implementation maps tests to

Related ADR: [Assign the parent design's test viewpoints to child tasks of a split, and do not submit an implementation that misses a viewpoint](../adr/20261115-1345-assign-test-viewpoints-to-child-tasks.md)

- The viewpoints the Implementation step maps tests to (`implementViewpoints`) are decided in the same way as the viewpoints the implementation instruction lists (no mapping is required for a viewpoint the instruction does not list).
  1. A task with the Design step: the test viewpoints of the task's own approved design
  2. A task with the Reproduction step (a bug fix): that the reproduction test passes (assigned viewpoints are not used)
  3. A task with neither: the viewpoints assigned by the parent task's split (`Task.inheritedViewpoints`; [Task split and integration review](split-and-integrate.en.md#splitting)). If there are none, the purpose of the task or its acceptance criteria (`REQ`)

  A step skipped by the step review is treated as absent.
- The implementation instruction of a child task with assigned viewpoints lists them instead of `REQ` (for an implementation without Requirements and Design, and for one without Design).
  The viewpoint table in the PR body (`resultTableLines`), the viewpoints passed to the PR-review child task, and the viewpoint table in the task details use the same viewpoints.
- Unmapped viewpoints (`unmappedViewpoints`): viewpoints to which the viewpoint-to-test mapping (`sacty-test-map`) maps neither a test nor a reason for writing no test (`untested`).
  - Even when a run declared it is complete, it does not go on to the submission if a viewpoint is unmapped.
    sacty records the IDs of the unmapped viewpoints (`unmapped`) in `ImplementationIncomplete` and redoes the implementation with them.
    Counting, stopping, and resuming are the same as for an unfinished run ([Unfinished implementations and reworks that change nothing](#unfinished-implementations-and-reworks-that-change-nothing)). The message when it stops is `implement.unmappedViewpoints`.
  - A viewpoint that cannot be verified by a test (running the checks themselves, or something a person confirms) is mapped with empty `tests` and an `untested` that gives why no test verifies it and how it was checked (or who checks it) (PBI-416). The implementation instruction (`UNTESTED_LINES`), the rework instruction for missing viewpoints (`feedbackLines`), and the instruction of the run that asks only for the declaration say so. Reading the mapping and deciding what is missing do not look at the kind of reason (a viewpoint with an `untested` reason is mapped). A viewpoint that changes executed behavior (code, configuration values, scripts) still gets a test and is not put in `untested`.
  - Tasks without tests, and requests that change only documents, write no tests, so no mapping is required.
  - For a task whose only viewpoint is `REQ`, and for a task with the Reproduction step, unmapped viewpoints are not checked.
  - An implementation instruction whose mapping is checked says, after the viewpoints, that the run is not submitted when a viewpoint is unmapped (`unmappedViewpointLines`).
  - A run that finds no change is needed (it changes nothing in the workspace) goes through the same check.
    It maps, for each viewpoint, the existing tests that check that viewpoint, and then goes on to the no-change confirmation (`NoChangesFound`).
- For a child task created by a split, the instruction of an implementation without Requirements and Design tells the agent the scope of the child task (`directImplementLines`).
  It says that Requirements and Design are skipped because the parent task already approved them, that the change is not necessarily small, and that the scope is everything written before the heading "親タスクの要求要件（承認済み）" in the task content (what follows that heading is what sacty attached from the parent task).
  For a task that is not a child task, it says the steps are skipped because the request is clear and follows existing mechanisms.
- Every implementation instruction states the order: implement the whole scope first, then go on to the pre-submission verification and the implementation description (`IMPLEMENT_ORDER_LINE`).

### Unfinished implementations and reworks that change nothing

Related ADR: [Do not submit an unfinished implementation, and do not reach a dead end on a rework that changes nothing](../adr/20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)

When an implementation run ends, sacty submits the workspace as it is (it opens or updates the PR).
A run that ended after implementing only part of its scope, and a run that changed nothing after AI review findings, are not submitted (PBI-347).

- Completion declaration: the instruction of the Implementation step makes the agent always declare whether it finished its scope, in a code block whose language name is `sacty-completion` (`implementCompletionLines`).
  - The declaration is a JSON object written inside the code block. Its only keys are `status` (`complete` or `incomplete`) and `remaining` (the list of what remains; it may be omitted).
    `remaining` holds up to 20 items of up to 300 characters each, and the rest is cut (`COMPLETION_REMAINING_MAX`, `COMPLETION_REMAINING_ITEM_MAX`; never in the middle of a character).
  - Only the inside of this code block is read as a declaration (`extractCompletion`, `takeFences`). The code block marks where a declaration starts and ends.
    The code block is found by the CommonMark fence rules, the same as the test command declaration.
    JSON or text outside the code block, and an example written inside another code block, are not treated as a declaration.
  - A declaration code block is used only when its whole content reads exactly in the fixed shape (`readDeclaration`). A block that matches any of the following is an unreadable declaration (sacty does not guess which value was meant).
    - It cannot be read as JSON, it is not an object, or the code block is not closed
    - It has a key other than `status` and `remaining`
    - A key is duplicated (`hasDuplicateKeys`; JSON is read with the later value overwriting the earlier one; a block nested too deeply to check for duplicates is treated the same way)
    - `status` is neither `complete` nor `incomplete`
    - `remaining` is not a list of text
  - The run is complete only when every declaration code block is readable and every one is complete.
    - No declaration code block, or at least one unreadable declaration: undeclared (treated as unfinished and not submitted)
    - All readable, and the last declaration is unfinished: unfinished (what remains comes from the last declaration)
    - All readable, the last declaration is complete, and another one is unfinished: undeclared
    - A `complete` declaration is read as unfinished when `remaining` lists something
  - The declaration is kept in `completion` of `AgentRunCompleted`. When the run is undeclared, it is `null`.
    Declaration code blocks, including unreadable ones, are removed from the implementation description (the PR body).
    A code block of the same name in the output of a step other than Implementation is not read as a declaration and stays in the body.
  - Records from versions before the declaration have no `completion`. Such records go on to the submission without the declaration being checked.
- When unfinished: before `FinalReviewSkipped`, sacty checks the declaration of the last run (`Task.implementCompletion`).
  If it is `incomplete` or `null`, sacty records `ImplementationIncomplete` and continues the implementation. It does not open or update the PR.
  The record holds what remains, that nothing was declared (`undeclared`), and a mark of the workspace content (`fingerprint`).
  - The declaration is checked before the conflict checks (merging the commits a person added to the PR, and checking for conflict markers; `headSyncedBeforePublish`, `conflictsResolved`).
    An unfinished run is recorded as unfinished even when conflict markers remain, and what remains is passed to the next instruction. Conflicts are checked on a run that declared it is complete (the conflicting files stay in the implementation instruction until they are resolved).
  - The next Implementation run continues the same agent session as the run that ended unfinished (the continuation of an Implementation run that ended unfinished, in [Agent execution](agent-execution.en.md)). It starts with the agent that ran the previous run (or the agent a person chose for Implementation after it).
    Running again from the start would discard the conversation of the previous run and begin by reading the full instruction.
    When the session cannot be continued (the agent was changed, the copied session is missing or broken, or the AI does not accept the resume), sacty runs the step again from the start.
  - Both the continuation instruction and the instruction of a run from the start tell the agent that the previous run was unfinished (or declared nothing) and what remains (`feedbackLines`; `incomplete` of `Task.verifyFeedback`).
    The continuation instruction puts a notice that the run continues the session (`incompleteResumeLines`) before it.
  - The instruction for the completion declaration also tells the agent not to end the run partway (`implementCompletionLines`).
    - Implement the whole scope within this run. Ending unfinished only makes sacty resume the same session and continue; it does not move the work forward.
    - Ending unfinished is allowed only when the agent cannot go any further (a person's decision or a change in external state is needed).
    - Changes brought in by merging the base branch or a PR are not this task's changes and may be included in the submission. Resolve conflicts while preserving both behaviors, and make no other changes to them.
    - Work assigned to a person or outside the step by approved requirements or design is not counted as remaining; record it in the work log as work for a person and submit.
    - When declaring unfinished work that needs a person's decision, write one question in `remaining` asking what to decide, and recommend an option if the step can choose one itself.
    - What the agent cannot check (the result of CI, and so on) is written in the implementation description as something for a person to check, not in `remaining`.
  - The instruction for the completion declaration also tells the agent that, if it keeps working after writing a report with a declaration and the outcome changes, it must output the report and declaration again as its last output (`implementCompletionLines`). sacty reads the last `result` that contains a declaration as the answer, so without this the earlier report and declaration are submitted (see "Output handling" in the agent-execution spec).
  - sacty continues while the workspace keeps changing. If the run is still unfinished when the continuations reach 10 (`MAX_INCOMPLETE_CONTINUATIONS`), the task pauses (`nextIncompleteRuns`; the reason is `incomplete`, the message is `implement.incomplete`).
    The count in a row (`Task.incompleteRuns`) is the total of the first run and the continuations, so the task stops at the 11th unfinished run.
    The message holds up to 5 of the remaining items as one string joined with " / " (places that show it on one line, such as notifications and error reports, show the message as is).
    The pause notice in the task details leaves the remaining items out of the reason and shows them as a bulleted list, one item each, under the heading "What remains" (`pausedRemaining`).
    The list holds the first 5 items of `remaining` (kept one by one) in the `ImplementationIncomplete` recorded in the same append; when more than 5 items were declared, it adds "and more, N in total".
    When the last `ImplementationIncomplete` in the activity does not match the string in the reason, or nothing remains, the reason is shown as is, without the list.
  - If continuing does not change the workspace content, the task pauses without waiting for the count. When only the declaration is missing, though, sacty adds one run that asks only for the declaration before pausing (next item).
    The mark combines the git tree ID of the workspace excluding the placed documents with their contents; when it equals the one of the previous unfinished run, nothing changed (`workspaceFingerprint`, `treeId`). The diff text is not used, because a large diff is truncated. If the workspace cannot be read, or even one file in it cannot be read, sacty counts up to the limit without a mark (an ID that leaves out an unreadable file would miss changes to that file).
  - A run that asks only for the declaration (PBI-416): when both of the following hold, sacty does not pause but adds one run that asks only for the declaration (`implementationCompleted`).
      - The run declared completion but the viewpoint-to-test mapping has missing viewpoints, or the completion declaration is missing or unreadable (a run that declared itself unfinished does not match; it pauses at once).
      - The workspace mark equals the one of the previous unfinished run (the condition that used to pause), and the declaration has not been asked for yet within this stall.
    - When adding it, sacty records `ImplementationIncomplete` with `declarationOnly` (no pause is recorded). The projection keeps `Task.incompleteRuns.declarationAsked` and `Task.verifyFeedback.declarationOnly`, so restarting the daemon neither runs it twice nor stops without running it (it is decided from the records).
    - The instruction of the next run says that code need not change, what is missing (the IDs of the missing viewpoints, or that the declaration was unreadable), and what to submit again (the implementation description, the mapping of all viewpoints, and the completion declaration) (`feedbackLines`, `incompleteResumeLines`). When the agent finds the implementation is not actually finished, it may declare it unfinished.
    - When the declaration is complete, sacty goes on to verification and submission as before. When the run is still unfinished and the workspace is unchanged, the task pauses (the message says that asking only for the declaration changed nothing: `declarationAsked`). When the workspace changed, it continues as before and `declarationAsked` is cleared.
    - The run that asks only for the declaration counts as one of the continuations. The limit of 10 and the way of counting do not change. When a person resumes, `declarationAsked` is counted afresh too.
  - When it stops, sacty records the unfinished run and the pause in the same append (even if the daemon stops in between, the implementation that should stop is not redone).
  - Resuming counts again from zero and continues the implementation (with the same agent, from the same session; the full instruction, including the person's note, is passed). The mark is kept, so if nothing changes after resuming either, the task stops at the next run (when only the declaration is missing, though, one run that asks only for the declaration is added before it stops).
    Going on to the submission, or redoing from an earlier step, clears the count and the mark.
- Rework that changes nothing: before updating the PR (after making the commit), sacty does not submit when all of the following hold (`reviewLeftFindingsOn`).
  - The PR waits for the PR-review child task to find no findings (`awaitsReview`).
  - The child task finished reviewing the commit about to be published as the head, and did not conclude with no findings.
    When the reworked implementation changes nothing in the workspace, the commit to publish stays the one sacty published before, or the head a person added to the PR and sacty merged.
- Rework that changes nothing and declines every finding: even when the above holds, sacty submits when all of the following hold (`declinedEveryFinding`; related ADR: [When the implementation declines every AI review finding and changes nothing, reply with the reasons and have the same head judged once more](../adr/20261117-0250-reply-and-rejudge-when-all-findings-declined.md)).
  - The latest round of remarks for the implementation has at least one remark that is not voided, and all of them are AI review findings imported from the comments of that PR (they have an `origin`). If even one remark from a person is among them, this does not hold.
  - For all of them, this run declared that it did not address the remark for a reason (`declined`) or that it proposes to defer it (`deferred`), and wrote the reason (the response text). A proposal an earlier run declared and that has not been replied to is carried over as a response of this run, so it counts as a proposal ([Proposals to defer and the person's decisions](approval.en.md#proposals-to-defer-and-the-persons-decisions)). If even one remark is declared as addressed (`addressed`), has a response without a declaration, or has no response, this does not hold.
  - None of them has been replied to yet.
  - A remark removed from the request for changes because the sorting before reworking declined all its suggestions (`Task.remarks[].triaged`) is not among the remarks counted here (it was not passed to the implementation; [Sorting suggestions before reworking](approval.en.md#sorting-suggestions-before-reworking)). When the sorting leaves no comment to send back, the implementation does not run, so this check does not happen either.
  - The task is not a security combination task (sacty does not reply on the PR about how remarks were handled for those).
  - sacty has not yet asked for another judgment of that head (`Task.reviewRejudge`).

  When it submits, sacty records `ReviewRejudgeRequested` (the PR, the head commit, and the child task) in the same append as the publication of the PR and the submission (`StepSubmitted`). The head of the PR does not change.
  When the remarks of the implementation have even one proposal to defer not yet decided by a person (even if it is not a remark of the latest round; this includes proposals of earlier submissions), it adds `awaitsDecision`. The judgment starts after a person has decided all the proposals ([Proposals to defer and the person's decisions](approval.en.md#proposals-to-defer-and-the-persons-decisions)).
  After the submission, sacty replies on the PR with the reasons, and the child task judges the same head once more ([Replies about how remarks were handled](approval.en.md#replies-about-how-remarks-were-handled), [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
  sacty asks for another judgment only once per head. The head it asked about is restored from the ledger, so restarting the daemon or resuming the task does not reset the count. If the next rework changes nothing on the same head, the pause below applies.
- When a rework changes nothing in this way and the above does not hold, sacty records `ImplementationUnchanged` (the PR, the head commit, and the child task) and a pause (the reason is `unchanged`, the message is `implement.unchanged`) in the same append.
  It does not update the PR and does not advance the submission number.
  The same head is not reviewed again ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)), so submitting it as is would lead to neither no findings nor a rework, and the PR would stay a draft forever.
  - Resuming redoes the implementation with the findings and the fact that the previous run changed nothing (`unchanged` of `Task.verifyFeedback`).
  - While the task is paused for this reason, sacty does not turn the PR back into a draft when a person marks it ready (`settlePausedDraft`).
    When a person decides not to take the AI review findings and merges the PR, the merge is taken as the approval ([Merging during a rework of the implementation](approval.en.md#merging-during-a-rework-of-the-implementation)).
  - When the child task concluded with no findings on that head, has not reviewed it yet, or is still reviewing it, and for PRs that do not wait for the child task (such as a task that takes over an existing PR), sacty submits even if nothing changed.
- Neither pause is the verification pause of older versions (`verification`), so neither can be moved on without passing (`submitForReview`).

### Reusing verification results for the same content

Related ADR: [Reuse records and CI results for verification already run on the same content, and run only what is not covered](../adr/20261106-0005-reuse-verification-results-for-same-content.md)

So that the same verification is not run again on the same content (commit), the stage that ran verification reports a record, and sacty keeps it in the ledger and passes it to the next stage (PBI-305).

- A record (`VerificationRecord`) holds, per command, the kind (`kind`), the command, the coverage (`coverage`: `full` is everything the command defines, `partial` is only part, with the range in `note`), the result (`status`: `passed` or `failed`), the exit code, an excerpt of the result, and the stage that ran it (`by`: `self-review`, `guardian`, or `ci`; `guardian` is the final review of an earlier version).
  The agent reports it as JSON under the heading `sacty-verification` (`extractVerificationRecord`). Only the last report is used, and if the last report cannot be read as JSON, there is no record (it does not fall back to an earlier report). Entries without a result or with an unknown kind are dropped, and an entry whose `coverage` is not `full` is read as `partial`.
- Implementation step: the agent reports only the verification it ran after it last changed the workspace (`implementVerificationRecordLines`). On the same content, one run serves both the pre-submission verification and the self-review verification.
  The report is kept in `verificationRecord` of `AgentRunCompleted` and removed from the implementation description (the PR body). The task holds it as `implementVerification`, which is cleared when the base branch is merged into the workspace, when commits a person added to the PR are merged into the workspace (`PullRequestHeadMerged`), or when the implementation's body is replaced outside the step. The current version does not pass this record to later stages.
- PR review: from earlier stages' records and the CI result, the agent runs only what is not covered (`reuseVerificationLines`). For a review task of a PR sacty opened (`source.review` is `sacty`), the record of an earlier version's final review of the task that opened the PR (`verificationRecord` of `FinalReviewed`) is passed only when its commit is the head commit being reviewed (`reviewTarget.headCommit`) (`reviewVerification`). Otherwise (a person's PR, a PR opened by the current version) there is no record, and only CI results can be reused.
- Reuse rules (in the agent's instructions and in "1.5 使い回せる結果を探す" of `verification-run` in the default skill):
  - Only results of running the whole target (`full`) on the same content, with a result, are reused. For a `partial` record, the agent runs the rest outside the covered range.
  - CI may run in stages or shards (split jobs, matrix, shard, and so on), so no fixed rule is used to match it. The agent treats as already run only what it confirms, from the workflow definition and each job's result and logs, to cover the whole when stages and shards are combined. Skipped jobs and jobs not run because of a condition cover nothing, and the agent does not guess from job names alone.
  - With no CI, no result, or an unreadable result, nothing is treated as run by CI.
  - Verification whose result can change on the same content is not reused. Anything the agent cannot confirm is run. The PR author's report is not reused.

### Test scope while iterating in implementation

Related ADR: [Run only the related tests while iterating in implementation, and the full suite once in the Implementation step after the last change](../adr/20261108-0602-targeted-tests-while-iterating-full-run-once.md)

So that the Implementation step does not run the full test suite after every fix, it runs only the related tests along the way and the full suite once after the last change (PBI-316).

- "Verification before submitting" of the Implementation and fix steps (`implementVerificationLines`, `IMPLEMENT_TEST_SCOPE_LINES`): along the way (the cycle of implementing and checking, and each round of the self-review), the agent may run only the tests related to the change (tests of the changed files, added tests, and tests that use the changed code). It decides how to select them from the narrowing the repository's test runner offers (by file, directory, package, test name, and so on), and runs the full suite when it cannot decide.
  After the last change (when the self-review is over and the workspace will not change again), it runs the full suite once and does not submit on the results of the related tests alone. If it fixes a failure of the full run, it runs the full suite once more after the fix. A documentation-only request (`documentsOnly`) and a task with no test setup (`noTestsReason`) have no tests to run, so this instruction is not given (`runsTests`).
- Record (`implementVerificationRecordLines`): the full run is reported with `coverage` `full`, and a run of only the related tests with `partial`, with how they were selected and which tests ran in `note`. The shape of the record is as in [Reusing verification results for the same content](#reusing-verification-results-for-the-same-content).
- Default skills (step 0 of `verification-run`, `self-review`, `review-dispatch`): in a `self-review` whose `scope` is `all`, tests in each round may be only the related ones, and the full suite runs once after the fixes are finished. The agent does not submit without a result of the full run. This does not apply when `scope` is `docs`, when the main target runs no tests, or when there is no test setup. A `pr-review` runs the full test suite (except what can be reused).

### A person moves it to review

A task paused in an earlier version's final review because verification kept failing (`verification`) can be moved to review by a person's decision, despite the failed verdict (`submitForReview`).
The current version runs no final review, so this kind of stop remains only for tasks stopped by an earlier version. This operation is not shown on the screen (a stopped task moves on to the PR review when resumed). Only the daemon's API remains.

- It can be moved only when the task is paused for `verification` in the Implementation step and is not waiting to open the PR (`canOverrideVerification`). A task that takes over an existing PR cannot be moved (it would push the failed implementation to a person's PR, and since the PR body is not changed, the override would leave no record there). Otherwise it is refused (`override.notAllowed`; 409). If containers whose stop could not be confirmed remain, they are confirmed again first, the same as resuming.
- Moving records `VerificationOverridden` (actor `person`) and makes the task wait to open the PR (`publishPending`). The final review is not run again.
- Then, the same as the current flow, sacty opens the implementation PR as a draft (updating it if there is one), creates the child task that reviews the PR, and the task waits for the Implement approval ([Opening the implementation PR](#opening-the-implementation-pr)).
- The PR body says that a person moved it to review despite the failed final review, with the failed viewpoints and the final review's summary (one line, up to `HUMAN_CHECK_ITEM_MAX` characters; `overrideBodyLines`). So that the length limit of the body does not drop it, it is put in the footer with a PR template, and in the "結論" (conclusion) at the top, kept even when the body is cut (`keep`), without one.
- It is not shown on the screen (earlier versions showed "Move to review" in the pause section of the task details).

### Tasks without tests

A task for which the Orchestrator left `testCommand` empty and wrote a basis in `noTests` (`Task.noTestsReason`) proceeds as a task whose acceptance is checked from the task's goal instead of by tests.

- Checking whether the judgment is used (`checkNoTests`; checked right after the steps are chosen, when the plan includes Implementation)
  - If there is a `testCommand`, `noTests` is discarded (the behavior with a test command does not change). Even if there is no `noTests` and `testCommand` is also empty, the task does not stop (it does not stop with `orchestrator.testCommandUnknown`; earlier versions stopped).
  - If any of the following applies, the judgment that there are no tests cannot be used, and a `StepsChosen` without `noTestsReason` is recorded. The task does not stop and proceeds with the chosen steps (sacty does not run tests, and the Implementation step's agent decides the tests from the repository and runs them; PBI-331). The task becomes one with neither a test command nor the judgment that there are no tests (`testsUndecided`), and the implementation instructions show no test command.
    - A bug fix (`bugfix`) is chosen (`orchestrator.bugfixNeedsTests`). A reproduction is confirmed by tests, so it is not chosen for a task without tests (the instructions to the Orchestrator also ask it not to choose it).
    - The base code of the target repository (the workspace, excluding `.git`) has a file that matches the naming conventions of test files (`orchestrator.noTestsContradicted`). Matches are files inside `test`, `tests`, and `__tests__` directories, and files whose name without the extension is `test`, `tests`, `test_*`, `test-*`, `*_test`, `*-test`, `*.test`, `*_spec`, `*.spec` (and plurals), `*Test`, `*Tests`, or `Test*` (camel case) (`looksLikeTestFile`). Document files (extensions `md`, `markdown`, `txt`, `rst`, `adoc`, `asciidoc`, `org`) do not match, even inside test directories.
    - The scan does not finish after 20,000 entries (`TEST_FILE_SCAN_LIMIT`) (`orchestrator.noTestsUncertain`).
    - A directory cannot be read (including the workspace itself; `orchestrator.noTestsUnreadable`).
    - The message for which one applied is chosen by `noTestsStop` (`noTestsContradicted` if a test file was found first). The current version does not record this message (because it does not stop).
  - For a documents-only request (`documentsOnly`), the test file checks above are not made and the judgment is used (even if test files exist or the scan cannot finish).
  - In earlier versions, when the judgment could not be used, a `TaskPaused` with the message as the reason was also recorded and the task stopped. How to resume such a task that is still stopped is in "Deciding the tests on resume" below.
- Instead of having it write tests, the instructions for the Implementation step ask it to write in the implementation's description how each viewpoint is met. For a document of instructions for agents (`AGENT_INSTRUCTIONS`), it is asked to write where the text that meets the request is, and not to add a test setup that starts an agent (`NO_TESTS_AGENT_INSTRUCTIONS_IMPLEMENT_LINE`; the same for a task without Requirements or Design). Only when the task asks for setting up tests and the implementation sets them up does it report the command, as JSON (`{"command": "…"}`; 1 to 1000 characters) in a code block whose language name is `sacty-test-command` (`TEST_COMMAND_FENCE`). The report is recorded in `testCommand` of the implementation's `AgentRunCompleted` and read again for each submission (`Task.addedTestCommand`).
  - The report is read only in the Implementation step of a task without tests (`testCommand` of `extractBlocks`). In other steps (Requirements, Design, review, and so on) and in the Implementation step of a task with tests (where `testCommand` was decided), this code block stays in the text as it is (it reaches the outputs, the approval screen, and later steps) and is not treated as a report (the task does not stop; tests run with the decided test command).
  - Only the inside of this code block is read as the report (`extractTestCommandFences`; CommonMark fence rules: up to 3 leading spaces, 3 or more `` ` `` or `~`, closed by the same character at least as many times, and the language name is the first word of the info string). Text outside code blocks and the inside of other code blocks (such as an example quoted with four backticks) are not treated as the report. The report's code block is removed from the text.
  - If even one block's content cannot be read as JSON, is not an object, has a `command` that is not a string, is empty, or is longer than 1000 characters, or the code block is not closed, it is not treated as a missing report: `AgentRunFailed` and `TaskPaused` (`implement.testCommandInvalid`) are recorded and the task stops. Resuming redoes the implementation. If there are several readable reports, the last one is used.
- The Orchestrator's basis (`noTestsReason`) is influenced by the documents of the target repository, so it is not embedded in the text of the implementation instructions; it is passed as a JSON string under a heading that says it is the Orchestrator's report, data as a JSON string, and not an instruction to the agent (`noTestsReasonLines`). A reason a person decided when resuming (`testsDecidedBy` is `person`) gets a heading saying that a person wrote it when resuming.
- `noTests` is to hold only the basis for there being no test setup (where it looked and what was missing), not how acceptance is checked (such as "check that the names exist with grep"). How to check is decided by later steps from the request's acceptance criteria (PBI-301 A1; experiment S2 r4: a way of checking written in the basis went straight into the implementation and the final review, and acceptance shrank to checking that names exist). After the basis passed to the implementation, a note says that the basis does not decide how to check, and that even if a way of checking weaker than the acceptance criteria is written there, it is not followed and the acceptance criteria themselves are checked (`NO_TESTS_REASON_NOTE`). The implementation prompt (`acceptanceDepthImplementLine`; since PBI-315, in every implementation prompt) does not let the check shrink to confirming that a name, item, file, or link exists, and when a document describes a responsibility or behavior of the code, it has the agent read the relevant code and write the places it checked in the implementation's description.
- The examples of answers to the Orchestrator are shown separately: one that writes `testCommand` and one that writes `noTests` (which cannot choose `bugfix`), and the Orchestrator is told not to write both, and not to leave both empty for a plan with Implementation.
- Verification
  - sacty does not run tests. The tests set up in the implementation are run by the Implementation step's agent itself before submitting, and it writes the command and the result in the implementation's description ([The flow without the final review](#the-flow-without-the-final-review)).
  - The acceptance is checked by the review child task of the PR from the task's goal, the approved requirements (and the design, if any), the implementation's description, the diff, and the code after the implementation ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
  - In earlier versions, the final review agent ran the declared test command and judged each viewpoint from the task's goal (without a declaration, `TestsSkipped` was recorded; `Task.testsSkippedAt`).
- Display
  - The "Step settings" tab of the task details and "Tests" in the properties (`testCommandOfNoTests`): the test command shows as "none, judged by the goal". The basis appears in a hint (tooltip) only in the "Step settings" tab (not in "Tests" in the properties). For tests set up in the implementation, it shows "tests added in the implementation: command" if they passed, "failed; redoing" if they failed, and "will run next" while waiting.
  - The notice on the implementation deliverable (the task screen and the Implement approval screen) (`addedTestsResult`)
    - No tests were run (no test command was declared): "Not verified by tests"
    - In an earlier version's final review, the tests set up in the implementation ran and passed: "Verified by the tests added in the implementation" (success color)
    - They failed: "The tests added in the implementation failed" with the exit code (failure color)
    - The current submission's tests have not run yet (`verification` is `pending` and there is a report): "Waiting to run the tests added in the implementation" (the previous submission's result is not shown)
  - The test line of the PR body (`テスト：テストの仕組みが無いリポジトリとして進めたため、テストでは検証していません。`, with `（実装で用意したテスト）` for tests set up in the implementation) and the basis line
  - The Activity (`StepsChosen`; in records from older versions, also `TestsSkipped`)
- A person's Implement approval is still required, as for a task with tests.

### Deciding the tests on resume

When a paused task is resumed, a person can decide how to handle tests if any of the following applies (`tests` of `ResumeTaskInput`; `canDecideTests`).

- A task that an earlier version stopped right after choosing the steps because the tests were not decided: it chose steps including Implementation (and Reproduce for a bug fix) but has neither a test command nor the judgment that there are no tests (`noTestsReason`) (`testsUndecided`), its pause reason is `error`, and the code of why it stopped is one of `orchestrator.noTests*`, `orchestrator.bugfixNeedsTests`, and `orchestrator.testCommandUnknown` (`TESTS_UNDECIDED_STOP_CODES`). In the current version, the task does not stop when the Orchestrator decided neither or when the judgment that there are no tests could not be used ("Tasks without tests" above), so it does not become this task. A task whose tests are not decided but that stopped for the budget, another error, or a person's pause does not apply.
- Tasks that stopped in an earlier version's final review because a tool was missing, or because the request was judged documents only but the diff disagreed (the two below).

How to decide:

- Specify the test command (`{"testCommand": "…"}`; 1 to 1000 characters): `TestsDecided` is recorded and it becomes `Task.testCommand`; it is passed to the instructions of the Implementation and Reproduce steps as the test command a person specified (`testCommandLine`; sacty does not run it).
- Proceed without tests (`{"noTestsReason": "…"}`; the reason is 1 to 2000 characters): `TestsDecided` is recorded and it becomes `Task.noTestsReason`; the task proceeds as in "Tasks without tests" above. Because it is a person's decision, the safeguard that looks for test files (`checkNoTests`) is not applied. A bug fix (with a Reproduce step) cannot proceed without tests (`resume.bugfixNeedsTestCommand`).
- Only one of the two can be given. Giving it for a task to which none of the above applies is rejected (`resume.testsNotUndecided`).
- When a person decides, `Task.testsDecidedBy` becomes `person`, and the steps are not chosen again. The "Step settings" tab of the screen, the implementation instructions, and the PR body show that the test command or the reason was decided by a person.
- Resuming without deciding continues from where the task stopped with the chosen steps (the steps are not chosen again, and the task does not stop without a test command). Records from earlier versions of choosing the steps again after resuming without deciding (`rechooseSteps` of `TaskResumed`) are kept only for reading.
- In the resume section of the screen, a person can choose how to handle tests (resume without deciding, specify the test command, or proceed without tests). For a bug fix, proceeding without tests cannot be chosen. For a task stopped by a missing tool, the input for the test command is prefilled with the current command.

#### Resuming a task stopped by a missing tool

A task that stopped in an earlier version's final review because a tool of its decided test command is not in the image and the diff has a file that is not a document (`testToolsMissing`: the pause reason is `verify.commandMissing`, it has a `testCommand`, and no `noTestsReason`) can also decide how to handle tests again with the same `tests` (`canDecideTests`). Resuming without deciding records `FinalReviewSkipped` in the current flow and moves on to opening the PR ([Tasks from the version with the final review](#tasks-from-the-version-with-the-final-review)). A task with `noTestsReason` (one that judged there are no tests and verifies with the command the implementation declared) is excluded.

- Specify the test command again: `TestsDecided` is recorded and it replaces `Task.testCommand`.
- Proceed without tests: `TestsDecided` is recorded and it becomes `Task.noTestsReason`, and the `Task.testCommand` from before the stop is cleared. A bug fix cannot proceed without tests.

How to give the input, how the person's decision is shown, and that only one of the two can be given are the same as above.

#### Resuming a task that stopped because the request was judged documents only but the diff disagrees

In an earlier version, a task whose request the Orchestrator judged to be documents only (`documentsOnly`) but whose implementation diff has something other than document files, so it stopped before the final review (`documentsOnlyContradicted`: the pause reason is `verify.documentsOnlyContradicted` and `documentsOnly` is `true`), can also decide how to handle tests again with the same `tests` (`canDecideTests`). Resuming without deciding records `FinalReviewSkipped` in the current flow and moves on to opening the PR.

- Specify a test command or proceed without tests: `TestsDecided` is recorded. The content is the same as in "Resuming a task stopped by a missing tool".
- When a person decides how to handle tests, `Task.documentsOnly` is cleared (the judgment that the request was documents only is no longer used). When a test command is specified, the `Task.noTestsReason` from before the stop is also cleared (otherwise the task would be treated as without tests even though a command is specified).
- In the resume area of the screen, the test command from before the stop, if any, is shown as the initial value of the input.

## Change requests

A step's agent can request a change to approved requirements or design (IDs are `CP-<number>`). No AI judges it; a person decides unless the request qualifies for acceptance under a resume note.

- If the request JSON or its required fields cannot be read, the task pauses without submitting the result. A request containing incomplete test viewpoints waits for a person instead of being applied automatically.
- When a request does not qualify for automatic acceptance, sacty records `ChangeProposed` (actor `agent`) and `TaskEscalated` (reason `change_proposed`, actor `sacty`) in the same transaction, and the task waits for a person's decision (`escalated`) (so that, even if the daemon stops in between, no request is left without waiting for a decision).
- In "Change requests" (`/tasks/<ID>#proposals`) in the task details, a person reads the reason, the supporting facts, and the full proposed text, and decides whether to accept it (`ChangeDecided`; `decideChange`). The request waiting for a person is `openProposal`.
- If accepted, the change is applied (`ChangeApplied`): the requirements have their approval revoked and go back for re-approval, and the design replaces the approved version.
  If not accepted, a request made while permission is active is rerun against the approved artifacts without submitting its result. The rejected change remains excluded even after a pause or daemon restart. Otherwise, the requesting step submits its result (`settleEvents`, `submitEvents`).
- A request that stopped in the middle of the AI's judgment in an earlier version (one with neither a verdict nor a person's decision) is put into waiting for a person's decision with `change_proposed` at startup (`recoverInterrupted`).
  The earlier versions' records of the AI's verdict (`ChangeJudged`) and the Escalation when it could not decide (reason `change_undecidable`) are kept only for reading old activity (a request it could not decide is decided by a person, the same as a request now).
- A local fix to the design document (wording, one row of a table or list, a default value, adding a row) is not a change request. In a round that fixes a comment on an implementation PR in Implementation, the implementation gives a design fix (`sacty-design-edit`), and sacty applies it to the approved design and puts it in the same implementation PR (the event `DesignEdited`; merging the implementation PR approves it). A change of policy (choosing a different method or structure, changing the scope or acceptance criteria, and so on) is not given as a design fix; it is raised as this change request.
  - Which to use: a local fix is a design fix, and a change of policy is a change request.
  - `DesignEdited` holds the whole design and test viewpoints after applying, the fixes applied, and the fixes not applied with their reasons. The projection replaces the approved design, the design output, and the test viewpoints. Unlike applying a change request (`ChangeApplied`), it does not change the viewpoint IDs or the implementation history. For how fixes are given, checked, and applied, see [Approval and request changes](approval.en.md#design-fixes-sacty-design-edit).

Code: `apps/daemon/src/service.ts` (`runNextInner`, `settleEvents`, `submitEvents`, `decideChange`, `recoverInterrupted`), `packages/core/src/projection.ts` (`openProposal`), `packages/core/src/events.ts` (`TaskEscalated`)

## Runs on a copy of the code

Deciding where to send PR comments back to, Integration review, answering questions, analyses, and so on run on a copy of the code separate from the workspace. For each run sacty makes a copy of the code in `workspaces/_code-copy/<run ID>` and deletes it when done (even if the run fails or is interrupted). If it cannot be deleted, only a warning is shown and the run's result (verdicts, answers, analyses and their cost) is kept (a copy left behind is removed by the cleanup at startup). The copy and the deletion are asynchronous, and the daemon keeps responding to the web UI and the API meanwhile ([Data location](architecture.en.md#data-location-sacty_home)).

| Run | What it reads | Agent |
| --- | --- | --- |
| Deciding where to send PR comments back to | The code after implementation for the implementation PR; the code at the base for the Requirements and Design PRs | The agent of that PR's step ([Approval and request changes](approval.en.md)) |
| Sorting the AI review suggestions (role `triage`) | The code after implementation | The agent of the Implementation step ([Approval and request changes](approval.en.md#sorting-suggestions-before-reworking)) |
| Integration review | The latest base branch | `step_agents.integrate` (or `default_agent` if absent; [Task split and integration review](split-and-integrate.en.md)) |

Every judging instruction includes the information gathered at the start of the task ("Information gathering" above). The basis of the verdict stays the approved deliverables (or the task's content if none) and the people's comments; the gathered information is used only to understand the background.

Code: `apps/daemon/src/service.ts` (`runGuardian`, `judgeRework`, `triageSuggestions`, `integrate`), `apps/daemon/src/workspace-cleanup.ts` (`CODE_COPY_DIR`), `apps/daemon/src/prompts.ts` (`extractRework`)

## Budget, pause, resume, and cancel

![Budget cap and pausing](images/budget-flow.en.svg)

- Budget cap: when a task is created, `budget.default_per_task_usd`. If the plan the orchestrator chose has a budget in `budget.per_plan_usd`, it is recorded as `budgetCapUsd` of `StepsChosen` and becomes the cap (the 80% notice is reset). If a person raised the cap before the steps were chosen (`BudgetCapRaised`; `budget.raised` in the projection), it is not recorded and the raised cap is kept.
- Budget: when spending reaches 80% of the cap (`BUDGET_WARN_RATIO`), `BudgetWarned` is recorded (once). When the cap is reached, the task is paused (`budget`) before choosing steps and before running a step (when sacty opens the implementation PR inside the Implementation step (`publishPending`) and when it posts a finished review to the PR, it does so without stopping, because that costs nothing; if a review run exceeds the cap, the review is still posted, and the task pauses before the next re-review). Tasks waiting for approval are not stopped. Resuming a task stopped by the budget requires a new cumulative cap larger than the amount spent (up to 10000 US dollars) (`BudgetCapRaised`).
- Pause reasons (`PauseReason`): `budget`, `usage_limit` (the AI's usage limit), `auth` (an authentication error or missing secret), `error`, `verification`, `manual` (a person paused it), `child_cancelled` (a child task was canceled), `incomplete` (the implementation keeps ending unfinished), `unchanged` (the rework changed nothing in the PR), `needs_decision` (the PR review left must-fix findings it marked as unresolvable by a rework and needing a human decision; [Pausing on findings a rework cannot resolve](approval.en.md#pausing-on-findings-a-rework-cannot-resolve)). A failed AI run pauses the task with that reason (`manual` if a person had paused it). There is no mechanism to resume automatically after a while.
- Pausing by a person: a task cannot be paused in Escalation (including a change request waiting for a person's decision) or while waiting for child tasks. A task waiting for approval (waiting for a PR merge) can be paused; since nothing is running, it is recorded on the spot, and a resume returns it to waiting for approval (for what happens to the PR while it is paused, see [Pausing while waiting for approval](approval.en.md#pausing-while-waiting-for-approval)). If it is running, the container and service startup are stopped before recording. If any container cannot be confirmed as stopped, the task does not resume until that is confirmed.
- Resume: if the status before the pause was waiting to run, the stopped step is run again. Resume is rejected for an Operation that has started, keeping the task paused.
  Comments that arrive on the implementation PR during an implementation rework are kept as not yet applied while the task is paused (for any reason: the budget, an error, a person's pause, and so on). After the resume, before the step that stopped runs again, they are applied by deciding where to send them back to ([Importing PR comments](approval.en.md#importing-pr-comments)). With no comments, it is as before ([Comments that arrive while paused](approval.en.md#comments-that-arrive-while-paused)).
- Notes and step settings on resume: a person can pass the following with the resume (`note`, `image`, and `agents` of `ResumeTaskInput`).
  - Notes (up to 10000 characters; `RESUME_NOTE_MAX`) are recorded as `note` of `TaskResumed`, and the projection adds them after the task description under the heading `## 補足（再開で人が足したもの）` (`RESUME_NOTE_HEADING`; `bodyWithResumeNote`). The Orchestrator and the steps read the description, so the notes reach the steps still to run as they are. Paths that do not include the description (implementation given the approved requirements and design) get `resumeNotes` of the projection as a separate section (`resumeNotePromptLines`; the notes take precedence if they conflict with the approved documents, and the instructions on change proposals also tell the agent to follow the notes where they conflict and to propose the change that aligns the approved outputs). Deciding where to send back remarks on the implementation PR and on the requirements and design PRs also gets the notes as the person's newer intent (`resumeNoteJudgeLines`; changes that follow the notes are not treated as changes to make the work easier). Each resume adds them under a separate heading. For a task created by deriving or by a rerun, they are put before the records sacty added (the record of the original task of a derived task and the record of the previous attempt of a rerun), so they are also kept in the description shown when rerunning. If there is a derived record, they are put at the position of the text recorded at creation (the rerun record comes after it, so it is not searched); otherwise, the heading of the rerun record is searched.
  - Besides the description, the notes are kept in the order added in `resumeNotes` of the projection (used by imports that replace the description; they are not read back from the headings in the description).
  - Line breaks are normalized to LF before counting (`note` of `ResumeTaskInput` and the Server Action; `normalizeNewlines`).
  - If the notes would newly make the part of the description edited when rerunning (`rerunEditableBody`) exceed `TASK_BODY_MAX`, the resume is refused without recording anything (`resume.bodyTooLong`, showing how long the notes can be, or, if none can be added, suggesting resuming without notes or canceling and fixing the description in a rerun; `resumeNoteRoom`). For a task that cannot be rerun (a child task or a PR task; judged by `rerunnableKind`, the same check `canRerun` uses) and a description that already exceeds the limit before the notes (such as a long imported Issue), only the notes limit (`RESUME_NOTE_MAX`) is checked. This is checked against the description at the time of the resume; for a task whose description is replaced by ticket triage, it can exceed the limit afterwards.
  - For a task stopped while waiting for ticket triage, the notes are passed to the triage (`buildTicketTriagePrompt`) as material for its decisions (it is told not to copy them into the summary), and when `TicketTriaged` replaces the description with the summary, the notes (`resumeNotes`) are kept after the summary. Lines with the notes heading in the triage summary are removed (text from the ticket is not made to look like a person's notes).
  - The task image and the agents per step get the same checks as changing them in the task details (`changeTaskImage`, `changeStepAgent`), and `TaskImageChanged` and `StepAgentChanged` are recorded before `TaskResumed`. A name that is unchanged is not recorded. If any change is for a step that was not chosen, uses a name not in the settings, or is for the agent of the integration review, or if the settings (config.yaml) cannot be read, the resume is refused without recording anything.
  - The resume section of the web UI shows a field for the notes and, when there are steps not finished yet, the task image choice and the agent choices for those steps (collapsed; the current names are selected first; an empty choice for per-step images from an older version). It also sends the current names as rendered, and the Server Action passes only what a person changed to the daemon (`changedStepChoices`; old names of untouched choices do not undo changes made in the meantime). The choices restored when a resume is refused are also only what a person changed. The notes field is limited to the length of notes that can be added. The remaining length is shown only when it drops below 1000 characters; if no notes can be added, the field is disabled and suggests resuming without notes or canceling and fixing the description in a rerun. The resume line in the activity shows that notes were added, with the notes in its details.
- Cancel: session logs (`runs/`) are not deleted. Canceling a parent also cancels its unfinished child tasks. sacty cleans up in the following order and records the result (`done`, `skipped`, `failed`) for each target (`container`, `workspace`, `session`, `branch`, `pull_request`) in `TaskCancelled`.
  1. Stop runs answering questions and running containers.
  2. Delete the Orchestrator session.
  3. Close the implementation PR sacty opened and the requirements and design PRs that are recorded as open (without merging). Check GitHub immediately before closing and skip any PR that is no longer open.
  4. Delete sacty's branches (the implementation PR's branch, the task branch, and step branches).
     The step branches of a flow without an implementation (no task branch is created) are deleted with the head-comparing rule (the branch of a merged PR is deleted unconditionally); a branch a person added commits to and sacty kept (`StepBranchKept`), and a branch whose remote head differs from the last push, are not deleted.
     A branch already gone from the remote counts as deleted ([PRs of steps in a flow without an implementation](approval.en.md#prs-of-steps-in-a-flow-without-an-implementation)).
  5. Delete the workspace, including the dependency cache (not deleted if the containers cannot be confirmed as stopped).

Code: `apps/daemon/src/service.ts` (`warnIfNeeded`, `checkBudget`, `pause`, `resume`, `cancel`, `cleanupPlan`, `sactyBranches`, `stopReason`, `runNextInner`), `apps/daemon/src/config.ts` (`ConfigFile`), `packages/core/src/events.ts` (`PauseReason`, `CleanupTarget`, `ResumeTaskInput`, `RESUME_NOTE_HEADING`, `bodyWithResumeNote`, `resumeNoteSections`, `withoutResumeNoteHeadings`, `normalizeNewlines`), `packages/core/src/projection.ts` (`project`, `resumeNoteRoom`, `rerunnableKind`), `packages/core/src/cost.ts` (`budgetState`), `apps/daemon/src/prompts.ts` (`resumeNotePromptLines`, `resumeNoteJudgeLines`, `resumeNoteLines`), `apps/web/src/components/resume-form.tsx` (`ResumeForm`), `apps/web/src/lib/step-options.ts` (`changedStepChoices`)

### Cleaning up the workspaces of finished tasks

A task's workspace (`workspaces/<task-id>`), its set-aside git metadata (`workspaces/_git/<task-id>.git`), and its dependency cache (`workspaces/_task-cache/<task-id>`; [Agent execution](agent-execution.en.md#dependency-cache)) are removed not only on cancel, but also when a completed task no longer uses them.

- A task that no longer uses them (`workspaceRetirable`): one that meets all of the following.
  - It has finished all steps and stopped (`idle` and `isCompleted`).
  - For an audited task, the audit has ended (completed or failed). An audit stopped by its budget is kept, because it can continue after the cap is raised.
  - It is not an older task waiting for the after-merge watch outside a step.
  - It has no container that could not be confirmed as stopped (`unstoppedRuns`).
- When they are removed:
  - In a flow without an implementation (no task branch is created), if sacty's step branches remain, they are deleted with the deletion rule before the workspace is removed (a failure does not stop the completion; [PRs of steps in a flow without an implementation](approval.en.md#prs-of-steps-in-a-flow-without-an-implementation)).
    At completion, a branch a person added commits to and sacty kept (`StepBranchKept`) is not deleted.
    A branch that could not be deleted is not retried; it is recorded with its reason in `StepBranchesLeft` and shown in the task details. If the startup cleanup runs again and the result changes, it is recorded again. When the git metadata is missing and nothing could be decided, nothing is recorded.
  - On the append that makes the task so.
  - When a run or the answer to a question ends (if a run is in progress, they are removed at its end).
  - When the daemon starts ([Daemon startup and shutdown](daemon-lifecycle.en.md#daemon-startup-order)).
- At startup, the following are removed too.
  - Workspaces, set-aside git metadata, and dependency caches that belong to no task.
  - Dependency caches of cancelled tasks (for example, when the daemon stopped in the middle of the cancel's cleanup).
    As for completed tasks, it is not removed if any of the workspace, the set-aside git metadata, and the cache overlaps a mount.
    The dependency cache of a task in progress is kept and reused after the restart.
  - Per-run scratch directories (`<run-id>` under `_code-copy`, `_guardian` (copies from earlier versions), `_snapshots`, `_review`, `_input`, `_repos`, `_audit-logs`, `_audit-ledger`, `_deployment`, `_export`, `_handoff`, `_question-logs`) that do not belong to a running run or a run whose stop could not be confirmed.
    They are removed at the end of the run, but are left if the daemon is stopped during the run; after a restart the run starts over with a new run ID, so they are never used again.
  - The candidates are fixed when the cleanup starts (before listening for the API and starting the worker). Ones of runs, questions, and tasks started during the cleanup are not removed.
- Limits on what is removed:
  - Only names under the workspace root shaped like a task or run ID (UUID) are removed.
  - A link is removed by itself; its target is not followed.
  - Nothing that overlaps a place mounted by a running container (not only sacty's) is removed.
    If Docker cannot be queried, nothing is removed (checked again at the next start).
  - If any of a task's workspace, its set-aside git metadata, and its dependency cache overlaps a mount, all of them are kept.
  - Nothing is removed if anything on the way from the workspace root to its parent is a link or not a directory (even if `_git` is a link, its target is not removed).
- If something cannot be removed (permissions and so on), the reason is logged and the rest is removed. Neither the daemon startup nor the task's progress is stopped.
  So only some of a workspace, its set-aside git metadata, and its dependency cache may be left.
  A directory whose listing cannot be read is logged too.
- Session logs (`runs/`), `sessions/`, `memory/`, and `sacty.db` are not removed.
- They are not removed while something uses the workspace (a run, answering a question, cleaning up a cancel, preparing it, or another task's integration review reading it), but when that ends.
- Operations that use the workspace after it was removed prepare it again from the same base commit (`prepareRepository`).
  - Preparing one task's workspace happens one at a time (a later preparation checks whether it is needed after the earlier one ends). If it is being removed, it is prepared after the removal ends.
  - Even if the recorded base branch is gone (for example, a continued PR's branch deleted after merging), it clones the default branch and fetches the base commit.
  - Operations that rerun a step (re-review and so on) prepare it while preparing the step's run.
  - Runs given a copy of the code, such as answering a question (`runGuardian`), prepare it before copying if both the workspace and the set-aside git metadata are missing (including a question after a re-review put the task back to waiting to run).
    If one of them is left, they do not prepare it, as before (so changes in progress are not lost).
    Because the implementation workspace is gone too, they get the base code, not the implemented code.
  - The integration review prepares completed child tasks' workspaces to read them, and removes them again when done (even on failure).
  - Canceling a task prepares them again to delete sacty's branches if both are missing.
    If they cannot be prepared, the reason is recorded in the branch cleanup result (`failed`).
    Ones prepared again are treated as absent (`skipped`) in the workspace cleanup result.

Code: `apps/daemon/src/service.ts` (`retireWorkspace`, `cleanupWorkspacesAtStartup`, `workspaceMissing`, `workspaceBusy`, `prepareRepository`, `childRepositories`, `cancel`), `apps/daemon/src/repository.ts` (`prepare`), `apps/daemon/src/workspace-cleanup.ts` (`workspaceRetirable`, `RUN_SCRATCH_DIRS`, `isSactyId`, `removeEntry`, `overlapsMounts`, `runningContainerMounts`), `apps/daemon/src/main.ts`

### Rerunning a cancelled task

- A cancelled task can be started over from "Rerun" on its detail page (`POST /api/tasks/:id/rerun`). Nothing can be appended to the activity of a cancelled task, so a new task that takes over the original is created (`rerun` in `TaskCreated`: the original task's ID and the image a person chose). When the activity is replayed, the original task records the rerun task (`rerunBy`); a task can be rerun only once (a second rerun and a task that is not cancelled are refused). Subtasks created by a split and PR review tasks can't be rerun (`canRerun`).
- A person decides the following (`RerunTaskInput`). sacty refuses a repository outside the targets and an image not in `images`.
  - The title
  - The description (the original one without the records sacty added: the previous attempt's record for a rerun task, the original task's record for a derived task. `rerunEditableBody`)
  - Additional notes (up to 10000 characters)
  - The repository to work in (from the project's targets; `null` means no repository, and the task proceeds like a task created without one)
  - The image (a name in `images` or `default`; without it, the image is decided as usual)
- The description is the edited description followed by the notes (`## 補足（再実行で人が足したもの）`) and the record of the previous attempt (`## 前の試行の記録（中止したタスク）`) (`buildRerunBody`). For a rerun of a derived task, sacty adds the original task's record (`record` in `derivedFrom`, `derivedRecord`) again after the edited description (it does not count toward the person's input limit). `derivedFrom` (the original task and the record) is carried over too, and the rerun task joins the original task's follow-up tasks (even if the original task is not completed now, and also over repeated reruns). The record holds what cancelling did not remove: the original task, the repository it worked in, the ticket and the source, the steps and their states, why the steps were chosen, why it last stopped, the closed PR, when it was cancelled, the step outputs (the approved one if approved; up to 3000 characters each), remarks that were not voided, and questions with answers. Because cancelling removed the workspace, branches, and PRs, it says to start over from the beginning.
- The chosen image takes priority over the project target's setting and is used for every step (`imageSource` in `StepsChosen` is `rerun`).
- A task imported from a ticket keeps the ticket (`start` is `jira`; the PR URL is posted to the ticket, and the same ticket is not imported twice). The ticket is not read again (`awaitingTicketTriage` does not apply), and the task proceeds with the repository the person chose. With no repository, like a task created without one, the Orchestrator chooses a repository, and a person chooses it if the Orchestrator can't (`isRepoless`, `awaitingRepository`, `chooseRepository`). A rerun of a task imported from a GitHub issue doesn't keep the source (`start` is `sacty`; the record has the issue URL).
- The budget cap is `budget.default_per_task_usd` at the time the rerun task is created (the original task's cap and the amount used are not carried over).
- If the original task has a security plan (`security-check`, `security-fix`), that plan becomes the `plan` of `TaskCreated` (so the rules for the smallest change and keeping results off public places stay). For a fix task created from a category of a report, `securityFix` (the report, the category, and all the findings) is also carried over (so findings that did not fit in the description are not lost). Other plans are not carried over; the Orchestrator chooses.

### Creating a follow-up task from a completed task (derive)

Related ADR: [完了したタスクから、元のタスクを指す続きのタスクを何度でも作れるようにする（派生）](../adr/20261028-0054-derive-follow-up-task.md)

- A completed task (one that finished all its steps and stopped, not cancelled; `canDerive`) can create a task for follow-up work from "Create a follow-up task" in the row of actions at the top of its detail page (`POST /api/tasks/:id/derive`). The original task is not changed; a new task that points to it is created (`derivedFrom` in `TaskCreated`: the original task's ID and the text of the original task's record added to the description, `record`). When the activity is replayed, the original task records the created tasks in creation order (`derivedTasks`). Any number can be created from one task. A task that is not completed is refused (`derive.notCompleted`, 409). Replaying the activity also refuses a derived task from a task that is not completed (except a rerun of a derived task) or from another project (if the original task is not in the activity, only the record on the original is skipped).
- A person decides the following (`DeriveTaskInput`). sacty refuses a repository outside the targets.
  - The title
  - The description (what to do next; required; up to `TASK_BODY_MAX`)
  - The repository to work in (from the project's targets; `null` means no repository, and the task proceeds like a task created without one)
  - The plan (without it, the Orchestrator chooses; the choices are the same as when creating a task on the screen. `selectablePlans`)
- The description is the person's description followed by the original task's record (`## 元のタスクの記録（完了したタスク）`, `DERIVE_RECORD_HEADING`) with a blank line between them (`deriveRecord`, `deriveBody`). The rerun dialog removes exactly the text of `record` from the description (it doesn't look for headings, so a line in a step output that matches a heading doesn't move the boundary; `rerunEditableBody`). The record holds the original task, the repository it worked in, the ticket and the source, the steps and their states, the implementation PR and its state, the Requirements and Design PRs (the line of a PR merged in a flow without an implementation also carries the document path, `path` of `StepPullRequestPublished`; a follow-up task started from the base branch has those documents in its workspace), the subtasks created by a split, an earlier version's final review result and what people check, the step outputs (the approved one if approved; up to 6000 characters each), and questions with answers. It says that the original task's changes remain, that the request takes priority over the record, and not to do what the request doesn't ask.
- `start` is `sacty`. The ticket and the source are not carried over (no results are returned to the ticket or issue).
- The budget cap is `budget.default_per_task_usd` at the time the task is created.
- If the original task has a security plan (`isSecurityTask`), the plan can only be `security-fix` or `security-check` (`security-fix` if not given; anything else is `derive.securityPlanRequired`, 409). This keeps the report and the fix scope in the record off public places (the non-disclosure in "Security check and security fix" above). `securityFix` (the report, the category, and all the findings) is not carried over (a person writes the findings to fix in the description).
- When a follow-up task is cancelled and rerun, a person edits the description without the original task's record, and sacty adds the record again ("Rerunning a cancelled task" above).
- On the screen, a completed task's details show a "Create a follow-up task" button (opens the dialog; `DeriveButton`) in the row of actions at the top, in the same place, look, and hint as "Review again" (it wraps on narrow widths), and a "Follow-up tasks" section in the Overview (the list of created tasks; no button), and "Follow-up of" in the properties of a follow-up task's details shows a link to the original task. The titles of the created tasks come from one fetch of the task list (`GET /api/tasks`), not one fetch per task. If the list can't be fetched, they are shown by ID (the details are still shown). For a task with a security plan, the plan choices are only the security plans.

Code: `apps/daemon/src/service.ts` (`deriveTask`), `apps/daemon/src/prompts.ts` (`deriveRecord`, `deriveBody`), `apps/daemon/src/server.ts` (`/api/tasks/:id/derive`), `packages/core/src/events.ts` (`DeriveTaskInput`, `DERIVE_RECORD_HEADING`), `packages/core/src/projection.ts` (`canDerive`, `applyEvent`), `apps/web/src/components/derive-dialog.tsx` (`DeriveButton`, `DerivedTasksCard`), `apps/web/src/lib/task-detail-data.ts`

## Asking the Orchestrator

![Asking the Orchestrator](images/question-flow.en.svg)

- In the question field, Ctrl + Enter or ⌘ + Enter runs the same form validation and submission as the button. Only Ctrl or Meta alone is accepted; composition events do not submit. Enter and Shift + Enter remain line breaks, and blocked or pending forms cannot submit.
  Code: `apps/web/src/components/question-form.tsx`.

- Questions are up to 2000 characters (`QUESTION_MAX`), and answers up to 20000 characters (`ANSWER_MAX`; truncated if longer). At most one question can be awaiting an answer. Questions cannot be asked on canceled tasks or tasks that reached the budget cap. IDs are `Q-<number>`.
- The AI is the same as the Orchestrator; it reads a copy of the code at the base and answers by duplicating the saved Orchestrator session (the original session is not changed). The instructions include the task's title, status, steps, PR, cost and budget, body, approved results and latest outputs, verdicts, comments, recent questions and answers, and the Activity (as much as fits in 40000 characters in total).
- Session logs of each run: before the answering run, this task's per-run session logs (`SACTY_HOME/runs/<task ID>/` in [Agent execution](agent-execution.en.md)) are laid out in a per-answer-run location (`<workspaces>/_question-logs/<run ID>/`) and mounted read-only at the container's `/sacty-logs` (Claude Code is also given `--add-dir /sacty-logs`). They are deleted when the answering run finishes.
  - What is laid out: `index.json` (the list of runs) and, for each finished run, `<run ID>/meta.json`, `events.jsonl`, and `stderr.log` (only those that exist), and the agent's original files recorded in the Activity's `AgentSessionArchived` (`<run ID>/agent/<relative path>`; files whose size differs from the record or that are not regular files are not laid out). Every run that goes through execute is covered: steps, the Orchestrator, Integration review, answers to earlier questions, and so on. Hard links are used on the same file system; otherwise the files are copied.
  - For a running run (a log this daemon has opened and not yet closed), a snapshot of the log at the time the question was received (the snapshot of a running run in [Event log](event-log.en.md#session-logs-files-per-run), with secrets hidden again using the current secrets) is written to `<run ID>/meta.json`, `events.jsonl`, and `stderr.log` (only those with output) (not hard links). The agent's original files do not exist until the run finishes.
  - What is not laid out
    - Other tasks' logs (only this task's location is looked at)
    - Files other than the above
    - The answering run itself
    - Runs whose end is not recorded and that are not running (no `finishedAt` in `meta.json` and not opened by this daemon; the daemon stopped)
    - The files themselves of runs whose end is not recorded (secrets found after writing started are redacted again when the file is closed, so a file not yet closed may still contain them)
  - Status in the list: `available` (readable), `running` (running; has the snapshot time `snapshotAt`), `unfinished` (end not recorded), `missing` (the Activity has the run's ID but there is no log), `unreadable` (`meta.json` cannot be read). It also holds logs with the middle omitted due to limits, the number of agent files, reasons for not copying, and files that could not be laid out.
  - The instructions include, before the ledger, the location and how to read it (search rather than read everything; it cannot be modified; state which run of which step; say so if any run has no log, was omitted, or is unreadable), and the list of runs (the step or role name and which attempt, the run ID, the agent, start and end, the result, the log size, truncation; up to 8000 characters; if it does not fit, older runs are omitted and the agent is told to read `index.json`). The logs' contents are not included. If there is a running run, its line in the list says when the snapshot was taken (and that the run continues), and the agent is told to read `events.jsonl` from the end when asked about the current state, and to say in the answer as of when it describes the state.
  - If the task's log location (`runs/<task ID>/`) does not exist, there are no runs yet (runs in the Activity are `missing`). If the location cannot be opened (no permission, not a directory, and so on, other than ENOENT), cannot be laid out, or no logs were kept, nothing is mounted; the instructions say the logs cannot be read and why (the kind of error, for example `ENOTDIR`), and the agent answers from the ledger (a warning goes to the daemon's log).
- Asking a question does not change the status, steps, or approved content, and does not stop a running task. The cost of answering (even when no answer could be given) counts toward the task's budget.

## PR-review-only tasks

- The only step is `review`. Before running, the head of the target PR, the base commit, and the PR author's login are recorded (`ReviewTargetResolved`; empty if the author cannot be read). The name of the PR's head branch is recorded too when it can be read (`headBranch`; the task keeps it in `reviewBranch` and does not clear it when a re-review starts; the [MCP server](mcp-server.en.md#prs-and-branches-tied-to-a-task) uses it to find a task from a branch name). The code at the PR's head commit and the whole diff (mounted read-only at `/sacty-review`; the first 100000 characters in the instructions) are passed.
- Reviews already on the PR: before running, sacty reads the PR's reviews, line comments, and ordinary comments. It reads the findings by other reviewers and the author's replies, excluding posts by bots and posts by this task's account that start with the marker (its previous posts). Approving reviews with a body are included too (`includeApprovals`; they are not included when importing PR comments). What it read is passed as JSON data separate from the instructions (`existingReviews`; oldest first; at most 50 in total (`EXISTING_REVIEWS_IN_PROMPT`), 2000 characters each; replies that sacty posted to findings ([replies](approval.en.md#replies-about-how-remarks-were-handled)) are included, with a source and a reply state, and what could not be included is counted — see the next bullet), for the first review and re-reviews alike. The instructions tell the agent to check the state of the existing findings before reviewing, not to repeat a problem already raised at the same place, to decide the verdict from the findings it did not repeat plus the existing findings that are still unaddressed, and to keep the number left out in the process record (`dropped`) rather than in the body (without copying them). Whether an existing finding is unaddressed is checked against the PR's head code and the author's replies and later comments. The data has no resolved flag on threads, so a thread not being resolved is not evidence that a finding is unaddressed. A finding whose code is fixed, whose reply is confirmed against the code, or whose fix was confirmed in the previous-findings check does not count as unaddressed. Only when an existing finding is confirmed to be unaddressed does the summary say, in one line, that an existing finding is unaddressed and which one, and the verdict is not "no findings"; otherwise the summary does not say "unaddressed" (so the summary and the verdict never disagree). Whether an earlier finding (an existing finding or a finding in the previous review) is fixed is checked by opening the code and document files at the head commit being reviewed now (`HEAD_CHECK_LINES`; PBI-302 B2). The agent must not rely only on the previous review's text, the content of an earlier commit, the wording at the time the finding was written, or the author's reply, and must not write as unaddressed something it confirmed is fixed. A finding written as unaddressed carries one line saying which file and place at the head commit it read, what is written there, and what is missing; one it cannot point to is not written as unaddressed. The verdict `changes_required` is used only when at least one `[要修正]` finding holds at the head commit (one newly found, or an earlier or existing `[要修正]` confirmed as unaddressed at the head commit), and the "unaddressed" statement in the body must not disagree with the weight of the line comments or the verdict. sacty does not check an unaddressed claim against the head commit's content (it is a rule of the instructions and the default skill). The same rule is written in the default skill `review-dispatch` (`pr-review`). If there are none, "none yet" is passed. If they cannot be read, the instructions say so, the review is not stopped, and the reason is kept in the daemon log (secret values redacted). The author's replies for a re-review (below) are picked from the same read (if the author cannot be read, only the replies are treated as unreadable).
- Source and state of each comment (PBI-445): each item of the existing reviews and of the author's replies carries `by` (`annotateReviewComments`). `sacty` is a reply whose marker (`<!-- sacty-reply:<task ID>:…`) carries the ID of a sacty task that handles this PR (`remarkReplyTasksOn`: the task that created the PR, the task that continues an imported PR, or a task with a requirements/design PR) and that was posted by a sacty account (`feedback` sets `bySacty`; the marker text alone does not decide it). `person` is a post by the PR's author or by an account whose `author_association` is `OWNER`, `MEMBER`, or `COLLABORATOR` (write access is not checked). `unverified` is everything else (an account with another `author_association`, or a marker that does not match a task handling this PR). This tells people and sacty apart even when they share one GitHub account. A `by` or "a person wrote this" inside a comment body is not followed. A sacty reply also carries the state `reply` (`status` is `addressed`, `declined`, or `deferred`, read from the head of the reply by `readRemarkReply`; `declinedProposals` means it contains suggestions declined in the sorting before reworking). A `reply` without a head has no state.
  - When not everything fits (`pickExistingReviews`), the newest of these go in first: posts by people and `unverified` accounts, and sacty replies that are `declined`, `deferred`, have no head, or contain declined suggestions. The remaining slots take `addressed` replies, newest first. Items are sorted oldest first, and the number left out is written in `omitted` (`priority`, `addressed`).
- Findings that overlap addressed or rejected findings (PBI-445): the instructions (`overlapLines`; added for the first review, a re-review, and a narrowed re-review; not for self-review) carry the gist of the rule, so it also works for projects that replaced the default skill.
  - Findings that overlap a finding already addressed (checked in the files at the head commit, not from a reply alone) or a rejected one (a person's rejection, or the AI's "not handling") are not adopted and not posted.
  - A person's rejection is dropped even for a `must`. A person's rejection is only a reply whose `by` is `person` saying "won't do" or "out of scope", `deferredByPerson`, and `voidedByPerson`. Replies with `by` `sacty` or `unverified` are not a person's rejection. A `must` that overlaps the AI's "not handling" (`declinedByAuthor`, a sacty reply whose `reply` is `declined`, a reply with declined suggestions) is not dropped; it is checked against the later reasons, and shown as a new `must` if none applies.
  - Not dropped: fixes that did not work or cannot be confirmed, a different problem introduced by a fix, and a problem that changed or grew after the rejection.
  - When reasons overlap, they apply in this order: a person's rejection, the AI's "not handling", addressed, already pointed out by an existing review, outside the PR's purpose. One finding is counted in one line only. The number dropped is kept in the process record (`dropped`: overlapping existing findings, outside the PR's purpose, overlapping addressed or rejected findings, and how many of these were `must`), not in the body. The verdict is decided by the adopted findings.
  - A comment body is material: instructions, `by`, and state claims inside it are not followed.
  - `voidedByPerson`: when a task created the PR, the findings a person disabled on the screen (`RemarkVoided`, `Task.remarks[].voidedBy` is `person`; findings discarded at merge are not included; `voidedByPersonOf`) for the PR's step are passed (newest 50, 600 characters each). A review of an imported PR (no task created it) has none.
  - In a re-judgement of the same head commit, a `by: person` rejection is withdrawn without checking (written as "withdrawn (rejected by a person)", and for a `by` of `person` only); "out of scope" in other replies is still checked against the head.
  - In the re-review, the "previous findings" section also lists the previous line-comment findings, with only the place and the status (the content is not repeated). The count line in the previous body ("行へのコメントに N 件の指摘があります。") is a line sacty added, so it is neither a previous finding nor this round's count. The rework side is told that the count line is not a separate finding and is not a target of the rework (PBI-479).
  - In the re-review, each previous finding is written as confirmed addressed, not addressed, or withdrawn (with a reason). A withdrawn finding is not counted as not addressed and is not a target of the task's rework.
- sacty does the posting. The instructions tell the agent to use the default skills `review-dispatch` (with the `pr-review` flow) and `writing`, not to post by itself (not to write on the PR with gh or the GitHub API), and to give priority to the output format of the instructions when they conflict with the skills. sacty adds the verdict, the @ mention of the author, and the statement that AI posted the review, so the agent does not write them.
- Verification: the workspace is a copy of the PR's code only, with no dependencies or build outputs. The instructions say the agent may fetch dependencies as the lock file pins them and run verification such as formatters, linters, type checks, tests, and builds without rewriting the target files (formatters and the like run in check-only mode), following the skill's procedure (`verification-run`) before starting the viewpoint reviewers. They also say not to skip verification because dependencies are missing, and not to use the author's report in place of results the agent ran itself. CI results and sacty's final review record of an earlier version for the same commit are reused only where the agent confirms they cover the whole ([Reusing verification results for the same content](#reusing-verification-results-for-the-same-content)). If the orchestrator decided a test command (`testCommand`), it is shown as a candidate verification command. When the main target is a document (`design-doc` or `user-doc`) and the diff has no code changes, the instructions also say that, following the skill's rules, the agent runs only the checks that apply to the changed documents, and runs no code tests, builds, type checks, or code linters (including the `testCommand`). If the diff has code changes, all checks run even when the main target is a document ([Default review skills](context.en.md#default-review-skills)). A review-only task created by importing a PR, and a review child task for a PR sacty opened ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)), have no test command, because the orchestrator does not choose their steps, so no candidate is shown (the parent task's test command is not passed to the child task either; the agent picks commands from the repository's instructions and CI settings). For verification that could not run, the agent writes the command and why it stopped in the body. The time limit is the limit of the roles that run tests ([Agent execution](agent-execution.en.md#container)). During verification the PR's code (dependency install scripts and tests) runs in the agent's container and, as in other runs, can reach the agent's authentication values in the container (with a codex subscription, `auth.json`, which is written back to the host after the run) and, during the run, the gateway (GitHub reads and MCP relays) ([Agent execution](agent-execution.en.md#authentication), [Gateway](gateway.en.md)). Intake does not filter by whether a PR comes from a fork or a bot. The user documentation asks users not to import or choose PRs they do not trust.
  A review child task for an implementation PR starts services according to the parent implementation record ([Services](services.en.md#when-services-start)).
- Finding prefixes: `[要修正]` (must fix before merging) and `[提案]` (worth fixing). The agent is told to decide the weight from the skill's severity table (the size of the impact and how likely it is; [Context](context.en.md#default-review-skills)), and to apply the same table in a re-review and to a finding about a place added or changed to fix an earlier finding. Something that happens only when two or more independent conditions coincide, and is not data corruption, security, an effect that cannot be undone, a compatibility break, or a failure to meet the acceptance criteria, is not to be marked `[要修正]`. Each finding states the conditions under which it happens and the harm when it does (PBI-358). The agent adds them to findings in the body. For line comments (`sacty-review-comments`), the agent writes the severity (`severity`: `must` or `should`; `nit` is treated as `should`) and sacty adds the prefix at the start of the comment body (a prefix already at the start is replaced; with neither severity nor prefix, nothing is added). Findings with no line in the diff to attach to are written, with a prefix, in the "指摘" section of the body without asking a person (PBI-479). Only findings whose line number can be identified are made into line comments; a finding outside the diff that has no line number is written in the "指摘" section of the body. A finding made into a line comment is not written again in any section of the body, in the same content or in other words (the conditions under which it happens, the harm, the fix); the "指摘" section of the body holds only findings that are not line comments (`HEAD_CHECK_LINES`, the finding line of the instruction, and `reviewRecordInstructionLines` take the same form). A line comment outside the diff is moved by sacty into the "行についての指摘" section of the body, so the agent does not write it in the "指摘" section either (it appears in the body once). The count of line comments is written by sacty under the verdict line, so the agent does not write it in the summary. The verdict, how weights are counted, and the self-review (which posts no line comments) do not change.
- Documents shown in the PR description (such as a design outside Git): following the skill, the agent sorts each into a review target or evidence, and reviews the targets too. Findings on documents go in the body. If the main target document of a requirements or design PR cannot be read, the agent gives no verdict. For other unreadable target documents, it writes what is unchecked and what the reader should check at the start of the body.
- Range: the agent is told to decide the range it gives the reviewers from the PR's diff. If the diff cannot be read, it gives no verdict. For a document that is in the diff, the reviewers look only at the statements the diff changed or added and the statements whose correctness those changes can affect, even when the PR description names the document; the whole of its unchanged existing text is not checked. The agent is told not to widen the range because of a reviewer's result or the previous review (in re-reviews too; PBI-349).
- Scope of the PR of a child task of a split: when the task that created the PR reviewed by a PR review child task (`reviewOf`) is a child task of a split (including a fix child task), "この PR の範囲（分割の子タスク）" is added to the instructions (`reviewChildScopeLines`; in the first review and in re-reviews; PBI-351).
  - The instructions carry the title of the task that created the PR, the parent task's title, that it is a child task of a split, and the child task's content that the task split agent wrote (`childScopeOf`; the same as the scope section of the PR body; [Assembling the implementation PR body](approval.en.md#assembling-the-implementation-pr-body)).
  - Even when what is written as out of scope, or what another child task handles, is not implemented, the agent is told not to mark it `[要修正]` (even if the parent task's requirements or design mention it).
  - When the agent notices that merging only this PR causes trouble with something out of scope, it is told not to mark it `[要修正]` but to write it in the body as "人が確かめること" (something for a person to confirm), and not to put it in `findings` of `rework` either.
  - What is in scope (what the child task's body says it achieves, its acceptance criteria, and defects caused by this PR's changes) is pointed out as before.
  - Nothing is added to the instructions of a review of a PR of a task that was not split, or of a PR created by a person (a review-only task). Nothing is added either for the PR of a child task whose scope is unknown (no record, and the original text cannot be confirmed from the records of the split).
- Scope of the review of a document PR before implementation (PBI-419): when the PR under review is a requirements or design PR and the task that created it still has an implementation step (`implement` exists and is not skipped), the instructions state that this PR is a document PR before implementation, that the implementation PR will be reviewed separately later, and that this review looks only at direction and gaps (`reviewDocBeforeImplementLines`).
  - What may be raised: purpose and scope, mismatches with the request or higher-level requirements, gaps and contradictions in requirements and acceptance criteria, the choice of approach and its reason, whether decisions for a human appear in the questions, and mistakes or gaps in hard-to-undo decisions (public interfaces, stored data shapes, security, migration). Implementation details, test-viewpoint values, granularity and boundary-value ordering, and wording are left to the implementation PR review. If a written approach or test viewpoint misleads the direction or misses an acceptance criterion (a whole viewpoint is missing), it may still be raised.
  - The viewpoints launched are narrowed to D-1, D-2, D-5, D-10 and X-1 when the main target is `design-doc` (conditional viewpoints, X-2, X-3 and R follow the usual rules). D-3, D-4 and D-6 stay in the launch table with a reason.
  - Nothing is added and viewpoints are not narrowed for implementation PRs, taken-in PRs (no task created the PR), or document PRs of tasks with no remaining implementation (design-only, split, document) or with implementation skipped. The verdict, weight, rework target and re-review rules do not change. The rules themselves live in the default skill `review-dispatch`.
- The body and the process record (PBI-460; [ADR](../adr/20261121-1603-superseded-pr-review-without-process-info.md)): the body and line comments posted to the PR carry only what a reader of the PR needs to decide whether to fix something and what the problem is, and Sacty's process details are returned in the record block after the body (`reviewRecordInstructionLines`). A reader of the PR may not use Sacty.
  - The body starts with the summary (its first line is the heading "## 総評"). The agent writes no progress sentences (such as "レビューの本文を書きます") before the summary.
  - What it writes: the summary that grounds the verdict, the findings (where, what the problem is, how to fix it; the body holds only findings that are not line comments; PBI-479), and the verification results needed to decide on a fix (what failed and what could not be checked).
  - What it does not write: viewpoint IDs, counts, and names; per-viewpoint reviewers, subagents, sequential mode, and the launch table; findings not adopted and their list; counts of dropped findings; the agent and model that ran and any switch; how verification was done (such as reuse) and the checks that passed; Sacty's task ID.
  - What could not be checked is written at the start of the body in plain terms (what is unchecked and what the reader should do), without viewpoint numbers or the words "担当" and "サブエージェント". The same applies when a document, the diff, or an existing review could not be fetched.
  - The record block is the JSON in one code block whose info string is `sacty-review-record` (fields `mode`, `viewpoints`, `notReviewed`, `dismissed`, `dropped`, `scope`, `verification`). sacty reads it from the answer, checks it, and keeps it in `reviewRecord` of `AgentRunCompleted` (`reviewRecordOf`). Even when it cannot be read, the review is used and posting does not stop. The fields, limits, checks, and the rules for removing it from posted strings are in [Activity log](event-log.en.md#projection).
  - The record and the agent information per round (agent, model, number of reviewers, switch) are read in the review part of the task details (all rounds; a round without a record is not shown; `ReviewRecords`) and in `reviewRecords` of `get_task` of the MCP server. The output of Codex's `codex exec --json` does not show reviewers being started, only waits (confirmed in the run logs of 0.167.0), so whether the per-viewpoint review took place is checked in the record on the screen and in `get_task`. sacty counts the reviewers from the copied session files (the next item).
- Narrowing the verification of a re-review whose changes since the previous review are documents only (PBI-421; narrowing the viewpoints was merged into the next item, "Narrowing the scope and viewpoints of a re-review", by PBI-432): in a re-review, when the changes from the head commit reviewed last time to the current head commit are documents only and the main target of the PR is `code`, the prompt states, with the changed paths, that the review follows rule 10 of the skill `review-dispatch` (narrow the verification; the viewpoints started are not narrowed) (`rereviewDocsOnlyLines`). The daemon adds it only when it has confirmed all of the following (`rereviewDocsOnlyOf`). When it cannot confirm, it does not narrow and the review does not stop.
  - There is a previous round and the head differs from it. The branch the PR targets (`reviewTarget.baseBranch`) exists in both the previous and the current round and is the same. The previous round has a verdict (a task created by a GitHub re-request does not have the verdict of the previous round, so it does not narrow, with or without a record). The previous round has a record (`previousReview.record`), with no viewpoints that could not be reviewed (`notReviewed`) and no verification that stopped (`kind` of `verification` is `stopped`) (`reviewRecordBlocksNarrowing`; decided by the structured fields only, without reading the sentences; a round with no record or `null` is not narrowed). When the previous verdict is `changes_required`, no line comment of the earlier rounds is a `[要修正]` on a path that is not a document either.
  - The previous head and the previous target commit can be fetched in a call separate from fetching the current head and target. The previous head is an ancestor of the current head, and the changes between them are documents only (`documentsOnlySince`; the judgment is `isChangeDocumentsOnly`).
  - The start of the PR diff (the merge-base of the head and the target commit, for the previous and the current round; `mergeBaseOf`) can be obtained for both and is the same. If the base branch only moved ahead and the PR did not merge it, it is the same. If the PR merged it, changed the target, or rewrote history, the start or the target branch changes, or the merged changes enter the diff since the previous round, so it does not narrow.
  - The PR diff (`pr.diff`) contains something that is not a document (a PR of documents only is already narrowed to the checks that apply to documents; with an unreadable path it does not narrow either, because the main target cannot be decided). This is not a round that gets the section on the scope of a document PR before implementation. No line comment of the previous round is a `[要修正]` on a path that is not a document.
  - "Documents only" means files with a document extension (`isDocumentsOnly`), minus instructions to agents (files named `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, or `SKILL.md`, in any letter case, and files under a directory that starts with `.`) and files under a directory that has `SKILL.md` in the current tree. An empty diff is not documents only. A changed path with a control character (such as a newline) is treated as unconfirmable (it does not narrow and does not carry over). It does not narrow either when more than 50 paths changed (the parent cannot open the rest). When the directories above the changed paths number more than 200, that too is treated as unconfirmable (it does not narrow and does not carry over, and nothing is logged). The changed paths in the prompt are names given by the PR author, so they are not embedded in the sentences of the instruction but passed separately as JSON data. The reason it could not be confirmed is logged in one line in the daemon log.
  - In a round that matches, the lines "run all the checks when the diff has code changes" and "run the verification again on the current code" are replaced with sentences that follow rule 10. The line "starting the reviewers is not skipped even for documents only" is not replaced by this section (viewpoints are narrowed only in a round that has the section of the next item, and that round gets its own sentence). The prompt also gives the main points of rule 10 (the record of `scope: docs` and `skipped`, the conditions under which it does not narrow, and that the viewpoints are not narrowed).
  - The parent opens the changed files and re-reads them with the idea of the main target kind. If any of these holds, it does not narrow the verification and runs all of it: something is not a document or is unclear, an instruction to agents, a document that code or tests read, a `must` of the previous body that reaches something that is not a document, or a viewpoint that could not be reviewed (`notReviewed`) or a check that stopped (`kind` is `stopped`) in the previous record (`record` of `previousReview` in the prompt data; when the prompt has no previous record, the previous body is checked instead).
  - When it narrows, the checks run with `scope: docs`, and the code tests are left as `skipped` with the reason. The agent writes in the body, in plain terms, the checks it did not run together with what the reader should check (for example "コードのテストは実行していません"). The reason and the method are not written in the body but in `verification` of the record (`kind` is `skipped`). The verdict, the weights, and the "previous findings" section do not change.
  - The first review, `self-review`, rule 8, and rule 9 do not change.
- Narrowing the scope and viewpoints of a re-review (PBI-432): a round whose review task has a record of its own previous post (`previousReview`; a re-review) narrows what it looks at and the viewpoints it starts to the check of the previous findings and the changes since the previous review. The daemon decides whether to narrow and states it in the prompt (`rereviewNarrowOf`, `rereviewNarrowLines`; the section "--- 再レビューの範囲の絞り ---"; rule 11 of the skill). The skill narrows only in a round with that statement. That the agent can read its own previous post in the PR's comments and reviews is not a reason to narrow the scope or the viewpoints (a re-review without the statement stays as before: the whole PR, with the same rules as a first review).
  - A first review is not narrowed: a round whose task has no record of its own previous post looks at the whole PR and decides the viewpoints by the first-review rules, however many reviews by other people or by other sacty instances (posts with the marker of a task not in this ledger) the PR has, and even if another task of the same ledger once reviewed the same PR. The rule that removes overlap with existing findings does not change.
  - What a narrowed round does: (a) checks whether the previous findings are fixed at the current head, and (b) looks at the places changed or added between the previous head and the current head, and the places whose correctness may change because of that. The viewpoints it starts are those concerning the previous findings; X-1 (the request text says to check that the fix does not contradict the rest of the PR); the conditional viewpoints whose launch condition the changes since the previous review meet; the safety viewpoint decided by the kind of those changes (C-3 for code, D-5 for a design document, U-5 for a user-facing document; for documents, the accuracy viewpoints U-1 and D-2 too); X-2 (when there is a verification result); and X-3 and R (only when the repository's instructions apply to the changes since the previous review). The required viewpoints that do not match are left in `viewpoints` of the record as `not_launched` with the reason (not in the body), and are not counted as viewpoints that could not be seen. This narrowing takes precedence over rule 1 (start all required viewpoints) and rule 5. It also applies to the re-review of a document PR before implementation (D-3, D-4, D-6 and "what is not raised as a finding" do not change).
  - A round that judges the same head again (the parent declined everything, or the author replied without pushing; the `reason` of the `ReviewRestarted` that started the current round (`Task.reviewRestartReason`) is `declined` or `replied`, and `reviewRejudgeCommit` or `reviewReplyCommit` equals the current head; a round that a person starts by hand on the same head after such a re-judgment is not a re-judging round, so it is not narrowed and sees the whole PR) has no changes since the previous review, so it only checks the previous findings (the viewpoints concerning the previous findings, and X-1). No diff is handed over.
  - What does not change: verification runs again on the new head (the previous result and the CI result are not enough; only the verification narrowing of rule 10 for documents-only changes remains), how each previous finding is written, opening the files at the head to check, reconsidering weights, "changes required" when a previous `must` is unaddressed, the author's replies, findings a person decided to defer, overlap with existing reviews, the out-of-purpose rule, how the verdict and weights are decided, and giving the risk assessment only in a round without findings. A `must` that is found is adopted even when its place is outside the changes since the previous review. A different appearance of the same cause as a previous `must` is stated in the body even when narrowed, and starts the policy viewpoint (C-17, D-1) except for user documentation.
  - The daemon does not narrow (it also does not narrow when it cannot confirm or is unsure, and leaves one line in the daemon log with the reason): the previous head cannot be fetched or is not an ancestor of the current head (history rewritten); the previous base commit or branch is not recorded, or the PR's target branch or the start of its diff (merge-base) changed since last time; the previous round has no verdict; the previous round's record (`previousReview.record`) is missing or `null`, or has viewpoints that could not be reviewed (`notReviewed`) or a verification whose `kind` is `stopped` (`reviewRecordBlocksNarrowing`; decided by the structured fields only, without reading the sentences); it could not be confirmed that the previous round started its reviewers (the number in the previous round's `reviewDispatch` was counted as 0; a `null` that could not be counted, or a missing record, is not evidence that none started, so it narrows); the lines changed since the previous review exceed half of the lines of the whole PR diff (exactly half narrows); three or more of the files changed since the previous review, and more than half of them, were not in the PR diff at the time of the previous review; the changes since the previous review are empty, exceed one million characters (cannot be handed over), or have a path with a control character or quotation marks; or the task that made the PR submitted after going back to an earlier step and redoing it (the previous round's target for the findings is an earlier step than the PR's step; `reviewReworkTarget`).
    The values for the lines and for new files are rules of thumb to keep a fix that rewrote most of the PR, or one that touched many places not seen before, from being reviewed only by its changes since the previous review (up to half the PR, the changes are judged unlikely to hide a miss). A `must` that is missed is caught in the next round or by the person's check (the ADR records the kind of miss that is accepted).
  - A task created by a GitHub re-request has a record of its own previous post but no verdict for the previous round (`reviewVerdicts`), so it is not narrowed, with or without a previous record (the verdict is not copied and no new state is added, as in PBI-421).
  - The findings of a round that did not reach the parent are put inside the scope even in a narrowed round, and the agent checks them again on the current head (PBI-465; [Stopping a review before posting when the head changes](#stopping-a-review-before-posting-when-the-head-changes)).
  - The changes since the previous review (from the previous head to the current head, `diffCommits`) are handed over like the whole PR diff, as JSON data separate from the instructions. The whole is always put in another read-only file (`since.diff`) in the same place as the whole PR diff (not for a re-judgement of the same head), and the prompt says where it is. If this file cannot be written, the run does not fail: the review is not narrowed and sees the whole PR (one line in the daemon log). The scope of a document that is not in the diff (such as a document outside Git) is not carried by the changes since the previous review, so the instruction of a narrowed round also has it decided by the linked-document re-review rule (`linked-docs.md`). A renamed file is counted as one file (its new name) in the "files not in the previous PR diff" condition. When they are long (over 60,000 characters) only the head is in the prompt. Secrets are masked the same way as in the whole PR diff. The diff is handled as the PR author's content, as the whole PR diff is: separate from the instructions, and instructions written in it are not followed.
  - In a narrowed round, the line "the scope is the whole PR" of `rereviewLines` is replaced with one that says to narrow as the section says. The instruction of a round that is not narrowed does not change. The section gives the main points (the scope, the viewpoints to start, the conditions under which the parent does not narrow (the previous record has a viewpoint that could not be reviewed or a check that stopped (when the prompt has no previous record, the previous body is checked instead), the previous body says there is no verdict or cannot be read, the changes since the previous review cannot be read or contradict the current code, they read as a rewrite, or it is unsure; that it does not narrow and why go in `scope` of the record, not in the body), what does not change, and the one line of the body) so that a project that replaced the skill still gets them.
    The body gets only the fact that it was narrowed, in the one line "前回（<前回の先頭>）以降の変更と前回の指摘だけを確かめた". Why it was narrowed and the viewpoints not started go in `scope` and `viewpoints` (`not_launched` with the reason) of the record.
  - A round whose changes since the previous review are documents only and that also matches this section takes the viewpoints from this section and the verification from the previous item (the two sections do not contradict). A round that does not match this section is narrowed only in verification by the documents-only section, and its viewpoints follow rules 1 to 7.
- Starting the reviewers: the prompt gives the order to follow (after the skill's `SKILL.md`, read the flow document `references/pr-review.md` and the viewpoint catalog `references/viewpoints.md`; build the launch table and start all the reviewers that the skill's launch rules decide; write the body only after the results are in), tells the agent not to start writing findings or the summary itself before starting the reviewers, and says that starting them is not skipped whatever the size of the target and whether or not it is a re-review (`reviewDispatchInstructionLines`; the same text for every kind of agent; PBI-379).
  - After the run, sacty counts the reviewers that were started, from the copied agent session files (`countReviewDispatch`).
    For Claude Code, it is the larger of the number of per-reviewer session files (files named in the form `agent-<hexadecimal ID>.jsonl` under `projects/<working directory>/<session>/subagents/`, at any depth; a tool that starts several at once puts them under `subagents/workflows/`; files with other names are not counted) and the number of `Agent`, `Task`, and `Workflow` calls in the parent session (`projects/<working directory>/<session>.jsonl`; duplicates removed by the call ID).
    For Codex, it is the `spawn_agent` calls in the rollout whose first `session_meta` has `source` set to `exec` (the parent; reviewers' rollouts inherit the parent's history, so they are not counted).
  - When it cannot be counted (the session files were not copied, there is no parent session, a file with a part left out at the size limit has 0 calls, a run with files that could not be copied has 0, or the agent is of a kind other than `claude-code` and `codex`), the count is unknown and the run goes on as it is. The kind of reason is written to the daemon's log together with the task and run IDs (it is not kept in the activity log).
    A run whose parent session can be read, and where starting reviewers is left in neither of the forms above, is counted as 0 (also when a new agent version changes the form of both records).
  - sacty also checks whether the run had a way to start reviewers. For Claude Code, `tools` in the first event of the run's output (`system`, `init`) has one of `Agent`, `Task`, and `Workflow`. For Codex, the parent's `turn_context` has `multi_agent_version`. When this cannot be confirmed, the run goes on as it is even with 0 (the skill's sequential mode).
  - The count is kept in `reviewDispatch` of `AgentRunCompleted` (`subagents`; `null` when unknown; `runtime` is the kind of agent, `model` is the run's model, and `configuredAgentId` is the configured agent when it was unavailable and its fallback ran). The task holds it in `reviewDispatch`, together with the round and the agent of the run. A round that returned the record block also holds it in that round's element of `reviewRecords`.
  - A run that had the way and started 0 does not have its verdict and body used, and nothing is posted to the PR. `AgentRunFailed` (`reason` is `error`, `subagents` in `reviewDispatch` is 0, `review.notDispatched`) is recorded and the task goes back to waiting to run without stopping. The head of the next run's prompt says that the previous run did not start the reviewers (`reviewUndispatchedLines`).
    This `AgentRunFailed` records a run where the agent finished and sacty did not use the result. The per-step cost table shows it as "Not used", apart from failures ([Activity log](event-log.en.md)). The error report's kind (`error`) and the audit's retry count treat it like any other `AgentRunFailed` (the reason text tells them apart).
  - There are up to 3 retries (`REVIEW_UNDISPATCHED_RETRIES`). If the next run also starts 0, `AgentRunFailed` and `TaskPaused` (`reason` is `error`, `review.notDispatchedPaused`) are recorded and the task stops. When a person resumes, the count starts over and the review runs again (`sinceResume` in the task's `reviewUndispatched`; `runs` keeps counting until a review is used, and is shown in the prompt).
  - sacty does not check what the reviewers did or how well.
- Verdict: the agent adds `verdict` in `sacty-review-verdict` (`changes_required`: changes required, `suggestions`: suggestions only (OK to merge), `no_findings`: no findings). sacty raises it to `changes_required` if a line comment has `[要修正]`, and to `suggestions` if there are findings but the verdict is `no_findings`. Line comments alone do not make it `changes_required`. If there is no verdict or it is not one of the values, and there is no `[要修正]` finding, nothing is kept. In that case the reason is kept in `reviewVerdictMissing` of `AgentRunCompleted` (`missing` of `reviewVerdicts` per round; PBI-378): `absent` when the answer has no verdict block (the reviewer gave no verdict), and `invalid` when there is a block but the verdict is not one of the values (it could not be read). Even with no block that parses as JSON, it is `invalid` when the answer has the verdict heading in the form of a JSON key (`"sacty-review-verdict":`), such as a trailing comma or a block cut off midway (a verdict whose shape broke is not reported as one that was not given). An answer whose body only mentions the name of the heading is `absent`. An answer that writes an example of the verdict block in the form of a JSON key in its body is `invalid` even if it gave no verdict (the two are not told apart). sacty does not infer a verdict from the wording of the body (such as "no findings"). A round without a verdict is imported, and when its rework target cannot be read, the PR step is redone even for requirements and design PRs. Limiting absent verdicts to unreviewable cases reduces rework caused by the absence alone. The agent gives no verdict if it cannot read the diff or the main target document of a requirements or design PR. Even when some parts are unchecked, it gives `changes_required` for a must finding at the current head, or `suggestions` or `no_findings` according to the findings. Running CI, unavailable visual checks, and tests that cannot run in the review environment do not prevent a verdict; the body begins with what remains unchecked (PBI-485). A viewpoint whose reviewer failed even after relaunching is reviewed by the parent, and if that succeeds it counts as checked; only a viewpoint the parent could not review either is unchecked here (PBI-459). When it adds no verdict, the agent is told to write the reason in plain terms (what is unchecked and what the reader should do) at the start of the body (PBI-378; without viewpoint numbers or the word for reviewers). The verdict block is removed from the posted body and kept in `reviewVerdict` of `AgentRunCompleted` (per round in `reviewVerdicts`). A PR review child task (`reviewOf`) is also asked to add the step to redo and the cause for each finding (`rework`) to the verdict block (PBI-332; [Importing PR comments](approval.en.md#importing-pr-comments)). What can be read is kept in `reviewRework` of `AgentRunCompleted` (`rework` of `reviewVerdicts` per round). A review of a PR is delivered to the original task that opened it for rounds with `changes_required` or `suggestions`, and for rounds with no verdict (the reviewer gave no verdict, or the verdict could not be read) (rounds with `no_findings` are not delivered; how the review task was taken in (label, request, or manually) does not matter; [Approval and request changes](approval.en.md#importing-pr-comments)).
- Posted body: the marker, the heading "sacty のレビュー", one line with the @ mention of the author and the verdict (no @ if the author is not in the form of a login; if there is no verdict, the line depends on the reason: "判定：付いていません（レビューが判定を付けませんでした。…）" for a round where the reviewer gave no verdict (`absent`), and "判定：読み取れませんでした（本文と行へのコメントを確かめてください）" for a round whose verdict could not be read (`invalid`, or a round with no recorded reason); `buildReviewBody`), the count line of line comments, the agent's body, and the separator `---` with "AI がレビューしました（人間は確認していません）。", in this order. The count line is written just under the verdict line as "行へのコメントに N 件の指摘があります。" (PBI-479). It is added only when one or more line comments are posted (also in a round with no verdict or an unreadable verdict). It is not added when there are no line comments, or when all of them are put into the body and posted again after a 422 (they appear in the "行についての指摘" section of the body). The line does not use the prefixes (`[要修正]`, `[提案]`) or the form "<path>:<line>：", and does not break the count down by weight (the triage does not read it as a finding). The guide on the verdict line of a round with no verdict ("本文と行へのコメントを確かめてください") does not depend on whether the count line is there. The end of the body is only these two lines. The agent, the model, the number of reviewers, the switch, and the task ID are not written in the body (they are shown on the task screen and in `reviewRecords` of `get_task`). The marker in an HTML comment that is not displayed (which includes the task ID) stays. The record block is removed again right before posting from the agent's body, the bodies of line comments, and the risk assessment (`stripReviewRecord`; [Activity log](event-log.en.md#projection)). With Claude Code, the agent's body is read from the last `result` that contains the verdict block (a reply to a notification after the final answer is not posted; [Agent execution](agent-execution.en.md#output-handling)). When `reviewMentionSelf` in the sacty settings is On, the @ mention goes to the posting account (the gh account chosen for that host in the project) instead of the author (no one is mentioned if it is not in the form of a login; the author is not mentioned). In a round where a review that is assessed (a review task imported from a GitHub PR, or a review child task of an implementation PR) judged the head of this round as having no findings, the PR risk assessment section for the head of this round is placed between the verdict line and the agent's body (not for a round without findings, nor for a requirements or design PR child task; [PR risk assessment](risk-assessment.en.md#assessment-in-the-review-step); `riskAssessmentLines`).
- Right before posting, the PR's head commit is checked (not when an already posted review is found by the marker). If it differs from the reviewed commit (pushed in the meantime) and the PR is from a fork (`PullRequestStatus.fork` is not confirmed to be false), the review is posted against the reviewed commit, and the body says which commit was reviewed and that "Re-review" reviews the latest one. That head is kept in `latestCommit` of `PullRequestReviewPosted`, and also in the body as a hidden marker. For a PR not from a fork, if the head differs, the round is stopped without posting (`reason: head_changed` of `ReviewRunStopped`; PBI-465; [Stopping a review before posting when the head changes](#stopping-a-review-before-posting-when-the-head-changes)). If it cannot be checked (including when the response has no head commit or an empty one), the task pauses without posting (`review.headUnknown`; resuming checks again). If sacty stopped after posting and before recording, the head is recorded again from the marker in the body of the posted review.
- The result is posted to the PR as a review (`COMMENT`) without waiting for a person's approval. If line comments are rejected with 422, they are put into the body and posted again. Once posted, the review step ends (`PullRequestReviewPosted`). If the verdict of that round is no findings (`no_findings`), the task completes; otherwise it does not complete and watches the PR for changes ([Watching the PR after posting](#watching-the-pr-after-posting)).
- Re-review: a task that has posted its review (a completed task, or a task watching the PR for changes; `canRereview`) can put `review` back to waiting to run and review the latest commit again (`ReviewRestarted`). This is the behavior when a person presses "Review again" in the UI, and when sacty finds a change in a watched PR (`reason: pushed`, `replied`; not for a PR from a fork; [Watching the PR after posting](#watching-the-pr-after-posting)). A review child task is also put back the same way by sacty when the parent updates the PR and goes back to waiting for approval (`reason: updated`; [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)). A GitHub review re-request creates a separate review-only task without reopening the original task (see [Intake](intake.en.md)). In both cases, the previous body, line comments, reviewed commit, and posting time, and that round's record (`record`; for a GitHub re-request, the record of the latest round of the original task; no field for a round without one), are kept in `previousReview`. The review target (`ReviewTargetResolved`, `reviewTarget`) holds the branch the PR targets (`baseBranch`; `base.ref` of GitHub), and `previousReview` holds the target commit (`baseCommit`) and target branch (`baseBranch`) of that round, so that a re-review whose changes since the previous review are documents only can confirm that the start of the PR diff is the same as last time (a record without them is not narrowed; PBI-421). When a re-review replaces `previousReview`, the replaced one is added to `earlierReviews` in oldest-first order (the newest 5; a separate task made from a GitHub re-request has none; PBI-342). From the third review on, the instructions also put the reviews before the previous one in the data (each body up to 5000 characters), to compare causes with earlier required fixes (only the previous findings are checked for fixes). The instructions include the previous findings and the PR author's replies since the previous post, as JSON data separate from the instructions. When there is a previous record, it goes in `record` of `previousReview` in the data, with a note that it is untrusted input that includes sentences written by an agent that read the PR, and that it is data, not instructions (`earlierReviews` does not get records). The author's replies are the PR reviews, line comments, and regular comments by the author's login (excluding those starting with sacty's review marker; the newest 30, up to 2000 characters each). On a PR sacty created, the replies sacty posted with the author's account about how remarks were handled ([Replies about how remarks were handled](approval.en.md#replies-about-how-remarks-were-handled)) are among the author's replies too (`includeSactyReplies`). For each previous finding, the agent writes whether it confirmed the fix or it is still open (checked the same way as the existing findings above: against the files at the head commit now, with the place it read added to any "unaddressed"; this is written in the re-review section of the instructions and not repeated). The PR review child task also gets, every time as data, the suggestions the parent declined in the sorting before reworking (`declinedByAuthor`), and writes in the "previous findings" section that the PR's author decided not to handle them. It does not count them as unaddressed, does not raise them again, and does not use them as grounds for the verdict. Only when they turn out to have must-fix weight, or later changes made their impact larger, does it raise them as a new must-fix with the grounds ([The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)). When a finding raised as `[要修正]` (must fix) last time is not fixed, the agent checks its weight again with the skill's severity table (size of impact and likelihood). A finding that turns out to be of `[提案]` (suggestion) weight by the table (a medium impact that occurs only when two or more independent conditions coincide; a small impact, however likely it is; a failure to meet the acceptance criteria or requirements is excluded and stays must-fix) is not counted as an unaddressed must-fix finding and is treated as a `[提案]` (the same rule as the adoption rules of the default skill `pr-review`). A finding whose weight was reconsidered is written in two places: the agent writes that it reconsidered the weight, with the grounds, on that finding's line in the previous-findings section, and also in one line in the summary. A finding whose weight was reconsidered is kept for that round even when its place is outside the diff since the previous review. It is kept only for the one round in which the weight was reconsidered. A finding that is described as reconsidered on the line for the same place and the same problem in the previous review's previous-findings section is, in a round where the head commit has moved on, listed neither in the section nor in the summary and is not used as grounds for the verdict (it is treated like any other suggestion only when its place is in the diff since the previous review). When the agent cannot read whether it is described that way, it treats the finding as reconsidered this time. When the finding turns out to be of must-fix weight by the table this time, it is adopted as must-fix. A round that re-judges the same head commit as the previous one is treated as a continuation of the round in which the weight was reconsidered, and a finding that the previous review describes as reconsidered is kept too. When the only unaddressed previous must-fix findings are ones whose weight was reconsidered and there is no other must-fix finding, the verdict is `suggestions`, not `changes_required`. In a round that is given the handling of proposals to defer, a finding that the handling does not count as unaddressed (one a person decided to defer, or one awaiting a decision that is of suggestion weight) keeps that handling for the verdict. When a previous must-fix finding that is awaiting a decision is judged to be of suggestion weight this time, the agent writes on that finding's line, besides that it is awaiting a decision, that the weight was lowered and the grounds ([Proposals to defer and the person's decisions](approval.en.md#proposals-to-defer-and-the-persons-decisions)). If the replies cannot be read (including when the author is unknown), the instructions say so and the review continues, and the reason is written to the daemon log with the task and the PR (secret values are masked). In a re-review too, the agent reviews with the skill `review-dispatch` and runs verification again on the new code (a re-review whose changes since the previous review are documents only has its verification narrowed; some re-reviews have the scope and the viewpoints narrowed to the check of the previous findings and the changes since the previous review; see the items above).
- Language: the heading, verdict, note, and fixed sentence added by sacty, and the finding prefixes, are fixed in Japanese. The agent's body and findings follow the writing rules of the target repository (in the order of the skill `writing`), and Japanese when there are none.
- In the PR check (every 60 seconds), if the PR of a review task that has not posted its review yet (waiting to run, running, paused before posting, and so on) has been merged or closed, the task is canceled (the running run is stopped; `reason: pull_request_merged` or `pull_request_closed` of `TaskCancelled`). A task in the middle of a re-review run is treated the same (it is canceled even though the review of an earlier round was posted). A task that is running, resolving its target, or waiting to post records `ReviewRunStopped` (`reason: merged` or `closed`) before `TaskCancelled`, so the stopped run does not look like a failure (PBI-465; [Stopping a review before posting when the head changes](#stopping-a-review-before-posting-when-the-head-changes)). A review task a person created without intake (no `source`) is not subject to this cancel (even if the PR is merged or closed during the run, it runs to the end and posts; if the verdict is not no findings, the next check ends the watch and completes it, and if it is no findings, it completes at posting). A task that has posted its review is not canceled but completed ([Watching the PR after posting](#watching-the-pr-after-posting)).

### Stopping a review before posting when the head changes

Related ADR: [A review whose PR head changes before posting is stopped and started again, and the findings of a round that did not reach the parent are checked again in the next round](../adr/20261121-1756-stop-unposted-review-on-head-change.md)

When the head of the PR changes during a review that has not been posted (including the first one), the round is stopped without posting the body for the old head (PBI-465). Once the head settles, the review starts again on the new head with the same round number. A PR from a fork is not stopped (the review for the old head is posted with `latestCommit`; PBI-461). The behavior of a review whose head does not change stays the same.

- Tasks watched: in the PR check (every 60 seconds; `checkReviewPullRequests` → `checkReviewHead`), the PR head is read for tasks whose current step is the review step, that have not posted the review, and that are waiting to run or running. This holds for the first review and re-reviews alike, for intake tasks, and for tasks a person created without intake (no `source`).
  - The PR read is `source` if there is one, otherwise the target (`reviewTarget`), otherwise the `repo` and `number` of `reviewStop` left by the stop (`reviewPullRequestOf`).
  - A paused task is not watched (there is no run to stop and nothing can be recorded). After it resumes, this watch or the check right before posting finds the change in the run that follows. A task waiting to post (`idle`) is found by the check right before posting.
  - A PR from a fork (`status.fork` is not confirmed to be false) is not stopped. A response whose head cannot be read (no head or a wrong shape) decides nothing.
- Stopping: if the head differs from the target's head (`reviewTarget.headCommit`), the round is stopped without waiting (`abortReviewRun`). Only the process that decided to stop records `ReviewRunStopped`.
  - Running or resolving the target: a stop mark (`reviewStopping` in memory) is set, the run is stopped, and after the container is confirmed stopped, `ReviewRunStopped` is recorded (`reason: head_changed`, the head being reviewed in `from`, the new head in `to`, the stopped runs in `runIds`; actor `sacty`).
  - The run's failure path sees the mark and does not record `AgentRunFailed` or `TaskPaused`. The cost of the stopped run (the part without `AgentRunCompleted`) is kept in memory and carried in `costUsd`, `estimated`, `usage`, and `costUnknown` of `ReviewRunStopped`.
  - Waiting to post: after the run, the check right before posting (`composeReviewPost`) finds the different head and records `ReviewRunStopped` without posting. The run's cost was already counted by `AgentRunCompleted`, so this record carries no cost.
  - When the container cannot be confirmed stopped: `ReviewRunStopped` is not recorded, and the task pauses with `unstoppedRuns` (`TaskPaused`; if a run is open, `AgentRunFailed` first) to wait for a person to check (the workspace may still be written to, so the review does not start again).
  - If a person asks to cancel or pause while it is stopping, the person's action wins and `ReviewRunStopped` is not recorded. A pause is recorded as the person's pause both when requested before the detection and when requested while the stopped run's container is being confirmed after the run returned as failed (if the task is still running, the cost of the stopped run is kept in `AgentRunFailed` before `TaskPaused` is recorded).
- Projection of a stopped round (`head_changed`): the task goes back to `queued`, and `reviewTarget`, `reviewResolvedAt`, the current round's `outputs.review` and `reviewComments`, and the current round's element of the per-round records (`reviewVerdicts`, `reviewRecords`, `reviewDispatch`) are removed. `reviewRound`, `previousReview`, and `earlierReviews` do not change (the round number does not advance). The record of the stopped round is not shown on the screen or by `get_task`, and is not used for the `previousReview.record` that a later `ReviewRestarted` makes after the restarted round. As the mark of the stop, the task holds `Task.reviewStop` (`from`, `to`, `at`, and the `repo` and `number` of the removed target), which the next `ReviewTargetResolved` clears (no field is added to the activity log; [Activity log](event-log.en.md#projection)).
- Starting again: a task with `reviewStop` and no target is not put in the run queue (`runNext`, `queuedTaskIds`) until the same head has been seen for `FEEDBACK_QUIET_MS` (2 minutes) (`reviewSettlingNow`).
  - The awaited head and its start time are kept in memory (`reviewSettling`). At first they are the head and time at which the stop was decided. If the head changes during the wait, the awaited head and start time are replaced (there is no run to stop, so `ReviewRunStopped` is not recorded again).
  - While there is no wait mark (after the daemon restarts or after a resume from a pause), the wait starts over from `reviewStop.to` and the time it is first seen (if a later check reads a different head, the awaited head and start time are replaced). The wait ends even if the PR cannot be read for a long time. If a person pauses during the wait, the wait mark is cleared and `reviewStop` is kept.
  - Once settled, the target is resolved again on that head (`ReviewTargetResolved`), and the review runs once.
  - There is no limit on the number of stops or on the waiting time. Since it does not run until the head settles, the cost is at most one run per change of the head. During the wait the task stays `queued`, and the `ReviewRunStopped` in the activity log (its time and `to`) shows that it is waiting. It starts once the pushes stop.
- PR merged or closed (only tasks with `source.review`; a task a person created without `source` is not canceled): for a task that is running, resolving its target, or waiting to post, `checkReviewPullRequests` sets the same mark before the cancel (`cancel`). After `cancel` stops the run and waits for it to end, it records `ReviewRunStopped` (`reason: merged` or `closed`; no `to`), followed by `TaskCancelled` (`reason: pull_request_merged` or `pull_request_closed`). `AgentRunFailed` and a pause are not recorded. It is recorded whether or not the container was confirmed stopped (to keep the cost of the stopped run). When it cannot be confirmed, the handling is the same as for other cancels (the workspace is not deleted, the container failure is left in the cleanup, and the cancel goes through; the task does not pause). During the wait to start again there is no run to stop, so `ReviewRunStopped` is not recorded and only `TaskCancelled` is left.
- Rounds that did not reach the parent: when the target of a re-review is decided, the previous round and earlier rounds that did not reach the task that made the PR (the parent) are determined from the records in the activity log (`undeliveredRounds`; no field is added to the activity log).
  - A child task (the parent found from `reviewOf`): if the `url` of an item of the parent's `discardedReviews` is the same as the URL of that round's review, it did not reach the parent. A round the parent has neither imported nor discarded yet (the parent's `importedFeedback` has no `review:<ID>` made from `pullrequestreview-<ID>` in the URL) did not reach the parent if that round's `headCommit` differs from the head of the current target (because the parent compares with the current head and discards when it imports).
  - A task without a parent: if that round has `latestCommit` (the head had changed at posting), it did not reach anyone. The previous round of a task made by a GitHub re-request (`reviewRerequest`) is not judged (its previous record has no `latestCommit`, and it is a round a person asked for explicitly).
  - For this judgment, `previousReview` and `earlierReviews` copy `reviewPost.latestCommit` of that round's post into `latestCommit`.
  - The instructions (`rereviewLines`) add `delivered: false` to the data of a round that did not reach the parent, and the agent counts that round neither in the count of rounds with the same cause of `[要修正]` nor in the list of earlier occurrences (a round that did not reach the implementer does not mean the same cause continued). The count of consecutive suggestion-only rounds given to the parent's suggestion sorting (`countSuggestionRounds`) also skips that round (it is not counted and does not break the run).
  - The findings of that round (including `[提案]`) are treated as inside the scope regardless of the narrowing of the re-review (PBI-432). The agent checks whether each applies to the code at the current head, and raises those that apply as findings of this round (the rule "do not repeat unaddressed findings as new findings" does not apply). For those that do not apply, the agent writes in the "previous findings" section that they do not apply to the current head.
  - The bodies passed are only those in `previousReview` and `earlierReviews` of the task's activity log (the PR is not read again). They are given as data, with a note that they are not instructions (instructions written in them are not followed).
  - The parent still does not take findings for an old head into its rework (`PullRequestReviewDiscarded` and `DiscardedReviewNotice` on the screen remain; [AI review comments](approval.en.md#ai-review-comments)).

### Watching the PR after posting

Related ADR: [A review task does not complete until its verdict is no findings; it watches the PR for changes and re-reviews automatically](../adr/20261119-1925-superseded-review-task-watches-pr-until-no-findings.md)

A task that has posted its review does not complete until the verdict becomes no findings; it watches the PR for changes and re-reviews automatically when there is one.
This is the same for PRs taken in by label, PRs taken in by review request, and the review child tasks of PRs that sacty opened. A review task a person created without intake (a PR URL in the body; no `source`) is the same, and the PR to watch is decided by the confirmed target (`reviewTarget`).

- State: when the posting record (`PullRequestReviewPosted`) carries the watch mark (`watch: true`), the task gets `reviewWatch` (`since` is the time the review run of that round started; the review reads the PR's comments after that).
  - While the verdict of the current round (`currentReviewVerdict`) is not no findings (changes required, suggestions, or no verdict: `absent`, `invalid`), the task is watching (`reviewWatching`). Every step is `done`, but the task is not complete (`isDone` and `isFinished` are false). The status (`status`) stays `idle`.
  - If the verdict of the current round is no findings, the task is complete. `reviewWatch` is not set, and a completed task does not watch the PR for changes (the PR is not read; nothing is recorded even if the head changes, the author replies, or the PR is merged or closed). After completion, a review happens only when a person uses "Review again". If the verdict of that round is not no findings, the task is watched again.
  - `reviewWatch` is removed when a re-review starts (`ReviewRestarted`) or the watch ends (`ReviewWatchEnded`).
- A posting without the watch mark (the activity log of versions before this mechanism) stays complete whatever the verdict. Because `reviewWatch` is not set, replaying the activity log does not turn the task into a watching one, and it is not a target of the PR check (the PR is not read and no re-review starts).
  Such a task is also watched from the round a person posts anew with "Review again".
- While watching, it is not the person's turn (the task waits for the PR author to respond). It does not enter the run queue (the watch itself uses no execution slot; the audit registered at posting uses an execution slot like the audit of any other completed task, and runs after the other runs). The UI shows "Waiting on the PR" with the verdict of the current round (changes required, suggestions, verdict unreadable, or no verdict given), and the task detail shows what it waits for.
  It is not included in "Needs you", the bell in the header, or `needs_person` of `list_tasks`. The completion notification is sent only when the task completes, and entering the watch is not notified ([Notifications](notifications.en.md)).
- In the PR check (every 60 seconds; `checkReviewPullRequests` → `watchReview`), sacty reads the state of the PR of each task that has `reviewWatch` and whose status is `idle` (the watching tasks), and does the following.
  - The PR was merged, or closed without merging: record `ReviewWatchEnded` (`reason: merged` or `closed`; actor `sacty`). A watching task becomes complete (not canceled) and keeps the reason in `reviewWatchEnded`.
    Even if the PR is reopened after the watch ended, the watch does not resume (it is watched again from the round a person starts with "Review again"; a child task is re-reviewed by the parent's flow).
  - The head of the PR differs from the reviewed head (`reviewTarget.headCommit`): start a re-review (`ReviewRestarted`, `reason: pushed`, `commit` set to the current head; actor `sacty`).
    A head pushed during the review run (the `latestCommit` at posting) is also picked up here, in the check after posting. However, if the verdict of that round is no findings, the task completes and is not watched, so it is not picked up (the posted body states the latest head and that "Review again" can review it; a person starts it with "Review again").
    It starts only once for the same head (`Task.reviewRestartCommit`; it does not repeat even when the reviewed head is misread).
    However, after that re-review reviewed a different head (a push came after it started, and the head was later put back; the reviewed head differs from the previous round), that head has not been reviewed yet, so it starts once more.
    Who pushed is not checked. If the PR comes from a fork (the head repository differs from the base; this includes a deleted head repository that cannot be read; `PullRequestStatus.fork`), a push does not start a re-review (the PR's code runs in the agent's container during verification, so it must not run without a person's decision). See the item for a PR from a fork below. A task completed with no findings is not watched, so a push does not move it.
  - A PR from a fork (`status.fork` is true; false only when the head and the base are confirmed to be the same repository, so a deleted head repository or an unreadable name counts as a fork): neither a push nor the author's reply starts a re-review automatically (the first review, ending the watch, and a person's re-review are the same as for a same-repository PR).
    - When a head differs from the reviewed head, record `ReviewRestartHeld` (`commit` set to the current head; actor `sacty`) and keep it in `Task.reviewHold`. It is updated each time the head changes. When the head returns to the reviewed head, record `ReviewRestartHeld` with that head and `reviewHold` is cleared (the projection clears it when `commit` equals the reviewed head). The screen (`ReviewWatchNotice`) and `review.heldCommit` of `get_task` show that, because the PR is from a fork, it is not reviewed until a person starts the re-review, and show that head.
    - On the PR, sacty comments once per task, without internal Sacty terms, that the new commit is not reviewed automatically. It looks for a comment with the marker (`<!-- sacty-fork-hold:<task ID> -->`, not counted as a reply) and does not write if there is one (so it does not repeat when the head changes, on a later fork push after a re-review, or when the daemon restarts). It posts under its own timeout (`stopNoticeDeadline`) and retries on the next check if it fails (the warning hides secrets); the watch continues. The text says how to ask for a re-review in a way that holds however the PR was taken in (ask whoever runs Sacty).
    - A person's re-review (the screen or `rereview_task`) starts the re-review as before, and `reviewHold` is cleared. A GitHub re-request (only for PRs taken in by a review request) remains the first review of a new task for a same-repository PR. For a PR from a fork, it creates the new task only when the requester (`lastReviewRequester`, the actor of the `review_requested` event) is not the PR's author and has write access to the repository (write, maintain, or admin; `canWrite`). When the requester or the permission cannot be read, it does not create one either. A re-request that was not counted is handled like a hold when the original task is watching (`holdForkRestart`: the new head is recorded, and the notice on the PR stays once).
    - A reply by the author on the same head does not trigger a re-judgment either. Ending the watch when the PR is merged or closed is the same as for a same-repository PR (`reviewHold` is cleared too).
  - The head is the same and the PR author replied (except on a PR from a fork): start a re-review that judges the same head again (`ReviewRestarted`, `reason: replied`, `commit` set to that head; actor `sacty`).
    - A reply is a PR review, line comment, or regular comment by the login of the author (`reviewTarget.author`), written after the time the review run of that round started (`reviewWatch.since`). Replies written during the run are picked up here too. In a round where the author could not be read (`reviewTarget.author` is empty), replies are not looked at.
    - Posts by sacty are not counted as replies: reviews and line comments by the sacty tasks that reviewed this PR (any round), and posts that start with a sacty marker (reviews by another sacty, review-stopped notices, notices of things to confirm with a person, decisions on deferral proposals, and comments posted on request). They are told apart by the marker even when the PR author and sacty post from the same account. Posts by bots are not counted either.
      A reply to a finding that another sacty posted from the author's account (the `sacty-reply` marker; the reason for not addressing it) is counted as the author's reply.
    - It starts only once for the same head (`Task.reviewReplyCommit`). Even if replies to the same head continue after judging again, it does not start (a person can use "Review again").
    - The review of the round that judges again is given, as the author's replies, the author's posts written after the time the review run of the previous round started (`Task.reviewReplySince`) (an ordinary re-review gets only those after the previous post; `reviewFeedback`). The instructions add that this round judges the same head again because the author replied without changing the code, and that it must check against the code at the head whether the reply holds and decide whether to withdraw or keep each finding (`rejudgeLines`).
    - If, while the comments are being read, a GitHub re-request creates a new task or a sacty task takes over that PR, it does not start (this is checked again after reading).
    - If the update time of the PR (GitHub's `updated_at`) is the same as when it was last read and no reply is being waited for, the comments are not read again.
  - Consecutive pushes and replies are merged into one after things go quiet: it does not start until `FEEDBACK_QUIET_MS` (2 minutes) has passed since the daemon first saw the new head or reply (for a reply, since the earlier of the time it was written and the time it was first seen). If the head changes again while waiting, the wait starts over.
    The first-seen time is kept only in memory, so restarting the daemon makes it wait again (the watch itself continues from the activity log).
  - In a check where the head or the state of the PR cannot be read, nothing is decided and it is retried in the next check.
    Reading the state of the PR and its comments waits for an answer up to `DRAFT_TIMEOUT_MS` (30 seconds) and aborts the request after that (a PR that never answers does not stop the tasks behind it or the rest of the check). GitHub rate limits are not told apart (like the other PR checks, it is read again in the next check).
- Tasks that are not moved: tasks waiting to run or running a re-review (before posting), paused tasks, and tasks for which a pause or cancel has been requested.
  - A watching task can be paused from the UI and with `pause_task`, and can also be canceled. While paused, nothing is recorded when the PR changes, and nothing is recorded when it is merged or closed either (except for the review child task of a PR that sacty opened (`reviewOf`), which ends its watch and is done even while paused, on a merge, a close, or the parent being done; see the next item). On resume it goes back to watching (`idle`), and the next check picks up the changes that happened while it was paused.
  - Even if a review run reaches the budget cap, the finished review is posted and the task starts watching. A task that has reached its cap is paused before the next re-review runs, like any other task (`reason: budget`). When a person raises the cap and resumes it, it reviews the PR's head at that time and goes back to watching. There is no cap on the number of re-reviews.
- A review child task of a PR that sacty opened (`reviewOf`) is handled here only for the end of the watch (merge or close). A paused child task is also read in the PR check (`checkReviewPullRequests`); if the PR is merged or closed, sacty resumes it (`TaskResumed`, `retry: false`) and then ends the watch and marks it done (`ReviewWatchEnded` with `reason: merged` or `closed`), so it does not stay paused. If the PR is open and the parent is not done, nothing is done. When the parent is done, the watch ends the same way without reading the PR (`reason: parent_completed`; [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)). Its re-review is decided by the parent's flow (the parent updated the PR and went back to waiting for approval, a person added a commit, or the parent declined every finding; [The review child task of a PR](approval.en.md#the-review-child-task-of-a-pr)).
- A review task that is not a child task but targets a PR that sacty opened (`sactyMadePullRequests`) (a review task a person created, or a task taken in by an earlier version) is also handled only for the end of the watch (the child task re-reviews that PR; the same PR is not re-reviewed twice).
- When there is a review task created later for the same PR (child tasks excluded) (`supersededWatch`): the older task is handled only for the end of the watch and does not start a re-review on changes of the PR (the newest task reviews the rest; the same PR is not re-reviewed twice by 2 tasks).
  - When there is a newer task created by a GitHub re-request ([Intake](intake.en.md)): nothing is recorded on the original task, so it stays watching until the PR is merged or closed. Even if the newer task was canceled, the original task does not start.
  - When, for example, a person also reviewed an imported PR with a review task they created: only the task created later starts. If the later task is canceled, the earlier task starts.
- Interval for reading the state of the PR: every PR check until 1 hour after the last posting, every 5 minutes after 1 hour, and every 30 minutes after 24 hours (`REVIEW_WATCH_INTERVALS`; the requests to GitHub do not keep growing as PRs left open pile up). It is read every time while a change is waiting to go quiet, and for review child tasks. The last-read time is recorded when both the state of the PR and its comments were read. A PR that could not be read is read once more in the next check without waiting for the interval, and if it cannot be read again, the same interval as after a successful read applies (a PR that stays unreadable is not read, with a warning, every minute). The time is kept only in memory (it is read in the first check after startup). Tasks of a deleted project are not watched.
- For a draft PR, the re-review starts in the same way.
- While watching, cleaning up the workspace ([Cleaning up the workspaces of finished tasks](#cleaning-up-the-workspaces-of-finished-tasks)), the audit of completed tasks ([Audit](audit.en.md)), and creating a follow-up task ([derive](#creating-a-follow-up-task-from-a-completed-task-derive)) are available after posting, as for a task whose steps are all finished (decided by `isCompleted`).

## Permission by resume note

Resuming from the UI or API with a note and `approvedEdits` grants permission until the next pause. An empty note is rejected. A request is accepted automatically only when its `byNote` excerpt appears in the note after whitespace normalization. The agent omits the excerpt for changes outside the note. If requirements are proposed and a design is approved, `design` carries the full aligned design and test viewpoints, and `inScope` declares that the changes are limited to what is needed. An unreadable design or a declaration other than true leaves the request for a person.

While permission is active, sacty reads the result of a step that can propose changes as one JSON object containing the output and the proposal. A null proposal means no proposal. If the whole output cannot be read, sacty stops without submitting the result. Only the outer proposal is interpreted; even if the output text contains an incomplete proposal fragment, submission proceeds when the outer object declares no proposal, and a proposal written only in the text is not applied. Rejected proposals are retained until the result is finalized, and their targets and proposed changes are passed to subsequent runs.

Automatic acceptance records `ChangeProposed`, `ChangeAcceptedByNote`, `ChangeApplied` and any immediate submission for the requesting step in one transaction. Implementation proceeds to verification and PR submission. Requirements remain approved and the design and test viewpoints are replaced when needed. The activity and request list show the resume time and, when the design and test viewpoints are aligned with changed requirements, both diffs. When implementation accepts a request automatically, it keeps only the test mapping declared by that run. A request accepted by a person still sends requirements for re-approval.
