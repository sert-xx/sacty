# Tasks and steps

A task proceeds as a sequence of steps (Investigation, Requirements, Design, Implementation, and so on). The Orchestrator chooses which combination of steps (plan) to use when the task starts (if a person specified a plan when creating the task, that plan is used). Before that, the information gatherer collects and narrows down the information related to the task and gives its summary to the Orchestrator, every step, and the Goal Guardian ("Information gathering" below). Agents run the steps, and people decide only at approval steps (approval gates).

The Goal Guardian judges change requests, the final review, where to send PR comments back to, and Integration review.

Approval and Request changes are in [Approval and request changes](approval.en.md); Task split and Integration review are in [Task split and integration review](split-and-integrate.en.md).

## How tasks are created

`start` in `TaskCreated` records where the task came from.

| `start` | How it was created |
| --- | --- |
| `sacty` | Created in the web UI (the older `ticket` is also read as `sacty`) |
| `github_issue`, `github_pull_request` | Intake of a GitHub Issue or PR ([Ticket intake](intake.en.md)) |
| `jira` | Intake of a JIRA ticket |
| `deployment` | A task to fix a failure found by the after-merge watch (`fix` holds the original task, the kind, the marker, and the level. [After-merge watch](deployment-watch.en.md)) |
| `split` | A child task of Task split (`parent` holds the parent's ID and the child tasks that must finish first, `dependsOn`) |
| `schedule` | Created by a scheduled task (`schedule` holds the scheduled task's ID and the scheduled time. [Scheduled tasks](scheduled-tasks.en.md)) |
| `security` | A fix task created from a category of an approved security check report (`securityFix` holds the original task and the category. "Security check and security fix" below) |

- A PR-review-only task has `source.review` (`requested` or `label`; `sacty` if it is a PR that sacty created and gave the review label).
- When creating a task in the web UI, if no repository is specified (`repo: null`), or the repository is omitted and the project's targets are not exactly one repository, the task becomes a task without a repository (`noRepo`). It cannot be created in a project with no targets (`task.repositoryMissing`).
- The "Create task" button in the web UI reads only the list's project (the ID in the URL) before it appears (it does not appear for a project that does not exist). The repository suggestions (the daemon's `GET /api/projects/:id/repositories`; org targets are read with `gh`) are read when the create dialog opens, through the web route `GET /projects/:id/repositories` (read again on every open; a late result from an earlier open is dropped). Rendering the task list and its automatic refresh do not read them. The dialog shows that the suggestions are loading, could not be read, or are empty, and in every state the repository can be typed and the task created. For an org that could not be read, it shows the reason. Projects without targets do not read them.
- The initial budget cap is `budget.default_per_task_usd` (default 1 US dollar).
- The status values are in the "Projection" table of [Activity log](event-log.en.md). There is no "completed" status; a task is complete when every step is `done` or `skip` (`isCompleted`).

### Task templates

If the body of `POST /api/tasks` has `template`, the task is created from a template (`CreateTemplateTaskInput`). The templates are `sacty-setup` (Sacty setup) and `security-check` (Security check).

- Only `template`, `projectId`, and `repo` are accepted. Passing `title`, `body`, or any other item gives 400 (sacty decides the title and description). An unknown template, an empty `repo`, or `repo: null` also gives 400.
- The target repository is required. If omitted and the project's targets are exactly one repository, that one is used. Otherwise the task is not created (`task.templateRepositoryRequired`, 409). A repository outside the targets is not accepted, as with ordinary tasks (`task.repositoryUnknown`).
- `template` is recorded in `TaskCreated` (`start` is `sacty`, and `repo` is normalized to the registered name, as with ordinary tasks). It remains in the projection's `Task.template`.
- The title of `sacty-setup` is `Sacty セットアップ（<owner>/<name>）`, and the description (goal) is the text decided by `templateTask`. After creation, as with an ordinary task, the Orchestrator chooses the plan (the template does not decide the steps).
- The title of `security-check` is `セキュリティチェック（<owner>/<name>）`, and the description states the categories to check and that a fix task can be created for each category of the approved report. The `plan` of `TaskCreated` is `security-check` (as with a plan specified at creation, the Orchestrator does not choose the plan again). How to check and the answer format are given in the step's prompt ("Security check and security fix" below).
- The goal of `sacty-setup` is to check the agent configuration needed to handle the target repository with sacty, and to open a PR that fills in what is missing. The text does not assume any particular language or tool. It checks and fills in the following four items.
  1. Instructions for agents (AGENTS.md, CLAUDE.md, and so on; not maintained in two places)
  2. How to run tests (the command and prerequisites; whether they match the current configuration). If the repository has no tests yet, the agent writes that there are none and how to check changes, and does not add a new language or test framework (that is a separate task)
  3. Services needed for tests (how to start them and where to connect; if none are needed, say so)
  4. For repositories with CI/CD (even if they do not deploy), the after-merge watch skill `deployment-observer`. If there is no CI/CD, it is not created (the after-merge watch step is skipped). The original goes in `.agents/skills/deployment-observer/SKILL.md`, and `.claude/skills/deployment-observer` is a relative symbolic link to `../../.agents/skills/deployment-observer`. It has the agent write the front matter (`name`, `description`) and a reference on how to check CI/CD (`references/ci.md`: which workflows and checks verify what, failures that can be ignored, and how to read results and logs). If the repository deploys, the agent writes how to tell that a deployment finished, how to check it, how to connect, and what counts as an error; if it does not deploy, that the deployment check is skipped (`skipped` with a reason). It also writes the promises not to change anything, not to reveal secrets, not to wait long, and to answer `unknown` when it cannot judge, and the shape of the JSON answer under the heading `sacty-deployment` (the results of the CI/CD check and the deployment check). The location, link target, reference, and heading are built from the after-merge watch's `DEPLOYMENT_SKILL_PATHS`, `CI_REFERENCE`, and `DEPLOYMENT_HEADING` ([After-merge watch](deployment-watch.en.md)).
- The goal also says that if everything is in place and no change is needed, the task ends with Investigation only, without a PR, and leaves the check result for each item (if the Orchestrator chooses `investigate`, the task completes when the investigation result is approved in the web UI). If it turns out after the steps have run that no change is needed, the agent is asked to leave the files unchanged and write the check results and reasons in the implementation notes (no PR is opened; a person checks it and the task completes without changes. [Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).

## Steps

| Key | Step | What it does |
| --- | --- | --- |
| `investigate` | Investigation | Examines the code and reports |
| `review` | Review | Reviews an existing PR and posts to the PR |
| `requirements` | Requirements | Writes the requirements |
| `design` | Design | Writes the design and test viewpoints |
| `split` | Task split | Creates child tasks and waits for them to finish |
| `integrate` | Integration review | Checks whether the child tasks' results meet the parent's requirements |
| `reproduce` | Reproduce | Writes a test that reproduces the bug (fails) |
| `implement` | Implementation | Implements. After it passes verification, sacty opens the implementation PR and waits for a person's approval (merging the PR) |
| `deployment` | After-merge watch | After the implementation PR is merged, waits for CI/CD, checks as the skill says, and registers a fix task on failure (no human approval. [After-merge watch](deployment-watch.en.md)) |
| `document` | Document | Creates or edits a Markdown draft and waits for approval in the web UI |
| `operation` | Operation | Performs the requested external change once and submits evidence for result approval |

The steps fall into the following categories.

- Steps with an approval gate (`GATED_STEPS`): `investigate`, `requirements`, `design`, `integrate`, `implement`, `document`, `operation`. However, Investigation at the start of a plan that implements (preliminary investigation) moves on to the next step without approval (`StepCompleted`). Only Investigation in a task whose purpose is investigation (the last step is `investigate`) is approved. Implementation does not wait for approval as soon as the agent's run ends; it waits for approval only after it passes verification ("Verifying the implementation" below) and the implementation PR is opened.
- Steps that can be redone through Request changes (`REWORK_STEPS`): `investigate`, `reproduce`, `requirements`, `design`, `implement`, `document`.
- Steps that need a repository (`REPO_STEPS`): `implement`, `reproduce`, `review`.
- Steps that can use docker compose services (`SERVICE_STEPS`): `investigate` (only for bug investigation), `reproduce`, `implement`.
- Steps that can be exported (`EXPORT_STEPS`): `investigate` (only when it is the last step), `requirements`, `design`, `document`.
- Steps that are not run (not in `EXECUTABLE_STEPS`): `deployment`. After the previous step is approved, the task becomes idle and sacty advances it in the PR check. If the target repository has no skill, the step is skipped when the steps are chosen (`skip`. [After-merge watch](deployment-watch.en.md)). When moving to the next step, `skip` steps are passed over.
- Steps that the step review can skip (`SKIPPABLE_STEPS`): `requirements`, `design`, `reproduce`. Only when the plan has an implementation ("Step review" below).

Code: `packages/core/src/events.ts` (`StepKey`, `GATED_STEPS`, `REWORK_STEPS`, `EXPORT_STEPS`, `exportSteps`), `packages/core/src/projection.ts` (`investigationIsGoal`), `apps/daemon/src/service.ts` (`REPO_STEPS`, `submitEvents`), `apps/daemon/src/prompts.ts` (`SERVICE_STEPS`)

### Length of deliverables that people read

- The instructions of the steps whose deliverables people read (requirements, designs, documents, and the investigation result of a task whose goal is investigation) state a rule that keeps the first draft minimal (`minimalDraftLines`).
  The preliminary investigation is not read by people, so it does not get this rule.
  - The agent assumes that the reader has the background (tacit knowledge), and writes only what the reader needs to decide and work. When in doubt, it leaves the item out.
  - The agent does not write what the reader already knows (restating the request, background, general knowledge, explanations of terms), what the request does not ask for, alternatives it did not take, repeats, or a closing summary.
    Each kind of deliverable adds what not to write (requirements and designs below; for documents, mechanisms and history unrelated to the reader's goal; for investigation results, the steps taken and code explanations that do not support the conclusion).
  - Each item is one or two lines, and a reason is added in one line only when needed.
  - When a person sends the deliverable back asking for more detail, the agent adds detail only where asked and keeps the rest short. Text added at a person's request is not removed in later revisions.
- Requirements and designs are also written as follows (`readerLoadLines`).
  - The agent does not write explanations of existing code or mechanisms, behavior that existing mechanisms already guarantee and this change does not alter, unwanted behavior, boundaries, or non-functional concerns that this change cannot newly cause, or "out of scope" sections for viewpoints that do not apply.
  - The agent puts two sections at the start of the deliverable (right after the summary, if it writes one) and writes the details after them.
    - "確認したいこと" (questions): what a person must decide before it can be settled. Split into must and should, each in order of importance; each states the question, a recommended answer, and its reason. "なし" if there are none.
      - must: if the answer later turns out different, the work done until then is wasted. No limit on the number.
      - should: if the answer later turns out different, extra work is needed. Up to 5 (`SHOULD_QUESTIONS_MAX`).
    - "既定で決めたこと" (decided by default): among what the request does not say but the agent decided from the existing code, rules, and conventions, only what a person may disagree with. Up to 5 (`DECISIONS_MAX`). Simply following the existing way is not listed. When the should questions exceed the limit, the less important ones are decided with the recommended answer and moved here.
  - The target length of the whole deliverable is 20 lines for a small change and about 60 lines even for a large change (`DRAFT_LINES`; JSON blocks with a fixed format are not counted).
- The design has only the sections, among structure, data, flow, behavior on errors, and impact, that this change has something to say about. The test viewpoints cover all acceptance criteria and include the unwanted behavior and boundary values that this change can newly cause.
  A viewpoint for a change only to documents, comments or wording has what should be written as its expected result, and the implementation is checked in the diff (it is not a viewpoint that checks that a file exists or can be read; the requirements and design files sacty places are not viewpoints).
  The number of viewpoints is only what is needed to check the acceptance criteria, and each viewpoint is written in one sentence.
- sacty does not parse the two sections at the start (they stay in the deliverable's body and appear on the approval screen and in the PR).

Related ADRs: [Put what a person decides at the top of requirements and designs, keep their length in proportion to the change, and add an over-writing viewpoint to self-review](../adr/20261024-1330-superseded-reader-load-of-requirements-and-design.md), [Keep the first draft of deliverables that people read minimal, and add detail when a person sends it back](../adr/20261025-0222-minimal-first-drafts.md)

### Self-review before submitting

- The instructions of the Requirements, Design, and Implementation steps (`SELF_REVIEW_STEPS`; Implementation includes bug fixes and tasks without tests) tell the agent to self-review with the `self-review` flow of the default skill `review-dispatch` before submitting, and to repeat fixing and re-reviewing until no `must` findings are left (it passes) (`selfReviewLines`). The target kind is `design-doc` for Requirements and Design (the draft is written to a temporary file outside the workspace and reviewed) and `code` for Implementation. The round limit follows the skill (up to 5 including the first); if `must` findings are still left at the limit, the agent reports them and submits. For `design-doc`, a finding that adds text is fixed only when it is a `must`, and its `should` is not fixed. A `should` from viewpoint D-10, which points out over-writing, is also fixed (a rule of the instructions and the skill; see [Context](context.en.md)). Redoing after requested changes or PR comments runs with the same instructions.
- The agent reports the result as JSON under the heading `sacty-self-review` (`rounds`, `passed`, `remaining`, `notReviewed`, `summary`). sacty reads only the last one (`extractBlocks`) and removes every report from the deliverable. A report is found as an object whose first key is the heading, even when it is not valid JSON (`headingSpans`). For an unreadable report outside a code fence, only up to the end of the line where it starts is removed, and the text after it is kept. When the last report cannot be read, sacty does not fall back to an earlier one. The agent does not write the "self-review" section the skill puts at the end of the description.
- `rounds` is 1 to 5, and `passed: true` is allowed only when `remaining` is empty. A report that does not match is treated as a wrong shape (`SelfReview`).
- The report is recorded in `selfReview` of `AgentRunCompleted`. When there is no report, or it cannot be read or its shape is wrong, it is `null` (no record). The step does not stop. The projection keeps the report of the latest submission per step in `selfReviews` (absent for steps that do not self-review and for earlier records). When the text is replaced outside a step run (applying a change proposal, or a merge after a person edited the document in the PR), the earlier report did not see the new text, so it becomes no record.
- The screen shows passed (rounds), not passed (rounds and the number of findings left), or no record on the deliverable cards (not on approved deliverables), the Implementation card, and the approval screen. Not passed and no record use the warning color, and when it did not pass, the findings left and the viewpoints not reviewed are shown open. The "finished" line of the Activity also shows it.

Code: `apps/daemon/src/prompts.ts` (`selfReviewLines`, `SELF_REVIEW_HEADING`, `extractBlocks`), `packages/core/src/events.ts` (`SelfReview`, `SELF_REVIEW_STEPS`), `packages/core/src/projection.ts`, `apps/web/src/components/self-review.tsx` (`SelfReviewNote`)

## Plans

| `plan` | Steps |
| --- | --- |
| `standard` | `investigate` → `requirements` → `design` → `implement` → `deployment` |
| `skip-design` | `investigate` → `requirements` → `implement` → `deployment` |
| `direct` | `investigate` → `implement` → `deployment` (no requirements or design) |
| `investigate` | `investigate` (investigation only) |
| `design-only` | `requirements` → `design` (design only) |
| `review` | `review` (review only) |
| `split` | `investigate` → `requirements` → `design` → `split` → `integrate` |
| `bugfix` | `investigate` → `reproduce` → `implement` → `deployment` |
| `document` | `document` |
| `operation` | `operation` |
| `security-check` | `investigate` (security check) |
| `security-fix` | `investigate` → `implement` → `deployment` (security fix; skips Requirements and Design) |

The plans that can be chosen are restricted as follows (`allowedPlans`).

- `review`: only when there is a repository and the task points to a PR
- `split`: child tasks cannot choose it (splitting is one level only)
- The others (including `design-only`, `document`, and `operation`) can be chosen with or without a repository (`selectablePlans`)

### Plan specified at creation

A person can specify the plan when creating a task (`plan` in `CreateTaskInput`; when omitted, the Orchestrator chooses). The plan is recorded in `plan` of `TaskCreated` and becomes the task's `requestedPlan`.

- At creation, sacty checks that the plan can be chosen for the shape of the task (`selectablePlans`). `review` is accepted only when a target repository is chosen and the title or description has a link to a PR of that repository; otherwise it is rejected (`task.reviewPlanNeedsPullRequest`). A task without a repository can still specify a plan that needs one (`REPO_PLANS`): the Orchestrator chooses the repository, and after it is prepared, the steps are decided with the same plan.
- When choosing steps, `allowedPlans` returns only the specified plan. The prompt tells the Orchestrator not to choose again and to write that plan in `plan`, and to decide the base branch, test command, images, services, export destinations, and so on as usual (`pinnedPlanLines`). An answer whose `plan` differs from the specified one is treated as unreadable. If the specified plan can no longer be chosen for the shape of the task (which does not normally happen), it is ignored and the Orchestrator chooses as usual.
- A specified plan does not skip steps in the step review (see "Step review" below).
- The task details show the specified plan in the "Steps" section.

Code: `packages/core/src/events.ts` (`CreateTaskInput`, `TaskCreated`), `apps/daemon/src/service.ts` (`createTask`), `apps/daemon/src/prompts.ts` (`allowedPlans`, `pinnedPlanLines`, `pullRequestInText`), `apps/web/src/components/new-task-dialog.tsx`

## Non-development work and plan selection

The Orchestrator does not recommend `standard` unconditionally. It is told to choose from the deliverable (what the task ultimately asks for), not from keywords or whether there is a target repository, and to choose by scope and clarity only among the plans that implement (`PLAN_SELECTION_LINES`). Having a target repository is not a reason to choose a plan that implements (for example, writing a procedure document by reading the repository is `document`, and adding steps to the README is `direct` or `skip-design`). When in doubt, it decides by whether the request says the result should be reviewed in a PR and kept in the repository (a file name, a location, a PR instruction, and so on).

| Request | Plan |
| --- | --- |
| A question or cause analysis | `investigate` |
| A review of an existing PR | `review` |
| Overall design | `design-only` |
| Writing a draft read outside the repository (a procedure document, user guide, report, and so on) | `document` |
| Creating or editing external documents directly and revising them through Request changes (including multiple pages, or pages found by a condition and fixed together) | `document` |
| A local change whose request is clear as acceptance criteria and that uses existing mechanisms | `direct` (no requirements or design) |
| A file change in a repository, including documentation, that is local | `direct` or `skip-design` |
| A file change in a repository, including documentation, that needs broad design decisions | `standard` |
| A file change in a repository, including documentation, split into several PRs | `split` |
| Fixing an existing PR itself (addressing review comments on the PR, and so on; "Taking over an existing PR" below) | `direct` (`continuePullRequest`) |
| A reproducible bug | `bugfix` |
| A bug that needs design decisions | `standard` |
| Checking for vulnerabilities and supply chain risks | `security-check` |
| Fixing a specific security problem (a CVE, a GHSA, an alert, a finding of a check), whatever its size | `security-fix` |

The Orchestrator does not add steps by guessing at mechanisms the request does not mention (new roles, admin screens, and so on).

- `document` produces a Markdown draft without enforcing the Requirements or Design format. A person can request changes and approve it in the web UI. Like the other steps, the agent gets the composed context, the host's and the context's external PFs, the MCP servers, and the GitHub read relay (the gateway does not narrow the PFs or MCP servers). For a task with a target repository, the code at the base commit is placed in the workspace as a disposable copy for the agent to read as evidence (the repository is not changed). The instructions tell the agent that sacty saves the output (all of it except the JSON in fixed formats) as the step's result and a person approves it (`documentDeliverableLines`). Normally the deliverable is one draft: the agent outputs the full draft and is told not to write to external services or the repository (this is not enforced); it is exported after approval. If the task description (including the source ticket) instructs creating or editing external documents directly, the agent may write them externally as instructed, and the pages it wrote (one or more) become the deliverable. For an instruction such as "find the pages containing … and fix them", the agent finds the matching pages and fixes each. The output then has, per page, a heading (title and URL) and the content after the fix (for a long page, the fixed parts and their surroundings), which a person approves. The agent is told not to create pages or comments externally other than the deliverable, and not to write a work report (that it created something, task or agent IDs, steps) either externally or in the output. When it writes externally directly, it outputs the URLs of the pages it created or edited in that run as JSON under the heading `sacty-document-pages` (`pages`) (`extractDocumentPages`; only http(s) forms, no duplicates, up to `DOCUMENT_PAGES_MAX` (200)). sacty reads this report from the output before extracting the responses to remarks and the like (it is read even when it is in the same JSON object), removes the JSON from the output, and records it in `documentPages` of `AgentRunCompleted`. The projection adds the reported pages to the pages of earlier runs and keeps them in `Task.documentPages` (pages not edited in a run remain part of the deliverable). If there are `documentPages`, the instructions give them, and the agent edits the same pages when it fixes them (it is told not to create another page with the same content). If an export destination is decided, the instructions give the destination and its location. On Request changes, the agent revises the previous draft (or, if it wrote externally directly, the deliverable pages) and outputs the whole result again. It treats a remark asking to fix an external page as a remark on the deliverable, and may add pages when a remark asks to add target pages. If there are `documentPages`, nothing is exported even when an export destination is decided (`exportDue`); the web UI shows the pages written externally instead of the export result. Export is optional and uses the existing mechanism; an export failure does not stop the task from completing. To make a decided change to one unique target only once, use `operation` (creating or editing external documents directly and revising them through Request changes is `document`).
- `operation` runs as a single step. The existing Orchestrator chooses one destination, a unique target ID or URL, the requested change and its preconditions, and how to verify it. For tasks that can choose `operation`, with or without a target repository, the prompt for choosing the steps shows the settings to write, the available destinations, and the answer format (`OPERATION_SETTINGS_LINE`, `operationDestinationLines`). sacty adds no separate preparation agent, preparation deliverable, or approval gate before execution. If the target or destination is missing, the task stops before execution starts.
- The destination kind of an operation (`via`) is `platform`, `mcp`, or `github`. `github` is a GitHub host for which the project chose a gh account, and `name` is the host. The host is listed among the Orchestrator's destination candidates. Reading uses [the GitHub read relay](gateway.en.md#relaying-github-reads), and comments on PRs and issues are written by the agent in its output and posted by sacty after the result is approved ([Requesting comments on PRs and issues](#requesting-comments-on-prs-and-issues)). It cannot change or push code. If no account is chosen for the host, the task stops before execution (`operation.connectionMissing`).
- The task details show the chosen operation settings (`name`, `via`, `target`, `change`, `verification`) as read-only. These are the execution settings the Orchestrator chose, not a new deliverable or approval gate.
- The operation gets only the chosen destination and carries out the request. Apart from the chosen destination, however, [the GitHub read relay](gateway.en.md#relaying-github-reads) is always available (read-only; writes go only to the chosen destination and to sacty's posting after approval). The prompt requires checking the target and preconditions, a single write without retrying, and checking the change by reading it back. When a successful result with evidence comes back, the task waits for a person's result approval. On failure, interruption, restart, or an unknown result, the task stops. Based on the persisted start record, sacty rejects Resume and keeps the task stopped. After execution starts, Request changes is unavailable. A person checks the external state, cancels the task, and creates a new task for the work not yet done.
- sacty does not guarantee exactly-once on the external side. The single write and the read-back check are instructions to the agent. sacty does not add recurring runs, monitoring, arbitrary integrations, or control of work across several destinations. Split a request with several kinds of deliverables into tasks with clear approval boundaries.

## Requesting comments on PRs and issues

A step's agent cannot write to GitHub ([the GitHub read relay](gateway.en.md#relaying-github-reads) is read-only). To comment on a PR or an issue, it writes exactly one of the following JSON in its output. After a person approves the step's output, sacty posts it with the project's gh account.

```json
{"sacty-github-comments": {"comments": [{"url": "https://github.com/acme/app/pull/12", "body": "Markdown body"}]}}
```

- Every step except review can request comments (for `review`, sacty posts the written review). For a task with a security plan (`security-check`, `security-fix`), nothing is posted even if requested (`isSecurityTask`; the report and the fix scope can give attackers a lead). Posting uses the request in the approved output (`approved`). When the output is approved again (the approval time changes), the request of that version is posted. Nothing is posted for a cancelled, paused, or running task. It is posted before the next step (`awaitingGitHubComments`).
- If the request cannot be read (two or more, not JSON, a wrong shape, an empty body), there are more than 10 comments (`GITHUB_COMMENTS_MAX`), or a body is longer than 60000 characters (`GITHUB_COMMENT_BODY_MAX`), nothing is posted and the reason is recorded.
- The target must be the URL of a PR (`/pull/<number>`) or an issue (`/issues/<number>`) in the project's targets (a repository or its organization), or in the task's source or working repository. Otherwise only that comment is not posted, and the reason is recorded.
- Right before posting each comment, it checks that no pause or cancel has been requested and that the step's approval has not changed. If it has, no new comment is posted and nothing is recorded (on resume, the already posted ones are found by their markers and it continues).
- A marker (`<!-- sacty-comment:<task>:<step>:<approval time>:<index> -->`) is put at the top of the body and a note that AI wrote it and a person approved it at the end, and it is posted with the issue comments API. Before posting, a comment with the marker is searched for and used if found (no double posting even if it stops after posting and before recording).
- The result is recorded in `GitHubCommentsPosted` (the step, the approval time, the URL or the reason per comment, and the reason if unreadable). Even if posting fails, the task does not stop.
- The JSON request is removed from the investigation result returned to the source issue (`buildInvestigationComment`).

## Taking over an existing PR

When the title or description of a task has a link to a PR of the target repository and the task asks to fix that PR itself (addressing review comments on a PR a person opened, and so on), sacty takes over the PR. It opens no new branch or PR and pushes the implementation to the PR's source branch.

Related ADR: [A task that fixes an existing PR takes over the PR and pushes to the same branch, and a documentation-only viewpoint is checked in the diff without a test](../adr/20261025-1337-continue-existing-pull-request.md)

- Whether to take it over is decided by the Orchestrator with `continuePullRequest` in its answer for choosing the steps. The prompt shows this item only for a task that has a PR link and can choose a plan that implements (`CONTINUABLE_PLANS`: `standard`, `skip-design`, `direct`, `bugfix`, `security-fix`) (`continuablePullRequest`). It is not shown for a task imported from a PR or a child task of a split. The prompt asks not to write it when the task only refers to the PR for a different change or only reviews the PR, to choose `direct` when the review comments make the fix concrete and `security-fix` when it fixes a security problem, and not to write `baseBranch`. `continuePullRequest` in an answer with a plan that does not implement is not read.
- sacty checks the PR before recording the steps (`resolveContinuedPullRequest`). It takes over only a PR that is open, whose source branch is in the target repository (not a PR from a fork), and that no other sacty task (except cancelled ones) opened (as an implementation PR or a Requirements or Design PR) or took over (`continuedPullRequestOwner`). In case another task checks the same PR at the same time, it checks again right before recording the steps (with no await after that) that no other task handles it. If it cannot be taken over, to avoid opening a new PR, sacty records no steps; it records `OrchestratorFailed` (with the cost of the decision) and `TaskPaused` (`continue.unavailable`) and stops. Resuming chooses the steps again.
- When it can be taken over, the workspace is prepared again at the latest of the PR's source branch (`RepositoryPrepared`; the base branch is that branch and the base is its head), and it is recorded in `continuedPullRequest` of `StepsChosen` (the repository, number, URL, source branch, and target branch). It becomes `Task.continuedPullRequest` in the projection. If the workspace cannot be prepared again, the task stops as when it cannot be taken over.
- The prompts of the steps (except review and the post-merge watch) get the PR being taken over and the reviews, line comments, and regular comments on it (including approvals with a body and reviews posted by sacty tasks; up to the newest 30) as JSON data (`continuedPullRequestLines`, `passedContinuedFeedback`). They tell the agent to keep the PR's purpose and existing changes, change only what the task asks, and write the reason for comments it does not address in its description. If they cannot be read, the prompt says so and the reason goes to the daemon's log (the step does not stop).
- Requirements and Design are not opened as PRs; they are approved in the web UI (`stepPullRequestsOn`). This keeps their files out of the taken-over PR.
- An implementation that passes verification is pushed to the PR's source branch (`publishContinued`).
  - It is stacked on the base (the PR's head) or the previously pushed commit, without force-pushing. If the push fails and the branch's head differs from both the base and the previously pushed commit, it pushes again (if the push went through and only the response was lost, the head is this submission's commit, so it passes without changing anything). If that also fails, sacty treats it as pushed by a person and stops (`pr.continuedBranchMoved`).
  - If a pause or cancel has been requested right before a push (after waiting for authentication, and before pushing again), it does not push (on a pause, it stays waiting to open the PR).
  - If the PR is not open after the push, it stops (`pr.continuedNotOpen`).
  - It does not change the PR's title or description, and adds no review label.
  - If the PR is open, it is recorded in `PullRequestPublished` (with no template and no planned label), and the task waits for the implementation's approval (merging the PR).
  - When there are no changes, it is the same as other tasks ([Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).
- The comments passed to the prompt of a run of the Implement step are recorded in `ContinuedFeedbackPassed` (the run and the keys of the comments passed; `Task.handedOverFeedback` in the projection) when the run finishes, in the same append as its completion (`AgentRunCompleted`). Nothing is recorded if the run could not start or failed. Importing PR comments skips the comments passed, because the implementation addressed them (`handedOverFeedback`). Comments not passed (unreadable, over the limit, or added later) are imported as for other PRs ([Importing PR comments](approval.en.md#importing-pr-comments)).
- The post-merge watch records the PR's target branch as the merge target, not the workspace's base branch (the PR's source branch) (`deploymentWatchEvents`).
- Cancelling neither closes the taken-over PR nor deletes its source branch (it is excluded from `sactyBranches`).
- The web UI shows the PR being taken over (its number and source branch) in the Steps section of the task details.

## Security check and security fix

Security checks (the deliverable is a report) and fixes (the deliverable is a PR) use the plans `security-check` and `security-fix`. They use the Investigate, Implement, and After-merge watch steps as they are, and add rules to the prompts and the verification.

Related ADR: [セキュリティチェックとセキュリティ対応を、既存の工程の組み合わせとして足し、対応の差分を修正の範囲と照らして最小限に保つ](../adr/20261026-1520-security-check-and-fix-plans.md)

- Whether a task is a security task is decided by the chosen plan (before choosing, the plan specified at creation) (`taskPlan`, `isSecurityTask`). Both are plans that need a target repository (`REPO_PLANS`); for a task without a repository, the Orchestrator chooses one from the project's targets.
- The investigation prompt (`SECURITY_TOOL_LINES`): the agent does not set up for development, but runs the check tools in the workspace (osv-scanner, gitleaks, and so on), including network access to vulnerability databases, and uses the results as evidence. What it has no tool for or could not run is written as unchecked scope, and it does not write the values of secrets it finds or how to exploit a problem.
- Keeping it off public places: the result is not commented on the source issue or ticket (`awaitingIssueComment`). Requests for comments on PRs and issues are not posted either ("Requesting comments on PRs and issues" above). The export destination is decided as for other tasks.

Code: `apps/daemon/src/security.ts`, `apps/daemon/src/prompts.ts` (`SECURITY_TOOL_LINES`, `securityCheckLines`, `securityScopeLines`, `securityFixImplementLines`, `securityFinalReviewLines`, `finalReviewVerdictIds`, `securityScopeBodyLines`), `packages/core/src/projection.ts` (`taskPlan`, `isSecurityTask`, `canRequestSecurityFix`), `apps/daemon/src/service.ts` (`awaitingIssueComment`, `awaitingGitHubComments`)

### Security check

- The prompt of the investigation (a task whose goal is the investigation) asks for a check per category (`securityCheckLines`). The categories are `dependency` (dependency vulnerabilities), `supply-chain` (supply chain: CI workflows, where dependencies come from and lockfiles, install scripts, pinning image tags), `code` (code vulnerabilities), `secret` (leaked secrets; the workspace is a copy without .git, so only the files are checked and the history is written as unchecked scope), and `config` (configuration and IaC) (`SecurityCategory`).
- Tool results are sorted out (reachable, exploitable, false positive) before they become findings. For each finding, the agent writes the category, the severity (`critical`, `high`, `medium`, `low`), the title, the identifiers, the location, the evidence, and a proposal for the smallest fix.
- After the body of the report, the agent outputs JSON under the heading `sacty-security-findings` (`findings`: `id`, `category`, `severity`, `title`, `refs`, `location`, `fix`). The JSON stays in the body, and sacty reads the last one from the approved body (`extractSecurityFindings`; findings without a category or a title are dropped, a missing severity becomes `medium`, and a missing ID becomes `SF-<number>`).
- The task completes when a person approves it in the web UI (as with other tasks whose goal is the investigation).

### Creating fix tasks from the report

- For a security check task that was approved and completed (and is not cancelled) (`canRequestSecurityFix`), the task details show the findings per category and "Create fix task" (`GET /api/tasks/:id/security-findings`). If the findings cannot be loaded, this is shown separately from having no findings, with a hint to reload.
- The top of a fix task's details shows a link to the report task and the category.
- `POST /api/tasks/:id/security-fixes` (the input is `category` of `RequestSecurityFixInput`) creates the fix task for that category. Only once per category (`security.alreadyRequested`). It is not created if the report is not approved (`security.notReport`) or the category has no findings (`security.noFindings`) (all 409).
- First, `SecurityFixRequested` (the category, the ID of the task to create, the title, the body, all the findings of that category; the actor is `person`) is recorded on the original task, then `TaskCreated` is recorded with that ID. If the daemon stops before creating it, it is created at startup (`resumeSecurityFixTasks`).
- The task created has `start: security`, `plan: security-fix`, and `securityFix` (the original task, the category, and all the findings), and the repository of the original task. The title is `セキュリティ対応：<区分>（<元のタスクの題>）`, and the description has only the findings of that category and a request to fix them with the smallest change (`securityFixTask`). The description lists only the findings that fit in `TASK_BODY_MAX` and gives just the count of the rest (no finding is cut in the middle).
- The prompts of the fix task's steps (investigation, implementation) and of the final review get all the findings in `securityFix` as JSON data without omission, and the agent is told to solve all of them (`securityFindingLines`). If a finding is left unsolved without a reason, the final review fails the viewpoint `REQ`.

### Security fix

- The prompt of the preliminary investigation (`securityScopeLines`) has the agent confirm the problem and declare the fix scope as JSON under the heading `sacty-security-scope` (`paths`, `packages`, `verification`, `reason`). Dependencies are raised to the smallest version that solves the problem, and a breaking change, if needed, is stated. The scope is not approved (the preliminary investigation is not approved). sacty reads the last declaration from the body of the preliminary investigation handed over as approved (`securityScope`, `extractSecurityScope`; a declaration with empty `paths` is unreadable).
- The implementation runs with the prompt for an implementation without Requirements or Design ("Step review" above), with the rules for the smallest change (`securityFixImplementLines`) and the scope (as JSON data) added. It tells the agent not to change anything outside the scope (it may add files for regression tests), not to mix in refactoring or reformatting, to raise dependencies with the package manager, and the limit on changed lines. The viewpoint `REQ` is "the problem is solved"; for a dependency or configuration update that cannot be tested, the agent writes in `untested` that it is checked with the check command.
- In the verification, before the final review, sacty checks the diff against the scope (`scopeViolation`). The check uses not the diff given to agents (truncated at `DIFF_LIMIT`) but the untruncated added and removed lines per file (`diffStats`; `git diff --numstat --no-renames`). A rename is split into a deletion of the source and an addition of the destination (so a file outside the scope cannot be hidden by moving it into the scope). For a file without line counts (a binary, or one whose diff is hidden by `-diff` and the like in the workspace's `.gitattributes`), the lines of the old and new contents are counted as all removed and all added (so repository attributes cannot hide the count). An added file has 0 old lines and a deleted file 0 new lines (told apart with `git diff --name-status`); if existing contents cannot be read, the stats count as unobtainable and the task stops. The contents are read one at a time (not starting many processes at once). If they cannot be obtained, the task pauses without the final review, as with the diff (`verify.diffUnavailable`).
  - Files outside the scope: files that match none of `paths` (the path itself, below it if it ends with `/`, and `*` for any characters except `/`; `pathInScope`) and are not test files (in a test directory, or with a name following the test naming conventions).
  - Changed lines: the total of added and removed lines, excluding lockfiles (`package-lock.json`, `yarn.lock`, `go.sum`, and so on; test files are counted), exceeds `SECURITY_FIX_MAX_CHANGED_LINES` (300).
  - If the scope cannot be read, only the number of lines is checked.
- The viewpoints judged in the final review are `REQ` plus `SEC-MIN` (whether the diff is minimal; no tests are mapped to it) (`finalReviewVerdictIds`). The prompt (`securityFinalReviewLines`) has the Goal Guardian check `REQ` by running the scope's `verification` command, and judge `SEC-MIN` change by change by whether each is needed. If sacty found a violation, the prompt states it, and `SEC-MIN` fails whatever the Goal Guardian judged (the reason is `review.scopeViolated`; `extractFinalReview`). Redoing and pausing on failure are the same as for other implementations (`MAX_VERIFY_ATTEMPTS`).
- To widen the scope, cancel the task and rerun it (changes cannot be requested on the preliminary investigation; `reworkTargets`). The implementation prompt asks the agent, when it cannot fix the problem without changing something outside the scope, to write the reason and the scope to widen in its description. The rerun task keeps the security plan ("Rerunning a cancelled task" below).
- In the body of the implementation PR, the purpose section is "修正の範囲（セキュリティ対応）" (the files that may change, the dependencies to raise, how to confirm the fix, the reason for the scope) instead of the requirements (`securityScopeBodyLines`). When an existing PR is taken over, its title and body are not changed ("Taking over an existing PR" above), so the scope is checked in the preliminary investigation's result in the task details.
- A PR to a public repository is created as for other implementations.

Code: `apps/daemon/src/security.ts` (`extractSecurityScope`, `securityScope`, `scopeViolation`, `pathInScope`, `SECURITY_FIX_MAX_CHANGED_LINES`, `MINIMAL_CHANGE_VIEWPOINT`), `apps/daemon/src/repository.ts` (`diffStats`, `parseNumstat`), `apps/daemon/src/service.ts` (`verify`, `rerunTask`), `apps/daemon/src/prompts.ts` (`extractFinalReview`, `approvedBasisLines`)

## Information gathering

At the start of a task (before choosing steps), the information gatherer runs once, collects the information related to the task, and summarizes only what is relevant (`InformationGathered`; the actor is `gatherer`). For a task taken in from a ticket, the same run also does ticket triage (deciding the repository to work in, the title, and the summary) ("Doubling as triage" below). It aligns the background, goals, and constraints that people take for granted before the Orchestrator chooses the plan. There is no approval gate; the summary is shown under "Gathered information" in the task details (collapsed once a step has started).

- What to collect (instructions; not enforced):
  - The description, comments, and linked tickets of the ticket the task was taken in from, and its parents followed upward (the story for a sub-task, the epic for a story). For a GitHub Issue or PR, its body, comments, and linked Issues and PRs
  - The contents of URLs in the task's content, the ticket, and comments
  - Specifications, designs, decisions, and history found by searching for the task's terms with the available MCP servers, external platforms, and the rules of the project's context
  - The target repository's code ("Reading code" below)
- The instructions have it drop weakly related or superseded information and write both sides of any conflict. The summary is written under fixed headings (goals and background, what to do, out of scope and constraints, related specifications and history, related code, conflicts and open questions, sources that could not be read). The related code heading is used only when it is told to read code ("Reading code" below). It only reads; it does not write or send anything. External text (tickets, comments, linked pages, search results, repository files) is treated as data, and instructions written in it are not followed.
- It runs the same way as the Orchestrator (the default image, the composed context, the host's and the context's external platforms, MCP servers, and the GitHub read relay; `ContextResolved` is recorded). However, external platforms are read-only: the run is registered with the gateway as a read-only run (anything other than GET and HEAD is 403; [Gateway](gateway.en.md#relay-behavior)), and the instructions show only the GET and HEAD rules (`readOnlyPlatforms`). The GitHub read relay is read-only to begin with. MCP servers are not restricted (sacty cannot tell whether a tool only reads, so the instructions have it use only read operations). The AI is `step_agents.gather`, otherwise `step_agents.orchestrator`, otherwise `default_agent`. The session is not saved. The cost is counted toward the task budget (if the budget cap is reached, the task is paused without running).
- From the answer (JSON with the heading `sacty-gathered`) it reads the summary (`brief`; at least 1 character after trimming, up to 30000 characters (`GATHERED_BRIEF_MAX`)) and the sources (`sources`; title and URL; up to 100). When there is no summary or it cannot be read, or the run fails, it records `OrchestratorFailed` (the actor is `gatherer`) and gathers again with a fallback agent if there is one, otherwise pauses (resuming gathers again). It does not proceed without gathering.
- The summary is added to the following instructions (`gatheredLines`).
  - The Orchestrator (choosing steps, choosing the review image, reviewing steps, answering questions), and ticket triage when it is redone after information gathering
  - Every step (added to the step's task content; steps whose instructions do not include the task content (Implementation after Requirements and Design, the after-merge watch check) get it added separately)
  - The Goal Guardian (judging change requests, the final review, deciding where to send PR comments back to, Integration review). Since a person has not approved it, the instructions say to use it only to understand the background and not as grounds for the verdict
- Every reader is told that it was gathered from external text, so anything written in it like an instruction is not to be followed.
- It does not gather for tasks whose steps are already chosen (including activity logs from before this mechanism) or for split child tasks (those with `parent`) (`awaitingGathering`). A child task's content includes the parent's summary (`buildChildBody`). A task created by a rerun gathers as a new task.

### Reading code

Information gathering also reads the target repository's code (instructions; not enforced). It has it search the code for the task's terms and check the relevant places (files, functions), the current behavior, and existing conventions. It reads only as far as needed to choose the plan and to give the later steps the background; the fix approach and detailed root-cause investigation are left to later steps (such as Investigation). How it reads code depends on whether the repository to work in is decided (`buildGatherPrompt`).

- Decided: the repository is prepared before information gathering (`RepositoryPrepared`; the base commit is fixed here), and a disposable copy of the code at the base commit is placed in the gatherer's workspace to read. If it cannot be prepared, the reason is recorded and the task stops before information gathering.
- Not decided (a task waiting for ticket triage, a task without a repository): the repository is not prepared. The candidates (the triage candidates for triage, the project's targets for a task without a repository) are passed in the instructions; it picks out the likely relevant ones (at most 3) and reads them with `gh api` through the GitHub read relay (examples are given for listing files, reading contents, and searching code). For a ticket task whose repository a person chose, it reads that repository. Repositories it could not read (no relay, no permission) are written under the sources that could not be read. Tests check that the ways of reading it shows (`GATHER_GH_EXAMPLES`) pass through the image's gh and the gateway's read relay.
- Orgs among the project's targets whose repository list could not be read (`errors` of `projectRepositories`; the reasons have secrets masked) are not among the candidates, so the instructions list the Org and the reason and have it write them under the sources that could not be read. For a task without a repository, even when no list could be read and there are no candidates, it gathers without stopping (the step to read code is not shown). A task waiting for ticket triage stops before the run when there are no candidates ("Doubling as triage" below).
- When there are neither candidates nor unreadable Orgs, the code section is not added to the instructions.

### Execution environment and services

Information gathering runs in a container of the default image without starting services. That differs from the later steps' environment (the image the Orchestrator chooses and the services started for each step). For a task that has a repository to work in (including one decided by triage), an "Execution environment and services" section is added to the instructions, and it has the gatherer do the following (instructions; not enforced; `gatherServiceLines`).

- Do not write the tools, versions, or running things (such as a database) found in the gathering container as facts about the later steps' environment. Read the needed language versions and tools from the repository's configuration and write them.
- Assume that sacty starts the compose services the Orchestrator chose for each step run (they are not running during gathering), and that step agents cannot use docker commands but can connect to the services.
- Sort what tests and manual checks need into the following three groups by what each one runs, not by whether the compose service has `build`, and write them under the summary heading "Services needed for tests and manual checks".
  1. Apps that run this repository's code: the step agent starts them inside its container (the start procedure, the names of needed environment variables, and the services they connect to)
  2. Dependency apps managed elsewhere, and databases, caches, mocks, and so on: candidates sacty can start (the compose file and the service names)
  3. Dependencies not in compose: the name of a matching shared compose of the project (the instructions list their names, files, and descriptions), or otherwise a dependency sacty cannot start

The Orchestrator settles the services based on this grouping ([Services](services.en.md#when-services-start)). For a task without a repository, this section is not added.

### Doubling as triage

For a task taken in from a ticket whose repository to work in is not decided yet (`awaitingTicketTriage`), information gathering doubles as ticket triage.

- Before the run, it checks the ticket's destination (a platform of the host or the project's context) and the candidate repositories (the project's targets) (`ticketTriageTarget`). If there is no destination or no candidate, it records the reason (`ticket.triageFailed`) and stops without running.
- The instructions list the candidates and have it choose one repository to work in from the gathered information and write the title (with the key first) and the summary. If a person chose the repository, it is fixed to that repository. The answer is the `sacty-gathered` JSON with `repo`, `title`, `summary`, and `reason` added.
- When the summary of the gathered information can be read, it records `InformationGathered` and then one of the following (`ticketTriaged`).
  - If the repository is a candidate and there is a summary, `TicketTriaged` (the actor is `gatherer`). The cost is in `InformationGathered`, so `TicketTriaged` carries no cost. The task's title and content become the written title and summary.
  - If it could not decide (the repository is empty or not a candidate, there is no summary, or there is no answer), it records the reason and stops (`ticket.triageFailed`). The gathered information is kept. A person can choose the repository and resume; resuming redoes only ticket triage (`triageTicket`) (it does not gather again). That instruction also includes the gathered information.
- When the summary cannot be read, triage is not recorded either (as above, it gathers again or stops).

Code: `apps/daemon/src/service.ts` (`gatherInformation`, `ticketTriageTarget`, `ticketTriaged`, `triageTicket`, `runOrchestrator`, `runNextInner`), `apps/daemon/src/prompts.ts` (`buildGatherPrompt`, `gatherServiceLines`, `extractGathered`, `gatheredLines`, `buildChildBody`), `apps/daemon/src/config.ts` (`agentFor`), `packages/core/src/events.ts` (`InformationGathered`, `GATHERED_BRIEF_MAX`), `packages/core/src/projection.ts` (`awaitingGathering`), `apps/web/src/components/task-detail.tsx`

## Orchestrator

It runs once before the steps are chosen (when the task starts). The AI is `step_agents.orchestrator` (or `default_agent` if absent); it uses the default image and reads a disposable copy of the code at the base commit. Its cost counts toward the task's budget. If the budget cap has been reached, the task is paused without running it. Like step runs, it receives the default context and the project's context (rules, skills, MCP servers, external PFs, tier definitions), is told the usable PFs together with the host's PFs, and records `ContextResolved` (PBI-146). When a session that could not be resumed is started anew, it is recorded with that run's ID as well. If the context cannot be prepared, `OrchestratorFailed` is recorded and the task is paused without running it (no cost).

The following are read from the answer (JSON under the heading `sacty-steps`) and recorded in `StepsChosen`.

| Item | Meaning and handling |
| --- | --- |

## Step review

After the steps are chosen, each time a step finishes, the Orchestrator skips the remaining steps that are not needed. It does not add or reorder steps. The final deliverable is judged by the Goal Guardian's final review and approved by a person merging the PR.

- Skippable steps (`skippableSteps`): the remaining steps (active or to do) that are in `SKIPPABLE_STEPS` (`requirements`, `design`, `reproduce`). Only when the plan has an implementation (`implement`) that is not skipped. The design before a split and the design-only plan cannot be skipped. Tasks whose plan a person specified at creation (`requestedPlan`) skip nothing (no review).
- When: when a step finishes (completion of the preliminary investigation `StepCompleted`, approval `StepApproved`, and so on; `advance`) and skippable steps remain, the task holds the finished step in `stepReview`. On the next run (`runNextInner`), the steps are reviewed before running the step (`reviewSteps`). For example, `standard` is reviewed after the preliminary investigation (requirements, design) and after the requirements are approved (design); `bugfix` after the preliminary investigation (reproduce). `direct` is not reviewed.
- Prompt (`buildStepReviewPrompt`): it passes the task, the finished step's output (up to the first 30,000 characters), the remaining steps, and the skippable steps, and gives guidelines (skip the requirements when the request itself is the acceptance criteria, the design for a local change that follows existing mechanisms, the reproduction when the cause and fix are clear), and says not to keep steps by guessing at mechanisms the request does not mention. It runs as an Orchestrator run (`runOrchestrator`), resuming the task's Orchestrator session.
- The answer (`skip` and `reason` under the heading `sacty-step-review`; `extractStepReview`) is read and `StepsSkipped` (`after`, `steps`, `reason`, and the cost) is recorded as the Orchestrator's. When `steps` is empty, nothing is skipped. An answer that names a step that cannot be skipped, has no reason, or has the wrong shape is treated as unreadable.
- When the run fails or the answer cannot be read, the task does not stop: nothing is skipped and `StepsSkipped` (empty `steps`) is recorded by sacty (the reason is `orchestrator.stepReviewFailed`). However, if the run failed without confirming that its container stopped (`run.containerNotConfirmed`), the task then pauses (`TaskPaused`) so that the original container and the next step's run do not overlap. When the budget cap is reached, the review does not run (the task pauses before the next step and reviews after resuming). If a person pauses or cancels during the review, nothing is recorded.
- Projection: skipped steps become `skip`, and if the active step is skipped, the next step to do becomes active. `stepReview` is cleared by `StepsSkipped`, by redoing from an earlier step (`reopen`), and by starting a step's run (`AgentRunStarted`). A record when no review is pending, or that skips a step that cannot be skipped, is rejected.
- Changes are not sent back to skipped steps (`reworkTargets`). The task screen does not show the deliverables of skipped requirements, design, or reproduction.
- Steps after skipping: a design whose requirements were skipped treats the task as the requirements. An implementation without requirements and design (`direct`, or both skipped) follows the task and the preliminary investigation and verifies the viewpoint `REQ` as the task's purpose (the request) (`withoutRequirements`, `directImplementLines`). The final review and the PR body also treat `REQ` as the task's purpose. The verification basis (`verificationBasis`) treats skipped steps as absent.

Code: `packages/core/src/events.ts` (`SKIPPABLE_STEPS`, `StepsSkipped`), `packages/core/src/projection.ts` (`skippableSteps`, `advance`, `reworkTargets`), `apps/daemon/src/service.ts` (`runNextInner`, `reviewSteps`), `apps/daemon/src/prompts.ts` (`buildStepReviewPrompt`, `extractStepReview`, `withoutRequirements`, `directImplementLines`, `verificationBasis`)

## Changing a step's image

- On the task detail, a person can change the image of each step (`POST /api/tasks/:id/images`, input `step` and `image` of `ChangeStepImageInput`). The step's state does not matter (a step yet to run, running, failed or paused, awaiting approval, or done). A cancelled task cannot be changed.
- The choices are the names in `images` and `default` (the default image). The screen shows each description (`description` in `images`). Every step can be changed. sacty refuses the change with the reason (409) in these cases.
  - A name not in `images` (including a name removed from config.yaml; `image.notInImages`)
  - The current name (`image.unchanged`)
  - A step the task doesn't have (`image.stepMissing`)
  - config.yaml can't be read or parsed. The names can't be checked, so sacty refuses with the settings problem as the reason (`image.configUnavailable`; `default` too)
- When the daemon's status can't be fetched or the settings can't be read, the screen says the choices can't be checked and shows neither the warning that a name is not in `images` nor the change form (`stepImageOptions`; a temporary failure is not mistaken for a removed name).
- A change appends `StepImageChanged` (`step`, `from`, `to`; the actor is `person`). `from` is the name before the change (`default` if none was set). The projection sets the step's `images` to `to` and keeps the last change of each step in `imageChanges` (`from`, `to`, time). `StepsChosen` is not rewritten.
- The changed image is used from the next run of the step (starting a step that hasn't started, a retry, or a rerun after rework). The current run is not stopped. A step run fixes its image when `AgentRunStarted` is appended (a change while the run is being prepared does not change that run). The integration review works the same way.
- The final review that runs the tests also uses the Implementation step's image at the time the final review starts ("Verifying the implementation" below). If the Implementation image is changed while the Implementation step runs, the final review after that run uses the changed image.
- Tasks whose project target specifies an image can be changed too. The person's change takes precedence for that step only (other steps keep the target's image). Changing the target's image does not change the images of a task whose steps are already chosen.
- The screen shows, for each step, the image, where it came from (the time a person changed it and the previous name, the project target, the Orchestrator, or not set) and when a change takes effect (from the next run while running; from a retry or rework for a done step) (`stepImageRows`). Running means the agent run, the implementation verification, and the reproduction check (`stepRunning`). The Activity shows who changed which step, when, and from what to what.
- For a step the Orchestrator left on the default image, where it came from shows the reason for the default image (`defaultImageReasons`) or that no reason was given (`imagesUnexplained`) until a person changes it. After a person changes it, the person's change is shown. The "Steps chosen" line in the Activity stays as recorded when the steps were chosen (the later `StepImageChanged` line shows the change).
- On the screen, "Step images" is usually not changed, so only its heading is shown, collapsed. When the choices cannot be confirmed or a name not in `images` is in use, it is shown open so it is not overlooked.

Code: `apps/daemon/src/service.ts` (`changeStepImage`, `runNextInner`, `integrate`), `apps/daemon/src/server.ts`, `packages/core/src/events.ts` (`StepImageChanged`, `ChangeStepImageInput`), `packages/core/src/projection.ts` (`stepRunning`), `apps/web/src/lib/labels.ts` (`stepImageRows`, `stepImageOptions`)

## Changing a step's agent

- In the task details, a person can change the agent of each step (`POST /api/tasks/:id/agents`; the input is `step` and `agent` of `ChangeStepAgentInput`). The state of the step does not matter. A cancelled task cannot be changed. The targets are the steps run by step agents (`stepAgentChangeable`). Integration review is done by the Goal Guardian, so it is not shown on the screen and is also rejected by the API (`agent.stepNotChangeable`).
- The choices are the names of the usable agents (the defaults in `config/agents.yaml` with `agents` of config.yaml laid over them, that have an endpoint and a price; [Configuration](configuration.en.md#usable-agents)). A name is taken exactly as the key, without trimming spaces or limiting its length. Inherited names (`constructor`, `toString`, and so on) are not agent names (`definedAgent`). sacty rejects the change with a reason (409) in these cases.
  - A name not among the usable agents (`agent.notInAgents`)
  - The same name as now (`agent.unchanged`)
  - A step not in the task (`agent.stepMissing`)
  - Integration review (`agent.stepNotChangeable`)
  - config.yaml cannot be read (`agent.configUnavailable`)
- A change adds `StepAgentChanged` (`step`, `from`, `to`; actor `person`). `from` is the name before the change (the name decided by config.yaml if no person chose one). The projection sets `agents` to `to` and keeps the last change per step in `agentChanges`.
- Step runs, the check of the after-merge watch, operations, and exports use the agent a person chose in preference to `step_agents` and `default_agent` in config.yaml (`stepAgentFor`). It is decided at the start of a run (`AgentRunStarted`), so a running run does not change. Step runs and the watch read it from the latest task after preparing. An operation reads it from the latest task after looking up its connection. If it changes while an operation or export is preparing (its connection and context), the run does not start with the old agent; the task stays queued and the next run prepares again with the new agent. If a name chosen again while preparing is not in the settings that run read (it was added to config.yaml meanwhile), the task also stays queued without pausing, and the next run decides from the latest settings. If the chosen name is no longer among the usable agents (removed from the settings, or no endpoint or price), the task does not fall back to the default and pauses with `agent.chosenMissing` (an export records it as the reason it could not export). Tier subagents are placed with the chosen agent as the parent.
- The status (`GET /api/status`) returns the agents that can be chosen (name, runtime, model, reasoning effort; no secret values or endpoint URLs) and the name per step decided by config.yaml (`stepAgents`). The screen shows, for each step, the agent, where it came from (config.yaml, or the time and previous name of a person's change), and when it is used (`stepAgentRows`). The choices are not shown when the status cannot be read or the settings cannot be read, and stub is offered only when the current agent is stub (`stepAgentOptions`). A chosen name not among the usable agents is shown with a warning.
- On the screen, "Step agents" is usually not changed, so only its heading is shown, collapsed. When the choices cannot be confirmed or a name not among the usable agents is in use, it is shown open so it is not overlooked.

Code: `apps/daemon/src/service.ts` (`changeStepAgent`, `pauseForMissingAgent`, `status`), `apps/daemon/src/config.ts` (`stepAgentFor`), `apps/daemon/src/server.ts`, `packages/core/src/events.ts` (`StepAgentChanged`, `ChangeStepAgentInput`), `apps/web/src/lib/labels.ts` (`stepAgentRows`, `stepAgentOptions`)

## Tasks from the version with the "PR作成" step

Earlier versions had a "PR作成" (open PR) step (`pr`) after Implementation. That step was removed, with no compatibility layer. Its records can't be read as a step name, so at daemon startup, before the Activity is read, tasks with those records are deleted from the Activity (`purgeLegacyPrStepTasks`).

- Deleted tasks: tasks whose plan (`steps` in `StepsChosen`) contains `pr`, and tasks with a record that points to the `pr` step (`step` or `target` is `pr`). Tasks in progress (queued, waiting for approval, paused, and so on) are deleted too.
- Tasks deleted together: the parent and children of a task split (if either is deleted, the parent and all children), and a fix task from the watch after merge and its original task (if either is deleted, both). The links are followed through `parent` and `fix` of each `TaskCreated` (in both directions, repeatedly).
- Before deleting, the settings (`config.yaml`) are read and checked (`purgeLegacyTasksAtStartup`). If they have an error, nothing is deleted; the number of tasks and the settings error are written to the log and the daemon stops starting up (the old records can't be read). Fix the settings and start again to delete them. If there is nothing to delete, the settings are not read.
- The number of deleted tasks and their IDs are written to the daemon log. If there is nothing to delete, nothing is done.
- The Activity is append-only (a trigger rejects deletes), so the trigger is dropped only while deleting, inside the same transaction, and recreated afterwards.
- Not deleted: workspaces, session logs, Orchestrator sessions, and GitHub branches and PRs (open PRs stay open).
- `step_agents.pr` in `config.yaml` is a settings error. Instead of an unknown-step error, the message asks you to delete `pr` from `step_agents` (`config.stepAgentsPrRemoved`).

Code: `apps/daemon/src/activity.ts` (`purgeLegacyPrStepTasks`, `purgeLegacyTasksAtStartup`), `apps/daemon/src/main.ts`, `apps/daemon/src/config.ts` (`loadConfig`)

## Verifying the implementation

The flow from the end of the Implementation step to awaiting approval is as follows.

![From implementation to awaiting approval](images/verify.en.svg)

- When the Implementation step finishes, the task waits for verification (`verification = "pending"`); sacty gets the diff and moves on to the Goal Guardian's final review. sacty does not run the tests in a separate container (the Goal Guardian runs them inside the final review). If the diff cannot be obtained, the task is paused without a final review (`verify.diffUnavailable`; resuming starts again from getting the diff).
- The final review runs on a disposable copy of the implemented workspace, on the Implementation step's image (or the Reproduce step's image if absent), with that image's `env`. The copy's .git is not the workspace's .git but a copy of the metadata saved before the agent touched it (tests can use git; the implementation shows as changes from the base). If that image has been removed from `images`, the task is paused without running it (`verify.testsUnavailable`). If the Implementation step uses services, they are started and connected before the tests ([Services](services.en.md#when-services-start)).
- If there is a test (verification) command (the Orchestrator's `testCommand`, or for a task without tests, the command the implementation declared), the prompt (`testRunLines`) has the Goal Guardian run that command in the workspace before judging. The prompt says that setup (fetching dependencies and so on) is allowed, that the whole output must be checked, not just the end (every kind of test the command runs), that the tests count as passing only when the exit code is 0 with no failing or erroring tests (when every failure is caused by the environment, see "For a person to check" below), and that tests and commands must not be changed to make them pass. It also has the Goal Guardian check that the tests mapped to each viewpoint actually ran and passed (were not skipped or excluded), and the basis of judgment is the diff, plus the implemented code in the workspace and the results of the tests the Goal Guardian ran.
- The tests it ran are reported in `tests` (`command`, `exitCode`, `output` (an excerpt of the result), `missingCommands`, `environmentFailures`) inside the same `sacty-final-review` as the verdicts. sacty records them in `tests` of `FinalReviewed` (`command` is the command sacty passed; `output` is up to 8,000 characters; `environmentFailures` only when the exit code is not 0).
- The prompt (`humanCheckLines`) has the Goal Guardian hand what cannot be checked in the workspace, and test failures caused by the environment, to a person instead of failing the review for them (PBI-155).
  - For the parts of the approved acceptance checks that cannot be checked in the workspace (real devices, a specific OS, input methods, external services, visual checks, and so on), the Goal Guardian judges whether the tests verify what can be checked (with synthetic input or events, for example) and writes the rest in `humanChecks`. Anything that tests or code could check but did not is a reason to fail, not an item for `humanChecks`.
  - When there is a test command and every failure is caused by the environment (it fails the same way at the base without the change, or it is confirmed to fail because of an environmental factor unrelated to the diff), the Goal Guardian writes each failing test's name and evidence in `tests.environmentFailures` and does not fail the review for the test failures. If even one failure comes from the change or cannot be confirmed to come from the environment, it leaves the list empty.
  - sacty records `humanChecks` (string items only) in `FinalReviewed`.
- The final review judges each viewpoint and each comment, and passes only when all are met. On top of that, sacty applies the following (`extractFinalReview`).
  - When there is a test command, it passes only when the Goal Guardian reported exit code 0, or a code other than 0 together with `environmentFailures` (`guardianTestsPassed`; no report, or a code other than 0 without environment failures, fails regardless of the viewpoint verdicts).
  - A viewpoint the implementation did not map to a test fails regardless of the Goal Guardian's verdict, with the reason `review.viewpointUnmapped` (the prompt also says to fail that viewpoint). This does not apply to a task without tests.
  - The implementation can report a viewpoint that only has changes without behavior that runs (documents, comments, wording, and so on) as checked in the diff without a test (in the test mapping, `tests` is empty and `untested` has the reason; `TestMapping`). Such a viewpoint counts as mapped (`mappedViewpointIds`), and the Goal Guardian's prompt tells it to check in the diff that the change for the viewpoint does not change behavior, and to fail it if it changes behavior but has no test. If there are `tests`, `untested` is dropped, and an empty mapping without a reason counts as not mapped. The implementation's prompt says not to write tests that only check that a file exists, can be read, or contains a string, and not to test the requirements and design files sacty places (`UNTESTED_LINES`). The mapping table of the PR body and the implementation deliverable show that there is no test and it is checked in the diff, with the reason. The implementation deliverable shows `REQ` even for a task without a design, when the implementation mapped the viewpoint `REQ`.
  - The viewpoints are the design's test viewpoints if there is a design, `REPRO` if there is a reproduction, and otherwise `REQ` (the task's purpose when there are no requirements either; "Step review" above), the same as for the test mapping (`finalReviewViewpointIds`). The output format example at the end of the instructions lists every viewpoint ID under review as is (`REQ` for a task without a design, `REPRO` for a bug fix), and the instructions say to answer with those IDs (with the fixed example `TV-1`, a `REQ` task was answered with the example's ID and treated as having no verdict; PBI-137).
  - A viewpoint without a verdict fails. When the answer uses only IDs that are not under review, it is not reinterpreted: it fails with the reason `review.verdictIdMismatch` (the viewpoint and the answered ID differ). If there is no other ID either, the reason is `review.verdictMissing` (no verdict).

  If it passes, the task stays in the Implementation step, and sacty opens the implementation PR and the task waits for the Implement approval ("The PR for a verified implementation" below).

  Code: `apps/daemon/src/prompts.ts` (`finalReviewViewpointIds`, `buildFinalReviewPrompt`, `testRunLines`, `humanCheckLines`, `extractFinalReview`), `packages/core/src/events.ts` (`GuardianTests`, `guardianTestsPassed`)
- If the final review does not pass, the implementation is redone. The redo prompt gets the review's findings, the tests the Goal Guardian ran (command, exit code, and excerpt), and the viewpoints that were not verified (`feedbackLines`). Failures judged to be caused by the environment are passed with a note that the implementation is not expected to fix them. If it fails `MAX_VERIFY_ATTEMPTS` (3) times in a row, the task is paused (`verification`). Resuming resets the count.
- When a tool written in the test (verification) command is not in the image, redoing the implementation does not fix it. If, among the names the Goal Guardian listed in `missingCommands`, there is one that is written as a word in the test command and contains no `/`, sacty records no verdict, records the cost spent in `FinalReviewFailed`, and pauses the task (`verify.commandMissing`). The pause shows the tool names, the image name, and the step (Implementation), and suggests installing them with `images.<name>`'s `packages` or `run` and rebuilding with `sacty image build`, or changing to another image. For the default image, it suggests adding an image to `images`. Resuming redoes the final review (running the tests) without redoing the implementation. Names not written in the test command (such as tools used by scripts inside `npm test`) and names containing `/` (such as `./scripts/check.sh`) are repository problems, are not matched, and the review is judged as usual.

  Code: `apps/daemon/src/prompts.ts` (`extractFinalReview`), `apps/daemon/src/service.ts` (`verify`)
- After the Reproduce step (PBI-29): sacty does not run the reproduction test. The reproduce agent's prompt has it run the test it wrote with the test command itself, confirm that it fails because of the bug, and write `tests`, `reproduced`, `command`, `exitCode`, and `output` (an excerpt of the result) in `sacty-reproduction` (`extractReproduction`). sacty records `ReproductionChecked` in the same append as the step's completion (`reproductionChecked`). Only when a reproduction test was declared, `reproduced` is `true`, and a non-zero integer exit code was declared is the bug treated as reproduced, and the task moves to Implementation. Without a declared test it is `reproduce.noTests`, otherwise `reproduce.notChecked`; the bug is treated as not reproduced and the task waits for a person's decision (the Reproduce step cannot be approved; request changes or cancel).
  - A task that was waiting for sacty's check in an older version (`reproductionPending`) is recorded as not reproduced (`reproduce.notChecked`) on resume or restart, without running the tests (`checkReproduction`).

  Code: `apps/daemon/src/prompts.ts` (`extractReproduction`), `apps/daemon/src/service.ts` (`reproductionChecked`, `checkReproduction`)
- Activity logs from older versions: `TestsRun` (the result sacty ran in a test container), `TestsSkipped`, and `tests_passed` of `verification` are kept only for reading them (the current version does not record them). `FinalReviewed` and `FinalReviewFailed` are accepted whether `verification` is `pending` or `tests_passed`. The Implementation `AgentRunCompleted` clears the previous test results (`lastTests`, `testsSkippedAt`).
- The implementation deliverable (the task screen and the Implement approval screen) shows the tests the Goal Guardian ran (`tests` of the final review) as "Tests run by the Goal Guardian" (records from older versions as "Test run"). It shows the test results and the final review in the correspondence table only for the current submission's verification (`verificationResults`). Test results and final reviews after the verification of a redone implementation has started (`verification` is `pending`) are shown as the previous submission's. In records from older versions, final reviews older than the latest test result (or, if tests were skipped, the time they were skipped) are also shown as the previous submission's. These appear under the headings "Tests run by the Goal Guardian for the previous submission" (for records from older versions, "Test run for the previous submission") and "Final review of the previous submission", and the result in the correspondence table is "Not run". The hint (tooltip) next to the heading says that nothing has run or been judged for the current submission yet. For a task without tests, a viewpoint without tests is shown as "Judged by the goal" only when there is a final review of the current submission; while waiting for verification (before the judgment by the goal), it is "Not run" (`judgedByGoalForCurrent`).
- The test line of the PR body writes, after `テスト：`, the command, pass or fail, and `（ゴールガーディアンが実行。終了コード N）` (`resultTableLines`). When the tests passed with environment failures only, it adds 「環境による失敗だけ。下の「人が確かめること」」 after the exit code. The chat's explanation of the judgment also shows the command and exit code of the tests the Goal Guardian ran, the failures judged to be caused by the environment, and the items for a person to check (`chatJudgementLines`).
- `humanChecks` and `tests.environmentFailures` of the final review are shown as what a person checks at final approval (PBI-155).
  - PR body: a checklist (`- [ ]`) titled 「人が確かめること」. Line breaks become spaces so that each item is one line (`humanCheckBodyLines`). A task that took over an existing PR does not change the PR body, so the checklist does not appear there (check it in the final review on the task screen). So that the length limit of the body does not drop it, it is placed in the footer, before the approval guidance, both with and without a PR template. To keep the footer short, an item is capped at `HUMAN_CHECK_ITEM_MAX` (1,000 characters) and the list at `HUMAN_CHECKS_BODY_MAX` (6,000 characters); items that do not fit are replaced by the number left and a note to check them on the sacty task screen.
  - Implementation deliverable: shown as "For a person to check" in the final review, and the tests the Goal Guardian ran get "Environment failures only" (`HumanChecks`). Neither appears when there is nothing to show.
  - For tests that passed with environment failures only, the result in the correspondence table is "Tests passed" (`passed` of `verificationResults`).

### The PR for a verified implementation

- When the final review passes, the Implementation step is not finished; the task waits to open the PR (`Task.publishPending`; the status is queued). sacty then commits and pushes the implementation workspace and opens the PR ([Approval and request changes](approval.en.md#approval-through-prs)). No agent is used.
- After opening the PR, sacty records `PullRequestPublished` and the implementation submission (`StepSubmitted`, with `step` set to `implement`) in the same append, and the task waits for the Implement approval. If the implementation changed nothing, sacty records `NoChangesFound` and the implementation submission without opening a PR ([Approval and request changes](approval.en.md#when-the-implementation-has-no-changes)).
- If opening the PR fails, the reason is recorded and the task stops (`pr.failed` and so on). Resuming opens the PR again without redoing the implementation (waiting to open the PR survives a pause and a restart).
- The PR is opened even when the budget cap has been reached (it costs nothing and only waits for a person's approval; see "Budget, pause, resume, and cancel" below).
- Pausing by a person: if a pause or cancel has been requested before the push or right before opening the PR, the task stops without opening the PR (for a pause, it keeps waiting to open the PR; resuming opens it). If the request comes after opening the PR has started, the PR is finished and recorded first (stopping without recording the opened PR could open a second PR on resume, or leave a PR that cancelling can't close), and then the final state depends on the request.
  - Pause: the task stays waiting for the Implement approval and is not paused. The pause operation reports that the task was not paused because it is waiting for approval (`pause.reachedApproval`; 409).
  - Cancel: after opening the PR finishes, the recorded PR is closed and the task is cancelled (the cleanup in "Budget, pause, resume, and cancel" below).
- Waiting for approval (approval by merging the PR, Request changes, and importing PR comments) works the same as for Requirements and Design ([Approval and request changes](approval.en.md)). Approving the implementation by merging the PR moves on to the after-merge watch step (if it is skipped, the task is completed).

### Tasks without tests

A task for which the Orchestrator left `testCommand` empty and wrote a basis in `noTests` (`Task.noTestsReason`) proceeds without stopping even though there is no test command, and acceptance is judged from the task's goal instead of by tests.

- Conditions for treating a task as one without tests (`checkNoTests`; checked right after the steps are chosen, when the plan includes Implementation)
  - If there is a `testCommand`, `noTests` is discarded (the behavior with a test command does not change). If there is no `noTests` and `testCommand` is also empty, the task stops as before (`orchestrator.testCommandUnknown`).
  - If a bug fix (`bugfix`) is chosen, the task stops (`orchestrator.bugfixNeedsTests`). A reproduction is confirmed by tests, so it is not chosen for a task without tests (the instructions to the Orchestrator also ask it not to choose it).
  - If the base code of the target repository (the workspace, excluding `.git`) has a file that matches the naming conventions of test files, the task stops (`orchestrator.noTestsContradicted`; up to 5 found files are shown). Matches are files inside `test`, `tests`, and `__tests__` directories, and files whose name without the extension is `test`, `tests`, `test_*`, `test-*`, `*_test`, `*-test`, `*.test`, `*_spec`, `*.spec` (and plurals), `*Test`, `*Tests`, or `Test*` (camel case) (`looksLikeTestFile`). Document files (extensions `md`, `markdown`, `txt`, `rst`, `adoc`, `asciidoc`, `org`) do not match, even inside test directories.
  - The task also stops when the scan does not finish after 20,000 entries (`TEST_FILE_SCAN_LIMIT`) (`orchestrator.noTestsUncertain`).
  - The task also stops when a directory cannot be read (including the workspace itself) (`orchestrator.noTestsUnreadable`; it shows the path of the unreadable directory relative to the workspace (`.` for the workspace itself) and the error code (or the error message if there is none)).
  - In either case, if a test file was found first, the result is `noTestsContradicted`. The message is chosen by `noTestsStop`.
  - When stopping, a `StepsChosen` without `noTestsReason` and a `TaskPaused` with the reason are recorded (for how to resume, see "Resuming a task stopped without tests decided" below).
- Instead of having it write tests, the instructions for the Implementation step ask it to write in the implementation's description how each viewpoint is met. Only when the task asks for setting up tests and the implementation sets them up does it report the command, as JSON (`{"command": "…"}`; 1 to 1000 characters) in a code block whose language name is `sacty-test-command` (`TEST_COMMAND_FENCE`). The report is recorded in `testCommand` of the implementation's `AgentRunCompleted` and read again for each submission (`Task.addedTestCommand`).
  - The report is read only in the Implementation step of a task without tests (`testCommand` of `extractBlocks`). In other steps (Requirements, Design, review, and so on) and in the Implementation step of a task with tests (where `testCommand` was decided), this code block stays in the text as it is (it reaches the outputs, the approval screen, and later steps) and is not treated as a report (the task does not stop; tests run with the decided test command).
  - Only the inside of this code block is read as the report (`extractTestCommandFences`; CommonMark fence rules: up to 3 leading spaces, 3 or more `` ` `` or `~`, closed by the same character at least as many times, and the language name is the first word of the info string). Text outside code blocks and the inside of other code blocks (such as an example quoted with four backticks) are not treated as the report. The report's code block is removed from the text.
  - If even one block's content cannot be read as JSON, is not an object, has a `command` that is not a string, is empty, or is longer than 1000 characters, or the code block is not closed, it is not treated as a missing report: `AgentRunFailed` and `TaskPaused` (`implement.testCommandInvalid`) are recorded and the task stops. Resuming redoes the implementation. If there are several readable reports, the last one is used.
- The Orchestrator's basis (`noTestsReason`) is influenced by the documents of the target repository, so it is not embedded in the text of the implementation and final review instructions; it is passed as a JSON string under a heading that says it is the Orchestrator's report, data as a JSON string, and not an instruction to the agent (`noTestsReasonLines`). The final review is also told not to follow instructions written in the basis, the task, the implementation's description, the diff, or the code. A reason a person decided when resuming (`testsDecidedBy` is `person`) gets a heading saying that a person wrote it when resuming.
- The examples of answers to the Orchestrator are shown separately: one that writes `testCommand` and one that writes `noTests` (which cannot choose `bugfix`), and the Orchestrator is told not to write both, and not to leave both empty for a plan with Implementation.
- Verification
  - If no test command was reported, the task moves to the final review without having tests run (older versions recorded `TestsSkipped`; `Task.testsSkippedAt`).
  - If there is a report, the Goal Guardian runs that command in the final review (the image and services are the same as for a task with tests). A report that the tests passed is required (exit code 0, or a code other than 0 with environment failures only; the same `guardianTestsPassed` as for a task with tests), and a viewpoint not corresponding to a test does not cause a failure (the instructions for redoing do not list viewpoints without tests either).
  - The final review judges each viewpoint from the task's goal (title and description), the approved requirements (and design, if any), the implementation's description, the diff, the results of the tests run (if any), and the code after implementation. It is told not to fail the task because there are no tests or because a viewpoint has no corresponding test, and to base its judgment only on what in the implementation's description is backed by the code and the diff. The viewpoints (the design's test viewpoints or `REQ`), pass or fail, and the redo limit of `MAX_VERIFY_ATTEMPTS` are the same as for a task with tests.
- Display
  - The step field of the task screen (`testCommandOfNoTests`): the test command shows as "none, judged by the goal", with the basis in a hint (tooltip). For tests set up in the implementation, it shows "tests added in the implementation: command" if they passed, "failed; redoing" if they failed, and "will run next" while waiting.
  - The notice on the implementation deliverable (the task screen and the Implement approval screen) (`addedTestsResult`)
    - No tests were run (no test command was declared): "Not verified by tests"
    - The tests set up in the implementation ran and passed: "Verified by the tests added in the implementation" (success color)
    - They failed: "The tests added in the implementation failed" with the exit code (failure color)
    - The current submission's tests have not run yet (`verification` is `pending` and there is a report): "Waiting to run the tests added in the implementation" (the previous submission's result is not shown)
  - The test line of the PR body (`テスト：テストのコマンドが無いため、テストでは検証していません。目的から判定しました。`, with `（実装で用意したテスト）` for tests set up in the implementation) and the basis line
  - The Activity (`StepsChosen`; in records from older versions, also `TestsSkipped`)
- A person's Implement approval is still required, as for a task with tests.

Code: `apps/daemon/src/service.ts` (`checkNoTests`, `runNextInner`, `verify`), `apps/daemon/src/test-files.ts` (`findTestFiles`, `looksLikeTestFile`, `noTestsStop`, `TEST_FILE_SCAN_LIMIT`), `apps/daemon/src/prompts.ts` (`buildOrchestratorPrompt`, `extractStepPlan`, `buildPrompt`, `extractBlocks`, `extractTestCommandFences`, `buildFinalReviewPrompt`, `noTestsReasonLines`, `resultTableLines`), `packages/core/src/events.ts` (`StepsChosen`, `AgentRunCompleted`, `TestsSkipped`), `packages/core/src/projection.ts` (`noTestsReason`, `addedTestCommand`, `testsSkippedAt`), `apps/web/src/components/implementation.tsx`, `apps/web/src/lib/labels.ts` (`addedTestsResult`, `testCommandOfNoTests`)

### Resuming a task stopped without tests decided

A task that chose steps including Implementation (and Reproduce for a bug fix) but has neither a test command nor the judgment that there are no tests (`noTestsReason`) (`testsUndecided`) stops right after the steps are chosen or before verification (`orchestrator.testCommandUnknown`, `orchestrator.noTests*`, `orchestrator.bugfixNeedsTests`). When resuming such a task, a person can decide how to handle tests (`tests` of `ResumeTaskInput`).

- Specify the test command (`{"testCommand": "…"}`; 1 to 1000 characters): `TestsDecided` is recorded and it becomes `Task.testCommand`; as for a task with tests, the Goal Guardian runs it in the final review.
- Proceed without tests (`{"noTestsReason": "…"}`; the reason is 1 to 2000 characters): `TestsDecided` is recorded and it becomes `Task.noTestsReason`; the task proceeds as in "Tasks without tests" above. Because it is a person's decision, the safeguard that looks for test files (`checkNoTests`) is not applied. A bug fix (with a Reproduce step) cannot proceed without tests (`resume.bugfixNeedsTestCommand`).
- Only one of the two can be given. Giving it for a task that did not stop because its tests were undecided is rejected (`resume.testsNotUndecided`).
- When a person decides, `Task.testsDecidedBy` becomes `person`, and the steps are not chosen again. The step field of the screen, the implementation and final review instructions, and the PR body show that the test command or the reason was decided by a person.
- When resuming without deciding, if the task stopped right after the steps were chosen and no step has an output yet (`canRechooseSteps`), `rechooseSteps` of `TaskResumed` is recorded, the chosen steps and what the choice decided (images, services, export destinations, and so on; images and agents a person changed per step are also cleared; the budget cap is kept) are cleared, and the steps are chosen again. This keeps the task from continuing with the same steps and stopping for the same reason at verification after spending on them. After a step has started, the task resumes from where it stopped, as before (and stops at verification again).
- In the resume section of the screen, a person can choose how to handle tests (resume without deciding, specify the test command, or proceed without tests). For a bug fix, proceeding without tests cannot be chosen.

## Goal Guardian

The AI is `guardian_agent` (or `default_agent` if absent). For each run it makes a copy of the code in `workspaces/_guardian/<run ID>` and deletes it when done (even if the run fails or is interrupted). The copy and the deletion are asynchronous, and the daemon keeps responding to the web UI and the API meanwhile ([Data location](architecture.en.md#data-location-sacty_home)).

| Role | What it reads | Verdict |
| --- | --- | --- |
| Judging change requests | The code at the base | `approved`, `rejected`, `undecidable`. If it cannot read or fails, `undecidable`, which goes to a person's decision (Escalation) |
| Final review | The code after implementation and the diff, and the tests it runs itself (when there is a test (verification) command; it runs on the Implementation step's image) (for a task without tests, also the task's goal and the implementation's description) | Pass or fail ("Verifying the implementation" above) |
| Deciding where to send PR comments back to | The code after implementation for the implementation PR; the code at the base for the Requirements and Design PRs | The step to go back to, or `undecidable` ([Approval and request changes](approval.en.md)) |
| Integration review | The latest base branch | This AI if `step_agents.integrate` is absent ([Task split and integration review](split-and-integrate.en.md)) |

Change requests: a step's agent can request a change to approved requirements or design (IDs are `CP-<number>`). If approved, the requirements have their approval revoked and go back for re-approval, and the design replaces the approved version. If rejected, the requesting step submits its result.

Every judging instruction includes the information gathered at the start of the task ("Information gathering" above). The basis of the verdict stays the approved deliverables (or the task's content if none) and the people's comments; the gathered information is used only to understand the background.

Code: `apps/daemon/src/service.ts` (`judge`, `settleEvents`, `runGuardian`, `verify`, `judgeRework`), `apps/daemon/src/prompts.ts` (`extractVerdict`, `extractFinalReview`, `extractRework`)

## Budget, pause, resume, and cancel

![Budget cap and pausing](images/budget-flow.en.svg)

- Budget cap: when a task is created, `budget.default_per_task_usd`. If the plan the orchestrator chose has a budget in `budget.per_plan_usd`, it is recorded as `budgetCapUsd` of `StepsChosen` and becomes the cap (the 80% notice is reset). If a person raised the cap before the steps were chosen (`BudgetCapRaised`; `budget.raised` in the projection), it is not recorded and the raised cap is kept.
- Budget: when spending reaches 80% of the cap (`BUDGET_WARN_RATIO`), `BudgetWarned` is recorded (once). When the cap is reached, the task is paused (`budget`) before choosing steps, before running a step (except opening the PR for a verified implementation), and before verification. Tasks waiting for approval are not stopped. Resuming a task stopped by the budget requires a new cumulative cap larger than the amount spent (up to 10000 US dollars) (`BudgetCapRaised`).
- Pause reasons (`PauseReason`): `budget`, `usage_limit` (the AI's usage limit), `auth` (an authentication error or missing secret), `error`, `verification`, `manual` (a person paused it), `child_cancelled` (a child task was canceled). A failed AI run pauses the task with that reason (`manual` if a person had paused it). There is no mechanism to resume automatically after a while.
- Pausing by a person: a task cannot be paused while waiting for approval, in Escalation, waiting for child tasks, or while the Goal Guardian is judging. If it is running, the container and service startup are stopped before recording. If any container cannot be confirmed as stopped, the task does not resume until that is confirmed.
- Resume: if the status before the pause was waiting to run, the stopped step is run again. Resume is rejected for an Operation that has started, keeping the task paused.
- Cancel: a task cannot be canceled while the Goal Guardian is judging. Session logs (`runs/`) are not deleted. Canceling a parent also cancels its unfinished child tasks. sacty cleans up in the following order and records the result (`done`, `skipped`, `failed`) for each target (`container`, `workspace`, `session`, `branch`, `pull_request`) in `TaskCancelled`.
  1. Stop runs answering questions and running containers.
  2. Delete the Orchestrator session.
  3. Close the implementation PR sacty opened and the open requirements and design PRs (without merging).
  4. Delete sacty's branches (the implementation PR's branch, the task branch, and step branches).
  5. Delete the workspace (not deleted if the containers cannot be confirmed as stopped).

### Cleaning up the workspaces of finished tasks

A task's workspace (`workspaces/<task-id>`) and its set-aside git metadata (`workspaces/_git/<task-id>.git`) are removed not only on cancel, but also when a completed task no longer uses them.

- A task that no longer uses them (`workspaceRetirable`): one that meets all of the following.
  - It has finished all steps and stopped (`idle` and `isCompleted`).
  - For an audited task, the audit has ended (completed or failed). An audit stopped by its budget is kept, because it can continue after the cap is raised.
  - It is not an older task waiting for the after-merge watch outside a step.
  - It has no container that could not be confirmed as stopped (`unstoppedRuns`).
- When they are removed:
  - On the append that makes the task so.
  - When a run or the answer to a question ends (if a run is in progress, they are removed at its end).
  - When the daemon starts ([Daemon startup and shutdown](daemon-lifecycle.en.md#daemon-startup-order)).
- At startup, the following are removed too.
  - Workspaces that belong to no task.
  - Per-run scratch directories (`<run-id>` under `_guardian`, `_snapshots`, `_review`, `_audit-logs`, `_audit-ledger`, `_deployment`, `_export`, `_handoff`, `_question-logs`) that do not belong to a running run or a run whose stop could not be confirmed.
    They are removed at the end of the run, but are left if the daemon is stopped during the run; after a restart the run starts over with a new run ID, so they are never used again.
  - The candidates are fixed when the cleanup starts (before listening for the API and starting the worker). Ones of runs, questions, and tasks started during the cleanup are not removed.
- Limits on what is removed:
  - Only names under the workspace root shaped like a task or run ID (UUID) are removed.
  - A link is removed by itself; its target is not followed.
  - Nothing that overlaps a place mounted by a running container (not only sacty's) is removed.
    If Docker cannot be queried, nothing is removed (checked again at the next start).
  - If either a task's workspace or its set-aside git metadata overlaps a mount, both are kept.
  - Nothing is removed if anything on the way from the workspace root to its parent is a link or not a directory (even if `_git` is a link, its target is not removed).
- If something cannot be removed (permissions and so on), the reason is logged and the rest is removed. Neither the daemon startup nor the task's progress is stopped.
  So only one of a workspace and its set-aside git metadata may be left.
  A directory whose listing cannot be read is logged too.
- Session logs (`runs/`), `sessions/`, `memory/`, and `sacty.db` are not removed.
- They are not removed while something uses the workspace (a run, answering a question, cleaning up a cancel, preparing it, or another task's integration review reading it), but when that ends.
- Operations that use the workspace after it was removed prepare it again from the same base commit (`prepareRepository`).
  - Preparing one task's workspace happens one at a time (a later preparation checks whether it is needed after the earlier one ends). If it is being removed, it is prepared after the removal ends.
  - Even if the recorded base branch is gone (for example, a continued PR's branch deleted after merging), it clones the default branch and fetches the base commit.
  - Operations that rerun a step (re-review and so on) prepare it while preparing the step's run.
  - Runs given a copy of the code, such as answering a question (`runGuardian`), prepare it before copying if both the workspace and the set-aside git metadata are missing (including a question after a re-review put the task back to waiting to run).
    If one of them is left, they do not prepare it, as before (so changes in progress are not lost).
    Because the implementation workspace is gone too, they get the base code, not the implemented code.
  - The integration review prepares completed child tasks' workspaces to read them, and removes them again when done (even on failure).
  - Canceling a task prepares them again to delete sacty's branches if both are missing.
    If they cannot be prepared, the reason is recorded in the branch cleanup result (`failed`).
    Ones prepared again are treated as absent (`skipped`) in the workspace cleanup result.

Code: `apps/daemon/src/service.ts` (`retireWorkspace`, `cleanupWorkspacesAtStartup`, `workspaceMissing`, `workspaceBusy`, `prepareRepository`, `childRepositories`, `cancel`), `apps/daemon/src/repository.ts` (`prepare`), `apps/daemon/src/workspace-cleanup.ts` (`workspaceRetirable`, `RUN_SCRATCH_DIRS`, `isSactyId`, `removeEntry`, `overlapsMounts`, `runningContainerMounts`), `apps/daemon/src/main.ts`

### Rerunning a cancelled task

- A cancelled task can be started over from "Rerun" on its detail page (`POST /api/tasks/:id/rerun`). Nothing can be appended to the activity of a cancelled task, so a new task that takes over the original is created (`rerun` in `TaskCreated`: the original task's ID and the image a person chose). When the activity is replayed, the original task records the rerun task (`rerunBy`); a task can be rerun only once (a second rerun and a task that is not cancelled are refused). Subtasks created by a split and PR review tasks can't be rerun (`canRerun`).
- A person decides the following (`RerunTaskInput`). sacty refuses a repository outside the targets and an image not in `images`.
  - The title
  - The description (the original one; for a rerun task, without the record sacty added. `rerunEditableBody`)
  - Additional notes (up to 10000 characters)
  - The repository to work in (from the project's targets; `null` means no repository, and the task proceeds like a task created without one)
  - The image (a name in `images` or `default`; without it, the image is decided as usual)
- The description is the edited description followed by the notes (`## 補足（再実行で人が足したもの）`) and the record of the previous attempt (`## 前の試行の記録（中止したタスク）`) (`buildRerunBody`). The record holds what cancelling did not remove: the original task, the repository it worked in, the ticket and the source, the steps and their states, why the steps were chosen, why it last stopped, the closed PR, when it was cancelled, the step outputs (the approved one if approved; up to 3000 characters each), remarks that were not voided, and questions with answers. Because cancelling removed the workspace, branches, and PRs, it says to start over from the beginning.
- The chosen image takes priority over the project target's setting and is used for every step (`imageSource` in `StepsChosen` is `rerun`).
- A task imported from a ticket keeps the ticket (`start` is `jira`; the PR URL is posted to the ticket, and the same ticket is not imported twice). The ticket is not read again (`awaitingTicketTriage` does not apply), and the task proceeds with the repository the person chose. With no repository, like a task created without one, the Orchestrator chooses a repository, and a person chooses it if the Orchestrator can't (`isRepoless`, `awaitingRepository`, `chooseRepository`). A rerun of a task imported from a GitHub issue doesn't keep the source (`start` is `sacty`; the record has the issue URL).
- The budget cap is `budget.default_per_task_usd` at the time the rerun task is created (the original task's cap and the amount used are not carried over).
- If the original task has a security plan (`security-check`, `security-fix`), that plan becomes the `plan` of `TaskCreated` (so the rules for the smallest change and keeping results off public places stay). For a fix task created from a category of a report, `securityFix` (the report, the category, and all the findings) is also carried over (so findings that did not fit in the description are not lost). Other plans are not carried over; the Orchestrator chooses.

Code: `apps/daemon/src/service.ts` (`rerunTask`, `pinnedImage`, `chooseRepository`), `apps/daemon/src/prompts.ts` (`buildRerunBody`), `apps/daemon/src/server.ts` (`/api/tasks/:id/rerun`), `packages/core/src/events.ts` (`RerunTaskInput`, `rerunEditableBody`), `packages/core/src/projection.ts` (`canRerun`, `awaitingTicketTriage`, `isRepoless`), `apps/web/src/components/rerun-dialog.tsx`

## Asking the Orchestrator

![Asking the Orchestrator](images/question-flow.en.svg)

- In the question field, Ctrl + Enter or ⌘ + Enter runs the same form validation and submission as the button. Only Ctrl or Meta alone is accepted; composition events do not submit. Enter and Shift + Enter remain line breaks, and blocked or pending forms cannot submit.
  Code: `apps/web/src/components/question-form.tsx`.

- Questions are up to 2000 characters (`QUESTION_MAX`), and answers up to 20000 characters (`ANSWER_MAX`; truncated if longer). At most one question can be awaiting an answer. Questions cannot be asked on canceled tasks or tasks that reached the budget cap. IDs are `Q-<number>`.
- The AI is the same as the Orchestrator; it reads a copy of the code at the base and answers by duplicating the saved Orchestrator session (the original session is not changed). The instructions include the task's title, status, steps, PR, cost and budget, body, approved results and latest outputs, verdicts, comments, recent questions and answers, and the Activity (as much as fits in 40000 characters in total).
- Session logs of each run: before the answering run, this task's per-run session logs (`SACTY_HOME/runs/<task ID>/` in [Agent execution](agent-execution.en.md)) are laid out in a per-answer-run location (`<workspaces>/_question-logs/<run ID>/`) and mounted read-only at the container's `/sacty-logs` (Claude Code is also given `--add-dir /sacty-logs`). They are deleted when the answering run finishes.
  - What is laid out: `index.json` (the list of runs) and, for each finished run, `<run ID>/meta.json`, `events.jsonl`, and `stderr.log` (only those that exist), and the agent's original files recorded in the Activity's `AgentSessionArchived` (`<run ID>/agent/<relative path>`; files whose size differs from the record or that are not regular files are not laid out). Every run that goes through execute is covered: steps, the Orchestrator, the Goal Guardian, answers to earlier questions, and so on. Hard links are used on the same file system; otherwise the files are copied.
  - For a running run (a log this daemon has opened and not yet closed), a snapshot of the log at the time the question was received (the snapshot of a running run in [Event log](event-log.en.md#session-logs-files-per-run), with secrets hidden again using the current secrets) is written to `<run ID>/meta.json`, `events.jsonl`, and `stderr.log` (only those with output) (not hard links). The agent's original files do not exist until the run finishes.
  - What is not laid out
    - Other tasks' logs (only this task's location is looked at)
    - Files other than the above
    - The answering run itself
    - Runs whose end is not recorded and that are not running (no `finishedAt` in `meta.json` and not opened by this daemon; the daemon stopped)
    - The files themselves of runs whose end is not recorded (secrets found after writing started are redacted again when the file is closed, so a file not yet closed may still contain them)
  - Status in the list: `available` (readable), `running` (running; has the snapshot time `snapshotAt`), `unfinished` (end not recorded), `missing` (the Activity has the run's ID but there is no log), `unreadable` (`meta.json` cannot be read). It also holds logs with the middle omitted due to limits, the number of agent files, reasons for not copying, and files that could not be laid out.
  - The instructions include, before the ledger, the location and how to read it (search rather than read everything; it cannot be modified; state which run of which step; say so if any run has no log, was omitted, or is unreadable), and the list of runs (the step or role name and which attempt, the run ID, the agent, start and end, the result, the log size, truncation; up to 8000 characters; if it does not fit, older runs are omitted and the agent is told to read `index.json`). The logs' contents are not included. If there is a running run, its line in the list says when the snapshot was taken (and that the run continues), and the agent is told to read `events.jsonl` from the end when asked about the current state, and to say in the answer as of when it describes the state.
  - If the task's log location (`runs/<task ID>/`) does not exist, there are no runs yet (runs in the Activity are `missing`). If the location cannot be opened (no permission, not a directory, and so on, other than ENOENT), cannot be laid out, or no logs were kept, nothing is mounted; the instructions say the logs cannot be read and why (the kind of error, for example `ENOTDIR`), and the agent answers from the ledger (a warning goes to the daemon's log).
- Asking a question does not change the status, steps, or approved content, and does not stop a running task. The cost of answering (even when no answer could be given) counts toward the task's budget.

## PR-review-only tasks

- The only step is `review`. Before running, the head of the target PR, the base commit, and the PR author's login are recorded (`ReviewTargetResolved`; empty if the author cannot be read). The code at the PR's head commit and the whole diff (mounted read-only at `/sacty-review`; the first 100000 characters in the instructions) are passed.
- Reviews already on the PR: before running, sacty reads the PR's reviews, line comments, and ordinary comments. It reads the findings by other reviewers and the author's replies, excluding posts by bots and posts by this task's account that start with the marker (its previous posts). Approving reviews with a body are included too (`includeApprovals`; they are not included when importing PR comments). What it read is passed as JSON data separate from the instructions (`existingReviews`; oldest first; the newest 30 (`EXISTING_IN_PROMPT`), 2000 characters each), for the first review and re-reviews alike. The instructions tell the agent to check the state of the existing findings before reviewing, not to repeat a problem already raised at the same place, to decide the verdict without the findings it did not repeat, and to write briefly in the summary how many were left out (without copying them). If there are none, "none yet" is passed. If they cannot be read, the instructions say so, the review is not stopped, and the reason is kept in the daemon log (secret values redacted). The author's replies for a re-review (below) are picked from the same read (if the author cannot be read, only the replies are treated as unreadable).
- sacty does the posting. The instructions tell the agent to use the default skills `review-dispatch` (with the `pr-review` flow) and `writing`, not to post by itself (not to write on the PR with gh or the GitHub API), and to give priority to the output format of the instructions when they conflict with the skills. sacty adds the verdict, the @ mention of the author, and the statement that AI posted the review, so the agent does not write them.
- Verification: the workspace is a copy of the PR's code only, with no dependencies or build outputs. The instructions say the agent may fetch dependencies as the lock file pins them and run verification such as formatters, linters, type checks, tests, and builds without rewriting the target files (formatters and the like run in check-only mode), following the skill's procedure (`verification-run`) before starting the viewpoint reviewers. They also say not to skip verification because dependencies are missing, and not to use CI results or the author's report in place of results the agent ran itself. If the orchestrator decided a test command (`testCommand`), it is shown as a candidate verification command. A review-only task created by importing a PR has no test command, because the orchestrator does not choose its steps, so no candidate is shown (the agent picks commands from the repository's instructions and CI settings). For verification that could not run, the agent writes the command and why it stopped in the body. The time limit is the limit of the roles that run tests ([Agent execution](agent-execution.en.md#container)). During verification the PR's code (dependency install scripts and tests) runs in the agent's container and, as in other runs, can reach the agent's authentication values in the container (with a codex subscription, `auth.json`, which is written back to the host after the run) and, during the run, the gateway (GitHub reads and MCP relays) ([Agent execution](agent-execution.en.md#authentication), [Gateway](gateway.en.md)). Intake does not filter by whether a PR comes from a fork or a bot. The user documentation asks users not to import or choose PRs they do not trust.
- Finding prefixes: `[要修正]` (must fix before merging) and `[提案]` (worth fixing). The agent adds them to findings in the body. For line comments (`sacty-review-comments`), the agent writes the severity (`severity`: `must` or `should`; `nit` is treated as `should`) and sacty adds the prefix at the start of the comment body (a prefix already at the start is replaced; with neither severity nor prefix, nothing is added). Findings with no line in the diff to attach to are written in the body without asking a person.
- Documents shown in the PR description (such as a design outside Git): following the skill, the agent sorts each into a review target or evidence, and reviews the targets too. Findings on documents go in the body. If a document chosen as a target cannot be read, the review is treated as not completed and no verdict is given.
- Verdict: the agent adds `verdict` in `sacty-review-verdict` (`changes_required`: changes required, `suggestions`: suggestions only (OK to merge), `no_findings`: no findings). sacty raises it to `changes_required` if a line comment has `[要修正]`, and to `suggestions` if there are findings but the verdict is `no_findings`. Line comments alone do not make it `changes_required`. If there is no verdict or it is not one of the values, and there is no `[要修正]` finding, nothing is kept (unreadable). When the review could not be completed, the agent is told not to add a verdict. The verdict block is removed from the posted body and kept in `reviewVerdict` of `AgentRunCompleted` (per round in `reviewVerdicts`). A review of a PR is delivered to the original task that opened it for rounds with `changes_required`, `suggestions`, or an unreadable verdict (rounds with `no_findings` are not delivered; how the review task was taken in (label, request, or manually) does not matter; [Approval and request changes](approval.en.md#importing-pr-comments)).
- Posted body: the marker, the heading "sacty のレビュー", one line with the @ mention of the author and the verdict (no @ if the author is not in the form of a login; says so if the verdict is unreadable), the agent's body, and the fixed sentence saying that AI reviewed it, in this order. With Claude Code, the agent's body is read from the last `result` that contains the verdict block (a reply to a notification after the final answer is not posted; [Agent execution](agent-execution.en.md#output-handling)). When `reviewMentionSelf` in the sacty settings is On, the @ mention goes to the posting account (the gh account chosen for that host in the project) instead of the author (no one is mentioned if it is not in the form of a login; the author is not mentioned).
- Right before posting, the PR's head commit is checked (not when an already posted review is found by the marker). If it differs from the reviewed commit (pushed in the meantime), the review is posted against the reviewed commit, and the body says which commit was reviewed and that "Re-review" reviews the latest one. That head is kept in `latestCommit` of `PullRequestReviewPosted`, and also in the body as a hidden marker. If it cannot be checked (including when the response has no head commit or an empty one), the task pauses without posting (`review.headUnknown`; resuming checks again). If sacty stopped after posting and before recording, the head is recorded again from the marker in the body of the posted review.
- The result is posted to the PR as a review (`COMMENT`) without waiting for a person's approval. If line comments are rejected with 422, they are put into the body and posted again. The task completes once posted.
- Re-review: a task that completed after posting can put `review` back to waiting to run and review the latest commit again (`ReviewRestarted`). This is the behavior when a person presses "Review again" in the UI. A GitHub review re-request creates a separate review-only task without reopening the completed task (see [Intake](intake.en.md)). In both cases, the previous body, line comments, reviewed commit, and posting time are kept in `previousReview`. The instructions include the previous findings and the PR author's replies since the previous post, as JSON data separate from the instructions. The author's replies are the PR reviews, line comments, and regular comments by the author's login (excluding those starting with sacty's review marker; the newest 30, up to 2000 characters each). For each previous finding, the agent writes whether it confirmed the fix or it is still open. If the replies cannot be read (including when the author is unknown), the instructions say so and the review continues, and the reason is written to the daemon log with the task and the PR (secret values are masked). In a re-review too, the agent reviews with the skill `review-dispatch` and runs verification again on the new code.
- Language: the heading, verdict, note, and fixed sentence added by sacty, and the finding prefixes, are fixed in Japanese. The agent's body and findings follow the writing rules of the target repository (in the order of the skill `writing`), and Japanese when there are none.
- In the PR check (every 60 seconds), if the PR of an unfinished review task has been merged or closed, the task is canceled.
