# 仕様書

今の sacty がどう動くかを、正確に、人が理解しやすく表す。**実装と常に一致させる**。
方針は [docs の入口](../README.md) を参照。

## ファイルの分け方

- 機能・仕組みの単位で1ファイルにする（例 `architecture.md`（全体の構成）・`tasks-and-steps.md`・`context.md`・
  `gateway.md`・`daemon-lifecycle.md`）。1つの機能を変える PR で直すファイルが、なるべく1つで済む単位にする。
- ファイル名は英小文字・数字・`-` だけ。日時は付けない（今の状態を表すので）。
- 大きくなったら、`<機能>/` のディレクトリに分け、その中に `README.md`（概要と目次）を置く。
- このファイルの「目次」に、すべての仕様書へのリンクを並べる。

## 書き方の規則

- 今の振る舞いを現在形で書く。経緯・却下した案は書かず、関係する ADR へリンクする。
- 推測で書かない。コードやテストで確かめられないことは書かないか、`（未確認）` と明記する。
- 主な項目（節）の終わりに、対応するコードの場所を書く。ファイルはリポジトリのルートからの相対パスにし、
  必要なら関数・型の名前を添える。行番号は書かない（すぐずれるので）。

  ```markdown
  コード: `apps/daemon/src/<ファイル>.ts`（`<関数名>`）、`packages/core/src/<ファイル>.ts`
  ```

- 設定の項目・既定値・状態の名前など、コードに書いてある値は、コードの名前のまま書く。
- 実装を変える PR では、変えた振る舞いを書いている節を探して同じ PR で直す。対応するコードの場所が
  動いた・消えたときも直す。

## ひな形

```markdown
# <機能の名前>

<この機能が何をするかを2〜3文で。>

関係する ADR: [<タイトル>](../adr/<ファイル名>)

## <項目>

<振る舞い。入力・出力・状態の変わり方・エラーのときの扱い。>

コード: `<パス>`（`<関数名>`）
```
