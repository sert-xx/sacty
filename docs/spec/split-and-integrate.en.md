# Task split and integration review

With the `split` plan, an agent creates child tasks based on the approved design. When all child tasks are settled, Integration review checks whether the child tasks' results meet the parent's requirements. If it does not pass, the agent adds fix child tasks.

Related ADRs: [Dependent child tasks start stacked on the dependency's PR branch once that PR passes the final review](../adr/20261108-0615-stack-dependent-subtasks-on-reviewed-pull-requests.md)

## Splitting

When splitting a parent with multiple specified repositories, the agent reads a copy of each repository and uses the per-repository design to decide the child tasks. See [Tasks and steps](tasks-and-steps.en.md#steps) for where the copies are placed and how preparation failures are handled.

- The number of child tasks is from `MIN_SPLIT_CHILDREN` (2) to `MAX_SPLIT_CHILDREN` (10). From the second round, which adds fix child tasks, a single one can be created.
- The agent's answer (heading `sacty-split`) is checked for the count, duplicate `key` values, missing dependencies, self-dependencies, and dependency cycles. If it cannot be read, the task is paused.
- Assigning test viewpoints: in the first split, when the parent's approved design has test viewpoints, the split instruction includes them and makes the agent assign them to child tasks (`splitViewpointLines`; [ADR](../adr/20261115-1345-assign-test-viewpoints-to-child-tasks.md)).
  - Each child task in the answer lists, in `viewpoints`, the IDs of the viewpoints that child satisfies with its implementation and tests. One viewpoint may be assigned to several child tasks.
  - A viewpoint that the child tasks alone cannot fully check is listed, with its ID and a reason, in `integrationViewpoints` of the answer (it is checked in the integration review). If a child task can check part of it, the same viewpoint may also be assigned to that child task.
    The integration review judges every test viewpoint anyway. Its instruction also lists the viewpoints marked for the integration review with their reasons, and says for each one whether it is also assigned to a child task (if it is not, the implementations and reviews of the child tasks did not check it) (`splitIntegrationViewpointLines`).
  - sacty checks that every viewpoint is in the `viewpoints` of some child task or in `integrationViewpoints`.
    If any of the following is found, no child task is created and the task is paused (resuming redoes the split).
    - A viewpoint that is listed nowhere (`split.viewpointUnassigned`)
    - An ID that is not in the design (`split.unknownViewpoint`, `split.unknownIntegrationViewpoint`)
    - A viewpoint in `integrationViewpoints` without a reason (`split.integrationReasonMissing`)
  - The assigned viewpoints are recorded in each child's `viewpoints` (with the viewpoint contents) and in `integrationViewpoints` of `TaskSplit`.
    A child task receives them in `viewpoints` of `TaskCreated` (`Task.inheritedViewpoints`).
  - The implementation of a child task maps a test to every assigned viewpoint ([Viewpoints the implementation maps tests to](tasks-and-steps.en.md#viewpoints-the-implementation-maps-tests-to)).
  - A split whose parent design has no test viewpoints, and the addition of fix child tasks (from the second split on), assign no viewpoints.
    A child task with no assignment uses the purpose of the task (`REQ`) as its viewpoint.
- Scope of a child task: the child task's content that the task split agent wrote (the original text, without the requirements, design, and gathered information added from the parent task) is the scope of that child task.
  The scope (the original text, the parent task's title, and whether it is a fix child task, `fix`) is recorded in each child's `scope` of `TaskSplit`, and a child task receives it in `scope` of `TaskCreated` (`Task.childScope`).
  It is not read back from the text of the child task's body (`body`), so the scope is not mistaken whatever text the content or the title contains.
  The parent task also keeps, per split round, the output of the task split agent that decided the child tasks (`Task.split.outputs`; the output of `AgentRunCompleted` of the same run, right before `TaskSplit`).
  The original text of a child task without the `scope` record is read from it ([Assembling the implementation PR body](approval.en.md#assembling-the-implementation-pr-body)).
  It is carried as the scope section in the body of the child task's implementation PR ([Assembling the implementation PR body](approval.en.md#assembling-the-implementation-pr-body)) and is also passed in the instructions of the child task that reviews that PR ([PR review](tasks-and-steps.en.md#pr-review-only-tasks); PBI-351).
- Child tasks are created with `start: split` and `parent` (the parent's ID and `dependsOn`). The body includes the parent's approved requirements and design, and the information the parent gathered at the start of the task (if any). Child tasks do not gather information again ([Tasks and steps](tasks-and-steps.en.md#information-gathering)). Child tasks without dependencies start waiting to run; child tasks with dependencies start as `blocked` and become waiting to run once all their dependencies are settled (`TaskUnblocked`).
  When the PR review child task gives a dependency's PR no findings and the draft is removed, a child task may also start stacked on that PR without waiting for it to be settled (see "Child tasks stacked on a dependency's PR" below).
- A child task's repository is the child task's `repo`, or the parent's repository if absent. When splitting a parent without a repository, each child task's `repo` is checked against the project's targets; if it is missing or not in the targets, sacty does not use the split and stops the task. For a parent with multiple specified repositories, each child is chosen from that list even after a repository is selected; an answer outside the list stops the task with the name, and resume retries the split. The instructions tell the agent to complete each child task within one repository, and to split changes across repositories and connect them with `dependsOn`.
- Splitting is one level only (child tasks cannot choose `split`).
- The parent waits for child tasks in `waiting_children`. When all child tasks are settled (completed, or canceled with a person's acknowledgment), it moves to the next step with `SplitCompleted`.
- When a child task is canceled, the parent is paused (`child_cancelled`). Resuming the parent counts as acknowledging that cancellation.

## Child tasks stacked on a dependency's PR

A child task with dependencies starts, without waiting for the merge, from the branch of a dependency's implementation PR once the PR review child task gives the current commit no findings and sacty removes the draft ([The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)) (stacked PRs; PBI-317, PBI-331).
A PR waiting for no findings (`awaitingReview`) is not stacked on. "Passing" below means this no-findings result (in earlier versions, passing the final review).
A stacked PR gets its review child task after the dependency is merged and the PR is retargeted, and its draft is removed when there are no findings (retargeting does not remove the draft).

- Deciding whether to start (`blockedStart`; in the parent's `settleSplit`, for each `blocked` child task): dependencies are sorted into the following. When it cannot be decided, the child task waits.
  - In the base branch (`landed`): canceled with a person's acknowledgment, or completed or with its implementation PR merged (`implementationMerged`; the after-merge watch is under way), and not stacked on another PR.
    A dependency whose PR was merged while still stacked (a person marked it ready and merged it before the PR it is stacked on) is not in it yet, because its changes are only in the branch of the PR it is stacked on. It gets in once that PR is merged and its starting branch is changed (`StackedDependencyMerged`)
  - Stackable: an open implementation PR whose draft was removed with no findings, with the task waiting for approval of the implementation (`reviewedPullRequest`; it is stacked on the head given no findings, `reviewedCommit`). A PR made for the verification wait of an earlier version (`verifying`), the PR of the current submission that a person moved to review despite a failed final review, and a person's PR that was taken over are excluded. Only those in the same repository as the child task
  - Others
- How it starts:
  - When all dependencies are in the base branch, it starts from the base branch (`TaskUnblocked`; not stacked).
  - When one of the dependencies (X) is stackable, and the current changes of all other dependencies can be confirmed from the records to be in X's passing commit, it starts stacked on X (`stackedOn` of `TaskUnblocked`: X's ID, PR branch, and passing commit). The starting point is decided by this rule also when there are two or more dependencies.
    It is confirmed as follows (`covers`). When none applies, it cannot be confirmed and the child task waits.
    - A dependency in the base branch: X waited for it (including dependencies of dependencies; `waitedOn`) and started from the base branch without ever being stacked (no `Task.stack` or `Task.stackedBase`). When X started, that dependency was already in the base branch. When X started stacked, it may have been built on old content of the PR it was stacked on, so it cannot be confirmed (the child task waits until X is also in the base branch).
    - A dependency not in it yet: following the PRs X is stacked on from X reaches that dependency, and at each step the workspace's base (`workBaseCommit`) is the current passing commit of the dependency one step below. When the dependency below was fixed and passed again but has not been merged in yet, it cannot be confirmed (the child task waits until it is merged in and passes again).
  - Otherwise (no single target can be decided, another repository, not passed), it waits.
    For example, a child task that depends on A and B, which do not depend on each other, is not stacked on B when A is merged, because B's passing commit does not contain A's changes; it waits until B is also in the base branch.
- Starting point: a stacked child task (`Task.stack`), when its workspace is first prepared, clones X's PR branch and checks out the passing commit (`prepareRepositoryNow`).
  The recorded starting branch (`repository.baseBranch`) is X's PR branch, and the base commit is the passing commit. The workspace is not prepared again on the base branch the orchestrator chose.
  When X's PR is merged before the workspace is prepared, it is prepared on the latest of the changed starting branch (`Task.stackedBase`; `baseBranch` of `StackedDependencyMerged`). In this case too, the workspace is not prepared again on the base branch the orchestrator chose.
- Merging in (`syncBase`): it merges at the same points as the base branch merge ([Merging the base branch](tasks-and-steps.en.md#merging-the-base-branch)). While stacked, it merges X's PR's passing commit instead of the base branch (when X was fixed and passed again).
  It fetches X's PR branch, and does a three-way merge of the passing commit (not the branch head), with the commit the workspace is currently based on as the common ancestor. It is recorded as `BaseBranchMerged`.
  It does not merge when X has no passing PR (being reworked, or closed) or when the passing commit is the current base. Conflicts and failures are handled the same as in the base branch merge. It does not merge while waiting for approval.
- PR (`publish`): a stacked child task's implementation PR targets X's PR branch, and stays a draft while waiting for approval until X is merged, the target is changed, and the review child task gives no findings (to keep the merge order; GitHub cannot merge a draft PR).
  When the PR cannot be made a draft, the task stops instead of waiting for approval (`pr.stackDraftFailed`). Even when the repository cannot use draft PRs, it does not make a PR that is not a draft (`requireDraft` of `PullRequests.upsert`; it stops with `pr.failed` without making one). It also stops when an updated PR cannot be turned back into a draft, or the answer says it is not a draft. Resuming tries again from making or updating the PR.
  The target is also sent when the PR is updated (`retarget` of `PullRequests.upsert`), and it is recorded in `baseBranch` of `PullRequestPublished`. It is not recorded for the PRs of tasks that are not stacked (their target stays the base branch decided when the PR was made).
  At the top of the body (at the top of the summary when following a template), it writes X's PR number, URL, and the child task's title, that it must not be merged before X, and that once X is merged, sacty changes the target to the base branch, the review child task reviews it, and the draft is removed when there are no findings (`stackedBodyLines`; not cut by the body length limit).
- When X's PR is merged (`merged` of `stackAction`): sacty records `StackedDependencyMerged` on the child task, changes the starting branch to the branch X's PR went into (X's starting branch), and the child task is no longer stacked.
  When X was merged first while still stacked on another dependency (a person marked it ready), sacty waits without changing it (X's changes are only in the branch of the PR X is stacked on. Stacking again would leave the workspace's base (X's passing commit) and what is merged in (which may not contain X's changes) out of step, and merging in could remove X's changes). While waiting, X has no passing PR, so nothing is merged in. Once the PR X is stacked on is merged and X is changed, this child task is changed too.
  The recorded base commit and merge are not changed, so the next merge takes in the latest of the new branch with X's passing commit as the common ancestor.
  It is recorded even when the child task is completed.
- Changing the target of a PR waiting for approval (`retargetDue`, `retargetPullRequest`): at each PR check (every 60 seconds; `checkPullRequests`), when the recorded target of the PR of a child task waiting for approval differs from the current starting branch, sacty changes the target of the PR on GitHub and rewrites the body. When it is no longer stacked, it removes the draft of a PR that passed verification in an earlier version. For a PR waiting for no findings (`awaitingReview`), it does not; it creates the review child task after retargeting and removes the draft when there are no findings. It records `PullRequestRetargeted`.
  On failure, it records nothing, writes it to the daemon log, and tries again at the next check (the task is not stopped). The PR of a child task that is not waiting for approval is changed the next time the PR is updated.
  Whether to change the target is decided for each child task with the latest task at that time (while waiting for GitHub for an earlier child task, a later child task can change). It does not start for a child task that is running, and the child task is not run while its target is being changed.
  When the task changed (by a send-back, a pause, a cancellation, and so on: it is no longer waiting for approval, or its PR, commit, submission, starting branch, or stacked target differs), sacty does not record it at any point (the reworked submission updates the PR with the target and draft state at that time). In addition, depending on when the change is noticed:
  - While waiting for authentication and the body: it does not update the PR.
  - While waiting for the PR update: it does not mark the PR ready (the PR's target and body stay updated).
  - While waiting for marking the PR ready: it turns the PR back into a draft, also when the answer is lost (the PR may already be ready on GitHub) (`redraftAfterRetarget`; nothing is recorded, so this matches the draft state in the ledger. PRs of canceled or completed tasks are not turned back. If it cannot be turned back, it is written to the log).
- When X is canceled (`cancelled` of `stackAction`; something in the chain of tasks it is stacked on was canceled): when the child task is waiting to run, idle, or waiting for approval, it is paused (`stack.dependencyCancelled`). When it is running, it is stopped after that run ends.
  It was built on top of X's changes, so resuming is not accepted (it can be canceled; the parent's `child_cancelled` handling is as before). When X is canceled before passing, the child task does not start, as before (it stays `blocked`; once a person acknowledges the cancellation, it starts from the base branch).
- Merge order: when a person marks the child task's PR ready and merges it before X, the merge is taken as the approval, as before (the child task's changes go into X's PR branch).
  They are not in the base branch yet, so child tasks that depend on this child task wait until X is merged (`landed` above).
- The state is derived from the activity log (`stackedOn` of `TaskUnblocked`, `StackedDependencyMerged`, `baseBranch` of `PullRequestPublished`, `PullRequestRetargeted`, `BaseBranchMerged`), so it is not lost when the daemon restarts.
- Child tasks without dependencies and tasks that are not split have neither a stacked target nor a recorded PR target, and their behavior does not change.

## Integration review

- The AI is the agent of the Integration review step (`step_agents.integrate`, or `default_agent` if absent). It cannot be changed per task (`agent.stepNotChangeable`). The actor in the activity is `agent`.
- The latest base branch is fetched and passed as a disposable copy. For a parent without a repository or with multiple specified repositories, copies are laid out per child task repository and base branch, even after a repository is selected. The instructions include the approved requirements and design, the test viewpoints (`REQ` if none), a summary of the child tasks (title, status, PR URL, round, repository), the person's past comments, and the AI review's past comments (in separate sections). The viewpoint IDs in the output format example are the viewpoint IDs under review (`integrationViewpointIds`; PBI-137).
- The instructions keep the check of the acceptance criteria from shrinking to confirming that a name, item, file, or link exists (`ACCEPTANCE_DEPTH_REVIEW_LINE`), have the integration review agent check, when the diff newly adds or changes a shared mechanism (a queue, a lock, a cache, a flag, and so on), that later processing continues after an anomaly or failure (`sharedMechanismLines`; what could not be checked is written in the items for a person to check (`humanChecks`)), and have it write its output in the language of the task (`OUTPUT_LANGUAGE_LINE`; PBI-301).
- A viewpoint that leaves something that cannot be checked in the workspace (a real external service, real credentials, a real device, a specific OS, visual inspection, and so on) is judged within what can be checked with the code and tests, and what remains is written in `humanChecks` of the answer (`INTEGRATION_HUMAN_CHECK_LINES`; PBI-363).
  - When it is met within that range, the viewpoint is met (`verified: true`), and the reason says what was checked and what could not be checked.
  - `humanChecks` has, one item each, what to check and how, and the concern if the task goes on without checking. It is not written in `findings` (a fix child task cannot fix it).
  - When something is missing within what can be checked with the code and tests, the viewpoint is not met (`verified: false`), and what to fix is written in `findings`. What can be checked in the workspace is not passed to `humanChecks` unchecked.
- The answer (heading `sacty-integration-review`) passes only when every viewpoint is met, no comment has recurred, and `findings` is empty.
  `humanChecks` is not used for the verdict (having items does not fail the review). They are recorded in `humanChecks` of `IntegrationReviewed` (not recorded when there are none).
  - Information for the person is not dropped. Identical items become one, and only empty items are dropped. A value that is not an array is kept as one item, and an item that is not a string is kept as its JSON text. The length is not truncated.
  - The items the previous integration review listed (`Task.integration.humanChecks`) are carried over to the next integration review. Even when the previous round failed and the integration review redone after the fix child tasks lists no items, they stay until the wait for approval.
    The instructions pass the previous round's items as JSON data with numbers (`H1`, `H2`, ...) (they are text the previous round's agent wrote, so they are not to be read as instructions). Only the items that could now be checked or are no longer needed are written in `droppedHumanChecks` of the answer, one item each, as objects in the form `{"id": "<番号>", "resolution": "<verified か obsolete>", "reason": "<外す理由>"}` (the number, the kind of removal, and the reason for removing; `previousHumanCheckLines`). `resolution` is `verified` when the item could be checked with this round's code and tests, and `obsolete` when it is no longer needed. Items that are not removed (ones that still cannot be checked, or for which it is unclear whether they may be removed) are not to be written in `droppedHumanChecks` (the reason for not removing goes in the prose of the verdict). When the previous round has no items, this section and the example of `droppedHumanChecks` are not shown.
    `humanChecks` and `droppedHumanChecks` in the example of the output format are empty arrays (so that an answer that copies the example is not read as items for a person to check or as removal requests).
    Only an object that has all of the following removes an item (`readDroppedHumanChecks`): `id` points to exactly one number among the previous round's items; `resolution` is `verified` or `obsolete`; `reason` is a non-empty string. Whether to remove is not decided from the content of the reason text or from separator symbols (so that a sentence such as `H1：まだ確かめられないので外さない`, which says the item is not removed, does not remove an item that has not been checked).
    The number is read even when it is full-width, lowercase, in brackets, or contains spaces. For `resolution`, differences in letter case and surrounding spaces are read. A number or `resolution` longer than 32 characters is not read. The text of the reason is kept as written, with surrounding spaces removed. When there are several removal requests for the same number, the first one is used.
    Any other request removes nothing: one written as a string (even a sentence that intends removal, such as `H1：確かめられた`), one whose `resolution` is missing or has another value, one with no reason, one object with several numbers, and one whose number is not among the previous round's items. When a number appears in a request that removed nothing (including a string and an object whose number cannot be read as one number), the removal request for that number is not applied either (`mentionedHumanCheckIndexes`). With `["H1：まだ外さない", {"id": "H1", "resolution": "verified", "reason": "…"}]`, H1 is not removed (the order does not matter). Numbers are searched for as an H followed by digits (full-width and lowercase included, with up to 8 spaces in between), in a string and in the keys and string values inside an object or array. A request nested deeper than 32 levels is treated as if every number appeared in it. The numbers found are used only to stop a removal request, never to decide a removal.
    The removed items and reasons are recorded in `droppedHumanChecks` of `IntegrationReviewed` as pairs of the item (`check`) and the reason (`reason`) (`resolution` is not recorded). Requests that removed nothing, and removal requests that were stopped and not applied, are recorded in `unreadDroppedHumanChecks` (a string with surrounding spaces removed, anything else as its JSON text; the length is not truncated). A removed item is not put back into `humanChecks` even when the answer of the same round lists the same text again. A round whose answer could not be read also carries the previous round's items over.
    The carry-over happens while failures continue, at the next round after a person requested changes on a passed review, and at the round that waits for approval while still failing at the limit.
    When the JSON of the answer was repaired while reading, `humanChecks` and `droppedHumanChecks` are still read even when they are not arrays (for the other array items, a repaired answer is not used unless they are arrays).
  The comments are both the person's and the AI review's, and the instructions ask for a recurrence verdict on both (`REMARK_RECURRENCE_LINE`, `remarkVerdictLines`). An AI review comment with no verdict fails the review.
- A broken JSON answer is read with repairs (PBI-298: double quotes and control characters inside strings, and so on; the answer has no nested object, so a missing closing bracket is not added). A read with repairs is recorded in `outputRepaired` of `IntegrationReviewed`. If it still cannot be read, the review stays failed, and the summary says where it is broken (the line and column in the JSON; `integrate.unreadableAt`) or that fields are missing (`integrate.unreadableShape`).
- If it passes, the task waits for a person's approval.
  When there are items for a person to check (`humanChecks`), they are shown as "For a person to check" in the integration review section of the task screen and on the approval screen, and the notice of the wait for approval shows the count. When there are items removed from the previous round (`droppedHumanChecks`), they are shown in the same section with their reasons (the wording "Reason for removing:" is in the language of the screen). When there are removal requests that were not applied (`unreadDroppedHumanChecks`), they are shown as well, under "Removal requests that were not applied". The person checks them and then approves, or requests changes when one is not met (requesting changes adds fix child tasks from the comments). There is no mechanism that records the result of each item (the approval stands for having checked).
  When it fails and there are also items for a person to check, they are passed to the instructions for adding fix child tasks as things "not to make a child task for", as JSON string data (`integrationFindingLines`).
  If it fails, it goes back to `split` to add fix child tasks. If it fails `MAX_INTEGRATION_ATTEMPTS` (3) times in a row, it waits for a person's approval while still failing, without adding fix child tasks. Requesting changes while Integration review is waiting for approval resets the count.
