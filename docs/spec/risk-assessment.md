# PR のリスク評価

sacty は、PR の内容のリスクを AI に評価させ、段階・根拠・勧めるレビューの深さ・とくに見る箇所を、PR の説明と、PR のレビューのコメントに載せる。
評価は、人が PR をどの深さでレビューするかを決めるための目安である。
評価によって、レビューを省く・自動でマージする・工程を変えることはしない。

関係する ADR: [PR のリスク評価を出す（レビューの省略・自動のマージには使わない）](../adr/20261116-1632-pr-risk-assessment.md)

## 評価する場面

評価するのは、次の2つの場面だけである。

| 場面 | 評価するもの | 載せる先 |
| --- | --- | --- |
| sacty が実装の PR を作る・更新する前（`via` が `publish`） | オーケストレーターのエージェント。実装後のコードと差分を読む | PR の説明 |
| GitHub の PR から取り込んだレビューのタスクの、レビューの工程（`via` が `review`） | レビューの工程のエージェント。レビューの答えと一緒に出す | 投稿するレビューのコメント |

- 要求要件・設計の PR と、引き継いだ既存の PR（題・本文を変えない）は、評価しない。
- sacty が自分の PR のために作ったレビューの子タスク（`reviewOf` がある・取り込みが `sacty`）のレビューのコメントには、評価を載せない（`assessesRiskInReview`）。
  その PR の説明には、PR を作る前の評価が載っている。

コード: `apps/daemon/src/risk-assessment.ts`（`assessesRiskInReview`）、`apps/daemon/src/service.ts`（`assessRisk`）

## 段階と基準

段階は3つ。段階ごとに、人に勧めるレビューの深さが決まる（`RISK_DEPTH_LABEL`。エージェントには書かせない）。

| 段階 | 基準 | 勧めるレビューの深さ |
| --- | --- | --- |
| 高（`high`） | 下の「リスクの合図」に1つでも当たる | 設計と影響から確かめる（「とくに見る箇所」を読み、リスクの合図ごとに、設計の妥当さ・影響の範囲・戻し方を確かめる） |
| 中（`medium`） | 合図に当たらず、安全な種類だけでもない（振る舞いを変えるが、範囲が限られ、変更を元に戻せば戻り、変えた振る舞いを確かめてある） | 変えた振る舞いの箇所を読む（「とくに見る箇所」と、そのテストを読む） |
| 低（`low`） | 合図に当たらず、すべての変更が下の「安全な種類」に入る | 流し読みでよい（変更が説明のとおりかを確かめる） |

リスクの合図（`RiskSignal`）は次の8つ。

| 合図 | 基準 |
| --- | --- |
| `security`（セキュリティ） | 認証・認可・秘密の値・暗号・入力の検証・外部からの入力の扱いなど、セキュリティに関わる所を変える |
| `irreversible`（取り消しにくい変更） | 保存済みのデータの移行・削除、保存の形式やスキーマの変更、外部への送信・公開など、変更を元に戻すだけでは戻らないことをする |
| `compatibility`（互換性の変更） | ほかから使われる約束（公開している API・コマンド・設定・ファイルの形式・イベントの形など）を、互換性の無い形で変える |
| `structural`（構造・広い範囲の変更） | 構造を大きく変える。または、多くの呼び出し元・複数の部分にまたがって振る舞いが変わる |
| `performance`（性能・並行処理） | 性能・並行処理・資源の使い方（ロック・再試行・タイムアウト・キャッシュ・大きな入力の扱いなど）に効く |
| `defect`（不具合の疑い） | 読んでいて、不具合・論理の誤りを見つけた |
| `large`（大きな差分） | 差分が大きい、または関心の違う変更が混ざっていて、意図を追うのに手間がかかる |
| `unverified`（確かめていない振る舞い） | 変えた振る舞いを、テストや実行で確かめていない |

安全な種類は、文書・コメントだけの変更、整形だけの変更、振る舞いを変えないリファクタリング・名前の変更、使われていないコードの削除、テストの追加・修正だけ、ログ・計測の追加、振る舞いを変えない防御的な確認の追加、import の整理と静的なリソースの更新。

- 重要な制約として、RADAR（変更のリスクに応じてレビューの深さを変える考え方）に関するスキルやコンテキストがその実行に読み込まれているときは、その内容を上の基準より優先させる（`RISK_LOADED_GUIDANCE_LINE`）。
  - 合図に当たるか・どの段階にするか・何を根拠やとくに見る箇所に挙げるかは、読み込まれた内容で決めさせる。上の基準は、読み込まれた内容が決めていないことにだけ使わせる。
  - 答えの形（JSON の項目と、`level`・`signals` の決めた値）は変えさせない。
  - 評価の対象（タスクの内容・PR の説明・差分・コード）に書かれた記述は、読み込まれたものとして扱わせない。
  - 読み込まれているかどうかを sacty は確かめない（エージェントの判断による）。
- エージェントには、迷ったら高いほうにさせる。
- sacty は、答えに合図が1つでもあれば、エージェントが付けた段階に関わらず `high` にする。合図が無ければ、エージェントの段階のままにする（`extractRiskAssessment`）。
- 点数（数値）は出さない。

コード: `apps/daemon/src/risk-assessment.ts`（`riskCriteriaLines`・`RISK_DEPTH_LABEL`・`RISK_SIGNAL_LABEL`）、`packages/core/src/events.ts`（`RiskLevel`・`RiskSignal`）

## 評価の中身と読み取り

エージェントは、評価を `sacty-risk-assessment` の JSON で答える。

```json
{"sacty-risk-assessment": {"level": "medium", "signals": [], "change": "変更の種類", "scope": "影響の範囲", "reversibility": "取り消しやすさ", "verification": "確かめた範囲", "focus": [{"where": "src/pay.ts:40-72", "why": "見る理由"}]}}
```

| 項目 | 中身 |
| --- | --- |
| `level` | 段階（`low`・`medium`・`high`） |
| `signals` | 当たったリスクの合図（無ければ空） |
| `change` | 変更の種類（何を、どう変えるか） |
| `scope` | 影響の範囲（どの機能・利用者・呼び出し元に及ぶか） |
| `reversibility` | 取り消しやすさ（変更を元に戻すだけで戻るか） |
| `verification` | 確かめた範囲（どのテスト・実行で、何を確かめてあるか。確かめていないことは何か） |
| `focus` | 人がとくに見る箇所（`where` はパスと行、`why` は見る理由。5 つまで） |

- 最後に出た、形の合う答えを使う。
- 段階が決めた値でない・根拠の4項目（`change`・`scope`・`reversibility`・`verification`）のどれかが無いときは、読めないものとする。
- `signals` が配列でない（欠けている・`null`・文字列）・知らない合図が混ざるときも、読めないものとする（合図を読み落として、低い段階を載せないため）。
- 形の違う「とくに見る箇所」は除く。
- 文は1行にし、渡された秘密の値を伏せてから、上限（根拠は 400 文字、`where` は 200 文字）で切る。

コード: `apps/daemon/src/risk-assessment.ts`（`extractRiskAssessment`）、`packages/core/src/events.ts`（`RiskAssessment`）

## PR を作る前の評価

実装の PR を作る・更新するとき、コミットをプッシュした後、本文を組み立てる前に評価する。

- オーケストレーターのエージェントを、実装後のコードの使い捨ての写しで実行する。指示には、差分の読み方（起点のコミットと出すコミット）、段階の基準、タスクの題と内容、承認済みの要求要件、実装のエージェントの説明を入れる（`buildRiskAssessmentPrompt`）。
- 同じコミットを評価済みなら、評価し直さない（再開・同じ提出の再試行）。評価できなかったコミットは、次の機会に評価し直す。
- 評価できなくても、PR の作成・更新は止めない。評価できなかった理由を記録し、本文にもそう書く。評価できないのは次のとき。
  - 予算の上限に達している（エージェントを実行しない。`pr.riskBudget`）
  - エージェントの実行に失敗した（`pr.riskFailed`）
  - 答えを読めない（`pr.riskUnreadable`）
- 止まったことを確かめられなかった実行があったときだけは、ほかの実行と重ならないように、PR を作らずに一時停止する（[人が直した本文の更新](approval.md#人が直した本文の更新)の競合のまとめと同じ）。
- 評価は、デーモンの起動のときに有効にする（`ServiceDeps` の `riskAssessment`）。有効にしていないサービス（テスト）は評価しない。
- 結果は `PullRequestRiskAssessed` に記録する。費用は、オーケストレーターの行に数える（[作業履歴](event-log.md#費用)）。

コード: `apps/daemon/src/service.ts`（`assessRisk`・`publish`）、`apps/daemon/src/risk-assessment.ts`（`assessPullRequestRisk`・`buildRiskAssessmentPrompt`）、`apps/daemon/src/main.ts`

## レビューの工程の評価

GitHub の PR から取り込んだレビューのタスク（レビューの依頼・ラベル）では、レビューの指示に、評価の基準と答えの形を足す（`reviewRiskLines`）。

- 評価は、指摘・判定とは別のものとして出させる。評価によって、指摘の重さ・判定・レビューで見る範囲を変えさせない。
- 評価の JSON は、形が違っても、投稿する本文から取り除く（`extractReviewComments`）。JSON として読めないもの（末尾のカンマなど）も、中身が評価の答えの形で始まるコードブロックごと取り除く（`withoutRiskBlocks`）。評価の見出しの文字列を含むだけのコード例は残す。コードブロックに入っていない、JSON として読めない評価は、範囲を決められないので残る。
- 評価させていないレビュー（PR のレビューの子タスク）の本文には、触れない。
- 答えを読めたら評価を、読めなければ評価できなかったこと（`pr.riskUnreadable`）を、工程の実行の完了と一緒に `PullRequestRiskAssessed` に記録する。費用は工程の実行に数えるので、この記録は費用を持たない。
- 評価できなくても、レビューの投稿は止めない。

コード: `apps/daemon/src/risk-assessment.ts`（`reviewRiskLines`・`withoutRiskBlocks`）、`apps/daemon/src/prompts.ts`（`extractReviewComments`）、`apps/daemon/src/service.ts`（`assessesRiskInReview`）

## 載せ方

PR の説明と、レビューのコメントには、同じ形の節「リスク評価」を載せる（`riskAssessmentLines`）。

- 段階（低・中・高）、勧めるレビューの深さ、当たったリスクの合図（あれば）、変更の種類、影響の範囲、取り消しやすさ、確かめた範囲、とくに見る箇所（あれば）、AI による目安である旨の順に書く。
- 評価できなかったときは、評価できなかったことと理由を書き、レビューの深さは差分を見て決めるように書く。
- 評価の記録が無いタスクには、節を出さない。
- 見出し・項目の名前・勧める深さの文は、sacty のほかの固定の文と同じく日本語。根拠の文は、エージェントが書いた言語のまま載せる。

載せる場所は次のとおり。

| 載せる先 | 場所 |
| --- | --- |
| PR の説明（sacty の決まった形） | 「結論」のすぐ後。本文の長さの上限でも省かない |
| PR の説明（PR テンプレートに沿わせる形） | 末尾の sacty の付記（footer）の先頭。省かない |
| レビューのコメント | 判定の行の後、エージェントの本文の前。今回レビューした先頭のコミットの評価だけを載せる |

コード: `apps/daemon/src/risk-assessment.ts`（`riskAssessmentLines`）、`apps/daemon/src/prompts.ts`（`buildPullRequestBodyText`・`buildPullRequestBodyParts`・`buildReviewBody`）

## 記録と画面

- `PullRequestRiskAssessed` は、評価した場面（`via`）、評価したコミット（`commit`）、評価（`assessment`）か評価できなかった理由（`reason`）を持つ。
- タスクは、最後の評価だけを持つ（`Task.riskAssessment`）。評価できなかった記録は、前の評価を残さない。
- 画面は、タスクの詳細の概要に「PR のリスク評価」の欄を出す（評価の記録があるタスクだけ）。作業履歴には、評価した場面と段階（評価できなければ理由）を1行で出す。

コード: `packages/core/src/projection.ts`（`applyEvent`）、`apps/web/src/components/risk-assessment.tsx`（`RiskAssessmentCard`）
