# PR のリスク評価

sacty は、PR の内容のリスクを AI に評価させ、段階・根拠・勧めるレビューの深さ・とくに見る箇所を、PR のレビューのコメントと画面に載せる。
評価は、人が PR をどの深さでレビューするかを決めるための目安で、人が最終判断をするとき（レビューが指摘なしになったとき。判定し直した回に残った提案もすべて対応しないとして、ドラフトを外す前の、評価だけの実行を含む）にだけ出す。
PR を作る・更新する時点では評価せず、PR の説明にも載せない。
評価によって、レビューを省く・自動でマージする・工程を変えることはしない。

関係する ADR: [PR のリスク評価を出す（レビューの省略・自動のマージには使わない）](../adr/20261116-1632-superseded-pr-risk-assessment.md)、[PR のリスク評価の段階を、合図の重さと、依存の版の更新の上げ幅で決める](../adr/20261117-0433-superseded-risk-level-by-signal-weight.md)、[依存の版の更新の上げ幅を読み取れないときは、PR のリスク評価の段階を中にする](../adr/20261117-0455-unknown-dependency-update-is-medium.md)、[PR のリスク評価は、最後に出た答えだけを読み、読めなければ前の答えにさかのぼらない](../adr/20261117-1245-risk-assessment-reads-only-last-answer.md)、[PR のリスク評価は、レビューが指摘なしになった回だけにする](../adr/20261121-0300-superseded-risk-assessment-only-when-review-has-no-findings.md)、[リスクの判断材料と人間への確認依頼を独立した Alert に分ける](../adr/20261121-0345-superseded-risk-assessment-alerts.md)、[リスクの判断材料と人間への確認依頼を独立した Alert に分ける（理由を補った版）](../adr/20261121-2100-risk-assessment-alerts-rationale.md)

## 評価する場面

評価するのは、次の 2 つの場面だけである。
- PR のレビューの工程の、今回の先頭を指摘なしと判定した回（`via` が `review`）。評価するのは、レビューの工程のエージェント。レビューの答えと一緒に出す。
- 判定し直した回に提案だけが残り、それもすべて対応しないとして、ドラフトを外す前の、評価だけの実行（`via` が `suggestions_declined`。PBI-440）。再レビューはしない。オーケストレーターのエージェントに、実装後のコードと差分を読ませ、残った提案と対応しない理由を材料に渡す。結果は、PR のコメント（1 通）と画面に載せる。評価できなくても、理由を記録してドラフトを外す。同じ PR のその先頭には繰り返さない。費用は、評価の実行と同じに記録し、予算に数える。対象は、実装の PR を作ったタスクで、リスク評価を有効にしたデーモンだけ。

| 対象のレビューの工程 | 評価するか |
| --- | --- |
| sacty が自分の**実装の PR** のために作ったレビューの子タスク（`reviewOf.step` が `implement`） | する |
| GitHub の PR から取り込んだレビューのタスク（レビューの依頼・ラベル） | する |
| 要求要件・設計の PR の子タスク | しない |
| 既存の PR を引き継いだタスクの子タスク | しない |

- sacty が PR を作る・更新するときは、評価しない（評価のためのエージェントを実行せず、待ちも入らない）。
- 子タスクで評価する PR の範囲は、PR を作る・更新する前に評価していた範囲と同じ（要求要件・設計の PR と、引き継いだ既存の PR は評価しない）。
- 実装の PR の子タスクの評価は、リスク評価を有効にしたデーモン（`ServiceDeps` の `riskAssessment`。デーモンの起動のときに有効にする）だけが行う。取り込んだ PR のレビューは、今までどおりこの設定によらない。
- 「指摘なし」は、sacty がその回の判定を指摘なし（`no_findings`）と読み取った回である。判定のブロックが指摘なしでも、行へのコメントがあって提案ありに直された回・修正が必要の回・判定が無い回は、指摘なしの回ではない。

コード: `apps/daemon/src/risk-assessment.ts`（`assessesRiskInReview`）、`apps/daemon/src/service.ts`（`assessesReviewRisk`）

## 段階と基準

段階は3つ。段階ごとに、人に勧めるレビューの深さが決まる（`RISK_DEPTH_LABEL`。エージェントには書かせない）。

| 段階 | 勧めるレビューの深さ |
| --- | --- |
| 高（`high`） | 設計と影響から確かめる（「とくに見る箇所」を読み、リスクの合図ごとに、設計の妥当さ・影響の範囲・戻し方を確かめる） |
| 中（`medium`） | 変えた振る舞いの箇所を読む（「とくに見る箇所」と、そのテストを読む） |
| 低（`low`） | 流し読みでよい（変更が説明のとおりかを確かめる） |

段階は、当たったリスクの合図の重さと、依存の版の更新の上げ幅から、sacty が決める（`riskLevelFor`）。
合図から決まる段階と、依存の版の更新から決まる段階を比べて、高いほうにする。

| 決め手 | 段階 |
| --- | --- |
| 重い合図が1つでもある | 高 |
| 重い合図が無く、軽い合図が2つ以上ある | 高 |
| 重い合図が無く、軽い合図が1つだけある | 中 |
| 合図が無い | エージェントが付けた段階 |
| 依存の版の更新の上げ幅が `major` | 高 |
| 依存の版の更新の上げ幅が `unknown` | 中以上（合図から決まった段階が高なら、高） |
| 依存の版の更新の上げ幅が `minor` か `patch`、または更新が無い | 上げない（合図から決まった段階のまま） |

- 合図があるときは、エージェントが付けた段階を使わない（軽い合図が1つだけなら、エージェントが高を付けていても中にする）。
- 合図が無いときの段階は、エージェントに、すべての変更が「安全な種類」に入れば低、そうでなければ中、と決めさせる。エージェントが高を付けていれば、高のままにする。
- エージェントには、迷ったら高いほうにさせる。
- 評価点・確率は出さない。投稿するコメントの 1〜3 は、低・中・高の区分番号。

### リスクの合図

リスクの合図（`RiskSignal`）のうち、エージェントに挙げさせるのは次の7つ。合図の重さは `RISK_SIGNAL_WEIGHT` が持つ。

| 合図 | 重さ | 基準 |
| --- | --- | --- |
| `security`（セキュリティ） | 重い | セキュリティにかかわる振る舞いを変える（認証・認可・秘密の値の扱い・暗号・入力の検証・外部からの入力の扱いなど）。その近くのコードを触るだけで、セキュリティにかかわる振る舞いを変えない変更には付けない |
| `irreversible`（取り消しにくい変更） | 重い | 保存済みのデータの移行・削除、保存の形式やスキーマの変更、外部への送信・公開など、変更を元に戻すだけでは戻らないことをする |
| `compatibility`（互換性の変更） | 重い | ほかから使われる約束（公開している API・コマンド・設定・ファイルの形式・イベントの形など）を、互換性の無い形で変える |
| `structural`（構造・広い範囲の変更） | 軽い | 構造を大きく変える。または、多くの呼び出し元・複数の部分にまたがって振る舞いが変わる |
| `performance`（性能・並行処理） | 軽い | 性能・並行処理・資源の使い方（ロック・再試行・タイムアウト・キャッシュ・大きな入力の扱いなど）に効く |
| `large`（大きな差分） | 軽い | 差分が大きい、または関心の違う変更が混ざっていて、意図を追うのに手間がかかる |
| `unverified`（確かめていない振る舞い） | 軽い | 変えた振る舞いを、テストや実行で確かめていない |

- `defect`（不具合の疑い）は、合図として挙げさせない（不具合は、レビューの指摘と判定が別に示す）。
  - `RiskSignal` には、以前の記録を読むために残っている。重さは `retired` で、段階に数えない。
  - 答えの `signals` に `defect` があれば、読み捨てる（段階に数えず、記録にも残さない）。
  - 以前の記録の `defect` は、重さを添えずに名前だけを表示する。

安全な種類は、文書・コメントだけの変更、整形だけの変更、振る舞いを変えないリファクタリング・名前の変更、使われていないコードの削除、テストの追加・修正だけ、ログ・計測の追加、振る舞いを変えない防御的な確認の追加、import の整理と静的なリソースの更新。

### 依存の版の更新

変更が、使う外部のライブラリ・パッケージ・道具の版を変えるときは、エージェントに、その上げ幅を答えさせる（`RiskDependencyUpdate`）。
上げ幅は、その依存の版の付け方に従って、更新の前と後の版から読ませる。

| 上げ幅 | 意味 | 段階 |
| --- | --- | --- |
| `major` | 互換性の無い変更を含みうる上げ幅（その依存の版の付け方で、互換性を約束していない上げ幅を含む） | 高 |
| `minor` | 互換性を保ったままの、機能の追加の上げ幅 | 上げない |
| `patch` | 互換性を保ったままの、修正だけの上げ幅 | 上げない |
| `unknown` | 上げ幅を読み取れない（版の付け方が分からない、番号の版ではないもので指している、更新の前か後の版を確かめられない、版を下げている、など） | 中以上 |
| `none` | 依存の版の更新が無い | 上げない |

- 複数の依存を更新しているときは、いちばん大きい上げ幅を答えさせる（1つでも `major` なら `major`。`major` が無く、1つでも `unknown` なら `unknown`）。
- 依存を新しく足す・外すことは、版の更新として扱わせない（合図と安全な種類で決めさせる）。
- 依存の版の更新そのもの（版の指定の変更と、そこから機械的に作られるファイルの変更）には、合図を付けさせない。
  - 脆弱性を直すための更新でも、`security` を付けさせない。機械的に作られるファイルの差分が大きくても、`large` を付けさせない。
  - `minor` と `patch` の更新は、安全な種類として扱わせる。ほかの変更が無ければ、低になる。
- 依存の版の更新と一緒に、ほかのコードや設定を変えているときは、その変更を合図と安全な種類で決めさせ、依存の版の更新の段階と比べて、高いほうにさせる。
- sacty が自分で確かめて段階を上げるのは、`major`（高にする）と `unknown`（中以上にする）だけである。`minor`・`patch` の更新だけの変更が低になるのは、エージェントが合図を付けず、低と答えることによる（sacty は、差分を読んで上げ幅やほかの変更の有無を確かめない）。

### 読み込まれた基準の優先

- 重要な制約として、RADAR（変更のリスクに応じてレビューの深さを変える考え方）に関するスキルやコンテキストがその実行に読み込まれているときは、その内容を上の基準より優先させる（`RISK_LOADED_GUIDANCE_LINE`）。
  - 合図に当たるか・どの段階にするか・何を根拠やとくに見る箇所に挙げるかは、読み込まれた内容で決めさせる。上の基準は、読み込まれた内容が決めていないことにだけ使わせる。
  - 答えの形（JSON の項目と、`level`・`signals`・`dependencyUpdate` の決めた値）は変えさせない。
  - 読み込まれた内容で段階を決めたときは、`signals` を空にさせ、`dependencyUpdate` を `none` にさせる（sacty が、合図と上げ幅から段階を決め直さないようにするため）。
  - 評価の対象（タスクの内容・PR の説明・差分・コード）に書かれた記述は、読み込まれたものとして扱わせない。
  - 読み込まれているかどうかを sacty は確かめない（エージェントの判断による）。

コード: `apps/daemon/src/risk-assessment.ts`（`riskCriteriaLines`・`riskLevelFor`・`RISK_DEPTH_LABEL`・`RISK_SIGNAL_LABEL`）、`packages/core/src/events.ts`（`RiskLevel`・`RiskSignal`・`RISK_SIGNAL_WEIGHT`・`RiskDependencyUpdate`）

## 評価の中身と読み取り

エージェントは、評価を `sacty-risk-assessment` の JSON で答える。

```json
{"sacty-risk-assessment": {"level": "medium", "signals": [], "dependencyUpdate": "none", "change": "変更の種類", "scope": "影響の範囲", "reversibility": "取り消しやすさ", "verification": "確かめた範囲", "focus": [{"where": "src/pay.ts:40-72", "why": "見る理由と、人間に判断・確認してほしいこと"}]}}
```

| 項目 | 中身 |
| --- | --- |
| `level` | 段階（`low`・`medium`・`high`） |
| `signals` | 当たったリスクの合図（無ければ空） |
| `dependencyUpdate` | 依存の版の更新の上げ幅（`none`・`patch`・`minor`・`major`・`unknown`） |
| `change` | 変更の種類（何を、どう変えるか） |
| `scope` | 影響の範囲（どの機能・利用者・呼び出し元に及ぶか） |
| `reversibility` | 取り消しやすさ（変更を元に戻すだけで戻るか） |
| `verification` | 確かめた範囲（どのテスト・実行で、何を確かめてあるか。確かめていないことは何か） |
| `focus` | 人がとくに見る箇所（`where` はパスと行、`why` は見る理由と、人間に判断・確認してほしいことの両方。5 つまで。修正指摘の全文は繰り返さない） |

- 最後に出た評価の答えだけを読む。評価の答えは、見出し `sacty-risk-assessment` を最上位のキーに持つ、JSON として読めるオブジェクト。
- 最後の答えが読めないときは、前に出た答え（下書きなど）にさかのぼらず、読めないものとする（前の答えは、合図・上げ幅を足す前のものでありうるため）。
- 出力の中で最後に出た見出しのキー（`"sacty-risk-assessment":` の形）が、最後の評価の答えの中に無いときも、最後の答えが読めないものとする。
  - JSON として読めない答え（末尾のカンマ・途中で切れたなど。見出しが最初のキーでなくても）
  - ほかのオブジェクトの中に入れ子になっている答え
  - 本文が、見出しをキーの形で書いているだけの箇所（読める評価を捨てるほうへ倒す）
- 見出しの名前だけに触れている本文と、JSON の文字列の値の中に書かれた見出しは、数えない。
- 読めないときは、評価できなかった理由を、次のように決める。

  | 理由 | 場面 |
  | --- | --- |
  | `pr.riskLastUnreadable` | 最後の答えの形が合わず、前に読める答えがある（前の答えを使わなかった） |
  | `pr.riskKeyOutsideAnswer` | 最後に出た見出しのキーが、どの答えの中にも無く、前に読める答えがある（前の答えを使わなかった） |
  | `pr.riskUnreadable` | それ以外（答えが無い・読める答えが1つも無い） |
- 段階が決めた値でない・根拠の4項目（`change`・`scope`・`reversibility`・`verification`）のどれかが無いときは、読めないものとする。
- `signals` が配列でない（欠けている・`null`・文字列）・知らない合図が混ざるときも、読めないものとする（合図を読み落として、低い段階を載せないため）。
- `dependencyUpdate` が決めた値でないときも、読めないものとする（上げ幅を読み落として、低い段階を載せないため）。項目が無い・`null` の答えは、依存の版の更新が無いものとして読む。
- 記録する評価（`RiskAssessment`）は、段階を `riskLevelFor` で決め直したものにする。`dependencyUpdate` は、更新があるとき（`none` 以外）だけ持つ。
- 形の違う「とくに見る箇所」は除く。
- 文は1行にし、渡された秘密の値を伏せてから、上限（根拠は 400 文字、`where` は 200 文字）で切る。

コード: `apps/daemon/src/risk-assessment.ts`（`extractRiskAssessment`）、`packages/core/src/events.ts`（`RiskAssessment`）

## PR を作る・更新する時点

sacty が実装の PR を作る・更新するときは、リスクを評価しない（PBI-429）。
コミットのプッシュから PR の作成・更新までに、評価の待ちは入らない。

- `via` が `publish` の `PullRequestRiskAssessed` を、新しく記録しない。前回の評価を引き継ぐ記録（`inheritedFrom`）も作らない。
- 評価の実行が止まらないことを理由にした一時停止も起きない。
- PR の説明に、評価を載せない（sacty の決まった形・PR テンプレートに沿わせる形のどちらも）。版を上げる前の `via` が `publish` の記録を持つタスクが PR を更新するときも、古い評価を載せない。
- 提出の無い PR の本文は書き換えない（過去に作った PR の本文を、さかのぼって直さない）。
- 前回の先頭から今回の先頭までが文書だけかの判定（`documentsOnlySince`）は、再レビューの絞りのために残る（[再レビューの絞り](tasks-and-steps.md)）。

コード: `apps/daemon/src/service.ts`（`publish`・`documentsOnlySince`）

## レビューの工程の評価

[評価する場面](#評価する場面)の対象のレビューの指示に、評価の基準と答えの形を足す（`reviewRiskLines`）。

- 指示は、判定を指摘なしにするときだけ評価を出すよう求める。判定が修正が必要・提案ありのとき、判定を付けないときは、評価を出さない（評価のためにコードを読み込ませない）。評価は判定の JSON の前に、同じ答えの中に出させる。
- 評価は、指摘・判定とは別のものとして出させる。評価によって、指摘の重さ・判定・起動する観点・レビューで見る範囲・ドラフトを外すかどうか・マージ・工程を変えさせない。
- sacty は、判定を決めた後で、指摘なしの回だけ評価を使う（`extractReviewComments`）。指摘なしでない回は、評価を記録せず、投稿するコメントにも載せない（「評価できませんでした」とも載せない）。
- 評価の JSON は、指摘なしでない回の答えにあっても、形が違っても、評価の対象のレビューでは、投稿する本文から取り除く。JSON として読めないもの（末尾のカンマなど）も、中身が評価の答えの形で始まるコードブロックごと取り除く（`withoutRiskBlocks`）。評価の見出しの文字列を含むだけのコード例は残す。コードブロックに入っていない、JSON として読めない評価は、範囲を決められないので残る。
- 評価の対象でないレビュー（要求要件・設計の PR の子タスク、引き継いだ PR の子タスク、評価を無効にしたデーモンの子タスク）の本文には、触れない。
- 指摘なしの回に、答えを読めたら評価を、読めなければ評価できなかったこと（理由は `pr.riskUnreadable`・`pr.riskLastUnreadable`・`pr.riskKeyOutsideAnswer`。[評価の中身と読み取り](#評価の中身と読み取り)）を、工程の実行の完了と一緒に `PullRequestRiskAssessed` に記録する。評価のための追加の実行はしない。費用は工程の実行に数えるので、この記録は費用を持たない。
- 評価できなくても、レビューの投稿・ドラフトを外す流れ・承認の待ちは止めない。

コード: `apps/daemon/src/risk-assessment.ts`（`reviewRiskLines`・`withoutRiskBlocks`）、`apps/daemon/src/prompts.ts`（`extractReviewComments`）、`apps/daemon/src/service.ts`（`assessesReviewRisk`）

## 載せ方

レビューのコメントには、節「リスク評価」を載せる（`riskAssessmentLines`）。PR の説明には載せない。

- 共通レンダラーは、判断材料・人間への確認依頼・検証情報を分ける。
  - 段階と根拠は GitHub Alert に出す。低は `[!NOTE]` と **変更リスク: 低(1)**、中は `[!IMPORTANT]` と **変更リスク: 中(2)**、高は `[!WARNING]` と **変更リスク: 高(3)**。変更の種類・影響の範囲・取り消しやすさは、低では1段落、中・高では別の項目にする。勧めるレビューの深さ・当たったリスクの合図（重さ付き）・依存更新の上げ幅も同じ枠に残す。
  - 確認箇所があれば、独立した `[!TIP]` の **とくに見る箇所（人間への確認依頼）** に、対象箇所と記録にある理由・確認依頼を順に出す。過去の記録にない依頼は補わない。
  - **確認範囲・未確認事項** と AI による目安の注記は枠外に置く。既存の `verification` は自由文のままで、確認済み・未確認には自動分割しない。
- 各 Alert はトップレベルの独立した引用ブロックとし、引用外の空行で分ける。枠内は空行も過去の記録の複数行も、すべての行に引用記号を付ける。
- `focus[].where` が相対パスと正の行番号・行範囲（例 `src/cancel.ts:10-40`）なら、対象リポジトリの `riskAssessment.commit` へのコードリンクにする。Enterprise を含むホストを維持し、区切りを保ってパスの空白・日本語・括弧・角括弧・ハッシュ記号などを URL エンコードする（工程の成果物へのリンクと同じ `urlPathSegment`）。リンクの表示は、パスをバッククォートの中にそのまま書き、中にバッククォートがあれば、それより長いバッククォートで囲む（リンク先と綴りが食い違わない）。存在確認の追加 API は呼ばない。絶対パス・親ディレクトリ参照・不正や逆転した行番号・不正な Unicode・リポジトリやコミットが不明な場合・自由文はテキストのまま出す。
- 評価できなかったときは、評価できなかったことと理由を書き、レビューの深さは差分を見て決めるように書く。
- 載せるのは、指摘なしの回の、今回レビューした先頭のコミットの評価（と、その先頭で評価だけを実行した `suggestions_declined` の評価）だけ。前の回・前の先頭の評価、指摘なしでない回に残った評価は、今回のものとして載せない。同じ先頭を判定し直した回（指摘なし）は、その回の評価を載せる。
- 見出し・項目の名前・勧める深さの文は、sacty のほかの固定の文と同じく日本語。根拠の文は、エージェントが書いた言語のまま載せる。
- 載せる場所は、判定の行の後、エージェントの本文の前。投稿するレビュー本文全体を UTF-16 のコード単位で 60,000 以内に収める。評価と末尾の案内を残す分を先に確保して、エージェントの本文を省略する。評価の詳細だけで収まらない場合は、節の見出しだけを残し、その後に「リスク評価は長いため省略しました。」だけを書く（画面の案内・リンク・注釈は付けない。PR を読む人は Sacty を使っていないことがある）。全文は、タスクの画面と MCP の `get_task` の `riskAssessment` で読める（[MCP サーバー](mcp-server.md#get_task)）。評価の各文からも、投稿の前にレビューの記録のブロックを取り除く（[作業履歴](event-log.md#投影)）。

コード: `apps/daemon/src/risk-assessment.ts`（`riskAssessmentLines`）、`apps/daemon/src/markdown-text.ts`（`urlPathSegment`・`markdownCode`）、`apps/daemon/src/prompts.ts`（`buildReviewBody`）

## 記録と画面

- `PullRequestRiskAssessed` は、評価した場面（`via`）、評価したコミット（`commit`）、評価（`assessment`）か評価できなかった理由（`reason`）を持つ。新しく記録するのは `via` が `review`（指摘なしの回）と `suggestions_declined`（残った提案をすべて対応しないとした回の評価だけの実行）の記録だけ。
- 版を上げる前の記録も、読める。`via` が `publish` の記録（評価したときの PR の差分の起点 `base`・引き継いだ元のコミット `inheritedFrom` を持つものを含む）と、指摘のある回に記録された `via` が `review` の記録は、そのまま読み込める。タスクの詳細・作業履歴の1行・費用の集計の値は変えない（`agentId` の無い記録は、費用の行にしない）。
- タスクは、最後の評価だけを持つ（`Task.riskAssessment`）。評価できなかった記録は、前の評価を残さない。
- 画面は、「PR のリスク評価」の欄を出す。
  - レビューのタスク（子タスク・取り込んだ PR のレビュー）の詳細は、そのタスク自身の評価を出す。
  - PR を作ったタスクの詳細（承認の待ちを含む）は、その実装の PR のレビューの子タスクが出した評価を、子タスクを開かずに出す。子タスクの評価があれば、版を上げる前の `publish` の評価より先に出す。
  - どの先頭（コミット）の評価かを添える。「今の先頭」は、レビューの子タスクが最後にレビューした（している）先頭（`reviewTarget.headCommit`。対象を解決する前は `reviewRestartCommit`）。評価した先頭がこれと違えば、今の先頭の評価ではないと書く（評価は指摘なしの回と `suggestions_declined` の評価にしか記録されないので、先頭が進んで指摘のある回になると、前の先頭の評価が残る）。PR を作ったタスク自身の `suggestions_declined` の評価は、評価したコミットがその先頭なら、子タスクの前の先頭の評価より先に出す。比べる先頭が無いときも、今の先頭の評価としては見せない。レビューのタスク自身の詳細にも、同じ比べ方を当てる。版を上げる前の `publish` の評価は、PR の提出した先頭・指摘なしにした先頭と比べる。
  - 評価がまだ無い（指摘なしの回も、`suggestions_declined` の評価もまだ無い）ときは、何も出さない。
- 作業履歴には、評価した場面と段階（評価できなければ理由）を1行で出す。引き継いだ評価の記録（版を上げる前のもの）は、どのコミットの評価をどのコミットに引き継いだかを1行で出す。

コード: `packages/core/src/projection.ts`（`applyEvent`）、`apps/web/src/components/risk-assessment.tsx`（`RiskAssessmentCard`・`riskAssessmentToShow`）
