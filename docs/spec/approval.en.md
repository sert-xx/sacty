# Approval and request changes

At a step with an approval gate, the task moves to the next step when a person approves it. A person approves in sacty's web UI or by merging a PR to the target repository (approval = merge).

Requesting changes redoes the work from the chosen step. There is no limit on the number of a person's requests for changes to the same step. Whatever the number, the request for changes is recorded and the work is redone.
How tasks that stopped at the limit in an earlier version are handled is collected in [Tasks stopped by the limit in an earlier version](#tasks-stopped-by-the-limit-in-an-earlier-version).

## Approval in the web UI

- Approval is possible when all of the following hold.
  - The status is `awaiting_approval` or `escalated`
  - The step is the step waiting for approval (`gate.step`)
  - The submission round the web UI was showing (`submission`) is the current round (otherwise `gate.staleSubmission`)
- Document drafts and successful Operation results are approved in the web UI.
  - Operation has no pre-execution approval gate; it performs the request and then waits for result approval.
  - Changes cannot be requested after execution starts.
  - Failure or an unknown result cannot be approved to complete the task and requires checking external state.
- A Reproduce (`reproduce`) awaiting approval (the bug was not reproduced) cannot be approved.
- Steps that opened a PR (Implementation, and Requirements or Design with a PR) cannot be approved from the web UI (`gate.approveOnPullRequest`). An implementation for which no PR was opened because the implementation had no changes is approved in the web UI ("When the implementation has no changes" below).
- Approved results are fixed (an approved step's output does not change later). The exception is a local design fix in a round that fixes a comment on an implementation PR in Implementation: merging the implementation PR approves it ([Design fixes](#design-fixes-sacty-design-edit)). The approved design is replaced by the applied version. After approval, the next step becomes waiting to run if it can run, and otherwise the task becomes `idle`.

Code: `apps/daemon/src/service.ts` (`approve`, `gateTask`, `nextAfterApproval`), `packages/core/src/projection.ts` (`StepApproved` in `applyEvent`)

## Approval through PRs

Requirements and Design (`StepPullRequestKey`) and Implementation are approved through PRs. The implementation PR is opened as a draft when the Implementation step finishes, and its draft is removed once the PR review child task reports no findings ([Tasks and steps](tasks-and-steps.en.md#the-flow-without-the-final-review)).
How the PR is opened is in [Tasks and steps](tasks-and-steps.en.md#opening-the-implementation-pr), and how tasks with records of an earlier version's final review are handled is in [Tasks and steps](tasks-and-steps.en.md#tasks-from-the-version-with-the-final-review). Approval, Request changes, approval by merging the PR, and importing PR comments work the same for the three steps.

When Requirements, Design, and Implementation are all approved through PRs, the branches look like this (an example where the task ID starts with 1a2b3c4d).

![Branches when approving through PRs](images/approval-branches.en.svg)

- Whether a task is approved through PRs (`stepPullRequestsOn`)
  - If it has a task branch, it is always approved through PRs.
  - A task that takes over an existing PR (`Task.continuedPullRequest`) does not open Requirements and Design as PRs ([Taking over an existing PR](tasks-and-steps.en.md#taking-over-an-existing-pr)).
  - Without a task branch, it is approved through PRs when all of the following hold.
    - There is a target repository
    - The requirements and design have not yet been submitted in the web UI
    - The project has a GitHub account for that host
- The task branch `sacty/task-<first 8 chars of task ID>` is created from the base commit of the base branch (`TaskBranchCreated`).
- PRs for Requirements and Design
  - sacty writes the result to the file `<documentsDir>/<first 8 chars of task ID>/<step>.md` and opens it as a PR from the step branch `<task branch>-<step>-<round>` to the task branch.
  - The Orchestrator decides `documentsDir`. If its shape is not usable, the default `docs/sacty` (`DEFAULT_DOCUMENTS_DIR`) is used.
  - An HTML comment saying sacty created the file is put at its top, and the design includes the test viewpoints.
- Whether the Requirements or Design PR is recreated
  - If that step's PR is open and the head of the task branch has not changed, the same PR is updated (redoing that step).
  - In the following cases, a new branch and PR are created from the latest task branch, and the earlier open PR is closed.
    - The PR has been merged or closed
    - The task branch moved because a fix to an earlier step was merged
  - If a PR cannot be opened, the reason is recorded and the task stops.
- The implementation PR
  - If there is a task branch, the implementation is stacked on the latest task branch and opened as a PR from the task branch to the base branch (the implementation PR).
  - If there is no task branch, it is opened as a PR from a sacty branch (`sacty/task-<first 8 characters of the task ID>`) to the base branch.
  - If changes other than the requirements and design files have been stacked on the task branch, publishing stops (`pr.taskBranchChanged`).
    Commits a person added after sacty stacked the implementation do not stop it; they are merged into the workspace and sacty stacks on their tip ([Merging commits a person added to the PR](tasks-and-steps.en.md#merging-commits-a-person-added-to-the-pr)).
  - A task that takes over an existing PR opens no PR; it pushes to the source branch of the taken-over PR and uses that PR as the implementation PR.
- Each child task of Task split has its own task branch.
- The "review" link in the web UI (`personAction`)
  - The link appears in the task details, the task list, "Needs you" on the dashboard, and the header notifications.
  - When all of the following hold, the link opens the PR in a new tab (`reviewPullRequestUrl`). The label is "Review on the PR", and the sacty approval screen is skipped (PBI-136).
    - The task is `awaiting_approval`
    - The PR of the current submission (`gatePullRequest`) is `open`
    - The PR's URL starts with `https://`
  - In an escalation with a change request waiting for a person's decision (`change_proposed`, and also `change_undecidable` from earlier versions; one a person has not decided yet; `openProposal`), the link goes to "Change requests" in the task details (`/tasks/<ID>#proposals`).
  - In the following cases, the link goes to the sacty approval screen (`/tasks/<ID>/review`).
    - Any other escalation (such as confirming the step to redo for PR comments)
    - The task is `awaiting_approval` and the PR for the current submission is not open (it was closed, or it was merged and the next check has not recorded the approval yet) or does not exist
  - A link that opens outside is marked with "↗" and, for screen readers, "opens in a new tab" (`ActionLink`).
  - From the notifications, it opens without switching the project.
  - On the dashboard and in the notifications, the link is the task title, so only the title is truncated and the mark is placed outside the truncation. The mark stays even for a long title (PR #148 review suggestion).

## When the implementation has no changes

When opening the PR for an implementation, if the implementation workspace has not changed at all from the base commit (`NothingToCommitError`), no PR is opened.

- If no implementation PR has been opened yet, `NoChangesFound` (the Implementation round to be submitted next) is recorded, and the implementation is submitted (`StepSubmitted`). Since there is no PR, it can be approved in the web UI. This applies to every task (not only template tasks).
- Before the submission, sacty runs neither the tests nor the final review (sacty does not run tests; [The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)). Since there is no PR, no PR review child task is created either.
  The web UI shows the approval wait as "Implement awaiting approval with no changes". The approval screen says the implementation changed nothing and asks you to check the reason no change is needed in the implementation notes.
- Approving completes the task without opening a PR ("Done (no changes)"). Requesting changes redoes the work from Implementation as usual, and a PR is opened if there are changes. The no-changes handling applies only to that submission round (`deliveredWithoutChanges`: `noChanges.submission` is the current Implementation round and there is no PR).
- The same applies when there is a task branch (with the requirements and design PRs merged). No PR to the base branch is opened, and the task branch remains.
- In a task that already opened an implementation PR, if the redone implementation ends up with no changes, the reason (`pr.failed`, `git.nothingToCommit`) is recorded and the task stops, as before. A person decides what to do with the open PR.
- The Implementation step's instructions say that if it turns out no change is needed, the agent should leave the files unchanged and write the reason and evidence in the notes.

Code: `apps/daemon/src/service.ts` (`publish`), `packages/core/src/events.ts` (`NoChangesFound`), `packages/core/src/projection.ts` (`noChanges`, `deliveredWithoutChanges`), `apps/daemon/src/prompts.ts` (`NO_CHANGE_LINE`), `apps/web/src/lib/labels.ts` (`statusText`)

## The review child task of a PR

For each PR sacty opens (requirements and design PRs, and the implementation PR), sacty creates a child task that reviews that PR.
This is so that the PR is reviewed in a context separate from the step that opened it (a separate task and run), its findings are delivered to the parent (the task that opened the PR) through [Importing PR comments](#importing-pr-comments) to be fixed, and this repeats until there are no findings.
No label is attached to the PR (the review label `reviewLabel` is used only for taking in PRs sacty did not open; [Ticket intake and GitHub](intake.en.md)).

- When it is created: right after the requirements or design PR is opened.
  For the implementation PR, right after it is opened as a draft (the draft is removed when there are no findings; [Verifying the implementation](tasks-and-steps.en.md#the-flow-without-the-final-review)).
  An implementation PR stacked on a dependency's PR gets one after the dependency is merged and the PR is retargeted (not while it is stacked).
  In a task that continues an existing PR, it is created for the continued PR.
- The child task is a PR-review-only task (`source.review: sacty`; [Tasks and steps](tasks-and-steps.en.md#pr-review-only-tasks)), and holds the parent's ID and the step that opened the PR in `reviewOf` of `TaskCreated`.
  Its title is `[PR #<number>] <parent title>` (a form that does not depend on the language; up to 200 characters; a long parent title is cut with `…` without splitting a character), its project is the parent's, and its budget cap is `budget.default_per_task_usd` (the child task's cost counts toward the child task's budget).
  It is separate from split subtasks (`parent`), and is not waited for by a split or included in an integration review.
  When the parent task has information it gathered at its start, the child task inherits it and does not run the information gatherer ([Information gathering](tasks-and-steps.en.md#information-gathering)).
- Review scope: for a requirements or design PR whose task still has an implementation step, the child task's review is narrowed to direction and gaps (implementation details and test-viewpoint details are left to the later implementation PR review; [Tasks and steps](tasks-and-steps.en.md#pr-review-only-tasks)). Implementation PRs and document PRs of tasks with no remaining implementation are not narrowed.
- `ReviewTaskCreated` (the child task's ID, step, and PR) is recorded on the parent (`Task.reviewTasks`).
  One per PR (repository and number). A PR with a record does not get another when updated. When the PR is recreated (new number), one is created for the new PR.
  However, if the last child task was cancelled because the PR was closed (`reason: pull_request_closed`), the PR check after the PR is reopened creates a new child task and adds a record (a cancelled task cannot be re-reviewed; `needsReviewTask`).
  A child task a person cancelled is not recreated.
- "Related tasks" in the task detail shows links from the parent to its child tasks (the step, the PR number, and the child task's status) and from a child task to its parent (several child tasks for the same PR can be told apart by their status).
- When it is not created
  - The parent is canceled or a cancel was requested.
  - A review task for that PR (such as one taken in from the review label by an older version) exists and has not finished (no double review).
  - It is disabled in the daemon's dependencies (`reviewTasks`; for tests that check only the step flow. Enabled when the daemon starts).
- Failing to create it does not make opening the PR or waiting for approval fail (it is logged by the daemon and retried at the next PR check).
- Re-review right after a submission: right after the parent submits a fix and returns to waiting for approval (`publish`, `publishStepPullRequest`), the steps below are done for that parent alone, without waiting for the 60-second check (`reconcileReviewTask`).
  For an implementation PR waiting for no findings, if the head read from GitHub right after the submission differs from the submitted commit (GitHub may not have caught up), nothing is done.
  When it could not start (the head cannot be read, recording fails, and so on), only a warning is logged and the submission does not fail. The 60-second check starts it.
  This path and the 60-second check run one after the other per parent (key `review-reconcile:<parent ID>`), and the later one decides from the parent and child as recorded by the earlier one (a `ReviewRestarted` for the same head is never recorded twice, and a child task is never created twice).
- In the PR check (every 60 seconds), if the PR of the current submission (`gatePullRequest`) of a task waiting for approval (`awaiting_approval`) is open, the following is done (`reconcileReviewTasks`).
  Parents for which pause or cancel was requested are excluded.
  - If there is no record of a child task, one is created (when it stopped (shutdown or crash) after the publish was recorded but before creating it).
    If only the child task was created and it stopped before recording it on the parent, only the record is added without creating it again.
  - If the child task has posted its review (it can be re-reviewed: it is complete, or it posted a verdict other than no findings and is watching the PR for changes), and the head commit it reviewed (`reviewTarget.headCommit`) differs from the following head, a re-review starts (`ReviewRestarted`, `reason: updated`, that head in `commit`; actor `sacty`).
    - An implementation PR waiting for no findings (`awaitingReview`): the PR's current head on GitHub (`pullRequestHead`; including commits a person added). If it cannot be read, the next check tries again.
    - An implementation PR whose draft was removed after no findings: the GitHub head read in the PR check if it differs from the head given no findings (`reviewedCommit`) (a person added commits after the draft was removed), otherwise `reviewedCommit`.
    - Other PRs (Requirements and Design PRs): the commit the parent currently has on the PR.
    This is when the parent fixed the findings, updated the PR, and went back to waiting for approval, and when a person added commits to the PR. It does not start while fixing (not waiting for approval).
    It starts only once for the same commit (`Task.reviewRestartCommit`; even if a push elsewhere makes the reviewed head differ from the parent's commit, it does not repeat).
    If the parent's rework does not change the head of the implementation PR, no re-review starts. When findings remain on that head, the parent pauses instead of submitting ([Unfinished implementations and reworks that change nothing](tasks-and-steps.en.md#unfinished-implementations-and-reworks-that-change-nothing); when it declined every finding, see the next item).
    Child tasks that are paused, or for which pause or cancel was requested, are left alone.
  - When the parent declined every finding and submitted with the same head (`ReviewRejudgeRequested`), a re-review starts even though the head the child task reviewed is the current head (`ReviewRestarted`, `reason: declined`, with that head in `commit`; actor `sacty`; `rejudgeDue`).
    - It starts after the replies with the reasons are done (no remark is left to reply to; [Replies about how remarks were handled](#replies-about-how-remarks-were-handled)). While the replies wait for a GitHub rate limit, it waits and does not start. After a reply could not be posted and the failure was recorded, it starts without that reply.
    - It starts only once for the same head (`Task.reviewRejudgeCommit`). Restarting the daemon does not repeat it.
    - A re-review may be narrowed to the check of the previous findings and the changes since the previous review (the daemon decides and states it in the prompt; "Narrowing the scope and viewpoints of a re-review" in [PR-review-only tasks](tasks-and-steps.en.md#pr-review-only-tasks); PBI-432). This round, which judges the same head again, has no changes since the previous review, so when the conditions are met it checks only the previous findings. A submission after the parent went back to an earlier step and redid it is not narrowed and reviews the whole PR.
    - When there were proposals to defer not yet decided by a person at the parent's submission (`awaitsDecision` of `ReviewRejudgeRequested`; this includes proposals of earlier submissions), it does not start until a person has decided all of them ([Proposals to defer and the person's decisions](#proposals-to-defer-and-the-persons-decisions)).
    - The review instruction adds that this round judges the same head again (`rejudgeLines`). The reviewer checks, in the code of the head commit, whether the author's reasons for declining hold; it withdraws a finding whose reason holds, and keeps a finding as not addressed when the reason does not hold.
      It withdraws a finding only when it confirms that the finding itself does not apply. When the reason is about weight (rare, small impact) and the finding is not fixed, it does not withdraw it; it checks the weight again and, when it is of suggestion weight, keeps it as a finding whose weight was reconsidered (for reconsidering the weight in a re-review, see [PR-review-only tasks](tasks-and-steps.en.md#pr-review-only-tasks)).
      The line of an ordinary re-review that says not to raise again a point the author answered with "out of scope" or "to be handled later" is not given in this round; the reviewer decides such points too by checking the scope. The reviewer writes the findings it keeps in the "previous findings" section of the body (what reaches the parent is the review body).
    - With no findings, the draft is removed as below and the PR waits for a person's approval. When findings remain, the parent is paused ([Importing PR comments](#importing-pr-comments)).
  - When the parent declined every suggestion in the sorting before reworking and did not start a rework (`reason: triaged` of `ReviewRejudgeRequested`; [Sorting suggestions before reworking](#sorting-suggestions-before-reworking)), the child task also judges the same head again, once, after the replies are done, as above (`ReviewRestarted`, `reason: declined`).
    - The instructions add that the PR's author declined some suggestions before reworking and did not change the code (`rejudgeLines`). For those suggestions, the reviewer does not check whether the author's reasons hold, does not count them as unaddressed, and does not write that they were withdrawn. With no new must-fix, the verdict is no findings.
    - The lines above that check the author's reasons, such as "withdraw only when the finding itself does not apply", apply only to findings not in `declinedByAuthor` (findings the implementation declined and must-fix findings).
    - With no findings, the draft is removed and the PR waits for a person's approval. When a must-fix or a suggestion to handle remains, the parent goes to the rework without pausing. When only suggestions remain and all of them are declined too, the parent does not pause: after the replies, the draft is removed with the verdict still "suggestions", and the PR waits for a person's approval (`PullRequestMarkedReady` with `reason: suggestions_declined`; PBI-440). Before the draft is removed, the risk assessment alone is run once, without a re-review, and posted as a PR comment (`PullRequestRiskAssessed` with `via: suggestions_declined`; the draft is removed even if the assessment fails).
- The instructions for a same-head re-judgment started by the sorting (`reviewRejudge.reason` is `triaged`) say that the only new findings to raise are `[要修正]` (must-fix) ones; new `[提案]` (suggestion) weight findings are neither written in the body nor as line comments and are not a basis for the verdict (not adopted at aggregation even if a reviewer raises them; the verdict is decided as before from the new `[要修正]` and the handling of previous findings (unaddressed `[要修正]`, findings reweighted to suggestions), and is no findings only when there is neither a new `[要修正]` nor a remaining previous finding). This is added even when the re-review scope is not narrowed (`triagedRejudgeLines`, `ReviewDeferrals.triagedRejudge`). It is not added to a re-judgment after the implementation declined, nor to an ordinary re-review.
- How declined suggestions are passed: the parent's `Task.declinedSuggestions` is passed on every re-review (including those from rounds before the previous one, without relying only on the replies after the previous post) as data separate from the instructions (`declinedByAuthor`: `finding`, `reason`, `url`, and `findingTruncated` and `reasonTruncated` when cut) (`rereviewLines`, `declinedByAuthorLines`). The newest 50 are passed, each cut at 600 characters after hiding secrets (the same limits as `deferredByPerson`).
  - In the "previous findings" section, the reviewer writes for each previous finding one of: confirmed as addressed, not addressed, the PR's author decided not to handle it, or withdrawn (with a reason). A withdrawn finding is not counted as not addressed and is not a target of the rework by the task that created the PR (the rework instructions have it fix only the findings in the "findings" section and those written as not addressed in the "previous findings" section; lines written as withdrawn, decided not to handle, or sent to a follow-up are not fixed).
  - Declined suggestions are not counted as unaddressed, not raised again (not even as another occurrence of the same cause), and not used as grounds for the verdict. While they keep the weight of a suggestion, they are not kept as unaddressed even when the reviewer thinks the reason does not hold (the PR's author decides whether to handle them, and a person can override with a PR comment).
  - Only when a fresh check shows the suggestion has must-fix weight (a bug, security, data corruption, a requirement not met, or a broken compatibility), or later changes made its impact larger, does the reviewer raise it as a new must-fix with the grounds (then the rework starts as before).
  - The re-review rules of the default skill `review-dispatch`, in the flow `pr-review`, say the same ([Context](context.en.md#default-review-skills)).
- If the child task's verdict is no findings (`no_findings`), nothing is delivered to the parent and the verdict itself starts no re-review, so the PR waits for a person's approval (merge). Even after no findings, a re-review starts as above when the PR's head changes (for example when a person adds commits).
  For an implementation PR (`awaitingReview`), when the current commit of the PR gets no findings, the PR check has sacty remove the draft (`PullRequestMarkedReady`; [The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)).
  An implementation PR waiting for no findings is turned back into a draft at every check until the child task gives the current head no findings (`redraftAwaiting`; also for a PR that could not be turned back into a draft at submission, and during the review).
- sacty reads the CI state of the head commit being reviewed (workflow runs, checks, commit statuses, and the jobs inside workflows (GitHub Actions checks, so that jobs that did not run are passed even when the workflow succeeded); check names, status, conclusion, and URL; all failed and running checks are listed, succeeded ones (`success`, `neutral`; `skipped`, which did not run, is not left out) only up to `REVIEW_CI_MAX` in total, and the rest as a count) and passes it to the child task (`reviewCiOf`, `reviewCiLines`). Because sacty does not wait for the CI, the child task is told to make failures caused by the change required fixes, to write failures confirmed to be unrelated to the change as things a person should check in the body, and to review without waiting for unfinished checks, writing that they are running.
  sacty waits up to `REVIEW_CI_TIMEOUT_MS` (30 seconds) to read the CI. If there is no answer, it continues the review as if the CI could not be read.
  If it cannot be read, that is passed instead (the review does not stop).
  If GitHub's answer has no array of items (for example, a response from a proxy), sacty does not treat it as having no CI yet; it treats the CI as unreadable.
- For the implementation PR of a security fix, sacty passes the child task the fix scope declared by the preceding investigation (files that may be changed, dependencies to upgrade) and the result of sacty checking the diff against the scope (`securityScope` of `FinalReviewSkipped`; `reviewSecurityLines`).
  The child task is told to check whether the diff is the minimal change within the scope (viewpoint `SEC-MIN`) and to make changes outside the scope or unneeded changes required fixes. If sacty found a violation, that is also made a required fix.
  There is no limit on the number of rounds; they stop at the budget cap of the parent and of the child task.
- When the child task posts a verdict other than no findings, it does not complete and watches the PR for changes ([Watching the PR after posting](tasks-and-steps.en.md#watching-the-pr-after-posting)). The parent's flow does not change: the parent does not wait for the child task to complete, and moves on by the posted review and its verdict (taking in findings, re-reviewing, and removing the draft are decided by whether the child task has posted (`canRereview`; its steps are finished) and by the verdict of the current round). The watch does not re-review a child task on a change of the PR head or on a reply (only the re-reviews by the parent's flow above).
- If the PR is merged or closed before the child task posts its review (waiting to run or running, including a re-review run), the child task is cancelled (the same as PR-review-only tasks; `checkReviewPullRequests`). While watching, it is not cancelled; the watch ends and it completes (`ReviewWatchEnded`). After completion with no findings, it stays complete and nothing is recorded. This also applies to a watching child task that is paused: sacty resumes it, then ends the watch. A child task that has not posted yet is cancelled on merge or close even while paused.
- If the parent is done, the PR check (`reconcileReviewTasks`) settles the child tasks that have not finished, without reading the PR. A watching child task (including a paused one) ends its watch and is done (`ReviewWatchEnded` with `reason: parent_completed`; if paused, sacty resumes it first). A child task that has not posted yet (including a paused one) is cancelled (`reason: parent_completed` of `TaskCancelled`).
- If the parent is cancelled, the PR check also cancels the child tasks that have not finished, including watching ones (`reason: parent_cancelled` of `TaskCancelled`; even if the PR was not closed in the cancel's cleanup, the review and the watch do not continue).
  The PR check finishes only after the child tasks' cancellation (cleanup and records) finishes.
- Records from older versions (`label` and `intakeLabel` in the PR publish records, `PullRequestLabeled` and `PullRequestLabelFailed`) can still be read but are not treated as a plan to attach a label (the ledger is not rewritten).

## The PR check

Every 60 seconds the daemon checks the PRs of tasks that have a PR for the current submission (`gatePullRequest`) and are waiting for approval (`awaiting_approval`) or escalated (`escalated`) (the next check does not start until the previous one finishes).

- Merged: `PullRequestMerged` and `StepApproved` (both with actor `person`) are recorded.
  - It is also approval when the PR was merged with content different from sacty's submission (the PR's head differs from sacty's commit) (`edited`).
  - For Requirements and Design, the file is read from the merge commit, and the version the person edited becomes the approved result. If the file was deleted or cannot be read, sacty's version is approved. If it cannot be fetched, nothing is recorded and the next check tries again.
- Closed without merging: `PullRequestClosed` is recorded, and instead of approving, the task waits for a person's decision. It cannot be approved from the web UI (request changes or cancel).
- Reopened: `PullRequestReopened` is recorded and watching continues.
- Unchanged: if the PR is still open and the task is `awaiting_approval`, the following are done in order.
  1. The PR's current head on GitHub is remembered (`latestHeads`; it changes when a person adds commits; used to decide the head to re-review).
  2. For an implementation PR, a change in the conflict with the base branch is recorded ([Showing a conflict with the base branch](#showing-a-conflict-with-the-base-branch)).
  3. For an implementation PR, the draft state on GitHub is matched to the ledger (`settleDraft`; a PR waiting for no findings (except a PR stacked on a dependency's PR) that is not a draft is turned back into a draft, and for a PR whose draft was removed after no findings, if the review child task has given no findings for the current head on GitHub, it is made ready again when it is a draft, and if a person added commits after the draft was removed and the head changed, it is turned back into a draft until the re-review gives no findings for that head (`wantsDraft`); [The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)).
  4. Reviews and comments are imported as comments to address ([Importing PR comments](#importing-pr-comments)).
- If the status, PR, or commit changes during the check, nothing is recorded.
- If the PR is merged, or closed without merging, while comments are being imported (for example while the step to redo is being decided), changes are not requested. The status is read again within the same check and recorded as the merged or closed case above ([Importing PR comments](#importing-pr-comments)).
- When an implementation PR is merged and the after-merge watch step is not skipped, the after-merge watch starts in the same append ([After-merge watch](deployment-watch.en.md)).
- At the start of the check, the following are done in order.
  1. The implementation PR of a task that is reworking the implementation (not waiting for approval) is also checked (`checkReworkMerges`; [Merging during a rework of the implementation](#merging-during-a-rework-of-the-implementation)).
  2. The base of the PRs waiting for approval of child tasks stacked on a dependency's PR is changed (`retargetPullRequest`; [Child tasks stacked on a dependency's PR](split-and-integrate.en.md#child-tasks-stacked-on-a-dependencys-pr)).
  3. Comments that arrived on the implementation PR of a paused task are kept as not yet addressed (`checkHeldFeedback`; [Comments that arrive while paused](#comments-that-arrive-while-paused)).
- At the end of the check, the following are done in order.
  1. Memories whose PR promoting them to context was merged are deleted (`cleanupPromotedMemories`; [Memory](memory.en.md#promotion-to-context)).
  2. The PRs of PR review tasks are checked (`checkReviewPullRequests`). A task that has not posted its review is cancelled if the PR was merged or closed without merging. A task watching the PR for changes after posting ends its watch or starts a re-review ([Watching the PR after posting](tasks-and-steps.en.md#watching-the-pr-after-posting)).
  3. The review child tasks of PRs waiting for approval are put in order (one that stopped before being created is created, and if the parent updated the PR, a re-review starts; `reconcileReviewTasks`; [The review child task of a PR](#the-review-child-task-of-a-pr)).
  4. The implementation PRs of paused tasks that are not drafts on GitHub are turned back into drafts (`settlePausedDrafts`; [The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)).
  5. The CI/CD of tasks waiting for the after-merge watch is checked (`checkDeployments`).
  6. The CI of the head commit of one of the implementation PRs that wait for a person's approval is read, and a failure is recorded (`readPullRequestCi`; [Showing a CI failure after no findings](#showing-a-ci-failure-after-no-findings)).

Code: `apps/daemon/src/service.ts` (`checkPullRequests`, `latestHeads`, `settleDraft`, `settlePausedDrafts`), `apps/daemon/src/pr-watcher.ts`

### Merging during a rework of the implementation

If a person merges the implementation PR while the implementation is being reworked (after a rejection or imported PR comments; the task is not waiting for approval), the merge is taken as the approval and the rework is stopped. No new PR is created.

- Targets (`reworkingPullRequest`): tasks whose active step is Implement and whose status is queued (`queued`), running (`running`), waiting (`idle`, for example waiting to open the PR), or paused (`paused`), and whose PR in `Task.pullRequest` is open (`pullRequestState` is `open`) or was closed while waiting for approval and then sent back (`closed`; it may be reopened and merged on GitHub, and whether it is merged is decided by GitHub's state).
  - A continued existing PR (`Task.continuedPullRequest`) has no `Task.pullRequest` until the first submission. During that time, the continued PR is watched. The projection then records the continued PR as the implementation PR before recording the merge (the commit is the head of the PR when it was taken over).
  - While Requirements or Design is being redone (the active step is not Implement), nothing is watched. When the task reaches Implement and the PR is already merged, the rework is stopped in the same way.
  - Tasks waiting for approval or escalated are watched by the check above.
- Check: the PR status is read (with the project's gh account; if it cannot be read, the next check tries again). Only when it is merged, the following is done. Nothing is done while it is open or closed.
  1. If something is running, its containers are stopped and the task waits for it to end (the same as pause and cancel; the stopped run is not recorded as a person's pause). If it cannot be confirmed that the stopped containers are gone, the task is paused and does not move on (the next check confirms again).
     Until the approval or the pause is recorded, no run of the task is started (even if the stopped run ended normally, the worker does not start the next verification; `runNext` and `queuedTaskIds` look at `mergeStopping`).
     If the daemon stopped during an implementation run and was restarted, recovery (`recoverInterrupted`) keeps the run of an implementation rework (one with an open PR) in `unstoppedRuns` and pauses the task, so it does not move on to approval until the stop is confirmed.
     Runs whose containers could not be confirmed stopped when the task was paused (`unstoppedRuns`) are included in the stopped runs that are recorded.
     Even if the task had already paused because of the cost of the stopped run that ended normally (the budget, for example), the runs that could not be confirmed stopped are added to `unstoppedRuns` (the pause reason stays as it is; a `TaskPaused` for a task that is already paused is accepted only when it adds `unstoppedRuns`). The task does not move on to approval until they are confirmed.
  2. If, meanwhile, the task reached approval, was cancelled, or changed to another state, nothing is recorded here (a task that reached approval is handled by the check above).
  3. `ReworkStoppedByMerge` (actor `sacty`) is recorded, followed in the same append by `PullRequestMerged` and `StepApproved` (actor `person`; starting the after-merge watch is the same as in "Merged" above).
- Content of `ReworkStoppedByMerge`: the number of the merged PR, the stage when stopped (`was`: `queued`, `running`, `verifying`, `publishing`, `paused`), the stopped runs (`stoppedRuns`), the comments discarded before being passed to the rework (`discardedRemarks`: id and text; the comments of the last rejection that were not passed to a submitted PR), the kind of the discarded verification result (`discardedFeedback`: `tests`, `review`, `merge`, `incomplete`, `unchanged`), and the number of PR comments that arrived while paused and had not been applied (`discardedReview`; when `decision: true`, it is the number of marked findings of the paused round, and comments a person wrote after the pause are not counted; [Comments that arrive while paused](#comments-that-arrive-while-paused)), and whether it was a merge of a PR paused waiting for a human decision (`decision: true`; [Pausing on findings a rework cannot resolve](#pausing-on-findings-a-rework-cannot-resolve)). The reason is the merge.
  - The projection returns the task to waiting for the Implement approval (the gate's submission is the number of submissions so far, or 1 if there is none), voids the discarded comments, and clears the verification, the wait for PR creation, and the pause state. The following `PullRequestMerged` and `StepApproved` then approve it.
  - The body of the approved result (`approved.implement.output`) is the latest implementation report on record. The commit of the PR is the truth for what was merged.
- Just before the PR is updated (`publish`, including updating a continued existing PR), it is also checked whether the earlier PR has been merged. If it has, nothing is pushed and no PR is created; the same records approve it (for when the PR update starts before the check).
  If it is found merged by the check after the push (the check for whether to create a new PR, or the check of a continued PR), no new PR is created and the task is not paused either; the same records approve it (for when the PR is merged during the push).
- Later checks do not record again, because the task is already approved.

Code: `apps/daemon/src/service.ts` (`checkReworkMerges`, `stopReworkForMerge`, `endReworkByMerge`, `mergeApprovalItems`, `publish`, `pauseIfRequested`), `packages/core/src/projection.ts` (`reworkingPullRequest`, `unreflectedImplementRemarks`, `ReworkStoppedByMerge`)

### Comments that arrive while paused

Related ADR: [一時停止の間に届いた PR の指摘を、再開のときに取り込む](../adr/20261102-1900-superseded-hold-pr-comments-while-paused.md)

If a person writes comments on the implementation PR while the implementation rework is paused (for any reason: the budget cap, the AI usage limit, an authentication error, an error, or a person's pause), the comments are kept as not yet applied. After the task is resumed, they are applied before the step that stopped runs again.
The task is not waiting for approval, so "Importing PR comments" above does not run. The judgment is the same (the step to redo is decided by whoever decides it in "Importing PR comments" below).

- Targets: the same PR as in [Merging during a rework of the implementation](#merging-during-a-rework-of-the-implementation) (`reworkingPullRequest`). That is, tasks whose active step is Implement and whose implementation PR (including a continued existing PR) is open (or was closed while waiting for approval and then sent back).
  - A task that was paused while Requirements or Design was being redone is not a target. Comments that arrive then are imported as usual once the task reaches Implement and waits for approval.
- Keeping (`checkHeldFeedback`, `holdFeedback`): the PR check (every minute) reads the feedback on the implementation PR of paused (`paused`) tasks and records what has not been imported as `PullRequestReviewImported` (`held: true`).
  - They are marked as imported (`importedFeedback`) and added to `Task.pendingReview` (the same "imported but not yet applied comments" as for the import while waiting for approval). Comments are added to it, so comments that arrive in several batches become one. The limit (50 comments in total that are not yet applied) is the same as for the import while waiting for approval. A comment is not cut by length (PBI-413). While 50 are kept, a check cannot add any (the number that can be added is 0). The excess is not marked as imported; it is added after the kept comments are applied (by the usual import once the task waits for approval, or by the check if the task is paused again).
  - It does not wait for the writing to finish (they are applied on resume, so comments that arrive meanwhile can still be added).
  - It does not request changes, does not decide the step to redo, and costs nothing. The task stays paused.
  - sacty's own AI review comments are told apart from people's comments, as in [AI review comments](#ai-review-comments). `items[].source` of `PullRequestReviewImported` and `pendingReview.aiReview` are kept, and a batch of only AI review comments has actor `sacty`. Reviews of an old head are not kept; they are discarded with `PullRequestReviewDiscarded`.
  - If the PR feedback cannot be read, nothing is recorded and the next check tries again.
  - While there are comments whose step to redo has already been decided, none are added. After the resume (waiting to run or waiting), the check for paused tasks adds none either (nor when the resume happens while it is reading; only the applying side adds, so that it does not disagree with the judgment made after the resume).
  - If another check running at the same time (the check for paused tasks and the check after the resume) tries to discard the same AI review of an old head, only what is not yet imported is recorded (nothing is recorded twice).
- Screen: the details of a paused task show the number of comments that arrived (with the AI review breakdown) and what happens on resume (`HeldReviewNotice`; `heldReview`). The import row in the activity says the comments arrived while paused and were kept as not yet applied.
- Applying (`reworkHeldReview`): when the resumed task runs next (the start of `runNextInner`), before the step that stopped (the PR update, the implementation, and so on). A task that was stopped in an earlier version while waiting for the CI of the PR opened before the final review, and so is outside the wait for verification, also counts as waiting to run for applying (`heldReviewDue`; `queuedTaskIds`).
  1. Right after the resume, the PR feedback is read once more and kept (to pick up comments written just before the resume; `heldRecheck`. It is in memory only; even if a restart loses it, the comments kept so far are in the activity). If it cannot be read, or the head that the AI reviews were made against cannot be confirmed, the task waits without running the step that stopped until it can be confirmed (the cause is logged as a warning with the task and the PR, with the token hidden; the mark is kept and it is read again in the next cycle), so that comments written just before are not dropped.
  2. If there are no comments that are not yet applied, nothing is done and the step that stopped runs again as before.
  3. If the PR is already merged, nothing is applied (no judgment, no request for changes). The step that stopped is not run either; the merge is taken as the approval on the spot, with the same records as the [rework stop](#merging-during-a-rework-of-the-implementation) (`ReworkStoppedByMerge`, `PullRequestMerged`, `StepApproved`; the kept comments are discarded; `endHeldByMerge`). If another rework stop is in progress (`mergeStopping`), it is left to that one.
  4. If the budget cap has been reached, the judgment is not run and the task is paused for the budget (the same check as before running a step; judging costs money). Otherwise, sacty decides where to send the task back and the cause (`ReworkJudged`; the same judgment and instructions as [Importing PR comments](#importing-pr-comments), reading the implemented code). If the judgment cannot be adopted (the run was stopped by a pause, a rework stop (a PR merge), or the daemon stopping, the task was cancelled, or the comments or state changed), the judgment is not kept; only the cost and usage of the run are recorded in a `ReworkJudged` with `runResult: interrupted` (the comments stay unjudged and are judged again on resume). If it cannot judge, the implementation is redone. If every held comment asks for nothing (`noRework`), the task is not sent back and the stopped step is run again as usual. After the judgment is recorded, the PR status is read again just before sending back; if it is merged, the task is not sent back and the merge is taken as the approval on the spot (if the judged step were Design or Requirements, it would fall outside the rework stop, and the earlier step would run on a merged PR). If it cannot be read again, the task is sent back as it is. Just before sending back (also when a saved judgment is applied after a resume), a cancel, a rework stop in progress (a PR merge), or a pause request is checked; if there is one, the task is not sent back on the stale (still open) response and applying is skipped (the stop discards the kept comments and moves on as an approval).
  5. The task is sent back to the judged step (`ChangesRequested`; `settleHeldReview`). The actor is `sacty` if all the comments are AI review comments and `person` otherwise. The round number and comment IDs continue by the same rule as a send-back while waiting for approval. The progress of the step that stopped (the verification, the wait for the PR update, the wait for a step review) is not carried over. The runs after that are the same as after an ordinary send-back (the implementation is redone with the comments, or the task restarts from an earlier step).
- Number of a person's send-backs: the request for changes is recorded whatever the number (`overLimit` is false).
- A miss (`GuardianMissed`) is not recorded, because the implementation of the step that stopped has not gone through a passing verdict (the final review of an earlier version). The send-back cause (`cause`) is recorded as judged.
- If the PR is merged while paused, the [rework stop](#merging-during-a-rework-of-the-implementation) discards the kept comments (`pendingReview`) and records their number in `discardedReview` of `ReworkStoppedByMerge`.

Code: `apps/daemon/src/service.ts` (`checkHeldFeedback`, `holdFeedback`, `reworkHeldReview`, `settleHeldReview`, `withoutStaleReviews`, `resume`, `heldRecheck`), `packages/core/src/projection.ts` (`heldReview`, `PullRequestReviewImported`, `ChangesRequested`), `apps/web/src/components/task-detail.tsx` (`HeldReviewNotice`), `apps/web/src/lib/labels.ts` (`statusText`)

### Pausing while waiting for approval

Related ADR: [承認待ち（PR のマージ待ち）でも一時停止できるようにする](../adr/20261103-2300-pause-while-awaiting-approval.md)

A person can also pause a task that is waiting for approval (`awaiting_approval`). Use it when you want to stop PR imports while you wait for the merge. A task in escalation (`escalated`) cannot be paused.

- Pausing: there is no agent run, so `TaskPaused` (actor `person`, reason `manual`) is recorded on the spot. The approval gate (`gate`) and the PR records stay as they are, and `resumeTo: awaiting_approval` is kept as where to resume to.
- While paused, the task cannot be approved or sent back (its state is `paused`). What happens to the PR depends on the kind of PR.
  - The implementation PR: it is treated like the PR while the implementation is being reworked (`reworkingPullRequest`). If it is merged, `ReworkStoppedByMerge` (`was: paused`) is recorded, followed by `PullRequestMerged` and `StepApproved`, and the merge is taken as the approval ([Merging during a rework of the implementation](#merging-during-a-rework-of-the-implementation)). No resume is needed. Comments that arrive are kept as not yet applied ([Comments that arrive while paused](#comments-that-arrive-while-paused)). The step to redo is not decided.
  - A Requirements or Design PR: it is not watched while paused. Both merges and comments are handled by the check after the resume.
- Resuming: `TaskResumed` returns the task to waiting for approval (the approval gate is still there, so the approval screen can be used as it is). No agent runs.
  What happened while it was paused is picked up by the PR check after the resume (every 60 seconds).
  - If the PR was merged, the merge is taken as the approval ([The PR check](#the-pr-check)).
  - Comments that were kept (the implementation PR) are taken over by the import while waiting for approval as they are. sacty decides where to send the task back, and sends it back whatever the number of requests (it does not escalate). Comments written while paused are imported in the same check.
- Notification: a person paused it, so nothing is sent to Slack. When it is resumed and returns to the same approval gate, the approval notification is not sent again (`notificationFor`).

Code: `apps/daemon/src/service.ts` (`pause`), `apps/daemon/src/notifier.ts` (`notificationFor`), `packages/core/src/projection.ts` (`TaskPaused`, `TaskResumed`, `resumeTo`, `reworkingPullRequest`), `apps/web/src/components/task-detail.tsx` (`canPause`)

### Pausing on findings a rework cannot resolve

Related ADR: [レビューが直しでは解消できないと印を付けた指摘で止め、人の判断を待つ](../adr/20261121-2000-pause-on-findings-a-rework-cannot-resolve.md)

When the review child task of a PR marks a must-fix finding as "cannot be resolved by a rework (a change to the implementation) and needs a human decision", the parent does not start a rework. It pauses while still waiting for approval and waits for a person.
This applies to every task that has a review child task (implementation, requirements, and design PRs). A round with only unmarked must-fix findings or only suggestions goes into a rework as before.

- The mark: `needs_decision` in `rework.findings[]` of the verdict block (a sentence giving the grounds; cut at 2,000 characters; `ReviewRework.findings[].needsDecision`). The review instruction (`needsDecisionLines`) and the default review skill say when to add it: only when the grounds show it (changing the approach does not resolve it; the acceptance criteria and a constraint conflict); not when unsure; not on suggestions or on findings a person already decided.
- Conditions to stop (`needsDecisionOf`; right after the import, before sorting and the send-back judgment): all of the following.
  - The imported comments contain none from a person (`items[].by` is `person`). `unverified` (neither the PR author nor an OWNER, MEMBER, or COLLABORATOR) and AI reviews (`sacty_review`) do not count as a person. `by` is added at import (`importersOf`; the same criterion as `annotateReviewComments`).
  - Every imported AI review comment is from the last round of the child task, whose verdict is `changes_required` and has a marked finding.
  - A person has not already decided for the head of the PR (`Task.decisionPauses`).
- How it stops: `ReworkJudged` and `ChangesRequested` are not recorded; only `TaskPaused` (reason `needs_decision`, message `review.needsDecision`, `commit` is the head of the PR) is. The approval gate and the imported comments (`pendingReview`) stay, and no rework starts. The findings and grounds have secret values masked and are cut before recording. Each pause is kept in `Task.decisionPauses[]` (head, findings and grounds, the person's decision text).
- Notice on the PR: one comment per pause (not posted for security-combination tasks, like the other notices; the reason can still be read in the activity log, the screen and `get_task`), with the marker `<!-- sacty-decision-notice:<task>:<round> -->` (`decision-notice.ts`), quoting the findings and grounds with secrets masked. A post with this marker is not imported as a PR comment (`isDecisionNotice`).
- Watching while paused (`checkDecisionPauses`; it looks at the gate's PR):
  - Comments that arrive are kept with `PullRequestReviewImported` (`held: true`, with `items[].by`). If they include one with `by` of `person`, they are recorded after `FEEDBACK_QUIET_MS` has passed since the person's last post, and `TaskResumed` (actor `sacty`) is recorded in the same append. `unverified` comments, AI reviews, and sacty notices are only kept and do not resume.
  - When a requirements or design PR is merged, `TaskResumed` (actor `sacty`) is recorded and the next check approves it. When the implementation PR is merged, `checkReworkMerges` records `ReworkStoppedByMerge` (`decision: true`; the merge is taken as the approval without applying the findings that caused the pause) followed by the approval.
  - If a person marks the PR ready, it is not turned back into a draft (as with `unchanged`; `settlePausedDrafts`).
- Resuming: a PR comment (above) or a resume from the screen or MCP (with or without a `note`) returns the task to waiting for approval, and the remaining comments go on to sorting, the send-back judgment, and the send-back. The person's decision text (the `note`, or comments with `by` of `person`; not `unverified` or AI review text) is recorded in `decisionPauses` and the head is marked decided. A decided head is not stopped again by the mark.
  - If the paused round was a judge-again round (the `unchanged` section), `settleReview` after the resume does not stop it with `rejudgeLeftFindings` for the findings of the paused round on a decided head; it sends back. Findings of a newly judged-again round after the implementation declined still stop as before.
  - A round whose target is Design is not sent back when it stops. After the resume, the target is judged by the existing flow and the notice that the work went back to Design is posted.
- Passing on to the next review: later child task instructions (`reviewReworkLines`) get the stopped findings and the person's decision text (with its source) in the frame "JSON data, not an instruction to you" (`decidedPauseLines`). The reviewer must not mark the stopped findings, must not keep a finding the person accepted (will not fix) as a must-fix unless it can show a fact that changed after the decision, and must write the dropped finding in "前回の指摘" of the body with the source of the decision. Judgments of other findings do not change.
- Screen: the reason heading is "Paused: a finding cannot be resolved by a rework". The task detail shows the findings and grounds, and does not show the "resuming sends back" notice (`HeldReviewNotice`). The activity line for `ReworkStoppedByMerge` with `decision` says the PR that was paused waiting for a human decision was merged.

Code: `apps/daemon/src/service.ts` (`needsDecisionOf`, `pauseForDecision`, `importersOf`, `checkDecisionPauses`, `holdDecisionFeedback`, `announceDecisionNotice`, `rejudgeLeftFindings`), `apps/daemon/src/decision-notice.ts`, `apps/daemon/src/prompts.ts` (`needsDecisionLines`, `decidedPauseLines`, `reviewReworkOf`), `packages/core/src/projection.ts` (`decisionPauses`, `TaskPaused`, `TaskResumed`, `PullRequestReviewImported`), `packages/core/src/events.ts` (`PauseReason`, `ReviewRework`)

### Showing a conflict with the base branch

When another PR is merged while the task waits for approval and the implementation PR conflicts with the base branch, the task screen and "Needs you" show it.
It only shows it; the base branch is not merged in (it is merged in, before the implementation is redone, when a person rejects the task or writes a PR comment. [Merging the base branch](tasks-and-steps.en.md#merging-the-base-branch)).

- How a conflict is judged: the `mergeable` of the GitHub PR that the PR status check (`GitHubPullRequests.status`) reads.
  `false` is a conflict and `true` is no conflict. While GitHub is still computing it (`null`), or when it cannot be read, the answer is unknown and the earlier record is kept (`mergeable` of `PullRequestStatus` is present only for `true` and `false`).
  It is part of the one request that reads the PR status, so the number of requests to GitHub does not grow.
- Recording: it is recorded with actor `sacty`, only when the conflict changes. The same state is not recorded twice.
  - Conflicted: `PullRequestConflicted`. It is held in `Task.pullRequestConflict` (the PR number, the commit of the submission at that time, and the time).
  - Resolved (a person fixed it on GitHub, or the base branch went back): `PullRequestConflictResolved`. It clears `Task.pullRequestConflict`.
  - Only the implementation PR of a task in `awaiting_approval` is recorded. The Requirements and Design PRs (PRs to the task branch) and escalated tasks are not.
  - Nothing is started: no run, no merge, no PR update, and no write to GitHub.
- When it is shown (`pullRequestConflict`): the task is waiting for approval, the PR of the Implement gate is open, the recorded PR number and commit are the same as the current submission, and the step to redo for PR comments is not being decided (`pendingReview`).
  - The record is cleared when the PR is created again or updated (`PullRequestPublished`), and when it is merged, closed, or reopened (`PullRequestMerged`, `PullRequestClosed`, `PullRequestReopened`).
    When it is reopened, the next check looks again.
  - It is not shown once the task is rejected and no longer waits for approval.
- Where it is shown:
  - The status text (`statusText`) becomes "Implement PR conflicts with the base branch". It is the same in "Needs you" on the dashboard, in the header notifications, and in the task list and details. The task still needs you, and the row in "Needs you" opens the PR.
  - The rows of "Needs you" (the dashboard, and the cards above the task list) carry a note on how to merge the base in ("Send it back or comment on the PR to merge the base branch in"; `AttentionRow.note`, `NeedsYouCard.note`). The header notifications show only the status.
  - The waiting-for-approval notice in the task details and the PR block of the approval screen explain how to merge the base in (send the task back with a comment from this screen, or write a comment on the GitHub PR).
  - For a continued PR (`Task.continuedPullRequest`, which `mergesBase` does not merge into), the same places show how to resolve it on GitHub ("This is a continued PR, so the base branch is not merged in. Resolve the conflict on GitHub") instead of how to merge the base in. The conflict itself is shown as usual.
  - The Activity shows "PR #N conflicts with the base branch" and "The conflict on PR #N is resolved".
- The judgment does not decide whether the PR can be merged. If a person merges it while it conflicts, it is approved as a normal merge.

### Showing a CI failure after no findings

sacty does not wait for the PR's CI, and takes the PR out of draft when the review child task of the PR has no findings ([The flow without the final review](tasks-and-steps.en.md#the-flow-without-the-final-review)).
So when CI that was still running at the time of the review, or CI started by taking the PR out of draft, fails later, the task stays waiting for a person's approval (the merge). So that a person can notice, sacty reads the CI of the head commit of an implementation PR that waits for a person's approval, and when it was failing, shows it in the task details and on the task's row in the task list (PBI-364, PBI-371). When CI passes while sacty is still reading it, the notice is cleared (PBI-375).
It only shows it; it starts no run, no sending back, no re-review, no change to draft, and no CI rerun. To keep the mechanism small, it does not keep reading CI.

- What is read: at the end of the PR check (every 60 seconds; `checkPullRequests`), the CI state (`CiStatusReader.snapshot`; workflow runs, checks, commit statuses, and the jobs inside workflows) of the head commit of the PR (the current head on GitHub; when it cannot be read, the head that had no findings `reviewedCommit`, and when there is none, the submitted commit).
  - The target is an open implementation PR that waits for approval (`awaiting_approval`) and does not wait for the review child task's no findings (`watchesPullRequestCi`). It is not read for requirements and design PRs, while the step to send PR comments back to is being decided, or during an escalation. It is not read either when there is no CI reader (`ServiceDeps.ci`).
  - One round of the PR check reads only one PR. The candidate is looked for in order, starting after the task read last. When the request of the previous read has not ended, nothing is read.
  - For each head commit, it is read at most `PR_CI_READS_MAX` (12) times, `PR_CI_READ_INTERVAL_MS` (5 minutes) apart (about one hour after the first read when read in a row; an unsettled head has its remaining reads after it was unsettled, which can be more than one hour after the first read). The count is kept in the daemon's memory (`pullRequestCiReads`; counted again after a restart). The count of a task whose implementation PR is no longer open (merged, closed, or cancelled) is forgotten. A round that could not read the PR state temporarily does not restart the count.
  - Reading stops when no failure is shown and there is at least one CI item and everything finished without a failure, when the failure notice was cleared (both are "settled"), or when the count reaches the limit.
  - A head is settled only by a read that is at least `PR_CI_SETTLE_MS` (5 minutes; the same as the interval between reads) after both the first read of that head and the time sacty took that PR out of draft (`notePullRequestUndrafted`; taken out on no findings, taken out again, or taken out when a stacked PR was retargeted) (PBI-381). CI started by taking the PR out of draft may not be in the list yet right after that. A read before that is followed by another read after the interval even when there is no failure (that read also counts toward the limit).
    - When sacty takes the PR out of draft after a head was settled, the head is unsettled and read again (for a commit a person added after the draft was removed, whose CI was settled during the re-review). The count of reads does not start again, so a head whose count reached the limit is not read.
    - The time the draft was removed is kept in the daemon's memory (`pullRequestCiUndrafted`). After a restart, the time is counted from the first read of that head.
  - After a failure was recorded, CI is still read at the same interval within the same limit (the read that recorded the failure counts toward the limit). A read that fails or does not answer within `PR_CI_TIMEOUT_MS` (15 seconds) also counts as one (the reason goes to the daemon log; the token is redacted).
- Record: when there is a failure, `PullRequestCiFailed` (the PR number, the head whose CI was read `commit`, and the failed checks `checks`) is recorded once per head commit, with actor `sacty`. It is kept in `Task.pullRequestCiFailure` (the PR number, the submitted commit at that time, the head read `head`, the checks, and the time it was read).
  - What counts as a failure is the same conclusions as [After-merge watch](deployment-watch.en.md) (`isFailedCiCheck`). A check is a name and a link; the same name and link become one, up to `PR_CI_FAILED_CHECKS_MAX` (10) are kept, and only the count (`more`) is kept for the rest. A name is at most `PR_CI_CHECK_NAME_MAX` (200) characters. Only `http` and `https` links are kept.
  - When the state, the PR, or the commit changed while reading, nothing is recorded.
  - The record is cleared when the PR is recreated or updated (`PullRequestPublished`), merged, closed, or reopened (`PullRequestMerged`, `PullRequestClosed`, `PullRequestReopened`).
    - For a PR recorded as closed, the count of reads is forgotten too. When it is reopened, even the same head is read from the start, and when it is failing, it is recorded again.
- Clearing: when CI read while a failure is shown has passed, `PullRequestCiRecovered` (the PR number and the head whose CI was read `commit`) is recorded with actor `sacty`, `Task.pullRequestCiFailure` is cleared, and that head is no longer read (a read while the head cannot be settled yet only clears the notice, and the head is read again after the interval; when that read finds a failure, `PullRequestCiFailed` is recorded again).
  - CI has passed only when the CI list was read completely (not `CiSnapshot.truncated`) and the list (workflow runs, checks, commit statuses, and jobs) satisfies `ciAllPassed`: it is not empty, everything finished, every conclusion is `success`, or `skipped` or `neutral` (for a commit status, only `success`), and at least one is `success`.
  - The notice is not cleared when there is any cancelled (`cancelled`), stale (`stale`), or running item or an item without a conclusion, when the list is empty, or when the list could not be read completely (cut off at the page limit, or a next page could not be followed). Until the count reaches the limit, it is read again after the interval.
  - When a person added a commit to the PR and the head changed, the failure shown for the previous head is also cleared when the new head's CI passes (`commit` in the record is the head that passed). When the new head's CI is failing too, `PullRequestCiFailed` is recorded again for that head.
  - While CI on the same head keeps failing, nothing is recorded again. The recorded list of failed checks is not updated.
- Where it is shown (`pullRequestCiFailure`; the task waits for approval, the PR of the implementation gate is open, the PR number and commit of the record are the same as the current submission, the step to send comments back to is not being decided, and it does not wait for no findings):
  - The notice of the wait for approval in the task details shows the head commit whose CI was read and the time, that the current result should be checked on the PR, that sending the task back or commenting on the PR has it fixed, and the list of checks that were failing (as links when they have one; the count for the rest). The hint of the notice says that the notice clears when CI passes while sacty is still re-reading it, and that sacty re-reads up to 12 times per head commit of the PR (usually within about an hour of its first read), so later results are not reflected.
  - The status column of the task's row in the task list gets a "CI failed" mark (an icon and text) (`TaskRow.ciFailed`). The hint of the mark says that it is the result when Sacty read CI, that it clears when CI passes while Sacty is still re-reading it, that Sacty re-reads up to 12 times per head commit of the PR (usually within about an hour of its first read), so later results are not reflected, and that the task details list the checks that were failing. The status text and tone (`statusText`, `statusTone`) do not change, so the filters and the order of the list do not change.
  - The activity shows "CI was failing on PR #N". In the error report it is classified as a failed check (`check`) ([Error report](error-report.en.md)).
  - When the notice is cleared, the activity shows "CI passed on PR #N. The CI failure notice was cleared" (the error report does not count it as a failure).
- What it does not do:
  - Changes after reading stopped are not read or reflected (when a person reruns CI and it passes after the count reached the limit, the notice in the details and the mark in the list stay until the PR is updated, merged, or closed; the details show the time it was read, and the notice and the mark in the list have a hint, to make clear that it is the result at that time). CI is re-read only for the rest of the period that started with the first read of that head, so when the last read found the failure, it is not read again.
  - The period and the count of reads are not extended while a failure is shown. After a daemon restart the count starts again, so a head whose failure is shown is read again up to the limit.
  - The status text and tone (the task list, the dashboard's "Needs you", the header notifications) do not change. The list cannot be filtered by the mark. The dashboard, the "Needs you" cards, and the header notifications show no mark. No notification (Slack, desktop) is sent either.
  - CI that has not finished when the count reaches the limit (about one hour after the first read when read in a row), CI that starts after that, and CI that is rerun and fails after the head was settled (including after the notice was cleared and the head was settled) are not picked up (after a daemon restart, it is read again).
  - CI started by taking the PR out of draft is not picked up when it is not in the list `PR_CI_SETTLE_MS` after the draft was removed. CI started by a person taking the PR out of draft on GitHub is not picked up when it starts after that head was settled (unlike when sacty removes the draft, the head is not unsettled).
  - When listing CI was cut off at the limit (the page limit of `GitHubCiStatus`; 1,000 items per list), the part that could not be read is not looked at. A failure in the part that was read is recorded, but the notice is not cleared even when everything that was read has passed.
  - The verdict is not about whether it can be merged. When a person merges while CI is failing, it is approved as a normal merge.

## PR body and PR template

Related ADRs: [Fill the body of PRs sacty opens with fixed rules following the headings of the repository's or Org's PR template](../adr/20261014-1517-pr-body-follows-repository-template.md)

Whenever sacty opens or updates a PR, it looks for the PR template of the repository where the PR is opened, and if there is one, writes the body in the shape of its headings and items. This covers the implementation PR and the requirements and design PRs (the same goes for PRs of fix tasks created by the after-merge watch).

If there is no template or it cannot be used, sacty uses its own fixed body (`buildPullRequestBody`, `buildStepPullRequestBody`). In either case, opening the PR does not stop.

### Assembling the implementation PR body

The implementation PR body is written to be read short, conclusion first. The full text of the approved requirements and design, and long review text, are not included; they become a link or a collapsed section. The fixed body (`buildPullRequestBodyText`) contains, in this order:

1. The task ID line, and `Closes #<number>` (for a task taken in from an Issue)
2. "結論" (Conclusion)
   - Summary of the change: the head of the first paragraph (only lines without indentation; excluding headings, tables, code blocks, and indented lines) of the Implementation step's output. When there is no output, the line is left out. After a redo, the head of the description of the whole PR (see "Body after a redo" below).
   - The last fix: only after a redo, the head of the description of the last fix.
   - The record that a person moved the task on despite a failed final review of an earlier version, and the failed points (the failed viewpoints and the summary in one line as "最終レビューの所見"; if any; [A person moves it to review](tasks-and-steps.en.md#a-person-moves-it-to-review); `overrideBodyLines`)
   - What a person should confirm (if any; `humanCheckBodyLines`). One item is up to 1,000 characters and the list up to 6,000 characters. For an item that was cut and for items that did not fit, it gives the count and says the rest is in "省いた続き" (the omitted rest).
   - The risk assessment is not put in the body (PBI-429; the assessment goes into the PR review comment and the UI; [PR risk assessment](risk-assessment.en.md#how-it-is-shown)). An assessment record from before the version upgrade is not put in either.
3. "レビューの進め方" (How the review goes; `reviewGuideItems`; PBI-450)
   - It is a section outside the conclusion, one sentence per item, without parenthetical notes. The conclusion holds only the change, the last fix, and the lines that cannot be left out (the record of moving on despite a failure, and what a person should confirm).
   - The items are these five.
     - "Sacty のレビューの子タスクが、この PR をレビューして投稿します。" (the review child task reviews the PR and posts the review; `REVIEW_BODY_LINES`)
     - Sacty fixes any findings and removes the draft once there are no findings.
     - Sacty does not run tests or wait for CI, so the CI result is to be checked in this PR's checks.
     - "AI のレビュー：…": whether a Sacty AI review is attached to the current head ("Whether the current head has an AI review" under [AI review comments](#ai-review-comments); `aiReviewBodyLines`).
     - "この状況は本文を書いた時点のものなので、最新の状況はこの PR のレビューの欄で確かめてください。" (this state is as of when the body was written, so check the latest in this PR's reviews; `AI_REVIEW_STATUS_NOTE`)
   - The verdict and findings of an earlier version's final review are not put here either.
4. The omitted rest (if any; `omittedContinuationLines`; PBI-450)
   - The full text of the human-check items that were cut or did not fit, the full text of a cut summary, and the rest of a cut child-task content go into the collapsible section "省いた続き" (HTML comments are removed, `<details` is neutralised, and a zero-width space is put after the `@` of `@name`; a summary and a child-task content are quoted; one text is capped at 12,000 characters). The reader is never told to check the rest on a screen.
   - One text is up to 12,000 characters; the part beyond that is replaced by a sentence giving the omitted count and saying the body has a length limit.
5. The approved requirements (the bug reproduction for a reproduce task; `approvedBasisLines`)
   - The head of the first paragraph and where the full text is (`approvedBasisDigest`).
     - With requirements and design PRs approved by merging, the URL and file path of those PRs. The form of the links is as in "Links to earlier steps' outputs" below.
     - With no such PR, the full text is made readable inside the PR: it goes into `<details>` "全文" in the body. When putting it in would push the body over the limit (65,000 characters), the full text goes into Sacty comments (see "The full-text comment of the requirements" below) and the body links to that comment.
     - The full text is put in with secrets and internal paths hidden, HTML comments removed, and `<details` and `</details>` turned into `&lt;details` and `&lt;/details>` (case and spaces do not matter), and a zero-width space put after the `@` of `@name` (`approvedBasisFullText`; the collapsible section and the full-text comment get the same text; so a marker of a Sacty post or a closing tag in AI-written text cannot break importing, the three-way merge, or the collapsible section).
   - A task that skipped the requirements step, and the fix scope of a security fix, are short, so they stay as before.
6. "変更" (Changes): the Implementation step's output (after a redo, the description of the whole PR) without the first paragraph that the conclusion's change summary already carries (so the conclusion's sentences are not repeated; PBI-301 A7; the F3 recurrence in experiments S16 and S19). When nothing but headings is left (the output is only the summary, or only headings remain), the whole section is left out. When the first paragraph was cut short in the conclusion, the full text is shown. When there is no output, the heading is left out too. When the rest of the output itself starts with a heading (`#` or `##`), the empty "変更" heading is not put in front of it and the output starts from that heading (PBI-302 C2; experiment S2, r5, where "## 変更" was directly followed by "## 変更内容"). In a body that follows a template, "変更" is the full text, because there is no summary in it.
7. "最後の直し" (The last fix): only after a redo. The description of the last fix without the first paragraph that the conclusion's "最後の直し" line already carries (so the conclusion's sentences are not repeated; PBI-302 C2; experiments S2, S14, and S18, r5). When the last fix fits in one paragraph of the conclusion, the whole section is left out (see "Body after a redo" below).
8. The exported results
9. Viewpoint → test → result
   - The table columns are "観点" and "テスト". The viewpoint is the ID and title (up to 60 characters), and the test is the name of the first test (up to 70 characters) and "ほか N 件". Only when there is a record of an earlier version's final review (`lastReview`), the column "最終レビュー" is added, with ✅ or ❌ from its verdict ("（なし）" for a viewpoint without a verdict).
   - Below the table is the test line. When there are tests run in an earlier version's final review (`tests` of `lastReview`) or an earlier version's test result (`lastTests`), it shows that command and result. Otherwise it is "テスト：テストの仕組みが無いリポジトリとして進めたため、テストでは検証していません。" for a task without tests (`noTestsReason`), and there is no test line for others (sacty does not run the tests).
   - Each viewpoint's input, expected result, and all tests (and, with a record of an earlier version's final review, its verdict and findings) go into the collapsed section "観点ごとの詳細" outside the table. The summary of the final review is not shown here, so the findings are shown as they are (the summary appears only in the "最終レビューの所見" line of the record of moving on despite a failed review).
   - Test names are shown after the same test is reduced to one and format characters are replaced with a mark (`displayTestNames`; PBI-302 C3; experiment S18, r5, where the same test appeared twice with and without the describe prefix, 5 of 10 rows were duplicates, and `%j` was shown as a format). Names with the same file and the same test name whose describe chain is the tail of another's (the name with the prefix left out) are merged into the longer one, placed where that test first appears (the earlier of the short and the long name; tests with the same name under different describes, or in different files, stay separate). The separators are `›` and ` > `; names that differ only in the separator or whitespace are the same test, and the first spelling is kept. The format characters of a parameterized test name (`%s`, `%d`, `%i`, `%f`, `%j`, `%o`, `%O`, `%p`, `%#`, `%$`) are not expanded, because the values cannot be known from the name alone; they are replaced with `‹…›` (`%%` becomes `%`). The screen's viewpoint-test mapping does the same.

For the PR of a child task of a split (including a fix child task), a "この PR の範囲（分割の子タスク）" (scope of this PR) section is put between 4 and 5 (`childScopeBodyLines`; PBI-351).
Related ADR: [State the scope in the PR of a child task of a split, and keep the review from marking out-of-scope items as required changes](../adr/20261116-0036-pr-scope-for-split-child-review.md)

- The section gives the parent task's title, says that this is the PR of a child task of a split (or of a fix child task that fixes integration review comments), and says that what is written as out of scope is not changed in this PR.
- It then carries the child task's content that the task split agent wrote (what to achieve, acceptance criteria, out of scope) as it is, as a quote (`>`), without summarizing (`childScopeOf`).
  The part added from the parent task (the approved requirements and design, the gathered information, and the relation sentence sacty adds) is not included.
- The scope is the one recorded at the split (`Task.childScope`; [Splitting](split-and-integrate.en.md#splitting)).
  For a child task without the record (created before the record was introduced), the original text is read from the records of the split (`restoredChildScope`).
  The record of the original text is the output of the task split agent that decided the child task, which the parent task keeps per split round (`Task.split.outputs`; [Splitting](split-and-integrate.en.md#splitting)).
  The output is read again as a split plan, and the content of the child at the same position in that round's list of child tasks is taken as the original text.
  The original text is not built from the free text of the child task's body or from the parent task's current title and outputs (the parent task's title shown is the current one).
  When it cannot be confirmed that the record is the right one, the scope is treated as unknown and the section is not added.
  That is when the output is not kept or cannot be read as a split plan, when the number or the order of titles of the children in the plan differs from that round's record of child tasks, or when the child task's body does not start with that original text followed by sacty's separator.
- The carried content is up to 8,000 characters (`CHILD_SCOPE_BODY_MAX`). Beyond that, it is cut at a line break and a note gives the omitted character count and says the rest is in the collapsible section "省いた続き". When no line fits in the limit, no quote is shown and only the note is written.
- The section is also included when the body is rebuilt (a redo submission). The length limit of the whole body, secret values, and a body edited by a person are handled as for the other sections (the common rules below).
- It is not put in the PR of a task that has no scope record and whose original text cannot be confirmed from the records of the split (a child task with an unknown scope, above), or of a task that is not a child task of a split.

The common rules are as follows.

- Sentences that report the progress of the work are removed from the Implementation step's output (`withoutProgressReport`). The removed sentences are those of 100 characters or fewer that contain both a topic word (commit, push, reflecting to GitHub, and so on) and a state word (not done, incomplete, sacty does it, and so on). Only sentences in lines that are outside a code fence and do not start with whitespace are touched. Lines of code blocks (CommonMark fences: indentation of 0 to 3 spaces, closed by the same character at least as long as the opening), tables, and headings, and every indented line (code inside a list, indented code, and so on), are left alone. The rule does not parse Markdown piece by piece and errs on the side of keeping: one leftover progress sentence does less harm than broken code. The summary of the change (`leadParagraph`) also uses only lines without indentation. The Implementation step's output is saved with the indentation of its first line kept (only blank lines before and after and trailing whitespace are removed; `keepIndent` of `extractBlocks`; other steps still trim as before). The instructions for implementation also say that the notes are put into the PR body as they are and that progress reports are not to be written (`IMPLEMENT_REPORT_LINE`). They also say that the first paragraph goes as-is into the conclusion's change summary, so it is only a summary of what the whole PR changes, with no count or progress of review responses and no result of running checks (PBI-423). The rework run's instructions say the same: keep the first paragraph a summary of the whole PR (reflecting any change to the whole), write the count and progress of responses in the "最後の直し" section, and write the check results in the whole description's verification part with this run's results.
- The leading "合格。" or "不合格。" of an earlier version's final review summary is removed (the verdict is written separately, so it is not repeated as "合格。合格。").
- Paths inside sacty's workspace (such as `/sacty-input/task.md:77`, a path inside the container that a person cannot follow) are not shown in the PR body, in the requirements and design files, in the investigation result comment, in the comments a step requests (`sacty-github-comments`), or in the comment that tells people what to check (`withoutInternalPaths`; PBI-301 A7; experiment S16, where one appeared in the body of a Requirements PR). Input files are replaced with names such as "タスクの依頼" (the task request), "人の指摘" (a person's remarks), "調査の結果" (the investigation result), and "承認済みの要求要件" (the approved requirements); other internal paths (`/sacty-review`, `/sacty-memory`, and so on) are replaced with a name for the place, and line numbers of internal files are not written. Repository paths are not changed. The provenance classification prompt and the default skill `classify-provenance` also have the classifier not write the Input location in the references (`refs`).
- Body after a redo (PBI-299; experiment S5 r4, F44, where after two redos the conclusion, the changes, the verification, and the viewpoint table of the last body described only the last fix, and it was no longer clear what the PR was): however the redo started (a person's send-back or the remarks of an AI review; in earlier versions, also a failed final review), the body written when the PR is updated describes the whole PR at that time.
  - The output of each implementation submission is kept in `Task.implementHistory`, oldest first (built from `AgentRunCompleted` of the implementation; up to 10). It also keeps in `Task.implementBase` the base of the description of the whole PR as of the earlier submissions (none before the first submission; the first submission, or the part other than the section of a submission that rewrote the whole with a "最後の直し" section; a submission without the section leaves the base unchanged; `advanceImplementBase`). The base survives when the history drops old submissions at its limit. Both are emptied when an upstream step such as the requirements or the design is approved again, and when a proposal that changes an approved upstream output is applied.
  - The instructions for implementation (`implementReworkLines`; when the previous description is attached) tell the agent that the description is a description of everything the PR adds (rewrite the previous description with this fix reflected, and fold the content of an earlier "最後の直し" section into the whole), that this fix goes only once in a separate section "## 最後の直し" (`LAST_FIX_HEADING`) at the end of the description, and that the viewpoint-test mapping is also the mapping for the whole PR.
    The same instructions have the agent run the pre-submission verification again on the code after this fix (`REWORK_VERIFICATION_LINE`; PBI-365). The verification results written in the description and in the repository's documents (such as a work record) are only the ones obtained in this run, and results of an earlier round are not written as this round's results. Results of an earlier round left in the repository's documents are rewritten with this round's results, and a verification that was not run is written as not run, with the reason. It is not added to the instructions of the first run.
  - The body splits the description into the "## 最後の直し" section (`splitLastFix`; headings inside code blocks are not read; the section runs to the next heading of the same or a higher level) and the rest. The rest is the description of the whole PR (the summary of the change in the conclusion, and "変更"), and the section is the last fix (the "最後の直し" line of the conclusion and the "最後の直し" section) (`implementDescription`). The body that follows a template puts the description of the whole PR in "変更", followed by a bold "最後の直し" and its text.
  - A submission that wrote only the last fix, without the section, is not taken as the description of the whole PR. The base as of the earlier submissions (`implementBase`) is used as the whole, and the entire description of the last submission becomes the last fix. When there is no earlier submission (the first implementation), the description is left as it is even if it has the section. The body of a task with no redo is the same as before.
  - The viewpoint-test mapping (`Task.testMap`), when there is an earlier submission, lists for each viewpoint in this report the tests mapped up to the earlier submissions first and this submission's tests after them (the same test once; `mergeTestMaps`). A viewpoint to be checked in the diff without tests (`tests` is empty) uses this report as it is. A viewpoint that does not appear in this report keeps no earlier mapping (it stays an unmapped viewpoint and fails the verification as before).
- A long sentence in the conclusion is cut at a sentence break ("。") within `BODY_LEAD_MAX` (240 characters). If there is no break, "…" is added.

### Finding the template

sacty looks on the default branch, and file and directory names are case-insensitive. Once one is found in an earlier position, it is read at that point, and the listings of directories later in the order (such as `docs/`) are not fetched.

1. In the target repository, `.github/pull_request_template.md` → `pull_request_template.md` at the root → `docs/pull_request_template.md`
2. If none exist, the first `.md` by name order (case-insensitive) in the `PULL_REQUEST_TEMPLATE/` directories in the same order (`.github/`, the root, `docs/`). GitHub does not use multiple templates in a directory as the default, but sacty picks one.
3. If the target repository has none, the same locations in the Org's (or user's) `.github` repository (`https://<host>/<owner>/.github`). As with GitHub, only a public one (`private: false`) is used. If private, it is not used and this is noted. If the target is the `.github` repository itself, it is not searched.

A template is judged absent or unusable as follows.

- Treated as absent: a 404 on the repository or directory listing (including empty repositories and repositories that cannot be seen).
- Unusable (`unusable`)
  - A failure other than 404 when fetching a listing or file, a network failure, or a timeout (30 seconds for the whole search)
  - Larger than 32 KiB (`TEMPLATE_MAX_BYTES`; the size is judged from the listing's value without reading the content)
  - Not readable as UTF-8
  - Whitespace only
- If it is unusable in the target repository, the Org's `.github` is not searched.

### Filling the template

`fillTemplate` fills it, and no agent is used.

- The template is split by headings, and the kind is decided from the heading text.
  - Headings are lines `#` to `######` and lines that are bold in full such as `**概要**`. Those inside code blocks and HTML comments are excluded.
  - The kind is decided by matching `CATEGORY_RULES` from the top. The kinds are headings that cannot be filled (checklists, screenshots, breaking changes, other, and so on), related Issues, tests, changes, and purpose/summary.
  - For each kind, sacty's content goes only into the first matching heading.
- Explanations, example text, and code blocks in a heading are removed; HTML comments and checkboxes are kept. All checkboxes are unchecked, even if checked in the template (because sacty has not checked them).
- Headings with no content or that do not apply get "該当なし（Sacty は記入していません）" (Not applicable; Sacty did not fill this in) (`NOT_APPLICABLE`). Headings with checkboxes do not get it (only the unchecked checkboxes remain). Before the first heading, only comments and checkboxes remain.
- Content of the implementation PR (`buildPullRequestBodyParts`)
  - Purpose: that it is the result of a Sacty task, the number of items for a person to confirm (if any, "この PR の末尾にあります" (it is at the end of this PR)), for the PR of a child task of a split the scope of this PR (a bold heading; the content is as in [Assembling the implementation PR body](#assembling-the-implementation-pr-body)), and the approved requirements (the bug reproduction for a reproduce task; the head of the first paragraph and where the full text is, as in the conclusion above)
  - Changes: the Implementation step's output (without progress reports; after a redo, the description of the whole PR followed by a bold "最後の直し" and the description of the last fix)
  - Tests: the viewpoint → test → result table and the test results (the "viewpoint → test → result" item in [Assembling the implementation PR body](#assembling-the-implementation-pr-body))
  - Related Issue: `Closes #<number>` (for a task taken in from an Issue)
  - The exported results and the omitted rest (`omittedContinuationLines`; only a heading, because it is already inside a collapsible section) go into "the Sacty record". The omitted rest goes at the top of the record. The record is in the part that may be cut (main), but the full text of the rest lies outside the list of items a person should confirm.
  - What a person should confirm and the record that a person moved on despite the failure go into the last part (footer).
  - "How the review goes" (the same five items as above, one sentence each) also goes into the footer, before the approval guidance. The footer is never cut and only a fixed-length set of sentences is added, so the approval guidance and `sacty task <ID>` are never cut. The purpose section is limited to the content of the request.
- Content of the requirements and design PRs (`buildStepPullRequestBodyParts`)
  - Purpose: which step's result it is (and the approved earlier steps; the form of the links is as in "Links to earlier steps' outputs" below)
  - Changes: the result's file and the responses to comments
  - Related Issue: `#<number>` (a reference only; merging into the task branch does not close it)
  - There are no tests.
- Content that did not fit into a heading and "the sacty record" are placed at the end of the body in a collapsible section (`<details>`). If no heading could take any content (such as a template without headings), the purpose, changes, and tests are placed without collapsing. If the related Issue does not fit into a heading, it is placed before the last part.
- The last part (footer) always contains the following.
  - A note that sacty created the PR and the task's ID (`sacty task <ID>`)
  - Guidance that merging means approval of that step, and how to give comments (the implementation PR, and the requirements and design PRs)

### The "確認したいこと" section in the requirements and design PR body

sacty reads the 確認したいこと section at the top of the requirements or design output (`readStepQuestions` in `step-questions.ts`) and puts a section in the PR body.
The result of reading is not recorded in the task; the body is rebuilt from the output at that time on every submission.
A question that was answered and left the section also disappears from the body of the resubmission.

- Position: in the body without a template, after the approval guidance and before "## 確かめる所".
  In the body that follows a template, inside the purpose (summary), after the first sentence and the AI review line and before "**確かめる所**".
- Reading the section
  - It starts at the first heading (ATX) or bold label outside code blocks whose name begins with 確認したいこと.
    It ends at a heading of the same or a shallower level (a bold label counts as level 7). The phrase in body text, in a code block, or in 確認しないと決めたこと does not start it.
  - Counts are given only when both a `must` label and a `should` label are found (heading, bold label, or the head of a bullet; case-insensitive).
    The count is the number of items of the shallowest bullet or numbered list under the label. "なし" is 0. When a sentence follows the label and there is no list, it counts as 1.
    When the same label appears twice, no counts are given.
    Each line is judged after removing its leading spaces, bullet mark, and bold (an indented "なし" and `**must**：なし` are read too).
    Everything from 確認しないと決めたこと (including a line where it is followed by `：`, `:`, or the end of the line) to the end of the section is not copied.
    CRLF line breaks are read. A line longer than 2,000 characters is not read as a heading or label.
- Lines in the body
  - With questions: a heading (`## 確認したいこと`, or `**確認したいこと**` in the template form), a first line (the counts, with the meaning of must when there is one), two lines on how to answer (comment on the PR; merging without answering moves on with the recommended answers), and the copied contents.
  - When the counts cannot be given (no must/should distinction, and so on): no counts are written; it says that there are questions for a person to decide, and shows the two answer lines and the contents.
  - When the section is only "なし", or must and should are both "なし": one line, "確認したいこと：なし（must・should とも問いはありません）".
  - When the section is not found (such as an English output; also when the section exists but its contents are empty): one line that does not say "0件" or "なし" and points to the top of the result file.
  - When the output is empty: nothing is added.
- Copied contents
  - Taken from the output after secret values are hidden and internal paths are replaced, and cut at 6,000 characters. When cut, a sentence says so and points to the section in the result file.
  - Raw HTML outside code (`<!--`, `<details>`, and so on) is disabled by turning `<` into `&lt;`, and character references (such as `&#64;`) by turning `&` into `&amp;`. Inside code blocks and inline code, the text is copied as it is.
  - An unclosed code block is closed, and a blank line follows.
  - U+200B is put after `@` and between a closing keyword (`closes`, `fixes`, `resolves`, and so on) and `#`, so no notification is sent and no Issue is closed. For the URL form (`closes https://…`, `closes <https://…>`), it is put before the URL.
- Lines that are not omitted: the counts line and the two answer lines (and the one line for none or not found) stay even when the length limit omits the body (`keep`; `fillTemplate` adds `BodyParts.keep`).
- Right after the "確かめる所" heading, one line is added: it says that this is a check of sources (quotes, derivations, inferences) and that the questions a person should decide appear in 確認したいこと (PR body only; the words "確かめる項目" and the screen are unchanged).
- How merging is treated does not change (a remaining must does not stop the merge; merging without answering moves on with the recommended answers).

### Length, secret values, and the ledger

- Length (`limitBody`)
  - The body is kept to 65,000 characters (`PR_BODY_MAX`). This is a bit shorter than GitHub's limit of 65,536 characters and is measured by JavaScript length.
  - If it is longer, the end of the part before the last part is cut, and one sentence (`truncatedNote`) is written giving the number of omitted characters and GitHub's limit for a PR body (65,536 characters). The reader is never told to check the rest on a screen. HTML comments, code blocks, and collapsible sections left open at the cut are closed.
  - The same limit applies to bodies that do not use a template (`buildPullRequestBodyText`, `buildStepPullRequestBodyText`). The last part (the note that sacty created the PR and the guidance that merging means approval of the implementation) is not cut.
  - The omitted rest (human-check items, summary, and child-task content) and the full text of the approved requirements go into collapsible sections of the body (PBI-450): after the conclusion (main) in the fixed body, and at the top of the Sacty record (main) in a body that follows a template. Only lines with a limit go into the footer.
  - When putting the requirements' full text in would push the body over the limit, a link to the full-text comment is put in place of `<details>` (see below).
  - When a three-way merge of a body edited by a person exceeds the limit and the Orchestrator is asked to reconcile it, the instruction gains "where you cut, put one sentence giving the number of cut characters and GitHub's limit" (`buildPullRequestBodyMergePrompt`). This path does not go through `limitBody`, so this instruction leaves the omitted amount in the body.
  - Parts that cannot be cut (`keep`) are the task ID line, `Closes #<number>` (including one placed in a template heading), the guidance that merging the requirements and design PRs means approval, and, in the fixed body, what a person should confirm and the record that a person moved on despite the failure, both placed in the conclusion. If, after cutting, one of them does not remain in the body as a whole line (with line boundaries before and after) outside HTML comments and code blocks, it is put back before the last part. `Closes #12` is not considered to remain just because `Closes #123` is present.
- Secret values: secret values used in opening that PR (such as the GitHub token) are redacted from the body (`[REDACTED]`). So that the cut-off head of a secret is not left by a summary or truncation (the summary of the change, test names and viewpoint titles in the table, the items a person should check, the findings of an override, and so on), they are redacted from every string of the task before the body is built (`PullRequestBodyStage.secrets`). The replacement just before publishing is kept too. The reason text kept in the ledger is also redacted.
- Links into the container's workspace (`convertWorkspaceLinks`; PBI-366): from the body after the length limit and the handling of secret values, Markdown links and images whose target is the container's workspace (`CONTAINER_WORKSPACE`; `/workspace` and below) are turned into text that is not a link (they can appear in an agent's description, and cannot be opened on GitHub).
  - The link text is kept (for a link, as it was written; for an image, the alternative text). When the link text does not show the path (without what follows `#` or `?`), the path from the workspace (the path from the repository root) is added as inline code in full-width parentheses. When the link text is empty, only the inline code of the path is left. A link to the workspace itself becomes the link text only (when the link text is empty too, it is not changed, because nothing would remain and the text before and after would join across whitespace). An image into the workspace inside a link is also removed.
  - What is a link or an image is decided by a Markdown parser (`mdast-util-from-markdown`; CommonMark), and only that range is replaced. What the parser does not see as a link (inside code blocks and inline code, and escaped brackets) and other links (URLs, relative paths, paths of another name that starts with `/workspace`) are not changed. Reference-style links (and their definitions) and HTML links are not changed.
  - The replacement does not make the body longer (it is done after the length limit). When a path has a run of backticks and the code fence would be longer than the original link, only the link text is left, without the path. When there is no link text either, that link is not changed.
  - The body after the replacement is parsed too, and its syntax tree is checked to be the same as the original tree with "the removed links and images turned into their content (and the added path)" (`shapeOf`; the whole of kinds, values, and children is compared, without positions). When it is not the same, the body is used unchanged (the links into the workspace remain in that body). This is the case for a body where the link text joins the surrounding text into other syntax, such as a new link, an HTML comment or tag, a reference definition, or a list.
  - The syntax tree is checked with the CommonMark reading, so changes that exist only in GitHub's reading (GFM) are not found. So the following links are not changed (the links into the workspace remain in that body). The kinds of runs that could act differently outside a link are written in one table (`ACTIVE_RUNS`), and both the check of the link text and the check of joining use it.
    - A link whose text contains characters that could act differently on GitHub once they are outside a link (`activeOutsideLink`): a mention or an email address (`@` followed by a letter, a digit, `.`, `_`, `-`, or `/`), an issue or PR reference (`#` followed by a digit, or `GH-` followed by a digit; `Closes #12` closes the issue at merge), and an autolink (`://`, `www.`). `GH-` and `www.` are matched without regard to case. Also, a table column separator (`|`), and the strikethrough mark (`~`).
      Both the text as written and the text as read (with escapes and character references resolved; `readLabel`) are checked.
    - A link whose text, once removed, joins the text before or after it (`joinedSpans`): runs of mentions and email addresses, issue and PR references, autolinks, and strikethrough marks are picked up from the body after the replacement (`activeRuns`), and when a run overlaps or touches the replaced text and continues outside it, that link is not changed. This check uses the body with the replaced text turned into the text as read (an escape or a character reference inside the link text is not a run by itself; an `@` or `#` right before the link is hit when it forms a run together with the link text).
      This is the case for `ping [@](/workspace)octocat` (it becomes a mention), `Closes [#](/workspace)12`, `see [http](/workspace)://example.com/x`, and `[a](/workspace/a)www.example.com` (an autolink that was there stops working).
      A backslash escape or a character reference outside the replaced text cannot be read as a run from the text as written, so a stretch of ASCII characters that contains one (ended by whitespace or a non-ASCII character) is treated as a run too. A backslash escape counts only when the stretch has a symbol that can decide a run (`@`, `#`, `:`, `~`, `.`, `-`).
      Even in a Japanese sentence written without spaces, the stretch does not spread over the whole sentence.
      The links that were hit are left out and the replacement is done once more; when a link is still hit, the body is used unchanged.
    - A link whose path (after the link target is read) has a vertical bar: inside a table, the bar in the added path would become a column separator and split the row's cells.
  - Only the kinds above are checked. Other GitHub readings that change when the text joins after the removal are not checked: runs that join across whitespace (`[Fix](/workspace/Fix)es #12` becomes `Fixes #12`), links for commit SHAs, emoji (`:name:`), task list checkboxes, and, inside a table, a row taking the shape of a delimiter row, and a backtick of the added path pairing with an unpaired backtick in the same cell.
  - A body that cannot have a link into the workspace is not parsed (`cannotLinkToWorkspace`): a body without `](`, and a body with none of the workspace path, a backslash, or a character reference (such as `&#115;`). The link target is not read by sacty's own rules; every body that the parser could read as having a link into the workspace is parsed.
  - Parsing and the replacement run in a thread separate from the daemon (`convertOffThread`; PBI-372). Parsing is synchronous and cannot be stopped partway, so it does not run on the daemon's thread. While waiting for the parse, the daemon keeps answering other work (HTTP responses, stop operations, and so on).
    One separate thread is started for each body that is parsed, and it is stopped once the answer arrives (once per creation or update of a PR; when an update of an existing PR uses the body merged with a person's edits or the body an agent reconciled, once more for that body). It is not started for a body that cannot have a link into the workspace (such a body does not wait for its turn either).
  - Only one separate thread runs at a time (`PARSE_CONCURRENCY`). Other bodies wait in the order they came (`inTurn`). Even when slow bodies overlap, parsing uses the CPU and memory of one thread. The memory of the separate thread (the old-generation heap) has a limit (`PARSE_MEMORY_MB`; 128 MB).
  - The wait for the parse has a limit (`PARSE_TIMEOUT_MS`; 5 seconds). The limit is counted from when the body's turn comes and the separate thread is started (the time spent waiting for the turn is not included; with a slow body ahead, the wait is up to 5 seconds for each such body).
    At the body limit (65,000 characters), an ordinary body finishes in 0.1 to 0.3 seconds, including starting the separate thread. When a body that is parsed has symbols (`>`, `*`, `+`, and so on) running up to the limit, parsing takes seconds to tens of seconds, so it is cut off at the limit (the separate thread is stopped). Bodies that will be slow are not told apart by their shape before parsing.
  - When the parse was cut off or failed, the body is used without removing the links into the workspace (creating and updating the PR is not stopped; in that body, links into the workspace remain). A body sacty assembled still has its secret values redacted once more. A body merged with a person's edits and a body an agent reconciled are used as they are.
    A failure is an exception during parsing or the replacement (such as a stack overflow on deep nesting), an error in the separate thread (such as exceeding the memory limit), or the separate thread not starting, ending without answering, or answering with something that is not a body (or is longer than the original).
    That the links could not be removed, and the reason, are written to the daemon's log together with the task ID and the repository (`linksUnlinked`). The reason is the time limit, or a failure and its cause (the name of the exception, the error code, or the exit code; `errorLabel`). It is not recorded in the activity log. The content of the body and the message of the exception are not written to the log.
  - After the replacement, secret values are redacted once more (`unlinkedGeneratedBody`), because a secret value can appear in the already redacted body when a character reference in a link target turns back into its character, or when the text before and after a removed link joins. When the redacted result exceeds the length limit, the replacement is dropped and the body within the limit is used.
  - It is done for both the creation and the update of the requirements and design PRs and the implementation PR. In an update of an existing PR, it is also done for the body merged with a person's edits and the body an agent reconciled (`unlinkedMergedBody`; [Updating a body a person edited](#updating-a-body-a-person-edited)). The body kept in the ledger (`PullRequestBodyWritten`) is also the one after the removal. It is not done for reviews and comments posted to a PR.
- Ledger: `template` in `PullRequestPublished` and `StepPullRequestPublished` keeps the following.
  - The template used (`repo`: the URL of the repository where the template was, `path`)
  - Or the reason for using the fixed shape (`fallback`: `none` or `unusable`; `message`: `pr.templateFailed`, `pr.templateTooLarge`, `pr.templateInvalid`, `pr.templateEmpty`, `pr.templateOrgPrivate`, and so on)
  - `truncated` if it was cut
  - It is shown as "Body" in the PR section of the task screen. Records from before this version do not have it (nothing is shown in the web UI).

- Links to earlier steps' outputs (where the full approved requirements are in the implementation PR, and the approved earlier steps in the requirements and design PRs; `stepArtifactLink`; PBI-322)
  - One line per step: after `- <step>：`, the path of the output file as inline code linked to `<repository>/blob/<commit>/<path>`, then, in full-width brackets, `PR：` and a link to the PR URL (with the text `#<number>`).
  - The file link points to the commit of the merged content (the head commit of the PR; if a person edited and merged it, the person's final commit). Without that record, it points to the commit sacty pushed to the PR. GitHub keeps the head commit of a PR in the PR's ref, so it stays readable after the PR and task branches are deleted. The merge commit is not used, because it may become unreachable once the task branch is deleted.
  - The PR URL is also an explicit link. If full-width brackets or other characters follow the PR URL directly, GitHub's autolink includes them in the URL, opens `/pull/<number>（…`, and lands on the compare page.
  - The path is encoded segment by segment (parentheses too, so the link target does not close early), and the link text is the path as inline code (wrapped in a longer run of backticks if it contains backticks).
  - If the PR URL is not in the form `<repository>/pull/<number>`, the line is the path as inline code and, in full-width brackets, `PR：` and the URL in angle brackets (an autolink). Without a URL, only the path.

#### The full-text comment of the requirements

When there is no requirements or design PR approved by merging and putting the full text in the body would exceed the limit, only the full text of the approved requirements (the bug reproduction for a reproduce task) is split into PR comments (`syncBasisComments`; PBI-450). This lets a reviewer read every acceptance criterion inside the PR even above the limit.

- Marker: the comment starts with `<!-- sacty-basis:<task ID> -->`. The continuation comments start with `<!-- sacty-basis:<task ID>:<number from 2> -->`.
- Splitting: at a line break, in lengths that fit the comment limit (`GITHUB_COMMENT_BODY_MAX`), into continuation comments.
- Each time the body is rebuilt, the same marked comments (posted by the project's account) are rewritten; if there are none, they are posted. A continuation that is no longer needed is rewritten as an empty notice. The comments do not multiply.
- When the PR does not exist yet, the body is created saying "この PR を作った後に、Sacty がコメントに載せます" (Sacty will put it in a comment after this PR is created), the comment is posted right after, and the link in the body is rebuilt.
- The import side recognizes a comment that starts with the marker as a Sacty post and does not import it as a person's comment (`isBasisComment`).
- The full text is put in with secrets and internal paths hidden and HTML comments removed.
- Because the comments are rewritten on every body update, people watching the PR's notifications may get notifications separate from the body update.

#### Product name

The product name in text a person reads (PR bodies, comments, reviews, and replies; the bodies of requirements and design PRs; and the body of an Issue made from a PR comment) is "Sacty" (PBI-450).
Identifiers stay lowercase `sacty`: commands, labels, branch names, markers a machine reads (HTML comments), and `sacty task <ID>` in the body.
The "sacty" in instructions to agents is not covered, because people do not read it.

### Updating a body a person edited

A person may edit the body of a PR that sacty opened on GitHub (adding notes, formatting, rewording, and so on).
When sacty updates an existing PR, it keeps the person's edits and adds sacty's new content.
This applies to the implementation PR (`publish`), updates of the requirements and design PRs (`publishStepPullRequest`), and retargeting a stacked PR (`retargetPullRequest`).
A task that takes over an existing PR never changes the PR body in the first place.

Related ADR: [Merge commits a person added to a sacty PR into the workspace, and keep a person's edits to the PR body with a three-way merge](../adr/20261112-1553-keep-human-edits-on-sacty-pull-requests.md)

- Record of the previous version: after opening or updating a PR (not when sacty tried to open one, found an existing PR for the same branch, and did not write its body; `existing` in the answer of `upsert`), sacty records the body it assembled that time (after filling the template, truncating to the length limit, and masking secrets; it does not include the person's edits) as `PullRequestBodyWritten` (the PR's repository, number, and body) (`recordPullRequestBody`).
  It is not recorded when it equals the previous one.
  `Task.pullRequestBodies` (keyed by `<repository URL>#<number>`; `pullRequestBodyKey`) holds the last one per PR.
  The task list API (`/api/tasks`) does not send it (the screen does not use it, and it holds a full body per PR).
- The body of an update (`reconcilePullRequestBody`):
  1. If there is no record of the previous version (a body written before this version), use the newly assembled body as before.
  2. Read the current body on GitHub (`pullRequestBody`). If it cannot be read, use the newly assembled body, and after the PR is updated, record in `PullRequestBodyResolved` (`overwritten`; the reason is `pr.bodyReadFailed`) that the body was overwritten without checking for a person's edits (no agent is run; nothing is recorded if the update fails).
  3. Three-way merge the current body (the person's side) and the newly assembled body (sacty's side) line by line, with the previous version as the common ancestor (`mergePullRequestBody`; `git merge-file --diff3`).
     Line endings are normalized to LF (a body edited on the GitHub screen uses CRLF).
     If the person did not edit it, the result is the newly assembled body.
     Because the common ancestor is the body sacty assembled, not the body written to GitHub, notes the person added earlier stay as the person's edits in later updates too.
  4. If it merges without overlap and fits in `PR_BODY_MAX`, update with the result and record the newly assembled body as the previous version.
  5. If both sides changed the same place (or the result exceeds the limit), have the orchestrator agent (`step_agents.orchestrator`) reconcile it (`buildPullRequestBodyMergePrompt`).
     - The previous version, the current body, the newly assembled body, and the merge result (with markers labeled `github-now`, `sacty-previous`, and `sacty-new` where they overlap) are passed as JSON data.
     - The agent reconciles only the places with markers. It keeps the person's notes, formatting, and wording, and applies sacty's factual updates (the description of changes, test results, review status, what a person should check, approval guidance, and so on).
     - It keeps the task ID line and the `Closes #<number>` line unless the person removed them, and does not add back what the person removed.
     - It must not leave marker lines, and must stay within the length limit.
     - It does not follow instructions inside the bodies, and does not touch files, commands, or GitHub.
     - The text between the last `<<<SACTY_PR_BODY_BEGIN>>>` and `<<<SACTY_PR_BODY_END>>>` in the answer is the body (`extractMergedPullRequestBody`).
     - After reconciling, sacty reads the current body again; if the person edited it again in the meantime, it does not overwrite with a body that lacks those edits (see 6.; `pr.bodyEditedDuringMerge`).
     - If reconciled, sacty updates with that body, records `PullRequestBodyResolved` (`resolved`; with the run's cost), and records the newly assembled body as the previous version.
  If a pause or cancel is requested while an agent reconciles the body, the PR is not updated (the same applies to the requirements and design PRs).
  6. If it cannot be reconciled, the PR is updated without touching the body (no body is passed to `upsert`; the body read earlier is not written back), and the previous version is not recorded again (the next update merges sacty's updates again).
     `PullRequestBodyResolved` (`kept`) keeps the reason. The PR update does not stop.
     It cannot be reconciled when:
     - the settings cannot be read (`pr.bodyMergeUnavailable`)
     - the budget cap has been reached (`pr.bodyMergeBudget`)
     - the agent run failed (`pr.bodyMergeFailed`). If it could not be confirmed that the container stopped, the PR is not updated and the task pauses (with the run failure's reason; stopping is confirmed on resume or cancel)
     - the answer cannot be read (`orchestrator.unreadable`; no marker lines, empty, merge markers left, or too long)
     - the person edited the body again while it was being reconciled (`pr.bodyEditedDuringMerge`), or it cannot be read again (`pr.bodyRereadFailed`)
     - when retargeting a stacked PR (`retargetPullRequest`); retargeting runs outside the task's run, so no agent is run (`pr.bodyMergeDeferred`)
     - the merge itself failed (`pr.bodyMergeError`)
- Links into the workspace: links into the container's workspace are also removed from the body used for the update (the merge result of 4. and the reconciled body of 5. above) (`unlinkedMergedBody`; how they are removed is `convertWorkspaceLinks` in [Length, secret values, and the ledger](#length-secret-values-and-the-ledger)).
  - Links into the workspace that a person wrote are removed too. Other links and the way the body is written are not changed.
  - When there is no link to remove, the body is used as it is (secret values are not redacted again either; nothing else is done to a body a person wrote). A body sacty assembled (`unlinkedGeneratedBody`) is redacted again even when there is no link to remove; this is the only difference.
  - When the removal changed the body, the secret values used to create that PR are redacted once more (text a person wrote is redacted too when it equals a value). When the redacted result exceeds `PR_BODY_MAX`, the removal is dropped and the body before the removal is used.
  - When the parse was cut off or failed, the body is used as it is (secret values are not redacted again either), and that the links could not be removed is written to the log.
  - What is recorded as the previous version is still the newly assembled body.
- Cost: the cost of `PullRequestBodyResolved` is charged to the task budget (`CHARGED_EVENT_TYPES`). In the per-step cost table, it appears in the orchestrator row.
- In the activity log: "Wrote the body of PR #…", and whether an agent reconciled it or could not (with the reason).

Code: `apps/daemon/src/service.ts` (`reconcilePullRequestBody`, `recordPullRequestBody`, `publish`, `publishStepPullRequest`, `retargetPullRequest`), `apps/daemon/src/pr-body-links.ts` (`unlinkedMergedBody`), `apps/daemon/src/pr-body-merge.ts` (`mergePullRequestBody`, `buildPullRequestBodyMergePrompt`, `extractMergedPullRequestBody`, `hasMergeMarkers`), `apps/daemon/src/github.ts` (`pullRequestBody`), `apps/daemon/src/server.ts`, `packages/core/src/events.ts` (`PullRequestBodyWritten`, `PullRequestBodyResolved`), `packages/core/src/projection.ts` (`pullRequestBodies`, `pullRequestBodyKey`), `packages/core/src/cost.ts` (`CHARGED_EVENT_TYPES`), `apps/web/src/lib/step-costs.ts`, `apps/web/src/lib/labels.ts`

## Importing PR comments

- While a PR is open and waiting for approval, its reviews, line comments, and ordinary comments are imported as comments (`PullRequestReviewImported`, actor `person`; actor `sacty` for a round of sacty's own AI review comments only).
  - They are imported after waiting 2 minutes from the last feedback (`FEEDBACK_QUIET_MS`).
    The wait is counted from the newest not-yet-imported feedback that is a person's comment (one whose `source` is not `sacty_review`).
    A post by sacty's own review is written in one go (body and line comments), so it is not waited for and does not extend the wait.
    When the only not-yet-imported items are posts by sacty's review, they are imported by that check without waiting.
    When a person's comment is mixed in and 2 minutes have not passed since the newest one, sacty's review waits with it (they are not imported separately).
    The time of each feedback is the earlier of its GitHub time and the time the daemon first saw it (memory only; `feedbackSeenAt`).
    Even if GitHub's time is ahead of this machine's clock, the feedback is imported 2 minutes after it was first seen (it does not keep waiting for GitHub's time).
    If GitHub's time is behind, there is no wait when 2 minutes have already passed by the time it is seen.
    The times for tasks that are no longer in scope for import (no longer awaiting approval, cancelled, and so on) are dropped at the next check.
  - Import right after a post: right after a review child task records `PullRequestReviewPosted`, the parent's import starts without waiting for the 60-second check (`importFeedbackSoon`).
    Only when the parent is waiting for approval, the PR is open (the child's PR and the parent's PR are the same), a review is not being processed, and no cancel or pause is requested.
    The content of the post is not passed from the child; it is read from GitHub. When it could not be imported (GitHub does not return the post yet, or it cannot be read), only a warning is logged and nothing is recorded on the child or the parent. The 60-second check imports it.
  - Imports run one after the other per parent (key `feedback-import:<parent ID>`). The later one removes the already-imported keys from the ledger recorded by the earlier one before recording (the same key is never imported twice).
  - Up to 50 (`REMARKS_MAX`) are imported, oldest first. The body of a post (a summary, a person's review, a PR comment, a line comment) becomes the comment text without being cut by length (up to the 65,536 characters GitHub allows in one post; PBI-413). The 2000-character limit for a person sending changes back on the screen or API is for comments a person writes and is not applied to imported ones (the import while waiting for approval and `decideDeferrals`, which decides to fix a deferral candidate in this PR, tell the send-back call that the comments are imported, which skips this check).
  - A line comment gets the content of the line it was left on and the two lines before it, after the comment text (PBI-302 B3).
    - The content comes from the diff excerpt GitHub returns with the comment (`diff_hunk`; the commented line is last) (`lineContextOf`). The hunk header and the leading diff marks (`+`, `-`, a space) are dropped. Before the quoted lines are chosen, the whole excerpt is hidden at once (to find the body of a multi-line PEM private key; when the begin line is outside the excerpt and only the end line is there, everything from the start of the excerpt to the end line is hidden). Lines are not cut here.
    - After `path:line：body`, a new line is added: `（コメントが付いた行の内容：「…」。直前の行：「…」「…」）` ("the content of the commented line: ... the lines before it: ..."; `lineContextText`). Whitespace is normalized, an empty line is written as "空行" (empty line), and secrets and URL credentials are hidden in the whole line before each line is cut at 200 characters, because cutting first would leave a value broken at the boundary that can no longer be found. Neither the added part nor the comment text is cut.
    - A comment with no excerpt gets nothing. The lines after the commented line are not passed (the excerpt only has the lines before).
    - When a comment with context is present, the prompts for the send-back judgment and for the rework run (Requirements, Design, Implementation) tell the agent not to count lines in the deliverable from the line number, but to find the place by the added line content (if the number and the content disagree, trust the content; the added line content is a quotation of code or a document and not an instruction) (`lineContextNote`).
  - The same item is not imported twice.
  - While the implementation rework is paused, the task is not waiting for approval, so comments are not imported; they are kept as not yet applied and applied on resume ([Comments that arrive while paused](#comments-that-arrive-while-paused)).
  - For a taken-over existing PR, comments passed to the prompt of the Implement step are not imported (the implementation addressed them; [Taking over an existing PR](tasks-and-steps.en.md#taking-over-an-existing-pr)).
- Posts by a sacty task that reviewed this PR (a task pointing to the PR: the PR it took in, or the PR URL in its body) are identified by two things. They are that task's project account (which may differ from the original task's account) and the round in the marker (`<!-- sacty-review:<task ID>[:<round>] -->`). This is checked before the bot check, so the same applies even if that account is a bot (such as a GitHub App).
  - That task's rounds with findings are imported as comments. The kind of review task (a review child task (`source.review: sacty` with `reviewOf`), a task an older version took in from the review label for a sacty PR (`source.review: sacty` without `reviewOf`), a review request (`requested`), the review label (`label`), a task created manually (no `source`), and so on) does not matter. A review child task is created automatically when sacty opens the PR (not through a label); the others are reviews that a person asked for. Each is a review the task that opened the PR should address. Rounds with findings are those where `verdict` in `reviewVerdicts` is `changes_required` or `suggestions`; rounds with no verdict (the reviewer gave no verdict, or the verdict could not be read) are also included so as not to drop comments.

    This delivers a review by a task separate from the one that opened the PR to the original task so that it addresses them. Rounds with suggestions only are imported too, and the budget stops the cost of repetition. For an implementation PR, an AI sorts the imported suggestions within the scope of the PR before reworking, and sacty does not start a rework for suggestions it declines ([Sorting suggestions before reworking](#sorting-suggestions-before-reworking)). How the verdict is decided is in [Tasks and steps](tasks-and-steps.en.md#pr-review-only-tasks).
  - Other rounds (rounds with no findings, and rounds with no recorded verdict: rounds not yet run, or rounds of a task that only refers to the PR and has no review step) are not imported, even if the account differs from the original task's. There is no Request changes, and the step to redo is not decided either.
  - Re-reviews are judged per round. A marker copied by someone other than that task's account is treated as a person's comment.
  - The imported comments are told apart from a person's comments as AI review comments ("AI review comments" below).
- Otherwise, the following posts are not imported.
  - Posts by bots
  - Reviews and line comments posted by the original task's project account that start with sacty's review marker
- Once imported, sacty decides where to send them back to (redoing that step, or requesting changes to an earlier step) (`ReworkJudged`), and changes are requested without a person's confirmation. If it cannot decide, the first step that can be redone (Implementation for the implementation PR, that step for Requirements or Design) is redone.
  - When AI review suggestions reach an implementation PR, sacty sorts the suggestions before deciding the step to redo (`SuggestionsTriaged`; [Sorting suggestions before reworking](#sorting-suggestions-before-reworking)). A comment whose suggestions are all declined is removed from the request for changes. When no comment is left to send back, the step to redo is not decided and no rework starts. The deciders below decide the step for the comments that remain.
  - The target depends on how heavy the decision is that the comment would change (for comments on an implementation PR; the review child task and the step's agent use the same rule).
    Related ADR: [The step to redo for PR comments is decided by the weight of the decision, only a change of policy goes back to design, and a local design fix goes into the implementation PR](../adr/20261121-0241-rework-target-by-decision-weight.md)
    - Only a change of policy goes back to Design. Choosing a different method or structure, changing the scope or acceptance criteria, the shape of a public interface or of stored data, security, and migration are such decisions, which are hard to undo.
    - A local change is fixed in Implementation. Wording, one row of a table or list, a default value, and adding a row are local changes.
    - A round with even one change of policy (a mixed round) goes back to Design as a whole.
    - When it is hard to say which, it goes to Implementation. A comment that touches security, authorization, the shape of stored data, or migration is the exception: when in doubt, it goes back to Design.
    - A change only to the wording of a test viewpoint (without changing its input or expected result) is fixed in Implementation. A comment that changes the input or expected result, or adds or removes a viewpoint, goes back to Design.
    - When a person's comment says where to send it ("send it back to design" or "fix it in the implementation step"), that is followed, even for security and the like. A design fix in a round that fixes such a comment in Implementation is, however, not applied (see [Design fixes](#design-fixes-sacty-design-edit)).
    - The step to redo for a comment that changes a requirements decision (Requirements), and the rule for comments on a Requirements or Design PR itself, are unchanged.
    - Going back to an earlier step re-creates the approved output and has it approved again, which costs more effort and money. So only decisions that are hard to undo go back.
  - Who decides (PBI-332; in older versions, the Goal Guardian (actor `guardian`)):
    - When the comments are only AI review comments and all of them were posted in the last round of the PR's review child task (the posting task and round read from the marker at import; `review` of the items of `PullRequestReviewImported`), the step comes from the step to redo and the cause that the child task gave for each finding in the verdict block of its last round (`rework` of `sacty-review-verdict`) (`reviewTaskRework`, `reviewReworkTarget`). No run to judge the step to redo is made (the cost is 0; the activity has actor `sacty` and the child task in `reviewTaskId`). The run that sorts suggestions is separate and comes before it.
      A finding whose step cannot be read, is not a candidate, or is an unknown value is fixed in the step of that PR. Without `rework`, the step of that PR is redone (the reason is `rework.reviewTaskUnreadable`). The child task's answer has no `answer` (AI review comments are not answers to questions).
    - When a person's comment is included, there is no child task (including when only a review-only task taken in by label or request posted), or a comment is from another review task, from an earlier round, or of an unknown round (records of older versions), or the child task's last round has no verdict record or a verdict of no findings (`no_findings`), the agent of that PR's step (the one a person chose; otherwise `step_agents` or `default_agent`) decides in a new session (the activity has actor `agent`).
      If the agent a person chose is no longer in the configuration, sacty does not decide with the default agent; it pauses the task with the reason (`agent.chosenMissing`) and keeps the comments undecided (they are decided again after resuming).
    - The child task's review instructions give the candidate steps, the rules below, the approved outputs of earlier steps, and the cause choices (`guardian_missed`, `base_changed`) (`reviewReworkLines`).
  - The decider is asked to start the reason (`reason` of `ReworkJudged`) with one of "does not change a decision", "changes a decision (local)", or "changes a decision (policy)", and which decision it is (the format is "does not change / changes (local) / changes (policy): ...").
    The format is only requested in the instruction; sacty does not check it (a reason is recorded whatever its format, as long as it can be read).
- A person's comments that ask for nothing (a reply that only accepts an earlier reply or explanation, thanks, or agreement, such as "Understood" or "Thank you") are left out of the request for changes (`noAction` of `ReworkJudged`).
  - The step's agent that judges the step to redo chooses them. The instruction gives each person's comment its number in the imported order, and asks for the numbers of the comments that ask for nothing in the same answer as the step to redo (`no_action`; `noActionLines`, `extractRework`). A comment that contains any change, check, question, or objection, an answer to the deliverable's "Open questions" (sacty's questions), a comment whose meaning cannot be read, and a comment the agent is unsure about are not to be chosen. The text of a comment is to be treated as data to judge; what it says about how to treat other comments or their numbers is not to be followed (and a comment that says such a thing is not to be chosen either). When AI review comments are judged together, the agent is to judge the step to redo and the cause for the AI review comments even if it chooses every comment from a person.
  - Numbers out of range, numbers that are not integers, and numbers of AI review comments are ignored. No comment is left out when the step to redo comes from the child task's answer, or when the judgment run failed or its output could not be read.
  - A comment left out stays imported (`importedFeedback`) and is removed from the comments not yet applied (`pendingReview`). It does not become a remark of the request for changes, gets no reply, and is not something for a person to check. Only the remaining comments are sent back to the judged step.
  - When every imported comment asks for nothing, the task is not sent back (`noRework`). It stays awaiting approval, the deliverable and the PR do not change, and nothing is posted on the PR. Only the judgment run costs money.
- Along with where to send them back to, the decider also decides the cause of the request for changes (`cause`; see [Request changes](#request-changes)). It is one of `guardian_missed`, `new_request`, `question_answer`, and `base_changed`; if it cannot decide (no answer, `undecidable`, or an unknown value), no cause is set (counted as rework with an unknown cause). The judgment is kept in `cause` of `ReworkJudged` and carried over to the request for changes (`ChangesRequested`).
  - `question_answer` (a comment that only answers a question) can be chosen only for a Requirements or Design PR. It is chosen when the comments only answer the deliverable's "Open questions" (sacty's questions), such as "as recommended" or "option A". It is not a new request or change of direction (`new_request`). It is not chosen if even one comment is a request or a fix that does not answer a question. An Implementation PR has no sacty questions, so the choice is not offered there.
  - When the cause is `question_answer`, the decider also decides how the answers relate to the recommendations (`answer`; it is kept as the `answer` of `ReworkJudged`, `ChangesRequested`, and `prRework`). `as_recommended`: every answer matches the deliverable's recommended answer (including "as recommended" and "up to you") and no approved decision changes. `changes_decision`: at least one answer differs from the recommendation, or an answer changes an approved decision. When unsure, or when an answer cannot be read, it is `changes_decision`. `answer` is not read when the cause is not `question_answer`, and an unknown value is not read (no `answer` is kept).
  - Only with `as_recommended`, and only when the target is the step of that PR (Requirements or Design), is it a light rework that only reflects the answers (`settleReview` keeps `answer: as_recommended` in `ChangesRequested`). Going back to an earlier step, an Implementation PR, a target that could not be decided, or a missing `answer` keeps no `as_recommended` and is reworked as before. `changes_decision` is kept in `answer` and reworked as before (the deliverable is redone and self-reviewed).
  - The light rework (`isAnswerOnlyRework`): the Requirements or Design run started by that request for changes (exactly the set of comments that were judged) works from the previous draft, removes the answered items from "Open questions", and changes only the places that reflect the answers. Other sections, items, table rows, and IDs are kept exactly as they were (`answerOnlyReworkLines`). Only when the previous draft does not start (right after the title heading) with a "スコープ" (scope) section that has in-scope and out-of-scope label lines (such as "対象外：なし" at the start of a line; the word inside an explanatory sentence does not count) (a draft made before PBI-340; `scopeIsWritten`; a section with another name such as "スコープ外", or a scope section further down, does not count), the run is told, as an exception, to add the scope section or move it to the start, add any missing in-scope or out-of-scope line, and reorder the sections at the start to "スコープ", "確認したいこと", and "既定で決めたこと"; the check before submitting is replaced by a check of that order. The run does not self-review (no review perspective workers are started); before submitting it only re-reads the text and checks three things (answered items are removed, nothing else differs from the previous draft, no IDs are missing or duplicated), and it is told not to attach the self-review report (`sacty-self-review`) (`answerOnlyCheckLines`; this is recorded as "no record", and the next rework reviews the whole; in a step whose submission a PR review child task reviews, the agent does not self-review, so there is no record; [Tasks and steps](tasks-and-steps.en.md#self-review-before-submitting)). The provenance classification (the "Where to check" table) and the per-comment response report are as before. If the run finds the answers are not as recommended, it drops the light rework and responds as a normal rework (with the reason in its response). If the previous draft is empty and cannot be read, it is not a light rework.

  For a task with no approved requirements (one that skipped the Requirements step), the original request (the task's title and body) is also given to this judgment. A task with approved requirements does not get it (the requirements are the standard).
- If the judgment run was stopped because the daemon is stopping or the task is cancelled, it is not adopted as a failed judgment (that would redo the implementation). The same applies to the judgment for the import while waiting for approval: only the cost of the run is recorded in a `ReworkJudged` with `runResult: interrupted`, the comments stay unjudged, and they are judged again at the next check (after the restart).
- Just before requesting changes, the PR's status is read once more (a person may have merged or closed it during the judgment, or before a resumed check after the judgment was recorded).
  - If it is still open, changes are requested.
  - If it was merged, or closed without merging, changes are not requested. The imported comments (`PullRequestReviewImported`) and the judgment (`ReworkJudged`) stay in the ledger, and the status is checked again within the same check and recorded as "Merged" or "Closed without merging" in [The PR check](#the-pr-check) (for a merge, `PullRequestMerged` and `StepApproved`; `StepApproved` clears the state of the comments that were being worked on).
  - If the PR is reopened after being closed without merging, changes are requested with the judgment already recorded (it is not judged again).
  - If the status changed during the re-read (a person requested changes, the task was cancelled, and so on), nothing is recorded. If it cannot be read, the next check tries again.
  - Comments that arrive after a merge are not turned into a follow-up task or the like.
- Findings that remain after the same head was judged again: when the parent declined every finding and submitted (`ReviewRejudgeRequested`), and the comments imported after the child task judged the same head again are all AI review findings from that child task's last round, sacty records a pause (the reason is `unchanged`, the message is `implement.declinedAgain`, or `implement.deferredAgain` when the judgment waited for a person's decisions on proposals to defer) in the same append as the request for changes (`ChangesRequested`) (`rejudgeLeftFindings`). No rework starts (the two AIs do not keep going back and forth; a person decides).
  - Resuming redoes the step the changes were sent back to, with the remaining findings. While the task is stopped, it is handled like the pause of a rework that changes nothing (sacty does not turn the PR back into a draft when a person marks it ready, and a merge is taken as the approval; [Unfinished implementations and reworks that change nothing](tasks-and-steps.en.md#unfinished-implementations-and-reworks-that-change-nothing)).
  - If even one comment from a person or from another review task is among them, sacty does not stop and requests changes and reworks as before.
  - After a judgment again that was requested because the sorting declined every suggestion (`reason: triaged` of `ReviewRejudgeRequested`), sacty does not pause. When comments to send back remain after the sorting (there was a must-fix, or a suggestion to handle), it goes straight to the rework. When none remain, the draft is removed after the replies and the PR waits for a person's approval ([Sorting suggestions before reworking](#sorting-suggestions-before-reworking)).

### AI review comments

Related ADR: [Treat comments from sacty's own AI review separately from a person's comments](../adr/20261102-0843-superseded-distinguish-ai-review-remarks.md)

The reviews, line comments, and ordinary comments that sacty's review task posts on a PR still reach the original task as before.
They are, however, told apart from a person's comments.

- How they are told apart: by the marker of the post (`<!-- sacty-review:<task ID>[:<round>] -->`). The posts imported by the judgment of "a sacty task that reviewed this PR" above become AI review comments (`PullRequestFeedback.source: "sacty_review"`).
  The account that posted them is not used to tell them apart (the review is posted with the project's account, the same account as a person's).
  Even with the same account, a post without the marker stays a person's comment.
- Record: `PullRequestReviewImported` keeps `sacty_review` in `items[].source`.
  The positions of the AI review comments among the imported comments are kept in `pendingReview.aiReview`.
  They are carried over to the comments of the request for changes (`ChangesRequested`) (`remarks[].source`, `Task.remarks[].source`).
  - If an import has only AI review comments, the actor is `sacty` (not a person's action). If even one person's comment is mixed in, it is `person`.
  - The same goes for the request for changes: if all the comments are AI review comments, the actor is `sacty`.
- Count: a request for changes made only of AI review comments is not counted in the number of requests for changes by a person. There is no limit on the number of requests for changes.
  - The count for a person (`changeRounds`) is the number of rounds that have at least one person's comment. Rounds of AI review comments only are not counted (used for the display on the approval screen).
  - The round number and the comment IDs (`<step>-<round>-<number>`) continue through the AI review rounds as well (`lastChangeRound`).
  - The cost limit works as before.
- Reviews of an old head: if the head of the PR the review targeted (the review's commit; for a line comment, the parent review's `commit_id` (or else `original_commit_id`), not its own `commit_id`, which GitHub re-points to the current head after later pushes; `PullRequestFeedback.commit`) differs from the PR's current head at import time (`headSha` of `status`), it is discarded without being imported.
  - What is discarded is kept in `PullRequestReviewDiscarded` (actor `sacty`; `reason: stale_head`, the current head, and the discarded comments with their target commits) and marked as imported (`importedFeedback`). Changes are not requested and the step to redo is not decided. It is never imported again.
  - A post whose target commit is unknown is imported, because it cannot be told whether it is old. A short commit is compared by prefix.
  - When the PR's head cannot be read, only the AI reviews are left out this time and checked again at the next check (a person's comments are imported).
  - A person's comments are imported whatever the head.
  - What is discarded is delivered to the person (PBI-291). `items[].summary` of `PullRequestReviewDiscarded` keeps the gist of the comment (the first 400 characters of the same text that would be imported, without the post's marker and heading, whitespace normalized; older records have none), and it is accumulated in `Task.discardedReviews`. `discardedAiReviews` returns those for the PR being watched (the gate's PR; the implementation PR while it is being reworked), oldest first, and returns none once the PR is merged (until then they stay, even after the PR is closed or the task is sent back).
  - The approval screen and the top of the task detail (`DiscardedReviewNotice`) show them as "AI review comments not taken in": the reason (the old head and the PR's head at the time of the last discard; it is not updated when the PR is updated afterwards), the target commit of each comment, the gist, and a link to GitHub, so that the person notices before approving or merging.
  - The discarded comments are not imported into the rework automatically, the AI review is not re-run on the new head, and sacty does not post to the PR. If the person judges that a comment also applies to the new head, they convey it as a change request (or a PR comment); it is treated as a person's comment (no `source`; it counts toward the change count).
- Whether the current head has an AI review (PBI-302 D1; experiments S14 and S18: a person went on to merge before an AI review reached the reworked head): for the current head of the PR awaiting approval, it shows not attached (`none`), reviewing (`reviewing`), or attached (`attached`). The current head is not the submitted commit (`commit` of `gatePullRequest`) but the latest head read while the PR is open by the PR check (`checkPullRequests`; `latestHeads`; it changes when a person adds a commit, is used only for the same PR and the same submission, and is kept in the daemon's memory). When it has not been read yet (right after the daemon starts, right after a redo, or when GitHub returns no head), the state is unknown (`unknown`) and is never shown as attached. It does not block approving or merging.
  - Decision (`aiReviewFor`, `aiReviewOfHead`): it looks at the other sacty review tasks that point at the same PR (`referencedPullRequest`; those with a review step, excluding cancelled ones). If one reviewed and posted on the current head (`reviewPost` and `reviewTarget.headCommit`; for the round before a re-review, `previousReview.headCommit`; commits are compared by prefix, so a short form matches), it is attached. If one has not posted, is running (not paused or escalated), and its target head is the current head or not decided yet, it is reviewing. Otherwise none. A review of a different head does not count for the current head.
  - It is not restored from the activity log (it is computed by looking at other tasks). Only when the task is returned to the screen (`TaskService.view`; `GET /api/tasks/:id`) and in the list response (`TaskService.listView`; `GET /api/tasks`) is `Task.aiReview` (head, status, and the URL of the review when attached) added. It is not added for a task that is not awaiting approval or whose PR is not open. The list computes it in one batch only for the target tasks (`aiReviewsOfHeads`: one pass over all tasks, matching only reviews of the same PR number), with the same result as the details.
  - Screen: `AiReviewNotice` shows it on the approval screen and the task detail (status, the short head, and a link to the review when attached; for none, reviewing, and unknown, where it says the head has not been read, it adds that approving and merging are not blocked, and that going ahead before the review arrives means approving without seeing its comments).
  - PR body: an implementation PR gets one sentence, "AI のレビュー：…", and the sentence "この状況は本文を書いた時点のものなので、最新の状況はこの PR のレビューの欄で確かめてください。" in the "レビューの進め方" section (for a body that follows the template, in the footer before the approval guide). A requirements or design PR gets the same two sentences before the approval guide (in the summary for a body that follows the template) (`aiReviewBodyLines`). They have no parenthetical notes and point to the PR's review tab on GitHub, not to a screen. They describe the state when the body is built (updated) and do not reflect a review that arrives later.
- How they are passed to agents: a person's comments and AI review comments are passed separately.
  - In the rework instruction of the Implementation step (fixes included), it adds: when fixing a defect remark (an AI review `[要修正]`, or a person's remark that describes a bug or wrong behavior), look yourself for the other forms of the same cause (different shapes of input, other callers, other points in time) beyond the input or place that was pointed out, fix them together, and write the range searched in the `text` of the response to the remark (`causeSearchLines`). When a remark says the same cause continues, also add the property test it asks for (in a task that does not write tests, a documents-only task or a no-tests task, it stops at a fix that cuts the cause in one place and adds no property test). Remarks about documents only and remarks that are not defects (`[提案]`, wording) are asked for neither the search nor the property test. The steps such as Requirements and Design do not get it.
  - In the instructions to step agents (Implementation, Requirements, Design, and so on), the integration review, the judgment of where to send back to, answers to questions, and the audit instructions, they are split into a "comments from a person" section and an "AI review comments (not from a person)" section (`remarkSections`, `reworkRemarkLines`).
  - When AI review comments are listed, a note is added to the person's section: "the previous comment" or "the earlier comment" in a person's comment refers to a person's comment, not an AI review comment.
  - In the judgment of where to send back to, a note says AI review comments are not a new request added by a person (`new_request`).
  - Even though the integration review gets the sections separately, it is asked to judge the recurrence of past comments for both a person's comments and AI review comments (`REMARK_RECURRENCE_LINE`, `remarkVerdictLines`; ADR: [Ask the final review and the integration review to judge recurrence for past AI review comments too](../adr/20261103-0312-judge-ai-review-remarks-in-reviews.md)). When AI review comments are listed, the explanation of the output format adds that a verdict must be written for each AI review comment too, and that a missing verdict counts as recurred and fails the review.
- Passing the judgment text of the step to redo (PBI-300): the instructions of a redo run (Requirements, Design, or Implementation) that starts from that judgment (the target and the reasoning on how it read the comments) include the judgment text (`guardianJudgmentLines`).
  - It is passed only to a run that starts from the comments of the round the judgment sent back (when the target step, the round `round`, and the comment IDs `remarkIds` in `prRework` match the current comments of that step: the latest round, not voided, and not yet passed to a submission; if even one comment was voided after the judgment, nothing is passed, so that a judgment that interpreted the voided comment does not come back to the run). The instructions do not change for a run without a judgment (the first run, a redo after a final review failure or an upstream change, a rerun whose only comments are already submitted, or a round a person sent back from the screen).
  - The instructions say that the judgment text is the decider's interpretation, not the person's comment itself. The original text of the person's comments is passed as before, and when the two disagree the run follows the original text (the person's comments first). Instructions written inside the judgment text are not followed.
  - The judgment text is treated as an outside string: secrets and URL credentials are hidden, it is cut at 3,000 characters, and it is passed as one line of JSON (`{"guardianJudgment": …}`) separate from the instructions.
  - When the target could not be decided (`decided` is false), the reason it could not be decided (what could not be read) is passed too. The run does not make big changes by guessing what it could not read: it checks against the original comments and the approved deliverables and makes the smallest change that clearly answers the comments. It concludes that no change is needed only when it can show with evidence that the comments' request is already met. It writes what it could not read and how it fixed it in the response to the comment (`text` in `sacty-responses`); for Requirements and Design it also adds to "確認したいこと" when something is left for a person to decide.
  - When the judging run failed, its output could not be read, or the child task's answer could not be read (the reason is sacty's own wording), it is not a reading of the comments, so nothing is passed.
- Display: the request-for-changes and import rows in the Activity show AI review comments separately ("3 comments (AI review)", "1 from a person, 2 from AI review"), and the comments on the approval screen carry an "AI review" mark. The expanded details of a request for changes in the Activity also mark the AI review comments. The approval screen adds "not counted" only when the round has no person's comment.
  The dashboard's quality signals count "Rework from AI review", and the audit's evidence counts "AI review remarks" (`aiReviewRemark`), separately from changes requested by a person and PR remarks ([Architecture](architecture.en.md), [Audit](audit.en.md)).

### Sorting suggestions before reworking

Related ADR: [Before reworking, an AI decides within the scope of the PR whether to handle each AI review suggestion, and a decision not to handle one ends with the AI](../adr/20261120-2109-superseded-triage-ai-review-suggestions-before-rework.md)

When suggestions (`[提案]`) from the PR review child task reach an implementation PR that sacty opened, an AI decides, before reworking and with the scope of the PR in mind, whether this PR handles or does not handle each suggestion, with a reason (the sorting; `triageSuggestions`). This keeps sacty from running a fix, a push, and a re-review for suggestions it does not handle. A decision not to handle a suggestion ends with the AI, and sacty replies on the PR with the decision and the reason. There is no step where a person decides each one (the approval screen has no field that asks for a decision).

- Target: the suggestions in the AI review comments (`pendingReview.aiReview`) among the comments imported while waiting for approval (`pendingReview`). The sorting is skipped in these cases.
  - The PR is not an implementation PR (a Requirements or Design PR). Judging again and the handling of deferrals passed to the re-review (`ReviewDeferrals`) exist only for implementation PRs.
  - A task of the security combinations. No review child task is recorded for the PR (`Task.reviewTasks`).
  - A PR-review-only task taken in from GitHub (it does not open an implementation PR). The findings of the self-review before submitting are not sorted either.
  - Comments that arrived during a pause and are held ([Comments that arrive while paused](#comments-that-arrive-while-paused)).
  - Comments whose step to redo was already decided (`pendingReview.judgement`) or that were already sorted (`pendingReview.triage`). Once sorted, a restart of the daemon does not run the sorting again.
- Not sorted: must-fix findings (`[要修正]`) and text without a tag are always fixed (sacty leans toward fixing). A person's comments are not sorted; the judgment of the step to redo handles them as before. In a round where a person's comments and AI suggestions are mixed, only the AI suggestions are sorted, and the person's comments are not dropped.
- HTML comments in the suggestion text and the reason are removed until no `<!--` remains, including nested forms such as `<!-<!-- x -->-` (`withoutHtmlComments`), so a string that looks like a sacty post marker (`sacty-reply`, `sacty-review`, `sacty-human-ask`) does not reach the reply, the prompts, or the re-review data.
- The declined suggestion text and reason put into a reply (`triageReplyTextOf`) have HTML comments removed, secrets masked, and internal paths replaced before each item is cut (never inside a surrogate pair), so the first half of a secret that spans the cut is not posted.
- The unit of a suggestion (`splitSuggestions`, `suggestionUnitsOf`): the daemon splits the AI review comments into single findings and numbers them from `S1`.
  - The review body: one unit per `[提案]` or `[要修正]` at the start of a line (a bullet, a heading, or the bold heading form `**[提案] 題**（場所）` is allowed). A unit runs to the next tag, heading, or horizontal rule. Only the section whose heading text is exactly "指摘" is read (an allowlist; the review instructions fix this heading and how to tag a finding). Tags in any other section (overall comment, previous findings, review scope, and so on, whatever the heading is called) are not counted. When a body yields no unit at all (for example it has no "指摘" section) and the verdict of its round is suggestions (no must-fix), the whole body (without HTML comments) is selected as one suggestion, so a different heading form cannot make the selection a no-op and let the round trips continue; the previous findings and their responses are given as material. A body with no unit in a round whose verdict is changes required is not selected and is always fixed. A line comment without a tag is not a unit. When the same round also has units read from line comments, a body with no unit is not selected on its own (the whole body would otherwise be judged alone, and a body marked `address` would send the PR into a fix even though every suggestion in the line comments was declined): it follows the round, and is dropped from the fix when every suggestion of that round is declined (`droppedRemarks`). A body that has tagged lines outside the "指摘" section (the section sacty appends for line comments outside the diff, whose heading contains "行についての指摘") is never dropped on the strength of the units that could be read; it is fixed (`hasHeadedLinesOutsideFindings`).
  - A line comment: when a tag follows `<パス>:<行>：`, the whole comment is one unit.
  - When there is no suggestion, the sorting run is not made.
- Who sorts: the agent of the PR's step (Implementation; the one a person chose, otherwise `step_agents` or `default_agent`) decides in a new session, reading a read-only copy of the code after the implementation (role `triage`; [Runs on a copy of the code](tasks-and-steps.en.md#runs-on-a-copy-of-the-code)). When the run fails, it is redone with the fallback agent (`fallback`). When the agent a person chose is no longer in the configuration, sacty pauses without sorting (`agent.chosenMissing`; the comments stay unsorted).
- What the decision is based on (`buildTriagePrompt`): the task's title and request, the approved requirements and design (including the acceptance criteria), the PR description (up to 4,000 characters), this round's suggestions (with IDs) and must-fix findings, the implementation remarks of earlier rounds and their responses (`Task.remarks`; the newest 30), the suggestions declined so far (`Task.declinedSuggestions`; the newest 50), which review round this is, and how many rounds with suggestions only have come in a row including this one (counted from the per-round verdicts of the child task, `reviewVerdicts`). Text from outside has secrets hidden, is cut, and is passed as JSON data separate from the instructions. The cut is 2,000 characters per item for this round's suggestions and must-fix findings (so the problem, the condition, the harm, and the fix are not lost; PBI-440), and 600 characters per item for the earlier remarks, their responses, and the declined suggestions with their reasons. There is no total cap on the number of items, because the length of one review body already bounds it.
- The criteria (written in the instructions):
  - Handle: a suggestion inside the scope of the PR's purpose that, if this PR does not fix it, causes harm (wrong behavior, text that misleads readers, a gap in verification) or later rework.
  - Do not handle: a suggestion outside the scope of the purpose; preferences, formatting, and wording; a new suggestion about details of text added by a fix; another occurrence of the same cause that keeps coming as a suggestion (when a fix that removes the cause is needed, only that fix is handled, once); something the fixer answered in an earlier round that it cannot fix or cannot do in this environment; and raising again something already declined, or answered or decided to be handled later.
  - The later the round, the higher the bar for handling. When rounds with suggestions only have come twice or more in a row, the AI declines all of them in principle (it handles only one that asks for a fix that removes the cause and that it can show causes harm if not fixed).
  - When unsure: lean toward handling when rounds with suggestions only have not come in a row, and toward not handling when they have.
  - The reason is posted on the PR, so the AI writes in one or two sentences which criterion applies.
- The answer (`extractTriage`, `settleTriage`): the AI writes `id`, `decision` (`address` or `decline`), `reason`, and `sameAs` for each suggestion in JSON under the heading `sacty-triage`. Unknown IDs, duplicates, and unknown decisions are ignored.
  - A suggestion that could not be judged (the run failed, the answer could not be read, the suggestion has no decision, or a `decline` without a reason) is set to be handled (`address`, `defaulted`). This keeps sacty from dropping a fix.
  - When the same finding appears both in the body and in a line comment, the AI gives both the same decision with `sameAs`. When the decisions differ, both are set to be handled.
- Comments removed from the request for changes (`dropped`): an imported comment whose suggestions are all declined and that has no must-fix. A review body is removed only when the verdict of the round that posted it is suggestions (`suggestions`), so that a must-fix is not dropped by misreading the format. A line comment is one tagged unit, so it can be removed.
  - A removed comment is not fixed. It is added to `Task.remarks` as a remark that is not a target of fixing (`triaged: true`, `status: declined`, `round: 0`, the original comment `origin`). It is not counted in the rework round, the rework instructions, the rewrite of responses at submission, or the check of whether every finding was declined (`declinedEveryFinding`).
  - A comment where only some suggestions are declined stays in `pendingReview` with the text and reason of the declined suggestions (`pendingReview.triage.declined`, `declinedParts` of the request for changes), and only the rest is fixed.
  - Declined suggestions are piled up in `Task.declinedSuggestions` (text, reason, URL of the original comment, round) and never removed.
- Rework instructions (`remarkLines`, `triageDeclinedLines`): only the comments to handle are given as targets of the response. For a comment where only some suggestions are declined, the declined suggestions are given in the section "この PR では直さない提案（直しに入る前に選り分けた）" as JSON data separate from the instructions; the agent does not fix them or write responses for them (the same shape as `ownerDeferralLines`, which passes findings a person decided to defer).
- Replies: they use the shape of [Replies about how remarks were handled](#replies-about-how-remarks-were-handled) (the shape does not change).
  - A removed comment does not go through a submission, so sacty replies to it the next time the task waits for approval, whatever the submission. The text is "直しに入る前に AI が判断し、この PR では対応しません。直させたいときは、PR に要対応とコメントしてください。" (the AI decided before reworking and this PR does not handle it; to have it fixed, comment on the PR that it needs a fix), followed by the text and reason of each declined suggestion (`triageReplyTextOf`).
  - The reply to a comment where only some suggestions are declined adds the same note and the declined suggestions with reasons after the implementation's response (still one reply; `triageReplyTextOf`).
- When no rework starts: when no comment is left to send back (no suggestion to handle, no must-fix, and no person's comment), sacty does not run the implementation, commit, or push. It records `SuggestionsTriaged` and `ReviewRejudgeRequested` (`reason: triaged`) in the same append.
  - After the replies are done, the PR review child task judges the same head again, once (`reason: declined` of `ReviewRestarted`; `rejudgeDue`; [The review child task of a PR](#the-review-child-task-of-a-pr)).
  - When that round has no findings, the draft is removed and the PR waits for a person's approval. The risk assessment comes in that round.
  - When that round gives a must-fix, or at least one suggestion to handle, sacty goes to the rework without pausing (`settleReview`).
  - When that round leaves only suggestions and all of them are declined too, judging again happens only once, so sacty records `SuggestionsTriaged` with `stop` (`Task.triageStop`, which holds the PR number and the head commit and stops applying once the head moves). This applies only to a re-judging that the sorting asked for (`reviewRejudge.reason` is `triaged`); the re-judging after the implementation declined (PBI-357, 370) is not sorted and keeps the existing pause (`implement.declinedAgain`, `deferredAgain`).
  - After the replies are done (`triageStopDue`: nothing is left to reply to, nothing is held, and the PR number and head match `triageStop`), the task does not pause. The PR check removes the draft with `markReady` (`PullRequestMarkedReady` with `reason: suggestions_declined`; PBI-440). Unlike the draft removal for a round with no findings, the child task's verdict stays "suggestions", and the risk assessment is given by an assessment-only run (`assessDeclinedRisk`), not by a re-review. An orchestrator agent reads the code and the diff after the implementation, with the remaining suggestions and the reasons they were declined as material (the run, the record, and how the cost counts toward the budget are the same as for the assessment before a PR was opened in the earlier version; [the decision on when to give a risk assessment](../adr/20261120-2342-no-pause-when-rejudged-suggestions-all-declined.md)). The assessment for that head of that PR is found from the record (`via` and `commit` of `Task.riskAssessment`) and not repeated. There is one PR comment, with a marker (task and head) at its start; if a comment with the same marker exists, it is not written again, so restarting the daemon does not duplicate it. When the assessment cannot be made (budget cap, failed run, unreadable answer), the reason is recorded and written in the comment, and the draft is removed. If a run was not confirmed stopped, the task pauses and the draft is not removed. The target is the task that opened the PR, on a daemon with the risk assessment enabled (not a task that continues an existing PR, and not a requirements or design PR). A PR that `markReady` does not remove the draft from, such as the PR of a split child task (stacked), is not removed here either. After it is removed, `Task.triageStop` is cleared and `pullRequest.suggestionsLeft` is set. Whether the draft stays removed is decided in one place (`readyAt`): the child task's head is the PR's current head on GitHub, and either the child task judged no findings, or `suggestionsLeft` is set, `reviewedCommit` is that head, and the last verdict is "suggestions". The draft check (`wantsDraft`), the re-removal of the draft (`undraftMarkedReady`, including after a pause and resume), and the last check of `markReady` use it. The screen shows the "suggestions remain" notice only while `reviewedCommit` is the current head. `triageStopDue` also compares the head recorded in `triageStop` with the current head on GitHub; if a person added a commit, it does not apply, and the re-review and sorting work as usual. No further judging or sorting starts for that head. If the run was stopped for stopping the daemon, a cancellation, or a pause, it is not recorded as a failed assessment: only the cost is recorded in a `PullRequestRiskAssessed` without a commit, and the next check assesses the same head again. If the settings cannot be read, a `PullRequestRiskAssessed` with that reason is recorded and the draft is removed.
  - A person can read it in the activity log (the row for the draft removal says all remaining suggestions were declined) and in the approval screen and the task overview (`AiReviewNotice`: suggestions remain, the PR was not reviewed again, and to have them fixed, comment on the PR that they need action). Commenting on the PR is imported as a person's remark and starts the rework as before. When the head moves (a person's commit or a rework submission), the re-review and the sorting work as before.
  - A task that an earlier version paused with `triage.left` can still be read from its activity log (the `triage.left` message of `TaskPaused` is kept so it can be shown). `Task.triageStop` is not cleared by a pause, so resuming returns the task to waiting for approval and, if the head is the same, removes the draft (the task does not stop again).
- When the decision is not adopted: when, during the sorting, a person requested changes, the task was cancelled, the comments changed, or the task stopped waiting for approval, or when the run was stopped because the daemon is stopping or the task is cancelled, the decision is not adopted. Only the cost is kept in a `SuggestionsTriaged` with `runResult: interrupted`, and the comments stay unsorted and are sorted again at the next check.
- A person overrides: commenting on the PR that something needs a fix imports it as a person's comment (it is not sorted), and the rework starts. A person can also request changes from the sacty screen. A person can read the declined suggestions and the reasons both in the PR replies and in sacty's Activity.
- Record and display: `SuggestionsTriaged` (actor `agent`; [Activity log](event-log.en.md#cost)). The cost goes into the task's budget and shows in the "Sorting the suggestions" row of the per-step cost table. The Activity row on the screen shows "M of N suggestions will not be handled in this PR" with the cost, and the decision and reason for each suggestion are in the details of the row (`describeEventParts`). When some suggestions could not be judged and were set to be handled, the row and the details say so. A run that was not adopted is shown as such in the row. "Recent activity" in the overview cuts every row to two lines and shows no details.
- What does not change: the `declined` and `deferred` the implementation reports during a rework and the person's decisions ([Proposals to defer and the person's decisions](#proposals-to-defer-and-the-persons-decisions)), the self-review, the review of Requirements and Design PRs, PR-review-only tasks taken in from GitHub, and how replies are built (`remark-reply.ts`).

### Things for a person to check

Related ADR: [人に確かめてほしいことを、PR のコメントと承認の画面の目立つ所に出す](../adr/20261103-2302-surface-human-asks.md)

In a rework started by PR comments, there can be things only a person can check: whether the comments were read as meant. If they appear only in a corner of the approval screen or in the activity, the people looking at the PR do not notice them. The following two are collected as "things for a person to check" (`humanAsks`) and shown in the PR comment and in a prominent place on the approval screen and the task details.

- The reason it could not be decided (`undecided`): where to send the task back could not be decided (`prRework.decided` is false), and the implementation or another step was redone. The reason is the text the decider wrote (what could not be read). When the reason is sacty's own wording (the judging run failed, or its output or the child task's answer could not be read), it is not a reading of the comments, so it is not shown.
- A question or a guess from the run (`confirms`): a `confirm` that the rework run attached to its response to a comment (`sacty-responses`). The run is told to write it when it guessed because it could not read what the comment meant, when it recreated a value or wording it no longer had, when it changed something the comment did not ask for, or when it left a comment unaddressed (`confirmLines`). A response with nothing to check does not get one. The run is told not to repeat the same thing to check in the responses to several comments (one thing to check is written once, in the response to the comment it relates to most). It is cut at 1,000 characters. It is kept in `RemarkResponse.confirm`, and `Task.remarks[].confirm` holds only the one from the same submission as the response (it is cleared if the next submission has no response).

- Merging the same text: when a `confirm` with the same text is attached to several comments, it becomes one item, and the IDs of the comments it was attached to are listed in comment order (`remarkIds`). Whether the text is the same is compared without whitespace (leading and trailing whitespace, line breaks, and whitespace inside the text). The text shown is the one written for the first comment. Texts that differ by even one character other than whitespace are not merged, even if they seem to mean the same (sacty does not guess whether the meaning is the same). The screen and the PR comment both show the merged items, and the count is the number after merging.
- When it is shown: the task is waiting for approval, for the comments (not voided) that the current gate's submission (`gate.submission`) received. The reason it could not be decided is shown only when the `prRework` target is the gate's step and its comment round (`round`) is the latest round of that step (an old judgment is not shown after a later send-back). Nothing is shown when the task is not waiting for approval (during a rework or while paused).
- Screen (`HumanAskNotice`): shown as "N things for you to check" at the top of the approval screen and in the task details below the approval notice (visible on every tab). The reason it could not be decided shows the gist (the first one or two sentences) first, and the full text opens below ("How the send-back judgment text is shown" below).
- PR comment: when the reworked deliverable is back to waiting for approval (a `StepSubmitted` that makes the gate's step or submission new; if it could not be written while the task was paused, sacty tries again when the resume brings the task back to waiting for approval on the same submission, and it does not write again if it finds a comment with the marker), one comment is posted on the PR of that gate (the implementation PR, the Requirements PR, or the Design PR) (`announceHumanAsks`, `buildHumanAskNotice`).
  - The comment starts with a marker (`<!-- sacty-human-ask:<task ID>:<step>:<submission> -->`). If a comment with the marker already exists for the same submission, nothing is posted.
  - Notices for the same submission are processed one after another (`serialized`). Even if a pause and a resume start a second one while the first is still searching for the comment, the second looks for the marker again after the first finishes, so it does not write twice.
  - It is not written for a task with a security plan (`security-check`, `security-fix`), because what the run wants checked can include details of a vulnerability or the fix scope (it still appears on the approval screen; this is the same rule as for requested comments).
  - Paths inside sacty's workspace (such as `/sacty-input/task.md:77`) in those outside strings are replaced with a name a person can follow (`withoutInternalPaths`).
  - The body quotes the reason it could not be decided and what the run wants checked. Because they are outside strings, secrets are hidden before cutting at 600 characters, and a zero-width space is put after `@` so that `@name` does not notify other people. It ends by telling the reader to comment on the PR or send the task back on the task screen if the result is not what was meant.
  - It is posted with the project's gh account (nothing is posted for a project with no GitHub account chosen; the screen still shows it). It does not wait for the post, and the request has a 30-second deadline. If posting fails, the task state does not change (a warning is logged).
  - This comment is not imported as a person's comment in the next PR check (comments from the task's account that start with the marker are excluded; if someone else copies the marker, it is imported as a person's comment).

### Replies about how remarks were handled

Related ADR: [Reply on the PR, per remark, about how an imported PR remark was handled](../adr/20261116-0045-superseded-reply-to-review-feedback-on-pull-request.md), [Retry replies to remarks that hit a rate limit after the wait is over](../adr/20261117-0110-retry-remark-replies-after-rate-limit.md), [When the implementation declines every AI review finding and changes nothing, reply with the reasons and have the same head judged once more](../adr/20261117-0250-reply-and-rejudge-when-all-findings-declined.md)

When a step is redone because of remarks imported from PR reviews and comments and the PR is updated, sacty replies on the PR, per remark, about how it was handled. The person or AI who made the remark can read, where the remark is, whether it was addressed or declined.

- The comment a remark came from: when importing PR comments sends a task back, each remark carries the comment it came from (`origin`: the import key `review:<ID>`, `review_comment:<ID>`, or `comment:<ID>`, and the PR number) (`remarkOrigins`; `remarks[].origin` of `ChangesRequested`, and `Task.remarks[].origin`). It is kept for comments that arrived while paused and for the remaining comments (`pendingRemarks`) of a task escalated at the limit in an earlier version, which are carried over as they are when a person sends it back. Remarks written on the screen and remarks in earlier activity logs do not have it.
- Declaration: the step agent writes a `status` for each response to a remark (`sacty-responses`) (`statusLines`). `addressed` if it addressed the remark, `declined` if it did not for a reason (out of scope, the remark does not apply, already satisfied, and so on), with the reason in the response text (`text`). An unknown value or a missing declaration is treated as absent (the response is kept). It is kept in `RemarkResponse.status`, and `Task.remarks[].status` holds only the one from the same submission as the response.
  In the Implementation step, a response to a send-back remark can also be `deferred` (a proposal not to fix the remark in this PR and to defer it) ([Proposals to defer and the person's decisions](#proposals-to-defer-and-the-persons-decisions)).
- When sacty replies (`awaitingRemarkReplies`): the task is waiting for approval and the PR of the gate step is open. It does not reply in the review step, in tasks of the security plans, or in a project with no GitHub account chosen (`remarkRepliesDue`) (the same conditions as the comment about things for a person to check). It does not reply while redoing, while paused, or for a cancelled task either.
- Which remarks get a reply: remarks imported from comments of that PR (the PR number of `origin` is the same) that are not voided, have a response, and have not been replied to yet. For remarks of the gate step, only those answered in the current submission. A remark sent back to an earlier step (for example, a comment on the implementation PR fixed in the design) gets that step's latest response, in the submission that updated the PR. A remark without a response gets no reply (if a later submission adds a response, the reply is posted then).
- Each remark gets one reply only (`Task.remarks[].repliedIn`). If a later send-back writes a response to an earlier remark again, sacty does not reply again.
- The form of the post (`postRemarkReplies`, `buildRemarkReply`):
  - A remark imported from a line comment (`review_comment`): posted as a reply to that comment (`replyToReviewComment`). When GitHub rejects the reply because of its target (a 404, 410, or 422 answer: the original comment is gone, GitHub does not accept a reply to a reply, and so on; `replyRejected`), it posts a PR comment.
  - A remark imported from a review body or a regular comment (`review`, `comment`): posted as a PR comment.
  - A PR comment says in a sentence, on the line after the marker, what it replies to (`replyOpening`). The form is "<source><kind>（the text このレビュー, このコメント, or この行へのコメント, linked to the original）への返信です。", and the link target is `#pullrequestreview-<ID>`, `#issuecomment-<ID>`, or `#discussion_r<ID>` (`remarkOriginUrl`).
    - The kind is a review body, a regular comment, or a line comment.
    - The source follows the imported remark's `source`: "Sacty の AI が書いた" for `sacty_review`, "人が書いた" otherwise. A remark of a taken-over PR (`continuedResponses`) records neither the source nor the original text, so it names no source and has no quotation.
    - A reply to a regular comment has the start of the original comment on the next line, quoted on one line (`remarkQuote`, as `> 「…」`). It is made from the remark text (`Remark.text`): secrets are hidden, `withoutInternalPaths` is applied, HTML comments (markers) are removed, whitespace is collapsed, and the result is cut at 100 characters (`REPLY_QUOTE_MAX`, never between a surrogate pair). A zero-width space follows `@` (the cutting and the `@` handling are shared with `cutAtMax` and `withoutMentions` in `human-ask-notice.ts`). After that no characters are replaced; the text goes into inline code (so `#123` references, images, links, character references, and emphasis have no effect; a longer fence wraps text that contains a backtick). The source of a remark a person decided to fix in this PR (`fixOf`) is inherited from the original remark's `source` (`awaitingRemarkReplies`). The source and the quotation are put together by `remarkReplyOrigin`. Replies to a review body or a line comment have no quotation.
    - The opening and the signature at the end use the product name "Sacty" (PBI-450). The reading side (`readRemarkReply`) skips lines that end with "への返信です。" and quoted lines after the marker, so a reply with the earlier "sacty の AI が書いた…への返信です。" is read as the same state. Recognition is by the marker, so a wording change does not break it.
    - A reply in the thread of a line comment has no such opening.
  - The body starts with a marker (`<!-- sacty-reply:<task ID>:<remark ID>:<submission> -->`). Then it says "対応しました。" for `addressed` or "対応していません。理由：" for `declined`, followed by the response text. With no declaration, only the response text is shown. The end has the separator `---` and "Sacty の<工程名>の工程で、AI が書きました。" (the task ID and the remark ID are not written at the end and are kept only in the marker; `buildRemarkReply`).
    For `deferred`, the head says "この PR では直さず、後続に回したいという案です（人に確認中で、まだ決まっていません）。理由：", and after the response text a note says that the person who approves the task decides before the merge whether to defer it or fix it in this PR (`DEFERRAL_PROPOSAL_HEAD`, `DEFERRAL_PROPOSAL_NOTE`).
  - The response text comes from outside, so secrets are hidden first and then it is cut at 4,000 characters (`REPLY_TEXT_MAX`), and a zero-width space is put after `@` so that `@name` does not notify other people. Paths inside the workspace are replaced with names a person can follow (`withoutInternalPaths`).
- No double posting: before posting, sacty reads the line comments and the PR comments once each, to the last page, and uses as already-posted replies those posted by an account recorded as used for replying (including the current account) whose body starts with this task's marker (`listReviewComments`, `listIssueComments`; the match per remark ignores the submission). A post by someone else imitating or quoting the marker is not treated as posted. Even if the daemon stops after posting and before recording, it does not post twice. Replies of the same task are processed in order (`serialized`).
  - The account used for replying is recorded before posting in `RemarkRepliesStarted` (the step, the submission, the PR number, the account) and held in `Task.remarkReplyAccounts` (each account once). Even if sacty stops after posting and before recording the result, and the project's GitHub account changes in between, it finds the previous account's replies and does not post twice.
  - Every reply post (line replies and PR comments alike) goes through one entry per host and account (`remarkReplyPost`). It posts one at a time and leaves 1 second between posts (this also covers posts by other tasks that reply with the same account).
  - When it hits a GitHub rate limit (a 429, or a 403 whose body explains a rate limit or whose headers show zero remaining or a time to retry), it stops posting there and retries after the wait is over.
    - The remark that hit the limit and the remaining remarks of that submission are not posted and are not recorded as failed either (they stay not replied to; a remark whose posted reply is in the lists already read gets that reply recorded). A line reply rejected by the limit is not turned into a PR comment. When the first read of the lists hits the limit, no remark is recorded. When the search for a reply whose outcome is unknown hits the limit, only that remark is recorded as failed (so that it is not posted twice), and the rest stay unrecorded.
    - The wait is kept per host and account (`noteRemarkReplyLimited`). The time of the next try and the number of limits hit in a row are saved in `SACTY_HOME/github-rate-limits.json` (mode 0600; `GitHubRateLimitStore`), so a daemon restart does not lose them. If saving fails, sacty logs a warning and continues with the wait in memory.
    - The time to wait is the longer of the wait GitHub shows (the later of `retry-after` and, when the remaining count is 0, `x-ratelimit-reset`; `retryAfterOf`) and a wait that doubles each time the limit continues (from 1 minute, capped at 1 hour). The wait GitHub shows is capped at 1 day. Seeing the limit again during the wait (for example when reading the lists) does not raise the count and only moves the deadline to the later one. Once one post succeeds, the wait and the count of that account are cleared.
    - During the wait, no reply is posted with that account (neither the posts that were waiting their turn nor posts requested later by other tasks; `remarkReplyPost` returns `limited`). The lists are not read either. A task waiting to reply is not queued (it takes no run slot; `remarkRepliesReady`). The task state does not change (approving, sending back, and merging work during the wait). A task that only waits because another task with the same account hit the limit gets no record of the wait in its Activity (only the task that hit the limit does).
    - When the wait is over, the task is queued again and replies to the remarks that were left (finding already posted replies by the marker works the same way). If, in the meantime, the deliverable was approved, a new submission replaced it, the PR was closed, or the remark was voided, that reply is not posted (the conditions for replying no longer hold).
    - It retries up to 5 times. When the limit is hit beyond that (the 6th time in a row), the remaining remarks of that submission are recorded as failed (`github.replyGaveUpAfterRateLimit`) and are not retried. The count is per account, so until one post succeeds, a submission that hits the limit with the same account is recorded as failed right away.
    - When it coincides with a timeout (the request deadline below), the timeout handling wins (the remaining remarks are recorded as failed and are not retried).
    - If another request with the same account records a limit while a post is in flight, that wait is not cleared even when the post succeeds.
    - When the saved wait cannot be read or is broken, sacty starts with no wait and logs a warning (it does not warn when nothing was saved yet).
    - This covers only the replies about how remarks were handled. Other posts (requested PR comments, reviews, and the comment about things for a person to check) and reads from GitHub (importing remarks and checking the PR state) do not look at this wait (they still send requests during the limit). Their current handling is unchanged (checking the PR to review and posting the review retry temporary failures automatically; [Intake](intake.en.md)).
  - The split records are written in one write. sacty remembers that it stopped posting because of a timeout until the result is recorded (even if it then leaves without recording the result because of a pause, or retries after a failed record, it does not post the rest and records the failure).
  - When a list cannot be read, cannot be read to the end because of the page limit, or the answer cannot be read (not a JSON array; a comment whose body, ID, or author cannot be read; a next-page URL that cannot be followed), sacty cannot tell what was posted, so it posts to no remark and records the failure.
  - When it is unknown whether a line reply was posted (the answer was lost, the time limit passed, or a 5xx), sacty looks through the line comments again and uses the reply if found. If it is not found or the search fails, sacty does not add a PR comment and records the failure.
  - Getting the token and each request to GitHub (lists, replies, comments) have a 30-second limit each. When getting the token passes the limit, `gh` is stopped together with the processes it started. Once a request passes the limit, sacty does not try the remaining remarks and records the failure (`github.replySkippedAfterTimeout`), so that it does not wait for an unanswering GitHub once per remark (a remark whose posted reply is in the lists already read gets that reply recorded). Even if no answer comes back, the run slot is not kept occupied.
- Right before posting each remark, sacty checks that no pause or cancel has been requested and that the submission waiting for approval has not changed. If it has, sacty does not post anything new and does not record (after resuming, it finds what was posted by the marker and continues). If, while waiting, that remark was voided or its response changed, only that remark is skipped.
- Record: the result is kept in `RemarkRepliesPosted` (the step, the submission, the PR number, and per remark the key of the original comment, whether it was a line reply, the URL of the post, and why it could not be posted). Even if posting fails, the task does not stop. A remark that could not be posted is treated as replied and is not retried (a remark that hit a rate limit is not recorded here and is retried as described above). When sacty waits for a rate limit, it records `RemarkRepliesDeferred` (the step, the submission, the PR number, the number of remarks not replied to yet, the time of the next try, and the number of limits hit in a row); the state does not change, and `Task.remarkRepliesDeferred` holds the submission that is waiting. The `RemarkRepliesPosted` of a result retried after the wait carries `retried`. The Activity on the screen shows that it is waiting (in about how many minutes it retries, the number of remarks, and the count), that it retried after the wait, and that it gave up (as the reason it could not reply) (ja and en). The Activity row on the screen shows how many remarks were replied to and how many could not be, and the result per remark (those that could not be replied to first) is in the details of the row (`describeEventParts`). "Recent activity" in the overview cuts every row to two lines and shows no details (read the full text in the Activity tab).
- These replies are not imported as PR comments: a line comment or PR comment that starts with the marker `<!-- sacty-reply:` and was posted by the task's account or an account recorded as used for replying (`Task.remarkReplyAccounts`) is excluded from importing PR comments (while waiting for approval, while paused, and when reading a taken-over PR) (`feedback`, `isSactyRemarkReply`). One written by another account imitating the marker is not excluded.
- The review child task of a PR gets them as the author's replies: only the read for the review step includes these replies (`includeSactyReplies`; they are included even when sacty's account is a Bot, while posts by other Bots are still excluded). sacty's accounts here include the accounts recorded by the tasks that replied on that PR (the implementation PR, or the Requirements and Design PRs) (`remarkReplyAccountsOn`), so that the replies can be read even after that account is removed from every project. The author of a PR sacty created is sacty's account, so they are passed as the author's posts in the existing reviews and as the author's replies (`authorReplies`) in a re-review. The re-review rule "do not raise again a point the author answered as out of scope or to be handled later" applies to sacty's replies too ([Tasks and steps](tasks-and-steps.en.md)).
  Before starting a review, the review child task first posts the replies of the task that created the PR if they are not posted yet (`remarkRepliesSettled`; the parent and the child run side by side, so waiting for the parent's next run would read before the replies). It repeats until no remark is left to reply to, and when the result cannot be recorded or it cannot proceed because of a stop request, it does not start the review and tries again after a 1-minute pause. The pause after a failed record is set by the reply processing itself, so the task that created the PR is not queued during it either. During the pause, the child task is not queued, so that a review that cannot proceed does not keep taking a run slot and block the tasks behind it (`reviewWaitsForReplies`). The pause is gone when the daemon restarts (it is not a wait for a GitHub limit). When the replies are waiting for a GitHub rate limit, the child task starts the review without waiting for them (the wait can be long; those replies do not reach the review as the author's reply).
  Only posts by the same account as the PR author count as the author's replies (on a taken-over PR the author is a person, so sacty's replies are passed as existing reviews and comments). A point that was answered is still raised again when the scope changed or the current change is its direct cause.
- For a taken-over PR (a task that fixes a PR a person created; `continuedPullRequest`), sacty also replies, in the same form and under the same conditions, to the comments passed to the implementation.
  - In the instructions of the implementation step, the PR comment data carries an ID per comment (`id`; the import key), and the agent writes `remarkId` (the `id` of the data), `status`, and `text` in `sacty-responses` for the comments it addressed and those it does not or cannot address (`continuedResponseLines`). It writes nothing for those that need no response (the author's replies, finished exchanges, impressions, and so on). The Requirements and Design steps get no IDs (as before).
  - Of the responses read, those whose ID is the key of a passed comment are kept in `responses` of `ContinuedFeedbackPassed` (the key, the response text, the declaration) and held in `Task.continuedResponses` (per key: the response text, the declaration, the submission of the response, the submission of the reply). They are kept apart from responses to send-back remarks (`Task.remarks`). A response to an ID that was not passed is not read.
  - sacty replies, while the implementation waits for approval, to comments with a response written in the current submission that have not been replied to yet. Comments of a taken-over PR are passed again on every implementation run, so a comment that got a reply gets no further reply even if a later submission writes a response again (the response is not overwritten either). The rework instructions mark replied comments with `answered` so that the agent does not write the response again.
  - A comment imported from that PR after a submission (a send-back remark) gets its reply as an imported remark. When the same comment is also among the comments passed to the implementation, sacty does not reply twice.
  - The remark ID in the marker and the record is the key (`review_comment:<ID>` and so on). The end of the reply does not show the remark ID.
- When every finding is declined and nothing changes: when the reworked implementation does not change the head on which the PR-review child task left findings and declines all of those findings with a reason, sacty still submits and replies in the same form and under the same conditions ([Unfinished implementations and reworks that change nothing](tasks-and-steps.en.md#unfinished-implementations-and-reworks-that-change-nothing)). After the replies, the child task judges the same head once more, and the replies are passed as the author's replies ([The review child task of a PR](#the-review-child-task-of-a-pr)).
- A comment removed from the request for changes before reworking because all its suggestions were declined (`Task.remarks[].triaged`) does not go through a submission, so sacty replies to it the next time the task waits for approval, even when it is not a response of the current submission of the approval gate (the report is `declined`, so the reply starts with "対応していません。理由："). The text is a note that the AI decided before reworking and that a person who wants it fixed comments on the PR that it needs a fix, followed by the text and reason of each declined suggestion (`triageReplyTextOf`). The reply to a comment where only some suggestions are declined adds the same note and the declined suggestions with reasons after the implementation's response (still one reply; `triageReplyTextOf`). The marker, the signature, hiding, the length limit, and the handling of `@name` and internal paths are the same as other replies ([Sorting suggestions before reworking](#sorting-suggestions-before-reworking)).

#### Reviews with an empty body

Reviews with an empty body (COMMENTED) line up on an implementation PR, one per reply (PBI-450; for example PR #499 has 10 of 12 reviews, and #501 has 6 of 10).
The cause is that GitHub creates one review with no body for each reply to a line comment. Changing how Sacty posts would not avoid it, so the way of posting is not changed.

- What was checked: REST `POST /pulls/{n}/comments/{id}/replies` (`replyToReviewComment`). In every reply of PR #470, #480, #499, and #501, each reply carried its own `pull_request_review_id`.
- What was not checked: GraphQL `addPullRequestReviewThreadReply`. A reply always belongs to a review (`PullRequestReviewComment.pullRequestReview` in the schema), but whether an empty review is created when `pullRequestReviewId` is omitted was not checked, because writes cannot be tried.
- A method not adopted: putting the replies into one pending review. A pending review is limited to one per person per PR. Sacty posts with the same account as the person, so Sacty's replies would mix into a review the person is drafting on screen and be submitted with it.
- Effect: as many empty reviews as replies keep lining up in the reviewer's conversation tab. If GraphQL turns out to avoid it, the way of posting will be fixed.

### Proposals to defer and the person's decisions

Related ADR: [A person decides whether to defer a finding; the implementation only proposes it with a reason](../adr/20261117-0415-superseded-defer-proposals-decided-by-person.md), [A person chooses, per finding, how a deferred finding is handled](../adr/20261117-0504-choose-handling-of-deferred-findings.md), [A proposal to defer that has not been replied to carries its reason over to the next submission and is replied to](../adr/20261117-0822-carry-unreplied-defer-proposals.md)

The implementation can declare that it would rather not fix a remark in this PR and defer it. This is a proposal; a person decides, one by one on the approval screen, whether to defer it.
AI review suggestions that the AI declined in the sorting before reworking are not such proposals. The decision ends with the AI and does not wait for a person's decision ([Sorting suggestions before reworking](#sorting-suggestions-before-reworking)). Only what the implementation declares after the rework has started becomes a proposal.

- Declaration: in the Implementation step, the `status` of a response to a send-back remark (`sacty-responses`) can be `deferred`, with the reason in the response text (`deferLines`).
  - The instructions give the criteria for fixing now or proposing to defer. A remark with a large impact (data corruption or loss, security, an external effect that cannot be undone, a compatibility break, or not meeting an acceptance criterion) is fixed in this PR. Any other remark is fixed in this PR when the fix stays small within this change and is inside the task's scope. Only a remark of suggestion weight (a small impact, or a medium impact that occurs only when two or more independent conditions coincide) whose fix needs a new mechanism or lies outside the task's scope may be proposed for deferral. The implementation does not widen the scope by adding a new mechanism in order to fix a remark.
  - When one remark mixes things to fix and things to defer, the agent declares `deferred` and writes them separately in the response text.
  - `deferred` is not read in the responses of other steps or in the responses to the comments of a taken-over PR (`continuedResponses`); it is treated as no declaration. A `deferred` on a remark a person sent back with the decision to fix it in this PR (`fixOf`), or on a remark already decided, is treated as no declaration too (it does not become a proposal again).
- The record of a proposal: kept in `Task.remarks[].deferral` (the submission that declared it `proposedIn`, the reason `reason`, and the person's decision `decision`). Unlike the response text, it stays when a later submission has no response. If a later submission declares `addressed` before a person decides, the proposal is withdrawn. A proposal on a voided remark is not listed.
  - Carry-over: when a proposal has not been decided by a person and has not been replied to on the PR, and a later run has no response for it, the reason of the proposal is carried over as the response of that submission (`response` is the reason, `status` is `deferred`, and `respondedIn` is that submission). This applies when the run that declared the proposal did not reach submission (the implementation was run again because it was unfinished, conflicts with the base remained, or it was paused for changing nothing), and when it was submitted but reworked before the reply could be posted. What the agent wanted a person to confirm (`confirm`) is kept only while the run that declared it has not been submitted.
  - A proposal that was replied to (it has `repliedIn`) and a proposal a person decided are not carried over (the response goes back to unanswered; the proposal stays).
- Reply: a proposal on a remark imported from a PR comment is replied to as in [Replies about how remarks were handled](#replies-about-how-remarks-were-handled), stating that it is a proposal, that a person is being asked, and that nothing is decided yet. Even when the run that declared the proposal did not reach submission, sacty replies at the next submission with the reason carried over. After a person has decided, sacty does not post the reply to the proposal (also when the person decides while the reply is waiting; the decision stays on the PR in the decision comment). The response to the send-back remark of a remark decided to be fixed in this PR is replied to as usual.
- List (`deferProposals`): while the implementation waits for approval, the proposals not decided yet are shown on the approval screen (`DeferralNotice`). Each proposal shows the remark text, the reason, whether it is an AI review finding, a link to the original comment, and the choices (decide later, defer, fix in this PR). Decided proposals are shown below as a record. The task details show the count and a link to the approval screen (`DeferralPendingNotice`). Nothing is shown while reworking, while paused, or while escalated.
- Decision (`decideDeferrals`; the API is `POST /api/tasks/:id/deferrals/decide`): only the chosen remarks are decided, and `DeferralsDecided` is recorded (actor `person`; the step, the submission, and `defer` or `fix` per remark). Proposals that were not chosen stay undecided.
  - Only the proposals not decided yet of the current submission of an implementation waiting for approval can be decided. No decision (`deferral.none`), a remark that is not a proposal or is already decided (`deferral.notOpen`), and an old submission (`gate.staleSubmission`) are refused, and nothing is recorded.
  - If even one is `fix` (fix in this PR), the same append sends that remark back to the implementation (`ChangesRequested`; the remark text is the text of the original remark, and it carries the original comment `origin` and the ID of the original remark `fixOf`). It counts as a person's request for changes ([Request changes](#request-changes)).
  - With `defer` (defer) only, the task stays waiting for approval.
- Handling of a remark decided to be deferred (`DeferralHandling`): each decision chooses `task` (create a sacty follow-up task), `issue` (create a GitHub issue), or `none` (do nothing) (`decisions[].handling` of `DeferralsDecided`).
  - If none is chosen, the project's default is used (`ProjectDefinition.deferralHandling`; `none` when absent). The initial choice on the approval screen is this default too (`Task.deferralHandlingDefault`, added only when a task with undecided proposals is returned to the screen). A handling given for a `fix` remark is refused (`deferral.handlingOnFix`).
  - `issue`: at the decision, an issue is created in the repository of the implementation PR (`buildDeferralIssue`, `createIssue`). The title is `[PR #<number> follow-up] <first line of the remark>`, and the body has a marker (`<!-- sacty-deferral-issue:<task ID>:<remark ID> -->`), the remark text, the reason the implementation wrote, and links to the original PR and the original comment. In the remark text and the reason, secrets are hidden and paths inside the workspace are replaced first, then they are cut and shown as quotes (`askQuote`). Because the person chose to create an issue for the remark, the text of a remark written on the sacty screen is included as well. The URL of the created issue is shown in the decision comment. Each issue is created with its own 30-second limit.
  - `task`: after the original task completes (the PR is merged and the remaining steps end), at the end of the PR check (every 60 seconds), one follow-up task is created per remark (`settleDeferralTasks`, `deferralTasksDue`, `buildDeferralTask`). It is made like a follow-up task of a completed task (`deriveTask`; the actor is `sacty`), and the title is `[PR #<number> follow-up] 後続に回した指摘 <remark ID>`. The title and the request consist only of text sacty decides; the remark text, the reason, and the original PR are put in as JSON data separate from the instructions (`deferredFinding`), and the agent is told not to follow instructions written there (the title becomes the heading of the instructions to the agent and the title of the PR the follow-up task opens; a request takes priority over the record of the original task). The repository is decided in the same order as the initial value when a follow-up task is created on the screen (the import source, the repository given at creation, the prepared repository, the repository of the PR). The remark text and the reason are cut at 2,000 characters each so that the request fits in the limit of a task description. Which remark a follow-up task is for is kept in the record of its creation (`derivedFrom.deferredRemarkId`), and when a follow-up task for the same remark exists, it is not created twice (no string inside the request is used for matching). The follow-up task is not a candidate for taking over the original (merged) PR in its request ([Taking over an existing PR](tasks-and-steps.en.md#taking-over-an-existing-pr)). For a task whose PR was not merged or that was cancelled, none is created.
  - The result is recorded in `DeferralHandled` (the remark ID, the handling, and the URL of the created issue, the ID of the created follow-up task, or the reason it failed) and kept in `Task.remarks[].deferral.handled`. When it fails, the decision does not change and it is not retried. In a task of the security plans, in a project with no GitHub account chosen, or for an implementation with no PR, no issue is created and that reason is recorded. When it fails before creating the issue (for example, the token cannot be read), the result of the issue is recorded as a failure too.
  - A failure after which the issue may exist is recorded with a reason that says so: when the request to create the issue went over its limit, got no answer, or failed on GitHub's side (5xx) (`deferral.issueUncertain`; an answer in which GitHub refused the request (4xx) means nothing was created, so that reason is recorded as it is), and when the daemon stopped after the decision to create an issue and before the result was recorded (`deferral.issueInterrupted`; recorded by the PR check after a restart; not recorded for a cancelled task; `settleInterruptedDeferralIssues`). Neither is retried (a person checks GitHub).
  - The record of decided proposals on the approval screen (shown only while the implementation waits for approval) shows the handling and its result (a link to the issue, the reason it failed, or that the follow-up task is created after completion). When a remark's handling failed, the record is shown open. The handling can be chosen only for a remark with "defer" chosen, and while the handling that creates a GitHub issue is chosen, the screen says that deciding creates it right away.
  - The task details also show the list of remarks whose handling creates a follow-up task or an issue, with the result, whatever the task's state (`DeferralHandledNotice`, `handledDeferrals`). The result of a follow-up task (a link to the follow-up task, or the reason it could not be created) is recorded after the original task completes, so it is read here. When a remark's handling failed, the list uses the warning color. For a cancelled task, only the remarks with a recorded result are shown.
- PR comment (`announceDeferralDecisions`, `buildDeferralNotice`): on every decision, sacty posts one comment on the implementation PR with the decisions and the list of those remarks.
  - For a remark imported from a comment of that PR, it shows the remark text, the reason, and a link to the original comment. For a remark written on the sacty screen, it shows only the remark ID and the decision (text written on the screen, and the response to it, are not put on the PR).
  - For a remark decided to be deferred, it shows the handling (the URL of the created issue, that the issue could not be created, that a follow-up task is created after the task completes, or that nothing is done).
    When the issue could not be created, the reason is on the same line (`issueFailureLine`; PBI-450). From the already-redacted reason recorded in the activity log, it also hides URL credentials (`redactUrlCredentials`) and internal paths (`withoutInternalPaths`), puts it on one line, and cuts it at 500 characters (hide, then one line, then cut). It never says "it is in the activity log".
  - The task-screen link in the last sentence of the decision has a note (see "The note on task-screen links" below).
  - It starts with a marker (`<!-- sacty-deferral:<task ID>:<which decision> -->`). The remark text and the reason come from outside, so secrets are hidden first, then they are cut at 600 characters, a zero-width space is put after `@`, and they are shown as quotes (`askQuote`).
  - The result is recorded in `DeferralDecisionsPosted` (the PR number, which decision, and the URL of the comment or the reason it could not be posted). When it cannot be posted, the decision and the task's state do not change and it is not retried. In a task of the security plans, when the PR is not open, or in a project with no GitHub account chosen, sacty does not comment and records that reason. For an implementation with no PR (no changes), nothing is recorded.
  - This comment is not imported as a PR comment (only one that starts with the marker and was posted by the task's account; `isDeferralNotice`).
- How it is passed to the implementation (`remarkLines`, `ownerDeferralLines`): a remark proposed for deferral in an earlier submission or an earlier run is left out of the remarks to respond to and is passed as data separate from the instructions (the remarks a person decided to defer `deferredByPerson`, and the proposals awaiting a decision `awaitingDecision`). Neither is fixed in this PR, and no response is written for them. This data is passed even when there is no other remark to respond to. For a proposal awaiting a decision, the instructions say that sacty handles the replies on the PR (they do not assert that a reply will be or has been posted: a proposal from a run that did not reach submission has not been replied to yet, and a proposal on a remark written on the sacty screen or in a task of the security combination is not replied to). The remark text has its secrets masked and then only its first 600 characters are included; a text that was cut carries a mark (`truncated`), and the instructions say that it is only the beginning. A remark a person decided to fix in this PR is passed as a send-back remark marked as the person's decision, and it is not proposed again.
- How it is passed to the review (`deferralReviewLines`): in a re-review by the review child task of the implementation PR, the instructions say the following.
  - A proposal awaiting a decision: when the remark is of suggestion weight, it is not counted as unaddressed, not raised again, and not used as grounds for the verdict. When it is of must-fix weight, it stays unaddressed until a person decides to defer it.
  - A remark a person decided to defer: the remark text and the reason the implementation wrote are passed as data separate from the instructions (`deferredByPerson`). Whatever its weight, it is not counted as unaddressed, not raised again, and not used as grounds for the verdict. Only when this change made its impact large is it raised as a new finding. The remark text and the reason have their secrets masked and then only their first 600 characters are included; a text that was cut carries a mark (`findingTruncated`, `proposalTruncated`), and the instructions say that it is only the beginning.
  - Suggestions declined in the sorting before reworking are passed as separate data (`declinedByAuthor`) ([The review child task of a PR](#the-review-child-task-of-a-pr)).
- When a rework that changes nothing has proposals: when the implementation does not change the head and either declines or proposes to defer every remark of the latest round (including a proposal an earlier run declared and that was carried over), sacty submits and replies ([Unfinished implementations and reworks that change nothing](tasks-and-steps.en.md#unfinished-implementations-and-reworks-that-change-nothing)). The judgment of the same head starts after a person has decided all the proposals not yet decided (including proposals of earlier submissions and of remarks of earlier rounds) ([The review child task of a PR](#the-review-child-task-of-a-pr)).
- When the PR is merged while proposals are undecided, the merge is taken as the approval (the proposals stay undecided, and the replies on the PR stay as proposals).

### How the send-back judgment text is shown

The judgment text for where to send a task back (`reason` of `ReworkJudged`) can run 600 to 1,000 characters, which is hard to read when shown as it is. The screen shows the gist first and lets you open the full text (`summarizeDecision`).

- Gist: up to the first two sentences (split at a Japanese full stop, an English period followed by a space, or a line break; a full stop inside brackets does not split). If it is longer than 160 characters, it is cut at 160 characters and "…" is added. If the full text is the same as the gist, nothing is collapsed.
- Where: the send-back row in the activity (the gist in the row, the full text in the details), the send-back target in the PR card (`prRework`; the gist, with the full text to open below it), and the reason it could not be decided in the things for a person to check.
- Not changed: the activity record (`reason` of `ReworkJudged`) and the judgment text passed to the rework run ([how the judgment text of the step to redo is passed](#ai-review-comments)) stay in full.

### Design fixes (sacty-design-edit)

Related ADR: [The step to redo for PR comments is decided by the weight of the decision, only a change of policy goes back to design, and a local design fix goes into the implementation PR](../adr/20261121-0241-rework-target-by-decision-weight.md)

Only in a round that sends a comment on an implementation PR back to Implementation, and only when the design is approved, the implementation instruction adds how to give design fixes.
This path puts a local fix of the design document into the implementation PR and approves it when that PR is merged. A change of policy does not go through this path; it is raised as a change proposal ([Change requests](tasks-and-steps.en.md#change-requests)).

- How to give them: the implementation writes a `sacty-design-edit` block in its output. The shape is `{"sacty-design-edit": {"edits": [{"remarks": ["comment ID"], "viewpoint": "TV-n", "field": "title", "before": "approved original text", "after": "text after the fix", "reason": "reason", "sensitive": false}]}}`.
  - Edits are replacements (`before` and `after`); the whole design is not asked for.
  - `viewpoint` and `field` are written only for a fix to the wording of a test viewpoint. `field` is one of `title`, `input`, and `expected`.
  - `sensitive` is a mark the implementation puts on a fix that touches security, authorization, the shape of stored data, or migration. sacty does not check by words.
- Checks: a fix that matches any of the following is not applied. The reason for a fix that is not applied is kept in `DesignEdited` in the activity and in the PR body, and the implementation submission continues. Whether a fix stays within the scope is not checked by machine (the next round's AI review and the person who merges look at it).
  - `remarks` is not among the comments handled in this round.
  - `sensitive` is true. The same applies to a round where a person said "fix it in the implementation step".
  - `before` is empty, is not in the approved design or in the design file on the task branch, or appears in two or more places.
  - `before` of a body fix is in the first three sections (Scope, Open questions, Decided by default) or in the "Test viewpoints" section, or overlaps them even in part (the whole range of `before` is looked at).
  - `viewpoint` of a viewpoint fix is not an approved viewpoint, `field` is not one of the three names, `before` is not in exactly one place in that field of that viewpoint (and in that viewpoint's row of the design file, when there is one), or `after` changes the viewpoint's ID or the number of viewpoints.
  - It adds, removes, or changes a heading line (the list of headings is compared over the whole document after the fix. What counts as a heading follows a Markdown parser (CommonMark): underlined headings, headings inside quotes or lists, and indented headings are counted, and a `#` line inside a code block is not. When a document cannot be parsed, no fix is applied), `before` or `after` is over 2,000 characters, or it is the 11th or later.
  - The design file cannot be read (when it cannot be read, no fix is applied). An interruption by pause or cancel is not counted as "cannot be read": neither `DesignEdited` nor the run completion is recorded, and the run stops like a failed run (a resume redoes the implementation run).
  - `before`, `after`, or `reason` is not a string, or, for a viewpoint fix, the field after the fix is empty or `after` contains a line break.
  - `before`, `after`, or `reason` contains a secret value, or `before` or `after` contains an internal path (the `reason` of an applied fix is recorded with internal paths replaced). A name with `@` does not stop the fix.
  - The same output also has a change proposal. Nothing is applied and only the proposal is handled.
  - The block cannot be read. The fixes are treated as none, and the PR body says that it could not be read.
- Applying: the fixes that are applied are recorded in the event `DesignEdited` (`packages/core`).
  - It records the implementation submission round, the run ID, the whole design and test viewpoints after applying, the fixes applied, and the fixes not applied with their reasons (after redaction).
  - The projection replaces `approved.design`, `outputs.design`, and `testViewpoints` with the whole text and test viewpoints after applying, and marks the design's self-review and provenance classification as not recorded.
    It does not change the viewpoint IDs, `approved.design.at`, `implementHistory`, or `implementBase` (unlike `ChangeApplied`, this continues the same PR, so the explanations and the test mapping carry over).
  - When the implementation PR's commit stops after the push reached the remote and before it was recorded, and the task branch head already has the fixed file on resume, the fixes are not applied again (the fixes applied to the file at the last recorded push give the same file as the head, or `before` is absent and `after` is in exactly one place). If a fix still does not apply, the push stops and names which fix.
  - A second record for the same run is not made. It is recorded before the implementation submission is recorded. When a resume finds a record for the same run, it uses that record without checking again.
  - Later reviews, fixes, and redoing the design use the fixed design as the base.
- How it shows on the PR: the implementation PR's commit writes the design file by applying, in the order recorded, the replacements of `DesignEdited` not yet in a commit.
  - The design file stays in `keep` and is replaced with the whole fixed text (`overrides`). The replacements are applied to the file at the head of the task branch (keeping what a person fixed and the test viewpoints section). A viewpoint fix is applied only inside that viewpoint's row.
  - `before` is looked for in both the approved design and the file after the replacements. For a task without the file, only the approved design and the PR body are fixed.
  - The "Design fixes" section of the PR body lists, for each fix, the before, the after, and the comment. Fixes not applied are listed with their reasons.
  - In the body, `remarks` shows only the IDs of this round's comments, `viewpoint` only an approved viewpoint ID, and `field` only one of the three names, as they are; any other value becomes "(invalid value)".
    Text put in the PR body and events is redacted for secrets, has internal paths replaced, and has `@` neutralized.
  - Merging the implementation PR does not read the PR's design file back into the approved design (the approved design stays as the applied version).
- Activity: the task's activity screen shows a line with the number of fixes applied and not applied (in both languages).
- No going back: the previous version's daemon cannot read `DesignEdited` (`toEvent` in `activity.ts` fails on a kind it does not know, and the daemon does not start). After one is recorded, you cannot go back to the previous version.

Code: `packages/core/src/events.ts` (`DesignEdited`), `packages/core/src/projection.ts` (`DesignEdited` in `applyEvent`), `apps/daemon/src/activity.ts` (`toEvent`)

### The note on task-screen links

The four notices on the PR (things for a person to check, the work went back to design, the review stopped, and the decision on deferral proposals) contain a link to the task screen (PBI-450).
The screen runs on the requester's machine, so a person who reads only on GitHub cannot open it.
So right after the sentence with the link, one sentence is added: "タスクの画面は、依頼した人のマシンでだけ開けます。" ("The task screen opens only on the requester's machine."; `taskLinkNote`).

- It is added when the host of the screen URL (`SACTY_WEB_URL`; default `http://127.0.0.1:4700`) is `127.0.0.1`, `localhost`, or `[::1]` (`localOnly` of `taskLink`). It is not added for other hosts (for example `https://sacty.example.com`).
- It is added also when the value cannot be read as a URL. An unreadable URL may not open either, so the note errs on the side of warning people who cannot open it.
- The link is used only to mean "the task that made this PR" and to guide the requester's actions on the screen (sending back, resuming). What a reviewer needs to read is put in the PR.

If no cause is chosen, the cause is not judged and the rework has an unknown cause (no extra run is made just for the judgment).

  - A miss for the same review is recorded once.
  - The activity log from before causes were recorded is read as it is (a request for changes without a cause is in the summary it counts as a miss when a miss record (`GuardianMissed`) comes right before it, and as "unknown cause" otherwise; a miss already recorded is still counted as a miss).

### Tasks stopped by the limit in an earlier version

An earlier version turned a request for changes made after a person's requests to the same step reached the limit (3) into `TaskEscalated` (`too_many_changes`; the remaining comments are in `pendingRemarks`) and stopped, so that a person chose between approving and "request changes beyond the limit". There is no limit now, and it is no longer recorded. A task that has that record can be moved on as follows.

- Reading: `overLimit: true` of `ChangesRequested`, and `too_many_changes` and `pendingRemarks` of `TaskEscalated`, are read as they are. `overLimit` of a newly recorded `ChangesRequested` is always false. The activity display, `get_task`, and the screen show these as a record from an earlier version in words that say so.
- Screen: the approval screen of a task stopped with `too_many_changes` or `rework_confirmation` shows the remaining comments one by one as written, and a separate field for a person's notes. A person can choose between requesting changes and approving (a step that made a PR is not approved from the screen, as now).
- Request changes: when requesting changes during an escalation, `requestChanges` lines up the remaining comments in their original form (text, `source`, `origin`, `fixOf`; `id` is assigned again), and then a person's notes (`comments`; one per line) after them, as `remarks`.
  - They are carried over when the request goes to the step that escalated. `rework_confirmation` is carried over whichever step is chosen. For `too_many_changes` sent to another step, only a person's notes are used.
  - The checks on length and count (2,000 characters per comment, 50 comments) apply only to a person's notes. A remaining comment is not refused, however long it is.
  - With neither remaining comments nor notes, it is refused with `gate.remarksRequired` and nothing is recorded.
  - The "request changes beyond the limit" setting (`continueOverLimit`) sent by the screen or a call of an earlier version is ignored without refusing.
  - The reply for a comment that has `origin` is posted to the PR as a reply to the original comment, at the same time as for the comments of the current PR (when that PR's step is waiting for approval) ([Replies about how remarks were handled](#replies-about-how-remarks-were-handled)).
- `request_changes` of `sacty mcp` does not send back a task in an escalation ([MCP server](mcp-server.en.md)).
