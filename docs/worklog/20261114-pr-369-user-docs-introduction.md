# ユーザードキュメントに、sacty の概要を図と画面で伝える紹介のページを足す

- 日付: 2026-11-14（UTC）
- タスク: なし
- PR: #369
- ブランチ: ccr-f984f788-qo6ni0
- 関係する ADR: [ユーザードキュメントに紹介のページを置き、その画面は紹介のためのデータで撮る](../adr/20261114-1318-user-docs-introduction-page.md)

## 目的

sacty をはじめて知る人が、細かい設定や実装に入る前に、sacty で何ができて何がうれしいのかをつかめるページを作る。
長い文章や実装の細部を避け、一般的なプロダクトの紹介のように、図とスクリーンショットで「使ってみよう」と思ってもらえる形にする。

## したこと

経過は3段ある。最初の版を作り、依頼でコンテキストの層とゲートウェイを足し、その後に内容・図・構成を一から確かめ直して作り直した。
ここには、いまの形を書く。確かめ直しで見つけたことは「レビューの指摘と対応」にある。

- `docs/user/introduction.md`・`introduction.en.md`（sacty の紹介）
  - 冒頭の一文と、依頼から PR での判断までの流れの図。進め方（すぐ実装・まず再現・要求要件と設計を承認してから実装）の説明。
  - 困りごとを5つ挙げ、同じ順で特長を5つ書いた（困りごとと特長が1対1）。
    1. 背景を説明し直さなくていい（情報収集・コンテキストの層）
    2. AI の成果物を、AI が先に確かめる（セルフレビュー・PR のレビューの子タスク・マージの後の監視）
    3. あなたは、出番のときだけ判断する（並行実行・あなたの出番・通知・PR での承認と差し戻し）
    4. 回すほど賢くなる（監査・改修の提案・メモリー）
    5. 安心して任せられる（コンテナ・ゲートウェイ・GitHub の読み取りだけ・予算・作業履歴）
  - 任せられる作業の表、依頼の仕方、使うのに要るもの（macOS・Docker・GitHub CLI・Node.js・AI の契約）、始め方のリンク。
  - 工程・設定・コードの名前は本文に出さず、詳しいページへリンクした。
- 図（`scripts/docs-diagrams/diagrams/intro.mjs`。`npm run docs:diagrams` で日英の SVG を作った）
  - `intro-flow`：上の段があなた（依頼する・判断する）、下の段が sacty（下調べ・計画・作業・AI のレビュー）。判断から作業へ戻る線で、承認が工程ごとにあることを表す。
  - `intro-loop`：完了 → 監査 → 改修の提案 → 採用 → 改修のタスク。知見はメモリーに残り、次のタスクが読む。
  - `intro-context`：sacty の既定の上に、継承元（全社・チームは例）とプロジェクトのコンテキストを重ねる。
  - `intro-gateway`：社内の API・MCP サーバー・GitHub はゲートウェイが鍵を付けて中継する。AI のサービスは、エージェントが AI の認証で直接呼ぶ（別の線で描いた）。
- 画面（`intro-tasks`・`intro-audit`。日英）
  - 紹介のためのデータ `scripts/docs-screenshots/seed-intro.mjs` を足した。あなたの出番が2件（実装の PR・設計の PR のマージ待ち）、マージの後の監視中が1件、完了が4件と、監査の記録（判断待ちの提案・採用して改修済みの提案・メモリー）。
  - 承認待ちの PR には、レビューを終えた PR のレビューの子タスクを入れた。入れないと、デーモンが子タスクを作って実行し、失敗して「エラーで一時停止」が写る。
  - 監査の画面は、モックではなく、作業履歴の監査の記録（`AuditQueued`・`AuditSurveyed`・`AuditDeepDived`・`AuditCompleted`・`AuditProposalAdopted`）で撮った。
- 撮影の仕組み（`scripts/docs-screenshots/`）
  - `capture.mjs`：データを場面（`docs`・`intro`）ごとに分け、引数で場面を選べるようにした。
    ページの上から要素の下の端までを撮る `until` を足した（言語で行の折り返しが変わっても、区切りのよい所で切れる）。
    撮るときの設定に `update_check: false` を足した（新しい版のお知らせが、リリースの有無とネットワークによって写り込むため）。
  - `seed-lib.mjs`：`seed.mjs` にあった、イベントを書く道具を分けた。`seed.mjs` と `seed-intro.mjs` が使う。
  - `seed.mjs`：道具を `seed-lib.mjs` から読むようにした。入れるデータは変えていない。
- docs の規則と記録
  - `docs/README.md`：「ユーザードキュメントの書き方」に紹介のページの規則を、スクリーンショットの規則に場面の分け方を足した。
  - ADR を足した（上のリンク）。
  - ユーザードキュメントの目次の先頭に紹介のページを置き（番号を1つずつ繰り下げた）、入口の文とリポジトリの README（日英）から案内した。

## 確かめたこと

- 本文と図の主張を、仕様書（タスクと工程・承認と差し戻し・コンテキストの合成・監査・メモリー・ゲートウェイ・秘密情報・エージェントの実行）とユーザードキュメント（取り込み・通知・成果の書き出し・マージの後の監視・スケジュールタスク・はじめに）で、1つずつ確かめた。
- `seed.mjs` の道具を分ける前後で、入れたイベント（125 件の種類・中身・相対の時刻）を書き出して比べ、同じだった（`cmp` で一致）。
- `node scripts/docs-screenshots/capture.mjs intro`：日英の `intro-tasks`・`intro-audit` を撮った。
  既存の場面（`docs`）も、出力先を一時の場所にして日本語で撮り、14 枚すべてが撮れることを確かめた（リポジトリの既存の画像は撮り直していない）。
- `npm run docs:diagrams`：紹介の図の幅・高さの警告なし（出る2件は既存の図のもの）。図は、ライトとダークの表示で描画して、文字のはみ出し・線と見出しの重なりが無いことを目で確かめた。
- 紹介のページを HTML にして全体を撮り、図と画面の並びと分量を確かめた（日英）。
- `npm run lint`・`npm run typecheck`・`npx vitest run tests/docs`（3 ファイル・93 件）：通った。
- `npm run build`：通った（撮影のため）。

確かめるときの環境：リポジトリが求める Node.js 26.13.1 を npm の `node` パッケージで用意した。Playwright のブラウザーは環境にあるもの（Linux の Chromium）を使い、
起動の引数（ブラウザーの場所・`LANGUAGE`）を前置きのスクリプトで足した。このスクリプトはリポジトリに入れていない。
Linux の Chromium は、日付の入力欄の書式を `LANGUAGE` で決めるので、指定しないと日本語の画面でも `mm/dd/yyyy` になる。

確かめていないこと：`npx vitest run`（全体）は流していない。macOS では撮っていない（フォントは画面が同梱するものなので同じだが、細部の描画は違いうる）。

## レビューの指摘と対応

一から確かめ直したときに、最初の版・コンテキストとゲートウェイを足した版に見つけたこと。

| 指摘 | 対応 |
| --- | --- |
| 「AI のコンテナに渡るのは、その実行のあいだだけ使えるトークン」は誤り。AI のサービスの認証（API キー・サブスクリプションの認証）は、コンテナに渡る | 鍵の扱いを、ゲートウェイが持つもの（社内の API・MCP サーバー・GitHub）と、コンテナに渡るもの（AI のサービスの認証）に分けて書いた。図にも、AI のサービスを直接呼ぶ線を描いた |
| 「AI の呼び出しも、設定すればゲートウェイを通せる」は言い過ぎ。通せるのは、Codex を Bedrock か OpenAI 互換の接続先で使うときだけ | 「接続先によっては、ゲートウェイ経由にできる」にし、ゲートウェイのページへリンクした |
| 「あなたに届くのは、AI のレビューを通った PR」は言い過ぎ。ドラフトで待たせるのは実装の PR だけで、sacty はマージを止めない | 「実装の PR は、指摘が無くなるまでドラフトにしておき、無くなったらドラフトを外す」と、していることだけを書いた |
| 冒頭の図が、承認を最後の1回に描いていた。大きな作業では、要求要件・設計・実装のそれぞれで承認する | 図を、あなたと sacty の2段にし、判断から作業へ戻る線を足した。本文にも、進め方ごとの承認の違いを書いた |
| 「Issue・PR・JIRA にラベルを付けて渡す」は、PR の扱いが違う。ラベルの付いた PR は、レビューだけをする | Issue・JIRA の依頼と、PR のレビューを分けて書いた |
| 「社内の資料を読む」「Slack で知らせる」「Confluence へ書き出す」は、設定や接続が要る | 「つないでおけば」「設定すれば」を足した |
| 「組織・チーム・プロジェクトの層」は、決まった3層のように読める。層は `extends` の鎖で、数と分け方は自由 | 本文は「たとえば」とし、図は全社・チームを例として点線にした。下の層で変えられないように固定できることも書いた |
| 使うのに要るものに、Node.js と AI の契約が無かった | 「使ってみる」に足し、オープンソース（MIT）であること・AI の利用料は契約にかかることも書いた |
| 画面の画像が、紹介に向いていなかった。タスクの詳細は AI のレビューの状況が「分かりません」と出ていて隣の文と合わず、監査はモックの表示があり、ダッシュボードは5件のうち3件がエラーや上限で止まっていた | 紹介のためのデータを作り、タスクの一覧と監査の画面を撮り直した。タスクの詳細は載せるのをやめた |
| 困りごとと特長の対応が弱く、特長 6 は文・図・表で同じことを繰り返していた | 困りごとと特長を同じ順の5つにそろえ、重なっていた文を削った。ダッシュボードの節は、特長 3 にまとめた |
| マージの後の監視・タスクの分割・並行実行に触れていなかった | 特長 2・特長 3 と、任せられる作業の表に足した |
| 紹介のページをどう書き、どう保つかの規則と、決めた記録が無かった | `docs/README.md` に規則を足し、ADR を書いた |

## 残したこと

- 既存の場面（`docs`）のスクリーンショットは撮り直していない。
  いまの版で撮ると、承認待ちの PR にデーモンが PR のレビューの子タスクを作り、その実行が失敗するので、「エラーで一時停止」のタスクが1件写る（既存の `task-list.png` に写っている）。
  直すなら、`seed.mjs` にもレビューを終えた子タスクを入れる。この PR では、既存のデータは変えていない。
- 紹介のページに、実行中のタスクは写していない。撮るときは実際の AI・Docker を使わないので、実行中の状態を保てない。
