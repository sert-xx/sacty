# 最終レビューの判定基準を、実装の工程に先に渡す

- 日付: 2026-11-08（UTC）
- タスク: PBI-315
- PR: #321
- ブランチ: feat/issue-315-review-criteria-in-implement
- 関係する ADR: [最終レビューの判定基準を、同じ定義のまま実装の工程に先に渡す](../adr/20261108-0300-pass-final-review-criteria-to-implement.md)

## 目的

最終レビューで不合格になる基準を、実装の工程で提出の前に確かめさせ、実装と検証をまるごとやり直す回数を減らす。

## したこと

- `apps/daemon/src/final-review-criteria.ts` に、基準の言葉の定義（`FINAL_REVIEW_CRITERIA`）と、実装の指示の節（`implementReviewCriteriaLines`）を置いた。
- 最終レビューの指示（範囲外の変更・共有の仕組み・作業用のファイル・観点・受け入れの深さ）を、同じ定義で組むようにした。指示の文は変えていない。
- 実装・修正の工程のすべての分岐（`implementSelfReviewLines`）に、セルフレビューと提出の前の検証の前に基準の節を入れた。
  - 範囲外の変更の基準は、セキュリティ対応には入れない。
  - 観点を検証していないテストの基準は、テストの仕組みがあるタスクだけに入れる。
  - AI のレビューの過去の指摘への応え方は、その指摘があるときだけ入れる。
- 受け入れの深さの行（今まではテストの仕組みが無いタスクの分岐だけ）を、どの実装の指示にも入れた。要求要件を省いたタスクでは「依頼の受け入れ条件」と書く。
- 範囲の拠り所は、タスクの進め方の言葉にした（設計あり・要求要件だけ・不具合の修正・依頼だけ）。

## 確かめたこと

- `npm run lint`・`npm run typecheck`・`npx vitest run tests/docs`：通った。
- `npx vitest run --no-file-parallelism`：211 ファイル、4378 件が通った（3 件は既存のスキップ）。
- 最終レビューの指示が一字一句変わっていないこと：変更前（main）と変更後で、6 通りのタスク（AI の指摘あり・テストの仕組みなし・テストのコマンドあり／なし）の最終レビューの指示を書き出して比べ、同じだった（121,295 バイト）。
- 指示の長さ：要求要件・設計のある最小のタスクの実装の指示が 4,370 文字から 5,677 文字、要求要件を省いたタスクが 4,325 文字から 5,616 文字になった（約 1,300 文字増）。実際のタスクでは、タスクの内容・承認済みの成果物が加わるので、割合はこれより小さい。
- 修正を一時的に戻して、新しいテストが失敗することを確かめた：基準の節を外す（9 件失敗）・最終レビューの指示から定義を外す（4 件）・AI の指摘の基準を外す（1 件）・セキュリティ対応に範囲の基準を入れる（1 件）。
- 確かめていないこと：実際のエージェントで差し戻しが減るか（評価・実験はしていない）。
