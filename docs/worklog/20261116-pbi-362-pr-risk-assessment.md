# PR のリスク評価を出す

- 日付: 2026-11-16（UTC）
- タスク: PBI-362
- PR: #393
- ブランチ: claude/issue-362-pr-risk-assessment-688a67
- 関係する ADR: [PR のリスク評価を出す（レビューの省略・自動のマージには使わない）](../adr/20261116-1632-pr-risk-assessment.md)

## 目的

人が PR をどの深さでレビューするかを、PR の説明とレビューのコメントから決められるようにする。
Meta の RADAR の考え方のうち、まずリスク評価を出すことだけを入れる（評価によってレビューを省く・自動でマージすることは入れない）。

## したこと

- RADAR と Diff Risk Score の公開されている一次情報（論文2本と Meta のブログ）を読み、段・入力・合図・結果の使い方をまとめた（ADR の背景）。
- リスク評価のイベント `PullRequestRiskAssessed` と、段階（`RiskLevel`）・リスクの合図（`RiskSignal`）・評価（`RiskAssessment`）の型を足した。タスクは最後の評価を持つ。
- `apps/daemon/src/risk-assessment.ts` を足した。段階の基準と答えの形、PR を作る前の評価の指示、答えの読み取り、PR の説明・レビューのコメントの節の組み立て。
- 実装の PR を作る・更新する前に、オーケストレーターのエージェントで評価して記録し、PR の本文（決まった形は結論の後、テンプレートに沿わせる形は末尾の付記の先頭）に載せるようにした。
- GitHub の PR から取り込んだレビューのタスクのレビューの指示に、評価の基準と答えの形を足し、答えを読んで記録し、投稿するレビューの本文（判定の後）に載せるようにした。
- 評価の指示に、重要な制約として、RADAR に関するスキルやコンテキストが読み込まれているときはその内容を基準より優先することを足した（作業の途中の人の指示）。
- 画面のタスクの詳細に「PR のリスク評価」の欄を、作業履歴に評価の行を足した（日本語と英語）。
- 既定のレビューのスキルに、依頼した側がリスクの評価を求めたときの扱いを1項目足した。
- 仕様書（`risk-assessment`・`approval`・`tasks-and-steps`・`event-log`）、ユーザードキュメント（`tasks`・`intake`）を日英で直した。

- `npm run lint`: 成功（サイズ上限を超える既存の `daemon.test.ts` は警告付きで除外）。
- `npm run typecheck`: 成功。
- `npx vitest run --no-file-parallelism`: 成功（230 ファイル、4,653 件成功、1 件スキップ）。
- `npm run build`: 成功。
- 足したテスト：
  - `apps/daemon/src/risk-assessment.test.ts`：答えの読み取り（合図があれば高・形の違う答え・上限・秘密の値を伏せてから切る）、PR を作る前の評価の結果（評価できた・答えを読めない・実行の失敗・例外・予算の上限）、節の組み立て、PR の本文（位置・長さの上限・テンプレート・評価できなかったとき）、レビューの指示・読み取り・本文（子タスクには載せない）。
  - `apps/daemon/src/risk-assessment-service.test.ts`：サービスが偽の実行器で評価を実行して記録すること、失敗しても止めないこと、同じコミットを評価し直さないこと。
  - `packages/core/src/risk-assessment.test.ts`：記録の投影と費用、形の検査、理由の文言の日英。
  - `apps/web/src/components/risk-assessment.test.ts`：欄と作業履歴の行の日英。
- 画面：スクリーンショット用の架空のデータに評価の記録を一時的に足し、別のポートの一時のインスタンスで、タスクの詳細に「PR のリスク評価」の欄が出ることを確かめた（データの変更はコミットしていない）。
- 確かめていないこと：
  - PR の作成の流れ（プッシュから PR の作成まで）と、レビューの工程の完了から投稿までを通したテストは足していない。流れを通す偽物は `daemon.test.ts` の中にあり、そのファイルは別の作業で分割中のため。
  - 本物のエージェントでの評価（評価の中身が妥当か）は確かめていない。

## レビューの指摘と対応

| 指摘（1回目。提案3件） | 対応 |
| --- | --- |
| JSON として読めない評価（末尾のカンマなど）が、投稿するレビューの本文に残る | 評価の見出しを含むコードブロックごと取り除くようにした（`withoutRiskBlocks`）。テストを足した |
| 同じコミットでも、評価できなかったときは評価し直すことが、ユーザードキュメントと ADR に書かれていない | `docs/user/tasks`（日英）と ADR の記述を直した |
| `docs/spec/event-log` のイベントの種類の数が 122 のまま | 123 に直した（日英） |

| 指摘（2回目。要修正2件・提案1件） | 対応 |
| --- | --- |
| `signals` が配列でない答え（文字列・`null`・欠落）を、合図なしとして受け入れ、低い段階を載せる | 配列でない・知らない合図が混ざる答えは、読めないものとした（同じ原因の別の現れとして、知らない合図を黙って除くこともやめた）。テストを足した |
| 評価の見出しを含むコードブロックを無条件に除くので、レビューの中のコード例も消える。評価させていないレビューにも効く | 中身が評価の答えの形で始まるコードブロックだけを除き、評価させたレビューにだけ使うようにした。評価させていないレビューでは、評価の JSON の読み取りも除去もしない。テストを足した |
| 評価を使い回す条件は「同じ内容」ではなく同じコミット | `docs/user/tasks`（日英）を直した |

## 残したこと

- PR の説明・レビューのコメントの言語を選ぶ設定は無い。リスク評価の節の見出し・項目の名前は、sacty のほかの固定の文と同じく日本語。画面と、評価できなかった理由の文言は、日本語と英語の両方がある。
- 評価によってレビューの深さ・自動化の度合いを変えること。
- PR のレビューの子タスクのコメントに評価を載せるかどうか（人が決める）。
- 要求要件・設計の PR の評価。
- PR の作成の流れとレビューの投稿の流れを通したテスト（`daemon.test.ts` の分割の後）。
- 評価が当たっていたかの振り返り。
