# 依頼が軽いときは、自己レビューの観点を絞る

- 日付: 2026-11-17（UTC）
- タスク: PBI-369
- PR: #407
- ブランチ: feat/pbi-369-self-review-cost
- 関係する ADR: [依頼が軽いときは、自己レビューの観点を絞る](../adr/20261117-0359-narrow-self-review-for-light-requests.md)

## 目的

2 つのリポジトリの README に節を 1 つ足すだけの依頼で、要求要件の工程が $3.03、設計の工程が $3.36 かかり、その 44〜47% が自己レビューの担当（10〜12 件）だった。
依頼が軽いときに、自己レビューの費用と時間を、依頼の大きさに見合うものにする。

受け入れ条件は、リポジトリの持ち主の決定に合わせて、着手のときに次のとおりに固めた。

1. 工程を選ぶ時点で、オーケストレーターが依頼の大きさ（軽い・通常）と理由を判定し、記録する。セキュリティにかかわる変更・取り消しにくい変更を含む依頼は、軽いと判定しない。
2. 判定と理由を、タスクの詳細に出す。人が、タスクごとに「通常の深さで」と上書きできる。
3. 軽いタスク（上書きしていないもの）の自己レビューは、「要件への適合」と「横断」の 2 つの観点で動く。上位の段階の担当は 1 段下げ、横断の 2 回目は省く。リポジトリに独自の決まり・スキルがあれば、その観点も残す。
4. 軽くないタスク・判定の無いタスク・上書きしたタスクは、今までどおりの観点で動く。
5. 起動しなかった観点と理由が、記録に残る。
6. PR のレビュー（レビューの子タスク・取り込んだレビューのタスク）の観点は変えない。
7. 同じ依頼（README に節を足す）で、要求要件・設計の 1 工程が $1.5 以下になることを、実物で確かめる。届かなければ、残った費用の内訳を報告する。
8. 担当の完了を待つ間の、作業の進まない番と、成果物の 2 回の出力が起きていないことを、実物で確かめる。
9. 既定のコンテキストに、特定のリポジトリ・言語に寄せた記述を書かない。
10. 仕様書（日英）・ユーザードキュメント（日英）・ADR・作業履歴に反映する。

親の実行のコンテキストの大きさ（スキル・参照の読み込み方）は、範囲外。

## したこと

### 調べたこと（実行の記録。読むだけ）

- 元の依頼の要求要件の実行は、担当を 10 件起動していた（D-1・D-2・D-3・D-4・D-6・D-10・X-1・X-3、再レビューの X-1、出典の分類）。設計の実行は 12 件。どちらも、`must` が無く `should` だけを直した後に、X-1 をもう一度起動していた。「横断の 2 回目」は、この再レビューの X-1 を指すと読んだ。
- 要求要件の実行の費用は、記録の合計で $3.03（工程のエージェントのモデルが $2.41、担当のモデルが $0.62）。

### 変えたこと

- 判定：工程の選択の指示（`apps/daemon/src/prompts.ts` の `SELF_REVIEW_DEPTH_LINES`）に、依頼の大きさ（`selfReviewDepth`）と理由（`selfReviewDepthReason`）を答えさせる項目を足した。答えの読み取り（`extractStepPlan`）は、決めた値でない答えと、理由の無い `light` を、判定なしにする。
- 記録：`StepsChosen` に `selfReviewDepth`・`selfReviewDepthReason` を足した（`packages/core/src/events.ts`）。セキュリティ対応の組み合わせは、軽いと答えても通常にする。自己レビューをする工程が無い組み合わせには記録しない（`apps/daemon/src/service.ts` の `selfReviewDepthOf`）。
- 上書き：イベント `SelfReviewDepthChanged`、操作 `changeSelfReviewDepth`、API `POST /api/tasks/:id/self-review-depth` を足した。投影は、判定を `Task.selfReviewDepth`、上書きを `Task.selfReviewDepthOverride` に持つ（`packages/core/src/projection.ts`）。
- 指示：軽いタスクの自己レビューの指示に、観点を絞る行を足した（`lightSelfReviewLines`）。PR のレビューの工程と、自己レビューを省く工程には足さない。
- スキル：既定のスキル `review-dispatch` に、「軽い依頼の自己レビュー」の規則を足した（`SKILL.md` の規則 8、`references/self-review.md`、`references/viewpoints.md`）。作業の指示が明示したときだけ使う。`references/pr-review.md` には、対象が小さくても観点を絞らないことを書いた。実測と合わない「費用は小さい」の記述は消した。
- 画面：タスクの詳細の「工程の設定」タブに、深さ・判定の理由・「通常の深さで」の操作を出す（`apps/web/src/components/self-review-depth.tsx`）。作業履歴の行の文言を足した。文言は日英。
- docs：仕様書（`docs/spec/tasks-and-steps.md`・`context.md` と英語の版）、ユーザードキュメント（`docs/user/tasks.md` と英語の版）、ADR を直した。

### 自分で決めたこと（持ち主の確認は、まだ）

ADR の「実装で決めたこと」に書いた。要点は次のとおり。

- 「要件への適合」の観点は、`code` が C-1、`design-doc` が D-1、`user-doc` が U-1。
- X-2 は、実行した検証が失敗・警告を出したときだけ起動する。
- 再レビューは、前回の回で `must` を出した観点だけ。起動する観点が無ければ、再レビューをしない。
- 人の上書きは、軽いと判定されたタスクを通常の深さにすることと、その取り消しだけ。
- 上書きは、次の実行から使う。最初の工程は、工程の選択に続けて始まるので、判定を見てからの上書きは間に合わない（一時停止して再開すると、やり直しの実行から効く）。タスクの作成のときに先に指定する入力は、足していない。

## 確かめたこと

### 実物での確認

このブランチをビルドし、一時の `SACTY_HOME`・別のポート（4797・4798）で起動した。動いている sacty には触れていない。
依頼は、元の依頼と同じ文面・同じ形（リポジトリを指定せずに作り、動作確認用のリポジトリ 2 つを候補にし、進め方に「分割」を指定）にした。工程のエージェントは Claude Code（`claude_advanced`）。
設計の承認はしていない（子タスクも PR も作っていない）。確かめた後、タスクはすべて中止した。

| 依頼 | 判定 | 工程 | 自己レビューの担当 | 費用 | 元の費用 |
| --- | --- | --- | --- | --- | --- |
| README に節を足す（1 件目） | 軽い | 要求要件 | 3 件（D-1・X-1 は `standard`、X-3 は `entry`） | $1.16 | $3.03 |
| 同上 | 軽い | 設計 | 3 件（同上） | $1.22 | $3.36 |
| README に節を足す（2 件目。指示を直した後） | 軽い | 要求要件 | 3 件（同上） | $1.23 | $3.03 |
| README に節を足す（判定の後に上書き） | 軽い → 通常（人が指定） | 要求要件 | 11 件（D-1〜D-6・D-10・X-1・X-3、再レビューの D-4・X-1。D-2・X-1 は `advanced`） | $3.03 | — |
| タスクに優先度を付ける（振る舞いと保存の形を変える） | 通常 | 要求要件 | 11 件（D-1〜D-6・D-8・D-10・X-1・X-3、再レビューの X-1。D-2・X-1 は `advanced`） | $3.65 | — |

- (a) 軽い依頼は、軽いと判定された（上書きの確認のタスクを含めて 3 件とも）。理由は「変更の対象は 2 つの README の 1 節だけ。コード・公開している I/F・保存するデータの形は変えない。セキュリティにかかわる変更も、取り消しにくい変更も含まない」という内容だった。画面の「工程の設定」タブに、深さ・理由・「通常の深さで」のボタンが出ることを、ブラウザーで確かめた。
- (b) 軽い実行は、3 回とも担当が 3 件（ほかに出典の分類が 1 件）で、再レビューは行わなかった。起動しなかった観点と理由（「D-1 以外の必須観点と条件付き観点（軽い依頼：要件への適合と横断に絞る）」「X-2（軽い依頼：実行した検証が無い）」）が、自己レビューの報告に残った。
  - 1 件目の 2 回は、起動しなかった観点が、報告の `summary` ではなく `notReviewed`（見られなかった観点）に書かれた。意図して起動しなかった観点と、結果を得られなかった観点が混ざるので、指示に「`notReviewed` には書かない」を足した。直した後のコードでビルドし直して実行した 2 件目では、`notReviewed` は空で、起動した観点・起動しなかった観点と理由が `summary` に書かれた。
- (c) 軽い依頼の費用は、要求要件 $1.16・$1.23、設計 $1.22 で、どれも目標の $1.5 以下。1 件目の内訳は、工程のエージェントのモデルが $0.79・$0.88、担当のモデルが $0.36・$0.35。
- (d) 軽くない依頼は、通常と判定された（理由は、保存するデータの形と公開している I/F を変え、保存形式の版を上げると取り消しにくい、という内容）。担当は、今までどおりの観点・段階で動いた。
- (e) 軽いと判定されたタスクを、判定の直後に API で上書きした。要求要件の実行は、工程の選択と同時に始まっていて、上書きは間に合わなかった。タスクを一時停止して再開すると、やり直しの実行は通常の観点・段階で動いた。画面の「通常の深さで」「判定（軽い）に戻す」のボタンも、ブラウザーで押して、表示と作業履歴の行が変わることを確かめた。
- (f) 5 つの実行のすべてで、担当は起動のツールの結果で結果を返し（背景になった起動は 0 件）、実行の終わりの出来事は 1 回、成果物の出力は 1 回、通知の形の文面と待つためのコマンドは 0 件だった。

実行したタスクは 6 件（うち 1 件は、下の PR を作ったタスクのレビューの子タスク）で、費用は合わせて $15.00（情報収集・工程の選択・途中で止めた実行を含む）。

確かめられなかったこと・起きたこと。

- 軽い依頼の実行は、同じ依頼で要求要件 2 回・設計 1 回。ほかの種類の軽い依頼（コードの数行の変更など）と、実装・文書作成の工程は、実物では実行していない（指示の内容はテストで確かめた）。
- 判定の正しさは、軽い依頼 3 回（すべて軽い）と軽くない依頼 2 回（すべて通常）で見ただけ。境界の依頼（小さいがセキュリティにかかわる変更など）は、実物では試していない。
- 軽いタスクで `must` が出たときの再レビュー（`must` を出した観点だけを起動する）は、実物では通っていない（`must` が出なかったため）。
- Codex では実行していない。
- 軽くない依頼の 1 回目は、候補のリポジトリを 1 つにして、進め方に「設計だけ」を指定した。このタスクは PR で承認するタスクになり、自己レビューを省いて、動作確認用のリポジトリに要求要件の PR を 1 件作った（レビューの子タスクも作られた）。気づいてすぐに両方のタスクを中止し、PR が閉じ、ブランチが消えたこと、PR にレビュー・コメントが投稿されていないことを確かめた。この実行は、(d) の確認には使っていない。

## 残したこと

- 親の実行のコンテキストの大きさ（スキル・参照の読み込み方の見直し）。軽い実行でも、工程のエージェントのモデルの費用が $0.8〜0.9 残っている。
