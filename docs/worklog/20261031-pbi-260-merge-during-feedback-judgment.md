# 指摘の取り込みの判断の最中に PR がマージされても差し戻さず、最終レビューに PR の中身と作業領域の写しの違いを伝える

- 日付: 2026-10-31（UTC）
- タスク: PBI-260
- PR: #260
- ブランチ: feat/issue-260-merge-during-feedback-judgment
- 関係する ADR: なし（既存の方針（マージ＝承認、確認の途中で変わったら記録しない）どおりの不具合の修正と、指示の追記）

## 目的

実務での実証実験（小さな機能を要求要件 → 設計 → 実装で作るタスク）で見つかった 2 点を直す。

1. 実装の PR をマージしたのに、タスクが設計から差し戻された。sacty 自身のレビューを PR の指摘として取り込み、ゴールガーディアンが戻し先を判断している最中に、人が PR をマージした。sacty は判断の後に PR の状態を読み直さず、そのまま差し戻した。仕様の「マージ＝承認」「確認の途中で変わったら記録しない」に反する。マージは台帳に一度も記録されず、マージ済みのタスクが動き出して、予算も使った。
2. 最終レビューが「prettier も通った」と報告したのに、PR のブランチでは `prettier --check .` が落ちた。PR のコミットには sacty が `docs/sacty/` の下に成果物（要求要件・設計）を足すが、最終レビューが動く作業領域の写しにはそれが無く、指示にもその違いが書かれていなかった。

受け入れ条件の要点：

- 判断の最中にマージされたときは、差し戻さず、マージとして記録する。マージされていなければ今までどおり差し戻す。閉じられた場合なども、既存の仕様どおりに扱う。競合のタイミングを再現するテストがあり、修正を戻すと落ちる。
- 最終レビューの指示に、PR の中身と作業領域の写しの違いと、リポジトリ全体の検査は人の確認に回すことを足す。テストがある。
- 範囲に入れないもの：マージの後に届いた指摘を続きのタスクにするなどの新しい振る舞い、最終レビューの写しに成果物を足す変更（どちらも判断が要る）。

## 原因（コードで確かめた）

- `importFeedback` は、`judgeRework`（エージェントの実行。長い）の後に、取り込んだ指摘の状態（`pendingReview`）が変わっていないことだけを確かめ、PR の状態は読み直さずに `settleReview` → `requestChanges` へ進んでいた。`checkPullRequests` が PR の状態を読むのは、判断の始まる前の 1 回だけ。
- 差し戻すと承認待ちでなくなるため、60 秒ごとの確認はそのタスクの PR を見なくなり、マージが記録されないまま残る。

## したこと

- `importFeedback`（`apps/daemon/src/service.ts`）：判断（`ReworkJudged`）を記録した後、差し戻す直前に PR の状態を読み直す。
  - 開いたままなら、今までどおり差し戻す。
  - マージされた・マージされずに閉じられたなら、差し戻さず、`"pull_request_changed"` を返す。取り込んだ指摘と判断は作業履歴に残る。
  - 読んでいる間に、人が差し戻した・中止した・別の提出になったなどで状態が変わっていれば、記録しない（確認の途中で変わったら記録しない、と同じ）。読めなければ、判断は記録済みなので、次の確認で読み直しからやり直す（判断し直さない）。
  - 再起動の後などで、判断が記録済みのまま始まる経路も、同じ読み直しを通る。
- `checkPullRequests`：`importFeedback` が `"pull_request_changed"` を返したタスクは、同じ確認の中で一度だけ、状態を読み直して確かめ直す。既存のマージの経路が `PullRequestMerged` と `StepApproved` を、閉じられた経路が `PullRequestClosed` を記録する（60 秒待たない）。
- 閉じられていた場合は、承認にせず人間の判断を待つ（既存の仕様）。開き直されたら、記録した判断のまま差し戻す。
- マージの後に届いた指摘は、取り込んだ指摘として作業履歴に残る。続きのタスクにするなどはしていない。
- ゴールガーディアンの最終レビューの指示に、節「PR の中身と作業領域の写し」を足した（`pullRequestContentLines`、`apps/daemon/src/prompts.ts`）。
  - PR のコミットには、sacty が成果物（置き場所は、タスクの `documentsDir` があればそれ、なければ `docs/sacty`、の下のタスクの短い ID のディレクトリ）を足す。作業領域の写しには無い。
  - リポジトリ全体を対象にするフォーマッター・リンター・検査（`prettier --check .`・markdownlint など）の結果は、写しと PR の中身で違いうる。写しで実行したそのような検査は、それを理由に不合格にせず、PR の中身で通るかは未確認であることを `humanChecks` に書いて、人の確認に回させる。
  - テストのコマンドの有無にかかわらず入れる。
- 仕様書（`docs/spec/approval.md`・`tasks-and-steps.md` と、それぞれの `.en.md`）を直した。ユーザードキュメントは、利用者に見える設定・画面・文言を変えていないので直していない（既存の仕様どおりの動きに直した）。

  - 判断の最中でもマージされず開いたまま：今までどおり差し戻す。差し戻す前に PR の状態を読み直している（確認の 1 回と合わせて 2 回）。
  - 判断の最中に閉じられた：差し戻さず `PullRequestClosed` を記録し、承認待ちのまま人の判断を待つ。閉じられている間は差し戻さない。開き直されたら、判断し直さずに差し戻す。

  - 読み直しの間に人が差し戻した：重ねて差し戻さない。読み直しが失敗した：差し戻さず、次の確認で差し戻す。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| 読み直しを `ReworkJudged` の前に置くと、読み直しが失敗するたびに判断（エージェントの実行）をやり直して費用が増える | 判断を記録した後に読み直す。失敗しても、次の確認は記録済みの判断のまま読み直しからやり直す。テストあり |
| 判断が記録済みで始まる経路（再起動の後）は、読み直しを通らず差し戻せる | 判断の有無にかかわらず、差し戻す前に必ず読み直す。テストあり |
| 閉じられたのに差し戻すと、仕様の「閉じられたら承認にせず人間の判断を待つ」に反する | 閉じられていても差し戻さず、確かめ直しで `PullRequestClosed` を記録する。開き直されたら、記録した判断のまま差し戻す。テストあり |
| 読んでいる間に人が差し戻す・中止するなどで状態が変わると、二重に差し戻す | 読み直しの後に、状態・指摘・提出・PR を確かめ直し、変わっていれば記録しない。テストあり |
| 確かめ直しが、状態が行き来すると無限に繰り返す | 1 回の確認で、1 つのタスクにつき一度だけ |
| 成果物の置き場所を `docs/sacty` 固定にすると、オーケストレーターが別のディレクトリを決めたタスクで嘘になる | タスクの `documentsDir` を使う（無い・使えない形なら既定）。テストあり |
| 成果物を PR に足さないタスク（既存の PR の引き継ぎなど）では、節が当てはまらない | 指示に「足さないタスクでは当てはまらない」と書いた |

## 残したこと

- マージの後に届いた指摘（今回の例では、実装の欠陥を指す正当な指摘）の扱い（PR へのコメント、続きのタスクの下書き、人へのお知らせなど）。方針の判断が要るので、入れていない。今は、取り込んだ指摘として作業履歴に残るだけ。
- 最終レビューの作業領域の写しに成果物を足して、リポジトリ全体の検査の結果を PR と一致させる変更。写しの中身が変わるので、入れていない。
- 差し戻し中に実装の PR がマージされたときの扱い（承認待ちでない間は見守らない）。
