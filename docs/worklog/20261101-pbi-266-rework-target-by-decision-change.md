# PR の指摘の戻し先を、承認済みの決定を変えるかで決める

- 日付: 2026-11-01（UTC）
- タスク: PBI-266
- PR: なし
- ブランチ: feat/issue-266-rework-target
- 関係する ADR: [PR の指摘の戻し先は、承認済みの決定を変えるかで決め、変えない指摘は実装に戻す](../adr/20261101-1350-rework-target-by-decision-change.md)

## 目的

実務での実証実験で、S9 の「確認して決めたことを文書に書いて」という指摘が、設計の影響範囲に項目が無いことを理由に設計から作り直され、約 $26 かかって予算の上限を超えた（実装の差し戻しなら約 $2）。
S8 の「画面に見ている範囲を出す」は、設計が決めた画面を変える指摘なので、設計に戻したのは妥当だった。
人が決めた方針に従い、承認済みの要求要件・設計の決定を変えない指摘は実装に戻し、決定を変える指摘だけ前の工程に戻す。

受け入れ条件の要点：決定を変えるかで判断する・変えない指摘は実装に戻す・変える指摘は今までどおり前の工程・理由にどの決定を変える／変えないかを書かせる・仕様書、ユーザードキュメント（日英）、作業履歴・テスト。
範囲外：作り直しの軽さ（PBI-265）、差し戻しの原因の分類（PBI-268）。

## したこと

- ゴールガーディアンの戻し先の判断の指示（`buildReworkPrompt`）を変えた。
  - 実装・設計・要求要件の説明を「決定を変えずに直せる」「決定を変える必要がある」に書き直し、「できるだけ後ろの工程で」の一文を、決定を変えるかで決める基準（`reworkDecisionLines`）に置き換えた。
  - 基準：決定を変えない指摘（文書への追記・実装の直し・決定済みのことの反映漏れ）はその PR の工程に戻す。承認済みの成果物の書き漏れは、指摘の求めることが決定から導けるなら決定の変更としない。決定そのものを変える指摘だけ、その決定を持つ工程に戻す。複数の指摘のうち1つでも決定を変えるなら、その工程（複数なら前の工程）。
  - 理由の先頭に、どの決定を変える・変えないかを書かせる。出力の形式の例にも入れた。
  - 要求要件・設計の PR の指摘の判断にも、同じ基準と理由の書き方を使う。
- 戻し先の判断の出力の形（`ReworkJudged`）と、戻し先の候補は変えていない。
- 仕様書（`docs/spec/approval.md`・`.en.md`）、ユーザードキュメント（`docs/user/tasks.md`・`.en.md`）を直し、ADR を足した。
