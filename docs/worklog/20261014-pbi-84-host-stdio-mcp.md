# コンテキストの command の MCP サーバーを、既定でホストで起動してゲートウェイ経由にする

- 日付: 2026-10-14（UTC）
- タスク: PBI-84
- PR: #89
- ブランチ: feat/issue-84-host-stdio-mcp
- 関係する ADR: [コンテキストの mcp.yaml の command の MCP サーバーを、既定でホストで起動してゲートウェイ経由にし、コンテキストリポジトリを config.yaml と同じくらい信頼する](../adr/20261014-0927-context-command-mcp-on-host.md)

## 目的

コンテキストリポジトリの `mcp.yaml` の `command` の MCP サーバーを、`gateway.mcp_servers` と同じくホストで動かすのを既定にする。
エージェントの設定はゲートウェイの URL になり、`env` の秘密情報はコンテナに渡さない。`via_gateway: false` でコンテナの中に
戻せる。プロジェクトごとに分離し、使い回し・起動し直し・停止・前回の残りの片付け・準備の待ち・時間切れの規則を決める。
プレビュー・README・雛形にも反映する。

## したこと

- `apps/daemon/src/context.ts`：`command` のサーバーに `via_gateway`（既定 true）を足した。`routeMcp` で、ゲートウェイがあり
  ホストで起動できるときは、`command` のサーバーをゲートウェイの URL に置き換え、起動するもの（`hostedMcp`。秘密情報は参照のまま、
  書いた層つき）を返す。`gateway.mcp_servers` と同じ名前・書き出しの絞り込みで外したものは起動しない。プレビューの接続先に
  `hostCommand`（コマンド・`env` の参照・作業ディレクトリの層）を足した。
- `apps/daemon/src/context-mcp.ts`（新規）：`ContextMcpServers`。`HostMcpServers` をそのまま使い、ゲートウェイの中の名前を
  プロジェクトと中身のハッシュにする。実行ごとに確保（lease）し、終わったら返す。古くなった・30分使われないものを止める。
  層のリポジトリを `SACTY_HOME/context-mcp/layers` に写す（`.git` は除く）。起動時に前回の写しを消す。
- `apps/daemon/src/host-mcp.ts`・`host-mcp-processes.ts`：作業ディレクトリ（`cwd`）を渡せるようにした。起動の前にコマンドが
  ホストにあるか（PATH・作業ディレクトリからの相対パス）を確かめる。コンテキストのものは、mcp.yaml の名前と層で理由を出す
  （`context.mcpHostUnavailable`・`context.mcpHostReadyTimeout`・`context.mcpHostCommandMissing`）。
- `apps/daemon/src/gateway.ts`：`/ctx-mcp/<名前>` の中継先に、ホストで起動したもの（`{ host }`）を足した。実行に結びつけた
  名前だけを引く（`Object.hasOwn`。これまでは `constructor` などの名前で、オブジェクトの持つ値を引けてしまっていた）。
- `apps/daemon/src/service.ts`：`runContext` で、ホストで起動するものを確保して準備を待ち（人が止めたら待たない）、準備が
  できないものを作業履歴の注意に残す。書き出しの接続先なら理由を残して書き出さない。`executeLogged` で実行の登録に結びつける。
- `apps/daemon/src/main.ts`：プロセスの記録（`SACTY_HOME/host-mcp/processes`）を `gateway.mcp_servers` と共有して配線した。
- 画面：コンテキストのプレビューに、ホストで起動するコマンド・作業ディレクトリ・ホストで入れる環境変数を出す。
- README・コンテキストの雛形（`context-template.ts`）：既定がホストであること・信頼の前提・`via_gateway: false` の書き方・
  ホストで動かすときの規則。
- 方針の決定は ADR に書いた。仕様書・ユーザードキュメントの本文は、まだファイルが無いので README だけを直した。

## 確かめたこと

- 回帰テスト：`context-mcp.test.ts`（新規）・`context.test.ts`・`daemon.test.ts`・`context-template.test.ts` に足した。
  既定でホスト・コンテナの指定・プロジェクトの分離・中身の変更で起動し直す・使い回し・秘密情報がコンテナに渡らない・
  プレビュー・終了と前回の残り・コマンドが無いときの警告。
- 実際のプロセス（テスト）：MCP の SDK の本物のサーバーを stdio でホストに起動し、SDK の本物のクライアントでゲートウェイの
  `/ctx-mcp/<名前>` から初期化・ツールの一覧・呼び出しができること、デーモンの終了でプロセスと記録が消えること、所有元の
  デーモンが落ちた記録を次の起動の片付けで止めることを確かめた。
- 修正を戻すと落ちること：22か所の変更を1つずつ戻し、どれでも上のテストが落ちることを確かめた。
- 実際のデーモン（`sacty up`、一時的な `SACTY_HOME`、ポート 4940/4950、PATH の先頭に偽の `security`・`op`・`gh`・`docker`）：
  偽の `docker` がコンテナの代わりに、置かれた `mcp.json` からゲートウェイへつないで確かめた。
  - プロジェクト A の実行：ホストで起動したサーバー（作業ディレクトリは層の写し）に、ゲートウェイ経由で初期化・一覧・呼び出しができた。
    コンテナの環境変数に、ホストで起動したサーバーの秘密情報の値は無かった。`via_gateway: false` のものは、コンテナの中で起動する形のまま。
  - A の2回目は同じプロセス（使い回し）。プロジェクト B（同じ名前・違う中身）は別のプロセスで、B の中身を返した。
  - A のコンテキストに commit を足すと、次の実行で新しいプロセスになり、古いものは止まり、その層の写しも消えた。
  - `sacty up` を止めると、MCP サーバーのプロセス・記録・層の写しが残らなかった。デーモンを SIGKILL した後の再起動で、
    残った記録と層の写しを片付けた。
  - プレビュー（画面・API）に、エージェントから見える URL・ホストで起動するコマンド・`env` の参照・作業ディレクトリの層が出た。
- `npm run lint`・`npm run typecheck`・`npx vitest run`・`npm run build`：通った。
- レビュー対応の後：`npm run lint`（終了コード 0）・`npm run typecheck`・`npx vitest run --maxWorkers=2`（マシンの負荷が高い〈load average 約48〉ため並列を絞った。50ファイル・1179件通過）・`npm run build`・`npx vitest run tests/docs`：通った。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （DA のセルフレビュー）プロジェクトの分離・秘密情報・後片付け | 下の「残したこと」以外は、テストと実際のデーモンで確かめた |
| （PR #89 の DA レビュー、P2）複数のサーバーを確保する途中で層の写しに失敗すると、先に確保したものが使っている実行の数を持ったまま残り（30秒ごとの突き合わせで起動され、止まらない）、一時のコンテキストも消えない | `ContextMcpServers.lease` で、途中の失敗ではそこまでの確保を巻き戻す（使っている実行の数を戻し、その呼び出しで足したものを消し、使うもののない層の写しと途中まで写したものを消す）。`runContext` で、確保・準備の失敗では用意したコンテキストを消す。工程の実行で、コンテキストを用意してから実行の try（finally で消す）に入るまでの例外でも消すようにした。書き出し・人が止めたときの経路は、もともと消していることを確かめた。回帰テスト：写しの失敗（層が無い・読めないファイル）で1件目の確保が0に戻り、起動されず、写しが残らない。確保・準備の失敗で一時のコンテキストが消え、確保が返る。6か所の修正を1つずつ戻し、すべてでテストが落ちることを確かめた（工程の実行の try までの例外の経路は、起こす手段が無くテストしていない） |

## 残したこと

- MCP のツールの結果に秘密情報が含まれたときに伏せること（`gateway.mcp_servers` と同じく、しない）。
- ホストで動かしているコンテキストの MCP サーバーの準備の問題を、タスクの一覧の画面の状態に出すこと（作業履歴の注意にだけ出す）。
- 仕様書・ユーザードキュメントへの反映（PBI-81・82 で本文ができた後に追従する）。
