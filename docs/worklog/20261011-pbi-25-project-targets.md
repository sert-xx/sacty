# プロジェクトの「対象」を一本化し、ベースブランチとテストのコマンドはオーケストレーターが決める

- 日付: 2026-10-11（UTC）
- タスク: PBI-25
- PR: #30
- ブランチ: feat/issue-25-project-targets
- 関係する ADR: [プロジェクトの設定を「対象」（Org またはリポジトリ）の一覧だけにし、タスクの対象は対象の中から選び、PR作成の工程は常に PR を作る](../adr/20261011-1520-superseded-project-targets.md)、[ベースブランチとテストのコマンドは、タスクの開始時にオーケストレーターが決めて記録し、人が直す手段は設けない](../adr/20261011-1520-orchestrator-decides-base-branch-and-test-command.md)

## 目的

動作確認でのフィードバックに対応する。取り込み元とリポジトリの設定が分かれているのをやめ、プロジェクトには「対象」（Org またはリポジトリ）の一覧だけを登録する。Org の対象では、gh で読んだリポジトリからタスクの対象を選ぶ。PR作成許可は無くし、対象に登録すると PR が作られることを注意書きにする。ベースブランチとテストのコマンドはオーケストレーターが決めて記録し、画面に出す。取り込みのラベルは PBI-26 で sacty 全体の設定にするまで `sacty` に固定する。

## したこと

- プロジェクトの設定（`packages/core/src/projects.ts`）：`ProjectDefinition` を `targets`（`{scope: "org" | "repo", target}`）だけにし、`sources`・`repositories`・`pullRequest` を削った。重複の検査と、範囲が狭いほうが優先する規則は引き継いだ。エクスポートの形式の版を 2 にし、版 1 は読まない。設定画面は対象の一覧（単位・名前・× ボタン）と、PR が作られることの注意書きにした（`apps/web/src/components/project-editor.tsx`）。
- タスクの作成：対象の中のリポジトリだけを受け付け、リポジトリの対象と同じなら名前の大文字・小文字をそろえる。対象がリポジトリ1つだけなら、それが対象になる。
- 候補の API `GET /api/projects/:id/repositories`：リポジトリの対象と、プロジェクトの gh のアカウントで読んだ Org（Org でなければユーザー）のリポジトリを返す。アーカイブしたもの・ほかのプロジェクトがリポジトリ単位で担当するものは除く。読めなかった Org は、トークンを伏せた理由を返す。作成のダイアログは、入力して絞り込める欄（datalist）にした。
- ベースブランチとテストのコマンド：開始時はブランチを指定せずに既定のブランチを clone して記録する。オーケストレーターが工程と一緒に `baseBranch`・`testCommand` を出す（`apps/daemon/src/prompts.ts`）。`testCommand` は `StepsChosen` に記録する。既定と違う `baseBranch` は、その最新で用意し直して `RepositoryPrepared` を記録し直し、用意できなければ既定のブランチで進めて理由に添える。テストのコマンドが分からなければ、実装を含むタスクは費用をかける前に止める（調査・レビューだけは止めない）。検証はそのコマンドで行う。タスクの画面に両方を出す。
- PR作成の工程は常に PR を作る。`README.md` にも、対象に登録すると PR が作られることを書いた。
- 取り込みのラベルは、すべての対象で `sacty` に固定した。
- 保存の後にプルダウンの表示が最初の選択肢に戻っていたのを直した。フォームの action に渡すと、送信の後に React がフォームをリセットしていたため、送信を自分で呼び出すようにした。
- レビューの対応：個人のアカウントのときは、公開のリポジトリ（`/users/{owner}/repos`）に加え、トークンで読めるリポジトリ（`/user/repos?affiliation=owner,collaborator,organization_member`）のうちその持ち主のものも候補にした（重複・アーカイブは除く）。候補が無くても、対象があれば作成のダイアログでリポジトリ名を入力できるようにした。

## 確かめたこと

- テスト：294件が通った。対象の中から選ぶこと、対象外・ほかのプロジェクトの担当を拒むこと、Org のリポジトリの候補、既定のブランチの clone（実際の git）、ベースブランチの選び直しと用意できないときの扱い、テストのコマンドが分からないときの停止、Org のリポジトリの一覧の API（ページ・アーカイブ・ユーザーへの切り替え・失敗）、対象の重複の検査とエクスポートを足した。
- 次の修正を外すと、それぞれテストが失敗することを確かめた：対象の検査、ほかのプロジェクトの担当の除外、ベースブランチの用意し直し、開始時の停止、取り込みのラベル、既定のブランチの clone、アーカイブの除外。
- リント・型チェック・ビルドが通った。
- 一時的な環境で画面を確かめた：対象の一覧と注意書きが出た。個人のアカウントを対象にすると、gh で読んだリポジトリ（56件）がタスク作成のダイアログの候補に出た。
- レビューの対応で、公開・非公開・ほかの持ち主・アーカイブ済みが混ざった応答から、その持ち主の公開と非公開のリポジトリだけを返す回帰テストを足し、修正を戻すと失敗することを確かめた。実際の GitHub で、公開だけでは 56 件のところ、非公開を含めて 71 件を返した。
- 再レビューで、全295件のテスト・lint・typecheck が通った。
- 実際の AI でオーケストレーターがベースブランチとテストのコマンドを決めるところは試していない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| `GET /users/{username}/repos` はトークンを渡しても公開のリポジトリしか返さないので、個人のアカウントを対象にすると、アクセスできる非公開のリポジトリが候補から漏れる。候補が空だと入力欄が隠れ、直接入力もできない | トークンで読めるリポジトリ（`/user/repos`）のうち、その持ち主のものを合わせて候補にした。候補が無くても対象があれば入力できるようにした。回帰テストを足した |

## 残したこと

- 実際の AI でオーケストレーターがベースブランチとテストのコマンドを決めるところは試していない。
- プロジェクトの定義の形が変わるので、利用者の環境のプロジェクトは、設定画面で対象を登録し直す必要がある。
- 取り込みのラベルを sacty 全体の設定にすることは、PBI-26 で行う。
