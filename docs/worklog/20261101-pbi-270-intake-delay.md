# PR の指摘・ラベルの取り込みが約1時間遅れる原因を調べて直す

- 日付: 2026-11-01（UTC）
- タスク: PBI-270
- PR: #266
- ブランチ: feat/issue-270-intake-delay
- 関係する ADR: [GitHub の時刻がこの機械の時計とずれても取り込みが遅れないよう、PR の指摘の待ち時間と検索の読んだ位置を、この機械の時計で抑える](../adr/20261101-1352-intake-times-bounded-by-local-clock.md)

## 目的

次の2つの約1時間の遅れの原因を、記録で特定し、Sacty の作りに原因があれば、GitHub の時刻が機械の時計より先・後にずれていても遅れないように直す。

- 試行用の Sacty で、PR へのコメントを約1時間後に取り込んだ（同じタスクの別の PR では約2分）。
- sacty の PR にレビュー用のラベルを付けてから、レビューのタスクができるまで約1時間かかった。

## 調べたこと（根拠）

### 前提：この機械の時計は合っていた

- `timed` のログ（`log show --predicate 'process == "timed"'`）で、2026-11-01 15:28〜22:21（JST）の NTP の同期の差は最大でも2秒ほど。時計が1時間ずれた記録は無い。
- 調べた時点で、`date -u` は 13:41:43、`gh api -i` の `Date` ヘッダーは 13:41:44 GMT。

### GitHub が付けた時刻が、一定の時間だけ1時間先だった

Sacty の作業履歴の時刻（`activity.at`。この機械の時計）と、同じ出来事に GitHub が付けた時刻を並べた（UTC）。

| 出来事 | Sacty の記録 | GitHub の時刻 | ずれ |
| --- | --- | --- | --- |
| PR 258 のレビューの投稿 | 04:10:47 | 04:10:46 | 0 |
| PR 259 のレビューの投稿 | 07:38:10 | 07:38:11 | 0 |
| PR 259 のレビューの投稿 | 08:04:07 | 09:04:08 | +1時間 |
| 試行用の PR 11 の作成 | 08:10:04 | 09:10:05 | +1時間 |
| PR 259 のレビューの投稿 | 08:15:53 | 09:15:55 | +1時間 |
| 試行用の PR 12 の作成 | 08:26:10 | 09:26:11 | +1時間 |
| 試行用の PR 12 のドラフト解除 | 08:36:02 | 09:36:03 | +1時間 |
| PR 260 のレビューの投稿 | 08:40:31 | 09:40:32 | +1時間 |
| PR 260 のレビューの投稿 | 08:51:43 | 09:51:44 | +1時間 |
| 試行用の PR 13 の作成 | 09:52:49 | 09:52:50 | 0 |
| 試行用の PR 12 のドラフト化 | 10:01:17 | 10:01:17 | 0 |

- 07:38〜08:04 の間に始まり、08:51 より後、09:20 より前に終わった（PR 260 のマージは GitHub の時刻で 09:20:14。PR 260 の最後のコミットの時刻は 08:44:18 なので、このマージは時刻が戻った後）。
- 2026-11-01 は米国の夏時間が終わる日で、ずれた時間帯は 08:00〜09:00（UTC）と重なる。ただし、これが原因かは確かめていない。
- HTTP の `Date` ヘッダーは合っていた（試行の担当の記録では、`Date` が 08:53 GMT のとき、コメントの時刻は 09:39:18Z）。API の本文の時刻だけがずれていた。

### 原因1：PR の指摘を待つ時間（試行用の PR 12）

- コメント 6555636361 の GitHub の `createdAt` は 09:39:18Z（実際は 08:39:18）。
- 試行用の Sacty の作業履歴では、`PullRequestReviewImported` が 09:41:53 に記録されている。直前の `StepSubmitted` は 08:36:02 で、その間の1時間は何も起きていない。
- `importFeedback`（`apps/daemon/src/service.ts`）は、`this.now() - newest < FEEDBACK_QUIET_MS` で待つ。`newest` はコメントの GitHub の時刻、`this.now()` はこの機械の時計。コメントの時刻が1時間先なので、機械の時計が追いつく 09:41:18 まで待った。
- 同じタスクの PR 9 のコメントは、GitHub の時刻 06:58:24、取り込み 07:00:54（約2.5分）で、ずれていない時間帯だった。

### 原因2：検索の読んだ位置（sacty の PR 261）

- ラベルを付けた時刻（`labeled`）は GitHub の時刻で 09:21:44（時刻はもう戻っていた。同じ PR の直前の `automatic_base_change_succeeded` は 09:20:16 で、PR 260 のマージ 09:20:14 による）。
- 4700 番のレビューのタスク cde1c87b の `TaskCreated` は 10:23:58。ラベルから約62分後。レビューの取り込みの間隔は 60 秒（sacty の設定 `reviewIntervalSec`）で、デーモンは 10/31 17:06 から再起動していない。
- 10:23:12 に PR 261 へ新しいコミット f6638f9b を積んでいて、その46秒後にタスクができた。
- 取り込みの検索（`GitHubIssueSearch`）は `updated:>=<読んだ位置>` で探し、読んだ位置は返した最後の PR の GitHub の更新日時にする。レビュー用のラベルの付いた PR 260 は、08:51:43 の（GitHub の時刻で 09:51:44 の）レビューで更新日時が 09:51:44 になり、09:20:14 にマージされるまで開いていた。この間の検索で、読んだ位置は 09:51:44 になっていたはず。
- PR 261 の更新日時は、ラベルの 09:21:44、参照の 09:30:19 で、どちらも 09:51:44 より前。10:23:12 のコミットで初めて読んだ位置より新しくなり、検索に当たった。
- 読んだ位置はメモリーにだけあるので、値そのものは記録に残っていない。上は、記録された時刻からの再構成。取り込みのテストで、この経過を再現して確かめた（下）。

### 結論

遅れの引き金は、GitHub の API の時刻が一定の時間（08:00〜09:00 UTC ごろ）だけ1時間先だったこと（Sacty の外）。ただし、Sacty が GitHub の時刻を、この機械の時計と同じ軸で扱っていたため、一時的なずれが約1時間の遅れになった（Sacty の作り）。

## したこと

- PR の指摘の取り込み：各フィードバックの時刻を、GitHub の時刻と、デーモンが初めて見た時刻の早い方にして、2分待つ。GitHub の時刻が先でも、見てから2分で取り込む（`importFeedback`・`feedbackSeenAt`）。
- 取り込みの検索：持ち越す読んだ位置を、その検索を始めた時刻より先に進めない（`clampCursor`）。
- 仕様書（`docs/spec/approval.md`・`intake.md` と英語の版）に書き、ADR を足した。ユーザードキュメントの記述（最後のコメントから2分後に取り込む）は、時刻が合っているときの振る舞いのままなので変えていない。

## 確かめたこと

- `npx vitest run apps/daemon/src/intake.test.ts`：全41件が通る。ずれのある時刻のテストを3件足した（時刻が戻った後にラベルを付けた PR を拾う・合っていれば位置は更新日時のまま・先に進んだままでも拾い、二重に取り込まない）。`clampCursor` を使わない状態に戻すと、1件目が失敗する（持った位置が 09:51:44 のまま）。
- `npx vitest run apps/daemon/src/daemon.test.ts -t "PR へのフィードバックの取り込み"`：23件が通る。足した3件（GitHub の時刻が1時間先・新しいコメントのたびに数え直す・GitHub の時刻が遅れているとき）のうち、先に進んだ2件は、修正を戻すと失敗する。
- `npm run lint`・`npm run typecheck`：通る。
- `npx vitest run tests/docs`：93件が通る。
- `npx vitest run apps/daemon packages/core tests/docs`：4件が失敗した。`ci.test.ts`・`prompts.test.ts` の時間の判定の2件（長さに比例する時間）は、単独で再実行すると通る（マシンの負荷）。`install-security-tools.test.ts` の2件は、変更を退避した状態でも失敗する（今回の変更とは無関係）。

## 残したこと

- GitHub の時刻が、合っていた状態から遅れる側へ変わったときの検索の読んだ位置は、これまでどおり。持った位置より古い更新日時が付くと、次の更新まで検索に当たらない。
- GitHub の時刻がずれた原因（夏時間の切り替えとの関係）は確かめていない。
- フィードバックの初めて見た時刻はメモリーにだけ持つ。デーモンを再起動すると、先に進んだ時刻のコメントは再起動から2分待つ。
