# ゴールガーディアンで変更の申し出を判定する

- 日付: 2026-10-10（UTC）
- タスク: PBI-9
- PR: #5
- ブランチ: feat/issue-9-guardian
- 関係する ADR: [承認済みの成果物の変更の申し出は、判定ごとに新しいセッションのゴールガーディアンが判定し、要求要件の変更は人間の再承認に回す](../adr/20261010-0812-superseded-guardian-change-proposal.md)

## 目的

工程のエージェントが、承認済みの要求要件・設計の変更を申し出られるようにし、ゴールガーディアンが判定ごとに新しいセッションで、
必要な情報だけを受け取って判定する。設計の変更は反映し、要求要件の変更は人間の再承認を必須にすること、判定と理由を台帳に
記録してタスクの詳細に出すこと、判定できなければエスカレーションにすることが受け入れ条件の要点。

## したこと

- 工程のプロンプトに、申し出の形式（`sacty-change-proposal`）を足した（`apps/daemon/src/prompts.ts`）。申し出られるのは前の工程の承認済みの成果物だけ。
- ゴールガーディアンの実行（`apps/daemon/src/service.ts`・`agents/invocation.ts`）：判定ごとに別のコンテナ・空の作業領域で実行し、判定の後に消す。
  使う AI は `guardian_agent`（`apps/daemon/src/config.ts`）。
- 台帳のイベント `ChangeProposed`・`ChangeJudged`・`ChangeDecided`・`ChangeApplied` と復元（`packages/core/src/events.ts`・`projection.ts`）。
- 判定の結果の反映：設計は置き換え、要求要件は承認を取り消して再承認に出す。判定できなければエスカレーション。
- 画面：タスクの詳細の「変更の申し出と判定」（`apps/web/src/components/proposals.tsx`）と人間の判断のフォーム（`change-decision-form.tsx`）、
  再承認の画面での申し出の理由と根拠の表示。
- レビューの対応で、作業中の判定（`isWorking`）と人間の出番への導線（`personAction`）を `apps/web/src/lib/labels.ts` にまとめ、
  vitest の対象に web の lib を足した（`vitest.config.ts`）。

## 確かめたこと

- `npm test` が全件通った（79件。9件追加）。要求要件の再承認を外すと、2件のテストが失敗することを確かめた。
- スタブのエージェントで、画面から次の流れを確かめた：要求要件を承認する → 設計の工程が要求要件の変更を申し出る → ゴールガーディアンが
  判定できずエスカレーションになる → 人間が変更を認める → 変更後の要求要件が再承認待ちになる。
- 幅 375px で横スクロールが出ないことを確かめた。
- レビューの対応の後、画面で、一覧の「判断する →」から判断のフォームが開くことを確かめた。
- 再レビューでは `npm test`（84件）・`npm run lint`・`npm run typecheck` が通った。本物のコンテナ・外部のエージェント・ブラウザでの動作は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 判定（`ChangeJudged`）の保存と後始末の保存が別なので、その間で止まると、再起動の後にタスクが待機のまま進まず、人間の判断も拒否される | 判定と後始末、人間の判断と後始末、実行の完了と提出を、それぞれ同じトランザクションの1回の追記で記録するようにした。起動の時に、台帳の最後が `ChangeJudged`・`ChangeDecided`・`ChangeApplied` で止まっているタスクは、足りない後始末を記録して先に進める（冪等）。回帰テストを3件足し、修正前のコードでどれも失敗することを確かめた |
| 一覧の自動更新が実行待ち・実行中だけを見ているので、ゴールガーディアンの判定中に止まる | 作業中の判定を `isWorking(task)` にまとめ、未判定の申し出があるときも作業中とみなすようにした。一覧と詳細の両方で使う。テストを足した |
| 一覧の「あなたの出番」がエスカレーションを一律に `/review` へ誘導するので、判定できなかった申し出の判断のフォームにたどり着けない | 導線を `personAction(task)` にまとめ、判定できなかった申し出は `/tasks/:id#proposals` へ、差し戻しの上限によるエスカレーションと承認待ちは `/review` へ誘導するようにした。テストを足した |
