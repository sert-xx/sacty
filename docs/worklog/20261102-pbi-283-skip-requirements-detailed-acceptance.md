# 受け入れ条件が詳しく、人に確かめることが無い依頼では、要求要件を省く（S5）

- 日付: 2026-11-02（UTC）
- タスク: PBI-283
- PR: #285
- ブランチ: feat/issue-283-pbi-283
- 関係する ADR: [受け入れ条件が詳しく、人に確かめることが無い依頼では、要求要件を省く](../adr/20261102-2357-skip-requirements-for-detailed-acceptance.md)

## 目的

実験（S5）で、依頼に受け入れ条件が詳しく書かれていたのに要求要件が残り、細かい既定を決めるだけで費用の8割（$24.35 / $30.20）を使った。
受け入れ条件が詳しく、人に確かめることが無い依頼では、オーケストレーターが要求要件を省く組み合わせを選ぶようにする。曖昧・食い違い・言い忘れ・並行の衝突（S8・S9・S10・S13）では省かない。セルフレビューの回数・モデル・エフォートは変えない。

## したこと

- オーケストレーターの指示（`apps/daemon/src/prompts.ts` の `PLAN_SELECTION_LINES` に `DETAILED_ACCEPTANCE_LINE` を足した）：
  - 確かめられる受け入れ条件がそろい、人に確かめることが無く、設計の判断も要らないときは、局所的でなくても `direct` を選ぶ。`reason` に省いた理由を書く。
  - 曖昧・食い違い・人に確かめたい判断・書き忘れや衝突が見えるときは、要求要件を残し、当たったことを `reason` に書く。判断しきれないときも残す。設計の判断が要るなら `standard`。
  - `planDescriptions` の `direct`・`skip-design` の説明に、同じ基準を書いた。対象リポジトリの無いタスクの指示も同じ `PLAN_SELECTION_LINES` を使う。
- `direct` の実装の指示（`directImplementLines`）：細かい既定は既存の実装・規約に合わせて決め、実装の説明に「既定で決めたこと」の節を分けて1件1行で書かせる（実装の説明は PR の本文に載る。人は実装の PR で確かめる）。依頼に受け入れ条件が列挙されていれば、1つずつ満たすことを確かめさせる。
- 仕様書（`docs/spec/tasks-and-steps.md`・英語の版）、ユーザードキュメント（`docs/user/tasks.md`・英語の版）、ADR を直した。
- 工程の見直し（`buildStepReviewPrompt`）・セルフレビュー・組み合わせの種類は変えていない。

## 確かめたこと

- `apps/daemon/src/prompts.test.ts` に4件足した：詳しい受け入れ条件で省く指示（リポジトリの無いタスクの指示を含む）、曖昧・食い違い・確かめたいこと・衝突・設計の判断で残す指示、`direct` の説明、`direct` の実装の指示。`prompts.ts` を戻すと、4件とも落ちる（`git stash` で確認）。
- 実際の AI に、実験の依頼（`sacty-field-trials/scenarios/*/request.md` の題と依頼）を当てて、選ぶ組み合わせを比べた。`buildOrchestratorPrompt` の指示（変更前の `origin/main` と変更後）に、リポジトリが見えない旨の注意を足して、`claude -p`（モデル claude-opus-4-5）に答えの JSON だけを出させた（使い捨ての道具。コミットしていない）。集めた情報の無い入力では、S9 の食い違い・S10 の連携先は見えないため、S9・S10 は集めた情報の例（README と実装の食い違い・連携先と互換の方針）を足した版も流した。

  | 依頼 | 期待 | 変更前（`origin/main`） | 変更後（最終の指示） |
  | --- | --- | --- | --- |
  | S5（受け入れ条件が詳しい） | direct | direct 0/3（standard 2・skip-design 1） | direct 2/3（途中の文面では 7/8 が direct。残りは skip-design） |
  | S8（曖昧） | 残す | standard 3/3 | standard 4/4 |
  | S9（食い違いは集めた情報にしかない） | 残す | standard 3/3 | 集めた情報なし：残す 4/4（standard 3・skip-design 1）。ありの例：standard 4/4 |
  | S10（改名。連携先は集めた情報にしかない） | 残す | skip-design 1・standard 1・direct 1 | 集めた情報なし：残す 4/4（skip-design 3・standard 1）。ありの例：standard 4/4 |
  | S13a（詳しい受け入れ条件。並行する依頼は見えない） | 残す | skip-design 2・standard 1 | 残す 4/4（standard 3・skip-design 1） |

  - S13a は、最初の文面では direct が 3 回中 2 回だった（詳しい受け入れ条件で、並行する依頼がオーケストレーターに見えないため）。「既存の共有の状態・項目に新しい意味を載せる・状態を増やす」を残す条件に足して、残るようになった。S10 も同じ表の「外に公開している API・項目の名前や形を変える」で、集めた情報なしでも残るようになった。
  - 1 回の測定で、AI の判定は揺れる。表は指示の効果の大きさの目安。

## 残した制限

- オーケストレーターには、並行して進んでいるほかのタスクが見えない。S13 のように、片方がまだ PR を出していない並行の依頼の衝突は、集めた情報から見えるときだけ検出できる。今回は、依頼の中の「共有の状態への新しい意味」で残るようにした（衝突そのものの検出ではない）。
- 設計の判断が要る依頼は、受け入れ条件が詳しくても `standard`（要求要件が付く）にする。設計だけを残して要求要件を省く組み合わせは足していない。
- 「既定で決めたこと」は、実装の説明の一部として PR の本文の「変更」の節に載る。長さの上限で本文が縮められたときの扱いは、今までの実装の説明と同じ。
