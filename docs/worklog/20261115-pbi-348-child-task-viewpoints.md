# 分割の子タスクに、親の設計のテスト観点を割り当て、実装の指示を子タスクに合わせる

- 日付: 2026-11-15（UTC）
- タスク: PBI-348
- PR: #380
- ブランチ: feat/issue-348-child-task-viewpoints
- 関係する ADR: [分割の子タスクに、親の設計のテスト観点を割り当て、観点の対応が欠けた実装を提出にしない](../adr/20261115-1345-assign-test-viewpoints-to-child-tasks.md)

## 目的

タスク分割の子タスクの実装が、範囲の一部だけを実装して終わった件で、指示の側の2つの欠陥を直す（仕組みの側は PBI-347）。

- 子タスクに完了の基準が渡っていない：親の設計のテスト観点が、分割のエージェントにも子タスクにも届かず、子タスクの観点が「REQ：タスクの目的」の1つだけになる。
- 要求要件・設計を省いた実装の指示が、子タスクに合っていない：小さい変更という前提の文が固定で、範囲を実装し終えてから検証と報告に進む順序が無い。

受け入れ条件の要点は次のとおり。

- 分割の指示が、親の設計のテスト観点を子タスクに割り当てるよう求める。割り当てない観点は、統合レビューで確かめる観点として、理由と一緒に挙げさせる。
- どこにも入っていない観点・設計に無い ID があれば、子タスクを作らずに止める。
- 子タスクは割り当てられた観点を持ち、実装の指示・PR の本文・PR のレビューに渡す観点・画面が、その観点を使う。
- 観点とテストの対応に欠けた観点があれば、完了と申告していても提出しない（テストを書かないタスクは除く）。
- 子タスクの実装の指示が、子タスクの範囲を伝える。どの実装の指示も、進める順序を伝える。
- 観点の割り当てが無い子タスクは、タスクの目的（REQ）を観点にして進む。

## したこと

- `packages/core`
  - イベント：`TaskSplit` の子タスクごとの `viewpoints` と `integrationViewpoints`、`TaskCreated` の `viewpoints`、`ImplementationIncomplete` の `unmapped`。
  - 投影：`Task.inheritedViewpoints`、分割の記録の観点、`implementViewpoints`（実装がテストを対応させる観点）、`unmappedViewpoints`（対応の欠けた観点）。
  - 文言：分割の観点の検査（`split.viewpointUnassigned` など4つ）、`implement.unmappedViewpoints`（日本語と英語）。
- `apps/daemon/src/prompts.ts`
  - 分割の指示に、承認済みのテスト観点と、割り当て方を足した（`splitViewpointLines`）。答えの形の例にも、割り当てを入れる。
  - 分割の答えの読み取り（`extractSplitPlan`）で、割り当てを確かめる。
  - 要求要件・設計を省いた実装の指示（`directImplementLines`）：子タスクには、子タスクであること・小さな変更とは限らないこと・範囲を伝える。割り当てられた観点があれば、REQ の代わりに並べる。
  - 設計を省いた実装の指示・PR の本文の観点の表・PR のレビューの子タスクに渡す観点も、割り当てられた観点を使う。
  - どの実装の指示にも、進める順序を足した（`IMPLEMENT_ORDER_LINE`）。
  - やり直しの指示に、テストが対応していなかった観点を渡す（`feedbackLines`）。
- `apps/daemon/src/service.ts`
  - 分割の記録に、割り当てた観点を中身ごと残し、子タスクの作成の記録に渡す。
  - 提出の前の確認（`implementationCompleted`）で、完了と申告した実行でも、対応の欠けた観点があれば、欠けた観点を記録して実装をやり直す。
- `apps/web`：親タスクの「子タスク」に、子タスクごとの観点の ID と、統合レビューで確かめる観点を出す。子タスクの詳細に「割り当てられたテスト観点」を出す。実装の成果物の観点の表も、割り当てられた観点を使う。作業履歴の行の文言を足した（日本語と英語）。
- テストの偽の実行器（`FakeExecutor`）：分割の指示が割り当てを求めていて、テストの答えに割り当てが無ければ、すべての観点を統合レビューで確かめる割り当てを足す（本物のエージェントが指示どおり割り当てる代わり）。
  割り当ての無い答えを確かめるテストは、`unassignedViewpoints` で足さないようにする。
- 仕様書（タスク分割と統合レビュー・タスクと工程。日本語と英語）、ユーザードキュメント（タスク・困ったとき。日本語と英語）、ADR を直した。
- PR を作る前の見直しで、次を直した。
  - 実装がテストを対応させる観点（`implementViewpoints`）を、実装の指示が並べる観点と同じ決め方にした。
    はじめは「自分の設計のテスト観点があればそれ、無ければ割り当てられた観点」としていた。この決め方だと、再現の工程がある子タスク（不具合の修正）や、設計にテスト観点が無い子タスクで、指示に並んでいない観点の対応を求めて、実装が提出されなくなる。
    設計の工程があれば自分の設計の観点、再現の工程があれば無し、どちらも無ければ割り当てられた観点、にした。
  - 観点の対応を確かめる実装の指示（設計のある実装を含む）に、欠けがあると提出されないことを書いた（`unmappedViewpointLines`）。はじめは、子タスクの要求要件・設計を省いた実装の指示にだけ書いていた。
  - 変更が要らないとわかった実行も、観点の対応の確認を通る。指示に、変更が要らないときも既存のテストを対応させることを書き、対応を出し直した後に変更なしの確認に進むことをテストで確かめた。
  - 統合レビューの指示に、どの子タスクにも割り当てなかった観点と理由を渡した（そのときの名前は `integrationOnlyViewpointLines`。レビューの対応で `splitIntegrationViewpointLines` に変えた）。はじめは、分割の記録と画面に出すだけで、統合レビューには渡していなかった。
  - 画面のテストを足した（子タスクの詳細の「割り当てられたテスト観点」、親タスクの「子タスク」の観点の ID と統合レビューの観点、実装の成果物の観点の表）。
  - 子タスクの範囲を、区切り線ではなく、見出し「親タスクの要求要件（承認済み）」で伝えるようにした。はじめは「タスクの内容の最初の区切り線より前」と伝えていた。分割のエージェントが子タスクの内容に区切り線を書くと、範囲が狭く伝わる。

## レビューの指摘と対応

- sacty のレビュー（1回目。提案 5 件。判定は読み取れず）
  - 提案：`docs/spec/tasks-and-steps.md` の、要求要件・設計を経ない実装と PR の本文が常に `REQ` を使う、という説明が、割り当てられた観点を持つ子タスクと合わない。
    - 対応：割り当てられた観点を持つ子タスクは、指示も PR の本文も、`REQ` の代わりに割り当てられた観点を使うことを、日英の仕様書に足した。
  - 提案：要求要件があり設計を省いた子タスクで、テストを書かないとき、指示の冒頭は観点を `REQ` と説明し、後ろには割り当てられた観点を並べる。
    - 対応：冒頭も、割り当てられた観点があれば、そう説明するようにした。テストを足した。
  - 提案：分割案は、同じ観点を子タスクと `integrationViewpoints` の両方に入れられるのに、統合レビューの指示と画面は、全件を「どの子タスクにも割り当てていない」と伝えている。
    - 対応：両方に入れてよいことにそろえた（子タスクで一部を確かめ、組み合わせた後にも確かめる観点があるため）。分割の指示にもそう書いた。
      統合レビューの指示は、観点ごとに、子タスクにも割り当てているかを伝える（`splitIntegrationViewpointLines`）。画面の見出しは「統合レビューで確かめるテスト観点」にした。仕様書・ユーザードキュメント（日英）・ADR を合わせた。
  - 提案：画面とユーザードキュメントは、割り当てがあれば常にテストの対応が必須で、欠けると提出しない、と説明している。子タスクに設計・再現の工程があるとき、テストを書かないとき（テストの仕組みが無い・文書だけの依頼）は、対応を確かめない。テストを書かない理由でも、対応したことになる。
    - 対応：画面の補足と、ユーザードキュメント（日英）を、確かめる条件に合わせた。
  - 提案：設計を省いた分割の子タスクの PR のレビューに、割り当てられた観点を渡す経路を、テストが確かめていない。
    - 対応：レビューの指示に、割り当てられた観点が入り、割り当てていない観点が入らないこと・自分の設計がある子タスクは設計の観点になること・割り当ての無い子タスクは観点の節が出ないことを、テストで確かめた。
  - 足したテストは、対応する修正を戻すと落ちることを確かめた（3 件）。
