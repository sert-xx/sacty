# 統合レビューの「外す申告」が、「外さない」の文で、確かめていない項目を外さないようにする

- 日付: 2026-11-17（UTC）
- タスク: PBI-382
- PR: #417
- ブランチ: feat/pbi-382-dropped-checks
- 関係する ADR: [統合レビューが前の回の「人が確かめること」を外す申告は、外す種類を明示したオブジェクトだけを読む](../adr/20261117-0825-drop-human-checks-by-explicit-resolution.md)

## 目的

統合レビューは、前の回の「人が確かめること」を外すとき、答えの `droppedHumanChecks` に「<番号>：<外す理由>」を書く（PBI-363）。
読み取りは、番号の後に区切りの記号（`：`・`:`・ハイフン類）があれば、後ろの文の中身を見ずに理由として採っていた。
`H1：まだ確かめられないので外さない` や `H1 - 外さない` が、外す申告として読まれ、確かめていない項目が「人が確かめること」から外れる。

受け入れ条件の要点：

1. 外さない意図の文を、外す申告として読まない。エージェントの書き方の揺れで、確かめていない項目が外れない。迷う形は、外さない側に倒す。
2. 読み取れなかった申告は、これまでどおり記録に残す。
3. 区切りの記号つきの否定の文（日本語と英語）のテストがある。
4. 仕様書（日英）・作業履歴に反映する。

あわせて確かめること：1項目に複数の番号があるとき、理由が一部の番号だけに当たっていても全部が外れること。番号の後の長い空白で、読み取りが遅くなりうること。最終レビューに、同じ形の読み取りがあるか。

## 調べたこと

- 今の読み取り（`readDroppedHumanChecks`）の正規表現は、`H1：外さない`・`H1 - まだ確かめていない`・`H1: keep`・`H1: not verified yet` を、どれも H1 を外す申告として読む（直す前のコードに、足したテストを当てて確かめた）。
- 長い空白：統合レビューの読み取り（`extractIntegrationReview`）を直接呼んで、外す申告の1項目の長さを変えて測った（直す前のコード。手元の1台での値）。

  | 項目の形 | 1,000 文字 | 5,000 文字 | 20,000 文字 | 50,000 文字 |
  | --- | --- | --- | --- | --- |
  | `H1` + 空白 + 1文字 | 1.0 ms | 15.8 ms | 241.0 ms | 1,500.5 ms |
  | `H1` + 空白だけ | 1.3 ms | 0.6 ms | 0.4 ms | 0.9 ms |
  | `H1,` + 空白 | 0.2 ms | 0.2 ms | 0.4 ms | 0.7 ms |
  | `H1:` + 空白 | 0.0 ms | 0.1 ms | 0.3 ms | 2.2 ms |

  `H1` の後に空白が続き、区切りの記号が無いまま別の文字で終わる項目で、長さの2乗の時間がかかる（空白を読む部分が2つ続いていて、照合に失敗するたびに分け方を試し直す）。400,000 文字では 99.5 秒かかった。エージェントの答えの長さ次第で、同期処理のデーモンが止まる。
- 最終レビューの引き継ぎ（PBI-294。`[P1]` の番号と理由で外す）の読み取りは、以前の版の最終レビューの仕組みを消したとき（PBI-336）に、コードから消えている。残っているのは、記録の形（`FinalReviewed` の `droppedHumanChecks`。文字列の配列）だけで、番号と理由を読む処理は無い。同じ問題は、今のコードには無い。

## したこと

- `apps/daemon/src/prompts.ts`
  - `readDroppedHumanChecks`：外す申告を、`{"id": "<番号>", "resolution": "<verified か obsolete>", "reason": "<外す理由>"}` のオブジェクトだけから読む。番号が前の回の項目の1つを指し、`resolution` が `verified` か `obsolete` で、理由が空でないときだけ外す。文字列を読む正規表現は消した。
  - 文字列・`resolution` が無い、またはほかの値・理由が無い・1つのオブジェクトに複数の番号・前の回に無い番号は、外さずに、読み取れなかった申告として返す（記録の形は、これまでと同じ）。
  - 同じ番号に、外す申告と、外す申告として読めないオブジェクトの両方があるときは、外さない（両方を、読み取れなかった申告として返す）。
  - 番号は、全角・小文字・角括弧つき・空白入りでも読む（`droppedHumanCheckIndex`）。番号と `resolution` は、32文字より長ければ読まない。
  - 統合レビューへの指示（`previousHumanCheckLines`）：外す項目だけを、オブジェクトの形で書く。外さない項目・判断がつかない項目は `droppedHumanChecks` に書かず、外さない理由は判定の説明の文に書く。この形でないものは外れず、読み取れなかった申告として人に渡る、と伝える。
- 記録（`IntegrationReviewed` の `droppedHumanChecks`・`unreadDroppedHumanChecks`）と画面は、変えていない。
- docs：仕様書 `docs/spec/split-and-integrate`（日英）、ADR。

決めたこと：

- 文の中身を語の一覧で判定する方法は、採らなかった（理由は ADR）。外す意思を、決まった値の項目で書かせる。
- 文字列の申告は、外す意図の文（`H1：確かめられた`）でも外さない。指示に従わない答えでは、確かめ済みの項目が残るが、申告は「読み取れなかったもの」として画面に出るので、人が判断できる。
- 複数の番号は、1つのオブジェクトでは読まない（理由がどの番号に当たるかを、読み分けない）。
- 読み取れなかった申告の長さには、上限を設けなかった（人に渡す情報は切り詰めない、という今の決まりのまま）。
- 最終レビューの記録の形は、触っていない。

## 確かめたこと

- `npm run format`・`npx biome check --error-on-warnings .`：指摘なし。
- `npm run typecheck`：通過。
- `npx vitest run --no-file-parallelism`：258 ファイル・4,987 件が通過（1 件は、もとからスキップ）。
- 直し（`prompts.ts`）を戻すと、足した・直したテストのうち 6 件が落ちることを確かめた（戻し直した後に、通ることも確かめた）。長い項目のテストは、直す前は 99.5 秒かかって制限時間を超え、直した後は 42 ms だった。

足した・直したテスト：

- `apps/daemon/src/integration-dropped-checks.test.ts`（新しいファイル。読み取りを直接呼ぶ）
  - 番号・外す種類・理由がそろったオブジェクトで外す。番号と外す種類の書き方の揺れを読む。配列でない1つのオブジェクトも読む。
  - 区切りの記号つきの否定の文（`H1：外さない`・`H1 - まだ確かめていない`・`H1: keep`・`H1: not verified yet` など 17 個）を、1件ずつ・配列でない値・まとめて、のどれで答えても、外さずに記録する。
  - 外す種類が決まった値でない・理由が無い・番号が1つでない・形が違うオブジェクト（32 個。指示の形の説明を書き写したものを含む）を、外さずに記録する。
  - 同じ番号に、外す申告と、読めない申告の両方があるとき。前の回の項目が無いとき。申告が無い・空のとき。長い項目（400,000 文字）。
- `apps/daemon/src/daemon-split.test.ts`：統合レビューを通した流れのテストを、新しい形に直した（指示の文面、外した項目と理由の記録、読み取れなかった申告の記録、人が差し戻した後の回）。文字列の書き方の揺れを読むテストは、消した。

確かめていないこと：

- 実際のエージェントが、新しい指示のとおりに、オブジェクトの形で書くか。指示の文面と読み取りを、テストで確かめただけ。
- 実際のエージェントが、これまで「番号：外さない」の形で書いていた頻度。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 1 回目。[要修正] 外さない意図の申告と、同じ番号の外す申告のオブジェクトが並ぶと、項目が外れる。同じ番号の食い違いを止めるのが、`id` を番号1つとして読めたオブジェクトだけで、文字列・番号を読めないオブジェクト（`{"id": "H1,H2", …}`・`{"id": "H1 は外さない", …}`・`{"number": "H1", …}`）は止めない | 外さなかった申告に出てくる、H と数字の並びを探し（`mentionedHumanCheckIndexes`）、その番号の外す申告を採らないようにした。文字列の中と、オブジェクト・配列の中のキーと値を見る。入れ子が 32 段より深い申告は、すべての番号が出てきたものとして扱う。探した番号は、止める側にだけ使う。関数のコメント・仕様書・ADR を合わせた |
| 1 回目。[提案] 文字列・番号を読めないオブジェクトと、外す申告のオブジェクトの混在のテストが無い | 足した（指摘の 4 つの形を含む 19 個を、順序を入れ替えて）。番号を探す呼び出しを消すと、このテストが落ちることを確かめた |
| 1 回目。[提案] PBI-363 の ADR を置き換え済みにしなかった理由が、書かれていない | ADR の「理由」に書いた（その決定は今も成り立ち、外す申告の書かせ方と読み方を足しただけ） |
| 1 回目。[提案] 食い違いで採らなかった、形の正しい申告も「読み取れなかったもの」の見出しに出て、なぜ採られなかったかが分からない | 見出しを「外す申告のうち、採らなかったもの」（英語は `Removal requests that were not applied`）に変えた。ユーザードキュメント（日英）に、ここに出る申告の種類を書いた。記録の形（`unreadDroppedHumanChecks`）は変えていない。申告ごとの採らなかった理由は、記録の形を変えることになるので、出していない |

1 回目の指摘を直した後に確かめたこと：

- `npm run format`・`npx biome check --error-on-warnings .`：指摘なし。`npm run typecheck`：通過。
- `npx vitest run --no-file-parallelism`：258 ファイル・4,989 件が通過（1 件は、もとからスキップ）。
- 番号を探す処理の時間（`extractIntegrationReview` を直接呼んで、外す申告の1項目の長さを変えて測った。手元の1台での値）。どの形も、長さに比例している。

  | 項目の形 | 50,000 文字 | 400,000 文字 | 1,600,000 文字 |
  | --- | --- | --- | --- |
  | `H1` + 空白 + 1文字 | 2.4 ms | 11.2 ms | 20.1 ms |
  | `H` と空白1つの繰り返し | 0.9 ms | 11.1 ms | 39.7 ms |
  | `H` + 空白 + 数字1つ | 0.6 ms | 8.3 ms | 30.4 ms |
  | `H` + 数字の並び | 0.5 ms | 7.9 ms | 29.4 ms |
  | `H1` の繰り返し | 3.9 ms | 25.7 ms | 113.0 ms |
  | `H` の繰り返し | 1.0 ms | 9.4 ms | 43.8 ms |
  | `H` と空白8つの繰り返し | 0.7 ms | 9.9 ms | 36.1 ms |
  | オブジェクトの理由に、全角の `Ｈ` と全角の空白の繰り返し | 2.2 ms | 11.3 ms | 115.7 ms |

## 残したこと

- 採らなかった申告の長さの上限（記録と画面に、長い文字列がそのまま出る）。
- 採らなかった申告ごとの、採らなかった理由の表示（記録の形を変える必要がある）。
- 番号が H と数字の形で書かれていない食い違い（「1 番目はまだ」など）は、外す申告を止めない。
