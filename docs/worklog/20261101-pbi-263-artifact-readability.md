# 要求要件・設計の成果物から作業のメモを締め出し、判断すべきことが埋もれないようにする

- 日付: 2026-11-01（UTC）
- タスク: PBI-263
- PR: #263
- ブランチ: feat/issue-263-artifact-readability
- 関係する ADR: [要求要件・設計の本文から作業のメモを締め出し、依頼者に不利益な既定を「確認したいこと」に出させ、ID を欠番なく振らせる](../adr/20261101-1350-artifact-readability-for-decisions.md)

## 目的

実務での実証実験で、要求要件・設計は、おおむね読みやすかったが、人が承認の判断をする文書に、判断の邪魔になるものが残る、または判断すべきことが埋もれる例が出た。

- S13：要求要件の末尾の区切り線の後ろに、人の指摘への対応の報告（main の取り込みの経過）が残った。
- S9：依頼者に不利益な既定を「既定で決めたこと」に置き、「確認したいこと」に出さなかった。
- S8：依頼者が一番決めたいこと（どこまで速くするか）が should に埋もれ、推奨が逆向きだった。
- S6・S8：ID の欠番（R-5）と、別タスクの文書への参照だけの項目があった。

受け入れ条件の要点：

- 作業の経過・指摘への対応の報告・エージェント向けのメモが、成果物に残らない（提出の前に検出して直させる、など。方法は任せる）。
- 依頼の目的に関わる判断と、依頼者に不利益が出うる既定は、「確認したいこと」に出す。確認したいことは、依頼者が一番決めたいことから並べる。
- ID は欠番なく振り、別の文書を参照する項目は、中身を1行で併記する。
- 仕様書・ユーザードキュメント（日英）・作業履歴を直し、テストで振る舞いを確かめる。

## したこと

方法は、書く時点の指示と、提出の前のセルフレビューの観点の2つにした（理由は ADR）。sacty のコードで本文を機械的に検査して止める仕組みは足していない。

- 要求要件・設計の工程の指示（`apps/daemon/src/prompts.ts`）
  - `readerLoadLines`：目的に関わる判断を must に置く。確認したいことを、依頼者が一番決めたいことから並べ、推奨を依頼の意図に沿う向きにする。依頼者に不利益が出うる既定と目的に関わる判断を、「既定で決めたこと」に置かず「確認したいこと」に出す（should の上限を超えるときも、これらは既定に回さない）。
  - `deliverableBodyLines`（新規）：本文には成果物そのものだけを書かせる。作業の経過・指摘への対応の報告（`sacty-responses` に書かせる）・エージェント向けのメモ・ID を、区切り線の後ろを含めて書かせない。ID は欠番なく連番で振らせ、参照だけの項目には中身を1行で併記させる。提出の前に本文を読み直させる。
  - `selfReviewLines`（`design-doc`）：上の4つに当たる指摘は、記述を足す指摘でも `must` として直させる。
  - `earsLines`：ID を欠番なく連番で付ける。
- 既定のコンテキスト（`apps/daemon/default-context/skills/`）
  - `review` の D-6：本文に残った作業のメモ・ID の欠番・参照だけの項目の見つけ方（ID を拾って連番か確かめる手順を含む）と NG 例を足した。D-10：目的に関わる判断・不利益な既定が既定に紛れていないか、確認したいことの並びを足した。観点カタログ（`viewpoints.md`）の「見るもの」も合わせた。
  - `ears-requirements`：前の「ID は直しても付け直さない。消した要求の ID は使い回さない」は欠番を生むので、欠番なく連番で振り直す規則に変えた。人が ID で指した要求は、振り直した後の ID を返信に書く。別の文書を参照する要求の中身の併記を足した。
- docs：仕様書（`tasks-and-steps`・`context`、日英）、ユーザードキュメント（`tasks`、日英）、ADR。

## 確かめたこと

作業は、リポジトリの外の worktree で、`mise x --` の Node.js 26.12.1 を使って行った。

- `npx vitest run apps/daemon/src/prompts.test.ts apps/daemon/src/default-skills.test.ts`：追加したテストが通る。
  - 要求要件・設計の指示に、目的に関わる判断を must に置くこと・並べ方・不利益な既定を確認したいことに出すこと・本文に書かないもの・ID の連番・参照の併記・読み直し・セルフレビューでの `must` が入る。文書・調査の結果・実装の指示には入らない。
  - D-6・D-10 の観点カタログと参照のファイルに、足した観点が入る。`ears-requirements` から、欠番を生む前の規則が消えている。
- `npx vitest run tests/docs`・`npx biome check .`・`npm run typecheck`：通る。
- `npx vitest run` 全体：環境による失敗を除いて通る。
  - `install-security-tools.test.ts`（2 件）：`/usr/local/bin` に書けないため。
  - `prompts.test.ts` の「空白の無い長い URL の並びの出力も、長さに比例する時間で項目にする」：実行時間の上限（1 秒）を超えて落ちる。この変更を外した main でも約 1.4 秒で落ちるので、この機械の速さによる。
  - 全体を並列で回したときだけ、時間の上限に触れて落ちたもの（`tests/desktop/migration.test.ts`・`ci.test.ts`・`daemon.test.ts` のイベントループの 1 件）は、単独で実行すると通る。
- 修正を戻すと落ちることを確かめた：`prompts.ts` の変更を外すと、追加した指示のテスト 2 件が落ちる。
- 確かめられなかったこと：エージェント（LLM）が実際に指示とセルフレビューのとおりに、本文のメモを残さない・不利益な既定を確認したいことに出すか。実際のタスクで動かして確かめる必要がある。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| `ears-requirements` の「直しても付け直さない」が残ると、指示の「欠番なく」と食い違い、欠番を生み続ける | 規則を欠番なく振り直すものに変え、前の規則が消えていることをテストで確かめる |
| 振り直すと、人の指摘が ID で指した要求が追えなくなる | 振り直した後の ID を、その人への返信（指摘への対応）に書かせる |
| 目的に関わる判断を何でも must に置くと、must が増える | must は元から件数の上限が無い。「後で違うと分かると作業が無駄になる」ものとして、依頼の目的に関わる判断は定義に当たる。ADR の影響に書いた |
| should の上限を超えた分の回し先が、不利益な既定で埋まる | 上限を超えるときも、不利益な既定と目的に関わる判断は既定に回さず、害の小さいものを回す、と指示に書いた |
| 文書・調査の結果・実装の指示まで、要求要件・設計の決まりが混ざる | `readerLoadLines` は要求要件・設計だけが呼ぶ。入らないことをテストで確かめる |
| 公開リポジトリの既定のスキルに sacty 固有の語を書く | review スキルのテストが `sacty` の語を禁じているのに合わせ、D-6・D-10 は固有の語を使っていない |

## 残したこと

- 本文の機械的な検査（区切り線の後ろの文章・ID の欠番の検出）は足していない。検出した後に直させるには、エージェントの再実行の仕組みが要り、範囲外（予算・差し戻しの仕組み）に近い。LLM の遵守に頼るので、混入が減るかは実際のタスクで確かめる。
- 設計の本文に、テスト観点以外の ID（`TV-n` 以外）が出る場合の連番は、指示の一般則（要求・受け入れ条件・テスト観点などの ID）に任せている。
- 実装 PR の本文（PBI-264）は範囲外。
