# 要求要件・設計の成果物から作業のメモを締め出し、判断すべきことが埋もれないようにする

- 日付: 2026-11-01（UTC）
- タスク: PBI-263
- PR: #263
- ブランチ: feat/issue-263-artifact-readability
- 関係する ADR: [要求要件・設計の本文から作業のメモを締め出し、依頼者に不利益な既定を「確認したいこと」に出させ、ID を欠番なく振らせる](../adr/20261101-1350-artifact-readability-for-decisions.md)

## 目的

実務での実証実験で、要求要件・設計は、おおむね読みやすかったが、人が承認の判断をする文書に、判断の邪魔になるものが残る、または判断すべきことが埋もれる例が出た。

- S13：要求要件の末尾の区切り線の後ろに、人の指摘への対応の報告（main の取り込みの経過）が残った。
- S9：依頼者に不利益な既定を「既定で決めたこと」に置き、「確認したいこと」に出さなかった。
- S8：依頼者が一番決めたいこと（どこまで速くするか）が should に埋もれ、推奨が逆向きだった。
- S6・S8：ID の欠番（R-5）と、別タスクの文書への参照だけの項目があった。

受け入れ条件の要点：

- 作業の経過・指摘への対応の報告・エージェント向けのメモが、成果物に残らない（提出の前に検出して直させる、など。方法は任せる）。
- 依頼の目的に関わる判断と、依頼者に不利益が出うる既定は、「確認したいこと」に出す。確認したいことは、依頼者が一番決めたいことから並べる。
- ID は欠番なく振り、別の文書を参照する項目は、中身を1行で併記する（差し戻しの後に ID を詰めると、人の指摘・承認済みの文書の ID とずれるため、最初の提出に限る。下の「ID の扱いの修正」）。
- 仕様書・ユーザードキュメント（日英）・作業履歴を直し、テストで振る舞いを確かめる。

## したこと

方法は、書く時点の指示と、提出の前のセルフレビューの観点の2つにした（理由は ADR）。sacty のコードで本文を機械的に検査して止める仕組みは足していない。

- 要求要件・設計の工程の指示（`apps/daemon/src/prompts.ts`）
  - `readerLoadLines`：目的に関わる判断を must に置く。確認したいことを、依頼者が一番決めたいことから並べ、推奨を依頼の意図に沿う向きにする。依頼者に不利益が出うる既定と目的に関わる判断を、「既定で決めたこと」に置かず「確認したいこと」に出す（should の上限を超えるときも、これらは既定に回さない）。
  - `deliverableBodyLines`（新規）：本文には成果物そのものだけを書かせる。作業の経過・指摘への対応の報告（`sacty-responses` に書かせる）・エージェント向けのメモ・ID を、区切り線の後ろを含めて書かせない。ID は最初の提出では欠番なく振らせ（差し戻しで消した要求は、ID を詰めず「R-5（削除：理由）」の行を残させる）、参照だけの項目には中身を1行で併記させる。提出の前に本文を読み直させる。
  - `selfReviewLines`（`design-doc`）：メモの残り・参照だけの項目・目的に関わる判断や不利益な既定の紛れ込みの指摘は、記述を足す指摘でも `must` として直させる。理由の分からない ID の欠番は `should` でも直させる。
  - `earsLines`：ID は、最初の提出では欠番なく連番で付け、直しても付け直さない。
- 既定のコンテキスト（`apps/daemon/default-context/skills/`）
  - `review` の D-6：本文に残った作業のメモ・理由の分からない ID の欠番・参照だけの項目の見つけ方（ID を拾って欠番を確かめる手順を含む）と NG 例を足した。D-10：目的に関わる判断・不利益な既定が既定に紛れていないか、確認したいことの並びを足した。観点カタログ（`viewpoints.md`）の「見るもの」も合わせた。足した観点は、既定のスキルがあらゆるリポジトリの文書に使われるため、要求要件・設計など人が承認する成果物（D-10 は「確認したいこと」「既定で決めたこと」の節がある文書）に限り、ID を持たない文書・経緯を書く節がある文書（ADR・CHANGELOG など）には当てはめないと書いた。
  - `ears-requirements`：「ID は直しても付け直さない。消した要求の ID は使い回さない」は変えず、「最初の提出では 1 から欠番なく振る」「差し戻しで消した要求は、行を『R-5（削除：理由）』のように残して欠番の理由が分かるようにする」を足した。別の文書を参照する要求の中身の併記も足した。
- docs：仕様書（`tasks-and-steps`・`context`、日英）、ユーザードキュメント（`tasks`、日英）、ADR。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| `ears-requirements` の「直しても付け直さない」が欠番を生む | 最初に規則を振り直しに変えたが、コーディネーターの指摘で戻した（下の「ID の扱いの修正」） |
| 目的に関わる判断を何でも must に置くと、must が増える | must は元から件数の上限が無い。「後で違うと分かると作業が無駄になる」ものとして、依頼の目的に関わる判断は定義に当たる。ADR の影響に書いた |
| should の上限を超えた分の回し先が、不利益な既定で埋まる | 上限を超えるときも、不利益な既定と目的に関わる判断は既定に回さず、害の小さいものを回す、と指示に書いた |
| 文書・調査の結果・実装の指示まで、要求要件・設計の決まりが混ざる | `readerLoadLines` は要求要件・設計だけが呼ぶ。入らないことをテストで確かめる |
| 公開リポジトリの既定のスキルに sacty 固有の語を書く | review スキルのテストが `sacty` の語を禁じているのに合わせ、D-6・D-10 は固有の語を使っていない |

## 残したこと

- 本文の機械的な検査（区切り線の後ろの文章・ID の欠番の検出）は足していない。検出した後に直させるには、エージェントの再実行の仕組みが要り、範囲外（予算・差し戻しの仕組み）に近い。LLM の遵守に頼るので、混入が減るかは実際のタスクで確かめる。
- 設計の本文に、要求の ID（`R-n`）以外の、エージェントが振る ID が出る場合の連番は、指示の一般則（本文で振る ID）に任せている。
- 実装 PR の本文（PBI-264）は範囲外。

## ID の扱いの修正（コーディネーターの DA の指摘）

最初の実装は、ID を欠番なく振り直す規則にし、`ears-requirements` の「直しても付け直さない」を消した。次の指摘を受けて直した。

| 指摘 | 対応 |
| --- | --- |
| ID を振り直すと、人の指摘・承認済みの設計のテスト観点（TV が R を指す）・PR のコメントの ID がずれ、承認済みの文書と食い違う。返信に新しい ID を書かせる補いでは足りない | `ears-requirements` の規則を元に戻し、「最初の提出では 1 から欠番なく振る」「差し戻しで消した要求は、ID を詰めず『R-5（削除：理由）』の行を残す」だけを足した。要求要件・設計の指示（`deliverableBodyLines`・`earsLines`）、仕様書・ユーザードキュメント（日英）・ADR も合わせた |
| D-6 の「ID の欠番」は、理由の分からない欠番に絞る。重さは must でなくてよい | 「理由の分からない ID の欠番」とし、最初の提出で見つけたら番号を詰めさせる（`should`）。理由つきで行が残っていれば欠番と見なさない。例8 を、最初の提出の欠番（`should`）・参照だけの項目（`must`）・理由つきで残した行（指摘しない）に分けた。セルフレビューの指示では、`should` でも直させる（番号を詰めるだけで、記述を足さないため） |
| 既定のスキルはあらゆるリポジトリの文書に渡る。足した観点が、ID を持たない文書・既定の節が無い文書で誤って指摘を生まないか | D-6 の新しい確認（メモ・ID・参照）は、要求要件・設計など人が承認する成果物に限り、ID を持たない文書では確かめず、変更履歴・作業履歴・経緯の節がある文書（ADR・CHANGELOG・README など）は対象にしないと書いた。D-10 の新しい確認は「確認したいこと」「既定で決めたこと」の節がある文書に限り、節が無い文書では確かめないと書いた。テストで確かめる |
