# ブラウザで認証する MCP サーバーを、ホストで動かしてエージェントに使わせる

- 日付: 2026-10-12（UTC）
- タスク: PBI-36
- PR: #43
- ブランチ: feat/issue-36-host-mcp
- 関係する ADR: [ブラウザで認証する MCP サーバーは、ゲートウェイがホストで起動して持ち続け、期限の前に起動し直して、HTTP の MCP として中継する](../adr/20261012-1327-host-mcp-servers.md)

## 目的

起動時にブラウザで認証する MCP サーバーは、コンテナの中では動かせない。ゲートウェイがホストで起動して持ち続け、工程エージェントには
HTTP の MCP として中継する。認証の期限（数時間）の前に自動で起動し直して再認証する。受け入れ条件の要点：config.yaml にホストで動かす
MCP サーバーを書ける、ゲートウェイがホストで起動しブラウザの認証はホストで行える、設定した間隔で期限の前に起動し直す（準備ができてから
切り替える）・終了や認証エラーでも起動し直す、準備ができないときはどの MCP サーバーかと理由を画面に出し呼び出しには 503、
コンテナからは HTTP の MCP として Claude Code・Codex のどちらにも渡せる、コンテナからだけ使える（実行ごとのトークン）。

## したこと

- `apps/daemon/src/host-mcp.ts`（新規）：公式の SDK（`@modelcontextprotocol/sdk` 1.30.1）の stdio のクライアントでホストに起動し、MCP の初期化を待つ。
  HTTP 側は、リクエストごとに中継のサーバーを作って JSON で返す。起動し直し・切り替え・認証エラーの検知・準備ができないときの扱い。
- `apps/daemon/src/config.ts`：`gateway.mcp_servers`（`command`・`args`・`env`・`restart_every_min`・`ready_timeout_sec`）。
- `apps/daemon/src/context.ts`・`apps/daemon/src/agents/invocation.ts`：コンテキストの MCP に `<ゲートウェイ>/mcp/<名前>` の HTTP の MCP を加え、
  認証のヘッダーに実行ごとのトークンを入れる。
- `apps/daemon/src/gateway.ts`・`apps/daemon/src/main.ts`・`apps/daemon/src/service.ts`：中継の入口と起動、準備ができない MCP サーバーを
  タスクの一覧の警告（#42 の warnings）に出す。`README.md` に例を足した。
- 古いプロセスは途中の呼び出しが終わってから止め、いま使っている接続の失敗のときだけ起動し直すようにした。ツールの呼び出しを待つ上限を
  SDK の既定の 60 秒から 10 分にした。
- レビューの指摘で、起動の失敗の理由から秘密情報を伏せ、認証が切れた接続を使わず、例外として返る認証エラーでも再認証するようにした。

## 確かめたこと

- `npm test`（409 件）・`npm run lint`・`npm run typecheck` が通った。
- ホストの MCP サーバーのテスト（SDK のメモリー上の MCP サーバーを偽物にし、ゲートウェイには実際の HTTP で SDK のクライアントからつなぐ）：
  中継・秘密情報の環境変数・トークンの無い呼び出しの拒否・期限の前の起動し直し・プロセスの終了・認証エラー・準備ができないとき・設定の変更・
  起動の途中の設定の変更・途中の呼び出しが終わってから切り替える・待つ上限を過ぎたときに起動し直さない。
- 終了・認証エラー・間隔での起動し直し・起動の途中の設定の変更・準備ができたら警告を消す・途中の呼び出しを待つ・古い接続の失敗で起動し直さない・
  トークンを入れる・トークンを秘密情報として取り出さない、の修正を1つずつ戻すとテストが失敗することを確かめた。
- 実際の stdio の MCP サーバー（起動時に「ブラウザで認証」し、4秒で期限が切れる偽物）をホストで起動し、実際のコンテナから呼んだ。
  - 期限の前に3秒ごとに起動し直す設定では、プロセスが入れ替わっても呼び出しは一度も失敗しなかった。
  - 起動し直す設定が無いときは、期限切れの呼び出しが認証エラーとやり直しの案内を返し、2秒後の呼び出しは再認証したプロセスで成功した。
- 最後のレビューでは、全 409 件・lint・typecheck の成功と、HTTP 経由の独立した確かめで、JSON-RPC の認証エラーに対して起動が2回・起動し直しが1回に
  なることを確かめた。実際のブラウザの認証・実際の MCP サーバー、Claude Code・Codex のコンテナとの接続は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 環境変数に入れた秘密情報を MCP サーバーが認証の失敗で標準エラーに出すと、起動の失敗の理由に入り、ログ・画面の警告・エージェントへの 503 にそのまま出る。切り詰めの境界で一部だけ残る場合もある | 標準エラーを 64KB まで持っておき、秘密情報（値そのもの・前置きを付けた形・JSON の文字列にした形・各行）を伏せてから末尾（300 文字）を添え、理由を 600 文字に切り詰めるようにした。子プロセスが `'x'.repeat(N) + 'token=' + 秘密情報` を出して終わる回帰テストを N = 0・280・290・590・990・70000 で足し、伏せる処理を戻すと失敗することを確かめた |
| 再認証に失敗しても期限切れの接続が残り、以降の呼び出しも 200 で古い接続に転送される。認証エラーのたびに即時に起動し直すので、1分の間隔を待たずにブラウザの認証を繰り返す | 認証エラーを返した接続に期限切れの印を付け、準備ができるまで新しい呼び出しに使わず 503 を返すようにした。起動し直すのはその接続で1回だけ（失敗したら1分ごと）。最初の起動だけ成功する形で、認証エラーの後の3回の呼び出しが 503・起動が2回だけになるテストを足した。ツールの誤りの例外では起動し直さず、接続が切れたときだけ起動し直すようにした。元の形に戻すとそれぞれ失敗することを確かめた |
| 前の修正で、例外では接続が切れたときだけ起動し直すようにしたため、認証切れを JSON-RPC のエラー（`McpError(-32001, "401 Unauthorized: token expired")`）で返す MCP サーバーで再認証しなくなった | 例外の文が認証エラーらしいときも、結果の isError と同じく接続を期限切れにして起動し直すようにした。引数の誤りでは、これまでどおり起動し直さない。同じ例外を返す回帰テスト（引数の誤りでは起動し直さないことも含む）を足し、判定を戻すと失敗することを確かめた |

## 残したこと

- 実際の環境での確認（`gateway.mcp_servers` に MCP サーバーのコマンドと期限より短い `restart_every_min` を書き、起動時にブラウザの認証が進むこと、
  タスクでツールを呼べること、期限より長く動かしても起動し直しのたびに再認証されて呼び出しが続くことを確かめる）は、利用者の環境で行う。
