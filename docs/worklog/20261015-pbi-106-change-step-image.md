# タスクの詳細で、工程のイメージを変えられるようにする

- 日付: 2026-10-15（UTC）
- タスク: PBI-106
- PR: #116
- ブランチ: feat/issue-106-change-step-image
- 関係する ADR: [工程のイメージを、人がタスクの詳細でいつでも変えられるようにし、その工程を次に実行するときから使う](../adr/20261015-1115-superseded-change-step-image.md)

## 目的

オーケストレーターが工程に合わないイメージ（Playwright の要るリポジトリで既定のイメージなど）を選ぶとテストが失敗し、人が直す手段が
無いのでタスクを作り直すしかなかった。タスクの詳細で、工程ごとのイメージを `images` から選び直せるようにする。

## したこと

- 新しいイベント `StepImageChanged`（工程・変える前・変えた後。actor は person）を足した。投影は、その工程の `images` を変え、
  `imageChanges` に工程ごとの最後の変更（時刻を含む）を持つ。工程を決めたときの選んだ元（`imageSource`）も投影に持たせた。
- デーモンに `changeStepImage` と `POST /api/tasks/:id/images` を足した。工程の状態は問わない（実行中・終わった工程も変えられる）。
  `images` に無い名前・同じ名前・タスクに無い工程・PR作成（イメージが無い）・中止したタスクは、理由を示して断る（ja・en）。
- 工程の実行と統合レビューは、`AgentRunStarted` を足したときのイメージに決めるようにした（実行の準備の間に変えても、今の実行は変えない）。
  テストは、テストを始めるときのイメージで実行する（今までどおり）。
- 画面：タスクの詳細の「工程」の欄に「工程のイメージ」を足した。工程ごとに、イメージ・選んだ元（人が変えた時刻と変える前の名前、
  プロジェクトの対象の指定、オーケストレーター、指定なし）・変えたらいつから使うか（実行中なら次の実行から）と、説明つきの選択肢で
  変える操作を出す。作業履歴に、誰が・どの工程を・何から何に変えたかを出す。
- プロジェクトの対象でイメージを指定しているタスクも変えられ、人が変えた工程だけ優先すると決めた（ADR）。
- 仕様書（`tasks-and-steps.md`・`agent-execution.md`）と利用者向けの文書（`images.md`・`tasks.md`）を、英語の版も直した。

## 確かめたこと

- 回帰テスト：
  - `apps/daemon/src/daemon.test.ts` の「工程のイメージを人が変える（PBI-106）」7件。これから実行する工程・承認待ち・終わった工程を変え、
    手戻りと次の工程で変えたイメージを使うこと、台帳（person・from・to）と `StepsChosen` が書き換わらないこと。実行の準備の間（実行中）に
    変えても今の実行は変わらず、次の実行から使うこと。失敗して止まった工程を変えて再開すると変えたイメージで動くこと。実装の工程を変えると
    実装とテストが変えたイメージで動くこと。プロジェクトの指定より人の変更が優先すること。断る場合（ja・en の文言、config.yaml から
    消した名前を含む）と API（200・409・400）。
  - `packages/core/src/projection.test.ts`：実行中の工程の変更と記録、タスクに無い工程は作業履歴の誤り。
  - `apps/web/src/lib/labels.test.ts`：作業履歴の文（ja・en）と、工程のイメージの欄の行（選んだ元・いつから使うか・PR作成を出さない）。
  - 修正を戻すと落ちることを確かめた：投影でイメージを変えないと daemon の7件が落ち、実行の開始でイメージを決めるのを戻す（実行の直前に
    読む）と「実行中の工程を変えても今の実行は変えず」が落ちる。
- `npm run lint`（終了コード 0）・`npm run typecheck`・`npx vitest run`（1520 件）・`npm run build`・`npx vitest run tests/docs` が通る。
- 画面：自分のブランチを別のポートと一時的な `SACTY_HOME`（スタブの AI）で起動し、オーケストレーターが選んだ作っていないイメージで
  要求要件が失敗して止まる → 工程のイメージを変える → 再開する → 変えたイメージで要求要件が完了する、を動画に撮った。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （ステークホルダーの要件の変更）実行中・終わった工程を含め、いつでも変えられるようにする。今の実行は止めず、次の実行から使う | 状態で変えられない工程を作らないようにし、実行の開始でイメージを決めるようにした。画面にいつから使うかを出した |
| （DA のセルフレビュー）変えた直後に、選択の欄が前のイメージに戻って見えた（フォームのリセット） | イメージが変わったらフォームを作り直すようにした。動画を撮り直した |
| （PR #115・PBI-105 のマージへの追従）`StepsChosen` に、既定のイメージにした理由（`defaultImageReasons`）と理由の無い工程（`imagesUnexplained`）が入った。人がイメージを変えた後に、画面と作業履歴で矛盾しないか | main を取り込んだ（衝突なし）。投影に2つを持たせ、工程のイメージの欄の選んだ元に、人が変えるまで既定のイメージにした理由（か理由が無いこと）を出し、人が変えたら人の変更を出すようにした。作業履歴の「工程を決定」の行は決めたときの記録のまま残り、後の変更の行で変えたことがわかる。回帰テスト（`labels.test.ts`）を足し、理由を出す分岐を戻すと落ちることを確かめた。仕様書と利用者向けの文書（日英）に書き足した。デモの流れ（オーケストレーターが言語のイメージを選ぶ）の画面は変わらないので、動画は撮り直していない |
| （PR #116 のレビュー）config.yaml を読めない・解析できないときも、登録済みのイメージを「images にありません」と断り、名前の問題と誤解される | 設定を読めなければ、設定の読み込み・解析の失敗として理由を示して断るようにした（`image.configUnavailable`、ja・en）。回帰テストを足し、戻すと落ちることを確かめた |
| （PR #116 のレビュー）`getStatus()` の取得の失敗を空の `images` として扱い、有効なイメージにも消した名前の警告が付き、選択肢が default だけになる | 取得できない・設定を読めない・古いデーモンのときは、候補を確かめられないことを出し、警告と変更のフォームを出さないようにした（`stepImageOptions`）。回帰テストを足し、戻すと落ちることを確かめた。取得できないときの表示を動画に撮った |
| （PR #116 のレビュー）実装の実行中に変えたときの境界（今の実装は開始時のイメージ、その後のテストは変えたイメージ）と、統合レビューの実行中の変更を確かめていない | 実装のコンテナの実行中に変える回帰テストと、統合レビューを始めた後（コンテナの起動の前）に変え、今のレビューは開始時のイメージ、次の統合レビューは変えたイメージで動くことを確かめる回帰テストを足した。投影でイメージを変えないと前者が、実行の開始でイメージを決めるのを戻すと後者が落ちる |

## 残したこと

- PR作成の工程はコンテナで実行しないので、イメージを変えられない（画面にも出さない）。
