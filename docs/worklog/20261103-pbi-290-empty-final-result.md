# エージェントの最後の結果が空でも、中身のある成果物を提出する（空の成果物を PR にしない）

- 日付: 2026-11-03（UTC）
- タスク: PBI-290
- PR: なし
- ブランチ: feat/issue-290-pbi-290
- 関係する ADR: なし

## 目的

実験 S16 r2 の設計1回目で、設計の本文が出ていたのに最後のターンの空の結果が採用され、設計 PR の `design.md` が「（なし）」になった（費用 $30 がほぼ無駄になった）。
受け入れ条件の要点：原因を作業履歴に書く／最後の結果が空でも、その前の中身のある結果を成果物にする／中身のある結果が無ければ、空の成果物にせず失敗にする（今のエラーの扱いに合わせる）／成果物を最後の結果から取るすべての工程に当てる／再現のテスト。

## 原因

- 起きた場面：Claude Code（`claude -p --output-format stream-json`）の実行。設計1回目（タスク baa3df24、実行 8aaaddf0）では、レビュー担当を19件、バックグラウンドで起動していた。
  実行の出来事は、行 834 に設計の本文（7,774 文字）の `result`、行 835 に新しいターンの `system/init`、行 836 に `origin` が `task-notification` の `result`（0 文字）という順だった。バックグラウンドの担当の完了通知が、本文の後に空のターンを起こした。
- 最後の結果を選ぶ所：`ClaudeOutcomeReader.outcome`（`apps/daemon/src/agents/parse.ts`）が、最後の `result` の文を答えにしていた。例外は「目印を含む最後の `result`」を選ぶ役割（レビュー・最終レビュー・再現・分割・統合レビュー・情報収集）だけで、設計・要求要件・実装・調査・文書などの目印の無い役割は、最後の `result` がそのまま答えだった（PBI-154 の対策は、この役割に効かなかった）。
- 空の答えは `completed` として呼び出し側へ渡り、`service.ts` の工程の実行が本文を空のまま提出し、PR の本文は「（なし）」のひな形になった。空かどうかを見る所はどこにも無かった。
- 起きうる実行環境と工程：
  - Claude Code：どの工程でも起きうる。バックグラウンドの担当（サブエージェント・バックグラウンドのコマンド）を使う工程で、その完了通知が最後の答えの後に届くと起きる。目印の無い役割（要求要件・設計・実装・調査・文書など）が、結果を失う。目印のある役割は、目印を含む `result` があれば影響を受けないが、その `result` が無いと同じ。
  - Codex：`CodexOutcomeReader` は、最後の `agent_message` で答えを上書きしていたので、最後が空の発言なら同じことが起きうる。実際に起きた記録は無い（バックグラウンドの完了通知で番が進む仕組みを持たないため、起きにくいと考える）。

## したこと

- `ClaudeOutcomeReader`：中身のある（空白だけでない）最後の成功の `result` を覚え、最後の `result` が空のとき、それを答えにする。使い分けたときは `notice` で知らせる（デーモンのログとセッションログ）。`is_error` の `result` は置き換えない。
- 答えがどこにも空のときは、`completed` にせず `failed`（`error`、新しい文言 `run.emptyResult`）にする。使用量は残し、最後の `result` の後に始まった番があれば足して不明の印を付ける（PBI-281 と同じ扱い）。
- `CodexOutcomeReader`：空の発言で、前の中身のある発言を上書きしない。中身のある発言が無ければ失敗にする。
- 失敗は `AgentOutcome` として返るので、工程・ゴールガーディアン・最終レビューなど、すべての呼び出し側が今の失敗の扱い（代わりのエージェントへの切り替え、無ければ一時停止、再開で同じ工程をやり直す）に乗る。工程ごとの分岐は足していない。
- 既存のテスト `agents.test.ts`（認証ファイルの差し替え）の偽の Codex 出力に発言が無かったので、発言（`agent_message`）を1行足した（発言が無い実行は、いまは失敗になる）。
- docs：仕様書（agent-execution。日英）、ユーザードキュメント（config。日英）。

## 確かめたこと

結果は PR に書く。全体の `vitest run` は、負荷の高い実行で時間を測る3件（`ci.test.ts`・`prompts.test.ts` の長い文字列の処理時間、`tests/desktop/migration.test.ts`）が落ちたが、単独で実行すると通る（この変更とは関係しない）。

- 足したテスト `apps/daemon/src/agents/empty-result.test.ts`：S16 r2 の形（引き継ぎの `result` → 本文 → 通知の番の空の `result`）、空白・改行だけ、空が続く、前の中身のある `result` が複数、目印のある役割、中身のある `result` が無い（1つ・複数・json の形）、最後の `result` の後に始まった番、`is_error`、終了コードが 0 でない、`result` が1つだけ、Codex（空の発言・発言なし・終わっていない番）、偽の docker での通しの2件。
- 修正（`parse.ts`）を戻すと、14件のうち12件が落ちることを確かめた（残る2件は、これまでどおりの動きを確かめるもの）。

## 残したこと

- 短くても空でない返事（「待機します」など）が最後に来て本文が前にある場合は、中身があると扱うので、前の本文には戻らない。目印のある役割だけが、これを避けられる（PBI-154）。
- 空の成果物の失敗は、ほかの失敗と同じく、同じ工程の再実行になる。バックグラウンドの担当を使う工程が同じことを繰り返す可能性は、この PBI では扱わない。
