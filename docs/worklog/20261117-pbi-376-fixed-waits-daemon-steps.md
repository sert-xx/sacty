# デーモンのテストの「固定の時間を待つ」書き方を、条件を待つ形に置き換える（1：工程のテスト）

- 日付: 2026-11-17（UTC）
- タスク: PBI-376
- PR: なし
- ブランチ: feat/pbi-376-fixed-waits-steps
- 関係する ADR: なし

## 目的

デーモンのテストに、処理の完了を、固定の数十ミリ秒の待ちで待つ書き方がある。
2026-11-17、この書き方のテスト（`apps/daemon/src/daemon-steps.test.ts` の「タスクの並行実行（PBI-30）」>「同時に実行している中の1件を一時停止すると、そのタスクのコンテナだけを止める」）が、main の CI で 1 回落ちた（`expected [] to deeply equal [ 'タスクA', 'タスクB' ]`。2 つのタスクが実行に入る前に、30 ミリ秒の待ちが終わった）。
リポジトリの持ち主が、まとめて直すと決めた。

受け入れ条件の要点：

- 固定の待ちで処理の完了を待っている所を、条件が満たされるまで待つ形（上限つき）か、時計の差し替えに置き換える。「何も起きないこと」を確かめるための待ちは、理由を書いて残してよい。
- テストが確かめている内容（期待値）は変えない。本体のコードは変えない。
- 置き換えた後、負荷をかけた状態で繰り返し実行して、落ちないことを確かめる。
- テストのファイルごとに PR を分けてよい。最初の PR に、落ちたテストのあるファイルを入れる。

この作業履歴は、最初の PR（`daemon-steps.test.ts`）のもの。

## 最初に数えたこと

- `grep -c "settle("` は、5 つのファイルで 142 か所に当たる。ただし、その多くは、固定の待ちではない。同じ名前の別の補助（タスクが承認待ちか一時停止になるまで `runNext` を繰り返す関数。`daemon-split.test.ts`・`daemon-orchestrator-sessions.test.ts`・`daemon-step-pull-requests.test.ts` にある）の呼び出しで、時間に頼っていない。

  | ファイル | 補助の呼び出し | その場の `setTimeout` | 計 |

  | `daemon-implement.test.ts` | 45（5 ミリ秒の `settle`・`settleAsks`） | 6 | 51 |

  `daemon-split.test.ts` には、固定の待ちは無い。
- `daemon-*.test.ts` のほかのデーモンのテストには、同じ形が 32 か所ある（`host-mcp.test.ts` 10、`notifier.test.ts` 5、`secrets.test.ts` 4、`gateway.test.ts` 3、`repository.test.ts` 3、`drawio-shim.test.ts` 2、`context-mcp.test.ts`・`context-images.test.ts`・`gh.test.ts`・`host-mcp-processes.test.ts`・`workspace-cleanup.test.ts` が各 1）。完了を待つものか、何も起きないことを見るものかは、まだ分けていない。この PR では触っていない。

## したこと

`apps/daemon/src/daemon-steps.test.ts` の 11 か所のうち、処理の完了を待っていた 9 か所を置き換え、何も起きないことを見る 2 か所を、理由を書いて残した。本体のコードは変えていない。

- 「タスクの並行実行（PBI-30）」の 3 つのテスト（30 ミリ秒の `settle` が 8 か所）：
  - タスクが実行に入るのを待つ所は、止めてある実行の題が、期待する並びになるまで待つ（`held`）。
  - 上限を超えて始めていないこと・実行中のタスクを重ねて始めていないことは、Worker が始めた実行の数（`runNext` の呼び出しの数）で確かめる。Worker は、`tick` の中で、同期で `runNext` を呼ぶので、`tick` の直後に数が決まる。これまでは、30 ミリ秒の間に余計な実行が現れないことで見ていた。条件を待つ形だけにすると、余計な実行が遅れて現れるのを見逃すので、数の確認を足した。元の期待値（止めてある実行の題・工程を選んだ回数）は、そのまま残している。
  - 実行が終わって Worker が枠を空けるのを待つ所は、その実行（`runNext` が返した Promise）の終わりを待ち、イベントループを一巡させる（`freed`）。Worker は、実行の終わりに続く処理（マイクロタスク）で枠を空けるので、一巡で済む。
  - 工程を選んだ後に実行に入るのを待つ所は、止めてある実行にそのタスクが現れるまで待つ。
- 「停止時は、実行中の処理が作業履歴に記録されるまで待つ」（20 ミリ秒が 2 か所）：
  - 実行が始まるのを待つ所は、エージェントの実行が呼ばれるまで待つ。
  - 停止が終わっていないことを見る所は、残した（下）。
- 条件を待つのには、既にある `apps/daemon/src/testing/wait.ts` の `waitFor` を使った（期限は、テストの時間切れの少し前。期限を過ぎたら、何を待っていたかを書いたエラーで落ちる）。

残した 2 か所（どちらも 20 ミリ秒）：

- 「実行の前に、使うホストの MCP サーバーの準備を待ってからエージェントを動かし…（PBI-77）」：準備を待っている間に、エージェントを動かしていないことを見る。
- 「停止時は、実行中の処理が作業履歴に記録されるまで待つ」：実行中なのに、停止が終わってしまわないことを見る。

残した理由：どちらも、何も起きないことを見るための猶予で、処理の完了は待っていない。猶予が環境に対して短くても、テストは誤って落ちない（起きてはいけないことを見逃すことがあるだけ）。前提（準備を待ち始めた・実行が始まった）は、条件で確かめた後に置いている。
この種類の待ちを、完了を待つ固定の待ちと見分けられるよう、`apps/daemon/src/testing/wait.ts` に `idleFor` を足して、名前を付けた（テストの補助。本体のビルドには入らない）。

自分で決めたこと（人の確認は、まだ）：

- 何も起きないことを見る待ちは、時間を変えずに残し、`idleFor` という名前を付ける。
- 上限・重ねて始めないことの確認に、`runNext` の呼び出しの数の確認を足す（期待値の追加。元の期待値は変えていない）。
- PR は、`daemon-steps.test.ts`、`daemon-implement.test.ts`、残りの `daemon-*.test.ts` の順に分ける。`daemon-*.test.ts` のほかのテストの 32 か所は、この PBI の範囲に入れるかどうかを決めていない。

## 確かめたこと

PR を作る前のコードで実行した結果。

- 置き換える前に落ちることの再現：置き換える前の `daemon-steps.test.ts` を、6 並列で各 25 回（計 150 回）実行して、3 回落ちた。3 回とも「タスクの並行実行（PBI-30）」>「実行待ちのタスクを、古い順に上限の数まで同時に実行し、空いたら次を始める」で、CI で落ちたときと同じ形（`expected [] to deeply equal [ 'タスク1', 'タスク2' ]`、`expected [ 'タスク2' ] to deeply equal [ 'タスク1', 'タスク2' ]`、`expected [ 'タスク2' ] to deeply equal [ 'タスク2', 'タスク3' ]`。待ちが終わったときに、まだ実行に入っていない）。負荷は、同じテストの並列の実行そのもの（12 コアのマシンで 6 並列）。
- 置き換えた後：同じ条件（6 並列で各 25 回、計 150 回）を 2 度（自己レビューの直しの前と後。計 300 回）実行して、落ちた回は 0。
- 全テスト（`npx vitest run --no-file-parallelism`）を、CPU に負荷をかけた状態（CPU を使い切るプロセスを 5 つ動かす。12 コアのマシン）で 3 回実行して、3 回とも 4962 件が通った（1 件は以前からの skip。1 回 254〜261 秒）。1 回目の途中で自己レビューの直し（下）を入れたので、直した後のコードだけで実行したのは 2 回。
- `npm run lint`・`npm run typecheck`：通った。`npx vitest run tests/docs`：通った。
- 置き換えたテストが、本体の誤りを見つけること（本体の 1 行を消して実行し、元に戻した）：
  - `apps/daemon/src/worker.ts` の、実行中のタスクを飛ばす行を消す → 「工程を選んでいる間…重ねて始めない」が落ちる（`expected "runNext" to be called 1 times, but got 2 times`）。
  - 上限で打ち切る行を消す → 「…上限の数まで同時に実行し…」が落ちる（`expected "runNext" to be called 2 times, but got 3 times`）。
  - 停止で実行中の処理を待つ行を消す → 「停止時は…」が落ちる（`expected true to be false`）。

自己レビューで直したこと：

- `freed` が、待つ実行を見つけられないときに、何も待たずに先へ進んでいた。見つからなければ、理由を書いたエラーで落とすようにした。
- 工程を選び始めるのを待つ条件を、「1 回」から「1 回以上」にした（2 回選んでいたら、待ちの時間切れではなく、回数の確認で落ちるように）。
