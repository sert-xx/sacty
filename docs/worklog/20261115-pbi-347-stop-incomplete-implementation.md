# 終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない

- 日付: 2026-11-15（UTC）

- 関係する ADR: [終わっていない実装を提出にせず、変更の無いやり直しで行き止まりにしない](../adr/20261115-1224-superseded-stop-incomplete-implementation-and-unchanged-rework.md)

## 目的

タスク分割の子タスクの実装が、範囲の一部だけを実装して「実装は未完了です」と書いて終わり、sacty がそのまま PR を作った。
PR のレビューの子タスクの指摘を受けたやり直しも何も変えずに終わり、PR の先頭が変わらないので再レビューが始まらず、タスクが動かなくなった。
人から、この2つの仕組みの欠陥を1つの PR で直すよう指示された（指示の文の見直しは、次の PR）。

受け入れ条件の要点は次のとおり。

- 実装の工程の指示が、完了の申告を必ず付けるよう求める。
- 未完了と申告した・申告が無い実行は提出しない（PR を作らない・更新しない）。残っていることを渡して実装をやり直し、続けて終わらなければ一時停止して、残っていることを出す。
- 完了と申告した実行と、申告させる前の作業履歴は、今までどおり提出に進む。
- AI のレビューが指摘を残した PR の先頭を、やり直しが変えなかったら、提出にせず一時停止する。行き止まりにならないやり直しは、今までどおり提出する。
- 一時停止の理由が、画面・一覧・お知らせから分かる（日本語と英語）。

## レビューの指摘と対応

- sacty のレビュー（1回目。判定：修正が必要）
  - 要修正：作業領域が変わったかを、差分の文字列の目印で比べていた。差分は 200,000 文字で切り詰めるので、大きな差分の後ろだけをやり直しで変えると、進んでいるのに「何も変わらなかった」として止まる。
    - 対応：作業領域の内容の git のツリーの ID（`RepositoryWorkspace.treeId`）で比べるようにした。
      実際の git で、切り詰めた差分は同じでも、上限より後ろのファイルを変えると ID が変わることを確かめるテストを足した（`apps/daemon/src/repository.test.ts`）。
  - 提案：未完了の記録と一時停止を別々に記録していて、間でデーモンが止まると、止めるはずの実装を再起動の後にもう一度実行する。
    - 対応：止めるかを記録の前に決めて（`nextIncompleteRuns`）、同じ追記で記録するようにした。追記の単位を確かめるテストを足した。
  - 提案：ユーザードキュメントは「GitHub でドラフトを外してマージ」と案内しているが、一時停止したタスクの PR は、確認のたびにドラフトへ戻される。
    - 対応：変更の無いやり直しで止まったタスク（`unchanged`）の PR は、人がドラフトを外しても戻さないようにした（`settlePausedDraft`）。
      ドラフトを外しても戻されないこと、マージすると実装を承認して進むこと、ほかの理由の一時停止では今までどおり戻すことを確かめるテストを足した。
      仕様書・ユーザードキュメント（日本語と英語）・ADR に書いた。
  - 提案：ユーザードキュメントの「指摘なしにしていない PR」という説明だと、子タスクがまだレビューしていない・レビューの途中のときも止まるように読める。
    - 対応：子タスクがその内容のレビューを終えて指摘を残しているときに止めることと、まだレビューしていない・レビューの途中のときは今までどおり提出することを、日本語と英語で書き直した。
- sacty のレビュー（2回目。判定：修正が必要。1回目の4件は、対応を確認）

    - 対応：2つの理由を並びに足した。並びを、すべての理由に順位を付ける表（`satisfies Record<PauseReason, number>`）から作るようにして、理由を足したのに順位を付け忘れると型検査で落ちるようにした。
      どの理由も並びに入っていることと、2つの理由で止まったタスクが欄に出ることを確かめるテストを足した（`apps/web/src/lib/dashboard-data.test.ts`）。

  - 提案（5件。どれもテストの穴）：申告の項目が無い実装の完了をサービスが提出に進めること、子タスクの指摘なしを待たない PR、レビューの途中の子タスク、`ImplementationUnchanged` と一時停止が同じ追記であること、未完了のやり直しの間のマージ。
    - 対応：テストを7件足した（独立レビューのエージェントが、再現に使ったテストをもとに書いた。対応する実装を戻すと落ちることを、複製で確かめている。順序の入れ替えを戻すと2件が落ちることは、作業ツリーでも確かめた）。
  - 順序の入れ替えで変わること：未完了の実行では、人が PR に足したコミットの取り込みが、次の実行を始める前になる。作業領域の内容の目印は取り込みの前に取るので、「何も変わらなかった」の検出が、まれに1回遅れる（回数の上限では止まる）。
