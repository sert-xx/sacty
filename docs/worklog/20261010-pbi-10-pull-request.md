# PR の作成と成果物チェックのゲート、見逃しの記録を作る（PBI-10 の後半）

- タスク: PBI-10
- PR: #7

- 関係する ADR: [最終レビューに通ったら sacty が sacty のブランチにプッシュして PR を作り、成果物チェックのゲートで止める](../adr/20261010-0858-superseded-pull-request-and-deliverable-gate.md)、[成果物チェックで人間が差し戻したら、そのとき合格だったゴールガーディアンの最終レビューを「見逃し」として記録する](../adr/20261010-0858-superseded-guardian-missed-record.md)

## 目的

PBI-10 の後半（PBI-10b、受け入れ条件4〜5）。前半は #6 でマージ済み。最終レビューを通ったら、対象リポジトリにブランチを作って
PR を作成し、成果物チェックのゲートで止めること、人間が差し戻したらゴールガーディアンの合格の判定を「見逃し」として記録することが要点。

## したこと

- PR の作成（`apps/daemon/src/repository.ts`・`github.ts`・`service.ts`）：退避した git のメタデータでコミットを作り、`sacty/task-<id>` にプッシュする。
  再提出は前回のコミットに積む。`repository.pull_request` を設定したときだけ GitHub API で PR を作り、2回目以降は本文を更新する（`apps/daemon/src/config.ts`）。
- PR の本文：承認済みの要求要件・対応表・テストの結果・最終レビューを載せる。
- 成果物チェックのゲート：承認で完了、やり直す工程（実装・設計・要求要件、既定は実装）を選んで差し戻す（`apps/web/src/components/gate-form.tsx`・`review/page.tsx`）。
- 見逃しの記録（`GuardianMissed`、`packages/core/src/events.ts`・`projection.ts`）と、タスクの詳細での表示（`apps/web/src/components/pull-request.tsx`）。
- トークンはキーチェーンから取り出し、エラーの文から取り除いてから台帳に記録する。起点から変更が無ければ PR を作らずに止める。
- 起動の時に、PBI-10a で最終レビューに通って待機していたタスクを実行待ちにする。
- 動作確認用の作業領域（`.sacty`）を Biome の対象から外した（`biome.json`）。動作確認のリポジトリのファイルを整形していたため。

## 確かめたこと

- `npm test` が全件通った（111件。11件追加）。
- 本物の git で、ローカルの origin にコミットをプッシュし再提出は前回のコミットに積むこと、変更が無ければ同じコミットのままにすること、
  作業領域に仕込んだ clean フィルターや hooksPath がホストで実行されないこと、作業領域の HEAD を動かさないことを確かめた。
- GitHub API のクライアントは、偽の fetch で確かめた（作成、同じブランチの PR がすでにある場合、本文の更新、失敗したときのエラーの文）。
  実際の GitHub への PR の作成は、外部に公開される操作なので行っていない。
- 画面で、スタブのエージェントとローカルの対象リポジトリを使い、次の流れを確かめた：承認から実装・検証まで進む → ブランチにプッシュする →
  成果物チェックで実装へ差し戻すと見逃しが記録される → 実装をやり直し、成果物チェックに再提出する（2回目）→ 承認して完了になる。
- 幅 375px で横スクロールが出ないことを確かめた。
- 再レビューでは `npm test`（112件）・`npm run lint`・`npm run typecheck` が通った。実際の GitHub への PR の作成・本物のコンテナ・ブラウザでの動作は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| プッシュの後、台帳に記録する前に失敗すると、再開のときに古い親からコミットを作り直し、日時が変わって前回のプッシュと枝分かれし、non-fast-forward で拒否される | コミットの作者・コミッターの日時を、その提出の最終レビューの日時に固定した。同じ提出なら同じコミットになり、再開のときのプッシュは何も変えずに成功する。本物の git で1秒以上あけて2回 publish する回帰テストと、サービスの層で PR の作成の失敗から再開するテストを足した。日時の固定を外すと失敗することを確かめた |
| 実装への指摘の対応の `respondedIn` が実装の提出回で数えられ、常に 1 になるので、成果物チェックの2回目でも「1回目の提出での対応」と表示される | 実装の実行の完了で記録する `respondedIn` を、成果物チェック（PR の作成のゲート）の次の提出回にした。指摘の手順で 2 になることをテストに加え、修正前のコードで失敗することを確かめた |

## 残したこと

- 実際の GitHub への PR の作成は確かめていない。
