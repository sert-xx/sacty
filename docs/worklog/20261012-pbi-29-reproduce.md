# 「再現」の工程で、不具合を失敗するテストで再現してから直す

- 日付: 2026-10-12（UTC）
- タスク: PBI-29
- PR: #35
- ブランチ: feat/issue-29-reproduce
- 関係する ADR: [不具合の修正は「再現」の工程で失敗するテストを書かせ、sacty がテストの失敗を確かめてから承認なしに実装へ進める](../adr/20261012-0516-superseded-bugfix-reproduce-step.md)、[実装する工程の組み合わせの先頭に、人間の承認を挟まない前段の調査を置く](../adr/20261012-0516-preliminary-investigation-without-approval.md)

## 目的

オーケストレーターが不具合の修正に bugfix の組み合わせを選べるようにする。再現のエージェントが不具合を再現するテストを書き、
sacty がテストを実行して失敗する（再現できた）ことを確かめてから、そのテストを通すように直す。
受け入れ条件の要点：再現のエージェントは書き込める作業領域にテストを書いて申告する、失敗したら承認なしに実装へ進み結果を作業履歴に残す、
通った・申告なしなら判断待ち（差し戻すとやり直し、承認では進めない）、実装は再現のテストを通すように直し検証は REPRO、
画面で再現の説明と結果を読めて判断の導線がある（日本語・英語）。
途中で、実装する組み合わせの先頭に承認なしの前段の調査を置くことも足した（調査だけは承認する。前段の調査は Issue に返さず、
差し戻し先・変更の申し出の対象にしない）。

## したこと

- 工程 `reproduce` と工程の組み合わせ `bugfix`（調査 → 再現 → 実装 → PR作成）を足した（`packages/core/src/events.ts`・
  `packages/core/src/projection.ts`・`apps/daemon/src/prompts.ts`・`apps/daemon/src/service.ts`）。
- 再現の確かめ：再現のエージェントが clone にテストを書き、`sacty-reproduction` で申告する。sacty がテストのコマンドを実行し、
  `ReproductionChecked` を記録する。確かめの途中でデーモンが止まっても、再起動の後に確かめる（`reproductionPending`）。
  再現の申告のブロックは、再現の説明から取り除くようにした。
- 実装には、タスク・再現の説明・再現のテスト・再現のときのテストの出力を渡す。検証の観点は `REPRO`。成果物チェックからの差し戻しでは、
  再現には戻せない。PR の本文では、要求要件の代わりに再現の説明、観点の表に `REPRO` を載せる。
- 前段の調査：標準・設計を省く・タスク分割・不具合の修正の先頭に `investigate` を置き、終わったら承認なしに次の工程へ進める
  （`StepCompleted`）。結果を後の工程のエージェントに渡す。
- 画面（`apps/web/src/components/reproduction.tsx`・`apps/web/src/components/gate-form.tsx`・`apps/web/src/app/tasks/[id]/page.tsx` など）：
  工程・作業履歴に再現、再現の説明と確かめの結果、再現できなかったときは承認のボタンを出さずに差し戻しの導線。再現の成果物は
  人間の承認ではなく sacty の確かめと表示する。日本語・英語の文言。
- レビューの指摘で、テストの実行基盤の失敗を区別するようにした（`apps/daemon/src/agents/test-runner.ts`）。

## 確かめたこと

- `npx vitest run`：324 件すべて成功（既存のテストは、工程の先頭に調査が入ることに合わせて直した）。lint・typecheck も通った。
- 常に再現できたとする・再現を読み取り専用で実行する・承認で進める・成果物チェックから再現に戻せる・再起動の後に確かめない・
  観点を REQ にする・申告なしでもテストを実行する、の各変更でテストが失敗することを確かめた。前段の調査も、承認待ちにする・
  後の工程に渡さない・差し戻し先にする・変更の申し出を許す・Issue に返す、の各変更でテストが失敗することを確かめた。
- ビルドしたアプリ（スタブの AI。テストのコマンドを `exit 1`・`true` にして）で、再現できた → 実装へ、再現できなかった → 判断待ち →
  差し戻しでやり直し、を確かめた（動画あり）。
- 最後のレビューでは、`npm test`（24 ファイル・327 件）・`npm run lint`・`npm run typecheck` の成功を確かめた。実際の Docker の障害を起こす
  確かめ・実際の AI での動作・画面の操作は、レビューでは行っていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 非ゼロの終了コードをすべて再現できたとするので、テストの実行基盤の失敗（Docker を起動できない・時間切れ・コンテナの停止を確かめられない）でも実装へ進む | `DockerTestRunner` がこれらの結果に `infrastructure: true` の印を付け、再現の確かめでは印があれば `ReproductionChecked` を記録せず、理由（`reproduce.runFailed`）を示して一時停止するようにした。再開でテストを実行し直す。Docker を起動できなかった結果で止まり、再開で実装へ進む回帰テストを足し、修正を戻すと失敗することを確かめた。実装の検証（`TestsRun`）は、誤って先へ進むことはないので変えなかった |
| Docker の CLI は起動しても、デーモンに接続できない・イメージを取得できないときは注記なしに終了コード 125 で終わり、実行基盤の失敗に分類されない | 終了コード 125 なら注記 `run.dockerFailed` と `infrastructure: true` を付けるようにした（終了コード 1 などには付けない）。close(125) で印が付き close(1) では付かないテストと、125 で終わる docker を渡した `DockerTestRunner` でタスクが止まるテストを足し、修正を戻すと両方失敗することを確かめた |

## 残したこと

- 実装の検証（`TestsRun`）で、テストの実行基盤の失敗をテストの不合格と区別することはしなかった（実装のやり直しになり、続けば一時停止する）。
