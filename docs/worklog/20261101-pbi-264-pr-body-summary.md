# 実装の PR の本文を短く、結論から読めるようにする

- 日付: 2026-11-01（UTC）
- タスク: PBI-264
- PR: なし
- ブランチ: feat/issue-264-pr-body-summary
- 関係する ADR: [実装の PR の本文を、結論を冒頭に置き、要求要件・設計は要点とリンクにし、表のセルを短くする](../adr/20261101-1400-pr-body-conclusion-first.md)

## 目的

実務での実証実験で、実装の PR の本文が読みにくい問題が、記録のある 10 シナリオのうち 8 で出た（要求要件の全文の再掲、表の 1 セルの長文、結論が末尾、作業の報告の転記と判定の重複）。

受け入れ条件の要点：冒頭に変更の要約と最終レビューの結論・人が確かめることがある。要求要件・設計は全文を載せない。表のセルに長文を入れない。作業の報告と重複した文頭を載せない。PR テンプレートがあるときの扱いは保つ。仕様書・ユーザードキュメント（日英）・作業履歴を直し、テストで確かめる。

## したこと

`apps/daemon/src/prompts.ts` を直した。

- 決まった形の本文（`buildPullRequestBodyText`）：冒頭に「結論」（変更の要約・最終レビューの判定と所見の頭・不合格のまま進めた記録・人が確かめること）を置いた。後の 2 つは `keep` に入れ、上限で省いても footer の前に出し直す。
- 承認済みの要求要件・不具合の再現（`approvedBasisLines`）：最初の段落の頭と、全文のある場所（マージで承認した PR へのリンク。無ければタスクの画面）にした。独立していた「要求要件・設計の PR」の節はここに統合した。
- 表（`resultTableLines`）：列を「観点・テスト・最終レビュー」にし、セルは短くした（観点 60 文字・テスト 1 件目 70 文字と「ほか N 件」・✅/❌）。入力・期待結果・テスト全件・所見は折りたたみ「観点ごとの詳細」に出す。最終レビューの全文は、結論の頭より長いか、再発の確認があるときだけ折りたたむ。
- 実装の説明から作業の経過の報告の文を除く（`withoutProgressReport`）。実装の指示に `IMPLEMENT_REPORT_LINE` を足した。所見の頭の「合格。」「不合格。」は除いた。
- テンプレートに沿わせる本文（`buildPullRequestBodyParts`）：目的に結論と要点とリンクを入れ、人が確かめることの件数を書く。人が確かめること・不合格のまま進めた記録は従来どおり footer。最終レビューの全文は「sacty の記録」。

仕様書（`docs/spec/approval.md`・`tasks-and-steps.md` と英語の版）、ユーザードキュメント（`docs/user/tasks.md` と英語の版）を直し、ADR を足した。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| 「プッシュ通知は送信しません。」のように、機能を述べる文まで報告として除く | 話題の語を、助詞が続くか「コミットしています」の形のものに絞り、「プッシュ通知」「コミットメッセージ」は残す。テストあり |
| 説明が箇条書きで始まると、結論が「- 変更：- …」になる | 箇条書きの印を外す。テストあり |
| 結論の変更の要約と「変更」の節が同じ文を重ねる | 説明が最初の段落だけなら、「変更」の節は出さない。テストあり |
| 要求要件が見出しと表だけ・空のとき | リンクだけ、または「（なし）」にする。テストあり |
| 結論の途中が上限で切れると、人が確かめることが消える | `keep` で footer の前に出し直す。テストあり（戻すと落ちる） |
| 引き継いだ PR は本文を変えない | 変更なし（影響しない） |

## 残したこと

- 作業の経過の報告の除去は、日本語の定型の言い回しに頼る。言い回しが違う報告は残る（実装の指示で書かせないことが本筋）。
- テンプレートに沿わせる本文では、人が確かめることは末尾の footer のまま。冒頭には件数と場所だけを書く（テンプレートの見出しの並びを変えられないため）。
- 要求要件・設計の PR の本文（`buildStepPullRequestBodyParts`）は、このタスクの範囲外。
