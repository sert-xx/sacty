# 分割の子タスクの PR に範囲を明記し、レビューに範囲外を要修正にさせない

- 日付: 2026-11-16（UTC）
- タスク: PBI-351
- PR: #384
- ブランチ: feat/issue-351-pr-scope-for-split-child
- 関係する ADR: [分割の子タスクの PR に範囲を明記し、レビューに範囲外を要修正にさせない](../adr/20261116-0036-pr-scope-for-split-child-review.md)

## 目的

分割の子タスクの PR を、sacty のレビューの子タスクが、ほかの子タスクの担当（範囲外）が未実装だとして要修正にし続けた。
レビューの指示にも PR の本文にも、子タスクの範囲が入っていなかったためである。

- 分割の子タスクの実装の PR の本文に、その PR の範囲（親タスクの題・子タスクの内容・範囲外）を載せる。やり直しの提出でも載せる。
- PR をレビューする子タスクの指示に、PR を作った子タスクの題と内容・親タスクの題を渡し、範囲外を要修正にさせない。
  範囲外のことで困ることは、人が確かめることとして書かせる。範囲の中は今までどおり。
- 分割していないタスクの PR のレビューと、人が作った PR のレビューは変えない。

## したこと

- `apps/daemon/src/prompts.ts`
  - `childScopeOf`：分割のときに記録した範囲（`Task.childScope`）を返す。記録の無い子タスクは、子タスクの内容（`buildChildBody`）から読む（`legacyChildScope`）。
    sacty が添えた並び（区切り線・関係の文・あれば依存先の文・親タスクから添えた部分の見出し）が一意に決まるときだけ復元し、決まらなければ範囲不明（undefined）にする。
    関係の文は、`buildChildBody` と同じ定数（`CHILD_NOTE_PREFIX` など）で読む。
- `packages/core/src/events.ts`・`projection.ts`・`apps/daemon/src/service.ts`：`TaskSplit` の子タスクと `TaskCreated` に `scope`（原文・親タスクの題・修正の子タスクか）を足し、`Task.childScope` に持つ（レビューの指摘を受けて足した）。
  - `childScopeBodyLines`：PR の本文の「この PR の範囲（分割の子タスク）」の節。内容は引用としてそのまま載せ、8,000 文字（`CHILD_SCOPE_BODY_MAX`）を超えたら行の切れ目で切る。
    決まった形の本文では結論と要求要件の間、PR テンプレートに沿わせる本文では目的の欄に入れる。
  - `reviewChildScopeLines`：PR のレビューの子タスクの指示の「この PR の範囲（分割の子タスク）」。戻し先の指示（`reviewReworkLines`）と同じ材料（PR を作ったタスク）から作るので、service は変えていない。
- 決めたこと
  - 範囲の節は、本文の長さの上限で省けない部分（`keep`）にはしない。本文の前のほうに置き、節そのものに上限を設けたので、上限で切られるのは後ろの節になる。
  - 修正の子タスク（統合レビューの指摘を直す子タスク）も、同じ扱いにする。親タスクの一部だけを直す PR であることは同じため。
  - 範囲が不明な子タスク（記録が無く、内容からも一意に復元できない）には、節も指示も足さない。推測で範囲を作らない。
- 文書：仕様書（`approval`・`tasks-and-steps`・`split-and-integrate`。日英）、ユーザードキュメント（`tasks`。日英）、ADR。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （sacty のレビュー1回目・要修正）範囲を子タスクの内容の文字列から逆算しているので、内容に同じ見出しがあると後ろの受け入れ条件・範囲外が落ち、親タスクの題に改行があると題が欠けて添えた説明が範囲に混ざる | 範囲（原文・親タスクの題・修正の子タスクか）を、分割のときに `TaskSplit`・`TaskCreated` の `scope` に記録し（`Task.childScope`）、PR の本文とレビューの指示はそれを使うようにした。記録の無い子タスクのための文字列の読み方も、sacty が添えた並びの全体が合う所だけを境目にするよう直し、指摘の2つの形（同じ見出し・改行のある題）のテストを足した |
| （sacty のレビュー2回目・要修正）記録の無い子タスクでは、まだ自由記述から境目を推測している。原文に区切り線・関係の文・見出しの組の例があると後ろが落ち、関係の文が合わなくても同じ見出しで切られる | 記録の無い子タスクは、sacty が添えた並びが一意に決まるとき（見出しの行と、区切り線と関係の文の始まりが、それぞれちょうど1つ）だけ復元し、決まらなければ範囲不明として何も渡さないようにした。関係の文が無いときに見出しで切る読み方はやめた。範囲不明になる 8 つの形のテストを足し、実物の子タスク（PR #377）は復元できることを確かめた |
| （1回目・提案）最初の行だけで 8,000 文字を超えると、行の途中で切られる | 上限に収まる行が無ければ、引用を出さずに続きの場所だけを書くようにした。テストを足した |
| （1回目・提案）範囲を見分けられない子タスクには節も指示も足されないことが、ユーザードキュメントに無い | 日英に、その場合と、範囲の確かめ方（子タスクの詳細の内容）を書いた |
| （1回目・提案）ユーザードキュメントの「今までどおり」「今までと変わりません」では、今の振る舞いが伝わらない | 日英とも、今の振る舞い（範囲の中の何が指摘されるか・範囲の節とレビューの範囲が無いこと）を書いた |
| （セルフレビュー）PR の本文の「ここに書かれていないことは、ほかの子タスクが担当します」は、確かめられない言い切り | 「範囲外と書かれたこと（ほかの子タスクが担当すること）は、この PR では変えません」に直した |

## 残したこと

- 戻し先の判断が、範囲外の指摘を実装に戻さないようにすることは、していない（人の指摘は範囲外でも人の意思として扱う）。
- 指摘への返信の投稿は、別のタスク（PBI-352）。
- 子タスクの間のマージの順番や組み合わせを確かめることは、統合レビューの役割のまま。
