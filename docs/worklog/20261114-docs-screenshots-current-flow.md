# ユーザードキュメントのスクリーンショットのデータを今の実装の流れに直し、場面 docs の画像を撮り直す

- 日付: 2026-11-14（UTC）
- タスク: なし
- PR: なし
- ブランチ: claude/practical-dirac-gj66a3
- 関係する ADR: [スクリーンショットを撮る間は、GitHub の API にデータのとおりの答えを返し、デーモンが状態を変えようとしたら画像を置き換えない](../adr/20261114-1419-screenshots-github-answers-and-activity-check.md)

## 目的

設定・操作・トラブルの説明の画面（場面 `docs`）のデータ `scripts/docs-screenshots/seed.mjs` は、以前の版の流れでタスクを作っていた。
このため、撮るとデーモンが PR のレビューの子タスクを作って実行し、失敗した「エラーで一時停止」が画像に写っていた。
また、タスクの詳細の画像には「AI のレビューの状況は分かりません」が写っていた。

- データを今の実装の流れに直し、場面 `docs` の画像を日英で撮り直す。
- 「AI のレビューの状況は分かりません」の扱いを決めて、記録する。
- 画像に、撮影の副作用で止まったタスクが写らず、工程の並びが今の進め方と合うようにする。

## したこと

### 「AI のレビューの状況は分かりません」の扱い

撮る環境で GitHub の答えを用意して、「付いています」の状態で撮ることにした（ADR）。

- 理由
  - 「分かりません」は、ふだんは起動の直後や GitHub を読めないときにしか出ない。読む人には、いつも注意が出る画面に見える。
  - 表示は承認の案内のすぐ下にあり、タスクの詳細の並びを見せる画像から外せない。
  - 調べると、撮る間にデーモンが、架空のリポジトリの名前と架空のトークンで実際の GitHub の API に問い合わせていた（認証のエラーになる）。
    答えを用意すれば、撮影を実際の GitHub の API から切り離せる。
- 仕組み
  - `scripts/docs-screenshots/github-stub.mjs`（新規）：`api.github.com` への `fetch` に、決まった答えを返す。
    `capture.mjs` が、`sacty up` の `NODE_OPTIONS`（`--import`）に入れる。
    答えるのは、PR の確認が読むもの（PR の状態・PR のレビューとコメント・コミットの CI/CD）だけで、書き込みと答えを用意していない問い合わせは断り、ログとファイルに残す。
  - PR の状態（開いているか・先頭のコミット・ドラフトか・競合しているか）と、マージの後の監視で待っているコミットの CI/CD（実行中）は、データを入れるスクリプトが、入れた作業履歴から作って `SACTY_HOME` の `github-answers.json` に書く（`seed-lib.mjs` の `githubAnswers`）。
    PR のレビューとコメントは、いつも無いと答える。
  - タスクの詳細を撮る3つの画面は、「Sacty の AI のレビュー」が付いている状態になるのを待ってから撮る（`shots.mjs` の `aiReviewAttached`）。

### データ（`seed.mjs`）

今の実装が記録する流れ（`docs/spec/tasks-and-steps.md` の「進め方の組み合わせ」「最終レビューをしない流れ」、`docs/spec/approval.md` の「PR での承認」「PR のレビューの子タスク」）で、すべてのタスクを書き直した。

- 実装する進め方から、前段の調査（`investigate` と `StepCompleted`）を外し、タスクの開始時の情報収集（`InformationGathered`）を入れた。
  調査だけのタスクは残した。
- 最終レビュー（`FinalReviewed`）をやめ、実装の後を `FinalReviewSkipped` → ドラフトの実装の PR（`awaitingReview`・`draft`）→ `ReviewTaskCreated` とレビューを終えた子タスク → `PullRequestMarkedReady` にした。
  マージ済みの PR にも子タスクを入れた（sacty が作る PR には、必ず子タスクができるため）。
- 要求要件を画面で承認していた3件を、PR での承認にした（`TaskBranchCreated`・`StepPullRequestPublished`・子タスク・マージで承認）。
  対象リポジトリと GitHub のアカウントがあるタスクは、要求要件を PR で承認する（`stepPullRequestsOn`）。画面での承認は、PR での承認ができる前の版の流れである。
  ダッシュボードの「要求要件の承認待ち」は、「要求要件の PR のマージ待ち」になった。
- 標準の進め方で要求要件を承認したタスクに、工程の見直し（`StepsSkipped`。設計を飛ばさないと決めた）を入れた。
- 不安定なテストの台帳のための3件（中止したタスク。`FinalReviewed` の `flakyFailures`）を消した。
  台帳は今の監査の画面に出ない（`docs/spec/audit.md` の「不安定なテストの台帳」、`docs/user/audit.md`）ので、残す理由が無い。理由は `seed.mjs` の先頭のコメントに書いた。
- 予算の上限で止まったタスクは、前段の調査の費用（$0.52）の代わりに、情報収集を $0.25、要求要件を $1.38 にした。
  80% の通知（$1.66）と合計（$2.27）は変えていない。費用の表には「情報収集」の行が出る。
- 質問の答えの文から、「調査の結果で」を除いた（調査の工程が無くなったため）。
- 調査だけのタスクを、プロジェクトでいちばん先に完了させた。
  監査のモックは、完了した順に場面を割り当てる。レビューの子タスクが先に完了すると、原因の「該当するタスク」が子タスクだけになるため。
- タスクは 11 件から 14 件（うち PR のレビューの子タスクが 6 件）、イベントは 125 件から 145 件になった。

### 道具と撮影の仕組み

- `seed-lib.mjs`
  - 足した：`gather`（情報収集）・`reviewed`（レビューを終えた子タスクと、親の記録）・`stepPr`（要求要件・設計の PR）、`githubAnswers`（`finish` が書く）、`readActivity`（作業履歴の読み出し）・`readRefused`（断った問い合わせの読み出し）。
    `gather`・`reviewed` は、`seed-intro.mjs` にあったものを移した。
  - 消した：`review`（`FinalReviewed`）・`complete`（`StepCompleted`）。どのデータも使わなくなった。
  - 実装が記録する形に直した。
    - `merged`：担い手を人（`person`）にし、sacty が出したコミット（`submitted`）を足した。
    - `repo`：`RepositoryPrepared` の URL を、clone の URL（`.git` 付き）にした。タスクの詳細の「対象リポジトリ」に、そのまま出る。
    - `fail`：実行の失敗で止まったときの `TaskPaused` から、文を除いた（文は `AgentRunFailed` にある。画面の表示は同じ）。
    - `reviewed`：子タスクに、リポジトリの用意と情報収集を入れ、工程の決定をオーケストレーターの記録にした（撮るときの設定に `images` があるので、レビューの工程のイメージだけはオーケストレーターが選ぶ）。
- `seed-intro.mjs`：`gather`・`reviewed`・`merged` を道具のものにした。
  入れるイベントは 107 件から 111 件になった。違いは、上の道具の直し（子タスクのリポジトリの用意と情報収集・工程の決定、PR のマージの記録、`RepositoryPrepared` の URL）と、設計の PR の子タスクの向き先のコミットだけ。
- `capture.mjs`
  - 撮る間にデーモンが作業履歴に書き足したか、`github-stub.mjs` が断った問い合わせがあれば、失敗にする。画像は一時の場所に撮り、確かめてから出力先に置く。
  - `until` に要素をいくつか書けるようにし（いちばん下の端まで）、下の余白 `pad` を足した。
    `until` で撮るときは、画面の高さを撮る高さに合わせる（サイドメニューの背景が途中で切れ、右下に固定したボタンが画像の途中に重なるため）。
  - 先頭のコメントの Playwright の入れ方を直した（開発の依存に入っているので、`npm install` で入る）。
- `shots.mjs`：固定の高さで切っていた4つの画面を、区切りのよい所で切るようにした。
  - ダッシュボード：上の2段の欄の下の端まで（「終わっていないタスク」の欄が途中で切れていた）。
  - タスクの一覧：「すべてのタスク」の下の端まで（英語の版で、行の途中で切れていた。子タスクが親の下に並ぶ様子が入る）。
  - タスクの詳細：左の列の「集めた情報」と、右の列の「最近の作業履歴」の、下にあるほうまで（説明文にある「最近の作業履歴」が入っていなかった）。
  - 監査：原因と、判断待ちの改修の提案（2件）まで。
    完了したレビューの子タスクが増えて、モックの原因が 2 件から 5 件になり、今までの高さでは提案の途中で切れるため。

### 画像と説明

- 場面 `docs` の画像を、日英で撮り直した（28 枚）。
- `docs/user/tasks.md`・`tasks.en.md`
  - タスクの詳細の見方に、「Sacty の AI のレビュー」の説明を1項目足した（画像に写っているため）。
  - タスクの詳細・PR での承認・タスクの一覧の画像の説明文を、写っているものに合わせた。
- `docs/user/audit.md`・`audit.en.md`：監査の画像の説明文と前置きを、写っている範囲（原因と、判断待ちの改修の提案）に合わせた。
- `docs/user/dashboard.md`・`config.md`・`troubleshooting.md` などは、画像の説明文と本文が今の画像と合っているので、変えていない。
- `docs/README.md`：スクリーンショットの規則に、データの書き方・撮る間の GitHub の答え・撮る間の確かめを足した。
- ADR を足した（上のリンク）。

## 確かめたこと

- 直す前のデータで、撮影と同じ条件（代わりのスクリプト・設定）でデーモンを 75 秒動かした。
  作業履歴に 3 件（子タスクの `TaskCreated`・親の `ReviewTaskCreated`・子タスクの `TaskPaused`）が足され、デーモンのログに GitHub の API の 401 が出た。
- 直した後は、場面 `docs`・`intro` のどちらのデータでも、70 秒動かして、書き足しが 0 件、断った問い合わせが無く、デーモンの警告も無かった。
- 撮る間の確かめを、わざとずらしたデータの写しで試した。どちらも終了コード 1 で失敗し、出力先に画像を書かなかった。
  - 承認待ちの PR の子タスクを1つ抜く：書き足された 3 件と、断った PR へのコメント（`POST …/issues/43/comments`）を挙げた。
  - 実装の PR のドラフトを外した記録（`PullRequestMarkedReady`）を抜く：断ったドラフトの切り替え（`POST /graphql`）を挙げた（作業履歴への書き足しは無い）。
- `seed-intro.mjs` が入れるイベントを、直す前後で書き出して比べた（日英）。違いは「したこと」に書いたものだけだった。
- 場面 `intro` を一時の場所に撮り、リポジトリの画像と画素を比べた。
  違いは、サイドメニューの背景（画面の高さより下の部分）と、監査の画面の日時、1行の文字の位置（数ピクセル）だけで、写っている内容は同じだった。リポジトリの `intro` の画像は撮り直していない。
- 撮り直した 28 枚を、すべて目で確かめた。
  - PR のレビューの子タスクは、どれも「完了」で、「エラーで一時停止」は写っていない。
  - 工程の並びに、前段の調査が無い（実装 → マージの後の監視、要求要件 → 設計 → 実装 → マージの後の監視 など）。
  - 「Sacty の AI のレビュー」は、「今の head 9e1d0c4 に、Sacty の AI のレビューが付いています。」と出ている。
  - 監査の判断待ちの提案の宛先は、監査が選んだもの（対象リポジトリ・Sacty の既定のコンテキスト）が選ばれている。
- `node scripts/docs-screenshots/capture.mjs docs`：日英 28 枚を撮れた。デーモンの警告は無かった。
  `NODE_OPTIONS` をすでに設定している環境でも、撮れた。
- `npm run lint`：通った。
- `npx vitest run tests/docs`：3 ファイル・93 件が通った。
- `npx vitest run`（全体）：219 ファイルのうち 214 ファイルが通り、4247 件が通った。5 ファイル・8 件の失敗は、この環境によるもので、この変更とは関係が無い。
  - ブラウザーのテストの 2 ファイル（`question-form.browser.test.ts`・`menus.browser.test.ts`）は、リポジトリの Playwright の版に合うブラウザーが環境に無く、起動できなかった。
  - `agent-sessions.test.ts`（1 件）・`context-mcp.test.ts`（1 件）・`host-mcp-processes.test.ts`（6 件）は、変更前の main（6e6909a）でも同じ 8 件が失敗した（root で動く環境）。
- `npm run build`：通った（撮影のため）。

確かめるときの環境：リポジトリが求める Node.js 26.13.1 を npm の `node` パッケージで用意した。Playwright のブラウザーは環境にあるもの（Linux の Chromium）を使い、起動の引数（ブラウザーの場所・`LANGUAGE`）を前置きのスクリプトで足した。このスクリプトはリポジトリに入れていない。

確かめていないこと：macOS では撮っていない。

## レビューの指摘と対応

最初のコミットの後に、別のエージェントに差分をレビューさせた。

| 指摘 | 対応 |
| --- | --- |
| レビューの子タスクに、リポジトリの用意（`RepositoryPrepared`）と情報収集が無い。監査の提案の宛先の候補はタスクのリポジトリから作るので、子タスクの監査から出た提案の宛先が「Sacty の既定のコンテキスト」だけになり、監査の画像と、宛先の説明（`docs/user/audit.md`）が合わない | `reviewed` で、子タスクにリポジトリの用意と情報収集を入れた。監査の画像を撮り直し、判断待ちの提案の宛先に対象リポジトリが選ばれていることを確かめた |
| デーモンの直しが GitHub への書き込みから始まるずれ（ドラフトを外した記録が無いなど）は、作業履歴が増えないので、撮影が通ってしまう。答えに `node_id` が無く、書き込みの前で止まっていた | 答えに `node_id` を足し、`github-stub.mjs` が断った問い合わせをファイルに残して、あれば撮影を失敗にした。ずらしたデータで確かめた |
| PR のレビューとコメントは、いつも「無い」と答えるので、取り込む指摘のあるずれは見つからない。ADR の「必ず書き足す」「台帳と必ず一致」は言い過ぎ | ADR とコメントを、していることだけに直し、見つからないずれを「影響」に書いた。答えをデータから作るのは、要るようになってからにした |
| 開いている PR に、いつも競合していないと答える。競合を記録したデータだと、デーモンが解消を記録し、データのせいに見える | 競合しているかを、台帳の記録から答えるようにした |
| 紹介のためのデータ（`seed-intro.mjs`）の、マージ済みの PR の記録は簡略のまま（子タスク・ドラフトで作った記録・ドラフトを外した記録が無い）で、ADR の「以前の版の記録は入れていない」と合わない | ADR と `docs/README.md` を、場面 `docs` のデータについての記述に直し、紹介のデータの簡略を「影響」と「残したこと」に書いた。紹介のデータは変えていない（タスクの一覧の画像が変わるため） |
| 記録の形が実装と違う所がある（`RepositoryPrepared` の URL に `.git` が無い・PR のマージの記録に `submitted` が無い・実行の失敗の `TaskPaused` に文がある・子タスクの工程の決定が sacty の記録・設計の PR の子タスクの向き先のコミット） | どれも実装が記録する形に直した（「道具と撮影の仕組み」）。工程のブランチの回の番号（`-1`）は、どのデータも最初の回なので、そのままにした |
| 「実際の GitHub に問い合わせない」と言い切っているが、差し替えているのは GitHub の API だけで、データがずれると git がリポジトリを取得しようとする | `docs/README.md` とコメントを「GitHub の API に、実際には問い合わせない」に直し、git は差し替えていないことを書いた |
| デーモンが PR の先頭を読む前に撮ると、「分かりません」が写っても撮影が通る。答えのファイルを読めないと、PR も CI も無いと答えて、デーモンが記録する | タスクの詳細を撮る画面は、付いている状態を待ってから撮るようにした。答えのファイルを読めないときは、どの問い合わせも断って、撮影を失敗にした |
| PR を作ったら、この作業履歴の名前（`pr-<番号>-`）と PR の番号、ADR の PR の番号を直す | PR を作るときに直す（「残したこと」） |

## 残したこと

- 紹介のためのデータ（`seed-intro.mjs`）は、承認待ちの PR にだけレビューの子タスクを入れてあり、マージ済みの PR の記録は簡略のままである（子タスク・ドラフトで作った記録・ドラフトを外した記録が無い。要求要件の PR の子タスクと、工程の見直しの記録も無い）。
  そろえるとタスクの一覧の画像が変わるので、このタスクでは変えていない。
- 紹介の場面（`intro`）の画像は撮り直していない。次に撮り直すと、サイドメニューの背景が画像の下まで続く。
- git の通信は差し替えていない。データが今の流れと合っているかぎり、撮る間にデーモンは git でリポジトリを取得しない。
- PR を作ったら、この作業履歴の名前を `pr-<番号>-` で始まる名前に変え、この作業履歴と ADR に PR の番号を書く。
