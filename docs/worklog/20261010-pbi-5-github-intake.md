# プロジェクトと GitHub Issue の取り込みを作る（PBI-5 の前半）

- 日付: 2026-10-10（UTC）
- タスク: PBI-5
- PR: #8
- ブランチ: feat/issue-5-github-intake
- 関係する ADR: [プロジェクトに GitHub Issue の取り込み元を Org 単位かリポジトリ単位でラベルを条件に登録し、ポーリングで取り込んでタスクにする](../adr/20261010-0931-superseded-projects-and-github-issue-intake.md)、[Issue から作ったタスクは、その Issue のリポジトリに、プロジェクトのリポジトリの設定で実装する](../adr/20261010-0931-superseded-issue-task-repository-settings.md)

## 目的

PBI-5 は大きいので2つに分け、この PR は前半（PBI-5a、受け入れ条件1〜5）を扱う。プロジェクトの設定で GitHub Issue の取り込み元を
Org 単位かリポジトリ単位でラベルを条件に登録できること、同じ Org・リポジトリを複数のプロジェクトに登録できず範囲が狭い指定を
優先すること、ポーリングで取り込み、担当を取り込むたびに判定して同じ Issue を二重に取り込まないこと、Org の設定画面に除外
リポジトリを出すこと、取り込んだ Issue をタスクにして台帳に取り込み元を記録することが要点。エクスポート・インポートは後半（PBI-5b）に回した。

## したこと

- プロジェクト（`packages/core/src/projects.ts`・`apps/daemon/src/projects.ts`）：SQLite の `projects` テーブル、起動の時の「デフォルト」、重複の検査、担当の判定、除外リポジトリ。
- 取り込み（`apps/daemon/src/intake.ts`・`github.ts`）：`github.token_secret` と `poll_interval_sec` でのポーリング、検索 API のページ送り、二重の取り込みの防止、
  `TaskCreated` への `start: github_issue` と `source` の記録。
- Issue のタスクの実装先（`apps/daemon/src/service.ts`・`prompts.ts`）：Issue のリポジトリに、プロジェクトの「リポジトリの設定」で実装し、PR の本文に `Closes #<番号>` を入れる。
- 画面：ヘッダーからの「プロジェクト」の画面（`apps/web/src/app/projects/`・`apps/web/src/components/project-editor.tsx`）、「今すぐ取り込む」、
  最後の取り込みの時刻・件数・エラー、一覧と詳細での取り込み元の表示。
- レビューの対応で、取り込み元ごとの失敗の隔離、更新日時で区切る検索と cursor による続きからの取り込み、レート制限での打ち切り、
  不完全な結果での cursor の据え置きを足し、Issue の本文とタイトルを切り詰めないようにした。

## 確かめたこと

- `npm test` が全件通った（128件。16件追加）。重複の検査、担当の判定、除外リポジトリ、取り込み（ラベル・二重・担当の再判定）、Issue のリポジトリでの実装、
  ポーリングの間隔、失敗の記録、検索のページ送りをテストした。
- 画面で、プロジェクトを作って Org の取り込み元を保存できること、別のプロジェクトから同じ Org を登録すると拒否されて理由が出ること、
  リポジトリ単位で登録すると Org 側の画面に除外リポジトリとして出ること、幅 375px で横スクロールが出ないことを確かめた。
- 実際の GitHub からの取り込みは、トークンを使って外部のサービスにアクセスするので行っていない。検索 API のクライアントは偽の fetch で確かめた。
- レビューは、一時 SQLite と偽の検索・fetch で、取り込み元の一部の失敗・1,001 件・10,000 文字を超える本文・3,100 件と 31 リクエスト目のレート制限・
  不完全な応答を再現した。最後の再レビューでは `npm test`（134件）・`npm run lint`・`npm run typecheck` が通り、1ページ目は正常で2ページ目が
  不完全な応答のときも、次の検索で抜けた Issue を含む全 102 件が揃うことが確かめられた。実際の GitHub からの取り込み・本物のコンテナ・ブラウザでの動作は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| すべての検索を1つの try で囲んでいるので、1つの取り込み元の検索の失敗で、無関係なプロジェクトも取り込めない | 検索を取り込み元ごとに try で囲み、失敗を取り込み元ごとに記録し（トークンは取り除く）、ほかの検索と取れた結果の取り込みは続けるようにした。画面に条件ごとの理由を出す。1つだけ 422 で失敗させる回帰テストを足した |
| 毎回同じ検索の先頭 1,000 件だけを取るので、1,001 件目以降に永久に届かない | 1,000 件に達したら最後の Issue の日時から先を次の範囲として検索するようにした（最大 20 範囲）。同じ日時で 1,000 件を超える・範囲の上限に達した・`incomplete_results` のときは、取り込み元のエラーとして記録する。1,001 件と同じ日時の 1,200 件のテストを足した |
| 手入力のチケット用の 10,000 文字の制限を取り込みにも当てているので、それより後の受け入れ条件や制約が消えたまま実行される | 取り込む Issue の本文とタイトルを切り詰めずに台帳に記録し、エージェントにも全文を渡すようにした。制限は手入力のチケットにだけ残した。回帰テストを足した |
| 再レビュー：範囲を増やして1回の取り込みのリクエストが増え、検索のレート制限で毎回先頭から失敗して 0 件になる | 途中で失敗しても取れた分と cursor を返して取り込み、次の取り込みは `updated:>=<cursor>` から続けるようにした。レート制限ではその回のほかの検索をやめる。並びと範囲の区切りを更新日時に変えた。設定が変わったら先頭から読み直す。3,100 件のテストと、取り込みの層のテストを足し、修正前のコードで失敗することを確かめた |
| 再レビュー：不完全な検索結果でも返された最後の日時を cursor に入れるので、取れなかった Issue が次回以降も取れない | `incomplete_results: true` のときは、取れた分は取り込むが cursor はそのページの手前に留め、その回の検索を終えて警告を記録するようにした。指摘の手順を回帰テストにし、修正前のコードで失敗することを確かめた |

## 残したこと

- プロジェクト定義のエクスポート・インポートは、後半（PBI-5b）で行う。
- ヘッダーでのプロジェクトの切り替えは PBI-4 で行う（一覧はすべてのプロジェクトのタスクを表示し、画面で作るチケットは「デフォルト」に入る）。
- 実際の GitHub からの取り込みは確かめていない。
