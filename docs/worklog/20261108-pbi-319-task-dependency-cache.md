# 依存の準備の結果を、タスクごとのキャッシュで工程・実行の間で使い回す

- 日付: 2026-11-08（UTC）
- タスク: PBI-319
- PR: #325
- ブランチ: feat/issue-319-reuse-dependency-setup
- 関係する ADR: [依存の準備の結果を、タスクごとのキャッシュのディレクトリで工程・実行の間で使い回す](../adr/20261108-0739-task-dependency-cache.md)

## 目的

コンテナは実行ごとに作り直すので、工程ごとに依存をインストールし直していた。
同じタスクの中では、依存の準備の結果を工程・実行の間で使い回す。
特定の言語・パッケージ管理に寄せず、ツールのキャッシュの置き場所を使う仕組みにする。
別のタスクとは共有せず、タスクの完了・中止で消し、デーモンを再起動しても残骸を残さない。
キャッシュが壊れていても、タスクを止めない。

## したこと

- デーモン（`apps/daemon`）
  - タスクごとのキャッシュの場所 `_task-cache/<タスク ID>`（作業領域の根の下）を足し、`taskWorkspacePaths` に含めた（完了の後と起動の片付けで、作業領域と一緒に消す）。
  - 実行の前に用意する `prepareTaskCache`（`task-cache.ts`）を足した。`0700` で作り、ディレクトリでない・読み書きできないものは消して作り直す。根がリンク・ファイル、または作り直せなければ、ログに理由を残してキャッシュを使わずに実行する。
  - 工程・最終レビュー・統合レビューの実行だけに渡す（`ExecuteRun` の `taskCache`）。`DockerExecutor` が `/sacty-cache` にマウントし、`XDG_CACHE_HOME` を向ける。Claude Code 自身のキャッシュ（`claude-cli-nodejs`）は `--tmpfs` でコンテナの中だけにする（`Invocation` の `agentCacheDirs`、`dockerRunArgs` の `tmpfs`）。
  - 中止の片付けの「作業領域」でキャッシュも消す（途中の `_task-cache` がリンクなら先を消さない `removeEntry`）。中止の確認の画面の「作業領域」にも数える。
  - 起動の片付けで、どのタスクのものでもない・中止したタスクのキャッシュを消す。進行中のタスクのものは残す。
- キャッシュを渡す実行の指示に、使い方の短い案内（`taskCachePromptLines`）を足す：ツールのキャッシュを `XDG_CACHE_HOME` に置かせ、見ないツールはそのツールの設定で向けさせる。秘密の値を置かせず、キャッシュのせいで失敗するなら使わずに進めさせる。言語・ツールの名前は書いていない。最初は既定の規則（`rules.md`）に書いたが、最終レビュー・統合レビューに届かないので、レビューの指摘で指示の側に移した（`rules.md` は main と同じに戻した）。
- docs：仕様書（エージェントの実行・タスクと工程・構成。日英）、ユーザードキュメント（はじめに のデータの置き場所。日英）、ADR を足した。

## 確かめたこと

### 依存の準備の時間（Docker）

実際のエージェントは使わず、`sacty-agent:1.18.1` のコンテナを、sacty と同じマウント（`-v <_task-cache/<ID>>:/sacty-cache`・`XDG_CACHE_HOME=/sacty-cache`・`--tmpfs /sacty-cache/claude-cli-nodejs`、ディレクトリは `0700`）で起動し、このリポジトリ（`git archive HEAD` の写し）の依存を入れて測った。
Rancher Desktop（Docker 29.5.3、macOS、arm64）。キャッシュを使わない実行は、コンテナの中の `~/.npm` などを使う（実行ごとに空）。

1. Playwright のブラウザ（`npx playwright install chromium-headless-shell`。`XDG_CACHE_HOME` を既定で見る。sacty も Playwright も設定を足していない）

   | キャッシュあり 3回目 | 0.6 秒 | 0件 |

2. `npm ci`（373 パッケージ。npm は `XDG_CACHE_HOME` を見ないので、規則どおり `npm_config_cache=$XDG_CACHE_HOME/npm` を向けた。`node_modules` はコンテナの中に作った）

   | 実行 | 時間 |

### コンテナの実行ユーザーが書けるか（レビューの指摘への対応）

- 作業領域（`/workspace`）の扱いを調べた：sacty は作業領域の持ち主・権限を変えず（ホストのデーモンのユーザーが `git clone`・`mkdir` で作る。ディレクトリは umask のとおり `0755` が多い）、`docker run` に `--user` も付けない（イメージの `USER node`）。UID の違いは扱っていない。
- そのため、Linux のふつうのバインドマウントで作業領域に書けるのは、デーモンの UID とイメージの `node` の UID（ふつう 1000）が同じときだけ。キャッシュ（`0700`）に書ける条件も同じ（どちらも持ち主のほかは書けない）。`0755` にしても書ける条件は変わらないので、`0700` のままにした。
- Rancher Desktop（Alpine の仮想マシン、カーネル 6.18）で確かめた。
  - ホストのディレクトリ（`0700`）を `node`（1000）で・`--user 4242:4242` でマウントすると、どちらもコンテナの実行ユーザーの持ち物に見え、書けた（作業領域の `0755` も同じ）。仮想マシンへの共有が、持ち主を見せ替えるため。
  - Linux のカーネルの判定を、コンテナの中のディレクトリで再現した（root で UID 4242 の持ち物を作り、`node` で確かめた）：
    - キャッシュ `0700`・作業領域 `0755`：どちらも書けない。確かめのスクリプトが `[sacty] 依存のキャッシュ：/c に書けないので、使わずに実行します` を出し、`XDG_CACHE_HOME` を外して実行した。
    - キャッシュ `0755`：同じく書けない（作業領域と同じ）。
    - 持ち主が 1000 の `0700`：書け、`XDG_CACHE_HOME` はそのまま、確かめのファイルも残らない。
  - UID の違う Linux のホストのバインドマウントそのものは、この環境に無いので確かめていない。
- 書けないときに規則（使わずに進める）だけで足りるかを考えた：Go のビルドのキャッシュ・Playwright のブラウザなどは、キャッシュに書けないと止まる。作業領域に書かない実行（レビューの工程など）は、キャッシュを渡す前は `HOME` の下のキャッシュで動いていたので、向けたままにすると、これまで動いていた実行を失敗させうる。そこで sacty の側で、書けなければ `XDG_CACHE_HOME` を外すようにした。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| Sacty のレビュー（要修正）：Linux でデーモンとコンテナの UID が違うと、デーモンが持つ `0700` のディレクトリにコンテナから書けない。ホストの権限だけを見るので、そのまま `XDG_CACHE_HOME` に向き、依存の準備が権限エラーになりうる | 直した。作業領域も持ち主・権限を変えず `--user` も付けないので、書ける条件は作業領域と同じ（デーモンとコンテナの UID が同じ・ファイルを共有する仮想マシンの環境）と確かめ、`0700` のままにした。そのうえで、コンテナの中で書けるかを確かめ、書けなければ知らせを出して `XDG_CACHE_HOME` を外して実行する（`withTaskCacheProbe`）。UID の違う Linux のホストでは確かめられないので、カーネルの判定をコンテナの中で再現して確かめた（上の「コンテナの実行ユーザーが書けるか」）。仕様書（日英）・ADR も直した |
| Sacty のレビュー（提案）：起動時の中止したタスクの掃除は、キャッシュだけをマウントと照合するので、作業領域がマウントされていてもキャッシュを消し、仕様書と合わない | 直した。完了したタスクと同じく、作業領域・退避した git のメタデータ・キャッシュのどれかがマウントと重なれば消さない。仕様書（日英）にも書いた |
| Sacty の2回目のレビュー（要修正）：イメージの `env` などで指定された `XDG_CACHE_HOME` が上書きで失われ、書けるかの確かめに失敗しても元の設定先に戻れない | 直した。上書きする前の値と設定があったことを `SACTY_PREVIOUS_XDG_CACHE_HOME`・`SACTY_PREVIOUS_XDG_CACHE_HOME_WAS_SET` で確かめのスクリプトに渡し、書けなければ前の値に戻す（元が無ければ外す）。確かめのための変数はコマンドに渡さない。仕様書（日英）・ADR も直した |
| Sacty の2回目のレビュー（要修正）：最終レビューと統合レビューにはキャッシュを渡すが、`rules.md` の指示が届かない（コンテキストを渡していない） | 直した。案内を、キャッシュを渡す実行の共通の経路（`execute` の指示の組み立て）で指示に足すようにし、`rules.md` からは外した。キャッシュを渡す実行だけに届き、ほかの実行の指示は長くならない。特定の言語・ツールの名前は書いていない。仕様書（日英）・ADR も直した |
| Sacty の2回目のレビュー（提案）：知らせをデーモンのログに写すのが close の後だけで、時間切れのときに抜ける | 直した。標準エラー出力の先頭と末尾を実行の外側に持ち、時間切れ・停止の確認の失敗を含むどの終わり方でも、終わりの処理（`finally`）で、それまでに受け取った分から転送と依存のキャッシュの知らせを写す |
| セルフレビュー：中止の片付けで `rm` を使うと、途中の `_task-cache` がリンクのとき、リンクの先のディレクトリを消す | 直した。親までの途中のリンクをたどらない `removeEntry` で消し、リンクなら片付けの失敗にする |

## 残したこと

- タスクの削除の操作は今の sacty に無い（プロジェクトの削除はタスクを残す）。どのタスクのものでもないキャッシュは、起動のときに消す。
- 一時停止・失敗で止まったままのタスクのキャッシュは、完了・中止まで残る（再開で使うため）。
- Codex が `XDG_CACHE_HOME` の下に自身のものを置くかは確かめていない（Claude Code は 2.1.318 の本体で、env-paths の `claude-cli` を確かめた）。
- UID の違う Linux のホストのバインドマウントでは確かめていない（上のとおり、コンテナの中で再現した）。
- ツールがキャッシュの中身を壊したとき（展開の途中で止まったなど）を sacty は見分けない。規則で、使わずに進めさせる。
