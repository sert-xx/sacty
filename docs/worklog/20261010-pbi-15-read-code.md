# 要求要件・設計の工程でも、対象リポジトリのコードを読めるようにする

- 日付: 2026-10-10（UTC）
- タスク: PBI-15
- PR: #19
- ブランチ: feat/issue-15-read-code
- 関係する ADR: [対象リポジトリはタスクの開始時に clone して起点のコミットを固定し、要求要件・設計の工程には起点のコードを読み取り専用で渡す](../adr/20261010-2354-superseded-repository-snapshot-for-planning.md)

## 目的

動作確認で気づいたことへの対応。要求要件・設計のエージェントは空の作業領域で動いていて、既存のコードを読まずに書いていた。

- 要求要件・設計の工程でも、実装と同じ起点のコミットのコードを読める。
- 要求要件・設計の工程では、コードを変えられない。
- 対象リポジトリを用意できないときは、要求要件の工程の前に止める。
- 指示で、コードがあることと、読むだけであることを伝える。
- 差し戻しや変更の申し出でやり直すときも、同じ起点のコミットのコードを読む。

## したこと

- 起点のコミットの書き出し：`apps/daemon/src/repository.ts` の `RepositoryWorkspace.snapshot`（退避した git のメタデータから一時インデックスで書き出す）。
- サービス：`apps/daemon/src/service.ts` で、タスクの開始時に clone して `RepositoryPrepared` を記録し、要求要件・設計の実行ごとに書き出して渡し、実行の後に消す。
- マウント：`apps/daemon/src/agents/docker.ts` で、書き出したディレクトリを `:ro` でマウントする。
- 指示：`apps/daemon/src/prompts.ts` に、起点のコミットのコードがあることと読み取り専用であることを足した。
- 文言のコード：`packages/core/src/messages.ts`。
- コミットを重ねて、clone を工程にかかわらずタスクの開始時に行うようにし、レビューの対応で、作業領域を用意し直すときも記録済みの起点のコミットを使うようにした
  （`RepositoryWorkspace.prepare` に起点を渡し、ブランチの履歴に無ければコミットを直接取得し、それでも無ければ `git.baseCommitMissing` で止める）。

## 確かめたこと

- `npm test`：221件が通った（6件追加、既存の6件を「タスクの開始時に止まる」形に更新）。要求要件から始まらないタスク（実装から始まる）でも開始時に clone すること、
  要求要件・設計に起点のコードを読み取り専用で渡すこと、実装には clone を渡して書き出したものは実行の後に消すこと、実装の後に設計へ差し戻しても起点のコードを読むこと、
  書き出せない・clone できないときにエージェントを実行せずに止まること、指示の文、実際の git で起点のコミットのファイルだけを書き出すこと（作業領域の変更・
  起点の後のコミット・.git を含まない）、`docker run` の引数が `:ro` になることを確かめた。読み取り専用で渡すのをやめるとテストが失敗することも確かめた。
  レビューの対応の後は223件が通った。
- 実物で、テスト用のリポジトリを clone し、起点のコミットを書き出して、エージェントのイメージのコンテナに読み取り専用でマウントした。コンテナからファイルを読め、
  書き込みは `Read-only file system` で拒否された。
- レビューでは `npm test`・`npm run lint`・`npm run typecheck` が通ったことを確かめた。実際の Docker とブラウザでの動作は、レビューでは確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| P2：要求要件の承認の後に作業領域が消え、その間にベースブランチが進むと、clone し直したときに `RepositoryPrepared` が起点のコミットを上書きし、設計と実装が別のコミットを使う | 用意し直すときに記録済みの起点を渡してそのコミットに切り替え、`RepositoryPrepared` はタスクの開始時に一度だけ記録するようにした。起点を取得できない・記録と違うときは、起点を変えずに止める。サービスと実際の git の回帰テストを足し、起点を渡すのをやめると失敗することを確かめた |
