# デーモンを止めたら、ホストの MCP サーバーのプロセスを子孫ごと止め、前回の残りは次の起動で片付ける

- 日付: 2026-10-14（UTC）
- タスク: PBI-78
- PR: #86
- ブランチ: feat/issue-78-host-mcp-cleanup
- 関係する ADR: [ホストの MCP サーバーは自分のプロセスグループで起動して子孫ごと止め、前回の残りは記録と所有元のデーモンで確かめて次の起動で片付ける](../adr/20261014-0739-host-mcp-process-cleanup.md)

## 目的

`sacty up` を止めても、ホストの MCP サーバー（`gateway.mcp_servers`）のプロセスが親を失って残っていた。SDK の `StdioClientTransport` は直接の子にしか
シグナルを送らないので、`npx` のようなラッパーが起動した子孫が残る。デーモンが突然落ちたときに残ったものも片付けていなかった。
`sacty up` の終了（Ctrl-C・SIGTERM・デーモンの異常終了を含む）で、デーモンが起動したプロセスを子孫ごと止め、前回の残りは次の起動で、
sacty が起動したものだけを片付ける。

## したこと

- `apps/daemon/src/host-mcp-processes.ts`（新規）：
  - `GroupStdioTransport`：MCP サーバーを自分のプロセスグループで起動する stdio の transport。止めるときは標準入力を閉じて自分で終わるのを待ち（SDK と同じ2秒）、
    残ったグループと子孫（親をたどれるもの）を SIGTERM で止め、猶予の後に SIGKILL する。MCP サーバーが自分で終わったときも、残った子孫を止める。
  - `HostMcpProcesses`：起動したプロセスを `SACTY_HOME/host-mcp/processes/<pid>.json` に PID と開始時刻（ps の lstart。UTC・C ロケールで読む）の組で記録する。
    子孫も、初期化の直後と10秒ごとに記録し直す。次の起動の `cleanup()` では、PID と開始時刻が記録と一致するもの（と、その子孫・記録どおりに動いているリーダーのグループ）
    だけを止める。デーモン自身・その親・PID 1・デーモン自身のグループは止めない。ps が使えないときは何も止めず、記録も消さない。壊れた記録は止めずに消す。
- `apps/daemon/src/host-mcp.ts`：stdio の起動を `GroupStdioTransport` に替えた。`stop()` は、起動の途中のもの・切り替えた古いものも含めて子孫ごと止め、止めた後は起動しない。
- `apps/daemon/src/main.ts`：起動の前に `cleanup()` で前回の残りを片付ける。シャットダウンでは、実行の後片付け（最大20秒）を待たずにホストの MCP サーバーを止め始める
  （CLI の30秒の強制終了に巻き込まれないように）。例外などで終わるとき（`process` の `exit`）も、グループに SIGTERM を送る。
- README のホストの MCP の節に、止め方と前回の残りの片付けを足した。
- レビューの指摘を受けて：
  - 記録に、書いたデーモン（所有元）の PID と開始時刻を持たせ、所有元が動いているもの（同じ SACTY_HOME のほかの sacty）は止めず記録も残す。
  - compose のサービス（`apps/daemon/src/services.ts`）も、起動したデーモンをコンテナのラベル `io.sacty.owner` に残し、そのデーモンが動いているものは起動時の片付けで止めない
    （ラベルの無いものはこれまでどおり止める。所有元を確かめられないときは止めない）。
  - MCP サーバーの終了を `exit` で検知して子孫を止め、クライアントへの閉鎖の通知は1回だけにする。

## 確かめたこと

- `apps/daemon/src/host-mcp-processes.test.ts`（17件。偽の一覧で7件、実際のプロセスで10件）：SIGTERM/SIGINT・停止・起動の途中の停止・例外での終了、記録どおりのリーダー・
  PID の再利用・リーダーが先に終わった場合・壊れた記録・デーモン自身とその親・ps が使えない場合。
- 修正を1つずつ戻すと落ちる：プロセスグループで起動しない（4件）・開始時刻を比べない（4件）・リーダーを確かめずにグループを止める（3件）・起動時の片付けをしない（4件）・
  `stop()` で残りを止めない（1件）・自分で終わったときに子孫を止めない（1件）・`exit` でシグナルを送らない（1件）・記録の前に止められたときの取りこぼし（1件）・
  ps が使えないときに記録を消す（1件）・止めた後の起動（1件）。
- `npm run lint`（終了コード0）、`npm run typecheck`、`npx vitest run`（46ファイル・1057件。新しいテストは3回続けて通過）、`npm run build` が通った。
- 実際のプロセス：`SACTY_HOME` を一時ディレクトリにし、ポート 4900/4910 で `sacty up` を起動した（PATH の先頭に偽の `security`・`op`・`gh`・`docker`。本物の秘密情報・AI は使っていない）。
  偽の MCP サーバーは `sh -c "sleep 3600 & wait"` を起動し、標準入力が閉じたら自分だけ終わる。
  - Ctrl-C：MCP サーバー・sh・sleep の3つとも止まり、記録も消えた。
  - `sacty up` に SIGTERM：3つとも止まった。
  - デーモンに SIGKILL：sh と sleep が残った。続けて `sacty up` を起動すると、残りの2つを止めたというログが出て止まった。最後に Ctrl-C で、残ったプロセスは0。
  - 記録と PID が同じで開始時刻が違うプロセスを止めないことも確かめた。
- レビューの指摘への対応の後：2つ目のデーモンが1つ目の MCP を止めないこと（実際のプロセス）、所有元が終わった・所有元の PID が再利用された記録は片付くこと、compose で
  「動いている・終わった・PID が再利用された・ラベル無し」を区別することなどの回帰テストを足し、判定を戻すと落ちることを確かめた。同じ SACTY_HOME・同じポートで2つ目の
  `sacty up` を起動すると、2つ目は EADDRINUSE で終わり、1つ目の MCP のプロセス（3つ）は PID も含めて変わらず残った。Node のラッパーが標準入出力を引き継いだ `sleep` を
  起動して終わる形のテストで、子孫が止まり通知が1回だけであることを確かめた。レビューでテスト1093件・lint・typecheck が通った。
- Web の本番ビルドは、レビューの隔離した環境では確かめていない。画面の変更は無い。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 起動時の片付けが記録の PID と開始時刻だけを見ていて、記録を書いたデーモンがいまも動いているかを見ないので、同じ SACTY_HOME で2つ目の `sacty up` を起動すると、ポートの衝突に気づく前に1つ目が使っているホストの MCP サーバーを止める | 記録に所有元のデーモンの PID と開始時刻を持たせ、所有元が動いているものは止めずに記録も残すようにした。二重の起動を排除する方法は採らなかった。compose の起動時の片付けにも同じ問題があったので、所有元のラベルで判定するようにした。回帰テストを足した |
| MCP サーバーのコマンドが自分で終わっても、子孫が標準出力のパイプを開いたままだと `close` が来ず、子孫の回収に進まない | 終了を `exit` で検知して回収を始め、終わる直前の出力を読み終えるよう50ms待ってから通知する。閉鎖の通知は `exit` と `close` のどちらが先でも1回だけにした。回帰テストを足した |

## 残したこと

- 記録していない子孫は止めない。デーモンが突然落ちる直前（最後の記録から10秒以内）にリーダーが起動した子孫で、かつリーダーが先に終わっていたものは、次の起動でも片付けられないことがある。
- Windows は対象外（プロセスグループへのシグナルを使う）。
