# 実装が指摘を「後続に回したい」と申告でき、後続に回すかどうかを人が承認の画面で 1 件ずつ決める

- 日付: 2026-11-17（UTC）
- タスク: PBI-370
- PR: #406
- ブランチ: feat/pbi-370-defer-proposals
- 関係する ADR: [後続に回すかどうかは人が決め、実装は案と理由までを出す](../adr/20261117-0415-defer-proposals-decided-by-person.md)

## 目的

指摘を受けた実装には、「対応した」「理由があって対応しなかった」の 2 つの申告しか無く、範囲を広げてでも応じるか、断るかしかなかった。直しのために足した仕組みへの指摘が続き、往復が終わらない PR が出ていた。

この PR では、次を足す（人の決定は ADR にある）。

1. 実装が、指摘を「この PR では直さず、後続に回したい」と申告できる。申告は案で、基準（影響が大きいものは直す。提案の重みのうち、新しい仕組みが要る・範囲の外のものだけを案にする）を指示で伝える。
2. PR への返信に、案であり、人に確認中で、まだ決まっていないことを明記する。
3. 実装の承認の画面に、案の一覧を出し、人が 1 件ずつ「後続に回す／この PR で直す」を決める。
4. 「この PR で直す」は、差し戻しになる。
5. 決定と指摘の一覧を、PR のコメントに残す。
6. 人が後続に回すと決めた指摘を、PR のレビューが未対応に数えない。

人が後続に回すと決めた指摘の扱いの選択（sacty の後続のタスク・GitHub の Issue・何もしない）と、プロジェクトごとの既定は、この PR には含めない（次の PR）。

## したこと

- 申告と記録（`packages/core`）
  - 対応の申告に `deferred` を足した。実装の工程の対応だけが案になる（ほかの工程の `deferred` は、申告が無いものとして扱う）。
  - 案を `Task.remarks[].deferral` に持つ。対応の文と違い、後の提出で対応が無くても残る。
  - 人の決定を `DeferralsDecided`、PR のコメントの結果を `DeferralDecisionsPosted` に記録する。
  - 「この PR で直す」の差し戻しの指摘は、元の指摘の ID（`fixOf`）を持つ。
- 実装の指示（`apps/daemon/src/prompts.ts`）
  - 案の書き方と、いま直すか・案にするかの基準を足した。
  - 一度案にした指摘は、対応させる指摘から外し、指示とは分けたデータで渡す（人に確認中の案を、実装が黙って直さない・取り下げない）。
- 返信（`apps/daemon/src/remark-reply.ts`）：案の返信の頭と末尾の文を足した。
- 決定（`apps/daemon/src/service.ts`・`apps/daemon/src/server.ts`）
  - `decideDeferrals`（API は `POST /api/tasks/:id/deferrals/decide`）。「この PR で直す」があれば、決定と同じ追記で差し戻す。
  - 決定のコメント（`apps/daemon/src/deferral-notice.ts`）。指摘の文と理由を載せるのは、その PR のコメントから取り込んだ指摘だけにした（画面から書いた指摘の文は、今まで PR に出していないため）。
- レビュー（`apps/daemon/src/prompts.ts`・`apps/daemon/src/service.ts`）
  - 人が後続に回すと決めた指摘を、PR のレビューの子タスクに、指示とは分けたデータで渡す。
  - 人に確認中の案は、提案の重みなら数えさせず、要修正の重みなら残させる。
  - 先頭を変えずに、指摘のすべてを断るか案にしたときは、提出にして返信し、案のすべてを人が決めてから、同じ先頭を判定し直す。
- 画面（`apps/web`）
  - 承認の画面に、案の一覧と決定のフォーム（`DeferralNotice`）、タスクの詳細に、件数と承認の画面へのリンク（`DeferralPendingNotice`）。
  - 指摘の一覧に、案・決定の印。作業履歴に、決定と、PR のコメントの結果の行（日英）。
- docs：仕様書（`approval`・`tasks-and-steps`・`architecture`）、ユーザードキュメント（`tasks`・`troubleshooting`）を日英で直し、ADR を足した。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （自己レビュー）決定のコメントが、画面から書いた指摘の文を、初めて PR に出してしまう | その PR のコメントから取り込んだ指摘だけ、文と理由を載せるようにした |
| （自己レビュー）人に確認中の案を、後の実行が「対応した」と申告すると、PR の返信が「人に確認中」のまま食い違う | 一度案にした指摘を、対応させる指摘から外し、データで渡すようにした |
| （自己レビュー）1 件の指摘に複数の指摘がまとまっているとき、人が決めた範囲がレビューに伝わらない | レビューに、指摘の文と一緒に、実装が書いた理由を渡すようにした |
| （自己レビュー）「この PR で直す」が上限でエスカレーションになったとき、決定のコメントが「やり直して直します」と書く | まだ差し戻していないことを書くようにした |

## 残したこと

- 人が後続に回すと決めた指摘の扱いの選択（sacty の後続のタスク・GitHub の Issue・何もしない）と、プロジェクトごとの既定（次の PR）。
- 引き継いだ PR（人が作った PR を直すタスク）で、実装に渡した指摘には、案を出せない。
- 決めないままマージされた案は、PR の返信が「人に確認中」のまま残る。
- 「この PR で直す」の差し戻しは、原因を決めない差し戻しとして数える。
