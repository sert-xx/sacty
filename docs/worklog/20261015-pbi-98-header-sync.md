# 画面のヘッダー（お知らせ・表示しているプロジェクト）を、本文と今の状態に合わせる

- 日付: 2026-10-15（UTC）
- タスク: PBI-98
- PR: #106
- ブランチ: feat/issue-98-header-sync
- 関係する ADR: なし

## 目的

画面のヘッダーが今の状態とずれる問題を直す。タスクを承認してもお知らせの印が消えない、プロジェクト A を選んだまま B を作ると
B の設定の画面なのにヘッダーが A のまま、の2つ。ほかにヘッダーと本文がずれる所も洗い出して直す。

## 原因

- ヘッダーは全体のレイアウト（`apps/web/src/app/layout.tsx`）にあり、Next.js は画面の中の移動やサーバーアクションの `redirect`
  では、移る先と共通のレイアウトを描き直さない。承認・差し戻し（`gateAction`）とタスクの作成は `redirect` だけで、`refresh()` を
  呼んでいなかった（一時停止・中止などは `refresh()` を呼んでいたので、ヘッダーも変わっていた）。そのため、承認した後もお知らせは
  古いまま残り、実行中のタスクがあるときの3秒ごとの更新（`AutoRefresh`）か読み直しまで変わらなかった。
- 表示しているプロジェクトは cookie（`sacty-project`）に持ち、ヘッダーは cookie のプロジェクトを出す。cookie を変えるのはヘッダーの
  切り替え・お知らせ（`/switch`）だけで、プロジェクトの作成・インポートでは変えずに設定の画面（URL のプロジェクト）へ移っていた。
  同じ理由で、プロジェクトの一覧から別のプロジェクトの設定を開く・Slack の通知や URL から別のプロジェクトのタスクを開くと、
  ヘッダーは元のプロジェクトのままだった。
- 実行中のタスクが無いときは、ヘッダーは更新しないので、ほかのタブ・CLI でした承認などは、そのタブを読み直すまで出なかった。

## したこと

- `apps/web/src/app/actions.ts`
  - 承認・差し戻し（`gateAction`）とタスクの作成（テンプレートも）で、`redirect` の前に `refresh()` を呼ぶ（ヘッダーも描き直す。
    同じ応答で返るので、問い合わせは増えない）。
  - プロジェクトの作成・インポートで、作ったプロジェクトを表示しているプロジェクトにする（cookie を変える）。
  - 開いた画面のプロジェクトに合わせる `selectProjectAction` を足した。
- `apps/web/src/components/shell/follow-project.tsx`（`FollowProject`）・`select-project.tsx`：タスクの詳細・レビュー・実行のログ・
  プロジェクトの設定の画面で、cookie と画面のプロジェクトが違い、そのプロジェクトがあるときだけ、表示の後に `selectProjectAction`
  で cookie を変える（画面とヘッダーが描き直される）。同じならデーモンにも問い合わせない。削除したプロジェクトのタスクなど、
  プロジェクトが無ければ変えない。
- `apps/web/src/components/auto-refresh.tsx`（`RefreshOnVisible`）：タブに戻ってきたときに一度だけ画面を最新にする（ヘッダーに置く）。
  見えている間は問い合わせない。
- `apps/web/src/lib/project-select.ts`：cookie の属性と ID の形の検査を `/switch` と共通にした（`PROJECT_COOKIE_OPTIONS`・
  `isProjectId`）。合わせる必要があるかの判定（`needsProjectSelect`）。
- 仕様書 `docs/spec/architecture.md` に「画面のヘッダー」の節を足した（これまで書いた節が無かった）。ユーザードキュメント
  `docs/user/project-settings.md` に、ヘッダーのプロジェクトが切り替わる場面を足した。

## 洗い出したずれ（受け入れ条件3）

| 場面 | 結果 |
| --- | --- |
| 承認・差し戻し・タスクの作成の後のお知らせ | 直した（`refresh()`） |
| 一時停止・再開・中止・申し出の判断・質問・再レビュー・書き出し直し・取り込み | もともと `refresh()` を呼んでいた（変えていない） |
| プロジェクトの作成・インポートの後のヘッダー | 直した（作ったプロジェクトにする） |
| 一覧から別のプロジェクトの設定を開く・タスクの詳細から別のプロジェクトの設定へのリンク | 直した（`FollowProject`） |
| 通知・URL・親子や修正のタスクのリンクから、別のプロジェクトのタスク（詳細・レビュー・実行のログ）を開く | 直した（`FollowProject`） |
| ほかのタブ・CLI・デーモンでの変化 | 実行中・実行待ちの間の3秒ごと（もとから）と、タブに戻ってきたとき（足した） |
| プロジェクトの名前の変更 | もともと `refresh()` でヘッダーも変わる（確かめた） |
| 選んでいたプロジェクトが無い（cookie が古い） | ヘッダー・タスクの一覧・設定へのリンクは、どれも最初のプロジェクトにそろう（もとから。確かめた） |
| プロジェクトの削除 | sacty にはプロジェクトを削除する操作（画面・API・CLI）が無い。cookie が古いときと同じに扱われる |

直さないもの：

- 実行中のタスクが無く、タブを開いたまま見ている間は、ほかのタブ・CLI・デーモンでの変化は出ない（タブに戻る・操作する・読み直す
  まで）。常に問い合わせると重くなるため、今の更新の仕組み（実行中の間の更新）の範囲にとどめた。
- 別のプロジェクトの画面を開いたときは、表示した後にヘッダーが切り替わる（サーバーの描画では cookie を変えられないため、
  一瞬だけ元のプロジェクトが出る）。
- 複数のタブで別々のプロジェクトの画面を開いていると、表示しているプロジェクト（cookie はブラウザで1つ）は最後に開いた・
  戻ってきたタブのものになる。見ているタブの中では、ヘッダーと本文はそろう。

## 確かめたこと

- 再現（直す前）：一時的な `SACTY_HOME`・偽の `gh`・`docker`・ポート 4981/4982 で、一時停止中のタスク2つと要求要件の承認待ちの
  タスク1つを作業履歴に入れて起動し、Playwright で操作した。
  - タスクの一覧 → タスクの詳細 → レビュー（どれもリンクで移動）→ 承認すると、お知らせは3件のまま（読み直すと2件）。
  - プロジェクト A を選んだまま B を作ると、本文は「プロジェクトB の設定」、ヘッダーは「プロジェクトA」。
- 直した後：同じ手順で、承認の直後にお知らせが2件、B を作った直後にヘッダーが B になる。あわせて、一覧から A の設定を開く
  （ヘッダーが A。読み直しても余計なアクションは0回）、A の名前の変更（ヘッダーも新しい名前）、B の設定・A のタスクを URL で
  開く、ほかのタブで中止してから戻る（戻る前は3件、戻った後は2件）、cookie を無いプロジェクトにする（ヘッダー・本文・設定へのリンク
  が最初のプロジェクト）、無いプロジェクトの設定を開く（404。ヘッダーは変えない）を確かめた。
- 承認のときの問い合わせは、アクションの1回だけ（ヘッダーの描き直しは同じ応答で返る）。
- テストを足した：`apps/web/src/app/actions.test.ts`（承認・差し戻し・作成で `redirect` の前に `refresh()`、失敗では描き直さない、
  作成・インポートで cookie を作ったプロジェクトにする、保存では変えない、`selectProjectAction` の ID の検査）、
  `apps/web/src/lib/project-select.test.ts`、`apps/web/src/components/shell/follow-project.test.ts`（違えば合わせる・同じなら
  問い合わせない・プロジェクトが無い／デーモンにつながらなければ変えない）、`apps/web/src/components/shell/header-refresh.test.ts`
  （実行中のタスクが無くても、タブに戻ったときの更新を置く）。
- 修正を戻すと落ちること：`gateAction` の `refresh()`・作成とインポートの cookie・`needsProjectSelect`・ヘッダーの
  `RefreshOnVisible` を戻すと、5件落ちる。
- `npm run lint`（終了コード0）・`npm run typecheck`・`npx vitest run`（59ファイル・1383件が通過）・`npm run build`・
  `npx vitest run tests/docs`。

## わからないこと・確かめていないこと

- 本物のエージェントで工程を進めたとき（承認の後に次の工程が動き、また承認待ちになる流れ）は確かめていない（偽の `docker` で、
  承認の後は実行待ちのまま）。
- 各画面に `FollowProject` を置いたこと自体は、ブラウザで確かめた（画面のコンポーネントの単体のテストは無い）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （DA）削除したプロジェクトのタスクを開くと、cookie を無いプロジェクトに変えてしまい、選んでいたプロジェクトが最初のプロジェクトに戻る | `FollowProject` で、合わせる前にプロジェクトがあるかを確かめる（違うときだけ問い合わせる）。テストを足した |
| （DA）cookie がまだ無いとき（初めて開いた）も、プロジェクトの画面を開くとアクションが1回走る | 1回だけで、以後は cookie がそろうので走らない。そのままにした |
| （PR のレビュー）`FollowProject` が、プロジェクトの一覧を取れなかったことを「プロジェクトが無い」と同じに扱い、合わせない。作業中のタスクが無ければ、ずれたまま残る | 失敗と不在を分けた。一覧を取れなければ、無いとは扱わずに合わせる（画面はそのプロジェクトをデーモンから読んで表示した直後で、一覧の取得だけが失敗した場合のため。無いプロジェクトに合わせても、ヘッダーは最初のプロジェクトを出すだけ）。上の「デーモンにつながらなければ変えない」のテストは、合わせるテストに置き換えた |
| （PR のレビュー）デーモンにつながらず仮のヘッダー（`HeaderFallback`）を出したときは、タブに戻っても描き直さない | `HeaderFallback` にも `RefreshOnVisible` を置いた |
| （PR のレビュー）`RefreshOnVisible` のテストが、要素があることしか確かめていない | `visibilitychange` の処理を `watchVisible` に分け、見える状態に戻ったときに1回だけ・隠れるほうでは呼ばない・止めた後は呼ばないことを確かめた |
| （PR のレビュー）仕様書の3秒ごとの更新の対象が「実行中・実行待ち」だけになっていて、`isWorking` と合わない | `docs/spec/architecture.md` に `isWorking` の対象（待機のうち検証中・再現の確かめ中、判定がまだの変更の申し出）を書いた |

### レビュー対応で確かめたこと

- 修正を1つずつ戻すと、それぞれのテストが1件ずつ落ちる：一覧の取得の失敗を「無い」に戻す、`HeaderFallback` の `RefreshOnVisible` を
  外す、見える状態かの判定を外す、`visibilitychange` の登録を外す。
- `npm run lint`（終了コード0）・`npm run typecheck`・`npx vitest run`（59ファイル・1386件が通過）・`npm run build`・
  `npx vitest run tests/docs`。
- レビュー対応の変更は、ブラウザでは確かめていない（単体のテストで確かめた）。
