# 人が実装の PR をマージしたら、走っている作り直しを止めて完了に寄せる

- 日付: 2026-11-02（UTC）
- タスク: PBI-276
- PR: #278
- ブランチ: feat/issue-276-merge-stops-rework
- 関係する ADR: なし（「マージ＝承認」という既存の方針を、作り直しの間にも当てはめた不具合の修正）

## 目的

実際に動かした試行（雑な・矛盾したレビューを入れるシナリオ）で、人が実装の PR をマージした後も、AI のレビューの取り込みで始まった実装の再実行が走り続け、新しいドラフト PR を作った。タスクは完了せず、その PR をマージして初めて完了した（余分に実装 2 回・最終レビュー 2 回）。

受け入れ条件の要点：

- 実装の PR のマージを検知したら、そのタスクで走っている・待っている実装の作り直し（実装・最終レビュー・やり直し）を止め、マージを承認として次へ進める。新しい PR は作らない。
- 止めた実行と、捨てた未反映の指摘は、作業履歴に理由付きで残る。
- 要求要件・設計の PR のマージの振る舞いは変えない。
- 仕様書・ユーザードキュメント（日英）・作業履歴を直し、マージの検知と作り直しが重なる順序をテストで確かめる。

## 原因（コードで確かめた）

- PR の確認（`checkPullRequests`）が見守るのは、承認待ち・エスカレーションのタスクの PR だけ。差し戻して実装を作り直している間は、状態が実行待ち・実行中・待機になるので、その間のマージは誰も見ない。
- 作り直しの最後の PR の更新（`publish`）は、前の PR がマージ済みだと新しい番号の PR を作る作りだった（マージ済みの PR を更新しないため）。このため、マージが検知されないまま新しい PR ができ、承認待ちが 2 周目になった。

## したこと

- 作業履歴の新しいイベント `ReworkStoppedByMerge`（`packages/core/src/events.ts`）：マージされた PR の番号、止めたときの段階（`was`）、止めた実行（`stoppedRuns`）、捨てた指摘（`discardedRemarks`）、捨てた検証の結果の種類（`discardedFeedback`）。projection は、タスクを実装の承認待ちに戻し、捨てた指摘を無効にし、検証・PR の作成の待ち・一時停止の状態を消す。続く `PullRequestMerged`・`StepApproved`（既存の記録）が承認として進める。既存のマージの経路と同じ記録になるよう、記録の組み立てを `mergeApprovalItems` に取り出して共有した。
- 見守る対象（`reworkingPullRequest`）：実行対象の工程が実装で、実行待ち・実行中・待機・一時停止のタスクのうち、実装の PR が開いたままのもの。PR の確認の初めに、これらの PR の状態を読む（`checkReworkMerges`）。
- 止め方（`stopReworkForMerge`）：実行中ならコンテナを止めて終わりを待つ（人の一時停止と同じ仕組み。止めた実行は人の一時停止として記録しない）。止めたコンテナを確かめられなければ一時停止にして進めず、次の確認で確かめ直す。止めている間に承認待ちになった・中止されたなら記録しない。
- PR の更新の直前（`publish`）にも、前の PR がマージ済みか確かめる。マージ済みなら、プッシュも PR の作成もせず、同じ記録で承認として進める（確認の前に更新が始まる場合）。
- 捨てた指摘：最後の差し戻し（`round` が最新）の指摘のうち、無効でなく、提出済みの PR に渡していないもの（`unreflectedImplementRemarks`）。
- 作業履歴の表示（日英）、仕様書（`approval`・`tasks-and-steps`）・ユーザードキュメント（`tasks`）を日英で直した。

## 確かめたこと

作業は worktree（`sacty-wt-pbi-276`）で行った。

- `npx vitest run apps/daemon/src/daemon.test.ts -t "PBI-276"`：13 件通る。重なりの順序：実行待ち／エージェントの実行中／止める合図の時点で実行が正常に終わった／最終レビューの途中／最終レビューに通らずやり直しを待つ間／PR の更新の直前（確認の前）／一時停止中。そのほか、人が PR の中で直してからのマージ（`edited`）、開いたまま・閉じられた PR は止めない、要求要件・設計をやり直している間は止めない、PR の状態を読めない、止めたコンテナを確かめられない間は進めず確かめられたら完了、承認待ちの間のマージは従来どおり。

- `apps/web/src/lib/labels.test.ts`：作業履歴の表示（日英）。

## 残したこと

- 要求要件・設計をやり直している間のマージは見守らない。実装に進んだ時点で、PR がマージ済みなら同じ経路で止めて承認として進める（その時点の実装をやり直す前にマージの確認が入る）。
- 承認した成果の本文（`approved.implement.output`）は、記録している最新の実装の報告のまま。マージされた内容は PR のコミットが正。
- 捨てた指摘を続きのタスクにするなどはしない（利用者が続きのタスクを作る）。

| 指摘 | 対応 |
| --- | --- |
| [要修正] デーモンが実装中に止まって再起動し、コンテナが残っていると、停止の確認を通らず承認へ進む | 正しかった（`recoverInterrupted` は実装の実行を `unstoppedRuns` に残さず、`inflight` も失われる）。復旧で、実装の作り直し（開いた PR がある）の実行を `unstoppedRuns` に残して一時停止にする。PR のマージで止めるときは、一時停止中の `unstoppedRuns` を確かめてから承認へ進む。再起動を挟んだテストを足した。最終レビュー（ゴールガーディアン）の実行は、実行の ID を作業履歴に残していないので、再起動後は確かめられない（残した制限） |
| [要修正] 停止の合図と同時に実装が正常に終わると、印を消した後にワーカーが検証を再開できる | 正しかった。`mergeStopping` を、承認か一時停止を記録し終えるまで保ち、`runNext` と `queuedTaskIds` でも実行を始めさせない。停止の確認を途中で止めるテストを足した |
| [要修正] 引き継いだ PR（`publishContinued`）がマージ確認を通らず、元のブランチへプッシュする | 正しかった。確認を引き継ぎの分岐より前に移し、引き継いだ PR にも当てる。テストを足した |
| [要修正] 確認では開いていたが、プッシュの間にマージされると、後半の確認で新しい PR を作る | 正しかった。後半の確認（新しい PR を作るかの確認、引き継いだ PR の確認）でもマージなら、承認として進める。それぞれテストを足した |
| [提案] 停止を確認できず一時停止した後、次の確認で成功すると、`stoppedRuns` が空になる | 直した。一時停止のときの `unstoppedRuns` を、止めた実行に含める。既存のテストに期待を足した |
