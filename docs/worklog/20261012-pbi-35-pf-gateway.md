# 外部の PF（プラットフォーム）の API を、ホストのゲートウェイ経由で安全に使わせる

- 日付: 2026-10-12（UTC）
- タスク: PBI-35
- PR: #42
- ブランチ: feat/issue-35-pf-gateway
- 関係する ADR: [外部の PF（プラットフォーム）の API は、ホストのゲートウェイがホワイトリストに合うリクエストだけを PF の認証を付けて中継する](../adr/20261012-1207-platform-api-gateway.md)

## 目的

MCP サーバーが無い外部の PF を、エージェントが API で使えるようにする。ホストのゲートウェイ（#39）が、ホワイトリストに合うリクエストだけを
PF の認証を付けて中継し、認証情報はエージェントに渡さない。受け入れ条件の要点：PF ごとに転送先・認証のかけ方・ホワイトリストを書ける、
起動時に認証情報をまとめて取得しメモリーにだけ持つ、ホワイトリストに無いものは 403 で使える API の一覧を返す、API キーでトークンを取得する
PF に対応し期限の前・拒否で取り直す、コンテナからだけ届く（127.0.0.1・実行ごとのトークンを含む URL）、工程エージェントの指示に使える
PF と API の一覧を含める、認証情報を取得できない PF を画面に出しほかの PF は使える。

## したこと

- `apps/daemon/src/platforms.ts`（新規）：PF の設定・ホワイトリストの判定（`..`・`%2e` などは合わない）・認証の値の用意（トークンの取得と期限の管理。
  同時の取得は1回。窓口の応答に秘密情報が含まれていても理由には出さない）・指示に入れる一覧。
- `apps/daemon/src/gateway.ts`：`/r/<トークン>/pf/<PF>/…` を中継。エージェントが付けた認証・クッキーは捨てる。トークンの PF で 401・403 なら
  取り直して1回だけ送り直す。
- `apps/daemon/src/service.ts`：工程エージェントに `SACTY_PF_URL` と一覧を渡す。状態に、用意できない PF を warnings として出す。
- `apps/daemon/src/config.ts`・`apps/daemon/src/main.ts`：`gateway.platforms` と起動時の用意。
- 画面（`apps/web/src/app/page.tsx`）：タスクの一覧の上に warnings を出す。`README.md` に例を足した。
- レビューの指摘で、許可の判定を送るパスと一致させ、秘密情報を伏せる範囲と順序を直した。実際の git を動かすテスト（`apps/daemon/src/repository.test.ts`）の
  時間切れの上限を 30 秒に延ばした。

## 確かめたこと

- `npm test`（395 件）・`npm run lint`・`npm run typecheck` が通った。
- メソッドを合わせる・`..` などを拒否する・期限の前に取り直す・理由に秘密情報を出さない・ホワイトリストで拒否する・拒否されたら取り直す・
  `SACTY_PF_URL` を渡す、の修正を1つずつ戻すとテストが失敗することを確かめた。エージェントが付けた認証のヘッダーを捨てる処理は、戻しても
  テストは通った（ゲートウェイが同じヘッダーを本物の値で上書きするため。守りの二重化として残した）。
- 実際のコンテナ（sacty のイメージ）から `$SACTY_PF_URL` を呼び、ホストの偽の PF に、固定のキー（独自のヘッダー）と取得した JWT が付いて
  中継されること、ホワイトリストに無いものが 403 になること、コンテナの環境変数に秘密情報が無いことを確かめた。
- 最後のレビューでは、`npm test`（395 件すべて成功）・lint・typecheck を確かめた。途中のレビューでは、既存の Git のテスト1件が5秒で時間切れに
  なった（単独の実行では 12 件すべて成功）。実際の PF・実際の 1Password を使う接続は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 許可の判定は生のパスで行うが、送るときに `#` 以降はフラグメントとして落ちるので、`POST /api/v1/tickets/*/comments` だけを許可していても `…/123#x/comments` が通り、許可していない `/api/v1/tickets/123` に認証を付けて送られる | 送る URL を先に作り、パス・クエリが URL として解釈しても変わらないとき（`#`・空白・`.` や `..` のまとめが無い）だけ、同じパスで判定して送るようにした。変わるなら 400 で上流には送らない。生のパス（`#`・`/./`・クエリの後ろの `#`）を送って上流への送信が0件である回帰テストと、URL を作る関数のテストを足し、判定を戻すと失敗することを確かめた |
| 秘密情報を伏せるのは失敗の応答の本文だけで、ヘッダーの組み立てなどの例外は値をそのまま含む（改行を含む値を `X-Key: "{{secret}}"` に入れると、例外の文に値全体が出て、画面の警告・起動のログ・502 の本文に出る） | 秘密情報を取り出した後の処理を1か所で受け止め、どの失敗でも理由から秘密情報（値そのもの・JSON の文字列にした形・各行）を伏せるようにした。偽の値 `FAKE-SECRET\nBAD` で、例外・画面の警告・502 の本文に値が残らず `[secret]` になるテストを足し、伏せる処理を戻すと失敗することを確かめた |
| トークンの窓口の失敗の応答を 500 文字に切り詰めてから伏せるので、境界をまたぐ秘密情報の一部が残る | 本文は切り詰めずに理由に入れ、秘密情報を伏せてから理由を 600 文字に切り詰めるようにした。401 で `'x'.repeat(N) + 秘密情報` を返す回帰テストを N = 470・480・590・595 で足し、元の順に戻すと失敗することを確かめた。時間切れになった git のテストは、そのファイルの上限を 30 秒に延ばした |

## 残したこと

- 実際の環境での確認（`gateway.platforms` に PF の転送先・認証・使える API を書き、sacty を起動して警告が出ないこと、PF の API を使うタスクで
  `$SACTY_PF_URL` で呼べること、一覧に無い API が拒否されることを確かめる）は、利用者の環境で行う。
