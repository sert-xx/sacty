# 後続に回すと決めた指摘の扱い（後続のタスク・GitHub の Issue・何もしない）を、人が指摘ごとに選ぶ

- 日付: 2026-11-17（UTC）
- タスク: PBI-370
- PR: #411
- ブランチ: feat/pbi-370-deferral-handling
- 関係する ADR: [後続に回すと決めた指摘の扱いを、人が指摘ごとに選ぶ](../adr/20261117-0504-choose-handling-of-deferred-findings.md)

## 目的

PBI-370 の 2 つ目の PR。1 つ目（#406）で、人が、実装の案を 1 件ずつ「後続に回す／この PR で直す」と決められるようになった。この PR では、後続に回すと決めた指摘の扱いを、人がその場で選べるようにする。

1. 指摘ごとに、「sacty の後続のタスクを作る」「GitHub の Issue を作る」「何もしない」から選ぶ。
2. プロジェクトごとに、既定を決められる。
3. どれを選んでも、決定と指摘の一覧は、PR のコメントに残る（扱いも書く）。

ほかのチケット管理ツールでの作成は、範囲の外。

## したこと

- 扱いの記録（`packages/core`）
  - 決定（`DeferralsDecided`）に、指摘ごとの扱い（`handling`）を足した。結果は `DeferralHandled`（作った Issue の URL・作った後続のタスク・できなかった理由）に記録する。
  - プロジェクトの定義に、扱いの既定（`deferralHandling`）を足した。エクスポートには入れない。
- デーモン（`apps/daemon`）
  - 扱いを選ばない決定は、プロジェクトの既定（無ければ、何もしない）を使う。「この PR で直す」の指摘に扱いを渡すと断る。
  - GitHub の Issue：決定のときに作り、決定のコメントに URL を載せる（`createIssue`・`buildDeferralIssue`）。
  - sacty の後続のタスク：元のタスクが完了してから、PR の確認の終わりに、指摘ごとに 1 つ作る（`settleDeferralTasks`）。完了したタスクの続きのタスクと同じ作りにし、目印で、二度作らない。
  - 決定のコメントに、指摘ごとの扱いの行を足した。
  - GitHub に書けない理由の文言（アカウント無し・セキュリティのタスク）を、Issue にも当てはまる言い方に直した。
- 画面（`apps/web`）
  - 承認の画面の案ごとに、「後続に回すときの扱い」の選択を足した（初めの値は、プロジェクトの既定）。決定済みの記録に、扱いと結果を出す。
  - プロジェクトの設定に、「後続に回す指摘の扱い」の欄を足した。
  - 作業履歴に、扱いと、その結果の行（日英）。
- docs：仕様書（`approval`・`export`）、ユーザードキュメント（`tasks`・`project-settings`）を日英で直し、ADR を足した。

## レビューの指摘と対応

### 1 回目のレビュー（PR #411、先頭 `1da4e932`）

判定は「修正が必要」。リスク評価は「高」（合図：セキュリティ（重い）、取り消しにくい変更（重い））。

| 指摘 | 対応 |
| --- | --- |
| [要修正] Issue を作ると選んだ指摘で、結果が記録されない経路がある（トークンの取り出しの失敗・デーモンの停止） | 対応した。Issue を作る前の失敗でも、Issue の結果を失敗として記録する。決定の後に止まって記録が無い指摘には、起動し直した後の PR の確認で、途中で止まったことを記録する（作っている最中の指摘は除く） |
| [要修正] 後続のタスクの依頼に、外から来た文をそのまま入れている（指示として扱われる・目印の文字列で取り違える） | 対応した。依頼の文は sacty の文だけにし、指摘と理由は、指示とは分けた JSON のデータにした。照合は、作成の記録（`derivedFrom.deferredRemarkId`）で行う |
| [提案] 後続のタスクの依頼の文が、説明の上限を超えうる | 対応した。指摘と理由を 2,000 文字ずつで切り、JSON にすると長くなる文字でも上限に収まることをテストした |
| [提案] Issue の作成が 30 秒の共通の期限を分け合う。作成済みでも「作れなかった」と記録しうる | 対応した。Issue ごとに期限を持たせ、期限を超えた失敗は、作られているかもしれないと分かる理由で記録する。作る前の検索（目印での重複の確認）は足していない（人が GitHub で確かめる） |
| [提案] 分岐のテストが足りない | 対応した。セキュリティのタスク・アカウント無し・トークンの失敗・途中の停止・期限切れ、後続のタスクの照合（作成の記録・目印をまねた文）と作成の失敗、`deferralAction`、`mergeProjectDefinitions` のテストを足した。PR が閉じている・PR が無い実装で Issue を選んだ場合は、足していない |
| [提案] 完了後に、扱いの結果が見えない | 一部対応した。作業履歴の行に、作った後続のタスクの ID を出す。作った後続のタスクは、元のタスクの詳細の「続きのタスク」にも並ぶ（もとからの表示）。決定済みの一覧を完了後も出すことは、していない |
| [提案] 扱いの選択が、常に有効に見える | 対応した。「後続に回す」を選んだ指摘だけで選べる |
| [提案] ラベルに補足のボタンが入っている | 対応した。補足の印を、label の外に出した |
| [提案] Issue の整形が `askQuote` と重複し、内部のパスが載りうる | 対応した。`askQuote` に上限を渡せるようにして共有し、内部のパスを置き換える。題の上限の定数を 1 つにし、プロジェクトの定義は `DeferralHandling` を使う。結果を記録する処理が 2 か所にある点は、記録する中身（Issue と後続のタスク）と呼ぶ場所が違うので、そのままにした |

出し直しの検証（先頭は、この対応のコミット）：`npx biome check --error-on-warnings .` は誤り・警告なし、`npm run typecheck` は誤りなし、`npx vitest run --no-file-parallelism` は 256 ファイル・4,928 件が成功（1 件はもとからのスキップ）、`npm run build` は成功。実物の確認（日英の画面。44 項目）もやり直して、すべて合った。

## 残したこと

- ほかのチケット管理ツールでの作成。
- 扱いの既定は、プロジェクトのエクスポートに入らない。
- Issue・後続のタスクを作れなかったときは、やり直さない（理由を作業履歴と承認の画面に出す）。
