# レビューを依頼された PR とレビュー用のラベルの PR を取り込み、レビューだけを行う

- 日付: 2026-10-13（UTC）
- タスク: PBI-44
- PR: #55
- ブランチ: feat/issue-44-pr-review-intake
- 関係する ADR: [レビューを依頼された PR とレビュー用のラベルの PR を取り込み、オーケストレーターを使わずにレビューだけを行う](../adr/20261013-0335-review-only-pr-intake.md)

## 目的

ほかの利用者に sacty を広めるための最初の使い方として、PR のレビューだけを sacty に任せる流れを整える。

## したこと

- 「sacty の設定」に「PR のレビューの取り込み」を足した（Issue の取り込みのラベルとは別の設定。`apps/web/src/components/settings-form.tsx` など）。
  - 自分にレビューが依頼された PR を取り込む（切り替え）。自分は、プロジェクトでそのホストに選んだ GitHub のアカウント。個人としての依頼だけで、チームへの依頼は含めない
    （`user-review-requested:<アカウント>` で検索）。
  - PR のレビュー用のラベル。そのラベルの付いた PR を取り込む（Issue は取り込まない）。
  - github.com と GitHub Enterprise Server の両方で、ホストごとのアカウントで探す（`apps/daemon/src/intake.ts`・`apps/daemon/src/github.ts`）。
- この取り込みの PR は、オーケストレーターを使わずに、工程をレビューだけにする（`apps/daemon/src/service.ts`）。レビューはこれまで（PBI-19）どおり、人の承認を挟まずに PR にコメントのレビューとして投稿する。
  依頼とラベルの両方に当てはまっても、取り込むラベルも付いていても、タスクは1つで、レビューだけ。工程のカードの見出しは「PR のレビューの取り込み（レビューだけ）」。
- PR がマージ・クローズされたら、終わっていないレビューのタスクを中止する（作業履歴に理由を残し、中止したのは sacty）。
- タスクの詳細に「再レビュー」を足した（`apps/web/src/components/rereview-button.tsx`・`apps/daemon/src/server.ts`）。レビューを投稿して完了したタスクで、PR の最新のコミットをもう一度レビューして投稿する。
  回ごとに別の目印をレビューの本文に入れ、前回のレビューを今回の投稿済みと見なさない。
- これまでの Issue・PR の取り込み（取り込むラベル）は、そのまま動く。プロジェクトの一覧の取り込みの状況にも、PR のレビューの取り込みを出す。README に説明を足した。
- この PBI は、最初は別の agent が実装していたが、途中で止まっていたため、残りを引き継いで仕上げた。

## 確かめたこと

- build・typecheck・lint・全テスト（510件）が通った。
- 追加したテスト：
  - 検索の条件（依頼・ラベル、ホストとアカウントごと、切り替えを切ると依頼は探さない）。
  - 取り込み（依頼の PR・ラベルの PR、ラベルの Issue は取り込まない、両方に当てはまっても1つ、取り込むラベルと両方ならレビューだけ、二度は取り込まない、切り替えを切った後の依頼の PR は取り込まない）。
  - オーケストレーターを使わずにレビューだけを行って投稿する。
  - PR のマージ・クローズで中止し、開いている PR・ほかの取り込みのタスクは中止しない。
  - 再レビュー（投稿前はできない、最新のコミットで2回目を投稿、回ごとの目印）。作業履歴の文言。
- 主な判定を戻すと、テストが失敗することを確かめた（6通り）。
- 画面は動画で確かめた（一時的なデータの環境。最後の一時停止は、デモの環境のプロジェクトで GitHub のアカウントを選んでいないため）。
- 再レビューで、全513テスト・lint・型チェックが通った。GitHub での実際の自動の取り込み・レビューの投稿は、レビューでは未実施。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| レビューだけの工程に直接分岐すると、プロジェクトの対象で指定したイメージ（固定のイメージ）を通らず、既定の Node のイメージ・環境変数なしでレビューし、無い名前も検出しない | レビューだけの工程も、工程の選択と同じイメージの適用を通すようにした。対象で指定したイメージを review の工程に記録して使い、`images` に無い名前なら工程を決めずに理由を示して止まる（オーケストレーターは起動しない）。回帰テストを足し、適用を外すと失敗することを確かめた |
| 検索の結果に「依頼された」しか残さないので、担当のプロジェクトが別に決まったときに、誰への依頼だったかを確かめられない。Org とリポジトリで別のアカウントを選んだ構成で、片方への依頼がもう片方のプロジェクトのタスクとして取り込まれ、そのアカウントで投稿される | レビューの依頼の検索で見つけた PR に、検索したアカウント（`requestedFor`）を付けた。取り込みでは、担当のプロジェクトでそのホストに選んだアカウントと照らし合わせ、本人への依頼のときだけ「依頼」として取り込む（大文字・小文字は区別しない）。一致しない・誰への依頼かわからないものは、レビュー用のラベルが付いていなければ取り込まない。回帰テストを足し、照らし合わせを外すと失敗することを確かめた |

## 残したこと

- 利用者の環境で、次を確かめる（PR で依頼した）：自分にレビューが依頼された PR（github.com・GHE）が取り込まれ、レビューが PR に投稿されること。
  PR をマージ・クローズすると、終わっていないレビューのタスクが中止されること。
