# プロジェクトのコンテキストの秘密情報も、起動時と保存時にまとめて取り出す

- 日付: 2026-10-15（UTC）
- タスク: PBI-107
- PR: #117
- ブランチ: feat/issue-107-prefetch-context-secrets
- 関係する ADR: [起動時と保存時に、プロジェクトのコンテキストの秘密情報もまとめて取り出す](../adr/20261015-1303-prefetch-context-secrets.md)

## 目的

コンテキストリポジトリの `platforms.yaml`・`mcp.yaml` の秘密情報は、起動時のまとめての取り出し（PBI-48）の対象外だったので、工程の実行・
ゲートウェイでの PF の呼び出し・チケットのトリアージで初めて使うときに、参照ごとに 1Password の承認を求めていた。タスクを作った後の承認は
見落としやすい。承認を、起動時とプロジェクトの設定の保存時（と、利用者が押す「取り出し直す」）だけにする。

## したこと

- デーモン：
  - `contextSecretSources`（`context.ts`）：プロジェクトのコンテキストを取得・合成し（継承の鎖の上の層と既定のコンテキストを含む）、
    MCP サーバーと外部 PF を返す。
  - `contextSecretUses`・`projectSecretUses`（`secret-uses.ts`）：合成した `platforms.yaml` の認証と `mcp.yaml` の `env`・`headers` の参照を、
    書いた層とともに集める。ホストの PF・MCP サーバーと同じ名前（層のものを使わない）と、ゲートウェイのトークンは除く。参照に projectId を持たせた。
  - `prefetchSecrets`：コンテキストを同時に4件ずつ、全体で30秒まで取得してから、ほかの秘密情報と一緒に1回で取り出す。取得の失敗・時間切れは
    警告にし（git のエラー文は gh のトークンを伏せる）、起動は止めない。取り出せた数（`fetched`）を返すようにした。
  - `prefetchProjectSecrets`：プロジェクトの保存・作成・インポートの後に、応答を待たせずに、そのプロジェクトの通知先とコンテキストの秘密情報を
    取り出す。警告はプロジェクトごとに置き換え、続けて保存したときは最後の保存の結果だけを使う。
  - `OnePasswordSecretStore.prefetch`：まとめて取り出している最中の参照を使われたら、その結果を待たせる（別に `op read` しない）。
    まとめて取り出せなかったときの参照ごとの取り出しは、1件ずつ順に行う。
- 画面：「秘密情報を取り出し直す」の結果の件数を、デーモンが返す `fetched` で出すようにした（コンテキストを読めなかった警告で件数がずれないように）。
  説明の文に、保存時に取り出すこと・後から足した秘密情報の扱いを足した（ja・en）。
- 起動の後にコンテキストに足された秘密情報は、取り出す時点を足さず、使うときに取り出すことにした（理由は ADR）。
- 文言：`secret.savePrefetchFailed`・`secret.contextUnavailable`・`secret.contextTimedOut`（ja・en）。
- docs：仕様書（`secrets`・`daemon-lifecycle`・`context`）・利用者向けの文書（`secrets`・`context`）を英語の版も直し、PBI-48 の ADR を置き換えた。

## 確かめたこと

- 回帰テスト：
  - `apps/daemon/src/daemon.test.ts` の「プロジェクトのコンテキストの秘密情報も、まとめて取り出す（PBI-107）」7件。偽の op（`OpRunner`）で
    子プロセスの起動を数え、起動時に継承の鎖の上の層の参照を含めて `op run` 1回で取り出し、チケットのトリアージ・タスクの作成と工程の実行
    （コンテナの MCP の env・ゲートウェイ経由の MCP のヘッダー）・ゲートウェイでの PF の呼び出し（`PlatformCredentials`）で op を呼ばないこと。
    取得の失敗（警告・使うときの取り出し）、トークンを警告に出さないこと、プロジェクトが10件で取得が応答しないとき（同時に4件まで・
    上限の時間で打ち切る・後から返った取得を使わない）、保存・作成・インポートでの取り出し（持っている参照は問い合わせない・足した参照だけ
    取り出す・取り出せない参照の警告と置き換え）、承認を待つ間に保存が終わり、その間のタスクが別に問い合わせないこと、続けて保存したときの警告、
    取り出し直し。
  - `apps/daemon/src/secrets.test.ts`：まとめて取り出している間の同じ参照の使用と、取り出し直しが順に1件ずつであること。
  - `apps/daemon/src/secret-uses.test.ts`：コンテキストの参照の集め方。
  - 修正を戻すと落ちることを確かめた：コンテキストの参照を取り出しの対象から外すと PBI-107 の3件が落ち、`prefetch` を main の版に戻すと
    secrets のテストが落ち、保存の番号の確認を外すと続けて保存したときのテストが落ちる。
- `npm run lint`（終了コード 0）・`npm run typecheck`・`npx vitest run`（1529 件）・`npm run build`・`npx vitest run tests/docs` が通る。
- 画面：自分のブランチを別のポート（4870・4880）と一時的な `SACTY_HOME`（スタブの AI・偽の op・ローカルのコンテキストリポジトリ）で起動した。
  起動時の op の呼び出しは `run op://Work/Ticket/token op://Work/Docs/key op://Work/Wiki/token` の1回（Docs は継承した上の層）。
  「秘密情報を取り出し直す」（3件のうち3件）と、取り出せない参照のある層にコンテキストを変えて保存したときのホームの警告を動画に撮った。
- 本物の 1Password では確かめていない（業務の環境で確かめる手順を PR に書いた）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （DA のセルフレビュー）同じプロジェクトを続けて保存すると、先の取り出しが後から終わったときに新しい警告を上書きする | 保存ごとに番号を付け、最後の保存の結果だけを警告にした（下の PR #117 の指摘で、世代に置き換えた） |
| （PR #117）起動時・取り出し直しの `prefetchSecrets` が、終わったときに警告の全体を置き換えるので、重なった保存の後の警告が消える・解消した警告が戻る | 取り出しを始めるたびに世代を進め、全体とプロジェクトごとに最後に始めた世代を持つようにした。起動・取り出し直し・保存のどれも、後に始まった取り出しがある範囲の警告は書き換えない。回帰テストで、起動側と保存側の終わる順を入れ替えた2通りを確かめ、世代の確認を外すと2件とも落ちることを確かめた |
| （PR #117）30 秒の期限は待つのをやめるだけで、応答しない `git clone` の子プロセスと一時ディレクトリが残る | 期限で `AbortController` を中止し、コンテキストの取得に伝えるようにした。git はプロセスグループで起動し、中止したらグループごと止め、止まってから失敗にする（取得したリポジトリの一時ディレクトリを消す）。回帰テストは、応答しない偽の git（子プロセスも作る）で、子プロセスと一時ディレクトリが残らないことを確かめた。中止を伝えないと・グループごと止めないと落ちることを確かめた |
| （PR #117、PO の DA）止められる取得の git は別のプロセスグループで動くので、Ctrl+C が届かず、取得の途中でデーモンが終わると期限のタイマーも消えて、応答しない git が残る | 取得中の git のプロセスグループを記録し、デーモンが終わるとき（`exit` の後処理と、SIGINT・SIGTERM の `shutdown` の最初）に、すべてグループごと止めるようにした（`fetch-processes.ts` の `spawnStoppable`・`stopFetchProcessesSync`）。回帰テスト（`apps/daemon/src/context-fetch-exit.test.ts`）は、応答しない偽の git で取得を始めたデーモンの代わりを子のプロセス（素の `.mjs`）で動かし、SIGTERM・自分での終了・捕まえない例外の3通りで、git とその子プロセスが残らないことを確かめた。`exit` の後処理を外すと3件とも落ちることを確かめた |
| （PR #117）コンテキストを読めず、ほかに参照が無いと、画面が「使う秘密情報はありません。」と言い切る | API に、読めなかったコンテキストの数（`unreadContexts`）を足し、画面は、読めなかったコンテキストがあれば、その中の秘密情報は確かめていないと出すようにした（ja・en）。回帰テスト（`apps/web/src/i18n/secrets-wording.test.ts`）を足し、文言を戻すと落ちることを確かめた。動画を撮った |
| （PR #117 再レビュー）終了時のテストで、起動待ちがタイムアウトするとデーモンの代わりのプロセスを止めずに抜け、後のテストに響く。全体の初回の実行で2件が 15 秒のタイムアウトになった | 各ケースを `try/finally` で囲み、待ちに失敗しても子のプロセスを止めて回収するようにした。遅かったのは、子のプロセスを jiti（直接の依存ではない）で TypeScript のまま起動し、`context.ts` とその依存をすべて変換していたためと見た。止められる子プロセスの起動と記録を、`node:` のほかを import しない `fetch-processes.ts` に分け、子のプロセスは素の `.mjs` から Node の型の取り除きで読むようにした（jiti を使わない）。取得の git が記録されて止まることは、同じプロセスの中のテストで確かめた。全体のテストを3回続けて実行し、3回とも通ることを確かめた |
