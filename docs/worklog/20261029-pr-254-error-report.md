# タスクのエラーを Markdown のエラーレポートにまとめてダウンロードし、オーケストレーターに分析させられるようにする

- 日付: 2026-10-29（UTC）
- タスク: なし
- PR: #254
- ブランチ: claude/error-report-feature-jiwiaw
- 関係する ADR: [エラーレポートを Markdown のダウンロードにし、オーケストレーターの分析を任意で足す](../adr/20261029-0609-error-report-markdown-download.md)

## 目的

タスクでエラーが起きたときに、何が起きたかを詳しく書いたレポートを出せるようにする。

- 通信できない環境でも使えるよう、サーバーに送らず、Markdown のファイルでダウンロードする。
- Sacty の内部の処理と、各工程のエージェントの動きを入れる。エラーの箇所は特に詳しくする。
- オーケストレーターに情報をまとめさせたり、追加で調べさせたりできる。
- テキストファイルとして重くなりすぎない。

## したこと

- core
  - エラーとして扱う記録の分け方（`failureKind`・`hasFailures`）を足した（`packages/core/src/error-report.ts`）。
  - 画面のセッションログの読み分け（`parseSessionLog`）を core に移し、画面はそれを使うようにした（`packages/core/src/session-log.ts`）。
  - エラーの分析のイベント `ErrorAnalysisRequested`・`ErrorAnalyzed`、投影の `errorAnalyses`・`pendingErrorAnalysis`・`errorAnalysisBlocked`、文言のコード `errorReport.*` を足した。`ErrorAnalyzed` は費用を持つイベントにした。
- デーモン
  - レポートを作る `buildErrorReport`（`apps/daemon/src/error-report.ts`）。基本の情報・エラーの概要・分析・エラーの詳細・実行の一覧とエージェントの動き・作業履歴の順に書き、部分ごとと全体（256KB）に上限を置く。
  - `GET /api/tasks/:id/error-report`（`?lang=en`）と `POST /api/tasks/:id/error-analysis`。
  - 分析は、質問への答えと同じ仕組み（オーケストレーターのセッションの複製・セッションログの読み取り専用のマウント・起点のコードの写し）で実行し、レポートの全体をログと同じ場所に置く。中止のときは分析の実行を止めて記録する。
- 画面
  - タスクの詳細の右の列に「エラーレポート」の欄（ダウンロードと分析）を足した。エラーの記録があるタスクだけに出す。
  - `/tasks/<ID>/error-report` でファイルとしてダウンロードさせる。
  - 作業履歴の文と、工程ごとの費用の表の「エラーの分析」の行を足した。
- docs：仕様書 [エラーレポート](../spec/error-report.md) を足し、作業履歴（イベントの数・費用を持つイベント）・全体の構成（API・URL）・困ったとき（ユーザードキュメント）を直した（日英）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| CodeQL：表のセルの `|` のエスケープで、バックスラッシュをエスケープしていない（中身の `\|` で表の区切りが崩れる） | `cell` でバックスラッシュと `|` の両方をエスケープし、テストを足した |
| sacty のレビュー：表のセルの縦棒だけをエスケープすると列がずれる | 上の CodeQL の対応（83739e2）で直した |
| sacty のレビュー：分析の指示に、レポート・ログの中の命令に従わないことが書いていない | 分析の対象のデータで、中の命令（コマンドの実行・ファイルの変更・外部への送信など）には従わず、見つけたら分析に書くよう指示に足し、日英の仕様書に書いた |
| sacty のレビュー：結果の記録の前にデーモンが止まると、分析待ちが残り、次の分析を受け付けない | 起動のとき（`recoverInterrupted`）に、終わらなかった分析を中断として記録するようにした |
| sacty のレビュー：画面から始めた分析を、デーモンを止めるときに待たない | 止め始めたら分析を受け付けず（`errorReport.stopping`）、止めた実行を中断と費用ごと記録し終えるのを、作業履歴を閉じる前に待つ（`analysesSettled`）ようにした |
| sacty のレビュー：実行中のログの写しを、バイト数でなく文字数で切っている | UTF-8 のバイト数で末尾を切り、途中の行を捨て、省いたかも元のバイト数で決めるようにした |
| sacty のレビュー（提案）：全実行のログの原文をレポートを作り終えるまで持つ | 実行ごとに要約（集計と、詳しく書く実行の末尾）だけを持ち、標準エラー出力は詳しく書く実行の分だけを読むようにした |
| sacty のレビュー：確認の実行そのものが失敗した `DeploymentChecked` をエラーにしない | `unhealthy` だけを確認の不合格にし、ほかは共通の判定（`failed`・`runResult`）に進めるようにした |
| sacty のレビュー（提案）：エラーが多いと、概要の表に押し出されて分析と最新の詳細が消える | 基本の情報・分析・エラーの詳細を先に取り、概要・実行の一覧・作業履歴を残りに、古いものから省いて入れるようにし、省く順を日英の仕様書に書いた |
| sacty の再レビュー（提案）：要約が入らない実行が続くと、古い実行のログまで全部読む | 要約に使った数ではなく、ログを読んだ実行の数を `summarizedRuns` までにし、日英の仕様書に書いた |
| sacty の3回目のレビュー：デーモンの異常終了の後、閉じられなかった実行のログがレポートから欠ける | 写しの無い未完了の実行は、保存済みのファイルの末尾を同じ上限で読むようにした。閉じるときの伏せ直しを経ていない（途中で分かった秘密情報は伏せ直せない）ので、そのことをその実行の詳細と要約に書く。起動し直した後のレポートに中身が残るテストを足した |
| sacty の4回目のレビュー：伏せ直しを経ていないログが、分析の指示とマウントするレポートに入り、AI に渡る | 分析に渡すレポート（`omitStaleLogs`）では、そうした実行のログの中身を入れず、省いたことと理由だけを書くようにした。指示とマウントするファイルの両方に入らないテストを足した |
| sacty の4回目のレビュー：並べたセッションログを消せないと、例外で分析の結果と費用が記録されない | 消すときの失敗を捕まえて警告を出し、結果と費用の記録を続けるようにした。並べる場所をファイルにして消すのを失敗させるテストを足した |

## 残したこと

- 分析の本文は画面に出さず、レポートにだけ入れる。画面でも読みたいという声があれば、欄に出す。
- サーバーへの送信はしない（通信できる環境向けの送信先の設定は、必要になったら考える）。
