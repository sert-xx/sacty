# 最終レビューの作業領域の写しに、実装の PR に入る要求要件・設計の成果物を入れ、リポジトリ全体の検査を PR と同じ中身で行わせる

- 日付: 2026-11-01（UTC）
- タスク: PBI-262
- PR: なし
- ブランチ: feat/issue-262-sacty-docs-in-verify-copy
- 関係する ADR: [最終レビューの作業領域の写しに、実装の PR に入る要求要件・設計の成果物を PR のコミットの内容で入れ、リポジトリ全体の検査を PR と同じ中身で行わせる](../adr/20261101-0353-include-pr-documents-in-final-review-copy.md)

## 目的

実務での実証実験で、Sacty が PR に入れる `docs/sacty/<タスクの短い ID>/` の成果物が、最終レビューの作業領域の写しには無いため、`prettier --check .` のようなリポジトリ全体の検査が、写しでは通り、PR の中身では落ちた（S4 の試行 1・2、S6、S7 の計 4 回）。
毎回、人が PR で気づいて差し戻し、`.prettierignore` にタスクごとに行を足して直った。#260 で最終レビューの指示に「PR の中身では未確認なら人の確認へ回す」と足したが、合格のままで差し戻しは減らなかった。

人が決めた方針「写しに含めて検査」に従う。最終レビューの写しに PR に入る成果物を入れ、PR と同じ中身で検査する。落ちれば実装が直す。

受け入れ条件の要点：

- 最終レビューの写しに、PR のコミットと同じ内容で成果物が入る。成果物のせいで落ちる検査が不合格になる。範囲・過剰さの判定に成果物が混ざらない。回帰テストがあり、修正を戻すと落ちる。
- 実装の工程の作業領域にも入れるか、#260 の指示の整理、範囲の判定の守り方、直し方の指示は、既存のコードと仕様の文脈から決めて ADR に書く。
- 範囲に入れないもの：成果物の整形そのものを sacty が合わせること、対象のリポジトリの設定を sacty が書き換えること。

## したこと

- `copyWorkingTree`（`apps/daemon/src/repository.ts`）に、任意の `include`（コミットとパスの一覧）を足した。写した後、gitDir（退避したメタデータ）のそのコミットにあるファイルの内容を、写しに書く。
  - 写しにあった同じパスのファイルは置き換え、コミットに無いパスは写しからも消す（PR のコミットを作るときの `keep` と同じ扱い）。
  - 途中のディレクトリの場所がシンボリックリンクやファイルなら、消してから書く（作業領域はエージェントが書き換えられるので、リンクの先に書いて写しの外を書き換えない）。パスは `validPath` で確かめ、`include` には gitDir を要る。
  - 内容は既存の `readFile`（通常のファイルだけ・1 MiB まで・UTF-8 のテキストだけ）で読む。
- `stepDocumentsForReview`（`apps/daemon/src/service.ts`）：最終レビューの前に作った実装の PR のコミット（`pullRequestCi.commit`）と、要求要件・設計の PR のファイルのパス（PR のコミットを作るときに引き継ぐものと同じ一覧）を返す。タスクブランチが無い・既存の PR を引き継ぐ・要求要件・設計の PR が無い・PR のコミットがまだ無いときは返さない。コミットが退避したメタデータに無ければ取得し（`fetchCommits`）、取得できなければ警告だけ出して返さない（最終レビューは止めない）。
- `verify` が、返ってきた `include` を `runGuardian` に渡し、最終レビューの指示（`buildFinalReviewPrompt` の `stepDocumentsIncluded`）にも伝える。`runGuardian` は、`include` があるときだけ写しに入れる。実装の作業領域、変更の差分、範囲の照合、文書だけの差分の判定、監査や指摘の戻し先の判断の写しには入れない。
- `pullRequestContentLines`（`apps/daemon/src/prompts.ts`）を、写しに入れたかで分けた。
  - 入れたとき：検査は PR と同じ中身で実行される。成果物が原因の失敗も不合格にする（`humanChecks` に回さない）。成果物は実装の変更ではなく差分に出ないので、範囲・過剰さ・観点の判定に含めず、中身をレビューしない。成果物で検査が落ちたら、指摘に直し方を書く（書式は直させず、検査の設定をリポジトリの方針に合わせて直させる。方針が無ければ置き場所をまとめて対象外にし、タスクの ID ごとには足さない。設定の直しは範囲外・過剰としない。設定を確かめるだけのテストは足させない）。
  - 入れられなかったとき：#260 で足した指示のまま（写しで通った検査は未確認として人の確認に回し、写しで失敗した検査は不合格）。
  - 成果物を PR に足さないタスクには、これまでどおり節を入れない。
- 仕様書（`docs/spec/tasks-and-steps.md`・`.en.md`）と、ユーザードキュメント（`docs/user/tasks.md`・`.en.md` の「テスト（検証）のコマンド」）を直した。ADR を足した。

## 確かめたこと

作業は、リポジトリの外の worktree（`sacty-wt-docs-copy`）で、`mise x --` の Node.js 26.12.1 を使って行った。

- `npx vitest run apps/daemon/src/repository.test.ts`：全件通る。追加したテスト（実際の git で）：
  - `include` を渡すと、成果物のファイルがコミットの内容で写しに入り、実装の作業領域は書き換わらない。作業領域に同じパスのファイルがあれば置き換え、コミットに無いパスは消す。`include` に無いパスのファイルは残す。途中のディレクトリがホストのディレクトリへのリンクでも、リンクの先に書かない。不正なパス・gitDir の無い `include` は受け付けない。
  - 行末に空白があってはいけない、という検査（`node` の小さなスクリプト）が、`include` なしの写しでは通り、成果物を入れた写しでは落ちる（`prettier --check .` が PR だけで落ちた状況の再現）。
- `npx vitest run apps/daemon/src/daemon.test.ts -t "成果物を PR に足すタスク"`：要求要件・設計の PR を経て実装の PR をドラフトで作り、CI を待った後の最終レビューの写しに、成果物のパスと PR のコミットを `include` で渡す（写す元は実装の作業領域のまま）。指示は、写しに入れた文言になり、「PR の中身で通るかは未確認」を含まない。コミットを取得できないときは、`include` を渡さず、成果物が無い写しの文言（未確認として人の確認に回す）で最終レビューを続ける。
- `final-review-human-checks.test.ts`：写しに入れた指示の文言（PR と同じ範囲で実行される・成果物が原因の失敗も不合格・範囲・過剰さの判定に含めない・書式を直させない・方針に合わせる・まとめて対象外にする・タスクごとに足さない・設定を確かめるだけのテストを足させない）、テストのコマンドの有無にかかわらず入ること、置き場所をオーケストレーターが決めたディレクトリにすること、成果物を PR に足さないタスクには入らないこと。
- 修正を戻すと落ちることを確かめた：`runGuardian` が `include` を写しに渡さない・`copyWorkingTree` が `include` を無視する・途中のリンクを消さない、の 3 つで、それぞれのテストが落ちる。
- `npx biome check .`・`npm run typecheck`・`npx vitest run tests/docs`：通る。`npx vitest run` 全体：環境のために落ちる `question-form.browser.test.ts` と `install-security-tools.test.ts`（2 件）を除いて通る（3167 件）。この 2 つは、#260 の作業履歴にも main で落ちると書いてあるもの。
- 確かめられなかったこと：ゴールガーディアン（LLM）が、指示のとおりに成果物で落ちた検査を不合格にし、直し方を指摘に書くか。実際のタスクで動かして確かめる必要がある。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| 実装の作業領域にも入れないと、実装のエージェントは、最初の最終レビューまで成果物で落ちる検査に気づけない | 入れると、差分・範囲の照合・文書だけの判定・ベースブランチの取り込みに、sacty が置くファイルが実装の変更として混ざる。最終レビューの指摘で直る（やり直しの上限の中）。ADR に書いた |
| コミットの取得に失敗したとき、黙って成果物が無い写しになると、F9 が再発して気づけない | 警告を出し、指示を #260 の文言に戻す。写しで通った検査は未確認として人の確認に出るので、見落とさない |
| 作業領域の途中のディレクトリがリンクだと、リンクの先（ホスト）に成果物を書いてしまう | 書く前に、途中のリンク・ファイルを消す。テストあり（修正を戻すと落ちる） |
| 作業領域に同じパスのファイルがあるとき、PR に入らない内容で検査してしまう | `keep` と同じく、コミットの内容で置き換え、コミットに無いパスは消す。テストあり |
| 成果物のパスの一覧が、PR のコミットを作るときに引き継ぐ一覧とずれると、検査する中身が PR と違う | 同じ式（要求要件・設計の PR のファイルのパスの重複を除いた一覧）にした |
| 最終レビューの再開で、古い PR のコミットを使う | PR のコミットは、作業領域が変わるたびに作り直す記録（`pullRequestCi`）と同じ。実装をやり直すと記録が消え、新しいドラフトの PR のコミットになる |
| 監査・指摘の戻し先の判断など、ほかの `runGuardian` の呼び出しまで写しが変わる | `include` は、最終レビューの `verify` だけが渡す（既定は入れない） |
| 成果物が範囲・過剰さの判定に混ざると、設定の直しまで過剰と判定される | 指示で、成果物を判定に含めないこと、検査の設定の直しは範囲外・過剰としないことを伝える。ただし、設定を確かめるだけのテストは足させない |

## 残したこと

- 実装の作業領域で、実装のエージェントが成果物で落ちる検査を、最終レビューの前に確かめられるようにすること(決定 2 のとおり、範囲の判定を誤らせるので入れていない)。
- ゴールガーディアンが指示どおりに不合格にするかは、実際のタスクで確かめる。
- 実装の PR を引き継ぐタスクと、要求要件・設計を PR で承認しないタスクは、成果物を PR に足さないので対象外。
