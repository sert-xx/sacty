# 作業履歴

タスクごとの詳細な記録を残す。方針は [docs の入口](../README.md) を参照。

## ファイル名

```text
<日付>-<スラッグ>.md
```

- 日付：`YYYYMMDD`。**UTC** で、そのタスクの PR を作った日（PR が無いタスクは作業を始めた日）。
  過去のタスクを後から起こすときは、PR の作成日（`gh pr view <番号> --json createdAt`）。
- スラッグ：英小文字・数字・`-` だけ。PBI があるタスクは `pbi-<番号>-` で始める（例 `pbi-80-docs-structure`）。
  PBI が無いタスクは、PR があれば `pr-<番号>-` で始める。どちらも無ければ内容がわかる短い名前にする。
- 1つのタスク（PBI・PR）に1ファイル。同じ PR の中のレビューの対応・やり直しは、同じファイルに書き足す。
  別の PR で続きをしたら、新しいファイルを足す。
- すべての作業履歴を `docs/worklog/` の直下に置く（サブディレクトリに分けない）。
- 例：`20261014-pbi-80-docs-structure.md`

ファイル名の規則は `tests/docs/docs.test.ts` で確かめる。

## 本文のひな形

```markdown
# <タスクの内容を1文で>

- 日付: YYYY-MM-DD（UTC）
- タスク: PBI-<番号> | なし
- PR: #<番号> | なし
- ブランチ: <ブランチ名>
- 関係する ADR: [<タイトル>](../adr/<ファイル名>) | なし

## 目的

何のためのタスクか。受け入れ条件の要点（docs/pbi の内容を丸写しせず、要点を自分の言葉で）。

## したこと

変えたことを、まとまりごとに。変えたファイルの場所や、決めたことの理由（大きな方針は ADR に書いてリンクする）。

## 確かめたこと

実行したコマンドと結果（lint・typecheck・テスト・build・手で確かめた手順）。確かめられなかったことと、その理由。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| <指摘の要点> | <直したこと、または直さなかった理由> |

## 残したこと

このタスクではしなかったこと・後の課題（無ければ「なし」）。
```

- 秘密の値・個人の情報・特定の組織の内部を指す語は書かない。
- PR がマージされた後は、実装と矛盾しても直さない（今の振る舞いは仕様書に書く）。

### 先頭の項目の書き方

- 先頭の項目（`日付`・`タスク`・`PR`・`ブランチ`・`関係する ADR`）は、それぞれ1行だけ、`- <項目>: <値>` の形で書く
  （値の前後に空白を足さない）。
- `日付` は、ファイル名の日付と同じ日付を `YYYY-MM-DD（UTC）` で書く。
- `タスク` は `PBI-<番号>` か `なし`。ファイル名が `pbi-<番号>-` で始まるときは、その番号の `PBI-<番号>`。
- `PR` は `#<番号>` か `なし`（PR を作る前は `なし` にし、作ったら書き足す）。ファイル名が `pr-<番号>-` で始まるときは、
  その番号の `#<番号>`。
- 逆に、本文の `タスク` が `PBI-<番号>` ならファイル名は `pbi-<その番号>-` で、`タスク` が `なし` で `PR` が `#<番号>` なら
  `pr-<その番号>-` で始める。どちらも `なし` なら `pbi-`・`pr-` で始めない。

これらは `tests/docs/docs.test.ts` で確かめる。
