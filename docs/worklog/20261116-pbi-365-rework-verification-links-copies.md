# 実装の出し直しの検証・PR の本文のコンテナのパス・調査の工程への写しを直す

- 日付: 2026-11-16（UTC）
- タスク: PBI-365
- PR: なし
- ブランチ: feat/pbi-365-rework-verification-links-copies
- 関係する ADR: なし

PBI-366・PBI-367 も、この PR に入れた（3つとも小さく、互いに独立している）。

## 目的

複数のリポジトリを指定する機能を sacty 自身に実装させたときに、実物で見つかった次の3つを直す。

- 差し戻しを受けて出し直した PR の作業の記録に、直す前のコードでの検証の結果（「前回の実装では…通った」）が、今回の結果のように書かれた（3つの PR で繰り返した）。実装の指示に、出し直しのたびに検証をやり直す決まりが無かった（PBI-365）。
- sacty が作った PR の本文に、コンテナの作業領域のパスへのリンク（`[README.md](/workspace/README.md)`）が入った。GitHub では開けない（PBI-366）。
- 進め方が「調査だけ」のタスクでは、複数指定したリポジトリの写しが工程に渡らなかった（PBI-367）。

## したこと

- PBI-365：実装の直しの指示（`implementReworkLines`。前の実装の説明を添える実行）に、`REWORK_VERIFICATION_LINE` を足した（`apps/daemon/src/prompts.ts`）。
  提出の前の検証を直しの後のコードで実行し直すこと、実装の説明とリポジトリの文書に書く検証の結果は今回のものだけにすること、前の回の結果が文書に残っていれば書き換えること、実行しなかった検証はそう書くこと。
  あらゆるリポジトリの対象に渡る指示なので、言語・ツール・文書の名前を挙げていない。最初の実行の指示は変えていない。
- PBI-366：`apps/daemon/src/pr-body-links.ts` の `withoutWorkspaceLinks` を足し、PR の本文を組み立てる1か所（`service.ts` の `pullRequestBody`。要求要件・設計の PR と実装の PR の、作成と更新のすべてが通る）で、長さの上限の後に呼ぶ。
  リンクを外して表示の文字を残し、表示の文字からパスが分からなければ、リポジトリのルートからのパスをインラインのコードで添える。コードブロック・インラインコードの中と、ほかのリンクは変えない。
  はじめ正規表現で書いたが、角括弧やバッククォートが続く長い行で、時間が行の長さの二乗になった（20,000 文字で 2.6 秒）。行を1回走査する形に書き直し、表示の文字とリンク先を探す長さに上限を置いた。
  リンクを外すと必ず短くなる（`[`・`](`・`/workspace/`・`)` の 15 文字が消え、足すのは括弧とバッククォートの 4 文字まで）ので、長さの上限の後でよい。
- PBI-367：複数指定のタスクに写しを渡す工程の条件（`requirements`・`design`・`split`）が `service.ts` の 11 か所に書かれていたのを、`REPOSITORY_COPY_STEPS` と `copiesRepositories` にまとめ、`investigate` を加えた。
  写しの用意・失敗のときの停止と再開・片付けは、要求要件・設計・分割と同じ仕組みをそのまま通る。
  調査の指示（`buildPrompt` の `investigate`。調査だけと、前段の調査の両方）に、写しの場所・ブランチ・コミットを渡す。リポジトリを選ぶ前（作業領域に写しを並べる）でも、「プロジェクトのコンテキストをもとに」ではなく、コードを読んで調べさせる。
- 仕様書（日英）：`docs/spec/tasks-and-steps`（写しを渡す工程）、`docs/spec/approval`（直しの指示・本文のリンク）。利用者に見える設定・画面・コマンドは変えていないので、ユーザードキュメントは直していない。
