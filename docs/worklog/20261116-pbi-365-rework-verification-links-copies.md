# 実装の出し直しの検証・PR の本文のコンテナのパス・調査の工程への写しを直す

- 日付: 2026-11-16（UTC）
- タスク: PBI-365
- PR: #395
- ブランチ: feat/pbi-365-rework-verification-links-copies
- 関係する ADR: なし

PBI-366・PBI-367 も、この PR に入れた（3つとも小さく、互いに独立している）。

## 目的

複数のリポジトリを指定する機能を sacty 自身に実装させたときに、実物で見つかった次の3つを直す。

- 差し戻しを受けて出し直した PR の作業の記録に、直す前のコードでの検証の結果（「前回の実装では…通った」）が、今回の結果のように書かれた（3つの PR で繰り返した）。実装の指示に、出し直しのたびに検証をやり直す決まりが無かった（PBI-365）。
- sacty が作った PR の本文に、コンテナの作業領域のパスへのリンク（`[README.md](/workspace/README.md)`）が入った。GitHub では開けない（PBI-366）。
- 進め方が「調査だけ」のタスクでは、複数指定したリポジトリの写しが工程に渡らなかった（PBI-367）。

## したこと

- PBI-365：実装の直しの指示（`implementReworkLines`。前の実装の説明を添える実行）に、`REWORK_VERIFICATION_LINE` を足した（`apps/daemon/src/prompts.ts`）。
  提出の前の検証を直しの後のコードで実行し直すこと、実装の説明とリポジトリの文書に書く検証の結果は今回のものだけにすること、前の回の結果が文書に残っていれば書き換えること、実行しなかった検証はそう書くこと。
  あらゆるリポジトリの対象に渡る指示なので、言語・ツール・文書の名前を挙げていない。最初の実行の指示は変えていない。
- PBI-366：`apps/daemon/src/pr-body-links.ts` の `withoutWorkspaceLinks` を足し、PR の本文を組み立てる1か所（`service.ts` の `pullRequestBody`。要求要件・設計の PR と実装の PR の、作成と更新のすべてが通る）で、長さの上限の後に呼ぶ。
  リンクを外して表示の文字を残し、表示の文字からパスが分からなければ、リポジトリのルートからのパスをインラインのコードで添える。コードブロック・インラインコードの中と、ほかのリンクは変えない。
  はじめ正規表現で、次に行を1回走査する自前の解析で書いたが、レビューの指摘で Markdown のパーサーに置き換えた（下の「レビューの指摘と対応」）。
  パーサーは、記号が長く続く本文で時間がかかる（本文の上限 65,000 文字で、`>` の連続は 3.7 秒、`*a` の連続は 12 秒、`1. ` の連続は 29 秒、`+ ` の連続は 52 秒。ふつうのリンクが上限まで並ぶ本文は 0.05 秒）。そこで、作業領域へのリンクがありえない本文（`](` が無い、または、作業領域のパス・バックスラッシュ・文字参照のどれも無い）は解析しない。解析に回る本文で、かつ記号が上限いっぱいまで続くと、PR の作成・更新のたびに1回、数秒〜数十秒かかる（その間、デーモンのほかの処理は待つ）。
  置き換えは本文を長くしない（元のリンクより長くなる置き換えはしない）ので、長さの上限の後でよい。はじめ「リンクを外すと必ず短くなる」と書いたが、誤りだった（下の「レビューの指摘と対応」の2回目）。
- PBI-367：複数指定のタスクに写しを渡す工程の条件（`requirements`・`design`・`split`）が `service.ts` の 11 か所に書かれていたのを、`REPOSITORY_COPY_STEPS` と `copiesRepositories` にまとめ、`investigate` を加えた。
  写しの用意・失敗のときの停止と再開・片付けは、要求要件・設計・分割と同じ仕組みをそのまま通る。
  調査の指示（`buildPrompt` の `investigate`。調査だけと、前段の調査の両方）に、写しの場所・ブランチ・コミットを渡す。リポジトリを選ぶ前（作業領域に写しを並べる）でも、「プロジェクトのコンテキストをもとに」ではなく、コードを読んで調べさせる。
- 仕様書（日英）：`docs/spec/tasks-and-steps`（写しを渡す工程）、`docs/spec/approval`（直しの指示・本文のリンク）。利用者に見える設定・画面・コマンドは変えていないので、ユーザードキュメントは直していない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| [要修正] `pr-body-links.ts`：行ごとの自前の解析が Markdown の構文と食い違い、本文を壊す（括弧を含むパス `setup(ja).md` が途中で切れる、複数行のインラインコードや引用の中のコードブロックが書き換わる）。Markdown のパーサーで範囲を特定して置き換える | 直した。リンク・画像の範囲を `mdast-util-from-markdown`（Web の依存として既にロックファイルにある 2.1.0。デーモンの依存に足した）で決め、元の文字位置の範囲だけを置き換える。括弧・空白・バッククォートを含むパス、複数行のインラインコード、引用・箇条書き・字下げのコードブロック、打ち消した角括弧、CRLF を回帰テストに足した。書き直しの途中で、リンクの中の作業領域への画像（`[![図](/workspace/a.png)](/workspace/docs/a.md)`）が残ることに気づき、これも外すようにした |
| （2回目）[要修正] `service.ts`：リンクの変換は必ずしも本文を短くしない。バッククォートが続くパスでは、コードの書式の囲みが増え、65,000 文字の本文が 115,375 文字になる。PR の作成・更新が長さの上限で失敗する | 直した。置き換えが元のリンクより長くなるときは、パスを添えずに表示の文字だけにし、表示の文字も無ければ、そのリンクを変えない。返す本文は、渡した本文より長くならない。バッククォートが続くパスが上限いっぱいに並ぶ本文で、長くならないことをテストに足した。「必ず短くなる」という説明（コードのコメント・この記録・PR の説明）を直した |
| （2回目）[要修正] `pr-body-links.ts`：事前の判定が、Markdown の解釈の前の文字列で作業領域のパスを判定するので、`[手順](/work&#115;pace/docs/a.md)` のような有効なリンクが残る | 直した。リンク先を自前で読む判定をやめ、パーサーが作業領域へのリンクと解釈しうる本文は、すべて解析に回す（`](` があり、作業領域のパス・バックスラッシュ・文字参照のどれかがある本文）。リンク先の文字は、バックスラッシュの打ち消しと文字参照のほかは書いたままに読まれるので、この条件で見落としは無い。文字参照（10進・16進・名前）とバックスラッシュのリンク先を回帰テストに足した |
| （2回目）[提案] `pr-body-links.ts`：対象のリンクを含み、記号が上限近くまで続く本文は、同期の解析で約8〜9秒かかり、デーモンのほかの処理も待つ。解析を worker thread などに分けることを検討する | この PR では直していない。後続に回す案として返信し、人に確認中（決まっていない）。理由：デーモンには別スレッド・別プロセスで処理を分ける仕組みがまだ無く、デスクトップ版の同梱（asar）で別スレッドのファイルを読めるかの確認も要るので、この PR の範囲（PR の本文のリンクを外す）を超える。今の状態は、仕様書とこの記録に書いた |

## 残したこと

- PR に投稿するレビュー・コメントの本文の、コンテナのパスへのリンク（今回は PR の本文だけ）。参照形式のリンクの定義・HTML のリンク。
- PR のレビューが、古い検証の結果の記載を指摘すること（既定のスキルの変更になる）。
