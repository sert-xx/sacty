# デーモンのテストの「固定の時間を待つ」書き方を、条件を待つ形に置き換える（2：実装の工程のテスト）

## 目的

デーモンのテストの、処理の完了を固定の時間で待つ書き方を、条件を待つ形に置き換える（PBI-376）。背景・受け入れ条件・最初に数えた結果は、[1 つ目の作業履歴](20261117-pbi-376-fixed-waits-daemon-steps.md)にある。

この作業履歴は、2 つ目の PR（`apps/daemon/src/daemon-implement.test.ts` の 51 か所）のもの。

## したこと

`daemon-implement.test.ts` の、固定の時間を待つ 51 か所のうち、48 か所を置き換え、何も起きないことを見る 3 か所を、理由を書いて残した。本体のコードは変えていない。テストの期待値は変えていない（1 か所、確認を足した。下）。

置き換えた 48 か所：

- 待たずに送る処理の終わりを待っていた所（5 ミリ秒の `settle`・`settleAsks` のうち 37 か所と、100 ミリ秒・150 ミリ秒の各 1 か所）：送る処理が、すべて終わるまで待つ（`noticesSettled`）。
  - 対象は、レビューが止まったことの PR への知らせと、順に処理するもの（人に確かめてほしいことの PR への知らせ・指摘への返信の投稿）。
  - これらは、タスクの状態が変わったときに同期で登録され、終わると登録が消える。登録が無ければ（送るものが無い）、すぐに戻る。そのため、「書かれる」ことも、「書かれない」ことも、時間に頼らずに確かめられる。
  - 本体に、これを待つ口は無い。本体を変えないために、テストの補助（`apps/daemon/src/testing/daemon.ts`）から、登録の表（`TaskService` の private の `stopNotices`・`serialTails`）を直接見る。表の名前が変わったら、補助が例外で落ちる（黙って通らない）。
  - 続けて 2 回待っていた所（1 か所）は、1 回にした。
- 処理が、ある所まで進むのを待っていた所（6 か所）：その所まで進んだことが見える条件を待つ（`waitFor`）。
  - やり直しの前の待ちに入ること（やり直しの記録が 1 件になる）。
  - レビューの投稿が記録されること（3 か所）。
  - 知らせの投稿が始まること。
  - 投稿の通信が始まること（通信の偽物が、始まったら合図を出す）。
- マイクロタスクだけで進む処理を待っていた所（2 か所。放した通信の続き・順番待ちへの登録）：イベントループを一巡させる（`apps/daemon/src/testing/wait.ts` に足した `loopTurn`）。上の、100 ミリ秒を待っていた所も、一巡させてから、送る処理の終わりを待つ。
- 投稿の間隔（60 ミリ秒）を待っている間に、制限を記録する所（1 か所）：時計を差し替えた（Vitest の偽のタイマー。その部分だけ）。本物の時計では、10 ミリ秒の待ちが負荷で延びて、制限を記録する前に間隔の待ちが明けることがある。間隔を待っている最中であることの確認（待ちのタイマーが 1 つある）を足した。

残した 3 か所（`idleFor`。時間は変えていない）：

- 「先の処理が検索の最中に…」（5 ミリ秒）：先の処理が検索の最中の間に、後の処理が投稿していないことを見る。
- 「…一時停止して再開する…」（5 ミリ秒）：先の検索が終わっていない間に、通知を書いていないことを見る。
- 「…確認が終わるまで返らない」（10 ミリ秒）：停止の確認が終わる前に、一時停止が返っていないことを見る。

残した理由：どれも、処理を止めてある（合図を出すまで進まない）間に、何も起きないことを見るための猶予で、処理の完了は待っていない。猶予が環境に対して短くても、テストは誤って落ちない。前提（処理が止めた所に入った）は、合図で確かめた後に置いている。

数に入れていないもの：終わらない通信を、3 秒で諦める `setTimeout`（1 か所）。待ちではなく、テストが終わらなくなるのを防ぐ上限なので、そのままにした。

触っていないが、時間に頼っている所（この PBI の対象の形ではない）：知らせの期限（50 ミリ秒・800 ミリ秒）を、本物の時計で待つテストがある。そのうち 1 つは、経過した時間が上限より短いことも確かめている。時計の差し替えには、本体の期限（`AbortSignal.timeout`）を差し替える口が要るので、この PR では触っていない。

自分で決めたこと（人の確認は、まだ）：

- 送る処理の終わりを、本体に口を足さずに、テストの補助から private の表を見て待つ。
- 続けて 2 回待っていた所を、1 回にする。

## 確かめたこと

PR を作る前のコードで実行した結果。

- 置き換える前に落ちることの再現：置き換える前の `daemon-implement.test.ts` を、6 並列で各 10 回（計 60 回）実行して、落ちた回は 0。再現できなかった（このファイルの 5 ミリ秒の待ちの多くは、マイクロタスクだけで進む処理を待っていて、待ちが明ける前に済む）。
- 置き換えた後：同じ条件（6 並列で各 10 回、計 60 回）で、落ちた回は 0。
- 全テスト（`npx vitest run --no-file-parallelism`）を、CPU に負荷をかけた状態（CPU を使い切るプロセスを 5 つ動かす。12 コアのマシン）で 2 回実行して、2 回とも 4962 件が通った（1 件は以前からの skip。1 回 261〜277 秒）。
- `npm run lint`・`npm run typecheck`：通った。`npx vitest run tests/docs`：通った。
- 置き換えたテストが、本体の誤りを見つけること（`apps/daemon/src/service.ts` の 1 行を消して実行し、元に戻した）：
  - セキュリティのタスクでは PR に書かない、という行を消す → 「人に確かめてほしいことを PR に知らせる」の 1 件が落ちる（`expected [ … ] to have a length of +0 but got 1`）。
  - 解消が、投稿の最中の知らせを待つ行を消す → 「レビューが止まったことを…知らせる」の 4 件が落ちる。
  - 投稿の間隔を待つ行を消す → 時計を差し替えたテストが落ちる（待ちのタイマーが無い）。
  - 間隔を待った後に制限を確かめる行を消す → 同じテストが落ちる（`expected { value: 2 } to be 'limited'`）。
