# 実装の PR の指摘の戻し先を、決定の重さで分け、局所の設計の直しを実装の PR に入れる

- 日付: 2026-11-21（UTC）
- タスク: PBI-446
- PR: なし
- ブランチ: sacty/task-1c12956b
- 関係する ADR: [PR の指摘の戻し先は、決定の重さで分け、設計に戻すのは方針の変更だけにし、局所の設計の直しは実装の PR に入れる](../adr/20261121-0241-rework-target-by-decision-weight.md)

## 目的

実装の PR の指摘の戻し先を、「方針の変更は設計、局所の変更は実装」に分ける。
実装で直す回は、実装が出した設計の直しを sacty が承認済みの設計に反映し、同じ実装の PR に入れる（承認は実装の PR のマージで兼ねる）。
設計に戻した回は、実装の PR に知らせを1通投稿する。
採らなかった案は、変更の申し出（人が画面で1件ずつ認める）で直すこと。

## したこと

- 基準：実装の PR の2経路（レビューの子タスクの `rework`、工程のエージェントの判断）で、方針の変更だけを設計に戻す。
  - 局所の変更は実装。1つでも方針の変更があれば全部を設計に戻す。迷えば実装に倒し、セキュリティ・認可・保存するデータの形・移行に触れる指摘は迷えば設計に戻す。
  - テスト観点の文言だけの変更は実装、入力・期待結果の中身を変える・観点を足す・消す指摘は設計。人の指摘が戻し先を明示していれば従う。
  - 理由の書式は「決定を変えない／変える（局所）／変える（方針）：…」。
  - 変えないもの：要求要件の決定を変える指摘の戻し先、要求要件・設計の PR の指摘の基準、直しに入る前の提案の選り分け（PBI-436・440）、`cause` の選択肢、指摘の重み（PBI-358）、変更の申し出の条件と画面。
- 設計の直し（`sacty-design-edit`）：実装に戻した回で、設計が承認済みのときだけ、実装の指示に出し方（置き換えの形）を足す。
  - 反映しない直しの検査（指摘の ID・`sensitive`・`before` の場所と数・冒頭の3節とテスト観点・観点の ID と欄・見出し・文字数と件数・秘密情報と内部のパス・変更の申し出との同居・ブロックが読めない）。反映しない直しは、理由を残して実装の提出は続ける。
  - イベント `DesignEdited`（`packages/core`）を足した。投影は、承認済みの設計・設計の出力・テスト観点を置き換え、設計のセルフレビューと出典の分類を記録なしにする。観点の ID・`implementHistory`・`implementBase` は変えない。
  - 実装の PR のコミットで、設計のファイルに置き換えを当てる。PR の本文に「設計の直し」を足す。マージで設計のファイルを承認済みの設計に読み戻さない。
  - 作業履歴の画面に、反映した件数と反映しなかった件数の行を足した（日英）。
- 設計に戻した知らせ（`rework-notice.ts`）：1回の差し戻しにつき1通。目印 `<!-- sacty-rework-notice:<タスク ID>:<回> -->` で二重の投稿を防ぐ。新しい版が記録した design の判断の後だけ投稿する。PR の指摘の取り込みと、レビューの見守りの返信の数え方から外す。
- 前の版には戻せない：前の版のデーモンは `DesignEdited` を読めず、起動できない。前の版で読める保存の形にはしていない。
- 文書：`docs/spec/approval(.en).md`・`docs/spec/tasks-and-steps(.en).md`・`docs/user/tasks(.en).md`・ADR（2026-11-01 の ADR を置き換え。ファイル名とステータスを変え、作業履歴のリンクを直した）。

## 確かめたこと

- 基準の文：`apps/daemon/src/prompts-design-weight.test.ts` で、実装の PR の2経路（工程のエージェントの指示・レビューの子タスクの指示）に同じ基準が入り、要求要件・設計の PR の基準は起点のまま（重さの文・人の明示に従う文が入らない）ことを確かめた。
- 設計の直しの検査と適用：`apps/daemon/src/design-edit.test.ts` で、反映する直し（本文・観点の文言・前の直しの after に重なる before）と、反映しない直し（指摘に無い ID・`sensitive`・承認済みの設計に無い before・2か所の before・凍結した節・観点の ID を変える after・見出し・文字数・件数・秘密情報・内部のパス）を確かめた。
- 実装の PR の流れ：`apps/daemon/src/daemon-design-edit.test.ts` で、局所の直しの反映（承認済みの設計・PR の設計のファイル・PR の本文・再生）、再開で二重に記録しないこと、人が直した設計への2回目の直し、設計のファイルが無いタスク、直しを反映しない回の提出、設計に戻した知らせ（1通・秘密情報・@・600 文字・失敗・セキュリティの組み合わせ）を確かめた。
- 投影・画面・取り込み：`packages/core/src/design-edited.test.ts`・`apps/web/src/lib/labels.test.ts`・`apps/daemon/src/github.test.ts`・`apps/daemon/src/daemon-review-watch.test.ts`。
- 文書：`tests/docs` が通ることを確かめた（日英の版の構成・リンク・ADR の置き換え）。
- 全体：`npm run lint`・`npm run typecheck`・`npm test` を実行した。`npm test` の全件実行では、画面のブラウザのテスト（`hint.browser.test.ts`）と文書のテストが、並列の負荷で時間切れになることがあった。単独で実行すると通る。

## 残したこと

- 承認済みのテスト観点 TV-14 の入力の列には「@ の付く名前を含む after」が反映しない側に入っているが、承認済みの設計の本文（エラー時の振る舞い・TV-14 の期待結果・TV-17）は、@ の付く名前は反映を止めず、PR の本文・知らせで無効にする。設計の本文に従い、@ の付く名前を含む after は反映した。
- レビューの子タスクの経路と工程のエージェントの経路は、どちらも同じ差し戻しの処理（`settleReview`・`settleHeldReview`）で知らせを投稿する。結合したテストは、工程のエージェントの経路で確かめた。
