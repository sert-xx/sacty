# 指摘なしの後に実装の PR の CI が失敗していたら、タスクの詳細に出す

- 日付: 2026-11-17（UTC）
- タスク: PBI-364
- PR: #404
- ブランチ: feat/pbi-364-ci-failure-notice
- 関係する ADR: [指摘なしの後に実装の PR の CI が失敗していたら、タスクの詳細に出す（読み続けず、自動では扱わない）](../adr/20261117-0320-superseded-show-ci-failure-after-no-findings.md)

## 目的

PR のレビューの子タスクが、CI の実行中に「指摘なし」を出し、その後 CI が落ちても、PR を作ったタスクは人の承認待ち（マージ待ち）のままで、画面からは分からなかった。
「指摘なし」の後に CI が失敗したことが、タスクを見た人に分かるようにする。

はじめは #396 に入れていたが、CI を読み続ける仕組み（回復の判定・読む間隔の切り替え・件数が多いときの並べ方）へのレビューの指摘が6回続いたので、#396 から外した。
この PR では、求められていること（人に分かる）に絞って、仕組みを小さく作り直した。

## したこと

- イベント `PullRequestCiFailed` と、`Task.pullRequestCiFailure`・判定の `pullRequestCiFailure` を足した。回復のイベントは持たない。
- PR の確認（`checkPullRequests`）の最後に、人の承認を待つ実装の PR のうち1件の、先頭のコミットの CI を読む（`readPullRequestCi`）。
  - 先頭のコミットごとに、5分おきに、12回まで。失敗していたら、1度だけ記録して、その先頭は読むのをやめる。終わっていて失敗が無ければ、読むのをやめる。
  - 1回の確認で読むのは1件だけで、前の読み取りの通信が終わるまでは、次を読まない。これで、GitHub への問い合わせの数・1回の確認で待つ時間（15秒まで）・未完了の通信の数（1つまで）が、決まった上限になる。
- 画面：タスクの詳細の承認待ちの案内に、CI を読んだ先頭のコミットと時刻、その後の結果は反映されないこと、失敗していたチェックの一覧を出す。作業履歴の文言を足した。状態の表示（一覧・「あなたの出番」）は変えない。
- エラーレポートでは、確認の不合格（`check`）に分類する。
- #396 のレビューの指摘のうち、作り直しで当たらなくなったもの：
  - ほかの PR の確認を遅らせる・未完了の通信が積み重なる（読むのは、確認の最後に1件だけ）。
  - 取り消された CI・空の一覧を通ったと扱う、一覧の取得が打ち切られたときに通ったと扱う（回復の判定を持たない。読むのをやめる条件は、回数の上限でも抑えている）。
  - 実行中の CI を読み続けると、GitHub の API の利用の上限に達しうる（先頭のコミットごとに12回まで）。
- できなくなったことは、仕様書の「しないこと」に書いた（再実行の結果を反映しない・一覧の状態に出さない・1時間より後の CI は拾わない など）。
- docs：仕様書（日英。`approval` の「指摘なしの後の CI の失敗の表示」・`tasks-and-steps`・`error-report`）、ユーザードキュメント（日英。`tasks`）、ADR。

## 確かめたこと

レビューの1回目の指摘への対応の後のコードで実行し直した結果を書く。実際の画面での確認だけは、その前のコードで行った（対応で変えたのは、回数の記録を忘れる条件だけ）。

- `npx vitest run --no-file-parallelism`：250 ファイル・4822 件が通った（1 件は以前からの skip）。
- `npm run typecheck`：通った。`npx biome check apps packages docs tests scripts`：指摘なし（`npm run lint` は、Git 管理外の `.claude/settings.local.json` の整形の指摘 1 件で落ちる。リポジトリのファイルの指摘は無い）。`npm run build`：通った。
- 足したテスト：`daemon-implement.test.ts` の 11 件（PR の状態を一時的に読めない確認があっても、回数と間隔を数え直さない。実行中 → 失敗で、先頭のコミットごとに1度だけ記録し、その後は読まない。再起動しても同じ。失敗したチェックの件数の上限。通った先頭は読むのをやめる。実行中のまま・CI が無いままなら、12回で読むのをやめる。読めないときも1回と数え、マージの検出を止めない。1回の確認で読むのは1件で、前の読み取りが終わるまで次を読まず、タスクの間で回す。指摘なしを待つ PR は読まない。先頭を読めなかったとき・先頭が変わったとき・閉じたとき）、`error-report.test.ts`（分類）、`labels.test.ts`（作業履歴の文言。状態の表示は変えない）、`live-screens.test.ts`（タスクの詳細の案内。`http`・`https` でないリンクをリンクにしない）。
- 修正を戻すとテストが落ちること：読む回数と間隔の条件を外すと、`daemon-implement.test.ts` の 6 件が落ちた（1回目の対応の前のコードで確かめた）。1回目の対応（回数を忘れる条件）を、前の形に戻すと、足したテスト 1 件が落ちた。どちらも、戻して通ることを確かめた。
- 実際の画面での確認（`scripts/docs-screenshots/` の種データと偽の GitHub を使い、別のポート・一時の `SACTY_HOME`・一時の `HOME` で起動した。動いている sacty には触れていない）：偽の GitHub が、実装の PR のマージ待ちのタスクの先頭のコミットの CI を「失敗」と答えるようにすると、デーモンが PR の確認で読み取り、タスクの詳細の承認待ちの案内に、読んだコミットと時刻・その後の結果は反映されないこと・失敗していたチェック（`CI`・`test (unit)`。リンク付き）が出た。状態の表示は「実装の PR のマージ待ち」のままだった。作業履歴に「PR #128 の CI が失敗していた」が出た。
- 確かめていないこと：実際の GitHub の CI での動き。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （1回目）[提案] `service.ts`：読んだ回数の記録を、その確認で候補に入らなかったタスクについて消している。PR の状態の取得が一時的に失敗すると、回数と間隔が数え直され、「先頭ごとに12回まで」を超えて問い合わせる | 直した。回数を忘れるのは、実装の PR が開いていなくなった（マージした・閉じた・中止した・タスクが消えた）ときだけにした。PR の状態を読めない確認をはさんでも、回数が12回のままであることを、テストで確かめた |

## 残したこと

- CI の失敗を自動で扱うこと（実装の工程へ差し戻す・レビューの子タスクに再レビューさせる・CI が終わるまで指摘なしやドラフトの解除を待つ）。人が決める。
- CI の失敗を、状態の表示（一覧・「あなたの出番」）や通知に出すこと。回復を記録する仕組みが要る。
- 実際の GitHub の CI での動きは、確かめていない。
