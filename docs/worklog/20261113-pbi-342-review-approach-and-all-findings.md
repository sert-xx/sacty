# 既定のレビューで、直し方の方針を確かめ、同じ原因の指摘を1回で出し切るようにする

- 日付: 2026-11-13（UTC）
- タスク: PBI-342
- PR: #366
- ブランチ: feat/issue-342-review-approach-and-all-findings
- 関係する ADR: [既定のレビューで、直し方の方針を確かめ、同じ原因の指摘を1回で出し切る](../adr/20261113-2328-review-approach-and-all-findings.md)

## 目的

セキュリティ対応のタスクで、PR のレビューの子タスクが回ごとに同じ原因の別の抜け道を1つずつ指摘し、実装との往復が8回続いた。
方針（中継する本文を自前で解析する）を見直す指摘は一度も出なかった。
レビューで方針そのものを確かめ、同じ原因の指摘を1回で出し切り、同じ原因が回をまたいで続いたら方針を見直させる。

## したこと

- 観点カタログ（`review-dispatch/references/viewpoints.md`）のコードの必須観点に C-17（方針の妥当性）を足した。段階は `advanced`。C-5・C-15 の「見ないもの」に C-17 を書いて境界を分けた。
- 担当の資料 `review-execution/references/C-17.md` を足した（確かめる手順・チェックポイント・NG 例・見落としやすい所）。NG 例は複数の言語で、特定のリポジトリに寄せずに書いた。
- 担当の手順（`review-execution/SKILL.md`）に、欠陥ごとに原因を書き、同じ原因のほかの現れを探して1件にまとめる手順を足した。
- 集約（`aggregation.md`）で、観点をまたいで同じ原因の指摘をまとめ、C-17 の方針の指摘に現れをまとめる決まりと、「回をまたいで同じ原因が続くとき」に C-17 を起動し直す決まりを足した。
- `SKILL.md`・`pr-review.md`・`self-review.md` に、出し切る決まりと、回をまたぐときの C-17 の起動を足した。
- PR のレビューの子タスクの指示（`prompts.ts` の `review`）に、指摘を出し切る行と、再レビューで同じ原因の別の現れが続いたら方針を見直す指摘にする行を足した。
- 仕様書（`docs/spec/context.md`・英語の版）に C-17 と出し切る決まりを書いた。

## 確かめたこと

- `npx vitest run apps/daemon/src/default-skills.test.ts apps/daemon/src/prompts.test.ts`：268 件が通った。スキルとプロンプトの変更を戻すと、足した 3 件と変えた 2 件が落ちることを確かめた。
- `npm run lint`・`npm run typecheck`・`npx vitest run tests/docs`：通った。
- `npx vitest run --no-file-parallelism`：219 ファイル・4,261 件が通った（スキップ 1 件）。
- 画面の変更が無いので、画面の動作確認はしていない。スキルの変更がエージェントのレビューを実際にどう変えるかは、エージェントを動かして確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 「回をまたいで同じ原因が続くとき」が、主対象が設計書・利用者向け文書のレビューでも、コードの観点 C-17 を起動させる（セルフレビュー） | 設計書では C-17 の代わりに D-1 で扱い、利用者向け文書には当てはめないと書いた。テストと仕様書の日英も直した |
| C-17 の方針の指摘が `should` のとき、他の観点の `must` の現れをまとめると、必須の修正が提案に下がる（sacty のレビュー 1 回目） | まとめるのは方針の指摘が `must` のときだけにし、重要度は最も高いものにした。`should` のときは `must` の現れを別の指摘に残す |
| SKILL.md・self-review.md・プロンプトが、主対象を限らずに C-17 を起動させ、集約の「設計書は D-1、利用者向け文書は対象外」と食い違う（同） | 「方針の観点（code は C-17、design-doc は D-1。user-doc には無い）」にそろえた |
| `review-execution` だけを古い版で差し替えると、C-17 の資料が無く、担当がレビューを完了できない（同） | 担当への依頼文に、観点の資料が無ければ「見るもの」「見ないもの」だけで見て `limitations` に書く（`failed` にしない）行を足した |
| C-17 の Go の例で、`filepath.Rel` の確認だけではシンボリックリンクによる脱出を防げない（同。提案） | `os.Root` などの開き方を勧め、パスの文字列の検査だけでは防げないと書いた |
| 再レビューの指示が、同じ原因の現れを常に方針の指摘にするよう求め、集約の規則（方針を変える `must` が出なければ現れを `must` に残す、利用者向け文書には当てはめない）と食い違う（sacty のレビュー 2 回目） | 指示を、前回までの `must` との一致を条件にし、集約の規則どおりに扱う書き方に直した。仕様書の日英も直した |
| 3回目以降の再レビューでは、前々回以前の指摘が入力に残らず、同じ原因を照らせない（sacty のレビュー 3 回目） | 「再レビュー」で置き換える前回のレビューを、タスクの `earlierReviews` に古い順に積み（新しい 5 件まで）、3回目以降の指示のデータに入れた。スキルと仕様書の日英も直した |
| 仕様書に、C-17 を起動していても方針の指摘が出なかったときに起動し直す条件が無い（同。提案） | 日英に書き足した |
| 仕様書の再レビューの節のコードの参照に、`earlierReviews` を積む投影が無い（sacty のレビュー 4 回目。提案） | 日英のコードの参照に `packages/core/src/projection.ts`（`applyEvent` の `ReviewRestarted`・`EARLIER_REVIEWS_MAX`）を足した |
