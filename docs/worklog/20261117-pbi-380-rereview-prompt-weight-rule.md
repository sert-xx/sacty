# 再レビューの指示文を、前回の要修正の重みを見直す決まりに合わせる

- 日付: 2026-11-17（UTC）
- タスク: PBI-380
- PR: #416
- ブランチ: feat/pbi-380-rereview-prompt
- 関係する ADR: [レビューの指摘の重みを、影響の大きさと起きやすさで決め、自己レビューは要修正だけを修正に戻す](../adr/20261117-0244-review-finding-weight-by-impact-and-likelihood.md)

## 目的

既定のスキル（`pr-review` の「採用の規則」）・ADR・仕様書は、「前回 `must` として出した指摘を確かめ直して、表では `should` に当たると分かったときは、未対応でも `must` に数えない。総評に、重みを見直したことを 1 行で書く」と言っている。
デーモンが組み立てる再レビューの指示文は、「未対応の前回の `[要修正]` があれば、判定は `changes_required` にする」のままだった。
2 つの文に従うと、重みを見直した指摘は「未対応」と書くしかなく、判定が「修正が必要」になる。

受け入れ条件の要点：

1. 再レビューの指示文が、前回の要修正を表で見直して提案に下げた場合の書き方と、そのときの判定を伝える。
2. 人が後続に回すと決めた指摘を未対応に数えない決まり（PBI-370）と食い違わない。
3. 指示文とスキルの食い違いを捕まえるテストがある（古い文が残っていないこと）。
4. 仕様書（日英）・作業履歴に反映する。

あわせて、文書作成の工程の自己レビューの指示の 1 行（前提を知っている読者に向けた原稿の `should` の扱い）を、自己レビューは `must` だけを修正に戻す決まりに合わせる。

重みの基準と、スキルの決まりは変えない。

## したこと

- `apps/daemon/src/prompts.ts`
  - `rereviewLines`：前回 `[要修正]` として出した指摘が直っていないときは、スキルの重要度の表で重さを確かめ直させる行を足した。表では `[提案]` の重さに当たると分かった指摘は、未対応の `[要修正]` に数えさせず、`[提案]` として扱わせる。「前回の指摘」の節のその行と、総評に、重みを見直したことを書かせる。
  - `rereviewLines`：判定の行を、「未対応の前回の `[要修正]` のうち、今回も表で `[要修正]` の重さに当たるものがあれば `changes_required`」に直した。重みを見直した指摘だけが残り、ほかに `[要修正]` が無ければ、`suggestions` にさせる。
  - `rereviewLines`：後続に回したい案の扱い（`deferralReviewLines`）を渡す回には、その扱いで未対応に数えない指摘は、その扱いを優先させる行を足した。重みを見直した指摘として書かせず、`suggestions` の根拠にもさせない。人に確認中の指摘の重さは、今回確かめ直した重さで決めさせる。`deferralReviewLines` の文は変えていない。
  - `HEAD_CHECK_LINES` と、判定の説明（`changes_required`・`suggestions`）：重みを見直して `[提案]` として扱う前回の指摘を、`[要修正]` に数えないことを足した。
  - `selfReviewLines`（文書作成の原稿）：「記述を足す指摘は must だけを直し、should は直さない」を、「記述を足す指摘は must だけを直す。記述を足す should は、must を直す回でも直さない。ほかの should・nit は、スキルの決まりのとおりに扱う（should・nit だけでは、修正に戻さない）」に直した。
- `apps/daemon/src/prompts.test.ts`：下の「確かめたこと」のテストを足し、古い文を確かめていた 2 箇所を直した。
- 仕様書（`docs/spec/tasks-and-steps.md`、英語の版）とユーザードキュメント（`docs/user/intake.md`、英語の版）に、同じことを書いた。

決めたことと理由：

- 重みを見直した指摘だけが残るときの判定を、`suggestions` にした。スキルは「`should` として扱い」と言い、判定は「`should`・`nit` だけなら提案あり」なので、そこから導いた。`no_findings` にすると、直っていない提案が残っているのに、指摘なしと伝えることになる。
- 重みを見直したことを書く場所を、「前回の指摘」の節のその指摘の行と、総評の 1 行の両方にした。スキルは「総評の前回の指摘の状況に 1 行」と言う。指示文は、前回の指摘ごとの状況を「前回の指摘」の節に書かせているので、節の行に「未対応」とだけ書かれないようにした。
- 設計書の自己レビューの行（「記述を足す指摘は must だけを直し、should は直さない。記述を削る指摘（D-10）は should も直す」）は変えていない。スキル（`self-review`）の文と同じで、工程の指示が直すと決めている提案の例外を述べている。
- 同じ先頭の判定のし直し（`rejudgeLines`）の文は変えていない。足した行は、その回にも出る。
- ADR は足していない。決まりは、関係する ADR ですでに決まっていて、この変更は、指示文をそれに合わせるもの。

## 確かめたこと

- 足した・直したテスト（`apps/daemon/src/prompts.test.ts`）
  - 「再レビューの指示は、スキルの「採用の規則」と同じく、重みを見直した前回の要修正を、未対応の要修正に数えさせない」：スキルの文（指示文が合わせる先）があること、指示文が同じ決まりと判定を言うこと、古い文（「未対応の前回の [要修正] があれば、判定は changes_required にする」など）が残っていないこと、最初のレビューには足さないこと。
  - 「後続に回したい案の扱いは、重みの見直しより優先すると伝える」：優先の行が、案の扱いの行の後に出ること、案の扱いを渡さない回には出ないこと。
  - 文書作成の自己レビューのテスト：新しい文があり、古い文が無いこと。
- `prompts.ts` を変更前に戻すと、上のテストと、直した既存のテストの計 4 件が落ちることを確かめた。
- `npx vitest run --no-file-parallelism`（全テスト）、`npm run lint`（フォーマットの検査を含む）、`npm run typecheck`：通った（全テストは 257 ファイル・4982 件が通り、1 件はスキップ）。
- 確かめられなかったこと：エージェントが、直した指示文に実際に従うか（実物の再レビューでは確かめていない）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （自己レビュー）人が後続に回すと決めた指摘が、表で提案の重さに当たるとき、「重みを見直した」と書くのか「人が後続に回すと決めた」と書くのか、判定を `suggestions` にするのかが、2 つの行で食い違う | 案の扱いを渡す回に、案の扱いを優先させる行を足した |
| （自己レビュー）見られなかった観点があるときの判定の文に「未対応と確かめた前回・既存の要修正」が残る | 足した行に、この指示のほかの行が言う未対応の前回の要修正にも数えないことを書いた。長い文そのものは変えていない |
| （レビュー・提案）人に確認中の案と重なったとき、前回の要修正を提案の重さに下げた根拠が、どこにも書かれない | 案の扱いを優先させる行を直した。判定では案の扱いを優先し、「前回の指摘」の節のその行に、人に確認中と書くのに加えて、重さを下げたことと根拠を書かせる |
| （レビュー・提案）判定のし直しの回で、作者の理由が「稀な条件でしか起きない」のとき、取り下げるのか、重みを見直して残すのかが、どちらにも読める | `rejudgeLines` に行を足した。取り下げるのは、指摘そのものが当たらないと確かめたときだけ。重さについての理由で、直っていない指摘は、重さを確かめ直して、提案の重さなら重みを見直した指摘として残させる（判定は `suggestions`。指摘が残るので、人の判断まで止まる）。テストを足した。仕様書（`docs/spec/approval.md`、英語の版）にも書いた |
| （レビュー・提案）文書作成の自己レビューの括弧書きが、スキルが `must` の無い回でも直すと決めている提案まで止める、と読める | 「スキルと工程の指示が直すと決めている should を除き」を足した |
| （レビュー・提案）影響が小で稀でない前回の要修正の扱いが、スキルの文で二通りに読める。スキルだけを読むと、重みを見直した指摘を差分の外として不採用にできる | この PR では直していない（スキルの側の話。後続に回す） |

## 残したこと

- エージェントが、スキルと指示文のどちらに従っていたかは、確かめていない。
