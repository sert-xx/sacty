# 取り込みの間隔を、取り込みの種類ごとに sacty の設定の画面で決められるようにする

- 日付: 2026-10-15（UTC）
- タスク: PBI-100
- PR: #109
- ブランチ: feat/issue-100-intake-intervals
- 関係する ADR: [取り込みの間隔を、取り込みの種類ごとに sacty の設定に持つ](../adr/20261015-0310-intake-intervals-per-kind.md)

## 目的

取り込みの間隔は `config.yaml` の `github.poll_interval_sec` だけで、すべての取り込みに共通だった。`github:` が無いと JIRA のチケットも
取り込まれず、画面からは変えられなかった。Issue の取り込み・PR のレビューの取り込み・チケットの取り込みの種類ごとに、画面で間隔を決め、
種類ごとに独立して取り込むようにする。互換の処理は作らない（ステークホルダーと合意）。

## したこと

- 設定（`packages/core/src/projects.ts`）：`IntakeKind`・`DEFAULT_INTAKE_INTERVAL_SEC`（300）・`MIN_INTAKE_INTERVAL_SEC`（60）・
  `intakeIntervalSec` を足し、`SactySettings` に `issueIntervalSec`・`reviewIntervalSec`・`ticketIntervalSec` を足した。画面の文字列と空も
  受け付ける。誤りは、画面の3つの欄が同じ名前なので、どの種類かがわかる文言のコード（`input.issueIntervalInvalid` など）にした。
- 取り込み（`apps/daemon/src/intake.ts`）：種類ごとの状態（最後に始めた時刻・実行中の取り込み・読んだ位置・プロジェクトの版）を持ち、
  `tick` で間隔が来た種類を並行に取り込む。`runOnce` を `runGitHub`（Issue と PR のレビューを、取り込み元の `review` の有無で分ける）と
  `runTickets` に分けた。思わぬ失敗は、その種類の失敗として記録する。
- 状況（`apps/daemon/src/service.ts`）：`IntakeStatus` の直近の取り込みを種類ごとの `runs` にし、`recordIntake(kind, run)` にした。
  `config.yaml` を読めれば `intake` を返す。
- `config.yaml`（`apps/daemon/src/config.ts`）：`github` の項目・型・雛形を消した。書いてあっても読まない（知らない項目の扱いのまま）。
- 画面（`apps/web`）：設定の画面の3つの区画に間隔の欄、フォームを `noValidate`（誤りは画面の言語の文で出す）。プロジェクトの画面に
  種類ごとの最後の取り込み（`apps/web/src/lib/intake.ts` の `intakeRuns`。On で設定のある種類だけ）。文言は日本語・英語。
- docs：仕様書（intake・configuration・architecture）、ユーザードキュメント（intake・config・troubleshooting）を直した。ADR を足し、
  gh のアカウントの ADR を一部置き換え（`superseded`）にしてリンクを直した。

- `npm run lint`（終了コード 0）・`npm run typecheck`・`npx vitest run`（63 ファイル・1447 件）・`npm run build`・
  `npx vitest run tests/docs`（69 件）。main（PR #105）を取り込んだ後にも通した。
- 修正を戻すと落ちること：
  - `intake.ts` を PBI-99 の版に戻すと、`github:` が無いので取り込みのテスト 19 件が落ちる。`github:` の条件だけ外した旧実装でも、
    種類ごとの間隔・設定の反映・種類をまたぐレート制限・失敗と遅れの独立のテスト 4 件が落ちる。
  - `noValidate`・間隔の送信・Off の種類を出さない処理を戻すと、web のテストが 3 件落ちる。
- 動作確認の動画：一時的な SACTY_HOME（`github: poll_interval_sec: 120` を書いた `config.yaml`）・偽の gh / docker・別のポートで起動し、
  30 秒・90.5 秒の誤り（日本語）、正しい値の保存と再読み込み、プロジェクトの画面の種類ごとの最後の取り込みと「今すぐ取り込む」、
  59 秒の誤り（英語）を録画した。
- 確かめていないこと：本物の GitHub・JIRA での取り込み。

### PR #109 のレビューへの対応

PR #108 のレビュー対応（`97881ba` など）と main（PR #110）を取り込んだ。`docs/user/troubleshooting.md` の衝突は、取り込みの行を
Issue・チケット・PR（ラベル・依頼）に分けて解いた（`github:` の確認は消した）。

| 指摘 | 対応 |
| --- | --- |
| [要修正] sacty の設定を読めないと `tick` が reject し、定期実行で処理されない rejection になる | `tick` で捕まえ、取り込み中でない種類の失敗として記録し、間隔の起点にせずに次の確認でやり直す。テストを足した |
| [要修正] 取り込み元の無い回も間隔の起点になり、On にしても最長で間隔だけ待つ | 取り込み元の無い回は起点にせず、記録も消す（取り込んだように見せない）。On にすると次の確認ですぐに取り込む。テストを足した |
| [提案] 見つからなくても `importIssues([])` で全タスクを調べる | 見つからなければ `importIssues`・`importTickets` を呼ばない。テストを足した |
| [提案] テストにチケットの取り込み元が無く、JIRA の間隔を確かめていない | 偽の JIRA と取り込み元を共通の準備に足し、種類ごとの検索の回数で確かめる |
| [提案] テストが 10 ms の実時間の待ちに頼り、tick を待たない | 実時間の待ちをやめ、記録と検索の始まりの Promise で同期し、起動した tick はすべて待つ |
| [提案] 平らにしたエラーで種類が失われる | エラーに種類を残し、プロジェクトの画面で「【Issue】」のように添える |
| [提案] Off の種類でも「いまは X 秒ごと」と出る | 止まっている種類は「取り込みを始めると、X 秒ごとに取り込みます」にする |
| [提案] トラブルシューティングにチケットの確かめ方が無い | チケットの行を分け、ラベル・取り込み先・PF の接続の設定を書いた。中身のテスト（`tests/docs/intake-docs.test.ts`）を足した |
| [提案] 古い版へのロールバックの案内 | 案内は作らない（破壊的に変えるとステークホルダーが決めたため。PR #108 と同じ方針）。ADR に、切り戻しは対象外で、古い版に戻すと取り込みが動かないことを書いた |

### PR #109 の再々レビューへの対応と、順序の洗い出し

| 指摘 | 対応 |
| --- | --- |
| [要修正] 取り込んだ後に設定を一度だけ読めず、次の確認までに直ると、古い起点のまま最大約5分待つ | 設定を読めなかったとき、取り込み中でない種類の間隔の起点を戻す。「成功 → 一度失敗 → 直る」のテストを足した |
| [提案] 定期の確認の前に状況を取ると、設定を読めない理由が出ない | 状況は、読めなかった理由（`settingsError`）も返す。画面は案内の文に続けて理由を出す。定期の確認の前に `GET /api/status` を呼ぶテストを足した |

同じ「読めない・間隔の起点」の穴が、ほかの順序に無いかを洗い出した（「起点」は、間隔を測り始める時刻 `lastRun`）。

| 順序 | 修正の前 | いま | テスト |
| --- | --- | --- | --- |
| 起動 → 確認 | すぐに取り込む | 同じ | 種類ごとの間隔 |
| 成功 → 設定の読み取りの失敗 → 直る | 古い起点のまま最大約5分待つ | 次の確認ですぐに取り込む（今回の要修正） | 一度だけ読めず直る |
| 失敗 → 失敗 → 直る | 次の確認ですぐ | 同じ | 設定を読めなくても reject しない |
| 成功 → 取り込みの途中の思わぬ失敗（途中で設定を読めないなど）→ 直る | 起点が残り、間隔を待つ | 次の確認ですぐに取り込む（洗い出しで見つけて直した） | 途中の思わぬ失敗 |
| 成功 → 検索の失敗・レート制限 | 間隔を待つ | 同じ（そのままにした。続けて叩かないため） | レート制限は種類をまたがない |
| 成功 → Off（保存）→ 確認 → On（保存） | 取り込み元の無い回で起点を戻す | 同じ | 取り込み元が無い回 |
| 成功 → Off（保存）→ On（保存）→ 確認 | 起点が残る | 次の確認ですぐ（前回の要修正） | Off → On |
| 成功 → ラベル・依頼を変える（保存）→ 確認 | 起点が残り、新しいラベルの検索が最大で間隔だけ遅れる | 次の確認ですぐ（洗い出しで見つけて直した） | ラベル・依頼を変えたら |
| 成功 → 間隔だけを変える（保存）→ 確認 | 前の起点から新しい間隔で測る | 同じ（仕様どおり） | 間隔を変えたら / ラベル・依頼を変えたら |
| 成功 → プロジェクトの対象を足す → 確認 | 間隔を待つ（読む位置は先頭に戻す） | 同じ（そのままにした。「今すぐ取り込む」で取り込める。対象が無かったときは、取り込み元の無い回なので次の確認ですぐ） | 既存のテスト |
| 設定を読めない → 状況の取得（定期の確認の前） | 状況の API が失敗 | 読めない理由を返す（今回の提案） | 定期の確認の前に状況を取る |
| 設定を読めない → force（今すぐ取り込む） | 状況の API が失敗 | 理由を記録して状況を返す | 保存先が読めなくても API で返す |
| 取り込み中 → force | その取り込みを待つ | 同じ | 遅れの独立 |
| 取り込み中 → Off → On（保存）→ 確認 | — | 取り込みが終わった後の確認で、起点を戻して取り込む | （Off → On のテストと同じ仕組み） |
| `config.yaml` を読めない → 直る | 前の起点から間隔で測る | 同じ（そのままにした。読めない間は種類の記録も無く、取り込みが止まっていることは状況の `intake: null` で出る） | 設定ファイルを読めなければ取り込まない |

確かめたこと：今回の4つの修正（設定を読めないときに起点を戻す・途中の思わぬ失敗で起点を戻す・理由を状況で返す・ラベルの変更で起点を戻す）を
それぞれ戻すと、足したテストが落ちることを確かめた。lint・typecheck・`npx vitest run`・build・`tests/docs` が通る。
