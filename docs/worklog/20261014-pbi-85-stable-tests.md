# 負荷が高いときに時間切れや競合で落ちるテストを、確かめる性質を変えずに安定させる

- 日付: 2026-10-14（UTC）
- タスク: PBI-85
- PR: #94
- ブランチ: feat/issue-85-stable-tests
- 関係する ADR: なし

## 目的

複数の作業が並んでマシンの負荷が高い（load average 20〜150 以上）ときに、全体のテストを流すと、いくつかのテストが毎回のように
時間切れや競合で落ちていた（単独では通る）。原因をテストごとに調べ、時間切れを延ばすだけで済ませずに、原因に合わせて直す。
境界・伏せてから切り詰める順番・後片付けなど、確かめている性質は弱めない。本体のコードは変えていない（本体の不具合は見つからなかった）。

## したこと

負荷をかけた状態（CPU を回すだけのプロセスを 24 個並べ、`--maxWorkers=16`。load average 120〜280）で、修正前の全体のテストを
繰り返し流し、落ちたテストを記録して、原因を調べた。

| テスト | 原因 | 直し方 |
| --- | --- | --- |
| `agents/output-relay.test.ts` の 20MB・8MB・fallocate | 大きな出力の中身を、数千万の要素の配列（`Array.from`）から作っていた。テストの側と、動かすコマンドの側の両方で作るので、それだけで負荷が高いと数秒かかった | 251 バイトの並びを `Buffer.alloc(size, 並び)` で繰り返して埋める（中身は同じ）。20MB のテストは 1.8 秒から 0.55 秒になった |
| 同 「後ろで書き続けるプロセスがあっても待ち続けず」 | 後ろのプロセスが書き始めるのを、コマンドを始めてからの固定の `sleep 0.3` にしていた。負荷が高いと、コマンドの出力（1MB）を書き終える前に書き始めて混ざる。終わるまでの時間の確かめ（5秒未満）は、既定の時間切れと同じで意味が重なっていた | コマンドが終わる直前に置く合図のファイルを待ってから書き始める（その後の 1 秒は、中継がコマンドの終わりに気づくまでの猶予。読み手を止めておく時間は 1 秒から 2 秒にし、猶予より長くする）。時間の確かめの代わりに、中継が終わったときに後ろのプロセスがまだ動いていることを確かめる |
| 同 「中継がコンテナの標準出力に書けなくなったら、コマンドを止めて」 | 中継は SIGKILL を送ってすぐ終わるので、コマンドが消える（親を失って引き取られる）前に、消えたかを確かめることがあった | 消えるまで待つ（`vi.waitFor`、3秒まで）。止めていなければ、コマンドは書き続けるので消えずに落ちる |
| `host-mcp-processes.test.ts` の SIGTERM・SIGINT（`ENOENT`） | 記録のディレクトリは、最初の記録を書くときに作られる。子孫が見えてから記録を書くまでの間に、記録の数を数えようとして `readdirSync` が `ENOENT` で例外になっていた（待つ処理の中の例外は、待たずにそのまま落ちる）。本体の不具合ではない（記録は `ps` で開始時刻を読んでから書く） | 記録のディレクトリが無ければ空として数える |
| 同 「突然落ちて残ったものは」 | 子孫が3つ見えたら進めていたが、親（デーモンの代わり）が記録の更新のために動かす `ps` も子として数えていた。sh と sleep が起動する前に進むと、確かめる対象が `ps` などの一時的なものになり、デーモンを落とした後に「残る」はずのものが無かった | 親の子・孫・ひ孫（MCP サーバー・sh・sleep）の3代がそろうのを待ち、その3つを確かめる |
| 同 「例外で終わったら」「自分で終わったら」「標準出力・標準エラーを開いたままなら」 | 偽のプロセスが、起動してからの固定の時間（1.5 秒・1 秒・0.7 秒）で例外を投げる・終わる。負荷が高いと、テストが子孫を見つける前に進む | テストが子孫を見つけてから置く合図のファイルを待って、例外を投げる・終わる |
| `session-logs.test.ts` の総当たり（サロゲートペア） | 約 800 回、セッションログのファイルを作って読む。1回あたり数ミリ秒のファイルの操作（作ったばかりのファイルを読むのが遅い）で、全体で 3〜8 秒かかり、既定の5秒を超えた | 確かめる組み合わせ（秘密情報の有無3通り × 上限5通り）ごとに、15 のテストに分ける。届いた分の境目は、どのテストでも今までと同じくすべて確かめる。実行ごとに場所を作り直さない |
| 同 「伏せてから切り詰める」 | 同じく約 260 回ファイルを作って読む | 先頭の上限ごとに 20 のテストに分ける（確かめる組み合わせは同じ） |
| 同 「途中で止めた実行」 | 偽の docker が出力を書くのを、固定の 300ms で待っていた | 出力を書き終えた合図のファイルを待ってから止める |
| `agent-sessions.test.ts` 「秘密情報が、残す先頭の終わり・末尾の始まりをまたいでいても」 | 200 の位置を1つずつ写して待っていた。時間の大半は、ファイルの読み書きを待つ時間（CPU のプロファイルではほとんど idle） | 残す先頭・末尾の大きさを目印から読み、秘密情報が境目にかかる位置をすべて（と前後の1つ）確かめる。境目は、先頭の終わり・伏せた後の末尾の始まり・伏せる前の末尾の始まりの3つ。並べて待つ。修正前の決め打ちの範囲（2640〜2699）は、伏せる前の末尾の始まり（2651）にかかる位置の一部（2622〜2639）と、伏せた後の末尾の始まり（2631）を含んでいなかったので、確かめる位置は減らずに増えた。1 秒から 0.24 秒になった |
| `repository.test.ts` の PBI-57 のテスト | git を数十回動かす1つのシナリオで、負荷が高いと 43 秒かかり、時間切れ（30 秒）を超えた | マージの前（タスクブランチ・成果のファイルのコミット・受け付けないパス・ブランチの削除）と後（成果のファイルを引き継いで実装を積む）の2つのテストに分け、準備を共通にする |
| `context.test.ts` のシンボリックリンクのテスト | 5つのケースごとに、リポジトリを作ってからもう一度コミットし（git を7回）、取得を1つずつ待っていた | シンボリックリンクを最初のコミットに含め（git を5回）、取得は並べて待つ。8 秒から 2.6 秒になった |

`context-mcp.test.ts`（PR #89 で入った）は、PBI では一度だけ落ちたとされていたが、テストの名前もエラーも記録が無かった。
PR #89 のマージの後の main で、負荷をかけて（load average 120〜280）このファイルを含む少数のファイルだけで 14 回、全体で 20 回以上流したが再現しなかった。
固定の時間で進める待ちは無く（待ちは条件と期限つき）、記録のファイルを数える箇所は、記録を書くのを待ってから
（`ready` は記録を書き終えてから返る）数えている。変えていない。

時間切れを延ばしたテストは無い。既にあった時間切れ（`repository.test.ts`・`context.test.ts` の git の describe の 30 秒、
fallocate のテストの 30 秒など）はそのまま。

## 確かめたこと

- `npm run lint`（終了コード 0）・`npm run typecheck`・`npm run build`：通った。
- `npx vitest run`（既定の並列数）：7回とも全件通過。最後の2回は、PR #93 のマージの後の main に rebase した最終の形（1229 件）で、47.5・48.0 秒。修正前（同じ時間帯・load average 約 35）は
  49.6〜50.4 秒で、1回は `host-mcp-processes.test.ts` の2件が落ちた。
- 負荷をかけた確認（CPU を回すだけのプロセスを 24 個並べ、`--maxWorkers=16`）：
  - 修正後：15 回とも全件通過（load average 120〜283。最後の2回が rebase した最終の形）。83.8〜90.5 秒。
  - 修正前：5回とも 4〜5 件落ちた（上の表の `output-relay`・`session-logs`・`agent-sessions`・`host-mcp-processes` のテストが毎回のように落ち、1回は `host-mcp.test.ts` の1件も落ちた。`repository.test.ts` の PBI-57 は、途中の形（ほかを直した後）を load average 約 200 で流したときに落ちた）。
  - 同じ負荷で JSON に記録して比べると、全体は修正前 79.3 秒・修正後 84.7 秒。いちばん長い `repository.test.ts`（全体の長さを決める）が
    分けた準備の分だけ 78.8 秒から 84.2 秒に延びた。ほかの対象のファイルは短くなった（`output-relay.test.ts` は 24.5 秒から 5.9 秒）。
    負荷の無いときは、全体は短くなった。
  - 負荷のプロセスは、確かめ終わるたびに止めた（自分で起動したものの PID だけを止めた。ほかの作業のプロセス・ポート・`~/.sacty` には触れていない）。
- 修正の前後で、テストが同じ不具合を検出できるか（本体にわざと不具合を入れ、修正前と修正後のテストを流した。終わったら本体は元に戻した）：

  | わざと入れた不具合 | 修正前 | 修正後 |
  | --- | --- | --- |
  | 秘密情報を伏せるために持っておく分を、サロゲートペアの途中で切る | 落ちる | 落ちる（12 件） |
  | セッションログの先頭を、UTF-8 の文字の途中で切る | 落ちる | 落ちる（4 件） |
  | 届いた分の境目をまたぐ秘密情報を持っておかない | 落ちる | 落ちる（16 件） |
  | エージェントのファイルを、切り詰めてから伏せる | 落ちる | 落ちる |
  | 出力の中継を使わない（標準出力がパイプのまま） | 落ちる | 落ちる |
  | 中継が、コマンドが終わった時点ではなく、追いつくまで流す | 落ちる | 落ちる |
  | 中継が、書けなくなってもコマンドを止めない | 落ちる | 落ちる |
  | デーモンが例外で終わるときに、MCP サーバーのグループに SIGTERM を送らない | 落ちる | 落ちる |
  | デーモンを止めるときに、MCP サーバーを止めない | 落ちる（2 件） | 落ちる（2 件） |
  | MCP サーバーが自分で終わったときに、残った子孫を止めない | 落ちる（2 件） | 落ちる（2 件） |
  | 設定・規約・スキルのシンボリックリンクを止めない | 落ちる | 落ちる |
  | 実装を積むときに、成果のファイルを引き継がない | 落ちる | 落ちる |
  | すでに無いブランチを消すときに失敗にする | 落ちない | 落ちない（修正前と同じ。このテストのローカルのリポジトリでは別の理由で通る。変えていない） |

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （DA のセルフレビュー）後ろで書き続けるテストの猶予が 0.3 秒のままでは、負荷が高いと、中継がコマンドの終わりに気づく前に書き始めて、また混ざりうる | 猶予を 1 秒にし、読み手を止めておく時間を 2 秒にした（猶予より長く止めるので、追いつくまで流し続ける不具合なら、猶予の後に書いた分が混ざって落ちる。わざと入れた不具合で落ちることを確かめ直した） |
| （DA のセルフレビュー）総当たりを分けただけなら、時間切れを延ばしたのと同じではないか | 分けた後も、組み合わせ・届いた分の境目は修正前とすべて同じで、1つのテストの仕事が 15 分の 1（伏せてから切り詰めるテストは 20 分の 1）になった。全体の時間は延びていない（負荷の無いときは短くなった）。わざと入れた不具合では、分けたテストのうち 4〜16 件が落ちる（修正前は1件） |
| （DA のセルフレビュー）合図を待つ形にすると、合図を置き忘れたときに待ち続けるだけで、わかりにくい | 合図は、待つ箇所の直前にテストか偽のプロセスが置く。待つのは期限つきの `until`（10 秒で理由つきの例外）か、テストの時間切れで落ちる |
| （DA のセルフレビュー）PBI-57 を分けたので、マージの後のテストで、作業領域の git の設定を評価しないことを確かめなくなっていないか | 修正前も、実装を積む前に `.gitattributes` を消していたので、マージの後の部分では確かめていなかった（確かめているのはマージの前のテストで、そのまま残した） |

## 残したこと

- `repository.test.ts` は、全体の中でいちばん長いファイルで、全体の実行時間を決めている。ファイルを分けて並べれば全体は短くなるが、
  このタスクではしなかった。
- `context-mcp.test.ts` の一度だけの失敗は、再現せず、原因はわからない。
