# 既定のスキル writing に、後から読まれる文書の組み立て方と図・画像の決まりを足し、文書作成の工程でセルフレビューをさせる

- タスク: なし

## 目的

ユーザードキュメントを読みやすく直した後（#371）、人から次のことを頼まれた。

- 人が読みやすい文書は、どのような構成・文章・図や画像を持つかを踏まえて、既定のコンテキストの `writing` スキルと、各工程の指示が、文書を作るときの決まりとして適切かを確かめる。
- 確かめた結果の4つの直しを、PR にする。

確かめた結果は、次のとおりだった。

- `writing` と工程の指示は、承認のための文章（PR の本文・要求要件・設計）には合っている。
- 前提を知らない人が後から読む文書（ユーザーガイド・手順書・README）の決まりが無い。
  「情報を絞る」を当てると、読む人が知らない語と前提まで削られる。
- 図と画像の決まりが、書く側のどこにも無い。
- 文書作成の工程は、初版を最小限にする決まりを使い、セルフレビューもしない。
- テンプレート「ドキュメント構築」は、構成と流れを書かせるが、図を求めない。

## したこと

### 既定のスキル `writing`

- `SKILL.md`
  - 決まりの最初に、読む人がその件の前提を知っているかで文章の種類を決めることを置いた。
    「情報を絞る」は、承認・判断・返信のための文章に当てる。
  - 後から読まれる文書と、図・画像の要点を足した。
  - 書く手順に、種類を決める手順を足した。
  - 「見直し」に、後から読まれる文書と、図・画像を使ったときに確かめることを足した。
  - 説明（`description`）に、ユーザーガイド・手順書・README などの文書を足した（文書を書くときにもスキルが使われるようにする）。
- `references/documents.md`（新規）：後から読まれる文書の組み立て方。
  文章の種類の表、読む人と目的、最初に書くこと、並べる順、見出しと節の最初、手順、説明の書き方、今の状態だけを書くこと、ほかの節の指し方、長い文書、既存の文書への書き足し方。
- `references/figures.md`（新規）：図と画像。
  図にするもの・しないもの、図の作り方と形式、スクリーンショットの使い所・撮り方・撮れないとき、表とコードの例。
- `references/sentences.md`：「情報を絞る」の節に、読む人が知らない語と前提は書くことを足した。
- `SKILL.md`・`references/layout.md`：ほかの節を位置で指していた所（「下の「見直し」」など）を、節の名前で指すように直した（足した決まりと、スキルの本文を合わせるため）。

前からある決まり（改行、箇条書きと表、語と言い回し、確認の懸念、スコープ、簡潔さ）は変えていない。

### 文書作成の工程（`apps/daemon/src/prompts.ts`）

- `documentDraftLines`（新規）：原稿の書き方。
  初版を最小限にする決まり（`minimalDraftLines`）の代わりに使う。
  読者が前提を知っているかで書く量を決めさせ、前提を知らない読者に向けた原稿の組み立て方と、図・画像の要点を書く。
  細かい決まりは、`writing` の資料があれば従わせる。
- `selfReviewLines` に、原稿のための種類 `manuscript` を足した。
  - 主対象の種類は、原稿の種類でエージェントに決めさせる。
  - 下書きを一時ファイルに書いて対象にさせ、リポジトリの検証は実行させない。
  - 外部に直接書く文書は、書く前の下書きをセルフレビューし、直し終えてから書かせる。
- 差し戻しの直しは、前回の提出がパスしていて、前回の原稿が空でなければ、指摘に関わる観点だけで見させる（`fixRunCauses`）。
- `packages/core/src/events.ts`：`SELF_REVIEW_STEPS` に `document` を足した。
  記録（`AgentRunCompleted` の `selfReview`）と画面の表示は、工程を問わない作りなので、変えていない。
- `review-dispatch` の `references/self-review.md`：直しの実行の最初のレビューが当てはまる成果物の種類の例に、文書を足した。

### テンプレート「ドキュメント構築」（`apps/daemon/src/task-templates.ts`）

- 全体の構成（依存の向き）と、主な処理の流れ（通る順と分かれ道）を、図でも示させる。
- 書き方の約束に、次の3つを足した。
  - 最初に、何について書いたものか・どの作業の前に読むかを書く。
  - 図は関係にだけ使い、形式は既存の図に合わせる（無ければ、Markdown の中にテキストで書ける形式）。
  - 細かい決まりは `writing` に従う。
- 直すスキル（`docs-update`）に、図にした構成・流れが変わったら図も直すことを書かせる。

- ADR を足した。
  セルフレビューの ADR（文書作成の工程を対象にしない部分）と、初版を最小限にする ADR（文書の部分）を、一部置き換えた。

## 残したこと

- 足した決まりで、エージェントが書く文書がどれだけ読みやすくなるかは、実際のタスクで確かめていない。
- レビューの観点（U-3 など）は変えていない。
  節の最初の要点や経緯の言い回しのような細かい所を、レビューの側でも見るかは、実際の原稿を見てから決める。
