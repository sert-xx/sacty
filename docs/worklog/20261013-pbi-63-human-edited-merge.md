# 人が PR の中で直してからマージしても承認・完了として進め、sacty の成果と人が直した最終の成果を記録する

- 日付: 2026-10-13（UTC）
- タスク: PBI-63
- PR: #70
- ブランチ: feat/issue-63-human-edited-merge
- 関係する ADR: [人が PR の中で直してからマージしても承認・完了として進め、sacty の成果と人が直した最終の成果の両方を記録する](../adr/20261013-1425-accept-human-edited-merge.md)

## 目的

PR が sacty の出したコミットと違う内容でマージされたとき（`merged_outdated`）に人の判断を待つのをやめ、承認・完了として進める。
監査のために、sacty の成果と人が直した最終の成果を記録する。受け入れ条件の要点は次のとおり。

- 要求要件・設計の PR が違う内容でマージされても承認として進み、承認済みの成果は人が直したファイルの内容になる。
- 実装の PR が違う内容でマージされても、タスクが完了になる。
- 台帳に両方のコミット・違いの有無・（要求要件・設計は）両方の版の本文が残り、画面で人が直してマージしたことと両方のコミットが分かる。
- 前の版の `merged_outdated` で止まっているタスクも進み、過去の作業履歴を読み込める。

## したこと

- 承認の流れ（`apps/daemon/src/service.ts`）：違う内容でマージされても承認として進め、実装の PR ならタスクを完了にする。最終レビューは
  やり直さない。前の版の `merged_outdated` のタスクも次の確認で進む。
- 成果のファイルの読み取り（`apps/daemon/src/repository.ts`・`apps/daemon/src/github.ts`）：マージの時点のコミット（`merge_commit_sha`、
  取れなければ PR の先頭）から、成果のファイルだけを退避した git のメタデータで読む（`readFile`）。消された・読めないときは sacty の版を
  承認済みにして記録し、一時的に取得できないときは何も記録せず次の確認でやり直す。読んでいる間の中止・差し戻し・再提出では承認を記録しない。
- 台帳（`packages/core/src/events.ts`・`packages/core/src/projection.ts`）：`PullRequestMerged` に `submitted`・`commit`・`mergeCommit`・`edited`・
  両方の版の本文（省略できる項目）。
- 画面（`apps/web/src/components/pull-request.tsx`・`apps/web/src/app/tasks/[id]/page.tsx`・`apps/web/src/lib/labels.ts` ほか）：作業履歴の
  「人の直した内容でマージされた → 承認（sacty の提出 → 人が直した最終）」、PR の欄の「人が直してマージした」・両方のコミット・
  GitHub の比較へのリンク・マージのコミット、成果の欄の人の版と「sacty が出した版を見る」。
- PO の判断：設計の承認済みの成果は人が直した全文。最終レビューの基準のテスト観点は sacty のものを引き継ぐ。成果のファイル以外も
  直されていたときは、PBI-57 の守りのまま。

## 確かめたこと

- `npm run lint`・`npm run typecheck`・`npx vitest run`（649 件）・`npm run build` が通った。レビューの対応の後、レビューでは 679 件・
  lint・typecheck・`diff --check` の成功を確かめた。
- 要求要件・設計・実装の PR で、違う内容・同じ内容のマージ、消された・読めない・一時的に取得できない、前の版の merged_outdated、
  再起動の後、読んでいる間の中止。実際の git で、マージ後のタスクブランチから読む（大きな日本語・バイナリ・NUL・大きすぎる・
  シンボリックリンク・ディレクトリ・不正なパス・作業領域の git のフィルターが動かない）。
- 主要な処理を 16 か所わざと壊し、すべてテストが落ちることを確かめた。
- 画面は、テストの流れで作った作業履歴をアプリで開いて確かめた（実際の GitHub の PR は使っていない）。
- 未確認：実際の GitHub でのマージの操作とブラウザの表示（レビューでも未検証）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 人が直してマージした文書を、マージの時点ではなくタスクブランチの最新のコミットから読むので、マージの後に積まれた未レビューの変更まで承認済みの成果に取り込む | マージの時点のコミット（`merge_commit_sha` を優先し、取れなければ PR の先頭のコミット）から読むようにした。読むコミットが無ければ取得し、取得できない一時的な失敗やどちらのコミットも取れないときは、何も記録せず次の確認でやり直す。`document.commit` に実際に読んだコミットを記録する。要求要件・設計・同じ内容・消された・読めない、のそれぞれでテストを足し、実際の git でも確かめた。先端を読むように戻すとテストが落ちることも確かめた |

このほか、コミット e575bae で、タスクブランチを取得できないときは sacty の版で承認せず、何も記録せずに次の確認でやり直すように直した
（レビューの指摘によるものかは記録に無い）。

## 残したこと

- 台帳に、両方の版の本文を最大 1MiB ずつ残す。
- 人が Markdown の中でテスト観点を直しても、最終レビューの基準には反映しない（PO の判断）。
