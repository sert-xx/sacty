## 概要

実務実証実験の r4 とそれ以前に残った問題を、3 群に分けて直した（A：レビュー・指示の質、B：止まる・届かない・食い違う、C：画面・人への知らせ）。1 つの PBI なので、作業履歴は 1 ファイルにまとめ、群ごとに見出しで分ける。3 群は別の担当が並行して作り、あとで 1 つの PR にまとめた。

## A 群：レビュー・指示の質

### 目的

実験 r4 までで残った、レビューと指示の質の問題 A1〜A8 をまとめて直す。B（止まる・届かない・食い違う）と C（画面・人への知らせ）は別の担当で、ここでは触れない。ほかの振る舞いは変えない。

- A1 受け入れの確かめが名前の確認に縮む（S2 r4）
- A2 最終レビューが、新しく入れた共有の仕組みの回帰を見逃す（S16 r4）
- A3 フォーマッターなどの検証の漏れ（S18 r4）
- A4 リポジトリの文書が読まれず、正しい要件がセルフレビューで消える（S14 r4）
- A5 最終レビューの所見が英語で出る（S16 r4）
- A6 「人が確かめること」に、確かめようのない環境の項目が入る（S18・S5 r4）
- A7 PR の本文の重複と内部のパス（F3 の残り）
- A8 コミットメッセージがリポジトリの形にならない（S5 r2）

### したこと

- `apps/daemon/src/prompts.ts`
  - A1：オーケストレーターの `noTests` を、テストが無い根拠だけにした。根拠のデータの後ろに「根拠は確かめ方を決めない」を添えた（`NO_TESTS_REASON_NOTE`）。実装の指示（テストなし）に、名前の存在の確認に縮めないことを足した（`ACCEPTANCE_DEPTH_IMPLEMENT_LINE`）。最終レビューと統合レビューに同じ趣旨の節を足した（`ACCEPTANCE_DEPTH_REVIEW_LINE`）。
  - A2：最終レビューと統合レビューに「共有の仕組みの確認」を足した（`sharedMechanismLines`）。確かめられなかったことは、最終レビューは `humanChecks`、統合レビューは判定の説明（人が確かめることの欄が無い）。
  - A3：要求要件・設計の指示に「提出の前の検証（成果物のファイル）」を足した（`documentVerificationLines`。文書に効く検証だけを成果物の置き場所のパスで実行させ、実行しなかった理由をセルフレビューの報告に書かせる。コードの検証は実行させない）。
  - A3：実装・修正の指示に「提出の前の検証」を足した（`implementVerificationLines`）。セルフレビューの指示に、`verification-run.md` を全体を読んで従うことを足した。最終レビューに「変更の検証」を足した（`verificationScopeLines`）。
  - A4：情報収集に、参照されていない文書も探して読むことを足した。設計のセルフレビューの指示に、根拠のある記述を「要求要件に無い」だけで消さないことを足した。
  - A5：最終レビューと統合レビューに「出力の言語」を足した（`OUTPUT_LANGUAGE_LINE`）。sacty には出力の言語の設定が無いので、タスクの言語に合わせる。
  - A6：`humanCheckLines` に、作業領域の内部の物の確認を `humanChecks` に書かないことを足した（`WORKSPACE_ONLY_CHECK_LINE`）。前の回から引き継ぐ項目の指示にも、この種の項目を外す例外を足した。
  - A7：PR の本文の「変更」の節を、結論に載せた最初の段落を除いた残りにした（`firstParagraph`・`bodyAfterLead`）。内部のパスを人が辿れる呼び方に置き換える `withoutInternalPaths` を足し、実装・要求要件・設計の PR の本文と成果物のファイル、調査のコメント、確かめる所の根拠に掛けた。
- `apps/daemon/src/commit-message.ts`（新規）・`service.ts`：A8。起点のコミットから定めを読み、Conventional Commits を定めているときだけ、コミットの1行目に `feat:`・`fix:`・`docs:` を付ける。定めの読み取りは起点のコミットごとに覚える。
- 既定のコンテキスト：U-1 に責務・振る舞いを照らす手順と NG 例（A1）、D-10 に根拠のある記述を消さない節（A4）、`viewpoints.md`・`self-review.md`・`verification-run.md` の対応する文、`classify-provenance` に `refs` へ Input のパスを書かない指示、`rules.md` に内部のパスを書かない規則（A7）。
- 仕様書（`tasks-and-steps`・`approval`・`split-and-integrate`・`context`、日英）、ユーザードキュメント（`tasks`、日英）、ADR 2件。

### レビューの指摘と対応（自分で悪魔の代弁者として確かめた）

| 指摘 | 対応 |
| --- | --- |
| 結論の「変更」から最初の段落を除くと、見出しだけの節が残る | 中身の無くなった見出しを除き、見出しだけが残るときは節ごと出さない。テストあり |
| 最初の段落が切り詰められて結論に載ったとき、残りだけを出すと情報が欠ける | 切り詰められたときは全文を出す。テストあり |
| コミットメッセージの定めの読み取りで、25 個のファイルを毎回 git で読む | 起点のコミットごとに覚える。読めないものがあった回は覚えない |
| 要求要件・設計の PR のコミットを実装と同じ種類にすると、`feat:` が成果物だけの PR に付く | 要求要件・設計の PR のコミットは `docs` にした |
| 出力の言語の指示を、設定が無いのに「設定に従う」と書くと、無い設定に従わせてしまう | 設定が無いことを書き、タスクの言語に合わせる指示にした |

### 残したこと

- A5 の出力の言語は、タスクの題と内容の言語に合わせる。sacty に出力の言語の設定を足してはいない。
- A6 は指示だけで、sacty は項目を機械的に消さない。
- A8 は Conventional Commits だけ。1行目の長さの上限と、種類を限る設定（`type-enum`）は扱わない。
- どれも指示の文面の対策で、実タスクで効くかは未確認。

## B 群：止まる・届かない・食い違う

### 目的

実務実証実験の r4 とそれ以前に残った、次の 5 件（PBI-301 の B 群。A 群・C 群と 1 つの PR にまとめた）をまとめて直す。

- B1：AI のレビューが GitHub の一時的な失敗（503）で止まると、自動で再開せず、その後のどの head にもレビューが付かなかった。
- B2：実装の再実行が出した返信案（`sacty-github-comments`）が、Sacty の画面にだけあり、GitHub の PR に投稿されなかった。
- B3：レビューが「指摘なし」と書きながら「既存の指摘に未対応のものがあります」とも書いた。
- B4：プロジェクト設定の同時保存で、409 のやり直しの後も、ほかの担当の追加が消えた。
- B5：claude-code の費用の見積もりが、CLI の報告額の約 4.5〜5 倍になった。

### したこと

#### B1 一時的な失敗の自動のやり直し

- `apps/daemon/src/github.ts`：`isTransientGitHubFailure`。GitHub の 5xx・429・レート制限と説明する 403・接続の失敗（`fetch failed`・ECONNRESET・ETIMEDOUT など）を一時的とし、401・403（権限）・404・422 や GitHub の失敗でないエラーは一時的としない。
- `apps/daemon/src/service.ts`：`retryTransient`。レビューの対象の PR の確認（`resolveReviewTarget`）とレビューの投稿（`postReview`。本体を `composeReviewPost` に分けた）を、止める前に、15 秒・1 分・3 分・5 分の間隔で最大 4 回やり直す（`reviewRetryDelaysMs`）。やり直す前に `ReviewGitHubRetried` を記録する。待つ間に一時停止・中止・デーモンの停止があれば、1 秒以内にやめる（何も記録せず、一時停止の理由も上書きしない）。
- 「止まりました」の知らせとの整合：やり直している間はタスクを止めないので、PR に知らせを書かない（矛盾しようがない）。上限まで失敗したら、これまでどおり一時停止して知らせる。投稿のやり直しは、前に投稿したレビューを目印で見つけて使うので二度投稿しない。
- `packages/core`・`apps/web`：`ReviewGitHubRetried` のイベント・画面の文言（日英）。

#### B2 返信の PR への投稿

- PR のマージで承認する工程（実装・要求要件・設計）の `sacty-github-comments` を、承認（マージ）を待たず、成果が承認待ち（PR が開いている）になったときに 1 回投稿する（`awaitingSubmittedGitHubComments`・`postGitHubComments` の `submitted`）。提出ごとに 1 回で、マージの後に同じ提出の頼みを重ねて投稿しない。条件（レビュー・セキュリティのタスク・中止・一時停止中・実行中は投稿しない、投稿先の制限、目印、投稿直前の確かめ）は承認の後と同じ。
- 目印の承認の日時の所は `submission-<提出の回>`、末尾は「AI が書きました。この工程の成果は PR のマージで承認されます」。`GitHubCommentsPosted` に `submission` を足した（承認の日時は空）。
- 投稿した返信が新しい指摘として取り込まれ、差し戻しが続かないよう、そのタスクのアカウントが投稿した目印（`<!-- sacty-comment:`）で始まるコメントを PR の指摘の取り込みから除いた（`isSactyGitHubComment`。他人が目印をまねたものは除かない）。
- 投稿できなかったときは、理由を `GitHubCommentsPosted` の結果に残す（画面の作業履歴に出る。タスクは止めない）。

#### B3 「指摘なし」と「未対応あり」の食い違い

- 原因の見込み：既存の指摘の状況は PR のコメントの本文だけで渡し、スレッドが解決済みかどうかは渡していない。レビューのエージェントは、返信が付いてコードが直った指摘も「未対応に見える」と書きうる。既定のスキル（`pr-review.md`）と指示（`existingReviewLines`）が「未対応に見えるものがあれば 1 行添える」としていたことも原因。
- 指示とスキルを直した：未対応かはコードと作者の返答で確かめる／解決済みにされていないことを根拠にしない／コードが直っている指摘・返答が確かめられた指摘・前回の指摘の確認で対応を確かめた指摘は数えない／確かめて未対応だったときだけ総評に添え、判定を「指摘なし」にしない／無いときは総評に「未対応」と書かない。スキルは言語・ツール・リポジトリに寄せない書き方にした。

#### B4 プロジェクト設定の同時保存

- 消えた原因は、実験の記録とコードの読みからは特定できなかった（未確認）。版の照合と保存は同期の処理で、画面は読み直すと内容と版を取り直す。
- そこで、拒否と読み直しに頼らず、サーバーが 3 つの定義（読み込んだ版・今・保存しようとする定義）で併合するようにした（`mergeProjectDefinitions`）。対象は 1 件ずつ、ほかの項目は項目ごとに、一方だけが変えたならその変更を採り、両方が違うように変えたら併合できない（409）。元の定義は版ごとに 50 版まで残す（`project_revisions`）。併合した結果も通常の検査に通す。
- 画面：併合して保存したときは、版に進めず、併合したことと再読み込みのボタンを出す。再読み込みするまで保存を止める（古い基準の版のまま保存すると、自分が足した対象を消せないため。PR のレビューの指摘）。
- PBI-274 の ADR の「併合：しない」を置き換える ADR を書いた。

#### B5 費用

- 実際のログ（`~/.sacty/runs/<タスク>/<実行>.jsonl` の最後の `result`、916 件。読むだけ）で確かめた：
  - `total_cost_usd` は、`modelUsage` のモデルごとの `costUSD` の合計と全件で一致した。
  - 雛形の単価（Opus で全部を換算）は、報告額の合計 $791.54 に対して $3,202.60（4.05 倍）。複数のモデルを使った 72 件では $341.99 に対して $1,649.44（4.82 倍）。
  - Sonnet の使用量は、入力 $2・出力 $10・キャッシュ読み出し $0.1・キャッシュ書き込み $2.5 で換算すると、報告額と完全に一致した。Opus は、入力 $4.2〜$6.1（中央値 $5.3）で、実行ごとにばらつく（原因は未確認）。
  - 例の単価を Opus 入力 $5/読み出し $0.25/書き込み $6.25/出力 $25、Sonnet 入力 $2/$0.1/$2.5/$10 にして、モデルごとに換算し直すと、916 件の合計は $818.71 で、報告額の 1.03 倍。
- `apps/daemon/src/agents/parse.ts`：Claude の `result` の `total_cost_usd`（`reportedCostUsd`）・モデルごとの使用量（`modelUsages`）・報告に入っていない使用量（`unreportedUsage`）を持つ。セッションを再開・複製した実行は使わない。
- `apps/daemon/src/agents/cost.ts`（新規）：`runCost`。報告があればそれを実行の費用にする（読めない値と、使用量があるのに 0 の報告は換算に回す）。無ければ、モデルごとの使用量を、そのモデルの単価で換算する（単価が設定に無いモデルは、工程のエージェントの単価）。
- `apps/daemon/src/config.ts`：エージェントが、同じ接続先のモデルごとの単価（`modelPrices`）を持つ。雛形の Claude の単価の例と `per_plan_usd` の例（`standard: 30`・`split: 100`）を直した。既定の上限は変えない。
- 作業履歴：報告を使った実行と、モデルごとに換算した実行は `RunCostRecorded`（`reported`／`converted`・実行の費用・設定の単価で換算した額・単価が設定に無かったモデル）を記録する。使用量を工程のエージェントの単価で換算しただけの実行（Codex など）は、これまでと同じなので記録しない。
- ADR 20261016-1455 の既知の制約を置き換える ADR を書いた。
