# 要求要件・設計を、タスクブランチへの PR のマージで承認する

- 日付: 2026-10-13（UTC）
- タスク: PBI-57
- PR: #67
- ブランチ: feat/issue-57-step-pull-requests
- 関係する ADR: [Git 管理のリポジトリでは、要求要件・設計を工程ごとにタスクブランチへの PR にし、そのマージを人の承認とする](../adr/20261013-1318-superseded-step-pull-request-approval.md)、[タスクブランチに sacty が積んでいない変更があれば、実装を積まずに止め、人の変更を自動では取り込まない](../adr/20261013-1318-stop-on-unexpected-task-branch-changes.md)

## 目的

Git 管理のリポジトリで、人の承認が要る工程（要求要件・設計）ごとに PR を作り、承認をマージにする。受け入れ条件の要点は次のとおり。

- タスクブランチが作られ、要求要件・設計の PR が成果のファイル入りで順にタスクブランチへ作られる。
- マージで承認として記録されて次に進み、PR を作った工程は画面から承認できない。
- PR の指摘を取り込み、ゴールガーディアンがやり直しか差し戻しかを判断して台帳に残す。前の工程に戻したら直しの PR を作り、後ろの PR を作り直す。
- 設計の PR のマージの後、タスクブランチで実装し、実装の PR をベースブランチへ作る。
- 承認が要らない工程・調査だけのタスクでは PR を作らない。中止したら sacty が作った PR をすべて閉じ、ブランチを消す。

## したこと

- イベント（`packages/core/src/events.ts`・`packages/core/src/projection.ts`）：`TaskBranchCreated`・`StepBranchPushed`・`StepPullRequestPublished`。
  `StepsChosen` に成果のファイルの置き場所（任意）。マージ・クローズ・指摘の取り込みは既存のイベントを工程の PR にも広げて使う。
- リポジトリの操作（`apps/daemon/src/repository.ts`）とデーモン（`apps/daemon/src/service.ts`・`apps/daemon/src/prompts.ts`）：タスクブランチの作成、
  成果のファイル（既定 `docs/sacty/<短いID>/requirements.md`・`design.md`）の PR、マージでの承認、指摘の取り込みとゴールガーディアンの判断、
  直しの PR と後ろの PR の作り直し、中止での PR の閉じとブランチの削除、要求要件・設計の無いタスクでは作らないこと。
- 画面（`apps/web/src/components/pull-request.tsx`・`apps/web/src/app/tasks/[id]/review/page.tsx` ほか）：承認の画面に PR への案内（承認の
  ボタンは出さない）、状態の表示（「設計の PR のマージ待ち」など）、PR の欄に工程の PR の一覧・タスクブランチ・戻し先。作業履歴・
  Slack の通知（`apps/daemon/src/notifier.ts`）の PR のリンク。ja/en。
- `README.md` に「PR での承認」の節。
- レビューの対応：実装を積む前に、タスクブランチに sacty が積んでいない変更があれば、実装の PR を出さずに止める。

## 確かめたこと

- `npm run lint`・`npm run typecheck`・`npx vitest run`（635 件）・`npm run build` が通った。レビューの対応の後、レビューでは 636 件・
  lint・typecheck の成功を確かめた。
- 受け入れ条件ごと・境界（設計を省く・調査だけ・不具合の修正・分割の子）・競合（中止の前後のマージ、閉じられた PR、違う内容でのマージ、
  状態の確認中の差し戻し、PR の作成中の中止、再起動の後の続き、作り直しの途中で止まった、差し戻しの上限）のテスト。実際の git を使う
  テストも 1 件。
- 主要な処理を 24 か所わざと壊し、21 か所でテストが落ちた。残り 3 か所は、効いていなかった条件（消した）、いまの流れでは起きない
  食い違いの守り、ローカルの git では確かめられない消えたブランチの削除。
- 未確認：実際の GitHub での動作（タスクブランチへの PR・ブランチの削除）と画面の動画（GitHub の PR が要るため）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 実装の公開で、リモートの最新を親にしつつ起点のままの作業領域からツリーを作るので、人がタスクブランチに積んだ変更（ベースブランチのマージも同じ）を打ち消すコミットができ、そのまま push される（実際の git で再現） | 実装を積む前に、sacty が最後に積んだコミット（無ければ起点）からタスクブランチの最新までに変わったパスを確かめ、要求要件・設計のファイルのほかに変更があれば、変わったパスを示して一時停止するようにした。人がその変更を取り除いて再開すると実装の PR を出す。テストで確かめていないコードが PR に混ざるので、自動の取り込みはしない。実際の git で見つけること・公開を止めて再開で出すこと・出し直しのときに sacty 自身の変更と取り違えないことのテストを足した |

## 残したこと

- 実装の作業領域は起点のコミットのまま。人がタスクブランチに要求要件・設計のファイル以外の変更を直接積んだときは、止まって人の対応を待つ。
- 実装の工程からの設計の変更の申し出をゴールガーディアンが認めても、リポジトリの `design.md` は更新しない。
- 実際の GitHub での動作と画面の動画の確認。
