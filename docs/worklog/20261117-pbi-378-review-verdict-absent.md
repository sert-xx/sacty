# PR のレビューの判定が無い回を、レビューが付けなかった回と、読めなかった回に分けて伝える

- 日付: 2026-11-17（UTC）
- タスク: PBI-378
- PR: #413
- ブランチ: feat/pbi-378-review-verdict-absent
- 関係する ADR: なし

## 目的

sacty が PR に投稿するレビューの判定の行が、「読み取れませんでした（本文の指摘を確かめてください）」になった回が、2026-11-17 に 2 回あった。
本文にはレビューの結果が書かれていて、判定だけが無かった。原因を調べて直す。

受け入れ条件の要点（調べた後に固めたもの）：

1. 判定が無かった 2 回の答えの形を写したデータで、sacty が「レビューが判定を付けなかった」と読み分け、PR の本文と作業履歴に、そのとおりに出る。
2. 本文の記述（「指摘：なし」など）から、判定を推し量らない。判定のブロックが無い・読めない答えを、指摘なし・提案ありにしない。判定を付けた跡があるのに読めない答えは、今までどおり「読み取れませんでした」にする。
3. 判定が無い理由が、作業履歴に残る。
4. 仕様書・ユーザードキュメント（日英）・作業履歴を合わせる。

## 調べたこと（原因）

2 回の実行の記録（エージェントの最後の答えと、実行のログ）を読んだ。確かめられたこと：

- どちらの答えにも、判定のブロック（`sacty-review-verdict`）が無かった。付いていたのは、1 回はリスク評価のブロックだけ、もう 1 回は行へのコメントのブロックとリスク評価のブロックだった。
- 答えは途中で切れていない（どちらも、エージェントが自分で終えている）。付いていた JSON のブロックは、どれも読めた。判定のブロックが 2 つある・形が崩れている、ということも無かった。
- どちらの回も、レビューのエージェントは、観点ごとの担当（サブエージェント）を 1 つも起動していなかった。本文に、「観点ごとの担当は起動していません。親が 1 人で、…を読みました」と書いていた。
- レビューの指示は、「見られなかった観点があるときは、要修正の指摘があれば `changes_required` を付け、無ければ判定を付けない」としている（PBI-343）。2 回の答えは、この指示のとおりの形になっている。
- sacty の読み取り（`extractReviewComments`）は、判定のブロックが無い答えを、判定なしとして正しく扱っていた。

つまり、sacty が判定を読み損ねたのではない。レビューが、見ていない観点があるので、判定を付けなかった。
投稿する本文の「読み取れませんでした」という文が、この 2 つを区別せず、読み損ねたように伝えていた。

推測（確かめられていないこと）：

- エージェントが、指示のこの決まりを意識して判定を省いたのかどうか。エージェントの考えの中身は、実行の記録に残っていない。
- 差分の大きい PR でだけ起きた理由。同じ日のほかのレビューの実行にも、担当を起動しなかった回が多くあったが、それらは判定を付けていた（下の「残したこと」）。

ほかの種類の判定：

- 最終レビュー・統合レビューの指示には、判定を付けない選択肢が無い。判定が無い・読めないときは、理由を作業履歴に残して、やり直す（既にある仕組み）。
- 提出の前のセルフレビューは、報告が無ければ「記録なし」として扱い、工程を止めない。
- 「指示が、判定を付けないことを認めている」のは PR のレビューだけなので、同じ型は、ほかの種類の判定では起きない。

## したこと

- `packages/core/src/events.ts`：判定が無い理由 `ReviewVerdictMissing`（`absent`：答えに判定のブロックが無い。`invalid`：ブロックはあるが読めない）を足し、`AgentRunCompleted` に `reviewVerdictMissing` を足した（判定があるとき・これより前の作業履歴には無い）。
- `packages/core/src/projection.ts`：回ごとの `reviewVerdicts` に `missing` を足した。判定がある回には残さない。
- `apps/daemon/src/prompts.ts`
  - `extractReviewComments`：判定が無いときに、理由を返す。答えに判定の見出しが書かれているのに、JSON として読めたブロックが無いとき（末尾のカンマ・途中で切れた・見出しを本文に書いただけ）は、`invalid` にする。付けようとして形が崩れたものを、「付けなかった」と伝えないため。判定の読み取りそのもの（どの答えを、どの判定にするか）は、変えていない。
  - `buildReviewBody`：`absent` の回の判定の行を、「判定：付いていません（レビューが判定を付けませんでした。見ていない観点がある・対象を読めなかったレビューには、判定を付けません。本文を確かめてください）」にした。`invalid` の回と、理由の記録が無い回（これより前の作業履歴）は、今までどおり。
  - レビューの指示：判定を付けないときは、付けない理由（見ていない観点・読めなかったもの）を総評に書く、と足した。指示の中の「sacty は判定を読めなかったものとして本文に書き」は、「判定が付いていないことを本文に書き」に直した。
- `apps/daemon/src/service.ts`：レビューの工程の完了の記録に、判定が無い理由を載せる。
- `apps/web`：タスクの詳細の「関連するタスク」の、子タスクの最後の回の表示に、「判定が付いていない」（英語は `no verdict given`）を足した。
- docs：仕様書 `docs/spec/tasks-and-steps`（日英）、ユーザードキュメント `docs/user/intake`（日英）。

決めたこと：

- 本文から判定を推し量る読み取りは、足さなかった。判定が無かった 2 回の答えは、「見ていない観点がある」と書いたうえで判定を省いている。これを「指摘なし」と読むと、見ていない所があるレビューを、指摘なしとして扱うことになる。
- 判定が無い回の下流の扱い（元のタスクへ、指摘として届ける。指摘なしとして扱わない）は、変えていない。
- 方針は変えていない（表示と記録の区別だけ）ので、ADR は足していない。

## 残したこと

- PR のレビューのエージェントが、観点ごとの担当を起動せずに、親が 1 人で見る回が多い。2026-11-17 の、答えを読めたレビューの実行 26 回のうち 23 回で、担当を 1 つも起動していなかった（うち 21 回は判定を付け、2 回は付けなかった）。既定のスキルは、PR のレビューでは観点を絞らないとしている。担当を起動しなかったレビューの判定を、どう扱うか（付けさせない・付けさせる・起動を強める）は、方針の決定なので、この PR では決めていない。
