# 後続に回した指摘の扱いの結果をタスクの詳細に出し、後続のタスクを元の PR の引き継ぎの候補にしない

- 日付: 2026-11-17（UTC）
- タスク: PBI-384
- PR: #422
- ブランチ: feat/pbi-384-deferral-task-result
- 関係する ADR: [後続に回した指摘の扱いの結果をタスクの詳細に出し、後続のタスクを元の PR の引き継ぎの候補にしない](../adr/20261117-1245-show-deferral-results-on-task-details.md)

## 目的

後続に回すと決めた指摘の扱いに「sacty の後続のタスクを作る」を選んだとき（PBI-370）の、見直しのレビューで見つかった 2 点を直す。

1. 後続のタスクを作った・作れなかったことが、完了したタスクの詳細で読める。仕様書・ユーザードキュメントと、コードを合わせる。
2. 後続のタスクが、元の PR の引き継ぎの候補にならない（引き継ぐと判断されて、工程を決めずに止まらない）。

後続のタスクの依頼の文（題と依頼は sacty が決めた文だけ。指摘は JSON のデータ）は、変えない。

## したこと

- 画面（`apps/web`）
  - タスクの詳細に、後続のタスクか Issue を作る扱いの指摘と、その結果の一覧を足した（`deferral-handled.tsx` の `DeferralHandledNotice`）。タスクの状態によらず出す。できなかった指摘があれば、注意の色にする。中止したタスクでは、結果の記録がある指摘だけを出す。
  - 扱いと結果の 1 行（リンク・できなかった理由・予定）を、承認の画面の決定済みの記録と共有した（`DeferralHandledLine`）。承認の画面の出し方は、変えていない（後続のタスクへのリンクは、画面の中の移動のリンクにした）。
  - 見出しの文言を、日英で足した（「後続に回した指摘の扱い（N件）」）。
- デーモン（`apps/daemon`）
  - 人が後続に回すと決めた指摘の後続のタスク（作成の記録に、指摘の ID がある）を、既存の PR の引き継ぎの候補から外した（`continuablePullRequest`）。オーケストレーターに、引き継ぐかを決めさせる項目を出さず、答えにあっても読まない。
  - sacty が説明に足した記録（続きのタスクの元のタスクの記録・再実行で作ったタスクの前の試行の記録）の中のリンクを、引き継ぎの候補にしないようにした（レビューの対応。人が書いた題と説明だけを見る。`rerunEditableBody`）。
- docs
  - 仕様書（`approval`・`tasks-and-steps`）とユーザードキュメント（`tasks`）を、日英で直した。後続のタスクの結果が出る場所を、タスクの詳細に直した。
  - ADR を足した。

決めたことと理由は、ADR に書いた。

- 足したテスト

  - `apps/daemon/src/daemon-step-pull-requests.test.ts`：元のタスクを完了させて作った後続のタスクで、オーケストレーターが「タスクにある PR を引き継ぐ」と答えても、PR を確かめに行かず、工程を決める。オーケストレーターへの指示に、引き継ぐかの項目が出ない。同じ依頼でも、後続に回した指摘の記録が無い続きのタスクは、今までどおり候補になる。
  - 修正（`continuablePullRequest` の 1 行）を戻すと、このテストが落ちる（工程が空のまま、一時停止になる）ことを確かめた。
- 実物での確認（別のポート 4866・4867、一時のホーム。GitHub には問い合わせず、偽の応答で受けた）
  - 台帳は、結合テストが作ったもの（後続のタスクを作って完了したタスク・作れずに完了したタスク）を、そのまま置いた。
  - 日本語と英語の画面で、次を確かめた（確かめた 20 項目がすべて合った）。
  - 完了したタスクの詳細に、「後続に回した指摘の扱い（1件）」と、後続のタスクへのリンクが出る。リンクを押すと、後続のタスクの詳細が開く。
  - 作れなかったタスクの詳細には、理由（プロジェクトに対象が無い）が、注意の色で出る。
- 確かめられなかったこと
  - 実物のエージェントでの、後続のタスクの工程の選択（実際の AI と Docker、マージ済みの PR が要るため。結合テストで、オーケストレーターの答えを差し替えて確かめた）。
  - 直す前に、実際のエージェントが「引き継ぐ」と答えるかどうか（エージェントの判断しだい）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 【提案】仕様書で、扱いの選択の説明が、承認の画面の項から、タスクの詳細の項へ移っている（日英） | 文を、承認の画面の項へ戻した（日英）。タスクの詳細の項には、一覧と結果だけを書いた |
| 【提案】同じ原因で止まる経路が、人が作った続きのタスクに残る（元のタスクの記録に、マージ済みの PR の URL が必ず入る） | 続きのタスクでは、sacty が足した元のタスクの記録の中のリンクを、引き継ぎの候補にしないようにした（`withoutDerivedRecord`。作成のときに記録した本文そのものを除く）。人が題か依頼に書いたリンクは、今までどおり候補にする。理由を ADR に書いた。人が作った続きのタスクで、オーケストレーターが引き継ぐと答えても工程を決めること、記録を除く直しを戻すと落ちることを、テストで確かめた |
| 【提案】英語の見出しが、プロジェクトの設定の欄と同じ名前（Handling of deferred findings） | 英語の見出しを `Results for deferred findings (N)` に変え、ユーザードキュメント（英語）もそろえた |
| 【提案】結果の一覧に指摘の文が無く、複数件のときに見分けにくい | 各行に、指摘の文を 2 行までで添えた（全文は、マウスを載せると読める） |
| 補足：`handling: "none"` を持つ決定と、中止したタスクの失敗の結果（注意の色）のテストが無い | 両方のテストを足した |

## 残したこと

- 作った後続のタスクは、もとから、完了したタスクの詳細の「続きのタスク」にも並ぶ。作れなかったことは、そこには出ない。
- マージ済み・閉じた PR を、人が作ったタスクでも引き継ぎの候補から外すことは、していない（ADR の理由のとおり）。
