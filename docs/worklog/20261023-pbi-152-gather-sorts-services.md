# 情報収集にサービスの起動のルールを伝え、オーケストレーターがそのまとめからサービスを確定させる

- 日付: 2026-10-23（UTC）
- タスク: PBI-152
- PR: #211
- ブランチ: feat/issue-152-gather-services
- 関係する ADR: [情報収集がテストと動作確認に要るサービスを分け、オーケストレーターはそれをもとに依存だけを起動させ、対象のアプリは工程がコンテナの中で起動する](../adr/20261023-1410-gather-sorts-services-for-orchestrator.md)

## 目的

テストとアプリの起動ができるかを試すタスクで、調査の工程が、sacty が起動した DB と Redis を使わずに「Docker が使えないので、アプリの起動は確かめられない」と報告した。
情報収集が、自分のコンテナ（既定のイメージ・サービスなし）で確かめたことを後の工程の事実としてまとめに書き、オーケストレーターと工程の指示もアプリの起動のしかたを伝えていなかった。
情報収集に sacty のサービスの仕組みを伝えてサービスを分けさせ、オーケストレーターがそれをもとにサービスを確定させるようにする（ステークホルダー）。

## したこと

- `apps/daemon/src/prompts.ts`
  - `gatherServiceLines` を足し、作業するリポジトリがある（トリアージで決まるものを含む）タスクの情報収集の指示に「実行の環境とサービス」の節と、まとめの見出し「テストと動作確認に要るサービス」を足した。
    自分のコンテナの環境を後の工程の事実にさせないこと、sacty が工程ごとにサービスを起動すること、要るものを3つ（対象のアプリ・起動できる依存・compose に無い依存）に分けることを書く。
    共用の compose があれば、compose に無い依存の候補として並べる。手順の番号は変えていない。
  - `buildGatherPrompt` に `sharedComposes` を足した。
  - オーケストレーターの services の指示から「アプリ本体など、要らないサービスは含めない」と「localhost ではない」を除き、対象のアプリは含めず依存は含めること・build の有無でなく何を動かすかで分けること・情報収集の分類をもとに確定させることを足した。
  - `servicePromptLines` の案内に、このリポジトリのアプリは docker を使わずにコンテナの中で起動してサービスにつなぐよう足した（行は増やしていない）。
- `apps/daemon/src/service.ts`：情報収集に、プロジェクトの共用の compose の名前・ファイル・説明を渡す（取得の先は渡さない）。
- テスト：`prompts.test.ts`（情報収集の節・共用の compose の有無・リポジトリの無いタスクでは足さない・オーケストレーターの文言・サービスの案内）、`daemon.test.ts`（プロジェクトの共用の compose が情報収集の指示に入る）。
- 仕様書（`spec/tasks-and-steps` の「実行の環境とサービス」、`spec/services` の「いつ起動するか」）・ユーザードキュメント（`user/compose`）の日英、ADR を足した。
