# ビルドキャッシュの片付けの後はイメージを最初から作り直すことを、文書に正しく書く

- 日付: 2026-11-18（UTC）
- タスク: PBI-391
- PR: #430
- ブランチ: feat/pbi-391-build-cache-prune-rebuild-docs
- 関係する ADR: [ビルドキャッシュの片付けの後はイメージを最初から作り直すと分かったうえで、期間の絞り込みの無い片付けを続ける](../adr/20261118-0820-keep-ageless-build-cache-prune-with-full-rebuild.md)

## 目的

PBI-389 で、ビルドキャッシュの片付けを、期間で絞らない `docker builder prune -f` にした。
そのときの文書は、「片付けの後は、いまあるイメージと共有していない層を作り直す」「共有している層は残る」と書いた。
実測では、片付けの後のビルドはキャッシュに1手順も当たらなかった（層の実体は残るが、キャッシュとしては使われない）。
リポジトリの持ち主は、動きは変えずに続けると決めた。文書と、同じ誤りのあるコードのコメントを、実測に合わせる。

受け入れ条件の要点：

1. ユーザードキュメント（日英）の `image build` の説明・OS の更新を取り込む手順・ディスクの行を、今の動きに合わせる。
2. 仕様書（日英）に、片付けの後のビルドがキャッシュに当たらないことを、確かめた環境を添えて書く。
3. ADR を足す（実測・続ける決定・理由・失うもの・採らなかった案）。PBI-389 の ADR との関係は、ADR の規則に従う。
4. 作業履歴を足し、`npx vitest run tests/docs` を通す。
5. コードの動きは変えない。

## したこと

ADR：

- 新しい ADR を足した。PBI-389 の ADR（期間の絞り込みをやめた決定）は、「影響」の見込みだけを置き換えたので、ファイル名に `superseded` を付け、`ステータス` と `置き換え先` を直した（本文は書き換えていない）。
  一部だけの置き換えなので、`置き換え先` に、置き換えた部分（「影響」の見込み）と、期間で絞らない決定はそのままであることを書いた。
- 名前の変更で切れるリンクを直した（ADR 2件と、PBI-389 の作業履歴の「関係する ADR」）。

ユーザードキュメント（日英）：

- `docs/user/cli.md` の `sacty image build`：「共有している層は残ります」を、「ディスクには残るが、消した後のビルドでは使わない」に直した。続けて実行しても毎回最初から作り直すことと、確かめた環境を足した。
- `docs/user/images.md` の「コンテキストのイメージ」：同じ直しに加えて、消した後に作ったキャッシュは次に消すまで使うことを書いた。
- `docs/user/images.md` の「OS のセキュリティの更新を入れる」：「`image build` はビルドのキャッシュを使うので、作り直しただけではパッケージを取り直さないことがある」という前提をやめた。
  sacty が入れるコマンドは、作り直すと取り直す。ビルドのログに `CACHED` と出た手順があれば、`docker builder prune` で消してから作り直す、という手順にした。
  元のイメージにあるコマンドの更新は元のイメージの側で入れる、という手順は残した。
- `docs/user/troubleshooting.md` のディスクの行：`npx sacty image build` は最初から作り直すので時間がかかること、片付けるのはすべて作れた後なので、空きが足りずに作れないときは先に次の手順へ進むことを足した。

仕様書（日英）：

- `docs/spec/agent-execution.md` の `sacty image build` の項：片付けの後のビルドがキャッシュに当たらないこと、層の実体は残ること、片付けは作り終えた後に1回走ること、確かめた環境を書いた。
  「ビルドのキャッシュ」の先頭に、層のキャッシュと cache マウントが効くのは片付けを挟まないビルドの間だけ、と書いた。cache マウントの項に、片付けの後に記録が残っていなかったことを書いた。
- `docs/spec/daemon-lifecycle.md` の「コンテキストのイメージの作成」：片付けの後に作るイメージが最初から作り直しになることを書き、詳しくは `sacty image build` の項へ向けた。

コードのコメント（動きは変えていない）：

- `apps/daemon/src/image.ts` の `buildCachePruneArgs`：片付けの後のビルドがキャッシュに当たらないことを足した。
- `packages/cli/docker/Dockerfile`：cache マウントの説明（`sacty-build-cache`）の「ビルドのキャッシュが消えたときも取り直さない」を外し、片付けを挟むとマウントの中身も消えて取り直す、と書いた。
  npm の cache マウント（`sacty-npm-cache`）の「CLI の版を上げても、変わらないパッケージは取り直さない」に、片付けを挟まないビルドの間は、という条件を添えた（レビューの対応）。

コードと照合したこと：

- `packages/cli/src/index.ts`（`imageBuild`）：名前ごとに `docker build` を実行し、すべて作れた後に1回だけ `pruneOldImages` を呼ぶ。作るのに失敗すると例外で止まり、片付けは走らない。
- `apps/daemon/src/image.ts`（`imageBuildArgs`）：`docker build` に `--no-cache`・`--pull` は付けない。
- `packages/cli/docker/install-tools.sh`：作業用の CLI を入れる手順は、毎回 `apt-get update` をしてから、元のイメージに無いものだけを入れる（`upgrade` はしない）。手順が実行し直されれば、その時点の版を取る。
- `packages/cli/docker/with-build-cache.sh`：パッケージの一覧は cache マウントに置かない。置いた `.deb` は、一覧のハッシュと合うときだけ使う。cache マウントが残っていても、新しい版は取り直す。

## 確かめたこと

- `npx vitest run tests/docs`：93 件が通った。
- `npm run lint`（biome。フォーマットの確かめを含む）：指摘なし。
- `npx vitest run apps/daemon/src/image.test.ts apps/daemon/src/with-build-cache.test.ts`（コメントを直したファイルに関係するテスト）：31 件が通った。
- 直した節を、日本語の版と英語の版で読み比べた。
- 「キャッシュ」「cache」「共有してい」「取り直」を、ユーザードキュメント・仕様書・README・コードで探し、「共有している層は残る」「作り直しただけでは取り直さないことがある」と読める記述が残っていないことを確かめた（このとき、Dockerfile の npm の cache マウントのコメントを見落としていた。レビューの対応で直した）（置き換え・過去の ADR と作業履歴は直さない）。
- 実測（リポジトリの持ち主との調査。2026-11-18。Rancher Desktop、Docker 29.5.3、buildx v0.35.0、BuildKit v0.30.0）は、ADR の表のとおり。このタスクでは、片付け・イメージの作成・削除は実行していない。
- `docker version`・`docker buildx version`：サーバーは 29.5.3、buildx は v0.35.0（BuildKit の版は、このタスクでは読み取っていない。調査のときの値）。
- `docker buildx du --verbose`（読み取りだけ）：記録は 88 件で、すべて種類が `regular`、イメージと共有（Shared 12.03GB、Private 0B）。種類が `exec.cachemount` の記録は0件だった。
  片付けの後の状態で、cache マウントの記録は残っていない。片付けの直前に記録があったことは、この読み取りでは確かめていない（その前のビルドは cache マウントを使う手順を実行している）。

レビューの後に、リポジトリの持ち主が足した実測（同じ環境。2026-11-18。このタスクでは実行していない）：

- cache マウントの前後の比較：`RUN --mount=type=cache` を持つ小さな Dockerfile を、build-arg を変えて3回作ると、2回目から中身が残っていた（`docker buildx du --verbose` に `exec.cachemount` が1件。同じ ID のまま、使用回数が増えた）。
  `docker builder prune -f` の後は、`exec.cachemount` の記録が0件になり（`source.local` の2件も消えた）、次のビルドではマウントの中身が空だった。
  試したのは小さな Dockerfile で、`sacty-build-cache`・`sacty-npm-cache` のマウントそのものではない。
- `docker build --no-cache` で作ると、cache マウントも毎回新しくなった（ID が毎回変わり、中身は空）。
- 既定のイメージを2回作り直した後、`docker images -f dangling=true` に sacty のイメージは無かった（無関係の小さなものが2つだけ）。作り直しても、前のイメージがタグの無いまま残ることは、この環境では無かった。

レビューの対応の後に、もう一度確かめたこと：

- `npx vitest run tests/docs`：93 件が通った。`npm run lint`：指摘なし。
- `npx vitest run apps/daemon/src/image.test.ts apps/daemon/src/with-build-cache.test.ts`：31 件が通った。

確かめられなかったこと：

- 層の実体が残るのに、キャッシュとして使われない理由。
- デーモンの片付けの後のビルド（同じ引数なので同じになると見ているが、試していない）。
- 容量の上限つきの片付けの、12GB と 2GB の間の値。
- ほかの版の Docker・BuildKit での動き。
- 言語ごとのイメージ・コンテキストのイメージを最初から作り直す時間。
- デーモンがコンテキストのイメージを作った後のキャッシュに、`sacty image build` の手順が当たるか（片付けを挟まなければ同じ Dockerfile で当たることは実測にあるが、既定のイメージとコンテキストのイメージの間では試していない）。
  ユーザードキュメントは、`CACHED` と出たら消して作り直す、という手順で受けている。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| （自分での見直し）仕様書で、「片付けは作り終えた後に1回走る」（コードで確かめたこと）まで、「確かめた環境での動き」にまとめていた | 環境を添えるのを、キャッシュに当たる・当たらないの動きだけにした |
| （自分での見直し）ADR で、デーモンの片付けの後のビルドも最初から作り直す、と言い切っていた（試したのは、`sacty image build` と、手での片付けの後） | 同じ引数なのでそうなると見ている、試していない、と書いた |
| （自分での見直し）英語の版で、確かめた環境の文が、括弧の中の文になっていて読みにくい | 日英とも、括弧の外の文にした |
| （PR のレビュー 1）確かめていないことを、確かめた事実のように書いている（Dockerfile の cache マウント、仕様書の「ビルドのキャッシュ」の先頭、デーモンの片付けの後のビルド、ADR の「失うもの」） | cache マウントは、持ち主の足した実測（小さな Dockerfile での前後の比較）で「片付けで消える」と書き、sacty のマウントそのものでは比べていないと添えた。デーモンの片付けの後のビルドは、仕様書・ユーザードキュメント（日英）・ADR とも「同じ引数なので同じになると見ている（試していない）」に揃えた |
| （PR のレビュー 2）採用中の cache マウントの ADR（2026-11-12）との関係が無い | 「一部だけ置き換えるとき」の規則で、その ADR に `superseded` を付け、新しい ADR の `置き換え元` に足した。置き換えたのは、「層のキャッシュが外れても、マウントにあれば取り直さない」が片付けの後にも成り立つという読み方だけ。名前の変更で切れるリンクを直した |
| （PR のレビュー 3）「`docker system df` の量は減らない」が、共有している分だけだと読み取れない | 仕様書（日英）と ADR を、「その分は減らない。共有していない分は消える」に直した。ADR の「得るもの」は、量（32.58GB が消えて 14.1GB が残った・14.79GB のうち共有していない分は 3.1GB）で書いた |
| （PR のレビュー 4）Dockerfile の npm の cache マウントのコメントが、直した箇所と食い違う | 片付けを挟まないビルドの間は、という条件を添えた。「したこと」にも足した |
| （PR のレビュー 5）`troubleshooting.md` のディスクの行のセルが長く、分岐が埋もれている | セルを元の短さに戻し、分岐（作成がエラーで止まったら手順 3 を先にして、もう一度手順 2）を表の下の文にした（日英）。作り直すと前のイメージがタグの無いまま残る、という推測は、持ち主の実測で、この環境では残らなかったので、手順は足していない |
| （PR のレビュー 6）`CACHED` が出る場面が書かれていない | 前の作成が途中で失敗したとき・片付けに失敗したとき、と添えた（どちらも、片付けが走らないことをコードで確かめている）。デーモンが作ったキャッシュに当たるかは試していないので、書いていない |
| （PR のレビュー 7）容量の上限つきの案が、試した範囲より強く言い切られている | 試した値（100GB・12GB・2GB）と、12GB と 2GB の間は未確認であることを書いた |
| （PR のレビュー 8）「今日より前」・「ビルドのキャッシュ／ビルドキャッシュ」の揺れ | 日付（2026-11-18 より前）にした。`cli.md`・`images.md` の「コンテキストのイメージ」に足した文を、その節の「ビルドキャッシュ」に揃えた |

## 残したこと

- 2026-11-18 より前（期間つきの片付けの頃）に、既定のイメージが版ごとに最初から作り直されていた理由は、分かっていない（このタスクの範囲の外）。
- 片付けの頻度・方式は変えていない（持ち主の決定）。
