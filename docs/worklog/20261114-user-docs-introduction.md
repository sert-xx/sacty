## 目的

sacty をはじめて知る人が、細かい設定や実装に入る前に、sacty で何ができて何がうれしいのかをつかめるページを作る。
長い文章や実装の細部を避け、一般的なプロダクトの紹介のように、図とスクリーンショットで「使ってみよう」と思ってもらえる形にする。

## したこと

- `docs/user/introduction.md`・`introduction.en.md`（sacty の紹介）を足した。
  - 冒頭の一文と、依頼から PR のマージまでの流れの図。
  - 「こんなことに困っていませんか」で課題を挙げ、特長を5つ（前提を集めてから動く・作業に合わせて進め方を選ぶ・要所で判断するだけ・
    回すほど賢くなる・安心して任せられる）に分けて、短く書いた。
  - 既存のスクリーンショット（タスクの詳細・監査・ダッシュボード）を使った。新しく撮り直してはいない。
  - 任せられる作業の表・使える AI と組織に合わせた設定・始め方（はじめに・タスクを進める・コンテキストリポジトリへのリンク）。
  - 工程の名前・設定の名前・コードの名前は本文に出さず、詳しいページへのリンクに任せた。
- 図を2つ足した（`scripts/docs-diagrams/diagrams/intro.mjs`。`intro-flow`：依頼から PR のマージまで、`intro-loop`：監査・改修の提案・
  メモリーで次のタスクが良くなる流れ）。`npm run docs:diagrams` で日英の SVG を作った。
- ユーザードキュメントの目次の先頭に紹介のページを置き（番号を1つずつ繰り下げた）、入口の文に紹介のページへの案内を足した。
  リポジトリの README（日英）のドキュメントの節にも、紹介のページへのリンクを足した。

本文の内容は、仕様書（タスクと工程・承認と差し戻し・監査・メモリー・ゲートウェイ・通知）と照らして書いた。
要求要件・設計が PR になるのはリポジトリに置くときだけで、PR にならない成果は画面で承認するため、そのように書いた。

## 追加：コンテキストの層とゲートウェイ

依頼を受けて、紹介のページに次を足した。

- 特長「5. チームのやり方を教えられる」：コンテキストリポジトリを、sacty の既定の上に組織・チーム・プロジェクトの層として重ねることを、
  新しい図 `intro-context` で示した。
- 特長「6. 安心して任せられる」（前の 5）：使い捨てのコンテナと、ゲートウェイが鍵を付けて中継することを、新しい図 `intro-gateway` で示した。
- 最初の版の表の「API キーやトークンは、コンテナに渡しません」は正確でなかったので直した。ゲートウェイを通すのは社内の API・MCP・GitHub の読み取りと、
  `via_gateway` を設定した Codex の AI の呼び出しで、ゲートウェイを通さない AI の認証の値はコンテナに渡る（仕様書「秘密情報」のコンテナへの値の渡し方）。
  表の行は「社内の API・MCP サーバー・GitHub の鍵はゲートウェイだけが持つ。AI の呼び出しも、設定すればゲートウェイを通せる」にした。
- 表に「GitHub を勝手に書き換えないか」の行を足した（コンテナの中の `gh` は読み取りだけで、プッシュと PR は sacty が行う。仕様書「エージェントの実行」「ゲートウェイ」）。
- 「使える AI と、組織に合わせた設定」の節は、組織に合わせた設定を特長 5 に移したので「使える AI」にした。

確かめたこと：`npm run docs:diagrams` で新しい図の警告が無いこと、ライトとダークで描画して重なりが無いこと、`npx vitest run tests/docs` が通ること。
