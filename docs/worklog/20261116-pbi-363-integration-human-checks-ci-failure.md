# 統合レビューの人の確認を承認待ちに出し、指摘なしの後の CI の失敗を画面に出す

- 日付: 2026-11-16（UTC）
- タスク: PBI-363
- PR: #396
- ブランチ: feat/pbi-363-integration-human-checks-ci-failure
- 関係する ADR: [統合レビューで人の確認だけが残った観点は、不合格にせず、人が確かめることとして承認待ちに出す](../adr/20261116-2255-integration-review-human-checks.md)、[指摘なしの後に実装の PR の CI が失敗したら、画面に出す（自動では扱わない）](../adr/20261116-2256-show-ci-failure-after-no-findings.md)

PBI-364（CI の失敗の表示）も、この PR に入れた。どちらも、レビューの結果を人にどう渡すかの変更で、コア・デーモン・画面の同じ所（承認待ちの案内）に触る。

## 目的

複数のリポジトリを指定する機能を sacty 自身に実装させたときに、実物で見つかった次の2つを直す。

- 統合レビューで、作業領域では確かめられず人の確認が要る観点だけが残ったとき、不合格になり、修正の子タスクが作られた。子タスクでは直せない。人が確かめた結果を伝える手段も無かった（PBI-363）。
- PR のレビューの子タスクが CI の実行中に「指摘なし」を出し、その後 CI が落ちても、タスクは人の承認待ちのままで、画面からは分からなかった（PBI-364）。

## したこと

### PBI-363 統合レビューの人が確かめること

- `IntegrationReviewed` に `humanChecks`（任意）を足した（`packages/core/src/events.ts`）。以前の版の記録は、そのまま読める。
- 統合レビューの指示に、作業領域では確かめられないことが残る観点の扱いを足した（`INTEGRATION_HUMAN_CHECK_LINES`）。確かめられる範囲で判定し、残ることを `humanChecks` に書く。`findings` には書かない。作業領域で確かめられることを、確かめずに回さない。
- 答えの読み取り（`extractIntegrationReview`）で `humanChecks` を読む。合否には使わない。同じ項目は1件にし、1件の長さを抑える。答えの JSON を直しながら読む形（`INTEGRATION_REVIEW_SHAPE`）にも項目を足した。
- 不合格で人が確かめることもあるときは、修正の子タスクを足す指示に「子タスクにしない」ものとして渡す（`integrationFindingLines`）。
- 画面：統合レビューの欄（タスクの詳細と承認の画面で同じ部品）に「人が確かめること」を出し、承認待ちの案内に件数を出す。
- 人が確かめた結果を伝える手段は、新しく作らず、統合レビューの承認・差し戻しにした（理由は ADR）。

### PBI-364 指摘なしの後の CI の失敗

- イベント `PullRequestCiFailed`・`PullRequestCiRecovered` と、`Task.pullRequestCiFailure`・判定の `pullRequestCiFailure` を足した。ベースブランチとの競合の表示（`PullRequestConflicted`）と同じ形。
- PR の確認（`checkPullRequests`）で、人の承認を待つ実装の PR の先頭のコミットの CI を読む（`recordPullRequestCi`）。失敗したチェックが変わったときだけ記録し、失敗も実行中のものも無くなったら解消を記録する。
- 読む間隔を空ける（すべて通った先頭は読み直さない・失敗した先頭は5分ごと・CI の無い先頭は30分でやめる）。
- 画面：状態の表示が「実装の PR の CI が失敗」になり、タスクの詳細の承認待ちの案内に、失敗したチェックの一覧を出す。作業履歴の文言を足した。
- 出すだけにした。差し戻し・再レビュー・ドラフトへの変更・CI の再実行・通知は行わない（理由は ADR。自動でどこまで扱うかは、人が決めていない）。

### docs

- 仕様書（日英）：`split-and-integrate`（統合レビュー）、`approval`（「指摘なしの後の CI の失敗の表示」の節・PR の確認の手順）、`tasks-and-steps`（CI を待たないことの行）。
- ユーザードキュメント（日英）：`tasks`（「「指摘なし」の後に CI が失敗したとき」「統合レビューの結果を確かめる」の節）、`dashboard`。
- ADR を2つ足した。

## 確かめたこと

main（#395 までを含む `0ed1a2da`）を取り込んだ後のコードで実行した結果を書く。実際の画面での確認だけは、main を取り込む前のコードで行った（取り込んだ変更は、PR の確認・画面の表示に触れていない）。

- `npx vitest run --no-file-parallelism`：245 ファイル・4710 件が通った（1 件は以前からの skip）。
- `npm run typecheck`：通った。`npx biome check apps packages docs tests scripts`：指摘なし（`npm run lint` は、Git 管理外の `.claude/settings.local.json` の整形の指摘 1 件で落ちる。リポジトリのファイルの指摘は無い）。
- `npm run build`：通った。
- 足したテスト：
  - 統合レビュー：`daemon-split.test.ts`（人が確かめることだけが残ると、合格にして修正の子タスクを作らずに承認待ちにする・直すことがあれば不合格にして、人が確かめることは子タスクにさせない・配列でない／無い答えは今までどおり）、`integration.test.ts`（画面の欄。日英・無ければ出さない）、`live-screens.test.ts`（承認待ちの案内の件数）。
  - CI の失敗：`daemon-implement.test.ts` の 9 件（実行中 → 失敗 → 再実行 → 通った、の一連。失敗したチェックが変わったときの記録し直しと件数の上限。読めない・返らないときに記録を変えず、マージの検出を止めないこと。CI の無い PR を読み続けないこと。先頭が変わったとき・読めなかったとき。閉じて開き直したとき。作業履歴の読み直し。指摘なしを待つ PR は読まないこと）、`labels.test.ts`（状態の表示と作業履歴の文言。競合が先・前の提出の記録や指摘なしを待つ間は出さない）、`live-screens.test.ts`（タスクの詳細の案内。`http`・`https` でないリンクをリンクにしない）。
- 途中で見つけて直したこと：
  - 全テストで、既存のテスト（GitHub の先頭を読めないときのドラフトの扱い）が落ちた。GitHub の先頭が空文字のときに、空のコミットで CI の失敗を記録しようとして、記録の検査で例外になり、PR の確認が止まっていた。先頭が空のときは、指摘なしにした先頭・提出のコミットの順に使い、CI の記録の例外で PR の確認のほかの処理を止めないようにした。テストを足した。
  - PR を閉じて開き直した後、失敗の読み直しの間隔（5分）が残っていて、すぐに出し直さなかった。記録が消えていれば、すぐに読み直すようにした。
  - チェックの名前の切り詰めを、文字の数ではなく UTF-16 の長さで上限に収めるようにした（絵文字の名前で、記録の検査の上限を超えるため）。
- 実際の画面での確認（`scripts/docs-screenshots/` の種データと偽の GitHub を使い、別のポート・一時の `SACTY_HOME`・一時の `HOME` で起動した。動いている sacty には触れていない）：
  - 偽の GitHub が、実装の PR のマージ待ちのタスクの先頭のコミットの CI を「失敗」と答えるようにすると、デーモンが PR の確認で読み取り、タスクの状態が「実装の PR の CI が失敗」になり、承認待ちの案内に、読んだコミット・sacty は自動では直さないこと・失敗したチェック（`CI`・`test (unit)`。リンク付き）が出た。作業履歴に「PR #128 の CI が失敗している」が出た。
  - 偽の GitHub の答えを「成功」に切り替えると、読み直しの間隔（5分）の後に表示が消え、作業履歴に「PR #128 の CI の失敗が無くなった」が出た。
- 確かめていないこと：
  - 実際の統合レビューのエージェントが、足した指示のとおりに、人が確かめることを `humanChecks` に分けるか（指示の文と、答えの読み取り・合否・画面は、テストで確かめた）。
  - 統合レビューの欄の「人が確かめること」の、実際のブラウザでの見え方（種データに統合レビューのタスクが無い。部品の描画は jsdom のテストで確かめた）。
  - 実際の GitHub の CI での動き。

## 残したこと

- CI の失敗を自動で扱うこと（実装の工程へ差し戻す・レビューの子タスクに再レビューさせる・CI が終わるまで指摘なしやドラフトの解除を待つ）。人が決める。
- CI の失敗の通知（Slack・デスクトップ）。
- 人が確かめた結果を、項目ごとに記録すること。
- ユーザードキュメントのスクリーンショット（統合レビューの欄・承認待ちの案内）は、足していない。
