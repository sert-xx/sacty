# コンテキストの合成で、ゲートウェイの外部 PF の設定も扱う

- 日付: 2026-10-14（UTC）
- タスク: PBI-74
- PR: #83
- ブランチ: feat/issue-74-context-platforms
- 関係する ADR: [コンテキストリポジトリの層の platforms.yaml で、プロジェクトごとのゲートウェイの外部 PF を mcp.yaml と同じ規則で定義する](../adr/20261014-0534-context-platforms.md)

## 目的

コンテキストの合成で、ゲートウェイの外部 PF（プラットフォーム）の設定も mcp.yaml と同じように扱えるようにする。層に PF の設定のファイルを置け、
認証は秘密情報の名前で参照し、合成の規則は MCP と同じにする。ほかのプロジェクトの PF は使えないようにし、チケットの取り込みなど PF の名前を
参照するほかの機能でも使えるようにする。設定の誤りの表示・画面・README も揃える。

## したこと

- 層の `platforms.yaml`（`platforms: { <名前>: … }`）を読む。書ける項目は `gateway.platforms` と同じ（upstream・description・auth・allow）で、
  名前の規則も同じ。`sacty context init` の雛形と既定のコンテキストの README にも足した（`apps/daemon/src/context.ts`・`context-template.ts`）。
- 合成：`mergeNamed` に `platforms` を足し、下位の層が上書きし、`locked.platforms`・`remove.platforms` も使える。ホストの `gateway.platforms` と
  同じ名前ならホストのものを使い、`context.hostPlatform` の警告を作業履歴と画面に出す。
- 認証の値は、ホストのゲートウェイだけが使うときに取り出す（`PlatformCredentials`）。エージェントに渡すファイル・プロンプト・作業履歴・画面には、
  名前・層・説明・allow だけを出す。
- 分離：コンテキストの PF は、その実行のトークンにだけ登録する（`AiGateway.register` の3番目の引数）。ゲートウェイはホストの PF を先に、次に
  その実行の PF を引く。ほかの実行のトークンでは 404 にし、上流に送らない（`apps/daemon/src/gateway.ts`）。
- チケットの取り込み・トリアージ・結果のコメント・成果の書き出しで、コンテキストの PF も使える（`service.ts`・`intake.ts`・`platforms.ts`）。
  ホストに無い名前のときだけコンテキストを取得し、取り込みでは1回の取り込みでプロジェクトごとに1度だけ取得する（セルフレビューで直した）。
- 誤りの表示：形の誤りは `context.fileInvalid` で層と `platforms.<名前>.<項目>` を示して止める。認証を用意できないときは、ゲートウェイの 502 に
  `(platforms.yaml of <層>)` を添える。
- 画面：プロジェクトの設定に「使える外部 PF」の区画（名前・どこで定義したか・説明・使える API）を足し、作業履歴の「コンテキストを用意」にも出す。
  チケットの取り込み先の選択肢にもコンテキストの PF を入れた。
- README の外部 PF の API の節の下と、既定のコンテキストの README・雛形に書き方を足した。信頼の考え方（コンテキストリポジトリに書いた PF は、
  書いた秘密情報を書いた転送先に送る）も README に書いた。
- レビューの指摘を受け、コンテキストの PF のチケットをプロジェクトとあわせて識別するようにした（下の表）。

## 確かめたこと

- 回帰テスト：層ごとの定義と上書き・locked/remove、ホストとの同名、ほかのプロジェクトの PF を使えないこと（ゲートウェイ・登録）、秘密情報の名前の解決と
  見つからないとき、誤った設定（8通り）、取り込み・トリアージ・コメント・書き出し、PF の設定の無いプロジェクト。修正を戻す17通りの変更を試し、すべて落ちた。
- lint・typecheck・テスト・build が通った。
- 一時の SACTY_HOME で起動し、ローカルの git のコンテキストリポジトリ（上位の層 → 下位の層）で手で確かめた（本物の AI・本物の PF は使っていない）：
  `platforms.yaml` のあるコンテキストのプロジェクトをインポートし、「使える外部 PF」に config.yaml・上位の層・下位の層の PF が出ること、同じ名前で警告が
  出ること。取り込み先に下位の層や上位の層の PF を選べること。allow の無い `platforms.yaml` のプロジェクトでは、層と `platforms.docs.allow` が示され、
  config.yaml の PF だけが出ること。動画を PR に添付した。
- レビューの指摘への対応の後：同じ名前・同じキー・違う接続先の2プロジェクトで、両方保存できること、それぞれのチケットが別のタスクになり二度は取り込まないこと、
  調査の結果のコメントがそれぞれの接続先に行くこと、ホストの PF の同じキーは今までどおり拒否することを確かめた。修正を戻す5通りの変更で、すべて落ちた。
  レビューでテスト1023件・lint・typecheck が通った。
- 本物の AI・本物の PF との結合と、ブラウザでの操作は、レビューでは確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 設定の保存の競合の判定が、全プロジェクトの（PF の名前, キー）を重複として扱うので、別のプロジェクトがそれぞれ別の接続先を同じ名前で定義し、同じキーを使うと、2つ目の保存が拒否される。検索の結果にプロジェクトが残らず、取り込みの担当の判定・重複の排除も PF の名前とキーだけなので、別の接続先のチケットを区別できない | 競合の判定は、ホストの PF だけプロジェクトをまたいで行うようにした。コンテキストの PF で見つけたチケットにプロジェクトを付け、担当の判定はそのプロジェクトだけを見て、重複の排除は（PF の名前, キー, プロジェクト）で行う。取り込んだタスクのチケットに `scope: project` を記録する（無い既存のイベントはホストの PF として扱う）。回帰テストを足した |

## 残したこと

- 本物の AI・本物の PF との結合の確認。
