# 実装の PR がベースブランチと競合したままにならないよう、ホストでベースブランチの最新を作業領域にマージし、マージコミットで出す

- 日付: 2026-11-01（UTC）
- タスク: なし
- PR: #261
- ブランチ: feat/issue-261-merge-base-on-conflict
- 関係する ADR: [実装の PR がベースブランチと競合しないよう、Sacty がホストでベースブランチの最新を作業領域にマージし、親が 2 つのマージコミットで出す](../adr/20261101-0340-merge-base-branch-into-workspace.md)

## 目的

実務での実証実験（S7 試行 1）で、並行する別のタスクの PR が先にマージされ、実装の PR が README.md と .prettierignore で `CONFLICTING` になった。
人が差し戻しで解消を頼んだが、実装の作業領域には認証付きの `git fetch` も `gh` も無く、エージェントは main の差分を読み取り API で取ってファイルとして書き込んだ。
Sacty はそれを親が 1 つの通常のコミットとして push するので、PR は競合のまま、別のタスクの変更（38 ファイル +1743/-74）が実装の変更として混ざった。
最終レビューは 2 回不合格になり、約 9 ドルを使って一時停止した。S4 試行 1 の PR も同じ根。

人が決めた方針「ホストでマージ」に従う。PR が base と競合しうるときは、Sacty がホストで base を作業ブランチにマージする（親が 2 つのマージコミット）。
競合したファイルは目印付きのままエージェントに直させ、マージコミットとして push する。履歴は書き換えない（強制プッシュ・リベースをしない）。
競合しなければ、そのままマージコミットを push する。

受け入れ条件の要点：

- マージコミット（親が 2 つ）を作って push できる。競合の有無、目印の解消、解けないときの止まり方の回帰テストがある。修正を戻すと落ちる。
- いつ検知するか、エージェントへの指示、最終レビューとの関係、解けなかったときの止め方は、既存のコードと仕様の文脈から決めて ADR に書く。
- 範囲に入れないもの：既存の PR を引き継ぐタスク、承認待ちの PR がベースブランチに遅れたことの自動の検知。

## したこと

決めたことと理由は ADR に書いた。要点だけ。

- ホストで 3 方向マージ（`apps/daemon/src/repository.ts` の `mergeBase`）：退避したメタデータの git で、作業領域の内容と、取得したベースブランチの先頭を、作業領域が今ベースにしているコミットを共通の祖先にして `git merge-tree --write-tree` でマージし、結果を `git read-tree -m -u` で作業領域に書く。作業領域の git の設定は読まず、コミットも作らない。競合したファイルには目印が入る。
- 提出するコミット（`publish` の `merge`）：取り込んだ先頭が、親の履歴にまだ含まれていなければ第 2 の親にする。含まれていれば親は 1 つ（再開しても同じコミットになる）。内容が親と同じでも、含まれていなければマージコミットを作る。
- 取り込む時点（`apps/daemon/src/service.ts`）：実装の実行を始める前（`runNextInner`。初回も、差し戻し・PR の指摘の取り込み・再レビューも）と、最終レビューの前（`syncBeforeVerify`。PR を作って CI を待つ間は取り込み直さない）。承認待ちの間は取り込まない。既存の PR を引き継ぐタスクは取り込まない。ホストの設定 `ServiceDeps.mergeBase` で切れる（テスト用）。
- 競合の扱い：競合したファイルの一覧と解消の仕方を実装の指示に渡す（`mergeConflictLines`）。目印が残ったまま最終レビューの前になったら、ゴールガーディアンを実行せず、`BaseConflictsRemained` を記録して実装をやり直す。ほかの検証の失敗と同じ上限（`MAX_VERIFY_ATTEMPTS`、3 回）で一時停止し、競合したファイルを理由に示す（`verify.mergeConflictsRemain`）。目印の残る実装は「レビューへ進める」ことができない（`canOverrideVerification`）。
- 起点の扱い：記録した起点のコミットは変えず、`Task.baseMerge`（最後の取り込み）を足した。実装の差分・ファイルごとの変更・変更なしの判定・作業領域の用意し直しの起点は、取り込んだ先頭（`workBaseCommit`）。
- 最終レビューの指示（`baseMergeLines`・`guardianCodeLines`）：取り込んだこと、差分は取り込んだ先頭からの変更であること、ベースブランチ側の変更は範囲・過剰さの判定に含めないこと、競合の解消が壊していないかを確かめることを伝える。
- 取り込めなかったとき：理由（`merge.failed`。ホストの git が 2.40 より古ければ `git.mergeTreeUnsupported`）を示して一時停止し、再開で取り込みからやり直す。
- 画面：作業履歴の 2 つのイベントの文言（日本語・英語）。
- 仕様書（`docs/spec/tasks-and-steps.md` と `.en.md`。節「ベースブランチの取り込み」と図 `verify`）、ユーザードキュメント（`docs/user/tasks.md` と `.en.md`、`docs/user/troubleshooting.md` と `.en.md`）、ADR を足した。

## 確かめたこと

作業は、リポジトリの外の worktree（`sacty-wt-s7-merge-base`）で行った。

- `npx biome check .`・`npm run typecheck`：通る。
- `npx vitest run tests/docs`：通る（日本語の版と英語の版の突き合わせを含む）。
- `npx vitest run`（全体）：追加分を含めて通る。環境のために main でも落ちる `install-security-tools.test.ts`（3 件）と `question-form.browser.test.ts` を除く（変更を stash した main の状態でも同じ 2 ファイルが落ちることを確かめた）。
- 実際の git での回帰テスト（`apps/daemon/src/repository.test.ts`）：
  - 競合しない取り込み：作業領域にベースブランチの変更と実装の変更の両方が入り、提出は親が 2 つ。ベースブランチの先頭を祖先に含み、ベースブランチとの `merge-tree` が競合しない。ベースブランチとの差は実装のファイルだけ。再開して同じ入力で作り直すと同じコミット。取り込み済みの次の提出は親が 1 つ。変わらなければ同じコミット。
  - 競合する取り込み：競合したファイルに目印が入り（上が実装、下がベースブランチ）、競合しなかったファイルはそのまま。目印が残るうちは検出され、解消すると検出されない。解消した内容を親が 2 つのコミットで出すと、ベースブランチと競合しない。比較として、同じ内容を親 1 つで出すとベースブランチと競合する（S7 の PR の状態）。
  - ベースブランチが続けて進んだとき（前に取り込んだ先頭を起点にする）、取り込むものが無いとき、タスクブランチの要求要件・設計のファイルを引き継ぐ提出（`keep`）。
  - 目印の検出（最初の版は、始めと終わりの行がそろったときだけ。レビュー対応で、ID のラベルの付いた行が1つでも残っていれば検出する形に直した）。シンボリックリンク・無いファイル・作業領域の外は読まない。
  - 作業領域の git の設定（フィルター・フック・属性）を使わない。不正なコミットは受け付けない。
- 台帳を通した回帰テスト（`apps/daemon/src/daemon.test.ts`、偽のリポジトリ）：実行の前の取り込みと記録・起点の扱い、ベースブランチが進んでいなければ何もしない、競合を指示に渡す、目印が残ったら最終レビューに進まず（ゴールガーディアンを実行せず）競合したファイルを渡してやり直す、解消したら最終レビューへ進みマージコミットで出す、3 回で一時停止してレビューへ進めない、取得できなければ実行せずに止める、取り込みを切ると従来どおり、最終レビューの指示。そのほか `packages/core` の状態の復元と、`prompts.test.ts`。
- 修正を戻すと落ちることを確かめた（変更ごとに戻して、該当のテストが落ちるのを見た）：第 2 の親を付けない・取り込みの結果を作業領域に書かない・実装の前の取り込みをやめる・最終レビューの前の確認をやめる・差分とコミットの起点を戻す・目印の検出をやめる。
- 実際のエージェントを使った全体の通しは、していない。

| 指摘 | 対応 |
| --- | --- |
| 起点のコミットの記録を取り込んだ先頭に書き換えると、タスクブランチの確認（`known`）が、ベースブランチの変更を「人が積んだ変更」と見て止める | 記録した起点は変えず、`baseMerge` を別に持つ。差分・変更なしの判定・用意し直しだけ、取り込んだ先頭を起点にする。タスクブランチの提出もテストした |
| 作業領域を用意し直すと、起点のコミットに戻って取り込みが消える | 取り込んだ先頭で用意し直す |
| 取り込み済みなのに毎回マージコミットを作ると、検証に通った後の PR が最終レビューの前のコミットと別になる | 先頭が親の履歴に含まれていれば親は 1 つ。内容も同じなら同じコミットのまま |
| 内容が親と同じでも、取り込んだ先頭が親の履歴に無ければ、ベースブランチと競合したままになる | その場合はマージコミットを作る（テストあり） |
| 目印が残ったまま、ベースブランチがさらに進んで、目印の上に重ねて取り込む | 目印が残っているうちは取り込まない。解消してから次を取り込む |
| 目印の検出が、Markdown の見出しの下線（`=======`）や、作業領域の外へのシンボリックリンクに反応する | 始めと終わりの行の両方がそろったときだけ。通常のファイルだけを読み、作業領域の外は読まない。テストあり |
| 目印が残ったまま通らないのを、ふつうの検証の失敗と同じ文言で止めると、人が「レビューへ進める」で目印の残る PR を出せてしまう | 専用の文言で止め、目印の残る実装は進められない |
| ファイル名の改行などで、実装の指示に行を足される | 指示に載せるときに制御文字を置き換える。テストあり |
| ホストの git が古いと、理由のわからない失敗になる | `git merge-tree --write-tree` が使えないときは、専用の文言で git の更新を案内する |
| 承認待ちの PR の遅れを自動で検知して実装をやり直さない | 範囲に入れない（人の差し戻しか指摘で、やり直す前に取り込む）。ADR に書いた |

## 残したこと

- 承認待ちの PR がベースブランチに遅れたことの自動の検知と、自動のやり直し（PR の `mergeable` を読むか、ホストの確認で見るか）。
- 既存の PR を引き継ぐタスクでの、ベースブランチの取り込み（人の PR のブランチに積むので、人が決める）。
- 競合のうち、目印を入れられないもの（バイナリ・片方での削除など）の解消の確認。
- ホストでの取り込みと記録の間でデーモンが止まったときの復旧（まれなので作らなかった）。

## レビュー対応（別の DA のレビュー。判定は PASS）

| 指摘 | 対応 |
| --- | --- |
| 目印の検出が、部分的な消し忘れ（`<<<<<<<` だけ・`>>>>>>>` だけ）を見逃す | sacty が書く、ID のラベルの付いた始めの行か終わりの行が1つでも残っていれば「残っている」とする形にした。ラベルの無い似た行と単独の `=======` は目印にしない。このため、始めと終わりの行を消して `=======` だけが残る場合は検出できない（ADR の影響に書いた）。実際の競合から作った3通りの消し忘れと、ラベルの無い似た行・見出しの下線・リンクを誤検出しないことをテストした。戻すとテストが落ちる |
| ディレクトリとファイルの競合で git が避けた名前（`docs~<ID>`）が、解消済みと見なされる | 避けた名前のパスが残っているうちは、解消していないものとする。指示に、何が起きたかと、消すことを書いた。実際の git でテストした。戻すと落ちる |
| 実行の間にベースブランチが進んで新しく競合したのも、検証に通らなかった回数に数えている | 最終レビューの前の取り込みで新しく競合したときは数えない（`BaseConflictsRemained` の `fresh`）。前の取り込みの目印が残っているときは数える。ADR に、数えない回数に上限が無いこと（ベースブランチが進み続ける限りやり直しが続きうる）を書いた。戻すと落ちる |

範囲外のまま：デーモンが止まったときの復旧、承認待ち中の検知、`.gitignore` のファイルとの衝突。

## 実タスク（S7 試行 2）で見つかった抜けへの対応

実タスクで、取り込み自体は効き、PR は親が 2 つのマージコミットで MERGEABLE になった。ただし、競合で一時停止したタスクを 1 回目に再開したとき、取り込まずに古い head のまま最終レビューが走り、同じ理由で不合格になって、また一時停止した（1 巡ぶん、約 3.8 ドルの無駄）。2 回目の再開で、初めて取り込みが動いた。

- 原因（作業履歴で確かめた）：1 回目の再開は「実装をやり直さない再開」（`retry: false`）で、タスクは検証の待ちに戻った。このとき、前の PR の CI の結果（`pullRequestCi`）がすでにあった。最終レビューの前の取り込み（`syncBeforeVerify`）は、「PR の CI の結果がある間は取り込まない」という条件を付けていて、この経路ではそれに当たって何もしなかった。実装の実行の前の取り込みは、実装を走らせない再開では動かない。
- 直し：その条件を外した。PR の CI を待つ間は最終レビューに進まないので、条件が無くても、待つ間に取り込むことはない。CI の結果が出た後でベースブランチが進んでいれば取り込み、競合すれば実装をやり直し（新しい競合は数えない）、競合しなければ `BaseBranchMerged` が前の CI の結果を捨てて、PR をマージコミットで作り直して CI を待ち直す。
- テスト：CI の結果が出た後に進んで競合した場合（古いコードで最終レビューが走らず、競合したファイルを渡してやり直す）と、競合しない場合（取り込み、PR を作り直し、CI を待ち直してから最終レビュー）を `daemon.test.ts` に、検証の待ちで取り込むと CI の結果を捨てることを `projection.test.ts` に足した。条件を戻すと 2 件とも、CI の結果を捨てる処理を戻すと後者が落ちる。
- ADR・仕様書（日英）を直した。

## レビュー（sacty のレビュー。`f6638f9b` に対する「修正が必要」）への対応

3 件とも妥当と判断して直した。

| 指摘 | 対応 |
| --- | --- |
| 使っている `git merge-tree --merge-base` は、案内していた 2.38 以上でも使えない版がある（2.39.5 で追加テストが終了コード 129 で失敗する） | `--merge-base` が使えるのは 2.40 以上なので、最低版を 2.40 に直した（エラーの文言 `git.mergeTreeUnsupported`・ADR・日英の仕様書・日英のユーザードキュメント）。2.38 でも動く方式（作業領域のツリーからコミットを作ってマージする）にはしていない：手元の git が新しい版（2.56）で、古い版での動作を確かめられないため。2.39 以前の git（Debian 12 の標準など）では、取り込みの前に案内を出して止まる |
| 両側が同じファイルを別名へ改名して内容も競合すると、git は 8 文字・パス付きの目印（`<<<<<<<< <ID>:ours.txt`）を書き、検出できず、解消済みとして進む | 実際に git が書いた形を再現して確かめた（`<<<<<<<<`・ID のあとに `:パス`）。目印は 7 文字以上、ラベルは ID のあとのパス付きも見る。実際に取り込んで書かれた目印が検出され、消せば解消になるテストと、目印の行の見分け（ラベルの無い似た行・短い ID・行の途中は目印にしない）のテストを足した |
| 競合が 101 件以上のとき、先頭 100 件だけを記録するので、101 件目以降の目印が検査されず、解消したことになる | 切り捨てをやめ、全件を記録する（イベントの上限を `MAX_BASE_CONFLICTS`＝1000 に上げた。昔の記録は 100 件以下なので読める）。1000 件を超えるときは、作業領域を書き換える前に、件数と上限を示して止める（`git.tooManyConflicts`。書いてしまうと、記録できない目印が残るため）。150 件の競合で先頭 100 件だけ解消したら最終レビューに進まないこと、上限を超えたら取り込みを記録せずに一時停止することをテストした |

DA として確かめた：3 つの修正を戻すと、足したテスト 5 件が落ちる。
