# 範囲外の変更を、最終レビューで不合格にする

- 日付: 2026-11-01（UTC）
- タスク: PBI-273
- PR: #264
- ブランチ: feat/issue-273-out-of-scope-review
- 関係する ADR: [最終レビューで、依頼にも承認済みの要求要件・設計にも無い変更と、既存のテストの期待を変える変更を、観点 SCOPE の不合格にする](../adr/20261101-1348-fail-out-of-scope-changes-in-final-review.md)

## 目的

実務での実証実験（S13a）で、ベースブランチを取り込んだ後の実装が、依頼にも承認済みの要求要件・設計にも無い変更（狭い画面向けのカード表示、「一覧を再取得」ボタン）を足し、先にマージした PR のテスト（`rooms.spec.ts` の `scrollWidth > clientWidth`）の期待を逆にした。
ゴールガーディアンは不合格にせず、「人が確かめること」に回しただけだった。人が差し戻して直った。

受け入れ条件：

- 承認済みの要求要件・設計・依頼のどれにも無い振る舞いの変更や、既存のテストの期待を弱める・逆にする変更があれば、最終レビューは不合格にし、外すよう実装に戻す。
- 範囲内か判断できないもの（依頼の解釈が分かれる）は、今までどおり人の確認に回す。
- 既存の「範囲・過剰さ」の判定との関係を整理して、仕様書・ユーザードキュメント（日英）・作業履歴を直す。テストで確かめる。

## したこと

- 最終レビューの指示（`outOfScopeLines`）に「範囲外の変更」の節を足した。差分の変更ごとに、載せている承認済みの要求要件・設計（省いたタスクは依頼・再現のテスト）と人の過去の指摘が求めているか、求めた変更に要るかを確かめさせる。範囲外は `outOfScope` に1件ずつ申告させる。判断できないものは `humanChecks`（不合格にしない）。セキュリティ対応には入れない（`SEC-MIN` が見る）。
- 判定の出力に `outOfScope` を足し、`extractFinalReview` が1件でもあれば観点 `SCOPE`（不合格）を判定に足す。申告が無ければ何も足さないので、既存の観点・テストの対応は変わらない。
- 実装のやり直しの指示（`feedbackLines`）に、範囲外の変更だけを起点の状態に戻して外し、ほかの変更と元からあった指定は残すこと、外した後に差分で確かめることを足した（S13a で、直しが元の `minWidth` まで外して再び不合格になったため）。
- 画面（実装の成果物の最終レビュー）に、`SCOPE` が不合格のとき「範囲外の変更」と理由を出す。
- 仕様書（日英）・ユーザードキュメント（日英の「範囲外の変更」）・ADR を足した。

### 既存の「範囲・過剰さ」の判定との関係

- 既存の「ベースブランチ側の変更・成果物を範囲・過剰さの判定に含めない」は、そのまま。含めない側の除外で、今回は含める側の判定を足した。
- 要求要件・設計を省いたタスクの観点 `REQ` の「依頼に無いものを作っていないか」は残す。今回の `SCOPE` は、それとは別に、どのタスクでも、`REQ`・設計の観点の判定にかかわらず不合格にする。
- セキュリティ対応は `SEC-MIN` がより厳しく見るので、`SCOPE` は入れない。
- 空回りの歯止めは既存の `MAX_VERIFY_ATTEMPTS`（3回）。続けて通らなければ一時停止し、範囲内と判断する人は「レビューへ進める」で進められる。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として、受け入れ条件を1つずつ確かめた。

| 指摘 | 対応 |
| --- | --- |
| 設計の観点が複数あるとき、範囲外をどの観点に落とすか決まらない | 設計の観点とは別に、申告があったときだけ観点 `SCOPE` を足す形にした |
| 常設の観点にすると、判定の無い観点は不合格になり、既存の判定・テストの対応・画面の表が変わる | 申告があったときだけ足す（ADR に比べた案を書いた） |
| 範囲内の変更を範囲外と誤ると、実装が外せず空回りする | 不合格にするのは、根拠を書ける範囲外だけ。判断できないものは人の確認。3回で一時停止、人が進められる |
| 空の申告・「なし」・読めない形が不合格になる | `reportedItems` で捨て、何も足さない（テストあり） |
| 申告に秘密情報が混ざる | `humanChecks` と同じ読み方で伏せる（テストあり） |
| セキュリティ対応で `SEC-MIN` と二重に不合格になる | 指示・出力の形に出さず、申告も読まない（テストあり） |
| やり直しで、外しすぎて元からあった指定まで消す（S13a で起きた） | 挙げられた変更だけを外し、起点にあった指定・テストの期待は残すと伝える |
| 画面に `SCOPE` の理由が出ない（設計の観点の表に無い） | 最終レビューの欄に「範囲外の変更」として出す |
| ゴールガーディアンが誤って、ベースブランチ側の変更や成果物を範囲外とする | 判定に含めないと、新しい指示にも書いた（テストあり） |
