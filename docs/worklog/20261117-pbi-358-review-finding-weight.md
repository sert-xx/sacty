# レビューの指摘の重みを、影響の大きさと起きやすさで決める

- 日付: 2026-11-17（UTC）
- タスク: PBI-358
- PR: #401
- ブランチ: claude/pbi-358-review-finding-weight-02412d
- 関係する ADR: [レビューの指摘の重みを、影響の大きさと起きやすさで決め、自己レビューは要修正だけを修正に戻す](../adr/20261117-0244-review-finding-weight-by-impact-and-likelihood.md)

## 目的

既定のレビュー用スキルは、起こりうる不具合を、稀な条件でだけ起きるものでも `must`（要修正）にしていた。
PR のレビューは `must` が 1 件でもあれば「修正が必要」になるので、直しのために足した仕組みの、稀な条件での穴への要修正が続き、往復が終わらない PR が繰り返し出た。

リポジトリの持ち主が決めた基準を、レビューの側に入れる。受け入れ条件は次のとおり。

1. 重要度を、影響の大きさと起きやすさの表で決める。影響：大は常に `must`。影響：中は、独立した条件が 2 つ以上重なったときだけ起きる「稀」なら `should`、それ以外は `must`。影響：小は `should`、稀なら出さない。受け入れ条件の不適合は、起きやすさを問わず `must`。
2. 担当は、指摘ごとに、起きる条件と、起きたときの実害を書く。
3. 再レビューと、直した箇所への指摘にも、同じ基準を当てる。
4. 自己レビューは、`must` だけを修正に戻す。
5. PR のレビューの判定の決まり（`must` があれば「修正が必要」）は変えない。
6. 既定のコンテキストに、特定のリポジトリや言語に寄せた記述・例を書かない。
7. 仕様書・ユーザードキュメント（日英）、ADR、作業履歴に反映する。

指摘を受けた側の「後続に回したい」の申告と、人の決定の画面は、別の PBI で扱う（この PR の範囲外）。

## したこと

- 担当のスキル（`apps/daemon/default-context/skills/review/review-execution/SKILL.md`）
  - 「重要度」の節を、影響（大・中・小）と起きやすさ（普通・条件つき・稀）の表に書き換えた。
  - 条件の数え方を書いた（障害・珍しい入力や量・処理の重なり・珍しい操作を数える。ふつうの使い方で満たされる前提と、外部の者が意図して揃えられる条件は数えない。1 つの原因が続けて引き起こすことは 1 つ）。
  - 不適合の範囲を書いた（根拠が述べる場面そのもので、求められた振る舞いにならないこと。根拠に書かれていない条件がさらに重なったときだけ起きるものは、表で決める）。
  - 出力に `condition`・`impact`・`likelihood`・`impact_level` を足し、条件と実害を書き出してから重要度を決める手順にした。
  - 観点の資料の NG 例の重要度は書き換えず、稀なときは表で決め直すと書いた。
- 親のスキル（`review-dispatch`）
  - `references/aggregation.md`：「重みの確認」の節を足した（担当の重要度を、書かれた条件と実害から同じ表で確かめ、決め直したものを `reweighted` に残す。「影響：小 × 稀」は不採用）。判定の「`should` のみ：自己レビューでは修正に戻す」を、「戻さない」に変えた。
  - `references/pr-review.md`：再レビューの採用の規則に、同じ表を当てること、直しに見つけた穴だからといって `must` にしないこと、前回の `must` が表では `should` に当たるなら未対応でも `must` に数えないことを足した。指摘に、起きる条件と実害を書かせる。判定の決まりは変えていない。
  - `references/self-review.md`：`must` だけを修正に戻す。`must` が無い回は、`should`・`nit` を直さずに提出へ進む。`design-doc` の記述を削る `should`（D-10）は、これまでどおり直す。
  - `references/finding-format.md`・`SKILL.md`：上に合わせた。観点の選び方・担当の段階は変えていない。
- PR のレビューの子タスクの指示（`apps/daemon/src/prompts.ts` の `buildPrompt` の `review`）
  - 指摘に、起きる条件と実害を添えさせる。重さはスキルの表で決めさせ、再レビューと直した箇所にも同じ表を当てさせる。
- テスト：`apps/daemon/src/default-skills.test.ts`（重みの基準の 6 件）、`apps/daemon/src/prompts.test.ts`（指示の文言）。
- 仕様書（`docs/spec/context.md`・`tasks-and-steps.md`）、ユーザードキュメント（`docs/user/intake.md`）、それぞれの英語の版、ADR。

決めたことの理由は、ADR に書いた。

  - B は、1 版目では `must` のままだった。担当は「稀・影響は中」と書きながら、PR の本文と仕様書に書かれた振る舞いを満たさないことを理由に、不適合として `must` にした。仕様が述べる場面（時間切れと制限が重なる）に、仕様に無い条件（一時停止か記録の失敗）がもう 1 つ重なったときだけ起きる穴だった。

  - A は、旧のスキルでも `nit` だった。実物のレビューの要修正との差は、基準の差だけでは説明できない（候補を渡したこと・モデルの違いがありうる）。
