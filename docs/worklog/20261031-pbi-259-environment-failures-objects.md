# ゴールガーディアンが環境による失敗をオブジェクトの配列で申告しても、環境による失敗だけとして読み、指摘が無いままの不合格を防ぐ

- 日付: 2026-10-31（UTC）
- タスク: PBI-259
- PR: #259
- ブランチ: feat/issue-259-environment-failures-objects
- 関係する ADR: なし（既存の方針どおりの不具合の修正）

## 目的

実務での実証実験（複数言語のモノレポ。Go・Python・Node）で、ゴールガーディアンが「要求を満たす」と判定し、テストは終了コード 2（イメージに ensurepip と go が無く `make setup` が失敗）・環境による失敗に「起点のコミットでも同じ失敗」と根拠を書いたのに、最終レビューが「不合格（0 件）」と記録された。
実装は指摘が無いまま同じコミットを再送し、3 回続いて一時停止した。ユーザードキュメントの「失敗がすべて環境によるものだとゴールガーディアンが判断したときは、テストは通ったものとします」と食い違う。
考え方は変えず、ドキュメントどおりに動くように直す。

## 原因（ログとコードで確かめた）

- 不合格になった 2 回の最終レビュー（実行のログ）の `tests.environmentFailures` は、`[{"name": "...", "reason": "..."}]` というオブジェクトの配列だった。観点は検証済み・指摘は再発なし・`exitCode` は 2。
- 読み取り（`extractFinalReview`）は、環境による失敗を `texts()`（文字列の項目だけ読み、文字列でないものは捨てる）で読んでいた。オブジェクトはすべて捨てられて空になり、`guardianTestsPassed` が「終了コード 0 でなく、環境による失敗の申告も無い」ので偽を返し、観点と指摘が問題なしのまま不合格になった（指摘 0 件の不合格）。
- 終了コード 0 で `environmentFailures: []` と申告した回は、環境の問題は同じでも合格だった。申告の形が違っただけで結果が変わっていた。
- 指示に、各項目の形（文字列か）を書いていなかった（出力の形式の例は `environmentFailures: []` だけ）。
- 同じ読み方の `humanChecks`・`tests.otherFailures`・`tests.missingCommands` も、オブジェクトを捨てる。`otherFailures` を捨てると、文書だけの差分でツール不足のほかの本物の失敗を見逃す（#258 の歯止めが外れる）。

## したこと

- `reportedItems`（`apps/daemon/src/prompts.ts`）：一覧の 1 件を、文字列はそのまま、オブジェクトは決めた項目名（名前：`name`・`test`・`check`・`command`、根拠：`reason`・`message`・`description`・`evidence`）だけを、JSON の並びにかかわらず「名前：根拠」の 1 行にして読む。読めない項目・空の項目・「なし」「none」「n/a」「environment: false」のような「無い」を表す項目は捨て、配列でない値は読まない。読んだ項目は、人に見せる前に `redactLog`・`redactUrlCredentials` と、秘密らしい名前（token・key・secret・password・auth・signature など）のクエリ・フラグメントの値の伏せ字を通す（クエリ・フラグメント全体は伏せず、確かめる URL を残す）。値が false の `environment` などの旗が付いた項目は、環境による失敗として読まない。`environmentFailures`・`humanChecks` に使う。記録の形（文字列の配列）は変えない。
- `hasReportedFailure`：`otherFailures` は止める側の欄なので、読める形かにかかわらず、書いてあれば「失敗の申告あり」とする（文字列・数値・真・オブジェクト（空でも））。
- `reportedNames`：`missingCommands` の項目に `{"name": "go"}`（`command`・`tool`）も読む。
- ゴールガーディアンへの指示に、`environmentFailures` は「名前：根拠」の文字列の配列で書くことを足した。
- 実装のやり直しの指示（`feedbackLines`）：観点がすべて検証済みで指摘も再発していない（テストが通らなかったことだけが理由）ときは、そう伝え、実装で直る失敗が無ければ無関係な変更を足さないよう添えた。
- 仕様書（`docs/spec/tasks-and-steps.md`・`.en.md`）を直した。ユーザードキュメントは、書かれている振る舞いに実装を合わせたので、直していない。

## 確かめたこと

作業は、リポジトリの外の worktree（`sacty-wt-s5-env-failures`）で、Node.js 26.12.1 を使って行った。

- 実際に不合格になった出力の形（終了コード 2・`{name, reason}`）の再現：合格になり、「名前：根拠」で記録され、`GuardianTests` の形として読める。デーモンの通しのテスト（`daemon.test.ts`）でも、最終承認の待ちへ進み、再実行せず、PR の本文の「人が確かめること」に出る。
- 境界（`final-review-failure-shapes.test.ts`）：環境による失敗だけ（文字列・オブジェクト・混在）は合格／申告なし・空・読めない項目だけ・配列でない値は終了コード 2 のまま不合格／環境の失敗が空で本物の失敗（`otherFailures`）があるときは不合格／終了コードの申告なしは不合格／終了コード 0 は合格のまま（環境による失敗は記録しない）／観点が未検証・指摘が再発していれば不合格のまま。
- `humanChecks`・`missingCommands` がオブジェクトでも読む。`otherFailures` は読めない形（文字列・入れ子・`[{}]`・数値など）でも、文書だけの差分でツール不足を通さない。空・「なし」だけなら通す。
- オブジェクトの `output`・`log` などは読まない。項目の並びが `{reason, name}` でも「名前：根拠」。秘密情報・URL の認証情報は伏せる。`{environment: false}`・「なし」「n/a」などは環境による失敗として通さない。
- 修正（`prompts.ts`）を戻すと、新しいテストとデーモンの通しのテストが落ちることを確かめた。`otherFailures` の見方・「無い」の除外・伏せ字・項目名の限定をそれぞれ戻しても、対応するテストが落ちる。

## レビューの指摘と対応

自分で悪魔の代弁者（DA）として確かめた。

| 指摘 | 対応 |
| --- | --- |
| 配列でない `environmentFailures`（「なし」の文字列）まで 1 件として読むと、環境による失敗でないのに通る | 配列だけ読む。テストあり |
| 環境による失敗の申告が 1 件でも本物の失敗と混ざる場合に通る | 指示で、混ざるときは空にさせる既存の取り決めのまま。`otherFailures` が環境による失敗の申告と重ねて書かれた場合の扱いは変えていない（残したこと） |
| `otherFailures` のオブジェクトを捨てると、文書だけの差分でほかの失敗を見逃す | 読める形に頼らず、書いてあるかで見る（`hasReportedFailure`）ようにした。テストあり |
| オブジェクトの全文字列の値を連結すると、`output`・`log` などの余計な項目が伏せ字を通らずに PR の本文に出る | 読む項目名を限り、連結後に伏せ字を通した。並び順に依存しない。テストあり |
| `environment: false`・「なし」を環境による失敗として通してしまう | 「無い」を表す項目を除いた。テストあり |
| クエリ・フラグメントまで伏せると、確かめる URL（`http://localhost:3000/#/settings?tab=2`）が消える | URL の認証情報と、秘密らしい名前のクエリの値だけ伏せるようにした。テストあり |
| `{name, environment: false}` のような旗付きの項目が環境による失敗として読まれる | 旗が false の項目は読まない。テストあり |
| `otherFailures` の「無い」に `no`・`false` の文字列まで含めると、失敗の申告を見逃す | 「なし」「none」「n/a」と空だけを「無い」とした。テストあり |

## 残したこと

- 指摘が無いまま、同じコミットで実装を再送する空回りは、本来の原因（環境による失敗の取りこぼし）を直したことで起きにくくした。ただし、テストが本当に失敗していて実装で直らないときに、差分なしの再送を検知して早く止める仕組み（再送前後のコミットの比較・新しい一時停止の理由）は、工程の変更になるので入れていない。
- ゴールガーディアンが環境による失敗と本物の失敗を `environmentFailures` に混ぜて申告したときは、見分けられない（申告に頼る）。
- 実際のゴールガーディアン（AI）での再試行は、していない。自動のテストは、実際に不合格になった出力の形を差し替えて確かめている。
