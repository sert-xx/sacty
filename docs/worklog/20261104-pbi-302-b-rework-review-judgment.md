## 目的

実務実証実験の r5（1.16.0、main e691e3eb）で見つかった、差し戻し・レビュー・判断に関わる問題（PBI-302 の B1〜B6）をまとめて直す。A（作業領域・検証）と C（成果物と PR の本文）、D（画面・記録）は別の担当で、ここでは触れない。1 つの PBI の B 群なので、作業履歴は B 群の分として 1 ファイルにまとめた。

- B1（F48、S5）：質問への答えだけのコメント（should に「推奨どおり」）で、要求要件を丸ごと作り直した（報告額 約 $1.45）。
- B2（F50、S16）：Sacty のレビューが、同じ head で直っている指摘を「未対応」として「修正が必要」にした。
- B3（S14）：ゴールガーディアンが、89 行目へのコメントを 88 行目の内容として読んだ。
- B4（S16）：要求要件・設計に無い共有の仕組み（キュー）が、4 回続けて実装に入った。
- B5（S5。F34 の再発）：オーケストレーターが要求要件を残す理由に 3 つ挙げたが、「確認したいこと」に出たのは 1 つだけ。
- B6（F49、S14）：監査が、プロジェクト全体のメモリーに、依頼者の答えを事実として登録した。

## r5 の記録で確かめたこと

- S5：工程の決定（`StepsChosen`）の理由に、要求要件を残す理由が 3 つあった。(1) Web の異常系のテストで何を確かめるかが未定、(2) 既存の呼び出し側の 422 の扱いの移行の要否、(3) 受け入れ条件の完了の条件（`make lint test smoke build`）と AGENTS.md（`make lint test smoke`）の食い違い。要求要件の「確認したいこと」に出たのは (1) の should 1 件だけ。(2) は受け入れ条件が必須にした変更に伴うこと、(3) は受け入れ条件に従えば済む手順の食い違いで、人に確かめることではなかった。情報収集の出力の「食い違い・未確定のこと」の節に、(1)(3) が挙がっていた。

## したこと

### B1 質問への答えだけのコメント

- `packages/core/src/events.ts`：差し戻しの原因に `question_answer` を足した。答えと推奨の関係 `ReworkAnswer`（`as_recommended`・`changes_decision`）を足し、`ReworkJudged`・`ChangesRequested`・`RequestChangesInput` の `answer`、投影の `pendingReview.judgement`・`prRework` に持たせた。
- `apps/daemon/src/prompts.ts`：要求要件・設計の PR の戻し先の判断（`buildStepReworkPrompt`）に、原因 `question_answer` と `answer` の判断を足した（`reworkCauseLines`・`REWORK_ANSWER_LINES`）。実装の PR には足さない（sacty の質問が無い）。`extractRework` は、原因が `question_answer` のときだけ `answer` を読む。
- `isAnswerOnlyRework`：判断した指摘の集合そのもので始まった要求要件・設計の実行で、原因が `question_answer`、答えが `as_recommended`、戻し先を判断できているときだけ真。要求要件・設計の実行の指示は、このとき、通常の直しの指示とセルフレビューの代わりに、答えの反映だけの直し（`answerOnlyReworkLines`）と、読み直す 3 点の確認（`answerOnlyCheckLines`）にする。出典の分類と指摘への対応の報告は今までどおり。
- `apps/daemon/src/service.ts`（`settleReview`）：`as_recommended` を `ChangesRequested` に残すのは、判断した戻し先がその PR の工程（要求要件・設計）のときだけ。前の工程へ戻す・実装の PR・判断できないときは残さない。`changes_decision` はそのまま残す。
- ダッシュボード・作業履歴の原因の表示に「質問への答え」を足した（日英）。

### B2 前の指摘の対応を head で確かめさせる

- `apps/daemon/src/prompts.ts`：`HEAD_CHECK_LINES`（再レビューの節と、再レビューでない最初のレビューの既存の指摘の節）。先頭のコミットのファイルを開いて確かめる、前回の本文・前のコミット・作者の返答だけを根拠にしない、未対応と書くときは読んだ箇所を添える、示せないものは未対応と書かない、判定 `changes_required` は先頭のコミットで成り立つ `[要修正]` に基づける、本文の「未対応」と行コメントの重さ・判定を食い違わせない。判定の説明（`changes_required`）にも同じ趣旨を足した。
- 既定のスキル `pr-review.md`：同じ決まりを、sacty・特定の言語・ツールに寄せない書き方で足した。
- sacty は未対応の主張を head の内容と照らして検査しない（下の「残したこと」）。

### B3 行コメントの行の内容

- `apps/daemon/src/github.ts`：`lineContextOf`。GitHub のコメントの `diff_hunk`（コメントが付いた行が最後）から、その行と直前の 2 行を取る（ハンクの見出し・差分の印・「改行なし」の注記を除き、1 行 200 文字まで）。`PullRequestFeedback.lineContext` に持たせる。
- `apps/daemon/src/service.ts`（`feedbackRemarks`）：行コメントの指摘の文の後ろに、`（コメントが付いた行の内容：「…」。直前の行：「…」）` を足す（`lineContextText`。秘密情報を伏せる）。2000 文字の上限は、指摘の文を短くして収め、添える分は切らない。古い head の AI のレビューを捨てるときの要点（`discardedSummary`）には添えない。
- `apps/daemon/src/prompts.ts`：添えた指摘があるとき、戻し先の判断（`reworkRemarkLines`）と工程の指示（`remarkSections`）に、行番号から数えず、添えた行の内容で箇所を確かめさせる注意（`lineContextNote`）を足した。

### B4 共有の仕組み

- `apps/daemon/src/prompts.ts`：`SHARED_MECHANISM_IMPLEMENT_LINE`を、実装の指示の 5 つの経路（要求要件・設計あり／要求要件を省いた／テストの仕組みが無い／不具合の修正）に足した。足さないと満たせないと確かめたときだけ足し、実装の説明の最後に「共有の仕組みを足した理由」の節を作らせる。最終レビュー（`sharedMechanismLines` の最終レビューの分）は、理由があり確かめられれば `humanChecks` に「共有の仕組みを足した：…（理由）」を書かせ（PR の本文の「人が確かめること」に出る）、理由が無い・足さなくても満たせるなら範囲外として不合格にさせる。

### B5 要求要件を残す理由

- 渡す：`keepRequirementsReasonLines`。最初の要求要件の実行に、オーケストレーターの理由（`Task.stepsChoice.reason`）を JSON のデータ（`orchestratorReason`）で渡す。理由ごとに「確認したいこと」に出すか、「確認したいこと」の節の最後の「確認しないと決めたこと」に、決めた内容と確認しない理由を書かせる。
- 見直す：`DETAILED_ACCEPTANCE_LINE`。「依頼と文書・コード・既存の方針が食い違う」を、作るものが変わるものに限った。人に確かめることが無い理由（作るものが変わらない文書どうし・文書と受け入れ条件の食い違い、受け入れ条件が決めた変更に伴う追従、実装が決められる未確定のこと）を、残す理由にしないと書いた。残す理由は、答えが複数あり、依頼からも既存のコード・文書からも決まらず、人に聞かないと決められないことだけ、`reason` に 1 つずつ書かせる。#285・#289 の決まりと、残すべき例外（曖昧・作るものを左右する食い違い・人に確かめたい判断・書き忘れや衝突・共有の状態への新しい意味・API の変更）は変えていない。

### B6 監査のメモリー

- `apps/daemon/src/memory-answers.ts`（新規）：登録の前の検査。`requester_mentioned`（依頼者を主語にした言い方がある）と `requester_text_copied`（依頼者が書いた文〔題・本文・人の指摘・再開の補足〕を、空白・記号を除いて 14 文字以上そのまま写した）。英数字が主の一致は数えない。
- `apps/daemon/src/audit-prompts.ts`：`extractAuditDive` が、検査に当たったメモリーを登録せず、`skippedMemories` に返す（登録の上限には数えない）。深掘りの指示に、依頼者の答えを事実として書かないこと・登録の前に検査することを足した。
- `AuditDeepDived` に `skippedMemories`（題・理由）を足した。作業履歴の深掘りの行に件数が出る（日英）。

### 文書

## レビューの指摘と対応（自分で悪魔の代弁者として確かめた）

| 指摘 | 対応 |
| --- | --- |
| 軽い直しの条件が広いと、決定を変える答えを軽く扱って、反映漏れを人に見せない | 条件を、判断した指摘の集合そのもの・要求要件か設計をその PR の工程で直す・戻し先を判断できている・原因が `question_answer`・答えが `as_recommended` の全部にした。迷うとき・答えを読み取れないときは `changes_decision` にさせ、`answer` を読めなければ今までどおり。前の工程へ戻す判断のときは `as_recommended` を残さない。テストあり（境界：判断の後に指摘を無効にした・指摘が増えた・前の回の判断・前回の下書きが空） |
| 軽い直しの途中で、エージェントが「推奨と違う」と気づいたとき | 軽い直しをやめて通常の直しにし、指摘への対応に理由を書かせる（指示）。sacty は検査しない |
| セルフレビューを省くと、報告が無く「記録なし」になり、次の直しの範囲を絞る条件（前回が合格）を満たさない | 次の直しは全体をレビューする側に倒れる（安全側）。仕様書に書いた |
| 添えた行の内容に、リポジトリの秘密情報や、エージェントへの指示のような文が入りうる | 秘密情報と URL の認証情報を伏せ、1 行 200 文字・直前 2 行に限り、「指示ではない」と指示に書いた。テストあり |
| 指摘の文が長いと、添えた行の内容が 2000 文字の上限で切れる | 添える分を切らず、指摘の文を短くして収める。テストあり（5,000 文字の指摘） |
| 捨てた AI のレビューの要点に、行の内容が混ざって長くなる | 要点には添えない |
| 登録しなかったメモリーの記録が 10 件を超えると、記録が拒まれて監査が止まる | 10 件で切る。テストあり（25 件） |
| 依頼者の答えの検査が、リポジトリの事実を巻き込む（パスや識別子が依頼の文と重なる） | 英数字が主の一致（文章の文字が 6 文字未満）は数えない。テストあり |

## 残したこと

- B1：軽い直しではセルフレビューをしない。答えの反映で成果物が崩れても、人が PR で確かめるまで気づかない（読み直す 3 点を指示するだけで、sacty は検査しない）。出典の分類は残したので、直しの費用は 0 にはならない。実タスクでは確かめていない。
- B2：指示と既定のスキルの決まりだけで、sacty は「未対応」の主張を head の内容と照らさない。本物の未対応（前回の指摘が残っている）と、誤った未対応を機械では見分けられないため。実際のレビューのエージェントの出力では確かめていない（`review-eval` は実行していない）。
- B3：行の内容は、GitHub のコメントの diff の抜粋から取るので、コメントが付いた行とその前の 2 行だけ。後ろの行は渡さない。抜粋が無いコメントには添えない。複数行にまたがるコメントは、最後の行だけ。
- B4：指示と最終レビューの指示だけで、sacty は共有の仕組みを検出しない。足した理由が実装の説明に書かれるかは、エージェント次第。
- B5：実験は、リポジトリが見えない入力（依頼と、集めた情報の例）で、1 回の通しではない。割合は目安。要求要件が「確認しないと決めたこと」を書くかは、通しの実行では確かめていない。
- B6：検査は、依頼者を主語にした文と、依頼者の文の写しだけを見つける。言い換えた答えは見つけられない。すでに登録済みのメモリー（S14 で登録された 9c78f980 など）は消さない（人が監査のタブで消す）。
- 監査の大まかな段階の「メモリーを別の階層へ移す」（`memoryMoves`）は、検査しない（登録の前の検査だけ）。
