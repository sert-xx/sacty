# 要求要件の工程と承認ゲート（差し戻し・指摘の累積・エスカレーション）を作る

- 日付: 2026-10-10（UTC）
- タスク: PBI-7
- PR: #3
- ブランチ: feat/issue-7-requirements-gate
- 関係する ADR: [工程の成果物を人間の承認ゲートで止め、差し戻しの指摘を累積してエージェントに渡し、上限を超えたらエスカレーションにする](../adr/20261010-0732-approval-gate.md)

## 目的

要求要件の工程の後に人間の承認ゲートを置き、成果物チェックの画面で承認・差し戻しができるようにする。差し戻しの指摘を累積して
再提出のたびにエージェントへ渡すこと、指摘ごとのエージェントの対応を表示すること、前提が変わった指摘を無効にできること、
差し戻しが上限を超えたらエスカレーションにすること、操作をすべて台帳に記録することが受け入れ条件の要点。
指摘の「再発なし」の判定は、合意のうえで PBI-10 に回した。

## したこと

- 台帳のイベントと復元（`packages/core/src/events.ts`・`projection.ts`）：提出（`StepSubmitted`）・承認・差し戻し・指摘の無効化・エスカレーション。
- デーモン（`apps/daemon/src/service.ts`・`server.ts`・`prompts.ts`）：ゲートの操作の API、前回の下書きと有効な指摘の全件をプロンプトに入れる処理、
  エージェントが返す指摘ごとの対応（JSON のブロック）の取り出し。
- 承認待ちのあいだは予算の超過で止めず、次の実行の前に判定するようにした（PBI-2 のテストをこの仕様に合わせて直した）。
- 画面：成果物チェック（`apps/web/src/app/tasks/[id]/review/page.tsx`・`apps/web/src/components/gate-form.tsx`）、タスクの詳細の案内、一覧の「あなたの出番」。

## 確かめたこと

- `npm test`（59件）・`npm run lint`・`npm run typecheck` が通った。
- スタブのエージェントで、画面から次を確かめた。
  - チケットの作成 → 承認待ち → 指摘を付けて差し戻し → 再提出（2回目、エージェントの対応が出る）→ 指摘の無効化 → 承認 → 設計が実行の対象になって待機。
  - 差し戻しを4回目まで続けるとエスカレーションになり、書いた指摘が残ったまま「上限を超えて差し戻す」か「承認する」を選べる。
- レビューの指摘の対応の後、画面でも、タブ A で1回目を開いたままタブ B で差し戻し、2回目の提出の後にタブ A から承認すると拒否されることを確かめた。
- 再レビューでは `npm test`（61件）・`npm run lint`・`npm run typecheck` が通り、一時 DB と API で、提出回なしは 400、古い提出回は 409、
  最新の提出回の承認は 200 で、拒否の時に台帳が変わらないことが確かめられた。ブラウザでの表示、本物の Docker とエージェントでの実行、
  クリーンな環境での全体のビルドは確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 承認・差し戻しの照合が工程の名前だけなので、古い成果物を開いたタブから、未確認の新しい成果物を承認できる | 承認・差し戻しの入力に、画面が表示していた提出回 `submission` を必須で含め、現在のゲートと一致しなければ 409 で拒否するようにした（最新の提出回を案内する文言つき）。回帰テストを足し、修正前のコードで失敗することを確かめた |
| 再提出で回答されなかった指摘に、前回の対応の文が残って表示される | 再提出のたびに、その工程の有効な指摘の対応をいったん未回答に戻し、今回回答されたものだけを入れるようにした。対応を書いた提出回（`respondedIn`）も記録して画面に出し、未回答・無効の指摘はそうとわかる表示にした。指摘の手順を回帰テストにし、修正前のコードで失敗することを確かめた |

## 残したこと

- 指摘の「再発なし」の判定は PBI-10 で足す。
- 設計の工程は PBI-8 で実装する（この時点では、承認の後に待機する）。
- 指摘を入力したまま「承認する」を押すと、入力した指摘は確認なしに捨てられる。
- PBI-2 で作ったタスクは、承認ゲートの導入前の台帳なので、承認待ちにならない。
