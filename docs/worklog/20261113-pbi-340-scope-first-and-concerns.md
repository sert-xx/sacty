# 要求要件・設計はスコープを最初に置き、人への確認に確認しない場合の懸念を添え、writing スキルに書き出し先ごとの改行と語の選び方を足す

- 日付: 2026-11-13（UTC）
- タスク: PBI-340
- PR: #363
- ブランチ: feat/issue-340-writing-scope-concerns
- 関係する ADR: [要求要件・設計はスコープを最初に置き、人への確認には確認しない場合の懸念を添える](../adr/20261113-0708-scope-first-and-concerns-in-questions.md)

## 目的

人の要望に合わせて、sacty が書く文章を読みやすくする。
要求要件・設計はスコープから読めるようにし、人への確認には確認しない場合の懸念を添える。
writing スキルに、書き出し先ごとの改行、英語を直訳しないこと、一般的な言い回しを足す。

## したこと

- 既定のスキル `writing`
  - SKILL.md：決まりの要点・書く手順・見直しに、書き出し先ごとの改行、語と言い回し、人への確認の懸念、スコープを先に書くことを足した。
  - layout.md：書き出し先ごとの改行の書き方の表（GitHub のコメント、Markdown のファイル、Confluence のエディタとストレージ形式、チャット）と、要求要件・設計の並べ方を足した。
  - sentences.md：人に確認を求める書き方を足した。
  - wording.md（新規）：英語を単純に置き換えないこと、カタカナ語の扱い、一般的な言い回しの例。
- 既定の規則 `rules.md`：人に確認・判断を求めるときは、確認しない場合の具体的な懸念を添える。
- 工程の指示（`prompts.ts`）
  - 要求要件・設計の冒頭を「スコープ」「確認したいこと」「既定で決めたこと」の順にし、確認したいことに懸念を書かせる。差し戻しの質の基準にもスコープを足した。
  - 人が確かめること（`humanChecks`、受け入れの確かめ方の「人が確かめること」）に懸念を添えさせる。
- 既定のスキル `ears-requirements`：書く手順の最初に、スコープを要求より先に書くことを足した。
- 観点 D-10：スコープが最初にあるかと、確認したいことに懸念があるかを確かめる手順を足した。
- 仕様書（context・tasks-and-steps）とユーザードキュメント（context・tasks）を日英で直し、ADR を足した。

## 確かめたこと

- `npx vitest run apps/daemon/src/prompts.test.ts apps/daemon/src/default-skills.test.ts`：通過。
  足したテスト（スコープが確認したいことより前、懸念の指示）は、`prompts.ts` を main に戻すと失敗することを確かめた。
- `npx vitest run tests/docs`：通過。

## レビューの指摘と対応

- セルフレビュー（DA）：SKILL.md の箇条書きの1項目に、「。」の後の改行が無い所があった。改行して直した。
- セルフレビュー（DA）：`ears-requirements` の書く手順が「何を実現するか」から始まり、スコープを先に書く決まりと食い違っていた。手順の最初にスコープを足した。
- 人の指摘：リポジトリの Markdown のファイルで、「。」の後の改行が表示でつながるままにせず、表示でも改行されるようにしてほしい。
  「。」で終わる行の行末に `\`（強制改行）を置く決まりにした（段落の最後の文・見出し・表のセル・コードブロックには付けない。行末の半角スペース2つは見えず消されやすいので使わない。リポジトリの決まりがあればそれに従う）。
- 人の回答：スコープを「確認したいこと」より前に置く順で良い。
- 人の回答：分量の目安は少し増やしてよい。
  スコープの節（3〜5行）の分として、`DRAFT_LINES` を小さな変更で 20 行から 25 行に、大きな変更で 60 行から 65 行に増やした。
- 人の指摘：スコープには、含むことと含まないことの両方を書いてほしい。
  対象外を条件付き（読む人が含まれると思いそうなものがあるときだけ）にしていたのを改め、必ず両方書かせ、対象外が無ければ「対象外：なし」と書かせるようにした。
- セルフレビュー（DA）：D-10 と writing は「該当なし」の行を書きすぎとして消させるので、セルフレビューで「対象外：なし」が消されるおそれがあった。スコープの「対象外：なし」を例外にした。
- sacty のレビュー（`prompts.ts` の答えの反映だけの直し）：スコープの節の無い前の版の下書きを、推奨どおりの答えだけで差し戻すと、ほかの節を一字一句保つ決まりのせいでスコープを足せない。
  前回の下書きにスコープの節が無いとき（`scopeComesFirst`）だけ、スコープの節を足して冒頭の節を並べ直すことを例外として許し、提出の前の確認もその順にした。
  テストは、例外の指示を外すと失敗することを確かめた。
- sacty のレビュー（ADR）：行数の目安は、採用中の ADR（初版を最小限にする）が決めた値を変えている。
  古い ADR を `superseded` にし、置き換えた部分（行数の目安）と、新旧の ADR の相互のリンクを書いた。
- sacty の再レビュー（`prompts.ts` のスコープの判定）：文書のどこかにある「## スコープ」や「## スコープ外」にも一致し、冒頭にスコープが無い下書きでも例外の指示が出なかった。
  題の見出しの次の最初の節が「スコープ」という名前かで判定する `scopeComesFirst` に変え（コードブロックの中は数えない）、後ろにあるスコープは冒頭に移すよう指示した。
  テストは、古い判定に戻すと失敗することを確かめた。
- sacty の3回目のレビュー（`prompts.ts` の通常の差し戻し）：スコープの無い前の版の下書きを、スコープと関係の無い指摘で差し戻すと、冒頭にスコープを求める指示と、関係の無い節を保つ指示が食い違う。
  軽い直しと同じ例外（スコープの節を足すか冒頭に移して並べ直す）を、通常の部分的な直しにも入れた。
  テストは要求要件・設計の両方で、例外を外すと失敗することを確かめた。
- sacty の4回目のレビュー（`prompts.ts` のスコープの判定）：冒頭にスコープの節があっても、対象外の行が無い前の版の下書きでは、例外の指示が出なかった。
  冒頭のスコープの節に対象と対象外の行があるかまで見る `scopeIsWritten` に変え、足りない行を補うよう指示した。
  テストは、通常の差し戻しと答えの反映だけの直しの両方で、古い判定に戻すと失敗することを確かめた。
- CI の check：タスクの並行実行（PBI-30）のテストが1件失敗した（`expected [ 'タスク2' ] to deeply equal [ 'タスク2', 'タスク3' ]`）。
  今回の変更は並行実行に触れておらず、手元では通る。次のコミットの CI で、通ることを確かめた。
- sacty の5回目のレビュー（`prompts.ts` の対象外の判定）：本文のどこかに「対象外」という語があるだけで、対象外の行があるとみなしていた。
  行の頭に札（「対象外：」「**対象外**」「| 対象外 |」、節の中の小見出し）を置いた行だけを数えるようにし、スコープの節は同じか浅い見出しで終わるようにした。
  テストは、札の判定を古い形に戻すと失敗することを確かめた。
- sacty の5回目のレビュー（仕様書、提案）：「sacty は冒頭の節を読み取らない」と書いていたが、差し戻しでは `scopeIsWritten` がスコープの節を読む。
  本文のまま表示することと、差し戻しの判定を分けて書き直した（日英）。
