# オーケストレーターが、チケットとリポジトリを読んで工程を選ぶ

- 日付: 2026-10-11（UTC）
- タスク: PBI-17
- PR: #23
- ブランチ: feat/issue-17-orchestrator
- 関係する ADR: [タスクの開始時に、オーケストレーター（AI）がタスクと対象リポジトリのコードを読んで、決まった候補から工程を選ぶ](../adr/20261011-0139-orchestrator-chooses-step-plan.md)

## 目的

固定の工程をやめ、タスクの開始時に AI のオーケストレーターがチケットと対象リポジトリのコードを読んで、sacty が決めた候補から工程を選ぶ。選んだ工程・理由・費用は作業履歴に残し、人間は承認しない。判断できないときは標準の工程で進める。設計を省いたタスクも、実装の検証（テストと最終レビュー）を行う。画面に選んだ工程と理由を出す。

## したこと

- チケットを作った時点では `TaskCreated` だけを記録し、工程を決めない。最初の実行で対象リポジトリを用意した後に、オーケストレーターを新しいセッションで実行し、起点のコードを読み取り専用で渡す（`apps/daemon/src/service.ts`）。選んでいる間に人間が止めた・中止したら記録しない。
- 候補 `STEP_PLANS`（`standard`・`skip-design`）と、オーケストレーターへの指示・出力の読み取り（`apps/daemon/src/prompts.ts`）。
- 作業履歴：`StepsChosen`（組み合わせ・理由・費用、actor は `orchestrator`）。失敗したときは `fallback: true` と理由（`orchestrator.fallback`）を残す（`packages/core/src/events.ts`・`packages/core/src/projection.ts`）。
- 設計を省いたタスク：実装の指示で、要求要件の受け入れ条件をテストで確かめるよう伝え、観点を `REQ` にする。最終レビューも `REQ` を観点にする。
- 画面：タスク詳細の工程の下に「選んだ理由」、標準の工程にしたときはその旨、選ぶ前は「オーケストレーターが工程を選びます」を出す。作業履歴の「工程を決定」に理由を添える。チケットの作成の画面の説明も直した。
- あわせて、`packages/cli/bin/sacty.js` を git でも実行できるファイル（100755）にした（中身は同じ）。`npm install` のたびに作業ツリーに変更が残っていたため。
- レビューの対応：テストを対応させる観点を検証の最初に設計の有無で一度だけ決め、テストの対応の確かめ（`unmappedViewpoints`）と最終レビューで同じものを使うようにした。

## 確かめたこと

- `npm test`：250件が通った（5件追加、既存の6件を「工程はタスクの開始時に選ぶ」形に更新）。チケットと起点のコードを読み取り専用で渡し、工程と理由・費用を記録して最初の工程を続けること、失敗したときに標準の工程で進めて記録すること、設計を省いたタスクで `REQ` が入り成果物チェックまで進むこと、出力の読み取り、作業履歴の表示を確かめた。選んだ工程を無視して標準にするとテストが失敗することを確かめた。
- 画面で確かめた（スタブの AI の環境）：チケットを作ると、対象リポジトリの用意 → 工程を決定（理由つき）→ 要求要件の順に記録された。タスク詳細に「選んだ理由：スタブのため標準の工程」と出た。費用にオーケストレーターの分が入っていた。
- 再レビューで、全体のテストは250件が通り、変更の対象外の `context.test.ts` の1件が5秒で時間切れになった。そのファイルだけを実行し直すと12件すべて通った。`npm run lint`・`npm run typecheck` も通った。
- 実際の AI（Claude Code）での工程の選択は確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 設計を省いた経路で、`REQ` をテストの段階の必須の観点にしていないので、`REQ` にテストを対応させなくても合格扱いになる | 観点を検証の最初に一度だけ決め（設計があれば承認済みのテスト観点、無ければ `REQ`）、テストの対応の確かめと最終レビューで共通に使うようにした。`REQ` の対応を返さない実装で `TestsRun` が `passed: false`・`unmappedViewpoints: ["REQ"]` になり、最終レビューをせず実装をやり直す回帰テストを足し、戻すと失敗することを確かめた |

## 残したこと

- 実際の AI での工程の選択は確かめていない。
- タスクの分割・調査・レビュー・再現などの工程は、後のタスクで足す。
