# 言語ごとのイメージを定義し、オーケストレーターが工程ごとに選ぶ

- 日付: 2026-10-13（UTC）
- タスク: PBI-41
- PR: #53
- ブランチ: feat/issue-41-language-images
- 関係する ADR: [言語ごとの実行イメージを config.yaml の images に定義し、オーケストレーターが工程ごとに選ぶ](../adr/20261013-0138-superseded-language-images-per-step.md)

## 目的

Python・Go・Java などのリポジトリを扱えるよう、言語ごとの実行イメージを定義し、オーケストレーターが工程ごとに選ぶ。
1つのリポジトリに複数の言語がある場合（モノレポなど）も、工程ごとに違うイメージを使えるようにする。

## したこと

- イメージの定義と作成（`apps/daemon/src/config.ts`・`apps/daemon/src/image.ts`・`packages/cli/docker/Dockerfile`・`packages/cli/src/index.ts`）：
  - `config.yaml` に `images` を足した。名前ごとに、説明・元のイメージ・環境変数・Maven/Gradle のミラーを書ける。
  - 元のイメージは、Node.js の入っていない Debian・Ubuntu 系か、RHEL 系（Rocky Linux など）でよい。sacty が Node.js（`node_image`、無ければ `image_build.base_image` か
    `node:22-bookworm-slim` から写す）・git・Claude Code・Codex を足し、`node` ユーザーで動かす。git は apt-get・dnf・microdnf・yum のどれかで入れる。
  - `env`：言語ごとのレジストリなど（`PIP_INDEX_URL`・`GOPROXY` など）。エージェントとテストのコンテナに名前だけを渡す（値はコマンドラインに出さない）。
    認証の値（`TOKEN`・`PASSWORD` などを含む名前、ユーザー名・パスワードを含む URL）と、`PATH`・`HOME`・`DOCKER_*`・`SACTY_*`・`CODEX_*` などの sacty や docker とぶつかる名前は書けない。
  - `maven_mirror`：Maven（`settings.xml` の mirror）と Gradle（init スクリプト）の取得先を、すべてその URL に向ける。
  - `sacty image build [<名前>...]`：名前を省くと、既定のイメージと `images` のすべてを作る（`default` は既定のイメージ）。既定のイメージは、これまでどおり作れる。
- イメージの選び方（`apps/daemon/src/service.ts`・`apps/daemon/src/prompts.ts`・`packages/core/src/projects.ts`）：
  - オーケストレーターは既定のイメージで動き、工程を選ぶときにイメージの候補（名前と説明）も見て、工程ごとに選ぶ。テストのコマンドは、実装（不具合の修正では再現）の工程のイメージで実行する。
  - プロジェクトの対象（リポジトリ・Org）ごとにイメージを指定できる。指定すると、オーケストレーターに選ばせず、すべての工程でそれを使う（リポジトリの指定が Org の指定より優先）。
  - 選んだイメージと理由は、作業履歴（工程の決定）に残す。`images` に無い名前を選んだ・指定したときは、工程を決めずに理由を示して止まる。工程を決めた後に設定から消したときも、その工程を実行せずに止まる。
- 画面：プロジェクトの設定の対象の行に、イメージの選択（オーケストレーターが選ぶ・default・images の名前）を足した（`images` を書いていなければ出さない）。
  作業履歴の「工程を決定」に、工程ごとのイメージと、決めたのが誰か（理由）を出す。
- 統合レビューにも、選んだイメージと環境変数を使うようにした（レビューの指摘）。
- README に説明を足した。

## 確かめたこと

- build・typecheck・lint・全テスト（484件）が通った。
- 追加したテスト：設定の検証（認証の値・予約された名前・危ない URL・名前の形）、雛形の例、イメージの作成の引数、作る対象の選び方、docker の環境変数（名前だけ渡す・実行の環境変数が優先）、
  プロンプトと出力の読み取り、対象の指定の優先、オーケストレーターの選択・対象の指定・無い名前・設定から消した場合、工程とテストのイメージ（再現と実装で別）、作業履歴の文言。
- 主な判定を戻すと、テストが失敗することを確かめた（8通り）。
- 実際にイメージを作って確かめた。
  - Rocky Linux 9・Python 3.12・Go 1.23・Maven（eclipse-temurin 17）・Gradle 8.10 を元にしたイメージで、Node.js・git・Claude Code・Codex が動き、`node` ユーザーで実行される。
  - Maven・Gradle：`maven_mirror` に向けた依存の取得が、ミラー（存在しないアドレス）に向かう。ミラーの無い元のイメージでは同じ依存を取れる。
  - Go：実行のときに渡した `GOPROXY` が効く。
  - 既定のイメージは、これまでどおり作れる（Node.js の写しを入れない）。
- 画面は動画で確かめた（一時的なデータの環境）。
- 再レビューで、全485テスト・lint・型チェックが通った。Docker のイメージの実際のビルドは、レビューでは未実施。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 統合レビュー（integrate）は専用の処理に分かれていて、既定のイメージに固定され環境変数も渡していなかった。`images.integrate` に java を選んでも既定の Node のイメージで動き、選んだ後に定義を消しても止まらなかった | 統合レビューでも、工程の実行と同じく選んだイメージを決め、イメージと環境変数を渡すようにした。`images` から消した名前なら、実行せずに理由を示して止まる。回帰テストを足し、戻すと失敗することを確かめた。ほかに既定のイメージで動くオーケストレーター・ゴールガーディアンは、コードを読むだけの判断なので、意図どおり既定のイメージのままにした |

## 残したこと

- 利用者の環境で、次を確かめる（PR で依頼した）：利用者の CI のイメージ（Rocky Linux）を `base_image` にして `sacty image build <名前>` で作れること。
  利用者のレジストリの URL を `env`・`maven_mirror` に書いて、対象リポジトリのセットアップ・テストが通ること。
