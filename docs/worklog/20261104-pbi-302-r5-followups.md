## 概要

実務実証実験の r5（2026-11-04、sacty 1.16.0・main e691e3eb）で見つかった問題を、4 群に分けて直した（A：作業領域・検証、B：差し戻し・レビュー・判断、C：成果物と PR の本文、D：画面・記録）。1 つの PBI なので、作業履歴は 1 ファイルにまとめ、群ごとに見出しで分ける。A・D、B、C は別の担当が並行して作り（`feat/issue-302-r5-followups-a`・`-b`・`-c`）、あとで 1 つのブランチ・1 つの PR にまとめた（下の「まとめたときの確認」）。各群の節は、その担当が書いたときの記録で、群の中の「別の担当で、ここでは触れない」はそのときの分担を指す。

## A・D 群：作業領域・検証・画面・記録

### 目的

実験 r5 で見つかった問題のうち、作業領域・検証（A1・A2）と画面・記録（D1・D2）を直す。

- A1（F47）：作業用のファイル（`.sacty-tools/` の検証の記録）がリポジトリの検査を落とし、人の確認と PR の本文に入る。指示を足すだけでは効かなかった（PBI-301 A6）ので、仕組みで防ぐ。
- A2：テストの終了コードが 0 でないのに「合格」とだけ出る。理由を出す。
- D1：AI のレビューが付く前に、作り直した head が承認待ちに進む。今の head の AI のレビューの状況を出す。
- D2：Codex の実行の費用が「概算」のままで、報告か換算かが分からない。

### 調べたこと（r5 の証拠）

- S18：レビューの記録（ログ・`aggregation.json`・`dispatch.md`）が `.sacty-tools/review*/` に書かれ、`prettier --check .` が `.sacty-tools/review-fix/dispatch.md` で落ちた。最終レビュー 2 回目の終了コードが 1 で、環境による失敗だけとして合格にし、説明が人が確かめることの 2 件になった。
- S14：同じく `.sacty-tools/review/summary.json` が prettier を落とした。
- S16：検証のスクリプト（`test/capture-baseline.js`）が `.sacty-tools/baseline` を使い、リポジトリのコードに名前が入った。
- 原因：検証のスキルの「一時ディレクトリ」が場所を示さない。指示が「`.sacty-tools/` は PR・コミットに入れない」と書くので、作業用のファイルの置き場と読まれた。最終レビューの指示は、`.sacty-tools/` があるだけで「その環境だけの結果」を人の確認に入れさせていた。
- `RunCostRecorded` は、報告を使った実行とモデルごとに換算した実行だけを記録していた（PBI-301）。Codex は使用量だけを報告し、費用は報告しないので、記録が無かった。

### したこと

- A1
  - 置き場所：`WORKSPACE_SCRATCH_DIR`（`/tmp/agent-scratch`）を決め、既定のスキル（検証の実行・集約・リンク先の文書・画面の撮影）の「一時ディレクトリ」をこの場所にした。`.sacty-tools/` は道具だけと、既定の規則・実装の工程の指示・最終レビューの指示に書いた。
  - 差分の内部の名前：`internalNamesInDiff` で、追加された行の内部の名前を見つけ（依頼・要求要件・設計が挙げたものは除く）、最終レビューの指示にデータとして渡し、`extractFinalReview` で観点 `SCOPE`（範囲外の変更）の不合格にした。
  - 人が確かめることから外す：内部の名前を含む項目を外して `droppedHumanChecks` に残し（「この環境だけの結果」は入れたツールの注記なので残す）、環境による失敗の申告の内部の名前を含むものは 1 件の中立な文（`WORKSPACE_FILE_FAILURE`）にして、人が確かめることに出さない。`/tmp/sacty-…` のパスを `withoutInternalPaths` で除く。
  - 最終レビューの指示：`.sacty-tools/` の中の作業用のファイルが検査を落としたときは、写しから消して検査をやり直して判定させる。`.sacty-tools/` があるだけでは「その環境だけの結果」にしない（入れたツールがあるときだけ）。
- A2：PR の本文のテストの行に、終了コードが 0 でないのに合格にした理由を添えた（`environmentPassNote`）。画面の観点ごとの結果を「テスト合格（環境による失敗のみ）」にし、テストの欄に理由を足した。
- D1：`aiReviewFor`・`aiReviewOfHead`（`ai-review-head.ts`）で、同じ PR を指すほかのレビューのタスクから、今の head の状況（none・reviewing・attached）を計算する。`TaskService.view`（`GET /api/tasks/:id`）が `Task.aiReview` を足し、承認の画面とタスクの詳細（`AiReviewNotice`）に出す。PR の本文の結論に 1 行入れる（`aiReviewBodyLine`）。承認やマージは止めない。
- D2：使用量のある実行のすべてで `RunCostRecorded` を記録する。作業履歴の文を「CLI が費用を報告しなかったので、使用量を単価で換算した額」にした。
- 仕様書（`tasks-and-steps`・`approval`・`agent-execution`）・ユーザードキュメント（`tasks`・`intake`・`config`）を日英で直した。ADR を足した。

選んだこと：

- `.sacty-tools/` 自体は作業領域の外に移さなかった。実装の工程で入れたツールが、使い捨ての写しで検証するゴールガーディアンに渡らなくなる（PBI-278 の設計を変えることになる）ため。
- 内部の名前の持ち込みは、sacty 自身のリポジトリを直すタスクのように求められる場合があるので、依頼・要求要件・設計が挙げた名前は除いた。
- AI のレビューの状況は、承認の画面は最新、PR の本文は書いた時点のものとした。

### 確かめたこと

- 新しいテスト：`apps/daemon/src/r5-followups-a.test.ts`（スキルと指示の文面、`internalNamesInDiff` の 0・1・上限超え・削除したファイル・許可した名前・似た名前、最終レビューの結果（不合格・外す・言い換え・中立な文・PR の本文）、A2 の本文、D1 の判定と本文）、`apps/web/src/components/ai-review-notice.test.ts`、`implementation.test.ts`（A2 の画面）、`daemon.test.ts`（D2）。
- `npx biome check .`・`npm run typecheck`：エラーなし。
- `npx vitest run`（全体を1回）：202 ファイル・4051 テストが成功（3 件は元から skip。終了コード 0）。`tests/docs` も成功。
- 修正を戻すと落ちること：差分の内部の名前を範囲外にする処理・人が確かめることの除外・環境による失敗の中立な文・AI のレビューの「レビュー中」の判定・`RunCostRecorded` を全実行で記録する処理・`/tmp/…` のパスの除去を、それぞれ戻すと、対応する新しいテストが落ちた（戻して成功を確認）。サービスが `internalNames` を最終レビューの判定に渡さないようにすると、`daemon.test.ts` の統合のテストが落ちた。

### 残した制限

- `.sacty-tools/` の下に入れた道具に、フォーマッター・リンターが検査するファイル（`npm install` した `package.json` など）が含まれると、検査はそれで落ちうる。道具の置き場は変えていない（ADR 参照）。
- AI のレビューの状況は、同じデーモンのレビューのタスクだけを見る。PR の本文の行は、本文を書いた時点の状況で、その後は更新されない。
- 実際の Docker での、エージェントが `/tmp/agent-scratch/` に記録を書くことは確かめていない（指示と、差分・結果の機械的な検出で防ぐ）。

## B 群：差し戻し・レビュー・判断

### 目的

実務実証実験の r5（1.16.0、main e691e3eb）で見つかった、差し戻し・レビュー・判断に関わる問題（PBI-302 の B1〜B6）をまとめて直す。A（作業領域・検証）と C（成果物と PR の本文）、D（画面・記録）は別の担当で、ここでは触れない。1 つの PBI の B 群なので、作業履歴は B 群の分として 1 ファイルにまとめた。

- B1（F48、S5）：質問への答えだけのコメント（should に「推奨どおり」）で、要求要件を丸ごと作り直した（報告額 約 $1.45）。
- B2（F50、S16）：Sacty のレビューが、同じ head で直っている指摘を「未対応」として「修正が必要」にした。
- B3（S14）：ゴールガーディアンが、89 行目へのコメントを 88 行目の内容として読んだ。
- B4（S16）：要求要件・設計に無い共有の仕組み（キュー）が、4 回続けて実装に入った。
- B5（S5。F34 の再発）：オーケストレーターが要求要件を残す理由に 3 つ挙げたが、「確認したいこと」に出たのは 1 つだけ。
- B6（F49、S14）：監査が、プロジェクト全体のメモリーに、依頼者の答えを事実として登録した。

### r5 の記録で確かめたこと

- S5：工程の決定（`StepsChosen`）の理由に、要求要件を残す理由が 3 つあった。(1) Web の異常系のテストで何を確かめるかが未定、(2) 既存の呼び出し側の 422 の扱いの移行の要否、(3) 受け入れ条件の完了の条件（`make lint test smoke build`）と AGENTS.md（`make lint test smoke`）の食い違い。要求要件の「確認したいこと」に出たのは (1) の should 1 件だけ。(2) は受け入れ条件が必須にした変更に伴うこと、(3) は受け入れ条件に従えば済む手順の食い違いで、人に確かめることではなかった。情報収集の出力の「食い違い・未確定のこと」の節に、(1)(3) が挙がっていた。
- S5：「推奨どおり」のコメント（09:44）が、ゴールガーディアンの判断で「新しい要望・方針の変更」の差し戻しになり、要求要件が再実行された（判断 $0.128 ＋ 再実行 $1.322）。
- S16：レビュー本文の根拠は「既存の指摘に未対応のものがあります」。レビューした head（7ed51c5）の設計は、その指摘を処理の流れと TV-5 に反映済みだった。行コメントは [提案] 1 件だけ（`evidence-b3.md`）。
- S14：台本 3 の行コメント（89 行目）を 88 行目の内容として解釈した。ゴールガーディアンの指示に渡る指摘は `path:行：本文` の文字列だけで、行の内容は渡っていなかった。
- S16：要求要件にも設計にも無いキューが r2〜r5 の 4 回続けて入った。
- S14：監査が SactyTest 全体のメモリー（9c78f980）に、依頼者の答えを事実として登録した。題が「…依頼者は削られたくないものとして扱った」、中身に「依頼者は『もっとシンプルにして』と書いた」。

### したこと

#### B1 質問への答えだけのコメント

- `packages/core/src/events.ts`：差し戻しの原因に `question_answer` を足した。答えと推奨の関係 `ReworkAnswer`（`as_recommended`・`changes_decision`）を足し、`ReworkJudged`・`ChangesRequested`・`RequestChangesInput` の `answer`、投影の `pendingReview.judgement`・`prRework` に持たせた。
- `apps/daemon/src/prompts.ts`：要求要件・設計の PR の戻し先の判断（`buildStepReworkPrompt`）に、原因 `question_answer` と `answer` の判断を足した（`reworkCauseLines`・`REWORK_ANSWER_LINES`）。実装の PR には足さない（sacty の質問が無い）。`extractRework` は、原因が `question_answer` のときだけ `answer` を読む。
- `isAnswerOnlyRework`：判断した指摘の集合そのもので始まった要求要件・設計の実行で、原因が `question_answer`、答えが `as_recommended`、戻し先を判断できているときだけ真。要求要件・設計の実行の指示は、このとき、通常の直しの指示とセルフレビューの代わりに、答えの反映だけの直し（`answerOnlyReworkLines`）と、読み直す 3 点の確認（`answerOnlyCheckLines`）にする。出典の分類と指摘への対応の報告は今までどおり。
- `apps/daemon/src/service.ts`（`settleReview`）：`as_recommended` を `ChangesRequested` に残すのは、判断した戻し先がその PR の工程（要求要件・設計）のときだけ。前の工程へ戻す・実装の PR・判断できないときは残さない。`changes_decision` はそのまま残す。
- ダッシュボード・作業履歴の原因の表示に「質問への答え」を足した（日英）。

#### B2 前の指摘の対応を head で確かめさせる

- `apps/daemon/src/prompts.ts`：`HEAD_CHECK_LINES`（再レビューの節と、再レビューでない最初のレビューの既存の指摘の節）。先頭のコミットのファイルを開いて確かめる、前回の本文・前のコミット・作者の返答だけを根拠にしない、未対応と書くときは読んだ箇所を添える、示せないものは未対応と書かない、判定 `changes_required` は先頭のコミットで成り立つ `[要修正]` に基づける、本文の「未対応」と行コメントの重さ・判定を食い違わせない。判定の説明（`changes_required`）にも同じ趣旨を足した。
- 既定のスキル `pr-review.md`：同じ決まりを、sacty・特定の言語・ツールに寄せない書き方で足した。
- sacty は未対応の主張を head の内容と照らして検査しない（下の「残したこと」）。

#### B3 行コメントの行の内容

- `apps/daemon/src/github.ts`：`lineContextOf`。GitHub のコメントの `diff_hunk`（コメントが付いた行が最後）から、その行と直前の 2 行を取る（ハンクの見出し・差分の印・「改行なし」の注記を除き、1 行 200 文字まで）。`PullRequestFeedback.lineContext` に持たせる。
- `apps/daemon/src/service.ts`（`feedbackRemarks`）：行コメントの指摘の文の後ろに、`（コメントが付いた行の内容：「…」。直前の行：「…」）` を足す（`lineContextText`。秘密情報を伏せる）。2000 文字の上限は、指摘の文を短くして収め、添える分は切らない。古い head の AI のレビューを捨てるときの要点（`discardedSummary`）には添えない。
- `apps/daemon/src/prompts.ts`：添えた指摘があるとき、戻し先の判断（`reworkRemarkLines`）と工程の指示（`remarkSections`）に、行番号から数えず、添えた行の内容で箇所を確かめさせる注意（`lineContextNote`）を足した。

#### B4 共有の仕組み

- `apps/daemon/src/prompts.ts`：`SHARED_MECHANISM_IMPLEMENT_LINE`を、実装の指示の 5 つの経路（要求要件・設計あり／要求要件を省いた／テストの仕組みが無い／不具合の修正）に足した。足さないと満たせないと確かめたときだけ足し、実装の説明の最後に「共有の仕組みを足した理由」の節を作らせる。最終レビュー（`sharedMechanismLines` の最終レビューの分）は、理由があり確かめられれば `humanChecks` に「共有の仕組みを足した：…（理由）」を書かせ（PR の本文の「人が確かめること」に出る）、理由が無い・足さなくても満たせるなら範囲外として不合格にさせる。

#### B5 要求要件を残す理由

- 渡す：`keepRequirementsReasonLines`。最初の要求要件の実行に、オーケストレーターの理由（`Task.stepsChoice.reason`）を JSON のデータ（`orchestratorReason`）で渡す。理由ごとに「確認したいこと」に出すか、「確認したいこと」の節の最後の「確認しないと決めたこと」に、決めた内容と確認しない理由を書かせる。
- 見直す：`DETAILED_ACCEPTANCE_LINE`。「依頼と文書・コード・既存の方針が食い違う」を、作るものが変わるものに限った。人に確かめることが無い理由（作るものが変わらない文書どうし・文書と受け入れ条件の食い違い、受け入れ条件が決めた変更に伴う追従、実装が決められる未確定のこと）を、残す理由にしないと書いた。残す理由は、答えが複数あり、依頼からも既存のコード・文書からも決まらず、人に聞かないと決められないことだけ、`reason` に 1 つずつ書かせる。#285・#289 の決まりと、残すべき例外（曖昧・作るものを左右する食い違い・人に確かめたい判断・書き忘れや衝突・共有の状態への新しい意味・API の変更）は変えていない。

#### B6 監査のメモリー

- `apps/daemon/src/memory-answers.ts`（新規）：登録の前の検査。`requester_mentioned`（依頼者を主語にした言い方がある）と `requester_text_copied`（依頼者が書いた文〔題・本文・人の指摘・再開の補足〕を、空白・記号を除いて 14 文字以上そのまま写した）。英数字が主の一致は数えない。
- `apps/daemon/src/audit-prompts.ts`：`extractAuditDive` が、検査に当たったメモリーを登録せず、`skippedMemories` に返す（登録の上限には数えない）。深掘りの指示に、依頼者の答えを事実として書かないこと・登録の前に検査することを足した。
- `AuditDeepDived` に `skippedMemories`（題・理由）を足した。作業履歴の深掘りの行に件数が出る（日英）。

#### 文書

- 仕様書（`approval`・`tasks-and-steps`・`memory`・`architecture`、日英）、ユーザードキュメント（`tasks`・`dashboard`・`audit`、日英）、ADR 1 件。
