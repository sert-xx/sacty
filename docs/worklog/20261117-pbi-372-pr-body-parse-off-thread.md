# PR の本文のリンクの解析で、デーモンのほかの処理が待たないようにする

- 日付: 2026-11-17（UTC）
- タスク: PBI-372
- PR: #427
- ブランチ: feat/pbi-372-pr-body-parse-blocking
- 関係する ADR: [PR の本文のリンクの解析を別スレッドで行い、5 秒で打ち切る](../adr/20261117-1638-parse-pr-body-links-off-thread.md)

## 目的

sacty が作る PR の本文から、作業領域（`/workspace`）へのリンクを外す変換は、本文を Markdown として同期で解析していた。
記号が本文の上限（65,000 文字）近くまで続く本文では、解析に数秒〜数十秒かかり、その間、デーモンのほかの処理（HTTP の応答・停止の操作）が待つ。
解析の間も、デーモンがほかの処理に応えるようにする。

受け入れ条件の要点。

- 遅くなる入力（`>`・`*a`・`*_`・`1. `・`+ ` の繰り返しを上限近くまで）で、デーモンのスレッドが止まる時間が、決めた上限に収まる。
- 解析しなかった・打ち切った本文は、変えずに使う（PR の作成・更新は止めない）。そのことが、作業履歴かログで分かる。
- ふつうの本文の変換の結果は、変わらない。
- 仕様書（日英）の既知の制約の記述を直す。

## したこと

- 直す前のコードで測り、直し方を決めた（[ADR](../adr/20261117-1638-parse-pr-body-links-off-thread.md)）。解析する前に、遅くなる本文を形・大きさで見分ける案は、見分けられない形が残ったので採らず、解析を別スレッドに分けて、時間で打ち切ることにした。
- 変換の本体（`convertWorkspaceLinks`。これまでの `withoutWorkspaceLinks` の中身）を、`apps/daemon/src/pr-body-links-worker.ts` に移した。変換の中身は変えていない。
  - 作業領域のパスを、引数で受け取るようにした（別スレッドで読むファイルが、ほかのソースファイルを import しないため）。
  - 例外で外せなかったことを、結果で返すようにした（`failed`）。これまでは、外すリンクが無いときと区別が付かなかった。
  - ファイルの最後に、別スレッドの入口を置いた。仕事（`ConvertJob`）を付けて別スレッドで起動されたときだけ、変換して、結果を1回送る。
- `apps/daemon/src/pr-body-links.ts` に、別スレッドで変換する処理（`convertOffThread`）を置いた。
  - 作業領域へのリンクがありえない本文は、別スレッドを起動せずに返す。
  - 時間の上限（`PARSE_TIMEOUT_MS`。5 秒）で別スレッドを止めて、本文を変えずに返す。
  - 別スレッドの中の失敗・起動の失敗・答えずに終わったときも、本文を変えずに返す。
  - 別スレッドで読むファイルは、ビルドした成果物では `.js`、ソースのまま動かすとき（テスト）は `.ts`。
  - 同期の `withoutWorkspaceLinks` は、デーモンから呼ばれなくなったので消した（1回目のレビューへの対応）。テストは、変換の本体（`convertWorkspaceLinks(body, "/workspace").body`）を直接呼ぶ。
- `unlinkedGeneratedBody`・`unlinkedMergedBody` を、非同期にした。結果は、本文と、外せなかった理由（`skipped`。`timeout`・`error`）。秘密の値の伏せ直しと、長さの上限の扱いは、これまでと同じ。
- `apps/daemon/src/service.ts`：3か所の呼び出しを、待つ形にした。外せなかったときは、タスクの ID・リポジトリ・理由をログに出す（`linksUnlinked`）。本文の中身は出さない。`pullRequestBody` に、タスクの ID を渡すようにした。
- 仕様書（`docs/spec/approval.md`・`approval.en.md`）：「同期に行い、その間デーモンのほかの処理は待つ」の記述を、別スレッド・時間の上限・ログの記述に直した。コードの参照に、移したファイルを足した。

| `>` | 0.05 秒 | 0.09 秒 | 0.99 秒 | 3.70 秒 |
| `*a` | 0.22 秒 | 0.57 秒 | 2.22 秒 | 14.95 秒 |
| `*_` | 0.54 秒 | 2.08 秒 | 9.83 秒 | 53.97 秒 |
| `1. ` | 0.43 秒 | 1.58 秒 | 6.05 秒 | 26.91 秒 |
| `+ ` | 0.77 秒 | 2.83 秒 | 11.67 秒 | 56.17 秒 |

挙がっていた5つのほかの形（16,000 文字）：`*a_` 3.52 秒、`1) ` 1.62 秒、`> + ` 1.35 秒、`> 1. ` 0.94 秒、`**_` 0.91 秒、`[*` 0.78 秒、`a*` 0.74 秒。`* `・`_a`・`***`・`- [ ] ` は 0.03 秒以下。

受け入れ条件の目安（1 秒以下）に対して、どの形でも 5 ミリ秒未満。

テスト。

- 足したテスト（`apps/daemon/src/pr-body-links.test.ts` の「本文の解析の間も、デーモンがほかの処理に応える」）。
  - 5つの形の上限近くの本文で、打ち切って本文を変えずに返すこと。待つ間に、先に予約したコールバックが動くこと（時間は測らず、動いた順で確かめる）。
  - 打ち切った本文でも、sacty が組み立てた本文は秘密の値を伏せ直し、人の直しを含む本文はそのまま返すこと。
  - 時間の上限の中で終わる解析は、同期の変換と同じ結果になること。上限までリンクが並ぶ本文の結果が、これまでと同じこと。
  - 解析の失敗（深い入れ子）で、本文を変えずに返し、失敗と分かること。
  - 空の本文・作業領域へのリンクがありえない本文は、解析しないこと。同時に呼んでも、それぞれの結果を返すこと。
- 足したテスト（`apps/daemon/src/daemon-implement.test.ts`）：解析に失敗しても PR を作り、本文は変えず、ログに1行出ること。
- 修正を戻すと落ちることの確認：`convertOffThread` を、同期の変換を直接呼ぶ形に戻すと、足したテストのうち3件が落ちた（待つ間にコールバックが動かない・打ち切りにならない）。戻した後、通ることを確かめた。
- 既存のテストは、期待値を変えていない。`unlinkedGeneratedBody`・`unlinkedMergedBody` を呼ぶ5件は、待つ形（`await`）と、結果の形（`{ body }`）に合わせた。

コマンドと結果。

- `npm run lint`：問題なし。
- `npm run typecheck`：問題なし。
- `npx vitest run --no-file-parallelism`：261 ファイル、5,124 件が通った（1件はもともとのスキップ）。
- `npx vitest run tests/docs`：93 件が通った。

手で確かめたこと。

- ビルドした成果物（`apps/daemon/dist/pr-body-links.js`）を Node.js から直接呼び、上の「直した後」の表を測った。別スレッドのファイル（`pr-body-links-worker.js`）を読めている。
- デーモンの停止の最中：65,000 文字の `+ ` の解析を始めて 0.3 秒後に `process.exit(0)` を呼ぶと、すぐに終わった（全体で 0.5 秒。終了コード 0）。デーモンの停止は `process.exit` で終わるので、解析の途中の別スレッドは、停止を待たせない。
- メモリ：65,000 文字の5つの形を続けて解析したとき、プロセスのメモリ（RSS）は、始まりの 110MB ほどから、最大で 530MB ほど。直す前（同じ解析をデーモンのスレッドで最後まで行う）のメモリは、測っていない。

  結果は同じだった：ふつうの本文は 0.11 秒で外れ、65,000 文字の `*a`・`*_`・`1. `・`+ ` は 5.00 秒で打ち切り、`>` は 3.65 秒で失敗。デーモンのスレッドが止まった最大は 2.9 ミリ秒。

確かめられなかったこと。

- デスクトップ版の同梱（`npm run desktop:package`）を動かしての確認。同梱の手順（`apps/desktop/scripts/package.mjs`）を読み、`apps/daemon` を `src` を除いて写し、同梱した Node.js で動かすこと（asar に入るのは Electron の側だけ）を確かめた。代わりに、まっさらな複製で、ビルドの後に `apps/daemon/src` を消した状態でも動くことを確かめた。
- CI（Node.js 26.13.1）での、TypeScript のままの別スレッドの読み込み。手元は Node.js 24.22.1。PR の CI で確かめる。
- 実際のデーモンを動かして、PR を作るところまでの確認（動いているデーモンには触れていない）。

### 1回目のレビューへの対応で確かめたこと

計測（同じ開発機。ビルドした成果物）。

- 単独：65,000 文字の `>`・`*a`・`*_`・`1. `・`+ ` は、どれも 5.00 秒で打ち切り。デーモンのスレッドが止まった最大は 3.8 ミリ秒。ふつうの本文（上限までリンクが並ぶ）は 0.14 秒で外れた。
- メモリの上限とふつうの本文：長さの上限いっぱいの3種類（リンクの並び・見出しと表とコードと箇条書き・日本語の文とリンク）は、ヒープの上限が 40MB 以上なら外れた。32MB では、見出しと表の本文がメモリ不足（`ERR_WORKER_OUT_OF_MEMORY`）になった。128MB では、3種類とも外れた（0.11・0.23・0.14 秒）。
- 重なり（4件を同時に呼ぶ）：
  - 遅い本文4件：5.00・10.00・15.00・20.00 秒で順に打ち切り。プロセスのメモリ（RSS）は 110MB から最大 395MB。デーモンのスレッドが止まった最大は 2.4 ミリ秒。
  - ふつうの本文4件：0.13・0.27・0.39・0.49 秒で順に外れた。RSS は最大 224MB。
  - 遅い・ふつう・遅い・ふつう：5.00 秒（打ち切り）・5.11 秒（外した）・10.11 秒（打ち切り）・10.22 秒（外した）。
  - 上限を付ける前の同じ遅い本文（`+ `）4件では、RSS は 47MB から最大 1,462MB だった（別スレッドを直接4つ起動して測った）。
- デーモンの停止：遅い本文を4件重ねて（1件が解析中、3件が順番待ち）0.3 秒後に `process.exit(0)` を呼ぶと、全体で 0.49 秒で終わった（終了コード 0）。

修正を戻すと落ちることの確認。次の12通りを1つずつ戻し、足したテストが落ちることを確かめた（戻した後、通る）。

- 順番待ちをやめる（2件が落ちた）、長くなった答えを使う（1件）、答える前の終了を見ない（3件）、別スレッドのエラーを見ない（4件）、起動の例外を捕まえない（1件）、変換の例外の答えを使う（1件）、例外のメッセージをそのまま出す（2件）、時間の上限を短く数える（1件）、別スレッドを止めない（3件）、このスレッドで同期に変換する（3件）、ログに原因を添えない（2件）、ログを出さない（4件）。
- メモリの上限（`resourceLimits`）を外しても落ちるテストは、無い（メモリ不足を、時間に依存せずに起こす入力が無いため）。上の計測で確かめた。

コマンドと結果。

- `npm run lint`・`npm run typecheck`：問題なし。
- `npx vitest run --no-file-parallelism`：261 ファイル、5,134 件が通った（1件はもともとのスキップ）。
- origin/main の取り込み：進んでいなかった（取り込むものは無かった）。
- まっさらな複製：このブランチを clone し直し、`npm install`・core と daemon のビルドの後、`apps/daemon/src` を消して、同じ計測をした。結果は同じだった（遅い本文は 5.00 秒で打ち切り、ふつうの本文は 0.12 秒。遅い本文4件で RSS は最大 398MB。重ねた最中の `process.exit(0)` は 0.49 秒で終わった）。

## 残したこと

- 打ち切り・失敗を、作業履歴（タスクの記録）にも出すこと。ログだけにした（ADR）。
- 時間の上限（5 秒）・メモリの上限（128MB）・同時に動かす数（1）の値の見直し。持ち主の確認は、まだ。
- 遅い本文が重なったとき、後ろの本文の PR の作成・更新が、前の遅い本文の数 × 5 秒まで遅れること（ADR）。
- リンクを外す方針そのものの見直し（範囲の外）。
