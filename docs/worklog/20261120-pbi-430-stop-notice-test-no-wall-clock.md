# レビューが止まったときの知らせのテストの、実時間の上限の検査を、時間に頼らない検査に置き換える

- 日付: 2026-11-20（UTC）
- タスク: PBI-430
- PR: #475
- ブランチ: sacty/task-b08a6d6d
- 関係する ADR: なし

## 目的

機械が遅いと、振る舞いが正しくても落ちるテストを直す（main の CI で 1 件落ちた）。

## したこと

- `daemon-implement.test.ts` の「解消が期限を超えて知らせを待てなかったとき…」から、知らせ2の投稿の開始からの実時間に上限を置く検査と、そのための `at` を除いた。
- 代わりに、知らせ2の通信を止めた合図の理由が `AbortError`（解消が止めた）で、`TimeoutError`（知らせ自身の期限）でないことを確かめる。知らせ1は自分の期限で止まるので `TimeoutError` を確かめる。
- 本体（`service.ts`）は変えていない。

## 確かめたこと

- `npx biome check --error-on-warnings .`：通った。
- `npm run typecheck`：通った。
- `npx vitest run --no-file-parallelism`：通った。
- 本体の、解消が期限を超えたときに知らせの通信を止める処理（`service.ts` の `pending?.abort()`）を外すと、このテストが落ちる。落ちるのは、理由の検査より前にある `aborted` の検査（`expected false to be true`）である。理由の検査（`AbortError`）が捕まえるのは、知らせ2が解消の止める合図ではなく自分の期限で先に止まる場合である。確かめた後は元に戻した。
- 30 回の繰り返し：`npx vitest run --no-file-parallelism apps/daemon/src/daemon-implement.test.ts -t "解消が期限を超えて知らせを待てなかったとき"` を 30 回実行し、失敗は 0 件だった。
- CPU 負荷のもと：6 コアの機械で、CPU を使い切るプロセスを 5 つ動かしたまま、同じコマンドを 30 回実行し、失敗は 0 件だった。

## 残したこと

- 知らせ2が `AbortError` になるには、準備（知らせ1の投稿の開始から解消の開始まで）が `timeoutMs`（800ms）未満であることが前提になる。上の 30 回の繰り返しと CPU 負荷は、この余裕の範囲での結果である。
- `AbortSignal.timeout` をテストの中だけで差し替え、期限を手で切る案がある（`apps/web/src/app/actions.test.ts` などに前例）。この PR では採っていない。
- ほかのファイルの実時間に上限を置く検査は、範囲外なので直していない。
