# レビューが止まったときの知らせのテストの、実時間の上限の検査を、時間に頼らない検査に置き換える

- 日付: 2026-11-20（UTC）
- タスク: PBI-430
- PR: #475
- ブランチ: sacty/task-b08a6d6d
- 関係する ADR: なし

## 目的

機械が遅いと、振る舞いが正しくても落ちるテストを直す（main の CI で 1 件落ちた）。

## したこと

- `daemon-implement.test.ts` の「解消が期限を超えて知らせを待てなかったとき…」から、知らせ2の投稿の開始からの実時間に上限を置く検査と、そのための `at` を除いた。
- 代わりに、知らせ2の通信を止めた合図の理由が `AbortError`（解消が止めた）で、`TimeoutError`（知らせ自身の期限）でないことを確かめる。知らせ1は自分の期限で止まるので `TimeoutError` を確かめる。
- 本体（`service.ts`）は変えていない。

## 確かめたこと

- 整形・リンター・型検査・全テスト（`--no-file-parallelism`）：通った。
- 本体の、解消が期限を超えたときに知らせの通信を止める処理を外すと、このテストが落ちる。
- このテストだけを 30 回繰り返して通った。CPU を使い切るプロセスを並べた状態でも通った。

## レビューの指摘と対応

- 日付・ファイル名・PR・ブランチの欄を、決まりに合わせて直した。
- 「知らせ1を解消の開始後にテストから終わらせる」案は採らなかった。知らせ2の期限は知らせ1が終わった時点から数えるので、解消の期限が先に切れるには、解消の開始が知らせ1の投稿の開始から `timeoutMs` 未満である必要がある。知らせ1を手で終わらせても、知らせ1自身の期限（同じ `timeoutMs`）が先に来れば同じ条件になり、余裕は広がらない。

## 残したこと

- 知らせ2が `AbortError` になるには、準備（知らせ1の投稿の開始から解消の開始まで）が `timeoutMs`（800ms）未満であることが前提になる。この余裕の範囲で、30 回の繰り返しと CPU 負荷のもとで通った。

- ほかのファイルの実時間に上限を置く検査は、範囲外なので直していない。
