# PR の本文の、前の工程の成果物へのリンクを、ファイルを開けるリンクにする

- 日付: 2026-11-08（UTC）
- タスク: PBI-322
- PR: #<番号>
- ブランチ: feat/issue-322-step-artifact-links
- 関係する ADR: なし

## 目的

利用者から、sacty が作る PR の本文の、要求要件など前の工程の成果物へのリンクを押すと、GitHub の「compare changes」の画面に飛んで中身を読めない、という報告を受けた。
前の工程の成果物（`docs/sacty/<タスクの短い ID>/requirements.md` など）を、人がクリックして中身を読めるリンクにする。

## 見つけた経緯と原因

- 今の main で、実装の PR の本文の承認済みの要求要件の節は `- 要求要件：https://github.com/acme/app/pull/7（` に続けて成果のファイルのパスをインラインのコードにし、全角の閉じ括弧で閉じる形だった（`mergedStepPullRequests`）。古い版だけの振る舞いではなかった。
- GitHub の Markdown の描画（`gh api markdown -f mode=gfm`）で確かめると、自動リンクが URL の後の全角の括弧・パス・閉じ括弧まで URL に含め、リンク先が `/pull/7%EF%BC%88%60docs/…` になった。`/pull/<番号ではないもの>` は compare の画面になる。
- 要求要件・設計の PR の「承認済みの前の工程」（`earlierStepLines`）は、行末が PR の URL なのでリンクは壊れていなかったが、成果物のファイルへのリンクは無かった。

## したこと

- 前の工程の行を、両方の本文で同じ形にした（`stepArtifactLink`。`apps/daemon/src/prompts.ts`）：成果のファイルを `/blob/<コミット>/<パス>` への明示的なリンクにし、PR へのリンクも `[#<番号>](<URL>)` で残した（実装の PR の本文の「全文は、マージで承認した次の PR にあります」の意図どおり、承認した PR を辿れるように）。
- コミットは、マージされた内容（PR の先頭のコミット。人が直してマージしたならその最終のコミット）、記録が無ければ sacty が PR に出したコミット。PR の先頭のコミットは GitHub が PR の参照に残すので、ブランチが消えても読める。マージのコミットはタスクブランチの上にあり、タスクブランチが消えると辿れないことがあるので使わなかった。
- パスは区切りごとに符号にし（括弧も）、リンクの文字のインラインのコードは、バッククォートを含むパスでも崩れないようにした。PR の URL が読めない形なら、パスと `<URL>` の自動リンクにする。
- 仕様（日英。`docs/spec/approval.md`）に、リンクの形を足した。

## 確かめたこと

- `gh api markdown` で、新しい形の行が、成果物のファイルの `/blob/…` と PR の `/pull/7` の2つのリンクになることを確かめた（空白・括弧・バッククォートを含むパスも）。
- ブランチを消した既存の PR（sert-xx/sacty の #300）の先頭のコミットで、`gh api repos/sert-xx/sacty/contents/<パス>?ref=<コミット>` がファイルを返すことを確かめた。
- 回帰テストを `apps/daemon/src/pr-body-summary.test.ts` に足した。`prompts.ts` を main に戻すと 5 件落ちることを確かめた。
- `npm run lint`・`npm run typecheck`：通った。
- `npm test`：212 ファイルのうち 211 が通った。落ちた 1 件（`final-review-json-repair.test.ts` の時間が出力の長さに比例するかのテスト）は、全件の並列の負荷の下での時間の測り方によるもので、単独で流すと 41 件すべて通った（このタスクの変更とは関係しない）。
