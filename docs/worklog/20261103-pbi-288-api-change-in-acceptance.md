# 受け入れ条件が明示した API の変更では、「公開 API の形を変える」を要求要件を残す理由にしない（S5 r2）

- 日付: 2026-11-03（UTC）
- タスク: PBI-288
- PR: #289
- ブランチ: feat/issue-288-pbi-288
- 関係する ADR: [受け入れ条件が明示した API の変更では、「公開 API の形を変える」を要求要件を残す理由にしない](../adr/20261103-0530-api-change-in-acceptance-keeps-no-requirements.md)（[PBI-283 の ADR](../adr/20261102-2357-superseded-skip-requirements-for-detailed-acceptance.md)の一部を置き換えた）

## 目的

S5 の再実験（r2）で、PBI-283（#285）の後も要求要件が残り、$33.47 かかった（出てきた要求要件は「確認したいこと：なし」）。
残した理由は2つで、(1) 公開 API の形を変える（POST /api/orders に必須の項目を足す。ただし受け入れ条件にはっきり書かれていた）、(2) 異常系のテストの中身・空の入力・列の位置のような細かい既定が残る（#285 が省いてよいとしたもの）。
(1)(2) を要求要件を残す理由にしないようにする。受け入れ条件に書かれていない変更や、使う側との食い違いを人に確かめる必要があるときは、今までどおり残す。

## したこと

- オーケストレーターの指示（`apps/daemon/src/prompts.ts` の `DETAILED_ACCEPTANCE_LINE`）：
  - 例外「外に公開している API・項目の名前や形を変える」を、「受け入れ条件に書かれていない変更が要る・使う側との食い違いを人に確かめたい」に狭めた。
  - 受け入れ条件が変更後の名前・形・必須かどうか・エラーのときの扱いをはっきり書き、使う側との食い違いも確かめることが無いときに限り、公開 API・項目の変更を残す理由にしない。改名のように使う側がどうなるかが決まらない変更は、はっきり書いたことにならない。集めた情報に、使う側が変更で動かなくなりうるとあり、その扱いが決まっていないときは残す。
  - 細かい既定が残ることを、残す理由にしない（#285 の決めを、理由として使われないように書き足した）。
  - ほかの例外（曖昧・食い違い・人に確かめたい判断・書き忘れや衝突・共有の状態への新しい意味）と、設計の判断が要るときの `standard` は変えない。共有の状態への新しい意味は、依頼が既存のフラグを使うよう指定していても当たることを書き足した（下の S13a の揺れへの対処）。
- 仕様書（`docs/spec/tasks-and-steps.md`・英語の版）、ユーザードキュメント（`docs/user/tasks.md`・英語の版）、ADR（PBI-283 の ADR の一部を置き換え）を直した。PBI-283 の作業履歴は、ADR のファイル名の変更に合わせてリンクだけ直した。

## 確かめたこと

- `apps/daemon/src/prompts.test.ts`：PBI-283 の「残す指示」のテストの期待を新しい文言に直し、新しい指示のテストを1件足した。`prompts.ts` を戻すと、この2件が落ちる（`git stash` で確認）。
- 実際の AI に、実験の依頼を当てて、選ぶ組み合わせを比べた（PBI-283 と同じ形。`buildOrchestratorPrompt` の指示を、変更前の `origin/main` と変更後で作り、リポジトリが見えない旨の注意を足して、`claude -p`（claude-opus-4-5、道具なし）に答えの JSON だけを出させた。使い捨ての道具で、コミットしていない）。
  - S5 の依頼の原文（題・依頼・受け入れ条件）に、集めた情報の例を足した3通りも流した。S5h は S5 r2 の理由を再現するため、集めた情報に「POST /api/orders は README に載る公開 API で、必須の項目を足すと既存の呼び出し側が 422 になる」と細かい未確定のこと（異常系のテストの受け持ち・空入力の形・列の位置など）を書いた。S5x は、さらに「別のリポジトリのアプリが、項目を送らない現行の版を配布済みで、必須にすると注文できなくなる。扱いは受け入れ条件に無い」を足した（人に確かめることがある例）。集めた情報は評価のために作った例で、実際の情報収集の出力ではない。

  | 依頼 | 期待 | 変更前（`origin/main`） | 変更後 |
  | --- | --- | --- | --- |
  | S5（依頼の原文だけ） | 省く | direct 4/4 | direct 4/4 |
  | S5g（集めた情報の例） | 省く | direct 3/4 | direct 3/4 |
  | S5h（S5 r2 の理由を再現） | 省く | direct 1/8（standard 7） | direct 4/8（standard 4） |
  | S5x（使う側が壊れうる） | 残す | 残す 8/8 | 残す 8/8 |
  | S8（曖昧） | 残す | 残す 4/4 | 残す 4/4 |
  | S9（食い違いは集めた情報にしかない） | 残す | 残す 4/4 | 残す 4/4 |
  | S9（食い違いを集めた情報で足した例） | 残す | 残す 4/4 | 残す 4/4 |
  | S10（改名） | 残す | 残す 4/4 | 残す 4/4 |
  | S10（連携先を集めた情報で足した例） | 残す | 残す 4/4 | 残す 4/4 |
  | S13a（共有のフラグへの新しい意味） | 残す | direct 4/8（skip-design 2・standard 2） | direct 1/8（skip-design 4・standard 3） |

- 途中の文面では、S10 が direct 2/4、S13a が direct 7/8 になった（受け入れ条件が詳しい改名や、既存のフラグを使うよう指定された依頼を、省く側に倒した）。改名は「使う側がどうなるか決まらない変更ははっきり書いたことにならない」、S13a は「指定されたフラグに別の意味を載せるなら当たる」を足して戻した。
- 1 回の測定で AI の判定は揺れる。S13a は変更前でも direct が 8 回中 4 回で、変更後の 1/8 は目安。

## 残した制限

- S5h の direct は 4/8 で、S5 r2 のように残す判断はまだ半分ある。S5 の原文だけ（集めた情報なし）では、変更前も省いていた。
- 評価は、リポジトリが見えない入力と、作った集めた情報での選択で、実際の通しの実行ではない。実際の S5 の再実験（r3）で確かめるまでは、割合は目安。
- 使う側との食い違いは、オーケストレーターが集めた情報から見える範囲でしか判断できない。受け入れ条件が API の変更を書いていて、使う側が見えないときは、省かれる。
- S13a のように、並行するタスクの衝突は依頼の性質（共有の状態への新しい意味）でしか見分けられない。PBI-283 の制限と同じ。
