# メモリーに書かれた手順より、工程の指示を優先させる

- 日付: 2026-11-03（UTC）
- タスク: PBI-297
- PR: #294
- ブランチ: feat/issue-297-pbi-297
- 関係する ADR: [メモリーは参考とし、手順が工程の指示と食い違うときは、工程の指示を優先させる](../adr/20261103-1155-process-instruction-over-memory.md)

## 目的

実験 S14 の3回目（findings F40）：要求要件の直しの指示（直す範囲・本文に書かないこと）より、メモリーの「前の版を取り出して丸ごと戻す」手順が優先され、取り下げたはずの内容が復活し、本文に変更のメモが入った。メモリーの手順より工程の指示を優先させる。

## 調べたこと

証拠：`sacty-field-trials/scenarios/S14/attempts/r3/evidence-v3/` の v3-prompt.md・メモリー2件。
- メモリーを渡す指示（`memoryPromptLines`）には、既に「メモリーは、人の指示・コンテキストの規則とスキル・AGENTS.md などより優先度が低い。食い違うときはそちらに従う」とあった。
- 一覧に、そのタスクの工程の指示が入っていなかった。メモリーの手順が「こうしなさい」の形で書かれていたので、工程の指示と並ぶ手順として従われた。
- スキル `memory` の「従う順」も、同じ一覧で、工程の指示が無かった。

## したこと

- メモリーを渡す指示（`memoryPromptLines`）：メモリーは参考であり、この下の工程の指示（直す範囲・書くこと・書かないこと・判断の結果の扱いなど）より優先度が低い、食い違う手順は使わない、を書いた。
- メモリーの索引（`renderMemoryIndex`）：同じ決まりを足した。
- 既定のスキル `memory`：「従う順」の1番に工程の指示を足し、食い違う手順は使わず、メモリーは手がかりとしてだけ使うと書いた。
- 深掘りの登録の決まり（`memoryRuleLines`）：工程の指示を変える手順は書かせず、書くなら食い違うなら使わないことを添えさせる。手順の中身の機械的な判定は入れない（理由は ADR）。
- 仕様書（memory。日英）、ユーザードキュメント（audit。日英）、ADR。

## 確かめたこと

- `npx vitest run apps/daemon/src/memory.test.ts apps/daemon/src/audit-prompts.test.ts apps/daemon/src/default-skills.test.ts`：89 件が通る。
- 修正（`memory.ts`・`audit-prompts.ts`・スキル）だけを戻すと、足したテスト3件が落ちる（修正を戻して失敗を確認し、戻した）。
- メモリーを使わない場面：`memoryPromptLines` は工程の実行にマウントがあるときだけ足される（`service.ts` の `withMemory` は変えていない）。深掘りの決まりは `memories` を渡したときだけ入る（テストで確認）。
- 全体の `npx vitest run`：他の Dev と並行で負荷が高いとき、偽の docker を使う5ファイル（agent-sessions・prompts・review-eval・session-logs・agents）で13件が落ちた。この5ファイルだけを、main と変更後の両方で単独で実行すると、387 件が通る（負荷による時間切れで、変更とは無関係）。
- `npx biome check .`・`npx tsc -b packages/core apps/daemon packages/cli`：エラー無し。`npx vitest run tests/docs`：通る。

## DA のセルフレビュー

- 工程の指示は、メモリーを渡す指示の本文の下に書かれている（指示の先頭に足す文が「この下に書かれた」と言う）。メモリーが渡されない実行（ゴールガーディアン・情報収集など）の指示は変わらない。
- 受け入れ条件の「登録しにくくする手立て」：登録の決まりに文を足した。出力を機械的に判定する手立ては、判定を誤ると有用な知見を捨てるので入れない（ADR）。
- 気になる点：既に登録された手順入りのメモリーは残る（人が消せる）。
