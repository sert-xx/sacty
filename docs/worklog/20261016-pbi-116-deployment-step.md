# マージの後の監視を工程にし、するかどうかを対象のリポジトリのスキルの有無で決め、どこまで見るかはスキルに任せる

- 日付: 2026-10-16（UTC）
- タスク: PBI-116
- PR: （PR を作った後に書き足す）
- ブランチ: feat/issue-116-deployment-step
- 関係する ADR: [マージの後の監視を工程にし、するかどうかを対象のリポジトリのスキルの有無でタスクごとに決め、どこまで見るかはスキルに任せる](../adr/20261016-0633-deployment-watch-step.md)

## 目的

マージの後の監視（CI/CD を待つ → デプロイの確認 → 失敗したら修正のタスク）を、プロジェクトの設定 `deploymentWatch` の On・Off で
裏で動かすのをやめ、実装の後の工程にする。するかどうかは、対象のリポジトリにスキル `deployment-observer` があるかで決める。
作業の途中で、どこまで見るかをスキルに任せること（2b）と、Sacty セットアップで作るスキルを合わせること（2c）が受け入れ条件に足された。
まだ本番で使っていないので互換の層は作らない。作業履歴は書き換えない。

## したこと

- core
  - `StepKey` に `deployment` を足し、`STEP_PLANS` の `standard`・`skip-design`・`bugfix` の最後に置いた。
  - `StepsChosen` に `deployment`（`skill` か `skipped`）を足した。投影は、飛ばすなら工程を `skip` にし、工程を進めるとき `skip` に
    進まない（`advance`）・戻しても `skip` のまま（`reopen`）にした。実装の PR をマージせずに実装を承認したら、監視の工程を `skip` にする。
  - 監視の記録（`Deployment*`）の後に、監視が終わって修正のタスクを決めた後なら工程を終える（`settleDeploymentStep`）。
    `DeploymentWatchStarted` は、工程があるタスクでは監視の工程が active のときだけ受け付ける。工程の無い以前のタスクは、これまでどおり
    完了したタスクで受け付ける。
  - `DeploymentChecked` に `ci`・`deployment`（それぞれの結果・要点・理由）と `retry`（止めた確認を結果にせず確かめ直す）を足した。
  - `stepRunning` で、確認の実行中を工程の実行中にした。
  - `ProjectDefinition` から `deploymentWatch` を外した。エクスポートの読み込みは、以前のファイルにあっても捨てる。
  - 文言：`deploy.noSkill`・`deploy.skillLookupFailed`・`deploy.stepSkipped` を足し、`deploy.undetermined` を範囲によらない文にした。
- daemon
  - 工程を選んだ後、`StepsChosen` の前に起点のコミットでスキルを探し、するか・飛ばすかを決める（`deploymentChoice`）。飛ばすなら、
    この工程の既定のイメージの理由・理由が無いことは記録しない（`withDeploymentChoice`）。
  - 監視の開始を、プロジェクトの設定ではなく、監視の工程が `todo` かで決める。一時停止中のタスクは CI/CD を見ない。
  - 確認：工程のイメージ（工程の無い以前のタスクは実装のイメージ）で実行する。指示に、sacty が見た CI/CD の実行・チェックをデータとして
    渡し、範囲と確かめ方はスキルに従う・長く待たない・飛ばしたものは `skipped` と理由・指示の答えの形を優先することを書いた。答えは
    `ci`・`deployment` の両方を読み、全体の結果を sacty が決める（`overallDeploymentResult`）。人が止めた確認は `retry` を記録する。
  - 再起動：確認の実行中に止まったら、工程なら `retry` と `TaskPaused`（`error`）。以前のタスクはこれまでどおり。
  - 中止：マージした実装の PR は閉じない。
  - 二重の登録の判定から、監視しているタスク自身を除いた（工程になって、監視の間は「終わっていない修正のタスク」に見えるため）。
  - オーケストレーターへの組み合わせの説明・イメージの指示・前段の調査の「このあと」の工程（飛ばした工程を除く）・実装の PR の本文
    （監視の工程があれば、それを終えて完了すると書く）を直した。
  - 通知の工程の名前に `deployment` を足した。
  - Sacty セットアップのゴール：CI/CD のあるリポジトリでは、デプロイしていなくてもスキルを作り、CI/CD の確認の仕方の reference
    （`references/ci.md`。`CI_REFERENCE`）を作り、デプロイしていなければデプロイの確認を飛ばすと書かせる。答えの形を新しい形にした。
- web
  - 工程の名前（マージの後の監視・After-merge watch）、状態の表示（マージの後の監視中（CI/CD を待っている／スキルで確かめている））、
    監視のカード（始める前・飛ばした理由・CI/CD の確認とデプロイの確認それぞれの結果）、作業履歴の文（工程を決めた記録の監視の
    決定・止めた確認）、費用の表（監視の工程の行。実行中も出す）を直した。
  - プロジェクトの設定から「マージの後の監視」のチェックを消した。
- docs：仕様書（deployment-watch・tasks-and-steps・approval・configuration・daemon-lifecycle・event-log・export・README）、利用者向けの
  文書（deployment-watch・project-settings・tasks・config・README）を日英で直した。前の ADR を置き換え、新しい ADR を足した。

## 自分で決めたこと

- 工程の名前は「マージの後の監視」・After-merge watch（画面・作業履歴・通知で使っていた名前にそろえた）。キーは `deployment`
  （`step_agents.deployment` と費用の表の行がそのまま使える）。
- 決めるのは、組み合わせを選ぶ AI ではなく sacty（スキルの有無はファイルで決まるため）。起点のコミットで探す。
- 決めた後にスキルが増えたら、そのタスクでは見ない（工程の並びを途中で変えない）。消えたら、CI/CD を見て、確認は飛ばして通ったにする。
- 待つ・時間の上限・CI/CD の失敗の判定・ログを伏せることは sacty に残し、CI/CD が通った後にスキルに従ってエージェントに確かめさせる
  （エージェントには待たせない）。sacty の判定で CI/CD が失敗したら、エージェントを使わずに修正のタスクを登録する。
- 確認の実行の失敗・答えを読めない・判断できないときは、今どおり確かめられなかったとして飛ばす（タスクは止めない）。予算の上限も今どおり
  飛ばす。人が止めた・デーモンが止まったときだけ、ほかの工程と同じく確かめ直す。
- 以前の形の答え（`result` だけ）は読まない。

## レビューの指摘と対応

- セルフレビュー（DA）
  - 実装の承認待ちの案内・実装の PR の本文が「マージするとタスクが完了」のままだった → 監視の工程があれば、それを終えて完了すると直した。
  - 監視のカードの見出し「デプロイの確認」が、CI/CD の確認だけのスキルでは合わない → 「スキルに従った確認」にした。
  - スキルに別の答えの形が書いてあると、指示の形と食い違う → 指示の形を優先すると書き、テストを足した。
  - エージェントの実行に時間の上限があるか → 既存の上限（30分）で止まり、実行の失敗になることを仕様書に書いた。
