## 目的

承認待ちだったセキュリティチェックのレポート6件（2026-11-06〜11-11 の定期実行）の指摘を、今の main で確かめ、コードで直せるものを直す。

## レポートの指摘と扱い

| 指摘 | 件数 | 扱い |
| --- | --- | --- |
| ゲートウェイがクエリの `_method` を上流へ送る（読み取りだけの実行・許可リストを、上流のメソッドの上書きで越えうる） | 4 | 直した |
| `user@host:path` の形の継承先を、デーモンのカレントディレクトリの同じ名前のエントリから読みうる | 3 | 直した（修正を戻すと、ローカルから取得することをテストで再現した） |
| 非公開の脆弱性の報告（GitHub の private vulnerability reporting）が無効なのに、`SECURITY.md` が第一の窓口として案内している | 3 | 直していない（リポジトリの設定の変更か `SECURITY.md` の変更かは、利用者の判断待ち） |
| CI のワークフロー・Dependabot の設定が無く、main のルールセットの承認数が 0 | 2 | 直していない（PBI-306 から利用者の判断待ち） |
| 依存の `cn@0.4.0` の正当性が確かめられていない | 1 | 直す必要が無いと判断した（下の「確かめたこと」） |

## したこと

- `apps/daemon/src/gateway.ts`：組織内 PF への中継で、クエリにメソッドを上書きする名前（`_method`・`x-http-method-override`・`x-http-method`・`x-method-override`）があれば、上流に送らずに 400 にした（`overridesMethodInQuery`）。
  名前はデコードしてから、大文字と小文字・`-`・`_`・`.`・空白・末尾の `[]` をそろえて比べる（PHP は名前の `.`・空白を `_` に変える）。`;` も区切りとして読む。
  取り除いて送る形にしなかったのは、許可を判定したクエリと送るクエリを同じに保つため（`sentUrl` と同じ考え）。
- `apps/daemon/src/context.ts`：最初の `:` より前に `/` が無い指定（git が scp の形として読むもの）は、空の一時ディレクトリをカレントディレクトリにして `git clone` するようにした。
  `git clone` は、そのような指定と同じ名前のディレクトリがカレントディレクトリにあると、ネットワークの先ではなくそこから読む。
- 仕様書（`docs/spec/gateway.md`・`docs/spec/context.md` と英語の版）に、今の振る舞いを書いた。

## 確かめたこと

- 足したテストは、修正を戻すと失敗する（`?_method=DELETE` が 200 で上流に届く／カレントディレクトリの同じ名前のリポジトリから取得できてしまう）。
- `cn@0.4.0`：npm の登録者は shadcn、SLSA の provenance は `github.com/shadcn-ui/cn` の `release.yml`（main）でビルドされたもの。`npm audit signatures` で、署名と attestation が検証できた。
- Node.js 26.12.1（`mise exec`）で `npm run lint`・`npm run typecheck`・`npx vitest run`。

## セルフレビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| `;` を区切りに使う上流では、`?a=1;_method=DELETE` が通る | `;` も区切りとして読み、テストを足した |

## 残したこと

- 非公開の脆弱性の報告の窓口と、CI・ルールセットの承認数（利用者の判断待ち）。
- フォームの本文の `_method` による上書き（書き込みのメソッドで許可されたパスに、本文で別のメソッドを指定する場合）。レポートの指摘の範囲外。
- ゲートウェイの読み取りだけの実行で、上流がほかの仕組みでメソッドを上書きする場合は、上流ごとに確かめていない。
