# AI の呼び出しをホストのゲートウェイ経由にし、レート制限（429）をリトライする

- 日付: 2026-10-12（UTC）
- タスク: PBI-37
- PR: #39
- ブランチ: feat/issue-37-ai-gateway
- 関係する ADR: [AI の呼び出しをホストの sacty のゲートウェイ経由にでき、ゲートウェイが API キーを持ってレート制限（429）などをリトライする](../adr/20261012-1025-host-ai-gateway-retry.md)

## 目的

利用者の環境の Bedrock のレート制限で 429 が返るとエージェントが止まるので、ホストで sacty のゲートウェイを動かし、Codex の向き先を
そこにして、429 のリトライをゲートウェイに任せる。受け入れ条件の要点：エージェントごとにゲートウェイ経由にでき API キーはコンテナに
渡さない、429 と 5xx の一時的な失敗を Retry-After（無ければ指数的な間隔）でリトライする、上限を config.yaml で変えられ上限で
エージェントにエラーを返す、上限で失敗したらレート制限で止まったとわかる理由で一時停止する、待っている間も一時停止・中止で止められる、
リトライを作業履歴に残す、エージェントのコンテナからだけ使える。

## したこと

- `apps/daemon/src/gateway.ts`（新規）：ゲートウェイ。トークンの差し替え・リトライ・ストリーミング・接続が切れたときの扱い。
- `apps/daemon/src/main.ts`：起動時にゲートウェイを動かす。`apps/daemon/src/agents/docker.ts`：`--add-host host.docker.internal:host-gateway`。
- `apps/daemon/src/agents/invocation.ts`：`via_gateway` のとき、向き先（`base_url`）をゲートウェイにし、実行ごとのトークンを渡す。
- `apps/daemon/src/config.ts`：エージェントの `via_gateway`、`gateway.retry`（`max_attempts`・`max_wait_sec`）。
- 作業履歴に `AiRequestsRetried` を足した（`packages/core/src/events.ts` など）。`README.md` に例を足した。
- 「利用上限で一時停止」の説明を、API のレート制限にも当てはまる文にした（`apps/web/src/i18n/messages/labels.ts`）。
- レビューの指摘で、本文の受信の途中で接続が切れても、デーモン全体を終わらせないようにした。

## 確かめたこと

- `npm test`（362 件）・`npm run lint`・`npm run typecheck` が通った。
- ゲートウェイのテスト：キーの差し替え・知らないトークンとパスの拒否・Retry-After と倍の間隔・5xx と接続の失敗・リトライしない失敗・
  回数の上限・一続きの失敗の上限と数え直し・あきらめた後のやり直し・ストリーミング・接続が切れたら待たない。
- 429 をリトライする・Retry-After に従う・成功で数え直す・あきらめた後は待たない・キーの差し替え・接続が切れたらやめる・作業履歴への記録・
  コンテナに API キーを渡さない、の修正を1つずつ戻すとテストが失敗することを確かめた。
- 実際の Codex（イメージの 0.160.0）をコンテナで動かし、ホストの偽の Bedrock（2回 429 → 401）につないだ。ゲートウェイが Retry-After に従って
  2回リトライし、上流には本物のキー、コンテナにはトークンだけが渡ることを確かめた。
- レビューでは、全 362 件（25 ファイル）・lint・typecheck の成功と、独立した Node のプロセスでの切断の再現が終わらずに終了コード 0 になることを
  確かめた。実際の Bedrock・実際の Codex のコンテナでの疎通は、レビューでは確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 本文の受信の途中で接続が切れると、`readBody` の reject が処理されず（`handle` の Promise を捨てている）、未処理の ECONNRESET でデーモン全体が終わる。ほかの並行のタスクや管理の API まで止まる | 本文の受信の失敗は、そのリクエストだけの終わりとして扱い、上流には送らないようにした。`handle` の失敗は必ず受け止め（応答を返す前なら 502、返し始めていれば接続を閉じる）、リクエスト・応答の `error` のイベントにも受け手を付けた。`Content-Length: 10000` で1文字だけ送って切断し、上流に送らず、続くリクエストが 200 になる回帰テストを足し、修正を戻すと `Unhandled Rejection` で失敗することを確かめた。指摘と同じ独立したプロセスでの再現でも、プロセスは終わらなかった |

## 残したこと

- 実際の環境での確認（Codex × Bedrock のエージェントに `via_gateway: true` を足してタスクを動かし、429 が返った実行に作業履歴のリトライの記録が
  出ること）は、利用者の環境で行う。
