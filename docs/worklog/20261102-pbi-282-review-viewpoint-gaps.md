# セルフレビュー・最終レビューの観点の取りこぼし（S18・S12）を直し、指示の変更を実在の例で確かめる方法を残す

- 日付: 2026-11-02（UTC）
- タスク: PBI-282
- PR: #280
- ブランチ: feat/issue-282-review-viewpoints
- 関係する ADR: [セルフレビューはリポジトリの決まりから導いた条件を消さず、最終レビューは既存の振る舞いの変化を範囲外として申告する](../adr/20261102-0840-review-viewpoint-gaps-s12-s18.md)

## 目的

実験で見つかったレビューの取りこぼし 2 件を直す。

- S18：要求要件の 1 回目の下書きにあった、版・CHANGELOG・生成物の条件（R-2）を、セルフレビューの観点 D-10 が「README の変更の決まりの書き直し」として消し、依頼者の差し戻し（約 $14）が要った。リポジトリの決まりから導いた条件は消さない。
- S12：作成の検査を共通の関数に分けた結果、「開始が過去」かつ「会議室が利用停止」の入力で 422 のメッセージが変わった。設計に書かれず、既存のテストも通り、最終レビューも指摘しなかった。既存の振る舞いが承認済みの要求要件・設計に無い形で変わっていないかを、最終レビューが確かめる。
- 指示の変更を、実験の入力に近い例に実際の AI を当てて確かめる方法を残す。

## したこと

- 観点 D-10（簡潔さ・範囲）
  - 観点カタログ（`review-dispatch/references/viewpoints.md`）の D-10 の「見ないもの」に、リポジトリの決まり（README・CONTRIBUTING・AGENTS.md・変更履歴の方針・PR テンプレート・CI の設定など）がこの種の変更に求める条件とその確かめ方を足した。親が担当への依頼文にそのまま写す欄なので、担当に直接届く。
  - 観点の資料（`review-execution/references/D-10.md`）に、節「リポジトリの決まりから導かれる条件は消す指摘にしない」、手順 3 への 1 項目、逆向きの NG 例（例 9。指摘にしない例）、見落としやすい所を足した。決まりは変更する人が守って成り立つので「既存の仕組みが保証する振る舞い」ではないこと、結果で書いた確かめ方は「実装方法に踏み込む」ことにならないこと、条件の中身が誤っていれば消さずに直す指摘にすることを書いた。D-10 の本来の役割（例 1〜8）は変えていない。
- 自己レビューの流れ（`review-dispatch/references/self-review.md`）と、要求要件・設計の指示（`prompts.ts` の `selfReviewLines`）に、D-10 の指摘に従うときも、決まりから導いた条件は消さず、消すなら決まりから導かれないと確かめた理由を総評（報告の `summary`）に書くことを足した。実装の指示には入れていない。
- 要求要件・設計を書く指示（`readerLoadLines` の「書かない」）の「既存の仕組みが保証して変わらない振る舞い」に、決まりが求める条件は当たらず、書くことを添えた。
- 最終レビューの指示（`prompts.ts` の `outOfScopeLines`）に、既存の振る舞い（エラーの種類・状態コード・メッセージ、検査の順番、応答の形・項目、既定値）が承認済みの要求要件・設計に無い形で変わっていないかを、変更した関数ごとに確かめる項目を足した。共通化・分割・移動のリファクタリングも例外にしない。変更前の側と実装後のコードを読み比べ、検査が複数ある関数は異常が同時に当たる入力で先に働く検査と返すエラーを追わせる。既存のテストが通っていても同じとし、求められていない変化は `outOfScope` に「どの入力で、変更前は何を返し、変更後は何を返すか」を書かせる（観点 `SCOPE` の不合格になる既存の仕組みに乗せた）。「振る舞いを変えない整形・リファクタリングは範囲外としない」の行に、「変えていないことは次の項目で確かめる」を添えた。
- 実例で確かめる道具（`apps/daemon/src/testing/review-eval/`、`apps/daemon/src/review-eval.test.ts`）
  - 例 s18：実験の要求要件の 1 回目の下書き（R-2 の "query" の記述だけ、リポジトリの動作と合わせて外した）、担当に渡った根拠（集めた情報・要求要件の書き方）、README・CHANGELOG・API の定義・生成スクリプトを縮めたリポジトリ。
  - 例 s12：作成の検査の変更前後のコード（実験の PR #4 の形を縮めた）、承認済みの要求要件・設計（縮めたもの）、実際の `buildFinalReviewPrompt` の指示。対照として、同じ共通化で検査の順番を保った版も置いた。
  - 常に走る確認：例が問題の形になっていること（s12 は、異常が 1 つだけの入力は変更前後で同じ結果で、「開始が過去かつ利用停止」の入力でだけメッセージが変わる。対照は全組み合わせで変更前と同じ）、指示の文言（観点カタログ・D-10・自己レビュー・要求要件/設計/最終レビューの指示）、判定の読み取り。
  - `SACTY_REVIEW_EVAL=1` のときだけ走る確認：実際の AI（`claude -p`。モデルは `SACTY_REVIEW_EVAL_MODEL`、コマンドは `SACTY_REVIEW_EVAL_AGENT`）に例を渡し、`SACTY_REVIEW_EVAL_RUNS` 回流す。
    - s18：D-10 が R-2 を消す・縮める指摘を出さず、ほかの書きすぎは指摘すること。
    - s12：最終レビューが検査の順番の変化を範囲外として申告すること。対照は申告しないこと。
  - 手順は CONTRIBUTING.md に、人が手で指示を変えるときに任意で使う手動の測定手順として書いた（必須にはしていない。工程の指示 `prompts.ts` の「エージェントを起動して確かめるテストを書かない」との衝突を避けるため。PR #280 のレビュー指摘）。
- 仕様書（`docs/spec/context.md`・`tasks-and-steps.md`、英語の版）、ユーザードキュメント（`docs/user/tasks.md`、英語の版）、ADR を直した。

## 確かめたこと

### 実際の AI に当てた結果（Claude Code の `claude -p`、モデル claude-opus-5-5）

指示を変える前（`origin/main` の観点カタログ・観点の資料。`SACTY_REVIEW_EVAL_SKILLS_DIR` に `git archive` で取り出した版を指定）と後で、同じ例を流した。

| 例 | 変更前 | 変更後 |
| --- | --- | --- |
| s18：D-10 が R-2 を消す・縮める指摘を出した回数 | 6 回中 5 回（should 3・nit 2。should は「R-2 と確かめ方の R-2 の行を消し、ID を詰める」など） | 6 回中 0 回。毎回、空文字の既定の重複・R-5 の並びの書き直しなど、ほかの書きすぎは指摘した（D-10 は黙っていない） |
| s12：最終レビューが検査の順番の変化を範囲外として申告した回数 | 5 回中 0 回（毎回 `outOfScope` は空。順番の変化に気づいて文章に書いた回があっても、不合格にしなかった） | 5 回中 5 回（「開始が過去かつ会議室が利用停止なら、変更前は "Reservations must start in the future"、変更後は "Room ... is not available for booking"」の形で申告） |
| s12（対照）：順番を保った共通化を申告した回数 | （未測定） | 4 回中 0 回 |

- s18 は、最初に作った例（R-2 の記述を外し、依頼に無い要求 R-7 を足したもの）では、変更前でも 18 回中 0 回しか再現しなかった。実験の担当の入力（集めた情報の「決まりから要る」という記述、依頼者の書き方の指示）を足し、R-7 を外した今の例で、実験の下書きに近づけて再現した。
- s12 は、最初の例が設計に「作成の既存の検査が変わらないこと」というテスト観点を含めていて、指摘を誘っていた。外した例で測り直した結果が上の表（誘う例でも、変更前は 3 回中 0 回だった）。
- 結果は揺れる。表の回数は 1 回の測定で、指示の効果の大きさの目安である（再現しない回もありうる）。
- ログは、`SACTY_REVIEW_EVAL_LOG` に追記される。
- 最初の変更前の測定（6 回中 4 回）は、変更前のスキルを指定しても依頼文の観点の行だけが現行のカタログから入る不具合があった（PR #280 のレビューで指摘）。直した後に、変更前の版だけで測り直した値が上の表である。
- 実行の失敗（起動できない・異常終了）、判定の JSON として読めない出力（観点・status・指摘の形、最終レビューは期待する観点がすべて揃うこと・verified・summary まで確かめる）、`SACTY_REVIEW_EVAL_RUNS` が安全な正の整数でないことは、評価せず失敗させる。観点担当の status は passed・changes_required だけを受け付け（failed は評価しない）、最終レビューは sacty 本体が判定として採る最後の見出しのブロック（`findBlock`。囲み方は問わない）を検証する。判定を確かめる関数は環境変数を既定で読まず、環境変数を指定した実行でも固定のテストが通る。`SACTY_REVIEW_EVAL` は `1` のときだけ有効。

### 固定のテスト

- `npx vitest run apps/daemon/src/review-eval.test.ts`：14 件が通り、AI を呼ぶ 3 件はスキップ。
- 指示を変更前に戻すと失敗することを確かめた（`prompts.ts` と D-10.md・self-review.md・viewpoints.md を `HEAD` に戻して実行。指示の文言の 3 件が失敗し、戻すと通った）。
- `npx biome check`・`npm run typecheck`・`npx vitest run tests/docs`・`npx vitest run apps/daemon/src/prompts.test.ts apps/daemon/src/default-skills.test.ts apps/daemon/src/final-review-out-of-scope.test.ts`（結果は PR に書く）。

## 残したこと

- 最終レビューの比較は、AI が読み比べて追う指示で、機械的な検査ではない。検査が多い関数・複雑な共通化では見落としうる。指示が過剰に働いて、求められた変化を範囲外にする誤判定は、対照 1 件でしか測っていない。誤って範囲外とされたときは、これまでどおり 3 回の不合格で一時停止し、「レビューへ進める」で進められる。
- コードの観点 C-6（互換性・影響範囲）には足していない。実装のセルフレビューで共通化の前後の振る舞いを比べる観点は、必要なら別の PBI にする。
- 例は 2 件だけである。ほかの取りこぼし（F18 など）は足していない。
