# 既定のレビューに、既存の実装との調和を見る観点 C-18 を足す

- 日付: 2026-11-19（UTC）
- タスク: PBI-405
- PR: #449
- ブランチ: feat/issue-405-review-harmony-with-existing-code
- 関係する ADR: [既定のレビューに、既存の実装との調和を見る観点 C-18 を足す](../adr/20261119-1605-review-viewpoint-for-harmony-with-existing-code.md)

## 目的

既存のコードベースに変更を足す PR のレビューで、文書に書かれていないが、リポジトリを読み解けば分かる決まり（命名の方針・技術の使い方の方針・業務のロジックの置き場所の意図）への準拠を見られるようにする。
これまでは C-5（保守性・設計）の一部で、慣習を導く手順が無く、段階も `entry` だった。

## したこと

- 観点カタログ（`review-dispatch/references/viewpoints.md`）のコードの必須観点に C-18（既存の実装との調和）を足した。段階は `standard`。
- 担当の資料 `review-execution/references/C-18.md` を足した。
    - 慣習を導く手順（差分の外の同じ種類のコードを読む・慣習を書き出す・そろっているかを判定する・迷えば検索して数える）。
    - チェックポイント（命名の方針・置き場所・業務のロジックの置き場所・層の飛び越し・データアクセスの方法・共通の仕組みの迂回など）。
    - 重要度の決め方と、指摘にしないもの（割れている・例が少ない・理由が書かれている外れ）。
    - NG 例は 6 つの言語で書き、指摘にしない例を 2 つ入れた。特定のリポジトリには寄せていない。
- C-5 から、既存の規約・構成との整合を外した（カタログの行と `C-5.md`）。C-5 は、言語の一般的な慣習とリポジトリの書き方が食い違うとき、リポジトリの書き方に合っているものを指摘しない。
- 隣の観点の「見ないもの」に C-18 を書いた（C-15・C-17・X-3。カタログと各資料）。
- 明文の決まりとの照合を X-3 に任せる分担を、C-5 から C-18 に移した（`repo-guidance.md` の 5、`X-3.md` の例、`review-execution/SKILL.md`）。
- `self-review.md` の報告の例と、`review-execution/SKILL.md` の資料の範囲（C-1〜C-18）を直した。
- 仕様書（`docs/spec/context.md`・英語の版）に C-18 を書き、X-3 との分担の記述を直した。

起動の規則（再レビューの絞り方・軽い依頼の自己レビュー）と、ほかの観点の段階は変えていない。

## 確かめたこと

- `npm run lint`・`npm run typecheck`：通った。
- `npx vitest run tests/docs apps/daemon/src/default-skills.test.ts apps/daemon/src/prompts.test.ts`：450 件が通った。
- スキルと仕様書（`apps/daemon/default-context`・`docs/spec`）を main の版に戻す（`C-18.md` も消す）と、`default-skills.test.ts` の 105 件のうち、足した 5 件と直した 3 件の計 8 件が落ちることを確かめた。
- `npx vitest run --no-file-parallelism`：271 ファイル・5,430 件が通った（スキップ 1 件）。
- 画面の変更が無いので、画面の動作確認はしていない。足した観点が、エージェントのレビューを実際にどう変えるか（慣習を導けるか・指摘が増えすぎないか）は、エージェントを動かして確かめていない。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| X-3 を起動しない回は C-18 が規約の文書も見ると決めたのに、C-18 の基準と手順に規約の文書を読む段が無い（sacty のレビュー 1 回目。提案） | 基準に規約の文書を足し、手順の初めに規約の文書を読む段を足した（X-3 を起動した回は、書き方と層の意図を知るためだけに読む） |
| 仕様書の日英に「C-5 など」が残っている（同。提案） | 日英とも C-18 に直し、残っていないことを確かめるテストを足した |
| 「理由が書かれた外れは指摘にしない」が、仕組みが効かなくなる `must` にも及ぶように読める（同。提案） | 手順の順を入れ替え、効かなくなる仕組みの確認を先にした。効かなくなるものは理由が書かれていても `must` で出すと、手順・重要度・例 6 に書いた |
| 変更前の版を読めないときの扱いが無い（同。提案） | 差分に現れる行と足されたファイルを根拠から除くこと、既存の例が残らない種類は導かずに `limitations` に書くこと（`failed` にはしない）を足した |
| 理由による例外の範囲が箇所ごとに揃っていない。「慣習の仕組みでは要件を満たせない」は理由が書かれていなくても成り立ち、チェックポイント・例 6 と逆の答えになる。承認済みの設計が決めた外れに `must` の断りが無い。仕様書日英と ADR に断りが届いていない（sacty のレビュー 2 回目。提案） | 例外を「理由が根拠かコードのコメントに書かれている」だけにし、書かれていない外れは、要件を満たせないと分かるときでも理由を書くことを `should` で求めると決めた。承認済みの設計が決めた外れも、効かなくなる仕組みがあれば `must` で出すと書いた。仕様書日英と ADR にも断りを足した |
| 作業履歴の、戻したときに落ちるテストの件数と vitest の件数が、先頭コミットと合っていない（同。提案） | main の版に戻して数え直し、書き直した（8 件が落ちる。関係するテストは 450 件） |
| 承認済みの設計が決めた外れの扱いが、理由による例外と答えが逆になる。同じ規則を多くの箇所が別々の言葉で書いていて、直すたびに食い違う（sacty のレビュー 3 回目。提案） | 判定の順を `C-18.md` の「重要度の決め方」の 1 箇所に決めた（効かなくなる仕組み → `must`、理由か承認済みの設計がある → 出さない、どちらも無い → `should`）。手順・見落としやすい所・例 6 は、そこを指すだけにした。仕様書日英と ADR は、同じ順の要約にした |
| 作業履歴に「残したこと」の節が無い（同。提案） | 足した |
| ADR の再レビューの記述が、`pr-review` の規則と合わない（同。提案） | `self-review` と `pr-review` に分けて書いた |
| 仕様書日英の照合が、片方の言語の句だけでも通る（同。提案） | ファイルごとに、その言語の句（判定の順の 3 つ）を照合するようにした |
| 「見落としやすい所」が、設計が決めた外れを条件なしで判定の 2（出さない）に送っている（sacty のレビュー 4 回目。提案） | 「順（1 → 2）で扱う」に直した |
| `nit` の段の「慣習と言えるかが弱いもの」が、手順 6 の分類と逆の答えになる（同。提案） | 慣習と言えるかの判定を手順 6 だけに置き、`nit` の段は、そろっている慣習の表記の細部だけにした |
| 仕様書日英と ADR が判定の順を 3 段で言い直していて、資料の 4 段と合わない（同。提案） | 言い直しを消し、正本（`C-18.md` の「重要度の決め方」）を指すだけにした。残したのは、仕組みが効かなくなる外れは理由があっても `must`、の 1 文。テストも、指す句の確認に替えた |
| テストのコメントが同じ位置に 2 行続いて読みにくい（同。提案） | 1 行にまとめた |
| ADR の「関係する PR・タスク」に PR 番号が無い（sacty のレビュー 5 回目。提案） | `#449、PBI-405` に直した |
| `C-18.md` の「見落としやすい所」の 2 項目が、冒頭の基準の言い直しになっている（同。提案） | 重なる 2 項目を削り、`evidence` に書くことの条件だけを残した |

## 残したこと

- 足した観点が、エージェントのレビューを実際にどう変えるか（慣習を導けるか・指摘が増えすぎないか）は、測っていない。
- C-18 の段階（`standard`）で見落としが多いかは、使ってみて確かめる。多ければ段階を上げる。
