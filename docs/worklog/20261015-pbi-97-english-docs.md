# README・ユーザードキュメント・仕様書に英語の版を用意する

- 日付: 2026-10-15（UTC）
- タスク: PBI-97
- PR: #107
- ブランチ: feat/issue-97-english-docs
- 関係する ADR: [README・仕様書・ユーザードキュメントに、同じディレクトリの `*.en.md` で英語の版を置き、2つの版の形をテストで突き合わせる](../adr/20261015-0048-english-docs-side-by-side.md)

## 目的

OSS として公開するため、リポジトリの README・ユーザードキュメント（docs/user）・仕様書（docs/spec）に英語の版を用意する。
日本語の版は保ち、ADR と作業履歴は日本語のままにする（ステークホルダーの決定）。今後の PR で、両方の言語を直すようにする。

## したこと

- 英語の版を34ページ作った（`README.en.md`、`docs/user/` の16ページ、`docs/spec/` の17ページ。各 README を含む）。
  日本語の版と同じディレクトリに、`.md` を `.en.md` に変えた名前で置いた。日本語の版の名前と場所は変えていない。
- 日本語の版と英語の版の最初の行（ユーザードキュメントでは先頭の HTML コメントの次）に、もう一方の言語へのリンクを置いた。
  日本語の版の変更は、この行を足しただけ（`docs/spec/README.md` は、英語の版の規則の1項目も足した）。
- 訳の方針：
  - 設定の名前・既定値・コマンド・コードの参照・コードブロックの中のコマンドと値は、日本語の版のまま書いた。コードブロックの中の
    日本語のコメントと、例の値（`description: チケット管理` など）は英訳した。日本語のプレースホルダ（`<名前>` など）は `<name>` のように英訳した。
  - プログラムが日本語のまま出す・受け取る文字列（`Sacty セットアップ（<owner>/<name>）`・`**概要**`・`[sacty] localhost の転送：`・
    `目印：sacty-export:…`・「該当なし（sacty は記入していません）」など）は、日本語のまま残した。
  - 画面・工程・状態の名前は、画面の英語の文言（`apps/web/src/i18n/messages/`）に合わせた。「マージの後の監視」は画面の
    "After-merge watch"、タスクの作業履歴は "Activity"（仕様書の作業履歴は "activity log"）。
  - 英語の版の仕様書のコードの参照は `Code:` で始め、名前の括弧を半角にした。ユーザードキュメントの先頭のコメントは `<!-- Code: ... -->`、
    目次の見出しは `## Contents`。
  - リンクは、相手に英語の版があれば英語の版へ向け、ADR・作業履歴・`docs/README.md` へは日本語の版のまま。
- `tests/docs/docs.test.ts` に検査を足した：
  - 仕様書・ユーザードキュメントのファイル名に `.en.md` を許す。
  - 英語の版の仕様書の `Code:` の参照を、日本語の版の「コード:」と同じように確かめる（ファイルがあり、括弧の中の名前がそのファイルにある）。
  - 英語の版のユーザードキュメントが英語の目次（`## Contents`）にあり、先頭に `<!-- Code: ... -->` があること。英語の README から
    `docs/user/README.en.md` へリンクしていること。リンク切れ・アンカーの検査の対象に `README.en.md` を足した。
  - 対象のページ（README・docs/spec・docs/user）ごとに、もう一方の言語の版があること（`checkPairs`）。
  - 2つの版の突き合わせ（`checkPair`）：最初の行の言語のリンク、見出しの深さの並び、表の行の数、コードブロックの数と行の数、
    インラインコードの数（日本語の版で ASCII だけのものと、両方にあるもの）、リンクの行き先（日本語の版のリンクの相手に英語の版があれば
    英語の版と見なす。外部の URL はそのまま）。
  - これらの部品の回帰テスト（そろっていれば通り、言語の行・見出し・表の行・コードブロック・既定値・名前・リンクの片方だけの変更で落ちる）。
- `docs/README.md` に「英語の版」の節（対象・置き場所と名前・最初の行・書き方・メンテナンス・検査）を足し、冒頭とユーザードキュメントの
  書き方から参照した。docs の方針のスキル（`.claude/` と `.agents/` の2つの写し。同じ中身）に、英語の版を同じ PR で直す項目と、
  テストで突き合わせを確かめることを足した。
- ADR を足した（置き場所の判断と、突き合わせの検査）。

## 確かめたこと

- 34組の日本語の版と英語の版で、行の数・箇条の数・段落の数が一致する（`docs/spec/split-and-integrate` の末尾の改行の1行だけ違う）。
  本文の数値（インラインコードの外）を突き合わせ、違いが「1つ」「2つ」「16進」など語にした数だけであることを見た。
- 英語の版に、言語の行と、プログラムが出す日本語の文字列のほかに日本語が残っていないことを見た。「本業」「社内」にあたる語が無いことを見た
  （`internal` は `host.docker.internal` と例のホスト名だけ）。
- 足した検査が落ちることを、実際のページを一時的に壊して確かめた（英語の版を消す・表の行を消す・日本語の版だけ既定値を変える・
  `Code:` の名前を壊す・言語の行を消す（両方の言語）・英語の目次から1ページ消す・見出しを消す・リンクを日本語の版へ向ける・
  コードブロックに行を足す）。どれも落ち、戻すと通る。
- `npm run lint`（終了コード0）・`npm run typecheck`・`npx vitest run`（57ファイル・1390件が通過）・`npm run build`・
  `npx vitest run tests/docs`（85件が通過）。

## わからないこと・確かめていないこと

- 訳の中身（文の意味が日本語の版と同じか）は、テストでは確かめられない。数・名前・リンクは機械的に突き合わせ、本文は一部のページを
  読み比べた。全文を1文ずつ照合してはいない。
- 本文の語（インラインコードの外）だけを片方で変えたときは、テストでは見つけられない（例：日本語の版の文だけを直す）。レビューで見る。
- 英語の版にだけ ASCII のインラインコードを足したときも、テストでは見つけられない（置き換えの例の訳と見分けられないので）。
- 画面とコードの変更は無いので、動作確認の動画は撮っていない。

## レビューの指摘と対応

PR #107 のレビューの提案4件に、同じ PR で対応した。日本語の版にも同じ問題があるものは、両方の版を直した。

1. はじめにのセットアップのブロックで、設定・秘密情報の前に `npx sacty image build` が走り、公開のレジストリを使えない環境では
   書いてある順のとおりに操作すると失敗する：ブロックからビルドを外し、手順3（設定と秘密情報の後）にまとめた（`getting-started.md`・
   `getting-started.en.md`）。README の `image build` の行にも、公開のレジストリを使えないなら先に `image_build` を書くことを足した（両方の版）。
2. `sacty up` は URL を端末に出すだけで、ブラウザーを自動では開かない（`packages/cli/src/index.ts` の `Open ... in your browser.`）：
   英語の版の `opens` を「端末に表示する。ブラウザーで開く」に直した（README・はじめに・CLI）。日本語の版の「表示します」も、端末に表示し
   自動では開かないことがわかるように直した。
3. Jira Cloud の値の作り方の例（`echo -n 'me@example.com:<API トークン>' | base64`）で、トークンがシェルの履歴やプロセスの引数に残る：
   YAML のコメントを外し、表示しない入力（`read -rs`）でトークンを受け取り、組み込みの `printf` から標準入力で `base64` に渡して
   クリップボードに置き、1Password に貼り付けた後にクリップボードを空にする手順にした（`intake.md`・`intake.en.md`）。
   bash と zsh で、入力を流し込んで実行し、`printf '%s' 'me@example.com:<トークン>' | base64` と同じ値になり、変数が消えることを確かめた。
4. 英語の版の参照で、名前を囲む括弧が任意のため、パスの後に全角の括弧で存在しない名前を書いてもファイルの部分だけが一致して通る：
   「コード:」「Code:」の後ろの全体を、言語ごとの書き方（日本語：`（`・`・`・`、`、英語：` (`・`, `）として解析する `parseCodeRefs` を足し、
   合わないもの（括弧の種類の違い・閉じ括弧の欠け・区切りの違い・コードでない語・余計な文字）を「参照の書き方が違う」として失敗させた。
   日本語の版にも同じ弱さ（半角の括弧や閉じ括弧の欠けで名前を確かめずに通る）があったので、両方に入れた。
   回帰テストに、全角・半角の括弧の取り違え・閉じ括弧の欠け・括弧の前の空白の欠け・区切りの違い・余計な語・apps 等の下でないパスを足した。
   実際のページ（`docs/spec/gateway.en.md`）でも、全角の括弧で無い名前を書く・閉じ括弧を消すと落ち、戻すと通ることを確かめた。

確かめたこと：`npm run lint`（終了コード0）・`npm run typecheck`・`npx vitest run`（57ファイル・1390件が通過）・`npm run build`・`npx vitest run tests/docs`（85件が通過）。

## main への追従（PR #103 の後）

- PR #103（PBI-96：LICENSE・CONTRIBUTING・SECURITY）が main に入ったので、main をこのブランチにマージした。`tests/docs/docs.test.ts` のぶつかりは、
  両方の意図を保つように解消した：ルートの文書（`ROOT_DOCS`）に `README.en.md` を足してリンク切れ・アンカーの対象にし、日本語の版と英語の版の
  突き合わせには README の2つの版（`ROOT_READMES`）を使う。ライセンス・コントリビュート・セキュリティへのリンクの検査は、README の両方の版に広げた。
- README に足された「コントリビュート・セキュリティ」「ライセンス」の節を `README.en.md` に訳した。CONTRIBUTING・SECURITY の英語の版は
  このタスクの範囲の外なので作らず、`README.en.md` からは日本語の版へリンクする（「(in Japanese)」と添えた）。突き合わせの検査は、相手の英語の版が
  無いリンクを同じ行き先として比べるので、このままで通る。
- CONTRIBUTING の「ドキュメント」に、README・仕様書・ユーザードキュメントは両方の言語を直すことを書き足した（冒頭の「日本語で書いています」にも、
  英語の版があることを添えた）。
