# MCP サーバーに、起動とツールの呼び出しの時間切れを書けるようにする

- 日付: 2026-10-14（UTC）
- タスク: PBI-75
- PR: #82
- ブランチ: feat/issue-75-mcp-timeouts
- 関係する ADR: [MCP サーバーごとに起動とツールの呼び出しの時間切れを秒で書け、各エージェントとゲートウェイにそれぞれの形で効かせる](../adr/20261014-0458-mcp-timeouts.md)

## 目的

`mcp.yaml` の各サーバーに、起動とツールの呼び出しの時間切れ（秒）を任意で書けるようにする（範囲の検証あり）。Codex には同じ名前の設定で渡し、
Claude Code には同じ意味の設定があれば渡し、無ければ README に書く。ホストの MCP・ゲートウェイ経由の MCP でも、意味の通る範囲で効かせる。
書いていないときの動作は変えない。`default_tools_approval_mode` は足さない（ステークホルダーの判断）。

## したこと

- 設定：`mcp.yaml` の各サーバー（`command`・`url`）と `gateway.mcp_servers` に、`startup_timeout_sec`（1〜3600 秒）・`tool_timeout_sec`
  （1〜86400 秒）を任意で書けるようにした。整数で、範囲の外・小数・文字列は場所（例 `servers.a.tool_timeout_sec`）つきの設定の誤りにする
  （`apps/daemon/src/context.ts`・`host-mcp.ts`）。
- Codex：`config.toml` の `mcp_servers.<名前>` に同じ名前で書く。
- Claude Code：ツールの呼び出しはサーバーごとの `timeout`（ミリ秒）に `tool_timeout_sec × 1000` を書く。起動はサーバーごとの設定が無いので、
  全体の環境変数 `MCP_TIMEOUT` に、書いた値と、書いていないサーバーの既定（30秒）の大きい方を渡す。どのサーバーにも書かなければ渡さない。
- ゲートウェイ（`apps/daemon/src/gateway.ts`）：ゲートウェイ経由のコンテキストの MCP は、書いた値の大きい方が中継の fetch の既定（5分）を超えるときだけ、
  待つ上限を延ばした接続（undici の `Agent`、値ごとに使い回す）で中継する。そのため `apps/daemon` に `undici` を依存として足した
  （lockfile にすでにあった 7.30.0。Node 22 の組み込みの fetch に外の Agent を渡すと版の違いで動かないことがあるため、undici の fetch と組にする）。
- ホストの MCP：ゲートウェイの中継のツールの呼び出し（既定10分）・一覧（既定60秒）を、書いた値より先に切らない（既定より短くはしない）。
  時間切れだけを変えたときは、ホストの MCP サーバーを起動し直さない（ブラウザの再認証を起こさない）。
- レビューの指摘を受け、エージェントの実行全体の上限を定数 `AGENT_RUN_TIMEOUT_MS`（30分）にまとめ、`DockerExecutor` の既定もこれを使うようにした。
  エージェントに渡す MCP サーバー（ホストの MCP を含む）の時間切れが上限以上なら、コンテキストを用意するときに警告 `context.mcpTimeoutOverRun` を作業履歴に残す。
  README に実行全体の上限を書き、例（README・`mcp.yaml` の雛形・設定の雛形）を900秒にした。

## 確かめたこと

- 手元の CLI の本体で渡し方を確かめた：
  - Codex（codex-cli 0.160.0）：sacty が作った `config.toml` を `CODEX_HOME=… codex mcp list --json` で読ませ、`"startup_timeout_sec": 45.0, "tool_timeout_sec": 1800.0`
    と読まれること、書いていないサーバーは `null` のままであることを確かめた。負の値は Codex 自身が読み込みを拒否する。
  - Claude Code（2.1.299）：stdio・http のサーバーの設定のスキーマに `timeout`（正の整数、ミリ秒）があり、1000 ミリ秒より短い値は使われない。作った設定を
    `claude mcp get` で読ませ、`Timeout: 1800000ms` と表示されることを確かめた。起動はサーバーごとの設定が無く、全体の `MCP_TIMEOUT`（既定30000）だけであることを
    本体の処理で確かめた。
- 延ばした接続が本物の上流の SSE をそのまま中継すること、リダイレクトをたどらないこと、決めた上限まで待ち、過ぎたら `UND_ERR_HEADERS_TIMEOUT` で切ることを、
  本物の HTTP で確かめた（`gateway.test.ts`）。エージェントとゲートウェイの間の HTTP サーバーが応答の遅さでは切れないことも別に確かめた。
- 範囲の検証（0・負・上限超え・小数・文字列、境界の1・3600・86400）を `context.test.ts`・`host-mcp.test.ts` で、出力を `agents.test.ts`・`daemon.test.ts` で確かめた。
  書いていないときは `mcp.json`・`config.toml` の出力が前と同じで、`MCP_TIMEOUT` を渡さない。
- 修正を部分ごとに戻して、対応するテストが落ちることを確かめた（書き出し5件、中継への受け渡しと範囲の検証2件、ゲートウェイ・ホストの MCP の中継3件、
  起動し直さない1件、サービス・起動の組み立て2件）。
- `npm run lint`（終了コード0）、`npm run typecheck`、`npx vitest run`（45ファイル・981件）、`npm run build` が通った。依存を足したので、まっさらな複製で
  `npm ci`・`npm run build`・該当のテストが通ることも確かめた。
- レビューの指摘への対応の後：上限より1秒短い値では警告せず、上限ちょうどと超える値では警告すること、ホストの MCP も対象で作業履歴に残ることをテストで確かめた。
  警告を外す・判定を `>` に変えると落ちる。README の分の数が定数と一致することもテストで確かめる。レビューでテスト1001件・lint・typecheck が通った。
- 本物の AI・本物の Docker での長時間の実行は確かめていない（レビューでも未確認）。画面の変更は無い。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| エージェントの実行全体は開始から30分で止まり、MCP の時間切れはこれに反映されないので、README の例（30分かかるツール）や `tool_timeout_sec: 3600` は完走できない。上限を調整できるようにするか、制約を明記して完走できる例にしてほしい | 実行全体の上限は変えずに、定数 `AGENT_RUN_TIMEOUT_MS` にまとめた。README に上限と、それ以上にしても意味が無いことを書き、例を900秒にした。上限以上の値は設定の誤りにせず、警告 `context.mcpTimeoutOverRun` を作業履歴に残す（上限は実行の側の値で、後で調整できるようになることもあり得るため） |

## 残したこと

- 本物の AI・本物の Docker での長時間の実行の確認。
- `default_tools_approval_mode` は足していない（ステークホルダーの判断）。
