# ホストの MCP の設定の変更を、すぐ反映する

- 日付: 2026-10-14（UTC）
- タスク: PBI-77
- PR: #84
- ブランチ: feat/issue-77-host-mcp-reconcile
- 関係する ADR: [工程エージェントの実行の前に、使うホストの MCP を設定と突き合わせ、いまの設定での準備を待ってから動かす](../adr/20261014-0636-host-mcp-ready-before-run.md)

## 目的

ホストの MCP（`config.yaml` の `gateway.mcp_servers`）は30秒ごとに設定と突き合わせていたので、足した直後の実行では `/mcp/<名前>` が 404
（unknown MCP server）に、起動中は 503 になり得た。実行の前に設定と突き合わせ、足したものは起動を待ってから（上限あり）動かす。失敗したら、
どの MCP かわかるようにする。消したものは新しい実行に渡さない（今と同じ）。

## したこと

- `HostMcpServers.ready(names)`（`apps/daemon/src/host-mcp.ts`）：設定と突き合わせ（足したものを起動し、消したものを止める）、起動・再認証の途中の
  ものは準備ができるまで待つ（上限は MCP ごとの `ready_timeout_sec`）。
  - 並行する実行は、同じ MCP の起動の待ちを共有する（起動は1度だけ）。
  - 起動に失敗して1分ごとの起動し直しを待っているものは、待たずに理由を返す（実行のたびに起動し直してブラウザの再認証を増やさない）。
  - 時間切れの値だけの変更では起動し直さない（#82 の動作を維持）。
- 実行（`runContext`、`apps/daemon/src/service.ts`）：準備ができないものは、どの MCP かがわかる注意（`gateway.mcpUnavailable`、新しい `gateway.mcpReadyTimeout`）を
  作業履歴の「コンテキストを用意」に残して実行する。ホストの MCP への成果の書き出しは、その MCP だけを待ち、準備ができなければ理由を残して書き出さない
  （画面から書き出し直せる）。
- 待つ間に人間が一時停止・中止したら、上限まで待たずに戻る（コンテナは起動しない）。
- README に挙動を書き足した。
- レビューの指摘を受け、いまの接続を起動したときの設定（時間切れを除いた設定のキー）を持ち、いまの設定で起動した接続だけを準備済みとみなすようにした。

## 確かめたこと

- `host-mcp.test.ts`：「設定に足した直後の実行でも、起動を待ってから使える」（足した直後は 404、`ready` は起動が終わるまで待ち、その後ゲートウェイ経由でツールを呼べる）、
  「準備を待つ上限を過ぎたら、どの MCP サーバーかを返して先に進む」「上限の既定は ready_timeout_sec」「起動に失敗したら、どの MCP サーバーかと理由を返す」、
  並行する実行の起動の待ちの共有・再認証中の待ち・一時停止、時間切れの値だけの変更では起動し直さず消したものは止めること。
- `daemon.test.ts`：エージェントは準備を待ってから動き、準備できない MCP は ContextResolved の注意に名前つきで残る。書き出しは `export.failed` に MCP 名を残して書き出さない。
- 修正を戻すと落ちる：`ready` の突き合わせと待ちを外すと host-mcp の7件、`runContext` の待ちを外すと daemon の2件、一時停止の打ち切りを外すと該当のテスト（5秒で時間切れ）。
- `npm run lint`（終了コード0）、`npm run typecheck`（終了コード0）、`npx vitest run`（45ファイル・1034件）、`npm run build`（終了コード0）が通った。
- レビューの指摘への対応の後：「設定を変えた MCP サーバーの準備を待つ」のテストで、command・args・env の変更の後に新しいプロセスの準備まで待つこと、新しい起動の失敗で注意が
  返ること、新しい起動の時間切れ、時間切れの値だけの変更では待たないことを確かめた。判定を戻すと5件が落ちる。lint（終了コード0）・typecheck・vitest（1040件）・build が通った。
- 本物の AI・本物の Docker・本物の MCP の認証の操作は、レビューでは確かめていない。画面の変更は無い（作業履歴の注意の文言が増えるだけ）。

## レビューの指摘と対応

| 指摘 | 対応 |
| --- | --- |
| 準備済みの判定が「いまの接続があり期限切れでない」だけなので、既存の MCP の command・args・env を変えて新しいプロセスを起動している途中でも、古い接続で `ready` が成功する。直後の工程や書き出しが変更前の接続へ送られ、新しい起動が失敗しても注意が返らない | いまの接続を起動したときの設定のキー（時間切れを除く）を持ち、いまの設定で起動した接続だけを準備済みとみなすようにした。切り替えの完了・失敗・時間切れを待ち、失敗なら古い接続が残っていても理由を返す。進行中の呼び出しのために古い接続を残す動作と、時間切れの値だけの変更で起動し直さない動作は変えていない。回帰テストを足した |

## 残したこと

- 本物の AI・本物の Docker・本物の MCP の認証の操作での確認。
