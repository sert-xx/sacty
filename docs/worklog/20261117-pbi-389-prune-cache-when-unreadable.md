# どれかのプロジェクトのコンテキストを読めない間もビルドキャッシュの片付けを走らせ、片付けの期間の絞り込みをやめる

- 日付: 2026-11-17（UTC）
- タスク: PBI-389
- PR: #428
- ブランチ: feat/pbi-389-prune-cache-when-unreadable
- 関係する ADR: [どれかのプロジェクトのコンテキストを読めない間も、ビルドキャッシュの片付けは走らせる](../adr/20261117-2239-prune-build-cache-while-context-unreadable.md)、[ビルドキャッシュの片付けで、期間の絞り込みをやめ、使っていないものをすべて消す](../adr/20261117-2249-prune-build-cache-without-age-filter.md)

## 目的

2つの変更を、1つの PR で行う（どちらも、リポジトリの持ち主の決定）。

1つ目：デーモンの片付けは、どれかのプロジェクトのコンテキストを読めない間は、何もせずに戻っていた。
ビルドキャッシュの片付けは残すイメージの一覧を使わないのに、同じ条件で止まり、1つ読めないだけでビルドキャッシュが増え続けた。その間もビルドキャッシュの片付けは走らせる。

2つ目（作業の途中で足された要件）：ビルドキャッシュの片付けを、3日より長く使っていないものに絞っていたが、実物ではほとんど消えなかった。期間の絞り込みをやめる。

受け入れ条件の要点：

1. 設定は読めていて、どれかのプロジェクトのコンテキストを読めない間も、ビルドキャッシュの片付けは走る（間隔・上限の時間・ログの決まりは変えない）。
2. その間、コンテキストのイメージの片付けは走らない（イメージを1つも消さない）。
3. 作成中・読み直しの最中には、今までどおり走らせない。デーモンの停止・時間切れの扱いも変えない。
4. 仕様書・ユーザードキュメント（日英）の「読めない間は消さない」の記述を合わせ、ADR と作業履歴を足す。
5. ビルドキャッシュの片付けの引数を `docker builder prune -f` にする（`--filter` も `--all` も無い）。ログの文言・仕様書・ユーザードキュメント（日英）から「3日」を外し、ADR で期間の決定を置き換え、失うものを文書に書く。

## したこと

読めない間も走らせる：

- `apps/daemon/src/context-images.ts`
  - `ContextImageBuilder` の `prune`：コンテキストを読めなかったプロジェクト（`loadError`）があるときは、戻らずに、片付け（`removeStale`）へ残す一覧の代わりに `null` を渡す。
    読んでいる途中・読む前のプロジェクトがあるとき、読み直しの最中、設定を読めないときは、今までどおり戻る。
    設定を読めないときに読んだままのプロジェクトがあるときも、今までどおり戻る。
    この状態を、プロジェクトごとの印（`configUnread`）で持つようにした。前は「今の定義を読めていない（`current` でない）」で見分けていたが、読み込みの失敗が残っているプロジェクトと見分けられないため。
  - `pruneContextImagesAndBuildCache`：残す一覧が `null` なら、イメージの片付け（`docker image ls`・`docker image rm`）を飛ばし、ビルドキャッシュの片付けだけをする。間隔・打ち切りの扱いは変えていない。
  - `removeStale` の型：残す一覧を `readonly string[] | null` にした。
- `apps/daemon/src/main.ts`：コメントだけ（組み立ては、一覧をそのまま渡すので変わらない）。

期間の絞り込みをやめる：

- `apps/daemon/src/image.ts`：`buildCachePruneArgs` を `builder prune -f` にし、期間の定数 `BUILD_CACHE_MAX_UNUSED_DAYS` を消した（`sacty image build` の片付けとデーモンの片付けの両方が、この引数を使う）。
- `apps/daemon/src/context-images.ts`：成功のログの文言を「使っていないビルドキャッシュの片付けを実行しました」にした。
- `packages/cli/src/index.ts`：`sacty image build` の、消せなかったときの文言を「古いビルドキャッシュ」から「使っていないビルドキャッシュ」にした（期間で絞らなくなったため）。

docs：

- 仕様書 `docs/spec/daemon-lifecycle`・`docs/spec/agent-execution`（日英）、ユーザードキュメント `docs/user/images`・`docs/user/cli`・`docs/user/troubleshooting`（日英）。
- ADR を2つ足した（決定が2つのため）。PBI-388 の ADR は、「コンテキストを読めていないときはビルドキャッシュも消さない」と「3日より長く使っていないものだけを消す」の2つの部分を置き換えたので、名前に `superseded` を付け、PBI-313 の ADR と PBI-388 の作業履歴からのリンクを直した。

決めたこと（ADR に書いた）：

- イメージを消さないことを、空の一覧や読めた分だけの一覧ではなく、`null` で表す（渡した先でイメージが消える取り違えを、型の検査で見つけるため）。
- 設定を読めないときに読んだままのプロジェクトがあるときは、ほかのプロジェクトが読めなくても、今までどおり何も消さない（設定を読めないときの扱いは、このタスクの範囲の外）。

## 確かめたこと

- 足したテスト（`apps/daemon/src/context-images.test.ts`。docker の実行は差し替えた。手元にあるイメージの一覧は、どれも今の定義の名前でないものを返し、イメージの片付けが動けば `image rm` が呼ばれる形にした）
  - 読めないプロジェクトが1つ・全部：docker の呼び出しは `builder prune` だけ（`image ls`・`image rm` は無い）。成功の行が出て、時刻が進む。
  - 読めないプロジェクトが無い：`image ls`・`image rm`（3件）の後に `builder prune`。
  - 前に読めていたプロジェクトが読めなくなったとき：前に読んだ定義を使い続け、イメージは1つも消さない。
  - 読めるようになったら、次の読み直しでイメージも消す（間隔の内なので、ビルドキャッシュは走らせない）。
  - 読めない間の間隔：6時間の1ミリ秒前は走らせず、ちょうど過ぎたら走らせる。
  - 設定を読めないとき：読めないプロジェクトがあっても、間隔が過ぎていても、docker を動かさず、ログも出さない。
  - 設定を読めないときに読んだままのプロジェクトがあるとき：読み直すまで docker を動かさない。読み直すと、ビルドキャッシュだけを片付ける。
  - 読めなかった後に、設定を読めないときに読んだままのプロジェクト（前の読み込みの失敗が残っている）があるとき：読み直すまで docker を動かさない。
  - 読めないプロジェクトがあっても、ほかのプロジェクトを読み直している最中・イメージを作っている最中は、docker を動かさない。終わってから、ビルドキャッシュだけを片付ける。
  - 読めない間の片付けの重なり（同時に2つ動かさない）・時間切れ（時刻を進めず、次の読み直しで試し直す）・デーモンの停止（途中でも止まり、止めた後は片付けない）。
  - `pruneContextImagesAndBuildCache` に `null` を渡すと、`image ls` に消せるイメージがあっても `builder prune` だけを呼ぶ。始める前に打ち切られていたら、docker を動かさず、理由を出す。
- 直したテスト（期間の絞り込み）

  - `apps/daemon/src/context-images.test.ts`：デーモンの片付けが動かす docker も `builder prune -f` で、ログの文言に期間が無い。
- 修正を戻して、テストが落ちることを確かめた。
  - `context-images.ts` を元に戻す（読めないプロジェクトがあれば何もしない）：14 件（読めないプロジェクトが無いときの 1 件は、元から通る）。
  - 読めないプロジェクトがあるときに、読めた分だけの一覧を渡す（イメージを消してしまう誤り）：12 件。
  - 設定を読めないときに読んだままのプロジェクトの確かめを外す：2 件（うち 1 件は、前からあるテスト）。
  - その確かめを、印ではなく「今の定義を読めておらず、読み込みの失敗も無い」で見分ける形にする：1 件。
  - 引数に `--filter until=72h` を戻す：32 件。`-a` を足す：32 件。

    期間を外した `docker builder prune -f` の結果（消えた量・残ったもの）は、リポジトリの持ち主が実物で確かめた値を ADR に書いた。

## 残したこと

- 設定（`config.yaml`）を読めない間は、ビルドキャッシュも消さない（決めていない。変えていない）。
- 設定を読めないときに読んだままのプロジェクトがある間（設定が戻ってから、次の読み直しまで。遅くとも5分）は、ビルドキャッシュも消さない。
- ビルドキャッシュが期間に関わらず消えるので、片付けの後の最初のビルドに時間がかかる（ADR の「影響」）。
