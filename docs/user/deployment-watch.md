# マージの後の監視（CI/CD とデプロイ）

sacty のタスクの実装の PR がマージされたら、マージでできたベースブランチのコミットの CI/CD が通ったか、デプロイされたアプリが動いているかを
sacty が見届け、失敗していたら修正のタスクを自動で登録します。これは、実装の後の工程「マージの後の監視」として行います。

## 使う

1. 対象のリポジトリに、マージの後の監視のスキル `deployment-observer` を置きます（下の「スキル」）。
2. タスクを作ると、sacty が工程を選ぶときに、リポジトリにスキルがあるかを見ます。
   - あれば、実装の後に「マージの後の監視」の工程が入ります。
   - 無ければ、この工程を飛ばします（CI/CD も見ません）。飛ばした理由は、タスクの画面と作業履歴に出ます。

- プロジェクトの設定で On・Off する必要はありません（設定の項目はありません）。
- 実装を含む進め方（標準・設計を省く・不具合の修正）で使います。タスク分割では、子タスクそれぞれの実装の PR を見ます。
- プロジェクトの GitHub のアカウントに、対象のリポジトリの Actions とチェックを読む権限が要ります。
- タスクを始めた後にスキルを足しても、そのタスクでは見ません（次のタスクから見ます）。実装の PR がスキルを消したときは、CI/CD だけを見ます。

## 何をするか

1. 実装の PR をマージすると、この工程に進みます。タスクは完了にならず、終わっていないタスクとして一覧とダッシュボードに出ます
   （状態は「マージの後の監視中」）。人の承認は要りません。
2. マージのコミットの CI/CD（GitHub Actions のワークフローの実行・ほかのアプリのチェック・コミットの状態）を、sacty が1分ごとに確かめます。
   - 5分たっても1つも現れなければ、CI/CD が無いとして監視を飛ばします。
   - 60分たっても終わらなければ、時間切れで終えます（修正のタスクは作りません）。
   - `cancelled`・`skipped`・`neutral` は失敗とみなしません。
3. CI/CD が失敗したら、修正のタスクを登録します。本文には、元のタスク・PR・コミット・失敗したワークフローとジョブ・実行へのリンクと、
   ジョブのログの末尾（秘密情報を伏せたもの）が入ります。
4. CI/CD が通ったら、エージェントがスキルに従って確かめます。何を確かめるか（CI/CD の確認だけか、デプロイ後のアプリまでか）は、
   スキルの書き方で決まります。失敗やエラーを見つけたら、確認の結果と根拠を入れた修正のタスクを登録します。判断できなかったときは、
   修正のタスクを作らずに飛ばします。
5. 監視が終わったら、タスクが完了します。終わるのは、通った・飛ばした・時間切れのとき、または失敗して修正のタスクを登録するか作らないと
   決めた（下の「二重の登録と上限」）ときです。失敗しても、元のタスクは止めません。修正のタスクを登録したときは、修正のタスクに引き継ぎます。
   二重の登録や連鎖の上限のために作らなかったときは、タスクの詳細の「マージの後の監視」に出る理由（終わっていない同じ失敗の修正のタスクへの
   リンクか、連鎖の上限）を確かめてください。

修正のタスクは、ふつうのタスクとして進みます（そのマージでも、同じく監視します）。

## スキル

- 原本を `.agents/skills/deployment-observer/SKILL.md` に置き、Claude Code 用の `.claude/skills/deployment-observer` は原本への
  シンボリックリンクにします（どちらか一方だけでも使います）。
- タスクのテンプレート「Sacty セットアップ」で、このスキルを作る PR をエージェントに作らせることもできます
  （[タスクを進める](tasks.md#テンプレートsacty-セットアップ)）。CI/CD のあるリポジトリなら、デプロイしていなくても作ります。
- リポジトリの外を指すシンボリックリンクは、安全のため使いません（スキルが無いものとして扱い、理由を画面に出します）。
- スキルに書くこと：
  - CI/CD の確認の仕方（どのワークフロー・チェックが何を確かめているか、無視してよい失敗、結果やログの見方）。`references/ci.md` などの
    別のファイルに書き、SKILL.md から参照してもかまいません。
  - デプロイしているなら、何を「デプロイの完了」とみなすか、デプロイ後のアプリの確かめ方、アプリにどうつなぐか（プロジェクトの
    コンテキストの外部 PF・MCP サーバー）、エラーとみなす基準。
  - デプロイしていないなら、デプロイの確認を飛ばす（`deployment` の `result` を `skipped` にし、`reason` に理由を書く）こと。CI/CD の確認だけを
    して終わります。
- エージェントには、マージのコミットのコードの使い捨ての写しと、sacty が見た CI/CD の実行・チェックと、プロジェクトのコンテキストが渡ります。
  確かめるだけで何も変えないこと、長く待たないこと（待つのは sacty です）、最後に次の形で答えることを、sacty が指示します。

```json
{"sacty-deployment": {"ci": {"result": "passed", "summary": "必要なワークフローは通った"}, "deployment": {"result": "skipped", "reason": "デプロイしていない"}, "summary": "CI/CD だけ確かめた", "evidence": ["CI: success"]}}
```

| 項目 | 値 |
| --- | --- |
| `ci.result` | `passed`（通っている）・`failed`（失敗がある）・`skipped`（確かめない）・`unknown`（判断できない） |
| `deployment.result` | `healthy`（正しく動いている）・`unhealthy`（エラーになっている）・`skipped`（確かめない）・`unknown`（判断できない） |

- 確認に使う AI は、`config.yaml` の `step_agents.deployment`（書かなければ `default_agent`）です。

```yaml
step_agents:
  deployment: luna-low
```

## 費用と予算

- スキルに従った確認の費用は、元のタスクの費用に入ります（工程ごとの費用の表の「マージの後の監視」）。CI/CD の監視は AI を使いません。
- 予算の上限に達していたら、確認を実行せずに飛ばします（タスクは止めません）。

## 二重の登録と上限

- 同じ失敗（同じリポジトリで同じワークフロー・ジョブ、スキルに従った確認ならリポジトリ）の修正のタスクが終わっていなければ、新しく作りません
  （画面に、そのタスクへのリンクを出します）。
- 修正のタスクのマージでまた失敗すると、次の修正のタスクを作ります。元のタスクから3段（`MAX_FIX_CHAIN`）を超えては作りません。そのときは人が
  確かめてください。

## 画面で見る

- タスクの工程の並びに「マージの後の監視」が出ます（飛ばしたときは、飛ばしたことと理由）。工程のイメージも、ほかの工程と同じく変えられます。
- タスクの詳細の「マージの後の監視」に、状態（待っている・通った・失敗・飛ばした・時間切れ）・理由・コミット・CI/CD の実行とチェック・
  失敗したジョブとログ・スキルに従った確認の結果（CI/CD の確認とデプロイの確認それぞれ）・修正のタスクへのリンクが出ます。
  待っている間は自動で更新します。
- 修正のタスクの詳細の先頭に、元のタスクへのリンクが出ます。
- 作業履歴にも、工程に入れるか（飛ばす理由）・監視の開始・CI/CD の結果・確認・修正のタスクの登録（作らなかった理由）が残ります。

## 確かめられなかったとき

次のときは、修正のタスクを作らずに監視を終え、タスクが完了します。sacty は自動ではやり直しません。

- CI/CD が60分のうちに終わらなかった・GitHub の API を読めなかった（権限が無い・接続できないなど）：状態は「時間切れ」です。
- 5分たっても CI/CD が1つも現れなかった：状態は「飛ばした」（CI/CD が無い）です。
- スキルに従った確認で判断できなかった・確認を実行できなかった・答えを読めなかった・予算の上限に達していた：状態は「飛ばした」と理由です。

気づき方：

- タスクの詳細の「マージの後の監視」に、状態と理由が出ます。CI/CD の確認・デプロイの確認それぞれの結果が出るのは、エージェントの答えを
  読めたときだけです。確認を実行できなかった・答えを読めなかった・予算の上限に達していたときは、それぞれの結果は出ないので、全体の状態と
  理由を見てください。
- 作業履歴に「CI/CD が時間内に終わらなかった（時間切れ）」「スキルに従った確認の結果：判断できない」などの行が残ります。
- GitHub の API を読めなかった理由は、デーモンのログ（`[daemon] … の CI/CD の状態を読めませんでした`）に出ます。
- Slack の完了の通知は、監視の結果によらず同じ文です。結果は、通知のリンクからタスクの詳細を開いて確かめてください。

確かめ直す方法（手で行います）：

1. GitHub の API を読めなかったとき（デーモンのログに理由が出ます）だけ、プロジェクトの GitHub のアカウントの権限・接続を直します。
   予算の上限・答えを読めなかったなど、ほかの理由のときは要りません。
2. カードの「マージのコミット」のリンクから、GitHub でそのコミットの CI/CD（Actions・チェック）の結果を確かめます。
3. スキル（`.agents/skills/deployment-observer/SKILL.md` か `.claude/skills/deployment-observer/SKILL.md`）に書いた手順で確かめます。
   デプロイ後のアプリを確かめるのは、スキルがそれを求めているときだけです（CI/CD の確認だけのスキルなら、手順 2 で足ります）。
   実装の PR がスキルを消したときは、マージのコミットにスキルがありません。作業履歴の「対象リポジトリを用意」に出る、
   タスクを始めたときのコミットのスキルを見てください。
4. 直すことがあれば、新しいタスクを作ります。

## 一時停止・中止・再起動

- 監視の間も、ほかの工程と同じく一時停止できます。止めている間は CI/CD を見ず、確認もしません。再開すると続けます（60分の上限は、監視を
  始めた時刻から数えます）。確認の途中で止めたときは、再開すると確かめ直します。
- 中止すると、監視をやめます。マージした実装の PR はそのままです。
- デーモンを再起動しても、CI/CD を待っている監視はそのまま続きます。確認の途中で止まったら、タスクを一時停止にします。再開すると確かめ直します。
