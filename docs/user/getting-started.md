# はじめに

sacty をインストールし、起動して、最初のタスクを動かすまでの手順を説明します。
「必要なもの」から「最初のプロジェクトとタスク」までを、順に進めてください。
その後ろに、sacty の更新の仕方と、データの置き場所をまとめています。

## 必要なもの

- macOS
- Node.js 26.13.1 以上
  - 版は、リポジトリのルートの `.node-version` と `mise.toml` に書いてあります。
  - mise・nodenv・fnm などの版の管理ツールで、ディレクトリに合わせて版を切り替える設定（mise の `mise activate`、fnm の `--use-on-cd` など）をしていれば、その版が使われます。
  - 設定していなければ、`npm ci` の前に `fnm use` などで切り替えてください。
- Docker（Docker Desktop・OrbStack・Colima など。工程はコンテナの中で実行します）
- GitHub CLI（`gh`）
  - GitHub にアクセスするアカウントでログインしておいてください（[プロジェクトの設定](project-settings.md#github-アカウント)）。

## セットアップ

sacty のリポジトリ（[sert-xx/sacty](https://github.com/sert-xx/sacty)）を clone し、そのルートで次を実行します。

```sh
npm ci
npm run build
npx sacty config init   # ~/.sacty/config.yaml を作る
```

続けて、AI の接続先・鍵・コンテナイメージを用意します。

1. **AI の接続先を設定します。**
   `~/.sacty/config.yaml` を開き、`providers` に、使うツールの認証方式と、使えるモデルの単価（`available_models`）を書きます（[config.yaml の設定](config.md#接続先と単価providers)）。
   - 雛形は、Codex を API キーで使う設定（`providers.codex`）です。
   - 工程を実行する AI のモデルは sacty の既定を使うので、`agents` は書かなくてかまいません。
2. **鍵を保存します。**
   認証のトークンや API キーを、キーチェーンか 1Password に用意します（[秘密情報](secrets.md)）。
   雛形のままなら、OpenAI の API キーを `npx sacty secret set openai-api-key` で保存します。
3. **コンテナイメージを作ります。**
   エージェント実行用のコンテナイメージを `npx sacty image build` で作ります。
   - Docker Hub や npm の公開レジストリを使えない環境では、作る前に `image_build` を書いてください（[コンテナイメージ](images.md)）。
   - イメージが無いまま起動すると、`sacty up` の出力と画面の上に、作るコマンドが出ます。
     Docker が起動していないときも、そのことが出ます。

### どのディレクトリでも sacty を使う

`npx sacty` は、sacty のリポジトリの中でだけ使えます。
ほかのディレクトリ（対象リポジトリの手元の clone など）でも `sacty` と打って使うには、sacty のリポジトリで次を実行します。

```sh
npm run cli:install
```

このコマンドは、ビルド（`npm run build`）の後に、`sacty` の起動の入口を置き、`sacty --version` がこのリポジトリの版を出すことを確かめます。
何度実行してもかまいません。

入口を置く場所は、次のように決まります。

- `~/.local/bin/sacty` に置きます。
  mise を使っていても、mise には登録しません。
- 環境変数 `SACTY_BIN_DIR` を指定すると、その中に置きます。
- 置き場所が `PATH` に無いか、`PATH` で先に別の `sacty` が見つかると、`[sacty] 注意：` で知らせます。
- 前の版の sacty が mise に登録した `sacty` があれば、外します。
  外せなかったときは、`[sacty] 注意：` で、手で消すものを知らせます。

入口は、次のように動きます。

- 入口は、このリポジトリを指します。
  sacty を更新してビルドし直せば、新しい版で動きます。
  別の場所に clone した sacty で実行すると、`sacty` はその clone を指すように切り替わります。
- 入口は、実行したときの Node.js（sacty のリポジトリで mise などが選んだ版）で sacty を動かします。
  mise などでディレクトリごとに Node.js の版が違っても、どのディレクトリでも同じように動きます。
- sacty の更新で Node.js の版が変わったら（`mise.toml`）、もう一度実行してください。
  入口の Node.js が新しい版に切り替わります。
  古い版の Node.js を消した後に実行し忘れると、`sacty` がやり直しを知らせます。

別の `sacty` が先に使われるときは、次を確かめてください。

- 前に `npm link` で入れた `sacty`（いまの Node.js の版のもの）は、このコマンドが外します。
  ほかの Node.js の版で入れたものが残っていると、その版が有効なディレクトリで先に見つかることがあります。
  その版で `npm rm -g @sacty/cli` を実行して消してください。
- シェルの `alias` で `sacty` を定義していると、そちらが先に使われます。

入口を消すときは、`~/.local/bin/sacty`（`SACTY_BIN_DIR` を指定したなら、その中の `sacty`）を消します。

## 起動する

```sh
npx sacty up
```

`sacty up` は、デーモンと画面を起動し、端末に画面の入り口の URL（`http://127.0.0.1:4700/auth?token=…`）を表示します。
ブラウザーで開いてください（自動では開きません）。
この URL を開いたブラウザーだけが画面を使えます。

Ctrl+C で両方が終了します。
ポートは `--port`・`--daemon-port` で変えられます（[CLI](cli.md#sacty-up)）。

## 画面の構成

画面を開くと、まずダッシュボードを表示します。

| 画面 | URL | 中身 |
| --- | --- | --- |
| ダッシュボード | `/dashboard`（`/` を開いたときも） | すべてのプロジェクトをまたいで、あなたの出番・止まっているタスクの理由・終わっていないタスク・費用と予算・工程の待ち行列・取り込みの状況・流量・品質の信号を出します（[ダッシュボード](dashboard.md)）。Slack の通知を送れなかったときは、欄の上に理由を出します |
| タスクの一覧 | `/projects/<ID>/tasks` | そのプロジェクトのタスク。「タスクを作成」もここにあります |
| プロジェクトの設定 | `/projects/<ID>/settings` | そのプロジェクトの設定（[プロジェクトの設定](project-settings.md)） |
| プロジェクトの一覧 | `/projects` | プロジェクトの作成・インポート |
| タスクの詳細 | `/tasks/<ID>` | タスクの進み具合・承認・実行のログ |

画面の間は、ヘッダーとサイドメニューで移ります。

- ヘッダーのプロジェクトの切り替えで「すべてのプロジェクト」を選ぶとダッシュボードに、プロジェクトを選ぶとそのプロジェクトのタスクの一覧に移ります。
  ヘッダーは、開いている画面のプロジェクト（ダッシュボードなどでは「すべてのプロジェクト」）を表示します。
- サイドメニューの「タスク」「設定」は、ヘッダーで選んでいるプロジェクトのタスクの一覧・設定を開きます。
  「すべてのプロジェクト」を選んでいる間は「タスク」を出さず、「設定」はプロジェクトの一覧を開きます。
- `/projects/<ID>` を開くと、そのプロジェクトのタスクの一覧に移ります。
  無いプロジェクトの ID を開くと、ページが見つからないと表示します。

## 最初のプロジェクトとタスク

1. プロジェクトを作ります。
   プロジェクトの一覧（`/projects`）でプロジェクトを作り、「対象」（GitHub の Org かリポジトリ）と、ホストごとの「GitHub アカウント」を登録します（[プロジェクトの設定](project-settings.md)）。
2. タスクを作ります。
   そのプロジェクトのタスクの一覧で「タスクを作成」を押し、タスクを作ります（[タスクを進める](tasks.md)）。
   Issue・PR を取り込んでタスクにするときは、[Issue・PR・チケットの取り込み](intake.md) を設定してください。

対象に登録すると、タスクの内容によっては、sacty が対象のリポジトリにブランチをプッシュし、PR を作ります。

## sacty を更新する

sacty は、1日ごとに GitHub の sacty の最新のリリースを確かめます。
いま動いている版より新しい版がリリースされていれば、どの画面でも上に「Sacty の新しい版があります」と表示します。
推奨のモデル（[既定のエージェント](config.md#既定のエージェント)）や修正を取り込むため、表示が出たら更新してください。

- 表示は、開いている画面にも、リロードしなくても現れます（30 秒ごとに取り直します）。
- 表示の「リリースの内容を見る」から、GitHub のリリースの説明を確かめられます。
- 確かめられないとき（インターネットに出られない・リリースがまだ無いなど）は、何も表示しません。
  開発中の版（最新のリリースより新しい版）でも表示しません。
- インターネットに出られない環境では、`config.yaml` に `update_check: false` と書くと、確かめを止められます（[config.yaml の設定](config.md)）。

更新は、次の順に行います。

1. 動いている `sacty up` を Ctrl+C で止め、終わるのを待ちます。
2. データをバックアップします（[更新前のバックアップと旧版への復帰](#更新前のバックアップと旧版への復帰)）。
3. sacty のリポジトリで、次のコマンドを実行します。

```sh
git pull origin main
npm ci
npm run build
npx sacty image build
npx sacty up
```

コマンドごとに、知っておくことがあります。

- `npm ci` は、`package-lock.json` のとおりに依存を入れ直します。
  `package-lock.json` を書き換えないので、npm のレジストリを設定で変えていても作業ツリーに差分が残らず、次の `git pull` がぶつかりません。
- `npm run build` は、画面のビルドの結果（`apps/web/.next`）を消して作り直します。
  `sacty up` を動かしたまま実行すると、画面が壊れることがあるので、必ず止めてから実行してください。
  - `npm run cli:install` で `sacty` を入れた場合は、`npm run build` の代わりに `npm run cli:install` を実行してください（Node.js の版が変わったときも、入口が切り替わります）。
- `npx sacty image build` は、エージェントのイメージを作り直します。
  既定のイメージの名前（`sacty-agent:<版>`）は版に連れて変わるので、作り直さないとイメージが無いとして実行が止まります。
  - `config.yaml` の `image` が前の版の名前（`sacty-agent:<前の版>`）のままなら、`sacty up` の出力と画面の上に直し方が出ます。
    そのとおりに書き換えてから作り直してください。
  - `config.yaml` の `image` に自分の名前を書いている場合も、作り直すのが安全です。
    新しい版がエージェントの CLI の版を上げていることがあるためです。

更新で既定のモデルが変わると、`available_models` に単価の無いモデルの警告が出ることがあります。
そのモデルの単価を足してください。

### 更新前のバックアップと旧版への復帰

更新の前に、デーモンを止め、データディレクトリ（環境変数 `SACTY_HOME` の指定先。未指定なら `~/.sacty`）をバックアップしてください。
新しい種類の記録（文書作成・作業の工程を含むタスク、完了したタスクの監査と、その改修のタスクなど）を保存したデータベースは、それに対応していない旧版では読み込めず、起動に失敗するためです。

旧版へ戻すときは、次のようにします。

- 更新の前のバックアップを使ってください。
- 新しい工程の設定があるときは、設定も旧版に対応するものへ戻す必要があります。
- 戻す前のデータも別に保管し、失われる履歴を確かめてください。
  バックアップを復元すると、それ以後に作ったタスクや進捗の履歴は戻りません。

バックアップを復元しても、sacty の外で起きたことは元に戻りません。

- 予定表などに行った外部の変更は、元に戻りません。
- 監査の提案を採用して作った改修のタスクが、すでに PR を作っていることもあります。
- 外部の作業の開始の記録も、バックアップ以後のものは失われます。
  外部の実際の状態を確かめ、実施済みの変更を再実行しないでください。

## データの置き場所

sacty は、作業履歴・設定・作業領域を `~/.sacty/` に保存します。
環境変数 `SACTY_HOME` で変えられます。

作業領域（`~/.sacty/workspaces/`）には、次のものを置きます。

- タスクごとの対象リポジトリの clone と、実行ごとの一時的なコードの写し
- タスクごとの依存のキャッシュ（`~/.sacty/workspaces/_task-cache/`）。
  同じタスクの工程・実行の間で、パッケージのダウンロードなどの結果を使い回すためのもので、別のタスクとは共有しません

sacty は、作業領域のうち要らなくなったものを自分で消します。

- 完了したタスクの作業領域は、もう使わなくなった時点で消します（監査をするタスクは、監査が終わってから）。
- 中止したタスクの作業領域は、中止のときに消します。
- 依存のキャッシュは、そのタスクの作業領域と同じときに消します。
- デーモンを起動したときには、残っている次のものも消します。
  - 中止の途中でデーモンが止まって残った、依存のキャッシュ
  - 実行中にデーモンを止めた・再起動したときに残った、一時的な写し
  - 以前の版で完了したタスクの作業領域

次のものは消しません。

- 作業履歴（`~/.sacty/runs/` のセッションログ）・オーケストレーターのセッション・メモリー・`sacty.db`
- 動いているコンテナが使っている場所。
  Docker に問い合わせられないときも、消しません。
  消せなかったときは、デーモンの端末に理由が出ます。

消した後で作業領域が要るとき（完了したタスクの再レビューや、オーケストレーターへの質問）は、作業領域を同じ起点のコミットで作り直します（clone をし直すので、少し時間がかかります）。

同じ `SACTY_HOME` では、sacty を二重に起動できません（ポートを変えても同じです）。

- 2つ目の `sacty up` は、データに触れる前に、動いているデーモンの接続先と PID を表示して失敗で終わります。
- sacty は `SACTY_HOME/daemon.lock` の OS のファイルロックで判定します。
  そのため、前のデーモンが突然落ちても（SIGKILL など）、次の起動は妨げられません。
- 違う `SACTY_HOME` なら、ポートを変えて並行して動かせます。

## 開発するとき

```sh
npm test          # ユニットテスト
npm run lint      # Biome（整形とリンター）
npm run typecheck # 型チェック
npm run build     # ビルド
```

| パス | 役割 |
| --- | --- |
| `packages/core` | 作業履歴のイベント、イベントからタスクの状態を復元する処理、費用の計算 |
| `apps/daemon` | 常駐プロセス。作業履歴（SQLite、追記専用）への書き込みと、工程の実行（コンテナ）を行います |
| `apps/web` | 画面（Next.js、shadcn/ui）。操作はデーモンの API に依頼します |
| `packages/cli` | `sacty` コマンドと、エージェント実行用イメージの Dockerfile |

仕組みの詳細は [仕様書](../spec/README.md) にあります。
