# プロジェクトの設定

プロジェクトごとの設定は、画面のプロジェクトの設定で登録します（config.yaml には書きません）。

プロジェクトの設定は `/projects/<ID>/settings` で開きます（サイドメニューの「設定」は、ヘッダーで選んでいるプロジェクトの設定を開きます）。
表示するプロジェクトは、画面のヘッダーで切り替えます（選ぶと、そのプロジェクトのタスクの一覧に移ります）。
プロジェクトを作る・インポートすると、画面はそのプロジェクトに切り替わり、設定を開きます。
タスクやプロジェクトの設定を（一覧・通知のリンク・URL から）開いたときも、ヘッダーはそのプロジェクトに切り替わります（[画面の構成](getting-started.md#画面の構成)）。

| 欄 | 内容 | 詳しいページ |
| --- | --- | --- |
| 名前 | プロジェクトの名前（80文字まで） | |
| 対象 | タスクを作り、Issue・PR を取り込む Org とリポジトリ | [対象](#対象) |
| チケットの取り込み先（任意） | JIRA のチケットを取り込む接続先とキー | [取り込み](intake.md#jira-のチケット) |
| コンテキストリポジトリ（任意） | 工程エージェントに渡す規約・スキル・MCP・外部 PF | [コンテキストリポジトリ](context.md) |
| 使える外部 PF | 工程エージェントが `$SACTY_PF_URL` で呼べる API（表示だけ） | [ゲートウェイ](gateway.md#組織内-pf-の-api) |
| GitHub アカウント | ホストごとに使う `gh` のアカウント | [GitHub アカウント](#github-アカウント) |
| 共用の compose（任意） | テストに使う、チームで共用する docker compose | [docker compose のサービス](compose.md#共用の-compose) |

Slack の通知は、プロジェクトの設定ではなく「Sacty の設定」で、すべてのプロジェクトに共通の通知先を設定します（[Slack の通知](notifications.md)）。

マージの後の監視は、プロジェクトの設定で On・Off しません。
対象のリポジトリにスキルがあれば、タスクの工程に入ります（[マージの後の監視](deployment-watch.md)）。

## 対象

対象（GitHub の Org またはリポジトリ）は、ホストを含めた `https://` の URL で書きます（例 `https://github.com/acme/app`、`https://ghe.example.com/acme`）。
github.com も GitHub Enterprise Server も同じ形です。

- sacty は、末尾の `/`・`.git`、クエリ（`?…`）・`#…`、全角の文字、貼り付けで紛れ込む見えない文字を直して読みます。
- 読めない URL は、入力の下に理由（http・SSH・余分な `/tree/…`・Org とリポジトリの単位の取り違えなど）が出ます。
- 読めない対象のホストは、「GitHub アカウント」の欄に出ません。

対象は、次のように使います。

- 画面でタスクを作るときは、対象の中からリポジトリを選びます（Org の対象は、`gh` で読んだその Org のリポジトリから選びます）。
- sacty は、対象の開いている Issue と PR を取り込みます（[取り込み](intake.md)）。
  - 取り込むラベルの付いた Issue は、タスクとして取り込みます。
  - レビュー用のラベルの付いた（またはレビューを依頼された）PR は、レビューだけのタスクとして取り込みます。
- 同じ Org・リポジトリは、ほかのプロジェクトに登録できません。
  Org とその中のリポジトリが別のプロジェクトにあれば、リポジトリが優先します（Org のプロジェクトからは除かれます）。
- 対象ごとに「イメージ」（`config.yaml` の `images` の名前か `default`）を選ぶと、オーケストレーターに選ばせず、すべての工程でそれを使います。
  リポジトリの指定が Org の指定より優先します（[コンテナイメージ](images.md#どのイメージで動くか)）。

対象に登録すると、タスクの内容によっては、sacty が対象のリポジトリにブランチをプッシュし、PR を作ります。

## GitHub アカウント

sacty は、ホストの GitHub CLI（`gh`）にログイン済みのアカウントで GitHub にアクセスします。
アクセスするのは、Issue の取り込み、clone、プッシュ、PR の作成、調査の結果の Issue へのコメント、レビューの PR への投稿です。
github.com と GitHub Enterprise Server（いくつでも）を同時に使えます。

```sh
gh auth login                                 # github.com。使うアカウントごとにログインする
gh auth login --hostname ghe.example.com      # GitHub Enterprise Server も、ホストごとにログインする
```

- 使うアカウントは、プロジェクトの設定で、対象のホストごとに必ず選んでください（最初は、そのホストの `gh` のアクティブなアカウントが選ばれています）。
  - `gh` でアカウントを切り替えても、sacty はプロジェクトごとに選んだアカウントを使います。
  - 選んでいないあいだは、そのホストへのアクセスを理由つきで止めます。
- コンテキストリポジトリ・共用の compose だけで使うホストのアカウントは任意です。
  選ばなければ、ホストの git の認証を使います。
- API は、github.com なら `https://api.github.com`、GitHub Enterprise Server なら `https://<ホスト>/api/v3` を使います。
- HTTPS のリポジトリは、そのホストのアカウントのトークンで clone・プッシュします（ホストの git の認証の設定は要りません）。
  SSH の URL やローカルのパスは、ホストの認証（ssh-agent など）を使います。
- sacty はトークンを使うたびに `gh` から取り出し、作業履歴・ログ・画面・コンテナには出しません。
- 「GitHub アカウント」の欄の「Sacty が認識している gh のアカウント」を開くと、デーモンが `gh auth status` から読めたアカウントを、ホスト・アカウント・状態の一覧で確かめられます。
  ホストが一覧に無ければ、デーモンを動かしているユーザーの `gh` にログインしていません（`GH_CONFIG_DIR` などの違いも確かめてください）。
- `gh` にログインし直したり、アカウントを足したりしたら、「GitHub アカウント」の欄の「アカウントを読み直す」を押してください。
  デーモンが `gh auth status` をもう一度確かめ、選べるアカウントと一覧を新しくします。編集中の入力は残ります。
- 状態が「確認できず」のアカウントは、`gh` がトークンを確かめられなかったもの（一覧に理由が出ます）です。
  選べますが、社内のプロキシの先にある GitHub Enterprise Server では、デーモンを起動するシェルに `HTTPS_PROXY`・`NO_PROXY`・`SSL_CERT_FILE` などを設定しているか確かめてください。
  デーモンはこれらを `gh` に渡します。

## コンテキストリポジトリ

「コンテキストリポジトリ」の欄に、リポジトリ（git の URL かローカルのパス）と、ブランチ・タグ（任意。空なら既定のブランチ）を書きます。
書き方と中身は [コンテキストリポジトリ](context.md) を参照してください。
外すときは、リポジトリを空にして保存します。

保存するときに、sacty はコンテキストを読んで検査し、`mcp.yaml`・`platforms.yaml` などに誤りがあれば知らせます。
保存はしますが、このままでは工程の実行で止まります。

## エクスポート・インポート

プロジェクトの定義をエクスポートし、ほかの sacty でインポートできます。

- 含めるもの：名前・対象（イメージの指定を含む）・コンテキストリポジトリ・チケットの取り込み先・共用の compose。
- 以前の sacty でエクスポートしたファイルにマージの後の監視の設定があっても、読まずにインポートします。
- 含めないもの：GitHub アカウント（個人の設定）・トークン・Slack の通知（「Sacty の設定」にあり、プロジェクトの設定ではないため）。
- インポートでは、知らない項目があるファイルを受け付けません。
- 以前の版（版 3・4）でエクスポートしたファイルは、通知先を含むかによらず、インポートできません。
  画面に理由を出すので、今の sacty でエクスポートし直してください。
