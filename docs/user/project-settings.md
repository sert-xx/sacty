# プロジェクトの設定

プロジェクトごとの設定は、画面のプロジェクトの設定で登録します（config.yaml には書きません）。

プロジェクトの設定は `/projects/<ID>/settings` で開きます（サイドメニューの「設定」は、ヘッダーで選んでいるプロジェクトの設定を開きます）。
表示するプロジェクトは、画面のヘッダーで切り替えます（選ぶと、そのプロジェクトのタスクの一覧に移ります）。プロジェクトを作る・インポートすると、
そのプロジェクトに切り替わり、設定を開きます。タスクやプロジェクトの設定を（一覧・通知のリンク・URL から）開いたときも、ヘッダーはそのプロジェクトに
切り替わります（[画面の構成](getting-started.md#画面の構成)）。

| 欄 | 内容 | 詳しいページ |
| --- | --- | --- |
| 名前 | プロジェクトの名前（80文字まで） | |
| 対象 | タスクを作り、Issue・PR を取り込む Org とリポジトリ | [対象](#対象) |
| チケットの取り込み先（任意） | JIRA のチケットを取り込む接続先とキー | [取り込み](intake.md#jira-のチケット) |
| コンテキストリポジトリ（任意） | 工程エージェントに渡す規約・スキル・MCP・外部 PF | [コンテキストリポジトリ](context.md) |
| 使える外部 PF | 工程エージェントが `$SACTY_PF_URL` で呼べる API（表示だけ） | [ゲートウェイ](gateway.md#組織内-pf-の-api) |
| GitHub アカウント | ホストごとに使う `gh` のアカウント | [GitHub アカウント](#github-アカウント) |
| 共用の compose（任意） | テストに使う、チームで共用する docker compose | [docker compose のサービス](compose.md#共用の-compose) |
| マージの後の監視 | 実装の PR のマージの後に、CI/CD とデプロイ後のアプリを確かめ、失敗したら修正のタスクを登録する（既定は Off） | [マージの後の監視](deployment-watch.md) |
| Slack の通知（任意） | 人の出番とタスクの完了を知らせる | [通知](notifications.md) |

## 対象

対象（GitHub の Org またはリポジトリ）は、ホストを含めた `https://` の URL で書きます（例 `https://github.com/acme/app`、
`https://ghe.example.com/acme`。github.com も GitHub Enterprise Server も同じ形です）。末尾の `/`・`.git` は無視します。

- 画面でタスクを作るときは、対象の中からリポジトリを選びます（Org の対象は、`gh` で読んだその Org のリポジトリから選びます）。
- 対象の、取り込むラベルの付いた開いている Issue はタスクとして、レビュー用のラベルの付いた（またはレビューを依頼された）開いている
  PR はレビューだけのタスクとして取り込みます（[取り込み](intake.md)）。
- 同じ Org・リポジトリは、ほかのプロジェクトに登録できません。Org とその中のリポジトリが別のプロジェクトにあれば、リポジトリが
  優先します（Org のプロジェクトからは除かれます）。
- 対象ごとに「イメージ」（`config.yaml` の `images` の名前か `default`）を選ぶと、オーケストレーターに選ばせず、すべての工程でそれを
  使います（リポジトリの指定が Org の指定より優先します。[コンテナイメージ](images.md#どのイメージで動くか)）。

注意：対象に登録すると、タスクの内容によっては、sacty が対象のリポジトリにブランチをプッシュし、PR を作ります。

## GitHub アカウント

GitHub へのアクセス（Issue の取り込み、clone、プッシュ、PR の作成、調査の結果の Issue へのコメント、レビューの PR への投稿）は、
ホストの GitHub CLI（`gh`）にログイン済みのアカウントで行います。github.com と GitHub Enterprise Server（いくつでも）を同時に使えます。

```sh
gh auth login                                 # github.com。使うアカウントごとにログインする
gh auth login --hostname ghe.example.com      # GitHub Enterprise Server も、ホストごとにログインする
```

- 使うアカウントは、プロジェクトの設定で、対象のホストごとに必ず選んでください（最初は、そのホストの `gh` のアクティブなアカウントが
  選ばれています）。`gh` でアカウントを切り替えても、プロジェクトごとに選んだアカウントを使います。選んでいないあいだは、そのホストへの
  アクセスを理由つきで止めます。
- コンテキストリポジトリ・共用の compose だけで使うホストのアカウントは任意です。選ばなければ、ホストの git の認証を使います。
- API は、github.com なら `https://api.github.com`、GitHub Enterprise Server なら `https://<ホスト>/api/v3` を使います。
- HTTPS のリポジトリは、そのホストのアカウントのトークンで clone・プッシュします（ホストの git の認証の設定は要りません）。SSH の URL や
  ローカルのパスは、ホストの認証（ssh-agent など）を使います。
- トークンは使うたびに `gh` から取り出し、作業履歴・ログ・画面・コンテナには出しません。

## コンテキストリポジトリ

「コンテキストリポジトリ」の欄に、リポジトリ（git の URL かローカルのパス）と、ブランチ・タグ（任意。空なら既定のブランチ）を
書きます。書き方と中身は [コンテキストリポジトリ](context.md) を参照してください。外すときは、リポジトリを空にして保存します。

保存するときに、コンテキストを読んで検査し、`mcp.yaml`・`platforms.yaml` などに誤りがあれば知らせます（保存はします。ただし、このままでは
工程の実行で止まります）。

## エクスポート・インポート

プロジェクトの定義をエクスポートし、ほかの sacty でインポートできます。

- 含めるもの：名前・対象（イメージの指定を含む）・コンテキストリポジトリ・通知先（送り先・チャンネル・言語。秘密情報は名前か参照だけ）・
  チケットの取り込み先・共用の compose・マージの後の監視（On のときだけ）。
- 含めないもの：GitHub アカウント（個人の設定）・トークン・Slack のメンション（相手と種類）。メンションする相手は使う人や環境ごとに
  違うためです。インポートの後に、プロジェクトの設定の画面で、相手と種類の両方を必要に応じて設定し直してください
  （種類は既定の人の出番だけに戻ります）。
- インポートでは、知らない項目があるファイルを受け付けません。
- 以前の版（版 3）でエクスポートしたファイルは、メンションを含むかによらず、インポートできません。画面に理由を出すので、今の sacty で
  エクスポートし直してください。
