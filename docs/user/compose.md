# docker compose のサービス（DB・モック API など）

テストや動作確認に、docker compose で起動する DB やモック API が要るリポジトリでは、sacty がホストでサービスを起動し、エージェントと
テストのコンテナをそのネットワークにつなぐ（エージェントには Docker の権限を渡さない）。対象のリポジトリの compose ファイルを使うときは、
設定は要らない。

## 起動のしかた

- どの compose ファイルのどのサービスを、どの工程（実装・再現・不具合の調査）で使うかは、オーケストレーターが工程を選ぶときに、
  リポジトリ（compose ファイル・README・AGENTS.md・テストの設定）を読んで決める。内容の調査では起動しない。
- 工程のエージェントの実行と、テストの実行の1回ごとに、別のプロジェクト名で起動し（`docker compose up --wait`）、終わったらコンテナ・
  ネットワーク・ボリュームを消す。同じリポジトリのタスクを並行で動かしてもぶつからない。データは実行ごとに消える。
- エージェントとテストは、サービス名とコンテナのポートで接続する（例 `db:5432`）。`ports`（ホストのポート）と `container_name` は外して
  起動する。
- サービスのイメージは、compose ファイルに書かれた名前のまま、ホストの Docker で取得・ビルドする（組織のレジストリのイメージは、ホストで
  `docker login` しておく）。
- デーモンが途中で終わって残ったサービスは、次の起動のときに消す（起動したデーモンをコンテナのラベル `io.sacty.owner` に残し、
  そのデーモンが動いているもの、つまり同じ `SACTY_HOME` で動いているほかの sacty のものは消さない）。

## localhost のままでも届く

リポジトリの設定の接続先が localhost のままでも届くよう、サービスを起動した実行では、エージェントとテストのコンテナの中で
`127.0.0.1:<ポート>`（と、使えれば `[::1]:<ポート>`）をサービスの同じポート（`<サービス名>:<ポート>`）に転送する。転送は、コマンドの前に
sacty がコンテナの中で起動する小さな TCP の転送（イメージにある Node.js で動く。追加のパッケージは要らない）で、コマンドが終わると
止まる。コマンドの終了コードと出力は変わらない。サービスを起動しない実行では、何も変わらない（コマンドも同じ）。

- 転送するのは、サービスのコンテナのポート（`ports` の右側・`expose`）と、`ports` でホストに出すポート（published）。ローカルの開発の
  設定はホスト側のポートを指していることが多いので、`ports: ["15432:5432"]` なら `localhost:15432` と `localhost:5432` のどちらでも
  `db:5432` に届く（sacty はホストのポートには出さない。コンテナの中だけの転送）。
- `ports` は短い書き方（`"5432"`・`"15432:5432"`・`"127.0.0.1:15432:5432"`・範囲の `"8000-8001:8000-8001"`）と長い書き方（`target`・
  `published`）の両方を読む。published が無い・範囲の長さが合わないものは、コンテナのポートだけを転送する。UDP など TCP 以外のポート
  （`ports` の `/udp`・`expose` の `"8125/udp"`）は転送せず、ぶつかりの判定にも入れない（同じ番号の TCP のポートは転送する）。
- 同じサービスの中で、ホストに出すポートがほかのコンテナのポートと同じ番号のとき（`ports: ["8080:80", "18080:8080"]`）は、ホストから
  見た番号の対応を優先する（`localhost:8080` → `app:80`。`app:8080` へは `localhost:18080` から届く）。
- 複数のサービスが localhost の同じ番号を使うとき（ホスト側・コンテナ側を問わない）は、その番号は転送しない（どれにつなぐか決められない
  ため。サービス名で接続する）。作業履歴のサービスの起動の記録と、エージェントへの指示に、その番号を出す。
- そのポートをコンテナの中のほかのものがすでに使っているときは、そのポートは転送せずに続ける（失敗にしない）。理由を、テストの出力
  （標準エラー出力）か、デーモンのログ（エージェントの実行）に出す。
- 制限：転送は TCP だけ。MySQL のクライアントなど、ホストに `localhost` と書くと TCP ではなく UNIX ソケットで接続するものは届かない
  （`127.0.0.1` と書けば届く）。また、テストするアプリ自身がサービスと同じポートで待ち受けると、転送とぶつかって待ち受けられない
  （アプリのポートを変えるか、サービス名で接続する）。

## 使えない設定

compose ファイルは `docker compose config` で正規化してから確かめ、使うサービスとその依存に次の設定があれば、起動せずに理由を示して止まる。

- `privileged`・`cap_add`・`devices`・`volumes_from`・ホストのネットワーク・PID など（`network_mode: host`・`pid: host` など）・
  `security_opt` の unconfined
- Docker の API のソケットを渡す `use_api_socket`・ホストでコマンドを動かす `provider`・ビルドの `ssh`・`network: host`・`privileged`・
  `entitlements`
- 作業領域の外のパスのマウント（Docker のソケットを含む）・作業領域の外の `build`・`env_file`・`label_file`・`secrets`・`include`・
  `extends` のファイル（これらのパスに変数は使えない）
- external のネットワーク・ボリューム、bridge 以外のネットワークのドライバー、ボリュームのドライバーの指定

## 共用の compose

テストに要る Cassandra・Redis などの compose ファイルが、チームで共用する別のリポジトリにあるときは、プロジェクトの設定の「共用の
compose」に書く（複数書ける。エクスポートにも含む）。

| 欄 | 内容 |
| --- | --- |
| 名前 | 英小文字・数字で始まる、英小文字・数字・`_`・`-` の40文字まで。プロジェクトの中で重ならない |
| リポジトリ | git の URL（`https://`・`ssh://`・`git@<ホスト>:<パス>` など）か、ローカルの絶対パス（相対パスは使えない） |
| ブランチ・タグ | 任意。無ければ既定のブランチ |
| compose ファイル | リポジトリの根からの相対パス（`/` や `-` で始まるもの・`..`・`$` を含むものは使えない） |
| 説明 | 任意（1000文字まで）。オーケストレーターの判断の手がかり |

- 設定しただけでは起動しない。オーケストレーターがタスクごとに、リポジトリ（テストの設定・README・AGENTS.md）と説明から要るかを判断し、
  要るときだけ名前で選ぶ（対象のリポジトリの compose とどちらか一方）。要らないタスクでは取得も起動もしない。使う・使わない理由と、
  どの共用の compose（リポジトリ・ref・ファイル）を使うかは、作業履歴（タスクの画面）に残る。説明には、起動するサービスや、どの
  テストに要るかを書くと判断の手がかりになる。
- 工程・テストの実行の前に、sacty がリポジトリを取得する。リポジトリごとのキャッシュ（`$SACTY_HOME/cache/shared-compose`）を、実行の
  たびに ref の最新に更新し、そのコミットの中身を実行ごとのディレクトリに書き出して起動し、終わったら消す（並行するタスクが、ほかの
  タスクの初期化スクリプトを書き換えない）。起動のしかたと安全の確かめは、対象のリポジトリの compose と同じ（実行ごとのプロジェクト名・
  `up --wait` で healthcheck を待つ・ホストのポートは出さない）。マウントできるのは、取得したリポジトリの中だけ（compose ファイルからの
  相対のマウントは使える）。
- `container_name` は外して起動し、sacty のネットワークの別名にする（その名前でも、サービス名でも届く。ほかのタスクとはぶつからない）。
- HTTPS の GitHub は、対象のリポジトリ・コンテキストリポジトリと同じく、プロジェクトに選んだ `gh` のアカウントで取得する（「GitHub
  アカウント」でホストを選べる）。SSH・ローカルのパスは、ホストの git の認証を使う。URL にユーザー名・パスワード・トークンは書けない。
- 取得できない・compose ファイルが無い・安全の確かめに引っかかる・起動できないときは、どの共用の compose の何が原因かを示して、工程を止める。
