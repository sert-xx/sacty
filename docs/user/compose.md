# docker compose のサービス（DB・モック API など）

テストや動作確認に、docker compose で起動する DB やモック API が要るリポジトリでは、sacty がホストでサービスを起動します。
sacty は、工程のエージェントのコンテナをサービスのネットワークにつなぐので、エージェント（とエージェントが実行するテスト）は、サービスに接続できます。
エージェントには Docker の権限を渡しません。

## あなたが用意するもの

用意するものは、compose ファイルがどこにあるかで変わります。

- 対象のリポジトリの compose ファイルを使うときは、設定は要りません。
- チームで共用する別のリポジトリの compose ファイルを使うときは、プロジェクトの設定の「共用の compose」に書きます（[共用の compose](#共用の-compose)）。

どちらのときも、次のことを確かめてください。

- イメージ：組織のレジストリのイメージを使うときは、ホストで `docker login` しておいてください（[起動のしかた](#起動のしかた)）。
- compose ファイルの設定：[使えない設定](#使えない設定) があると、sacty はサービスを起動せずに止まります。
- 接続先：リポジトリの設定の接続先が localhost のときは、転送を試みます（[localhost への転送](#localhost-への転送)）。
  届かない場合もあります（[localhost で届かないとき](#localhost-で届かないとき)）。

## 起動のしかた

sacty は、次のようにサービスを起動し、片付けます。

sacty が作った実装の PR のレビューの子タスクでも、対象のコミットを作った実装が使ったサービスを、再レビューを含め実行ごとに起動します。
取り込んだ PR のレビューでは起動しません。
起動に失敗した場合や記録から取得元を特定できない場合は、サービス無しでレビューを続け、担当が確かめられなかったことを報告します。
同時実行数はタスクの上限に含まれるため、ホストのメモリーに合わせて調整してください。

- 使うサービスと工程：オーケストレーターが、工程を選ぶときに決めます。
  - オーケストレーターは、リポジトリ（compose ファイル・README・AGENTS.md・テストの設定）を読み、どの compose ファイルのどのサービスを、どの工程（実装・再現・不具合の調査）で使うかを決めます。
  - compose ファイルはサブディレクトリや様々な名前も探し、テスト・開発の手順書やスキルから参照されるファイルも調べるよう指示します。
  - テストや動作確認に必要なサービスを選ばない場合は、そのサービスと理由を作業履歴に残すよう指示します。
  - タスクの開始時の情報収集が、テストと動作確認に要るサービスを分けてまとめていれば、それをもとにします。
  - 内容の調査では起動しません。
- 起動するもの：sacty が起動するのは、別で管理されている依存アプリ（対象のリポジトリのコードを動かさないもの）と、DB・キャッシュ・モックなどです。
  - 対象のリポジトリのコードを動かすアプリは、工程のエージェントが、エージェントのコンテナの中で起動して、サービスにつなぎます。
  - 分け方は、compose の `build` の有無ではなく、何を動かすかによります（対象のリポジトリの Dockerfile でビルドする DB も、依存の側です）。
- 起動と片付け：sacty は、工程のエージェントの実行の1回ごとに、別のプロジェクト名でサービスを起動します（`docker compose up --wait`）。
  - 終わったら、コンテナ・ネットワーク・ボリュームを消します。
    データは実行ごとに消えます。
  - 同じリポジトリのタスクを並行で動かしてもぶつかりません。
- 接続：エージェント（とエージェントが実行するテスト）は、サービス名とコンテナのポートで接続します（例 `db:5432`）。
  sacty は、`ports`（ホストのポート）と `container_name` を外して起動します。
- イメージ
  - ビルドしないサービス（`image` だけ）のイメージは、compose ファイルに書かれた名前のまま、ホストの Docker で取得します。
    組織のレジストリのイメージは、ホストで `docker login` しておいてください。
  - ビルドするサービス（`build`）は、書かれた `image` の名前を使わず、実行ごとの名前でビルドします（[使えない設定](#使えない設定)）。
- 残ったサービス：デーモンが途中で終わって残ったサービスは、次の起動のときに消します。
  - sacty は、起動したデーモンをコンテナのラベル `io.sacty.owner` に残します。
  - そのデーモンが動いているもの（同じ `SACTY_HOME` で動いているほかの sacty のもの）は消しません。

各工程には、サービスを起動しない場合も生成された `docker-services` スキルを渡します。
サービスの起動・接続ではこのスキルを先に読みます。
層の同名のスキルは使わず、`context.reservedSkill` の注意を出します。
工程の指示にも先に読むよう書きます。

スキルは docker のコマンドを使えず、sacty がサービスを起動・停止することを伝えます。
接続先は候補で、localhost の転送は予定です。
届かないときは別の候補を試し、すべて届かなければ何を確かめられなかったかを報告します。
サービスが起動していないときも、サービスが無いため確かめられなかったことを報告します。

## localhost への転送

リポジトリの設定の接続先が localhost のときは、サービスへの転送を試みます。
サービスを起動した実行では、sacty がエージェントのコンテナの中で、`127.0.0.1:<ポート>`（と、使えれば `[::1]:<ポート>`）をサービスの同じポート（`<サービス名>:<ポート>`）に転送するためです。

例えば、db のサービスにつなぐときは、次のようになります。

![localhost の転送](images/compose-forwarding.svg)

転送は、コマンドの前に sacty がコンテナの中で起動する、小さな TCP の転送のプログラムが行います。
イメージにある Node.js で動くので、追加のパッケージは要りません。
転送はコマンドが終わると止まり、コマンドの終了コードと出力は変わりません。
サービスを起動しない実行では、何も変わりません（コマンドも同じです）。

### 転送するポート

sacty が転送するのは、次のポートです。

- サービスのコンテナのポート（`ports` の右側・`expose`）
- `ports` でホストに出すポート（published）。
  ローカルの開発の設定は、ホスト側のポートを指していることが多いためです。

`ports: ["15432:5432"]` なら、`localhost:15432` と `localhost:5432` のどちらからも `db:5432` への転送を試みます。
sacty はホストのポートには出しません。
コンテナの中だけの転送です。

`ports` は、短い書き方と長い書き方の両方を読みます。

- 短い書き方：`"5432"`・`"15432:5432"`・`"127.0.0.1:15432:5432"`・範囲の `"8000-8001:8000-8001"`
- 長い書き方：`target`・`published`

published が無いもの・範囲の長さが合わないものは、コンテナのポートだけを転送します。

同じサービスの中で、ホストに出すポートがほかのコンテナのポートと同じ番号のとき（`ports: ["8080:80", "18080:8080"]`）は、ホストから見た番号の対応を優先します。
`localhost:8080` から `app:80` へ、`localhost:18080` から `app:8080` への転送を試みます。

### localhost で届かないとき

次のポートは、転送しません。

- UDP など TCP 以外のポート（`ports` の `/udp`・`expose` の `"8125/udp"`）は転送せず、ぶつかりの判定にも入れません（同じ番号の TCP のポートは転送します）。
- 複数のサービスが localhost の同じ番号を使うとき（ホスト側・コンテナ側を問わない）は、その番号は転送しません。
  どれにつなぐか決められないためです。
  サービス名も候補として試してください。
  作業履歴のサービスの起動の記録と、エージェントへの指示に、その番号を出します。
- そのポートをコンテナの中のほかのものがすでに使っているときは、そのポートは転送せずに続けます（失敗にしません）。
  理由は、デーモンのログ（エージェントの実行の標準エラー出力）に出します。

転送には、次の制限があります。

- 転送は TCP だけです。
  MySQL のクライアントなど、ホストに `localhost` と書くと TCP ではなく UNIX ソケットで接続するものは届きません（`127.0.0.1` を試してください）。
- テストするアプリ自身がサービスと同じポートで待ち受けると、転送とぶつかって待ち受けられません。
  アプリのポートを変えるか、サービス名も候補として試してください。

## 使えない設定

使うサービスとその依存に次の設定があると、sacty はサービスを起動せずに、理由を示して止まります。
sacty は、compose ファイルを `docker compose config` で正規化してから確かめます。

- サービスの設定
  - `privileged`・`cap_add`・`devices`・`volumes_from`
  - ホストのネットワーク・PID など（`network_mode: host`・`pid: host` など）
  - `security_opt` の unconfined
  - Docker の API のソケットを渡す `use_api_socket`
  - ホストでコマンドを動かす `provider`
- ビルドの設定：`ssh`・`network: host`・`privileged`・`entitlements`・`cache_to`
- 作業領域の外を指すパス
  - 作業領域の外のパスのマウント（Docker のソケットを含む）
  - 作業領域の外の `build`・`env_file`・`label_file`・`secrets`・`include`・`extends` のファイル（これらのパスに変数は使えない）
- ネットワークとボリューム
  - external のネットワーク・ボリューム
  - bridge 以外のネットワークのドライバー
  - ボリュームのドライバーの指定

ビルドするサービス（`build`）の `image` と `build.tags` は、あっても止まりませんが、sacty は使いません。
毎回、その実行だけの名前でビルドします。
エージェントのイメージなど、ホストのイメージを書き換えないようにするためです。
ビルドしたイメージは、サービスを止めるときに消します。

## 共用の compose

テストに要る Cassandra・Redis などの compose ファイルが、チームで共用する別のリポジトリにあるときは、プロジェクトの設定の「共用の compose」に書きます。
複数書けます。
プロジェクトをエクスポートすると、共用の compose も含まれます。

欄には、次のものを書きます。

| 欄 | 内容 |
| --- | --- |
| 名前 | 英小文字・数字で始まる、英小文字・数字・`_`・`-` の40文字まで。プロジェクトの中で重ならない |
| リポジトリ | git の URL（`https://`・`ssh://`・`git@<ホスト>:<パス>` など）か、ローカルの絶対パス（相対パスは使えない） |
| ブランチ・タグ | 任意。無ければ既定のブランチ |
| compose ファイル | リポジトリの根からの相対パス（`/` や `-` で始まるもの・`..`・`$` を含むものは使えない） |
| 説明 | 任意（1000文字まで）。オーケストレーターの判断の手がかり |
| 使うリポジトリ | 任意。プロジェクトの対象のリポジトリか Org の URL を1行に1つ、最大50件 |

同じ URL は大文字・小文字の違いだけでは重複して指定できません。
Org の対象を指定すると、その配下のリポジトリに適用されます。
この欄を空にすると、説明を手がかりに使うかどうかを判断します。

### 取得の認証

リポジトリの取得に使う認証は、次のように決まります。

- HTTPS の GitHub は、対象のリポジトリ・コンテキストリポジトリと同じく、プロジェクトに選んだ `gh` のアカウントで取得します。
  そのホストのアカウントは、プロジェクトの設定の「GitHub アカウント」で選べます（[プロジェクトの設定](project-settings.md#github-アカウント)）。
- SSH・ローカルのパスは、ホストの git の認証を使います。
- URL にユーザー名・パスワード・トークンは書けません。

### 使うかどうかの判断

共用の compose を使うかどうかは、オーケストレーターがタスクごとに判断します。
設定しただけでは起動しません。

- オーケストレーターは、リポジトリ（テストの設定・README・AGENTS.md）と説明から要るかを判断し、要るときだけ名前で選びます。
- 対象のリポジトリの compose と複数の共用 compose を一緒に選べます。
- ひもづいたリポジトリでは原則使い、使わない理由を記録します。別のリポジトリにだけひもづいたものは候補になりません。
- 複数の compose は1つのネットワークで起動します。サービス名や別名が衝突すると、起動前に工程が止まります。
  `network_mode` を指定したサービスには、エージェントから届かないことがあります。
- 要らないタスクでは、取得も起動もしません。

使う・使わない理由と、どの共用の compose（リポジトリ・ref・ファイル）を使うかは、作業履歴（タスクの画面）に残ります。
説明に、起動するサービスや、どのテストに要るかを書くと、判断の手がかりになります。

### 取得と起動

オーケストレーターが選んだ共用の compose は、sacty が次のように取得して起動します。

- 工程の実行の前に、sacty がリポジトリを取得します。
  - リポジトリごとのキャッシュ（`$SACTY_HOME/cache/shared-compose`）を、実行のたびに ref の最新に更新します。
  - そのコミットの中身を実行ごとのディレクトリに書き出して起動し、終わったら消します。
    並行するタスクが、ほかのタスクの初期化スクリプトを書き換えないようにするためです。
- 起動のしかたと安全の確かめは、対象のリポジトリの compose と同じです（実行ごとのプロジェクト名・`up --wait` で healthcheck を待つ・ホストのポートは出さない。[起動のしかた](#起動のしかた)・[使えない設定](#使えない設定)）。
- マウントできるのは、取得したリポジトリの中だけです（compose ファイルからの相対のマウントは使えます）。
- sacty は、`container_name` を外して起動し、その名前を sacty のネットワークの別名にします。
  その名前でも、サービス名でも届き、ほかのタスクとはぶつかりません。

### 止まるとき

次のときは、sacty は、どの共用の compose の何が原因かを示して、工程を止めます。

- 取得できない
- compose ファイルが無い
- 安全の確かめ（[使えない設定](#使えない設定)）に引っかかる
- 起動できない
