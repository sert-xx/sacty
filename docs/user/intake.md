# Issue・PR・チケットの取り込み

sacty は、GitHub の Issue・PR や JIRA のチケットを定期的に取り込んで、タスクにします。
取り込みの設定は、すべてのプロジェクトに共通です。
画面の「Sacty の設定」（ユーザーメニュー）で決めます。

## 取り込みの間隔

取り込みは、「Issue の取り込み」「PR のレビューの取り込み」「チケットの取り込み」の種類ごとに、別々の間隔で動きます。
間隔は「Sacty の設定」の、それぞれの区画の「取り込みの間隔（秒）」で決めます。

- 60 以上の整数（秒）を書きます。
  空にすると 300 秒です。
  60 より短い値や整数でない値は保存できず、理由が画面に出ます。
- 変えた間隔は、デーモンを止めずに次の取り込みから効きます。
  デーモンを起動したときは、すべての種類をすぐに取り込みます。
- 「Sacty の設定」を保存したときの動きは次のとおりです。
  - On でラベルなどを設定している種類は、30 秒以内に取り込みます（間隔が過ぎるのを待ちません）。
    その後は、新しい間隔ごとに取り込みます。
  - Off の種類や、ラベルなどを設定していない種類は、保存しても取り込みません。
  - 保存したときにその種類を取り込んでいる途中なら、いまの取り込みが終わった後の確認（30 秒ごと）で、新しい取り込みが始まります。
    取り込みが長引くと、30 秒より遅れます。
  - 取り込みが止まっている種類の欄には、取り込みを始めたときの間隔が出ます。
- 1つの種類が失敗したり、GitHub のレート制限に当たったりしても、ほかの種類の取り込みは続きます。
- GitHub の検索は、同じドメイン・アカウントの対象を、プロジェクトをまたいで種類ごとに 30 個までまとめて行います。
  30 個を超えると、検索を分けます。
  そのため、対象が 30 個までなら、プロジェクトが増えても検索の数は増えません。
  どのプロジェクトのものかは、見つかった後に sacty が判定します。
- プロジェクトの画面の「今すぐ取り込む」で、すべての種類を間隔を待たずに取り込めます。
  プロジェクトの画面には、種類ごとの最後の取り込みと、取り込めなかった対象が、どの種類のものかとあわせて出ます（On にしていない種類は出ません）。
- `config.yaml` に取り込みの設定は要りません。
  JIRA のチケットも、`github:` を書かなくても取り込みます。
  以前の版の `github:`（`poll_interval_sec`）は、書いてあっても読みません。

## Issue

- sacty は、プロジェクトの対象の開いている Issue のうち、「Sacty の設定」の「Issue の取り込み」の「取り込むラベル」が付いたものを、タスクとして取り込みます。
  ラベルを設定していなければ取り込みません。
- PR は、取り込むラベルが付いていても取り込みません。
  PR は、次の「PR のレビュー」で取り込みます。
  PR の実装を任せたいときは、Issue にして取り込むか、画面からタスクを作ってください。
  すでに取り込んだ PR のタスクは、そのまま進みます。
- 「Issue を取り込む」で、ラベルを残したまま Off にできます。
- 使う GitHub のアカウントは、プロジェクトでそのホストに選んだものです（[プロジェクトの設定](project-settings.md#github-アカウント)）。

## PR のレビュー

PR は、レビューだけを任せる形で取り込みます（「Sacty の設定」の「PR のレビューの取り込み」）。

- 「自分にレビューが依頼された PR を取り込む」を On にすると、sacty は、個人としてレビューを依頼された PR を取り込みます。
  対象は、プロジェクトでそのホストに選んだ GitHub のアカウントへの依頼です（チームへの依頼は除きます）。
- 「PR のレビュー用のラベル」の付いた PR も取り込みます。
  「レビュー用のラベルの PR を取り込む」で Off にできます。
- レビュー用のラベルは、取り込むラベルと同じ名前にもできます（例：どちらも `sacty`。大文字・小文字だけが違う名前も同じとみなします）。
  同じ名前でも、そのラベルの Issue は通常のタスクとして、PR はレビューだけのタスクとして取り込みます。
  Issue をレビューとして、PR を通常のタスクとして取り込むことはありません。
- 取り込んだ PR では、sacty は工程をオーケストレーターに選ばせずにレビューだけを行い、PR にレビュー（コメント）として投稿します。
  実装や PR の作成はしません。
  `images` を設定していて、プロジェクトの対象でイメージを指定していないときは、レビューの工程のイメージだけをオーケストレーターが選びます。
  レビューで、対象のプロジェクトのテストなどの検証を実行するためです（[コンテナイメージ](images.md#どのイメージで動くか)）。
- エージェントは、PR の先頭のコミットのコードで依存関係を取得し、テスト・型チェックなどの検証を実行してからレビューします。再レビューでも、新しいコミットで実行し直します。
  実行できなかった検証（DB などのサービスや秘密情報が要るものなど）は、コマンドと理由を本文に書きます。
  - 検証では、PR のコード（依存関係のインストールのスクリプトやテスト）が、エージェントのコンテナで動きます。
    PR のコードは、エージェントと同じものに触れられます。
    - コンテナの中のエージェントの認証情報（AI のサービスのトークンなど）を読めます。
    - codex をサブスクリプションで使っているときは、コンテナの中の `auth.json` を書き換えられます。書き換えは、実行の後にホストの `auth_file` へ書き戻され、残ります。
    - 実行の間は、ゲートウェイを通して、プロジェクトで選んだ GitHub のアカウントでの読み取りと、エージェントに渡した MCP サーバーを使えます。
    - Bot の依存関係の更新の PR（`dependabot[bot]` など）でも、新しい版のインストールのスクリプトが動きます。
  - フォークからの PR や、作者を信頼できない PR には、レビューのラベルを付けたり、レビューを依頼したりしないでください。
    取り込みは、フォークや Bot の PR かどうかでは絞りません。ラベルを自動で付ける設定や、CODEOWNERS などによる自動のレビューの依頼があると、人が判断しないまま取り込まれることがあります。
    タスクの作成で「レビューだけ」を選ぶときも同じです。
- PR の説明に文書へのリンク（Git の外に書いた設計書など）があれば、エージェントは、それがレビューの対象か、背景として読むだけかを、PR のタイトル・説明・差分から判断します。
  - 対象と判断した文書もレビューします。
    指摘は PR の行に付けられないので、本文に、文書と節を添えて書きます。
  - 文書を読むには、その文書の置き場所を読める MCP サーバーなどを、エージェントの環境に用意してください。
  - 読めなかった文書は、本文の「レビューの範囲」に書きます。
- PR がマージ・クローズされたら、終わっていないレビューのタスクは中止します。
- 投稿するレビューの先頭には、PR の作者への @ メンションと判定（「修正が必要」「提案あり（マージは可）」「指摘なし」）が付きます。
  - PR の作者が Bot（`dependabot[bot]` など）のときは、@ メンションは付かず、判定だけが付きます。
  - 「Sacty の設定」の「レビューの投稿で、PR の作者ではなく自分にメンションする」を On にすると、作者の代わりに、プロジェクトで選んだ GitHub のアカウント（投稿する自分）に @ メンションします（既定は Off）。
    変わるのは本文の @ メンションの相手だけです。
    レビューはこれまでどおり PR に公開され、PR を購読している作者（ふつうは購読しています）には、GitHub の通常のレビューの通知が届くことがあります。
  - 指摘の頭には、マージの前に直すべきものは `[要修正]`、直すとよいものは `[提案]` が付きます。
  - sacty が付ける見出し・判定・頭は日本語です。
    指摘の文は、リポジトリの文章の決まりに合わせます（決まりが無ければ日本語です）。
- レビューしている間に PR に push されたときは、レビューしたコミットに対して投稿し、どのコミットのレビューかを本文に書きます。
- 新しいコミットが積まれたら、タスクの詳細の「再レビュー」で、最新のコミットをもう一度レビューして投稿します。
  - レビューの依頼で取り込んだ PR は、GitHub でレビューを再依頼（Re-request review）すると、Sacty が次の取り込みで見つけて、同じプロジェクトに新しいレビュータスクを作ります。
    完了した元タスクの状態・投稿・作業履歴・費用はそのまま残り、新タスクは新しい実行セッションでレビューします。
  - 再依頼 1 回につき新タスクは 1 つです。
    同じ依頼を繰り返し取り込んでも、再起動しても増えません。
    新タスクの完了後の再依頼は、さらに別タスクになります。
  - ラベルで取り込んだ PR と sacty が作った PR は、再依頼では再レビューしません（「再レビュー」を使ってください）。
  - 自動で再レビューするのは、レビューを投稿して完了した後の再依頼だけです。
    レビュー中の再依頼は次回分として予約されません。
    レビュー中に再依頼した場合は、完了後にもう一度再依頼するか、タスクの詳細の「再レビュー」を使ってください。
  - 再依頼を確かめられないときは、自動では始めず、取り込みの結果に理由を表示して次回に確かめ直します。
    「再レビュー」で手動でも始められます。
  - 画面の「再レビュー」は従来どおり、選んだタスクを再実行します。
  - 再レビューでは、前回の指摘ごとに、直っているか・まだかを書きます（前回の後の PR の作者の返答も読みます）。
- レビューに取り込むのは、開いている PR だけです。
- GitHub のレビュー再依頼で新タスクを作る場合を除き、同じ PR は二度取り込みません。
  すでにタスクがある PR（どのプロジェクトのタスクでも、中止したタスクでも）は、ラベルを付けても新しいタスクになりません。
- 以前の版で取り込んだ PR のタスクは、そのまま残ります。

## sacty が作った PR のレビュー

「PR のレビュー用のラベル」を設定していると、sacty は、自分が作る PR すべて（実装の PR と、要求要件・設計の PR）にそのラベルを付けます。
取り込むラベルは付けません。
実装の PR は、最終レビューの前にドラフトで作り、レビューへ進めるとき（ドラフトを外すとき）にラベルを付けます（[実装の PR と CI](tasks.md#実装の-pr-と-ci)）。

- リポジトリにそのラベルが無ければ、作ってから付けます。
  付けられなかった（権限など）ときも PR はそのままで、理由がタスクの作業履歴に出ます。
- ラベルを付けた PR は、次の取り込みで、作ったタスクとは別の「PR のレビューだけ」のタスクになります。
  レビューは PR に投稿されます。
  - 判定が「修正が必要」か「提案あり（マージは可）」なら、レビューは作ったタスクに PR の指摘として届きます。
    ゴールガーディアンが戻し先を判断して直します（繰り返しの費用は、タスクの予算で止まります）。
  - 「指摘なし」のレビューは届けず、差し戻しません（PR のマージを待ちます）。
- レビュー用のラベルを取り込むラベルと同じ名前にしていても、ラベルを付けた PR は「PR のレビューだけ」のタスクに1回だけなり、実装のタスクにはなりません。
  指摘は、同じように作ったタスクに届きます。
- ラベルを付けるのは1つの PR に1回です。
  直して PR を更新しても付け直さず、新しいレビューのタスクも作りません（もう一度レビューさせるときは、レビューのタスクの「再レビュー」を使ってください）。
  人が外したラベルも付け直しません。
- 「レビュー用のラベルの PR を取り込む」を Off にしていても、ラベルは付けます。
  Off の間は取り込まず、On に戻した時点でまだ開いている PR を取り込みます。
  取り込みは開いている PR だけを探すため、Off の間にマージ・クローズした PR は取り込まれません。

## JIRA のチケット

JIRA（Jira Cloud・Jira Server / Data Center）の接続先は、組織内 PF（`config.yaml` の `gateway.platforms`、またはコンテキストリポジトリの `platforms.yaml`）として書きます。
JIRA 専用の設定はありません（PF の書き方は [ゲートウェイ](gateway.md#組織内-pf-の-api)）。

```yaml
gateway:
  platforms:
    jira:                                     # Jira Server / Data Center（個人用アクセストークン）
      upstream: https://jira.example.com
      description: JIRA
      auth:
        header: Authorization
        prefix: "Bearer "
        secret: op://Work/Jira/token
      allow:
        - GET /rest/api/2/search              # 取り込み（デーモンがチケットを探す）
        - GET /rest/api/2/issue/**            # 情報収集がチケット・親・サブタスクを読む
        - POST /rest/api/2/issue/*/comment    # 調査の結果と PR の URL をコメントする
    jira-cloud:                               # Jira Cloud（メールアドレス:API トークン を base64 にした値）
      upstream: https://acme.atlassian.net
      description: JIRA Cloud
      auth:
        header: Authorization
        prefix: "Basic "
        secret: op://Work/JiraCloud/basic     # 値の作り方は下
      allow:
        - GET /rest/api/3/search/jql
        - GET /rest/api/2/issue/**
        - GET /rest/api/3/issue/**
        - POST /rest/api/2/issue/*/comment
```

Jira Cloud の値（`メールアドレス:API トークン` を base64 にしたもの）は、トークンをコマンドの引数や履歴に残さないよう、次のように作ります（bash・zsh）。
トークンは表示しない入力で受け取り、標準入力で `base64` に渡し、結果をクリップボードに置きます。
1Password の項目（上の例では `JiraCloud` の `basic`）に貼り付けたら、クリップボードを空にしてください。

```sh
printf 'API トークン: '; read -rs JIRA_TOKEN; echo
printf '%s' "me@example.com:$JIRA_TOKEN" | base64 | tr -d '\n' | pbcopy; unset JIRA_TOKEN
# 1Password に貼り付けた後
pbcopy < /dev/null
```

- プロジェクトの設定の「チケットの取り込み先」に、次の3つを書きます。
  1つのプロジェクトに複数書けます。
  - 接続先（上の名前）
  - 種類（Jira Cloud / Jira Server・Data Center）
  - JIRA のプロジェクトのキー（`PAY` など。英大文字で始まる英大文字・数字・`_`）
- `config.yaml` の PF の同じ接続先の同じキーは、1つのプロジェクトにだけ書けます。
  コンテキストリポジトリの `platforms.yaml` の PF はプロジェクトとあわせて識別するので、同じ名前・同じキーの取り込み先を、別のプロジェクト（別の接続先）に書けます。
- sacty は、「Sacty の設定」の「チケットの取り込み」の取り込むラベル（すべての取り込み先で共通）が付いた、終わっていないチケットをタスクにします。
  「チケットを取り込む」で Off にできます。
- デーモンはチケットのキーと要約だけを探します。
  タスクが始まると、情報収集のエージェントがゲートウェイ経由でチケット（親のストーリー・エピック、リンクしたチケット、コメントにある URL まで）を読み、集めた情報からプロジェクトの対象の中で作業するリポジトリを選び、タスクの題と概要を書きます（[タスクの開始時の情報収集](tasks.md#タスクの開始時の情報収集)）。
  選べなければタスクは止まります。
  タスクの画面でリポジトリを選んで再開できます。
- 調査の結果と PR の URL は、チケットにコメントします（チケットの状態は変えません）。
- `allow` に無い API は、デーモンも呼びません。
  JIRA ではない接続先を選んだときの動きは保証しません。

## タスクの並行実行

sacty は、「Sacty の設定」の「同時に実行するタスクの数」（1〜10。空なら 3）まで、実行待ちのタスクを古い順に同時に実行します。
増やすほど、マシンの負荷と AI の利用上限の消費が増えます。
