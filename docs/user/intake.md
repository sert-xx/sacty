# Issue・PR・チケットの取り込み

GitHub の Issue・PR や JIRA のチケットを、定期的に取り込んでタスクにします。取り込みの設定は、すべてのプロジェクトに共通の設定として、
画面の「Sacty の設定」（ユーザーメニュー）で決めます。

## 取り込みの間隔

取り込みは、「Issue の取り込み」「PR のレビューの取り込み」「チケットの取り込み」の種類ごとに、別々の間隔で動きます。
間隔は「Sacty の設定」の、それぞれの区画の「取り込みの間隔（秒）」で決めます。

- 60 以上の整数（秒）を書きます。空にすると 300 秒です。60 より短い値や整数でない値は保存できず、理由が画面に出ます。
- 変えた間隔は、デーモンを止めずに次の取り込みから効きます。デーモンを起動したときは、すべての種類をすぐに取り込みます。
- 「Sacty の設定」を保存すると、On でラベルなどを設定している種類は、30 秒以内に取り込みます（間隔が過ぎるのを待ちません）。
  その後は、新しい間隔ごとに取り込みます。Off の種類や、ラベルなどを設定していない種類は、保存しても取り込みません。
  保存したときにその種類を取り込んでいる途中なら、新しい取り込みは、いまの取り込みが終わった後の確認（30 秒ごと）で始まります
  （取り込みが長引くと、30 秒より遅れます）。取り込みが止まっている種類の欄には、
  取り込みを始めたときの間隔が出ます。
- 1つの種類が失敗したり、GitHub のレート制限に当たったりしても、ほかの種類の取り込みは続きます。
- GitHub の検索は、同じドメイン・アカウントの対象を、プロジェクトをまたいで種類ごとに 30 個までまとめて行います（30 個を超えると、
  検索を分けます）。そのため、対象が 30 個までなら、プロジェクトが増えても検索の数は増えません。どのプロジェクトのものかは、
  見つかった後に sacty が判定します。
- プロジェクトの画面の「今すぐ取り込む」で、すべての種類を間隔を待たずに取り込めます。プロジェクトの画面には、種類ごとの最後の取り込みと、
  取り込めなかった対象が、どの種類のものかとあわせて出ます（On にしていない種類は出ません）。
- `config.yaml` に取り込みの設定は要りません。JIRA のチケットも、`github:` を書かなくても取り込みます。以前の版の `github:`
  （`poll_interval_sec`）は、書いてあっても読みません。

## Issue

- 「Sacty の設定」の「Issue の取り込み」の「取り込むラベル」の付いた、プロジェクトの対象の開いている Issue を、タスクとして取り込みます。
  ラベルを設定していなければ取り込みません。
- PR は、取り込むラベルが付いていても取り込みません。PR は、次の「PR のレビュー」で取り込みます（PR の実装を任せたいときは、Issue にして
  取り込むか、画面からタスクを作ってください）。すでに取り込んだ PR のタスクは、そのまま進みます。
- 「Issue を取り込む」で、ラベルを残したまま Off にできます。
- 使う GitHub のアカウントは、プロジェクトでそのホストに選んだものです（[プロジェクトの設定](project-settings.md#github-アカウント)）。

## PR のレビュー

PR は、レビューだけを任せる形で取り込みます（「Sacty の設定」の「PR のレビューの取り込み」）。

- 「自分にレビューが依頼された PR を取り込む」を On にすると、プロジェクトでそのホストに選んだ GitHub のアカウントへの、個人としての
  レビューの依頼の PR を取り込みます（チームへの依頼は除きます）。
- 「PR のレビュー用のラベル」の付いた PR も取り込みます。「レビュー用のラベルの PR を取り込む」で Off にできます。
- レビュー用のラベルは、取り込むラベルと同じ名前にもできます（例：どちらも `sacty`。大文字・小文字だけが違う名前も同じとみなします）。
  同じ名前でも、そのラベルの Issue は通常のタスクとして、PR はレビューだけのタスクとして取り込みます。Issue をレビューとして、PR を
  通常のタスクとして取り込むことはありません。
- 取り込んだ PR は、オーケストレーターを使わずにレビューだけを行い、PR にレビュー（コメント）として投稿します。実装や PR の作成はしません。
- PR の説明に文書へのリンク（Git の外に書いた設計書など）があれば、レビューの対象か、背景として読むだけかを、PR のタイトル・説明・差分から判断します。
  対象と判断した文書もレビューし、指摘は（PR の行に付けられないので）本文に、文書と節を添えて書きます。
  文書を読むには、その文書の置き場所を読める MCP サーバーなどを、エージェントの環境に用意してください。読めなかった文書は、本文の「レビューの範囲」に書きます。
- PR がマージ・クローズされたら、終わっていないレビューのタスクは中止します。
- 投稿するレビューの先頭には、PR の作者への @ メンションと判定（「修正が必要」「提案あり（マージは可）」「指摘なし」）が付きます。
  PR の作者が Bot（`dependabot[bot]` など）のときは、@ メンションは付かず、判定だけが付きます。
  指摘の頭には、マージの前に直すべきものは `[要修正]`、直すとよいものは `[提案]` が付きます。
  sacty が付ける見出し・判定・頭は日本語です。指摘の文は、リポジトリの文章の決まりに合わせます（決まりが無ければ日本語です）。
- レビューしている間に PR に push されたときは、レビューしたコミットに対して投稿し、どのコミットのレビューかを本文に書きます。
- 新しいコミットが積まれたら、タスクの詳細の「再レビュー」で、最新のコミットをもう一度レビューして投稿します。
  レビューの依頼で取り込んだ PR は、GitHub でレビューを再依頼（Re-request review）すると、Sacty が次の取り込みで見つけて、同じプロジェクトに新しいレビュータスクを作ります。
  完了した元タスクの状態・投稿・作業履歴・費用はそのまま残り、新タスクは新しい実行セッションでレビューします。
  再依頼 1 回につき新タスクは 1 つです。同じ依頼を繰り返し取り込んでも、再起動しても増えません。新タスクの完了後の再依頼は、さらに別タスクになります。
  ラベルで取り込んだ PR と sacty が作った PR は、再依頼では再レビューしません（「再レビュー」を使ってください）。
  自動で再レビューするのは、レビューを投稿して完了した後の再依頼だけです。レビュー中の再依頼は次回分として予約されません。
  レビュー中に再依頼した場合は、完了後にもう一度再依頼するか、タスクの詳細の「再レビュー」を使ってください。
  再依頼を確かめられないときは、自動では始めず、取り込みの結果に理由を表示して次回に確かめ直します。「再レビュー」で手動でも始められます。
  画面の「再レビュー」は従来どおり、選んだタスクを再実行します。
  再レビューでは、前回の指摘ごとに、直っているか・まだかを書きます（前回の後の PR の作者の返答も読みます）。
- レビューに取り込むのは、開いている PR だけです。
- GitHub のレビュー再依頼で新タスクを作る場合を除き、同じ PR は二度取り込みません。すでにタスクがある PR（どのプロジェクトのタスクでも、中止したタスクでも）は、ラベルを付けても新しいタスクに
  なりません。
- 以前の版で取り込んだ PR のタスクは、そのまま残ります。

## sacty が作った PR のレビュー

「PR のレビュー用のラベル」を設定していると、sacty が作る PR すべて（実装の PR と、要求要件・設計の PR）に、そのラベルを付けます
（取り込むラベルは付けません）。

- リポジトリにそのラベルが無ければ作ってから付けます。付けられなかった（権限など）ときも PR はそのままで、理由がタスクの作業履歴に出ます。
- ラベルを付けた PR は、次の取り込みで、作ったタスクとは別の「PR のレビューだけ」のタスクになります。レビューは PR に投稿され、判定が「修正が必要」
  なら、作ったタスクに PR の指摘として届き、ゴールガーディアンが戻し先を判断して直します。「提案あり（マージは可）」と「指摘なし」の
  レビューは届けず、差し戻しません（PR のマージを待ちます）。
- レビュー用のラベルを取り込むラベルと同じ名前にしていても、ラベルを付けた PR は「PR のレビューだけ」のタスクに1回だけなり、実装の
  タスクにはなりません。指摘は、同じように作ったタスクに届きます。
- ラベルを付けるのは1つの PR に1回です。直して PR を更新しても付け直さず、新しいレビューのタスクも作りません（もう一度レビューさせるときは、
  レビューのタスクの「再レビュー」を使ってください）。人が外したラベルも付け直しません。
- 「レビュー用のラベルの PR を取り込む」を Off にしていても、ラベルは付けます。Off の間は取り込まず、On に戻した時点で
  まだ開いている PR を取り込みます（Off の間にマージ・クローズした PR は取り込まれません。取り込みは開いている PR だけを探すため）。

## JIRA のチケット

JIRA（Jira Cloud・Jira Server / Data Center）の接続先は、組織内 PF（`config.yaml` の `gateway.platforms`、またはコンテキストリポジトリの
`platforms.yaml`）として書きます。JIRA 専用の設定はありません（PF の書き方は [ゲートウェイ](gateway.md#組織内-pf-の-api)）。

```yaml
gateway:
  platforms:
    jira:                                     # Jira Server / Data Center（個人用アクセストークン）
      upstream: https://jira.example.com
      description: JIRA
      auth:
        header: Authorization
        prefix: "Bearer "
        secret: op://Work/Jira/token
      allow:
        - GET /rest/api/2/search              # 取り込み（デーモンがチケットを探す）
        - GET /rest/api/2/issue/**            # オーケストレーターがチケット・親・サブタスクを読む
        - POST /rest/api/2/issue/*/comment    # 調査の結果と PR の URL をコメントする
    jira-cloud:                               # Jira Cloud（メールアドレス:API トークン を base64 にした値）
      upstream: https://acme.atlassian.net
      description: JIRA Cloud
      auth:
        header: Authorization
        prefix: "Basic "
        secret: op://Work/JiraCloud/basic     # 値の作り方は下
      allow:
        - GET /rest/api/3/search/jql
        - GET /rest/api/2/issue/**
        - GET /rest/api/3/issue/**
        - POST /rest/api/2/issue/*/comment
```

Jira Cloud の値（`メールアドレス:API トークン` を base64 にしたもの）は、トークンをコマンドの引数や履歴に残さないよう、次のように作ります
（bash・zsh）。トークンは表示しない入力で受け取り、標準入力で `base64` に渡し、結果をクリップボードに置きます。1Password の項目
（上の例では `JiraCloud` の `basic`）に貼り付けたら、クリップボードを空にしてください。

```sh
printf 'API トークン: '; read -rs JIRA_TOKEN; echo
printf '%s' "me@example.com:$JIRA_TOKEN" | base64 | tr -d '\n' | pbcopy; unset JIRA_TOKEN
# 1Password に貼り付けた後
pbcopy < /dev/null
```

- プロジェクトの設定の「チケットの取り込み先」に、接続先（上の名前）・種類（Jira Cloud / Jira Server・Data Center）・JIRA のプロジェクトの
  キー（`PAY` など。英大文字で始まる英大文字・数字・`_`）を書きます。1つのプロジェクトに複数書けます。
- `config.yaml` の PF の同じ接続先の同じキーは、1つのプロジェクトにだけ書けます。コンテキストリポジトリの `platforms.yaml` の PF は
  プロジェクトとあわせて識別するので、同じ名前・同じキーの取り込み先を、別のプロジェクト（別の接続先）に書けます。
- 「Sacty の設定」の「チケットの取り込み」の取り込むラベル（すべての取り込み先で共通）が付いた、終わっていないチケットをタスクにします。
  「チケットを取り込む」で Off にできます。
- デーモンはチケットのキーと要約だけを探します。オーケストレーターがゲートウェイ経由でチケット（サブタスクなら親とほかのサブタスク）を
  読み、プロジェクトの対象から作業するリポジトリを選び、タスクの題と概要を書きます。選べなければタスクは止まり、タスクの画面で
  リポジトリを選んで再開できます。
- 調査の結果と PR の URL は、チケットにコメントします（チケットの状態は変えません）。
- `allow` に無い API は、デーモンも呼びません。JIRA ではない接続先を選んだときの動きは保証しません。

## タスクの並行実行

「Sacty の設定」の「同時に実行するタスクの数」（1〜10。空なら 3）まで、実行待ちのタスクを古い順に同時に実行します。
増やすほど、マシンの負荷と AI の利用上限の消費が増えます。
