# Issue・PR・チケットの取り込み

sacty は、GitHub の Issue・PR や JIRA のチケットを定期的に取り込んで、タスクにします。
取り込みの設定は、画面の「Sacty の設定」（ユーザーメニュー）で決めます。
すべてのプロジェクトに共通です（チケットの取り込み先だけは、プロジェクトごとに、プロジェクトの設定で決めます）。

このページでは、取り込みの種類ごとに、取り込むもの・設定の仕方・取り込んだ後の進み方・注意を説明します。

- [Issue](#issue)：取り込むラベルが付いた Issue を、タスクにします。
- [PR のレビュー](#pr-のレビュー)：レビューを依頼された PR と、レビュー用のラベルが付いた PR を、レビューだけのタスクにします。
- [sacty が作った PR のレビュー](#sacty-が作った-pr-のレビュー)：sacty が作る PR は、sacty が子タスクを作ってレビューします（ラベルの設定は要りません）。
- [JIRA のチケット](#jira-のチケット)：取り込むラベルが付いたチケットを、タスクにします。

取り込む間隔は [取り込みの間隔](#取り込みの間隔) を、同時に実行するタスクの数は [タスクの並行実行](#タスクの並行実行) を見てください。

## Issue

sacty は、プロジェクトの対象の開いている Issue のうち、取り込むラベルが付いたものを、タスクとして取り込みます。

取り込みは、次の手順で設定します。

1. 「Sacty の設定」の「Issue の取り込み」の区画で、「取り込むラベル」にラベルを書きます。
2. 保存します。

設定には、次の決まりがあります。

- ラベルを設定していなければ、取り込みません。
- 「Issue を取り込む」で、ラベルを残したまま Off にできます。
- 使う GitHub のアカウントは、プロジェクトでそのホストに選んだものです（[プロジェクトの設定](project-settings.md#github-アカウント)）。

取り込んだ Issue は、通常のタスクとして進みます（[タスクを進める](tasks.md)）。

PR は、取り込むラベルが付いていても取り込みません。

- PR は、[PR のレビュー](#pr-のレビュー) で取り込みます。
- PR の実装を任せたいときは、Issue にして取り込むか、画面からタスクを作ってください。
- 以前の版でこのラベルから取り込んだ PR のタスクは、そのまま進みます。

## PR のレビュー

sacty は、PR を、レビューだけを任せる形で取り込みます。
取り込んだ PR をレビューし、結果を PR にレビュー（コメント）として投稿します。
実装や PR の作成はしません。

この節では、次の順に説明します。

- 取り込むものと設定：[取り込む PR](#取り込む-pr)・[PR のレビューの取り込みを設定する](#pr-のレビューの取り込みを設定する)
- 取り込んだ後：[レビューの進み方](#レビューの進み方)・[投稿されるレビュー](#投稿されるレビュー)・[再レビュー](#再レビュー)・[レビューが止まったとき](#レビューが止まったとき)
- 注意：[信頼できない PR を取り込まない](#信頼できない-pr-を取り込まない)

### 取り込む PR

sacty は、開いている PR のうち、次のどちらかに当たるものを取り込みます。

- 個人としてレビューを依頼された PR
  - 対象は、プロジェクトでそのホストに選んだ GitHub のアカウントへの依頼です（チームへの依頼は除きます）。
- レビュー用のラベルが付いた PR

取り込みには、次の決まりがあります。

- 同じ PR は、二度取り込みません（GitHub のレビュー再依頼で新しいタスクを作る場合を除きます。[再レビュー](#再レビュー)）。
  すでにタスクがある PR（どのプロジェクトのタスクでも、中止したタスクでも）は、ラベルを付けても新しいタスクになりません。
- sacty が作った PR は、取り込みません（[sacty が作った PR のレビュー](#sacty-が作った-pr-のレビュー)）。
- 以前の版で取り込んだ PR のタスクは、そのまま残ります。

### PR のレビューの取り込みを設定する

レビューでは、PR のコードがエージェントのコンテナで動きます。
信頼できない PR を取り込まないようにしてください（[信頼できない PR を取り込まない](#信頼できない-pr-を取り込まない)）。

1. 「Sacty の設定」の「PR のレビューの取り込み」の区画で、取り込みたい PR に合わせて、次のどちらか、または両方を設定します。
   - レビューを依頼された PR を取り込むとき：「自分にレビューが依頼された PR を取り込む」を On にします。
   - レビュー用のラベルが付いた PR を取り込むとき：「PR のレビュー用のラベル」に、ラベルを書きます。
2. 保存します。

レビュー用のラベルには、次の決まりがあります。

- 「レビュー用のラベルの PR を取り込む」で、Off にできます。
- レビュー用のラベルは、取り込むラベルと同じ名前にもできます（例：どちらも `sacty`。大文字・小文字だけが違う名前も同じとみなします）。
  - 同じ名前でも、そのラベルの Issue は通常のタスクとして、PR はレビューだけのタスクとして取り込みます。
  - Issue をレビューとして、PR を通常のタスクとして取り込むことはありません。

同じ区画で、投稿するレビューの @ メンションの相手も変えられます（[投稿されるレビュー](#投稿されるレビュー)）。

### レビューの進み方

取り込んだ PR では、sacty は工程をオーケストレーターに選ばせずに、レビューだけを行います。
タスクは、次の順に進みます。

1. エージェントが、PR の先頭のコミットのコードで依存関係を取得し、テスト・型チェックなどの検証を実行します。
2. エージェントが、PR をレビューします。
3. sacty が、レビューを PR に投稿します（[投稿されるレビュー](#投稿されるレビュー)）。

`images` を設定していて、イメージが決まっていない（プロジェクトの対象・作成時・再実行で指定していない）ときは、タスクのイメージだけをオーケストレーターが選びます。
レビューで、対象のプロジェクトのテストなどの検証を実行するためです（[コンテナイメージ](images.md#どのイメージで動くか)）。

検証は、次のように実行します。

- 再レビューでも、新しいコミットで実行し直します。
- 実行できなかった検証（DB などのサービスや秘密情報が要るものなど）は、コマンドと理由をレビューの本文に書きます。
- PR の主な対象が文書（設計書・要求要件・ADR・利用者向けの文書）で、コードの変更が無いときは、変えた文書に効く検証だけを実行します。
  - 文書に効く検証は、文書のフォーマッター・markdown の lint・リンクの検査など、リポジトリにあるものです。
  - コードのテスト・ビルド・型チェックは実行しません。
  - 文書に効く検証が無ければ、検証は実行しません。
- 文書とコードの両方を変える PR（主な対象が文書でも、コードの変更があるもの）は、全部の検証を実行します。
- 検証では、PR のコードがエージェントのコンテナで動きます（[信頼できない PR を取り込まない](#信頼できない-pr-を取り込まない)）。

PR の説明に文書へのリンク（Git の外に書いた設計書など）があるときは、エージェントが、その文書がレビューの対象か、背景として読むだけかを判断します。
判断には、PR のタイトル・説明・差分を使います。

- 対象と判断した文書もレビューします。
  指摘は PR の行に付けられないので、レビューの本文に、文書と節を添えて書きます。
- 文書を読むには、その文書の置き場所を読める MCP サーバーなどを、エージェントの環境に用意してください。
- 読めなかった文書は、レビューの本文の「レビューの範囲」に書きます。

PR にすでにあるレビュー・コメントは、エージェントが読み、同じ問題は繰り返しません。

- 既存の指摘が未対応かは、コードと作者の返答で確かめます。
  スレッドを解決済みにしていないことだけでは、未対応としません。
- 確かめて未対応だったときだけ、総評に「既存の指摘に未対応のものがある」と添え、判定は「指摘なし」になりません。

レビューが終わる前に PR が変わったときは、次のように動きます。

- レビューしている間に PR に push されたときは、レビューしたコミットに対して投稿し、どのコミットのレビューかをレビューの本文に書きます。
- PR がマージ・クローズされたら、終わっていないレビューのタスクは中止します。

### 投稿されるレビュー

投稿するレビューの先頭には、PR の作者への @ メンションと判定（「修正が必要」「提案あり（マージは可）」「指摘なし」）が付きます。
指摘の頭には、マージの前に直すべきものは `[要修正]`、直すとよいものは `[提案]` が付きます。

@ メンションの相手は、次のように決まります。

- PR の作者が Bot（`dependabot[bot]` など）のときは、@ メンションは付かず、判定だけが付きます。
- 「Sacty の設定」の「レビューの投稿で、PR の作者ではなく自分にメンションする」を On にすると、作者の代わりに、プロジェクトで選んだ GitHub のアカウント（投稿する自分）に @ メンションします（既定は Off）。
  - 変わるのは、本文の @ メンションの相手だけです。
  - On にしても、レビューは PR に公開されます。
    PR を購読している作者（ふつうは購読しています）には、GitHub の通常のレビューの通知が届くことがあります。

見られなかった観点がある（たとえば、文書と実装の照らし合わせを終えられなかった）ときは、判定は「読み取れませんでした」になり、本文の最初に、見られなかった観点が書かれます。
ただし、見られた範囲に `[要修正]` の指摘がある（未対応と確かめた前回・ほかのレビュアーの要修正を含む）ときは、判定は「修正が必要」になります。

長い文書の一部を変えた PR では、変えた箇所と、その変更で正しさが変わりうる箇所だけを実装と照らし合わせます。
変えていない本文の全体は照らし合わせません。

レビューの本文には、総評の後に、観点をどう見たかが1行で書かれます。
観点ごとの担当に分けて見たときは観点の数が、担当を起動できずに1つずつ順に見たときはそのことが書かれます。

sacty が付ける見出し・判定・頭は、日本語です。
指摘の文は、リポジトリの文章の決まりに合わせます（決まりが無ければ日本語です）。

### 再レビュー

再レビューでは、PR の最新のコミットをもう一度レビューして、投稿します。
前回の指摘ごとに、直っているか・まだかを書きます（前回の後の PR の作者の返答も読みます）。

再レビューの始め方は、次の2つです。

- 画面から始める：新しいコミットが積まれたら、タスクの詳細の「再レビューして PR に投稿」を押します。
  sacty は、選んだタスクを再実行します。
- GitHub でレビューを再依頼（Re-request review）する：レビューの依頼で取り込んだ PR で使えます。
  sacty が次の取り込みで再依頼を見つけて、同じプロジェクトに新しいレビューのタスクを作ります。

GitHub での再依頼は、次のように扱います。

- 完了した元のタスクの状態・投稿・作業履歴・費用は、そのまま残ります。
  新しいタスクは、新しい実行セッションでレビューします。
- 再依頼 1 回につき、新しいタスクは 1 つです。
  同じ依頼を繰り返し取り込んでも、再起動しても増えません。
  新しいタスクの完了後の再依頼は、さらに別のタスクになります。
- 自動で再レビューするのは、レビューを投稿して完了した後の再依頼だけです。
  レビュー中の再依頼は、次回分として予約されません。
  レビュー中に再依頼した場合は、完了後にもう一度再依頼するか、タスクの詳細の「再レビューして PR に投稿」を使ってください。
- ラベルで取り込んだ PR と sacty が作った PR は、再依頼では再レビューしません（「再レビューして PR に投稿」を使ってください）。
- 再依頼を確かめられないときは、自動では始めず、取り込みの結果に理由を表示して、次回に確かめ直します。
  「再レビューして PR に投稿」で、手動でも始められます。

### レビューが止まったとき

レビューが止まったとき（エラー・AI の利用上限・認証エラー・予算の上限）は、sacty が、レビューを頼んだ PR にもコメントで知らせます。
コメントには、止まったこと・理由の要点・再開のしかた（タスクの画面へのリンク）が入ります。

再開するには、画面でそのタスクを開いて「再開する」を押します。

- sacty は、止まった処理から続けます（レビューの実行で止まっていれば実行し直し、投稿で止まっていれば書いたレビューを投稿し直します）。
- 再開してレビューを投稿すると、止まったことのコメントは「解消済み」に書き換わります。

sacty は、PR へのコメントを、次のように書きます。

- 同じ理由で止まっても、同じ PR に何度もは書きません。
  違う理由で止まったときは、別のコメントを書きます。
- あなたが一時停止したときは書きません。
- PR に書けなかったときも、タスクは止まったままです（画面と Slack の通知は、これとは別に届きます）。

一時的な失敗は、失敗の種類によって扱いが違います。

- GitHub への問い合わせ（レビューの対象の PR の確認・レビューの投稿）が、GitHub 側のエラー・レート制限・ネットワークの失敗で一時的に失敗したときは、止めずに、間を置いて自動でやり直します（15 秒・1 分・3 分・5 分の最大 4 回）。
  - やり直している間は、PR にコメントを書きません。
    やり直しても続けて失敗したときに、止まって、PR にコメントを書きます。
  - やり直したことは、タスクの作業履歴に出ます。
  - 権限がない・PR が見つからないなど、待っても変わらない失敗は、すぐ止まります。
- モデルの混雑のような、エージェントの実行の一時的な失敗は、自動ではやり直しません。
  代わりのエージェントを書いておくと、止めずに切り替えます（[失敗したときの切り替え](config.md#失敗したときの切り替え)）。

### 信頼できない PR を取り込まない

レビューの検証では、PR のコード（依存関係のインストールのスクリプトやテスト）が、エージェントのコンテナで動きます。
フォークからの PR や、作者を信頼できない PR には、レビューのラベルを付けたり、レビューを依頼したりしないでください。
タスクの作成で「レビューだけ」を選ぶときも同じです。

PR のコードは、エージェントと同じものに触れられます。

- コンテナの中のエージェントの認証情報（AI のサービスのトークンなど）を読めます。
- codex をサブスクリプションで使っているときは、コンテナの中の `auth.json` を書き換えられます。
  書き換えは、実行の後にホストの `auth_file` へ書き戻され、残ります。
- 実行の間は、ゲートウェイを通して、プロジェクトで選んだ GitHub のアカウントでの読み取りと、エージェントに渡した MCP サーバーを使えます。
- Bot の依存関係の更新の PR（`dependabot[bot]` など）でも、新しい版のインストールのスクリプトが動きます。

取り込みは、フォークや Bot の PR かどうかでは絞りません。
ラベルを自動で付ける設定や、CODEOWNERS などによる自動のレビューの依頼があると、人が判断しないまま取り込まれることがあります。

## sacty が作った PR のレビュー

sacty は、自分が作る PR（要求要件・設計の PR と実装の PR）ごとに、その PR をレビューする子タスクを作ります。
ラベルの設定は要りません。
sacty は、PR にラベルも付けません。

sacty が作った PR は、レビュー用のラベルを付けても、レビューを依頼しても、取り込みません（子タスクがレビューするため）。
以前の版で sacty がラベルを付けた PR も同じです。

この節では、次の順に説明します。

- 子タスク：[レビューの子タスク](#レビューの子タスク)・[子タスクが中止になるとき](#子タスクが中止になるとき)
- レビューの指摘：[指摘が元のタスクに届く流れ](#指摘が元のタスクに届く流れ)・[AI のレビューの指摘の扱い](#ai-のレビューの指摘の扱い)
- 注意：[承認・マージの前に確かめること](#承認マージの前に確かめること)

### レビューの子タスク

sacty は、子タスクを、1つの PR に1つ作ります。

- 実装の PR は、sacty がドラフトで作り、作った直後に子タスクを作ります。
  子タスクが「指摘なし」にしたら、sacty がドラフトを外します（[実装の PR のレビュー](tasks.md#実装の-pr-のレビュー)）。
- 依存先の PR に重ねた実装の PR は、依存先がマージされて向き先が付け替わったときに、子タスクを作ります。
- PR を更新しても、新しい子タスクは作りません。
- PR を作り直した（新しい番号の PR になった）ときは、新しい PR に子タスクを作ります。

子タスクは、画面に次のように出ます。

- 子タスクは「PR のレビューだけ」のタスクで、題は「[PR #番号] 元のタスクの題」です（画面の言語に関わらず同じです）。
- タスクの詳細の「関連するタスク」に、互いへのリンクが出ます。
  元のタスクでは「PR のレビュー」、子タスクでは「レビューする PR の元」として出ます。
- 元のタスクのリンクには、子タスクの状態（実行待ち・中止など）も添えます（PR を開き直して子タスクが複数あるときに区別できます）。
- 費用は、子タスクの予算に数えます。

### 子タスクが中止になるとき

子タスクは、次のときに中止になります。

- 子タスクが終わる前に、PR をマージ・クローズしたとき
- 元のタスクを中止したとき

クローズした PR を開き直すと、sacty は新しい子タスクを作ってレビューし直します（あなたが中止した子タスクは作り直しません）。

### 指摘が元のタスクに届く流れ

子タスクのレビューの指摘は、次の流れで元のタスクに届きます。

1. sacty が、子タスクのレビューを PR に投稿します。
2. 判定が「修正が必要」か「提案あり（マージは可）」なら、レビューは、元のタスクに PR の指摘として届きます。
   元のタスクは、子タスクが指摘ごとに示した戻し先で直します（[PR での承認](tasks.md#pr-での承認要求要件設計実装)）。
3. 元のタスクが直して PR を更新し、承認待ちに戻ると、子タスクが最新のコミットをもう一度レビューします。
4. 2 と 3 を、「指摘なし」になるまで繰り返します（回数の上限はなく、繰り返しの費用はそれぞれのタスクの予算で止まります）。
   「指摘なし」のレビューは届けず、差し戻しません（PR のマージを待ちます）。

### AI のレビューの指摘の扱い

sacty は、子タスクのレビューの指摘を「AI のレビューの指摘」として、あなたが書いた指摘と区別します。
レビューは、あなたと同じ GitHub のアカウントで投稿されますが、sacty は、投稿に入れた目印（`sacty-review:`）で見分けます。

- 作業履歴・承認の画面・ダッシュボード・監査で、「AI のレビュー」として分けて出します。
- AI のレビューの指摘だけの差し戻しは、あなたが差し戻した回数にも、同じ工程への差し戻しの上限（3回）にも数えません。
- エージェントには、あなたの指摘と分けて渡します。
  あなたの指摘にある「さっきの指摘」などは、あなたの指摘を指すものとして扱わせます。

### 承認・マージの前に確かめること

承認の画面とタスクの詳細には、AI のレビューについて、次の2つが出ます。

1つ目は、sacty が元のタスクに届けずに捨てた指摘です。

- レビューした時点より後に PR が更新されていたら（レビューが対象にしたコミットが PR の今の先頭と違うとき）、sacty は、そのレビューを届けずに捨てます。
  捨てたことと理由は、作業履歴に残ります。
- 捨てた指摘は、承認の画面とタスクの詳細に「取り込んでいない AI のレビューの指摘」として出ます（理由・捨てた時点の PR のコミット・対象のコミット・指摘の要点・GitHub へのリンク）。
  PR をマージするまで出るので、承認・マージの前に確かめてください。
- 元のタスクが承認待ちに戻ると、子タスクが今の PR をレビューし直します。

2つ目は、承認待ちの PR の今のコミットに、sacty の AI のレビューが付いているか（付いていない・レビュー中・付いた）です。

- 作り直した後のコミットには、レビューが届くまで時間がかかります。
  レビューが付く前に承認・マージすると、その指摘を見ないまま進むことになります。
- sacty は、承認やマージを止めません。
- PR の本文の「結論」にも、本文を書いた時点の状況が1行入ります。
  その後に付いたレビューは反映されないので、最新の状況は承認の画面で確かめてください。

## JIRA のチケット

sacty は、JIRA（Jira Cloud・Jira Server / Data Center）のチケットのうち、取り込むラベルが付いた、終わっていないものをタスクにします。
取り込みは、次の順に設定します。

1. JIRA の接続先を、組織内 PF として書きます（[JIRA の接続先を書く](#jira-の接続先を書く)）。
2. プロジェクトの設定にチケットの取り込み先を書き、「Sacty の設定」で取り込むラベルを設定します（[チケットの取り込み先とラベルを設定する](#チケットの取り込み先とラベルを設定する)）。

取り込んだ後の進み方は、[チケットを取り込んだ後](#チケットを取り込んだ後) にあります。

### JIRA の接続先を書く

JIRA の接続先は、組織内 PF（`config.yaml` の `gateway.platforms`、またはコンテキストリポジトリの `platforms.yaml`）として書きます。
JIRA 専用の設定はありません（PF の書き方は [ゲートウェイ](gateway.md#組織内-pf-の-api)）。

```yaml
gateway:
  platforms:
    jira:                                     # Jira Server / Data Center（個人用アクセストークン）
      upstream: https://jira.example.com
      description: JIRA
      auth:
        header: Authorization
        prefix: "Bearer "
        secret: op://Work/Jira/token
      allow:
        - GET /rest/api/2/search              # 取り込み（デーモンがチケットを探す）
        - GET /rest/api/2/issue/**            # 情報収集がチケット・親・サブタスクを読む
        - POST /rest/api/2/issue/*/comment    # 調査の結果と PR の URL をコメントする
    jira-cloud:                               # Jira Cloud（メールアドレス:API トークン を base64 にした値）
      upstream: https://acme.atlassian.net
      description: JIRA Cloud
      auth:
        header: Authorization
        prefix: "Basic "
        secret: op://Work/JiraCloud/basic     # 値の作り方は下
      allow:
        - GET /rest/api/3/search/jql
        - GET /rest/api/2/issue/**
        - GET /rest/api/3/issue/**
        - POST /rest/api/2/issue/*/comment
```

- `allow` に無い API は、デーモンも呼びません。
- JIRA ではない接続先を選んだときの動きは、保証しません。

Jira Cloud の値（`メールアドレス:API トークン` を base64 にしたもの）は、トークンをコマンドの引数や履歴に残さないよう、次のように作ります（bash・zsh）。
トークンは表示しない入力で受け取り、標準入力で `base64` に渡し、結果をクリップボードに置きます。
1Password の項目（設定の例では `JiraCloud` の `basic`）に貼り付けたら、クリップボードを空にしてください。

```sh
printf 'API トークン: '; read -rs JIRA_TOKEN; echo
printf '%s' "me@example.com:$JIRA_TOKEN" | base64 | tr -d '\n' | pbcopy; unset JIRA_TOKEN
# 1Password に貼り付けた後
pbcopy < /dev/null
```

### チケットの取り込み先とラベルを設定する

1. プロジェクトの設定の「チケットの取り込み先」に、次の3つを書きます。
   - 接続先（組織内 PF として書いた名前）
   - 種類（Jira Cloud / Jira Server・Data Center）
   - JIRA のプロジェクトのキー（`PAY` など。英大文字で始まる英大文字・数字・`_`）
2. 「Sacty の設定」の「チケットの取り込み」の区画で、取り込むラベルを書いて、保存します。

取り込み先とラベルには、次の決まりがあります。

- 取り込み先は、1つのプロジェクトに複数書けます。
- `config.yaml` の PF の同じ接続先の同じキーは、1つのプロジェクトにだけ書けます。
  コンテキストリポジトリの `platforms.yaml` の PF はプロジェクトとあわせて識別するので、同じ名前・同じキーの取り込み先を、別のプロジェクト（別の接続先）に書けます。
- 取り込むラベルは、すべての取り込み先で共通です。
- 「チケットを取り込む」で、Off にできます。

### チケットを取り込んだ後

チケットの取り込みと、その後のタスクは、次のように進みます。

- デーモンは、チケットのキーと要約だけを探します。
- タスクが始まると、情報収集のエージェントが、ゲートウェイ経由でチケットを読みます（親のストーリー・エピック、リンクしたチケット、コメントにある URL まで）。
- 情報収集のエージェントは、集めた情報から、プロジェクトの対象の中で作業するリポジトリを選び、タスクの題と概要を書きます（[タスクの開始時の情報収集](tasks.md#タスクの開始時の情報収集)）。
  - リポジトリを選べなければ、タスクは止まります。
  - タスクの画面でリポジトリを選んで、再開できます。
- sacty は、調査の結果と PR の URL を、チケットにコメントします（チケットの状態は変えません）。

## 取り込みの間隔

取り込みは、「Issue の取り込み」「PR のレビューの取り込み」「チケットの取り込み」の種類ごとに、別々の間隔で動きます。
間隔は、「Sacty の設定」の、それぞれの区画の「取り込みの間隔（秒）」で決めます。

- 60 以上の整数（秒）を書きます。
  空にすると 300 秒です。
  60 より短い値や整数でない値は保存できず、理由が画面に出ます。
- 変えた間隔は、デーモンを止めずに、次の取り込みから効きます。
- 取り込みが止まっている種類の欄には、取り込みを始めると何秒ごとになるかが出ます。
- 1つの種類が失敗したり、GitHub のレート制限に当たったりしても、ほかの種類の取り込みは続きます。

sacty は、次のときには、間隔が過ぎるのを待たずに取り込みます。

- デーモンを起動したとき：すべての種類を、すぐに取り込みます。
- プロジェクトの画面の「今すぐ取り込む」を押したとき：すべての種類を取り込みます。
- 「Sacty の設定」を保存したとき：On でラベルなどを設定している種類を、30 秒以内に取り込みます。
  - その後は、新しい間隔ごとに取り込みます。
  - Off の種類や、ラベルなどを設定していない種類は、保存しても取り込みません。
  - 保存したときにその種類を取り込んでいる途中なら、いまの取り込みが終わった後の確認（30 秒ごと）で、新しい取り込みが始まります。
    取り込みが長引くと、30 秒より遅れます。

プロジェクトの画面には、種類ごとの最後の取り込みと、取り込めなかった対象が、どの種類のものかとあわせて出ます（On にしていない種類は出ません）。

GitHub の検索の数は、対象が 30 個までなら、プロジェクトが増えても増えません。

- sacty は、同じドメイン・アカウントの対象を、プロジェクトをまたいで種類ごとに 30 個までまとめて検索します。
  30 個を超えると、検索を分けます。
- どのプロジェクトのものかは、見つかった後に sacty が判定します。

`config.yaml` に、取り込みの設定は要りません。
JIRA のチケットも、`github:` を書かなくても取り込みます。
以前の版の `github:`（`poll_interval_sec`）は、書いてあっても読みません。

## タスクの並行実行

sacty は、「Sacty の設定」の「同時に実行するタスクの数」（1〜10。空なら 3）まで、実行待ちのタスクを古い順に同時に実行します。
増やすほど、マシンの負荷と AI の利用上限の消費が増えます。
