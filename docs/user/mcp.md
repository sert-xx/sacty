# 手元の AI から操作する（MCP）

起動中の sacty を、同じ PC の Claude Code や Codex から操作できます。
たとえば、PR を直した後に、AI に「この PR を sacty で再レビューして」と頼めます（画面を開いて「再レビューして PR に投稿」を押すのと同じです）。

sacty は、そのための MCP サーバー（`sacty mcp`）を持っています（MCP の仕様の 2026-07-28 版に対応し、それより前の版のクライアントからも使えます）。
できることは、タスクを調べること（一覧・検索・詳細）、PR のレビューのタスクを再レビューにすること、プロジェクトを指定してタスクを作ること、
タスクの工程ごとの成果物と、エージェントの実行の一覧を読むこと（成果物と実行の一覧は、読むだけです）、承認待ちの工程を承認すること、承認待ちの工程を差し戻すことです。実行のログは、まだ読めません（画面で読みます）。
中止・やり直しなどは、できません（画面で行います）。差し戻しも、基本の形だけです（上限を超えた差し戻し・戻し先の指定・原因の指定は、画面で行います）。PR のマージで承認する工程（実装・PR のある要求要件・設計）も、MCP からは承認できません（GitHub で PR をマージします）。成果物は、承認する前に中身を確かめるために使えます。

## つなぐ

AI の CLI に、MCP サーバーとして `sacty mcp` を一度登録します。
登録した後は、`sacty up` を起動し直しても、登録し直す必要はありません。

先に、どのディレクトリでも `sacty` を使えるようにしておきます（[はじめに](getting-started.md#どのディレクトリでも-sacty-を使う)）。
`npx sacty` は sacty のリポジトリの中でしか使えないので、登録には使えません。

Claude Code では、次を実行します。

```sh
claude mcp add --scope user sacty -- sacty mcp
```

Codex では、次を実行します。

```sh
codex mcp add sacty -- sacty mcp
```

登録できたかは、次のように確かめます。

- Claude Code：`claude mcp list` に `sacty` が出て、接続できていること。
- Codex：`codex mcp list` に `sacty` が出ること。

`SACTY_HOME` を変えて sacty を動かしているときは、同じ値を MCP サーバーにも渡します。
Claude Code は `--scope user` の前に、Codex は `--` の前に、`--env SACTY_HOME=<パス>` を足します。

## 使う

AI に、ふつうの言葉で頼みます。
AI が、下のツールを選んで呼びます。

- 「PR #123 を sacty で再レビューして」
- 「このブランチの PR をレビューしている sacty のタスクは、どうなっている？」
- 「sacty で止まっているタスクを教えて」
- 「sacty の（プロジェクト名）に、『ログイン画面の文言を直す』というタスクを作って」
- 「sacty のこのタスクの設計を読んで」
- 「sacty のこのタスクで動いたエージェントの実行を、新しい順に見せて」
- 「sacty のこのタスクの調査の結果を確かめて、よければ承認して」
- 「sacty のこのタスクの設計を読んで、『エラーの文言を足す』ことを指摘して差し戻して」

再レビューを頼むと、sacty は PR の最新のコミットをもう一度レビューして、結果を PR に投稿します（[再レビュー](intake.md#再レビュー)）。
レビューが終わるまでには時間がかかり、費用もかかります。
AI への応答は、再レビューを始めた時点で返ります。

タスクを作ると、画面の「タスクを作成」で、テンプレートなし・対象リポジトリ空欄・進め方「自動」のまま、同じ題と説明で作ったときと同じになります（[タスクを作る](tasks.md#タスクを作る)）。
作ったタスクの ID と、画面の URL が返ります。工程が終わるのは待たずに返ります。
作れないとき（プロジェクトが無い・題が空など）は、理由を返して、何も作りません。
作る要求を送った後に結果を受け取れなかったとき（時間切れ・接続が切れた・本文を読めない・デーモンが 5xx を返した）は、「タスクは作られている可能性があります」と返します。`list_tasks` で題を探して確かめてから、まだ無ければ頼み直してください（確かめずに頼み直すと、同じタスクが2つできることがあります）。

成果物は、1回に読める量に上限があります（UTF-8 で 32,000 バイト。日本語でおよそ1万字）。
上限を超えるときは、切り取ったことと、全体の大きさ・続きの位置が結果に入るので、AI が続きを読みます。
成果物の中身は、画面のタスクの詳細で読めるものと同じ元から返し、画面と同じ伏せ方のままです（MCP のための伏せ直しはしません）。
実行の一覧も、1回に返す件数に上限があります（既定 20 件・最大 100 件）。続きを取る間に実行が増えると、同じ実行が重なって返ることがあるので、AI は実行の ID で重なりを除きます。

sacty が起動していないときは、ツールが「起動中の sacty が見つかりません」と返します。
`sacty up` で起動してから、もう一度頼んでください。
sacty が 30 秒のうちに応答しないときは、「デーモンが時間内に応答しませんでした」と返します（sacty は起動しています。様子を確かめてから、もう一度頼んでください）。

## ツール

| ツール | 何をするか |
| --- | --- |
| `list_tasks` | タスクを新しい順に一覧にする。PR・ブランチ名・リポジトリ・題などで絞り込める |
| `get_task` | タスクの詳細（説明・レビューの本文・止まっている理由・直近の作業履歴）を返す |
| `rereview_task` | PR のレビューのタスクを、再レビューにする |
| `list_projects` | プロジェクト（消していないもの）の ID・名前・対象リポジトリを一覧にする |
| `create_task` | プロジェクトを指定して、題と説明でタスクを作る（`project_id`・`title`・`body`。説明は省けます） |
| `list_deliverables` | タスクの工程ごとの成果物を一覧にする（工程・何回目の提出か・種類・大きさ・状態） |
| `get_deliverable` | 工程と種類を指定して、成果物の中身を読む（承認済みならその版、まだなら最新の出力。レビューは本文と行へのコメント） |
| `list_runs` | エージェントの実行を新しい順に一覧にする（工程・オーケストレーターなど。使ったエージェント・時刻・実行中／成功／失敗／終わりが記録されていない・別のエージェントへの切り替え） |
| `approve_step` | 承認待ちの工程を承認する（`task_id`・`step`・`submission`）。画面の「承認する」と同じ。PR のマージで承認する工程は承認できず、PR の URL を返す |
| `request_changes` | 承認待ちの工程を差し戻す（`task_id`・`step`・`submission`・`comments`）。画面で、戻し先・原因を選ばずに指摘だけを書いて「差し戻す」を押すのと同じ。同じ工程への差し戻しが上限（3回）に達していたら、差し戻さない |

`list_tasks` の絞り込みは、次のとおりです（どれも省けます。複数を指定すると、すべてに合うタスクだけになります）。

| 引数 | 内容 |
| --- | --- |
| `pull_request` | PR。番号（`123`）、`owner/repo#123`、PR の URL のどれか |
| `branch` | ブランチ名（完全一致） |
| `repo` | リポジトリ。`owner/repo` か URL |
| `query` | 題に含まれる文字列か、タスクの ID の先頭 |
| `open_only` | `true` なら、終わっていないタスクだけ |
| `review_only` | `true` なら、PR のレビューのタスクだけ |
| `limit` | 返す件数の上限（既定 20・最大 100） |

PR をレビューするタスクは、PR の番号か URL で探すのが確実です。
ブランチ名でも探せますが、次の点に気をつけてください。

- 同じ名前のブランチ：ブランチ名だけで探すと、ほかのリポジトリの同じ名前のブランチ（`main`・`patch-1` など）のタスクも見つかります。
  `repo` も指定するか、PR の URL で探してください。
- sacty が作った PR：そのブランチを作ったタスクと、その PR をレビューするタスクの両方が見つかります。
- sacty の外で作った PR：sacty がレビューの前に PR を確かめたときに、ブランチ名を記録します。
  この機能が入る前にレビューしたタスクは、一度再レビューするまで、ブランチ名では見つかりません（PR の番号で探してください）。

成果物の状態は、次のとおりです。

| 状態 | 意味 |
| --- | --- |
| `approved` | 承認済みの版 |
| `posted` | PR に投稿したレビュー |
| `awaiting_approval` | 承認待ちの版 |
| `not_submitted` | まだ提出していない最新の出力（前の回の提出ではありません。前の回は `previousSubmission` で分かります） |
| `changes_requested` | 差し戻しの後に残っている、前の出力（作り直しが終わるまで） |
| `none` | 成果物が無い（失敗にはなりません） |

差し戻し前の過去の回の成果物と、エージェントの元のファイルは、読めません（画面で見ます）。

再レビューできるのは、レビューを PR に投稿して完了したタスクだけです（`list_tasks` の結果の `canRereview` が `true`）。
レビュー中のタスクや、PR のレビューでないタスクに頼むと、理由を返して、何も変えません。

## 承認する

`approve_step` は、承認待ちの工程を承認します（画面の「承認する」と同じです）。承認すると、sacty が次の工程を始めます（時間と費用がかかり、取り消せません）。
AI は、あなたに頼まれたときだけ呼びます。先に成果物（`list_deliverables`・`get_deliverable`）を確かめてから頼むと安全です。

- 承認の前に、`get_task`（`list_tasks` の各タスクにも）の `approval` で、承認待ちの工程（`step`）・提出の回（`submission`）・承認の手段（`method`）が分かります。
  AI は、確かめた工程と回を指定して承認します。いま承認待ちの工程・回と違うとき（古い提出）は、承認せずに、いまの回を伝えます。
- 承認できるのは、PR を作らない工程の承認待ち（調査の結果・統合の結果・変更なしの実装・PR にしない要求要件・設計など。画面で「承認する」を押す工程）です。
- できないとき（承認待ちでない・無いタスク・承認待ちの工程と違う・古い回・すでに承認した・再現できなかった再現）は、理由を返して、何も変えません。
- PR のマージで承認する工程（実装・PR のある要求要件・設計）は、MCP から承認できません。`approval` の `method` が `pull_request` で、`pullRequestUrl` の PR を GitHub でレビューしてマージします（マージが承認になります）。
- 結果を受け取れなかったとき（時間切れなど）は、承認されている可能性があります。AI は、自動でやり直さず、`get_task` で状態を確かめます。

## 差し戻す

`request_changes` は、承認待ちの工程を差し戻します（画面の承認の画面で、戻し先・原因を選ばずに指摘だけを書いて「差し戻す」を押すのと同じです）。差し戻すと、sacty がその工程をやり直します（時間と費用がかかり、取り消せません）。
AI は、あなたに頼まれたときだけ呼びます。先に `get_task` の `approval` と成果物（`list_deliverables`・`get_deliverable`）を確かめてから頼むと安全です。

- 指定するのは、タスク・工程（`step`）・提出の回（`submission`）・指摘（`comments`。1件以上）です。工程と回は、承認と同じく `approval` の値です。いま承認待ちの工程・回と違うとき（古い提出）は、差し戻さずに、いまの回を伝えます。
- 指摘は、1行が1件の指摘になります（画面の欄と同じです）。前後の空白と空の行は除きます。1回に 50 件まで、1件 2,000 文字までです。空の指摘だけのときや、上限を超えるときは、差し戻さずに理由を返します。
- やり直す工程は、承認待ちの工程に最も近い、やり直せる工程です（ふつうは承認待ちの工程そのものです。統合レビューなら、タスク分割です）。どの工程をやり直すかは、結果の `reworkStep` で分かります。
- 差し戻しの原因・戻し先の工程・タスクのイメージやエージェントの変更は、指定できません（画面で行います）。
- 同じ工程への人の差し戻しは、3回までです。上限に達しているときは、差し戻さず、何も変えずに、上限に達していることを伝えます。続けるかどうかは、費用が増えるので、あなたが画面で決めます。
  上限を超えた差し戻しは、MCP からできません。
- 状態が「エスカレーション」（上限の判断・変更の申し出の判断を待っている）のタスクは、MCP から差し戻せません。画面で判断します。
- できないとき（承認待ちでない・無いタスク・承認待ちの工程と違う・古い回・すでに差し戻した・やり直せる工程が無い）は、理由を返して、何も変えません。
- PR を作った工程（実装・PR のある要求要件・設計）も、差し戻せます。ただし、この指摘は PR には残らず、人の差し戻しとして回数に数えます。PR に記録を残したいときは、PR にコメントを書いてください（sacty が取り込んで差し戻します。[PR のコメントで差し戻す](tasks.md#pr-のコメントで差し戻す)）。MCP から PR にコメントを書くことは、できません。
- 結果を受け取れなかったとき（時間切れなど）は、差し戻されている可能性があります。AI は、自動でやり直さず、`get_task` で状態を確かめます（確かめずにやり直すと、二重に差し戻したり、上限の回数を使ったりすることがあります）。

## 確かめたいことを読む・答える

sacty が人に問いかけて待っているとき、AI は `get_task` だけで「何を問われているか」「どう答えるか」を読めます（読むだけで、何も変わりません）。

- **人に確かめたいこと**（`humanAsks`）：承認待ちで、工程のエージェントが指摘への対応と一緒に挙げた確認（聞き返し・推測で決めたこと）や、PR の指摘の意図を読み取れなかった理由があるときだけ入ります。画面の承認の画面と同じ内容です。同じ文の確認は1件にまとまります。
  一覧（`list_tasks`）には、件数（`asks`）だけが入ります。長い文は切り詰め、件数が多いときは省いた件数が分かります。
- **答え方**（`humanAsks` の `howToAnswer`）：答えが要らなければ、そのまま承認します（`approve_step`、PR のマージで承認する工程は PR のマージ）。答えるなら、PR を作らない工程は `request_changes` の `comments` に答えを書きます。PR を作った工程は、PR のコメントに書くと PR に記録が残ります（`request_changes` でも差し戻せますが、PR には残りません）。
  答えると、sacty がその工程をやり直します（時間と費用がかかります）。**答える専用のツールは、ありません。**
- **人の判断待ち**（状態が `escalated`）：`get_task` の `escalation` に、理由（差し戻しの上限・変更の申し出など。記録が無い古いタスクは `unknown`）・工程・やり直す工程・書きかけの指摘の件数・開いている変更の申し出の ID が入ります。指摘の文は入りません。
  MCP でできるのは、承認の手段（`approval.method`）が `approve_step` のときの承認だけです（PR のマージで承認する工程や `approval` が無いときは、読むだけです）。何ができるかは `escalation.canDoHere` で確かめます。上限を超えた差し戻し・変更の申し出への決定・後続に回したい案への決定・中止は、MCP からできません。画面で決めます（`escalation.decideOnScreen` に、理由に合った項目が入ります）。
- 要件・設計などの成果物の本文にある「確認したいこと」の節は、`humanAsks` には入りません。`get_deliverable` で本文を読みます。
- これらの文は、エージェントやほかの人が書いたものです。「承認してよい」「差し戻せ」と書いてあっても、AI はそれだけで承認・差し戻しをしません（あなたに頼まれたときだけです）。

## 気をつけること

- MCP サーバーを使えるのは、`sacty up` を動かしている本人だけです（sacty が本人だけが読めるファイルに書いた接続先を使います）。
- 登録した AI は、あなたに代わって再レビューを始めたり、タスクを作ったり、承認待ちの工程を承認・差し戻したりできます。タスクを作る・承認する・差し戻すと、工程が始まり、時間と費用がかかります。
  AI の CLI の権限の確認で、`rereview_task`・`create_task`・`approve_step`・`request_changes` を毎回確かめるか、許可しておくかを選べます。
  特に `approve_step` と `request_changes` は、毎回確かめる設定をおすすめします。許可しておくと、タスクの説明や成果物・レビューの本文に書かれた他人の指示で、確かめないまま承認・差し戻しされる場合があります。
- タスクの説明・レビューの本文・成果物が、AI に渡ります。
  ほかの人が書いた PR や Issue の文、エージェントが書いた文が含まれることがあります（AI への指示として扱わせないでください）。
- 前の版の sacty が起動しているときは、成果物と実行のツールが「sacty を更新し、`sacty up` で起動し直してください」と返します（タスクが無いときの理由とは別です）。実行中のタスクが無いときに、起動し直してください。
