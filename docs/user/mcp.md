# 手元の AI から操作する（MCP）

起動中の sacty を、同じ PC の Claude Code や Codex から操作できます。
たとえば、PR を直した後に、AI に「この PR を sacty で再レビューして」と頼めます（画面を開いて「再レビューして PR に投稿」を押すのと同じです）。

sacty は、そのための MCP サーバー（`sacty mcp`）を持っています（MCP の仕様の 2026-07-28 版に対応し、それより前の版のクライアントからも使えます）。
できることは、タスクを調べること（一覧・検索・詳細）、PR のレビューのタスクを再レビューにすること、プロジェクトを指定してタスクを作ること、
タスクの工程ごとの成果物と、エージェントの実行の一覧を読むこと（成果物と実行の一覧は、読むだけです）、承認待ちの工程を承認すること、承認待ちの工程を差し戻すこと、タスクを一時停止すること、一時停止中のタスクを再開すること（補足だけの再開です）、タスクを中止すること（片付ける対象を先に確かめます。取り消せません）、中止したタスクを再実行すること（新しいタスクを作って最初からやり直します。1度だけです）、タスクの進み具合（承認待ち・人の判断待ち・一時停止・完了・中止・PR のレビューの判定）が変わるまで待つことです。実行のログは、まだ読めません（画面で読みます）。
題や説明を直しての再実行・リポジトリやイメージを変えての再実行・完了したタスクの続きの作成は、できません（画面で行います）。上限の引き上げ・テストの扱いの決定・子タスクの中止を認める判断・作業するリポジトリの選択が要る再開も、画面で行います。差し戻しも、基本の形だけです（上限を超えた差し戻し・戻し先の指定・原因の指定は、画面で行います）。PR のマージで承認する工程（実装・PR のある要求要件・設計）も、MCP からは承認できません（GitHub で PR をマージします）。成果物は、承認する前に中身を確かめるために使えます。

## つなぐ

AI の CLI に、MCP サーバーとして `sacty mcp` を一度登録します。
登録した後は、`sacty up` を起動し直しても、登録し直す必要はありません。

先に、どのディレクトリでも `sacty` を使えるようにしておきます（[はじめに](getting-started.md#どのディレクトリでも-sacty-を使う)）。
`npx sacty` は sacty のリポジトリの中でしか使えないので、登録には使えません。

Claude Code では、次を実行します。

```sh
claude mcp add --scope user sacty -- sacty mcp
```

Codex では、次を実行します。

```sh
codex mcp add sacty -- sacty mcp
```

登録できたかは、次のように確かめます。

- Claude Code：`claude mcp list` に `sacty` が出て、接続できていること。
- Codex：`codex mcp list` に `sacty` が出ること。

`SACTY_HOME` を変えて sacty を動かしているときは、同じ値を MCP サーバーにも渡します。
Claude Code は `--scope user` の前に、Codex は `--` の前に、`--env SACTY_HOME=<パス>` を足します。

## 使う

AI に、ふつうの言葉で頼みます。
AI が、下のツールを選んで呼びます。

- 「PR #123 を sacty で再レビューして」
- 「このブランチの PR をレビューしている sacty のタスクは、どうなっている？」
- 「sacty で止まっているタスクを教えて」
- 「sacty の（プロジェクト名）に、『ログイン画面の文言を直す』というタスクを作って」
- 「sacty のこのタスクの設計を読んで」
- 「sacty のこのタスクで動いたエージェントの実行を、新しい順に見せて」
- 「sacty のこのタスクの調査の結果を確かめて、よければ承認して」
- 「sacty のこのタスクの設計を読んで、『エラーの文言を足す』ことを指摘して差し戻して」
- 「sacty のこのタスクが、承認待ちになるか、PR のレビューの判定が出るまで待って、教えて」
- 「sacty のこのタスクを、一時停止して」
- 「sacty の一時停止しているこのタスクを、『名前は変えないで』と補足して再開して」

再レビューを頼むと、sacty は PR の最新のコミットをもう一度レビューして、結果を PR に投稿します（[再レビュー](intake.md#再レビュー)）。
レビューが終わるまでには時間がかかり、費用もかかります。
AI への応答は、再レビューを始めた時点で返ります。

タスクを作ると、画面の「タスクを作成」で、テンプレートなし・対象リポジトリ空欄・進め方「自動」のまま、同じ題と説明で作ったときと同じになります（[タスクを作る](tasks.md#タスクを作る)）。
作ったタスクの ID と、画面の URL が返ります。工程が終わるのは待たずに返ります。
作れないとき（プロジェクトが無い・題が空など）は、理由を返して、何も作りません。
作る要求を送った後に結果を受け取れなかったとき（時間切れ・接続が切れた・本文を読めない・デーモンが 5xx を返した）は、「タスクは作られている可能性があります」と返します。`list_tasks` で題を探して確かめてから、まだ無ければ頼み直してください（確かめずに頼み直すと、同じタスクが2つできることがあります）。

成果物は、1回に読める量に上限があります（UTF-8 で 32,000 バイト。日本語でおよそ1万字）。
上限を超えるときは、切り取ったことと、全体の大きさ・続きの位置が結果に入るので、AI が続きを読みます。
成果物の中身は、画面のタスクの詳細で読めるものと同じ元から返し、画面と同じ伏せ方のままです（MCP のための伏せ直しはしません）。
実行の一覧も、1回に返す件数に上限があります（既定 20 件・最大 100 件）。続きを取る間に実行が増えると、同じ実行が重なって返ることがあるので、AI は実行の ID で重なりを除きます。

sacty が起動していないときは、ツールが「起動中の sacty が見つかりません」と返します。
`sacty up` で起動してから、もう一度頼んでください。
sacty が 30 秒のうちに応答しないときは、「デーモンが時間内に応答しませんでした」と返します（sacty は起動しています。様子を確かめてから、もう一度頼んでください）。

## ツール

| ツール | 何をするか |
| --- | --- |
| `list_tasks` | タスクを新しい順に一覧にする。PR・ブランチ名・リポジトリ・題などで絞り込める。`needs_person` で、人の対応を待っているタスクだけを、待ち始めの古い順に出せる |
| `get_task` | タスクの詳細（説明・レビューの本文・止まっている理由・直近の作業履歴）を返す |
| `rereview_task` | PR のレビューのタスクを、再レビューにする |
| `list_projects` | プロジェクト（消していないもの）の ID・名前・対象リポジトリを一覧にする |
| `create_task` | プロジェクトを指定して、題と説明でタスクを作る（`project_id`・`title`・`body`。説明は省けます） |
| `list_deliverables` | タスクの工程ごとの成果物を一覧にする（工程・何回目の提出か・種類・大きさ・状態） |
| `get_deliverable` | 工程と種類を指定して、成果物の中身を読む（承認済みならその版、まだなら最新の出力。レビューは本文と行へのコメント） |
| `list_runs` | エージェントの実行を新しい順に一覧にする（工程・オーケストレーターなど。使ったエージェント・時刻・実行中／成功／失敗／終わりが記録されていない・別のエージェントへの切り替え） |
| `approve_step` | 承認待ちの工程を承認する（`task_id`・`step`・`submission`）。画面の「承認する」と同じ。PR のマージで承認する工程は承認できず、PR の URL を返す |
| `request_changes` | 承認待ちの工程を差し戻す（`task_id`・`step`・`submission`・`comments`）。画面で、戻し先・原因を選ばずに指摘だけを書いて「差し戻す」を押すのと同じ。同じ工程への差し戻しが上限（3回）に達していたら、差し戻さない |
| `wait_for_task` | 1つのタスクに「人の出番」（承認待ち・人の判断待ち・一時停止・完了・中止・PR のレビューの判定）が来るまで待つ（`task_id`・`timeout_seconds`・`cursor`）。読むだけで、何も変えない |
| `pause_task` | タスクを一時停止する（`task_id`）。画面の「一時停止」と同じ。実行待ち・実行中・承認待ち・検証中のタスクだけで、完了・中止したタスクなどは止めない |
| `resume_task` | 一時停止中のタスクを再開する（`task_id`・`note`。補足は省けます）。上限の引き上げ・テストの扱いの決定・子タスクの中止を認める判断・作業するリポジトリの選択が要る停止は再開せず、画面で決めることを返す |
| `get_cancel_plan` | タスクを中止したら何が起きるかを読む（`task_id`）。止める実行・閉じる PR・消すブランチ・作業領域とセッションの有無・残るものを返す。読むだけで、何も変えない |
| `cancel_task` | タスクを中止する（`task_id`・`close_pull_requests`・`delete_branches`）。画面の「中止」と同じ。**取り消せず、PR を閉じ、ブランチと作業領域を消す。** `get_cancel_plan` が返した PR・ブランチを渡し、一致したときだけ中止する |
| `rerun_task` | 中止したタスクを再実行する（`task_id`・`note`。補足は省けます）。画面の「再実行」を、既定値のまま補足だけ足して押すのと同じ。**新しいタスクを作って工程を始め、元のタスクは二度と再実行できなくなる** |

`list_tasks` の絞り込みは、次のとおりです（どれも省けます。複数を指定すると、すべてに合うタスクだけになります）。

| 引数 | 内容 |
| --- | --- |
| `pull_request` | PR。番号（`123`）、`owner/repo#123`、PR の URL のどれか |
| `branch` | ブランチ名（完全一致） |
| `repo` | リポジトリ。`owner/repo` か URL |
| `query` | 題に含まれる文字列か、タスクの ID の先頭 |
| `open_only` | `true` なら、終わっていないタスクだけ |
| `review_only` | `true` なら、PR のレビューのタスクだけ |
| `limit` | 返す件数の上限（既定 20・最大 100） |
| `offset` | 読み始める位置（既定 0）。結果の `nextOffset` を渡すと続きが返る |
| `needs_person` | `true` なら、人の出番のタスクだけ（下の「人の対応を待っているタスクを探す」） |
| `state` | 状態で絞る（1つ以上）。値は結果の `state` と同じ。知らない値は断られる |
| `project_id` | プロジェクトで絞る（`list_projects` の `id`）。無い・消したプロジェクトは断られる |

知らない引数（`status`・`project` など）は、無視されずに断られます（理由に引数の名前が入ります）。

PR をレビューするタスクは、PR の番号か URL で探すのが確実です。
ブランチ名でも探せますが、次の点に気をつけてください。

- 同じ名前のブランチ：ブランチ名だけで探すと、ほかのリポジトリの同じ名前のブランチ（`main`・`patch-1` など）のタスクも見つかります。
  `repo` も指定するか、PR の URL で探してください。
- sacty が作った PR：そのブランチを作ったタスクと、その PR をレビューするタスクの両方が見つかります。
- sacty の外で作った PR：sacty がレビューの前に PR を確かめたときに、ブランチ名を記録します。
  この機能が入る前にレビューしたタスクは、一度再レビューするまで、ブランチ名では見つかりません（PR の番号で探してください）。

## 人の対応を待っているタスクを探す

「sacty で人の対応を待っているタスクは？」と頼むと、AI は `list_tasks` を `needs_person: true` で呼びます。

- 条件は、画面のダッシュボードの「あなたの出番」と同じです。状態が承認待ち・エスカレーション・一時停止のタスクのうち、承認待ちで AI が PR の指摘の戻し先を判断している間のものを除きます。
- 画面のヘッダーのベルは、AI が判断中の承認待ちも数えるので、件数が違うことがあります。除いた件数は、結果の `excludedAiJudging` で分かります。
- 待ち始めの古い順（同じなら ID の順）に並び、各タスクに待ち始めた時刻（`waitingSince`）が入ります。`waitingSinceSource` が `dashboard` ならデーモンの集計の時刻、`updatedAt` なら記録が無いので `updatedAt` で補った値です。
- 件数が `limit` を超えるときは、結果の `nextOffset` を `offset` に渡すと続きが返ります。最後まで返すと `nextOffset` は入りません。
- 待ち始めの時刻を読めないときは、`updatedAt` に置き換えず、理由を返して失敗にします。
- 画面の状態の文と色・人が判断する場所へのリンク・PR の競合の案内は出ません。`state`・`approval`・`asks`・`pausedReason`・`url` を使ってください。
- 一覧は読むだけです。見つけたタスクの承認・差し戻し・再開などは、頼んだときだけ行います。

成果物の状態は、次のとおりです。

| 状態 | 意味 |
| --- | --- |
| `approved` | 承認済みの版 |
| `posted` | PR に投稿したレビュー |
| `awaiting_approval` | 承認待ちの版 |
| `not_submitted` | まだ提出していない最新の出力（前の回の提出ではありません。前の回は `previousSubmission` で分かります） |
| `changes_requested` | 差し戻しの後に残っている、前の出力（作り直しが終わるまで） |
| `none` | 成果物が無い（失敗にはなりません） |

差し戻し前の過去の回の成果物と、エージェントの元のファイルは、読めません（画面で見ます）。

再レビューできるのは、レビューを PR に投稿して完了したタスクだけです（`list_tasks` の結果の `canRereview` が `true`）。
レビュー中のタスクや、PR のレビューでないタスクに頼むと、理由を返して、何も変えません。

## 承認する

`approve_step` は、承認待ちの工程を承認します（画面の「承認する」と同じです）。承認すると、sacty が次の工程を始めます（時間と費用がかかり、取り消せません）。
AI は、あなたに頼まれたときだけ呼びます。先に成果物（`list_deliverables`・`get_deliverable`）を確かめてから頼むと安全です。

- 承認の前に、`get_task`（`list_tasks` の各タスクにも）の `approval` で、承認待ちの工程（`step`）・提出の回（`submission`）・承認の手段（`method`）が分かります。
  AI は、確かめた工程と回を指定して承認します。いま承認待ちの工程・回と違うとき（古い提出）は、承認せずに、いまの回を伝えます。
- 承認できるのは、PR を作らない工程の承認待ち（調査の結果・統合の結果・変更なしの実装・PR にしない要求要件・設計など。画面で「承認する」を押す工程）です。
- できないとき（承認待ちでない・無いタスク・承認待ちの工程と違う・古い回・すでに承認した・再現できなかった再現）は、理由を返して、何も変えません。
- PR のマージで承認する工程（実装・PR のある要求要件・設計）は、MCP から承認できません。`approval` の `method` が `pull_request` で、`pullRequestUrl` の PR を GitHub でレビューしてマージします（マージが承認になります）。
- 結果を受け取れなかったとき（時間切れなど）は、承認されている可能性があります。AI は、自動でやり直さず、`get_task` で状態を確かめます。

## 差し戻す

`request_changes` は、承認待ちの工程を差し戻します（画面の承認の画面で、戻し先・原因を選ばずに指摘だけを書いて「差し戻す」を押すのと同じです）。差し戻すと、sacty がその工程をやり直します（時間と費用がかかり、取り消せません）。
AI は、あなたに頼まれたときだけ呼びます。先に `get_task` の `approval` と成果物（`list_deliverables`・`get_deliverable`）を確かめてから頼むと安全です。

- 指定するのは、タスク・工程（`step`）・提出の回（`submission`）・指摘（`comments`。1件以上）です。工程と回は、承認と同じく `approval` の値です。いま承認待ちの工程・回と違うとき（古い提出）は、差し戻さずに、いまの回を伝えます。
- 指摘は、1行が1件の指摘になります（画面の欄と同じです）。前後の空白と空の行は除きます。1回に 50 件まで、1件 2,000 文字までです。空の指摘だけのときや、上限を超えるときは、差し戻さずに理由を返します。
- やり直す工程は、承認待ちの工程に最も近い、やり直せる工程です（ふつうは承認待ちの工程そのものです。統合レビューなら、タスク分割です）。どの工程をやり直すかは、結果の `reworkStep` で分かります。
- 差し戻しの原因・戻し先の工程・タスクのイメージやエージェントの変更は、指定できません（画面で行います）。
- 同じ工程への人の差し戻しは、3回までです。上限に達しているときは、差し戻さず、何も変えずに、上限に達していることを伝えます。続けるかどうかは、費用が増えるので、あなたが画面で決めます。
  上限を超えた差し戻しは、MCP からできません。
- 状態が「エスカレーション」（上限の判断・変更の申し出の判断を待っている）のタスクは、MCP から差し戻せません。画面で判断します。
- できないとき（承認待ちでない・無いタスク・承認待ちの工程と違う・古い回・すでに差し戻した・やり直せる工程が無い）は、理由を返して、何も変えません。
- PR を作った工程（実装・PR のある要求要件・設計）も、差し戻せます。ただし、この指摘は PR には残らず、人の差し戻しとして回数に数えます。PR に記録を残したいときは、PR にコメントを書いてください（sacty が取り込んで差し戻します。[PR のコメントで差し戻す](tasks.md#pr-のコメントで差し戻す)）。MCP から PR にコメントを書くことは、できません。
- 結果を受け取れなかったとき（時間切れなど）は、差し戻されている可能性があります。AI は、自動でやり直さず、`get_task` で状態を確かめます（確かめずにやり直すと、二重に差し戻したり、上限の回数を使ったりすることがあります）。

## 一時停止する

`pause_task` は、タスクを一時停止します（画面の「一時停止」と同じです）。AI は、あなたに頼まれたときだけ呼びます。

- 止められるのは、実行待ち・実行中・承認待ち・検証中のタスクです（画面で「一時停止」のボタンが出る状態と同じです。`get_task` の `canPause` が `true`）。
- 完了・中止したタスク、すでに一時停止中のタスク、人の判断待ち（エスカレーション）のタスク、ほかのタスクの完了待ち・子タスクの完了待ちのタスクは、止めずに理由を返して、何も変えません。
- 実行中の実行は打ち切られ、再開するとその工程を最初からやり直します（かけた費用は戻りません）。
- 承認待ちを止めると、再開するまで、承認ゲートと PR の見守りが止まります（止めている間は、承認も差し戻しもできません）。
- 止める前に作業が終わって承認待ちなどになったときは、止めずに、そのことを伝えます。
- 実行中のタスクを止めるときは、sacty がコンテナを止めて処理の終わりを待つので、時間がかかることがあります。30 秒のうちに応答が無くても、あとで一時停止になる（または承認待ちに達して止まらない）ことがあります。このとき AI は、「一時停止されている可能性があります」と返し、自動でやり直さず、`get_task` で状態を確かめます。`state` が一時停止の前と同じ（`running`・`queued`・検証中の `idle`）なら、一時停止が続いている可能性があるので、呼び直さずに `wait_for_task` で待ちます。`paused` なら止まっています。`awaiting_approval`・`escalated` になったときは、止まらなかったので、あなたに伝えます。
- 中止は、`cancel_task` でできます（[中止する](#中止する)）。「止めて」と頼んだときは、中止ではなく一時停止です。

## 再開する

`resume_task` は、一時停止中のタスクを再開します（画面の「再開」を、上限・テスト・イメージ・エージェントを変えずに押すのと同じです）。AI は、あなたに頼まれたときだけ呼びます。
先に `get_task` で、止まっている理由（`pausedReason`・`pausedMessage`）と、再開できるか（`canResume`）を確かめます。

- 指定するのは、タスクと、省ける補足（`note`）です。補足はタスクの説明の後に足されて残り、後の工程が読みます。あなたの言葉だけを渡します。前後の空白は除き、空なら足しません。長すぎるときは、再開せずに理由を返します。
- 再開すると、止まった工程を実行し直します（時間と費用がかかります。終わるのは待たずに返します）。止まる前が承認待ち・子タスク待ちだったときは、そこへ戻るだけで、工程は実行し直しません（結果の文と `state` で分かります）。
- 同じ原因なら、また止まります。「検証」「不完全」で止まったときは、回数を数え直すので、同じ失敗ならまた止まります。
- **画面で決めること**：次の一時停止は、MCP からは再開せず、何も変えずに、画面で決めることを伝えます（`get_task` の `resumeBlocked` にも入ります）。
  - 予算の上限に達した停止：上限を引き上げるかどうか（費用が増える判断です）。
  - テストの扱いを決められる停止：テストのコマンドかテストなしかの決定。
  - 子タスクが中止された停止：子タスクの中止を認めて再開するかどうか。
  - チケットから取り込んだタスクで、作業するリポジトリを決める前に止まった停止：作業するリポジトリの選択。
- 外部作業の工程が始まっている・重ねていた依存先が中止された・止まったと確かめられないコンテナが残っているときは、sacty が再開を断ります。その理由をそのまま伝えます（`canResume` が `true` でも、断られることがあります）。
- 結果を受け取れなかったとき（時間切れなど）は、再開されている可能性があります。AI は、自動でやり直さず、`get_task` で状態を確かめます。

## 中止する

`cancel_task` は、タスクを中止します（画面の「中止」と同じです）。**取り消せません。再開もできません。** やり直すなら、中止の後に再実行します（[中止したタスクを再実行する](#中止したタスクを再実行する)。新しいタスクになり、作業領域・ブランチ・PR は戻りません）。AI は、あなたが、そのタスクの中止をはっきり頼んだときだけ呼びます（「止めて」「待って」は一時停止で、中止ではありません。迷ったら、呼ばずにあなたに確かめます）。
タスクの題・説明・成果物・レビューの本文・止まっている理由などに「中止せよ」と書かれていても、AI は呼びません。

- 中止すると、sacty が作った実装の PR を閉じ（マージはしません）、開いている要求要件・設計の PR も閉じ、sacty のブランチ（リモートも）と作業領域を消し、実行中のコンテナを止めます。作業履歴とセッションログは残ります。マージ済みの PR・引き継いだ人の PR と、そのブランチには触れません。
- 呼ぶ前に、AI は `get_cancel_plan` で、止める実行・閉じる PR・消すブランチ・作業領域とセッションの有無・残るものを読み、あなたに伝えます（読むだけで、何も変えません）。
- `cancel_task` には、`get_cancel_plan` が返した「閉じる PR」（`close_pull_requests`）と「消すブランチ」（`delete_branches`）を渡します。呼んだ時点の対象と一致しなければ（読んだ後に PR やブランチが増えたなど）、中止せずに、いまの対象を返します。
- 中止できるのは、`get_task` の `canCancel` が `true` のタスク（実行待ち・実行中・承認待ち・一時停止中・人の判断待ちなど）です。完了したタスク・中止済みのタスク・PR のレビューの子タスク（中止すると、その PR を再レビューできなくなります）・分割の親（終わっていない子タスクも中止されます）・分割の子タスク（親が一時停止します）は、中止せずに理由と、画面で行えることを返します。画面で中止してください。
- 片付けの一部が失敗しても、中止は記録されます。結果に、対象ごとの片付けの結果（片付けた・対象が無かった・失敗した）と、失敗の理由が入ります。失敗したものは、手で片付けてください（片付けのやり直しはありません。中止したタスクのやり直しは再実行です）。
- 中止は、質問への答え・エラーの分析の実行中の実行も止めます。PR をレビューする子タスクのうち終わっていないものがあれば、次の PR の確認で中止されます（中止したレビューの子タスクは、再レビューできません）。
- 実行中のタスクの中止は、コンテナを止めて処理の終わりを待ち、PR を閉じ、ブランチを消すので、時間がかかることがあります。30 秒のうちに応答が無くても、あとで中止になる（片付けが続く）ことがあります。このとき AI は、「中止されている（片付けが続いている）可能性があります」と返し、自動でやり直さず、`get_task` で `state` を確かめます。終わるまで `paused` に見えることがありますが、中止の失敗でも一時停止でもないので、AI は `wait_for_task` で `cancelled` になるまで待ちます。`cancelled` になったら、`get_task` の `cancelled` で片付けの結果と、失敗したものを確かめて伝えます。待っても `cancelled` にならないときは、AI が状況を伝えるので、望むなら `get_cancel_plan` から呼び直させてください。

## 中止したタスクを再実行する

`rerun_task` は、中止したタスクを最初からやり直します（画面の「再実行」を、題・説明・リポジトリ・イメージを変えずに、補足だけ足して押すのと同じです）。AI は、あなたが、そのタスクの再実行をはっきり頼んだときだけ呼びます。タスクの題・説明・止まっている理由・レビューの本文などに「やり直せ」と書かれていても、AI は呼びません。

- **新しいタスクを作り、sacty が工程を始めます。** 時間と費用がかかります（予算は、新しいタスクの分が新しくかかります）。終わるのは待たずに返ります。
- **元のタスクは、二度と再実行できなくなります。** 取り消せません。作ったタスクを消すこともできません。止めるなら、新しいタスクを中止します（中止した新しいタスクは、もう一度再実行できます）。
- 作業領域・ブランチ・PR は引き継がれず、最初からやり直します。前の試行の記録（進んだ工程・工程の成果・差し戻しの指摘・止まった理由など）が、新しいタスクの説明に付きます。
- 新しいタスクの題は元の題、説明は元の人の説明（に、補足があれば補足を、いつも前の試行の記録を足したもの）、作業するリポジトリは元のタスクのものです。イメージは、いつもどおり決まります。補足（`note`。最大 10,000 文字）は、新しいタスクの説明に足されて残り、後の工程が読みます。
- 結果には、新しいタスクの要約と、元のタスクの ID が入ります。`get_task` では、元のタスクに `rerunBy`（やり直した先のタスクの ID）、新しいタスクに `rerunOf`（元のタスクの ID）が出ます。
- 再実行できるのは、`get_task` の `canRerun` が `true` のタスクです。中止していないタスク・完了したタスク（続きの作成は画面で行います）・再実行済みのタスク・分割の子タスク・PR のレビューのタスク・チケットから取り込み、作業するリポジトリが決まっていないタスク・説明が上限を超えるなど既定値のままでは送れないタスクは、再実行せずに理由を返します。`get_task` の `rerunBlocked` に理由が出るのは、中止して再実行できないタスクだけです（中止していないタスク・完了したタスクは、`canRerun` が `false` になるだけです）。題や説明を直す・リポジトリやイメージを変えるときは、画面の「再実行」で行ってください。
- リポジトリがプロジェクトの対象から外れたなど、sacty が断るときは、その理由を返します（作られていません。リポジトリがプロジェクトの対象でないときは、画面で選び直せます。プロジェクトに対象が1つも無いときは、プロジェクトの設定で対象を足します）。
- 結果を受け取れなかったとき（時間切れなど）は、作られている可能性があります。AI は、自動でやり直さず、元のタスクを `get_task` で読み、`rerunBy` を確かめます。あれば作られているので、そのタスクを見ます。無ければ作られていないので、呼び直してよいです（二重には作られません）。

## 状態が変わるまで待つ

`wait_for_task` は、1つのタスクに「人の出番」が来るまで待ちます（読むだけで、何も変えません）。
AI が `get_task` を繰り返さなくても、承認待ち・人の判断待ち・一時停止・完了・中止・PR のレビューの判定を待てます。

待ち方の例です。

1. **登録**：[つなぐ](#つなぐ)のとおり、`sacty mcp` を一度登録します。待つためだけの設定は、要りません。
2. **待つ**：AI に「このタスクが承認待ちになるまで待って」と頼みます。AI は、`wait_for_task` を `task_id` を指定して呼びます。
3. **起きたら読む**：変化があると、変わったこと（`changes`）・いまの要約・PR をレビューする子のタスクの状態が返ります。詳しい中身は、AI が `get_task`（子の本文は、子の `task_id` で `get_task`）で読みます。
   起きたからといって、AI は頼まれていない承認・差し戻しをしません（頼んだときだけです）。
4. **呼び直す**：変わらないまま時間切れになったときは、`changed` が `false` で返ります（失敗ではありません）。結果の `cursor` を渡して呼び直すと、続けて待てます。
   `cursor` を渡すと、前の結果の後に起きた変化があれば、待たずにすぐ返ります（取りこぼしません）。`cursor` を省くと、呼んだ時点が基準です。

- 起きる変化：承認待ちになった（別の工程・別の提出の回の承認待ちに変わったときも）・人の判断待ちになった・一時停止した（理由が変わったときも）・完了した・中止された・
  これらから動き出した・人に確かめたいことの件数が変わった・PR の状態が変わった（マージ・閉じた など）。
  PR をレビューする子のタスクの、増えた・人の出番の状態になった・レビューの回が変わった（再レビュー）・投稿された・判定が出た／変わったでも起きます。
  親が PR のマージ待ち（承認待ち）のままでも、子の判定だけで起きます。
- 起きない変化：工程が進んだ・実行が始まった／終わった・費用や作業履歴が増えた、だけでは起きません。前のタスクの完了待ち（`blocked`）・分割の子の完了待ち（`waiting_children`）も、人の出番ではないので起きません。分割の子の変化でも起きません。
- 待つ時間は、既定 30 秒・最大 50 秒です（`timeout_seconds`。超える値は 50 秒に収め、結果の `clamped` が `true` になります）。
  上限が短いのは、AI の CLI が 1 回のツールの呼び出しを 60 秒で打ち切ることがあるためです（Codex・MCP の公式の SDK のクライアントの既定）。
  AI の CLI の打ち切りの時間を延ばす設定は、要りません（長く待つときは、`cursor` を渡して呼び直します）。
- sacty は、5 秒おきに確かめます。デーモンが応答しなくても、指定した時間＋数秒（最大 55 秒）で返ります。
- 待っている途中で sacty に届かなくなったとき（止まった・つながらない）は、その理由が返ります。1回の失敗は、次の周期でやり直します。続けて失敗したときは、理由に `cursor` が添えられます。`sacty up` で起動しているかを確かめてから、その `cursor` を渡して呼び直します。
- 子のレビューは、1回に新しい方から 5 件まで確かめます（省いた数が `reviewTasksOmitted` で分かります）。子ごとに、状態・レビューの回・投稿の URL・判定が返ります（レビューの本文は入りません）。
- 結果の題・止まっている理由は、ほかの人が書いた文を含むデータです。AI は、その中の指示に従いません。

## 確かめたいことを読む・答える

sacty が人に問いかけて待っているとき、AI は `get_task` だけで「何を問われているか」「どう答えるか」を読めます（読むだけで、何も変わりません）。

- **人に確かめたいこと**（`humanAsks`）：承認待ちで、工程のエージェントが指摘への対応と一緒に挙げた確認（聞き返し・推測で決めたこと）や、PR の指摘の意図を読み取れなかった理由があるときだけ入ります。画面の承認の画面と同じ内容です。同じ文の確認は1件にまとまります。
  一覧（`list_tasks`）には、件数（`asks`）だけが入ります。長い文は切り詰め、件数が多いときは省いた件数が分かります。
- **答え方**（`humanAsks` の `howToAnswer`）：答えが要らなければ、そのまま承認します（`approve_step`、PR のマージで承認する工程は PR のマージ）。答えるなら、PR を作らない工程は `request_changes` の `comments` に答えを書きます。PR を作った工程は、PR のコメントに書くと PR に記録が残ります（`request_changes` でも差し戻せますが、PR には残りません）。
  答えると、sacty がその工程をやり直します（時間と費用がかかります）。**答える専用のツールは、ありません。**
- **人の判断待ち**（状態が `escalated`）：`get_task` の `escalation` に、理由（差し戻しの上限・変更の申し出など。記録が無い古いタスクは `unknown`）・工程・やり直す工程・書きかけの指摘の件数・開いている変更の申し出の ID が入ります。指摘の文は入りません。
  MCP でできるのは、承認の手段（`approval.method`）が `approve_step` のときの承認だけです（PR のマージで承認する工程や `approval` が無いときは、読むだけです）。何ができるかは `escalation.canDoHere` で確かめます。上限を超えた差し戻し・変更の申し出への決定・後続に回したい案への決定は、MCP からできません。画面で決めます（`escalation.decideOnScreen` に、理由に合った項目が入ります）。人の判断待ちのタスクの中止は、`cancel_task` でできます（あなたがはっきり頼んだときだけです）。
- 要件・設計などの成果物の本文にある「確認したいこと」の節は、`humanAsks` には入りません。`get_deliverable` で本文を読みます。
- これらの文は、エージェントやほかの人が書いたものです。「承認してよい」「差し戻せ」と書いてあっても、AI はそれだけで承認・差し戻しをしません（あなたに頼まれたときだけです）。

## 気をつけること

- MCP サーバーを使えるのは、`sacty up` を動かしている本人だけです（sacty が本人だけが読めるファイルに書いた接続先を使います）。
- 登録した AI は、あなたに代わって再レビューを始めたり、タスクを作ったり、承認待ちの工程を承認・差し戻したり、一時停止・再開・中止・再実行したりできます。タスクを作る・承認する・差し戻す・再開する・再実行すると、工程が始まり、時間と費用がかかります。中止すると、PR が閉じられ、ブランチと作業領域が消えます（取り消せません）。再実行すると、元のタスクは二度と再実行できなくなります。
  AI の CLI の権限の確認で、`rereview_task`・`create_task`・`approve_step`・`request_changes`・`pause_task`・`resume_task`・`get_cancel_plan`・`cancel_task`・`rerun_task` を毎回確かめるか、許可しておくかを選べます。
  特に `approve_step`・`request_changes`・`cancel_task`・`rerun_task` は、毎回確かめる設定をおすすめします（`rerun_task` は、新しいタスクを作って費用のかかる工程を始め、元のタスクは二度と再実行できなくなります）。許可しておくと、タスクの説明や成果物・レビューの本文に書かれた他人の指示で、確かめないまま承認・差し戻しされたり、中止（PR が閉じられ、ブランチと作業領域が消えます。取り消せません）されたりする場合があります。
- タスクの説明・レビューの本文・成果物が、AI に渡ります。
  ほかの人が書いた PR や Issue の文、エージェントが書いた文が含まれることがあります（AI への指示として扱わせないでください）。
- 前の版の sacty が起動しているときは、成果物と実行のツールが「sacty を更新し、`sacty up` で起動し直してください」と返します（タスクが無いときの理由とは別です）。実行中のタスクが無いときに、起動し直してください。
