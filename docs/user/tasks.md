# タスクを進める

タスクを作り、オーケストレーターとゴールガーディアンが工程を進め、人間は承認ゲートでだけ判断する。

## タスクを作る

- 画面でタスクを作るときは、プロジェクトの対象の中からリポジトリを選ぶ（[プロジェクトの設定](project-settings.md#対象)）。
  Issue・PR・チケットから取り込むこともできる（[取り込み](intake.md)）。
- リポジトリは選ばずにタスクを作ることもできる（調べもの・全体の設計・分割する大きなタスク）。オーケストレーターが、プロジェクトの
  コンテキスト（コンテキストリポジトリの規約・書き出しの接続先）と対象（リポジトリの一覧）から進め方を選ぶ。
  - コードを変えない仕事（調査だけ・設計だけ）は、リポジトリ無しのまま進め、sacty の画面で承認して完了する（PR やブランチは作らない。
    書き出し先があれば書き出す）。
  - 分割する大きなタスクは、タスク分割で子タスクごとに対象からリポジトリを選んで付け（選んだ理由を残す）、統合レビューでは子タスクの
    リポジトリごとにベースブランチの最新を読む。
  - コードの変更が要り分けないタスクは、オーケストレーターが対象からリポジトリを選び、用意してから工程を選び直す。選べなければ止まり、
    タスクの詳細で人がリポジトリを選んで再開できる。
- ベースブランチとテストのコマンドは、タスクの開始時にオーケストレーターがリポジトリを読んで決める。
- 工程の選択と、コードや仕組みを読んで説明する調査では、開発のセットアップ（依存のインストール・ビルドなど）を実行しない（リポジトリの
  AGENTS.md などにセットアップの手順があっても、こちらを優先する）。不具合の調査・再現・実装では、リポジトリの手順どおりセットアップする。

## PR での承認（要求要件・設計・成果物チェック）

人間の承認が要る工程（要求要件・設計・実装の成果物チェック）は、対象のリポジトリへの PR で判断する。承認＝マージで、PR を作った
工程は sacty の画面からは承認しない（画面は PR への案内と状況の表示）。

1. sacty が、ベースブランチの起点のコミットからタスクブランチ（`sacty/task-<タスクの短い ID>`）を作る。
2. 要求要件を、ファイル（既定 `docs/sacty/<タスクの短い ID>/requirements.md`）にして、タスクブランチへの PR にする。マージされたら
   要求要件の承認として記録し、次の工程に進む。
3. 設計（テスト観点を含む。`design.md`）も同じく、タスクブランチへの PR にする。
4. 設計の PR がマージされたら、タスクブランチに実装を積み、タスクブランチからベースブランチへの PR（成果物チェック）にする
   （CI が動く）。実装の PR には、要求要件・設計のファイルも含まれる。マージの後の CI/CD とデプロイは、プロジェクトの設定で On にすれば
   sacty が見届ける（[マージの後の監視](deployment-watch.md)）。

- ファイルの置き場所は、リポジトリやプロジェクトのコンテキストの規約に決まっていれば、オーケストレーターがそれに従う。
- PR のレビュー・行へのコメント・通常のコメント（bot と sacty の投稿は除く。ただし、その PR を取り込んだ sacty のレビューのタスクの
  投稿は含める。[sacty が作った PR のレビュー](intake.md#sacty-が作った-pr-のレビュー)）を指摘として取り込み（1分ごとに確かめ、最後のコメントから
  2分後）、ゴールガーディアンが、その工程のやり直し（同じ PR を更新）か前の工程への差し戻しかを判断する（人の確認は挟まない。判断と
  理由は作業履歴と PR の欄に残る）。同じ工程への差し戻しが上限を超えたら、エスカレーションになる。
- 前の工程に戻したときは、マージ済みの PR は戻さず、タスクブランチに直しの PR を新しく作る。直しがマージされたら、後ろの工程の PR を
  作り直す（開いていた前の PR は閉じる。実装の PR は、同じ PR を更新する）。
- マージされずに閉じられた・sacty の提出と違う内容でマージされたときは、承認にせずに判断を待つ（画面から差し戻すと、作り直した内容を
  新しい PR で出す）。
- 承認が要らない工程（前段の調査など）と、調査だけ・レビューだけ・不具合の修正（要求要件・設計の無いタスク）では、要求要件・設計の
  PR を作らない（調査だけのタスクは、画面で承認する）。PR での承認ができる前の版で、画面で要求要件・設計を提出したタスクは、
  そのまま画面で承認する。
- タスク分割の子タスクは、それぞれ自分のタスクブランチを持つ（親の要求要件・設計も親のタスクブランチへの PR で承認するが、親の
  タスクブランチはベースブランチにはマージしない）。

## オーケストレーターに質問する

タスクの詳細の「オーケストレーターに質問」で、タスクの状況を質問できる。

- オーケストレーター（`step_agents.orchestrator` か `default_agent`）が、タスクの台帳（作業履歴・承認済みの成果物・工程の出力・判定・
  費用）と、用意済みなら対象リポジトリの起点のコード（使い捨ての写し）を読んで答える。
- 各工程のエージェント・オーケストレーター自身などの実行ごとのセッションログ（秘密情報を伏せたもの。Claude Code・Codex が書いた
  元のファイルも）を読み取り専用で調べて、エージェントが実際に何をしたかも答える。答えには、どの工程・どの実行のログかが書かれる。
  実行中の実行・ログの無い実行・上限で間を省いたログ・読めないログは、その旨を書いて答える。
- 質問しても工程や承認済みの内容は変わらず、作業中のタスクでも作業を止めない。
- 答えの費用はタスクの費用に入り、予算の上限に達したタスクでは質問できない。

## 一時停止・再開・中止

- 予算の上限・AI の利用上限・認証エラー・エラーなどで止まったタスクは、原因を確かめてから画面で再開する（予算は
  [config.yaml の設定](config.md#予算)）。
- 中止すると、sacty が作った開いている PR をすべて閉じ、タスクブランチ・工程のブランチを消す（人間が作ったブランチや PR には触れない）。
  中止したタスクは再開できない。
