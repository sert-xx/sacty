# タスクを進める

タスクを作り、オーケストレーターとゴールガーディアンが工程を進め、人間は承認ゲートでだけ判断する。

## タスクを作る

- 画面でタスクを作るときは、プロジェクトの対象の中からリポジトリを選ぶ（[プロジェクトの設定](project-settings.md#対象)）。
  Issue・PR・チケットから取り込むこともできる（[取り込み](intake.md)）。
- リポジトリは選ばずにタスクを作ることもできる（調べもの・全体の設計・分割する大きなタスク）。オーケストレーターが、プロジェクトの
  コンテキスト（コンテキストリポジトリの規約・書き出しの接続先）と対象（リポジトリの一覧）から進め方を選ぶ。
  - コードを変えない仕事（調査だけ・設計だけ）は、リポジトリ無しのまま進め、sacty の画面で承認して完了する（PR やブランチは作らない。
    書き出し先があれば書き出す）。
  - 分割する大きなタスクは、タスク分割で子タスクごとに対象からリポジトリを選んで付け（選んだ理由を残す）、統合レビューでは子タスクの
    リポジトリごとにベースブランチの最新を読む。
  - コードの変更が要り分けないタスクは、オーケストレーターが対象からリポジトリを選び、用意してから工程を選び直す。選べなければ止まり、
    タスクの詳細で人がリポジトリを選んで再開できる。
- ベースブランチとテストのコマンドは、タスクの開始時にオーケストレーターがリポジトリを読んで決める。テストの仕組みが無いリポジトリ
  では、テストを使わずに進める（下の「テストの仕組みが無いリポジトリ」）。

### テンプレート「Sacty セットアップ」

リポジトリを sacty で扱えるように、AI エージェント向けの設定を整えるタスクを、リポジトリを選ぶだけで作る。

1. 「タスクを作成」の画面で、テンプレートの「Sacty セットアップ」を選ぶ。
2. 対象リポジトリを選んで「作成する」を押す（タイトル・内容は入力しない。sacty が決める）。

作ったタスクは、通常のタスクと同じく、オーケストレーターが進め方を選び、承認・PR を経て進む。エージェントは次を検査し、足りないものを
整える PR を作る。

- エージェント向けの指示（AGENTS.md・CLAUDE.md など）
- テストの実行の仕方（テストの仕組みがまだ無ければ、無いことと変更の確かめ方。このタスクでは言語やテストの仕組みを新しく入れない）
- テストに要るサービス（DB・モックなど）
- CI/CD でデプロイしているリポジトリでは、デプロイの確認のスキル `deployment-observer`（マージの後の監視で使う）。原本は
  `.agents/skills/deployment-observer/SKILL.md`、Claude Code 用の `.claude/skills/deployment-observer` は原本への相対のシンボリック
  リンクにする。

すでに整っていて変更が要らなければ、PR を作らずに、検査の結果を調査の結果として残して終える（画面で承認して完了）。
要求要件・設計・実装を進めた後に変更が要らないとわかったときも、PR を作らずに、実装の説明に検査の結果を残して、画面で承認して終える
（下の「実装に変更が無いとき」）。
テンプレートで作ったタスクは、一覧の「開始地点」・詳細の先頭・作業履歴の「タスクを作成」にテンプレートの名前が出る。

API からは、`POST /api/tasks` に `{"template": "sacty-setup", "projectId": "<プロジェクトの ID>", "repo": "<リポジトリの URL>"}` を
送る（`title`・`body` は渡さない）。CLI にはタスクを作るコマンドが無い。
- 工程の選択と、コードや仕組みを読んで説明する調査では、開発のセットアップ（依存のインストール・ビルドなど）を実行しない（リポジトリの
  AGENTS.md などにセットアップの手順があっても、こちらを優先する）。不具合の調査・再現・実装では、リポジトリの手順どおりセットアップする。

## テストの仕組みが無いリポジトリ

README しかないリポジトリのように、テストの仕組みがそもそも無いリポジトリでも、タスクは止まらずに進む。

- オーケストレーターが、テストの仕組みが無いと判断した根拠を残す。タスクの詳細の工程の欄に「テストのコマンド：なし（…根拠：…）」と出る
  （作業履歴の「工程を決定」にも出る）。
- 実装の検証では、テストを実行しない。ゴールガーディアンが、タスクの目的・要求要件（設計）と、実装後のコード・差分・実装の説明から、
  観点ごとに受け入れを判定する。通らなければ、テストのあるタスクと同じく実装をやり直し、3回続けて通らなければ一時停止する。
- 実装の成果物（タスクの詳細と成果物チェックの承認の画面）に「テストで検証していません」と出る。PR の本文のテストの行にも
  「テストのコマンドが無いため、テストでは検証していません。目的から判定しました。」と根拠が入る。テストで確かめていないので、
  承認の前に、変更の中身を自分で確かめる。
- タスクがテストの仕組みを用意するもの（言語のセットアップなど）で、実装がテストを用意したときは、そのテストで検証してから、目的から
  判定する（「実装で用意したテスト」と出る）。
- 不具合の修正（再現 → 実装）は、再現をテストで確かめるので、テストの仕組みが無いリポジトリでは選ばない。選ばれたときは止まる。

次のときは、テストなしでは進めずに止まる（「オーケストレーターが、対象リポジトリのテストのコマンドを決められませんでした」などの
理由が出る）。タスクの内容にテストの実行方法を書いて、作り直す。

- テストの仕組みはあるが、テストのコマンドを決められなかった。
- オーケストレーターはテストの仕組みが無いと判断したが、リポジトリにテストのように見えるファイル（`tests/` の中・`*.test.*`・
  `*_test.*`・`test_*`・`*Test.*` など）があった。見つけたファイルが理由に出る。
- ファイルが多すぎて、テストのファイルが無いことを確かめきれなかった。

## 実装に変更が無いとき

実装の工程が何も変えなかった（すでに満たしていて変更が要らないと判断した）ときは、PR を作らない。どのタスクでも同じ。

- タスクは「変更なしの成果物チェック待ち」になる。承認の画面で、実装の説明（変更が要らない理由と根拠）・テストの結果・最終レビューを
  確かめる。
- 変更なしでよければ「承認する」。PR を作らずに「完了（変更なし）」になる。
- 変更が要るなら、指摘を書いて差し戻す。実装からやり直し、変更があれば PR を作る。
- 要求要件・設計を PR で承認したタスクでは、タスクブランチは残る（要らなければ GitHub で消す）。
- すでに PR を作った後に、差し戻しで作り直した実装が何も変えなくなったときは、エラーで止まる（開いている PR をどうするか決めてから、
  中止するか、差し戻し直す）。

## PR での承認（要求要件・設計・成果物チェック）

人間の承認が要る工程（要求要件・設計・実装の成果物チェック）は、対象のリポジトリへの PR で判断する。承認＝マージで、PR を作った
工程は sacty の画面からは承認しない（画面は PR への案内と状況の表示）。

1. sacty が、ベースブランチの起点のコミットからタスクブランチ（`sacty/task-<タスクの短い ID>`）を作る。
2. 要求要件を、ファイル（既定 `docs/sacty/<タスクの短い ID>/requirements.md`）にして、タスクブランチへの PR にする。マージされたら
   要求要件の承認として記録し、次の工程に進む。
3. 設計（テスト観点を含む。`design.md`）も同じく、タスクブランチへの PR にする。
4. 設計の PR がマージされたら、タスクブランチに実装を積み、タスクブランチからベースブランチへの PR（成果物チェック）にする
   （CI が動く）。実装の PR には、要求要件・設計のファイルも含まれる。マージの後の CI/CD とデプロイは、プロジェクトの設定で On にすれば
   sacty が見届ける（[マージの後の監視](deployment-watch.md)）。

- ファイルの置き場所は、リポジトリやプロジェクトのコンテキストの規約に決まっていれば、オーケストレーターがそれに従う。
- PR のレビュー・行へのコメント・通常のコメント（bot と sacty の投稿は除く。ただし、その PR を取り込んだ sacty のレビューのタスクの
  投稿は含める。[sacty が作った PR のレビュー](intake.md#sacty-が作った-pr-のレビュー)）を指摘として取り込み（1分ごとに確かめ、最後のコメントから
  2分後）、ゴールガーディアンが、その工程のやり直し（同じ PR を更新）か前の工程への差し戻しかを判断する（人の確認は挟まない。判断と
  理由は作業履歴と PR の欄に残る）。同じ工程への差し戻しが上限を超えたら、エスカレーションになる。
- 前の工程に戻したときは、マージ済みの PR は戻さず、タスクブランチに直しの PR を新しく作る。直しがマージされたら、後ろの工程の PR を
  作り直す（開いていた前の PR は閉じる。実装の PR は、同じ PR を更新する）。
- マージされずに閉じられた・sacty の提出と違う内容でマージされたときは、承認にせずに判断を待つ（画面から差し戻すと、作り直した内容を
  新しい PR で出す）。
- 承認が要らない工程（前段の調査など）と、調査だけ・レビューだけ・不具合の修正（要求要件・設計の無いタスク）では、要求要件・設計の
  PR を作らない（調査だけのタスクは、画面で承認する）。PR での承認ができる前の版で、画面で要求要件・設計を提出したタスクは、
  そのまま画面で承認する。
- タスク分割の子タスクは、それぞれ自分のタスクブランチを持つ（親の要求要件・設計も親のタスクブランチへの PR で承認するが、親の
  タスクブランチはベースブランチにはマージしない）。
- PR の本文は、対象のリポジトリ（無ければ Org の公開の `.github` リポジトリ）に PR テンプレート（`pull_request_template.md`）が
  あれば、その見出しの形で書く。sacty が埋められない見出しは「該当なし」にし、チェックボックスにはチェックを付けない（レビューする人が
  付ける）。テンプレートが無い・読めないときは sacty の決まった形で書く。どちらにしたかは、タスクの画面の PR の欄の「本文」に出る。
  探す場所・埋め方の詳しい規則は[仕様書](../spec/approval.md#pr-の本文と-pr-テンプレート)を参照。

## オーケストレーターに質問する

タスクの詳細の「オーケストレーターに質問」で、タスクの状況を質問できる。

- オーケストレーター（`step_agents.orchestrator` か `default_agent`）が、タスクの台帳（作業履歴・承認済みの成果物・工程の出力・判定・
  費用）と、用意済みなら対象リポジトリの起点のコード（使い捨ての写し）を読んで答える。
- 各工程のエージェント・オーケストレーター自身などの実行ごとのセッションログ（秘密情報を伏せたもの。Claude Code・Codex が書いた
  元のファイルも）を読み取り専用で調べて、エージェントが実際に何をしたかも答える。答えには、どの工程・どの実行のログかが書かれる。
  実行中の実行・ログの無い実行・上限で間を省いたログ・読めないログは、その旨を書いて答える。
- 質問しても工程や承認済みの内容は変わらず、作業中のタスクでも作業を止めない。
- 答えの費用はタスクの費用に入り、予算の上限に達したタスクでは質問できない。

## 一時停止・再開・中止

- 予算の上限・AI の利用上限・認証エラー・エラーなどで止まったタスクは、原因を確かめてから画面で再開する（予算は
  [config.yaml の設定](config.md#予算)）。
- 中止すると、sacty が作った開いている PR をすべて閉じ、タスクブランチ・工程のブランチを消す（人間が作ったブランチや PR には触れない）。
  中止したタスクは再開できない。
