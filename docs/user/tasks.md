# タスクを進める

タスクを作ると、オーケストレーターとゴールガーディアンが工程を進めます。人間は承認ゲートでだけ判断します。

## タスクを作る

- 画面でタスクを作るときは、プロジェクトの対象の中からリポジトリを選びます（[プロジェクトの設定](project-settings.md#対象)）。
  - リポジトリの候補は、「タスクを作成」を押してダイアログを開いたときに読みます（Org の対象は `gh` で GitHub に問い合わせるので、
    数秒かかることがあります）。読んでいる間・読めなかったとき・候補が無いときは、ダイアログにそう出ます。どのときも、リポジトリの URL を
    入力すれば作れます。
  Issue・PR・チケットから取り込むこともできます（[取り込み](intake.md)）。
- リポジトリは選ばずにタスクを作ることもできます（調べもの・全体の設計・分割する大きなタスク）。オーケストレーターが、プロジェクトの
  コンテキスト（コンテキストリポジトリの規約・書き出しの接続先）と対象（リポジトリの一覧）から進め方を選びます。
  - コードを変えない仕事（調査だけ・設計だけ）は、リポジトリ無しのまま進め、sacty の画面で承認して完了します（PR やブランチは作りません。
    書き出し先があれば書き出します）。
  - 分割する大きなタスクは、タスク分割で子タスクごとに対象からリポジトリを選んで付け（選んだ理由を残します）、統合レビューでは子タスクの
    リポジトリごとにベースブランチの最新を読みます。
  - コードの変更が要り分けないタスクは、オーケストレーターが対象からリポジトリを選び、用意してから工程を選び直します。選べなければ止まり、
    タスクの詳細で人がリポジトリを選んで再開できます。
- ベースブランチとテストのコマンドは、タスクの開始時にオーケストレーターがリポジトリを読んで決めます。テストの仕組みが無いリポジトリ
  では、テストを使わずに進めます（下の「テストの仕組みが無いリポジトリ」）。
- 工程の選択と、コードや仕組みを読んで説明する調査では、開発のセットアップ（依存のインストール・ビルドなど）を実行しません（リポジトリの
  AGENTS.md などにセットアップの手順があっても、こちらを優先します）。不具合の調査・再現・実装では、リポジトリの手順どおりセットアップします。

### テンプレート「Sacty セットアップ」

リポジトリを sacty で扱えるように、AI エージェント向けの設定を整えるタスクを、リポジトリを選ぶだけで作れます。

1. 「タスクを作成」の画面で、テンプレートの「Sacty セットアップ」を選びます。
2. 対象リポジトリを選んで「作成する」を押します（タイトル・内容は入力しません。sacty が決めます）。

作ったタスクは、通常のタスクと同じく、オーケストレーターが進め方を選び、承認・PR を経て進みます。エージェントは次を検査し、足りないものを
整える PR を作ります。

- エージェント向けの指示（AGENTS.md・CLAUDE.md など）
- テストの実行の仕方（テストの仕組みがまだ無ければ、無いことと変更の確かめ方。このタスクでは言語やテストの仕組みを新しく入れません）
- テストに要るサービス（DB・モックなど）
- CI/CD のあるリポジトリでは（デプロイしていなくても）、マージの後の監視のスキル `deployment-observer`。原本は
  `.agents/skills/deployment-observer/SKILL.md`、Claude Code 用の `.claude/skills/deployment-observer` は原本への相対のシンボリック
  リンクにします。CI/CD の確認の仕方の reference（`references/ci.md`）も作り、デプロイしていなければデプロイの確認を飛ばすことを書きます
  （[マージの後の監視](deployment-watch.md#スキル)）。CI/CD が無ければ作りません。

すでに整っていて変更が要らなければ、PR を作らずに、検査の結果を調査の結果として残して終えます（画面で承認して完了します）。
要求要件・設計・実装を進めた後に変更が要らないとわかったときも、PR を作らずに、実装の説明に検査の結果を残して、画面で承認して終えます
（下の「実装に変更が無いとき」）。
テンプレートで作ったタスクは、一覧の「開始地点」・詳細の先頭・作業履歴の「タスクを作成」にテンプレートの名前が出ます。

API からは、`POST /api/tasks` に `{"template": "sacty-setup", "projectId": "<プロジェクトの ID>", "repo": "<リポジトリの URL>"}` を
送ります（`title`・`body` は渡しません）。CLI にはタスクを作るコマンドがありません。

## 文書作成と単発の外部作業

ユーザーガイド・議事録・翻訳草稿などを作る場合は、リポジトリを選ばず、読者・目的・元の内容をタスクに書いてください。「文書作成」で Markdown の原稿を確認し、差し戻し・承認できます。オーケストレーターが書き出し先を選んだ場合だけ、承認後に書き出します。タスクの工程欄で、選択された接続先・理由を確認してください（[成果の書き出し](result-export.md)）。書き出しの失敗は原稿の完了を止めませんので、外部への反映結果も確認してください。リポジトリの文書ファイルを変更したい場合は、対象リポジトリを選んでください。通常の実装・PR 承認で反映します。

文書作成中は外部の接続先・プロジェクトコンテキストを利用せず、外部にある原稿の読み取りも行いません。元の文章や必要な規約をタスク本文に含め、不足があれば差し戻しのコメントで補ってください。URL だけを渡しても、そのページの本文を取得して原稿を作ることはできません。

予定表や台帳、既存の外部ページを変更する場合も、リポジトリを選ばずに依頼できます。設定済みの接続先1つで行える単発の変更が対象です。

1. 対象の一意な ID/URL、変更内容・前提、期待する結果を依頼に書いてください。オーケストレーターが接続先・対象・依頼内容・確認方法を選定します。対象や接続先が不足しているときは実行開始前に停止します。
2. 単一の「作業」工程で、依頼に従って1回実行します。別の準備工程や実行前の承認はありませんので、タスクを開始する前に依頼内容が正しいことを確認してください。
3. 成功結果の根拠を確認し、結果を承認して完了します。失敗や結果不明は完了になりません。

工程選択後は、タスクの詳細で選定された接続先と接続方式、対象、依頼内容、確認方法を読み取り専用で確認できます。この表示は実行前の承認ゲートではなく、タスクの進行を止めません。

対象の情報が不足している場合は、依頼に情報を補って新しいタスクを作ってください。実行開始前に選定済みの接続先が使えなくなった場合は、接続の設定を修正してから再開できます。

実行が始まった後は差し戻せません。中断・再起動・失敗後の再開は拒否され、停止したままになります。外部サービスで実際の状態を確認してからタスクを中止し、まだ実施されていない変更だけを新しいタスクとして依頼してください。書込1回と変更後の確認をエージェントに指示しますが、外部サービス側の重複防止を保証するものではありません。

GitHub の PR・Issue への返信も、作業として依頼できます（例「https://github.com/acme/app/pull/12 のレビューの指摘に返信して」）。
プロジェクトの設定で GitHub のアカウントを選んだホストが、接続先の候補になります。エージェントは PR・Issue を読み、返信の内容を出力に
書きます。結果を承認すると、sacty が返信を投稿します（[PR と Issue へのコメント](#pr-と-issue-へのコメント)）。コードの修正やプッシュは
できません。PR のコードを直すときは、リポジトリを選んでタスクを作ってください。

定期更新・監視や、複数の接続先をまたぐ長期業務の自動化は対象外です。文書作成と外部更新など複数の成果が必要な依頼は、確認・承認できる単位に分けてください。

## PR と Issue へのコメント

工程のエージェントは GitHub を読めますが、書き込めません（[ゲートウェイ](gateway.md#github-の読み取り)）。PR・Issue へのコメントが
要るときは、エージェントが工程の出力にコメントの内容を書き、その工程の成果を人が承認した後に、sacty がプロジェクトの GitHub の
アカウントで投稿します。承認しなければ投稿しません。

- 投稿の内容は、承認の前に、成果の末尾の `sacty-github-comments` の JSON で確かめられます。差し戻して直した後に承認すると、直した版を投稿します。
- 投稿先は、プロジェクトの対象のリポジトリ（と、タスクの取り込み元・作業するリポジトリ）の PR・Issue だけです。それ以外の URL には投稿せず、
  理由を作業履歴に出します。
- コメントの末尾に、sacty のタスクで AI が書き、人が承認したことを添えます。
- 投稿の結果（コメントの URL・投稿できなかった理由）は、作業履歴に出ます。投稿できなくても、タスクは止まりません。
- レビューの工程は、これまでどおり、書いたレビューを sacty が PR に投稿します。

## テストの仕組みが無いリポジトリ

README しかないリポジトリのように、テストの仕組みがそもそも無いリポジトリでも、タスクは止まらずに進みます。

- オーケストレーターが、テストの仕組みが無いと判断した根拠を残します。タスクの詳細の工程の欄に「テストのコマンド：なし・目的から判定」と
  出て、横の補足の印（i）に根拠が出ます（作業履歴の「工程を決定」にも出ます）。
- 実装の検証では、テストを実行しません。ゴールガーディアンが、タスクの目的・要求要件（設計）と、実装後のコード・差分・実装の説明から、
  観点ごとに受け入れを判定します。通らなければ、テストのあるタスクと同じく実装をやり直し、3回続けて通らなければ一時停止します。
- 実装の成果物（タスクの詳細と実装の承認の画面）に「テストで検証していません」と出ます。PR の本文のテストの行にも
  「テストのコマンドが無いため、テストでは検証していません。目的から判定しました。」と根拠が入ります。テストで確かめていないので、
  承認の前に、変更の中身を自分で確かめてください。
- タスクがテストの仕組みを用意するもの（言語のセットアップなど）で、実装がテストを用意したときは、そのテストで検証してから、目的から
  判定します（画面には、テストが通れば「実装で用意したテストで検証しました」、通らなければ「実装で用意したテストが通りませんでした」と
  出ます。通らなければ実装をやり直します）。実装がテストのコマンドの申告（言語の名前が `sacty-test-command` のコードブロック）を正しく書かなかった（JSON として読めないときを
  含みます）ときは、
  エラーで一時停止します（再開すると実装をやり直します）。
- テストに通らずに実装をやり直しているあいだ、前の実装のテストの結果と最終レビューは「前の提出の…」という見出しで出ます
  （横の補足の印に、今の提出ではまだ実行・判定していないことが出ます）。今の実装の結果ではありません（これはテストの仕組みがあるタスクでも同じです）。
- 不具合の修正（再現 → 実装）は、再現をテストで確かめるので、テストの仕組みが無いリポジトリでは選びません。選ばれたときは止まります。

### テストなしで進めずに止まったとき

次のときは、テストなしでは進めずに一時停止します（理由がタスクの詳細に出ます）。

| 止まった理由 | 直し方 |
| --- | --- |
| テストの仕組みはあるが、オーケストレーターがテストのコマンドを決められなかった（「テストのコマンドを決められませんでした」） | タスクの内容にテストの実行方法（コマンドと前提）を書いて、作り直してください。 |
| オーケストレーターはテストの仕組みが無いと判断したが、テストのように見えるファイルがあった（「テストのように見えるファイルがあります（…）」。見つけたファイルが出ます） | 見つけたファイルが**本当にテスト**なら、上と同じく、タスクの内容にテストの実行方法を書いて作り直してください。**テストではない**ファイル（テスト用ではないスクリプトなど）を誤って当てたときは、作り直しても同じ理由で止まります。リポジトリでそのファイルの名前か置き場所を変え（`tests/` などの外へ移す・名前から `test`・`spec` を外す）、その変更をベースブランチに入れてから作り直してください。 |
| ファイルが多すぎて、テストのファイルが無いことを確かめきれなかった（「ファイルが多く、…確かめきれませんでした」） | テストがあるなら、タスクの内容にテストの実行方法を書いて作り直してください。本当にテストが無い大きなリポジトリでは、今は進められません。 |
| 作業領域のディレクトリを読めず、確かめきれなかった（「作業領域のディレクトリ（…）を読めず（…）」。読めなかった場所と、`EACCES`（権限が無い）などのエラーが出ます） | 出る場所は、そのタスクの作業領域 `$SACTY_HOME/workspaces/<タスク ID>/repo/`（`SACTY_HOME` を変えていなければ `~/.sacty/workspaces/<タスク ID>/repo/`）からの相対のパスです（`.` は作業領域そのもの）。タスク ID は、タスクの詳細の画面の URL（`/tasks/<タスク ID>`）の末尾です。sacty を動かしているユーザーが、その場所を読めるか（ファイルの権限・ディスクの状態）を確かめて直してから、タスクを作り直してください。再開しても、テストなしでは進めません。 |
| 不具合の修正を選んだ（「再現はテストで確かめるので、テストのコマンドが要ります」） | テストの実行方法を書いて作り直すか、不具合の修正ではなく、直す内容を書いたふつうのタスクとして作り直してください。 |

テストのように見えるファイルとして当たるのは、`test`・`tests`・`__tests__` のディレクトリの中のファイルと、`*.test.*`・`*.spec.*`・
`*_test.*`・`*_spec.*`・`test_*`・`*Test.*`・`Test*` のような名前のファイルです。文書のファイル（`.md`・`.txt`・`.rst`・`.adoc`
など）は当たりません（`tests/README.md` は当たりません）。

## 実装に変更が無いとき

実装の工程が何も変えなかった（すでに満たしていて変更が要らないと判断した）ときは、PR を作りません。どのタスクでも同じです。

- タスクは「変更なしの実装の承認待ち」になります。承認の画面で、実装の説明（変更が要らない理由と根拠）・テストの結果・最終レビューを
  確かめてください。
- 変更なしでよければ「承認する」を押します。PR を作らずに「完了（変更なし）」になります。
- 変更が要るなら、指摘を書いて差し戻します。実装からやり直し、変更があれば PR を作ります。
- 要求要件・設計を PR で承認したタスクでは、タスクブランチは残ります（要らなければ GitHub で消してください）。
- すでに PR を作った後に、差し戻しで作り直した実装が何も変えなくなったときは、エラーで止まります（開いている PR をどうするか決めてから、
  中止するか、差し戻し直してください）。

## PR での承認（要求要件・設計・実装）

人間の承認が要る工程（要求要件・設計・実装）は、対象のリポジトリへの PR で判断します。承認＝マージで、PR を作った
工程は sacty の画面からは承認しません（画面は PR への案内と状況の表示です）。

承認待ちで、今の提出の PR が開いていれば、GitHub の PR を新しいタブで直接開けます（sacty の承認の画面を挟みません）。

- タスクの詳細・タスクの一覧の「あなたの出番」：「PR でチェックする ↗」を押します。
- ダッシュボードの「あなたの出番」・ヘッダーのお知らせ：タスクの題（末尾に ↗ が付きます）を押します。

PR をマージすれば、sacty の画面に戻らなくても、次の確認で承認として進みます。次のときは、今までどおり sacty の承認の画面に案内します
（タスクの詳細・一覧では「チェックする」「判断する」、ダッシュボード・お知らせでは ↗ の無いタスクの題）。

- PR の指摘の戻し先を人が選ぶときなど、エスカレーションのとき。
- PR がマージされずに閉じられた・提出と違う内容でマージされた・まだ無いとき。

1. sacty が、ベースブランチの起点のコミットからタスクブランチ（`sacty/task-<タスクの短い ID>`）を作ります。
2. 要求要件を、ファイル（既定 `docs/sacty/<タスクの短い ID>/requirements.md`）にして、タスクブランチへの PR にします。マージされたら
   要求要件の承認として記録し、次の工程に進みます。
3. 設計（テスト観点を含む。`design.md`）も同じく、タスクブランチへの PR にします。
4. 設計の PR がマージされたら、実装の工程に進みます。実装がテストとゴールガーディアンの最終レビューに通ったら、実装の工程の中で、タスクブランチに
   実装を積み、タスクブランチからベースブランチへの PR にします（CI が動きます）。実装の承認待ちになり、PR をマージすると実装の承認になって、
   マージの後の監視の工程に進みます（対象のリポジトリにスキルが無く、工程を飛ばしたときは、タスクが完了します）。実装の PR には、要求要件・設計の
   ファイルも含まれます。マージの後の監視では、CI/CD とデプロイを sacty が見届け、終わるとタスクが完了します（[マージの後の監視](deployment-watch.md)）。

- ファイルの置き場所は、リポジトリやプロジェクトのコンテキストの規約に決まっていれば、オーケストレーターがそれに従います。
- PR のレビュー・行へのコメント・通常のコメント（bot と sacty の投稿は除きます。ただし、その PR を取り込んだ sacty のレビューのタスクの
  投稿は含めます。[sacty が作った PR のレビュー](intake.md#sacty-が作った-pr-のレビュー)）を指摘として取り込み（1分ごとに確かめ、最後のコメントから
  2分後）、ゴールガーディアンが、その工程のやり直し（同じ PR を更新）か前の工程への差し戻しかを判断します（人の確認は挟みません。判断と
  理由は作業履歴と PR の欄に残ります）。同じ工程への差し戻しが上限を超えたら、エスカレーションになります。
- 前の工程に戻したときは、マージ済みの PR は戻さず、タスクブランチに直しの PR を新しく作ります。直しがマージされたら、後ろの工程の PR を
  作り直します（開いていた前の PR は閉じます。実装の PR は、同じ PR を更新します）。
- マージされずに閉じられた・sacty の提出と違う内容でマージされたときは、承認にせずに判断を待ちます（画面から差し戻すと、作り直した内容を
  新しい PR で出します）。
- 承認が要らない工程（前段の調査など）と、調査だけ・レビューだけ・不具合の修正（要求要件・設計の無いタスク）では、要求要件・設計の
  PR を作りません（調査だけのタスクは、画面で承認します）。PR での承認ができる前の版で、画面で要求要件・設計を提出したタスクは、
  そのまま画面で承認します。
- タスク分割の子タスクは、それぞれ自分のタスクブランチを持ちます（親の要求要件・設計も親のタスクブランチへの PR で承認しますが、親の
  タスクブランチはベースブランチにはマージしません）。
- PR の本文は、対象のリポジトリ（無ければ Org の公開の `.github` リポジトリ）に PR テンプレート（`pull_request_template.md`）が
  あれば、その見出しの形で書きます。sacty が埋められない見出しは「該当なし」にし、チェックボックスにはチェックを付けません（レビューする人が
  付けます）。テンプレートが無い・読めないときは sacty の決まった形で書きます。どちらにしたかは、タスクの画面の PR の欄の「本文」に出ます。
  探す場所・埋め方の詳しい規則は[仕様書](../spec/approval.md#pr-の本文と-pr-テンプレート)を参照してください。

## オーケストレーターに質問する

タスクの詳細の「オーケストレーターに質問」で、タスクの状況を質問できます。

- オーケストレーター（`step_agents.orchestrator` か `default_agent`）が、タスクの台帳（作業履歴・承認済みの成果物・工程の出力・判定・
  費用）と、用意済みなら対象リポジトリの起点のコード（使い捨ての写し）を読んで答えます。
- 各工程のエージェント・オーケストレーター自身などの実行ごとのセッションログ（秘密情報を伏せたもの。Claude Code・Codex が書いた
  元のファイルも）を読み取り専用で調べて、エージェントが実際に何をしたかも答えます。答えには、どの工程・どの実行のログかが書かれます。
  ログの無い実行・上限で間を省いたログ・読めないログは、その旨を書いて答えます。
- 実行中の工程があれば、質問した時点までのその工程のログも調べます。処理が長引いているときに「いま何をしている？」
  「どこで時間がかかっている？」と聞くと、いまの様子を、いつの時点のものかを添えて答えます。
- 質問しても工程や承認済みの内容は変わらず、作業中のタスクでも作業を止めません。
- 答えの費用はタスクの費用に入ります。予算の上限に達したタスクでは質問できません。

## 提出の前のセルフレビュー

要求要件・設計・実装の工程では、エージェントが提出の前に、既定のスキル `review-dispatch` で観点ごとにセルフレビューし、
`must` の指摘が無くなるまで直してから提出します（初回を含めて最大 5 回）。

成果物のカード・実装のカード・承認の画面に、結果が出ます。

| 表示 | 意味 |
| --- | --- |
| セルフレビュー：パス・n回 | `must` の指摘が無くなるまで直しました |
| セルフレビュー：パスしていません・n回・残った指摘 m件 | 上限まで直しても `must` の指摘が残りました。残った指摘を確かめてから判断してください |
| セルフレビューの記録がありません | エージェントが結果を報告しませんでした。成果物を自分で確かめてください |

セルフレビューの費用は、その工程の費用に入ります。

## 工程のイメージを変える

タスクの詳細の「工程」の欄に、工程ごとのイメージと、選んだ元（オーケストレーター・プロジェクトの対象の指定・人間）が出ます。
普段は変えないので、見出しだけを出して閉じています（見出しを押すと開きます）。工程に合わないイメージなら、そこで選び直せます。変えたイメージは、その工程を次に実行するときから使います（実行中の工程は、次の実行から）。
くわしくは [コンテナイメージ](images.md#工程のイメージを変える) をご覧ください。

## 工程のエージェントを変える

タスクの詳細の「工程」の欄の「工程のエージェント」で、工程ごとに使うエージェントを、使えるエージェント（sacty の既定と config.yaml の `agents` のうち、接続先と単価があるもの）から選び直せます。
普段は変えないので、見出しだけを出して閉じています（設定から消えた名前を使っているときなど、確かめが要るときは開いて出します）。
エラーで止まった・差し戻した工程だけ、より強いエージェント（[工程ごとのモデル](config.md#工程ごとのモデル)で書いた、強いモデル・リーズニングエフォートのもの）で実行し直す、
といった使い方ができます。

- 変えたエージェントは、その工程を次に実行するときから使います。config.yaml の `step_agents` より優先します。ほかのタスクには効きません。
- 誰が・いつ・何から何に変えたかは、作業履歴に残ります。
- 選んだエージェントが使えなくなる（config.yaml から消した・単価を消したなど）と、その工程を実行するときに一時停止します。選び直してから再開してください。
- 統合レビュー（ゴールガーディアン）とオーケストレーターは、ここでは変えられません。

## 一時停止・再開・中止

- 予算の上限・AI の利用上限・認証エラー・エラーなどで止まったタスクは、原因を確かめてから画面で再開してください（予算は
  [config.yaml の設定](config.md#予算)）。
- 中止すると、sacty が作った開いている PR をすべて閉じ、タスクブランチ・工程のブランチを消します（人間が作ったブランチや PR には触れません）。
  中止したタスクは再開できません。
- 中止したタスクは、詳細の「再実行」から最初からやり直せます。開いた画面で、作業するリポジトリ（空欄ならリポジトリ無し）・イメージ・
  タイトル・内容を直し、補足を書けます。中止したタスクを引き継いだ新しいタスクを作り、内容の後に、補足と前の試行の記録（工程の成果・
  差し戻しの指摘・質問と答え・止まった理由）を足して渡します。チケットから取り込んだタスクは、チケットを引き継ぎ、読み直しません。
  再実行は1度だけで、再実行した後の中止したタスクには、作ったタスクへのリンクが出ます。
- 実装の PR を作っている途中に一時停止すると、PR を作り終えて実装の承認待ちになり、一時停止はしません（画面に、止めなかったことが出ます）。
  PR で判断するか、止めるなら中止してください。

## タスクの一覧

タスクの一覧の各行には、題の下に、作業するリポジトリの名前（`org/repo` の `repo` だけ）が出ます。リポジトリがまだ決まっていない
タスクには出ません（リポジトリを指定せずに作ったタスクは「リポジトリなし」）。Issue・PR から取り込んだタスクは、開始地点の下に
その番号（`#7` など）が出ます。

## 画面の補足

画面の文は、いまの状態と次にすることだけを短く出します。仕組みや理由は、見出し・項目の横の補足の印（i）にマウスを乗せると出ます。
キーボードでは Tab で印に止まると出て、スマホではタップで出ます。Esc か外側を押すと閉じます。補足が無い項目には印が出ません。

## 画面の自動の更新

ダッシュボード・タスクの一覧・タスクの詳細・ヘッダーのお知らせは、開いている間、3秒ごとに最新の状態を取り直して表示します。タスクの状態によらず
（タスクが無いとき・すべてが承認待ち・一時停止・完了のときも）取り直すので、取り込みで増えたタスク、ほかのタブや CLI での承認・再開、
デーモンが拾って動き出したタスク、承認待ちになったタスクが、操作しなくても画面に出ます。

- 画面は読み直さず、変わった所だけを表示し直します。書きかけの質問・コメント・フォームの値、選んだもの、開いたダイアログや欄、
  フォーカス、スクロールの位置は、そのまま残ります。
- タブが隠れている間は問い合わせません。タブに戻ると、すぐに最新にします。
- デーモンに届かない間は、画面をそのまま残し、「デーモンに届きません」（ヘッダーは「更新が止まっています」）と表示します。表示は最後に
  取得した内容です。届くようになったら、また最新にし、この表示を消します。
- 承認の画面・プロジェクトの一覧（取り込みの状況）も、同じように読み直さずに最新にします。書きかけのコメントは消えません。
- 実行のログは、実行中、新しい行を自動で後ろに足します。読んでいる途中のスクロールの位置は動きません。一番下を見ているときだけ、
  新しい行についていきます。実行が終わった後に、エージェントの元のファイルの一覧を読めないときは、そのことと取り直していることを
  表示し、読めたら一覧を出します。
- Sacty の設定・プロジェクトの設定の画面は、自動では更新しません（ヘッダーのお知らせだけを更新します）。最新を見るときは、
  開き直すか、ブラウザで読み直してください。

## 更新前のバックアップと旧版への復帰

新しい種類の記録（文書作成・作業の工程を含むタスク、完了したタスクの監査と、その改修のタスクなど）を保存したデータベースは、それに対応していない旧版では読み込めず、起動に失敗します。更新前にデーモンを停止し、データディレクトリ（環境変数 `SACTY_HOME` の指定先。未指定なら `~/.sacty`）をバックアップしてください。旧版へ戻す場合は、更新前のバックアップを使ってください。新しい工程の設定がある場合は、設定も旧版に対応するものへ戻す必要があります。

バックアップを復元すると、それ以後に作ったタスクや進捗履歴は復元されません。復帰前のデータも別に保管し、失われる履歴を確認してください。予定表などに実施した外部変更は元に戻りません。監査の提案を採用して作った改修のタスクが、すでに PR を作っていることもあります。外部作業の開始記録もバックアップ以後のものは失われるため、外部の実際の状態を確認し、実施済みの変更を再実行しないでください。

## 以前の版のタスク（「PR作成」の工程があった版）

以前の版には、実装の後に「PR作成」（工程 `pr`。英語の画面では「Open PR」、承認の画面によっては「成果物チェック」）の工程がありました。
今の版では、この工程を無くし、実装の工程の中で PR を作って、実装の承認を待ちます。以前の版のタスクは、そのままでは引き継げません。

- 以前の版で作った、「PR作成」の工程（`pr`）を含むタスクは、デーモンを起動したときに作業履歴から消えます。**処理中のタスク（実行中・承認待ち・
  一時停止など）も消えます。** タスク分割の親と子、マージの後の監視の修正のタスクと元のタスクは、どちらかが消えるときは一緒に消えます。
- 消えたタスクの件数と ID は、デーモンのログに出ます。
- GitHub のブランチと PR は、そのまま残ります。開いている PR を使わないなら、GitHub で閉じてください。続けたい作業は、新しいタスクとして
  作り直してください。
- `config.yaml` の `step_agents` に `pr` を書いていたら、消してください。書いたままだと設定の誤りになり、古いタスクがあるときは、
  消さずにデーモンが起動しません（ログに、設定の誤りと消すよう案内が出ます）。消してから起動し直してください。
