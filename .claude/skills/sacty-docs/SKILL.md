# sacty の docs を方針どおりに書く・直す

このスキルは sacty リポジトリ自体の開発のためのもの。sacty が対象のリポジトリへ配る既定のコンテキスト
（`apps/daemon/default-context/`）とは別物で、そちらには影響しない。

方針の正本は `docs/README.md`、ファイル名の規則とひな形の正本は各ディレクトリの `README.md`
（`docs/spec/`・`docs/user/`・`docs/adr/`・`docs/worklog/`）。書く前に、関係する README を読む。
このスキルと README が食い違ったら README に従い、このスキルを直す。

## PR を出す前に確かめること

1. **仕様書**：実装を変えたら、変えた振る舞いを書いている `docs/spec/` の節を、同じ PR で直す。ズレを残さない。
   対応するコードの場所（ファイル・関数）が動いた・消えたときも直す。書くのは今の振る舞いだけ（経緯は ADR）。
   コードで確かめられないことは書かないか、`（未確認）` と明記する。
2. **ユーザードキュメント**：利用者に見える変更（設定・コマンド・オプション・画面・既定値・エラーの文言）なら、
   `docs/user/` も同じ PR で直す。設定の項目・既定値・オプションはコードと照合する。リポジトリの `README.md` には
   中身を書かず、ユーザードキュメントへのリンクだけにする。
3. **ADR**：方針や仕様を決めた・変えたら、`docs/adr/` に新しい ADR を足す。
   - ファイル名は `YYYYMMDD-HHMM-<スラッグ>.md`（UTC。決定した日時）。
   - 古い ADR の本文（背景・決定・理由・影響）は書き換えない。置き換えたら、古い ADR を `git mv` で
     `YYYYMMDD-HHMM-superseded-<スラッグ>.md` に変え（やめただけなら `deprecated`、採用しなかったなら `rejected`）、
     `ステータス` と `置き換え先` を直し、新しい ADR の `置き換え元` に古い ADR へのリンクを書く。名前の変更で切れた
     リンクを直す。
4. **作業履歴**：タスクごとに `docs/worklog/YYYYMMDD-pbi-<番号>-<スラッグ>.md`（UTC。PR を作った日。PBI が無ければ
   `pr-<番号>-` か内容の名前）を足す。何をしたか・何を確かめたか（コマンドと結果）・レビューの指摘と対応を書く。
   同じ PR のレビュー対応は同じファイルに書き足す。
5. **直さないもの**：過去の作業履歴と、置き換え・廃止・却下した ADR は、今の実装と矛盾していても直さない
   （直してよいのは ADR のステータス・置き換えの関係・切れたリンクだけ）。
6. **確かめる**：`npx vitest run tests/docs` で、ファイル名の規則・リンク切れ・置き換えの関係・このスキルの2つの写しの
   一致を確かめる。

## 書くときの規則

- 公開リポジトリなので、特定の組織や勤め先の内部を指す語・その組織の名前・秘密の値・個人の情報を書かない。
  例の値は `example.com`・`acme` などの架空のものにする。
- `docs/pbi/`（git 管理しない一時ファイル）の内容を写さない・リンクしない。4種類のディレクトリに混ぜない。
- リンクは相対パスで書く。
- 理由がわからないことは、推測で作らず、わからないと書く。

## このスキルを直すとき

同じ内容を `.claude/skills/sacty-docs/SKILL.md`（Claude Code 用）と `.agents/skills/sacty-docs/SKILL.md`（Codex 用）に
置いている。片方を直したら、もう片方にも同じ内容を写す（`tests/docs` のテストで一致を確かめる）。
