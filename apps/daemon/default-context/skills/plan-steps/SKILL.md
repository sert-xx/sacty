# 工程の組み合わせを選んで JSON で答える

タスクの内容と対象を読み、依頼で示された候補から工程の組み合わせを選び、決められた形の JSON で答えるときの決まり。
答えは機械が読むので、選び方が正しくても JSON が壊れていれば（閉じ括弧の欠け・末尾のカンマ・注釈の混入など）答えは読めず、タスクは止まる。
出す前に必ず道具で検査し、通った内容だけを出す。

## 何より先に従うもの

次の順に従う。
上のものと食い違ったら、このスキルの決まりは使わない。

1. 依頼した人の指示（候補の組み合わせ・決める項目・答えの形と見出し）
2. 対象のリポジトリの決まり（CONTRIBUTING・AGENTS.md・CLAUDE.md・docs の方針など）
3. このスキル

## 手順

1. **依頼を読む**。候補の組み合わせ、決める項目、答えの形（見出しの名前、必ず書く項目、書かなくてよい項目、形の例）を書き出す。
   形の例にある注釈（「または」「（…のときだけ）」「（要らなければ書かない）」など）は、値の選び方の説明で、答えに写すものではない。
2. **タスクと対象を読む**。タスクの目的・成果物・変更対象・規模をつかむ。コードがあれば、変更の大きさや影響範囲を判断するのに要る分だけ読む。
   依頼が許していなければ、セットアップ・ビルド・テストの実行はしない。
3. **候補を比べる**。目的 → 成果物 → 変更対象 → 規模の順に、候補のそれぞれが合うかを比べる。
   - 依頼が候補ごとの使いどきを示していれば、それに従う。
   - どれか 1 つを無条件の既定や、分からない仕事の受け皿にしない。
   - 依頼が「選べない」とした候補を選ばない。
   - 情報が足りないときは、足りないまま標準的な候補で進めず、分かる範囲で選び、不明点を理由に書く。
4. **決める項目を埋める**。依頼が挙げた項目（ベースブランチ・テストのコマンド・使うイメージなど）を、読んだ根拠から決める。
   分からない項目は推測で埋めず、依頼の決まり（空にする・根拠を書く・省く）に従う。
   - テストのコマンドは、パッケージの設定（`package.json` の `scripts` など）・`Makefile` などのタスクの定義・CI の設定・
     README や CONTRIBUTING の開発の手順・テストのディレクトリやファイルを調べ、リポジトリが実際に使っているコマンドを書く。
   - 調べてもテストの仕組みが見つからなければ、テストのコマンドもその根拠も空のまま出さない。依頼の決まり（テストの仕組みが無い根拠を
     書く項目など）に従い、どこを見て何が無かったかを書く。エージェントのスキルやドキュメントを置くだけのリポジトリのように、
     テストを書く種類でないリポジトリも同じ。
   理由（`reason` などの項目）には、成果物・変更対象・候補を比べた結果・要る工程と省く工程の根拠・不明点を書く。
5. **答えを作って検査する**。答えの JSON をファイルに書き、[検査の手順](references/json-check.md)で、JSON として正しいか（構文）と、
   依頼した形か（見出しと必ず書く項目）を道具で確かめる。通らなければ直し、通るまで繰り返す。
6. **出す**。検査に通ったファイルの中身をそのまま、依頼した形（ふつうは ```` ```json ```` のコードブロック）で、本文の最後に 1 回だけ出す。
   手で書き直さない（書き直したら、もう一度検査する）。

## 答えの JSON の決まり

- 見出し（最上位のキー）と項目の名前は、依頼の形のまま使う。変えない・訳さない・省略しない。
- 候補を書く項目には、選んだ 1 つの値だけを書く（「A または B」のような形の例の書き方を写さない）。
- 「要らなければ書かない」とされた項目は、キーごと省く。空の文字列・`null`・空のオブジェクトで埋めない。
  「分からなければ空にする」とされた項目だけ、空の文字列にする。
- 文字列の中の改行・引用符・バックスラッシュはエスケープする。コメント・末尾のカンマ・引用符の無いキーは書かない。
- 下書き・途中の JSON・直す前の JSON を本文に出さない。出すと、どれが答えか分からなくなる。
- 答えの JSON の前後に説明を書いてよいが、JSON のコードブロックの中には書かない。
