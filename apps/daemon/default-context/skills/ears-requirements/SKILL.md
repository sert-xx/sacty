# EARS 形式で要求要件を書く

要求要件の受け入れ条件を、EARS の決まった文型で書くときの決まり。
条件・きっかけ・振る舞いを文型で分けて、抜けと曖昧さに気づきやすく、そのまま検証できる要求にする。

## 何より先に従うもの

次の順に従う。
上のものと食い違ったら、このスキルの決まりは使わない。

1. 依頼した人の指示（出力の形・見出し・言語）
2. 対象のリポジトリの要求要件の決まり（AGENTS.md・CLAUDE.md、docs の方針、テンプレート、既存の要求要件の書き方）
3. このスキル

文章の書き方（改行・箇条書き・簡潔さ）は、既定の `writing` があれば、それにも従う。

## 文型

1つの要求を、次のどれか1つの文型で書く。
`<システム>` は要求の主語になるもの（システム・部品・機能の名前）で、文書の中で同じ名前を使う。

| 文型 | 使うとき | 日本語 | 英語 |
| --- | --- | --- | --- |
| 常時 | 条件なしに、いつも成り立つ | `<システム>は、<応答>しなければならない。` | `The <system> shall <response>.` |
| イベント駆動 | きっかけ（出来事）が起きたときに応答する | `<きっかけ>とき、<システム>は、<応答>しなければならない。` | `When <trigger>, the <system> shall <response>.` |
| 状態駆動 | ある状態が続いている間、成り立つ | `<状態>の間、<システム>は、<応答>しなければならない。` | `While <precondition>, the <system> shall <response>.` |
| 望まない振る舞い | 異常・失敗・不正な入力への応答 | `<望まない事象>場合、<システム>は、<応答>しなければならない。` | `If <trigger>, then the <system> shall <response>.` |
| オプション | ある機能・構成を含むときだけ成り立つ | `<機能>を含む場合、<システム>は、<応答>しなければならない。` | `Where <feature is included>, the <system> shall <response>.` |
| 複合 | 状態ときっかけなど、複数の条件が要る | `<状態>の間、<きっかけ>とき、<システム>は、<応答>しなければならない。` | `While <precondition>, when <trigger>, the <system> shall <response>.` |

文型ごとの例と、選び方に迷う場合は [文型の例と選び方](references/patterns.md) を読む。

## 書き方の決まり

- 1つの文に1つの要求を書く
  - 「〜し、〜する」と応答が2つ以上あれば、要求を分ける
  - 条件を足すときは、複合の文型にする。文の後ろに「ただし」で足さない
- 応答は、第三者が観察して合否を決められる形にする
  - 数・時間・回数・範囲・状態の名前など、確かめられる値で書く
  - 「適切に」「速やかに」「十分な」「使いやすい」「など」のような、合否を決められない語を使わない
- 正常な振る舞いと対になる異常系は、望まない振る舞いの文型で書く
  - 入力の誤り、外部の失敗、時間切れ、権限の不足、上限を超えたときを確かめる
  - 書くのは、今回の対象で新しく起こりうる異常系だけにする。既存の仕組みが扱っていて、今回の対象で変わらないものは書かない
- 要求の数は、対象の大きさに合わせ、最小限にする。足りない要求は、読む人が求めたときに足す。次のものは要求にしない
  - 依頼に無い機能・将来の拡張
  - 既存の仕組み（フレームワーク・基盤・既存のコード）がすでに保証していて、今回の対象で変わらない振る舞い
  - 同じ振る舞いの言い直し
- 実装の方法（使う技術・データの持ち方・画面の部品）を書かない。何が成り立つかを書く
- 要求に ID を付ける（例：`R-1`、`R-2`）
  - ID は文書の中で一意にし、直しても付け直さない。消した要求の ID は使い回さない
  - 最初の提出では、1 から欠番なく振る
  - 差し戻しで要求を消したときは、ID を詰めず、行を「R-5（削除：理由）」のように残して、欠番の理由が分かるようにする
  - 別の文書（ほかのタスクの要求要件など）を参照する要求は、参照だけにせず、参照先の中身を1行で併記する
- タスクの内容から判断できないことは、推測で要求にしない。確かめたいこととして、別に挙げる

## 書き出す形

要求は、文を箇条書きに並べず、文型ごとの表にして書き出す。
人が読むときに、同じ文型の要求を同じ列で見比べられるようにする。

- 文型ごとに見出しを分ける
  - 見出しの名前は、文型の名前（`常時`・`イベント駆動`・`状態駆動`・`望まない振る舞い`・`オプション`・`複合`）にする
  - 見出しは、文型の表の順に並べ、要求が無い文型の見出しは書かない
  - 要求を機能や画面のまとまりで見出しに分けているときは、その見出しの1つ下の見出しにする（例：まとまりが `###` なら `####`）
- 文型ごとに、次の列の表にする

| 文型 | 列（日本語） | 列（英語） |
| --- | --- | --- |
| 常時 | ID・システム・応答 | ID・System・Response |
| イベント駆動 | ID・トリガー・システム・応答 | ID・Trigger・System・Response |
| 状態駆動 | ID・状態・システム・応答 | ID・State・System・Response |
| 望まない振る舞い | ID・トリガー・システム・応答 | ID・Trigger・System・Response |
| オプション | ID・機能・システム・応答 | ID・Feature・System・Response |
| 複合 | ID・状態・トリガー・システム・応答 | ID・State・Trigger・System・Response |

- 表の1行に1つの要求を書く。行を左から読むと、文型の1文になるようにする
  - トリガー・状態・機能の列は、文型のつなぎの語まで書く（`〜とき`・`〜の間`・`〜場合`・`〜を含む場合`。英語は `When`・`While`・`If`・`Where` を除いた部分）
  - 応答の列は、`しなければならない`（`shall`）を除いて書く。してはならない応答は、`〜してはならない`（`shall not`）まで書き、否定が読み取れるようにする
- セルの中の `|` は `\|` と書く

例（イベント駆動）：

```markdown
#### イベント駆動

| ID | トリガー | システム | 応答 |
| --- | --- | --- | --- |
| R-1 | 利用者が予約を確定したとき | 予約システム | 確定の通知を利用者に送る |
```

## 書く手順

1. 何を実現するかを、1〜3文で書く
2. 主語にする `<システム>` の名前を決める
3. 振る舞いを洗い出し、それぞれに文型を選ぶ
   - 正常系（常時・イベント駆動・状態駆動）を書いてから、それぞれについて今回の対象で起こりうる異常系（望まない振る舞い）を足す
4. 決まりに沿って1文ずつ書き、ID を付ける
5. 「書き出す形」のとおり、文型ごとの見出しと表に書き出す
6. 下の「見直し」で確かめて直す

## 見直し

書き終えたら、次を確かめる。

- どの要求も、表のどれか1つの文型に当てはまる
- 1つの文に、応答が1つだけある
- 応答を、第三者が観察して合否を決められる
- 合否を決められない語が無い
- 正常系のきっかけ・状態ごとに、必要な異常系がある
- 依頼に無い要求、既存の仕組みが保証する振る舞いの言い直し、今回の対象で起こりえない異常系が無い
- 同じ条件で食い違う応答を求める要求が無い
- 実装の方法を書いていない
- ID が一意で、主語の名前がそろっている
- 要求が、文型の見出しの下の、その文型の列の表にある
