# C-8 性能・リソース

見るもの：計算量、不要な呼び出し、メモリ・ファイルハンドル・接続の増加、キャッシュの無効化、バッチ化できるもの。
見ないもの：小さな対象での微細な最適化（出さない）。
起動条件：ループの中の I/O・クエリ、大量データ、N+1、メモリに全部載せる処理、キャッシュ、ホットパスの変更、再帰。

## 確かめる手順

1. 変更した処理が「何回・どれだけの量で」実行されるかを見積もる：リクエストごと、1 秒に何回、データの件数（10 件か 100 万件か）。見積もりの根拠（設計・既存のデータ量・設定の上限）を探す
2. ループを見つけ、中に I/O（DB・HTTP・ファイル・子プロセス）や重い計算（正規表現、パース、ソート、シリアライズ）があるかを見る
3. データを「全部メモリに載せる」所を探す：ファイル全体の読み込み、全行の取得、配列に積んでから処理、文字列の全体連結
4. 増え続けるもの：キャッシュ・マップ・リスト・リスナー・タイマー・goroutine/スレッドに追加だけして削除しない所
5. 計算量：ネストしたループで線形検索（O(n²)）、毎回ソート、`contains` をセットに替えられる所
6. 性能の指摘には「どの入力の規模で問題になるか」を添える。規模が小さいと分かっているなら出さない

## チェックポイント

- N+1：一覧を取ってから 1 件ずつ関連を取る（ORM の遅延ロード、ループ内の `find`）。JOIN・IN 句・バッチ API・eager load
- ループの中の I/O を直列に待つ（並列化・バッチ化できるか。並列度の上限は C-7 と相談）
- 全件読み：ストリーム・イテレータ・ページング・カーソルで処理できる所。巨大な JSON/XML の一括パース
- 不要な呼び出し：同じ値を同じリクエストの中で何度も取得・計算する。ループの外に出せる計算。毎回の設定ファイル読み込み
- 計算量：内側のループでの線形検索（ハッシュにする）、文字列の繰り返し連結（Java/Python/Go の不変文字列 → Builder）、毎回のソート、再帰の重複計算（メモ化）
- 正規表現：ホットパスで毎回コンパイル（事前コンパイル・キャッシュ）、バックトラックが爆発するパターン
- メモリ：増え続けるマップ・リスト（上限・TTL・LRU）、クロージャが大きなオブジェクトを掴む、リスナーの追加だけ、goroutine/スレッドのリーク、巨大なオブジェクトのコピー
- ファイルハンドル・接続：開いて閉じない（C-2 の失敗経路だけでなく、正常経路で数が増える）、接続プールの無いクライアントを毎回作る、プールのサイズ
- キャッシュ：無効化の条件（更新したら消すか）、キーの選び方（衝突・漏れ）、ヒット率を下げる設計、一貫性、サンダリングハード
- DB：インデックスの無い列での検索・ソート、`SELECT *`、トランザクションの長さ、ロックの範囲、OFFSET の大きいページング
- ログ：ホットパスでの大量ログ、巨大オブジェクトのシリアライズ、デバッグログの文字列を無条件に組み立てる
- 同期 I/O：イベントループ・リクエストスレッドの中のブロッキング I/O（Node の `*Sync`、asyncio の中の `requests`）
- 起動時間：モジュールのトップレベルで重い処理、不要な import、起動時の全件ロード
- タイムアウトと再試行の積：再試行 × 内側の再試行で待ち時間が掛け算になる
- アロケーション：ホットループでの不要なオブジェクト生成（GC 言語）、ボクシング、スライスの再確保
- 並列度の無制限：全件を同時に投げる `Promise.all`/`gather`/goroutine（接続数・メモリ・相手のレート制限）

## NG 例

### 例1（Ruby on Rails）：N+1

```ruby
tasks = Task.all
tasks.each { |t| puts t.owner.name }  # タスクごとに users へのクエリ
```

タスク 1,000 件で 1,001 クエリ。`Task.includes(:owner)`。一覧 API なら `must`、管理用の数十件なら出さない。

### 例2（Java）：増え続けるキャッシュ

```java
private static final Map<String, Result> cache = new HashMap<>();
Result get(String key) { return cache.computeIfAbsent(key, this::compute); }
```

キーが利用者の入力なら無限に増える（スレッド安全でもない）。上限か TTL（Caffeine 等）。常駐プロセスなら `must`。

### 例3（Python）：内側のループで線形検索

```python
for a in list_a:
    b = next((x for x in list_b if x.id == a.id), None)
```

O(n·m)。`{x.id: x for x in list_b}` にする。両方が数千件以上になりうるなら `should`、数十件なら出さない。

### 例4（Go）：全件をメモリに載せる

```go
data, _ := os.ReadFile(logPath)
lines := strings.Split(string(data), "\n")
```

ログが GB 単位になる運用なら落ちる。`bufio.Scanner`。入力の規模の根拠を添えて `should`〜`must`。

### 例5（TypeScript）：同期 I/O がリクエスト処理を止める

```ts
app.get("/config", (req, res) => res.json(JSON.parse(readFileSync(path, "utf8"))));
```

リクエストごとに同期読み込み。起動時に読むかキャッシュ。頻度が高ければ `should`。

### 例6（SQL）：インデックスの無い列で絞る

```sql
SELECT * FROM events WHERE JSON_EXTRACT(payload, '$.user_id') = ?
```

全件走査。列を持たせてインデックスを張る。テーブルが大きくなる前提なら `should`。

## 見落としやすい所

- 「いまのデータ量なら問題ない」が、増える前提が設計にあるか
- 性能の指摘の多くは推測になる。計測していないなら `confidence: medium` と書き、どの規模で問題かを明示する
- 微細な最適化（ループの書き方、文字列連結の 2 回程度）は出さない

## 指摘の書き方の例

- title：`タスク一覧で所有者をタスクごとに取得し、件数分のクエリになる`
- problem：`Task.all の後に t.owner で 1 件ずつクエリが出る。一覧 API はページ上限が 200 件（app/controllers/tasks_controller.rb:12）なので、1 リクエストで最大 201 クエリ`
- evidence：`app/views/tasks/index.json.jbuilder:5 を読み、ページ上限の設定を確かめた。計測はしていない`
- suggestion：`includes(:owner) で一括ロードする`
