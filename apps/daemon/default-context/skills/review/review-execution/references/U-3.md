# U-3 読み手の適合

見るもの：想定読者と前提知識が合っているか、用語の説明、最初に知るべきことが先にあるか、目的別に探せる構成、例の適切さ。
見ないもの：表記の細部（U-4）。

## 確かめる手順

1. 文書の想定読者を特定する（初めての利用者・運用者・開発者・管理者）。文書に明示があるか、無ければ内容から推定する
2. その読者が知らないはずの用語・概念・前提が、説明なしに使われていないか。逆に、読者が知っているはずのことを冗長に説明していないか
3. 読者の目的（導入したい・使いたい・直したい・調べたい）ごとに、必要な情報に最短で辿れるか。見出し・目次・冒頭の要約
4. 最初に知るべきこと（何ができるか・何が要るか・注意すべきこと）が先にあり、詳細が後にあるか
5. 例：読者の実際の状況に近いか、最小で動くか、例の値が現実的か（`foo`・`bar` だけでない）

## チェックポイント

- 想定読者の不明：開発者向けの内部構造の説明と、利用者向けの操作説明が混ざる
- 前提知識の不一致：読者が知らない用語（内部の概念・略語・他ツールの知識）を説明なしに使う。用語集・リンクの有無
- 順序：詳細な設定の説明が先で、「何をするツールか」が後。導入の手順の前に高度な使い方
- 構成：目的別に探せない（「〜したいとき」の見出しが無い）、1 つの長い節、目次が無い長い文書
- 冒頭の要約：何ができ・誰のためで・何が要るかが最初の数行で分かるか
- 例の適切さ：最小で動く例があるか、例が複雑すぎる・単純すぎる、例の値が現実的か、例が本文の説明と対応しているか
- 概念の説明：仕組みを知らないと操作の意味が分からない所で、仕組みの説明（図・一文）があるか
- 「なぜ」の説明：手順の理由が無く、応用や判断ができない（手順の成立は U-2。理由の有無はここ）
- 選択肢の提示：複数の方法があるとき、どれをいつ選ぶかの指針
- よくある質問・つまずき：初めての人が必ず当たる問題への案内
- 情報の過多：読者に不要な詳細（内部実装・歴史）が本流を遮る。付録・別文書へ
- 対象外の明示：この文書で扱わないことと、その参照先
- 一貫した視点：「あなた」「利用者」「我々」の混在、読者を誰と想定しているかの揺れ

## NG 例

### 例1：用語の説明が無い

```
取り込んだチケットはトリアージの後、ゲートで判定されます。
```

初めての利用者に「取り込み」「トリアージ」「ゲート」の説明が無い。用語の節かリンク。`should`。

### 例2：詳細が先

README の最初の節が全設定項目の一覧（50 行）で、「何をするツールか」「まず動かすには」が 3 節目。`should`。

### 例3：例が非現実的

```yaml
repo: foo
token: bar
```

実際には URL の形式と、トークンの入手先が要る。読者は何を入れればよいか分からない。`should`。

### 例4：読者の混在

利用者向けの操作手順の途中に、内部の DB スキーマの説明が入り、操作の流れが途切れる。開発者向けの文書に分ける。`should`。

### 例5：最小の例が無い

高度なオプションを全部使った例だけがあり、最小で動く例が無い。初めての人が削り方を判断できない。`should`。

### 例6：なぜが無い

「この設定は必ず false にしてください」とあるが理由が無く、別の状況で true にしてよいか判断できない。`nit`〜`should`。

## 見落としやすい所

- 書いた人は内容を知っているので、知らない人の視点を失いやすい。「初めて読む人」を具体的に想像して読む
- 「分かりにくい」で止めず、どの読者がどこで何を知らないために止まるかを書く
- 読みやすさの好み（文体・段落の長さ）は `nit`。読者が目的を果たせないことと区別する

## 指摘の書き方の例

- title：`初めての利用者向けの冒頭で、未定義の用語（取り込み・トリアージ・ゲート）が説明なしに使われる`
- problem：`README の「概要」は利用者向けだが、2 段落目で「取り込み」「トリアージ」「ゲート」を説明なしに使う。用語集も無く、初めて読む人は流れを理解できない`
- evidence：`README.md の概要と全体を読み、各語の初出と定義の有無を確かめた`
- suggestion：`概要の直後に用語の節を置くか、初出で 1 文の説明を添える`
