# D-3 完全性

見るもの：今回の変更で起こりうる異常系・境界・失敗時の振る舞い、影響範囲、既存機能への影響、移行・ロールバック、運用（監視・設定）、並行・性能の考慮が必要な箇所が書かれているか。
見ないもの：書かれている内容の正しさ（D-2）、書きすぎ（D-10）。

「書かれていないこと」を探す観点。書かれていることの是非は他の観点に任せる。
指摘は文書を長くし、承認する人が読む量を増やす。指摘にするのは、書かれていないと実装や運用が誤る・揺れる欠落だけにする。

## 確かめる手順

1. 今回の変更が足した・変えた処理の流れの各段階について「ここで失敗したら」「ここに来る入力が異常なら」「ここが遅かったら」を問い、答えが文書にあるかを確かめる
2. 影響範囲：変更が触れる既存の機能・データ・利用者・他システムを列挙し、それぞれへの影響が書かれているか
3. ライフサイクル：導入（移行・初期データ・設定）、運用（監視・ログ・手動の操作）、変更（互換・バージョン）、撤去（ロールバック・データの扱い）の各段階が書かれているか
4. 非機能：性能・容量・並行・可用性・セキュリティ・保守のうち、今回の変更が関係する項目について、対応が書かれているか。関係しない項目に「対象外」の記載を求めない
5. 境界：入力の上限・下限・空・重複・同時、利用者の権限の違い、環境の違い

## チェックポイント

- 異常系：外部の失敗、タイムアウト、不正な入力、権限なし、部分的な成功、途中での停止、再試行の扱い
- 境界：0 件・1 件・上限、空文字、最大長、同時に同じ操作、期限ちょうど
- 状態：すべての状態と遷移が書かれているか、途中状態（処理中）からの復帰、不整合な状態の検出と修復
- 影響範囲：既存の API・画面・バッチ・レポートへの影響、既存データの扱い、他チーム・他システムへの連絡
- 移行：既存データの変換、段階的な切り替え、新旧の共存期間、切り戻し
- ロールバック：戻せるか、戻したときのデータ、戻す判断の基準
- 運用：監視（何を見て異常と分かるか）、アラート、ログ、手動の操作（再実行・修正）、設定項目とその既定値、容量の見積もり
- 性能・容量：想定の量と増加、ボトルネックの見積もり、上限に達したときの振る舞い
- 並行：同時実行、順序、重複、ロック（要件が無ければ「単一実行を前提」と明示されているか）
- セキュリティ：認証・認可・データの分類・ログに残すもの（詳細は D-5。ここでは「節が無い」ことを見る）
- テスト：どう検証するか（テスト観点・環境・データ）。D-4 の詳細ではなく、節の有無
- 依存：外部サービス・ライブラリ・他チームの成果物への依存と、それが遅れたときの扱い
- 期限・段階：フェーズ分けがあるなら各段階の完了条件
- 用語・ID：新しい概念の定義、ID の体系（D-6 と接する。概念そのものの欠落はここ）
- 「対象外」の明示：書かないことが「考えていない」のか「意図して外した」のか区別できるか

## NG 例

### 例1：異常系の節が無い

正常な流れが 2 ページ書かれているが、外部 API の失敗・タイムアウト・不正な入力の扱いが一切無い。実装者が各自で決めることになる。`must`。

### 例2：移行が無い

既存の `status` 列を `state` に変える設計だが、既存の 300 万行の扱い（変換するか、読み込みで解釈するか、いつ）が書かれていない。`must`。

### 例3：運用の節が無い

常駐のワーカーを追加する設計で、止まったときにどう気づくか、再起動の手順、設定項目が無い。`should`、障害時の影響が大きければ `must`。

### 例4：同時実行の未記載

「毎時バッチが集計する」とあるが、前回が終わらないうちに次が始まる場合の扱いが無い。単一実行の保証も書かれていない。`should`。

### 例5：影響範囲の未記載

タスクの ID の体系を変える設計で、ID を表示・リンクしている既存の画面・通知・外部連携への影響が書かれていない。`must`。

### 例6：変更が関係する非機能の未記載

一覧の API に全件を返す取得を足す設計で、件数が増えたときの上限・ページ分けが書かれていない。対象のデータは 1 日数万件増える。`should`。

## 指摘にしないもの

- 既存の仕組み（フレームワーク・基盤・既存のコード）が扱っていて、今回の変更で変わらない異常系・境界
- 今回の変更が関係しない観点（性能・移行・運用など）の節が無いこと。「対象外」と書くことも求めない
- 実装の既定（リポジトリの規約・既存の実装）で一意に決まり、書かなくても実装が揺れない細部

## 見落としやすい所

- 正常系が詳しいほど、異常系の欠落が目立たない。段階ごとに「失敗したら」を機械的に問う
- 「既存の仕組みに従う」で済ませている所。その仕組みが本当にこの場合を扱えるか（D-2 に知らせる）
- 欠落を全部 `must` にしない。影響の大きさ（データ損失・停止・セキュリティ）で重み付けし、小さいものは `should` にまとめる

## 指摘の書き方の例

- title：`外部 API の失敗・タイムアウト時の振る舞いが設計に無い`
- problem：`3 章の流れは成功だけを扱い、通知先の API が 5xx・タイムアウト・429 を返したときに、再試行するか・失敗を誰に伝えるか・ジョブの状態をどうするかが決まっていない。実装者が各自で決めると挙動が揺れる`
- evidence：`docs/design/notify.md の全節を読み、「失敗」「タイムアウト」「再試行」の語が無いことを確かめた`
- suggestion：`異常系の節を足し、失敗の種類ごとに、再試行の方針・最終的な失敗の記録先・運用者への通知を書く`
