# C-9 データ・永続化・移行

見るもの：移行の順序と可逆性、既存データとの両立、デプロイの途中（新旧が混在）での動作、インデックス・制約、デフォルト値、データの破損の可能性。
見ないもの：読み書きの論理の誤り（C-1）。
起動条件：DB スキーマ、マイグレーション、永続データの形式、シリアライズ、ファイルの構造を変える。

移行の仕組みは問わない（Flyway・Liquibase・Alembic・Rails migration・golang-migrate・Prisma・手書き SQL・JSON ファイルの版上げなど）。

## 確かめる手順

1. 変更前と後のデータの形（スキーマ、JSON の形、ファイルの構造、シリアライズ形式）を並べて書き、違いを列挙する：追加・削除・改名・型の変更・制約の追加・既定値
2. 「すでに保存されているデータ」が変更後のコードで読めるか、1 つずつ確かめる。NULL・欠けたキー・古い enum 値・古い版番号
3. 移行の手順を追う：順序（列を足してから埋めるか）、失敗したときの状態、再実行できるか（冪等）、戻せるか（down）
4. デプロイの途中を想像する：新しいコードと古いコードが同時に動く時間、古いコードが新しいデータを読む、片方だけが移行済み、複数インスタンスが同時に移行を実行
5. 制約・インデックス：一意性・外部キー・NOT NULL を足すとき既存データが満たすか。インデックスの追加が本番で時間・ロックを要しないか

## チェックポイント

- 移行の欠落：形を変えたのに移行がない（既存データが読めなくなる）。移行はあるが新しい書き込みが古い形のまま
- 順序：NOT NULL の列を既定値なしで足す、列を消す前にコードが参照しなくなっているか、複数段階の移行を 1 デプロイで行う危険（expand → migrate → contract）
- 冪等性：移行を 2 回実行しても壊れないか（`IF NOT EXISTS`、済みの記録）。複数インスタンスの同時実行の防止
- 可逆性：down の移行があるか、無いなら戻せない変更だと明示されているか。データを失う変更（列の削除・型を狭める）は先にバックアップか段階化
- 既存データの前提：NULL が入っている列に NOT NULL、重複がある列に UNIQUE、長さ超過、外部キーの孤児
- 型の変更：文字列 → 数値（変換できない値）、精度の低下（float → int、decimal の桁、タイムゾーンの喪失）、文字コード・照合順序
- 既定値：DB の既定とアプリの既定の不一致、既定値の変更が既存行に適用されるか、ORM 側だけの既定
- 新旧の混在：古いコードが知らないキー・enum 値を書かれて落ちる、新しいコードが古い行の欠けたキーで落ちる。前方・後方の両方
- ID・キー：自然キーの変更、ID の再利用、外部に公開した ID の形の変更、自動採番の衝突
- シリアライズ：版番号の有無、未知のキーの扱い（捨てるか保持するか）、日時の形式、null と欠落の区別、大きな整数の精度（JSON）、浮動小数、バイナリ
- ファイル形式：改行・文字コード・BOM、部分書き込み（C-2）、同時書き込み（C-7）、原子的な置き換え
- 破損の検出：読めなかったときに黙って既定で上書きしていないか（データを失う）。壊れたデータを隔離して続けるか止めるか
- 時刻：UTC で保存しているか、タイムゾーン付きか、ミリ秒か秒か。既存データと混ざらないか
- 削除：物理削除で参照が切れる所、論理削除のフラグを見ていないクエリ、カスケード削除の範囲
- 容量・性能：大きなテーブルへの ALTER（ロック時間、MySQL/PostgreSQL の差）、インデックスの追加（CONCURRENTLY）。本番の規模の根拠
- バックアップ・復元の手順への影響、レプリケーションへの影響

## NG 例

### 例1（Python）：形を変えたが既存データを読めない

```python
# before: {"status": "open" | "closed"}
# after:  {"state": {"kind": "open"}}
kind = task["state"]["kind"]   # 古い行は state が無く KeyError
```

読み込み時の変換（`status` があれば `state` に写す）か、一括移行。`must`。

### 例2（SQL）：移行の順序が壊れる

```sql
ALTER TABLE tasks ADD COLUMN owner_id INTEGER NOT NULL;
```

既存行があると失敗する（または DB によっては 0 で埋まり、外部キーが壊れる）。既定値付きで足す → 埋める → NOT NULL にする。`must`。

### 例3（Go）：読めなかったら既定で上書き

```go
state, err := load(path)
if err != nil { state = defaultState() }
save(path, state)   // 壊れていた元のファイルが消える
```

一時的な読み取り失敗や自分のバグで、データを失う。読めないファイルは別名に退避し、止めるか警告する。`must`。

### 例4（Java/Flyway）：移行が再実行できない

```sql
-- V12__add_note.sql
ALTER TABLE tasks ADD COLUMN note TEXT;
```

Flyway は済みを記録するが、手書きの移行スクリプトで記録が無ければ、途中で落ちて再実行すると「列がある」で止まる。仕組みに済みの記録が無いなら `must`、あるなら出さない。

### 例5（Rails）：デプロイの途中で古いコードが落ちる

新しいコードが `priority: "urgent"` を書き始めるが、同時に動く古いインスタンスの `case` は `else raise`。段階化（先に読める版をデプロイ）。複数版が同時に動く運用なら `must`。

### 例6（JSON のファイル）：版番号が無い

```json
{ "tasks": [ ... ] }
```

形を変えるたびに「どの形か」を推測で判定することになる。`"version": 2` を持たせ、読み込みで分岐。`should`（今回の変更で形が変わるなら）。

## 見落としやすい所

- JSON・YAML・CSV のファイルも「永続データ」。スキーマの無い分、形の変更が検出されない
- 「開発環境では動く」は、既存データが無いから。本番のデータの多様さ（NULL、古い形式、重複、巨大）を想定する
- 移行そのもののテスト（古い形のデータを用意して読む）があるか。無ければ C-4 に知らせる

## 指摘の書き方の例

- title：`state への移行が無く、既存のタスクの行を読むと KeyError になる`
- problem：`Task の status を state に変えたが、既存の行は status しか持たない。task["state"]["kind"] の参照で落ち、一覧 API 全体が 500 になる`
- evidence：`app/models/task.py と app/store/read.py:21 を読んだ。migrations/ に対応する移行が無いことを確かめた`
- suggestion：`読み込み時に status → state の変換を入れるか、移行を足す。古い形の行を読むテストを足す`
