# D-9 外部連携

見るもの：契約（I/F・SLA・認証・バージョン）の明示、相手の障害時の振る舞い、責任の分界。
見ないもの：自システム内の流れ（D-2）。
起動条件：他システム・外部 API・組織外との契約がある。

## 確かめる手順

1. 外部との接点を列挙する：呼ぶ相手、呼ばれる経路、やり取りするデータ、頻度・量
2. 接点ごとに契約が明示されているか：I/F の仕様（版・スキーマ・文書の所在）、認証の方式、レート制限・SLA、データの形式と文字コード、時刻の基準
3. 相手が落ちた・遅い・仕様を変えた・想定外を返したときの自分側の振る舞いが設計されているか
4. 責任の分界：どこまでが自分の責任で、どこからが相手か。障害時に誰が誰に連絡するか、データの正はどちらか
5. 相手側の作業：相手に設定・開発・承認を依頼する必要があるか、その時期と依頼先

## チェックポイント

- 契約の未記載：「X の API を呼ぶ」だけで、どの版・どのエンドポイント・どの認証か無い
- 仕様の所在：相手の文書へのリンク・版・確認日が無い。口頭の合意だけ
- 認証：方式（API キー・OAuth・mTLS）、鍵の発行と更新の手続き、失効時の対応、鍵の保管（D-5 と接する）
- レート制限・SLA：相手の上限と自分の呼び出し量の見積もりの整合、SLA を超えたときの扱い、契約上の上限
- データの形式：スキーマ・必須項目・enum・日時の形式とタイムゾーン・文字コード・サイズの上限・ページング
- 版・互換：相手の版の固定、変更の通知を受ける経路、非互換の変更への備え
- 相手の障害：タイムアウト・リトライ・サーキットブレーカー・縮退運転（相手無しで動く範囲）の方針
- 相手の想定外：エラーを 200 で返す、スキーマ違反、順序の逆転、重複配信、遅延。検証と記録
- 冪等性・重複：再送が起きる前提での設計（C-10 の内容を設計で扱っているか）
- 責任の分界：データの正、変換の責任、障害時の連絡経路と窓口、監視の分担
- 相手側の作業：IP 許可・アカウント発行・Webhook の登録・契約。時期と依頼先、遅れたときの影響
- テスト環境：相手のサンドボックスの有無、本番と違う点、テストデータ
- 監査・コンプライアンス：相手にデータを渡す規約（D-5）、ログの保持
- 撤退：相手を替える・やめるときの影響範囲（ロックイン）
- 費用：呼び出し量に応じた課金、上限

## NG 例

### 例1：契約の未記載

```
翻訳は外部の翻訳 API を使う。
```

どのサービスの・どの版・どの認証・上限はいくらか。設計の成立が判断できない。`must`。

### 例2：相手の障害の未検討

決済 API を同期で呼び、応答を待って画面に結果を出す設計で、API が落ちた・遅いときの扱い（タイムアウト・利用者への表示・後で確認する手段）が無い。`must`。

### 例3：レート制限との不整合

相手の上限は 1 分 60 回だが、設計は「タスクごとに 3 回呼ぶ」で、ピーク時 1 分 200 タスク。上限を超えて失敗する。`must`。

### 例4：責任の分界が曖昧

「在庫の情報は両システムで持つ」とあるが、どちらが正か、不一致のときどう直すかが無い。`should`、金額・在庫など業務に直結するなら `must`。

### 例5：相手側の作業の未記載

Webhook を受ける設計だが、相手に Webhook の URL を登録してもらう必要があり、その依頼先・時期・テストの方法が無い。`should`。

### 例6：版の未固定

「相手の API の最新版を使う」。相手の変更で突然壊れる。版を固定し、変更の通知を受ける。`should`。

## 見落としやすい所

- 同じ組織の他システムも「外部」。契約が口頭で済まされやすい
- 相手の文書を読まずに設計書を評価しない。相手の仕様（上限・形式）を実際に確かめる
- 外部連携の多くは「相手が正常」の前提で書かれる。障害・変更・想定外の 3 つを機械的に問う

## 指摘の書き方の例

- title：`翻訳 API の契約（サービス・版・認証・上限）が設計に無い`
- problem：`3.3 は「外部の翻訳 API を使う」とだけあり、どのサービスか・認証の方式・レート制限・費用の上限が無い。1 日の呼び出し量（3.1 の見積もりで約 2 万回）が相手の上限に収まるか判断できない`
- evidence：`docs/design/i18n.md 3.1・3.3 を読んだ`
- suggestion：`サービス名・API の版・文書のリンク・認証方式・上限と費用・障害時の縮退（原文のまま表示）を書く`
