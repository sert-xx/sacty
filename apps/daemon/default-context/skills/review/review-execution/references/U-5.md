# U-5 安全性

見るもの：取り返しのつかない操作の警告と確認、秘密情報を文書に書かせない、最小の権限、実行する環境の取り違えの防止。
見ないもの：手順の順序（U-2）。
起動条件：破壊的な操作（削除・上書き・force push・本番環境への適用）、秘密情報、権限の付与を含む手順。

## 確かめる手順

1. 手順の中の「戻せない操作」を列挙する：削除、上書き、履歴の書き換え、本番への適用、権限の付与・剥奪、課金の発生、外部への送信
2. それぞれの直前に、何が起きるか・戻せないこと・事前の確認（バックアップ・対象の確認）が書かれているか
3. 秘密情報：文書に本物の値（トークン・パスワード・鍵・内部 URL）が書かれていないか。プレースホルダーの形が本物と見分けられるか。入手と保管の方法が安全か
4. 権限：手順が要求する権限が最小か、`sudo`・管理者・広いスコープのトークンが本当に要るか、一時的な権限を戻す段階があるか
5. 環境の取り違え：本番と検証で同じコマンドを使う手順で、どちらに向いているかを確かめる段階があるか。環境名の明示、プロンプトでの確認

## チェックポイント

- 破壊的な操作の警告：`rm -rf`、`DROP`、`TRUNCATE`、`git push --force`、`reset --hard`、`kubectl delete`、本番 DB への移行、料金の発生する操作
- 事前の確認：バックアップ、対象の件数・名前の確認（dry-run・`--dry-run`・`SELECT` で確かめてから `DELETE`）、影響範囲の表示
- 取り消しの手段：戻す手順、戻せない場合の明示
- 秘密情報の直書き：例に本物らしいトークン・パスワード・内部のホスト名・個人情報、スクリーンショットに秘密情報
- 秘密情報の扱いの指示：コマンドライン引数に渡す（履歴・`ps` に残る）、平文のファイルに保存、チャットで共有、ログに出す手順
- 権限：`sudo` の濫用、`chmod 777`、全権限のトークン、管理者アカウントでの日常作業、権限を付けた後に戻さない
- 環境の取り違え：本番・検証・開発で同じ手順を使うときの区別（環境変数・コンテキスト・プロファイルの確認段階）、既定が本番になっている
- 外部への送信：外部サービス・公開リポジトリ・チャットへデータを送る手順で、送るデータの範囲と確認
- 自動化の危険：手順をスクリプトにしたときに確認が消える、cron で破壊的な操作
- `curl | sh`：検証なしに外部のスクリプトを実行する手順、ダウンロードの検証（チェックサム・署名）
- 共有環境への影響：他の利用者・他のサービスに影響する操作（再起動・ポートの占有・共有ファイルの変更）の周知
- 失敗時の安全：途中で失敗したときに危険な中間状態（権限が開いたまま、サービスが止まったまま）が残る手順
- 監査：誰が実行したかが残るべき操作で、個人を特定できるアカウントで行う指示があるか

## NG 例

### 例1：警告の無い破壊的な操作

```
3. データを初期化する: rm -rf data/ && tool init
```

既存のデータが消えることの警告・バックアップの指示が無い。`must`。

### 例2：本物らしい秘密情報

```yaml
token: ghp_8sK2...（本物の形式の 40 文字）
```

例が本物のトークンの可能性があり、そうでなくても本物と見分けられない。`<GitHub の Personal Access Token>` の形に。本物なら `must`（C-3 に当たる重大事）、形式だけなら `should`。

### 例3：環境の取り違え

```
kubectl apply -f deploy.yaml
```

本番・検証の手順が同じで、どちらのコンテキストかを確かめる段階（`kubectl config current-context`）が無い。`must`。

### 例4：秘密情報をコマンドライン引数に

```
$ tool login --password mypassword
```

シェルの履歴と `ps` に残る。環境変数・標準入力・プロンプトで渡す。`should`。

### 例5：過剰な権限

「権限のエラーが出たら `sudo` を付けて実行してください」。原因を直さず全権限で実行させる。`should`。

### 例6：検証なしの外部スクリプト

```
curl -fsSL https://example.com/install.sh | sh
```

内容を確認せず実行する。チェックサムの確認か、ダウンロードして内容を見る段階。組織の規定次第で `should`〜`must`。

## 見落としやすい所

- 「開発環境向け」の手順が本番でも使われる。文書が環境を限定しているか
- 秘密情報の例は、形式が本物と同じだと検索やスキャンに引っかかり、本物かどうかの確認の手間を生む
- 破壊的な操作は 1 行の中に埋もれる（`&&` で連結）。コマンドを 1 つずつ読む

## 指摘の書き方の例

- title：`初期化の手順が既存データを警告なしに削除する`
- problem：`docs/setup.md 3 の rm -rf data/ && tool init は、既存の data/ を消す。再セットアップで実行する人が過去のデータを失う。警告もバックアップの指示も無い`
- evidence：`docs/setup.md 3 と、data/ に永続データが置かれること（src/store.py:12）を確かめた`
- suggestion：`警告を入れ、バックアップ（mv data data.bak）の段階を先に置く。初期化が要らない再セットアップの手順を分ける`
