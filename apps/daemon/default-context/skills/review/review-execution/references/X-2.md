# X-2 横断（検証結果の分析）

見るもの：親が実行した検証コマンド（フォーマッター・リンター・型チェック・テスト・ビルド）の結果と CI の結果を読み、失敗・警告・実行されなかった検証を、変更のどこが原因かと結びつける。今回の変更が持ち込んだ失敗か既存の失敗か、不安定なテスト、検証を黙らせる変更（リントの無効化・型エラーの抑止・閾値の緩和）、ローカルと CI の結果の食い違い。
見ないもの：テストの設計の良し悪し（C-4）、依存・ビルド・CI の設定の変更そのものの妥当性（C-11）、検証が通っているコードの論理の誤り（C-1 など各観点）。

依頼文の「検証の結果」に、`summary.json`（コマンドごとの種類・状態・終了コード・ログの場所）の場所が書かれている。まずそれを読む。

## 確かめる手順

1. `summary.json` を読み、コマンドを `failed`・`error`・`timeout`・`skipped`・`passed` に分ける。`not_found`（見つからなかった種類）と `ci` も確かめる
2. `failed` のコマンドごとにログを読み、失敗を 1 件ずつ取り出す（テスト名・リントのルール・型エラーのメッセージ・ファイルと行）。件数が多いときは同じ原因ごとにまとめる
3. 失敗ごとに原因の箇所をコードで特定する。スタックトレース・エラーの行から差分の変更箇所へたどる。ログの行番号が差分のどこに当たるかを確かめる
4. 今回の変更が持ち込んだ失敗かを判断する。`note` の「ベースでも失敗／ベースでは成功」を使う。比較が無いときは、失敗の箇所・原因が差分に含まれるかで判断し、根拠を `evidence` に書く
5. `error`・`timeout` の原因を読む（依存の不整合・設定の誤り・無限ループ・環境の不足）。変更が原因（新しい依存を入れ忘れた・設定ファイルを壊した）なら指摘にし、環境の問題なら `limitations` に書く
6. `passed` でも、ログで警告の増加・skip されたテスト・0 件のテスト実行（`collected 0 items`・`no test files`）が無いかを確かめる
7. 差分で、検証を黙らせる変更を探す（下のチェックポイント）
8. CI の結果があれば、ローカルの結果と比べる。CI だけで失敗している・ローカルだけで失敗している場合は、環境差の原因を推定し、根拠を書く
9. 必要なら、対象を変更しない範囲で、失敗した個別のテストやリンターを対象のファイルに絞って再実行して確かめてよい（結果は `evidence` に書く）

## チェックポイント

- 変更が持ち込んだテストの失敗：変更した関数・分岐・期待値が原因で落ちている
- 変更が持ち込んだリント・型エラー：差分の行に対する違反。CI で必須のチェックなら、マージを止める
- フォーマットの差分：確認モードで差分が出ている。CI で必須なら `must`、そうでなければ `should`
- 既存の失敗：ベースでも失敗している。今回の変更の指摘にはしない（`checked` に記録）。ただし、今回の変更で失敗が増えた・既存の失敗が新しい失敗を隠しているなら指摘する
- 不安定なテスト：再実行で結果が変わった。変更した箇所が関係するか（時刻・順序・並行）を確かめる
- 実行されていない検証：新しいテストファイルがテストのコマンドで拾われていない（実行件数が増えていない）、`skipped` の理由が変更による、`not_found` で CI にはある検証がローカルで見つからない
- 検証を黙らせる変更：`eslint-disable`・`# noqa`・`# type: ignore`・`@ts-ignore`・`@ts-expect-error`・`//nolint`・`#[allow(...)]`・`@SuppressWarnings` の追加、リンターの設定でルールを外す・対象から外す、カバレッジや警告の閾値を下げる、CI のジョブを `continue-on-error` にする。理由の説明が無ければ指摘する
- 警告の増加：ビルド・リンター・テストの警告（deprecation など）が変更で増えている
- ローカルと CI の食い違い：版の違い・環境変数・OS・タイムゾーン・並列度の差。どちらが正しいかを根拠とともに書く
- `error` の原因：依存の追加漏れ・ロックファイルとの不整合・設定ファイルの構文の誤りなど、変更が原因のもの

## NG 例

### 例1：変更が持ち込んだテストの失敗

```
FAILED tests/test_price.py::test_discount_zero - ZeroDivisionError
```

ベースでは成功。`src/price.py:30` で割引率の計算を変え、0 のときに割り算する。`must`。`path` は原因の `src/price.py:30`（テストのファイルではない）。

### 例2：リントの無効化で通している

```diff
+ // eslint-disable-next-line @typescript-eslint/no-floating-promises
  sendAudit(event);
```

リンターは通るが、await の漏れを黙らせている。理由の説明が無い。`should`（実害がある経路なら `must`）。

### 例3：新しいテストが実行されていない

`tests/new_feature.spec.ts` を追加したが、テストのログの実行件数がベースと同じ。ランナーの対象が `*.test.ts` だけ。テストは一度も実行されていない。`must`。

### 例4：既存の失敗

`test_legacy_import` はベースでも失敗している。今回の変更と関係しない。指摘にしない（`checked` に「既存の失敗：ベースでも失敗」と記録）。

### 例5：依存の追加漏れで止まった

```
ModuleNotFoundError: No module named 'httpx'
```

差分で `import httpx` を追加したが、`pyproject.toml` に依存が無い。テストが実行の前に止まっている（`error`）。`must`。

## 見落としやすい所

- 終了コードが 0 でも、ログに `0 tests`・`skipped`・警告が出ている
- 失敗の件数が多いときに、先頭の数件だけを見て残りを見ない。原因ごとにまとめて全件を分類する
- テストのファイルに失敗が出ていても、原因は実装の変更にある。`path` は原因の箇所にする
- 検証を黙らせる 1 行の追加は差分の中で目立たない。差分を抑止の語で検索する

## 指摘の書き方の例

- title：`割引率が 0 のとき割り算で例外になり、test_discount_zero が失敗する`
- problem：`src/price.py:30 の変更で、割引率 0 のときも rate で割るようになった。test_discount_zero が ZeroDivisionError で失敗する`
- evidence：`summary.json の pytest が failed。ログ（test-pytest.log）の 120 行目に ZeroDivisionError と src/price.py:30 のトレース。ベースでは成功（note）`
- suggestion：`rate が 0 のときの分岐を戻す。境界のテストは既にあるので、それが通ることを確かめる`
