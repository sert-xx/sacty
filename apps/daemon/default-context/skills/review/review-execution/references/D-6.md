# D-6 形式・明確さ

見るもの：曖昧な語・未定義の用語、文書内の矛盾、読み手が同じ理解に至れるか、構成（必要な節があるか・順序）、図と本文の一致、リンクと参照の正しさ。
見ないもの：内容の妥当性（D-1〜D-5）。

## 確かめる手順

1. 想定読者（実装者・レビュアー・運用者・将来の保守者）を決め、その読者が「この文書だけで同じ理解に至れるか」を問いながら読む
2. 曖昧な語を拾う：「適切に」「必要に応じて」「など」「基本的に」「原則として」「可能であれば」「将来的に」。それぞれ、具体に置き換えられるか
3. 用語：初出で定義されているか、同じ概念に別の語を使っていないか、プロジェクトの用語集・既存文書と一致するか
4. 矛盾：節の間、図と本文、表と本文、冒頭の要約と本文で食い違う所
5. 構成：読者が必要な情報に辿れるか（目次、節の順序、要約）。長すぎる節、1 文が長い、箇条書きの粒度の混在
6. 参照：リンク先が存在するか、参照する節番号・図番号が正しいか、外部文書の版

## チェックポイント

- 曖昧な語の多用（上記）。特に判断を含む所（「必要なら再試行」の「必要」とは）
- 未定義の用語・略語、同じ概念の表記揺れ（「タスク」と「チケット」、「承認」と「マージ」）
- 主語の無い文（誰がやるのか）、受動態で主体が隠れる文
- 文書内の矛盾：数値（上限・期間）、名前（API・テーブル）、手順の順序、状態の名前
- 図と本文の不一致：図にあるが本文に無い要素、矢印の向き・数、ラベルの違い
- 構成：背景・目的・範囲・設計・異常系・運用・検証・未決事項のうち、その文書の種類に要る節が無い。順序が追いにくい（詳細が先、目的が後）
- 粒度：箇条書きの中に段落が混ざる、1 つの箇条書きに複数の決定、見出しの階層の飛び
- 「未決事項」「確認したいこと」が本文に混ざり、決定と区別できない
- 決定と案の区別：「〜する」と「〜する案もある」が混ざる。何が決まったことか
- 数値の単位・基準の欠落（「30 以内」の単位、「午前 3 時」のタイムゾーン）
- 参照の誤り：節番号・図番号のずれ、リンク切れ、古い版の文書への参照
- 表：列の意味が無い、空欄の意味（未定か該当なしか）
- 変更履歴：版・日付・変更点があるか（文書の種類が要求するとき）
- 言語・文体：敬体・常体の混在、句読点、記号の揺れ（nit に留める）

## NG 例

### 例1：曖昧な判断

```
失敗した場合は必要に応じて再試行する。
```

「必要」の基準（どの失敗を・何回・間隔）が無く、実装者ごとに違う。`must`（判断を含む曖昧さ）。

### 例2：文書内の矛盾

2.3 では「保持期間は 30 日」、5.1 では「90 日後に削除」。どちらが正か。`must`。

### 例3：未定義の用語

「ゲートを通過したタスクは次の工程に進む」とあるが、「ゲート」の定義が文書内に無く、用語集にも無い。`should`。

### 例4：決定と案の混在

```
通知は Slack で送る。メールで送る案もある。
```

決定なのか、未決なのか。未決なら「未決事項」の節に移す。`should`。

### 例5：主語の無い文

```
承認されたら、ブランチをマージして、通知を送る。
```

誰が承認し、誰（人か・システムか）がマージし、誰に通知するか。`should`、責務の所在に関わるなら D-2 に知らせる。

### 例6：単位の欠落

```
タイムアウト: 30
```

秒かミリ秒か分か。`should`。

## 見落としやすい所

- 書き手が分かっていることは省かれる。読者が実装者だけでなく運用者・将来の保守者であることを想定する
- 「分かりにくい」で止めず、どの文のどの語が 2 通りに読めるかを書く
- 文体・記号の揺れは `nit`。判断や決定に関わる曖昧さと混ぜない

## 指摘の書き方の例

- title：`「必要に応じて再試行」の基準が無く、実装者ごとに挙動が分かれる`
- problem：`3.4 の「失敗した場合は必要に応じて再試行する」は、どの失敗（タイムアウト・5xx・4xx）を・何回・どの間隔で再試行するかを決めていない。再試行の有無は二重送信の有無に直結する`
- evidence：`docs/design/notify.md 3.4。異常系の節（4 章）にも再試行の条件は無い`
- suggestion：`再試行する失敗の種類・回数・間隔・最終的な失敗の扱いを表にする`
