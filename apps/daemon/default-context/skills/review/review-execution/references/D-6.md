# D-6 形式・明確さ

見るもの：曖昧な語・未定義の用語、文書内の矛盾、読み手が同じ理解に至れるか、構成（必要な節があるか・順序）、図と本文の一致、リンクと参照の正しさ、（要求要件・設計など、人が承認する成果物のとき）本文に残った作業の経過・指摘への対応の報告・エージェント向けのメモ、理由の分からない ID の欠番、別の文書を参照するだけの項目。
見ないもの：内容の妥当性（D-1〜D-5）。

## 確かめる手順

1. 想定読者（実装者・レビュアー・運用者・将来の保守者）を決め、その読者が「この文書だけで同じ理解に至れるか」を問いながら読む
2. 曖昧な語を拾う：「適切に」「必要に応じて」「など」「基本的に」「原則として」「可能であれば」「将来的に」。それぞれ、具体に置き換えられるか
3. 用語：初出で定義されているか、同じ概念に別の語を使っていないか、プロジェクトの用語集・既存文書と一致するか
4. 矛盾：節の間、図と本文、表と本文、冒頭の要約と本文で食い違う所
5. 構成：読者が必要な情報に辿れるか（目次、節の順序、要約）。長すぎる節、1 文が長い、箇条書きの粒度の混在
6. 参照：リンク先が存在するか、参照する節番号・図番号が正しいか、外部文書の版
要求要件・設計など、人が承認する成果物では、次の7〜9も確かめる。変更履歴・作業履歴・経緯の節がある文書（ADR・CHANGELOG・README など）は、そこに経過が書かれていて当然なので、7〜9 の対象にしない。

7. 本文の末尾と区切り線（`---`）の後ろを読み、文書そのものではない文章（作業の経過・指摘への対応の報告・エージェント向けのメモ）が無いかを確かめる
8. 要求・受け入れ条件・テスト観点などの ID を、出てくる順に全部拾い（例：`grep -oE 'R-[0-9]+' draft.md | sort -u -t- -k2 -n`）、欠番が無いかを確かめる。ID を持たない文書では確かめない。欠番があっても、その行が「R-5（削除：理由）」のように理由つきで残っていれば欠番とは見なさない（差し戻しで消した要求の ID は詰めない）。本文と、表・参照・テスト観点の対応の欄で、同じ ID が使われているかも見る
9. 別の文書（ほかのタスクの要求要件・チケット・PR など）を参照している項目を拾い、参照先を開かなくても何を求めるかが、その項目の中で分かるかを確かめる

## チェックポイント

- 曖昧な語の多用（上記）。特に判断を含む所（「必要なら再試行」の「必要」とは）
- 未定義の用語・略語、同じ概念の表記揺れ（「タスク」と「チケット」、「承認」と「マージ」）
- 主語の無い文（誰がやるのか）、受動態で主体が隠れる文
- 文書内の矛盾：数値（上限・期間）、名前（API・テーブル）、手順の順序、状態の名前
- 図と本文の不一致：図にあるが本文に無い要素、矢印の向き・数、ラベルの違い
- 構成：背景・目的・範囲・設計・異常系・運用・検証・未決事項のうち、その文書の種類に要る節が無い。順序が追いにくい（詳細が先、目的が後）
- 粒度：箇条書きの中に段落が混ざる、1 つの箇条書きに複数の決定、見出しの階層の飛び
- 「未決事項」「確認したいこと」が本文に混ざり、決定と区別できない
- 決定と案の区別：「〜する」と「〜する案もある」が混ざる。何が決まったことか
- 数値の単位・基準の欠落（「30 以内」の単位、「午前 3 時」のタイムゾーン）
- 参照の誤り：節番号・図番号のずれ、リンク切れ、古い版の文書への参照
- 要求要件・設計など、人が承認する成果物の本文に、文書そのものではない文章が残っている（`must`）：作業の経過・手順・結果の報告（「〜を取り込みました」「コミット・プッシュはしていません」）、前の版との違いの説明、人間の指摘・PR の指摘への対応の報告（指摘の ID を含む）、エージェントに向けたメモ。区切り線の後ろに足されていることが多い
- 理由の分からない ID の欠番（R-4 の次が R-6 で、R-5 の行も理由も無い、など）。最初の提出で見つけたら、番号を詰めさせる（`should`）。差し戻しで消した要求の ID を詰めるのは誤りなので、指摘しない
- 要求要件・設計などで、別の文書への参照だけの項目（「R-5：別タスクの要求要件の R-3 に従う」のように、中身が書かれていない）。参照先を開かないと何を求めるか分からない（`must`）
- 表：列の意味が無い、空欄の意味（未定か該当なしか）
- 変更履歴：版・日付・変更点があるか（文書の種類が要求するとき）
- 言語・文体：敬体・常体の混在、句読点、記号の揺れ（nit に留める）

## NG 例

### 例1：曖昧な判断

```
失敗した場合は必要に応じて再試行する。
```

「必要」の基準（どの失敗を・何回・間隔）が無く、実装者ごとに違う。`must`（判断を含む曖昧さ）。

### 例2：文書内の矛盾

2.3 では「保持期間は 30 日」、5.1 では「90 日後に削除」。どちらが正か。`must`。

### 例3：未定義の用語

「ゲートを通過したタスクは次の工程に進む」とあるが、「ゲート」の定義が文書内に無く、用語集にも無い。`should`。

### 例4：決定と案の混在

```
通知は Slack で送る。メールで送る案もある。
```

決定なのか、未決なのか。未決なら「未決事項」の節に移す。`should`。

### 例5：主語の無い文

```
承認されたら、ブランチをマージして、通知を送る。
```

誰が承認し、誰（人か・システムか）がマージし、誰に通知するか。`should`、責務の所在に関わるなら D-2 に知らせる。

### 例6：単位の欠落

```
タイムアウト: 30
```

秒かミリ秒か分か。`should`。

### 例7：作業のメモが文書の末尾に残る

要求要件の末尾の `---` の後ろに、「main を取り込む作業（[requirements-1-1]）について、要点は次の 2 つです。…」という段落が続く。人間の指摘への対応の報告で、承認する人が読む文書ではない。対応の報告は、文書の外（指摘への返信・コメント）に書く。`must`。

### 例8：理由の分からない欠番と、参照だけの項目

最初の提出の要求要件で、受け入れ条件が R-1〜R-4、R-6〜R-9 で、R-5 が無い。消した理由も書かれていない。番号を詰めて R-1〜R-8 にさせる。`should`。

同じ要求要件の R-4 は「別タスクの要求要件の R-3 を満たす」とだけあり、何を求めるかが分からない。R-4 に別タスクの R-3 の中身を1行で併記させる。`must`。

差し戻しの後の版で、R-5 が「R-5（削除：他のタスクで扱うため）」の行として残っているなら、欠番ではない。指摘しない。

## 見落としやすい所

- 書き手が分かっていることは省かれる。読者が実装者だけでなく運用者・将来の保守者であることを想定する
- 「分かりにくい」で止めず、どの文のどの語が 2 通りに読めるかを書く
- 文体・記号の揺れは `nit`。判断や決定に関わる曖昧さと混ぜない

## 指摘の書き方の例

- title：`「必要に応じて再試行」の基準が無く、実装者ごとに挙動が分かれる`
- problem：`3.4 の「失敗した場合は必要に応じて再試行する」は、どの失敗（タイムアウト・5xx・4xx）を・何回・どの間隔で再試行するかを決めていない。再試行の有無は二重送信の有無に直結する`
- evidence：`docs/design/notify.md 3.4。異常系の節（4 章）にも再試行の条件は無い`
- suggestion：`再試行する失敗の種類・回数・間隔・最終的な失敗の扱いを表にする`
