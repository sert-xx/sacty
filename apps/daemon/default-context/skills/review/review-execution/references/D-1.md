# D-1 要件適合・目的

見るもの：要求（Issue・タスク・上位の要件）との対応、何のために・なぜこの選択か、代替案と採らなかった理由、スコープ（やらないこと）の明示、前提の妥当性。
見ないもの：書き方の形式（D-6）。

## 確かめる手順

1. 根拠（Issue・タスク・上位の要求要件）から「解くべき問題」と「満たすべき条件」を箇条書きにする
2. 文書の各節が、どの問題・条件に答えているかを対応表にする。答えの無い条件は「未対応」、問題に対応しない節は「要求に無い内容」
3. 「なぜ」を探す：主要な判断（構成・技術・方式）ごとに、理由と比較した代替案が書かれているか。書かれていなければ、判断が正しいかを読み手が検証できない
4. スコープ：やること・やらないこと・後回しにすることが明示されているか。やらないことの理由
5. 前提：文書が依存している前提（利用者数、既存システムの振る舞い、組織の方針）が明示され、妥当か。前提が崩れたときに何が変わるか

## チェックポイント

- 問題の記述が無い、または解法から始まっている（何を解くかが読み手に伝わらない）
- 受け入れ条件・成功の基準が無い、測れない（「使いやすくする」「十分に速い」）
- 要求と文書の間の飛躍：要求は「通知したい」、設計は「メッセージ基盤を導入」（規模の飛躍に理由が無い）
- 要求に無い内容（将来の拡張、別の問題の解決）が混ざり、範囲が広がっている
- 代替案の不在：採った方式だけが書かれ、他の選択肢と比較の軸（コスト・複雑さ・リスク・既存との整合）が無い
- 代替案が藁人形：明らかに劣る案だけを並べて比較にしている
- 判断の理由が「一般的だから」「よく使われているから」だけ
- 前提の未記載：既存システムの振る舞い・データ量・利用者の行動を仮定しているが書いていない
- 利害関係者の視点の欠落：運用者・セキュリティ・既存の利用者・他チームへの影響
- 「やらないこと」の未記載。読み手が「それも入っている」と誤解する
- 要求の解釈の違い：Issue の曖昧な語を一方的に解釈し、確認した記録が無い
- 既存の決定（ADR・過去の設計）との矛盾、または既存の決定を知らずに再発明
- 成功の測り方：リリース後に目的が達成されたかをどう知るか

## NG 例

### 例1：解法から始まる設計書

```
# 通知機能の設計
Redis Streams を使ってイベントを配信し、ワーカーが Slack API を呼ぶ。
```

何を解きたいのか（誰が・いつ・何に気づけない問題）が無く、Redis が要る規模かも判断できない。「背景・課題」の節を求める。`must`（目的が無いと他の観点が評価できない）。

### 例2：代替案の不在

```
## 方式
gRPC を採用する。
```

REST・メッセージキューなどと比べた軸（既存の技術スタック、チームの経験、相互運用）が無い。`should`。

### 例3：要求に無い拡張

Issue は「失敗時にメールで通知」だが、設計には Slack・SMS・Webhook のプラグイン機構が含まれる。範囲が広がり、実装とレビューの負荷が増える。`should` で「今回の範囲と将来の範囲を分けて書く」。

### 例4：測れない受け入れ条件

```
- 一覧の表示が十分に速いこと
```

「95 パーセンタイルで 500ms 以内（1 万件のとき）」のように測れる形に。`must`（D-4 とも接するが、目的の達成基準としてここで指摘）。

### 例5：前提の未記載

「既存の API は冪等なので再送してよい」と設計に書かれているが、根拠（API の仕様・確認した結果）が無い。前提が崩れると二重処理になる。`should`、設計の中核を支える前提なら `must`。

## 見落としやすい所

- 文書が流暢だと「なぜ」が無いことに気づきにくい。判断ごとに「なぜこれか」を自問する
- 要求の「行間」を設計者が勝手に埋めている箇所。確認済みか、仮定として明示されているか
- 自分の好む方式と違うことを「要件に合わない」と言わない。要件と比較の軸で判断する

## 指摘の書き方の例

- title：`解くべき問題と成功の基準が書かれておらず、方式の妥当性を判断できない`
- problem：`文書は Redis Streams の構成から始まり、「誰が何に気づけないか」「どれだけの頻度・量か」が無い。Issue #12 には「失敗時に担当者が気づけない」とあるが、文書との対応が無い`
- evidence：`docs/design/notify.md 全体と Issue #12 を読んだ`
- suggestion：`冒頭に背景・課題・成功の基準（例：失敗から 5 分以内に担当者が気づく）を書き、方式の選択をそれに結び付ける`
