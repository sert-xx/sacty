# C-13 UI・アクセシビリティ

見るもの：状態（読み込み中・空・エラー・長い文字列）の表示、キーボード操作、ラベル・コントラスト、レスポンシブ、既存の UI の規約との整合、文言の分かりやすさ。
見ないもの：表示の背後の論理（C-1）。
起動条件：画面・UI コンポーネント・スタイル・フォームを変える。

Web・モバイル・デスクトップ・TUI/CLI の出力を含む。枠組み（React・Vue・SwiftUI・Jetpack Compose・Flutter・Qt など）は問わない。

## 確かめる手順

1. 変更した画面・コンポーネントごとに、取りうる状態を列挙する：初期・読み込み中・成功（0 件・1 件・多数）・エラー・権限なし・オフライン・処理中（二重送信）
2. 状態ごとに表示とできる操作を追う。欠けている状態（空のときに何も出ない、エラーが沈黙する）
3. データの極端な値：長い文字列（折り返し・省略）、空文字、絵文字・多言語、巨大な数値、過去・未来の日付、null
4. 操作：ポインタ無しで到達・操作できるか（Tab の順序、フォーカスの見え方、Enter/Escape）、スクリーンリーダー向けのラベル（`aria-label`、`contentDescription`、`accessibilityLabel`、`alt`、フォームの `label`）
5. 既存の UI の規約：コンポーネントライブラリの使い方、余白・色・文言の統一、既存画面との一貫性
6. レスポンシブ・画面サイズ：狭い幅・小さい画面での崩れ、横スクロール、固定幅、文字サイズの拡大

## チェックポイント

- 状態の欠落：読み込み中の表示が無く空に見える、0 件の説明が無い、エラーがコンソールにだけ出る
- 二重送信：送信ボタンが処理中に押せる、連打で 2 回 POST
- 長い文字列：はみ出し、ボタンの位置が崩れる、タイトルの省略と全文を見る手段
- フォーム：必須の表示、検証エラーの位置と文言（どの項目が・なぜ）、入力の保持（エラー後に消えない）、Enter での送信、入力の種類（数値・メール）の指定
- ラベル：アイコンだけのボタンにラベル、画像に代替テキスト、`label` と入力の対応、見出しの階層
- フォーカス：モーダルを開いたときのフォーカス移動と閉じたときの復帰、フォーカスの見える表示を消していないか、Tab の順序、フォーカストラップ
- キーボード：Escape で閉じる、Enter で決定、矢印でリスト移動（既存の規約に従う）
- コントラスト・色：色だけで状態を伝えていないか（アイコンや文言も）、コントラスト比、ダークモード
- 文言：動詞の統一、専門用語、エラー文の「何をすればよいか」、i18n の仕組みを通しているか（C-14）
- 既存の規約との不一致：独自のボタン・独自の色、余白の単位、既存の共通コンポーネントを使わない
- レスポンシブ：固定の幅・高さ、狭い幅でのテーブル、タッチ操作のサイズ、文字拡大での崩れ
- 動き：アニメーションの軽減設定の尊重、自動更新で読んでいる途中に内容が飛ぶ、点滅
- 破壊的な操作：確認の有無、取り消しの手段、ボタンの配置（誤って押さない）
- 更新の反映：操作後に表示が更新されるか（キャッシュの無効化）、別の画面に戻ったときの状態
- 既定の挙動の破壊：リンクを div + クリックで作る（右クリック・中クリック・履歴が壊れる）、ボタンでない要素のクリック、スクロールの奪い取り
- CLI/TUI：端末の幅、色が使えない端末（NO_COLOR）、パイプしたときの装飾、進捗の表示、終了コード

## NG 例

### 例1（React）：0 件のときに何も出ない

```tsx
{tasks.map((t) => <TaskRow key={t.id} task={t} />)}
```

読み込み中なのか 0 件なのか分からない。読み込み中・0 件の表示を分ける。`should`。

### 例2（Android/Compose）：アイコンだけのボタンにラベルが無い

```kotlin
IconButton(onClick = onStop) { Icon(Icons.Default.Stop, contentDescription = null) }
```

スクリーンリーダーで「ボタン」としか読まれない。`contentDescription = "停止"`。`should`。

### 例3（Vue）：処理中に連打できる

```vue
<button @click="submit">作成</button>
```

API が遅いと 2 回作られる。処理中は `disabled` にし、表示を変える。サーバーに重複の防止が無いなら `must`。

### 例4（SwiftUI）：色だけで区別する

完了と中止を緑と赤の背景だけで区別し、文言は同じ「終了」。色覚の差で区別できない。文言かアイコンを足す。`should`。

### 例5（HTML）：リンクを div で作る

```html
<div onclick="location.href='/tasks/1'">タスク 1</div>
```

キーボードで到達できず、右クリック・中クリック・履歴が壊れる。`<a href>`。`should`。

### 例6（CLI）：パイプしても色の制御文字が出る

```
$ tool list | grep done
[32mdone[0m ...
```

端末でないときは装飾を消す（isatty・NO_COLOR）。機械で読む用途があれば `should`。

## 見落としやすい所

- 実装者が試すのは「ふつうのデータ」。極端なデータと状態を頭の中で表示する
- ライブラリのコンポーネントを使っていれば大半は満たされる。独自実装の部分に集中する
- UI の好み（色・配置）は規約に反しない限り出さない
