# C-16 UX・利用者の流れ

見るもの：利用者が変更した機能の目的を達せるか（たどり着けるか・何をすればよいか分かるか・操作の手数）、操作の結果が分かるか（成功・失敗・処理中のフィードバック）、画面の中の情報の優先度と配置（大事なものが目に入るか・関係するものが近くにあるか）、既存の画面との導線と一貫性（同じ操作が同じ場所・同じ見た目か）、誤操作のしやすさと取り返し、画面の見た目の崩れ（重なり・はみ出し・切れ・揃っていない）。
見ないもの：状態ごとの表示の有無・キーボード操作・ラベル・コントラスト・レスポンシブの細部（C-13）、文言の翻訳・書式（C-14）、表示の背後の論理（C-1）。
起動条件：画面・UI コンポーネント・スタイル・フォームを変える。

C-13 が「部品が正しく作られているか」を見るのに対し、この観点は「利用者が目的を達せるか」を見る。
依頼文の「画面の記録」に `screens.json` があれば、画像を見て判断する。「画面は撮っていない」と渡されたら、コードから画面を組み立てて判断し、`limitations` に「画面を見ずにコードで確かめた」と書く。

## 確かめる手順

1. 根拠（タスク・Issue・PR の本文）から、利用者が誰で、変更した機能で何をしたいかを 1〜2 文にまとめる
2. 利用者がその目的を達するまでの操作を、入口（どの画面から・どのリンクやボタンで）から順に書き出す
3. 画面の記録があれば、`screens.json` を読み、書き出した操作の順に画像を見る。変更前（`version: base`）があれば並べて比べる。各画像で、次を確かめる
    - 次に何をすればよいかが、画面を見て分かるか
    - 目的に要る情報・操作が目に入る所にあるか。要らないものが目立っていないか
    - 崩れ（重なり・はみ出し・切れ・ずれ）、狭い幅での崩れ
    - `console_errors` にエラーが無いか
4. 画面の記録が無いときは、変更したコンポーネント・スタイル・ルーティングを読み、2 の操作の順に、各画面に何がどの順で並ぶかを組み立てて確かめる
5. 同じ種類の操作をしている既存の画面を探し、配置・見た目・手順が揃っているかを比べる
6. 誤って押したとき・途中でやめたとき・失敗したときに、利用者が状況を理解して戻れるかを追う

## チェックポイント

- 入口：新しい機能へのリンク・ボタン・メニューが無い・見つけにくい、URL を直接打たないとたどり着けない
- 手数：同じ目的に、既存の画面より多い操作が要る。毎回同じ値を入れさせる。確認の画面が多すぎる
- 次の操作：主な操作（主ボタン）がどれか分からない、主な操作と副の操作が同じ見た目、押せない理由が示されない
- フィードバック：操作の後に何が起きたか分からない（成功の表示が無い・画面が変わらない・失敗が目立たない）、処理中が分からない
- 情報の優先度：大事な情報（状態・期限・エラー）が下や端に埋もれる、要らない情報が目立つ、同じ情報が何度も出る
- 配置：関係するものが離れている（入力と、その説明・エラー）、読む順と操作の順が合わない
- 一貫性：既存の画面と同じ操作が違う場所・違う見た目・違う手順、同じものを違う名前で呼ぶ
- 誤操作：破壊的な操作が主な操作の隣にある・同じ見た目、取り消せない操作に確認が無い、確認が多すぎて読まれない
- 戻り方：途中でやめると入力が消える、失敗した後にどこからやり直すか分からない、戻るボタンで意図しない画面に行く
- 見た目の崩れ：要素の重なり、はみ出し、文字の切れ、揃っていない余白・高さ、狭い幅で操作が画面の外に出る
- 変更前との差：変更前にあった情報・操作が、説明なく消えた・移った

## NG 例

### 例1（Web）：操作の結果が分からない

設定の画面で「保存」を押しても、画面に何も変化が無い（成功の表示も、ボタンの変化も無い）。利用者は保存できたか分からず、何度も押すか、別の画面で確かめる。保存の後に短い成功の表示を出す。`should`。

### 例2（Web）：破壊的な操作が主な操作の隣にある

タスクの詳細の画面で、「完了にする」と「削除」が同じ見た目のボタンで並んでいる（スクリーンショット `task-1280-detail.png`）。削除は取り消せない。削除を目立たない場所に移すか、見た目を変えて確認を挟む。`should`（取り消せず、誤って押しやすい配置なら `must`）。

### 例3（Web）：新しい機能への入口が無い

エクスポートの画面（`/export`）を足したが、どの画面からもリンクが無い。URL を知らない利用者は使えない。一覧の画面の操作のメニューに入口を足す。`must`（依頼が利用者に使わせることなら）。

### 例4（モバイル）：狭い幅で主な操作が画面の外に出る

375px の幅で、フォームの「送信」ボタンが横にはみ出し、横にスクロールしないと押せない（スクリーンショット `form-375-initial.png`）。`should`。

### 例5（Web）：既存の画面と手順が違う

ほかの一覧はすべて行の右端のメニューから編集するのに、新しい一覧だけは行を選んで上のツールバーの「編集」を押す。利用者は画面ごとに手順を覚え直す。既存の画面に合わせる。`should`。

## 見落としやすい所

- 作者は機能の入口と手順を知っている。初めて使う利用者として、入口から順にたどる
- 画像は「動いているか」ではなく「利用者が迷わないか」で見る。1 枚ずつではなく、操作の順に続けて見る
- 好み（色・余白の大きさ・言い回し）だけの指摘は出さない。利用者が迷う・誤る・手数が増える、の根拠を示せるものを指摘にする
- 既存の画面の UX の問題は範囲の外。今回の変更が持ち込んだもの・悪化させたものだけを見る
- 画像が無いとき、コードから読み取れない見た目（実際の幅での折り返し・重なり）は断定しない。`confidence: low` にするか `limitations` に書く

## 指摘の書き方の例

- title：`保存しても画面が変わらず、保存できたか分からない`
- problem：`設定の画面で「保存」を押すと API は成功するが、成功の表示も画面の変化も無い。利用者は保存できたか分からず、別の画面で確かめるか、何度も押す`
- evidence：`スクリーンショットの settings-1280-before-save.png と settings-1280-after-save.png が同じ。web/src/settings/Form.tsx:80 の onSuccess は値を再取得するだけで表示を変えない`
- suggestion：`保存の後に「保存しました」を短く表示する（既存の一覧の画面と同じ通知の部品を使う）`
