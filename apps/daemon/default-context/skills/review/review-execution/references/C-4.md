# C-4 テスト

見るもの：観点・受け入れ条件をテストが本当に検証しているか、欠けたケース、壊れやすいテスト、テストがリポジトリのテストのコマンドで実行されるか。
見ないもの：実装の論理の誤り（C-1）。

テストの枠組みは問わない（pytest・JUnit・go test・Jest・RSpec・cargo test など）。

## 確かめる手順

1. 根拠（テスト観点・受け入れ条件）を 1 つずつ取り、それを検証すると申告されたテストを開く。「入力を与え、期待結果を assert している」かを確かめる。申告が無い観点は「対応なし」
2. 各テストで「実装を壊したら落ちるか」を考える。期待値を実装から写しただけ、存在確認だけ、例外が出ないことだけ、のテストは落ちない
3. 変更した分岐・境界ごとに、通すテストがあるかを数える。無い区画を列挙する
4. テストの独立性を見る：順序、共有の状態、実時刻、乱数、ネットワーク、ファイルシステム、環境変数、並列実行
5. テストの発見：ファイル名・場所・関数名がテストランナーの規約に合うか（`test_*.py`、`*_test.go`、`*Test.java`、`*.test.ts`）、skip・only・`@Disabled`・`xit`・`t.Skip` が残っていないか

## チェックポイント

- 期待結果が具体か：真偽値だけ（`assertTrue(result != null)`、`toBeTruthy`）、例外が出ないことだけ、スナップショットの無批判な更新
- 観点との対応：観点「空のときはエラー」を、空でない入力のテストに対応させている
- モックが実装を置き換えすぎ：テスト対象そのものをモックしている、モックの戻り値が本物と違う形、全依存をモックして結合を見ていない
- 異常系・境界：空・1 件・上限・不正な型・失敗する I/O のテストがあるか。正常系だけで「網羅」としていないか
- 壊れやすさ：現在時刻（`time.Now()`、`new Date()`、`LocalDate.now()`）、乱数、実時間の sleep、外部サービス、固定ポート、絶対パス、ロケール、並行実行での共有ファイル、マップやセットの反復順序（Go・Python 3.6 以前）
- 後始末：作った一時ファイル・DB の行・環境変数を戻しているか。失敗したときも戻るか（teardown・`defer`・`finally`・fixture）
- 非同期：await の漏れで assert の前に終わる、Go で goroutine の完了を待たない、`done` の未呼び出し、reject/panic を検証していない
- アサートの数：ループの中で assert して 0 回実行で通る（件数を先に確かめる）
- テストの名前と中身の一致：名前は「エラーになる」なのに成功を確かめている
- 実装の写し：期待値を実装と同じ関数で計算している
- カバレッジでなく意味：行は通るが結果を見ていない
- 実行されるか：テストのコマンド（Makefile・CI・package.json・build.gradle）の対象に入るか、新しいファイルがランナーの include に合うか、ビルドタグや profile で除外されていないか
- 統合の穴：単体テストだけで、変更した呼び出し元との結合が検証されていない（大きな変更のとき）
- 不安定化：既存のテストを skip・緩い assert に変えて通している差分
- 修正の再現：不具合の修正なら、修正前に落ちて修正後に通るテストがあるか
- テーブル駆動・パラメータ化のケースに重複や抜け（同じ入力が 2 回、境界が無い）

## NG 例

### 例1（Python）：形だけのテスト

```python
def test_limit_zero():
    r = list_items(limit=0)
    assert r is not None
```

20 件返っても通る。`assert r.items == []`。観点に対応すると申告されていれば `must`。

### 例2（Java）：テスト対象をモックしている

```java
when(priceService.calc(any())).thenReturn(100);
assertEquals(100, orderService.total(order)); // total の中身は calc を呼ぶだけ
```

`calc` を 100 に固定して 100 を確かめている。何も検証していない。`must`。

### 例3（Go）：goroutine の完了を待たない

```go
go worker(ch)
if got := len(results); got != 3 { t.Errorf(...) } // worker が終わる前に数えている
```

タイミングで通ったり落ちたりする。完了を待つ（WaitGroup・channel）。`must`（不安定なテストは信頼を壊す）。

### 例4（TypeScript）：実時刻に依存する

```ts
expect(isExpired(token)).toBe(false); // token の期限は固定の日付
```

期限を過ぎた日に落ちる。時刻を注入するか fake timers。`should`。

### 例5（Ruby）：ループの中の assert が 0 回

```ruby
findings.each { |f| expect(f.path).to start_with("lib/") }
```

`findings` が空なら何も確かめずに通る。件数を先に確かめる。`should`。

### 例6（任意）：テストを緩めて通す差分

```diff
- assert result.count == 3
+ assert result.count > 0
```

実装の変更に合わせて期待を緩めた。意図が説明に無ければ `must`（回帰を隠す）。

## 見落としやすい所

- 「テストは全部通った」という説明。何を確かめたかを読む
- テストの追加より、既存テストの変更・削除。削除の理由
- fixture の中身（期待する値と fixture が偶然一致している）
- 新しいテストファイルの置き場所（ランナーの対象外で一度も実行されていない）

## 指摘の書き方の例

- title：`TV-2（空のときはエラー）に対応するテストが、エラーを確かめていない`
- problem：`tests/test_listing.py:40 は not None だけで、空の入力でエラーになることを assert していない。実装がエラーを返さなくなっても通る`
- evidence：`申告 TV-2 → test_empty を開き assert を読んだ。実装 app/listing.py:12 の空のチェックを外しても通ることを確かめた（self-review のとき）`
- suggestion：`pytest.raises(ValueError) で例外を確かめる`
