# C-12 運用性・可観測性

見るもの：失敗が運用者に分かるか（ログの粒度・レベル・相関 ID）、設定の既定値と検証、起動・停止・再起動の挙動、ロールバックできるか、秘密情報がログに出ないか。
見ないもの：セキュリティの設計（C-3）。
起動条件：ログ・メトリクス・設定・デプロイ・常駐プロセス・バッチ・スケジュールに触れる。

## 確かめる手順

1. 「本番で壊れたとき、運用者は何を見て気づき、どう原因に辿るか」を変更した機能ごとに想像する。ログ・メトリクス・アラート・画面の警告のどれで気づけるか
2. ログを読む：失敗時に、何が・どこで・どの対象（ID）で・なぜ、が 1 行から分かるか。レベル（error/warn/info/debug）が適切か
3. 設定を読む：新しい設定項目の既定値、検証（型・範囲・必須）、誤った設定での起動時の振る舞い（すぐ止まるか、後で壊れるか）、文書化
4. ライフサイクル：起動時の依存の確認、停止時の後始末、再起動後の状態の復元、クラッシュからの回復
5. 変更をロールバックしたときに何が残るか（設定・データ・スケジュール）
6. ログ・エラーに秘密情報・個人情報が含まれないか（見つけたら C-3 にも知らせる）

## チェックポイント

- 失敗が沈黙する：捕まえてログ無し、warn で済ませる致命的な失敗、リトライ中であることが分からない
- ログの内容：対象の ID（ジョブ・リクエスト・利用者）、相関 ID・トレース ID、エラーの原因（cause・スタック）、相手の応答（ステータス）
- ログの量：ループの中の info、巨大オブジェクトのダンプ、同じ警告の洪水（まとめる・レート制限）
- ログの形式：既存の仕組み（構造化ログ・ロガー）を使っているか、`print`/`console.log`/`fmt.Println`/`System.out` の混入、表記の一貫性
- レベル：期待される失敗（利用者の入力ミス）を error にする、運用者の対応が要る失敗を info にする
- メトリクス・ヘルスチェック：長く動く処理の進捗・滞留、キューの長さ、失敗率。ヘルスチェックが依存の状態を反映するか（readiness と liveness の区別）
- 設定：既定値の妥当性、単位（秒かミリ秒か）の明示、検証と誤りの報告（どのキーが・なぜ）、環境変数と設定ファイルの優先順位、文書との一致（文書の正確さは U-1）
- 起動：必須の依存（DB・外部）が無いときに明確に止まるか、起動順序、マイグレーションの自動実行の是非、環境変数の未設定
- 停止：シグナルの処理（SIGTERM・SIGINT）、処理中の作業の扱い、タイマー・接続の後始末、強制終了までの時間（コンテナの猶予）
- 再起動・復旧：中断した作業の再開（二重実行は C-7）、一時ファイル・ロックファイルの残骸、状態の整合性の確認
- ロールバック：新しい設定キー・データ形式・スケジュールが古い版を壊さないか（C-6・C-9 と接する）
- スケジュール・バッチ：重複起動、実行時間の見積もり、失敗時の通知、手動で再実行する手段、タイムゾーン
- デプロイ：手順の変更（環境変数の追加）が周知されているか、ダウンタイム、feature flag
- 秘密情報：ログ・エラー・メトリクスのラベル・URL に出ていないか、デバッグログで本文を丸ごと出していないか
- デバッグの手がかり：問題の再現に必要な情報（入力の要約、版、環境）が残るか。残しすぎ（個人情報）でないか
- 利用者への伝達：運用者だけでなく利用者が気づく必要のある失敗（通知の失敗など）が画面・応答に出るか
- リソースの監視：ディスク（ログ・一時ファイルの増加）、ファイルディスクリプタ、接続数

## NG 例

### 例1（Java）：致命的な失敗が warn で流れる

```java
} catch (NotificationException e) { log.warn("notify failed"); }
```

通知の失敗は人が気づく手段の喪失。error にし、対象（ジョブ ID・送り先）と原因を含め、画面や代替の経路にも出す。`must`（運用で気づけない）。

### 例2（Go）：ログに手がかりが無い

```go
log.Printf("failed to process")
```

何の処理か、どの対象か、原因は何かが無い。数百のジョブが動く中で辿れない。`should`、障害時の切り分けに必須の経路なら `must`。

### 例3（Python）：誤った設定で後から壊れる

```python
interval = float(os.environ.get("POLL_INTERVAL", ""))  # 未設定で ValueError、"0" で busy loop
```

起動時に検証し、既定値か明確なエラーにする。`must`。

### 例4（任意）：停止で処理中の作業を失う

SIGTERM で即座に exit し、実行中の子プロセスが残り、作業の記録が書かれない。後始末の猶予と記録。`must`。

### 例5（Ruby）：デバッグログに本文を丸ごと出す

```ruby
logger.debug("payload: #{payload.inspect}")  # 個人情報・トークンを含む
```

debug でもログ基盤に残る。要約か伏せ字。`should`、秘密情報が確実に含まれるなら `must`（C-3 にも知らせる）。

### 例6（Kubernetes）：readiness が依存を見ない

アプリは起動したが DB に繋がらない状態で readiness が 200 を返し、トラフィックが流れて全部エラーになる。`should`。

## 見落としやすい所

- 「ログは出している」で止めず、そのログだけで原因に辿れるかを考える
- 新しい設定項目の文書化。無ければ U-1 に知らせる
- 常駐プロセスの変更は、起動・停止・再起動の 3 つを必ず通す

## 指摘の書き方の例

- title：`POLL_INTERVAL 未設定で起動時に ValueError、"0" で busy loop になる`
- problem：`float("") は ValueError で起動が止まる。"0" を渡すと sleep(0) のループで CPU を使い切り、相手の API を秒間数百回叩く。検証も既定値も無い`
- evidence：`app/intake.py:18。README に POLL_INTERVAL の既定値の記述が無いことも確かめた`
- suggestion：`設定の読み込みで数値・範囲（1 秒以上）を検証し、未設定は既定（60 秒）にする。README に書く`
