# D-2 実現可能性・整合性

見るもの：既存のコード・構成・データと矛盾しないか、処理の流れ・データの流れが成立するか（抜けた段階、循環、誰が呼ぶか）、責務の所在、I/F の整合、技術的に可能か。
見ないもの：書かれていない異常系（D-3）。

## 確かめる手順

1. 文書に出てくる既存の要素（モジュール・API・テーブル・設定・外部サービス）を、実際のコード・構成で確かめる。名前・振る舞い・制約が一致するか
2. 処理の流れを、開始から終了まで自分で辿る（誰が起動し、何を渡し、どこに書き、誰が読むか）。辿れない所・2 通りに読める所を記録する
3. データの流れ：各データがどこで生まれ、どこで変換され、どこに保存され、誰が消すか。生まれるが使われない、使われるが生まれない項目
4. I/F の整合：文書内で同じ I/F が別の形で書かれていないか（図と本文、節と節）。呼ぶ側と呼ばれる側の引数・戻り値・エラーが合うか
5. 技術的な前提：使う技術が主張する機能を持つか（例：そのキューは順序を保証するか、その DB はその分離レベルを持つか）。ライブラリの版・制限

## チェックポイント

- 既存コードとの不一致：文書が前提にする関数・テーブル・設定が存在しない、または振る舞いが違う
- 既存の構成との矛盾：認証の仕組み・デプロイの単位・ネットワークの到達性・権限の境界を越える設計
- 流れの抜け：イベントを発行するが購読者が無い、状態を「完了」にする主体が無い、エラーの通知先が無い
- 循環：A が B を待ち、B が A を待つ。初期化の順序の循環
- 責務の所在：同じことを 2 つのコンポーネントがやる、誰もやらない、境界が曖昧（「適宜連携する」）
- I/F の不整合：図のメッセージ名と本文の API 名が違う、呼ぶ側が渡す項目を呼ばれる側が受け取らない、同期と非同期の取り違え
- データの不整合：同じ情報を 2 箇所に持ち、どちらが正か決まっていない。ID の体系の不一致
- 技術の思い込み：「at-least-once なので重複しない」「トランザクションで外部 API も戻る」「キャッシュは常に最新」
- 規模の前提との不整合：1 日 1 億件を同期処理、全件をメモリに載せる設計
- 時間の前提：処理の順序・同時性の仮定（イベントの到着順、クロックの一致）
- 権限・認証の流れ：誰の権限で何が実行されるか、トークンの受け渡しの経路が成立するか
- 環境の差：開発・検証・本番で成立しない前提（ネットワーク、権限、外部サービスのサンドボックス）
- 図と本文の一致：シーケンス図の矢印の数と本文の手順の数、構成図に無いコンポーネントが本文に出る

## NG 例

### 例1：存在しない前提

```
既存の TaskService.markDone() を呼び出し、完了イベントを発行する。
```

コードを見ると `markDone` は存在せず、`complete()` は状態を変えるがイベントは発行しない。設計の前提が崩れている。`must`。

### 例2：流れの抜け

```
3. ワーカーが処理を終えると結果をキューに書く。
4. 利用者は画面で結果を確認する。
```

キューから画面までの経路（誰が読んで DB に書くか、画面は何を読むか）が無い。`must`。

### 例3：技術の思い込み

```
メッセージは at-least-once で配信されるため、処理の重複は起きない。
```

at-least-once は重複が起きる保証。冪等性の設計が要る。`must`。

### 例4：図と本文の不一致

シーケンス図では API ゲートウェイが認証するが、本文では各サービスが認証する。どちらが正か決まらず、実装者が別々に解釈する。`must`（D-6 の形式ではなく、設計の決定が 2 つあることが問題）。

### 例5：責務の重複

「バッチが古いデータを削除する」と「API が参照時に古いデータを削除する」が両方書かれ、削除の基準も違う。`should`。

### 例6：規模との不整合

要件は「1 日 5,000 万イベント」だが、設計は「全イベントを 1 つの SQLite ファイルに追記し、集計は全件走査」。`must`。

## 見落としやすい所

- 文書の中だけで整合していても、コードと合っているかは別。既存の要素は必ず実物を見る
- 「連携する」「適切に処理する」「必要に応じて」の裏に、決まっていない流れが隠れている
- 図は本文より先に書かれて古くなりがち。図の要素を本文と 1 対 1 で突き合わせる

## 指摘の書き方の例

- title：`前提にしている TaskService.markDone() が存在せず、完了イベントも発行されない`
- problem：`設計 3.2 は markDone() が完了イベントを発行するとしているが、コードには complete() しか無く、イベントの発行も無い。この前提の上に通知の流れ全体が乗っている`
- evidence：`docs/design/notify.md 3.2 と src/service/task.py を読んだ`
- suggestion：`complete() にイベントの発行を足す変更を設計に含めるか、別の起点（DB の変更の監視など）に変える`
