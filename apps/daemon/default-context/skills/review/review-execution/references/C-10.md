# C-10 外部連携

見るもの：タイムアウト・リトライ・レート制限、失敗時の振る舞い、冪等性、契約（スキーマ・バージョン・認証）の一致、秘密情報の受け渡し、相手側の障害の切り分け。
見ないもの：自分側の論理（C-1）、脆弱性（C-3）。
起動条件：外部 API・メッセージキュー・Webhook・サードパーティのサービス・他システムを呼ぶ、または受ける。

## 確かめる手順

1. 外部との接点を列挙する：呼ぶ側（HTTP・gRPC・SDK・CLI・メッセージの送信）、受ける側（Webhook・コールバック・キューの消費・ファイルの受け取り）
2. 接点ごとに契約を確かめる：相手の仕様（ドキュメント・OpenAPI・Protobuf・SDK の型）と、コードが送る・受ける形が一致するか。必須の項目、型、enum、ページング、版
3. 相手が「遅い・落ちている・変な応答を返す・部分的に成功した」ときの振る舞いを追う：タイムアウト、リトライ、エラーの判定、ログ、利用者への伝え方
4. 冪等性：リトライや再送で副作用が重ならないか（冪等キー、重複の検出）
5. 認証と秘密情報の受け渡し（どこから取り、どう渡し、ログに出ないか）。脆弱性は C-3 だが、契約（ヘッダー名・形式・更新）の一致はここ
6. 相手の障害と自分の不具合を切り分けられるか（ログに相手の応答のステータス・ID が残るか）

## チェックポイント

- タイムアウト：無い（既定が無限のクライアント：Python `requests`、Go の `http.Client{}`、Node `fetch`、Java の古い `HttpURLConnection`）、長すぎる、接続と読み取りの区別、全体の上限
- リトライ：どのエラーを再試行するか（4xx を再試行していないか、429・503・接続断を再試行するか）、回数と間隔（指数バックオフ・ジッター）、再試行の総時間、再試行できる操作か
- レート制限：相手の制限を知っているか、429 と `Retry-After` の扱い、並列度の上限
- 冪等性：POST の再送で二重に作られる。冪等キー、クライアント側の重複チェック、相手の「既にある」応答の扱い
- 契約：項目名の綴り、必須項目の欠落、型（数値を文字列で送る）、日時の形式、ページングの続きの取り方、API の版の固定、文字コード
- 応答の検証：相手の応答を信頼して型を付けていないか（スキーマ検証）、空・null・想定外の enum、エラーを 200 で返す相手
- 部分的な成功：バッチ API の一部失敗、送信は成功したが記録に失敗
- Webhook の受け側：署名の検証（C-3 と接する）、重複配信（同じイベントが 2 回来る）、順序の逆転、遅延、ペイロードの版、応答を早く返して処理は後で
- キュー：ack のタイミング（処理前に ack して失う、処理後に ack で二重処理）、可視性タイムアウト、デッドレター、毒メッセージ、順序の保証の有無
- 認証：トークンの期限と更新、401 の扱い（更新して 1 回再試行か）、秘密情報の取得元、ログへの漏れ
- 切り分け：相手のリクエスト ID・ステータス・応答の一部をログに残すか（秘密情報は伏せる）、相手の障害を自分のエラーとして利用者に出していないか
- 依存の障害の伝播：相手が落ちると自分の全機能が止まるか、関係ない機能は動くか
- モックとの乖離：テストのモックが本物の応答の形と違う（C-4 と接する）
- 環境差：開発・本番で URL・認証方式が違う所の設定、プロキシ・TLS、サンドボックス環境
- 時刻のずれ：相手との時計の差（署名の有効期間、期限の判定）

## NG 例

### 例1（Python）：タイムアウトが無い

```python
r = requests.get(url)  # 既定では無限に待つ
```

相手が応答しないと処理が止まり続ける。`timeout=(3, 30)`。リクエスト処理の中なら `must`。

### 例2（Go）：4xx を再試行する

```go
for i := 0; i < 5; i++ {
    resp, err := client.Do(req)
    if err == nil && resp.StatusCode < 500 { return resp, nil }
    time.Sleep(time.Second)
}
```

一見よいが、`resp.StatusCode < 500` は 429 も「成功」として返す。429 は再試行・400 は即失敗、と区別する。`should`。

### 例3（任意）：POST の再送で二重に作る

Webhook の送信後にネットワーク断で応答が届かず、再試行で同じイベントが 2 回届く。冪等キー（イベント ID）を付け、受け側で重複を捨てる。`must`。

### 例4（Java）：応答を検証せずに使う

```java
ListResponse res = mapper.readValue(body, ListResponse.class);
for (Item i : res.getItems()) ...   // 相手がエラーを 200 で返すと items が null
```

null・形の確認。相手の品質に依存。`should`。

### 例5（Ruby/Sidekiq 等）：ack してから処理する

```ruby
msg = queue.receive
queue.ack(msg)
process(msg)   # 失敗するとメッセージが失われる
```

処理後に ack し、二重処理に備える。`must`。

### 例6（TypeScript）：401 で無限に更新を繰り返す

```ts
async function call() { try { return await api(); } catch (e) { if (e.status === 401) { await refresh(); return call(); } throw e; } }
```

更新しても 401 が続く（権限が取り消された）と無限再帰。再試行は 1 回まで。`must`。

## 見落としやすい所

- 相手のドキュメントを読まずに「動いたからよい」。契約の確認が根拠になる
- 正常応答だけを想定したコード。相手の障害時の経路を頭の中で通す
- LLM・外部の AI サービスの呼び出しも外部連携。応答の形が揺れる前提で検証しているか

## 指摘の書き方の例

- title：`外部 API の呼び出しにタイムアウトが無く、応答が無いと処理が止まり続ける`
- problem：`requests.get に timeout を渡していない。相手が接続を受け付けて本文を返さないと、await 相当の待ちが解けず、ジョブ全体のタイムアウト（45 分）まで何も進まない`
- evidence：`app/clients/github.py:55。呼び出し元のジョブのタイムアウトを app/jobs/review.py で確かめた`
- suggestion：`timeout=(3, 30) を渡し、タイムアウトは再試行の対象にする`
