# D-7 性能・容量

見るもの：目標の根拠、ボトルネックの見積もり、スケールの方法、測り方。
見ないもの：機能の正しさ（D-2）。
起動条件：性能・容量・レイテンシの目標がある、大量データ・高頻度の処理を扱う。

## 確かめる手順

1. 性能・容量の目標（レイテンシ・スループット・同時接続・データ量・保持期間）が数値で書かれているか。数値の根拠（現状の計測、見込みの利用者数、契約）
2. 処理の流れの各段階で、量がどう変わるか（1 リクエストが何回の I/O・何件のデータになるか）を見積もり、最も重い段階（ボトルネック）を特定する。文書がそれを認識しているか
3. 増加への対応：量が 10 倍になったときにどこが先に壊れるか、スケールの手段（水平・垂直・分割・キャッシュ）が書かれているか
4. 測り方：目標の達成をどう確認するか（負荷試験・本番の計測・ダッシュボード）、いつ測るか
5. 上限：量が想定を超えたときの振る舞い（拒否・遅延・劣化・落ちる）が設計されているか

## チェックポイント

- 目標が無い、または根拠の無い数値（「1 秒以内」の理由）
- 現状の計測値が無い（改善の設計なら、何から何へ）
- 見積もりの欠落：1 日の件数・ピーク時の倍率・データの増加速度・保持期間からの容量
- ボトルネックの未認識：全段階を同じ重さで扱い、N+1・全件走査・外部 API の直列呼び出し・ロックの競合を見ていない
- 同期処理の限界：利用者を待たせる処理の中に、時間が読めない処理（外部 API・大量の I/O）がある
- スケールの手段：単一インスタンス・単一ファイル・単一 DB の前提で、増えたときの手が無い
- キャッシュ：効果の見積もり（ヒット率）、無効化、一貫性への影響
- DB：インデックスの設計、クエリの計画、パーティション、アーカイブ
- 容量：ログ・一時ファイル・添付・履歴の増加と削除の方針、ディスク・メモリの上限
- 上限時の振る舞い：レート制限・キューの上限・バックプレッシャー・優先度。何も無く落ちる設計
- 測り方：負荷試験の計画（データ・環境・ツール）、本番のメトリクス、閾値とアラート
- コスト：スケールの手段のコスト（クラウドの費用・運用の手間）が目標と釣り合うか
- 過剰設計：要件が小さい（1 日数十件）のに分散システムを設計している（D-1 にも接する）

## NG 例

### 例1：根拠の無い目標

```
API の応答は 200ms 以内とする。
```

なぜ 200ms か（画面の要件・契約・現状）が無い。達成できないときに何を妥協するかも決められない。`should`。

### 例2：ボトルネックの未認識

「一覧 API はタスクごとに担当者と最新のコメントを取得する」。1 ページ 100 件で 201 クエリ。文書に言及が無い。`must`（目標 200ms に対して成立しない）。

### 例3：増加への手が無い

「イベントは 1 つの JSON ファイルに追記し、集計は全件読み込み」。1 日 5 万件で 1 年後に 1,800 万件。読み込みが数十秒になる。`must`。

### 例4：上限時の振る舞いが無い

Webhook の受け口に流量の上限が無く、相手が大量に送ると全部キューに積み、メモリを使い切る。`should`、公開エンドポイントなら `must`。

### 例5：測り方が無い

目標は書かれているが、どの環境でどう測るか、本番でどう監視するかが無い。達成を確認できない。`should`。

### 例6：過剰設計

要件は「1 日 50 件のタスクを 10 人が使う」だが、設計はシャーディングとメッセージ基盤を含む。複雑さがコストになる。`should`（D-1 と相談）。

## 見落としやすい所

- 「性能」の節があっても、数値が無ければ無いのと同じ
- ピークと平均の区別。平均で設計してピークで落ちる
- 性能の指摘は推測が多い。見積もりの根拠（件数・回数）を示し、`confidence` を正直に書く

## 指摘の書き方の例

- title：`一覧 API がタスクごとに 2 クエリを発行し、目標の 200ms を満たせない`
- problem：`3.2 の一覧は 1 ページ 100 件で、タスクごとに担当者と最新コメントを取得する設計（201 クエリ）。1 クエリ 2ms でも 400ms を超え、2.1 の目標 200ms と矛盾する。文書にボトルネックの言及が無い`
- evidence：`docs/design/list.md 2.1・3.2 を読み、クエリ数を見積もった。計測はしていない（confidence: medium）`
- suggestion：`JOIN か一括取得で 3 クエリ以内にし、負荷試験で確認する計画を足す`
