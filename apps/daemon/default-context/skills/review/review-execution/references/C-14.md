# C-14 国際化・表記

見るもの：翻訳の漏れ、ハードコードされた文言、タイムゾーン・ロケール、複数形・文字幅、既存の文言の規約（用語・敬体）との整合。
見ないもの：UI の構造（C-13）。
起動条件：利用者に見える文言、日時・通貨・数値の書式、言語の切り替えに触れる。

仕組みは問わない（gettext、ICU MessageFormat、i18next、Rails I18n、Android の strings.xml、iOS の Localizable.strings、Java の ResourceBundle、Go の go-i18n など）。

## 確かめる手順

1. リポジトリの i18n の仕組みを知る（辞書の場所、キーの命名、言語の切り替え、サーバー側の文言の仕組み）
2. 差分の中で利用者に見える文字列を列挙する：画面の文言、API のエラーメッセージ、通知・メール、生成する文書、ログのうち利用者が読むもの
3. それぞれが仕組みを通っているか（辞書のキーか、直書きか）。全言語の辞書にキーがあるか
4. 日時・数値・通貨の書式：ロケールとタイムゾーンをどこで決めているか、保存は UTC か、表示でだけ変換しているか
5. 文言の規約：既存の用語と一致するか、敬体・常体、記号、英数字の前後の空白、句点
6. 文の組み立て：文を部品の連結で作っていないか（語順が言語で変わる）、複数形、数の表現

## チェックポイント

- 直書きの文言：テンプレート・ビューの中の日本語・英語、エラーの文字列、ダイアログ、ボタンの文言、メールの件名
- 辞書の欠落：片方の言語にだけキーがある、キーの綴り違い、未使用のキーの残骸、プレースホルダーの数の不一致
- 文の連結：`"残り " + n + " 件"` のような組み立て（プレースホルダー付きの文にする）
- 複数形：英語の `1 items`、言語ごとの複数形の規則（ICU の plural、gettext の ngettext）
- 日時：既定ロケールでの書式化（`toLocaleString()` の引数なし、`strftime` の環境依存、`DateFormat.getInstance()`）、保存時のタイムゾーン、相対時刻（「3 分前」）の翻訳、週の始まり
- 数値・通貨：桁区切り、小数点（`,` と `.`）、通貨記号の位置、単位（バイト・KB の計算と表記）、パーセント
- ソート・比較：ロケール依存の文字列比較（collation）、大文字小文字（トルコ語の i）
- 文字幅・長さ：翻訳で長くなる言語でのレイアウト（C-13 と接する）、`length` が文字数でない（サロゲートペア・結合文字・絵文字）、全角と半角
- 入力：全角・半角、正規化（NFC/NFKC）、前後の空白、改行コード、右から左の言語
- 用語の統一：同じ概念に別の語、英語表記の揺れ、略語
- 敬体・常体の混在、句読点の有無、記号の統一（半角コロンと全角コロン）
- サーバー・バッチが作る文言（通知・生成文書・コメント）が多言語化の仕組みを通っているか、受け手の言語設定を見ているか
- ログは翻訳しない（運用者向け・検索のため）が、利用者に見せるものと混ざっていないか
- 文字コード：ファイルの読み書きで UTF-8 を明示しているか（Java・Python 2 系・Windows の既定）

## NG 例

### 例1（Rails）：直書きの文言

```erb
<%= button_to "中止", cancel_path %>
```

英語の画面で日本語が出る。`t("tasks.cancel")`。i18n の仕組みがあるなら `should`、全言語の対応が受け入れ条件なら `must`。

### 例2（Java）：文の連結

```java
String msg = t("remaining") + " " + n + " " + t("items");
```

語順が言語で変わり、複数形も扱えない。`MessageFormat`/ICU のプレースホルダーと plural。`should`。

### 例3（Python）：ロケール・タイムゾーンが環境依存

```python
label = dt.strftime("%c")
```

サーバーの環境で表示が変わり、利用者のタイムゾーンと合わない。ロケールとタイムゾーンを明示して渡す。`should`、記録として残る文（生成文書）なら `must`。

### 例4（Android）：片方の言語にだけキーがある

`values/strings.xml` に `cancel_task` を足したが `values-en/strings.xml` に無い。既定にフォールバックして日本語が出る（または lint で失敗）。`should`。

### 例5（JavaScript）：文字数の数え方

```js
title.slice(0, 20) + "…"; // 絵文字やサロゲートペアの途中で切れる
```

`Intl.Segmenter` か `[...title]`。表示が壊れる。`should`。

### 例6（Go）：用語の揺れ

新しい画面で「チケット」を使っているが、リポジトリは「タスク」に統一している（用語集あり）。`should`。

## 見落としやすい所

- サーバー・バッチが作る文（通知・生成文書・コメント）は画面の i18n の外にあることが多い。仕組みが別なら、その仕組みを通っているか
- 片方の言語だけ動作確認されている。もう片方の辞書を開く
- 日時は「保存・計算は UTC、表示でロケール」の原則から外れた所を探す

## 指摘の書き方の例

- title：`通知の本文が日本語で直書きされ、受け手の言語の設定が無視される`
- problem：`notifier.rb:40 の文字列は日本語の直書きで、プロジェクトの設定 notify.language が en でも日本語で送られる。既存の通知は I18n.t を通している`
- evidence：`app/services/notifier.rb:40 と、既存の通知 app/services/notifier.rb:22 の書き方を比べた`
- suggestion：`I18n.t のキーにし、ja と en の両方の辞書に足す`
