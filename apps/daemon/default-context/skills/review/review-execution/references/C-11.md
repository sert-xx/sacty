# C-11 依存・ビルド・CI

見るもの：依存の必要性とライセンス、版の固定、ロックファイルとの整合、ビルド・CI の変更が意図どおりか、再現性、供給元の信頼。
見ないもの：依存の使い方の脆弱性（C-3）。
起動条件：依存の追加・更新・削除、ロックファイル、ビルド・パッケージ・CI・コンテナの設定を変える。

パッケージの仕組みは問わない（npm/pnpm/yarn、pip/poetry/uv、Go modules、Maven/Gradle、Cargo、Bundler、NuGet、Composer など）。

## 確かめる手順

1. 依存の変更を列挙する（manifest とロックファイルの差分）。追加・更新・削除ごとに理由が説明にあるか
2. 追加した依存：本当に必要か（標準ライブラリ・既存の依存でできないか）、保守されているか、ライセンス、推移的な依存の量、実行時依存と開発時依存の区別
3. 更新：メジャー更新なら変更履歴の破壊的変更を確かめたか、ロックファイルが同時に更新されているか、manifest と一致するか
4. ビルド・CI の変更：何が実行されなくなったか（テストのスキップ、lint の除外、失敗の無視）、環境の差（ランタイムの版、OS）、キャッシュのキー
5. 再現性：ロックファイルの有無と CI でのロック準拠のインストール（`npm ci`、`pip install -r` の固定、`go mod verify`、`--locked`）、`latest`、ビルドが時刻・環境に依存しないか
6. コンテナ：ベースイメージのタグ（`latest`・digest 固定）、不要なファイルの混入、root での実行（C-3）、レイヤーのキャッシュ

## チェックポイント

- manifest とロックの不一致：manifest だけ変えてロックを更新していない、逆。`go.sum` の欠落
- 版の指定：`*`・`latest`・広すぎる範囲（semver のメジャー 0 系は破壊的変更を含む）、Git の URL やブランチ指定、`>=` だけ
- 不要な依存：1 関数のために大きなパッケージ、既存の依存と重複する機能（2 つの HTTP クライアント、2 つの日付ライブラリ）
- 開発時依存の混入：実行時に不要なものが実行時依存に（配布サイズ、攻撃面）、逆に実行時に要るものが開発時に（本番で欠ける）
- 供給元：名前が似た別パッケージ（typosquatting）、ダウンロード数・最終更新・保守者、スコープ・グループ ID の取り違え、プライベートレジストリと公開の混同（dependency confusion）
- ライセンス：プロジェクトの方針と合うか（方針が無ければ指摘しない）
- 削除：まだ使っている所が無いか（動的 import、設定ファイル、スクリプト、プラグインの読み込み）
- ビルド設定：出力先、ソースマップ・デバッグ情報、target の版、最適化の有効化、環境変数の埋め込み（秘密情報は C-3）
- CI：テストが実行されなくなる変更（パスのフィルタ、matrix の削減、`if` 条件）、失敗を無視する設定（`continue-on-error`、`|| true`、`allow_failure`）、タイムアウト、権限の拡大、サードパーティ Action の版固定（SHA）
- キャッシュ：キーに依存の内容が入っているか（古いキャッシュで通る）、キャッシュの汚染
- スクリプト：インストール時に走るスクリプト（`postinstall`、`setup.py` の任意コード、追加した依存が持つもの）、ビルドスクリプトの変更が他を壊さないか
- 再現性：ビルドの中でネットワーク取得（`curl | sh`）、時刻・乱数の埋め込み、ツールチェーンの版の未固定
- 配布物：パッケージに含まれるファイル、不要なファイルや秘密情報の混入、実行ファイルのパス・権限
- 複数パッケージ（monorepo/workspace）：版の整合、相互参照、ビルド順序
- コンテナ：タグの固定、OS パッケージの版、不要なツール、`.dockerignore`、マルチステージでの秘密情報の残留、root ユーザー

## NG 例

### 例1（npm）：ロックファイルを更新していない

`package.json` で `yaml` を `^2.4` → `^2.6` にしたが `package-lock.json` が元のまま。`npm ci` が不一致で失敗するか、古い版で動く。`must`。

### 例2（Python）：1 関数のための依存

```python
import left_pad   # str.rjust で足りる
```

推移的な依存と供給元の危険を増やす。`should`。

### 例3（GitHub Actions）：CI でテストを黙って減らす

```diff
-      run: pytest
+      run: pytest --ignore=tests/integration
```

統合テストが実行されなくなる。説明に理由が無ければ `must`。

### 例4（GitHub Actions）：Action の版が浮く

```yaml
- uses: some-org/deploy-action@main
```

Action の変更で壊れる・乗っ取られる。タグか SHA に固定。`should`、デプロイに関わるなら `must`。

### 例5（Dockerfile）：ベースイメージが latest

```dockerfile
FROM python:latest
```

再現できず、突然壊れる。版（できれば digest）を固定。`should`。

### 例6（Go）：replace でローカルパスを指している

```
replace example.com/lib => ../lib
```

CI や他の開発者の環境で解決できない。開発中の一時的な指定が残っている。`must`。

## 見落としやすい所

- ロックファイルの差分は大きくて読まれない。追加された推移的な依存の名前を眺め、見慣れないものを確かめる
- 「依存を上げただけ」の変更に、破壊的変更の確認が無い
- CI の条件の変更で、ある分岐だけテストが走らなくなる

## 指摘の書き方の例

- title：`package.json の yaml の更新に package-lock.json が追従していない`
- problem：`package.json は yaml ^2.6 だが、ロックは 2.4.5 のまま。npm ci はロックと manifest の不一致で失敗する`
- evidence：`package.json:23 と package-lock.json の "node_modules/yaml" を比べた`
- suggestion：`npm install を実行してロックを更新し、差分に含める`
