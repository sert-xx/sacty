# D-10 簡潔さ・範囲

見るもの：依頼・上位の要件に無い要求や機能、読む人がすでに知っていること（依頼の言い直し・背景・一般論・用語の説明・既存のコードの説明）、既存の仕組みが保証していて今回の変更で変わらない振る舞いの書き直し、今回の変更で起こりえない異常系・非機能、当てはまらない観点のための「対象外」の節や行、採らなかった案、重複、人間が判断することが冒頭で分かるか（判断することと、作者が既定で決めたことの区別。「確認したいこと」「既定で決めたこと」の節がある文書では、依頼の目的に関わる判断と、依頼者に不利益が出うる既定が、既定に紛れていないか。判断する項目が、依頼者が一番決めたいことから並んでいるか）、分量が最小限か。
見ないもの：書かれていないこと（D-3）、文言の曖昧さ（D-6）、リポジトリの決まりがこの種の変更に求める条件とその確かめ方（下の「リポジトリの決まりから導かれる条件は消す指摘にしない」）、リポジトリの文書や既存の振る舞いに根拠のある記述（下の「根拠のある記述は、依頼に無いことだけを理由に消さない」）。

「書きすぎていること」を探す観点。D-3 などの観点は欠落を探すので、それだけでは文書が回を重ねるごとに長くなる。
この観点は、承認する人が読む量を、判断に要る分まで減らす。
読む人は前提（暗黙知）を持っているので、文書の初版は最小限でよい。足りない所は、読む人が求めたときに足す。
情報が多いと、読む人は読み切れずに承認してしまい、レビューの目的を失う。

## 確かめる手順

1. 根拠（タスク・Issue・上位の要件）を読み、依頼が求めることを短く書き出す
2. 文書の要求・節・項目を1つずつ、書き出した依頼のどれのためにあるかに結びつける。結びつかないものは、依頼に無い要求か、要らない記述の候補
3. 候補ごとに、既存のコード・規約で、それが今回の変更の前から成り立っているかを確かめる。成り立っていて、今回の変更で変わらないなら、書き直しにすぎない
   - 成り立っているか確かめる前に、候補が「リポジトリの決まり」から導かれる条件でないかを確かめる（README・CONTRIBUTING・AGENTS.md・変更履歴の方針・PR テンプレート・CI の設定、依頼の根拠に添えられた「決まりから要る」という記述）。導かれるなら書き直しではなく、消す指摘にしない（下の節）
4. 異常系・境界・非機能の記述ごとに、今回の変更でそれが新しく起こりうるかを問う
5. 記述ごとに、読む人がそれを知らないと判断や作業を誤るかを問う。誤らないなら、読む人がすでに知っていることの候補
6. 冒頭を読み、人間が判断すること（確認したいこと）と、作者が既定で決めたことが、詳細を読まずに分かるかを確かめる
   - 「確認したいこと」「既定で決めたこと」の節がある文書（要求要件・設計など）では、次の2つも確かめる。節が無い文書では確かめない
   - 「既定で決めたこと」の項目ごとに、依頼の目的に関わるか、依頼者に不利益が出うるか（元に戻せない・失われる・使えなくなる・手間や費用が増える・依頼の意図と逆に働く）を問う。当てはまるものが既定に置かれていたら、確認したいことに移させる
   - 「確認したいこと」を、依頼者が一番決めたいこと（依頼の目的に直結すること）から並んでいるかを確かめる。目的に関わる判断が should や後ろの方に埋もれていないか、推奨の答えが依頼の意図と逆を向いていないか
   - 「確認したいこと」の項目ごとに、確認しないまま進めた場合の具体的な懸念（何が・誰に・どう困るか）が書かれているかを確かめる
   - 要求要件・設計では、スコープ（何を実現するかと、対象・対象外）が最初にあり、要求や設計の中身より前で範囲が分かるかを確かめる
7. 全体の分量を、変更の規模（触れるファイル・振る舞いの数）と比べ、削っても判断が変わらない記述が残っていないかを確かめる

## チェックポイント

- 依頼に無い機能・画面・設定・将来の拡張を、要求や設計にしている
- 既存の仕組みがすでに保証する振る舞い（フレームワークの入力の検証・既存の認可・既存のエラー処理）を、今回の要求として書き直している
- 今回の変更で起こりえない異常系（触れていない外部連携の失敗、変えていない入力の誤り）を書いている
- 関係しない観点（性能・移行・運用・国際化など）のために「対象外」「該当なし」の節や行を作っている
- 同じことを複数の節で書いている（冒頭の要約と詳細、要求と設計の言い直し）
- 依頼の言い直し・背景・一般論・用語の説明・既存のコードの説明など、読む人がすでに知っていることを書いている
- 検討して採らなかった案や、長い理由の説明を書いている（理由は要るときだけ1行でよい）
- 作者が既存のやり方にそのまま従っただけのことを、「既定で決めたこと」に並べている
- 確認したいことが多すぎる（後で違うと分かっても追加の作業で済むものが 5 件を超える）、重要度の順になっていない、推奨の答えが無い、確認しない場合の懸念が無いか一般論だけ。作者が既定で決められることを人に問うている
- 人間が判断することが本文の途中に埋もれ、冒頭で分からない
- 「既定で決めたこと」の節がある文書で、依頼の目的に関わる判断や、依頼者に不利益が出うる既定（戻すときに判定し直さない、など）を、「既定で決めたこと」に置いている。確認したいことに出ていない（`must`）
- 「確認したいこと」の節がある文書で、依頼者が一番決めたいことから並んでいない。目的に関わる判断が should に埋もれている、推奨の答えが依頼の意図と逆を向いている（`must`）
- 要求要件・設計など、人が承認する成果物の本文に、作業の経過・指摘への対応の報告・エージェント向けのメモが残っている（`must`。見つけ方は D-6）
- 小さな変更なのに、節や要求の数が大きな変更と同じ
- 記述の根拠をリポジトリの文書・既存の振る舞いに探さずに、「依頼に無い」だけを理由に消す指摘を出している（`must`。消した記述が、文書や既存の振る舞いが定める前提だった）

## リポジトリの決まりから導かれる条件は消す指摘にしない

リポジトリの決まりが、この種の変更に求める条件（版を上げる・変更履歴に書く・生成物を作り直して定義と一致させる・ドキュメントを直す・特定の検査を通す、など）は、依頼の文に無くても、今回の変更が満たすべき条件である。次の理由で、「既存の仕組みが保証していて今回の変更で変わらない振る舞いの書き直し」でも「依頼に無い要求」でもない。

- 決まりは、変更する人が守って初めて成り立つ。今回の変更が守らなければ、守られない（既存の仕組みが保証しているのではない）
- 要求要件に無ければ、設計・実装・レビューが、決まりを満たす根拠を失う。承認する人も、決まりを満たす変更かを確かめられない
- 「作業手順」ではなく結果を条件にしているなら（生成物が作り直した結果と一致する・版が定義と一致する・変更履歴に行がある）、実装方法に踏み込んでいない

指摘にする前に、候補がこれに当たらないかを確かめる。

- 候補の条件を、決まりの出典（ファイルと節）に結びつける。依頼の根拠（タスクの本文・集めた情報）に「決まりから要る」とあれば、その記述も出典になる。結びつけたら、その出典を `checked` に書き、指摘にしない
- 条件の中身が誤っている・確かめられない（例：生成物に出ない項目を、生成物に載ると書いている）なら、消す指摘にせず、直す指摘にする（条件は残し、誤りを直す）
- 決まりを引けず、依頼にも根拠にも無い条件だけが、通常どおり「依頼に無い要求」の候補になる
- 決まりの全文の書き写し・決まりの理由の説明・今回の変更に当てはまらない決まり（変更しないファイルの決まりなど）は、通常どおり消す指摘にしてよい

## 根拠のある記述は、依頼に無いことだけを理由に消さない

「依頼や上位の要件に無い」は、消す理由の候補にすぎない。記述が、リポジトリの文書（README・AGENTS.md・docs の運用や仕様の文書など）や、既存のコードの振る舞いに根拠を持つなら、依頼の文に無くても、今回の変更が満たすべき前提の可能性がある。依頼に無いという理由だけで消すと、前提を満たさない設計・実装になる。

- 消す前に、記述の根拠を探す。タスクの語や記述の主題で、リポジトリの文書の置き場（docs などのディレクトリ。README や AGENTS.md から参照されていない文書を含む）と、関係するコードを調べる
- 根拠が見つかれば、消す指摘にしない。根拠（文書とその節、コードの場所）を `checked` に書いて残す。根拠の文書が要求要件・設計に書かれていなければ、出典として添える指摘（直す指摘）にする
- 根拠を確かめられない（調べても見つからない・文書と食い違う）が、依頼の目的に関わりうる記述は、消さずに、人に確かめる「確認したいこと」に回す指摘にする
- 調べても根拠が無く、依頼の目的にも関わらない記述だけが、通常どおり「依頼に無い要求」として消す対象になる

## NG 例

### 例1：依頼に無い機能

依頼は「一覧に作成日の列を足す」だけだが、要求要件に「作成日で並べ替えられる」「作成日で絞り込める」がある。実装の範囲が依頼の 3 倍になる。`must`。

### 例2：既存の仕組みの書き直し

ログインの画面の文言を変える要求要件に、「パスワードを 5 回間違えたらロックする」「セッションは 30 分で切れる」がある。どちらも既存の認証の振る舞いで、今回の変更で変わらない。`should`。

### 例3：起こりえない異常系

表示だけを変える設計に、「データベースへの接続が切れた場合」「外部 API が 429 を返した場合」の振る舞いがある。今回の変更はデータベースにも外部 API にも触れない。`should`。

### 例4：「対象外」の節

1 ファイルの関数を直す設計に、「性能：対象外」「移行：対象外」「運用：対象外」「セキュリティ：対象外」の節が並ぶ。`should`。

### 例5：確認したいことが多すぎる

確認したいことが 12 件あり、そのうち 8 件は既存のコードの規約で決まる（ログの形式、エラーの文言の書き方など）。人間が読んで判断する量が増える。規約で決まるものは作者が規約に従って決め、どこにも書かない（「既定で決めたこと」にも並べない）。「既定で決めたこと」に残すのは、人間が異論を持ちうる判断だけにする。`should`。

### 例6：読む人がすでに知っていることの説明

一覧の画面に列を足す設計の冒頭に、画面の構成・使っている表のライブラリ・既存の API の説明が 20 行ある。承認する人は、どれも知っている。今回の変更で何が変わるかが、その後ろに埋もれる。`should`。

### 例7：依頼者に不利益な既定が、既定に紛れている

予約の論理削除の依頼で、「既定で決めたこと」に「利用停止（`isActive`）は、戻すときに判定し直さない」がある。戻した予約が、停止中の会議室に入ってしまう。依頼者に不利益が出うるので、確認したいことに「戻すときに判定し直すか（推奨：…）」として出す。`must`。

### 例8：依頼者が一番決めたいことが埋もれる

一覧の高速化の依頼で、確認したいことの先頭が「ログの形式」で、「どこまで速くするか（初期表示か、操作の応答もか）」が should の 3 番目にある。目的に関わる判断を must の先頭に置き、規約で決まるものは後ろ（または既定）にする。`must`。

### 例9：リポジトリの決まりから導かれる条件を、書き直しとして消させる（指摘にしない）

API の定義と生成物のあるリポジトリで、要求要件に「API の定義と生成した型・リファレンスに項目を載せ、版を 1.4.0 にする」（R-2）と、確かめ方「生成物の一致を確かめる検査が通り、版と変更履歴の行がある」がある。README の「変更の決まり」が「API の変更は変更履歴に書き、定義とパッケージの版を同じ値に上げる」「定義を変えたら生成し直す」と定めている。
「README の変更の決まりの書き直しで、依頼の振る舞いのどれにも対応しない。R-2 と確かめ方を消す」とする指摘は、出さない。決まりは変更する人が守って成り立つもので、書き直しではない。消すと、設計・実装が決まりを満たす根拠が要求要件から消え、承認する人も確かめられず、差し戻しでやっと入り直す。出典（README の「変更の決まり」）を `checked` に書いて残す。
条件の中身に誤りがあれば（生成物に出ない項目を載ると書いている、など）、R-2 を消さずに、直す指摘にする。

### 例10：文書に根拠のある記述を、依頼に無いとして消させる（指摘にしない）

予約の画面の依頼で、設計に「作成・キャンセルの後に空き状況を取り直す」がある。依頼の文には無いが、運用の文書（docs/operations.md）に「空き状況は常に DB の最新」と定めがある。
「依頼に無い。消す」とする指摘は出さない。文書の節を `checked` に書いて残し、設計に出典として添える。文書が README や AGENTS.md から参照されていなくても、同じ。

## 見落としやすい所

- 1 つ 1 つは正しい記述なので、正しさの観点（D-2）では指摘されない。「依頼のどれのためにあるか」で読む
- 前回のレビューの指摘（D-3 など）に応えて足した記述が、今回の変更に関係しないまま残る
- 削る指摘も、要る記述を消させないこと。依頼のためにある記述、今回の変更で起こりうる異常系は残す
- 読む人（承認する人・依頼した人）が差し戻しで詳しく書くよう求めて足した記述は、削る指摘にしない
- 「README に書いてあるから書き直し」という見方。README・CONTRIBUTING などの決まりが、この種の変更に求める条件は、書き直しではなく、今回の変更が満たすべき条件である。書き直しなのは、決まりそのものの説明・全文の写しだけ

## 指摘の書き方の例

- title：`依頼に無い並べ替え・絞り込みが要求要件にある`
- problem：`依頼は作成日の列を一覧に足すことだけだが、R-4（作成日で並べ替える）と R-5（作成日で絞り込む）がある。このまま承認すると、依頼に無い機能まで実装とテストの範囲になる`
- evidence：`タスクの本文と要求要件の R-1〜R-6 を突き合わせ、R-4・R-5 が依頼のどの文にも対応しないことを確かめた`
- suggestion：`R-4・R-5 を消す。要るなら、確認したいことに「並べ替え・絞り込みも要るか（推奨：要らない。依頼に無いため）」として挙げる`
