# C-18 既存の実装との調和

見るもの：文書に書かれていないが、既存のコードを読めば分かる慣習に、変更が合っているか。命名の方針（語彙・接頭辞と接尾辞・単数と複数・ファイルの名前）、置き場所と構成（ディレクトリ・ファイルの分け方・テストの置き方）、層の分担（どの層に何を置き、何を置かないか。業務のロジックの置き場所・依存の向き・境界の越え方）、技術の使い方の方針（データアクセス・外部の呼び出し・エラーの表し方・ログ・設定・依存の渡し方・非同期の書き方・テストの書き方で、どの仕組みを使い、何を使わないか）。
見ないもの：リポジトリの慣習に依らない読みやすさ・責務の大きさ・重複・言語の一般的な慣習（C-5）、別の方針のほうが優れているか（C-17）、画面の見た目と UI の部品の規約（C-13）、利用者に見える文言の規約（C-14）、既存の慣習そのものの良し悪し（気づいたら `out_of_scope_notes`）、リポジトリの指示が明文で定める決まりとの照合（X-3。依頼文の「見ないもの」に書かれている回だけ。書かれていなければ、規約の文書との整合もこの観点で見る）。

ほかの観点は、変更そのものの良し悪しを見る。この観点は、変更が「このリポジトリの書き方」になっているかだけを見る。
1つ1つは正しく動くコードでも、既存と違うやり方が混ざると、次に読む人はどちらに合わせればよいか分からなくなり、既存の仕組みが前提にしていること（どの層を通るか・何を使うか）が崩れる。

基準は、対象のリポジトリの既存のコード。依頼文の「見ないもの」に X-3 が書かれていない回は、リポジトリの規約の文書（CONTRIBUTING・コーディング規約・lint 設定など）も基準にする。
自分の好み、「一般にはこうする」という知識、他のリポジトリの慣習を基準にしない。
既存の慣習が一般的な書き方と違っていても、変更には慣習に合っていることを求める。

## 確かめる手順

1. 規約の文書を読む（CONTRIBUTING・コーディング規約・lint 設定、README やアーキテクチャの説明）。依頼文の「見ないもの」に X-3 が書かれている回は、既存の書き方と層の意図を知るためだけに読み、明文の決まりとの照合は X-3 に任せる。書かれていない回は、文書が定める決まり（命名・置き場所・層の分担・技術の使い方）も、下の手順で導く慣習と同じように差分と照らす。依頼文の「基準にしないリポジトリの指示」に挙げられた文書は、どちらの回でも使わない
2. 差分から、変更が足した・変えたコードの種類を書き出す（例：リクエストの入口、業務のロジック、データアクセス、外部の呼び出し、バッチ、設定、テスト、移行）。種類ごとに、置いた場所と、使った仕組みを控える
3. 種類ごとに、差分の外から、同じ種類の既存のコードを選んで読む。あれば 3 つ以上読む
    - 同じディレクトリ・同じ層にある隣のファイル
    - 同じ役割を名前で示しているファイル（同じ接尾辞・同じ置き場）
    - 似た機能のうち、いちばん新しく足されたもの
    - 変更したファイルの、今回変えていない部分
4. 今回の変更が足した・書き換えたコードは、慣習の根拠にしない。生成されたコード、依存として取り込んだ他者のコード、テストの fixture・例・テンプレートも根拠にしない
    - 変更前の版を読めるとき（依頼文が写しを渡している、作業領域で履歴を読める）は、変更前の版を根拠にする
    - 読めないときは、差分に現れる行と、差分が新しく足したファイルを根拠から除き、差分に含まれない既存のファイルと、変更したファイルの差分に現れない行だけで導く
    - 除いた結果、ある種類のコードの既存の例が残らない・足りない（その種類のコードの大半を今回の変更が書き換えた）ときは、その種類の慣習を導かず、導けなかったことと理由を `limitations` に書く。導けた種類だけで判定してよい（`failed` にはしない）。リポジトリにその種類の既存のコードがもともと少ないときは、`limitations` ではなく `checked` に「慣習が無い」と書く
5. 読んだコードから、慣習を「〜は〜で行う」「〜には〜を置かない」の形で書き出す。次の軸を順に当てる
    - 命名：同じ役割のものに付けている語・接頭辞・接尾辞、同じ概念を指す語（業務の用語）、ファイルとディレクトリの名前の形
    - 置き場所：この種類のコードをどこに置くか、1 ファイルに何を入れるか、テストをどこに置くか
    - 層の分担：ディレクトリの構成と依存の向き（どこがどこを読み込んでいるか）から層を読み取り、それぞれの層が持つものと持たないものを確かめる（例：入口は入力の変換と呼び出しだけを持つ、業務の判定は業務の層が持つ、データアクセスは決まった層だけが行う）
    - 技術の使い方：同じことをするのに、既存がどの仕組み・ライブラリ・書き方を使っているか。使っていない書き方は何か（例：問い合わせは決まった API で組み立て、文字列で組み立てない）
6. 書き出した慣習ごとに、慣習と言えるかを判定する。迷うものは、リポジトリ全体を検索して数える（そろっている件数と、外れている件数）
    - そろっている（外れが無い。あっても少数で、理由がコメント・名前・置き場から読み取れる）：慣習とする
    - 割れている（2 通り以上が、理由なく並んでいる）：慣習としない。ただし、新しいコードが片方にそろっていて、古いコードだけがもう片方なら、移行の途中とみなし、新しい側を慣習とする
    - 例が 1〜2 件しか無い：慣習としない
7. 差分を、慣習と1つずつ照らす。外れている所ごとに、迂回したことで効かなくなる既存の仕組みが無いかを確かめる（認可・入力の検証・トランザクション・監査の記録・利用者ごとの絞り込みなどを、決まった経路が担っていないか）。効かなくなる仕組みがあれば、外れる理由が書かれていても指摘にする（`must`）
8. 効かなくなる仕組みが無い外れは、外れる理由があるかを確かめる。根拠（タスク・Issue・PR の本文・要求要件・設計）かコードのコメントが理由を述べていれば、指摘にしない。理由がどこにも書かれていない外れは、慣習の仕組みでは今回の要件を満たせないと分かるときでも、外れる理由をコメントに書くことを `should` で求める（次に読む人が、意図した外れかを判断できないため）。慣習の仕組みで満たせるなら、慣習に合わせることを `should` で求める
9. `checked` に、慣習としたもの（読んだファイルか、数えた件数を添える）と、慣習としなかったもの（割れている・例が少ない）を残す

## チェックポイント

- 命名の方針：同じ役割のものに、既存と違う語・接頭辞・接尾辞を付けている。既存が1つの語で呼んでいる概念を、別の語で呼んでいる。ファイル・ディレクトリの名前の形が既存と違う
- 置き場所：この種類のコードを、既存と違うディレクトリ・ファイルに置いている。既存が分けているものを 1 ファイルにまとめている。テストの置き方・名前が既存と違う
- 業務のロジックの置き場所：既存が業務の層に置いている判定・計算・状態の遷移を、入口・画面・データアクセス・バッチの側に書いている
- 層の飛び越し：既存が必ず経由している層を飛ばして、下の層や外部を直接呼んでいる（入口からデータアクセスを直接呼ぶ、業務の層から外部の API を直接呼ぶ）。既存が守っている依存の向きに逆らっている
- データアクセスの方法：既存が決まった仕組み（問い合わせを組み立てる API・決まった層の関数）だけでデータを読み書きしているのに、別の方法（文字列で書いた問い合わせ・別のクライアント）を持ち込んでいる
- 共通の仕組みの迂回：既存が共通の仕組み（エラーの型と変換・ログ・設定の読み方・依存の渡し方・外部の呼び出しの入口・日時の取り方）を通しているのに、直接書いている
- エラーの表し方：既存が失敗を表す方法（例外・戻り値・結果の型・エラーコード）と違う方法で表している
- 同じ仕組みの二重化：既存が使っているものと同じ役割の、別のライブラリ・別の書き方を持ち込んでいる（2 つ目の HTTP クライアント、2 つ目の検証の仕組み、2 つ目の日時のライブラリ）
- テストの書き方：既存のテストが使う仕組み（準備の方法・代役の作り方・検証の書き方）を使わず、別のやり方で書いている
- 理由の書かれていない外れ：慣習の仕組みでは要件を満たせず、外れる理由がある変更なのに、理由が根拠にもコードにも書かれていない

## 重要度の決め方

- `must`：層の分担・決まった経路から外れたことで、その経路が担っている仕組み（認可・入力の検証・トランザクション・監査の記録・利用者ごとの絞り込みなど）が、今回の変更で効かなくなる。外れる理由が書かれていても変わらない
- `should`：そろっている慣習（命名の方針・置き場所・層の分担・技術の使い方）から、理由なく外れている
- `nit`：表記の細部。慣習と言えるかが弱いもの（外れがいくつかある）
- 出さない：慣習としなかったもの（割れている・例が少ない）、理由が根拠かコードのコメントに書かれている外れ（`must` に当たるものを除く）

## NG 例

### 例1（Python）：既存が使っていない方法でのデータアクセス

```python
def count_overdue(session, owner_id):
    row = session.execute(text("SELECT COUNT(*) FROM invoices WHERE owner_id = :o AND due < now()"), {"o": owner_id})
    return row.scalar()
```

既存の読み書きは、どれも問い合わせを組み立てる API で書かれ、文字列で書いた問い合わせは 1 件も無い（検索して数える）。
既存の API で書ける問い合わせなので、`should`。
既存の経路が利用者ごとの絞り込みを自動で足していて、この書き方で絞り込みが外れるなら `must`。

### 例2（Java）：業務のロジックを入口に書く

```java
@PostMapping("/orders/{id}/cancel")
public Response cancel(@PathVariable long id) {
    Order order = orders.findById(id);
    if (order.getStatus() == Status.SHIPPED || order.getPaidAt().isBefore(now().minusDays(30))) {
        return Response.conflict();
    }
    order.setStatus(Status.CANCELLED);
    orders.save(order);
    return Response.ok();
}
```

既存の入口は、入力を変換して業務の層のメソッドを呼ぶだけで、状態の判定と遷移は `Order` の側（`order.ship()` など）にある。
取り消せる条件を入口に書くと、別の入口（バッチ・管理画面）から同じ条件が効かない。`should`。

### 例3（Go）：命名の方針

```go
func (r *UserRepo) GetUserFromDB(ctx context.Context, id int64) (*User, error)
```

既存のリポジトリの層は、`FindByID`・`FindByEmail`・`ListByTeam` のように、型の名前を繰り返さず、1 件は `Find`、複数は `List` で始めている（12 個の関数がそろっている）。`should`。
関数が 2〜3 個しか無く、形が割れているなら、慣習とせず、出さない。

### 例4（TypeScript）：失敗の表し方

```ts
export async function parseConfig(path: string): Promise<Config> {
  const raw = await readFile(path, "utf8");
  if (!raw.trim()) throw new Error("empty config");
  return schema.parse(JSON.parse(raw));
}
```

同じディレクトリの読み込みの関数は、どれも `Result<T, ConfigError>` を返し、例外を投げない。呼び出し元は戻り値だけを確かめている。
例外にすると、呼び出し元で捕まえられずに落ちる。呼び出し元で捕まえられない経路が実際にあれば `must`、無ければ `should`。

### 例5（Ruby）：割れているものは、慣習としない

```ruby
class ReportMailer
  def deliver_weekly = HTTParty.post(ENDPOINT, body: payload)
end
```

既存の外部の呼び出しは、`Faraday` が 6 箇所、`HTTParty` が 5 箇所で、新しさにも偏りが無い。
どちらが慣習とも言えないので、指摘にしない。`checked` に「HTTP クライアントは割れている（6 対 5）ので、慣習としなかった」と残す。

### 例6（Kotlin）：理由が書かれている外れは、指摘にしない

```kotlin
// 集計は 200 万行を対象にする。ORM では行ごとに読み込むため、ここだけ SQL で集計する（設計 3.2）
val totals = jdbc.query("SELECT region, SUM(amount) FROM sales GROUP BY region", mapper)
```

既存のデータアクセスは ORM だけだが、外れる理由がコメントと設計にある。指摘にしない。
ただし、ORM の経路が担う仕組み（利用者ごとの絞り込みなど）がこの問い合わせで効かなくなるなら、理由が書かれていても `must`。
理由がどこにも書かれていなければ、「外れる理由をコメントに書く」ことを `should` で求める。

## 見落としやすい所

- 差分だけを読んで判定しない。この観点の根拠は差分の外にある。既存のコードを読まずに出した指摘は、好みと区別がつかない
- 自分の好みを慣習と呼ばない。`evidence` に、既存の例（ファイルと行）を 2 つ以上か、数えた件数を書けない指摘は出さない
- 既存の慣習が良くないと思っても、変更に別の書き方を求めない。慣習を変える提案は、この変更の範囲の外（`out_of_scope_notes` に1行）
- 承認済みの要求要件・設計が、既存と違うやり方を決めているときは、指摘にしない（設計そのものの妥当性は、設計のレビューで扱う）。ただし、そのやり方で効かなくなる仕組みがあるとき（手順 7）は、設計が決めていても `must` で出し、設計と食い違うことを `problem` に書く
- 古いコードだけに残るやり方を、慣習として新しいコードに求めない。新しく足されたコードがどちらにそろっているかを見る
- 既存のコードが少ないリポジトリ（始まったばかり・この種類のコードが初めて）では、慣習が無い。無いことを `checked` に書き、無理に導かない。指摘が無ければ `passed` でよい
- 同じ慣習からの外れが差分の中に何箇所あっても、1 件の指摘にまとめ、箇所を列挙する
- 依頼文の「基準にしないリポジトリの指示」に挙げられた文書は、規約として使わない

## 指摘の書き方の例

- title：`取り消しの条件を入口に書いていて、業務の層に置く既存の分担と違う`
- problem：`取り消せるかの判定（出荷済み・支払いから 30 日）と状態の変更を、入口のメソッドに書いている。既存の入口は業務の層のメソッドを呼ぶだけで、状態の判定と遷移は Order にある。別の入口から取り消すと、この条件が効かない`
- evidence：`OrderController.java:41-49。既存の入口 OrderController.java:20-28（ship）・RefundController.java:15-22 は、order.ship()・order.refund() を呼ぶだけ。Order.java:60-95 に状態の遷移がまとまっている`
- suggestion：`Order に cancel() を足して条件と遷移を移し、入口はそれを呼ぶ`
