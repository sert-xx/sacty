# C-6 互換性・影響範囲

見るもの：公開 I/F（API・CLI・設定・イベント・データ形式・ライブラリの公開シンボル）の変更と既存の呼び出し元への影響、後方互換、既定値の変更、変更した関数の全呼び出し元が追従しているか、移行の要否、feature flag の扱い。
見ないもの：DB スキーマの移行の手順（C-9）。

## 確かめる手順

1. 変更した「外から見える面」を列挙する：公開関数・メソッド・型の引数と戻り値、HTTP/gRPC API の形、CLI の引数と出力、設定ファイルのキーと既定値、イベント・メッセージの形、ファイル・ログの形式、環境変数、ライブラリなら semver 上の公開 API
2. それぞれの利用者を探す：リポジトリ内の呼び出し元（全文検索。動的な参照も）、他リポジトリ・利用者（README・公開 API なら全員）、保存済みのデータ（古い形式のファイル・DB の行・キュー内のメッセージ）
3. 利用者ごとに「変更後も動くか」を判定する。動かないなら、追従の変更が差分に入っているか、移行の手順があるか、互換の層があるか
4. 既定値の変更は「何も設定していない利用者」の振る舞いが変わる。その影響と周知を見る
5. 削除・改名は、使っている所が本当に無いかを検索で確かめる。文字列で参照されるもの（イベント名、設定キー、JSON のキー、リフレクション、動的 import、テンプレート）はコンパイラが検出しない

## チェックポイント

- シグネチャ変更：引数の追加（必須か任意か）、順序の変更、戻り値の形の変更。呼び出し元を全部直したか。静的型が検出しない変更（動的型の言語、`any`、同じ型の引数の順序、キーワード引数の名前）
- 省略可能だったものが必須になる、エラーにならなかった入力がエラーになる（厳格化は互換を壊す）
- 戻り値の意味の変更：null を返していたのが例外になる、配列の順序が変わる、ID の型が変わる、ゼロ値と「無し」の区別
- HTTP API：フィールドの削除・改名、必須化、ステータスコードの変更、エラーの形、ページング、認証方式。バージョニングの規約
- gRPC/Protobuf/Avro：フィールド番号の再利用、required の追加、enum 値の削除、型の変更
- CLI：フラグの改名・削除、出力の形式（人が読む用と機械が読む用）、終了コード。スクリプトが出力を解析している
- 設定：キーの改名（古いキーを読んで警告するか）、既定値の変更、型の変更、新しい必須キー（既存の設定で起動できない）
- 保存済みデータ：古い形式を新しいコードが読めるか（読み込み時の移行）。新しい形式を古いコードが読む状況（ロールバック、複数版の同時稼働）
- イベント・メッセージ：購読側が別プロセス・別リポジトリにいる。形の変更はデプロイ順序に依存する
- ライブラリの公開 API：semver（破壊的変更ならメジャー）、deprecation の期間、再エクスポート、継承されているクラスのメソッド追加（Java のインターフェースへの追加、Go のインターフェースの拡張）
- feature flag：両方の経路が動くか、flag の既定、flag を消す時期
- 環境・プラットフォーム：ランタイムの最低版、OS 依存（パスの区切り、改行、大文字小文字）、ブラウザ対応、依存のメジャー更新
- ロールバック：この変更をデプロイして戻したとき、残るデータ・設定で古い版が動くか
- 周知：互換を壊す変更が説明・CHANGELOG・README に書かれているか（文書の正確さは U-1。「書かれているべきこと」の欠落はここ）
- 既存のテストの変更：互換を壊したから直したテスト（意図した変更か）

## NG 例

### 例1（Python）：キーワード引数の改名で呼び出し元が壊れる

```python
def parse(text, strict=False): ...   # 以前は lenient=True
```

`parse(text, lenient=True)` と呼ぶ 2 箇所が TypeError になる。動的型なので実行時まで分からない。`must`。

### 例2（Go）：インターフェースへのメソッド追加

```go
type Store interface { Get(k string) ([]byte, error); Set(k string, v []byte) error; Delete(k string) error /* 追加 */ }
```

他パッケージ・他リポジトリの実装がコンパイルできなくなる。公開ライブラリなら破壊的変更。`must`（公開）、内部なら実装を全部直したか確かめる。

### 例3（任意）：既定値の変更が黙って入る

```
timeout = config.get("timeout", 10)  # 以前は 30
```

設定していない利用者の処理が、以前は成功していた 20 秒の操作で失敗し始める。説明に無ければ `must`、意図があっても周知が無ければ `should`。

### 例4（Protobuf）：フィールド番号の再利用

```proto
message Task { string title = 1; /* string owner = 2 を削除 */ int32 priority = 2; }
```

古いメッセージの `owner` が `priority` として解釈される。番号は reserved にする。`must`。

### 例5（JSON API）：エラーの形の変更

```diff
- {"error": "invalid"}
+ {"errors": [{"code": "invalid"}]}
```

クライアントが `error` を見ている。全クライアントを直せる範囲か、両方返す期間を置くか。`must`。

### 例6（任意）：文字列で参照される名前の改名

イベント名 `"task:done"` を `"task.completed"` に改名したが、別モジュールが文字列で購読している（grep で見つかる）。`must`。

## 見落としやすい所

- 差分に出ない呼び出し元。必ず検索する（関数名・設定キー・イベント名・JSON のキー）
- 「内部 API だから」という前提。他リポジトリ・スクリプト・運用手順が使っていないか
- 型の変更が動的型・`any`・JSON の境界で検出されない所
- 変更の正当性ではなく「追従と周知」を見る。変更自体の是非は C-1・C-5

## 指摘の書き方の例

- title：`parse の引数 lenient の改名に scripts/migrate.py の呼び出しが追従していない`
- problem：`parse(text, strict=...) に変えたが scripts/migrate.py:22 は lenient=True のまま。実行時に TypeError で移行スクリプトが止まる`
- evidence：`grep "parse(" で 3 箇所を確かめた`
- suggestion：`旧名も受け付けて警告するか、呼び出し元を直す`
