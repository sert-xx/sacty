# C-7 並行・非同期

見るもの：競合状態、デッドロック、完了待ちの漏れ、順序の仮定、二重実行、キャンセルと中断、共有状態の保護。
見ないもの：単一スレッドでの論理の誤り（C-1）。
起動条件：並行処理、非同期、ロック、共有状態、キュー、タイマー、シグナル、複数プロセス・ワーカーに触れる。

並行の仕組みは言語で違う（スレッド、goroutine、async/await、イベントループ、アクター、プロセス）。どれでも「同時に動く経路が共有する物と、完了・失敗・中断の扱い」を見る。

## 確かめる手順

1. 共有される状態を列挙する：グローバル・モジュール・シングルトンの変数、オブジェクトのフィールド、ファイル、DB の行、キャッシュ、プロセス間の資源
2. それぞれに「同時に触る経路」があるかを見る：複数スレッド・goroutine、並列の await（`Promise.all`、`asyncio.gather`）、複数のリクエスト、複数ワーカー・プロセス、タイマーとメインの処理、イベントハンドラ、シグナルハンドラ
3. 「読んでから書く」の間に、他の経路が入れる隙があるか（check-then-act）。await・ロック解放・I/O の間
4. ロック・mutex・トランザクションがあれば、取得の順序（複数ロックの逆順でデッドロック）、解放の経路（失敗時も解放）、タイムアウト、再入
5. 非同期の呼び出しを全部追う：完了を待たない呼び出し（未 await、`go f()` の結果を見ない、スレッドの join 無し）、fire-and-forget の失敗、一部失敗の扱い
6. キャンセル・中断：処理中に止める経路（context・CancellationToken・AbortSignal・シグナル・タイムアウト）で、途中の状態と資源がどうなるか

## チェックポイント

- check-then-act：「無ければ作る」「残高を見てから引く」「ファイルが無ければ書く」を存在確認 + 操作で実装している（原子的な操作・一意制約・compare-and-swap が要る）
- 読み・変更・書きの非原子性：カウンタの `n = read(); write(n+1)`、`map[k]++`（Go は map への同時書き込みで panic）、Python の `+=` も GIL を超えて原子的ではない
- 共有コレクションの同時変更：反復中の変更（Java の ConcurrentModificationException、Python の RuntimeError、Go の map）、スレッド安全でないコレクションの共有
- 順序の仮定：並列処理の完了順、イベントの到着順、ファイルシステムの通知順、複数ワーカーの処理順、map の反復順に依存していないか
- 完了待ちの漏れ：戻り値を使わない非同期呼び出し。例外が未処理になる（Promise の reject、goroutine の panic でプロセス全体が落ちる、スレッドの例外が黙って消える）
- 二重実行：同じジョブが 2 つのワーカーで同時に走る。タイマーが重なる（前回が終わる前に次が始まる）。再起動後の再実行。cron の重複起動
- キャンセル：キャンセルの合図を下に渡しているか（context の伝播）、中断後に結果を書き込まないか（遅れて届いた応答が新しい状態を上書きする）、キャンセルされた側の後始末
- 終了処理：SIGTERM で処理中の作業を待つか・捨てるか、タイマーを止めるか、接続を閉じるか。待ちすぎて止まらないことはないか。デーモンスレッド
- デッドロック：ロック A → B と B → A の経路。ロックを持ったまま I/O・外部を待つ。同じロックの再取得（再入不可の mutex）。channel の送受信の片方だけ
- 共有状態の可視性：グローバル変数をリクエスト間で共有している（リクエストごとの状態が混ざる。Web フレームワークのモジュール変数、Java の static、Python のモジュール変数）
- メモリの可視性：ロック無しの読み書き（Java の volatile/happens-before、Go の data race、C/C++ のアトミック）
- 並列度の制御：無制限の並列（接続数・レート制限・メモリ・スレッド数）。本来は C-8 だが、順序と失敗の扱いはここ
- 部分失敗：`Promise.all`/`gather` で 1 つが失敗すると他の結果が捨てられ、進行中は続く。`allSettled`/`return_exceptions`/errgroup のキャンセル伝播
- 時間：タイマーの基準（単調時刻か壁時計か）、`setInterval`/固定レートの重なり、長い処理の中のタイムアウト判定
- プロセス間：ファイルロックの実装、PID ファイル、同じポートの衝突、子プロセスの終了待ち、共有メモリ
- スレッド安全でないライブラリの共有（DB 接続、HTTP クライアント、乱数生成器、日時フォーマッタ）

## NG 例

### 例1（SQL + 任意の言語）：同時に 2 回作る

```python
if not repo.find_by_key(key):
    repo.insert(key=key, ...)
```

2 つのリクエストが同時に来ると両方 insert する。一意制約が無ければ重複、あれば片方が例外。upsert（`INSERT ... ON CONFLICT`）か制約 + 例外の処理。`must`。

### 例2（Go）：map への同時書き込み

```go
var cache = map[string]Result{}
func handle(k string) { cache[k] = compute(k) } // 複数 goroutine から呼ばれる
```

`fatal error: concurrent map writes` でプロセス全体が落ちる。`sync.Map` か mutex。`must`。

### 例3（TypeScript）：forEach の中の await

```ts
items.forEach(async (i) => { await process(i); });
console.log("done"); // 何も終わっていない
```

完了を待たず、例外も捕まらない。`for...of` か `Promise.all`。`must`。

### 例4（Java）：ロックを持ったまま外部を待つ

```java
synchronized (this) { response = httpClient.send(request); update(response); }
```

外部が遅いと全スレッドが止まる。ロックの中は共有状態の更新だけにする。`should`、デッドロックの経路があれば `must`。

### 例5（Python）：遅れた応答が新しい状態を上書きする

```python
async def search(q):
    r = await api(q)
    state.results = r   # q1 の応答が q2 の後に届くと古い結果が残る
```

世代番号か、キャンセル。UI なら `should`、永続する状態なら `must`。

### 例6（任意）：タイマーの重なり

```
every 1 second: poll_and_process()   # 1 秒以上かかると重なる
```

前回の完了後に次をスケジュールするか、実行中フラグ・ロック。二重処理の副作用があれば `must`。

## 見落としやすい所

- 「シングルスレッドだから安全」という前提。await・yield・コールバックの間に別の処理が走る
- テストでは直列に走って再現しない競合。コードで経路を追う。race detector（`go test -race`、TSan）があるなら実行結果を根拠にできる（self-review のとき）
- 正常終了の経路だけでなく、中断・再起動の経路
- 複数プロセス（ワーカー、CLI の同時起動）を前提にしていない共有ファイル

## 指摘の書き方の例

- title：`同じキーの同時リクエストで重複して insert される`
- problem：`find_by_key → insert の間に他のリクエストが入れる。tasks.key に一意制約が無いため重複行ができる`
- evidence：`app/repo.py:40-44。schema.sql に key の一意制約が無いことを確かめた`
- suggestion：`key に一意制約を足し、INSERT ... ON CONFLICT DO NOTHING にする`
