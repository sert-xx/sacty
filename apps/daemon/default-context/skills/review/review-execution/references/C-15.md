# C-15 簡潔さ・範囲

見るもの：依頼・要件のどれのためにもない変更（機能・オプション・設定・拡張点・リファクタ）、起こりえない状態への防御（不要な null の確認・二重のエラー処理・型や呼び出し元が保証する値の再検査）、使われないコード（引数・export・関数・分岐・feature flag の片側・設定の項目）、今回の変更で使われなくなった既存のコードの消し忘れ、1 つしか実装の無い抽象化・要求に無い一般化、何をしているかを言い直すだけのコメント・説明、同じことを確かめる重複したテスト、残す理由の無い互換のための層。
見ないもの：責務の分け方・命名・既存の規約との整合（C-5）、テストの不足（C-4）、要求に対して足りない変更（C-1）。

「消せるもの」を探す観点。ほかの観点は欠陥や不足を探すので、それだけではレビューを回すほどコードが増える。
要らないコードは、読む量・テスト・依存・将来の変更の手間を増やし、どれが本当に要るのかを分からなくする。
1 つ 1 つは正しく動くので、正しさの観点（C-1）では指摘されない。「依頼のどれのためにあるか」「消すと何が困るか」で読む。

## 確かめる手順

1. 根拠（タスク・Issue・PR の本文・要求要件・設計）を読み、依頼が求めることを短く書き出す
2. 差分の変更を 1 つずつ（関数・分岐・引数・設定・テスト・コメント）、書き出した依頼のどれのためにあるかに結びつける。結びつかないものは、依頼に無い変更か、要らないコードの候補
3. 候補ごとに「消すと何が困るか」を問う。困る入力・呼び出し元・利用者をコードで探す。呼び出し元は検索（`grep`・`rg`・IDE の参照の検索）で確かめ、公開 I/F（外部に配る API・CLI・設定）か内部のものかを分ける
4. 防御のコード（null の確認・try/catch・値の検査・既定値）ごとに、その状態が起こりうる経路を探す。型・呼び出し元・枠組みが保証していて起こりえないなら候補
5. 今回の変更で呼ばれなくなった・意味が無くなった既存のコード（古い分岐・使われなくなった関数・設定・テスト・文書）を探す。置き換えた側の古い実装が残っていないか
6. 抽象化（インターフェース・基底クラス・汎用の関数・オプション）ごとに、今の実装と呼び出し元の数を数える。差し替える要求が無く、実装が 1 つなら候補
7. 候補ごとに、消した後の形を具体的に書けるかを確かめる。書けないものは出さない

## チェックポイント

- 依頼に無い変更：要求に無い機能・オプション・設定の項目・拡張点、「ついで」のリファクタや整形の混入
- 起こりえない状態への防御：型が null を許さないのに null を確かめる、呼び出し元が検証済みの値を再検査する、枠組みが処理する例外を個別に捕まえる、同じエラーを二重に処理する
- 握りつぶすだけの防御：失敗を捕まえて何もせず続ける、意味の無い既定値で隠す（堅牢さの欠陥なら C-2 に回し、ここでは「要らない」ことだけを見る）
- 使われないコード：引数・戻り値・export・関数・型・定数・import、到達しない分岐、常に同じ値の設定・フラグ、コメントアウトされたコード
- 消し忘れ：置き換えた古い実装、使われなくなった設定・環境変数・依存・テストの fixture・文書の記述
- 過剰な抽象化：1 つしか実装の無いインターフェース、1 か所からしか呼ばれない汎用の関数、要求に無い「将来のため」のオプション、不要なデザインパターン、1 行の処理を包むだけの関数の層
- 要らないコメント：コードを言い直すだけのコメント、変更の経緯（「〜に変更した」）をコードに書く、古い TODO
- 重複したテスト：同じ経路・同じ入力を確かめるテスト、実装をなぞるだけのテスト、すでに型や別のテストが保証することのテスト
- 互換のための層：呼び出し元がすべて追従済みなのに残る古い名前の別名・変換・非推奨の経路。公開 I/F で外部の利用者がいるなら残してよい
- 分量：変更の規模に比べてコードやテストが多すぎる（同じことを短く書ける）

## NG 例

### 例1（TypeScript）：起こりえない状態への防御

```ts
function label(task: Task): string {
  if (!task) return "";              // 型が Task（null を許さない）。呼び出し元もすべて Task を渡す
  return task.title ?? "（無題）";    // title は string で必須
}
```

どちらの分岐も到達しない。読む人は「null が来る経路があるのか」を探すことになる。2 行を消す。`should`。

### 例2（Python）：今回の変更で使われなくなった関数

```python
# 新しい parse_v2 に置き換え、呼び出し元をすべて直した
def parse_v1(raw): ...   # どこからも呼ばれない
```

残すと、どちらを使うべきかが分からなくなる。消す。`should`。

### 例3（Go）：1 つしか実装の無いインターフェース

```go
type Notifier interface { Notify(ctx context.Context, msg string) error }
type slackNotifier struct{} // 実装はこれだけ。差し替える要求も、テストでの差し替えも無い
```

要求に無い抽象化は読む量を増やす。具体の型を直接使う。`should`（テストでの差し替えに使っていれば出さない）。

### 例4（Java）：要求に無いオプション

一覧の並び順を作成日に変える依頼で、`sortKey`・`sortOrder` の設定の項目を足し、既定値を作成日の降順にしている。誰も変えない設定が増え、組み合わせのテストも要る。設定を消して固定にする。`should`。

### 例5（Kotlin）：コードを言い直すコメント

```kotlin
// ユーザーの ID でユーザーを取得する
val user = repository.findById(userId)
```

コメントを消す。`nit`。

### 例6（Ruby）：同じことを確かめるテスト

`spec/models/order_spec.rb` に、合計金額の計算を同じ入力で確かめるテストが 3 つある（名前と書き方が違うだけ）。1 つにまとめる。`nit`〜`should`。

## 見落としやすい所

- 消す指摘も、要るコードを消させないこと。消してよいと言うには、使われていない・起こりえないことをコードで確かめる（呼び出し元の検索、型、枠組みの保証）。確かめられなければ `confidence: low` にするか出さない
- 公開 I/F（外部に配るライブラリの API・CLI・設定・データ形式）は、リポジトリの中に呼び出し元が無くても外部の利用者がいる。消す指摘にしない（互換は C-6）
- 防御のコードのうち、外部からの入力（利用者の入力・ネットワーク・ファイル・環境変数）の検証は要る。型が信頼境界を越えて保証するとは限らない
- 既存の要らないコードは範囲の外。今回の変更で要らなくなったもの、今回の変更が足したものだけを見る
- 作者が依頼で求められた変更は、要らないと思っても出さない（依頼そのものへの疑問は X-1）

## 指摘の書き方の例

- title：`置き換えた parse_v1 がどこからも呼ばれずに残っている`
- problem：`今回 parse_v2 に置き換え、呼び出し元 3 か所をすべて直したが、parse_v1 と、そのためだけのテスト（tests/test_parse.py:10-40）が残っている。どちらを使うべきかが分からなくなる`
- evidence：`rg "parse_v1" で、定義（app/parse.py:12）とテストのほかに参照が無いことを確かめた。公開 API の一覧（app/__init__.py の __all__）にも無い`
- suggestion：`parse_v1 とそのテストを消す`
