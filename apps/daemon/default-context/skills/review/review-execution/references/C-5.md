# C-5 保守性・設計

見るもの：読みやすさ、責務の分け方、重複、命名、リポジトリの既存の規約・構成との整合、過剰な抽象化や未使用のコード、コメントと実装のずれ、変更が追いやすいか。
見ないもの：表記の好み（nit に留める）、性能（C-8）。

基準は「そのリポジトリの規約と、その言語の一般的な慣習」。自分の好む言語の慣習を他の言語に持ち込まない。

## 確かめる手順

1. リポジトリの規約を先に知る：CONTRIBUTING・コーディング規約・lint 設定・既存の似た機能の書き方（ディレクトリ、命名、エラーの返し方、ログの書き方、テストの置き方）
2. 変更を「初めて読む人」として読む。どこで何をしているかが、名前・構造から追えるか。追えない所にコメントがあるか
3. 同じことをしているコードが既存に無いかを探す（ユーティリティ、似た関数）。差分の中の重複も見る
4. 関数・モジュール・クラスの責務を 1 文で言えるか。言えないなら分けすぎか、まとめすぎ
5. 変更が将来どう変わりそうかを想像し、その変更が 1 箇所で済むかを見る。ただし「将来のため」の抽象化を要求しない

## チェックポイント

- 既存の規約との不一致：命名の規則（言語の慣習とリポジトリの慣習）、エラーの表し方、ログの仕組み、i18n の仕組み、DI の仕組みを独自に再発明していないか
- 重複：既存のユーティリティがあるのに書き直している。差分の中で同じ 10 行が 2 回出る（違いが 1 箇所なら引数にする）
- 責務：1 つの関数が I/O・変換・判定・出力を全部やる。逆に、1 行の関数を何層も重ねる。神クラス
- 名前：中身と違う名前（`getUser` が作成もする）、否定の否定、略語、`data`/`info`/`tmp`/`result2`、言語の慣習に反する（Go の `GetX` ゲッター、Python の camelCase）
- マジックナンバー・文字列：意味の分からない定数、同じ文字列を複数箇所で比較
- 引数：真偽値のフラグで振る舞いを分ける、引数が多い、順序を間違えやすい同型の引数
- 深いネスト：早期 return で浅くできる所。コールバックの入れ子
- 未使用：使われない引数・import・関数・feature flag の片側、コメントアウトされたコード
- 過剰設計：1 つしか実装の無いインターフェース、使われない拡張点、設定にする必要の無い値、要求に無い一般化、不要なデザインパターン
- コメント：何をしているかの繰り返し（なぜ、を書くべき）、実装と食い違うコメント、古い TODO、消し忘れたデバッグ出力
- 型：`any`・`Object`・`interface{}`・`dynamic` の濫用、不要なキャスト、型で表せる制約を実行時チェックだけにしている、Optional の濫用
- 変更の局所性：ある概念を変えるのに何箇所も直す必要がある構造（列挙の追加で switch を 5 箇所直す）
- 依存の方向：下の層が上の層を import している、循環依存、パッケージの境界の破り（内部実装への直接参照）
- ファイルの置き場所：規約と違うディレクトリ、巨大なファイルへの追加（分けるべき兆候）
- 公開範囲：public/export する必要の無いもの、テストのためだけの公開（規約を見る）
- 一貫性：差分の中で同じことを 2 つの書き方でしている
- 言語固有の慣習：Go の error ラップ・context の第一引数、Python の例外クラス・`__all__`、Java の不変オブジェクト・equals/hashCode、Rust の所有権の無理な clone、JS の `var`

## NG 例

### 例1（Python）：既存のユーティリティの再発明

```python
def to_slug(s): return s.lower().replace(" ", "-")
# utils/text.py に slugify がある（Unicode の正規化も行う）
```

2 つの実装が食い違う。既存を使うか、既存を直す。`should`。

### 例2（Java）：真偽値のフラグで振る舞いを分ける

```java
notify(task, true, false); // 何が true で何が false か読めない
```

enum かビルダーか、別のメソッド名。`should`（規約が無ければ）。

### 例3（Go）：コメントと実装のずれ

```go
// retries up to 3 times
for i := 0; i < 5; i++ { ... }
```

どちらが正しいか分からない。`should`。

### 例4（TypeScript）：使われないインターフェース

```ts
interface Storage { get(k: string): Promise<string>; set(k: string, v: string): Promise<void>; }
class FileStorage implements Storage { ... } // 実装はこれだけ。差し替える要求は無い
```

要求に無い抽象化は読む量を増やす。`nit`〜`should`（規模とリポジトリの方針による）。

### 例5（Ruby）：巨大なメソッドへの追加

既存の 300 行のメソッドに 60 行の分岐を足している。分けるべき兆候だが、この変更で全体の分割を要求すると範囲が広がる。`should` で「新しい分岐をメソッドに出す」程度の、この変更の中でできる提案にする。

### 例6（Rust）：所有権を避けるための clone の連発

```rust
let name = user.name.clone(); let email = user.email.clone(); // 参照で足りる
```

慣習に反し、意図が読めない。`nit`〜`should`。

## 見落としやすい所

- 好みと規約の区別。規約（リポジトリに書かれている・既存コードが一貫している）に反する所は `should`、好みだけなら `nit` か出さない
- 「読みにくい」で止めず、どこを読んで何が分からなかったかを書く
- 大きな構造の問題を、この変更のせいにしない（既存の問題は範囲の外。変更が悪化させている部分だけ）

## 指摘の書き方の例

- title：`slugify の再実装で、既存と Unicode の扱いが食い違う`
- problem：`新しい to_slug は空白だけを置き換え、既存の utils/text.py の slugify は NFKD 正規化もする。同じ入力で別の slug になり、URL の衝突や不一致が起きる`
- evidence：`app/post.py:14 と utils/text.py:3 を比べた`
- suggestion：`slugify を使う。要件が違うなら slugify にオプションを足す`
