# X-1 横断（欠陥探索）

見るもの：観点に縛られず、対象の全体を「作者が知れば直すであろう具体的な問題」の視点で読む。他の観点のどれにも入らない問題、複数の観点にまたがる問題、変更の意図と実際のずれ、変更が触れていないが壊れる周辺、要求に対して足りない・余計な変更。
見ないもの：他の観点の担当が見るはずのもの（気づいたら `out_of_scope_notes` に 1 行で残し、指摘にはしない）。検証コマンドの結果の分析（X-2）。

依頼文には、起動している他の観点の一覧が渡される。それらが見るものは重複して出さない。カタログの観点の「隙間」と「またがる所」を見る担当。

## 確かめる手順

1. 変更の意図を自分の言葉で 1〜2 文にまとめる（説明・Issue・差分から）。まとめられないなら、意図が不明確なことがまず指摘
2. 差分を上から下まで、観点を決めずに読む。「おかしい」「意図と違う」「なぜここを変えた」と感じた所を全部メモする（この段階では分類しない）
3. 差分の外を見る：変更した物の呼び出し元・呼び出し先・同じパターンの他の箇所・関連する設定と文書。変更が触れていないが前提が変わる所
4. メモを分類する：他の観点に入るもの → `out_of_scope_notes`。どの観点にも入らない・複数にまたがる・意図とのずれ → 指摘の候補
5. 候補ごとに根拠を確かめる（他の観点と同じ基準）。「作者が知れば直すか」を問い、そうでないものは出さない
6. 最後に「この変更で一番壊れそうな所はどこか」を 1 つ挙げ、それが他の観点か自分で見られているかを確かめる

## チェックポイント

- 意図とのずれ：説明に書かれた変更と差分が一致しない（説明にあるが差分に無い、差分にあるが説明に無い）
- 要求との差：足りない（受け入れ条件の一部が無い）、余計（要求に無い機能・リファクタ・フォーマット変更の混入）
- 変更の一貫性：同じパターンの箇所が複数あるのに一部だけ直している（検索で見つかる）
- 周辺の破壊：変更した物に依存している、差分に出ない箇所（設定・文書・スクリプト・他のモジュール・テストの fixture）
- 複数の観点にまたがる問題：例「エラー処理の変更（C-2）が互換性（C-6）を壊し、文書（U-1）も古くなる」を 1 つの問題として
- カタログの隙間：どの観点の「見るもの」にも入らない問題（例：ライセンスヘッダーの欠落、生成コードの手編集、コミットに混ざった無関係なファイル、大きすぎる変更の分割の提案、デバッグ用の残骸）
- 「なぜここを変えたか」が分からない変更：説明が無く、周辺のコードと関係が見えない差分
- 消し忘れ：デバッグ出力、TODO、コメントアウト、一時的なフラグ、テスト用の値、`skip`
- 偶然の変更：フォーマッターの一括適用、改行コードの変更、無関係なファイルの変更が差分を膨らませ、本質の変更を隠す
- 変更の大きさ：1 つの変更で複数の関心事を扱い、レビュー・ロールバックが難しい
- 作者の説明の正しさ：「〜は影響しない」「〜はテスト済み」の主張をコードで確かめる
- 直感：「何かおかしい」と感じたが分類できない所。感じた理由を言葉にして、根拠を探す。根拠が無ければ `confidence: low` で出すか出さない

## NG 例

### 例1：説明と差分のずれ

説明「ログのレベルを調整」だが、差分には設定ファイルの既定値の変更とリトライ回数の変更も含まれる。意図しない変更か、説明の不足。`should`、既定値の変更が利用者に影響するなら `must`。

### 例2：一部だけ直している

タイムアウトの単位を秒からミリ秒に変えたが、同じ関数を呼ぶ 5 箇所のうち 3 箇所だけ 1000 倍している。残り 2 箇所は 1000 分の 1 のタイムアウトになる。C-1（正しさ）と C-6（影響範囲）にまたがるが、「変更の一貫性」として 1 つの問題。`must`。

### 例3：消し忘れ

```python
print("DEBUG", payload)   # 本文に秘密情報が含まれうる
SKIP_AUTH = True
```

デバッグの残骸。認証のスキップは C-3 の範囲でもあるが、「消し忘れ」として横断で拾い、C-3 に知らせる。`must`。

### 例4：無関係な変更の混入

機能の変更 50 行と、フォーマッターによる 2,000 行の変更が同じ差分にある。本質の変更がレビューできない。分割の提案。`should`。

### 例5：周辺の破壊

関数の戻り値の型を変えたが、それを読む別リポジトリ向けのエクスポートスクリプト（`scripts/export.py`）が差分に無い。C-6 の担当が「リポジトリ内の呼び出し元」を見ていても、スクリプトを見落とす可能性。検索して見つけたら指摘。`must`。

### 例6：作者の主張の検証

説明「既存の挙動は変えていない」だが、差分で条件の `>=` が `>` に変わっている。境界の挙動が変わる。C-1 が見るはずだが、「主張とコードの不一致」として横断でも拾う（重複は親が統合する）。`must`。

## 見落としやすい所

- 他の観点が見ているはずのものを「誰かが見る」と流す。見ているはずでも、またがる問題や主張との不一致は横断の役目
- 観点を決めずに読むと、流し読みになる。差分の全行を読み、周辺も開く
- 「作者が知れば直すか」の基準。好みや一般論は出さない。具体的な箇所と理由

## 指摘の書き方の例

- title：`タイムアウトの単位の変更が、5 箇所の呼び出しのうち 2 箇所に反映されていない`
- problem：`wait_for の引数を秒からミリ秒に変えたが、呼び出し元 5 箇所のうち services/sync.py:40 と jobs/cleanup.py:18 は値がそのまま（30）で、30 ミリ秒のタイムアウトになる。説明には「全呼び出し元を更新」とある`
- evidence：`grep "wait_for(" で 5 箇所を確かめ、各箇所の値を読んだ`
- suggestion：`2 箇所を 30_000 に直す。単位を型か引数名（timeout_ms）で表して再発を防ぐ`
