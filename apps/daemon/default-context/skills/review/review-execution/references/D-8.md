# D-8 運用・移行

見るもの：移行の手順と順序、切り戻し、新旧の共存、利用者への影響と周知、運用の変化。
見ないもの：設計の内部構造（D-2）。
起動条件：既存のデータ・利用者・稼働中のシステムがある、段階的な切り替えが要る。

## 確かめる手順

1. 「いま動いているもの」を列挙する：データ、利用者の操作、稼働中のプロセス、他システムとの連携、スケジュール
2. それぞれについて「変更を適用する瞬間」と「適用の途中」に何が起きるかを追う。止まるか、二重になるか、失うか
3. 移行の手順が、順序・所要時間・実行者・確認方法・失敗時の対応を含むか
4. 切り戻し：どの時点まで戻せるか、戻すと何が失われるか、戻す判断の基準と手順
5. 利用者・運用者への影響：見た目・操作の変化、停止時間、周知の方法と時期、問い合わせへの備え
6. 運用の変化：新しい監視・アラート・手順・権限・コスト。既存の運用手順書の更新

## チェックポイント

- 移行の手順が無い、または「移行する」の 1 文だけ
- 順序：データの変換・コードのデプロイ・設定の変更・DNS・証明書などの依存関係と順序
- 新旧の共存：切り替えの途中で古い版と新しい版が同時に動く時間があるか、その間の整合（C-9 の内容を設計で扱っているか）
- 停止時間：必要か、どれだけか、いつ（利用者の少ない時間）、周知
- 大量データの移行：所要時間の見積もり、途中で止めたときの再開、本番への影響（負荷・ロック）
- 検証：移行後に正しく移ったことをどう確かめるか（件数・サンプル・チェックサム）
- 切り戻し：手順、戻せる期限（新しい形式で書かれたデータが増える前）、戻した後のデータの扱い
- 段階的な展開：一部の利用者・一部のデータから始める手段（feature flag・カナリア）、進める・戻す判断の基準
- 利用者への影響：操作の変化、URL・ID の変更、通知の変化、必要な利用者側の作業（再ログイン・設定）
- 周知：誰に・いつ・何を・どの経路で。問い合わせ先
- 運用の変化：新しい監視項目、アラートの閾値、定期作業、障害対応の手順、必要な権限、費用
- 既存の文書・手順書の更新（U-1・U-2 が文書を見る。設計に「更新が要る」と書かれているかはここ）
- 他システム・他チームへの連絡と、相手側の作業の時期
- 古いものの撤去：古いコード・テーブル・設定・権限をいつ消すか

## NG 例

### 例1：移行が 1 文

```
既存データは新形式に移行する。
```

何件を・誰が・いつ・どの手順で・どう確認し・失敗したらどうするか。`must`。

### 例2：共存の未検討

API の応答の形を変える設計で、デプロイの途中に古いクライアントが新しい応答を受ける時間の扱いが無い。`must`。

### 例3：切り戻しが無い

列の削除を含む移行で、切り戻しの手順が無い。削除後は戻せない。削除を後の段階に分けるか、バックアップと復元の手順。`must`。

### 例4：検証が無い

300 万行を変換する移行で、変換後の確認（件数の一致・サンプルの比較）が無い。`should`。

### 例5：運用の変化の未記載

常駐ワーカーを足すが、監視・再起動・ログの場所・担当が無い。運用者が知らないまま本番に入る。`should`、停止が業務に影響するなら `must`。

### 例6：周知の未検討

URL の体系が変わり、利用者のブックマーク・外部からのリンクが切れるが、リダイレクトも周知も無い。`should`。

## 見落としやすい所

- 「新規導入」でも、既存の利用者・運用・他システムは存在する。影響ゼロと決めつけない
- 開発者の視点では「デプロイしたら終わり」。運用者・利用者の時間軸で考える
- 切り戻しは「できる」と書かれていても、手順と期限が無ければできない

## 指摘の書き方の例

- title：`応答形式の変更で、デプロイ中に古いクライアントが新形式を受ける時間の扱いが無い`
- problem：`4.1 でエラー応答を {error} から {errors: []} に変えるが、クライアント（モバイルアプリ）の更新は利用者次第で、数週間は古いクライアントが残る。共存期間の方針（両方返す・版で分ける）が無い`
- evidence：`docs/design/api-v2.md 4.1 と、クライアントのリリース方式（docs/release.md）を読んだ`
- suggestion：`移行期間は両方の形を返すか、Accept ヘッダー・パスの版で分け、古い形を消す時期を決める`
