# C-1 正しさ・仕様適合

見るもの：要求要件・設計・Issue・テスト観点との対応。分岐の漏れ、境界値、null 相当の値、型の取り違え、計算・比較・状態遷移の誤り、戻り値の扱い。
見ないもの：異常入力や失敗時の振る舞い（C-2）、テストの良し悪し（C-4）。

言語は問わない。以下の「配列」はリスト・スライス・ベクタを、「null」は nil・None・Optional の空・ゼロ値を含めて読む。

## 確かめる手順

1. 根拠（要求要件・設計・Issue）から「この変更が満たすべきこと」を箇条書きにし、差分のどこが各項目に対応するかを対応表にする。対応の無い項目は「未実装」、対応の無い差分は「要求に無い変更」として候補にする
2. 変更した関数ごとに入力の空間を分ける（空・1 件・複数・上限・負数・0・重複・順序違い・最大長・非 ASCII）。区画ごとにコードを頭の中で実行し、期待と違う区画を探す
3. 分岐ごとに else・default・早期 return が意図どおりか見る。否定が重なる条件、`&&`/`||`（and/or）の優先順位、`<` と `<=` の境界を 1 つずつ確かめる
4. 戻り値を呼び出し元がどう使うかを追う。無視された戻り値（Go の `_`、Java の捨てられた戻り値、未 await の Promise）、エラーを表す値（`-1`・null・空）の取り違え
5. 状態を持つもの（フラグ、キャッシュ、enum の遷移）は遷移表を書き、行き止まりや戻れない遷移を探す

## チェックポイント

- 受け入れ条件・テスト観点に 1 つずつ対応する実装があるか。「ほぼ満たす」は満たしていない
- 設計と違う構造・名前・振る舞いは、意図した逸脱か（説明に書かれているか）
- off-by-one：ループの範囲、部分列の終端（Python の `[a:b]`、Go の `s[a:b]`、Java の `subList`）、ページングの offset、「以上・以下・未満・超」
- 空の入力：空配列の集約（初期値のない reduce、`max()` の空）、空文字列の分割、先頭要素への直接参照
- null 相当：Optional/Maybe の空、Go のゼロ値と「未設定」の区別、Python の `None` と `""` と `0`、JS の `||` が `0`・`""`・`false` を落とす、JSON に無いキー
- 型：数値と文字列の比較、日時の文字列比較、ID の数値化、浮動小数の等価比較、整数のオーバーフロー（Go/Java/Rust の固定幅整数）、符号付きと符号なし
- 計算：単位（秒とミリ秒、バイトと KB）、丸めの方向、整数除算、0 除算、パーセントと比率
- 比較と並べ替え：比較関数の一貫性、安定ソートへの依存、ロケール依存の文字列比較
- 状態遷移：同じイベントが 2 回来たとき、途中の状態で別のイベントが来たとき、初期状態への戻し
- 非同期の戻り値：未 await の Promise/Future を真偽値として判定、Go で channel の結果を待たない
- 重複排除・集合演算：キーの選び方（参照の比較、大文字小文字、前後の空白、構造体の等価性）
- 時刻：タイムゾーン、月末・年末、うるう年、DST、月が 0 始まりの API
- 既存の挙動の変更：変更前に動いていた入力が、変更後も同じ結果になるか

## NG 例

### 例1（Python）：`or` で 0 を既定値に置き換える

```python
limit = options.get("limit") or 20   # limit=0 を指定しても 20 になる
```

`0` が正当な値なら `if limit is None` で判定する。仕様で 0 を許すなら `must`。指摘には「`limit=0` を渡すと 20 件返る」と入力を明示する。

### 例2（Go）：スライスの終端で最後の 1 件が落ちる

```go
page := items[offset : offset+size-1]
```

スライスの終端は含まないので `size-1` では 1 件足りない。`size` 件ずつ返す仕様なら `must`。

### 例3（TypeScript）：Promise を真偽値として判定する

```ts
if (isAllowed(user)) { ... } // isAllowed は async
```

Promise は常に truthy で、常に許可になる。「論理が常に真になる」ことを C-1 で指摘し、認可に関わることは `out_of_scope_notes` で C-3 に知らせる。

### 例4（Java）：状態遷移の行き止まり

```java
if (status == RUNNING && event == PAUSE) status = PAUSED;
if (status == PAUSED && event == RESUME) status = RUNNING;
// PAUSED で CANCEL が来たときの遷移が無い
```

遷移表に無い組み合わせは「何も起きない」のか「エラー」なのか。設計に書かれていれば `must`、無ければ欠落として `should`。

### 例5（Rust）：整数の型の取り違え

```rust
let remaining: u32 = total - used; // used > total のときパニック（debug）か wrap（release）
```

負になりうる計算を符号なしで行っている。`checked_sub` か符号付き。入力次第で起きるなら `must`。

### 例6：要求に無い変更

差分に、Issue で触れていない既定値の変更（タイムアウト 30 秒 → 10 秒）が混ざっている。意図が説明に無ければ `should` で「意図を書くか、別の変更に分ける」。

## 見落としやすい所

- 差分に出ない呼び出し元。関数の意味が変わったのに呼び出し元が古い前提のまま（C-6 と接する。こちらは「結果が間違う」ことを見る）
- テストが通っていることを根拠にしない。テストが間違った期待を固定していることがある
- 「正常系は動く」で止めない。区画ごとに最後まで見る

## 指摘の書き方の例

- title：`limit=0 を渡すと既定の 20 件が返る`
- problem：`options.get("limit") or 20 は 0 を偽として捨てる。受け入れ条件 3「0 件を指定できる」に反する`
- evidence：`app/listing.py:42 を読み、呼び出し元 app/api.py:88 がクエリの limit をそのまま渡すことを確かめた`
- suggestion：`None のときだけ 20 にし、limit=0 のテストを足す`
