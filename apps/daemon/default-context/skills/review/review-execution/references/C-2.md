# C-2 堅牢性・エラー処理

見るもの：異常な入力・想定外の状態、失敗したときの振る舞い（握りつぶし、部分的な失敗、途中で止まったときの状態）、リソースの解放、リトライと冪等性、タイムアウト、エラーメッセージが原因を示すか。
見ないもの：正常な入力での論理の誤り（C-1）、悪意のある入力（C-3）。

エラーの表し方は言語で違う（例外、error の戻り値、Result 型、エラーコード）。どの方式でも「失敗が呼び出し元に正しく伝わり、適切に扱われるか」を見る。

## 確かめる手順

1. 変更した処理ごとに「失敗しうる箇所」を列挙する：I/O（ファイル・ネットワーク・DB・子プロセス）、パース（JSON・YAML・数値・日時）、外部の戻り値、環境変数、権限、メモリ・ディスクの枯渇
2. 失敗箇所ごとに「失敗したら何が起きるか」を追う：例外・error の伝わる先、catch/recover の中身、戻り値の扱い、ログ、利用者に見える結果
3. 複数の段階がある処理は、段階の間で止まったときの状態を書き出す（半分だけ書かれたファイル、DB の片方だけ更新、送信済みだが記録なし）
4. リソース（ファイル、接続、一時ファイル、ロック、タイマー、子プロセス、goroutine/スレッド）を確保している所で、失敗経路でも解放されるかを見る
5. リトライがあれば、何を・何回・どの間隔で・どの失敗だけ再試行するか、再試行で二重に起きて困る副作用がないかを見る

## チェックポイント

- 失敗の無視：空の catch、Go の `_ = f()` や `err` の未確認、Python の `except: pass`、Rust の `unwrap()`/`let _ =`、Java の捕捉して何もしない catch
- catch が広すぎる：想定の失敗（ファイルが無い）と想定外（権限、バグ）を同じに扱う。`except Exception`、`catch (Throwable)`、`recover()` の濫用
- 原因の喪失：文字列に変えて投げ直し、元の原因（cause・スタック・errno）が消える。Go の `%w` を使わない、Python の `raise ... from` の欠落、Java の原因の未連結
- 失敗の戻り値の規約：null を返す関数の呼び出し元が null を見ているか、Go の `(value, err)` の value を err 確認前に使う、`-1`/空の取り違え
- 部分的な失敗：10 件のうち 3 件目で失敗したら、残りは処理するのか、全部やめるのか、済んだ分を戻すのか。仕様とログがそれに合うか
- 途中で止まったときの状態：一時ファイルに書いて rename、トランザクション、順序（記録してから送る、送ってから記録する）
- 二重実行：同じ入力が 2 回来ても結果が同じか（冪等）。「作成」が 2 回で 2 件、Webhook の再送
- タイムアウト：無限に待つ I/O が無いか。タイムアウト後の後始末（接続の破棄、子プロセスの kill、context のキャンセル）
- リソースの解放：`finally`、`defer`、`with`、`try-with-resources`、RAII。確保の失敗と使用の失敗で経路が違わないか
- 入力の検証：外から来る値（API・ファイル・環境変数）を型・範囲・必須で検証しているか（悪意の観点は C-3）
- エラーメッセージ：何が・どこで・どうすればよいかが分かるか。利用者向けと開発者向けの区別。秘密情報を含まないか（含むなら C-3 に知らせる）
- 既定値への黙った置き換え：設定が読めないときに既定で動き続け、利用者が気づけない
- 非同期の失敗：未処理の Promise の reject、goroutine 内の panic、スレッドの未捕捉例外、イベントハンドラ内の例外、タイマー内の例外
- 子プロセス・外部コマンド：終了コードを見ているか、stderr を捨てていないか、見つからないときの扱い
- 終了処理：シグナルでの後始末、処理中の作業の扱い
- パニック・クラッシュ：配列の範囲外、nil 参照、型のキャスト失敗、再帰の深さ。入力次第で起きるか

## NG 例

### 例1（Go）：エラーを確認せずに値を使う

```go
data, _ := os.ReadFile(path)
cfg := parse(data) // 読めなかったとき空のデータを設定として使う
```

ファイルが無い・権限が無い場合に空の設定で動き続ける。`err` を確かめて止めるか既定を明示する。設定次第で振る舞いが変わる処理なら `must`。

### 例2（Python）：失敗を飲み込んで成功を返す

```python
try:
    save(record)
except Exception:
    logger.info("save failed")
return {"ok": True}
```

保存に失敗しても呼び出し元には成功が返り、原因も残らない。利用者が「保存できた」と信じる経路なら `must`。

### 例3（Java）：途中で止まると壊れたファイルが残る

```java
Files.writeString(path, json); // 書き込みの途中で落ちると壊れた JSON が残る
```

一時ファイルに書いて `Files.move(..., ATOMIC_MOVE)`。読み手が壊れたファイルを想定していなければ `must`。

### 例4（Ruby）：リトライが副作用を重ねる

```ruby
3.times do
  begin
    client.post_comment(body); break
  rescue Net::ReadTimeout
  end
end
```

投稿は成功したが応答が届かなかったとき、2 回目で同じコメントが二重に付く。冪等キーか投稿前の存在確認。`must`。

### 例5（Rust）：unwrap で入力次第のパニック

```rust
let n: u32 = args[1].parse().unwrap();
```

数値でない引数でパニックし、エラーメッセージも原因を示さない。`?` や `match` で扱う。CLI の利用者が与える値なら `must`。

### 例6（TypeScript）：原因を捨てる投げ直し

```ts
catch (e) { throw new Error("failed to load config"); }
```

どのファイル・どの行・権限か、が消える。`{ cause: e }` を付けるか原因を文に入れる。`should`。

## 見落としやすい所

- 正常経路の横にある、失敗経路だけが通らないテスト。失敗経路は頭の中で通す
- 成功時だけ return し、失敗時に null/undefined/ゼロ値が落ちてくる関数
- 複数の I/O を並べた処理の、2 つ目が失敗したときの 1 つ目の副作用
- Go の `defer` の中のエラー（Close の失敗）の無視

## 指摘の書き方の例

- title：`保存の失敗が呼び出し元に成功として返る`
- problem：`save の例外を捕まえて info ログを出すだけで、戻り値は ok=True。呼び出し元の API は 200 を返し、利用者は保存できたと誤解する`
- evidence：`app/store.py:30-36、呼び出し元 app/api/records.py:52 が戻り値の ok だけを見ることを確かめた`
- suggestion：`例外を伝えるか ok=False とエラーを返し、API で 5xx にする。失敗のテストを足す`
