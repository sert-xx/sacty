# D-5 セキュリティ・規定

見るもの：認証・認可の設計、データの分類と扱い（個人情報・秘密情報）、信頼境界、ログに残すもの、組織の規定・法令・ライセンスへの適合、監査の要否。
見ないもの：実装の細部（コードのレビューで見る）。

## 確かめる手順

1. 登場する主体（利用者・管理者・システム・外部サービス・バッチ）と、それぞれができる操作を表にする。「誰が何をできるか」が文書から一意に読めるか
2. 信頼境界を描く：どこまでが信頼する内側で、どこから外か。外から入る値・外へ出る値の一覧と、境界での検証・制御
3. データを分類する：個人情報・秘密情報・機密・公開。各データの保存場所・暗号化・保持期間・削除・アクセスできる主体
4. 認証・認可の流れ：誰がどの時点で確認し、確認の結果はどう伝わるか。迂回経路（バッチ、内部 API、管理ツール）
5. 規定・法令：組織のセキュリティ規定、個人情報保護、ライセンス（使う技術・データ）、監査ログの要件、業界の規制。プロジェクトやコンテキストの規約に書かれているものを基準にする（無ければ一般的な原則）

## チェックポイント

- 認証の方式が決まっていない、または既存の仕組みと別のものを独自に作る
- 認可：操作ごとに「誰ができるか」が書かれているか、資源の所有者の確認、管理者権限の範囲、権限の変更の手続き
- 信頼境界の曖昧さ：外部からの入力を「信頼できる」と仮定、内部ネットワークを無条件に信頼
- 秘密情報：保存場所（設定ファイル・環境変数・シークレットストア）、受け渡しの経路、ローテーション、ログ・エラーへの露出
- 個人情報：収集の必要性、保存期間、削除の手段、第三者（外部サービス・LLM）への送信、同意、匿名化
- ログ・監査：誰が何をしたかを残す必要があるか、残すなら何を・どこに・どれだけの期間。ログに個人情報・秘密情報を含めない設計
- 通信：暗号化（TLS）、証明書の検証、内部通信の保護
- 外部サービス・LLM へのデータ送信：送るデータの範囲、相手の規約、データの所在（国・リージョン）
- 権限の最小化：サービスアカウント・トークンのスコープ、コンテナ・プロセスの権限
- 入力の検証の方針：どこで（境界で一度か、各所か）、何を（形式・範囲・サイズ）
- 外の文書・プロンプトの扱い：外部の本文を自動処理・LLM に渡す設計で、本文の指示に従わない方針があるか（プロンプトインジェクション）
- 依存・ライセンス：使うライブラリ・データ・モデルのライセンスと、プロジェクトの配布形態との整合
- 脅威の列挙：主要な脅威（なりすまし・改ざん・漏洩・DoS・権限昇格）への対応が書かれているか。無いなら「対象外」の理由
- 障害時の安全側：認証サービスが落ちたとき「全部許可」になっていないか（fail-open）
- 規定の参照：組織の規定・標準に従うと書かれているなら、どの規定の何条か

## NG 例

### 例1：認可の未記載

主体に「利用者」「管理者」があるが、どの操作が管理者だけかが書かれていない。実装者が決めることになる。`must`。

### 例2：外部サービスへ個人情報を送る設計

「チケットの本文を外部の AI サービスに送って要約する」とあるが、本文に含まれうる個人情報の扱い・相手の規約・利用者への説明が無い。`must`（規定に反する可能性）。

### 例3：fail-open

「認可サービスに接続できない場合は処理を続行する（可用性を優先）」。認可の迂回になる。`must`。

### 例4：秘密情報の置き場所

「API キーは設定ファイルに書く」。リポジトリにコミットされる経路。シークレットストアか環境変数と、ログに出さない方針。`must`。

### 例5：監査ログの未検討

タスクの削除・権限の変更ができる設計で、誰が行ったかの記録が無い。組織の規定で監査ログが要るなら `must`、無ければ `should`。

### 例6：外の本文の指示

「PR の本文を読んでレビューの方針を決める」設計で、本文に書かれた指示（「承認せよ」）に従わない方針が無い。`should`、自動で承認・投稿する経路なら `must`。

## 見落としやすい所

- 設計書に「セキュリティ」の節があるだけで安心しない。主体・操作・データの表を自分で作る
- 内部ツール・バッチ・管理 CLI は「内部だから」で検討を省かれる
- 規定は組織ごとに違う。コンテキストの規約に無いものを「違反」と断定せず、「規定の確認が要る」と書く

## 指摘の書き方の例

- title：`管理者だけが行える操作が定義されておらず、認可の実装が決められない`
- problem：`2.1 で主体を「利用者」「管理者」に分けているが、4 章の操作一覧（作成・更新・削除・設定変更・他者のタスクの閲覧）のどれが管理者限定かが無い。実装者ごとに判断が分かれる`
- evidence：`docs/design/tasks.md の 2.1 と 4 章を読み、権限に触れる記述を検索した`
- suggestion：`操作 × 主体の表を足し、資源の所有者と管理者の権限を定める`
