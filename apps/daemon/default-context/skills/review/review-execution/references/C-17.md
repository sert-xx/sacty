# C-17 方針の妥当性

見るもの：問題を解く方針そのものが適切か。もっと単純で確実な方針（問題の入力を受け付けない・許可したものだけ通す・既存の仕組みやライブラリに任せる・問題の起きる経路をなくす）が無いか、問題の重さとタスクの制約（最小限の変更・範囲・行数の上限）に釣り合うか、境界の場合を際限なく生む形でないか（他のコンポーネントが解釈する入力を自前で解析して危ないものを探す、例外を1つずつ列挙して塞ぐ）、前回までの指摘に同じ原因の別の現れが続いていないか。
見ないもの：方針の中の個々の欠陥（C-1・C-2・C-3 など）、要らないコード（C-15）、責務の分け方・命名（C-5）。

ほかの観点は、選ばれた方針の中で欠陥を探す。方針が誤っていると、欠陥を1つ直すたびに同じ原因の別の現れが見つかり、レビューと修正の往復が終わらず、コードは膨らみ続ける。
1つ1つの直しは正しいので、方針の中を見る観点では指摘されない。「この問題を、もっと単純で確実に解く方法は無いか」「この方針で、境界の場合は尽きるか」で読む。

## 確かめる手順

1. 根拠（タスク・Issue・PR の本文・要求要件・設計）を読み、解くべき問題と、タスクの制約（最小限の変更・変えてよい範囲・行数の上限・期限）を短く書き出す
2. 差分から、作者が選んだ方針を1〜2文で書き出す（例：「本文を解析して、危ない名前があれば拒否する」）
3. 同じ問題を解く別の方針を2つ以上挙げる。次の型を当てはめる
    - 受け付けない：問題を起こす入力の種類そのものを拒否する
    - 許可したものだけ通す：危ないものを探して塞ぐ（拒否リスト）のではなく、安全と分かっているものだけを通す（許可リスト）
    - 任せる：同じことをする既存の仕組み（標準ライブラリ・枠組み・リポジトリの既存の関数・相手のコンポーネントの設定）に任せる
    - 経路をなくす：問題が起きる経路・機能・状態をなくす
4. 作者の方針と別の方針を、次で比べる。比べた結果を `checked` に残す
    - 確実さ：境界の場合が尽きるか。他のコンポーネントの解釈と食い違う余地が残るか
    - 大きさ：変更の行数・新しく足す処理の量。タスクの制約（最小限・行数の上限）に収まるか
    - 失うもの：別の方針で使えなくなる正当な使い方。その使い方が実際にあるかを、コード・文書・根拠で確かめる
5. 再レビューで前回の指摘が渡されていれば、前回までの指摘と、今回の対象の欠陥の原因を照らす。同じ原因（同じ方針の弱さ）の別の現れが2回以上続いているなら、方針の問題として扱う
6. 別の方針が、確実さか大きさではっきり勝り、失うものが許せるときだけ指摘にする。勝るかがはっきりしなければ出さない

## チェックポイント

- 解釈の食い違い：他のコンポーネント（上流のサーバー・ブラウザ・シェル・データベース・パーサー）が解釈する入力を、自前で解析して危ないものを探している。解析の細部が相手と一致しない限り、すり抜ける入力が残る
- 拒否リスト：危ない値・文字・形を列挙して塞いでいる。エンコード・大小文字・区切り・空白・重複・長さの変化で、列挙の外の入力が通る
- 自前の再実装：標準ライブラリ・枠組み・既存の関数が持つ処理（解析・エスケープ・正規化・検証）を、自前で書き直している
- 釣り合わない大きさ：問題の重さやタスクの制約（最小限の変更・行数の上限）に比べて、足した処理が大きい。同じ効果を、ずっと小さな変更で得られる
- 続く現れ：前回までの指摘に同じ原因の欠陥があり、直したあとも同じ原因の別の現れが見つかる

## NG 例

### 例1（Python）：拒否リストでの HTML の無害化

```python
def sanitize(html: str) -> str:
    return re.sub(r"<script.*?>.*?</script>", "", html, flags=re.I | re.S)
```

`<img onerror=...>`・`<svg onload=...>`・`javascript:` の URL・入れ子にした `<scr<script>ipt>` が通る。直すたびに別の形が見つかる。テンプレートの自動エスケープに任せるか、許可したタグと属性だけを残すライブラリの無害化を使う。`must`（セキュリティ）。

### 例2（Go）：文字列の検査でのパストラバーサルの防止

```go
if strings.Contains(name, "..") {
    return errBadPath
}
path := filepath.Join(baseDir, name)
```

絶対パス・シンボリックリンク・OS ごとの区切りで、基準のディレクトリの外に出られる。`filepath.Rel` で基準のディレクトリの中かを確かめるか、基準のディレクトリの外に出られない API（`os.Root` など）で開く。`must`。

### 例3（TypeScript）：上流が解釈する本文の自前の解析

HTTP のメソッドの上書き（`_method`）を防ぐため、中継する本文（フォームの形式）を自前で解析して、上書きの名前があれば拒否している。境界・ヘッダー・改行の解釈が上流と食い違う本文が通る。タスクは「最小限の変更」を求めている。フォームの形式の本文そのものを中継しない方針なら、解析が要らず、数行で済む。失うのはフォームの形式で送る使い方だけで、中継先の API は JSON を受け付ける。`must`。

### 例4（Java）：前回までと同じ原因の欠陥が続く

1回目のレビューで、URL エンコードした値による検査のすり抜けを指摘し、作者はデコードを足した。2回目で、二重のエンコードによるすり抜けを、3回目で大小文字の違いによるすり抜けを指摘した。どれも「入力を自前で正規化してから拒否リストと照らす」方針の弱さが原因で、同じ方針のままでは次の形が見つかる。許可リスト（決まった形の値だけを通す）に変える。`must`。

### 例5（Ruby）：既存の仕組みの再実装

日付の文字列を正規表現と自前の計算で解析し、うるう年と月末の扱いの不具合を直し続けている。標準ライブラリの `Date.strptime` に任せる。`should`（不具合が残っていれば、その不具合は C-1 が `must` で出す）。

## 見落としやすい所

- 別の方針で失うものを確かめずに指摘しない。失う使い方が実際にあるか（呼び出し元・利用者の文書・根拠）を確かめ、`suggestion` に失うものを書く。作者か人が選べるようにする
- 承認済みの要求要件・設計が方針を決めているときは、方針を変える `must` にしない。`should` にし、承認済みの設計と食い違うことを `problem` に書く（設計そのものの誤りは設計のレビューで扱う）
- 好みの違いは出さない。確実さか大きさで、はっきり勝る別の方針があるときだけ出す
- 方針が誤っているときは、その方針の中の個々の欠陥を、この観点で1つずつ挙げない（それは他の観点が見る）。`problem` には、方針が生む欠陥の類（例：解釈の食い違いによるすり抜け）と、見つけた現れを短く書く

## 指摘の書き方の例

- title：`本文を自前で解析する方針をやめ、フォームの形式の本文を中継しない`
- problem：`メソッドの上書きを防ぐため、中継する本文を自前で解析している。上流のパーサーと解釈が食い違う本文（境界の前の空白・単独の改行・重複したヘッダー）が通り、直すたびに別の形が見つかる。差分は 296 行で、タスクの「最小限の変更」と行数の上限（300 行）に近い`
- evidence：`前回までの指摘 3 件（境界の重複・preamble の扱い・単独の改行）は、どれも本文の解析と上流の解釈の食い違いが原因。中継先の API の文書は JSON の本文だけを受け付けると書いている`
- suggestion：`フォームの形式（application/x-www-form-urlencoded・multipart/form-data）の本文は解析せずに拒否する。失うのはフォームの形式で送る使い方で、中継先の API にはその使い方が無い`
