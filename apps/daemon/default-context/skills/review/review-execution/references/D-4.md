# D-4 検証可能性

見るもの：受け入れ条件・テスト観点が第三者に検証できる具体さか（入力・期待結果）、受け入れ条件を観点が網羅しているか、異常系・境界値を含むか、曖昧な条件。
見ないもの：設計そのものの妥当性（D-2）。

## 確かめる手順

1. 受け入れ条件・テスト観点を 1 つずつ取り、「誰が・何を与え・何を見て・どうなれば合格か」を書き出せるかを試す。書き出せないものは具体さが足りない
2. 受け入れ条件と観点の対応表を作る。対応の無い条件（観点で検証されない）、条件に対応しない観点（何を検証しているか不明）
3. 観点ごとに、正常系だけか、異常系・境界値があるかを数える
4. 曖昧な語を拾う：「適切に」「正しく」「十分に」「速く」「問題なく」「必要に応じて」「など」
5. 検証の手段：どの環境・データ・ツールで確かめるか。再現できる手順か。自動化できるか、人の目が要るか

## チェックポイント

- 入力が無い観点：「正しく保存される」（何を保存して何を読むか）
- 期待結果が無い観点：「エラーにならない」「動作する」（何が出れば合格か）
- 測れない条件：「速い」「使いやすい」「安全」。数値・比較対象・判定の手順を求める
- 観点の網羅：受け入れ条件のすべてに少なくとも 1 つの観点があるか。複合的な条件は複数の観点に分かれているか
- 異常系・境界値の欠落：正常な入力の観点だけ。空・上限・不正・失敗・権限なし・同時
- 観点の独立性：1 つの観点が複数のことを確かめている（落ちたときに何が悪いか分からない）
- 前提の明示：観点が依存する状態（既存データ、設定、時刻）が書かれているか
- 再現性：手順を読んだ別の人が同じ結果を得られるか。環境・データ・順序
- 否定の検証：「〜しないこと」の観点（削除されない、通知されない）が、どうやって「しなかった」と確かめるかまで書かれているか
- 非機能の検証：性能・容量・セキュリティの条件に、測り方（負荷・ツール・閾値）があるか
- 自動化の見通し：自動テストにできる観点と、人の確認が要る観点の区別
- 観点の ID と参照：条件と観点が相互に参照でき、後から追えるか
- 設計の変更との整合：設計を変えたのに観点が古い形のまま

## NG 例

### 例1：入力も期待結果も無い

```
- TV-1: タスクが正しく保存されること
```

何を保存し、何を読んで、何と一致すれば合格か。「タイトル・担当者を指定して作成し、一覧 API で同じ値が返る」のように。`must`。

### 例2：測れない条件

```
- 一覧の表示は十分に速いこと
```

「1 万件のとき 95 パーセンタイルで 500ms 以内（検証環境、計測ツール X）」。`must`。

### 例3：受け入れ条件に対応する観点が無い

受け入れ条件 4「権限の無い利用者は削除できない」に対応する観点が無く、正常な削除の観点だけ。`must`。

### 例4：複合的な観点

```
- TV-3: 作成・更新・削除が正しく動き、通知も送られること
```

4 つのことを 1 つで確かめている。落ちたときに切り分けられない。分割。`should`。

### 例5：否定の検証手段が無い

```
- TV-5: 完了したタスクには通知が送られないこと
```

「送られない」をどう確かめるか（通知の送信ログが 0 件、モックの呼び出し回数が 0）が無い。`should`。

### 例6：前提の未記載

```
- TV-7: 期限を過ぎたタスクが一覧の先頭に出る
```

「期限を過ぎた」の基準時刻（現在時刻をどう固定するか）が無く、日によって結果が変わる。`should`。

## 見落としやすい所

- 観点が多いと網羅していると錯覚する。条件側から対応を追う
- 「異常系」が「不正な入力でエラー」の 1 つだけで済まされている。失敗・境界・同時・権限を別に数える
- 実装者が書いた観点は実装の都合に寄る。利用者の視点の条件（画面で何が見えるか）が抜けやすい

## 指摘の書き方の例

- title：`受け入れ条件 4（権限の無い利用者は削除できない）を検証する観点が無い`
- problem：`テスト観点 TV-1〜TV-6 はすべて権限のある利用者の操作で、権限が無い場合の観点が無い。条件 4 が実装されなくても観点はすべて通る`
- evidence：`requirements.md の受け入れ条件と design.md のテスト観点の対応表を作って確かめた`
- suggestion：`TV-7「閲覧権限のみの利用者が削除 API を呼ぶと 403 が返り、タスクは残る」を足す`
