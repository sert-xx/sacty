# 自己レビュー（`self-review`）

自分（またはこのタスク）が作っている成果物を、提出（PR の作成、工程の成果の提出、文書の公開）の前に、他者の目で見直して直す流れ。
指摘は修正に戻せるので、指摘 → 修正 → 再レビューを、収束するまで繰り返す。どこにも投稿しない。

## 入力

- 成果物：コードなら作業開始時点からの変更（未コミットなら `git diff` と `git status`、コミットしていれば `git diff <開始時点>...HEAD` も）、文書なら全文。文書を Git の外に書き出すときは、書き出す文書（またはその下書き）の全文を対象にする
- 根拠：タスク・Issue、承認済みの要求要件・設計・テスト観点、人の過去の指摘（あるもの）
- 検証の結果：[verification-run.md](verification-run.md) に従って、担当の起動前に実行する
- 画面の記録（画面を変えたとき）：[screen-capture.md](screen-capture.md) に従って、撮れる環境のときだけ担当の起動前に撮る
- 範囲：初回は成果物の全体。再レビューと、直しの実行の最初のレビューは下の規則

根拠が無いときも進めてよいが、要件適合の観点（C-1・D-1）には「根拠が無い」と伝え、対象の内部の整合だけを見させる。

## 完了できないとき

成果物そのものが読めない（差分が取れない・文書が無い）ときは、担当を起動せずに成果物を整えてからやり直す。
担当が `failed` を返したら1回だけ起動し直し、それでも失敗なら、その観点は「見られなかった」として記録し、残りの観点で続ける（提出物の説明に、見られなかった観点を書く）。

## 初回

1. 検証を実行する（[verification-run.md](verification-run.md)）
2. 主対象の種類の必須観点を全部、条件付き観点を判定して、横断（X-1、検証の結果があれば X-2）を起動する。C-13・C-16 を起動するなら、その前に画面を撮る（[screen-capture.md](screen-capture.md)）
3. 集約（[aggregation.md](aggregation.md)）する
4. `must` と `should` を修正する。`nit` は作者の判断で直す。修正しない指摘には理由を記録する
    - 主対象が `design-doc` のときは、記述を足す指摘（D-3 などの「書かれていない」の指摘）は `must` だけを直し、`should` は直さない。文書は、読む人が前提（暗黙知）を持っているので、初版は最小限にし、足りない所は読む人が求めたときに足す。情報が多いと、読む人は読み切れずに承認してしまう。記述を削る指摘（D-10）は `should` も直す
    - 記述を削る指摘（D-10）に従うときも、リポジトリの決まり（README・CONTRIBUTING・AGENTS.md・変更履歴の方針・PR テンプレート・CI の設定など）から導いた条件（版・変更履歴・生成物・ドキュメントの更新など）とその確かめ方は、「決まりの書き直し」として消さない。決まりの出典を引ける条件は残す。消すなら、決まりから導かれないと確かめた理由を、直さなかった指摘・総評に記録する。条件の中身が誤っている・確かめられないという指摘（D-4 など）には、条件を消さずに、誤りを直して応える
    - 記述を削る指摘（D-10）に従うときも、リポジトリの文書（README・AGENTS.md から参照されていないものを含む）や既存の振る舞いに根拠のある記述は、「依頼・要求要件に無い」だけを理由に消さない。根拠を示して残すか、残すかを人に確かめる項目にする。消すなら、根拠が無いと確かめた理由を、直さなかった指摘・総評に記録する
5. 修正したら再レビューへ

修正は親（成果物の作者）が行う。担当は対象を変更しない。

## 再レビュー（2回目以降）

- 対象：前回の修正箇所と、その修正が直接必要にした既存の箇所。初回の対象にしかなく、前回の指摘になかった箇所を、新たに指摘しない（収束させるため。本当に放置できない `must` だけは例外として出し、「初回で見落とした」と記録する）
- 起動する観点：**前回の回で `must` を出した観点と、横断の X-1 だけ**。前回の回の結果が `must` 1 件以上の観点を、初回と同じ段階で起動する。それ以外の観点は起動しない
    - 前回の回に `must` が無く、`should`・`nit` だけを直して再レビューに進むときは、X-1 だけを起動する
    - 前回の回の結果だけで決める。2 回前に `must` を出したが前回は出さなかった観点は、起動しない
    - 観点の起動条件（条件付き観点）や、必須観点の「全部起動する」は、初回の規則であって、再レビューでは決め直さない。観点を足したり、1 人の担当にまとめたりしない
    - X-2 も同じ扱いにする（前回の回に `must` を出したときだけ起動する）。ただし、修正後に実行し直した検証が失敗・警告を出したときは、X-2 も起動する（修正が検証を壊したのに、誰も分析しない状態にしない）
    - C-13・C-16 を起動しない回は、画面を撮り直さない
    - 起動しなかった観点は、起動表に「起動しない」、理由に「再レビュー：前回の回で must なし」と記録し、成果の説明の「起動した観点」でも分かるようにする（下の「出力」）。起動しなかった観点が見るはずの問題を、修正が持ち込んでいたときは、X-1 が指摘してよい（X-1 の依頼文の「他の観点」には、この回に起動した観点だけを書く）
    - 検証は修正後のコードで実行し直す（修正で内容が変わるので、前回の結果は使い回さない。verification-run.md の 1.5）。テストは、変更に関係するものだけでよい（全件は、修正を終えたときに 1 回。下の「ループの上限」、verification-run.md の 0）。実行する範囲は決め直す（主対象が文書で `scope` が `docs` なら文書に効く検証だけ。X-2 は、文書に効く検証が失敗・警告を出したときに起動する。実行した検証が無ければ起動しない）
- 担当には、前回の指摘と、それへの修正の内容を渡す。観点の担当には、その観点の前回の指摘を渡す。X-1 には、前回の回で採用した指摘のすべてと、それぞれの修正の内容を渡す（起動しなかった観点の指摘への修正が、新しい問題を持ち込んでいないかも見させる）。担当には「指摘が直ったか」と「修正が新しい問題を持ち込んでいないか」の両方を見させる
- 前回の指摘が直っていなければ、同じ指摘として（別の指摘にせず）残す

## 直しの実行の最初のレビュー

作業の指示が「この実行は、人の差し戻し・AI のレビューの指摘・最終レビューの不合格を受けた直しである。この実行の最初のセルフレビューを、直しの実行の最初のレビューの規則で行う（初回ではなく、再レビュー（2回目以降）として扱う）」と**明示している場合に限り**、その実行の**最初のセルフレビューは、初回ではなく再レビュー（2回目以降）として扱う**。前の実行の中で成果物はすでにセルフレビューを通っていて、今回の実行は指摘に応えるために直したものだからである。成果物の種類（要求要件・設計・実装）は問わない。

明示が無いときは、初回の規則で全部の観点で見る。タスクの最初の実行はもちろん、指示が「差し戻しの直しである」「指摘に関わる所だけを直す」「レビューの範囲を直した所に絞る」としか書いていないときも同じである。これらはレビューの範囲や直し方を決める指示であって、観点を絞る指示ではない。前の実行のセルフレビューが合格していないと、前回の未解決の問題が今回の指摘の外に残りうるので、そのときは明示が無く、範囲が絞られていても、観点は初回と同じに全部起動する。

- 対象：この実行で直した箇所と、その直しが直接必要にした既存の箇所。直しを始める前の状態（コミット・ファイルの写し・文書の前の版など）を控えておき、そこからの差分を担当に渡す。指示がレビューの範囲を決めているときは、それに従う
- 起動する観点：**今回の指摘に関わる観点と、横断の X-1 だけ**。それ以外の観点は起動しない。指摘に関わる観点は、次の順で決める
    1. 指摘が観点の ID を示しているときは、その観点
    2. 示していないときは、指摘が述べる問題を、観点カタログ（[viewpoints.md](viewpoints.md)）の「見るもの」に当てはめ、当てはまる観点を選ぶ。指摘が複数あれば、指摘ごとに選んで合わせる
    3. 最終レビューの不合格は、不合格の理由（満たしていない要件・失敗したテスト・再発した指摘）ごとに、2 と同じ方法で選ぶ
    4. 1 つの観点に決められない、または観点の境界にまたがるときは、当てはまりうる観点をすべて起動する（迷ったら起動する）
- 観点の起動条件（条件付き観点）や、必須観点の「全部起動する」は、初回の規則であって、ここでは決め直さない。観点を足したり、1 人の担当にまとめたりしない。直しが指摘と無関係な箇所に及んで持ち込んだ問題は X-1 が拾う
- X-2：指摘が検証の失敗（テスト・型チェック・リンター・フォーマッターなどが通らない）に関わるとき、または直した後に実行し直した検証が失敗・警告を出したときだけ起動する。それ以外は起動しない。検証は直した後のコードで実行し直し、範囲は決め直す（再レビューと同じ）
- C-13・C-16 は、指摘に関わるときだけ起動し、画面を撮る。起動しない回は画面を撮らない
- 担当には、今回の指摘（原文と ID）と、この実行での直しの内容を渡し、「指摘が直ったか」と「直しが新しい問題を持ち込んでいないか」の両方を見させる。X-1 には、今回の指摘のすべてと、それぞれの直しの内容を渡す。依頼文の「他の観点」には、この回に起動した観点だけを書く
- 起動しなかった観点は、起動表に「起動しない」と理由（直しの実行：今回の指摘に関わらない）を残し、成果の説明の「起動した観点」でも分かるようにする
- 指摘が直っていなければ、同じ指摘として（別の指摘にせず）残す。この実行の中の次の回からは、上の「再レビュー（2回目以降）」の規則どおり（前回の回で `must` を出した観点と X-1 だけ）
- 回数の上限は、この実行の最初のレビューを 1 回目として数える（最大 5 回）

## ループの上限

最大5回（初回を含む）。通常は2〜3回で収束する。
同じ指摘が3回続くなら、修正の方針が合っていない。修正を変えるか、指摘の妥当性を見直し、記録する。
上限に達しても `must` が残るなら、提出物の説明に「残っている問題」として指摘を書く。黙って提出しない。

`scope` が `all` で、実行するテストがあるとき（テストの仕組みがあるリポジトリ）は、修正を終えたら（`must` が無くなった、または上限に達した）、提出の前にテストの全件を 1 回実行する。最後の回の検証が全件なら、実行し直さない。全件の結果が無いまま提出しない（[verification-run.md](verification-run.md) の 0）。`scope` が `docs` のとき、主対象が要求要件・設計などでテストを実行しないとき、テストの仕組みが無いときは、この規則は当てはまらない（テストを足して実行しない）。

## 出力（提出物に残すもの）

成果の説明（工程の出力・PR の本文・文書の冒頭ではなく、説明の末尾）に、短く残す。依頼したプロンプトが求める出力形式（決まった JSON のブロックなど）は変えず、その前の説明に入れる。

```
## 自己レビュー
- 回数：3 回。主対象：code。起動した観点：初回は C-1〜C-6・C-9・C-15・X-1（C-7・C-8・C-10〜C-14・C-16 は条件に当てはまらず起動せず）、2 回目は C-1・C-4・X-1、3 回目は X-1（再レビューで起動しなかった観点は、前回の回で must なし）。直しの実行の最初のレビューなら、「1 回目は指摘に関わる C-1・X-1（ほかは今回の指摘に関わらず起動せず）」のように書く
- 検証：format・lint・typecheck・test を実行。最終回はすべて passed、test は修正を終えた後に全件で passed（実行するテストがあるとき）（失敗が残るなら、コマンドと理由）。`scope` が `docs`（主対象が文書で、差分にコードの変更が無い）なら、実行した文書に効く検証（無ければ「実行していない（文書が主対象）」）
- 直した指摘：must 2・should 4・nit 1
- 直さなかった指摘：should 1（理由：…）
- 見られなかった観点：なし
- 残っている問題：なし
```

成果の説明の文章は、スキル `writing` に従って書く。

起動表と不採用の指摘の全文は、成果の説明には載せない（実行のログに残る）。成果物のファイルにも書かない。
