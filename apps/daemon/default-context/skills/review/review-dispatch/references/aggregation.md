# 集約

起動した担当の結果を検証し、1つのレビューにまとめる。親はここで初めて指摘の内容を読む（それまでは待つだけ）。

## 結果の検証

1. 起動した全観点の結果を回収する。足りない観点があれば、揃うまで集約しない
2. 各結果が [finding-format.md](finding-format.md) の形式を満たし、依頼した観点と一致することを確かめる。形式が壊れていれば、その担当に出力形式だけを直させる（レビューをやり直させない）
3. `failed` の観点は、理由（`limitations`）を読んでから扱う
    - 理由が、依頼文の範囲の外を見ていないこと（変えていない既存の箇所・文書の全体など）だけ：起動し直さない。範囲の中は見終えているので、`findings` に `must`・`should` があれば `changes_required`、無ければ `passed` として扱い、見られなかった観点に数えない。起動表の「結果」に「範囲の外を理由にした failed を読み替えた」と残す。範囲を広げた担当を足さない
    - 理由が、依頼文の範囲を見きれなかったこと（範囲が1つの担当には大きい）：1回だけ起動し直す。そのとき、同じ観点のまま、範囲をファイルや節で分けて複数の担当に渡す（範囲は広げない）
    - それ以外（入力が足りない・読めない・実行できない）：1回だけ起動し直す
    - 担当を起動できなかった・時間切れで結果が届かなかった観点も、`failed` と同じに、1回だけ起動し直す
    - 起動し直しても失敗（起動できない・`failed`・時間切れ）なら、下の「親が代わりに見る」を行う。それでも見られなかったときだけ、流れの資料の「完了できないとき」に従う

4. `checked` を見て、観点の「見るもの」が依頼文の範囲の全体にわたって確かめられているかを確かめる。明らかに途中で止まっている（差分の前半しか見ていない等）なら、残りを見させる。範囲の外を見ていないことは、途中で止まっていることではない（見させない）

## 親が代わりに見る

起動し直しても失敗した観点（起動できない・`failed`・時間切れ）だけ、親が自分でその観点を見る。これは、観点のレビューを親が自分では行わない決まりの、唯一の例外（逐次モードを除く）である。

- 行ってよいのは、すべての担当の起動と起動し直しの結果が揃った後だけ。それより前に、親は調査・レビューをしない
- 対象は、起動し直しても失敗した観点だけ。範囲の外を見ていないことだけを理由にした `failed`（上の 3）は、起動し直していないので、代わりにも見ず、見られなかった観点にも数えない。入力の取得を再試行しても差分または必要な主対象文書を読めない回には当てはめない
- 見方は、担当に渡すはずだった依頼文・範囲・観点の資料（review-execution の `references/<観点ID>.md`）のとおり。「ここから観点 <ID> の担当として見る」と区切り、自分で書いた依頼文を入力にして review-execution に従い、同じ形式の結果を作る。範囲は広げない。担当に依頼文を書くときと同じに、依頼文に「あなたはレビューの観点担当です」の1文と「禁止」の行を含める（SKILL.md の逐次モードの手順 1・2）
- 範囲を分けて起動し直した担当の一部だけが失敗したときは、失敗した範囲だけを見る（成功した範囲の結果はそのまま使う）
- 見終えたら、その観点を「見られた観点」に数える。指摘は担当の指摘と同じに、「重みの確認」・採否・併合にかける
- 代わりに見ても見られなかったとき（対象を読めない・見きれないなど）は、その観点を「見られなかった観点」にして、流れの資料の「完了できないとき」に従う
- 代わりに見たことは、投稿する本文・提出物の説明に書かない。集約の記録の `launched` の該当の行に、`substituted_by_parent`（見られたら `true`、見られなかったら `false`）と `failure_reason`（担当が失敗した理由）を残す（本文に貼らない）

## 重みの確認

担当が付けた重要度を、指摘の `condition`（起きる条件）と `impact`（実害）に照らして、review-execution の「重要度」の表で確かめる。初回でも、再レビューでも、前回の指摘への直しで足した・変えた箇所への指摘でも、同じ表で確かめる。

| | 普通 | 条件つき（条件 1 つ） | 稀（独立した条件が 2 つ以上） |
| --- | --- | --- | --- |
| 影響：大 | `must` | `must` | `must` |
| 影響：中 | `must` | `must` | `should` |
| 影響：小 | `should` | `should` | 出さない |

- 受け入れ条件・要求要件の不適合は、起きやすさを問わず `must`。不適合とは、根拠（受け入れ条件・要求要件・設計）が述べる場面そのもので、求められた振る舞いにならないこと。根拠が述べる場面に、根拠に書かれていない条件がさらに重なったときだけ、求められた振る舞いにならないものは、不適合ではない。重なる条件を数えて、表で決める
- 不適合を理由にした `must` は、`impact` に書かれた条件と場面を、根拠で確かめる。根拠に書かれていない条件が重なったときだけ起きるものは、表で決め直す
- `condition`・`impact`・`likelihood`・`impact_level` が無い指摘は、その担当に出力形式だけを直させる（レビューをやり直させない）
- 書かれた条件と実害が、`likelihood`・`impact_level`・`severity` と合わないときは、条件と実害から表で決め直す。条件の数え方と影響の分け方は、review-execution の「重要度」のとおり。親は、条件や実害を足さない・削らない（足りなければ、担当に確かめさせる）。書かれた条件に、数え方の規則（ふつうの使い方で満たされる前提は数えない。1 つの原因が続けて引き起こすことは 1 つ。信頼できない入力またはセキュリティに関わる場合だけ外部の者が意図して揃えられる条件は数えない）を当てはめて、数え直すことはしてよい。数が変わったときは、`reweighted` に理由を残す
- 決め直した指摘は、記録の `reweighted` に、もとの重要度・決め直した重要度・理由を残す
- 「影響：小 × 稀」に当たる指摘は不採用にする（理由は「稀で、実害が小さい」。再レビューの新しい指摘と、`pr-review` の再レビューで重みを見直した前回の指摘は除く。再レビューの新しい指摘は、前回以降の変更が生んだ後退なら `must`、それ以外は `should` にする。下の「重みを見直した前回の指摘」）
- 担当が `not_raised` に残したもの（「影響：小 × 稀」として出さなかったもの）も、書かれた条件と実害を同じ表で確かめる。数え直して「影響：小 × 稀」でなくなるものは、表の重要度の指摘として採用し、`reweighted` に残す。「影響：小 × 稀」のままのものは、再レビューの新しい指摘なら、前回以降の変更が生んだ後退は `must`、それ以外は `should` にし、初回なら `dismissed` に、条件・実害と理由（「稀で、実害が小さい」）を残す（PR には投稿しない）。`pr-review` の再レビューで、前回の `must` を確かめ直したものは除く（下の「重みを見直した前回の指摘」）
- 同じ原因の現れをまとめた指摘は、まとめた現れのうち、最も重いもので決める

## 指摘の統合

- 同じ箇所・同じ問題が複数の観点から出たら1つにまとめる。観点を併記し、`confidence` は高い方にする
- 同じ問題の別の現れ（同じ原因で複数箇所・複数の入力）は、観点をまたいでも1件にまとめる。代表の1箇所に付け、他の現れを代表の指摘の本文（行へのコメントなら、そのコメント）に列挙し、直し方は個々の現れではなく原因に向ける
- C-17（方針の妥当性）が方針を変える `must` を出し、他の観点の指摘がその方針を変えれば無くなる現れなら、その現れは C-17 の指摘にまとめて列挙し、別の指摘にしない。方針を変えないと作者が決めたときに直す現れとして、C-17 の指摘に添える。まとめた指摘の重要度は、C-17 とまとめた現れのうち最も高いものにする（方針を変えるか現れを直すかのどちらかをしないと、`must` の欠陥が残るため）
- C-17 の方針の指摘が `should`（承認済みの設計が方針を決めているときなど）なら、他の観点の `must` の現れはまとめない。現れはそれぞれの重要度のまま別の指摘にし、C-17 の指摘を参照として添える（方針を変えるかは任意のまま、欠陥の解消は必須に残す）
- `out_of_scope_notes`（観点外の気づき）は、他の観点の指摘と照らす。どの観点にも拾われていない気づきで、根拠が示せるものは、親が根拠を確かめた上で採用してよい（採用した指摘には「横断で拾った」と記す）。確かめられないものは不採用にする
- 相反する指摘（ある観点は「分けろ」、別の観点は「まとめろ」）は、根拠と影響を比べて1つに決め、決めた理由を記録する

## 再レビューの重さ

再レビューでは、前回以降の変更が生んだ後退、直っていない前回の `must`（重みの見直しの規則を適用する）、ふつうの使い方か1つの条件で起きる不適合または影響が大のもの、ふつうの使い方で起き影響が中のものだけを `must` にする。1つの条件で起き影響が中で不適合でないものを含む、ほかの新しい指摘は表の重さによらず `should` にする。

## 回をまたいで同じ原因が続くとき

再レビュー（`self-review` の2回目以降と直しの実行の最初のレビュー、`pr-review` の再レビュー）では、採用する `must` ごとに、前回までの `must`（前回の指摘と、前回のレビューが「前回の指摘」として挙げたもの。依頼した側が前々回以前のレビューを渡していれば、その指摘も）と原因を照らす。
前回までに直したはずの原因の別の現れ（同じ原因で、入力の形や箇所だけが違う）なら、現れを塞ぐ直しでは収まっていない。
依頼した側が渡した前回・前々回以前のレビューのうち、`delivered` が `false` の回（古い先頭宛てに投稿され、PR を作った側に届かなかった回）は、同じ原因の `must` の回数にも、前回までの現れの一覧にも数えない。
その回の指摘は、依頼文の指示どおり、今回の先頭で当てはまるかを確かめ、当てはまるものを今回の指摘として扱う。

同じ原因が続き、レビューが示した範囲を絞る案で残る現れが再レビューの `must` に当たらないものだけなら、その現れは `should` にし、人の判断を求めず、印も `needsDecision` も付けない。その回の総評に、範囲を絞って提案にしたことと残る現れを書く。

次の4項目の方針の観点の見直しと現れの統合は、同じ原因の別の現れが見つかったときに限る。
同じ指摘が未修正で残るだけの場合は方針の観点をそのために起動せず、本文への明示・範囲を絞る案・人の判断の求めは以下の条件に従う。

- 主対象が `user-doc` 以外で、C-17 が今回の回で方針を変える指摘を出していれば、その現れは上の範囲を絞る案の例外に当たらなければ「指摘の統合」のとおりに扱う（`must` ならまとめ、`should` ならまとめずに `must` の現れを残す）
- 主対象が `user-doc` 以外で、C-17 を起動していない、または方針を変える指摘を出していないときは、C-17 の担当を1回だけ起動する（起動し直す）。依頼文の「前回の指摘」に、前回までの同じ原因の `must` と、今回の現れを書く。親は自分で方針を判断しない
- 主対象が `user-doc` 以外で、C-17 が方針を変える指摘を出せば、上の「指摘の統合」のとおりに扱う。出さなければ（今の方針のままで原因を直せると判断した）、上の例外に当たらない現れをふつうの `must` として採用する
- 主対象が `user-doc` 以外なら、起動表の C-17 の行の理由に「回をまたいで同じ原因が続く」と残す
- 範囲を絞る案の例外に当たらず、方針の観点が方針を変える指摘を出したかどうかに関わらず、今回の `must` が前回までの `must` と同じ原因で続いているなら（同じ指摘が残る場合も含む）、同じ原因が続いていることを本文に明示する（上の分岐の結果は変えない）。次を書く
    - 同じ原因が続いていること、原因（1文）、同じ原因の `must` が何回目か（前回までの回が分からないときは「少なくとも N 回目」）、前回までの現れの一覧（回と現れを短く）
    - `pr-review` では、総評か、その指摘の本文の、人が読んで分かる場所に書く。`self-review` では、記録と、依頼した側へ返す結果（報告の総評）に書く
- 2回目以降、範囲を絞る案を1つ以上、総評か指摘の本文に添える。受け入れる・範囲の外にする・後続に回す場合と残る影響を書き、承認済みの要求要件・受け入れ条件（無ければ依頼の受け入れ条件）と照らして、満たせなくなる条件を明記する
- 3回目以降は人の判断を求める。`pr-review` はその `must` に印を付け、`self-review` は報告の `needsDecision` に原因・回数・案・満たせなくなる条件を書く。人の判断後に同じ原因の `must` が続いた回も同様に扱う。
- 2回目の時点から（方針を変える指摘が出ないときも、主対象が `user-doc` 以外なら）、その指摘の直し方の案を、今回の現れを塞ぐ手当てだけにしない。次を示す
    - 原因を1か所で断つ直し（同じ原因のどの現れにも効くもの）
    - 残りうる現れの、軸による数え上げ（例：切れ目の種類 × 処理する時点 × 値どうしの関係）。レビューが確かめた組み合わせと、確かめていない組み合わせを分けて書く
    - 性質で確かめるテスト（決まった例ではなく、乱数や網羅で作った入力に対して「どの入力でも〜にならない」を確かめるもの）を、内側の関数ではなく、外から見える入口（利用者や呼び出し側が実際に使う経路）に当てること。テストを書く場面（主対象が `code` で、文書だけの変更でも、テストなしのタスクでもない）にだけ求める。`design-doc`・テストを書かない場面では求めず、上の2つまでにする
- 上の範囲を絞る案の例外を除き、判定・重さ・再レビューの範囲は変えない
- 主対象が `design-doc` のときは、C-17 の代わりに D-1（代替案と採らなかった理由を見る）で同じように扱う。`user-doc` は方針の観点を起動せず、上の例外に当たらない現れを通常の `must` として採用し、直し方の3項目も求めない。本文への明示・範囲を絞る案・3回目以降の人の判断の求めは適用する

## リポジトリの指示との重なりと相反

R（リポジトリのレビュー用のスキル）と X-3（リポジトリの指示への準拠）を起動したときは、次のように扱う（[repo-guidance.md](repo-guidance.md)）。

- R・X-3 の指摘が、他の観点の指摘と同じ箇所・同じ問題なら、1つにまとめて観点を併記する（R はスキルの名前も添える）。重要度は高い方にする
- R・X-3 の指摘も、他の観点と同じ基準で検証する（形式、`checked`、根拠）。担当がスキルの独自の形式・採点・総合の判定を返してきたら、出力形式だけを直させる
- 担当の `limitations` に、スキルが求めていて行わなかったこと（投稿・修正・分担など）があれば、記録に残す。親も、それを代わりに行わない
- 他の観点の `should`・`nit` が、基準にしたリポジトリの指示の明文の決まりと相反するとき（決まりのとおりに書かれたものを、直すよう求めている）は、リポジトリの決まりを優先して不採用にする。理由は「リポジトリの決まりに従っている」とし、決まりの出典（ファイルと節）を添える
- `must`（不具合・セキュリティ・データ破損・要件の不適合・互換性の破壊）は、リポジトリの決まりと相反していても不採用にしない。採用し、決まりと相反することを指摘に添える（決まりの側を見直す材料になる）
- 基準にしなかった指示（`pr-review` で PR が変えた・足した指示）は、指摘を不採用にする根拠にしない

## 不採用

次は不採用にし、理由を `dismissed` に残す（PR には投稿しない。自己レビューでは記録だけ）。

- 観点の外（担当が「見ないもの」を指摘した）
- 範囲の外（PR の変更が持ち込んでいない既存の問題で、`must` に当たらないもの。再レビューで前回以降の差分の外の通常の `should`・`nit`（再レビューの規則で提案にした新しい指摘を除く）。絞った再レビュー（規則 11）で担当が差分の外に見つけた `should`・`nit` も同じ。`must` は、差分の外でも不採用にしない）
- PR の目的の範囲の外（`pr-review`。下の「PR の目的の範囲の外」。理由は「PR の目的の範囲の外」と書き、上の「範囲の外（既存の問題）」と区別する）
- 根拠が無い・`confidence: low` で親が確かめられない
- 好みだけ、意図された振る舞いの変更、同じ問題の言い換え
- 稀で、実害が小さい（初回だけ。上の「重みの確認」の「影響：小 × 稀」）
- 作者が対象外・後続対応を明示した論点（理由は、下の「対応済み・却下済みとの重なり」の「却下済みの指摘と重なる」にまとめる。返答の出どころで扱いが分かれる）
- 基準にしたリポジトリの指示の明文の決まりと相反する `should`・`nit`（理由は「リポジトリの決まりに従っている」。`must` は不採用にしない。上の「リポジトリの指示との重なりと相反」）
- PR にすでにある他のレビュアーの指摘と同じ箇所・同じ問題（`pr-review`。言い換えを含む。理由は「既存のレビューで指摘済み」。`must` でも繰り返さない。規則は流れの資料の「既存の指摘との重なり」）
- 対応済みの指摘と重なる（`pr-review`。前に出た指摘が求めたことを、先頭のコミットで満たしていると確かめたのに、同じ箇所に同じ趣旨の求めを重ねるもの。理由は「対応済みの指摘と重なる」。下の「対応済み・却下済みとの重なり」）
- 却下済みの指摘と重なる（`pr-review`。人が「やらない」「対象外」とした指摘、人が後続に回すと決めた指摘、人が画面で無効にした指摘、再開の補足で人が範囲の外・受け入れる・後続に回すとした事柄、AI が「対応しない」とした提案と、同じ箇所・同じ問題のもの。言い換えを含む。理由は「却下済みの指摘と重なる」。人の却下は `must` でも落とす。下の「対応済み・却下済みとの重なり」）

`must` は、過去の指摘の履歴や「前回は出なかった」という理由だけで抑えない（他のレビュアーがすでに同じ指摘をしているとき、人の却下と重なるときは除く。作者にはすでに届いている。人の却下は下の「対応済み・却下済みとの重なり」）。

## PR の目的の範囲の外

`pr-review` の集約では、重みを上の「重みの確認」の表で決めた後に、各観点の指摘が PR の目的の範囲の外の求めでないかを確かめる。自己レビューには当てない（[self-review.md](self-review.md)）。

- PR の目的は、PR の説明、示された依頼・受け入れ条件・要求要件・設計、差分が述べる目的から読み取る
- 目的の範囲の外の求め（その変更に要らない機能の追加、関係の薄い箇所の作り直し、目的の外の文書やテストの拡充など）は、指摘箇所が差分の中にあっても不採用にする。理由は「PR の目的の範囲の外」。PR には投稿しない
- `must`（不具合・セキュリティ・データ破損・要件の不適合・互換性の破壊）は、目的の範囲を理由に不採用にしない。既存の問題の `must`（上の「重みの確認」で `must` に当たるもの）も同じ。落とすために重みを下げない。依頼した側や PR の説明が変更の範囲を宣言しているとき（最小限の修正に限る、分けた変更の一部である、など）に、その宣言に反する変更への `must` も落とさない
- 担当が `must` と出し、表で `should` に決め直した指摘は、担当が `must` と出したことを理由に、「PR の目的の範囲の外」では不採用にしない。決め直した後の `should` として、ほかの不採用の理由だけを当てる（再レビューで残す前回の指摘は、下の節で扱う）
- 目的を読み取れないとき（PR の説明が無い・目的が書かれていないなど）と、範囲の中か外か迷うときは、この理由（PR の目的の範囲の外）では不採用にしない。ほかの不採用の理由は、そのまま当てる
- その PR が変えた・足した箇所そのものの正しさ・分かりやすさ・テストへの指摘は、範囲の中である。「目的の外」を広く取って、変更そのものへの指摘を落とさない
- 既存のレビューで指摘済みに当たるものは、そちらの理由で不採用にし、この規則の件数には数えない
- 落とした件数は、集約の記録の `dropped` に残す（本文には書かない）。再レビューで前回の指摘を取り下げるときの書き方は、[pr-review.md](pr-review.md) の「指摘と判定の書き方」が決める（ここでは言い直さない）。初回も再レビューも同じ規則を当てる

## 対応済み・却下済みとの重なり

`pr-review` の集約では、各観点の指摘を、渡された材料（前回・前々回以前の自分のレビュー、作者の返答、既存のレビュー・コメント、依頼した側が渡した人・AI の決定）と照らし、対応済みの指摘と重なるもの・却下済みの指摘と重なるものを採用せず、PR に投稿しない。自己レビューには当てない（[self-review.md](self-review.md)）。材料の読み方（出どころ・弾かないもの）は [pr-review.md](pr-review.md) の「対応済み・却下済みとの重なり」が決める（ここでは言い直さない）。

- 理由が重なるときは、次の順に当て、最初に当たった理由だけで不採用にする（1件を1つの理由・1つの件数の行でだけ数える）。
  1. 却下済みの指摘と重なる（人の却下）。`must` でも落とす
  2. 却下済みの指摘と重なる（AI の「対応しない」）。`should`・`nit` の重みなら落とす。`must` は落とさず、3〜5 に照らす。どれにも当たらなければ、新しい `must` として採用する
  3. 対応済みの指摘と重なる。先頭のコミットで直っていると確かめたものだけ。`must` でも落とす
  4. 既存のレビューで指摘済み（未対応・未却下のもの）
  5. PR の目的の範囲の外。`must` は落とさない
- 理由は、`dismissed` の `reason` に、ほかの不採用の理由と区別して書く（「対応済みの指摘と重なる」「却下済みの指摘と重なる」）
- 直しが効いていない・確かめられない指摘、直しが新しく持ち込んだ別の問題、却下の後の変更で問題が変わった・影響が大きくなった指摘は、この規則では落とさない
- 判定は、採用した指摘（と未対応の前回の指摘・既存の指摘）で決める。落とした指摘は、判定の根拠にしない

## 重みを見直した前回の指摘

`pr-review` の再レビューで、前回の `must` を確かめ直して `should` として扱うもの。どれが当たるか、何回残すか、本文のどこに書くか、判定は、[pr-review.md](pr-review.md) の「採用の規則」と「指摘と判定の書き方」が決める（ここでは言い直さない）。集約では、次のように扱う。

- 残す回には、上の「不採用」の「範囲の外」（前回以降の差分の外）・「PR の目的の範囲の外」・「稀で、実害が小さい」を理由に不採用にしない。担当が `findings` に入れたものも、`not_raised` に残したものも同じ。不採用のほかの理由（作者が対象外・後続対応を明示した論点など）は、そのまま当てる
- 採用（`adopted`）に入れない。`reweighted` に、もとの重要度・決め直した重要度・理由を残し、`previous` を `true` にする
- 本文を書き起こすときは、`reweighted` の `previous` が `true` のものだけを、前回の指摘の一覧と総評に書く。新しい指摘にしない

## 判定

- `must` が1件以上：修正が必要（`changes_required`）
- `should`・`nit` のみ：自己レビューでは修正に戻さない（合格として提出へ進む。主対象が `design-doc` のときに直す `should` は [self-review.md](self-review.md)）。PR レビューでは「提案あり（マージは可）」
- `pr-review` の再レビューで、重みを見直した前回の指摘が残るときの判定は、[pr-review.md](pr-review.md) の「指摘と判定の書き方」で決める
- 不採用にした指摘（既存のレビューで指摘済みのものを含む）は、判定に数えない。PR の目的の範囲の外として不採用にしたものも、判定の根拠にしない。対応済み・却下済みの指摘と重なるとして落としたものも同じ。人が却下した既存の指摘は、未対応の既存の指摘に数えない
- 指摘なし：合格（`passed`）。ただし、見られなかった観点があれば、判定に「見られなかった観点」を併記する
- PR レビューでは差分を読めない、または要求要件・設計の PR で主対象の文書を読めないときは判定を書かない。見られなかった観点や文書があっても、読めた場合は指摘の重さで判定する（[linked-docs.md](linked-docs.md)）
- 検証のコマンドが失敗しているのに、その原因が指摘になっていない（X-2 が既存の失敗・環境の問題と判断した）ときは、判断の根拠を確かめる。今回の変更が原因でないと確かめられなければ、自己レビューでは合格と書かない。PR レビューでは原因を確定できないことと読む人が確かめることを本文の最初に書き、確認できた指摘の重さで判定する

## 順序

`must` → `should` → `nit`。同じ重要度では、影響（データ破損・セキュリティ・不具合 → 互換性 → 保守性）の大きい順、次にファイルの順。
