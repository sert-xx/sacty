# 文書の組み立て

前提を知らない人が、後から読む文書の組み立て方。
ユーザーガイド、手順書、README、運用の文書、引き継ぎの文書などに使う。
例の「悪い例」は、決まりを破った形をわざと書いている。

## 文章の種類を決める

読む人が、その件の前提を知っているかで、書き方を変える。

| 種類 | 例 | 読む人 | 書き方 |
| --- | --- | --- | --- |
| 承認・判断・返信のための文章 | PR の本文、レビュー、コメント、要求要件・設計、調査の結果、作業の報告 | いま、その件に関わっている人。前提を知っている | 情報を絞る（[文の組み立て](sentences.md)） |
| 後から読まれる文書 | ユーザーガイド、手順書、README、運用の文書、引き継ぎの文書 | その場にいなかった人。前提を知らない | この資料に従う |

- 種類は、依頼に書かれた読む人で決める。
  書かれていなければ、文書の置き場所と、同じ場所にある文書で決める
- 後から読まれる文書でも、読む人の目的に要らないこと（内部の仕組み、経緯、検討の過程）は書かない。
  違うのは、読む人が知らないこと（用語、前提、全体像）を、要る情報として書くところ

## 読む人と目的を決める

書く前に、次の2つを決める。

- 読む人：初めて使う人、ふだん使う人、運用する人、開発する人など
- 読んだ後にできるようになること：導入する、操作する、直す、調べる、判断するなど

1つの文書には、1つの目的だけを持たせる。
目的が2つあれば（使い方の説明と、仕組みの説明など）、文書か節を分ける。

読む人が知らないはずの語と前提を挙げておく。
語は、最初に出る所で一言で説明するか、説明のある文書へリンクする。

## 最初に書くこと

文書の最初の数行で、次のことが分かるようにする。

- 何の文書か（読むと何ができるようになるか）
- 誰のための文書か
- 先に要るもの（環境、権限、先に読む文書）

悪い例（何の文書かが分からないまま、設定の一覧が始まる）

```text
# 同期ツール

## 設定

| 項目 | 意味 |
| --- | --- |
| interval | 同期の間隔（秒） |
```

直した例

```text
# 同期ツールを使う

在庫のデータを、倉庫のシステムから注文のシステムへ、決まった間隔で写すツールです。
このページでは、初めて使う人に向けて、インストールから最初の同期までを説明します。
使うには、両方のシステムの管理者の権限が要ります。
```

## 並べる順

- 全体像、ふつうの使い方（手順）、細かい条件と例外、引くための一覧（設定の項目、コマンド）の順に並べる
- 節は、読む人が進む順（用意する、始める、使う、困ったとき）に並べる。
  書き足した順や、実装の順に並べない
- ふつうの場合を先に書き、例外、細かい条件、古い版の話は後に書く
- 手順と、引くための一覧を混ぜない。
  手順の途中に、すべての設定の表を置かない

## 見出しと、節の最初

- 見出しは、読む人が探す言葉で書く。
  することなら「〜する」、引くものなら、その名前にする
- 見出しだけを拾い読みして、文書の流れが分かるようにする
- 見出しの階層を深くしない（文書の題の下に、3階層まで）。
  階層を飛ばさない
- 節の最初に、その節の要点（何ができるか・いつ使うか）を1〜2文で書く。
  見出しの直後に、表や箇条書きだけを置かない
- 「この節では〜を説明します」のような予告にしない。
  予告は、読んでも何も分からない

悪い例（節が、細かい条件の箇条書きから始まる）

```text
## 同期

- 同期の間に注文が入ると、その注文は次の同期に回る。
- 倉庫のシステムが止まっているときは、5分ごとにやり直す。
```

直した例

```text
## 同期する

同期は、決めた間隔で自動で始まります。
すぐに同期したいときは、次のコマンドを実行します。
```

## 手順

- 読む人がすることは、番号付きの手順にする。
  1つの手順には、1つの操作だけを書く
- 手順の前に、前提を書く（要るもの、権限、どこで実行するか）
- 手順ごとに、結果を書く（何が表示されるか、何ができるようになるか）。
  失敗したときに確かめることも、分かっていれば書く
- コマンドと設定は、写してそのまま使える形で書く。
  読む人が置き換える値には、何を入れるかを書く
- 環境によって手順が違うときは、手順の中に混ぜずに、分かれる所で分けて書く

悪い例（操作と結果と注意が、1つの段落に混ざっている）

```text
設定ファイルを作って接続先を書き、同期を実行すると件数が表示されますが、接続先を間違えるとエラーになるので注意してください。
```

直した例

```text
1. 設定ファイル `sync.yaml` を作り、`source` に倉庫のシステムの URL を書きます。
2. 次のコマンドを実行します。

   sync run

   写した件数が表示されれば、同期できています。
   「接続できません」と表示されたときは、`source` の URL を確かめてください。
```

## 説明の書き方

- 同じものは、同じ語で呼ぶ。
  画面やコマンドに出る名前は、そのとおりに書く
- 読む人が判断に使う理由は、1文で添える（「この設定を変えると、次の同期から効きます」）
- 例は、最小で動くものを先に書く。
  値は、実際に近いものにする
- 条件や項目が3つ以上並ぶ文は、箇条書きか表にする（[改行・段落・箇条書き・表](layout.md)）

## 今の状態だけを書く

- 文書には、今どう動くか・今どうするかを書く。
  「これまでどおり」「以前は」「〜に変わりました」のような経緯は、変更履歴やリリースノートに書く
- 古い版から使っている人への案内（移す手順など）は、それと分かる節にまとめる。
  今の説明の途中に混ぜない
- しないことから書き始めない。
  することを先に書き、しないことは、読む人がすると思いそうなときだけ書く

悪い例

```text
同期は、これまでどおり5分ごとに動きます。
以前は手動での実行が必要でしたが、自動になりました。
```

直した例

```text
同期は、5分ごとに自動で動きます。
```

## ほかの節・文書の指し方

- ほかの節や文書は、位置（「下の」「上記の」）で指さずに、名前とリンクで指す。
  節を入れ替えても、指す先が変わらない
- リンクの文字は、行き先が分かる語にする（「こちら」にしない）
- 同じ説明を2か所に書かない。
  片方に書き、もう片方からリンクする

## 長い文書

- 1つの文書や節が長くなったら、読む人の目的ごとに分ける
- 分けられない長い文書には、最初に案内を置く（したいことと、読む節の対応）
- 文書を足したら、入口（目次、README）から辿れるようにする

## 既存の文書に書き足すとき

- 箇条書きの最後に、項目を足すだけにしない。
  その節の流れ（要点、手順、例外）のどこに入るかを決めて書く
- 書き足して、1つの箇条書きに種類の違う話（ふつうの場合、例外、古い版の話）が混ざったら、何の話かを示す1文を付けて分ける
- 書き足した後に、節の最初の要点と、文書の最初の案内が、中身と合っているかを確かめる
